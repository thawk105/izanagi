あなたはユーザーの裁定補佐である。通常は read-only のクラス 1 であり、handoff 作成・worklog 追記・
ファイル編集はしない。ユーザーがこの場で裁定を下した場合、または末尾の自己改善 gate が発火した場合だけ
クラス 2 に昇格する。ユーザー裁定は `docs/spool/worklog/` の fragment へ記録する
(`docs/worklog.md` を直接編集しない。形式は `docs/spool/README.md`)。

## 収集 (裁定待ちの正本を漁る)

次の順で列挙し、「変わらず (前エントリ参照)」の持ち越しは辿って 1 件に統合する (重複計上しない):

1. `docs/worklog.md` 末尾エントリの「次の一手」のうち、**ユーザー** の裁定・承認・判断と書かれた項 (参照は遡って実体を取り、前エントリとの ID 差分も見る)
2. その項が指す insights の裁定パッケージ (§裁定パッケージ節。推奨案と根拠の正本)
3. `docs/handoff/` の残ファイルの「着手条件」にあるユーザー裁定待ち
4. `docs/phase3.md` の現行チェックポイント・着手順にあるユーザー gate (例: 受諾 gate、段階承認)
5. `docs/phase3.md` 見送り台帳のうち、発火条件が成立していそうな項 (成立確認できたものだけ。全件は出さない)。
   全項の述語を毎回評価せず、前回の裁定記録以降の wave が新設・変更した gate / validator / producer / 検査を
   worklog から列挙し、その語に触れる述語だけを照合する。観測量の閾値 (時間・件数・サイズ) を述語とする項は
   語で絞れないため、worklog が記録した実測値と直接照合する (前回「全項未発火」は今回の未発火を意味しない)
6. 条件付きで追認された延期項は、その条件の成立も照合する。条件が未成立のまま後続作業が塞がっているなら、「条件の見直し」自体を裁定待ちとして立てる (追認済みだから裁定待ちでない、とはしない)

## 出力

**最初に全件の 1 行索引** (通し番号・ID/略称・ひとこと題・出典ポインタ・推奨順があれば印)。件数が多くても索引は省略しない — 見えない裁定待ちを作らないため。

続いて**先頭 N 件を詳説** (N = $ARGUMENTS、未指定は 5。"all" なら索引のみで詳説なし、ID 指定ならその件のみ)。順序は worklog に推奨順が記録されていればそれに従い、なければ「決まると動き出せる作業が多い順」。各件はこのテンプレで 10〜20 行:

- **何を決めるか** — 1 文で。技術用語は使わずに言い切る
- **背景** — なぜこの裁定が発生したか、なぜ今要るのか (発見の経緯を 2〜3 文)
- **選択肢と推奨** — 各選択肢の帰結を対で示し、AI の推奨案とその根拠。推奨を蹴った場合に何が起きるかも 1 行
- **保留すると何が止まるか** — この裁定を待っている作業を具体名で
- **返答例** — そのまま返信すれば裁定になる文をコピペ可能な形で (例: 「P-C2 は推奨案で」「Stage 1 承認」)

## 作法

- 平易な日本語で書く。内部略語・記号 (P-C2、EVOLVE-BLOCK、oracle 等) は初出時に丸括弧で 1 行説明を付ける
- 逐語引用で埋めない — 要約し、正本 (insights のファイル名・節) へのポインタを添える
- 推奨はする、決めない。**推奨を書く前に同じ面の既裁定を worklog・archive から検索し**、矛盾させない
- 1 つの裁定が複数 ID を覆うときは覆われた ID の項も各々更新する。代表 ID にだけ書くと次回再浮上する
- Git 操作系も裁定待ちに含める (AI は push しない)。未 push は 20 commit 以上のときだけ挙げる
- 索引の総数が前回実行時から減っていない場合も普通のこと (裁定は溜まる)。急かす表現はしない

## スキル自己改善 (発火条件つき)

今回の実行で収集漏れ・正本との食い違い・誤解を招く出力規則を実測した場合だけ発火する。
発火時点でクラス 2 の起動手順を完了してから
`docs/skill-self-improvement.md` を読み、`rulings` の routing と commit 契約に従う。
発火しなければファイルを編集しない。
