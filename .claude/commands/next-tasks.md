# next-tasks — 今すぐ投げられる dev-wave を $1 件提案する

izanagi プロジェクト専用。提案件数 = `$1` (未指定なら 2 件)。
出力された投げ文をユーザーが tmux のコピーモード (ctrl-b [) でコピーして
別セッションへペーストする運用である。

## 常設の前提 (ユーザーが毎回言わずに済むよう固定する)

ユーザーは `/next-tasks` を打つたび、次の 2 点を口頭で添えていた。以後は毎回の指示を待たず、
**既に言われたもの**として選定・並び順・出力・codex への brief すべてに効かせる
(2026-08-29 ユーザー指示「わざわざ毎回言いたくない」)。

- **目的は論文を早く書き進めること。** 候補の価値は「論文の主張・図表・実験節がどれだけ前へ
  進むか」で測る。研究・実験を進める候補を上に置き、土台側を上げてよいのは**研究の実行または
  記録を今まさに止めている**場合だけ (止めている根拠を実測で書けないなら上げない)。
- **過剰な実装・ガードレールを避ける。** 成果物はアカデミアのプロトタイプであり、production 級の
  堅牢性は目標にしない (memory `research-first-prototype-robustness`、D205)。仮想リスクや将来
  可能性だけの gate・検査・台帳・framework・一般化・互換層は、候補にもしないし投げ文でも求めない。
  **ただし絶対規律 1〜6 と、実測で確認された正しさ欠陥の修正はこの制限の外**であり、
  この前提を規律・受入要件・既存防壁の緩和に使わない。

## 手順 (毎回この順で、回答直前に実測する)

道具置き場 (以下 `<tools>`、所在は `docs/pegasus-runbook.md` §7.2) を解決し、
呼出し時は `<tools>` をその path に置き換える。

1. **スナップショット**: `bash <tools>/next_tasks_snapshot.sh` と
   `ListAgents` ツールを両方実行する (handoff は wave 起動から遅れるので ListAgents が権威)。
   **毎回使う道具は `<tools>` に置いてある。その場で書き起こさず、
   足りなければ同 directory へ足して次回から使う** (2026-08-17 ユーザー指示)。
2. **裁定の確定状況**: snapshot が出す**未 land の控えを全件**読む (mtime の窓で切らない —
   land されないまま古くなった裁定が黙って落ちる。2026-08-13 に 8c 多世代開放の裁定が
   最新 7 件の窓から押し出される寸前だった)。`authority: user` と確定発話があるものだけを
   「裁定済み」と扱う。推奨提示のみ・収集のみの束は未裁定。
3. **母集合**: 次の 4 つを揃えて読む。どれか 1 つで代替しない。
   **母集合は作業ツリーの `docs/worklog.md` ではなく `git show main:docs/worklog.md` から取り、
   回答を出す直前にもう一度 main を取り直す。** /rulings 全件の一括裁定が入ると裁定状態が
   数十件まとめて反転する (2026-09-02 実測: 回答までに main が 33 commit 進み、裁定待ちを
   理由に外した候補と、他セッションへ送った警告がまとめて誤りになった)。
   稼働セッションへ助言を送るときも、送る直前に main の現物で裏を取る。
   - snapshot の「open な P1」— **持ち越し (carry) 項の本文を archive まで遡って解決した一覧**。
     stub 連鎖をそのまま辿る解決器は
     `python3 <tools>/worklog_carry_resolve.py --label P1`
     (`--grep` は語での総ざらい、`--pending` は裁定待ちの定型で絞る)。
     carry stub は `- [T-971] (540)` の形で本文を持たないため、末尾エントリを見るだけでは
     研究側の P1 が丸ごと落ちる (2026-08-13 に [T-971] 床値 SWO oracle を落とし、提案 4 件が
     全て土台側になった)
   - worklog 末尾エントリの非 carry 項 (snapshot が抽出する)
   - **worklog 末尾エントリの本文そのもの** — `sed -n` で全文を読み、「別タスク候補」「未修正」
     「別作業が持つ」と書かれた項を母集合へ入れる。**これらは task ID を持たないので carry にも
     非 carry 項の T-ID 一覧にも一切現れない** (2026-09-02 実測: entry 1186 が実測で潰した機構欠陥の
     うち signal handler 破損は「本 wave では未修正」、`analysis_commit` の偽の無効化は「絶対規律 7 に
     反する。別タスク候補」、トレース切り捨ての疑いは「正しさ主張に関わるので別タスク候補」と
     本文に書かれていたが、P1 carry 31 件にも非 carry T-ID 一覧にも 1 件も出ず、carry 一覧だけを
     渡した相談相手も 3 件とも落とした)。「A-5 (台帳 ID 未起票)」と同じ形で出所を明記して母集合へ入れる
   - 終端した wave の handoff が返した後続
   - **論文ストーリー最新版 §8 の A 群 / B 群** —
     `python3 <tools>/next_tasks_paper_gaps.py`。
     **A 群は「論文の但し書きを外すために要る証拠」そのもので、研究側の最上位になりうるが、
     台帳の carry に task ID を持たないことがあり P ラベル検索では 1 件も出ない**
     (2026-09-02 実測: `A-5` 別 boot 再取得 (D1100 ユーザー裁定済み) と `A-6` read-heavy
     certification は P1/P2 の carry 一覧 267 件のどこにも現れず、相談相手の上位 10 件にも
     入らなかった。両者とも論文の但し書きを 1 本ずつ外す項目である)。ID の無い項は
     「A-5 (台帳 ID 未起票)」のように出所を明記して母集合へ入れる
4. **codex への相談 (毎回行う)**: 母集合が揃った時点で、**別実装の同役 (codex) へ独立見解を
   求める**。自分の候補一覧を作る前に投げ、待つ間に下の編集面重複検査を進める。
   - 投げ方 = `bash <tools>/next_tasks_consult.sh codex <brief>.md <out>.md`
     (brief と out は job の tmp へ置く)。呼出しは read-only で、相手に書き込み・commit・
     wave 投入はさせない。**環境に API キーを置かない** — 同スクリプトは
     `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` があれば相談を中止する (鉄則の自己検査)。
   - **必ず背景で投げる。前景で待たない。** 疎通は 10 秒で返るが、本番の brief では
     10 分を超える (2026-08-26 実測: 前景の 10 分上限で切られ、出力が 1 byte も残らなかった)。
     `nohup bash ... &` で投げ、**このスクリプト自体を `timeout` で包まない** —
     包むとラッパーだけ死んで本体が孤児化する。締切はスクリプトの内側にあり、
     既定 1800 秒 (`CONSULT_DEADLINE_S` で変えられる)。
   - 回収は `<out>.md.done` (中身は `rc=<終了コード>`) が出てからにする。`<out>.md.log` は
     CLI の進捗で数 MB になるので**全文を読まない** (末尾数十行だけ)。判断に使うのは
     `<out>.md` の本文だけ。
   - brief には「原則この brief だけで答える・repo の広い探索はしない・裏取りは最大 3 件・
     15 分以内に返す・確信の無い点は未確認と書く」を必ず入れる。入れないと相手が repo を
     探索し始めて締切を使い切る (同日実測)。
   - brief は**自己完結**にする。相手は本セッションの文脈を持たない。最低限、
     (a) 件数と依頼の言い回し、(b) 候補一覧 (task ID・P ラベル・裁定状態・本文要約)。
     **候補を自分の判断で間引かず、未確認は「未確認」と書いて載せる。**
     **P1 だけを載せない — P1 が稼働・裁定待ちで埋まっている日は P2 にしか着手可能項が残らず、
     相手は「5 件は成立しない」としか返せない** (2026-09-07 実測: P1 30 件は稼働 12 件・裁定待ち 6 件・
     順序待ち 7 件でほぼ塞がっており、P1 だけの brief に対し codex は「確実に出せるのは 1 件」と返した。
     私が P2 271 件を実測すると T-2353 / T-2090 / T-2228 / T-2339 が裁定待ちゼロ・機構実在・非稼働で
     残っていた)。**P1 が枠を満たさないと分かった時点で P2 も引いてから brief を書く。**
     (c) 稼働 wave の slug 一覧と占有状況、(d) 選定規則の要点 (研究側下限・裁定待ちゼロ・
     機構実在・非稼働・全件同時に即投入可・P3 を出さない)、(e) **上の「常設の前提」2 点を逐語で**入れる。
     (e) を落とすと相手は防壁・台帳の整備を上位に返してくる (相手も同じ目的で並べ替えるため)。**自分の推奨順位は brief に書かない** —
     書くと相手が追認するだけになり、独立見解の価値が消える。
   - 相手に求めるのは、(i) 同じ母集合からの**独自の上位 N 件と理由**、(ii) 母集合から
     落ちている候補、(iii) 各候補の着手不能リスク (裁定待ち・機構不在・稼働重複) の指摘。
   - **相談は 1 往復。事実を追加して再評価を求める 2 巡目だけ、全候補をまとめて 1 回認める。**
     2 巡目の依頼は新しい事実の提示と再評価要求に限り、母集合の再収集を頼まない。
     スクリプトは毎巡 brief の先頭へ `CONSULT-MODE` の前置きを必ず付け、相手に
     (i) スキルを起動しない、(ii) 手順を再実行しない、(iii) さらに相談を投げ返さない、を課す。
     これが無いと相手自身の next-tasks が自動発火し、往復が止まらない。**外して呼ばない。**
   - **自分が `CONSULT-MODE` の入力を受け取った側になったときは、この手順を実行しない。**
     snapshot も母集合の再収集もせず、渡された brief だけを読んで独立見解を返し、
     codex へ相談を投げ返さない。
   - **相談が失敗しても止めない。** CLI 不在・rc≠0・出力が空のいずれでも、その事実と理由を
     出力の冒頭に 1 行で明記し、相談なしで提案を出す。相談を省いたのに省いたと書かない、は不可。
     **2 巡目の失敗は初回の判断を無効にしない。** 初回の結論を保ち、未解決分を不足として書く。

## 選定規則 (すべて満たすものだけ提案する)

- **系統 blocker は全てに優先し、その 1 件だけを出す** (2026-08-13 ユーザー指示)。
  系統 blocker = **全 wave が通る実行経路の赤** — codex 子の起動 (launcher・hook trust・
  evidence grace)、worktree 起動導線 (startup check・submodule init)、受入全走、land。
  ここが赤のまま $1 件提案すると、投げた全部が同じ穴で死んで帰ってくる
  (2026-08-13 実測: launcher の hook-trust 誤分類で 2 wave が段 2 で fail-closed 停止)。
  - 検知は次のいずれか。**1 本だけなら個別要因を疑い、系統と即断しない**:
    snapshot の worktree 占有で `locked` かつ `unoccupied` が 2 本以上 /
    直近の handoff に「fail-closed 停止」「起動不能」が 2 本以上 /
    main の受入全走が赤 / land が連続で rc≠0
  - **生死の判別を必ず行う (これを飛ばすと誤検知する)**: 停止した wave より**後に起動した
    wave が現在 occupied なら、共通経路は生きている** — 系統 blocker ではなく、個別事象か
    resume 待ちで保全中の残骸として扱い、通常どおり $1 件提案する。停止 handoff に
    「再開条件」が書かれているものは保全中であって現在の閂ではない。
    停止時刻は handoff の更新時刻、起動時刻は worktree の更新時刻で比べる。
    (2026-08-13 の実測: 11:29/11:30 に停止した 2 wave の worktree が残る一方、
     16:06〜18:10 に起動した 7 wave が occupied で走っており、共通経路は生きていた。
     生死の判別が無いと、この状態で系統 blocker と誤判定して提案が 1 件に潰れる)
  - 見つけたら**提案はその修正 1 件のみ**。`$1` 件の指定より優先し、冒頭に
    「N 件でなく 1 件にした理由 = 全 wave 共通の経路が赤」と 1 行で書く。
  - 同じ経路を通らない作業でも既定は併走させない (docs 編集が codex 子の起動を
    阻む例がある)。併走させるなら、その根拠を実測で示す。
- **今すぐ着手可能**: 裁定待ちゼロ、かつ**投入・実行の機構が repo に実在する** —
  「裁定で認可された」だけでは不可。機構の実在が不明なら grep で実測してから出す。
  検証できないものは precheck wave (実装差分ゼロで返す形) として明示するか、出さない。
  - **「裁定済み」ラベルは最新の全文再言及まで確認する** — round 集約ファイルや最初に
    見つかった `**P` 付き本文だけで確定と即断しない (`grep -rn '\[T-ID\] \*\*' docs/` の
    **最後の**ヒットを見る)。実装着手後に未記録の前提が発覚し「ユーザー再裁定待ち」へ
    差し戻った例がある (2026-08-19: [T-1310] は round 7 で「択 β 確定・実測開始」に見えたが、
    後続の実装で 12 predicate 制約が発覚し再裁定待ちに戻っていた)。
  - **「実装 wave 起票可」のまま残る carry は、対象 file を `git log --grep=D<番号>`
    (無ければ `--grep=\[T-ID\]`) で先に消す** — carry 更新漏れで land 済みのことがある。
    squash 件名が ID を含まず空振りする例もあるので、**ID grep が空でも即「未着地」と断定せず、
    対象 file/関数名そのものを grep するか `main..<branch>` の差分有無で裏取りする**。
  - **「実走可能」「次 wave で実機投入」と書かれた実験項は、成果物の実在で裏取りする** — carry の
    実走後も状態語が古い例がある。`output/insights/` の日付配下と旧直下を新しい順に列挙し、
    その実験の attempt 記録・receipt が既に在るかを見る (2026-08-29 実測: 完走して outer status
    まで記録済みの実験の carry が「実走可能」のままで、相談相手が最重要候補に挙げた)。
  - **carry が指す成果物 path は、投げ文へ書く前に同じ directory の新しい版を確かめる** — results や
    事前登録のような append-only 系列では、旧稿を 1 byte も変えずに新しい日付の稿が改版として置かれる。
    carry の本文は旧 path のまま更新されない (2026-09-07 実測: [T-2329] の carry は
    `docs/paper-story/results/2026-09-04-a2-certification-reject.md` を指していたが、現行の正本は
    同 directory の `2026-09-07-...` 改訂稿で、旧稿の「採用静的 backoff が無 backoff 対照を下回った」は
    誤りと改訂稿が明記していた。旧 path のまま投げると撤回済みの記述を英語化させる)。
    併せて、その成果物が「使ってよい」状態かも本文で確かめる (同稿の図 5 は D1645 により取り直しまで
    使用禁止だった)。
  - **取り残し branch の未着地判定に三点 diff の file 数・行数を使わない** — main が先へ進むほど
    三点 diff は膨らむ。`git log --no-merges main..<branch>` が空なら残骸、非空なら
    その commit が触る file が main の blob に在るかを `git ls-tree -r --name-only main` で照合する
    (2026-08-29 実測: 三点 diff で 1061 file の未着地と報告された branch が、実は着地済みだった)。
- **過剰追加を候補にしない** (常設の前提の具体化。判断に迷ったら「過剰でない」側でなく
  「出さない」側へ倒す): 確定済みの主目的・scope を満たす本体実装と、それに足りる既存機構の
  再利用・局所修正を優先する。それを超える追加実装・追加防壁は、追加手段がユーザーの明示要求の
  範囲内か、現在の目的達成・実在する正しさ欠陥の解消・現在の受入要件の充足に必要で、既存機構・
  局所修正では足りないことを既存資料または実測で確認できる場合だけ候補にする。ユーザー要求の
  範囲外では仮想リスクや将来可能性だけの framework・一般化・互換層・gate・検査・台帳は除外し、
  この基準を既存安全規律、ユーザー要求、受入要件の削除・弱化に使わない。
- **非稼働**: ListAgents の稼働セッション・生きた worktree・handoff のいずれにも
  担当が居ないこと。**task 単位だけでなく file 単位でも見る** — 提案候補の対象 file を稼働中
  worktree の merge-base からの diff (`<tools>/next_tasks_wave_impl_diff.sh`。`git diff main` は
  main の進行分が混じり読めない) と照合する。task-ID が別でも編集面が重なれば実質的に
  非稼働ではない (2026-08-20 実測で 4 file が task-ID の異なる稼働 wave と衝突した。
  ListAgents のセッション名一覧だけでは検出できない)。
- **既存規定の下で、事実は自分、選定判断は codex が権威を持つ。** 裁定状態・機構実在・着地・
  稼働重複・系統 blocker・ユーザー手番の事実は自分で実測し、相手の断定で代替しない。
  順位・採否・件数・研究/土台の振り分けなどの選定判断は codex が権威で、**覆せるのは判断の
  前提事実の誤りを実測で示すか、既存規定との矛盾を示すときだけ**。出所の明記・投げ文・
  最終出力の文責は自分が負う。
- **相手が「未確認」と書いた候補と、母集合外から相手が挙げた候補を、実測せずに外さない。**
  自分で実測し、結果をまとめて 2 巡目へ返し、**再評価の返答を採否へ反映してから出力する**。
  2 巡目で出た候補も実測し、着手不能なら除外して不足を書く (3 巡目へ進めない)。
- **件数を満たすために、相手が外した候補を残さない。** 順位を下げて枠に残すのは外したことに
  ならない。再評価後の結論が $1 件に届かないなら「M 件のみ」と不足を明記する。
- **不一致は表に出す。** 上位 N 件が食い違った場合、または相手が指摘したリスクを退けた場合は、
  その 1 件ごとに「相手の見立て / 自分の判断 / 分けた根拠」を 1 行で書く。一致した場合は
  「一致」と 1 行で書く。**相談したことにだけ触れて中身を書かない要約は不可。**
- **「これをやったら投げられる」型 (現在着手不能) は出さない。** ユーザーは出た投げ文を全部すぐ
  同時に投げる。稼働 wave・他候補の land 待ち、順序の条件、起動時の重複検査で止まりうる
  ものは投げ文にしない。互いに衝突する候補は 1 件に絞るか 1 wave に束ねる。投げ文の後ろに
  「実は待ちが要る」の但し書きや順序の節を置かない (2026-09-21 ユーザー是正)。
- **実験は計算ノードを占有して走るので、login 側の dev-wave と並行に投げられる**
  (D289。「計測中だから実験は投げられない」は誤り。2026-08-13 ユーザー是正)。
  実験の枠数を計測資源の都合で絞らない。
- **研究側に半分以上を確保し、両側とも優先度の高い順に取る** (2026-08-13 ユーザー指示。
  下限であって目標ではない — 常設の前提により、研究側に着手可能項があるだけ取ってよい)。
  研究側 = CC 合成・計測・床値・campaign・descriptor・oracle・verifier 実験など、
  成果物が測定値・certified な選択・材料レポートへ向かうもの。
  土台側 = 受入・land・hooks・docs・dev-wave 運用。
  - **下限は `ceil($1 / 2)` 件を研究側から**。研究側の着手可能項がそれに満たないときだけ
    下回ってよく、**足りない件数を明示する** (0 件なら「0 件」と言う)。
  - 残りの枠は、研究側・土台側を通して優先度の高い順に取る。**上限は設けない** —
    土台側の最上位が研究側より低い優先度なら、全枠が研究側でよい。ちょうど半々にしない。
  - **並べる順は研究側が先、各側の中は台帳の P ラベル順** (常設の前提: 研究を止めない
    土台項は P1 でも研究側の後)。ただし**研究の実行または記録を実際に止めている土台項は
    ラベルに関係なく先頭**へ置き、**何を止めているかを見出しに 1 行で書く**。
    止めている根拠を書けないなら先頭には置かない。
  - P1 が尽きたら `python3 <tools>/next_tasks_carry_p1.py P2`
    で P2 を引く。**P3 は既定で出さない** — 低優先度で枠を埋めない。
  - snapshot が出す一覧は**本文 entry の新しさ順であって優先度順ではない**。同ラベル内は
    本文を読み、律速性 (他項の前提になっている・実測が止まっている) で並べ替える。
  - 研究/土台の振り分けは codex の判断に従い、機械判定ではない。**迷ったら研究側に数えない**
    (研究枠を水増ししないため)。
  「直近で裁定された」ものだけを見ると裁定の新しい土台タスクばかりが並び、律速の研究項が
  残る (2026-08-13 の実測: 提案 4 件が全て土台側になり、床値の [T-971] が残った)。
- **取り残し成果の回収・掃除も高優先** (2026-08-12 ユーザー指示): branch や worktree に
  成果が取り残されて忘れ去られていないかをスナップショットの worktree 一覧と
  `git branch --no-merged main` で実測し、あれば「マージして land する」または「不要と
  判断できたら掃除する」wave を提案する。branch 削除はユーザー指示があるときのみ
  (memory 正本)、掃除手順は cleanup-branches スキルと runbook に従う。
  取り残しが**研究成果 (計測値・campaign artifact・材料レポート) を含むなら研究側として扱う**。
  含まないただの掃除は土台側として、上の優先度順の規則に従って土台枠から取る。
- **P2 まで見て $1 件に満たなければ、そこで止めて「M 件のみ」と言う。**
  P3 や優先度不明の項で水増ししない — 低優先度の提案は枠を埋めるだけで害になる。
  **ユーザー手番へ回してよいのは、AI に構造的に不可能なものだけ**である
  (サブスク認証の再ログイン、Pegasus からの push、F47 ラッチ解除)。
  「承認」「凍結」「設計を固める」「SHA を記入する」は AI 作業であり、手番に積まず
  dev-wave として出す。tty 等の誤操作防壁は迂回せず設計を変えて AI 実行可能にする
  (memory 正本、2026-08-17 ユーザー是正)。**台帳が「ユーザー手番ではない」と
  裁定済みの項を手番へ戻さない** — [T-1255] は「あなたでできるものを私にやらせないで」で
  既に裁定されている。該当があれば提案枠と別に 1 行で列挙する。

## 出力形式

- 冒頭 1 行: 「HH:MM JST 時点 / 稼働 wave: <slug を列挙>」。
- 冒頭 2 行目: 「codex 相談: 一致」または「codex 相談: 不一致 N 件 (内訳は各提案の後)」
  または「codex 相談: 実施できず (理由)」。内訳は各提案の後、除外分は末尾へ書く。
- 各提案: 見出し 1 行 (タスク ID・**台帳の P ラベル**・**論文のどこが前へ進むか**・裁定の根拠) +
  fenced code block に投げ文 1 段落。**blockquote (>) は使わない** (コピーで行頭に | が入るため)。
- 並び順は上の選定規則に従った codex の順位とする。
  ラベル順から外して並べた提案があるなら、その 1 件だけ理由を 1 行で書く。
- **投げ文は `/dev-wave ` で始める。「dev-wave を起動してください」等の散文で書かない** —
  散文入力とスラッシュコマンドによるスキル発動は振る舞いとして等価ではない
  (2026-08-12 ユーザー是正)。`/dev-wave` に続けて依頼本文を同じ段落に書く。
- 投げ文は自己完結にする: 裁定の控えパス (rulings-inbox/...)、正本 (insights / handoff /
  canonical worklog 項)、制約 (規律 2 を緩めない、Codex author = D95、scope 外の扱い) を
  本文に含める。継承 branch がある場合は branch 名と tip を書く。
- **main の SHA を「base」として投げ文に書かない。** 投げる時点で main は進んでいる
  (2026-08-25 実測: 21 分で 35 commit)。wave の開始 gate `tools/check_wave_startup.py` は
  HEAD == local main を要求し、1 commit の遅れでも段 1 が fail-closed で止まる。書くなら
  「着手直前の local main から fresh worktree を作る」と条件で書く。継承 branch の tip
  (上行) は base ではなく引き継ぎ対象の同定なので、そちらは SHA を書いてよい。
- **投げ文に scope 外を 1 句で書く**: 「本題の実装だけ。仮想リスク向けの gate・検査・台帳・
  一般化の追加は scope 外」。長い説明にしない (投げ文は従来の半分の長さ、memory 正本)。
  規律 2 を緩めない旨の 1 語は従来どおり残す — 削るのは**追加**であって既存防壁ではない。
