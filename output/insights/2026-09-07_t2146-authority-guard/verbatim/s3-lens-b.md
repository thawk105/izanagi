## 裁定パッケージ候補

1. D906 が要求する署名権限の境界

   - 事実: 現行案は秘密鍵を読めず・使えずにするものではなく、同一 uid の issuer が鍵を読み署名できる。
   - 推奨裁定: T-2146 は「直接書込み hardening」として着地させつつ、真正性の有効化条件には、AI process から秘密鍵と signer 実行権限の双方を隔離する別 uid・別 host・hardware-backed signer 等の外部境界を要求する。
   - 代替裁定: 同一 uid の読取りを許容し、保証を「鍵の偶発的・直接的な上書き抑止」へ明示的に格下げする。この場合「AI による受領証偽造不能」は主張しない。

2. authority root の Bash 防護範囲

   - 事実: parent directory の破壊、`pushd`、`env -C/--chdir`、内部例外時の canonical alias は、現在の段2設計でも直接 Bash 面に穴を残す。
   - 推奨裁定: これらは新しい一般 gate ではなく、今回掲げた「hook が観測する直接操作」の同一層なので本 wave の防護範囲に含める。
   - 代替裁定: 現設計のまま着地し、各操作を README の明示的残余にする。

3. MCP・apps・plugins・子・同一 uid process を含む「AI が書けない」の意味

   - 推奨裁定: T-2146 の主張を PreToolUse の2 surface に限定し、全 tool surface の閉包は別 wave とする。その別 wave が済むまでは D906 全体の完了根拠に数えない。
   - 代替裁定: 今回の目的文自体を OS 権限を含む全 surface の隔離へ広げる。これは明確な scope 拡大になる。

4. 人間による鍵更新・issuer 入替え

   - 推奨裁定: AI-visible な env/argv bypass は設けず、人間専用の hook 外・別権限経路を正当運用面とする。
   - 注意点: 単に「同一 uid の端末だから人間用」とするだけでは AI process との機械的区別にならないため、真正性境界の裁定とは分けられない。

## 総括

段2プランは、P1-c/P1-d の不足、repo 外 cwd、HEAD blob 束縛、秘密鍵読取り残余を親 brief より正確に捉えている。しかし現状のままでは、D374 に従う適用経路が存在せず、さらに parent-directory 破壊、`pushd`/cwd wrapper、内部例外時の canonical alias という直接 Bash 面の穴が残る。

変更は通常形の直接書込みを減らす実効性を持つが、秘密鍵と署名権限を AI から隔離しない。したがって「観測可能な直接書込み面を狭めた」とは言えるが、「AI は受領証を偽造できない」「D906 を満たした」とは言えない。公開鍵・秘密鍵の読取りは process 内部の `O_RDONLY` 操作なので、静的には受入全走を赤にしない。
