# 並行 wave が同一 file を別方向から触るときの、merge 前 静的検査の軸

2026-09-01 の一晩に、12 wave が同時に land を待つ状況で観測された軸の一覧である。
**網羅的な分類ではない。1 晩の観測にすぎない。**

## この文書の要点

**静的検査の限界は、検査の質ではなく軸の列挙にある。**

今夜の 3 件はいずれも「merge して赤を見る前に、両者の diff を読めば出る」ものだった。
しかし実際には、探そうとした軸だけが見つかった。T-1814 の子は「個数を pin する test」を
探して軸 2 を探さず、本 wave の親は指摘を受けるまで自分の `.replace()` を見なかった。
**軸を挙げられなければ、どれだけ丁寧に読んでも出ない。**

各軸には「どの走で発火するか」を併記する。ここが軸ごとに違うことが、
焦点走の緑を根拠に受入全走の緑を予測できない理由である。

**出所は軸ごとに分け、中継の段数まで書く。** 自分で実測した軸と、他 wave が実測して
中継で受け取った軸を混ぜない。**中継者を出所として書くと 1 段ずれる** — 実測したのは
中継元であって中継者ではない。本文書は初版でこの誤りを 1 件持っており、指摘を受けて直した
(軸 1 の出所を中継者に帰属させていた)。未実測を実測として残すのは、証拠を自作するのと
同じ向きである。

## 軸の一覧

### 1. 共有 module scope fixture の consumer 閉包

- **発火する走:** 受入全走のみ。焦点走では出ない。
- **形:** 新しい module scope fixture を作ると、それを取る node の集合が
  「共有 fixture の consumer 閉包が正本の node 一覧に登録されていること」という契約に掛かる。
  `orchestrator/tests/test_real_repo_serialization.py::test_real_repo_group_collection_exactly_matches_canonical_nodes`。
- **回避:** fixture を新設せず helper を各テストの先頭で直接呼ぶ。
  依存グラフを変更前と同一形状に保てば閉包検査は動かない。
- **出所:** 受入修正の所有 wave が、受入 attempt 2 の全走で実測した
  (上記 node が落ちたのが一次資料)。**取りまとめ役の中継経由で受領。本 wave は未実測。**

### 2. `str.replace` の byte 一致アンカーが静かに不発になる

- **発火する走:** 焦点走。静的確認では出ない。
- **形:** `.replace()` で導出している fixture は、元 fixture を編集するとアンカーが
  一致しなくなる。**`str.replace` は例外を出さず元の文字列をそのまま返す。**
  導出先が元と同一になり、単一理由の負例が 2 理由で落ちたり、対照が消えたりする。
- **回避:** 元 fixture を編集する前に `\.replace(` の全出現を読む。
  導出直後に「導出先 != 元」を assert すると、静かな不発が可聴になる。
  これは保証を増やす関門ではなく、既にある失敗を診断可能にするだけである。
- **出所:** 条件 10 の充足を開く wave が、`fields` へ 1 行足した際の焦点走で実測した
  (アンカーが不発になり、単一理由の負例が 2 理由で落ちた)。取りまとめ役の中継経由で受領。
  本 wave も自分のコードで同型を静的に特定した — `NEUTERED_VALUE_CHECK_C10` は
  `ACTIVE_VALUE_CHECK_C10` から `if actual_value != expected_value:` の byte 一致で
  導出されており、reader の実体化で字下げに触れば対照が消える。
- **補足:** 本 wave の場合は実行時の差も assert しているため同一化しても緑にはならない。
  **ただし落ち方が「原因の読めない例外」になる。安全であることと診断可能であることは別である。**

### 3. 新設された述語が、既存 fixture を落とす

- **発火する走:** 焦点走で出る。ただし**相手の diff を読まないと merge 前には出ない。**
- **形:** 一方の wave が判定器へ新しい述語を足すと、他方の wave が持つ合成 fixture が
  その述語に掛かる。今夜の実例は `_c10_reader_is_not_noop` で、docstring を剥がした後の
  body が `ast.Pass` だけの reader を拒否する。本 wave の新設 fixture 2 つは
  `def read_and_verify_bytes(): pass` で始まっており、merge 後は
  `EVIDENCE_UNDEFINED` ではなく `UNSATISFIED` へ倒れる。
- **回避:** 相手の diff で**新設された述語を列挙**し、自分の fixture を 1 つずつ通す。
- **出所:** 本 wave が両者の diff から静的に特定。merge 前。

### 4. 契約を締めた側が、充足を主張する他 wave の fixture を落とす

- **発火する走:** 焦点走で出るが、**両 wave のどちらも単独では見えない。**
- **形:** 一方が証拠契約へ新しい field を足し、他方が「充足する」fixture を新設すると、
  後者が前者の新 field を持たないために包含が不成立になる。
  今夜の実例は `C10_SATISFIED_VERIFIER` で、`proposal_build_source_bindings` を持たない。
- **これは回帰ではなく、意図した検出力である。** 契約が新しい証拠 field を要求する以上、
  充足を主張する fixture はその field を示さねばならない。
  「契約を広げたのに、充足の主張が古い基準のまま通る」ほうが問題である。
- **回避:** 契約を締める側が、相手の「充足」fixture を merge 前に読む。
  直す場所は**契約側ではなく fixture 側**である。
- **出所:** 本 wave が静的に特定。裁定により相手が land 前に自分で修正した。

### 5. 版番号・世代番号の衝突と、その解消順序

- **発火する走:** land の直前、あるいは merge の add/add 競合として。
- **形:** 同じ条件を扱う 2 wave が、判定器版と条件凍結世代を同じ番号で取る。
- **回避で注意する点:** `prepare_revision` は世代番号の**連続**を強制する。
  先行 wave の世代が自分の HEAD へ入るまで、次の世代は発行できない。
  **したがって「着地を待つ間に番号を寄せ直しておく」は機構上できない。**
  順序は「先行 wave の land → 取り込み → 版 bump → 世代発行」になる。
- **出所:** 本 wave が実測 (`generation-gap`)。

### 6. spool fragment の `base:` digest が先行 land で陳腐化する

- **発火する走:** land の lock の中。**受入が緑でも land が `landed` を返さない。**
- **形:** 複数 wave が並んで land すると、先行の fold が canonical 台帳を動かし、
  後続 fragment の `base:` が一致しなくなる。
- **回避:** main を取り込むたびに `spool_fold.py --dry-run` を回して base を取り直す。
  取り込み直後に回せば lease 窓を捨てずに済む。
- **出所:** 本 wave が指摘し、全セッションの手順へ入った。既知の性質の運用面である。

## 使い方

新規の失敗型として台帳へ立てる性質のものではない。軸 2 と軸 6 は既存の型の再発であり、
新規 F を立てると台帳が重複する。**merge 前に読むチェックリストとして使う。**

並行 wave が同一 file を触ると分かった時点で、相手の diff に対して次を行う。

1. 相手が**新設した述語**を列挙し、自分の fixture を 1 つずつ通す (軸 3)。
2. 相手が**締めた契約**に対し、自分の「充足」fixture が満たすか確かめる (軸 4)。
3. 自分の file の `\.replace(` を全出現読み、相手と自分の編集がアンカーを壊さないか見る (軸 2)。
4. 新しい共有 fixture を作っていないか見る (軸 1)。
5. 版・世代番号の衝突と、解消の順序制約を確かめる (軸 5)。
6. 取り込み直後に `--dry-run` で base digest を取り直す (軸 6)。
