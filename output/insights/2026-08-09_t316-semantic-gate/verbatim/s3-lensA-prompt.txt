## レンズ A = 「封じ込め不足と reward-hack 面」
親 brief と段 2 プランの推奨が、脅威を過小評価していないかを突く。特に:
1. **(ii) sandbox は本当に脅威 α を絞るか。** credentialless・network 無しでも、build 生成物 (binary)
   が後続段で cache hit 再利用され sandbox 外で走る経路 (D127 決定(5) の cache class 束縛未実装) は
   開いたままではないか。sandbox が build 時だけで run 時に外れる設計なら封じ込めは空振りする。
2. **auditor advisory 化 (脅威 β) は規律2 を緩めないか。** auditor を security credit から外すと、
   reward hack (verifier を欺く variant) の検出役が消える。sandbox は reward hack を塞がない
   (blast radius の話で正しさの話ではない)。「β を非 load-bearing 化」が実は「正しさの番人を捨てる」に
   すり替わっていないかを、auditor_gate.py と規律2 の観点で検証せよ。
3. **非対称 (iii) は sort 軸の穴を残さないか。** (i) を scalar/wire 軸に限定し sort 軸は (ii) だけ、
   という推奨は、sort 軸の comparator コード片に対する source-level の構造制約を放棄する。
   sort comparator に 1 行 C++ 注入が可能なら、(ii) の run-time 封じ込めだけが最後の砦になる。
   その砦が (1) の cache 再利用で破れるなら二重に開く。この連鎖を file:line で追え。
4. **DW-O13**: 提案 gate の入力 (coder diff / auditor verdict / build admission) が実成果物のどの field に
   存在するか。同名識別子の二義化 (D75) がないか。
