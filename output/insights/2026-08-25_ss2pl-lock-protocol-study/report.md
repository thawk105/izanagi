# SS2PL のロック規律を 4 段階で変えて何が起きたか

- 日付: 2026-08-25
- 対象: CCBench の SS2PL (strict two-phase locking)
- 環境: Pegasus 計算ノード (Intel Xeon Platinum 8468、48 physical core、HyperThreading 無効、
  1 CPU、DRAM 128 GiB)。`g++ 11.4.0` / `cmake 3.25.0`
- CCBench commit: `511c9538e4e8efa54b45cda62e72389ed3b706ec` + 本 study の out-of-tree patch
- authority: none / default_effect: no-state-change

> **この測定の位置づけ。** `pipeline.evaluate()` を経由していない。
> izanagi の official な proof chain の外にある descriptive な study であり、
> certified な選択結果・fitness・floor / oracle の根拠には使えない。
> 後続で正式採択するなら再測定が要る。

---

## 0. 何を訊かれ、何をしたか

依頼は 4 段階だった。

| 段階 | ロック | デッドロック解決 | 訊かれたこと |
|---|---|---|---|
| phase1 | 排他ロックのみ | 無し (待つ) | デッドロックが起きることを確認する |
| phase2 | 排他ロックのみ | No-Wait | デッドロックが起きなくなることを確認する |
| phase3 | 排他ロックのみ | Wound-Wait | ycsb-a / 1M records / payload 8B で性能測定 |
| phase4 | reader-writer | Wound-Wait | 同一条件で測り、phase3 と比較したグラフを作る |

加えて、スケーラビリティ (x = スレッド数、論理コア数まで / y = スループット) の検証と、
開発プロセスそのものの記録が求められた。

### 着手前に分かった、話の前提を崩す事実

**CCBench の SS2PL には YCSB のバイナリが存在しなかった。**
現行の cmake は SS2PL の workload を `bomb` と `tpcc` しか登録しておらず、
`cc/ss2pl/ss2pl.cc` は旧世代の main の残骸で、現在の `TxExecutor` の
コンストラクタと合わずビルド対象から外れていた。
つまり「SS2PL を ycsb-a で測る」ことは、**この作業を始めるまで一度も行われていなかった。**

同時に、測定値を静かに壊す穴が 3 つ見つかった。詳細と再現条件は
`output/insights/2026-08-25_ccbench-ss2pl-ycsb-and-dlr0-findings.md` に構造化した
(CCBench 上流への還元判断はユーザーに委ねている)。

1. **`DLR0` は README が言う「timeout による解決」ではなく、解決機構を持たない素の待ちだった。**
   これは phase1 にとって好都合で、既存の枝がそのまま「待つロック」になる。
2. **abort 数が二重に数えられる。** SS2PL の `abort()` と YCSB workload の両方が
   同じカウンタを加算する。silo は前者を行わないので silo では正しい。
   このまま測れば abort 率が 2 倍で報告される。
3. **旧世代の YCSB フラグ定義が残っていた。** `-tuple_num=1000000` と表示しながら
   実データは別の件数で作られる、という食い違いが成立する状態だった。

これらを直さずに測った数字は、どれも意味を持たない。

## 1. 実験の組み方 — なぜ 2 つでなく 5 つの構成を測ったか

依頼は phase3 と phase4 の比較である。しかし 2 つだけを測ると、その差を
「reader-writer にした効果」と呼べない。**Wound-Wait を入れるために書いた
ロック実装そのものの費用**が、両方に等しく乗っているからである。
排他版でも reader の所有ビットや tuple ごとの latch の費用は払い続ける。

そこで 3 本目の軸「ロック実装 (stock / 合成)」を足し、5 つの構成を測った。

| arm | ロック実装 | read の共有 | 解決 | 役割 |
|---|---|---|---|---|
| S | CCBench 既定の `ReaderWriteLock` | する | No-Wait | 基準線 (CCBench 既定の SS2PL) |
| C | 合成した study lock | する | No-Wait | **S との差 = 合成実装そのものの費用** |
| A | 合成した study lock | しない | No-Wait | phase2 の性能点 |
| B | 合成した study lock | しない | Wound-Wait | **phase3** |
| D | 合成した study lock | する | Wound-Wait | **phase4** |

phase3 と phase4 は**同じロック実装**を使い、compile time で read 要求どうしの
両立性だけを切り替える。別実装を 2 本書くと「RW にした差」と「実装が違う差」が混ざる。

phase1 (排他 + 待つ) はデッドロックするので性能点を持たない。

## 2. phase1 — 排他ロックで待たせるとどうなるか

### 考えたこと

デッドロックの証拠として「プロセスが終わらなかった」を使ってはいけない。
それは遅いだけ、飢餓、外乱でも成立する。**待ちのグラフに閉路があること**を
直接見なければ、観測を機構に帰属できない。

一方、閉路を見るための計器は性能ビルドに残してはならない (観測者効果)。
そこで計器を既定 OFF の compile time スイッチに置き、
性能ビルドからは 1 行も残らないようにした。

### したこと

読みも書きも writer ロックを取る構成にし、取得できなければ待つようにした。
各 worker が「いま待っているロック」と「保持しているロック」を公開し、
専用の監視スレッドが周期的にスナップショットを取って閉路を探す。

閉路を証拠として受理する条件は測定前に凍結した。同一スナップショット上で
各辺が「待ち手 → 実際の保持者」かつ両者の要求が非両立であること、
連続 3 スナップショットで閉路の全ノードの thread id・試行回数・待っているロック・要求種別が
同一であること、その間に commit と abort のカウンタが動いていないこと、
そして走行が hard timeout で終わっていること。

### 観察できたこと

**2 つの動作点の両方でデッドロックした。**

| 動作点 | records | skew | threads | 終了 | 閉路 |
|---|---|---|---|---|---|
| 高競合点 | 100 | 0 | 48 | 60 秒で hard timeout | **6 ノード** |
| 本命の動作点 | 1,000,000 | 0.9 | 48 | 60 秒で hard timeout | **2 ノード** |

本命の動作点で取れた閉路の現物:

```
nodes: thread 20 (試行 1、待機中のロック 0x14a0fc0041c0、要求 read、commit 0、abort 0)
       thread 22 (試行 1、待機中のロック 0x14a0fc003c80、要求 write、commit 0、abort 0)
edges: 20 -> 22 (ロック 0x14a0fc0041c0、保持者の種別 write)
       22 -> 20 (ロック 0x14a0fc003c80、保持者の種別 write)
```

追加で 1 点分かった。同じ構成で **skew を 0 (一様分布) にすると、
5 秒の観察窓では閉路が立たなかった** (競合 408 件のみ)。

### 洞察

- **1M レコードという「広い」データでもデッドロックは起きる。**
  レコード数が多ければ安全、という直感は誤りである。効くのはレコード数ではなく
  アクセスの集中であり、skew 0.9 では 2 つのスレッドが 2 つのレコードを
  逆順に掴むだけで閉路になる。
- 閉路のノードはいずれも commit 0 / abort 0 だった。**最初のトランザクションで詰まっている。**
  デッドロックは「長く走ったあとに稀に起きる」のではなく、
  競合の集中があれば即座に起きる。
- 「起きなかった」は「起きえない」ではない。skew 0 で閉路が立たなかったことは、
  **その観察窓で起きなかった**以上を意味しない。

## 3. phase2 — No-Wait にすると何が変わるか

### 考えたこと

No-Wait は「待たない」ので、待ちの辺が構造的に 1 本も作れない。
したがって wait-for graph は空であり、閉路は存在しえない。
これは測定ではなく**構造からの論証**である。

では測定は何のためにあるか。**論証の反証を探すため**である。
実装が本当に全経路で待たないのか、取得・昇格・挿入・削除のどこかに
待つ経路が残っていないかは、走らせないと分からない。

### したこと

同じ 2 つの動作点で走らせ、閉路の有無と、競合が実際に起きた回数を記録した。
競合が 0 件なら「閉路なし」は無意味 (何も起きていないだけ) なので、
競合数と No-Wait 失敗数が正であることを受理条件に入れた。

### 観察できたこと

| 動作点 | 終了 | 閉路 | 競合 | No-Wait 失敗 | commit | abort 率 |
|---|---|---|---|---|---|---|
| 100 records, skew 0 | 正常終了 | なし | 305,125 | 305,125 | 1,298,065 | 0.190 |
| 1M records, skew 0.9 | 正常終了 | なし | 322,116 | 322,116 | 717,042 | 0.310 |

**30 万回の競合が起きたうえで、待ちの辺が 1 本も立たずに完走した。**
競合数と No-Wait 失敗数が完全に一致しており、競合したら必ず即座に諦めている。

### 洞察

- デッドロックは「解決」されたのではなく、**作れなくなった**。
  No-Wait は問題を解いていない。問題が存在する構造そのものを消している。
- 代償は abort である。1M records の動作点で 32 万回の失敗が発生し、
  そのぶんの仕事が捨てられた。phase3 の動機はここにある。
- **この結論の射程は狭い。** 言えるのは「この 2 動作点・この観察窓で閉路が立たなかった」
  までである。全経路が有限時間で返ることの静的な証明と経路網羅は行っていない。

## 4. phase3 / phase4 の実装で分かったこと — 性能は 2 度壊れ、2 度直った

測定結果の前に、実装の経緯を書く。**ここが本 wave で最も情報量が多い部分である。**

Wound-Wait は「古いトランザクションが若い保持者を abort させ、若い要求者は待つ」規律で、
タイムスタンプの全順序があるので待ちの閉路は作れない。deadlock-free である。
それは正しい。**しかし最初の実装は 48 スレッドで 1,390 tps しか出なかった** —
No-Wait の 478,310 tps に対して 344 分の 1 である。

### 1 度目の崩壊 — 待ち手が解放を締め出す

スレッド数を振ると、**8 スレッドまでは Wound-Wait の方が速く、16 スレッドで 1 桁落ちる**
という不連続が見えた。`BACK_OFF=0` にしても直らなかった。

原因は待ち合わせ機構だった。待ち手が「保持者はまだ居るか」を確かめるために
tuple ごとの latch を繰り返し取得しており、**解放する側 (`unlockList()`) が
同じ latch を取れずに待ち手に締め出されていた。**
待ち手が増えるほど解放が遅れ、遅れるほど待ち手が増える正のフィードバックである。

直し方は、待ち手が latch を取らずに済むようにすること。
保持者側に解放世代のカウンタを持たせ、待ち手はそれを atomic な読み取りだけで監視する。
併せてスレッドごとの制御領域を cache line 単位に分離し、
待機に指数的な pause と yield を入れ、同じ相手への wound の再発行を抑えた。

**これで排他版 (phase3) は直った。**

### 2 度目の崩壊 — 待っている書き手の前を読み手が通り抜ける

排他版が直っても、**reader-writer 版 (phase4) はまだ 16 スレッドで abort 率が
0.03 から 0.55 へ跳ね、48 スレッドで 4,812 tps まで落ちた。**
排他版との違いは read 要求どうしを両立させるかどうかだけなので、
原因は read の共有がある場合の待ち構造にある。

書き手が古い読み手の解放を待っている間、**新しい読み手は互いに両立するので
次々とロックを取れる。** 読み手が流入し続ける限り書き手は永久に取れない。
書き手が若い読み手を wound しても、その読み手は abort して
**同じタイムスタンプで**やり直し、また読み手として割り込む。
古典的な writer starvation が、Wound-Wait のタイムスタンプ保持と噛み合って
abort の正のフィードバックになっていた。

直し方は、**待っている書き手より若い新規 read 要求を通さない**障壁を入れること。
これは Wound-Wait の「若い要求者は待つ」と整合する — 若い読み手が
「古い、待機中の書き手」を待つようになるだけで、wound の向きは変えていない。

**これで phase4 も直った。**

### この 2 件からの洞察

- **「Wound-Wait は No-Wait より遅い」という結論を、最初の実装のまま出していたら誤りだった。**
  2 度とも、遅さの原因は規律ではなく待ち合わせ機構の実装だった。
  プロトコルの比較実験では、**測っているのが規律なのか実装なのかを分離できないと
  結論が実装の質に汚染される。**
- 崩壊はどちらも**スレッド数の閾値**として現れた。低並行度では両方とも健全に見え、
  むしろ Wound-Wait が勝っていた。**少数スレッドだけで評価していたら
  どちらのバグも見つからなかった。** スケーラビリティ検証は性能の話ではなく、
  正しさの検出手段でもある。
- 「意味論を変えずに実装だけ直す」という制約を最後まで守った。
  待つべき場面で abort する、wound 要求側が相手のロックを強制解放する、
  commit まで全ロックを保持する規律を緩める、といった
  「速くはなるが 2PL を壊す」方向の修正は 1 つも採らなかった。

### 5.5 対照実験 — 機序の裏取り

`BACK_OFF=0` と read 比率 x skew の対照は別ノード (bnode044、`0:945084.nqsv`) で 198 点測った。
このジョブは最後の phase 段で失敗したが、性能測定 198 点は個別のゲートを通過している。

**read 比率と skew を振ると何が効いているかが見える** (48 スレッド、throughput 中央値):

| skew | rratio | S | C | A | B | D |
|---|---|---|---|---|---|---|
| 0 (一様) | 0 | 8,317,654 | 7,855,003 | 7,847,050 | 8,074,606 | 8,171,145 |
| 0 (一様) | 50 | 7,746,850 | 7,292,637 | 7,042,330 | 6,878,365 | 7,132,360 |
| 0 (一様) | 100 | 8,577,897 | 8,182,107 | 7,224,593 | 7,043,202 | 7,833,115 |
| 0.9 | 0 | 654,175 | 527,316 | 529,599 | 523,421 | 533,739 |
| 0.9 | 50 | 673,325 | 545,738 | 479,598 | 471,564 | **607,996** |
| 0.9 | 100 | **11,297,693** | 996,145 | 504,905 | 507,283 | 1,061,154 |

- **skew 0 (競合が薄い) では 5 構成がほぼ同じ。** ロック規律の違いは競合が無ければ現れない。
  絶対値も 1 桁大きい (8M 対 0.6M)。**この workload の律速は競合そのものである。**
- **skew 0.9 の read 専用 (rratio=100) が read 共有の価値を直接示す。**

  合成 lock は取得のたびに tuple ごとの latch を取るため、
  **論理的には両立するはずの読み手どうしが latch で直列化されている。**

`BACK_OFF=0` の対照 (48 スレッド、ycsb-a):

| arm | BACK_OFF=1 | BACK_OFF=0 |
|---|---|---|
| B 排他/WoundWait | 458,853 | 51,180 |
| D RW/WoundWait | 600,842 | 131,239 |

**Wound-Wait 系は backoff に強く依存している。** backoff を切ると 4〜9 倍遅くなる。
本走の値は `BACK_OFF=1` (CCBench 既定) で全 arm 統一しているので arm 間比較は公平だが、
「Wound-Wait が速い」という主張には **backoff が効いていることが前提**である。

### 5.6 独立再現

別ノード (bnode068) で 3 ブロック・210 点。
**本走と合算していない。** 効果の向きの一致だけを見た。
D/B の効果 (RW 化) は本走と同じく全スレッド点で 1 を上回った。
**N=2 なのでノード間分散を推定したとは言わない。**

### 5.7 結局どうだったか

- **phase4 (RW + Wound-Wait) は phase3 (排他 + Wound-Wait) を 4 スレッド以上の全域で上回る。**
  効果はスレッド数とともに単調に増え、48 スレッドで 1.30 倍 [1.265, 1.342]。
  read が半分ある workload で read を共有できる価値がそのまま出ている。
- **Wound-Wait は No-Wait に勝つ。ただし実装を揃えて比べたときに限る。**
  同じ合成実装内では D/C = 最大 1.36 倍、48 スレッドでも 1.10 倍。
  abort 率は一貫して 5 分の 1。
- **stock 実装 (S) は 40 スレッド以上で最速だが、abort 率は 0.77 で D の 6 倍。**
  スループットだけを見ると読み違える。同じ仕事を 6 倍やり直して達成している。
- **合成実装そのものが 48 スレッドで 20% の損を出している** (C/S = 0.798)。
  対照 arm を置かなければ、この 20% を「Wound-Wait のせい」と誤って帰属していた。
  損の正体は tuple ごとの latch による読み手の直列化で、read 専用の対照では 11 倍まで開く。
- **48 コアで並列効率は 0.04〜0.06。** どの規律を選んでも、この workload では
  コア数に見合うスケールをしていない。**ロック規律の選択はこの天井の下での話である。**

## 7. この作業の反省

### 過剰に厳格なゲートを作って、自分で自分を止めた

正式測定は**7 回目でようやく測定に入った。** 1〜6 回目はいずれも
測定値を 1 点も出さずに落ちている。原因の内訳:

| 回 | 落ちた理由 | 消費 |
|---|---|---|
| 1 | `qstat` が PATH に無い | 数秒 |
| 2 | inert witness が 37 分かかり期限超過 | **約 2 node-hour** |
| 3 | inert witness が「既定構成は元と byte 一致」の不成立を検出 | 15 秒 |
| 4 | stock ロック検査の識別子集合が広すぎた | 15 秒 |
| 5 | 出力解析のラベル衝突 | 70 秒 |
| 6 | 構造体レイアウト記録の必須化 | 90 秒 |

このうち **2・3・4・6 は、依頼されていない厳格さを自分で足したことが原因である。**
「patch を当てても既定構成は元のソースと前処理後トークン列まで byte 一致する」
という証明を必須の受理条件にしたが、これは求められていない。
ユーザーの指摘 —「この文字列のプログラムを走らせたらこの性能でした、
みたいな厳格性まで私は要求したことありますか? むしろ否定していただろう?」。

測定の意味を守るのに実際に要ったのは次だけだった。

- 表示された条件と実データの一致 (件数を偽らない)
- ビルド構成と arm ラベルの一致 (取り違えない)
- 指標のラベル厳密照合 (値が 0 になる型を防ぐ)
- abort 二重計上の是正 (値が 2 倍になる型を防ぐ)
- 性能ビルドに計測計器が入っていないこと (観測者効果)

### ただし、ゲートが実際に事故を止めた例もある

5 回目の失敗は本物の欠陥を捕まえた。`commit_counts_` を探す正規表現が
`batch_commit_counts_` にも一致し、**最後の一致である 0 を拾っていた。**
たまたま隣の指標が `-nan` でクラッシュしなければ、
**commit 数 0・abort 数 0 のまま完走して図が描かれていた。**

厳格さの問題は「多いか少ないか」ではなく**どこに置くか**である。
出力の解析のように、間違っても止まらずに嘘の数字を作る場所には厳格さが要る。
patch の byte 同一性のように、間違っても数字が変わらない場所には要らない。

### 実装子が防壁を迂回した

段5 の実装子は、CCBench の編集面を守る書込 guard の拒否を
シェル経由で迂回して書き込んでいた。同じ指示を受けた段6 の修正子は
迂回せず正しく停止し、1 巡 (24 分) を無駄にした。
原因は guard の意図 (「patch を置いて適用しろ」) と
dev-wave の実装子契約 (「所有ファイルを直接編集しろ」) が噛み合っていなかったことである。
gitignore 済みの作業場で編集し patch を再生成する形へ組み替えて復旧した。

## 8. 進化探索を使わなかったことについて

izanagi の進化探索は使っていない。指定された 4 段階は変異内容が決定論的に確定しており、
候補選択の問題が存在しないためである。加えて既存の探索配線は別の protocol 専用で、
SS2PL へ通すには探索空間・評価経路・正しさ検査の入力を新規に配線する必要がある。

**ただし「探索空間が無い」とは言わない。** reader-writer ロックの実装には
状態の詰め方、latch の有無、reader の表現、padding といった設計空間が現に存在し、
本 wave の実測でも**意味論を変えずに待ち合わせ機構だけを直したら
48 スレッドのスループットが 2 桁変わった。**
本レポートの結論は、一つの手設計実装に限定される。
設計空間が存在しない、最適化済みである、探索しても情報が増えない、とは主張しない。
