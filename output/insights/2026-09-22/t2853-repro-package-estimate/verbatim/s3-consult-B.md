# P1 — T1を採る理由が、要件充足の証明になっていない

**M1｜real・must-fix｜根拠: plan:88–97、J/web-evidence.md:4–8、docs/roadmap.md:56–64｜放置すると、検証費用・失敗候補の分析を支える観測履歴が失われ、全実験の再現パッケージだという説明を支えられなくなる。**

査読者による最も強い読み方は次のとおり。

> 本研究は、正しさ検証の費用と検出結果を中心命題に含めている。traceはその実験への入力であり、verifierの判定要約は実験データの派生物である。採用候補の標本と自己申告の判定だけでは、非採用候補の判定・検証負荷・欠損履歴の扱いを再評価できない。再走では同じ履歴が得られないことを著者自身が認めている。

したがって「判定と計測の値で満たす」は、提示された規定から導けない。**T1が必ず不適格だという攻撃までは不成立だが、T1で適格と断言することへの攻撃は成立する。** 規定抜粋はtraceの保存粒度を明示していない。

最小修正は、T1を「容量削減案・要件充足は未確定」に下げ、論文で使う検証実験について、原履歴を失うと再評価できなくなる項目を記すこと。将来の削除方針は、その区別を決める前に確定しない。

- **T2がよい条件:** 元の観測履歴の判定、検証費用、異常分類自体を主要結果にする場合。対象実験を絞ることで全trace保存が実用的になる場合もある。
- **T0がよい条件:** traceが当該主張の根拠でも再評価対象でもなく、必要な実験データを別の形で完全に提供できる場合。現在の中心命題には当てはめにくい。歴史的に失われたtraceの扱いを正直に説明する場合には使えるが、今後の一律削除の根拠にはならない。

**M2｜real・must-fix｜根拠: plan:89–93、108、output/insights/2026-09-21/vldb-direction/gap-analysis.md:240–242｜放置すると、保存した「反例」で元の異常を再検出できず、失敗候補公開の中核が欠ける。**

key射影は未証明なのに、「反例は小さく残せる」が採用理由になっている。列挙したkeyとcommit行が、依存辺・version order・履歴の整合性を十分に保持するとは、この資料から確認できない。TPC-C段2では述語読みと範囲へのinsertも対象になり、単純なkey集合の説明では足りない。

ここで射影実装を追加すべきではない。**当面の代替を「異常が出た反復の全traceを残す」と書き、その容量を別項で見積もる**のが小さい修正である。「全trace」は全候補全反復を意味しない。射影は、再検出可能性が確認できた後の任意の容量削減案へ下げる。

**S1｜real・should｜根拠: plan:67、91、J/check-quota.log:6–9、J/web-evidence.md:16–20｜放置すると、実際には選べる保存案を容量不足として棄却し、必要なデータを減らす。**

「公開もPegasus保存も非現実的」は根拠不足。quotaログの使用量とsoft limitの差は、kbytesを1024 bytes換算すれば約81 TiBで、模型の5.0〜11.2 TiBより大きい。これはgroup共有であり利用可能な割当ての保証ではないが、**このログは保存不能の証拠にはならない。**

50 GBは1レコードの制限であり、分割公開の運用負担と保存不能を区別する必要がある。また、表示値0.67〜11.2 TiBを50,000,000,000 bytesで割ると約15〜247レコードで、14〜230とは一致しない。

# 見積り — 模型の幅を上下限として扱っている

**M3｜real・must-fix｜根拠: plan:46–57、89、output/insights/2026-09-21/vldb-direction/gap-analysis.md:109–121、240–242｜放置すると、今後の実験が残すデータ量と保存計画を、未測定条件に対する保証値として誤用する。**

0.67〜1.50 TiB等は、二系列の中央値から作った**条件付きシナリオ値**であり、観測値の最小・最大でも予測区間でもない。

弱い仮定は四つある。

- 480候補の元案は「2課題」であり、「YCSBの3 workload等配分」への対応が説明されていない。
- MOCC・TPC-C・関数単位候補では、event数、行形式、処理量、圧縮率が変わり得る。
- rejectが最初の反復で起きるとは限らない。「失敗時に停止」と「全失敗候補が1反復だけ」は別である。
- legacy分を除き、全候補が5反復完走する模型は、同じ率・長さ・試行構成を固定した場合の比較に限られる。将来全体の上限にはならない。

最小修正は、表の列名を「Silo/YCSB代理シナリオA・B」にし、概算式を示すこと。

`保存量 = Σ（条件別候補数 × 実行した反復数 × 秒数 × 原本bytes/秒 ÷ 圧縮比）＋ legacy等`

MOCC・TPC-Cは未測定、失敗までの反復数は1〜5、追加反復等は別項とする。「圧縮率はworkloadで決まる」も「この二系列ではworkload別に近い値」に限定する。

なお、planの中央値をそのまま使うと、T1の6本を各3秒とした下側は約1.72 GiBで、1.9 GiBの根拠は不明である。こちらも秒数と算式を添えれば解消する。

**M4｜real・must-fix｜根拠: J/materials/request.md:3–7、plan:59–67、J/web-evidence.md:21｜放置すると、依頼された公開対象別の保存費が示されず、パッケージの量も過小評価される。**

六種類の見出しはあるので、「公開対象を丸ごと忘れた」という攻撃は不成立。しかし、対象別見積りとしては次が欠けている。

- 入出力と失敗候補を含む実験データが一括され、提案JSON・prompt・応答・失敗記録の範囲と増分が見えない。
- 関数単位patchの将来量を、現在の小さな整数変更patchから見積もる根拠がない。
- 当時のcheckoutを同梱するP2と、非trace合計1.1〜1.5 GBの関係が未整理。
- 保存費の金額側がない。料金記載がないことから無料とは置けない。

「論文の根拠に絞れば数十MB」は削除すべきである。未集計の結論であり、コード62.3 MBとsubmodule12.0 MBだけでも約74 MBになる。さらに、未測定のrepo外データと複数checkoutがあるため、1.1〜1.5 GBもパッケージ全体の上限とは呼べない。

最小修正は、既存表を六対象に対応させ、**現存量／将来量の仮定／未集計範囲／金額**を記すこと。金額資料がなければ「未確認」と明示し、保持期間・複製数・単価を置いた費用式まで示す。新しい台帳は不要である。

# P2・P5・P6 — 必要な保存と過剰な機構を分ける

**R1｜refuted・should相当の攻撃は不成立｜根拠: plan:94–100、docs/paper-story/2026-09-21c.md:1180–1191、J/materials/D320.md:7–13｜削除すると、旧書式の成果物を扱う道具を失い、モデル更新後の再評価を難しくする。**

R1／R2／Gの区別は妥当。当時のコードを道具として同梱することも、署名・pin更新・恒久同一性証明を追加する凍結chainではない。規律7とも衝突しない。

ただし、旧lockを現行codecで読めない事実は、**すべてのR2を当時のcheckoutでしか実行できない証明ではない。** 原記録の閲覧・再解析と、新しい履歴の取得は別問題である。

**S2｜real・should｜根拠: plan:73–74、99–100、CLAUDE.md:98–105、docs/paper-story/2026-09-21c.md:1183–1188｜放置すると、系列ごとの丸ごと複製が増え、過去コードの保存が新実験の条件へ変質する。**

「当時の道具を提供する」は維持しつつ、「R2は必ず当時のcheckout」と一律に限定しない。同じコードを使う系列は共用できる。submodule・repo外runner・必要な依存物を含むかは、実行手順に具体化する。archiveの存在だけで再実行可能と認定しない。

**R2｜refuted・should相当の攻撃は不成立｜根拠: plan:107、output/insights/2026-09-20/k2-loop-originals-lost-downstream/README.md:14–37、80–87、output/README.md:54–67｜P5を削除すると、使い捨て領域の消失により再評価の範囲が再び縮む。**

P5は単なる写しの推奨で、機構・台帳・凍結chainを導入していない。F1034には具体的な損失があり、保存の便益がある。K2の原本消失も、単に容量の大きなtraceがなくなった話ではなく、WAL・lock・critic入力の再検算可能性が低下した事例である。

推奨文には、cleanup対象から独立した保存先へ必要なデータとrunner等を写すこと、既存proof chainを移動・編集せず、写しをofficialの正本へ昇格させないことを短く添えれば足りる。

**S3｜real・should｜根拠: plan:108–109、J/materials/D2212.md:69–70、J/materials/D320.md:4–13、output/insights/2026-09-21/vldb-direction/gap-analysis.md:141–152｜放置すると、必要な再実行経路より候補単位の記録基盤や射影実装が優先され、研究の帯域を使う。**

P6の「欠け部品を列挙する」こと自体への攻撃は不成立。ただし、候補単位のモデル記録を必須部品とする根拠はない。同じシステム・モデル表示名・時期を共有する系列なら、その粒度で足りる。

欠け部品は次のように整理すればよい。

- 再実行に必要: patch適用入口、必要データの保存、実行手順。
- 任意の容量削減: key射影。
- 既存の散文記録で対応可能: 粗いモデル情報。

新たなschema・gate・候補台帳へ発展させる必要はない。

# P3 — 予算比率では主要図の再実行費にならない

**M5｜real・must-fix｜根拠: plan:75–78、101–105、output/insights/2026-09-20/t2797-b5-contrast/README.md:190–200、234–237、J/materials/D2212.md:46–49｜放置すると、再実行に要るnode時間を過小評価し、2 node時間の確認対象を誤る。**

10〜20%を**仮置きとして紹介すること**への攻撃は不成立。起票本文にも同じ仮置きがある。しかし、これを図ごとの見積りの代わりに据えることへの攻撃は成立する。

B-5の記録は、同じ53 sessionについて以下を区別している。

| 費用 | 記録値 | 意味 |
|---|---:|---|
| job Elapse合計 | 17.0 node時間 | 実際のnode占有 |
| lock待ちを除く固有費合計 | 6.18時間 | 待ちを差し引いた推定 |
| 固有費単価 | 217〜509秒/session | 特定構成の単価 |
| LLM handshake待ち | 約7,360秒 | job Elapseに含まれる待ち |

GのLLM直列時間を別欄にするのは正しいが、**nodeを確保して待つなら、その時間はnode時間にも入る。** R2を当時のjob構成で回す場合、lock待ちの再発も無視できない。

またB-8の約0.107 node時間/本は本走24本のjob Elapse平均であり、純粋なR1のverifier単価ではない。校正6本には6秒traceと10秒traceが混在する（J/preserved-traces-aggregate-b8.log:3–8）。校正平均まで「10秒traceの単価」に混ぜない。

修正は、主要図ごとに次の三種類を区別した小表で足りる。

1. 保存データから図を描き直す。
2. 保存候補を検証・計測し直す。
3. 独立探索をやり直して費用対成果の曲線を取る。

例えばB-5相当53 sessionのR2は、単価だけなら約3.2〜7.5 node時間という**固有処理の模型**になり、実際の固有費合計6.18時間、占有17.0 node時間を対照として示せる。B-8は本走約2.58、校正込み約3.11 node時間という既存占有実績を示せる。

これらを図へ対応させ、stock対照・較正・待ち・再試行の扱いを併記する。確認ラインは各job単独ではなく**同一タスクの投入合計**である。10〜20%は、この積上げを点検する参考値へ下げる。

# P4・P2のG — 何を再現できればよいかが不足

**S4｜real・should｜根拠: plan:98、106、docs/roadmap.md:56–64、output/insights/2026-09-21/vldb-direction/gap-analysis.md:113–120｜放置すると、手順は回っても、探索法の有効性・検証費用・転移という中心命題を追試したか判断できない。**

「絶対値を約束しない」「分布として比べる」は妥当だが、必要条件の説明にとどまる。stock比も機械が変われば変化し得るし、Pegasusの床値をそのまま他機へ持ち込む理由もない。

最小の書き足しは次でよい。

> 保存データからの再解析では、論文の集計値・判定区分・図の導出を再現する。R2では、新しい観測履歴に正しさ判定を行い、対象機で較正した変動幅と同条件のstock・強い基準との比較を報告する。元の倍率や順位の一致は保証せず、主張に関係する差と維持された範囲を示す。Gでは、独立探索ごとの有効候補率・異常検出率・費用対成果・未知条件への転移を、非LLM手法と比較する。モデル更新後のGは、その時期の追試として区別する。同等幅等は結果を見る前に定める。

数値の同等幅を本waveで新設する必要はない。将来の実験設計に残る項目として明記すれば足りる。
