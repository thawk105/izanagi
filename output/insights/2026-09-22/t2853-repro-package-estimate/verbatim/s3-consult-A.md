# key 射影：辺を保つ攻撃は不成立、原判定全体の再現とは別

- **A5｜refuted・不成立｜must-fix 相当の疑義を棄却｜根拠 `orchestrator/verifier/dsg.py:344`、同`:645`、同`:671`｜選択 key の全アクセスと、それら全取引の C 行を順序保持で残す射影では、当該 key の辺が消える／偽の辺が生えるという攻撃は成立しない。**

  実装の辺は次のように決まる。

  | 辺 | 実装が使う情報 |
  |---|---|
  | ww | key ごとの C 行由来の commit 版を辞書式に並べ、その隣接 writer |
  | wr | R 行の `(key, ver_epoch, ver_tid)` と、その版を作った writer の完全一致 |
  | rw | R 行で読んだ版より厳密に大きい、同じ key の最初の版の writer |

  version order は txid 順・壁時計順ではなく **commit `(epoch, tid)` 順**である。全アクセスを保持すれば、producer と版集合と読んだ版が保持されるため、選択 key の辺も保持される。cycle の各辺を支える key が選択集合にあれば、その cycle は残る。

  ただし「関係 txn」は **cycle 上の txn だけでなく、選択 key に触れた全 txn** と定義する必要がある。後者の R/W を残して C を落とせば parser の取引対応が壊れる。さらに txn を間引く別案では、例えば同じ key の writer A・B・C から B を落とすと ww の A→B→C が A→C に変わり、B の版を読んだ wr は失われる。これは親の「全行」条件を守る射影への反例ではない。

- **A6｜real｜should｜根拠 `parse.py:265`、同`:402`、同`:752`、`core.py:173`、`model.py:511`｜射影は原判定の integrity・件数・全 witness を再現せず、これを完全な R1 と呼ぶとパッケージの保証内容が変わる。**

  E 行を落とす、他 key の R/W を落とす、txn を丸ごと落とすことで、missing-end・count-mismatch・missing_txids が増える。しかし **cycle 検出は実行され、cycle があれば `non-serializable` が integrity 不整合より優先される**。したがって「framing が壊れるから anomaly 再検出不能」とする攻撃も不成立である。

  射影で保証できるのは、条件を満たす履歴についての **少なくとも一つの cycle の再検出**。元と同じ witness の選択、全 cycle 数、同じ integrity、key を持たない P 行等の失敗理由までは保証できない。

  私なら、今回の初段では射影を必須実装から外し、**anomaly を検出した反復の全 trace を保存する**。原入力をそのまま残せ、射影の新しい仕様を要しない。計画§3の率を使った条件付き量は次のとおり。

  | 3秒の失敗反復1本 | 原本 GiB | 保存 GiB |
  |---|---:|---:|
  | write-heavy | 約0.92〜0.95 | 約0.149 |
  | balanced | 約0.80〜1.57 | 約0.178〜0.354 |
  | read-heavy | 約2.15〜5.76 | 約0.532〜1.414 |

  3 workload 等配分なら、失敗反復1本／候補で保存約 **0.286〜0.639 GiB**。仮に480件全部がこの条件の失敗なら約 **137〜307 GiB**、3,600件なら約 **1.01〜2.25 TiB**。これは失敗反復だけの量で、先行する成功反復・legacy・retry は含まない。異常候補の trace 率が正常候補と同程度という未測定の仮定も残る。
