## D1343. B-4 の先行提案と実 campaign の束縛は実行ループ側で閉じる (2026-09-01)

**決定 (ユーザー裁定):** B-4 の先行提案と実 campaign の束縛は、**実行ループ側で閉じる。**
ループが提案の canonical hash を再計算し、封印済み registry と一致しなければ**実行前に拒否する。**

**理由:**

- issuer は期待 hash を封印できるが、実際に消費される proposal との一致は強制できない。
  一致を強制できるのは実行直前のループだけである。
- 束縛が閉じないまま実走すると、raw 記録は「事前固定した 201 試行」ではなく
  「registry のラベルを付けた 201 の選択可能な証拠」に留まる。受理集合を狭める向きの検査であり、
  絶対規律 2 と整合する。

**却下した選択肢:**

- **issuer 側だけで閉じる** — 封印はできても、消費される proposal との一致を強制できない。
- **束縛を閉じないまま実走する** — 記録が事前固定を意味しなくなる。

## 4. ユーザーへ返す裁定パッケージ (scope 外・実装しない)

1. **precursor と campaign の束縛を誰が閉じるか。** `initial_proposal_sha256` を実際に計算・記録する
   経路が repo に無い。閉じるには loop 側か issuer 側の変更が要る (T-2050 / T-2051 の領域)。
   閉じないまま B-4 を実走すると、raw 記録は「事前固定した 201 試行」ではなく
   「registry のラベルを付けた 201 の選択可能な証拠」に留まる。

   registry 側を整数・有限十進に制限するか、消費側 (凍結 closure) を変えるかの択一。
3. **凍結 closure 外の producer をどの層が認証するか。** 5-file pin を動かさない限り、
   source bytes の hash が一致しても「どの producer 意味論で作られたか」を verdict が識別できない。
