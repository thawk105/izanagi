## 3. task → predicate → evidence 対応

### [T-068] — 移行契約により superseded

- **closure predicate**: D78 (9) の明示的 supersede 裁定。
- **evidence**: `orchestrator/campaign/t080_freeze_migration.py` の ancestry 判定が missing-commit /
  not-ancestor を typed status にし、git 障害と non-commit object だけを refusal に残す。
  gate 側は ancestry の `refusal_reason` がある場合だけ refusal へ積む。
  `(i)` の出力で `frozen_at_head` 2 件が `missing-commit` の typed observation として現れる。
- **注意 (理由付けの訂正)**: 「post-R に拒否が 4→2 へ減ったから方式 B と同値」ではない。元の [T-068] は
  `frozen_at_head` **ancestry** の格下げであり、消えた 2 拒否は source / design **drift** である。
  移行契約は ancestry の typed 化と source repin の**両方**を実装したため、より強い形で supersede した。

### [T-077] — design_source 再 pin + generator M 化

- **closure predicate**: R の receipt が有効な下で design_source が basis blob へ repin され、
  generator が metadata 扱い (M 化) になること。
- **evidence**: `(i)` の observation に
  `/design_source/sha256` = `repinned-to-basis-blob` (holdout) と
  `/generator/sha256` 2 件 = `metadata-only` が現れる。
  holdout generator は recorded `1910fff3…` ≠ observed `41c0b6a7…` でも通る — **M 化が非恒真に効いて
  いる証拠**である (一致するだけなら M 化していなくても通ってしまう)。
- **強度の限界**: receipt の決定論 field は H_mig blob から再導出されるため自己申告だけでは
  `active-valid` にならないが、real-repo test は observed 期待値を receipt 自身から組み立てており、
  15 件の独立 literal pin ではない (D78 (6)(f) の承認済み残余。下記 §5)。

### [T-078] — S2-4.6 承認値の外部固定 fixture

- **closure predicate**: 承認値を production literal と**別の値源**で固定し、predicate 単独 mutant が
  hit 数を 1→0→1 と動かすこと。
- **evidence**: `orchestrator/tests/t080_fixture_roots.py` が S2-4.6 承認値 (path / root key / sha256) を
  test 側 literal として固定。production 側は `orchestrator/campaign/t080_freeze_migration.py` が同値を
  独立に持つ。`orchestrator/tests/test_s8b_holdout_freeze.py` が raw bytes hash と両 literal の一致を
  別 node で検査し、fixture bytes を変えずに rratio predicate だけを 50→51 に変える mutant で
  hit 数の 1→0→1 を exact assert する。
- **強度**: raw root / test literal / production literal / 検索 predicate の四面が分離されており、
  「fixture と期待値を同時に動かせば常に通る」形ではない。ただし test 本文・raw literal・predicate まで
  協調編集する攻撃は test trust boundary の外であり、「変更不能」ではなく
  「複数面レビューで検出する」性質である。

## 5. 正直な限界 — closure は残余を解消しない

D78 (6) の承認済み残余 (a)〜(g) は**すべて現存する**。closure は「(9) の条件が発火した」ことの確定で
あって、「全機械証拠が充足した」という主張ではない。とくに:

- **(a)** builder 実走の実在は機械検証されない (決定論 field の byte 一致 + finalize の fail-closed +
  人間確認に依存)。
- **(b)** `live_scan_sha256` は形式 (64hex) 検査のみで、stored hash と実走値の一致は保証されない。
- **(f)** observed 値の独立 literal pin は不在。**H_mig が確定した今は可能になった**ため、
  hardening 候補として起票した。

さらに本 wave の敵対相談が新たに指摘し、親が一次資料で確認した検出力の穴が 3 件ある。いずれも
**今日の判定値・受理集合・proof 参照・試行欠落を変えない** (検査は現に走っており、穴は「将来の退行が
静かに通る」こと) ため、最初の E2E 1 cycle 前の hardening を限定する gate に従い 1 cycle 後へ送った。

1. `_verify_receipt_derivation` を **public `verify_receipt()` 経由**で撃つ negative test が無い。
   `receipt.derivation_mismatch` を期待するテストは内部関数の直呼びと、consumer 側へのエラー注入 mock
   だけである。さらに full-gate fixture は当該関数を no-op へ stub 化する。
2. real-repo gate test は R の OID を pin せず、receipt commit を reachable history ごと除去すると
   pre-R の 4 拒否分岐を正解として受理する。通常の追加 commit による削除は production が拒否するので
   fail-open ではないが、履歴書換に対する pin ではない。
3. 上記 (f)。
