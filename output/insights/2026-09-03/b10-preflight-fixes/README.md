## 1. 依頼の前提を最初に実測した — 5 件のうち 1 件は既に直っていた

設計文書 §6 (1) は、ジョブスクリプトのシグナル処理が
`local name=$1 number=$2 rc=$((128 + number))` と書かれていて `set -u` で落ちる、と現在形で書いている。
**現物はそうなっていない。** commit `2d6f2dbf5`「b10 job の signal handler を set -u 下で到達可能にする」が
main の祖先で、`local` は既に 2 文へ分かれており、SIGTERM から rc=143 と failure 引数を検査する
挙動テストも同 commit で入っている。

したがって本 wave の実装 scope は (2) 壁時計、(3) ビルドキャッシュ置き場、
(4)+(4-b) 集約の分離と完全性の分母、(5) 実行ノード名の 4 件である。
**設計文書 §6 (1) の記述は着地前の状態を指しており、次の投入判断を誤らせるので訂正した。**

## 2. 完走済み write-heavy はどれか — 選択の余地は無かった

D1509 決定 3 は「完走済みの write-heavy 45 セルは残す」と定めるが、
官製 output には write-heavy の campaign が 2 本あり、どちらも block record を 45 件持つ。
全数を読んだ結果は次のとおり。

| campaign | 記録 | 正しさ認証 | 性能 binary の SHA | 測定不能 | throughput |
|---|---:|---|---|---|---:|
| `write-heavy-formal-e3de15eb` | 45 | 45 件すべて true | 45 件すべて有り | 45 件すべて false | 45 |
| `write-heavy-formal-068fd2cd` | 45 | 45 件すべて true | **0 件** | **45 件すべて true** | 0 |
| `balanced-formal-15e75b3f` | **記録ディレクトリ自体が無い** | — | — | — | — |
| `read-heavy-formal-ed8a676b` | **記録ディレクトリ自体が無い** | — | — | — | — |

`068fd2cd` の 45 件はすべて `performance-measurement-failed:PreflightError:[perf-binary-binding]`
で終わっている (設計文書 §5.2 が「45 セル全部が SHA 不一致で測れずに終わった」と書いた相)。
**したがって採用する campaign に選択の余地は無い。** balanced と read-heavy は
旧 campaign に性能セルが 1 件も無いので、混ざる元が存在しない。

段 3 のレンズが「採用 campaign 集合を実装が暗黙に決めている」と指摘したが、この実測により refuted とした。

## 3. driver 自身の bytes が campaign の同一性へ入る — 不一致は本 wave 以前から成立していた

`b10_backoff_shape_sweep.py` の `ANALYSIS_REL` は driver 自身の path で、その bytes の SHA-256 が
`analysis_code_sha256` として事前登録の束縛へ入り、`search_config` を経て campaign 同一性まで流れる。
つまり §6 の修正を実装すると新しい束縛・新しい campaign ID になる。

**重要なのは、この不一致が本 wave 以前から成立していたことである。**

| 対象 | analysis_code_sha256 |
|---|---|
| 起点 main の driver | `94d2cb330476bdf5572aa6844fec4441a5379f8278558af68fcd8eb983baafb8` |
| `e3de15eb` の記録 | `34072fb2a5a5aed0e19ff1e653bb31bb71c3c434f32b3055c4b0b7a9e422c4ed` |
| `068fd2cd` の記録 | `8f91074e4c05b8ef975458e1558ec796842d579956b2b3b60def4c42280326de` |

通常の block record 検査は記録の束縛が**現行**の束縛と一致することを要求するので、
**起点 main の時点で既に旧 45 セルを集約へ入れられない。**
D1509 決定 3 の「規則は登録内容ではなく集約側に持たせる」は、まさにこの型への裁定である。

## 4. 有限集合へ閉じないと規律 2 に反する

段 2 のプランは、旧 write-heavy を「campaign ID + 歴史的な束縛の形」で受理する案を出した。
段 3 のレンズ A がこれを **real な受理集合の拡大**として棄却し、親が採用した。

理由は、記録の封筒が**自己 hash であって秘密に束縛された署名ではない**ことである。
正規の格子・束縛・受領証 hash を保ったまま `correctness_certified` や `median_tps` を書き換え、
封筒の hash を計算し直した入力が通ってしまう。これらの値は判定へ直接入る。

採用した形は、**現存 45 record の内容 digest 集合を実装内に凍結して exact 照合する**ことである。
封筒の合成 field を除いた記録の全 key/value を canonical JSON 化して hash するので、
判定へ入るどの欄も digest の外に無い。段 6 のレンズ C が官製 45 file から独立に集合 digest を計算し、
実装の定数と一致することを確かめた。

## 5. 段 6 が親の裁定を 2 件訂正した

### 5.1 キャッシュ置き場の鍵 — nonce では再開性が壊れる

親は R5 で「置き場を分ける」ことだけを裁定し、実装子は鍵に submission nonce を選んだ。
段 6 のレンズ D が、これが設計文書 §7 の
「性能測定の途中で切られた場合は続きから取れる」を壊すことを実測で示した。

投げ直すと鍵が変わって冷えた置き場から再ビルドになる。cross-job の bytes 再現性は
`output/insights/2026-08-31_t1905-b10-formal-run/README.md` が
**path 非依存化を 2 巡実装して差分が 149 → 56 → 45,454 bytes と収束しなかった**と記録しており、
成立しない。セル記録は一度きりの作成なので、一致しないセルは測定不能で固定される。

鍵を workload へ変えた。分散の単位が workload ごと 3 本なので分離度は同じままで、再開性が戻る。

**同時にレンズ D は、cross-cache-root の bytes 一致テストを実装の先行条件にすべきでないことも示した。**
段 2 のプランはこれを先行条件に置いており、そのままなら §6 (3) は構造的に実装不能だった。
SHA 一致条項が要求しているのは同一 job の中での照合である。

### 5.2 凍結集合の照合が実効経路へ繋がっていなかった

実装した digest 照合は、テストが helper を直接呼ぶだけで、**実際の受理経路からその helper を呼ぶ
1 行を検査していなかった。** その 1 行を消しても全テストが緑のままで、
事前登録していた変異 M6 が生き残る形だった。段 6 の 2 レンズが独立に同じ穴を指摘した。

期待 digest 集合を引数で受け取る注入 seam を作り、正例と負例を実効経路経由で通す形へ変えた。
変異 matrix でこの 1 行を消す変異が KILLED になることを実測した。

## 7. 開示と受理規則の境界

設計文書は完全性の 3 行を「参考値であって受理規則ではない」と明記している。
段 2 のプランは WAL の無終端 tail・登録外タグ・反復の上限超過を**レポート発行の拒否理由**にしており、
段 3 のレンズ A がこれを境界を越えるものとして指摘した。正しい 135 セルが揃っていても
付随情報の異常だけでレポートと判定が発行されなくなる。開示だけに限定した。

反復番号の明示欄は成果物に存在しない。段 2 は試行ごとに出現順で番号を振る案を出したが、
親が官製 4 campaign の WAL を数え直し、`(workload, 変種, タグ)` ごとの**件数**で
完了記録数を順序非依存に再現できることを実測した。件数法を採った。
ただし観測標本に複数試行も上限超過も含まれていないので一般性は主張せず、
**重複 frame と別 repetition はどちらの数え方でも識別できない**という限界を明記している。

## 8. 135 セルの照合は「全 3 本の終端」を証明しない

段 6 のレンズ D が、135 記録が揃う時点が job 終端より早いことを示した。
集約は他 job の終端記録へ到達する経路を持たない (自分の受領証しか知らない)。

**証明を偽装せず、終端の保証が投入手番であることをレポート本文へ明記する形にした。**
機械的な終端 gate は他 job の記録へ到達する新しい配線を要するため、本依頼の
「仮想リスク向けの gate を足さない」に従い実装していない。

## 9. この記録が主張しないこと

- 実装した 4 件で正式走が投げられるとは主張しない。設計文書 §8 の残りの項目
  (検査の多重化、複数本を 1 本の待ち手で待つ投入側の段取り) は本 wave の外にある。
- read-heavy が枠に入るとは主張しない。道の選択は D1509 決定 2 により律速測定の後である。
- ビルドキャッシュ置き場を分けても binary の bytes が置き場に依存しないことを、
  **bytes の水準では証明していない。** 既存テストは prefix map と RPATH 無効化を
  argv の水準で検査している。同一 job 内の SHA 照合は変えていないので、
  この不確かさは SHA 一致条項の強さには影響しない。
- 完走済み 45 セルを集約へ入れる規則は**この系列限り**である。次に driver を編集すると
  本 wave で作る balanced / read-heavy も歴史的な束縛の側へ回る。
  次系列で再利用する campaign を事前に名指しする規則はユーザー裁定に属する。
