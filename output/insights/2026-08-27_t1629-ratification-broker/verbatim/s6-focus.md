## `87532e9f` の方針変更

判断はコードで裏付けられます。

`require_signed_ratification` が受け取るのは `blob_sha256s` だけで、binding commit は渡されません。receipt の `source_commit` は receipt repository の HEAD からの reachability と source blob digestへ束縛されますが、外側 binding commit との同一 DAG は検査対象に存在しません。[receipt:958](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t1629-ratification-broker/orchestrator/campaign/enforcement_source_ratification_receipt.py:958)、[receipt:1016](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t1629-ratification-broker/orchestrator/campaign/enforcement_source_ratification_receipt.py:1016)

したがって共有 fixture の役割は、実 binding が指定した bytes と合成 receipt repo の source bytes が同じ digest であることです。これは [conftest:225](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t1629-ratification-broker/orchestrator/tests/conftest.py:225) と [conftest:241](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t1629-ratification-broker/orchestrator/tests/conftest.py:241) で保持されています。

将来「同一履歴」を要求するなら、fixture 修正では足りず、binding commit を receipt gate へ渡す API/schema 変更が必要です。
