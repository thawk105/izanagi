# B-10 正式走のトレース切り捨て — 起きていない。頭打ちは横軸の取り違えだった

worklog エントリ 1186 が「655 万件超で所要が頭打ちになる観察は未確認で、トレース切り捨ての
可能性がある (正しさ主張に関わるので別タスク候補)」と残した宿題への回答である。

**判定: トレース側だけで件数が減る切り捨ては起きていない。** 45 cell の
`correctness_certified=true` の意味は変わらない。本書は当時の判定を昇格も降格もさせず、
追記として記録する (絶対規律 7)。判定の限界は最後の節にまとめた。

## 何を突き合わせたか

対象は B-10 正式走系列の 4 campaign の WAL に残る `verify_done` 記録 **287 件**である。
各記録は 1 回の trace 有効走 (ベンチマーク実行 → トレース書き出し → 直列化可能性検査) に対応する。

| campaign | WAL 更新 | verify 反復 | 位置づけ |
|---|---|---:|---|
| write-heavy `068fd2cd` | 2026-09-01 05:00 | 90 | 相を分けた先行 attempt。verify は完走し、perf が binary SHA 不一致で全滅した |
| balanced `15e75b3f` | 2026-09-01 11:00 | 85 | 6 時間枠で 15 変種中 14 変種まで進んで打ち切り |
| write-heavy `e3de15eb` | 2026-09-02 00:52 | 90 | **報告済みの 45 cell を認証した完走 attempt** |
| read-heavy `ed8a676b` | 2026-09-02 06:52 | 22 | 15 点中 3 点で撤去 |

**45 cell の `correctness_certified` は、`e3de15eb` の 15 変種 × 6 反復 = 90 回の trace 有効走に
由来する。** 同一 point の 3 block は同じ `variant_id` と同じ `build_attempt_id` を共有するので、
1 変種の認証を 3 cell が受け継ぐ (成果物の 45 record を数え直して確認した。distinct な
(variant_id, build_attempt_id) は 15 組)。反復は「1 件でも失敗すれば即 reject」なので、
変種が COMMIT へ到達したこと自体が 6 反復すべての認証を意味する。残る 197 反復は同系列の裏づけである。

突き合わせた 3 つの数は次のとおりで、生まれる経路が違う。

| 数 | 何を数えているか | どこで作られるか |
|---|---|---|
| `commit_witness.commit_counts` | CCBench 自身が commit のたびに増やす集計 counter | ベンチマークの標準出力の `commit_counts_:` 行 |
| `commits` | ディスク上のトレースに実在する `C ` 行 | orchestrator が `trace_*.log` を読んで数える |
| `observed_commits` | 検査器が構文解析して重複排除した committed txn 数 | 検査器の内部 |

counter と C 行が本当に別経路であることは submodule のソースで確かめた。

- counter は workload 側の `include/ycsb.hh` にあり、`tx.commit()` が真を返した**後**に、
  トレースとは無関係に無条件で 1 増える (`#if TRACE` の外にある)。
- C 行は並行性制御側の `cc/silo/transaction.cc` の `writePhase()` 冒頭、`#if TRACE` の中で出る。

したがってトレース側が落ちても counter は減らず、その逆も無い。ただし両者は同じプロセスの
中にあるので、共通要因で同時に落ちる形は残る (最後の節)。なお C 行は counter の増分より**先**に
出るので、最後の 1 件でプロセスが死ねば C 行が counter を上回りうるが、その場合は実行体の
返り値が非 0 になり検査器の手前で拒否される。287 反復ではいずれも完全一致だった。

## 判定の根拠

### 1. 検査器自身が 287 回すべてで完全性を表明している

`certified` は `serializable` かつ `Integrity.clean()` である。`clean()` は純粋な連言で、
とりわけ次を要求する。

- `observed_commits == expected_commits` — 検査器が読んだ committed txn 数が、
  ベンチマーク自身の counter と一致すること。
- `missing_txids == 0` — txid の欠番が無いこと。txid は commit 経路でだけ採番される
  0 始まりの単調 counter なので、取引が丸ごと落ちれば欠番になる。
- `framing_violations == 0` — `C` 行が宣言した read/write 件数と実際の R/W 行数が一致し、
  `E <txid>` で閉じていること。末尾が途中で切れれば破れる。
- `orphan_reads == 0` — 非 genesis なのに produce した write がトレースに無い read が
  無いこと。

**287 件すべてが `certified=true` である。** つまり検査器が毎回この連言を通した。

親は WAL に残る `commits` (トレースの C 行) と `commit_witness` を数え直し、287 件すべてで
一致することを確認した。**ただしこれは独立な第二の証拠ではない。** `serializable` verdict が
integrity clean を要求し、clean が `observed_commits == expected_commits` と `dup_txids == 0` を
要求するので、C 行数の一致は verdict から導ける。この数え直しで確かめられるのは
「WAL に残った投影が検査器の判定と食い違っていない」ことまでである。

### 2. 検査が拒否した走行は 1 件も無い。ただし「異常終了なし」ではない

不一致や構文解析の失敗は `_abort` が WAL へ `abort` stage として書く。4 campaign の
stage 内訳は `build_start` / `build_done` / `verify_done` / `commit` だけで、**`abort` は 0 件**
である。したがって「不一致で落ちた走行が記録に現れないから一致率 100% に見える」という
選択バイアスは成立しない。

一方で「異常終了が一つも無い」とは書けない。4 campaign 合わせて `build_start` は 49 回、
`commit` は 47 回で、balanced と read-heavy に**終端に達しなかった変種が 1 つずつある**。
予定が 49 × 6 = 294 反復なのに対し観測は 287 なので、**7 反復は実行されずに終わっている**。
これは外側 job の壁時計打ち切りによるもので、検査が拒否した結果ではない。実行されなかった
7 反復は何の正しさ主張も担っておらず、その 2 変種は 45 cell に含まれない。

### 3. 切り捨ての形態ごとに検出器が実在し、空振りしない

想定できる切り捨ての形を列挙し、それぞれがどこで止まるかを対応づけた。

| 形態 | 止まる場所 | 実在する正例テスト |
|---|---|---|
| トレースが空 (C 行 0) | 検査器の手前で `trace-empty` として拒否 | — |
| スレッド 1 本分のファイルが丸ごと欠ける | commit witness の不一致 | `test_commit_count_witness_detects_removed_trace_file` |
| 末尾の取引が丸ごと落ちる | commit witness (欠番検査は `max(txid)+1` で数えるので末尾欠落だけは捕えられない。D295 を入れた主目的がここ) | `test_characterization_tail_txid_gap_is_indeterminate_with_commit_witness` |
| 中間の取引が落ちる | txid の欠番 | `test_missing_txid_gap_indeterminate` |
| 取引の途中で切れる (C は残り R/W/E が消える) | 宣言件数不一致と missing-end | `test_characterization_txn_tail_loss_is_indeterminate` |
| 行の途中で byte が切れる | 構文解析エラーとして拒否 | — |
| 実行体の timeout・異常終了で buffer が失われる | 検査器の手前で timeout / 非 0 終了として拒否 | — |

通る正例は `test_commit_count_witness_accepts_complete_trace` である。
`clean()` が要求する 4 項 (`observed==expected` / `missing_txids` / `framing_violations` /
`dup_txids`) は、いずれも他 3 項を 0 に保ったまま単独で赤にできる入力が構造上存在する。
**恒真な項も、前置条件で到達不能な項も無い。** これらの形態はどれも 287 反復で発火しなかった。

### 4. 書き出し経路に切り捨てる箇所が無い

トレース書き出しは CCBench submodule の `include/trace.hh` にある、スレッドごとの
`std::ofstream` である (submodule pin `511c9538`)。**件数上限もリングバッファも持たない。**
上限で捨てる実装がそもそも存在しないので、「トレースに上限があって切り捨てられている」という
起票時の仮説は機構としても成り立たない。

正確に書くと、この stream は開いたまま逐次追記する形で、明示的な `flush()` も書き込み成否の
検査も無く、ワーカースレッドが正常終了したときのデストラクタに依存する。したがって
異常終了で末尾が失われる余地はある。ただしその場合は実行体の返り値が非 0 になり、
検査器へ渡る前に拒否される。

## 頭打ちの正体 — 横軸の取り違え

起票元は所要を **試行数 (commit + abort)** に対して見ていた。実測では、cell 間で所要を
説明するのは **commit 数**であり、試行数ではない。

write-heavy 正式走 (`e3de15eb`) の 15 点を試行数の順に並べると、これが一目で分かる。

| point | commit 数 | 試行数 | 1 反復の所要 |
|---|---|---|---|
| adaptive | 1.10M-1.12M | 2.07M-2.22M | 76.8-80.5 秒 |
| constant-mu100 | 1.73M-1.74M | 2.95M-2.97M | 116.2-127.2 秒 |
| symmetric-modulo-mu100 | 1.80M | 3.02M | 123.4-131.9 秒 |
| constant-mu50 | 2.05M-2.06M | 4.35M-4.37M | 142.1-149.8 秒 |
| symmetric-modulo-mu50 | 2.11M-2.13M | 4.41M-4.43M | 151.1-153.8 秒 |
| constant-mu25 | 2.31M-2.34M | 6.52M-6.56M | 165.0-172.6 秒 |
| symmetric-modulo-mu25 | 2.36M-2.37M | 6.55M-6.56M | 160.6-163.6 秒 |
| symmetric-modulo-mu10 | 2.52M-2.56M | 10.74M-10.83M | 172.9-179.1 秒 |
| constant-mu10 | 2.50M-2.52M | 10.83M-10.86M | 170.7-183.7 秒 |
| symmetric-modulo-mu5 | 2.50M-2.52M | 13.98M-14.09M | 171.1-181.2 秒 |
| constant-mu5 | 2.50M-2.52M | 14.33M-14.46M | 170.3-184.6 秒 |
| symmetric-modulo-mu2 | 2.44M-2.45M | 17.05M-17.34M | 170.5-179.0 秒 |
| constant-mu2 | 2.46M-2.49M | 17.25M-17.54M | 170.8-184.1 秒 |
| none | 2.27M-2.36M | 20.14M-21.16M | 158.3-174.0 秒 |
| zero-loop | 2.39M-2.40M | 20.94M-21.24M | 164.8-175.0 秒 |

**所要は commit 数にぴったり付いていき、commit 数が 2.5M 付近で頭打ちになると所要も頭打ちになる。**
試行数はその先も 21M まで伸び続けるが、所要は増えない。trace 有効ビルドではトレース書き出しが
効くのでスループットに天井があり、commit 数はそこで飽和する。一方 abort 率は mu を小さくするほど
上がるので、試行数だけが伸びる。**これが「頭打ち」の正体である。上限ではなく、横軸が
所要と無関係だっただけである。**

数値でも同じことが出る。

- performance タグ 238 反復で、所要と commit 数の相関は **r = 0.9991**。
  試行数との相関は **r = 0.4044**。
- campaign 別に分けても r(commits) は 0.9826-0.9975。r(attempts) は write-heavy 0.67-0.69、
  balanced 0.78 に留まる (read-heavy だけ 0.997 だが、そこは abort が少なく
  commit ≒ 試行数のため両者を区別できない)。
- 両方を同時に入れた回帰では、試行数の寄与が消える。

      所要 = -26.517 秒 + 84.625 マイクロ秒 × commit 数 - 0.309 マイクロ秒 × 試行数
      R^2 = 0.998152  (238 反復)

  **commit 数を固定したとき、試行が 1 件増えることの費用は実質 0 である** (符号すら負)。

### 起票元の 3 数値がどこから来たか

「約 25.6 マイクロ秒/件」と「655 万件」は、**mu=25 の 2 点 (10 反復)** の実測である。
そこは試行数 6.52M-6.56M、試行あたり 25.5-26.4 マイクロ秒で、平らな帯が始まる左端に当たる。
「175 秒あたり」は平らな帯そのものの高さを丸めた読みで、実際の帯は 158.3-184.6 秒に広がる。

**3 つを同時に満たす単一の測定は無い。** `6.55M × 25.6 マイクロ秒 = 167.7 秒`であって
175 秒ではない (4.4% のずれ)。3 数値は近傍の複数行をまとめて読んだ記述であり、
1 つの傾向線でも一般の単価でもない。全 performance 反復の試行あたり所要は
7.5-74.2 マイクロ秒に散らばる。

## 所要の内訳と、並列化への入力

1 反復の所要は WAL の時刻差であり、**混合区間**である。ベンチマーク本体 (extime 3 秒) のほかに、
トレースの書き出しとスレッド終了時の flush、C 行の数え直し、標準出力の解析、直列化可能性検査、
一時ディレクトリの作成と削除、WAL への書き込みを含む。**「検査器そのものの費用」ではない。**

campaign 別の単回帰は次のようになる。

| campaign | 反復数 | 傾き | 切片 | RMSE |
|---|---:|---|---:|---:|
| write-heavy `e3de15eb` | 75 | 70.043 マイクロ秒/commit | 1.91 秒 | 4.32 秒 |
| write-heavy `068fd2cd` | 75 | 72.492 マイクロ秒/commit | -4.30 秒 | 5.34 秒 |
| balanced | 70 | 79.187 マイクロ秒/commit | -5.74 秒 | 8.65 秒 |
| read-heavy | 18 | 87.002 マイクロ秒/commit | -70.75 秒 | 31.25 秒 |

**workload ごとに単価が違うので、全体をまとめた 84.4 マイクロ秒/commit を一律に使ってはいけない。**
切片は物理的な固定費ではなく、観測範囲内の経験回帰の係数である。

この関係は **cell 間の予測**であって、機構上の限界費用を測ったものではない。同一変種の
5 反復の中では相関が r=-0.0213 まで落ちる。ただしこれは反復内に信号が無いためで、
同一変種内の commit 数の振れ幅は中央 0.93% しかないのに所要の振れ幅は 6.99% ある。
**反復内の時間ノイズが commit 数の微小変動を覆い隠しているだけで、cell 間の関係を否定しない。**

read-heavy が 5 時間かかった理由もここで確定する。**read-heavy の検査対象は
write-heavy の約 7 倍である。** read-heavy で走った 4 変種のうち 3 変種は
1 反復あたり commit 16.83M-17.19M で、所要は 1346.9-1465.6 秒だった
(残る 1 変種は adaptive で commit 5.54M-5.62M、所要 401.7-427.4 秒)。
同じ 1 反復が write-heavy では commit 1.10M-2.56M・所要 76.8-184.6 秒である。

起票元が「検査対象の合計は write-heavy とほぼ同じ約 2000 万件」と書いたのは
**試行数の合計**であり、検査が実際に扱う量ではない。同じ段落の「commit が 1690 万件」の
方は正しく、所要を決めていたのはそちらである。

これは T-2191 (直列性検査の並列化) への入力になる。分割の単位を考えるときの注意は 2 つある。

1. **並べる軸は試行数ではなく committed txn 数である。**
2. **費用の単位は 45 cell ではなく 15 認証単位である** (1 変種 = legacy 1 回 + performance 5 回)。
   同一点の 3 block は同じ変種の認証を共有するので、45 cell 分を積むと 3 倍の過大評価になる。

## この判定が保証しないこと

**判定の射程は「トレース側だけで件数が減る切り捨ては起きていない」である。** 次は否定していない。

- D295 が明記した非検出限界。**trace と counter は同じ実行体から出るので、両方が同時に落ちる
  common-mode failure と、個数を保存する破損は検出しない。** 具体的には (a) 実際の commit が
  N+K 件でも末尾 K 件が trace と counter の両方から同時に失われる形、(b) ワーカー 1 本の
  trace ファイルと同じワーカーの counter 集計が共に落ち、その欠落が末尾側にある形、
  (c) C 行の件数を保ったまま R 行を構文上妥当な別の R 行へ差し替える形。本書はこれを
  「独立 witness」と言い換えない。言えるのは「trace 外 counter による個数の裏取りが
  287 回すべて通った」である。
- 実行されずに終わった 7 反復。これらは何も検査していないが、何の正しさ主張も担っていない。
- **トレースの実体はもう残っていない。** 検査を通った走行の一時ディレクトリは削除される。
  したがって後から byte 単位で E 終端や txn 数を数え直すことはできず、本判定は実行時に
  検査器が下した判定と WAL に残った件数に依存する。トレースを永続化しない現行設計の帰結であり、
  永続化は本 wave の scope 外とした。
- 検査の対象は **committed transaction の履歴**である。abort した試行は DSG に入らない。
  これは覆っている割合の偽装ではない — commit した取引が、commit されていない版を読んでいれば
  `orphan_reads` が立つ。ただし「全 transaction を検査した」「全試行を検査した」とは書けない。
- `correctness_certified` が指すのは trace 有効ビルドでの変種単位の認証であり、性能計測に使った
  trace 無効ビルドの走行そのものの履歴を検査した意味ではない (絶対規律 1 による別ビルド・別走)。
  この射程は当時から変わっていない。
- 頭打ちの説明は所要の**混合区間**についてのものである。ベンチマーク本体・トレース書き出し・
  検査のどれが律速かは、この時刻差からは分離できない。
- write-heavy で commit 数が 2.56M を超える領域は、この走行では観測されていない。
  hard cap の否定は read-heavy campaign の中だけで閉じる (同 campaign 内で
  5.61M commits / 414.6 秒 と 16.90M commits / 1425.4 秒 が並ぶ)。

## 集計の再現手順

WAL からの抽出は次の 1 コマンドで行った (campaign ごとに繰り返す)。

    jq -r '[.ts,.variant,.stage,(.payload.workload.tag//"-"),(.payload.commits//0),
            (.payload.commit_witness.commit_counts//"null"),(.payload.aborts//0),
            (.payload.anomalies//"-"),(.payload.verdict//"-")]|@tsv' <WAL>

1 反復の所要は、同じ variant の直前の WAL イベント (`build_done` または `verify_done`) との
時刻差である。variant と point の対応は成果物 `reports/write-heavy/b10_backoff_shape_provenance.json`
の `records[].variant_id` と `records[].point` から取った。集計に使った使い捨てスクリプトは
repo へ入れていない (実装面は Codex author の所有であり、本 wave の実装面差分は 0 である)。
