# [T-338] 裁定パッケージ — RF producer が止まっている本当の場所 (2026-08-17)

本 wave は実装しなかった。理由と、前へ進めるための選択肢をここに置く。
**判断はユーザーが行う。親は推奨を添えるが決めない。**

## 分かったこと (一言で)

D481 は「pilot を公表層から切り離したので producer から着手できる」と書いた。切り離しは正しく、
公表層はもう producer を止めていない。**しかし producer を止めているものが別にもう 1 つあり、
D481 はそれを見ていなかった。** それは T-139 の投入 gate である。

連鎖はこうなっている。

1. 受領証を**ファイルとして書き出す関数**は、承認済みの記録項目 (record-items-v2 §6.10) により
   `PreregBinding` という部品を必ず受け取らなければならない。別経路の writer は禁止されている。
2. その `PreregBinding` は、D264 が「投入 gate が完成するまで外に出してはならない」と定めた
   4 つの名前の 1 つである。D282 がこの禁止を維持している。
3. したがって、**投入 gate が完成するまで、受領証を書き出す producer は作れない。**

さらに、書き出す以前の問題として、受領証の中身に**実際にクラスタへ投入した事実**
(qsub の結果・測定開始の印) が必須である。`declared_use_class = "dry"` にこれを免除する規定は無い。
投入せずに値を作れば、それは事実ではなくなる。`pilot_submission = forbidden` は維持されている。

**残るのは「試行台帳だけを作って producer 実装済みと記録する」形だが、D264 はこれを名指しで
却下している** — 「台帳だけが『producer 実装済み』へ進む半実装は、直前の wave が blocker と
判定した形である」。だから本 wave は実装しなかった。

## 止めているのは物理ではなく、自分たちで課した証拠水準である

念のため明記する。producer が作れないのは技術的に不可能だからではない。**自分たちが置いた
4 つの規則が同時に効いているから**である。どれもそれぞれには正当な理由がある。

| 規則 | 何を要求しているか | 出典 |
|---|---|---|
| 唯一 writer | 受領証を書く関数は `PreregBinding` を受け取れ。別経路の writer 禁止 | record-items-v2 §6.10 |
| 非 export | `PreregBinding` は gate 完成まで外に出すな | D264 |
| 事実性 | 受領証の attempt は実際の qsub 結果を持て | pin 済み schema |
| 投入禁止 | pilot を投入するな | D292 / D481 決定 (5) |

規則を緩めるかどうかは**ユーザーの判断**である。緩めない選択も正当であり、その場合は下の (a) になる。

## 選択肢

### (a) T-139 の投入 gate を 1 単位で完成させ、そのあと producer を書く  ← 親の推奨

D264 が既に想定している唯一の順路である。**新しい緩和を 1 つも要らない。**
gate は「承認 manifest・祖先検査・受領証照合」の 3 段で、完成させれば `PreregBinding` を
export でき、受領証 writer が正規に作れる。

- 良い点: 規律を 1 つも緩めない。D264 の却下理由 (部品だけが先にあると通ったように見える) も回避する。
- 悪い点: scope が大きく、T-338 ではなく **T-139** の作業になる。T-338 は gate 完成待ちへ回る。
- 注意: gate を作ることは投入の解禁ではない。gate は正しく拒否する側も含む。
  ただし D264 は「恒真 deny stub」を却下しているので、拒否専用の見せかけは作れない。

### (b) D264 の射程を限定し、durable な RF 試行台帳だけを先に入れる

「台帳を入れるが producer 実装済みとは記録しない」ことを新しい decision で明記する案。

- 良い点: pilot が走るときに記録先が既にある。台帳の設計 (canonical な置き場所・外部固定 tip・
  producer が選べない intent authority) を先に確定できる。
- 悪い点: **D264 が名指しで却下した形に自分から入る。** かつ本 wave の実測では、この台帳は
  D229 決定 (8) の必須 kill 3 件を 1 件も達成しない (消費者も無い)。過去に 2 度却下された
  「未結線 leaf」の型でもある (D147 決定 (3) / D163 決定 (1))。
- 条件: 採るなら、台帳が満たすべき性質 (campaign / study_stage の identity、外部固定 tip、
  producer 外の intent authority) を先に決める必要がある。本 wave の敵対レビュー 2 本が
  この 3 点を欠くと権威にならないことを独立に示した。

### (c) 局所実行の「下書き」受領証を、正当な生データとして認める

クラスタへ投入せず手元で走らせた測定から受領証を書くことを、新しい decision で認める案。
`declared_use_class = "dry"` を使い、`cluster_slot_or_null` は空にする。

- 良い点: D481 が挙げた困りごと (「producer が無いので validator は合成 fixture しか読めない」) が
  **実際に解ける。** 手元実行の受領証は合成 fixture ではなく実データである。
- 悪い点: これは**証拠水準を下げる決定**である。ユーザーの明示的な承認が要る。
  また唯一 writer の規則 (§6.10) との関係を決める必要がある。
- **必ず添える条件:** この受領証を D162 発火条件 (ii) の証拠に**しない**こと。(ii) は環境タグ・
  測定 checkout・pin を producer の自己申告以外の経路で照合できることを要求しており (D481 決定 (2))、
  手元実行はこれを満たさない。満たすと書けば受理拡大になり、絶対規律 2 に触れる。

### (d) pilot が動かせるようになるまで producer を止める (現状維持)

- 良い点: 何も緩めない。
- 悪い点: pilot は producer を必要とし、producer は gate を必要とする。**(a) を選ばない限り
  この待ちは自力では終わらない。** 事実上 (a) の先延ばしである。

## 併せて決めてほしいこと

### Q2. D229 決定 (8) の必須 kill 3 件を、producer 段の条件から外すか

D229 決定 (8) は「失敗した投入を台帳と raw の双方から落とす」「新しい親系列 ID を自己申告して
累積有意水準をリセットする」「anomaly を clean と申告する」の 3 変異を必須 kill と定めた。
本 wave の実測では、**3 件とも producer 単独では達成できない。**

- 1 件目は producer の外にある durable な intent authority と PBS driver との結線が要る。
- 2 件目は族の根から測定 head までの全履歴 validator が要る。
- 3 件目は生の正しさ証拠を再計算する独立 semantic validator が要る。

いずれも D229 決定 (6) の順序では producer より後の段の機構である。
**択 (a):** 3 件を validator / consumer 段の受入条件へ移す (producer 段では登録しない)。← 親の推奨
**択 (b):** producer 段の条件として残し、producer は 3 件が kill できるまで完成としない。

### Q3. 再利用先の棚卸しを次 wave の段 1 要件にするか

本 wave の親は「土台は `orchestrator/qualification/`」と暫定裁定したが、敵対レビューが
調査不足を指摘した。`attempt_ledger.py` のほかに `qualification/series.py`、
`s8b_holdout_admission.py` の O_EXCL 台帳などが候補にある。
**択 (a):** 次 wave の段 1 でこれらを棚卸ししてから設計を決める。← 親の推奨
**択 (b):** 新規実装で通す。

## 親の推奨をまとめると

**Q1 = (a)**、**Q2 = (a)**、**Q3 = (a)**。

理由は 1 つである。(a) の組は**規律を 1 つも緩めずに前へ進める唯一の組**であり、
かつ止まっている場所 (T-139 の gate) を正しく名指ししている。
D481 は producer の閂を公表層だと見ていたが、実際の閂は gate だった。ここを直せば
`producer → pilot → validator/consumer → 本走` の順序はそのまま生きる。

ただし **(c) を選ぶ判断も筋が通る。** D481 が挙げた困りごとを最短で解くのは (c) であり、
「証拠水準を自分で上げすぎて動けなくなっている」状態を解く手でもある。
採る場合は上記の「必ず添える条件」を外さないこと。
