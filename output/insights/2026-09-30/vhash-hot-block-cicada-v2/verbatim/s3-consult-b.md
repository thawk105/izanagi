### B1: 待ちの解消幅を事前に見積もれない

**重大度: should-fix。** 根拠: md_23 一次資料 §5・§6、plan.md:29–32。更新中心では B の待ちが約 9.8万〜11.8万 cycles/update commit、保持が約 2,800〜3,800 cycles/update commit。B-post は CAS と位置探索を区間外へ出すので、長い保持を減らす筋はある。ただし偏り 0.9・48 thread では、CAS の競合と、その直後の同じ key の `vh_seq_` 取得が残る。`latest_` と `vh_seq_` は隣接しており、同じ cache line に載る可能性も高い。これらの数値から **待ちが何割減るか、stock 比がどこまで戻るかについて非自明な上下限は出ない**。

放置すると、一次資料の性能値を「10万 cycles の主因を除去した効果」と過大に解釈する。推奨: COUNT で CAS 再試行数、CAS 後の guard 待ち・保持、隣接確認の成功・失敗を分け、perf の比と突き合わせる。より単純な代案を一つ挙げるなら、**K=1 の最新版手がかりだけを CAS 後に更新し、`latest_` 一致時だけ採用する設計**を先に測る。疎な K=8 の保守を除いたまま、排他を CAS 外へ出す問いに答えられる。

### B2: 読みの利得を隣接 load が相殺しうる

**重大度: should-fix。** 根拠: md_23 一次資料 §5・§6、plan.md:9–13,30。md_23 の ro95 は既に stock 比 0.980〜1.011。GC 10 µs では読みの約 82% が版を一つも飛ばさず、GC 100 ms では K=8 でも cold が約 2,335万回ある。B-post は hit ごとに隣接版または `latest_` を追加で読み、疎な cold は `latest_` から再走査する。

放置すると、書き側の改善があっても ro95 の比が下がった理由を図から説明できない。推奨: 計器 build で hit・隣接失敗・cold・追加の pointer load を分けて記録し、性能上の結論は計器なし build の同時刻比だけで述べる。

### B3: 三つの perf job の同時投入には実行木の条件が抜けている

**重大度: must-fix。** 根拠: plan.md:80–82、md_23 一次資料 §9。md_23 では同じ計測木から六 job を並列 dispatch して五本が `rc=16` で止まり、同一 worktree からの dispatch は直列という規律が記録されている。三 node での同時実行という計画だけでは、この制約を満たさない。

放置すると、予定した六 round の perf 表が欠け、同時刻対照が成立しない。推奨: job ごとに独立した固定 tip の計測木を用意し、binary・patch hash を束縛して三 node に同時投入する手順を plan に書く。

### B4: 比較は問いに答えられるが、支持の判定語には限界がある

**重大度: should-fix。** 根拠: plan.md:80–82、md_23 一次資料 §5.1。12 cell × 五腕 × 六 round の同一 job・round・cell 内の stock 比と post/B 比は、「更新中心の比がどこまで戻るか」に直接答える。腕の回転も順序効果を抑える。一方、md_23 と同じ格子には評価草稿の主 cell（ro95・GC 100 µs）と A/A 腕がなく、草稿の「予備的に支持」は出せない。node 差は各対を同一 node 内で作れば比からある程度除けるが、node ごとの結果も残す必要がある。

放置すると、一次資料で探索段の「支持」や node をまたぐ絶対 throughput の改善を言い過ぎる。推奨: 比の六点と node 別内訳を図に残し、結論を今回の格子における回復幅に限定する。perf、COUNT、trace の別 build・別 run は plan の方針どおり維持する。

### B5: node 時間の算術は正しいが、上限判定の対象が狭い

**重大度: should-fix。** 根拠: plan.md:82、md_23 一次資料 §8、request-common.txt:22–27。引用した成功 job の和は `308 + 247 + (518+518+521) + 85 + (254+32) = 2,483 秒` で正しい。約 3,000 秒という予想も 2 node 時間未満の概算としては妥当。ただし md_23 の全投入実績は失敗・変異・test を含む **4,034 node 秒**であり、新しい壊し、B2 診断、追加 build の所要は 2,483 秒に入っていない。

放置すると、一次資料の「合計 2 node 時間未満」の事前判定が本走以外の投入を落とす。推奨: smoke 後の estimate には予定する全計算 node job を列挙し、その合計で 7,200 秒と比較する。現時点で超過が確定したとは言えない。

### B6: B2 の仮説は列挙されているが、一走の識別規則がない

**重大度: should-fix。** 根拠: plan.md:55–64、md_23 一次資料 §3.3。T1・T2 には既存の committed 事象がそれぞれ 67・4,331 件あり、各一走でも材料は得られそうである。しかし plan の五仮説は相互排他的でなく、「どの観測ならどれを棄却するか」と event の read→validation→commit の結合キーが未定義。status は途中で変わるので、単独のスナップショットでは PENDING の飛ばしと後の ABORTED 化を区別できない。

放置すると、診断ログは増えても「validation に止められなかった機序」が未確定のままになる。推奨: 結果前に事象 ID、各時点の status と版 generation、ro/update、validation の開始版・到達版を結ぶ規則と、仮説ごとの予測表を固定する。該当事象がゼロなら未識別と記す。

### B7: 図の修正と COUNT v1 の読取廃止が衝突する

**重大度: should-fix。** 根拠: plan.md:68–74、md_23 一次資料 §5・§6。fig-write の欠落は **md_23 の既存図が待ちを描いていない**ことだが、plan は新 aggregate で旧 COUNT `schema_version=1` を読めなくしてよいとする。これでは現行の生成器から md_23 の既存値を使った修正版を再生成できない。

放置すると、旧図の欠陥が残るか、旧 commit の道具だけが再生成経路になる。推奨: v1 の必要な待ち・保持 field だけを局所的に読めるようにするか、旧 aggregate から修正版を固定生成して一次資料に生成手順を残す。汎用互換層は要らない。42 bucket の新 schema は snapshot 計器の目的に限って実装する。

### B8: 所有外の変更と、sha 検索の一般化

**重大度: should-fix。** 根拠: request-md37.txt:22–29、request-common.txt:15–20、brief の scope・DW-O09、plan.md:44,74,88–99。依頼の所有欄には `tools/plotting/plot_vhash_cicada_hot_block.py` と `orchestrator/tests/test_plot_vhash_hot_block.py` が明記されていない。brief が作図を所有へ追加したことは、依頼の所有範囲を広げる根拠にならない。condition gate、materializer、共有テストへの変更も所有外であり、plan の「新 macro なし・既存 build 経路」で済むなら削るべきである。また brief の「五 file の変更前 SHA 先頭16桁の git grep が零件」は、その文字列による静的参照が見つからなかった事実に限られる。path 参照、短縮 hash、生成済み manifest、追跡外 artifact に依存がないとは言えない。

放置すると、patch・図・検査の変更範囲を取り違え、成果物の再現経路を見落とす。推奨: 所有外の図とそのテストは親が依頼の所有を確認して扱い、gate などは実際に失敗した箇所だけ局所修正する。SHA 検索結果は「検索した五 file・表記・追跡範囲で零件」と記す。

## 総括

B-post は CAS を長い書き区間から出す有効な一設計点だが、10万 cycles の待ちが消える量も ro95 の利得も実測前には決まらない。五腕の対比較は依頼の主問に答えられる。実行前に、独立計測木による同時投入、全 job を含む node 時間、B2 の識別規則、旧図の再生成経路、所有範囲を修正するのがよい。静的検査のみで、build・test・計測は実行していない。
