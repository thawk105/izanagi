## 概要

多版同時実行制御 (MVCC) は、実行中の transaction (以下 tx) から見えうる旧版を回収できない。最古の実行中 tx の時刻で回収境界を決める設計では、
長い tx が 1 本あるだけで、その開始より後に不要になった版まで回収が止まる。本稿は、実行中の tx の時刻を、既に読んだ版がすべて見え続ける範囲で
後の時刻へ進め (前進)、その前進を**確かめてから確定し、確定した後にだけ** GC に公開する保護下限 (floor) へ反映する機構を示す。
前進の確認 → 確定 → 公開の順序を 1 段でも崩すと GC 安全か直列化が破れることを小さいモデルの反例で示し、読み取りを終えて待つ型の長い tx について、
「floor を上げる前進の確認を始めた後は新しく読まない」条件の下で、**抽象仕様の上で**論理的な GC 安全と直列化が成り立つことを紙の上で論証する。
Cicada の試作のコードをその仮定で照らすと、書き込み検査の走査中に版が回収されうる箇所など 3 つの不成立が見つかったので、定理は試作の安全へは移さない。
CCBench の Cicada に既定で挙動を変えない patch として実装した予備評価では、読み取りの後に 10 ms 待つ長い tx がいる YCSB で、
前進先を「既読の可視区間に収まる最大の時刻」(E-max) にすると、偏りの無い負荷と中程度の偏り (zipf 0.6) の負荷で回収境界の遅れが縮んだ
(zipf 0.6 で 19.5 → 10.0 ms)。強い偏り (zipf 0.9) では E-max の効果は小さいが、前進できず commit できないと確定した tx を安全点で早く終える方策を E-max に足すと、
遅れがさらに縮んだ (zipf 0.9 で 19.6 → 15.2 ms)。どちらも計器入り build の未検証の診断値で、throughput の差は検出できなかった。
版を読むコストを下げるために直近の版を手元に置く配置 (仮称 VHash の hot block) は、Cicada の外の微小計測では速かったが、Cicada の中では throughput を上げなかった。

**図の読み方。** 上段が本稿の扱う問題の連鎖、下段が本稿の機構である。点線は「前進を保護下限へ反映すると、回収境界がその tx の旧時刻から離れうる」ことを表す。
**図から読み取ってはならないこと:** 矢印は論証のつながりで、効果の大きさを表さない。前進が常に成り立つわけではない (§6.4)。

MVCC の GC は、実行中の tx が見るかもしれない版を残し、誰からも見えなくなった版だけを回収する。多くの実装は「実行中の tx の時刻の最小」を回収境界にする
(Hekaton 2013、Cicada 2017 の境界規則。md_9 §5.1 の K17)。この規則の下では、長い tx が 1 本走り続けると境界がその tx の時刻に止まり、
後から上書きされて不要になった版まで回収できない。製品の公式文書もこの構造を書いている (§2.1)。

既存の対処は、読んだ製品文書の範囲では、長い側を終わらせる・待つ時間に上限を置く・長い側の snapshot を失効させる・書き込み側を遅らせる、のどれかで、
何かを諦める (md_27 §3)。境界の内側にある不要な途中版を掃除する区間 GC (Steam・HANA・vDriver) は版の列を短くするが、回収境界そのものは最古の実行中 tx に縛られたまま残る (§6.10、§7 の (d))。
本稿が狙うのは別の道である。長い tx が**時刻を動かしてよい tx** (固定 snapshot を約束していない read-write tx) であれば、
その tx の時刻を後へ進めても、既に読んだ版がすべて新しい時刻でも見えるなら、tx の結果は変わらない。前進した tx は古い時刻の版を必要としなくなるので、
その前進を GC に伝えれば境界が進みうる。

ただし「前進を GC に伝える」だけでは安全にならない。前進の確認が済む前に保護下限を上げると、まだ要る版を GC が回収する (§4.4 の反例)。
確認が済んでも、公開の後に新しく版を読むと、その版は確認に覆われない (§4.3 の条件 RA)。さらに実装では、commit の書き込み検査が版の列を 1 つずつ辿る間に、
公開した floor のせいで辿り先の版が回収されうる (§4.3.1)。本稿の中心は、この**確認 → 確定 → 公開の順序と、それが成り立つ条件**である。

**本稿の貢献 (範囲つき):**

1. 実行中の tx の前進を、確認 → 確定 → 公開の順で GC の保護下限へ反映する機構 (§3)。この機構は、OpenAlex・arXiv・DBLP を事前登録した検索式 N01〜N05 で調べた範囲
   (OpenAlex と arXiv は 2026-09-29 取得、DBLP は 2026-09-28 の全件書き出し。取得時刻の全文は §7) と読んだ原典の範囲では見当たらなかった (本文未取得の 5 本を除く)。目的と境界規則は既知である (§7)。
2. 順序の各段が要ることを示す小さいモデルの反例 (§4.4) と、読み取りを終えて待つ型の tx について、抽象仕様の上での論理的な GC 安全と直列化の論証 (§4.3、条件つき)。
   長い tx を「読み続ける型・読み終えて待つ型・固定 snapshot の型」に分け、それぞれで何が言えるかを表にした (§2.3)。
   あわせて、論証の仮定を Cicada の試作のコードで照らし、**どこで仮定が崩れるか**を具体的な実行列で示した (§4.2・§4.3.1)。
3. CCBench の Cicada への inert patch 実装 (§5) と、回収境界の遅れを縮めた予備的な観測、強い偏りで効かない理由と、早い abort を足した方策の観測 (§6、すべて未検証の診断値)。
4. 負の結果: 直近の版を手元に置く配置 (hot block) は Cicada の中では throughput を上げなかった (§6.7)。比較相手 Cicada に見つかった実装上の欠陥 (read-only の commit が GC の公開を止める、ほか 4 件) は本案の成果と分けて書く (§6.8・§6.9)。

## 2. 問題: 長い transaction が回収境界を止める

![GC 境界・公開間隔・回収時年齢・論理生存版数 (md_2、計器入り build の観測)](../../2026-09-29/vhash-cicada-version-measure/figures/gc_lifetime.png)

**図の読み方 (md_2 の図 3)。** 上から回収境界の年齢・公開の間隔・回収時の年齢・論理的な生存版数を、GC 間隔ごとに並べた。色が長い tx の型である。
**言えること:** 読み取りの後に待つ長い tx があると、境界の年齢と公開間隔が伸びる向きである (md_2 §0 項 4: 10 ms 待機で境界年齢 p50 が 32 µs → 32768 µs の bucket、
論理生存版数 1.03e6 → 1.41e6)。**言えないこと:** 計器入り build の観測で性能値ではない。境界年齢は timestamp 空間の値 (clock boost を含む) の 2 倍刻みの bucket 上界である。

### 2.1 実運用で起きていること

md_27 は製品の公式文書・技術資料 38 頁と論文・資料 10 本を読んだ (md_27 §1.1・§6)。論文の動機づけに使えるのは次の範囲である。

- 最古の実行中 tx が回収境界を決める tx 型の GC (PostgreSQL・MySQL InnoDB・SQL Server・TiDB 6.1.0 以降・Aurora MySQL) では、長い tx が回収を止めると公式文書に書かれている。
  時間型の GC (Oracle・Spanner・YugabyteDB・CockroachDB) では通常の読み取りについて回収は止まらず、代わりに長い読み取りが失敗する (md_27 §5.1 の M1)。
- 回収が止まると容量・性能・可用性が悪化する (M2)。**ただし研究側の症状の数値は、読んだ 10 本の範囲ではすべて固定 snapshot の読み手 (下の C1) の実験の値である** (md_27 §0 項 4・§4)。
- 問題が実運用で起きている頻度の根拠は、HANA の 1 システムの統計 (408,664 query 中 6 cursor が 1 時間超) だけである (M3)。
- 読んだ 10 製品系と HANA の範囲では、既存の対処は「長い側を終わらせる」「待ち上限で強制前進」「snapshot の失効」「書き込み側を遅らせる」のどれかである (M4)。

**本稿の動機の穴。** 本案が縮める「読み取りを続ける長い read-write tx」(下の C2) と「読み終えて待つ tx」(C3) が回収境界をどれだけ止めるかの数値は、読んだ外部資料に無い (md_27 §8)。
評価で自分で示す必要がある (T-2916。D2322 項 1 は、評価で構成 D より T-2930 系と T-2916 を先にするとした)。本稿は「長い tx は頻繁に起きる」とも「本案は C1 の症状の数値の分だけ縮める」とも書かない。

### 2.3 型ごとに、何が言えて何が言えないか

**この表が本稿の主張の範囲の正本である。** 構成 E の成果 (§4.3 の定理と §6 の観測) を「読み続ける長い tx 全般」へ広げない。また、抽象仕様についての定理を試作の安全へ広げない。

| 型 | 本稿の前進の契機 | 直列化について言えること | GC 安全について言えること | 実物で観測したこと (すべて未検証の診断値) | 言えないこと |
|---|---|---|---|---|---|

## 3. 方式: 確認 → 確定 → 公開の順序

```mermaid
flowchart LR
  subgraph T["tx T の側 (安全点または cold に入る read)"]
    t0["前進先 t′ を選ぶ<br/>(既読の可視区間に収まる最大 ほか)"] --> t1["既読版すべての rts を<br/>t′ 以上へ上げる"]
    t1 --> t2["版の列を観測し直し<br/>既読版が t′ で見えるか確かめる"]
    t2 -->|全部見える| t3["確定: T の時刻 := t′"]
    t2 -->|どれかが見えない| tf["時刻も floor も変えない"]
    t3 --> t4["公開 (別の step):<br/>floor := max(floor, t′ 以下の値)"]
  end
  subgraph G["GC の側"]
    g1["境界 B := 実行中の tx の<br/>floor の最小"] --> g2["後続の確定版が B 以下にある版だけを回収"]
  end
  t4 -.-> g1
```

**図の読み方。** 左が前進する tx の手順、右が GC の手順である。点線は「公開した floor を GC が境界の計算に使う」ことを表す。
**図から読み取ってはならないこと:** この図は構成 E の安全点での前進 (§3.3) の形で、構成 C のアクセス駆動の前進 (§3.4) は現行では右へ公開しない。
右の「境界 B := floor の最小」は抽象仕様の 1 step で、Cicada の leader はこれを thread ごとに非原子的に読む (§4.3.1)。

### 3.1 用語

- **時刻 (候補時刻) c_T:** tx T が読むときに使う timestamp。前進すると後の値になる。
- **floor f_T:** T が GC に「この時刻より古い版は要らない」と公開している値。GC は実行中の全 tx の floor の最小を回収境界 B にする。
  Cicada では各 thread の `ThreadRtsArray` と leader の `MinRts` に当たる (md_26 §2.3 の読み替え: f := ThreadRtsArray − 1、B := MinRts − 1)。
- **既読版:** T が既に読んだ版。前進しても、新しい時刻でその版が「見える版」(その時刻以下で最大の、aborted でない版) のままでなければならない。
- **前進の確認:** 既読版の rts を t′ 以上へ上げ、**その後に**版の列を観測し直して、各既読版が t′ で見えるか確かめること。
- **回収:** 版 y を版の列から外すこと。確定版 y を回収してよいのは、同じ key に確定版 z があって y.wts < z.wts ≤ B のときだけ (md_4 の R10、Cicada の `gc_versions`)。
  ABORTED の版はいつでも回収してよく、PENDING の版は回収しない (md_26 §2.1。Cicada の実装には PENDING を除く検査が無く、stock と試作では floor の条件から導けるだけである、md_36 §2 の RC 行)。
- **判定 D (確定した abort):** read-only でない tx の read set のどれかについて、既読版より新しく自分の現在の時刻より古い committed / deleted の版が版の列にあること。
  pending は含めない (md_31 §2、D2320 項 1)。D が真なら、その tx の commit の既読検査は成功しない (小モデルの有限範囲、§4.4)。

### 3.2 前進先の選び方: 可視区間

版 v が見える時刻の区間を I(v) = [b(v), e(v)) と書くと、既読版の集合 R_T が同時に見える時刻の区間は、下限 L_T = max b(v)、上限 U_T = min e(v) (v ∈ R_T) で、
L_T < U_T のときだけ共通の時刻がある (出典メモ §9 の記法。同じ形のモデルは Hekaton 2011 が Begin / End として実装に使っている、md_1 §8.1)。
**これは read 集合の整合の必要条件であって、更新 tx 全体の commit 条件ではない** (書き込み側の制約・一意性・並行する writer は別に要る)。

```text
時刻  →   t1    t2    t3    t4    t5    t6    t7    t8
既読 A    [===========================)                  A の見える区間 [t1, t6)
B の版          B@t2        B@t4  B@t5        B@t7  B@t8
                └── cold ──┘      └──────── hot ─────────┘
T の現在              ^t3

固定          : t3 のまま → B@t2 を読む          → cold を辿る
今へ前進      : t8 へ進む → B@t8 を読む          → A が見えない (t8 は [t1, t6) の外)
最小の前進    : t5 へ進む → B@t5 を読む          → A も見える、cold を避けられる
区間内の最大  : t6 の手前へ進む → B@t5 を読む    → A も見え、時刻はより新しい
```

**図の読み方。** 既読の版 A が t1 から t6 の手前まで見えているとき、4 つの前進先の帰結を並べた記号の例である (例の上の帰結で、一般の性質ではない)。

| 前進先の方策 | 定義 (md_21 §2、md_31 §2) | 本稿での扱い |
|---|---|---|
| 今 (E-now) | 自 thread の時計から作る厳密に新しい時刻 (cap) | 構成 E の初版 (md_14)。強い偏りではほぼ失敗する |
| 区間内の最大 (E-max) | 上端 U があれば min(cap, below(U))、無ければ cap。旧時刻・公開済みの時刻以下なら前進先なし (`no_room`) | **構成 E の主な腕** (D2315)。評価計画の §5.5 の当てはめでも p\* = c (= E-max) になった (md_34、D2325) |
| (追加の方策 c) E-max + 早い abort | E-max の要求が `no_room` を返したときだけ判定 D を評価し、真なら abort | **E-max とは別の腕として書く** (md_31、D2320 項 2)。前進先の選び方ではなく、前進できない試行の扱いを足したもの |
| (参考の方策 b) 早い abort だけ | 前進せず、待機の各 slice で D を評価し、真なら abort | 単独では採らない (D2320 項 2)。回収境界がほとんど縮まない (§6.4) |
| 最小の前進 (C-min) | 先頭 K 版の最古の確定版の直後の時刻 | **構成 C の既定** (D2287・D2315) |
| 部分前進 (C-partial) | 目標に届かなくても現在より新しければ進む | 構成 C の別腕 (完了率が上がらない限り既定にしない、D2315) |

上端 U は、各既読版について版の列の先頭から既読版まで辿ったときの「既読版の直上の aborted でない版」の wts の最小である。below(U) は U − 1 以下で下位 8 bit が自 thread 番号の最大の時刻である (md_21 §2)。
**U は pending の版も含む**ので、`no_room` は「commit できないことが確定した」ことを意味しない (md_31 §3.3)。

**新規性についての注意。** 「最新でない版を選べる」「前へ進んで既読と両立する旧版を読む」こと自体は既知である (SI-STM 2006、CockroachDB 2020。md_9 §5)。本稿はこれを貢献に数えない。

### 3.3 待機の安全点での前進 (構成 E) — 擬似コード

読み終えて待つ型の tx は、待機中に新しい read が無いので、アクセス駆動の前進 (§3.4) は発火しない (md_6 §5.1)。構成 E は、GC が公開を待っているときに、
待機中の tx 自身が待機の安全点で前進を試す形 (md_10 の SP、D2290) を Cicada に入れたものである。

```text
// 待機中の tx T が、待機を 100 µs に刻んだ各安全点で呼ぶ (md_14 §2)
procedure SAFEPOINT(T):
  if not (GC 間隔が経過 and T の GC flag が 0): return        // GC の要求がない
  t' := CHOOSE_TARGET(T)                                       // §3.2。E-max なら既読の可視区間に収まる最大
  if t' が無い or t' <= max(T.ts, 公開済みの時刻):              // no_room: 前進先がない
      SET_GC_FLAG(T); return                                   // flag だけ立てる (E-hb と同じ)
  if not PRECHECK(T, t'):                                      // 既読と write set の事前確認 (早期判定、rts は書かない)
      SET_GC_FLAG(T); return                                   // 失敗: T.ts も floor も変えない
  // (1) 確認: rts を上げてから観測し直す (順序が逆だと割り込みを見逃す、§4.4)
  for v in T.read_set: v.rts := max(v.rts, t')                 // CAS-max。rts は減らない
  fence (seq_cst)
  for v in T.read_set:
      if VISIBLE(v.key, t') != v or 可視の位置に他 tx の PENDING がある:
          SET_GC_FLAG(T); return                               // 失敗: T.ts も floor も変えない
  // (2) 確定
  T.ts := t';  T の未設置の書き込み版の wts := t'
  // (3) 公開: 確定の後の別の step で、成功したときだけ
  T.floor := max(T.floor, p)   (p <= t')                        // 抽象仕様 E の公開 (md_26 §2.1)
      // Cicada の実装: ThreadWtsArray := t'、ThreadRtsArray := max(旧, t' - 1) (CAS-max)。
      // md_26 §2.3 の読み替え f = ThreadRtsArray - 1 では p = t' - 2 に当たる
  SET_GC_FLAG(T)

// GC の leader (Cicada の既存の手順のまま)
procedure GC_LEADER():
  if 全 worker の GC flag が立った:
      B := 実行中の各 tx の floor の最小                         // Cicada: MinRts (と MinWts) を公開。B = MinRts - 1 と読み替える
                                                               // 実装は thread ごとに Wts と Rts を 1 つずつ読む (非原子的、md_36 §2)
      境界 B を公開し、flag を下ろす

// 各 worker が自分の確定した版について (Cicada の gc_versions のまま)
procedure RECLAIM(key):
  確定版 z で z.wts < MinRts のものがあれば、z より古い版を切り離す   // md_4 の R10 と同じ形。status は問わない
  // 抽象仕様 E の規則 (§3.1): 確定版 y は同じ key の確定版 z と境界 B で y.wts < z.wts <= B のときだけ、
  // ABORTED の版はいつでも回収してよく、PENDING の版は回収しない (md_26 §2.1)
```

**擬似コードの読み方。** 確認・確定・公開の行は md_14 が作り (D2295)、md_21 は `CHOOSE_TARGET` (目標時刻の計算) だけを変えた (md_21 §2)。
回収そのもの (`gc_versions`) は変えていない (md_14 §2)。どの経路で戻っても GC flag は立てる (前進を試さない E-hb と同じ)。
確認の段で失敗した前進は rts を上げた跡を残すが (rts は減らない、md_13 の仮定 A7)、時刻と floor は変えない。
floor の行は抽象仕様 E (§4.3) の形で書き、Cicada の実装の値はコメントに分けた。md_26 §2.3 の読み替えでは、実装の slot (ThreadRtsArray = t′ − 1) と
読み替えた floor (t′ − 2) の差は 1 である。md_10 のモデルの公開値 p = t′ と実装に当たる p = t′ − 2 は 2 違うが、どちらも p ≤ t′ を満たすので定理の条件 (PUB) の形は変わらない。
**この擬似コードは commit の手順を書いていない。** commit の書き込み検査は stock のままで、公開した floor はその走査を守らない (§4.3.1 の (a))。

### 3.3.1 追加の方策 c: 前進できず、commit できないと確定した試行を安全点で終える

```text
// md_31 の方策 c (fallback)。上の SAFEPOINT の no_room の分岐だけを置き換える (D2320 項 2)
  if t' が無い or t' <= max(T.ts, 公開済みの時刻):              // no_room
      if not T.is_readonly and DOOMED(T):                      // 判定 D (§3.1)。共有状態を書かない
          return ABORT                                         // 待機ループを抜け、既存の tx.abort() を通って再実行する
      SET_GC_FLAG(T); return

procedure DOOMED(T):
  for v in T.read_set:
      最新の版から v まで辿り、途中に status が committed か deleted で v.wts < wts < T.ts の版があれば true
      v に辿り着けなければ false (abort しない側)
  return false
```

**読み方。** 方策 c は前進先の選び方 (E-max) を変えず、前進できない試行のうち commit できないと確定したものだけを終える (md_31 §2)。
中止した tx は既存の `tx.abort()` を通り、その `mainte()` が stock と同じ条件で GC flag を立てるので、回収境界への効果は flag を立てる経路と同じである (md_31 §2)。
**判定 D の健全性は小モデルの有限範囲でだけ確かめた** (§4.4)。対象は現行 genome (`INLINE_VERSION_PROMOTION=0`) と read-only でない tx で、前進成功後の遷移は W* を仮定する (D2320 項 4)。
AggressiveGC との違いは §7 の (d) に書く。

### 3.4 cold に入る read での前進 (構成 C) — 擬似コード

```text
// 読み続ける型にも届く、アクセス駆動の前進 (md_6 §2 の仕様 v2)
procedure READ(T, key):
  p := T.ts で見える版の、版の列の先頭からの位置 (先頭 = 1)
  if p > K and T が read-write で未 abort、scan 中でなく、insert・delete・scan をしていない:  // 論理 K 境界 = cold に入る (U1)
      t' := CHOOSE_ACCESS_TARGET(T, key)        // C-min: 先頭 K 版の最古の確定版の直後の時刻
      if t' があり PRECHECK(T, t') が通る:       // 既読の一致と write set の制約。rts は書かない
          T.ts := t'; 未設置の書き込み版の wts := t'; 探索の開始位置を捨てる
          // floor は公開しない (GC の保護は旧時刻のまま)
  stock と同じ探索で版を選ぶ
// commit は stock の validation を最終の T.ts で走らせる (最終保証)
```

**読み方。** 構成 C の前進は read 相だけで行い、最終保証は stock の validation (PENDING 版の設置 → 既読版の rts を上げる → 既読の一致を確かめる → 書き込み側の検査) を最終の時刻で走らせることに置く (md_6 §2)。
前進の後に insert・delete・scan を呼ぶと abort する。**現行の構成 C は floor を公開しない** ので、単独では回収境界を動かさない (md_6 §2 の表の GC 行)。
前進の事前確認は既読版の rts を上げずに見え方だけを照らすので、md_13 の確認 (R5) には当たらない。md_13 の系 6 の範囲では、commit での全既読の検証が最終の条件になる (md_36 §2 の A5 行)。
F は同じ発火条件で abort して再実行する対照である。

### 3.5 戻れる段階と戻れない段階

```mermaid

  state "保護を公開" as s3
```

### 4.1 小さいモデルで分かったこと (md_4・md_10)

md_4 は、キー 2・tx 2〜3 (+ GC 1 thread)・操作 1〜3・逐次一貫なメモリの固定 10 場面で、選択的前進の規則を 1 つずつ崩した版の全 interleaving を探索した (md_4 §6・§7.3)。
md_10 は、待機中の tx が安全点で前進して公開する形 (SP) を足した固定 6 場面を探索した (md_10 §5・§8)。

| 規則 | 崩した版 | 結果 (固定場面の範囲) | 出所 |
|---|---|---|---|
| 書き込み側の直前版の rts 検査は PENDING を越えて最初の確定版まで (R9′) | v0 (直前版 1 つだけを検査) | 閉路の反例、30 step | md_4 §7.3 |
| 既読版の rts を上げてから可視を確かめる (R9 の順序) | U1v | 閉路の反例、26 step | md_4 §7.3 |
| 確定してから GC へ公開する (R6 → R7) | U3a | GC 違反、3 step | md_4 §7.3 |
| 後続の確定版を根拠に回収する (R10) | U4 | GC 違反、2 step | md_4 §7.3 |
| 確定してから公開する (SP) | UG1 (確認の前に公開) | GC 違反、4 場面で 5〜31 step | md_10 §8 |
| 確定で保護下限を外さない | UG2 (確定時に floor を無限大) | GC 違反、2 場面で 10・21 step | md_10 §8 |
| 公開の後は公開した floor より古い時刻へ戻らない | UF1 | GC 違反、2 場面で 22・47 step | md_10 §8 |

仕様 v1 は 10 場面すべてで反例なし (md_4 §8)、SP の健全版 24 構成はすべて反例なし (md_10 §5.1)。**反例なしは固定場面の初期状態からの全 interleaving に限る。**
これらの模型には、境界の非原子的な読みと thread の floor の下降は入っていない (md_36 §7)。

### 4.2 直列化の論証 (md_13) と、その仮定の実装での状態

```mermaid
sequenceDiagram
  participant R as reader T
  participant V as 既読版の列
  participant W as writer W
  R->>V: 既読版の rts を s まで上げる
  R->>V: 版の列を観測し直して可視を確かめる
  W->>V: 自分の PENDING 版を設置する
  W->>V: PENDING を越えて最初の確定版まで rts を調べる
  Note over R,W: どちらの順で割り込んでも<br/>reader の観測か writer の検査が相手を見る
```

**図の読み方。** md_13 の論証の芯である 2 つの順序 (reader は rts を上げてから観測し直す、writer は設置してから PENDING を越えて最初の確定版まで検査する)。

**定理 (md_13 §0 の要旨):** 固定したキー集合への point read / update だけを行い、逐次一貫なメモリと md_4 の原子性の下で、md_4 仕様 v1 (R9′ を含む) に従う tx について、
commit 時の検証を通って確定した tx の依存グラフ (ww・wr・rw) は閉路を持たず、確定時刻の順がそのまま直列化の順になる。
**ただし仮定 A1〜A11 を前提とする** (時刻の一意性 A2、rts の単調性 A7、検査が触れる版が論理的に回収されていないこと A9、途中入場が無いこと A10 など)。
発火の契機と前進先の選び方には依らない (md_13 の系 5)。

**この定理の地位。** 対象は小モデル仕様 v1 で、Cicada の実装にも試作にも届かない (D2292)。Cicada の「PENDING を待つ」書き込み検査は条件 W* を置いた補題 2′ で同じ結論になる (md_13 §5・§7)。

**仮定を Cicada 実装で照らした結果 (md_36 §2、計測で使った設定の YCSB の read-write tx が既存キーへ point read / update する経路について)。** 「手順」と「保証」を分けて書く。

| 仮定 | 手順 (コードの順序・形) | 保証 (定理が使う性質) | 補足 |
|---|---|---|---|
| A1 逐次一貫、版の列の原子的な観測、R9′ の走査は 1 step | 満たさない | 満たさない | 版の列は next pointer を 1 つずつ読み、status は版ごとに順に書く。観測の線形化点を置く実装向けの置換補題が要る (md_36 §8 の N4) |
| A2 異なる tx は同じ時刻を持たない | — | **満たさない** | abort の後の時計の上乗せが実時刻より先に出たまま次の tx が commit すると、その次の begin で時刻が進まず、同じ thread の続く 2 つの tx が同じ時刻を持ちうる (md_36 §5)。確かめた経路では空振りの abort になる。閉路の完成列は作れていない |
| A5 確認は rts を上げてから観測し直す | stock の commit と構成 E は満たす。**構成 C の前進は満たさない** (rts を上げない) | 記憶順序と寿命は別 | 構成 C は commit で全既読を最終時刻で検証し直す (O1 を採らない) ので、md_13 の系 6 の範囲では結論に効かない。構成 C の実装の直列化の認定ではない |
| W* (設置の後に降順に走査、待機の後に status を読み直す、止まった版の rts をその時点で読む) | **満たす** | **到達と寿命は満たさない** | 並行する GC が版の列を切り離して delete / 再利用するので、「設置前からある版を必ず訪れる」の物理的な保証が無い。構成 E では論理的にも崩れる (§4.3.1 の (a)) |
| A7 rts は max で更新され減らない | 満たす | 版の再利用をまたいでは満たさない | 再利用 (`REUSE_VERSION=1`) で同じアドレスの rts が 0 に戻る |
| A9 補題 2 が扱う版は版の列に残る | — | md_26 が定理 G に置き換え | 構成 E では W* の走査中に反例がある (§4.3.1 の (a)) |
| A10 途中入場なし | 満たさない | — | tx は随時 begin する。md_26 が開始 floor の条件 FS-a/b/c に置き換えた (§4.3) |
| 記憶順序 (読み手と書き手の相互見落とし) | — | **判定できない** | C++ の模型では除けない実行がある。x86 では除かれる見込みだが、対象バイナリの命令列は確かめていない |

**論文に書ける文** (md_36 §0.1): 「stock Cicada の書き込み検査は、条件 W* の局所手順に対応する。並行する回収の下での到達と参照の寿命は示していない。」
**書けない文:** 「stock・C・E は論証の全仮定を満たす」(md_36 §0.1)。

### 4.3 GC 接続の論証 (md_26): 読み終えて待つ型について

md_26 は、§3.3 の手順を抽象化した仕様 E (待機の安全点で tx 自身が確認 → 確定 → 別 step で公開し、公開した floor を下げず、回収は後続の確定版を根拠にする) について、
途中入場する tx と古い境界での回収も含めて次を示した。**主語は抽象仕様であり、Cicada 実装と物理的な非接触は主張しない** (md_26 §0、D2319)。

- **定理 G (論理的な GC 安全):** 回収された版は、回収の時点で実行中の tx にも、その後に始まる tx にも、読み・確認・commit の検証・書き込み検査・前進先の計算のどれでも「必要な版」として現れない。
- **定理 S (直列化):** 構成 E の確定した tx の依存グラフは閉路を持たず、確定時刻の昇順が直列化の順を与える (md_13 定理 4 の仮定 A9 を、定理 G から導いた補題 A で置き換えたもの)。
- 前進先 t′ については一意で現在の時刻より大きいことしか使わないので、E-max にも E-now にも同じく当てはまる。

論証の芯は 3 つの不変条件である (md_26 §4)。

| 不変条件 | 中身 | 何を守るか |
|---|---|---|
| (I0) | GC が読んだどの境界 B も、実行中のどの tx の floor 以下 | 境界が実行中の tx を越えない |
| (I1) | 各実行中の tx で floor ≤ 候補時刻 | 以後の読みの時刻で見える版 |
| (I2) | 各実行中の tx の各既読版について、他 tx の確定した後続版の wts はすべて floor より大きい | 既読版そのもの |

**前提の条件 (md_26 §3.1) と、Cicada のコードでの状態 (md_36 §2・§4)。** 初稿では「未確認」と書いた欄を、md_36 の照合で置き換えた。判定の範囲は md_36 §1 の経路 (計測の設定の YCSB) に限る。

| 条件 | 中身 | stock | 構成 E の試作 |
|---|---|---|---|
| FS-a | 登録時の floor ≤ 開始時刻 | 満たす (非 0・非 wrap の範囲) | 同じ |
| FS-b | 登録時の floor ≥ それまでに GC が読んだどの境界 (途中入場) | **導出上満たす** (thread の Wts・Rts がともに非減少なので、非原子的な集計でも古い値は新しい値以下、md_36 §4.1) | **満たさない場合がある** (thread の floor が前進で上がり次の begin で下がるので、非減少が崩れる、md_36 §4.2)。ただし前進しない thread 0 (leader) の floor が境界を上から抑えるので、既読版の回収に至る列は作れない (md_36 §4.3) |
| FS-c | 登録の後に他 tx が設置する版の wts はすべて開始 floor より大きい | 満たす (thread の時刻が非減少・非 wrap の範囲) | 同じ |
| PUB | floor が変わるのは公開だけで、成功した確認・確定の後に確定時刻以下へ上げる | 前進なし | 満たす (`gc_advance` の成功時だけ Wts := t′ の後に Rts := max(旧, t′ − 1)。失敗時は何も公開しない) |
| CAND | 時刻が変わるのは確定 (上げる) と公開前の取り消し (試行前へ戻る) だけ | — | 満たす (成功経路) |
| **RA** | **floor を上げる前進について、その確認を始めた後は外部 read をしない** (公開の後も、確認の成功と公開の間も) | — | **計測した待機型の長い tx では満たす** (全 read と update の後に待機ループへ入り、ループの後は commit だけ)。安全点の API 自体は以後の read を禁じないので、API 一般では判定できない |
| RC | 回収は後続の確定版を根拠にするだけで、PENDING 版は回収しない | **一部だけ満たす** (確定版を根拠に下を切る形は対応するが、PENDING を除く検査はコードに無い。stock では floor の条件から導ける) | 同じく一部。試作でも floor の条件から導けるが、thread の floor が下がりうる一般の E では古い読みで崩れうる |
| 境界の読み | GC は実行中の tx の floor の最小を 1 step で読む (md_26 §2.1) | 満たさない (thread ごとに Wts と Rts を交互に読む非原子的な読み)。FS-b の導出で代わりにする | 満たさない。thread の floor の下降と合わせて §4.3.1 の (b) |

**条件 RA がこの論証の射程を決める。** md_26 は、RA を崩すと floor だけでは既読版を守れない列を 2 つ紙の上で作った (探索はしていない)。
列 X1 は「floor を上げた後に新しく読む」、列 X2 は「確認に成功してから公開するまでの間に新しく読む」で、どちらも新しく読んだ版が確認に覆われず、
並行する writer の確定版を根拠に回収されうる (md_26 §8)。したがって定理 G は、**読み終えてから前進して公開する型 (§2.3 の 1 行目) の抽象仕様には届き、読み続けながら floor を上げる型には届かない。**
読み続ける型の前進 (構成 C) は現行で floor を公開しないので、この定理を必要としないが、回収境界も動かさない (§2.3 の 2 行目)。

**Cicada で既読版を守っている暗黙の不変条件との対応。** stock Cicada は「tx 開始時の下限を tx の間変えない」ことで既読版を物理的に守っている (md_14 §3.3)。
md_26 はこれを FS-c (開始時に (I2) を成り立たせる) と PUB (floor を上げるのは確認に成功した時刻以下へだけ) の 2 つに分けて明示した。§4.4 の P5 は PUB を破った実例である。

### 4.3.1 構成 E の試作が定理の外にある 3 箇所 (md_36、D2326 項 3)

md_36 は、試作のコードの手順を抽象仕様の step に対応させたうえで、対応が崩れる箇所を 3 つ挙げた。**どれも紙の上の実行列で、実走・探索・判定器では観測していない。頻度も分からない** (md_36 §9)。

**(a) 書き込み検査の走査中に、止まる予定の版が回収されうる (W* × GC)。** 計測した長い tx (10 read + 1 update の後に待機し、待機中に前進して floor を t′ − 1 へ上げ、その後に commit する) の手順に、
update の key が既読キーと異なる場合にそのまま乗る (md_36 §0 項 1・§3.2)。

```mermaid
sequenceDiagram
  participant T as T (長い tx、update の key x は既読でない)
  participant L as キー x の版の列
  participant Z as Z (T より前から活動、時刻 z は x の確定版 c と t′ の間)
  participant G as leader と Z の thread の GC
  T->>T: 安全点で t′ へ前進に成功し、floor を公開する
  T->>L: commit: 自分の版を設置 (その next = c)
  T->>L: 書き込み検査の走査: 手元の pointer が c を指す
  Z->>L: 自分の版を T の版と c の間へ設置する
  Z->>L: 自分の検査は c で通り、確定して回収の候補に積む
  G->>G: leader の round が進み、境界が z を越える
  G->>L: Z の版を根拠に c を切り離し、解放か再利用
  T->>L: 手元の pointer で c の status と rts を読む
```

**図の読み方。** md_36 §3.2 の列を、時刻の値を記号にして描いた。stock と構成 C では T の floor が開始時の値のままなので、境界は T の floor を越えず、Z の版は回収の根拠にならない。
構成 E では T が floor を t′ − 1 へ上げているので、境界が z を越えうる。成り立つには、T が c を指してから c の rts を読むまでの間に leader の round が少なくとも 2 つ進む必要がある (T の thread の中断など)。
計測の設定 (`REUSE_VERSION=1`) では、切り離された版は別の書き込みに作り直され、T はその版を見て、他人の PENDING を待つ・rts 0 で通る・next の空 pointer を辿る、のどれにもなりうる (md_36 §3.2)。
**直列化について:** 有効な版の参照と逐次一貫の下では、この列から閉路は作れない。しかし T は解放・再利用後の値を読むので、その議論は当てはまらず、閉路が無いとも言えない (md_36 §3.2)。
md_26 の条件 RA は外部 read だけを縛り、commit の書き込み検査の走査は縛らないので、RA を満たす計測の workload でもこの列は残る (md_36 §3.3)。

**(b) 境界の読みと開始 floor の条件 FS-b。** 構成 E では、前進の成功で thread の floor が上がり、同じ thread の次の tx の begin が無条件に floor を書き直すので、thread の単位で floor が下がる。
leader の集計は非原子的なので、leader が前の tx の高い floor を読んだまま、新しい tx の低い floor を読まずに境界を公開しうる (md_36 §4.2)。
試作では thread 0 (leader) が長い thread にならず前進しないので、thread 0 の floor が境界を上から抑え、既読版の回収に至る列は作れなかった (md_36 §4.3)。
どの thread も前進しうる一般の構成 E では、既読版が回収される列 G1 が完成する (md_36 §4.4)。**thread 0 の抑えは試作の構成に偶然ある性質で、構成 E の規則ではない。**

**(c) 時刻の重複 (A2)。** stock の時刻生成は同じ thread の続く 2 つの tx に同じ時刻を返しうる (§4.2 の A2 行)。前進しない begin は stock の生成器を使うので、C・E も同じである (md_36 §2)。

**直し方の候補と、並走中の修理。** md_36 §6 は (a) に 3 つの候補 (書き込み key を持つ tx は floor を公開しない、公開値を抑える、走査中の版を epoch などで保護する) を、(b) に 2 つの候補 (leader の集計を一貫した snapshot にする、thread 0 の抑えを規則にする) を挙げた。
(a) の穴を再現して最小の修理を入れる wave が並走中である。【空欄: md_39 (構成 E の書き込み検査の走査中の回収の再現と最小の修理)】
md_36 §6 のとおり、(a) の候補のうち「書き込み key を持つ tx は floor を公開しない」を採ると md_14・md_21 の長い tx (1 update を持つ) は前進の対象から外れるので、その腕の GC 改善は修正版で測り直さないと主張できない。
**過去の計測値は当時の観測として残す** (規律 7、D2326 項 5)。md_14 の保持版検査は、待機中の tx の既読版を待機の前後で照らすもので、書き込み検査の走査中の版も次の tx の既読版も見ない (md_36 §6)。

**早い abort の判定 D の健全性 (md_31 §3.1)。** md_31 は、key ごとの物理的な版の列・GC の切り離しと再利用・前進・validation を持つ小モデルで、
「D が真になった状態から到達する全状態で、その tx の validation の既読検査が成功しない」(SOUND) を調べた。validation は D と別の関数で、保存した later_ver_ から鎖を辿る (Cicada の validation の写し)。
2 tx の全列挙 115 状態と 3 tx の予算内列挙 1,446 状態で違反なし、壊した判定 2 種 (pending を含める・既読版自身を含める) は validation 成功までの反例を出した。
**有限の範囲での確認であって証明ではない** (読む key は 1 個、writer は 1〜2 tx、前進成功の遷移は W* を仮定、md_31 §3.1)。

**判定器には、この型の誤りが見えない。** P5 と E-now の壊しでは、直列化の判定器の巡回は 0 のまま、保持版検査だけが変化を検出した (md_14 §3.3、md_21 §5)。
今の計装は読んだ時点の wts を控えるだけで、早すぎる回収はそれが巡回を作らない限り判定器の対象外である (md_24 §1 項 3)。§4.3.1 の (a) の列も、判定器と保持版検査のどちらの照合範囲にも入らない (md_36 §6)。

### 5.1 土台と比較相手

- **CCBench の Cicada、pin C (`68106660`)。** VHash の測定と検査はすべて pin C の上に patch を重ねて行った。CCBench 側の修理 (build 不能の修理 G、削除経路の修理 2 本、promotion・insert・abort の修理 4 本) は local branch にあり、push は人間の手番である (D2308・D2310・D2327)。pin は C のままである。
- **比較相手は「CCBench の Cicada (pin C) を md_11 の観測最良設定で」と書く。** 観測最良は `BACK_OFF=0, INLINE_VERSION_OPT=1, INLINE_VERSION_PROMOTION=0, REUSE_VERSION=1, WRITE_LATEST_ONLY=0` で、
  既定の設定より rr5・rr50・rr95 で 2.15〜4.54 倍速い (md_11 §6、正しさ未検証の診断値)。md_14・md_18・md_21・md_22・md_23・md_31 はこの設定を土台にした。md_6 の土台は CMake 既定の Cicada である (md_11 §10)。
- **主比較の相手は、この最良設定に ro-gcflag 修正 (`patches/cicada-ro-gcflag-variant.patch`) を入れたものとし、修正なしの stock は修正の効果を分ける対照として同じ round に置く** (D2322 項 2)。
  修正の効果 (a) と本案の効果 (b) は別の行で書く (§6.8)。**起点までの計測 (§6) は修正なしの stock を土台にしており、修正入りを土台にした本案の計測はまだ無い。**
  30 秒走行の追加計測は見積りを示し、1 タスクの合計が 2 node 時間以上なら投入前にユーザー確認を取る。最良設定の正しさの確認 (md_20、D2302) を修正入りの長時間走行へ無条件に転用しない (D2322 項 2)。

### 5.3 hot block (構成 B) の patch

`cicada-vhash-hot-block-variant.patch` (md_23、pin C の 3 file、421 行) は §3.6 の hot block を入れる。`read_internal` の第 1 段 (対象時刻より新しい版を飛ばすループ) だけを置き換え、

### 5.4 検査の計装

- **直列化の判定器:** Cicada の trace (`instr-cicada-trace*.patch`) を izanagi の判定器に掛ける (D2279・D2294)。性能用 build には入れない (観測者効果の分離)。
- **保持版検査:** 待機の開始で既読版の pointer・wts・status を控え、終わりに照合する (md_14 §3.3)。判定器に見えない早すぎる回収を見るための検査である。書き込み検査の走査中の版と次の tx の既読版は見ない (md_36 §6)。
- **GC の計器:** 回収境界の遅れ (leader が 10 µs ごとに取る等間隔標本)・論理生存版数・版の保持時間。計器入りの別 build で取り、性能値には使わない (md_14 §4.1)。

### 6.4 強い偏りでは E-max だけでは縮まず、早い abort を足すと縮んだ (md_21・md_31)

![E 腕の失敗理由 (md_21、未検証の診断値)](../../2026-09-29/vhash-forwarding-target-policy/figures/target-policy-reasons.png)

**図の読み方 (md_21 の target-policy-reasons)。** 失敗理由ごとの panel で、縦軸は理由の回数 / 要求 (%)。E-now の失敗はほぼすべて既読不一致、E-max は既読不一致 0 で `no_room` と書き込み制約、
E-max-once は 2 回目以降の要求が `once skipped`。

- zipf 0.9 では E-max でも遅れ −1.0 ms (20.4 → 19.4 ms) に留まり、E-max の要求の約 75% が `no_room` だった (条件別には 40〜78%) (md_21 §1 項 3・§4.3)。
- 「今」への前進 (E-now・md_14 の E) は zipf 0.9 で試行の 0.05〜0.27% しか成功せず、失敗の 88〜96% が既読不一致だった (md_14 §1 項 2)。
  md_14 の逐語: 「md_6 の zipf 0.9 の条件だけで試していたら、U0 の効果は見えなかった。」

**`no_room` の読みの訂正 (md_31 §3.3、D2320 項 3)。** 初稿は md_21 §4.3 に従い、`no_room` を「(a) 一度成功した後で上端が動かない」と「(b) 既読のどれかが上書き済みで validation での abort が決まっている」の混合と書いた。
md_31 が `no_room` を前進の成功前 / 成功後に分けて数えると、zipf 0.9 の方策 c の計数 rep で成功後が 2,465〜6,829 回、成功前が 944〜1,353 回で、**`no_room` の大半は前進に一度成功した後の再要求だった。**
また上端 U は pending の版も含むので、成功前の `no_room` でも pending が abort すれば validation は通りうる。**`no_room` は abort の確定ではなく、確定は判定 D (committed / deleted の witness) で言う。**
方策 c の計数 rep 15 本で、D が真になった総回数は成功前の `no_room` の回数以下 (13 本で等しく、2 本で 1 回少ない) だった。計数は D の真を成功前 / 成功後に分けていないので、言えるのは総回数の上限だけである (md_31 §3.3)。

```mermaid
  req["E-max の要求"] --> nr{"前進先があるか"}
  nr -->|ある| ok["確認・確定・公開"]
  nr -->|無い no_room| cnt["計数だけ成功前 / 成功後に分ける<br/>(判定の分岐ではない)"]

```

**図の読み方。** md_31 §2・§3.3 の手順である。方策 c は `no_room` を返した要求のたびに、前進の成功前か成功後かを問わず D を評価する (§3.3.1 の擬似コードと同じ)。
成功前 / 成功後の分けは、T-2930 の要求で足した計数の分け方で、判定の分岐ではない。観測としては、D が真になった総回数は成功前の `no_room` の回数以下で、評価回数 (成功後を含む) よりずっと少ない。計数は D の真を成功前 / 成功後に分けていないので、成功後の `no_room` で D が真になった割合はこの計数からは分からない (md_31 §3.3)。
**図から読み取ってはならないこと:** 各分岐の割合は図に書いていない。上の計数を見る。

### 6.6 長い tx の完了: 操作数型と待機型を分ける (md_6・md_21・md_31)

**初稿の「長い tx の完了率はどの腕でも 0.03% 以下」は操作数型 (1,000 操作の many_ops) の値である。** 待機型の長い tx (10 read + 1 write の後に 10 ms 待つ) は stock でも完了する (md_31 §6)。2 つを混ぜて書かない。

**図の読み方 (md_6 の図)。** 行 = workload、列 = (1) C の成功率と試行数、(2) 試行の内訳と試行前の除外、(3) stock 比の throughput、(4) 長い thread の commit と F の abort。

**(2) 待機型 (読み終えて待つ型): stock でも完了し、高い偏りでは待機のごく初めに既読が上書きされて落ちる (md_31)**

![長い tx の commit/秒・試行/秒・完了率 (md_31、計器なし build の記述値)](../vhash-early-abort-policy/figures/md31-early-abort-long.png)

**図の読み方 (md_31 の md31-early-abort-long)。** 横軸 = skew。上段 = 長い tx の commit/秒、中段 = 試行/秒、下段 = 完了率 (commit / 試行)。計器なし build の記述値。
早い abort の腕 (b・c) は試行/秒が増えるので、完了率は分母で下がる。**言えないこと:** rep の揺れが大きく、腕の間の差は判定できない。

| 待機 10 ms・GC 10 µs (md_31 §5.3、計器なし build、rep 中央値) | 完了率 stock / E-hb / E-max / b / c |
|---|---|
| skew 0.6 | 0.719 / 0.720 / 0.755 / 0.718 / 0.741 |
| skew 0.8 | 0.250 / 0.347 / 0.375 / 0.360 / 0.419 |
| skew 0.9 | 0.125 / 0.126 / 0.172 / 0.057 / 0.067 |
| skew 0.95 | 0.057 / 0.056 / 0.099 / 0.019 / 0.033 |

- **rep の揺れが大きい。** skew 0.9 の完了率の rep の値は stock 0.125 / 0.216 / 0.070、E-max 0.134 / 0.176 / 0.172 で、同じ条件の別 job (backoff job) では stock 0.075・E-max 0.051 だった。

- **何が待機型を落とすか。** skew 0.9 では長い tx の試行の約 43〜46% で、待機中に既読が committed の版に上書きされ、commit できないことが確定した (E-hb・E-max の shadow)。

### 6.7 hot 配置 (構成 B): Cicada の中では throughput を上げなかった (負の結果)

![hot 配置 (構成 B) の同時刻の stock 比 (md_23、未検証の診断値)](../../2026-09-29/vhash-hot-block-cicada/figures/fig-k.png)

**図の読み方 (md_23 の fig-k)。** 横軸 = cell (read-only 指定率 × GC 間隔、と通常 YCSB の rr5・rr50・rr95)、縦軸 = 同じ round の stock に対する比、菱形 = 6 round の中央値、点 = 全 round、
縦線 = 最小〜最大、破線 1.0 = stock。**言えること:** read-only 95% の 3 cell は 1.0 付近、更新中心の cell は大きく下回る。**言えないこと:** 判定の上限は indeterminate で、perf job が 2 node に分かれ node 差と K の効果を分けていない (md_23 §4)。

**Cicada の外では速かった。** 1 キー分の版選択を 1 thread の latency で測った微小計測 (md_5) では、LLC 外の最新版選択で連続配置 scalar が散在 linked の 0.55〜0.84 倍、
K=8 の深さ 7 で 0.12 倍だった (md_5 §0)。利益は配置 (連続であること) から来ており、この AVX2 実装の SIMD からは来ていない (md_5 §0 項 4)。

![K=8 の深さ別の版選択の時間 (md_5、Cicada の外の微小計測)](../../2026-09-29/vhash-hot-block-microbench/figures/fig-depth.png)

**図の読み方 (md_5 の fig-depth)。** 1 キー分の版選択を 1 thread・固定 core・依存連鎖の latency で測り、K=8 で目的の版の深さを 0 から 12 まで動かした (深さ 8 が hot と cold の境界)。
LLC 外で深さ 0→7 のとき、散在 linked は 187→1,269 ns、連続配置 scalar は 144〜152 ns でほぼ一定だった (md_5 §0)。
**言えないこと:** Cicada への組み込み・並行更新・many-core の throughput は測っていない (md_5 §1)。単位は 1 thread の latency で、下の 48 thread の throughput とは直接比べられない。

**Cicada の中では上がらなかった。** md_23 は 48 thread・100 万 tuple・zipf 0.9・3 秒で、12 cell × 5 腕 (stock、K = 1, 2, 4, 8) を同じ job・同じ round で回し、6 round の比を取った (md_23 §4)。

| cell (md_23 §5、K/stock の 6 round 中央値) | K=1 | K=2 | K=4 | K=8 |
|---|---|---|---|---|
| read-only 95%・GC 10 µs | 0.985 | 0.980 | 0.987 | 0.989 |
| read-only 95%・GC 100 ms | 1.000 | 0.999 | 1.006 | 1.011 |
| rr95 | 0.978 | 0.978 | 0.957 | 0.927 |
| rr50 | 0.229 | 0.262 | 0.231 | 0.229 |

- 評価計画の草稿 v1 §5.5 の探索段の語では、read-only 95% の 12 組すべてが「予備的に不支持 (差なし)」、read-only 0%・rr5・rr50 の全組と read-only 50% の一部が「予備的に不支持 (悪化)」、
  rr95 の K=8 が「判定不能」、主 cell (read-only 95%・GC 100 µs) が「欠測」である。md_34 の独立の再計算も md_23 §5.1 の語と全 48 組で一致した (md_34 §15.4)。
  **この設計には A/A 腕が無いので、仮に効いていても「予備的に支持」の語は出なかった。** 「差なし」は「探索の 6 対で対数比がすべて ±ln(1.10) 以内」の意味で、「効果は 10% 未満」とは書かない。
- **K\* = 1** (md_34 §15.4、D2325 項 2)。選択に使う cell (read-only 95%・GC 10 µs) で K = 1, 2, 4, 8 の throughput の反復中央値がすべて最大の K = 4 と同点だったので、規則により最小の K になった。確認段の H1 は B_1 対 A で比べる。【確認段で差し替え】
- 上がらなかった理由として md_23 が計器の数から挙げたのは 3 点である (因果の内訳ではない): (a) 深い読みが hot より奥に多い (GC 100 ms・read-only 95% で、第 1 段が飛ばした版数は 16 版以上が 21%)、
  (b) 浅い読みは元々速い (GC 10 µs では 0 版が 82%)、(c) hot を保守する key ごとの排他の待ち (更新中心の cell で 1 update commit あたり約 9.8 万〜11.8 万サイクル) (md_23 §1 項 3・4・§6)。
- 正しさ: 3 つの trace cell × 5 腕の 15 走すべてで巡回 0。hot を壊した版 2 本はどちらも巡回として検出された (md_23 §1 項 5・6)。

![更新中心の cell の比と書き区間の保持 (md_23、未検証の診断値)](../../2026-09-29/vhash-hot-block-cicada/figures/fig-write.png)

**図の読み方 (md_23 の fig-write)。** 上段 = 更新中心 4 cell の stock 比、下段 = read-only 0%・GC 10 µs の計器 build での hot の書き区間の**保持**サイクル / update commit。
**図の限界:** 下段は保持だけで、主因の「待ち」を描いていない (待ちは md_23 §6 の表で読む。図の修正は T-2927)。

**hot 配置の伸びしろの上限 (md_29 §0 項 3、計器入り build の機会量)。** 負荷の空間を広く測ると、版の列の先頭より奥を読む割合は、read-only 側 (古い snapshot) と、最良設定での高偏り・多操作の update read で大きかった
(層 O の水準別中央値で、全 read の位置 ≥ 1 の割合 h1 は、長い read-only tx を 1 worker が続ける条件 batchR で 0.51〜0.53、read-only 指定率 50・95% で 0.49〜0.52。update read の位置 ≥ 1 の割合 u1 は、層 S の最良設定・長い tx なしで skew 0.99 のとき 0.10〜0.22)。

指標は throughput だけ (commit あたりの LLC miss は測っていない) (md_23 §11)。**本稿は「hot 配置は効かない」「H1 は棄却された」とは書かない。**
書き込み側の排他を CAS の外へ出す設計は並走中である。【空欄: md_37 (構成 B の書き込み側の排他を CAS の外へ)】

D2322 項 2 はこれを受けて、主比較の相手を修正入りとし、stock を同じ round の対照として並べると決めた。本稿の比較の行は次の形で書く。

  長い read-only の rts が境界を押さえる分で、固定 snapshot の型 (C1) なので本案の対象外でもある (§2.3)。表の (a) の効果には数えない。

### 6.9 比較相手の較正と正しさ

![J2 確認値: GC 間隔と throughput (md_11、正しさ未検証の診断値)](../../2026-09-29/vhash-cicada-baseline-tuning/figures/vhash-cicada-j2.png)

  既定を相手にすると GC 側の伸びしろが既定の公開の遅さの分だけ大きく見えるので、比較相手は最良設定とし、既定設定の値を伸びしろの根拠にしない (D2329 項 2)。

- 修理後の branch では、promotion 有効の 8 genome が YCSB 32 走行と TPC-C 16 走行で巡回 0 (上限 indeterminate)、TPC-C が完走、ASan の報告 0 だった (md_32 §0 項 6)。

  promotion 有効の 8 genome を較正の空間へ戻す再計測は別 item である (md_32 §11)。初稿 §8 の「promotion 有効の 8 点は…原因未特定」は当時の記録として初稿に残し、原因の帰属はここで追記する (付録 E)。

### 6.10 評価の残りと、比較対照としての区間 GC

- **確認段の走行:** 評価計画の草稿 v1 (`docs/vhash-evaluation-preregistration-draft.md`、未発効) は主要な族 m = 19 の比較を、1 cell = 同じ job・同じ node で全構成を 1 回ずつ回す round を 14 取る設計で置いている。

- **動機の数値:** 読み取りを続ける長い read-write tx と読み終えて待つ tx が回収境界をどれだけ止めるか (T-2916)。D2322 項 1 は、評価で構成 D より T-2930 系 (早い abort) と T-2916 を先にするとした。
- **第 2 段の候補領域 (md_29 §4、D2329):** 負荷の空間のふるい分けで、事前登録した規則が (a) 読み比率 5%・batchR、(b) read-only 指定率 95%・thread 12、(c) 読み比率 5%・batchR・skew 0.9〜0.97、(d) batchR・read-only 指定率 0% の 4 領域を選んだ。

![層 S: 偏りと版探索の深さ (md_29、計器入り build の観測)](../vhash-workload-space/figures/skew_depth.png)

**図の読み方 (md_29 の skew_depth)。** 偏りの格子 (層 S: skew 0.5〜0.99 × 読み比率 × 長い tx の有無と型) で、版探索の位置の分布を並べた。**言えないこと:** 計器入り build の観測量で、性能や「VHash が速くなる」ことは言っていない。
「上限」は機構が完全に働いた場合でも取れる機会の大きさで、実装したときの効果ではない (md_29 §0)。

**比較対照としての区間 GC (md_18、D2323・D2324)。** 回収境界の内側にある不要な途中版を掃除する区間 GC は既知の方式である。最古と 2 番目の境界の間を掃除する最小形は vDriver の Fig 6(c)・定義 3.4・定理 3.5 に、
実行中の全 timestamp でどこからも見えない途中版を掃除する一般形は Steam §4.3・HANA の定義 1・vDriver の定理 3.5 に書かれている (md_18 §2)。
「区間 GC を入れた Cicada」は比較相手として審査で問われるので、md_18 は Cicada に最小形と一般形を試作した。

![区間 GC の試作の throughput と stock 比 (md_18、未検証の診断値)](../../2026-09-29/vhash-interval-gc/figures/interval-gc-a-throughput.png)

**図の読み方 (md_18 の interval-gc-a-throughput)。** cell ごとの throughput と stock 比。長い read-only tx の cell に `*` 印がある。**言えないこと:** 3 rep の小差は優劣未確定。
この試作は書き込みを tuple lock の下で挿入するので、比は install の費用と剪定の効果の和である (md_18 §8)。

- **試作は安全な物理再利用までは作れなかった。** 外した版を再利用する変種は 4 回の修正の後も異常終了したので、計測したのは「版を鎖から外すが、走行中は再利用しない」変種である (md_18 §3.4、D2323 項 4)。
- **この試作の遅さは試作の install の経路の費用で、区間 GC 一般の費用ではない。** throughput は stock 比で最小形 0.062〜0.692・一般形 0.025〜0.684 だったが、剪定が 0 回の長い read-only の cell でも最小形は 0.062 (rr50) まで落ち、
  install の lock 待ちが thread 時間の 8〜72% を占めた (md_18 §1 項 4・§6.3)。md_18 自身が「この試作 (tuple lock の install、再利用なし) は Steam・HANA の実装費用を代表しない」と書く (md_18 §7 の 4)。
  **本稿は区間 GC を「遅い」とは書かない。** 比較には、同じ install の経路で剪定しない対照 (mode 3) を先に取る (md_18 §9 の 1)。
- **鎖・hop の腕間差は書き込み量の差と交絡している。** 区間 GC の腕は install 数が stock の 1/1.3〜1/34 なので、hop 総数・鎖上の版数の減少を剪定の効果とは読めない (md_18 §1 項 5)。
- **長い read-only tx の cell では、試作は何もしなかった。** 同じ欠陥 (read-only の commit が GC flag を立てない、§6.8) で境界が公開されず、剪定の足場が無かった (md_18 §6.4)。stock はこの型で鎖上 2.17〜2.22 GB・RSS 6.0 GB (rr50) に達した。
- **更新型の長い tx (1〜10 ms) では、stock の鎖はそもそも長くなかった** (鎖上 192〜234 MB、キーあたり 1 版の基準は約 192 MB。md_18 §6.3)。
- **正しさ:** 正常 3 腕の 30 走行はすべて巡回 0。事前登録した壊し正例 (長い read-only tx の cell) は試作が剪定しないので発火 0 で不成立だった。事前登録外の cell での検出は補助として別に数える (md_18 §5、D2324)。
- **本案との分担 (md_18 §7 の見積り、測っていない)。** 安全な解放の条件 (外した時点で走っていた全 tx の終了) は長い tx 自身が塞ぐので、区間 GC が正しく実装できても、外した版の bytes は長い tx の終了まで返らない (Steam も解放を所有 tx の解放まで遅らせる)。
  鎖を短くして探索を減らすのが区間 GC、境界を動かして stock の GC の回収を早めるのが U0、という分担になる、と md_18 は見積もる。
  長い read-only tx の場面では、区間 GC と ro-gcflag 修正を重ねるのが先である (md_18 §7 の 2)。本稿は区間 GC と本案を重ねた計測を持たない。

関連研究は 5 系に分けて書く (md_1 §12 の 4 系に md_9 §8 が (e) を足したもの)。

- **(a) timestamp を後から決める系:** TicToc、Sundial、MaaT、Lomet ほか 2012。commit 時や read ごとに位置を決めるが、実行中の前進を回収境界へ反映しない。
  TicToc は旧版の wts を history buffer に置いて既読値を救う timestamp history を持つ (TicToc §5.3)。既定の設定に含まれるが、著者自身が §6.4 で
  "the timestamp history optimization does not provide any measurable performance gain in either workload." と報告している (md_1 §4)。TicToc を比較相手に挙げるときは、この効果が原典で測れなかったことを併記する。
- **(b) 衝突で直列化の順序を動かす系:** Shirakami、Rebirth-Retire、MV3C、Morty、実時間 DB の区間調整の系譜 (md_9 の K19)。
- **(c) 版の配置の系:** Cicada、HyPer、vDriver、LeanStore、Freitag 2022。時刻・可視区間・更新頻度から版の置き場所を決める。本稿の cold 契機はこの向きを逆にした形である。
- **(d) GC と長い tx の系:** Steam、HANA、CIDR 2021、AggressiveGC と、PostgreSQL・Oracle ほかの製品文書 (md_27)。
  - 途中版の剪定 (区間 GC・EPO) は版の列を縮めるが、長い snapshot から見える版は残す (md_27 の M5)。区間 GC の最小形は vDriver、一般形は Steam §4.3・HANA の定義 1・vDriver の定理 3.5 にあり、
    3 本とも「reader が辿っている途中版を物理的に解放しないための安全条件」は、読んだ範囲では独立に述べていない (md_18 §2)。本稿の比較対照としての試作は §6.10 に書いた。
  - AggressiveGC (CCBench 論文 §7.3、提案のみで実装なし) は、active または将来の tx が読む必要のある版の保持と read の成功を諦め、read が失敗した tx を新しい timestamp で再実行させる (md_31 §9)。
    本稿の方策 c との違いは、**回収を先に決めて tx を殺すか、tx が既に commit できないことを確かめてから境界を放すか**である。方策 c は commit できる tx を失わない (小モデルの範囲) 代わりに、
    上書きされていない長い tx が押さえる分は残し、それを前進で補う。方策 c は AggressiveGC を置き換えない (md_31 §9、D2320 の却下理由)。
  - Steam は active tx に必要な版を残し、回収境界は最古の active tx に縛られたまま境界内の不要な途中版を剪定する。長い tx の timestamp・snapshot は変えず、abort もしない。
    HANA の運用上の対処は、問題の cursor・tx の強制終了か版のディスク退避である (md_31 §9)。
  - 長い tx を走らせる worker は回収用の epoch を実行中に定期的に更新すべきという指摘は Silo にある (直列化位置は動かさない、md_9 の K18)。
  - Cicada 既存の EarlyAborts は書き込み・削除の時点で commit できないと分かった tx を止めるもので、待機中の既読の上書きは見ない (md_31 §2・§9)。
- **(e) 実行中に前進して既読を保つ系:** CockroachDB の read refresh (実行中に読み取り時刻を後へ進め、読んだキーに間の更新が無いことを確かめて続行する)、
  SI-STM / LSA (有効区間と重なる最も新しい版を選び、区間を縮める)。SI-STM は、位置を新しい側へ寄せる動機の 1 つに古い版を早く捨てられることを挙げるが、
  測定実装は旧版を個数で制限し、tx の位置を保護下限として公開する規則は読んだ節に無い (md_9 の K20)。

**本稿が既知として扱うもの (md_9 §5):** 実行中の前進と前進時の既読の再確認 (CockroachDB 2020)、既読と両立する旧版の選択と、新しい側へ寄せて古い版を早く捨てるという動機 (Riegel ほか 2006)、
区間による位置の調整 (Lomet ほか 2012)、実行中の tx の時刻の最小を回収境界にする規則 (Hekaton 2013、Cicada 2017)、区間 GC (Steam・HANA・vDriver、md_18 §2)。

**新規性の範囲 (md_9 §7 の案 B の範囲文を写した):** 実行中に既読を保ったまま後へ進めた transaction の位置を、GC に公開する保護下限へ反映する機構 (前進の確定 → 保護下限の公開の順序を含む) は、
OpenAlex・arXiv・DBLP を事前登録した検索式 N01〜N05 で調べた範囲 (OpenAlex は 2026-09-29 09:51〜10:20 JST 取得、arXiv は同 09:49〜09:50 JST 取得、DBLP は Last-Modified 2026-09-28 20:23:37 GMT の全件書き出し) と
読んだ原典の範囲では見当たらなかった (本文未取得の 5 本を除く)。位置を新しい側へ寄せれば古い版を早く捨てられるという動機 (Riegel ほか 2006) と、
実行中の tx の時刻の最小を回収境界にする規則 (Hekaton 2013、Cicada 2017) は既知である。

- 本文未取得の 5 本は vWeaver 2021・Diva 2022・Bayer ほか 1982・Boksenbaum ほか 1987・OCC-TI 1997 で、図書館経由の取り寄せは人間の手番である (T-2895)。
- cold 契機 (U1) を述べる文には「OCC-TI 1997 を除く」を必ず同じ文に置く (md_9 §5.2)。本稿の構成 C の範囲文は md_9 §7 の案 C を正本とし、ここへは写さない。U1 を述べるときは、未実装の構成 D と区別する (D2322 項 1)。

- md_9 の主張文は「アクセス駆動の前進」を念頭に書かれている。**構成 E の安全点での前進を「読み取り後に待つ tx の保持を縮める」と書くときは、E の測定の範囲 (§6.1) を同じ文に置く** (md_9 §7 の使ってはならない言い方と、ストーリー §11.1)。

## 8. 限界

```mermaid
flowchart TB
  t2["読み続ける長い tx"] --> l2["前進は起きるが完了に結び付かない<br/>回収境界へ反映する論証が無い"]
  t3["読み終えて待つ tx"] --> l3["強い偏りでは前進先が無い試行が残る<br/>早い abort で一部を補う"]
  t1["固定 snapshot の読み手"] --> l1["前進の対象にしない<br/>rts が押さえる分は残る"]
  t4["止まった thread"] --> l4["代行による前進は<br/>対象外 (今後の課題)"]
  impl["Cicada の試作"] --> li["定理の仮定を満たさない箇所がある<br/>記録の水準が未実装"]
  base["比較相手"] --> lb["修理は local branch<br/>pin は C のまま"]
```

**図の読み方。** §2.3 の型ごとの限界と、実装・比較相手の限界を 1 枚にした。1 行目の問題を解いたことを、他の行まで解いたように書かない。

- **読み続ける長い tx (C2)。** 構成 C の前進は起きるが、操作数型の長い tx の完了率はどの前進先でも 0.03% 以下で、完了に結び付いていない (§6.6)。前進を回収境界へ反映する論証は条件 RA の外にあり、
  floor 以外の保護 (refs・epoch など) とその物理的な寿命の論証が要る (md_26 §11)。
- **強い偏り。** 読み終えて待つ型でも、zipf 0.9 では E-max の要求の多くが `no_room` になり、E-max 単独の効果は小さい。`no_room` の大半は前進に一度成功した後の再要求で、abort の確定ではない (§6.4)。
  方策 c は前進できず確定した試行を終えて遅れを縮めたが、上書きされていない試行が押さえる分は残る。判定 D の健全性は小モデルの有限範囲でだけ確かめ、実機の照合の検出力は示せていない (§4.4、md_31 §3.2)。
- **固定 snapshot の読み手 (C1)。** 前進の対象にしない。長い read-only の rts が境界を押さえる分は本案でも縮まない (§6.8)。
- **止まった thread (C4)。** 論文の対象に入れない (D2298・D2318)。md_16 §7.3 の文案を逐語で置く。

  > 本研究の前進は、待機中の transaction が安全点で GC からの要求を確かめられることを前提とする (評価に用いる CCBench の長い transaction は busy-wait で待つため、この前提を満たす)。sleep や preempt で完全に止まった thread の代わりに別の thread が前進させる設計 (代行による前進) は、小さなモデルの全探索で、descriptor の世代つき CAS が確定と公開を覆うこと、再開時に時刻を読み直すこと、代行する thread 自身が読み取り版を保護すること、失効させる場合は再開時に失効を確かめる前に読み取り値へ触れないことが必要だと分かった。ただし、止まった thread の静止を他の thread が代わりに宣言してよい条件は未検証であり、Cicada のように全 thread の静止を待って回収境界を更新する GC では、代行による前進は回収を進めない。代行による前進の実装と評価は今後の課題とする。

  併記: 安全点での前進を CCBench 自身の長い tx で評価するには、CCBench の待機ループ (`clock_delay`) に要求の確認を入れた安全点が要る。現行のループは要求を確かめない (md_16 §7.1、D2318 項 1)。
  本稿の構成 E は md_6 の試作が足した長い tx の待機を 100 µs に刻んで安全点を置いたもので、CCBench 自身の待つ型 (W5) ではない (§5.2)。
- **正しさの地位。** 論証はモデル仕様 v1 と抽象仕様 E についてである。**Cicada の試作は論証の仮定を満たさない箇所がある** (§4.2・§4.3.1): 書き込み検査の走査中に止まる予定の版が回収されうる (W* × GC)、
  境界の読みと thread の floor の下降で FS-b が崩れうる (試作では thread 0 の抑えで害の列は作れない)、同じ thread の続く tx が同じ時刻を持ちうる (A2)。
  加えて、版の列の原子的な観測 (A1)・記憶順序・版の ID と物理アドレスの分離は、実装向けの置換補題が無い (md_36 §8 の N4)。
  どの列も確定した tx の閉路までは完成しなかったが、解放・再利用後の版を読んだ実行には論証の前提が当てはまらないので、「直列化は壊れない」とも言えない (md_36 §0)。
  (a) の修理は並走中である (§4.3.1)。物理的な非接触 (回収済みの node の pointer を並行する走査が読まないこと、`REUSE_VERSION=1` での再利用) は主張しない。判定の上限は indeterminate で、中間案 M は未実装である (§4.5)。
- **進行保証。** 本稿は安全性だけを扱う。CAS は rts の CAS-max と版の設置に使うが、lock-free 性・進行保証・止まった thread の保護の解除は示していない。待ちが終わらない実行は「確定しない」として含むだけである (md_26 §11)。
  長い tx の完了率 (§6.6) は観測値で、進行保証の代わりにならない。
- **GC の効果の地位。** 回収境界の遅れと論理生存版数は計器入り build の値で、物理メモリの bytes ではない。`REUSE_VERSION=1` の pool は縮まない (md_14 §7)。本稿は「GC を改善した」とは書かない。
- **動機の数値。** 本案が縮める型 (C2・C3) の大きさの数値は外部資料に無い (§2.1、T-2916)。
- **比較相手。** 較正で探索できた空間は pin C で build できる 16 点である (§6.9)。promotion 有効の 8 点の巡回と TPC-C の異常終了は原因が特定され (前者は読み取り専用 tx の promotion、後者は promotion と無関係な `INLINE_VERSION_OPT=1` の insert の欠陥)、
  abort 時の use-after-free とともに CCBench の local branch で修理されたが、push と pin の前進は人間の手番で、pin C には入っていない (md_32 §12)。
  したがって pin C の上では OPT=1 の TPC-C を使えず (md_32 §12)、promotion 有効の 8 点は較正にも比較にも使っていない。本稿は「Cicada の最適化空間を全探索した」とは書かない。
  主比較の相手に入れる ro-gcflag 修正は variant patch で pin に入らない (D2322 項 2)。修正入りの土台での本案の計測はまだ無い (§6.8)。
- **区間 GC との比較。** 比較用の試作は安全な物理再利用が無く、install を tuple lock の下で行うので、方式の費用を代表しない (§6.10)。区間 GC と本案を重ねた計測も無い。
- **範囲。** 固定キーへの point read / update。範囲読み・insert・delete を含む tx は、試作では前進しない (前進の後に呼べば abort)。論証も範囲外に置く (md_13 §8、md_26 §11)。md_36 の照合も YCSB の経路に限り、TPC-C・scan・group commit などは読んでいない (md_36 §1)。負荷は YCSB だけである。

## 9. 結論

本稿は、実行中の tx を既読が見え続ける範囲で前進させ、その前進を確認 → 確定 → 公開の順で GC の保護下限へ反映する機構を示した。
順序の各段が要ることは小さいモデルの反例と Cicada の試作で実際に起きた破れで示し、読み終えて待つ型の tx について、抽象仕様の上での論理的な GC 安全と直列化を条件つきで論証した。
論証の仮定を Cicada の試作のコードで照らすと、書き込み検査の走査中の回収をはじめ 3 箇所で対応が崩れたので、定理は試作の安全へは移さない。
Cicada への予備的な実装では、偏りの無い〜中程度の偏りの負荷で E-max が回収境界の遅れを縮め、強い偏りでは前進できず commit できないと確定した試行を安全点で終える方策を足すと遅れがさらに縮んだ。
どちらも計器入り build の探索段の観測で、評価計画の語では支持を得ておらず、throughput の差は検出できなかった。直近の版を手元に置く配置は Cicada の中では throughput を上げなかった。

残る課題は、確認段の走行 (修正入りの比較相手の上での本案の効果、between-run floor を含む)、構成 E の試作の書き込み検査の走査中の回収の修理と、修理した試作での測り直し、境界の読みの一貫性、
記録の水準 (中間案 M) の実装、読み続ける型の前進を回収境界へ反映する保護の設計、そして本案が縮める型の大きさを示す測定である。【確認段で差し替え】
