## 所見

1. **must-fix — 禁止名は「参照」なら拒否されるが、「宣言」なら通る。** 現行パーサーの `name()` は型名と C++ キーワードを除く任意の識別子を許し、状態 field・ローカル変数・helper 名に使います（[silo_policy_grammar.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-lock-order-axis/orchestrator/campaign/silo_policy_grammar.py:149)、[同:210](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-lock-order-axis/orchestrator/campaign/silo_policy_grammar.py:210)、[同:252](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-lock-order-axis/orchestrator/campaign/silo_policy_grammar.py:252)）。したがって、表だけを差し替えるプラン（[plan.md:40](/work/1/SFC/tanab/dev-wave-jobs/dev-wave-lock-order-axis/plan.md:40)）では `OrderState` の field を `write_set_` や `result_` と名付けられ、仕様 §4.4 の「これらの名前を含む候補は拒否」に反します。`TRACE` という field は単独 compile と実 build でマクロ展開条件も異なり得ます。**影響:** 文法の受理集合と、台帳に記す禁止名の保証が仕様より広くなります。**対応:** 新 profile の全識別子宣言位置に禁止名検査を設け、参照・宣言・field・helper を別々に試してください。現物の名前解決では、未宣言の host 名の直接参照、他 namespace、`using`、operator 定義、default 引数、配列・pointer は拒否されます。上の抜け道だけで host オブジェクトへ到達するとは確認していません。

2. **must-fix — 文法の変異候補が検査したい層を変えない。** 「文法許可表へ `write_set_` を追加」という変異（[plan.md:84](/work/1/SFC/tanab/dev-wave-jobs/dev-wave-lock-order-axis/plan.md:84)）は、現行パーサーでは宣言名の許可表がなく、参照はスコープから解決します（[silo_policy_grammar.py:149](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-lock-order-axis/orchestrator/campaign/silo_policy_grammar.py:149)、[同:182](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-lock-order-axis/orchestrator/campaign/silo_policy_grammar.py:182)）。**影響:** 変異が生き残っても拒否テストの効力を判断できず、文法保証を誤って報告します。**対応:** 所見 1 の宣言名検査を実装した後、その検査だけを外す変異にし、検疫・compile に先取りされない入力で first rejection stage を確認してください。

3. **should-fix — `#error` はマクロの「未定義」も明示して確認する必要がある。** プランは ON 時に二つの値を要求します（[plan.md:66](/work/1/SFC/tanab/dev-wave-jobs/dev-wave-lock-order-axis/plan.md:66)）。`#if NO_WAIT_OF_TICTOC != 0` だけでは、未定義が 0 と評価されて通ります。既存 patch はこの点を `defined(...)` と値の両方で検査しています（[silo-function-policy-variant.patch:36](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-lock-order-axis/patches/silo-function-policy-variant.patch:36)）。**影響:** 供給漏れの build を前提成立として受理し得ます。**対応:** 両マクロについて未定義と不正値を別々に `#error` とし、各組合せを template test に入れてください。

4. **should-fix — 単独 compile の合格を骨格込み build の合格と区別する。** 予定する compile は header と候補を単独 TU に置きます（[plan.md:56](/work/1/SFC/tanab/dev-wave-jobs/dev-wave-lock-order-axis/plan.md:56)、[silo_policy_compile.py:95](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-lock-order-axis/orchestrator/campaign/silo_policy_compile.py:95)）。骨格 TU のマクロや名前との衝突は、この段階では分かりません。プランには統合 build があるものの（[plan.md:77](/work/1/SFC/tanab/dev-wave-jobs/dev-wave-lock-order-axis/plan.md:77)）、各提案文字列の gate は単独 compile 後に書き込みます（[plan.md:58](/work/1/SFC/tanab/dev-wave-jobs/dev-wave-lock-order-axis/plan.md:58)）。**影響:** gate 合格を「build 可能」と記録すると受理段階と報告値がずれます。**対応:** gate 合格は文法・単独 compile 合格と明記し、生死確認では hole 書き込み後の実 build 成否を別に記録してください。所見 1 の禁止名検査も、この差を縮めるために必要です。

5. **should-fix — UBSan harness の適用先を明記する。** プランは新 harness を作りますが（[plan.md:57](/work/1/SFC/tanab/dev-wave-jobs/dev-wave-lock-order-axis/plan.md:57)）、提案を通す gate の列は単独 compile までです（[plan.md:58](/work/1/SFC/tanab/dev-wave-jobs/dev-wave-lock-order-axis/plan.md:58)）。既存 harness も policy directory の `.cpp` を列挙する別入口です（[silo_policy_compile.py:158](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-lock-order-axis/orchestrator/campaign/silo_policy_compile.py:158)）。**影響:** 各候補を UBSan で検査したかのようにレポート・台帳へ記す恐れがあります。**対応:** 候補ごとの必須 gate にするか、手書き対照と test 用の検査だと成果物に明記してください。
