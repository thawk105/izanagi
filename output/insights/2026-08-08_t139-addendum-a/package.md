## R1. erratum を resolver / `PreregBinding` / 受領証へどう束縛するか

**事実。** 段 3 レンズ B が、erratum が「commit/blob 束縛されていない第 3 の権威」になりうると
指摘した。現行の `resolve_effective_preregistration` の署名は `core_ref` / `addendum_a` /
`addendum_b` しか受けないので、erratum を暗黙に読む resolver は署名の外から受理集合を書き換える。

**なぜ問題か。** 追補 A の exact-key の期待集合そのものを erratum が決めるため、
erratum が無検査だと「期待集合を後から差し替える」経路になる。
逆に erratum を追補 A の本文に埋めると、exact-key の**余剰 field 違反**になる。

**段 6 のレビュー 2 本が、初版の 2 点を独立に反証した。訂正を織り込んだ形で問う。**

- 訂正 1: 初版は「受理集合は狭い側へしか動かない」と書いたが**偽**である。
  literal な core は §14 で exact 13・§15 で exact 12 を同時要求するので、
  現在の受理集合は **`∅`** であり、erratum の適用は `∅` → `R13` の**受理拡大**である。
  承認は「拡大を承認する」ものとして扱う。
- 訂正 2: 初版の resolver 契約には**承認の trust root が無かった**。
  erratum blob と追補 A blob の digest を承認する canonical な manifest が無いと、
  producer が exact 13 key を持つ**未承認の追補 A′** (待機秒数や閾値だけ差し替えたもの) を
  `measurement_head` の祖先に置くだけで D234 の (iv)〜(vi) を満たす。

- 訂正 3 (焦点再レビュー): 初版の resolver 契約は「対象 core に一致する erratum が
  **ちょうど 1 件**でなければ失敗」としていたが、**R2(a) と R5(b) はいずれも同じ core への
  第 2 の erratum を選択肢に持つ。**singleton 契約のままだと R1(a) + R2(a) を裁定した瞬間に
  resolver が必ず失敗する。契約を **exact set** へ改めた。

**選択肢。**

- **(a) approval manifest + 承認済み erratum の exact set (推奨)。**
  canonical 台帳へ fold する approval manifest に、承認対象の追補 A と**全 erratum** の
  `(path, commit, sha256)`、適用順序、合成後 core の `composed_sha256` を逐語で持たせる。
  resolver は **manifest から** blob identity と `approval_fold_commit` を取得し
  (caller 引数・受領証からは取らない)、manifest の集合と解決できた集合が**完全一致**しなければ
  解決失敗とする。複数 erratum では `locator` が互いに重ならないことと合成後 digest の一致も要求する。
  erratum 側は散文でなく**要素数ちょうど 2 の構造化 operation 配列**とし、
  各要素に対象行の `old_sha256` (実測済み: `6e87b981…` と `b5e2c7b2…`) を持たせる。
  全文は `erratum-core-s15.md` §3 / §5。
- (b) erratum を resolver の**明示引数**として署名に足す (`errata=(commit, path, sha256)`)。
  → manifest を作らずに済むが、どの決定がその blob を承認したかを resolver が再導出できない。
  (a) と併用は可能だが単独では trust root にならない。
- (c) 一般の errata registry を作る。→ 将来の任意の core に適用できる汎用機構になり、
  「凍結文書の受理述語を後から書き換える」一般経路を開く。規律 2 の観点で不可。
- (d) 新しい core を起こす (別 study)。→ 最も保守的だが 2026-08-07 の裁定 11 件の再確認を伴う。

**親の推奨は (a)。**((b) は (a) の一部として自動的に満たされる。)

## R2. `a12` を「stress check」と呼び替えるか、cluster 効果込みの較正へ変えるか

**事実。** core §7 は「weak null の型 I 誤りは、同じ許容 schedule 集合を使う**事前 simulation で
較正する**」と書く。ところが段 3 レンズ A が、この simulation は cluster level の型 I 誤りを
較正していないことを反例つきで示した。

利用可能な raw は J=1 screen の 1 割当て分 (2 workload × 3 arm × 5 rep = 30 行) だけであり、
**割当て間 (cluster 間) の変動は 1 点も観測されていない** (core §17 が明記)。
レンズ A の反例: 未観測の cluster 効果 `P(U=a)=0.99, P(U=−99a)=0.01` を加えると
`E[U]=0` で weak mean null を満たすが、`J ≤ 13` の全 cluster が正側になる確率は
`0.99¹³ ≈ 0.878` あり、片側下限は高確率で正になる。この cluster 効果は J=1 データから識別できない。

**なぜ問題か。** 「較正した」と書くと、実際には保証していない性質を保証したことになる (規律 3)。

**段 6 のレビュー A が、初版の推奨だけでは閉じないことを示した。**
追補の中で「stress check」と呼び替えても、**core §7 が課した「較正する」という義務は消えない**
(D234 は追補による core の意味変更を禁じる)。したがって選択肢は次のとおり。

- **(a) core §7 の当該文へ第 2 の erratum を当て、義務を「事前固定 stress check」へ置換する (推奨)。**
  R1 の approval manifest と同じ機構に乗せ、operation を 1 つ足す。
  型 I 誤りの制御は `a11` の Hotelling / t / 非心 t が planning model のもとで与えるものとし、
  simulation は「事前固定した empirical stress model のもとで名目を超えないこと」の確認に留める。
  `addendum-a.md` の `a12` は既にこの限定を明記してある。
- (b) 追補の中で呼び替えるだけにする。→ **core §7 の義務が未達のまま残る。**
  レビュー A の判定は「R2(a) の呼び替えだけでは閉じない」。採らない。
- (c) 独立 cluster データを先に取ってから較正する
  (= pilot の前に、cluster 間変動を推定するための別 study を走らせる)。
  → 最も正しいが、割当ての追加と事前登録のやり直しを伴う。
- (d) cluster 効果を含む事前固定の分布族に対する worst-case 保証へ変更する。
  → 分布族の選び方自体に根拠が無く (観測ゼロ)、恣意的な族を選ぶと保証は見かけだけになる。
- (e) 新しい core を起こす。→ 最も保守的。

**親の推奨は (a)。**core §7 の逐語を変える行為なので、明示の裁定が要る。

## R3. primary 系列の正規の根と ordinal を `a13` へ移すか、`b03` のままにするか

**事実。** `a13` は `α_k = 0.05/[k(k+1)]`、本 study は `k=1` で `α₁ = 0.025` とする。
級数の総和は `0.05` なので**候補数上限 (`b01`) に依存しない**。
しかし core §14 は「累積台帳を束縛する正規の根の同定方法」を **`b03`** に置いており、
追補 B は本走の投入前 = **pilot の後**に凍結すればよい。

**なぜ問題か。** `α_k` は `k` に依存し、`k` は根の同定に依存する。根が pilot 後まで未定だと、
**primary の有意水準が pilot 前に固定されない。**さらにレンズ A の指摘どおり、
根を 3 つ自己申告して各 study を `k=1` にすれば、独立な 3 つの真の帰無で全体誤り率は
`1 − (1−0.025)³ ≈ 0.0731 > 0.05` になる。「追補 B が再現できなければ拒否」は、
B 自身の根選択が pilot 後なら防壁にならない。

**段 6 のレビュー A が、`a13` へ移すだけでは閉じないことを示した。**
追補が「根 = `F`、本 study は `k=1`」と**宣言する**だけでは、
3 つの study がそれぞれ同じ根に対し `k=1` を主張する経路を塞げない
(独立な 3 つの真の帰無で全体誤り率は `1 − (1−0.025)³ ≈ 0.0731 > 0.05`)。
**caller が選べない外部台帳での原子的な予約**が要る。

- **(a) `a13` へ移し、かつ caller 非選択の canonical 台帳で `(family_root, ordinal)` を
  原子的に予約する (推奨)。**
  根 = D234 を fold した commit `F`、本 study は `k=1`、予約は create-only、
  失敗・中断も番号を解放しない。受領証は台帳 path・予約 entry の digest・予約 commit を必須記録し、
  validator が台帳を読み直して重複が無いことを確認する。`b03` は個別公表系列の台帳の根だけを持つ。
  `addendum-a.md` の `a13` は既にこの形で書いてある (台帳の実体化は producer 実装 wave)。
- (b) `a13` へ移すが台帳を作らず、宣言だけにする。→ 上記の重複経路が残る。採らない。
- (c) `b03` のままにする。→ 有意水準が pilot 後まで宙に浮く。絶対規律 3 に抵触する。
- (d) 追補 B 全体を pilot 前に凍結する。→ core §10 / §14 が「B は本走の投入前」と定めた設計を
  前倒しする。B は `q` に影響しないので前倒しの必要性は薄く、代わりに B の内容 (候補数上限) を
  pilot 前に決めることになり、pilot からの情報を使えない不利がある。

**親の推奨は (a)。**core §14 の A/B 分割の読みを変えるため、明示の裁定が要る。

## R4. `a03` の閾値を未実測のまま承認するか、凍結前に環境 probe を要求するか

**事実。** `a03` は待機後の環境復帰を
`cpu_busy_core_equivalents = 48 × (total − idle)/total` (待機末尾 10 秒窓、`/proc/stat`) で判定し、
許容範囲を `[0, 1.0]` core-equivalents とする。これは形式上の恒真化 3 禁止
(定数指標・実現値を必ず含む範囲・範囲なし指標) のいずれにも該当しない。

**しかし、この範囲を正常な割当てが通る証拠は 1 件も無い。**

- 既存の 36 行 (`limited-screen.tsv`) が記録したのは `load1` であって `/proc/stat` counter ではない。
- **probe は run 間に待機を 1 秒も置いていない** (`t139_positive_control_probe.sh` に `sleep` が無い)。
  したがって「待機後に環境がどこまで戻るか」は本 study の資料に存在しない。
- 参考として `load1` は 36 行を通じて `3.29` → `40.18` へ単調に上昇している。
  仮に `[0,1]` を `load1` に当てれば 36/36 が不成立になる。

**なぜ問題か。** 閾値が厳しすぎると全 cluster が preflight で落ち、予備 2 本を使い切って
`design_not_feasible` になる (割当て 26 本が無駄になる)。緩すぎると恒真化し、
待機の十分性検査が空文になる。**どちらも受理集合を壊す。**

**選択肢。**

- **(a) 凍結前に非 study の環境 probe を 1 本走らせる (推奨)。**
  **`gen_S` で行う** (main と同じキュー。`debug` での代用は認めない — ノードの占有条件が
  main と同じである保証が無い)。測るのは 3 つ:
  (i) 待機 30 / 60 秒の末尾 10 秒の `/proc/stat` counter、
  (ii) **`CCBENCH_TRACE=1` の build が通るか** (現在 witness ゼロで、検証割当ての成立に必要)、
  (iii) **compiler の realpath・`--version`・bytes digest** (`a08` が数値で pin できていない)。
  これは本 study のデータではなく環境の特性づけなので、pilot 前に行っても事前登録を汚さない
  (`DW-G01` 生死実験先行の直接適用)。
  **閾値の導出写像は probe より前に凍結する** — 例えば「観測 36 点の最大値 + 0.5 core 相当」のように
  probe 結果から閾値を一意に決める規則を先に固定し、実測後に裁量が入らないようにする。
  そのうえで追補 A を再発行して凍結する。
- (b) 未実測の fail-closed 規範値として `[0, 1.0]` のまま承認する。
  → 実走で初めて可否が分かる。落ちた場合の損失は割当て 2〜26 本。
- (c) `a03` を「待機秒数の遵守だけを検査する」形へ弱める。
  → core §14 が明示的に禁じる恒真化に該当する。不可。
- (d) study を中止する。→ 環境が要求水準を満たさないと判明した場合の終端。
  probe は (d) の判断材料でもある。

**親の推奨は (a)。**この 1 本を惜しむと pilot 全体を失いうる。
なお **`a03` の初回 run 窓 (preflight 末尾 10 秒) と malformed counter の fail-closed 規則は、
どの選択肢でも修正が要る**ため、既に `addendum-a.md` へ反映済みである。

## R5. core §4 の Fieller 同値の文言へ第 2 の erratum を当てるか

**事実。** core §4 は「有界な集合が `(0,1)` に含まれることと `N>0 ∧ G>0` は**同値**である」と書く。
段 3 レンズ A が反例を示した — `(N̄, D̄) = (−1, −2)` で領域を十分小さくすると、
比の集合は約 `[0.445, 0.557] ⊂ (0,1)` になるが `inf N < 0` かつ `inf G < 0` である。
**この反例は正しい。**

**ただし親が独立に検算した結果、primary は汚染されない。** 反例の設定で
`A = D̄² − q² s_DD/J = 4 − 0.01 = 3.99 > 0` かつ `D̄ = −2 < 0` なので、
core §5 軸 2 の **first-match 順 2 `degradation_absent`** (正例 `false`) が、
軸 1 の区間の形を見る**前に**吸収する。さらに primary の判定は `N`・`H`・`G` の同時下限であって
比の区間ではない。

**選択肢。**

**段 6 のレビュー A が親の裁定を確認しつつ、推奨理由の不足を指摘した。**
「`degradation_absent` が発火せず、かつ比の区間が `(0,1)` に含まれ、かつ `inf N ≤ 0` または
`inf G ≤ 0`」となる配置は**存在しない** (先行状態が発火しないなら `A>0` かつ `D̄>0`、
よって領域全体で `D>0`、比が `(0,1)` に含まれれば各点で `0<N<D`、
compact なので `inf N>0` かつ `inf G>0`)。**primary の悪用は refuted。**
ただし「primary に実害が無い」から「偽の同値を公表文言に残してよい」は導けない。
材料レポート / proof chain が負分母枝でも偽の同値を保証として記載しうる。

- **(a) core は触らず、公表側に正分母 guard を課す (推奨)。**
  `RF` の区間を載せる表には**分母の符号の状態 (`qualification_status`) を必ず併記**し、
  `degradation_absent` の行では `RF` を「解釈しない」と明示する。
  追補 A の `a11` には「primary の権威は同時下限と §5 の first-match 表であり、
  `RF` 区間は §16 の公表用」と明記済み。core の bytes を変えない。
- (b) 第 2 の erratum を当て、同値を正分母枝 (`A>0 ∧ D̄>0`) に限定する。
  → 文言は正確になるが、erratum の射程が広がり D229 の本文にも及ぶ。
- (c) 何もしない。→ 偽の同値が公表文言に残る。レビュー A の判定により採らない。
- (d) 将来の別 study で新 core を起こすときに直す。→ (a) と併用できる。

**親の推奨は (a) + (d)。**初版の推奨 (「実害なしなので当てない」) は理由として不足だったため差し替えた。

## R6. 完全な機械可読 受領証 schema をいつ・誰が発行するか

**事実。** 段 6 のレビュー 2 本が独立に、`record-items.md` は
「全 nested object へ `additionalProperties: false` を課す」と宣言しながら、
`allocations[]`・`liveness[]`・`admission_telemetry[]`・`attempts[]`・`phase_caps[]`・
`translation_units{}`・`cluster_slots[]` などの exact key・型・必須性・配列長・
cross-field 制約を網羅していないと指摘した。

**なぜ問題か。** 2 つの実装が未知 field・`null`・参照整合性の扱いを違えても本文に適合でき、
**同じ受領証が validator A では適格・validator B では拒否**になりうる。
適格 cluster 集合と certified 判定が実装で分岐する。

**選択肢。**

- **(a) 完全な機械可読 schema を pilot 投入より前に 1 枚の blob として発行し、
  その digest を `PreregBinding` へ固定する (推奨)。**
  発行は producer 実装 wave の責務 (D234 実装境界)。`record-items.md` はその schema が
  満たすべき**要件**を定める文書として承認する。
- (b) 本 wave で schema 本体を書く。→ 機械設定であり docs-only の scope 外。
  実装子を立てる wave になる。
- (c) schema を発行せず、`record-items.md` の散文を validator の仕様とする。
  → 上記の分岐が残る。採らない。

**親の推奨は (a)。**

## R7. `a03` 不成立の予備置換を回復するために exec broker を作るか

**事実。** 焦点再レビューが、`a04` の「外部証拠」案は trust root にならないと指摘した —
job の stdout / scheduler 出力に書かれる内容の生成者は job、すなわち **producer 自身**である。
append-only は改竄防止であって、内容の真実性と全 exec の完全捕捉を保証しない。

**現在 producer の権限外にある exec の完全な記録は存在しない。**
そこで `addendum-a.md` の `a04` は、実現可能で fail-closed な唯一の写像を既定にした —
**`a03` の不成立は位置を問わず「性能測定の開始後の失敗」へ写し、予備で置換しない。**

**なぜ問題か。** この既定は安全だが、preflight 段階の環境不調でも cluster を 1 本失う。
26 割当ての予算に対し、環境が不安定なら pilot / 本走が予備を使い切って
`design_not_feasible` になる確率が上がる。

**選択肢。**

- **(a) 既定のまま (予備置換を使わない) で pilot へ進む (推奨)。**
  失う可能性のある割当ての本数は環境次第だが、trust root 無しの置換経路を作るより安全である。
  R4 の環境 probe が「preflight の不調がそもそも起きるか」の情報を与える。
- (b) producer 権限外の exec broker / 独立 collector を実装し、
  全 process launch の完全な列と署名を記録して、`a03` 不成立の予備置換を回復する。
  → 正しいが producer 実装 wave の作業が増える。pilot が遠のく。
- (c) `a04` を「marker 不在なら開始前」に戻す。
  → 焦点再レビューが示した偽装経路が開く。**規律 2 に抵触するため不可。**

**親の推奨は (a)。**(b) は pilot の実績を見てから判断できる。

## 6. 凍結の可否 — 台帳へ書く状態名

段 3 レンズ B の指摘に従い、状態を 3 段階に分ける。「追補 A 確定済み」と無限定に書くと、
resolver・submit gate・受領証・validator が 1 つも存在しないのに pilot 投入が可能になったように読める。

| 段階 | 状態名 | 現在地 |
|---|---|---|
| 1 | 追補 A 案・erratum 案・schema 案 = **承認待ち** | **← 本 wave の終端** |
| 2 | 文書発効済み / 機械 gate 未実装 / **pilot 投入不可** | 承認 + fold の後 |
| 3 | producer・resolver・validator・consumer の実装と受入の後だけ **投入 gate 有効** | producer 実装 wave の後 |

**本 wave は段階 1 で終わる。**R1〜R7 の裁定と、追補 A の凍結承認をユーザーへ返す。

**R4 を (a) と裁定した場合、追補 A は環境 probe の実測後に再発行される** (`a03` の閾値が変わり、
bytes が変わる)。したがって R4 = (a) なら本 wave の `addendum-a.md` は**凍結対象ではなく
確定前の版**として扱う。R4 = (b) なら本 wave の bytes のまま凍結できる。

**R4 = (a) のときの承認単位 (既定):** **3 本すべてを段階 1 に留め、新しい追補 A と、
それとの整合を確認し直した erratum・schema を一括で再提出する。**
erratum や record-items だけを先に fold して段階 2 へ進めることはしない —
probe の結果が指標や schema を変えた場合、先行承認済みの文書と再発行された追補 A が
食い違うためである。個別承認を望む場合は、対象 blob と再審査条件を明示して裁定してほしい。
