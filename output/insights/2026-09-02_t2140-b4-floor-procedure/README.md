## なぜ手続きを先に用意するか (現在地の確認)

§5.1.1 の分析契約は `floor` を欠落・値域外・非数のとき `floor_domain_error` と判定し、
出力は `analysis_invalid` になる。verdict の全域関数は分岐 1 でこれを **protocol violation** へ
写す。**正規経路で材料レポートが到達できる分析 verdict はこの 1 つだけであり、§7.1 の 4 分類は
実効化していない。** この鎖は本 wave で現物から確認した。

**ただしこの 1 分類は、§5 の floor 欄が未記入であることから動的に生じているのではない。**
材料レポートの生成器は本書を読まず、評価器へ**無条件に** floor 不在を渡す
(`p3_b4_material_report.py` の `evaluate_b4_artifacts(floor=None, ...)`)。これは D1377 が定めた
向きである。**したがって §5 の floor 行を埋めるだけでは正規経路は変わらない。**
権威ある floor 成果物を検証して評価器へ渡す接続を材料レポート側に作るかどうかは別の裁定であり、
本 wave は決めていない。**この点は段 6 のレビューが親の初稿の誤りとして捕まえた。**

   → floor 記入 commit の message へ、採用したユーザー裁定を D 番号で書くことを案に入れた。
2. **凍結項目の一部に決定主体が割り当てられていなかった。** → 凍結項目 12 行の割り当て表を作り、

### 測定の側 (レンズ B、7 件)

1. **測る量そのものがずれていた (中核)。** §5.1.1 が比べるのは共通参照点に対する
   2 つの相対利得の差 `D = |gain_1 - gain_2|` だが、既存の between-run floor driver が返すのは
   単一構成の session-median の変動係数である。独立・同分散という単純なモデルでも差のばらつきは
   片側のおよそ 1.41 倍になりうるため、変動係数を入れても保守側になる保証がない。
   → `D` を直接測る計画にした。
2. **保守側の合成が閉じていなかった。** 全セル・全時間窓の最大が保守側になるのは、対象集合と
   各セルの上限統計が結果を見る前に閉じている場合だけである。さらに **`D` に 1 未満の上界は
   無いのに、登録できる `floor` は 0 以上 1 未満**である。
   → 「上限が 1 以上なら丸めず、この動作点では床値を生成できないと記録する」規則を書いた。
   切り詰めて登録すると、判定式が tie を過剰に生む方向へ黙って緩む。
3. **「対象動作点」が一意でなかった。** 同じ文言から複数の測定集合が通り、別々の床値が出る。
   → 凍結前に一意化すべき 6 項目を列挙した。
4. **依存順序は循環なしで実行可能。ただし出力命名の一意化が要る。**
5. **要求する測定を起動できる sanctioned CLI が現行 repo に無い。** 正式 launcher に校正済み
   `PerfConfig` と対照対の入口が無く、各 driver は自ら「性能比較用の校正ではない」と宣言する
   既定設定を使う。s8b の floor driver が計算するのは絶対スループット基準の別量である。
   → 専用 driver / adapter が要ることを「測定開始の前提」として明記した。
   **本 wave では実装しない** (D1383 の範囲は案と計画までであり、依頼も起草だけである)。
6. **測定中の競合を排除できない。** 低水準の測定関数に競合 probe が無く、既存 driver も
   セッション開始前の確認しか行わない。→ s8b の「事前 probe → 測定 → 事後 probe → journal」を
   必須経路として流用する要件を書いた。落とした標本を値を小さくする方向の除外に使わない。
7. **標本数が未確定だった。** → 分布自由な片側許容限界の数値を採用した。
