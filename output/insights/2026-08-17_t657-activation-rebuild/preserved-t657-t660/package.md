## 1. 衝突 (1) — 盲検封印との紐付け (解決済み)

floor protocol を再発行すると、`s8b_floor_campaign.py:1497` の
「selector prediction を封印した時点の floor blob と現在の floor が一致すること」という
launch 条件が破れる。**production の拒否は正しい。**

この E2E は**再発行の前後どちらでも赤**だった (前は現行契約 g2 と protocol 契約 g1 の不一致、
後は封印時 floor と現行 floor の不一致)。g2 世界と既存の固定封印は構造的に両立しない。

**ユーザー再裁定 (発話「推奨で」) により E2E を 2 lane へ分けて解決済み。**
歴史 lane は clone を封印 commit へ detach し activation authority を合成 head=1 へ差し替えて
当時の世界を再現、現行 lane は launch が拒否されることを pin する。検査を 1 つも失っていない。

## 2. 衝突 (2) — 凍結の履歴不変条件 (未解決・本裁定の対象)

`s8b_ratified_freeze.py:469-485` の `_immutable_introductions` が張る条件は

> ∀C ∈ rev-list(HEAD): entry(C, path) ∈ {absent, HEAD の oid}

であり、実装コメントは目的を「削除→別 bytes 再作成の遮断」と明記する。呼び出しは `:998` で
`h_oid = HEAD の blob oid` を expected として渡す。

**凍結成果物は「一度書かれたら歴史上ずっと同じ bytes」でなければならず、再発行は原理的に
この検査と両立しない。** 再発行前は歴史全体が旧 bytes だったので通っていた。

裁定 §44 の前提 (b)「floor protocol の再発行」は、この不変条件を破る操作だった。
一方、再発行しなければ g2 で floor live admission が拒否される。**どちらを選んでも壊れる**のが
g2 活性化の本質的コストである。

## 3. 選択肢

### A. 活性化を見送り、凍結の世代交代とセットで再設計する (親の推奨)

floor protocol を元に戻し、第 2 世代の有効化も引く。「較正の世代交代」と「凍結の世代交代」を
一体の設計として起票し直す。

- **利点**: 防壁を 1 つも弱めない。判明した 2 つの制約を設計の入力にできる。確実に緑へ戻る。
- **欠点**: 裁定 §44 の前提を撤回することになる。活性化が先送りになる。
- **今日の成果は残る**: 活性化の実装・テスト追従・[T-660] の検出力実証・E2E の 2 lane 分割は
  世代交代がある限り必要で、そのまま再利用できる。

### B. 履歴不変条件の違反を拒否から記録へ落とす

floor protocol についてのみ、履歴に複数 bytes があっても拒否しない。検出と記録は残す。

- **利点**: 今日中に終わる。正当な世代交代が止まらなくなる。
- **欠点・懸念 (親が推奨を撤回した理由)**:
  - **多層防御の 1 層を抜く。** 親は当初「AI は再発行できないから安全」と論じたが、
    その根拠にした isatty 検査は、コード自身が
    **「actor 認証ではなく、PTY 割当・module 直呼びで迂回可能な誤操作防壁」**と明記しており、
    実効の保証は「規律・guard_write hook・AI provenance 監査の組合せ」に置かれている。
    履歴不変条件はその中で**唯一「後から見て改竄を検出する」層**である。
  - **親がこの案の設計文書を書こうとしたところ、harness の安全層が拒否した。**
    親の推論のどこかが甘い可能性を示す独立したシグナルとして記録する。
  - 採る場合は「放棄する保証の明示」「緩めすぎを検出する負例テスト」「越境変異の事前登録」を
    必須にする。

### C. 凍結の新世代 (v2 chain) を正式発効させる

設計が想定した世代交代の経路を通す。

- **利点**: 防壁を弱めない。設計の意図どおり。
- **欠点**: 発効には approval record・active pointer・generation record の 3 点セットを
  整合的に作る必要があり、いずれも `output/s8b-freeze/` 配下で **AI は書けない**
  (floor protocol と同じ hook が拒否する)。floor 再発行より複雑なユーザー手番になる。
  さらに現在赤の node は「**v2 未発効**」を前提に期待値を書いているため、発効させると
  それらの期待が一斉に変わる。次の wave 規模。

## 4. 親の推奨と、推奨を変えた経緯 (透明性のため記録)

親は当初 **B** を推奨した (脅威モデルが自分自身であること、完全防止は原理的に不可能であること、
2026-08-06 裁定「完璧な堅牢性は不要、防御的堅牢化は既定で見送り」との整合を根拠に)。

その後、**A へ改めた**。理由は §3-B の 2 点 (多層防御の 1 層を抜くこと、安全層が独立に拒否したこと)
に加え、C を実際に調べた結果 **「較正の世代交代は凍結の世代交代と不可分」** と判明したためである。
部分的に防壁を緩めて通すより、両方を一体で設計する方が健全だと判断した。

**ただし A は裁定 §44 の前提を覆すため、親の一存では決めない。**
