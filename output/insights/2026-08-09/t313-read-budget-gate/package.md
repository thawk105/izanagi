## Q1. 新規 L2 節の admission をどうするか

**事実:** 受理上限は `20,191 + 1,000N` (N = L2 節数) で、**N に上限がない**。
一次裁定の「常に読まない層は合計上限を持たないが無制限には増えない」を成立させるのは、
routing 3 の**削除**条件ではなく**登録**条件だが、後者は存在しない。
機械側は L2 の節 ID が checker の literal pin なので追加には code 編集とレビューが要るが、
byte の歯止めはない。[T-577] の見送り候補も L2 として再登録すれば復活できる。

| 択 | 内容 | 帰結 |
|---|---|---|
| (a) | 現状 (literal pin + code review) で足りるとする | 歯止めは人の目だけ。旧集約上限が担っていた層が消える |
| **(b) 推奨** | routing 3 の 3 条件 (発火実績・機械検査での義務代替・ユーザー裁定) を**新規登録側にも**課す規範を `docs/decisions.md` (byte 上限なし) へ D として記録する | 予算を使わずに書ける。[T-664] R6(a) と同型の先例がある |
| (c) | L2 の節数上限を置く | 現在値 13 以外に根拠がなく、「単節 cap のみ」という裁定より狭い |

**推奨 = (b)。** 判断を失わず、`docs/dev-wave/**` の予算も使わない。

## Q2. L0 command / self doc / Codex skill を常時読量に含めるか

**事実:** 本 gate の対象は `docs/dev-wave/**` の 4 冊だけである。実際に毎回読むものには
入口 command 9,443 bytes、`docs/skill-self-improvement.md` 5,997 bytes (段 8 で全節)、
Codex 側 skill 3,747 bytes がある。いずれも独立の個別 cap を持つが、層の概念はない。
したがって成果物を「dev-wave 全層の常時読量 gate」と呼ぶことはできない。
2026-08-03 のパッケージが「閉じていないこと」として残した項目であり、本 wave でも閉じていない。

| 択 | 内容 |
|---|---|
| **(a) 推奨** | 含めない。名称を「`docs/dev-wave/**` leaf の unique-footprint gate」に限定し、L0/self は現行の個別 cap のままにする |
| (b) | 複合 envelope を設計する。ただし「self doc のどの節を常時と数えるか」の追加裁定が要る |

## Q3. event 加重の読量 envelope を作るか

**事実:** 本 gate が測るのは **unique byte footprint** である。同じ節を複数の段で読む重複は
数えない。実測すると、常時段の読了 event を重複込みで足した値は **12,670 bytes** で、
gate が凍結した 10,625 とは異なる (差は `DW-G01`〜`DW-G05`、`DW-STOP` 等の複数段読了に由来)。
また段 dispatch 表の同一行を複製しても unique 値は変わらない (edge が集合で潰れるため)。

| 択 | 内容 |
|---|---|
| **(a) 推奨** | 作らない。unique footprint を指標と明示し、event 加重は既知限界として記録する |
| (b) | 別 wave で event 加重 envelope を設計する (段別 envelope は 2026-08-03 パッケージの択 3 に相当) |

## Q4. `DW-CTX` の実読取結線をどうするか

**事実:** 入口は外部 supervisor に「最初の `claude -p` spawn 前に `DW-CTX` を読む」と課すが、
`tools/dev_waves/daemon.py` と `worker.py` に読取処理は無い (段 6 レンズ B が実測)。
本 wave の位置修正は dispatch の分類重複を除いただけで、**起票文の言う「読み動線と不一致」を
完全には解消していない**。

| 択 | 内容 |
|---|---|
| **(a) 推奨** | 別タスクとして起票し、supervisor 側の結線で閉じる |
| (b) | 現状追認で閉じる (入口の記述を実態に合わせて弱める) — 安全義務を弱める方向なので推奨しない |
