## 3. 走らせられる軸が現存しない

3 アームを同一予算で走らせるには、対照の編集面 (substrate anchor) が必要である。
現状はこうなっている。

- **backoff** — 2026-07-10 追記 1 の軸適格性違反。スカラー 1 個の探索に還元できる軸は
  headline 候補にしない。P2-5/D21/D29 が「この型の空間では LLM は機械探索から分離できない」ことを
  既に実証しているため、失敗条件 (c) を構造的に誘発する。
- **sort** — D46 で「順序の質」由来の floor 超地形なしと決着。
- **trigger-gating** — D52 の (c') 事前自認。「軸内探索で LLM は機械列挙を上回れない」と
  最初から主張範囲外に置かれている (D48 決定 2、偵察空間 = coder 変異空間)。
- **データ構造水準 (write set の格納形式、[T-140])** — 2026-07-28 に実測して
  **択 (c) = 軸の廃止**を適用済み。再開条件は `max_ope` の大きい workload spec を
  campaign が採用する場合だけ (`docs/phase3.md:157-159`、
  一次資料 `2026-07-28_t140-setsize-distribution.md`)。

**D52 (2026-07-12、ユーザー承認) が対照 3/4 の編集面を休眠とし、発火を
「旧主張の復活条件成立時に日付付き追記で固定」と定めた。** 復活条件は
「非列挙のコード片軸の実体化 + 偵察で floor 超地形の確認」である。
2026-08-26 現在、**実体化した適格軸はゼロ**であり、第 1 項の時点で未充足である。
さらに `docs/phase3.md:354` は、段 6 前提タスク (a)〜(e) — この対照の設計タスク (c)(d) を含む —
自体が「旧 headline を復活させない限り休眠」と定めている。

## 4. 設計 — 発火したときに何を走らせるか

以下は拘束力を持たない設計案である。発火時に正本化する場合は、§6 の未解決事項を先に閉じる。

**アーム。** (1) LLM: 固定 model・prompt・射影入力から逐次候補を生成し、直前までの
構造化された正しさ・性能結果を次の提案入力にする。(2) random: 事前凍結した分布から、
性能結果に依存せず候補を生成する。(3) sweep-matched: 人間命名・事前凍結 grid を
LLM と同じ評価予算まで機械走査する。

**予算単位 = certification 評価 slot。** 1 slot は Tier0 を通過した候補 1 件を
certification pipeline へ投入する機会であり、**verifier が anomaly を返して reject された場合も
1 slot を消費する**。これは設計上の要である — 「成功して certified になった候補だけ」を数えると、
Tier0 不合格と anomaly を無制限に無料で捨てられ、正しさゲートの迂回が予算上の利益になる (規律 2)。
Tier0 前にも原提案上限 A を置き、A 未達を「その arm の敗北」ではなく判定不能へ倒す。

**bench 実時間は主予算にしない。** arm × workload × 系列ごとの `total_bench_s` を副次指標として
必ず報告する。したがってこの「同一予算」が意味するのは**同一の探索評価機会**であって、
同一の金銭費用・生成時間・総 wall time ではない。「LLM の方が安い・速い」はこの設計から導けない。

**停止条件は 3 アーム共通。** 固定予算を完走し、性能値・順位・有意性・floor 超えを理由とする
早期停止を禁じる。一度 floor 超え候補へ到達しても予算を完走する。
機械故障 retry は閉じた列挙 (非ゼロ終了・signal・build infrastructure error・runner exception) に
限る。候補内容や性能値を理由とする retry は禁止する。

**検定単位は系列。** slot や within-run reps ではない。試行は履歴依存で独立でないため、
P2-5 が検定単位を系列に置いたのと同じ扱いを継承する。

**判定規則。** workload ごとの「LLM の因果的必要性」は、LLM-vs-random と
LLM-vs-sweep-matched の**両方**が連言を満たしたときだけ成立とする。片方だけの勝ちを
「LLM でなければ到達できない」と読ませない。非有意を同等性の証拠へ読み替えない
(判定不能はそのまま判定不能と報告する)。勝った workload だけの選択報告を禁じ、
全セル・全 incomplete・全 anomaly・全 floor を報告する。

**ランダム変異の生成分布。** sweep grid からの一様抽出にはしない — D46 決定 4 が
「列挙の劣化版にしかならない」と既に退けている。型付き変異契約 (canonical AST、
順序付き mutable-site 一覧、各 site の許容 production の有限一覧、canonical serializer、
source path/line/blob hash) を正式アームの出力を見る前に凍結し、site 数と production から
候補を引く。Tier0 通過率と Wilson 区間を独立の必須報告とし、生成器の質を隠さない。

**機械 sweep の軸命名。** 正式 LLM アームの出力を見る前に人間が行い、命名者・日時・
参照した source/docs/insight/偵察成果物の**全一覧**を凍結する。「見たが命名には使わなかった」
資料も省略しない。軸の**発見**自体が LLM の実証済み価値である以上、命名手順が曖昧だと
失敗条件 (c) の判定がどちらへも倒せてしまう。grid の走査順は hash 順に固定し、
既知結果に合わせて「予算内に入る点」を人が並べ替える自由度を除く。

**規律 1 の対称性。** 3 アームの性能値はすべて trace-disabled build から取得し、
trace-enabled run の timing を混ぜない。`pipeline.py` 冒頭が
「buildcache (trace/perf 別ビルド, 絶対規律1) → verifier (正しさゲート, 絶対規律2)」を宣言しており、
trace-disabled という狭い性質については既存機構で担保できる。ただし同一引数・
同一 correctness workload・同一 COMMIT consumer までの対称性は、それだけでは保証されない (§6)。

## 5. この設計では B-5 を主張できない — 識別の三すくみ

段 3 の敵対相談 2 本が、**独立に**同じ構造的問題へ到達した。これが本 wave の最も重要な結果である。

> ランダム変異アームを有限の型付き変異契約に閉じ、LLM アームを閉じないと、比較は
> 「広い空間 vs 有限の部分空間」になり、探索器の優越と探索空間の差を取り違える。
> かといって LLM も同じ契約に閉じると、その空間には完全列挙器が構成でき、
> 休眠解除の第 1 条件「完全列挙器を持たない軸」と衝突する。

これは草案の書き方の不備ではない。[T-140] のレビューが既に
「非列挙性・構成的安全保証・同一支持集合対照」の三すくみとして特定していたものと同型である。

**帰結:** この設計が示せるのは「固定予算・固定編集面の下で、事前登録した 2 つの非 LLM 生成器より
高い score だった」までである。**「LLM でなければ到達できない」という必要性ではない。**
B-5 を残すなら、次のいずれかが要る。

1. 主張を「凍結した random / sweep 対照に対する条件付き優越」へ狭め、論文 §8 の「必要性」と
   明確に区別する。
2. LLM と非 LLM を同一の候補支持集合へ閉じ、軸発見・候補生成・探索方策を別々に ablate する。
   ただし有限契約へ閉じると D52 の非列挙条件を再裁定する必要がある。
3. D52 の系レベル設計へ戻り、軸内探索ではなく軸発見・オンボーディングまで含む非 LLM 対照を設ける。

## 6. 発効前に閉じるべき未解決事項 (敵対相談の must-fix)

正本化する場合、以下を先に閉じる。すべて段 3 の 2 レンズが実コード参照つきで指摘したものである。

1. **同一支持集合** — §5 の三すくみ。LLM 側の stock / no-op / 重複候補の扱いも未定義。
2. **certification 経路の exact 束縛** — 「certification pipeline」という一般名詞では足りない。
   `pipeline.evaluate` の既定 correctness は小構成 (tuple=200 / thread=4 / rr50) で
   性能は 1M / 48 である (`pipeline.py:127`)。`performance_correctness_workload(perf)` は
   実在するが optional で、`screening` 指定で bench-first にもなる (:774)。
   小構成でだけ正しい候補を塞げていない。
3. **incomplete の扱いが arm 依存の censoring になる** — LLM の生成遅延、random の低 Tier0
   通過率、純粋な機械故障を同じ incomplete にすると、本来は敗北である系列が判定不能へ消える。
   P2-5 は逆に未到達を予算上限の最悪値へ算入していた。
4. **anomaly を性能値へ変換しない** — anomaly の即 reject と slot 消費は正しいが、
   それを `-100%` の性能観測へ変換して平均差検定へ入れると、correctness failure が
   任意尺度の性能差になる。baseline の anomaly 数だけで p 値と受理が動く。
5. **次の一手へ渡す schema の固定と情報対称性** — 「最低限」と書くと追加 field を許す。
   さらに random / sweep は state に応じて分岐しないため、比較されているのは
   「LLM」ではなく「適応的 LLM 閉ループ vs open-loop baseline」であり、B-4 の還流効果と交絡する。
6. **`paired_stock` と `floor_cmp` を純関数として定義する** — 測定数、前後順、arm 間共有、
   失敗時処理、CV 推定量が未定義。比較対象別の floor 再実測義務 (「floor の流用禁止」) を
   機械確認できる形にする。
7. **Holm 族が 1 回の発火内でしか閉じていない** — 複数軸を順に承認・実走し、成功軸だけ報告する
   経路が残る。activation 総数、最初の適格軸を採る規則、軸間の α 配分、
   判定不能な比較を族へどう入れるかが要る。
8. **休眠解除条件を自己申告でなく機械 gate にする** — 「単一スカラーでない」「非列挙」は意味判断、
   閲覧資料台帳は記憶の自己申告、「同じ条件を強制できる」は実走がその consumer を通った保証でない。
   承認対象 commit・decision ID・実行権限 receipt への束縛が要る。
9. **既知結果台帳 (HARKing 境界)** — 現行事前登録の 2026-07-12 追記は改訂時点の既知結果を
   具体的に列挙している。本設計は将来の偵察台帳しか要求しておらず、同水準に達していない。
10. **独立な性能検証相** — 系列 score を探索中の単回計測の最大値で決め、同じ値を検定に使うと
    winner's curse と高分散候補優遇を除けない。endpoint 固定後の独立再推定が要る。
11. **予算の実質改訂** — 提案上限を置く形は D39 の「10 iteration または 3600 秒」と同値でなく、
    探索機会の拡大を含むため「制約方向のみ」(D44 決定 1) を自称できない。D52 と同じく
    改訂類型の明記とユーザー承認が要る。

## 7. 費用 — 規律 4 との整合

段 3 レンズ B が既存校正値から外挿した桁を、そのまま記録する
(EXTIME=3s / REPS=5 / THREADS=48 / RECORDS=1M の動作点、3 アーム × 3 workload × 12 系列 ×
10 slot を仮定した場合)。

- trace-disabled bench (探索 + floor) だけで **約 12 時間**
- correctness 側は約 1,900 回の trace + verify。既存実測は 3 秒 trace 1 件あたり
  verifier wall が **140.66 秒**、rr95 例では **433.33 秒** (`s2_verify_t48_skew0p9_rr50_rmw0.md`、
  `s1_verify_extime.json`)。単純外挿で verifier だけ **76〜234 時間**
- 直列 wall の合計は **10² 時間級**

**RECORDS=1M 自体は規律 4 違反ではない** — working set ≥ L3×4 を満たす最小値として校正済みである。
問題は系列数・floor・verify の乗算にある。判定力を落とさずに縮められるのは、
(a) 判定族外である sweep-ceiling を別 wave へ送る、(b) floor 標本の系列ごと複製を
block 別共通 stock へまとめる、の 2 点。系列数の削減は p 値解像度と引き換えになるため、
発火前の効果量非依存な感度解析が要る。**レコード数を勝手に下げてはならない** —
発火環境の校正がより小さい値を選んだ場合だけ変更する。

## 8. 親の段 1 実測の訂正

自分の誤りを消さずに残す。いずれも段 3 の敵対相談が指摘し、親が実コードで裏を取って認めたものである。

1. **「停止条件は実在」は不正確だった。** 実在するのは報告 literal であり、機構としての強制ではない
   (§2 の表)。ユーザーの依頼「停止条件を 3 アーム共通にしてください」は、今の repo では
   強制できない。
2. **「[T-140] は段階 B へ差し戻し、存廃が裁定待ち」は古かった。** 段階 A/B のパッケージ文書だけを
   読み、その後の決着を見落とした。現正本は 2026-07-28 実測後の択 (c) = 軸の廃止であり、
   再開は `max_ope` の大きい workload spec を採用する場合に限られる。
3. **sweep の棚卸しが不完全だった。** `s8a_trigger_sweep.py` を落としていた。
   preliminary・完全列挙・headline 対象外なので B-5 実行可能性は変わらないが、台帳として不正確だった。
4. **「評価回数予算と停止条件が実在」は B-5 互換性を過大一般化していた。** 実在するのは
   別実験の generation budget と用途固有 ledger、軸固有 sweep であり、
   B-5 の 3 アーム共通 slot consumer ではない。
5. **「全件検索 0 件」は方法を限定して書くべきだった。** 与えた検索語は別名実装を拾わない。
   結論自体は意味検索を広げても維持されたが、根拠の書き方が過剰だった。

## 9. ユーザー裁定へ返す事項

1. **B-5 の主張範囲。** §5 の三すくみを踏まえ、B-5 を「必要性」のまま残すか、
   「凍結対照に対する条件付き優越」へ狭めるか、D52 の系レベル設計へ戻すか。
   **狭める場合は論文 §8 の B-5 欄の文言も変わる。**
2. **休眠を解除するか。** 実体化した適格軸がゼロである以上、現時点の解除は
   走らせる対象のない解除になる。解除するなら、まず適格軸を作る作業 (軸オンボーディング) が先。
3. **費用の受容可否。** 直列 wall で 10² 時間級を許容するか。許容しないなら §7 の縮小案のどれを採るか。
   **観測後に子の判断で縮小してはならない** — 事前に決める必要がある。
4. **予算契約の改訂承認。** D39 の「10 iteration または 3600 秒」を B-5 用に改める場合、
   D52 と同じく改訂類型の明記とユーザー承認が要る。
5. **実装の認可。** ランダム変異生成器、Tier0、3 アーム共通 driver、B/A 台帳、
   report / 統計 consumer は中〜大規模の新規実装である。本 wave の docs-only 権限には含まれない。

## 10. まとめ

B-5 は「未取得」のままである。本 wave はそれを取得しなかったが、**なぜ取得できないかを
実コードの水準まで下ろした。** 走らせられない理由は資源不足でも実装漏れでもなく、
(a) 適格な軸が 1 本も実体化していないこと、(b) 有限対照と非列挙軸が両立しないという
識別上の三すくみ、の 2 つである。前者は軸オンボーディングの問題、後者は主張範囲の問題であり、
どちらも実装を足しても消えない。

論文素材 §8 の B-5 欄は「未取得。変化なし」のままでよいが、**「まだ測っていない」ではなく
「現在の基盤では、この形の対照では測れない」と書ける段階には来ている。**
