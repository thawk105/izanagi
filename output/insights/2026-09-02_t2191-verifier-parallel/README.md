# 直列性検査の並列化 — 2.2 倍まで縮み、判定は 1 bit も変わらなかった。12 時間枠には入らない

B-10 正式走の律速だった直列性検査 (`orchestrator/verifier/`) を並列化した。
**判定は変わらない。速さは 2.2 倍で頭打ちになり、read-heavy を 12 時間枠へ入れるには足りない。**
本書は測った値と、その射程の限界をそのまま記録する。

## 依頼の前提を最初に実測した

一次資料 (`output/insights/2026-09-02_b10-trace-truncation/README.md`) は、1 反復の所要が
**混合区間**であり「検査器そのものの費用ではない」と明記していた。そこでまず、検査器だけの
費用を分離して測った。

read-heavy 相当の合成 trace (48 file、1 txn 10 操作、95% read、鍵の版密度を実配分へ合わせる) を
使い、段別に計った。

| 段 | 170k txn | 340k txn | 占有率 (検査器内) |
|---|---:|---:|---:|
| `parse_trace_dir` | 5.72s | 12.05s | 54% |
| `DSG` 構築 | 3.74s | 8.77s | 39% |
| cycle 検出 | 0.60s | 1.38s | 6% |
| 検査器合計 | 10.06s | 22.21s | — |
| = 1 commit あたり | 59.2us | 65.3us | — |

参考として、編集面の外にある pipeline の C 行数え直しは 0.18s / 0.34s (1.0-1.1 マイクロ秒/commit) で
あり、混合区間全体に対して 1.5% しかない。

**検査器単体 59.2-65.3 マイクロ秒/commit は、read-heavy の実測傾き 87.0 マイクロ秒/commit の
68-75% を占める。** 17M commit へ外挿すると約 1000-1210 秒で、観測された 1 反復
1346.9-1465.6 秒の主要項である。**依頼の前提「検査器が律速」は確認された。**

外挿の形には幅がある。2 点の間で 1 commit あたり費用が 10.4% 増えており、局所一次外挿なら
約 1213 秒になる。**外れる向きは上側なので、検査器が主要項という結論は外挿の不確かさで
覆らない。** ただし「1000-1100 秒」と狭く断定はできない。

> **但し書き (D1529、2026-09-04)。** 「read-heavy の実測傾き 87.0 マイクロ秒/commit」の母集団は
> read-heavy の本規模 (performance) 18 反復、「観測された 1 反復 1346.9-1465.6 秒」は commit 数が
> 飽和した 3 変種 (反復数 5・5・3) で、いずれも campaign 記録上 commit (変種の認証確定) に到達
> しないまま打ち切られた実行 (以下「欠測 attempt」) である `constant-mu2` 変種 `292d58f1dad8` の
> 3 反復を含む。ここから出した「68-75%」と、17M commit への外挿「約 1000-1210 秒」「約 1213 秒」も
> 同じ入力に依る。検査器単体の 59.2-65.3 マイクロ秒/commit は合成 trace の実測で欠測とは無関係で
> ある。値を無効にするものではなく、欠測 attempt を除いた再計算は行っていない。

鍵の偏り (`ycsb_zipf_skew=0.9`) は費用をほとんど変えなかった (57.8 対 59.2 マイクロ秒/commit)。
鍵あたりの版数が平均 9.32・最大 5301 まで伸びても、版の探索が二分探索なので効かない。

## 設計を決めた 2 つの実測

**(1) 子から親へ何を返すかで勝負が決まる。** 170k txn の結果を返す費用は、

| 表現 | dump | load | bytes |
|---|---:|---:|---:|
| `Txn`/`Read`/`Write` の dataclass を pickle | 2.73s | 8.80s | 62.4MB |
| 列指向 `array('q')` + 鍵の id 化 | 0.06s | 0.05s | 58.6MB |

同じ入力の `parse_trace_dir` 本体が 6.74s なので、**オブジェクトを返す並列設計は往復だけで
parse 本体より高くつく。** 列指向なら実質無料である。

**(2) 記憶量が先に壁になる。** 並列化前は 1 commit あたり 5.1KB で、read-heavy 全規模
(17M commit) では約 87GB になる。計算ノードのユーザ利用上限 115GiB に対して余裕が乏しい。

> **但し書き (D1529)。** 「read-heavy 全規模 (17M commit)」という規模は、欠測 attempt を含む上記の
> read-heavy 観測から採った値である。1 commit あたり 5.1KB は合成 trace の実測で欠測とは無関係で
> ある。値を無効にするものではなく、規模を取り直した再計算は行っていない。

## 先行分析が閉じていた道と、開いていた道

`docs/b10-multinode-formal-run-design.md` §4 が同じ問題を検討し、次を確定していた。

- 検査を別プロセスへ配って結果だけ親へ戻す形は、受領証が発行時のプロセス番号を記録し消費時に
  一致を要求するため (`orchestrator/verifier/core.py`) 認証が成立しない。証明の連鎖を外して
  結果だけ受け取れば受理する範囲を広げることになり**絶対規律 2 に反する**。
- Python のスレッドは、検査が純 Python の CPU 仕事なので効かない。
- **残る形は 1 つ** — 判定と受領証の発行は元のプロセスに残し、純粋なデータ処理の段だけを並行にする。

同文書はこれを「正しさ防壁の中核に手を入れる変更であり、着手にはユーザーの判断が要る」として
範囲外にしていた。本 wave はその判断を受けて着手した。

## 実装した形

- ファイル単位の構文解析と、依存グラフの辺候補の計算を fork した子へ出す。
- 子はオブジェクトも判定も文字列も返さない。固定幅配列と token blob だけを返す。
- **判定 (SCC・cycle witness・三値 verdict)・`VerifyResult` の組立て・受領証の発行と消費は
  親プロセスに残す。** `core.py` のプロセス番号束縛には触れていない。
- `orchestrator/verifier/` に新しい file を作っていない。enforcement source closure
  (`orchestrator/campaign/campaign_lock.py` の exact 24 path) は verifier package の
  `__main__.py` / `cli.py` 以外をすべて含むので、新 module は正しさ実装を閉包の外へ置くことになる
  (D442 がまさにこれを規律 2 抵触として閉じた)。

判定の同一性は、辺候補へ**大域の論理 ordinal** (txid 昇順 → read 行順 → wr → rw → 鍵の初出順の ww)
を付け、結合前に ordinal 順で実際の集合へ再生することで保つ。子の結果は完了順でなく
ファイル順に消費し、全ファイル分がちょうど 1 件ずつ揃ったときだけ採用する。1 件でも欠けたら
部分結果を全廃棄して逐次で読み直す。構文解析の失敗は、親がそのファイル 1 本を既存のコードで
読み直して自然に例外を上げる。

## 測った結果

### 判定は変わらなかった

68 万 txn の同一 trace に対する `result_to_dict` の sha256。

| 版 | sha256 |
|---|---|
| 旧コード (並列化前) | `42db8b974f71b038df5aab536d393e06d075abd82d386c2871ad3ebfc110f35e` |
| 新コード workers=1 | 同上 |
| 新コード workers=16 | 同上 |
| 新コード workers=48 | 同上 |

17 万 txn では workers=1,2,4,8,16,24,32,48 の 8 通りすべてで一致した。
`trace_dir` だけ除いた全 field を sort_keys で JSON 化した比較である。

### 速さは 2.2 倍で頭打ちになる

68 万 txn、同一 trace、同一機体。

| 版 | 所要 | 1 commit あたり | 旧比 | 峰値 (親+全子、cgroup) |
|---|---:|---:|---:|---:|
| 旧コード | 45.92s | 67.53us | 1.00x | 3.60GB |
| workers=1 | 48.70s | 71.62us | 0.94x | 1.99GB |
| workers=8 | 22.97s | 33.78us | 2.00x | 2.34GB |
| workers=16 | **20.64s** | **30.35us** | **2.22x** | 2.94GB |
| workers=24 | — | — | — | 3.70GB |
| workers=32 | 21.13s | 31.07us | 2.17x | 4.50GB |
| workers=48 | 20.82s | 30.62us | 2.21x | 5.68GB |

**並列度 16 で飽和する。** 48.70 = S + P、20.64 = S + P/16 から親の直列部 S は 18.8 秒
(全体の 38.6%) で、**漸近上限は約 2.6 倍**である。段 2 のプランが見込んだ 5-12 倍には届かない。
残る直列部は親のマージ (winner 再生・write 走査・鍵の intern・shard 結合・隣接表の構築) と SCC で、
段 3 の相談が事前に指したとおりになった。

逐次経路は 6% 遅くなった (45.92 → 48.70 秒)。列指向への変換ぶんである。

記憶量は 1 commit あたり 5.12KB → 2.93KB の 1.75 倍削減。ただし**並列度を上げると増える。**

測定はログインノード (96 core / 250GB) で行い、**16 ユーザ共有・load average 20-30 の状態だった。**
専有ではないので、並列の伸びは抑えられている側の値である。

## B-10 read-heavy はまだ 12 時間枠に入らない

1 反復あたり検査器が 1000-1210 秒 → 2.2 倍で 420-500 秒。検査器外の 240-340 秒を足して
**660-840 秒/反復**。full-scale は 75 回 (15 変種 × performance 5 反復。残る legacy 15 回は
4 スレッド・1 秒で桁が違う) なので **13.7-17.5 時間**である。

現状 1350-1450 秒/反復に対して end-to-end で 1.7-2.1 倍であり、**律速は大きく下がるが外れない。**
これは共有ログインノードでの測定に基づく見積りであり、専有した 48 core の計算ノードでは
伸びる余地があるが、本 wave では測っていない。

> **但し書き (D1529)。** 「検査器 1000-1210 秒」「検査器外の 240-340 秒」「現状 1350-1450 秒/反復」
> は欠測 attempt を含む read-heavy 観測帯を入力にしており、そこから出した「660-840 秒/反復」
> 「13.7-17.5 時間」「end-to-end 1.7-2.1 倍」も同じ入力に依る。2.2 倍という並列器自体の倍率は
> 合成 trace の実測で欠測とは無関係である。値を無効にするものではなく、欠測 attempt を除いた
> 再計算は行っていない。

## 変異で歯を確かめた

7 変異すべてが期待 node 完全一致で KILLED になった (baseline PASSED、SURVIVED 0、MISMATCH 0)。

| # | 変異 | 赤になった node 数 |
|---|---|---:|
| M1 | 全ファイル分が揃ったことの検査を外す | 1 |
| M2 | 子の結果をファイル順でなく逆順に消費する | 4 |
| M3 | 辺の再生順を大域の論理 ordinal 順でなく到着順にする | 1 |
| M4 | 失敗ファイルの親再解析をやめ、子の args から例外を再構成する | 3 |
| M5 | 依存グラフの rw 辺 (読んだ版の直後版) を落とす | 18 |
| M6 | 重複 txid の判定を親再生でなく子ローカルに戻す | 1 |
| M7 | 同時実行の入力隔離を戻す (子が親の大域変数を fork で継承する) | 1 |

M2 と M5 は冗長 gate である。M5 が 18 件を同時に赤にするのは、rw 辺が直列性検査の中核だからである。

**M7 は敵対レビューが見つけた欠陥の回帰である。** 実装の初版は依存グラフの子への入力を
モジュール大域変数へ排他なしで置いていた。同一プロセスの別スレッドが 2 つの trace を同時に
検証すると、片方の子がもう片方の入力を継承しうる。件数の完全性検査は通るので、
**巡回のある trace が `certified=true` になりうる**。絶対規律 2 の直撃である。
呼出しごとの状態を作り、子へは初期化引数で渡す形に直した。

**変異の登録には 5 走かかった。** 初回は runner argv に `--force-dispatch` が無く baseline が
解析不能で止まった (runbook 7.4 の既知事項)。M7 は 2 走生存したが、いずれも注入の狙い違いで
あって防壁の不在ではない — 初版は逐次経路だけを、2 版は executor の構築時に評価される引数を
大域から取る形にしており、どちらもテストが同期させた fork 時点には効かなかった。3 版で
子側の初期化関数が fork 後に大域を読む形にしたところ KILLED になった。
各走の spec と台帳は本 directory へすべて凍結してある。

## この記録が保証しないこと

- **17M 規模で測っていない。** 所要も記憶量も 68 万 txn からの線形換算である。
  1 commit あたりの費用は 17 万 → 34 万 → 68 万で単調に増えているので、換算は下側に寄る。
- **共有ノードでの測定である。** 専有した計算ノードでの並列効率は測っていない。
- **判定の同一性は測った入力についての事実である。** 合成 trace 1 種と、
  `orchestrator/tests/test_verifier.py` の全 fixture (96 件) の範囲で一致した。
  すべての入力で同一であることの証明ではない。
- **既知の挙動差が 1 件ある。** 巨大で疎な txid (例: 単一 txn の txid が 10^12) は、
  従来の `set(range(max+1))` による実用上の `MemoryError` ではなく、
  欠番数を持つ `indeterminate` を返すようになった。拒否側へ倒れる安全な差であり、
  テストで固定してある。
- **既存の campaign lock は再開できなくなる。** `core.py` / `dsg.py` / `parse.py` は
  enforcement source closure に入るので、bytes を変えた時点で
  `ident.verify_against_lock` が `contract-loader-drift` で拒否する。
  B-10 正式走を分割で再開する運用は、本変更の後は新しい lock で始め直す必要がある。
  検査器を変える限り不可避である。

## 既定の並列度は所要でなく記憶量で決めた

**所要は並列度 16 で飽和するのに、記憶量は比例して増え続ける。** 48 は 16 と同じ所要に
1.93 倍の記憶量を払う最悪の点である。B-10 全規模 (17M commit、本測定の 25 倍) へ
線形換算すると次になる。

| 並列度 | 17M commit での峰値の見積り |
|---|---:|
| 8 | 58.5GB |
| 16 | 73.5GB |
| 24 | 92.5GB |
| 32 | 112GB |
| 48 | **142GB** |

計算ノードのユーザ利用上限は 115GiB (= 123.5GB) である。**当初の既定
`min(file 数, 割当てコア数, 48)` は 48 file・48 core の正式走でちょうど 48 を選ぶので、
全規模では容量を超えて落ちる。落ちれば認証済み成果物はゼロになる。**

> **但し書き (D1529)。** 「B-10 全規模 (17M commit、本測定の 25 倍)」という規模は、欠測 attempt を
> 含む read-heavy 観測から採った値で、表の 58.5-142GB はその規模への線形換算である。並列度ごとの
> 記憶量の実測は合成 trace のもので欠測とは無関係である。値を無効にするものではなく、規模を
> 取り直した再計算は行っていない。

そこで**既定の上限を 16 へ下げた**。明示指定した `workers` の上限 48 は変えていない。
16 が最適だとは主張しない — 根拠は「16 までは並列化前より速くかつ軽く (2.94GB 対 3.60GB)、
それ以上は所要が縮まないのに記憶量だけ増える」という 1 点の実測である。
既定・1・16・48 のいずれでも判定は同じ `result_to_dict` を返すことを確認した。

## main 取り込みの合成監査

`orchestrator/verifier/{core,dsg,parse}.py` は enforcement source closure に入るので、
main 取り込みは両側が同じ実装面 file を変更する形になった (`orchestrator/tests/test_verifier.py`
1 本。main 側は T-2176 の負例 fixture 追加で production 差分 0)。
自動 merge は競合なしで通ったが、**競合なしは合成の保証にならない** (F481) ため、
Codex `role=author` の合成監査を別に行った。

判定は「保たれている」。子は両側が変更した実装面 path を積集合から自分で取り直し、
merge の `--cc` patch body が空であること (手動解決による片側書き換えが無い)、
main 側 41 行と wave 側 416 行が両方生きていること、import・helper・定数の衝突が無いこと、
fixture 台帳と実 fixture が一致することを確認した。
**`orchestrator/verifier/` に main 由来の差分は 0 である。**

さらに、main の新 fixture `r9_dense_cycle4` が既定 2-worker の並列経路を通り、
逐次と同じ 4 辺・単一 G2 cycle を構成することを静的に追った。
これは実測でも裏づけられている — **変異 M5 (rw 辺の脱落) の赤が 18 件から 19 件へ増え、
増えた 1 件が `test_dense_cycle4_clean_g2` だった。** main の新 fixture は
並列経路を通って意図どおり rw 辺の防壁として働いている。
