## 5. 検査器の値をどう挟んだか — 2 系統の換算

### 5.1 合成 trace の単価からの外挿 (T-2191)

T-2191 は read-heavy 相当の合成 trace で、並列化前の検査器だけを段別に計った
(`output/insights/2026-09-02/t2191-verifier-parallel/README.md`):
1 commit あたり 59.2 μs (170k txn)、65.3 μs (340k txn)、67.5 μs (680k txn、同 insight の
「旧コード 45.92s」)。**規模とともに単価が上がる** (170k → 340k で +10.4%、340k → 680k で +3.4%)。
16.83M〜17.19M commit へ当てると、

- 最大の実測単価 67.5 μs をそのまま掛けて **1136〜1161 秒** (81〜82%)
- T-2191 自身の局所一次外挿で **約 1213 秒** (86%)
- 最小の単価 59.2 μs では 996〜1018 秒 (71〜72%)

この換算は 3 点を除くと**規模 25 倍の外挿**であり、login node (16 ユーザ共有、load 20〜30) で
計った単価である。上側へ外れる (単価が規模で伸びる) 可能性を T-2191 自身が書いている。

### 5.2 並列化後の走行との差分 (本 wave の純増)

同じ workload・同じ 4 変種を、並列化後の検査器 (source `2a338449b`、`d719c1e35` /
`da45b6b2b` / `76b824f94` を含む、既定 `workers` 16、bnode088、2026-09-05) で完走した
`acf840c8` の WAL 90 反復 (`acf840c8-intervals.tsv`) と対にした。

| 変種 | 直列 (`ed8a676b`) 中央値・帯 (秒) | commit | 並列 (`acf840c8`) 中央値・帯 (秒) | commit | 差 (秒) | 端-端比 |
|---|---|---|---|---|---:|---:|
| `84319b1127a6` | 1425.4 (1374.8〜1436.2) | 16.83M〜16.91M | 602.0 (595.5〜612.0) | 16.69M〜16.84M | 823 | 2.37 |
| `5053f150932e` | 1388.5 (1372.5〜1465.6) | 17.02M〜17.19M | 607.4 (603.9〜626.9) | 16.87M〜17.01M | 781 | 2.29 |
| `292d58f1dad8` | 1429.8 (1346.9〜1444.2、3 反復) | 16.92M〜16.94M | 611.8 (601.1〜619.8) | 16.77M〜16.94M | 818 | 2.34 |
| `602b4ce9c788` | 415.3 (401.7〜427.4) | 5.54M〜5.62M | 177.6 (173.1〜178.7) | 5.53M〜5.58M | 238 | 2.34 |

両 run で変わったのは検査器 (5) だけで、ベンチ本体・trace・数え直し・dir 操作は同じ code
(`_run_trace` と `_run_one_repetition` の段構成は `0a07481b8` と `2a338449b` で同じ) である。
直列の区間を `I_s = V + R`、並列を `I_p = V/s + R` と置く (V = 検査器、R = それ以外、
s = 計算ノードでの検査器の倍率)。17M 級で `I_s = 1408.8`、`I_p = 607.4` (3 変種 15 反復の
中央値)、差 `D = 801.4` 秒。

- **端-端比 2.29〜2.37 は、login node で計った検査器単体の倍率 2.22 (workers 16) より大きい。**
  R ≥ 0 なので端-端比は検査器単体の倍率を超えられない。**よって計算ノードでの検査器の倍率 s は
  2.32 以上** (R = 0 でも 1408.8 / 607.4 = 2.32 を下回れない) であり、login node の 2.22 は
  共有のぶん抑えられていた (T-2191 が書いたとおり)
- `V = D / (1 − 1/s)` なので、s = 2.6 (T-2191 の Amdahl 漸近上限) なら **V = 1302 秒 (92%)、
  R = 107 秒 (8%)**。s = 3.0 なら V = 1202 (85%)、R = 207。s = 4.0 なら V = 1069 (76%)、R = 340
- R の構造上の下限 (§4 の 2 + 3 + 7 ≈ 24 秒) から **V ≤ 1385 秒 (98%)**、s ≥ 2.37
- 5.5M 級 (`602b4ce9c788`) でも同じ形になる: D = 237.7、s = 2.6 で V = 386 (93%)、R = 29 (7%)

### 5.3 2 系統の交わり

5.1 は V ≤ 1213 秒 (単価が 17M でも伸びないなら 1136〜1161 秒) を、5.2 は s = 2.6 で
V = 1302 秒を指す。**両者が同時に成り立つのは、計算ノードでの倍率 s が 2.6 を超えている場合か、
合成 trace の単価が 17M 規模で 12〜20% 伸びている場合**で、どちらも既存の記録と矛盾しない
(前者は login node が共有だったこと、後者は単価が規模で伸びる実測から)。どちらか一方に決める
記録は無い。**したがって V は 1069〜1385 秒 (76〜98%)、R は 24〜340 秒 (2〜24%) と書く。**
R の大半は 2' (trace の flush と process 終了) に帰属するはずだが、それを計った記録は無い。

## 7. 本書が保証しないこと

- **反復の内側の時刻は測っていない。** §4 の値は「実測 (perf 相の bench 実時間、dir 削除の
  上限)」「換算 (T-2191 の単価、差分帰属)」「計時なし (trace flush)」の混合で、検査器の
  1069〜1385 秒は 2 系統の換算の交わりである。点推定ではない
- **計算ノードでの検査器単体の倍率 s は測っていない。** 2.32 以上という下限は端-端比から
  従う必然だが、上限を置く根拠は login node の Amdahl 漸近 2.6 だけで、計算ノードでは
  それを超えうる。R の上限 (340 秒) は s = 4.0 を置いた場合の値で、s に上限が無ければ R の
  上限も無い (ただし R ≤ I_p = 607 秒は自明に成り立つ)
- **合成 trace の単価を実 trace へ当てている。** T-2191 の合成 trace は 1 txn 10 操作・
  95% read・鍵の版密度を実配分へ合わせたものだが、実 trace ではない。実 trace で検査器だけを
  計った記録は無い
- **2 つの run は node が違う** (bnode022 と bnode088)。`docs/pegasus-node-variance-protocol.md`
  の node 間差 1〜2% は throughput の値で、検査器の実時間について測ったものではない
- **欠測 attempt を含む** (`292d58f1dad8` の 3 反復、D1529)。除いても結論は変わらない (§2)
- **並列化の効果や検査削減の是非には触れない。** §5.2 の並列走行は差分帰属の材料としてだけ使った
- 当時の判定 (`correctness_certified`、`serializable`) は本書で 1 件も変えない (絶対規律 7)
