### 5.3 等 R 模型の試算 (条件付き)

直列の区間を `I_s = V_s + R_s`、並列を `I_p = V_p + R_p` (V = 検査器、R = それ以外) と置く。
一般には `I_s − I_p = (V_s − V_p) + (R_s − R_p)` で、観測した差を検査器だけに帰属するには
**`R_s = R_p` (両 run で検査器以外の実費が等しい) を仮定しなければならない。** その上で
`V_p = V_s / s` (s = 計算ノードでの検査器の倍率) と置くと `V_s = D / (1 − 1/s)` になる。
変種別の差 D = 781〜823 秒 (17M 級)、pooled 中央値では 801.4 秒。

| s の仮定 | V_s (17M 級、D = 801.4) | 割合 | R |
|---:|---:|---:|---:|
| 2.6 (T-2191 が login node で見た Amdahl 漸近) | 1302 秒 | 92% | 107 秒 |
| 3.0 | 1202 秒 | 85% | 207 秒 |
| 4.0 | 1069 秒 | 76% | 340 秒 |
| 5.0 | 1002 秒 | 71% | 407 秒 |
| s → ∞ | 801 秒 | 57% | 607 秒 |

- **等 R を仮定すると**、区間全体の所要比 2.29〜2.37 は検査器単体の倍率を超えられないので
  s ≥ 2.32 (R = 0 でも 1408.8 / 607.4) が従う。login node で計った検査器単体の 2.22 (workers 16)
  より大きいことは、等 R の下では計算ノードの倍率が login node より高かったことを意味するが、
  原因 (共有による抑制など) はこの差からは確定しない
- **等 R は実証していない。** node が違う (bnode022 / bnode088)、trace が同一でない (commit 数が
  1% 程度違う)、code の段構成は同じだが完全に同一ではない (`2a338449b` の `_run_one_repetition` は
  検証への追加引数と `proof_surfaces` の WAL 出力を持つ、段 6 レビューの確認)。`workers` = 16 の
  並列枝が実際に発火したことも WAL からは確認できない (失敗時は逐次へ落ちる)
- **s に上限を置く根拠は無い。** 表の 2.6〜4.0 は例示で、s が大きいほど V は 801 秒 (57%) へ
  近づく。したがってこの模型から出る値は「等 R かつ s をこう置けば」という試算にとどまる
- 5.5M 級 (`602b4ce9c788`) でも同じ形になる: D = 237.7、s = 2.6 で V = 386 (93%)、R = 29

### 5.4 2 つの試算と §4 の関係

5.1 (71〜86%) と 5.3 (s = 2.6〜4 で 76〜92%) は重なるが、どちらも仮定付きで、どちらかに決める
記録は無い。§4 の「Python 側 約 91%」は timeout 契約からの条件付き上限の帰結で、数え直しの換算
(約 20 秒) を引けば検査器 ≈ 90% になる。3 つの見方がいずれも「検査器が最大の項で、ベンチ本体は
1 割未満」を指す点は共通で、**本書が主張するのはそこまで**である。

full-scale 10 回。§2 の但し書き (D1529) のとおり、いずれも欠測 attempt を含む帯から出している。

| 積み方 | 1 回 | 10 回 | `12:00:00` の倍率 |
|---|---:|---:|---:|
| D1489 (23 分を max として) | 1380 秒 | 3.83 時間 | 3.1 |
| 帯の中央値 (本書) | 1408.8 秒 | 3.91 時間 | 3.07 |
| 帯の上端 (D1554) | 1465.6 秒 | **4.07 時間** | **2.95** |

「23 分」は中央値なので、10 回積むと上端より 0.16 時間 (9.5 分) 少なく見える。走行が上端で

**walltime `12:00:00` は本書で動かさない** (D1489 の根拠には attempt 全損の非対称性が残る)。

参考として、同じ変種を並列化後の検査器で走らせた `acf840c8` の帯 (595.5〜626.9 秒) で
10 回積むと 1.65〜1.74 時間になる。これは既存の記録の事実であって、walltime の再裁定でも
並列化の処方でもない。

## 7. 本書が保証しないこと

- **反復の内側の時刻は測っていない。** §4 の「ベンチ process 約 120 秒以下、Python 側 約 1289 秒」は
  timeout 契約からの条件付き上限で、検査器の値は換算・試算である。点推定は書かない
- **120 秒は timeout の設定値であって、ベンチ process の実時間でも厳密な上限でもない。**
  `subprocess.run` の timeout は子の起動後 `communicate()` から計るので、起動直後に親が遅延した分は
  含まれない (その遅延を測った記録は無い)。実時間そのものの記録も無い。trace 無し版の別走実測
  3.35〜3.42 秒は参考値で、trace 有効版の下限として測ったものではない
- **数え直しの約 20 秒と trace dir 削除の 0.36 秒以下は、それぞれ合成 trace の換算と最後の 1 回の
  観測である。** 他の反復の削除、実 trace での数え直しは計っていない
- **等 R 模型 (§5.3) の前提は実証していない**: 両 run の検査器以外の実費が等しいこと、
  `workers` 16 の並列枝が発火したこと、計算ノードでの検査器倍率 s の値。s の下限 2.32 は等 R の
  下でだけ従う
- **合成 trace の単価を実 trace へ当てている** (§5.1)。実 trace で検査器だけを計った記録は無い
- **2 つの run は node が違う** (bnode022 と bnode088)。`docs/pegasus-node-variance-protocol.md`
  の node 間差 1〜2% は throughput の値で、検査器の実時間について測ったものではない
- **欠測 attempt を含む** (`292d58f1dad8` の 3 反復、D1529)。除いても中央値は 1398.7 秒で
  結論は変わらない (§2)
- **並列化の効果や検査削減の是非には触れない。** §5.2 の並列走行は差分の材料としてだけ使った
- 当時の判定 (`correctness_certified`、`serializable`) は本書で 1 件も変えない (絶対規律 7)
