## GRACE の値の過不足

**判断：2.0 秒を動かす根拠は不足している。暫定値として維持し、重負荷を保証する説明を削る。** 観測最大値に対して約14.94倍だが、倍率だけでは過大・過小のどちらも証明できない（`brief:27`、`probe/overshoot-T8.txt:2`）。

**real・総予算との競合は存在する**。overall cap は全体の待機を制限するが、後続 commit の判定機会を保護しない（`tools/check_branch_rescue.py:1568`、`:1985`、`:2065`）。

- 沈黙が続く仮定では、子待機の計算上限が `64×8=512秒` から `64×10=640秒` へ増える。
- inventory 等を無視しても、300秒で完了できる待機枠は概算37件から30件へ減る。
- ただし観測された子は約 `T+0.10〜0.134秒` で終了しており、毎回２秒を消費しない。

成果物影響：予算境界では後続の `assessment_reason=overall-timeout` が増え得る。これは沈黙時だけでなく、正常な報告回収の小さい追加時間でも境界上では起こる。

**疑い・実際の増加件数は不明**。提供ログには沈黙した checker はなく、子単体８走すべてが理由を返す。ただし「現状、沈黙 checker が存在しない」までは確認できない（`probe/overshoot-T1.txt:1`、`probe/overshoot-T8.txt:1`）。

成果物影響：640秒を通常所要として扱えば受入 wall を過大評価し、逆に後続への影響ゼロと扱えば判定件数を過大評価する。

小さくすれば重負荷時に `checker-timeout` へ戻る余地が増える。現時点では値変更より、根拠の適用範囲を限定する方が最小である。

## test 所要と flake

**real・+5秒を満たす設計余裕が足りない**。公称 `1.3+3.0+0.5=4.8秒` で、残り0.2秒しかない。plan の4.82〜4.96秒は未実測の見積りである（`plan:82`、`:90`）。

成果物影響：起動・環境準備・scheduler 遅延だけで test 所要の受入条件を超え得る。

最小の修正案：

- **正例だけ T=0.5** とし、sleep は `T+0.3=0.8秒`。
- 沈黙負例は T=1、overall 負例は `(T=5, remaining=0.5)` を維持。
- 公称合計は **4.3秒**。正例の終了余裕1.7秒、M4 用の負例の時間差も維持できる。
- 負例２ケースの parametrize は重複削減にはなるが、実行時間はほぼ減らない。

関数直呼びには rescue CLI の１秒下限が適用されない（`tools/check_branch_rescue.py:1565`、`:2161`）。両方の T を0.5にすれば3.8秒になるが、M4 の２秒と待機下限2.3秒の差が縮むため、優先しない。

**疑い・load 60超での flake 耐性は未確認**。正例の1.7秒、overall 負例の１秒の余裕は、load 値だけから十分と断定できない（`plan:135`）。overall 負例の上限は、例えば３秒でも M2 の約７秒とは分離でき、正常時の所要を増やさず遅延耐性を上げられる。

成果物影響：正常コードの偽赤、または親の遅延が早すぎる打切りを隠す変異の偽生存が起こり得る。+5秒の達成は後段実測まで未確定。

## scope 外の混入

## 親 brief の実測値と一般化

**real・観測範囲と一般的性質が混ざっている**（`brief:6`、`:15`、`:27`）。

## docs 変更の必要性

**real・P6 は必要。ただし２行程度で足りる**。現文は「既定８秒で checker-timeout」と説明しており、修正後の通常の期限報告と一致しない（`docs/unreachable-object-ledger.md:91`）。

最小の逐語案：

> landed 判定の子予算は既定8秒（`--assessment-timeout-seconds`、上限60）で、期限報告を回収できれば `assessment-timeout`、親が子予算＋2秒と全体残時間の短い方で打ち切れば `checker-timeout` となり、いずれも rc `2` になる。
> 最大待機の見積りは判定件数×（子予算＋2秒）に inventory 等を加え、必要に応じ全体の `--timeout-seconds`（既定300、上限900）を調整する。

P6 の「予算＋余裕でも応答しない場合」だけでは overall cap による早期打切りが抜ける（`brief:31`）。plan の案はこの点を含めている（`plan:120`）。

## 変異 matrix の本数

**real・指定資料には「等価変異１本」の定義がない**。brief／plan にあるのは M1〜M4 だけであり、５本目の必要性は検査できない（`brief:30`、`plan:98`）。

成果物影響：未定義の１本を受入へ加えると、根拠なく変異実走と記録時間が増える。追加しない。

| 変異 | 評価 |
|---|---|
| M1：GRACE→0 | 必須。追加猶予がなければ正例を回収できないことを示す。 |
| M2：overall cap 除去 | 必須。明示された親打切り上限を守る負例。 |
| M3：子にも GRACE 加算 | 有用だが、変更行そのものの最小検証ではない。子予算不変の明示条件を守る追加１本。 |
| M4：加算→max | **削除または別枠化候補**。現設計で赤になるのは elapsed 下限だけ。 |

**real・M4 の KILLED 帰属が弱い**（`plan:103`）。沈黙する子は２秒でも３秒でも同じ `checker-timeout`、rc=None、complete=False を返す。赤理由は一つに絞れても、理由 JSON の受理集合が変わった証拠にはならない。DW-M01 の単一理由性と、DW-M03/M08 の kill 意味論は別条件である（`docs/dev-wave/mutation.md:7`、`:18`、`:62`）。

成果物影響：elapsed の感度確認を、報告回収を保護した KILLED として変異台帳へ過大計上する。

**変更箇所と必須負例を押さえる最小は M1・M2 の２本。子予算不変も独立に守るなら M3 を含む３本**。M4 のために正例 sleep を延ばしたり、自己検査を復活させる必要はない。
