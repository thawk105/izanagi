## 所見 (CB-1 …)

**CB-1 — 推すのは A-3 と、4 経路の test 修正を同じ実装 wave に収める案。**
親の「production 整合が先」という判断には賛成する。ただし「設計 wave → 再裁定 → 実装 → 着地後に test 追随」は、余分な直列工程と発効前の受入問題を残す。今回の相談結果を親が採択し、新 D・設計・実装・境界 test・変異 matrix を一つの変更単位にするのが最短である。実装は D95 に従って Codex author が担当する。

A-3 は実現可能性を証明済みではない。**同等性を境界 test で確認できることを着地条件とする推奨**であり、不一致を見つけた場合に検査を省略して通す授権ではない。

**CB-2 — 最大の穴は「active 後の解決」と「active 前の受入」を混同していること。**
A-1～A-3 は承認済み active v2 を前提とする。一方、README §5 では A / X は chain・G の取り込み後の人間手番である。したがって、未発効の chain checkout で実 receipt を解決する受入 test は、production 整合だけでは救えない。

29 node についても「receipt が valid に戻れば現在の早期拒否は解ける」は正しいが、**A の実装だけで自動的に 29 本が緑になる、は成立しない**。`_run` は v2 gate 等を置換していても、receipt は実 root の解決値を使っている。さらに対照走がなく、後段に別の失敗がないことも未確認である。

**CB-3 — test 側は次の四つを同時に扱う必要がある。**

| 経路 | 必要な扱い |
|---|---|
| (i) 10 node | T-080 移行前の clean な履歴・output を持つ管理された fixture にする。draft の実走査と既存の欠陥注入は維持する。 |

(i)(ii) の**合成 tree 化という実装方式だけが唯一解ではない**が、実 checkout の現在の成果物から test 前提を切り離す修正は必要である。特に (ii) を production の A で通すと、D2077 の official clean scan を緩めることになる。

D96 が直接要求するのは受理集合の境界 test の同時更新である。今回の fixture 修正すべてを同条文の直接義務と断定する必要はないが、受入成立に必要なので同じ wave に含める。

**CB-4 — D2077 の仕様と、oracle への波及は分けるべきである。**
D2077 の決定文・理由は「成果物のある branch で以後の **official 床値**を起動できない」と定めている。したがって、(ii) の production 拒否は仕様どおりであり、その tree で成功を期待する test 前提が不適合である。

一方、candidate → 批准 → oracle まで恒久的に拒否することは、その決定文から導けない。receipt の zero-hit と v2 closure の期待 hit が併存する問題は、段階間の整合欠落として扱うのが妥当である。

「だから main に chain を置かないのが本来の運用」ともならない。D2120 項 2(a) はその帰結を承知で main 取り込みを選んでいる。D の運用も技術的には可能だが、既裁定を変更し、別 branch に A 相当の修正を運ぶ必要がある。

**CB-5 — hold は解決にならず、F1000 の射程にも注意が必要。**
F1000 の「1 件固定」は **flaky 登録簿**の契約であり、growth 登録簿全体を 1 件に制限する規則ではない。ただし、現行 DW-O18 は再赤・決定的赤でも hold 登録しないと明記する。

既存の growth hold は計算量増大を理由としており、今回の既知の意味論的不整合を隠す一般権限ではない。「A 着地まで」という時限指定にも、読んだ資料中に自動失効・解除を保証する制度はない。45 node の一括 hold は検出力を落とすうえ production 拒否を残すため、不採用とする。

**CB-6 — 並行 wave の前提は既に変わっている。**
読取り時点の事実は以下だった。未 commit 差分は参照していない。

## 順序 (並行 wave・受入・人間手番)

現在確認できた状態からは、次の一本に絞る。

1. **A-3＋四経路の test 修正を実装して先に land する。** chain のない main に着地させ、合成履歴で未発効・発効済み双方を検証する。両状態を green の対象にするとは限らず、production の未発効拒否は維持する。
2. **G wave を chain/X2/G の残作業統合単位にする。** 保存 branch の X2 を通常 merge で取り込み、X1'・G の元 commit と bytes を保存する。(a) の既に取り込まれた停止記録を再度独立 land する工程は作らない。
3. 実装 wave の fold 後の main を固定 SHA で取り込み、その統合 tip で受入を取って land する。受入後に main が進めば、既存手順に従って更新・再受入する。
4. 人間が A → X を連続 commit し、批准を検証する。spec のレビュー準備は実装と並行できるが、承認済みとは扱わない。
5. W-4 の承認と manifest 作成を完了し、v2 経路の gate が `allowed: true` となることを確認して W-5 へ進む。

元の「二つの chain-bearing wave」を維持する場合は、先発も実装修正後の main を取り込み、後発はさらに**先発 fold 後の main**を取り込んで再受入する。双方に同期は必要だが、「merge-base が二つになる対策」が双方で同じ時点に必要なのではない。現在確認した merge-base は各一つであり、rc=23 は実測した現障害ではない。

また、runbook の「毎回 v1 P3 の拒否 2 件 exact」は、chain 導入後の oracle 段階へそのまま適用できない。段階別の preflight を同じ変更で明確にし、未知の refusal を単に期待値へ追加しない。

## 推す択と根拠

**A-3＋test の同時修正を推す。**

A-3 は receipt の静的検証・履歴・epoch 束縛を残し、衝突する live scan の責務だけを承認済み v2 の full launch validation へ移せるため、変更範囲を最も限定しやすい。

- **A-1:** 同じ occurrence 検証を receipt 側にも実装すると、二重走査と検証ロジックの乖離を招く。同じ検証結果を共有する形へ絞るなら A-3 に近づく。
- **A-2:** receipt 全体を不要にすると、静的証拠と campaign epoch の代替まで設計対象が広がる。最短経路として選ぶ根拠がない。
- **B:** 必要な test 修正部分は採るが、単独案としては oracle に届かない。
- **C:** 受入の検出力を失っても production は拒否する。費用に対して進展がない。
- **D:** main の official 起動可能性を残す運用価値はあるが、今回は既裁定の変更と別 branch の維持を増やし、根本修正を省けない。

A-3 では、active pointer の存在だけで委譲してはいけない。**full validation の成功と同一の検証対象への束縛**を必要条件にし、余分な hit、closure 改変、無効な承認、receipt の静的欠陥、epoch 不整合を拒否する。official 床値の clean scan と、active v2 がない場合の既存検証は維持する。

## 総括

親の A 推奨は方向として正しい。修正すべき点は、**A-3 に絞り、発効前の受入を成立させる test 修正まで同時に行うこと**である。
