## この段の仕事

これは「gate を 1 byte も変えずに、SS2PL runner の condition gate 拒否を閉じる 2 案 (ii)(iii) の採否材料を計算ノードで実測する probe」の設計である。採否は決めない。**成果物は repo に入らない** (job dir に置く試作 patch・probe・shadow 登録簿)。repo に入るのは insight (docs) だけ。

brief の P1〜P6 を前提に、**file:line 粒度の実装計画**を起草する。brief も誤りうるので、行番号・gate の判定順・patch の `#if` 構造を現物で検算し、ずれは明示する。実装子 (Codex author 1 単位、workspace-write、probe 用 worktree に書く) がそのまま使える粒度に書く。

計画に含めるもの:

1. **試作 patch (`ss2pl-lock-protocol-study-define-only.patch`、現行 patch からの派生) の変更一覧。** 各変更を「現行 patch の行範囲 → 変更後の形」で書く。最低限: (a) `ss2pl_lock.hh` で `rwlock.hh` と `ss2pl_study_lock.hh` を**無条件** include し、`using ReaderWriteLock = SS2PLStudyLockT<…>` と stock の `class ReaderWriteLock` (`include/rwlock.hh`) の名前衝突をどう避けるか (候補: 試作では stock 側 header を触らず、study lock の class を `#if SS2PL_LOCK_IMPL == 1` で囲んだうえで `rwlock.hh` の中身を `#if SS2PL_LOCK_IMPL == 0` で囲む patch hunk を `include/rwlock.hh` に足す、など。S arm の前処理 bytes が stock と一致する条件で選ぶ); (b) 新規 header 3 本を `#pragma once` から include guard へ (親の実測: `-E -P` で `#pragma once` は 7 空白 + 改行の残渣、include guard は 0 byte); (c) `ss2pl_wfg.hh` の宣言と `wfg.cc` の定義を `#if SS2PL_WFG_DIAG` で囲み、`wfg.cc` を source list に**無条件**で置く (中身が空の TU が `-Wall -Wextra -Werror` で通るか: 空 TU は ISO C++ で警告になりうる → `-Wpedantic` の有無を `set_compile_options` で確認); (d) CMake の `DLR` marker を stock どおり `DLR1` 固定にし、`SS2PL_DLR` を純 define にする。stock transaction.cc の `#ifdef DLR0 / #elif defined(DLR1)` 分岐を `#if SS2PL_DLR == 0 / #elif SS2PL_DLR == 1` へ付け替えるか (IMPL=0 で DLR が効く = 非 inert DLR=0 vs 1 が通る)、DLR=2 && IMPL=0 の扱い (`#error` にすると arm B/D の DLR=2 要求は前処理失敗で red。試作では B/D を scope 外にしてよいが、その帰結を書く); (e) `ss2pl_lock.hh` の `#error "SS2PL_DLR=n requires DLRn"` 撤去; (f) transaction.cc の abort 二重計数除去 (`INERT_DECLARED_DIFFERENCES` の 1 件目) を `#if defined(SS2PL_WORKLOAD_YCSB) && SS2PL_WORKLOAD_YCSB` で囲む案と、囲まずに S arm の gate 比較を red のままにする案の**両方を cell として取れる**か (試作 patch を 2 版にするか、1 版で define を足して切り替えるか)。util.cc / bomb の宣言済み差分は owner TU (transaction.cc) の閉包に入らないので gate には無関係 — 検算せよ。
   また、試作 patch が **runner の静的契約**をどう満たす/破るかを列挙する: `validate_abort_counter_ownership` (:1061、token 走査は `#if` を見ない → 囲った増分も数える?)、`_study_lock_header_declarations` / `validate_default_stock_lock_absence` (:1334-1500、S arm の前処理に study lock の識別子が無いことを見る → 無条件 include でも `#if` で消えるので通るか)、`_validate_compile_definitions` (:911、`CACHE_TO_DEFINE` の 8 define が argv にあるか。`DLR1` 固定で `SS2PL_DLR=0` のとき矛盾を検出する検査があるか)。これらは pure Python なので probe が login でも走らせられる。
2. **shadow 登録簿の作り方。** `condition_meaning_gate.py` は相対 import (`from . import source_digest` 等) を持ち `_patch_changed_paths` が `Path(__file__).resolve().parents[2] / spec.patch_rel` を読む。案: job dir に `shadow/orchestrator/campaign/condition_meaning_gate.py` (登録簿の SS2PL 4 行だけ差し替え、他は byte 同一) と `shadow/patches/<試作>.patch` を置き、probe が `importlib.util.spec_from_file_location` で **package 名 `orchestrator.campaign` の下**に読み込む (`__package__` を設定して相対 import を repo の実 package へ解決)。差し替える行: `target` を `tpcc_ss2pl.exe` に (P1)、`SS2PL_LOCK_KIND` の companion を外す版と外さない版 (P2) — 2 版の shadow を作るか、1 版で `DEFINE_SPECS` の行を差し替えるか。diff が「登録簿の行だけ」であることを probe が `difflib` で検算して受領証に残す形。**repo の gate module は読むだけで変えない。** 代案 (プロセス内で `_DEFINE_SPECS` を書き換える) との比較と、どちらが監査しやすいか。
3. **cell matrix と期待 `reason_code`。** 行 = {arm S (inert ×4), arm phase1 (非 inert ×4)} × 列 = {現行 patch / 試作 patch} × {現行登録簿 / shadow (target=tpcc, companion あり) / shadow (target=tpcc, companion なし)} × {pristine / warm-up 後}。全部で何 cell になるか、どの cell が冗長で省けるか (例: pristine は現行 patch × 現行登録簿の phase1 だけで十分か — S arm は前処理前に `owner-tu-unresolved` で落ちるので pristine の証拠にならない、を検算)。各 cell の期待 `reason_code` を gate の判定順 (configure → owner entry → 前処理 → compiler identity → argv → 閉包 → bytes) で予測し、「予測と実測が違ったら何が分かるか」を書く。gate 1 要求の所要 (configure 2 回 + 前処理 2 回) と総所要の見積り (walltime 00:30:00 に収まるか。収まらなければ cell を落とす優先順位)。
4. **probe (`t2737_gate_probe.py`) の設計。** 引数: `--repo-root --patch-current --patch-redesigned --shadow-root --scratch-root --gflags-prefix --glog-prefix --thirdparty-root --jobs --output --cells <選択>`。手順: runner の production 関数 (`validate_required_commands`、`verify_canonical_submodule`、`clone_network_free`、`_apply_patch`) で stock clone 1 本 + patched clone 2 本 (現行 / 試作) を作り、gate は **runner の `_require_condition_gates` (:1980) と同じ 3 呼び出し** (`capture_define_inputs` → `make_define_request` → `evaluate_define_supply_effectuation` / `evaluate_define_runtime_meaning` → `require_condition_gate_family`) を probe 内で再現して **record の canonical JSON を全部保存**する (runner の関数は失敗時に文字列しか残さないため)。`configure_args` は runner の `_require_condition_gates` と同じ組み方 (:1988-2003)。warm-up は前 wave と同じ `cmake --build --target masstree_build` を試作 clone の別 build dir で 1 回。pristine cell は warm-up **前**に走らせる順序制御。試作 patch の plain build (`cmake --build --target ycsb_ss2pl.exe` を S と phase1 で 1 回ずつ、`-Werror` で通ることの確認、`_target_compile_entries` + `_validate_compile_definitions`)。`PBS_JOBID` は前 wave の `discover_pbs_jobid` と同じ。path に `wfg` を含めない。`--selftest`: 合成入力で (a) shadow diff 検算が「登録簿の行だけ」を通す/通さない 2 例、(b) cell 予測表の schema 検査、など login で走る形。起動形 (`python3 -B <job dir>/probe/t2737_gate_probe.py`、runner は `ROOT` を `sys.path` に入れる)。**generic dispatch は clean env・cwd = 投入 worktree** (`python3 tools/pegasus/dispatch_compute.py --task generic --walltime 00:30:00 -- python3 -B <絶対 path> …`)。
5. **login で親が先に確かめられること。** configure と `g++ -E -P` は login で可 (`cmake --build` は guard が拒否)。試作 patch を当てた木の S arm の transaction.cc を tpcc target の compile entry で前処理し stock と `cmp` する手順 (gate CLI `python3 -m orchestrator.campaign.condition_meaning_gate --source-root … --stock-root … --macro SS2PL_LOCK_IMPL --requested-value 0 --default-value 0 --stock-comparison --configure-arg=-D… --cxx c++` を shadow で回す形か、probe の `--cells` で login 向け subset を指定する形か)。ただし login の永続 cache は汚れているので pristine の証拠は取れない — 計算ノードで取る。
6. **insight に載せる表の形** と、(ii)(iii) それぞれについて「成立した比較 / 成立しない比較 / 成立に要る変更の層 (patch / 登録簿 / runner) / 費用と隙間 (P3 の TU 束縛、P2 の直交性)」をどう 1 表にするか。
7. **リスク・未確定点。** `c++` が計算ノードで何に解決されるか (前 wave の argv は `x86_64-linux-gnu-g++-11`)、`-E -P` の空行畳み込みが版依存でないか、`__FILE__` を含む header (`root_dependent_builtin_paths`) が S arm の root 置換判定に効く条件 (`location_only` は `replacement_count >= 1 and has_root_dependent_builtin` を要求 — bytes 完全一致なら不要)、shadow module の読み込みで `source_digest` 等の相対 import が repo の実 module へ解決されることの確認方法、`_patch_changed_paths` が shadow の patch を読むことの確認方法、stock clone に companion を渡す cell で `configure-failed` (CMake 警告) が出る前に `owner-tu-unresolved` へ届かない順序 (configure が先)。
