## 評価の前提

指定資料はすべて読めた。静的読解のみで、pytest・計測・ファイル変更は行っていない。

以下、`T` は `orchestrator/tests/test_s8b_oracle_driver.py`、`V` は `orchestrator/campaign/t080_freeze_migration.py`、`H` は `orchestrator/tests/growth_test_holds.py`、`plan` は指定の `s2-plan.md` を指す。資料名だけの参照は指定された `verbatim/` 内である。

plan による C の上限解釈の撤回、A−S の因果解釈の限定、wrapper の包含関係の処理は妥当。ただし、分割の検出力、固定費の帰属、model と判定条件に修正が必要である。

## must-fix

**M1 — 「固定費」を node 内外で取り違えると、分割の追加費用を落とす。**

根拠：T:903–916、943–955、plan:234–236、291–300、`sessions-fixed-cost-breakdown-since-0917-0900.md`:3–11。

共有 base の削除は `atexit` に登録され、最後の worker が実行する。したがって `get + copytree + pytest teardown` だけでは fixture の生涯費用を覆わない。分割で複製を増やした場合の終了費用も、node teardown にすべて現れるとは限らない。

また、既存資料の固定費は次のとおりで、「全 shard 共通の66秒」ではない。

| 指標の中央値 | shard-0 | shard-1 | shard-2 |
|---|---:|---:|---:|
| 固定費、3 shard が揃う95 session | 67.2秒 | 64.3秒 | 63.6秒 |
| collection＋worker 起動、内訳資料 | 59.4秒 | 60.3秒 | 60.0秒 |
| 最終 test 終了後、内訳資料 | 7.8秒 | 3.4秒 | 3.1秒 |

後二行の母集団は95／97／97 sessionで、第一行と混ぜて加算できない。93 session 一覧そのものは shard-0 しか含まないため、同じ93件の shard-1/2 値は提示資料からは再計算できない。

**成果物への影響：** 固定費を一定とした分割 model が、追加複製・終了処理の費用を過小評価する。

**是正案：** 三分法は概況として残し、次を明記する。

- node：setup、base取得、複製、検査、その他、teardown。
- session：worker 起動、collection、receipt memo prewarm、実行中の空白、worker 終了・共有 base 削除、集約・JUnit、process 終了。
- `wall−最大占有`：以上の一部を含む**残差**。一定の独立作業ではない。

本 wave の既定観測で開始前・実行区間・終了後の粗い分解は可能。ただし controller の時刻だけでは、worker 起動と collection、`pytest_collection_finish` 内の prewarm、JUnit 集約と xdist 終了を独立に同定できない。prewarm は該当処理の前後、共有 base 削除は `close` の前後を観測しなければ内包されたままである。追加観測を採らない項は「未分離」と表示し、終了残差をすべて「JUnit費用」と呼ばない。

**M2 — 正例2 call／欠陥3 callの分割は、既存の連続検査を保存しない。**

根拠：T:1837、1845–1890、1898–1913、V:2288–2389、plan:248–266、D2128:33–41。

現物の状態遷移は次の一本である。

| 段階 | 同じ root の状態 | 検査 |
|---|---|---|
| 初期 | 発行済み base の複製 | held／released の正例 |
| checkout変更後 | 親HEADのgitlinkは元pin、submodule HEADだけreplacement | releasedで単一理由 |
| 親commit後 | 親gitlinkもreplacement、working treeはclean | heldで受容、releasedで単一理由 |

`HELD=False` の patch は各 `with` の出口で復元される。正例の返り値を後続の引数へ渡してはいない。しかし root、Git履歴、checkout、および同一process内の呼出し履歴は共有されている。

現 `verify_receipt` の外側には明示的なroot変更は見えないが、これだけで将来の欠陥に対する検出集合の同値性は示せない。例えば、正例の判定をroot単位で誤って再利用し、checkout変更後にも使う欠陥は、現行の連続検査で露見しうる。別worker・別rootへ分ければ、この履歴を通らず両nodeが通る余地が生じる。

**成果物への影響：** 「同値性未証明」という抽象的な注意だけでは、分割で具体的に失う結合検出をユーザーが判断できない。

**是正案：** 2＋3案には「同じ複製での正例→変異後の再検証を失う」と記載する。D2128が述語の重複を代替と認めない理由と整合する。D2068も、現在のassertが緑であることだけでは消える拒否経路を正当化できないとしている。

静的に保存を説明できる境界は、**この5 callと変異列を一体として残す境界**である。同じroot・同じprocessで順序と全assertを維持して二つのnodeへ包装する案なら、この結合は残せるが並列化利得は得られず、planの `max(d_positive,d_defect)` は使えない。独立二nodeへ分ける案は、検出集合を縮める案として裁定へ載せるべきである。

**M3 — 分割・縮約の式は scheduling の下限であり、wall予測として比較すると偽の利得を作る。**

根拠：plan:259–261、271–276、D2121:7、`t2750-README-s14-64.md`:28。

`max(最長node, 直列和/48)` は、相方、unit拘束、開始遅れ、workerごとの実配布を含まない。現行Aにも適用すれば、実占有より小さくなりうる。その値へAの固定費を足しても、欠けた相方は戻らない。

**成果物への影響：** Aの実測wallから分割後の下限を引くと、分割で削っていない相方まで「改善」に算入する。

**是正案：** `W_split_model`／`W_reduce_model` を「固定duration・固定残差を仮定した理想化値」と明記し、Aにも同じ式を適用する。比較は同一model間で行い、Aの実測との差を別に示す。schedulerを織り込む場合も配布予測として区別する。

他M nodeへの律速移動も必須である。95 session資料では draft-finalize の中央値266.8秒に対し ccbench-current は273.3秒であり、ccbenchだけを短くしても近い床が残る。ただし、この中央値差を分割利得には使わず、各走の残存最大値で計算する。Cを無条件な上限としないplan:289の修正は維持する。

**M4 — pairingの採否を「10%未満」だけでも「3/3同符号」だけでも決められない。**

根拠：D357:3–14、D2121:7–9、`carry-T2766-T2767-1621.md`:1–5、plan:240。

D357の10%規則は逐語では**1走同士**の差に適用される。三反復の差へ機械的に適用して「変化なしなのでT-2766を閉じる」は導けない。一方、3組すべてで改善しても、ばらつきや条件差を除いた実在効果の確証にはならない。

**成果物への影響：** 小さい観測差を理由に誤って閉じる、または小標本の方向一致を採用証拠へ昇格させる。

**是正案：** 結果を見る前に、次の報告・判定を固定する。

- 各jobで短縮量をAのwall−Bのwallと定義し、3値、差の中央値、各Aを分母にした短縮率、条件別中央値差を示す。
- 3/3で正なら「方向が一致した観測差」。実配布で相方短縮が発火したことも別に確認する。
- 約20秒・5.8%なら「replicaで小さい短縮を観測。実受入での効果は未確認」。5.8%は歴史条件での目安で、一般的な硬い上限ではない。
- 符号不一致や律速移動があれば、採用効果は未確立とする。
- 3/3一致を有意差判定にはしない。T-2766を閉じる場合は「効果ゼロ」ではなく、実受入の証拠・300秒目標への寄与・後続費用を踏まえた見送りとして諮る。

**S4 — 裁定表に「何を失うか」と「今回決める行為」を足す。**

**是正案：** 現行三列に、少なくとも次を加える。

| 追加欄 | 記載内容 |
|---|---|
| 失う検出・残る不確実性 | 分割の連続検査、縮約の三欠陥型、replicaと実受入の差 |

記載は「実測成分から、仮定Xの下で理想化値Y。実装効果は未実証」とし、「実装すればY秒」としない。pairingと分割は技術的には併用可能なので、四行は自然な排他的選択肢ではなく、**今回どこへ投資するかの択一**と明記する。

## 規律2の射程と透過性の検算

判定は **(c) 一部射程内**。単なる時間集計・modelは正しさ判定を変更しない。一方、verifierをwrapする実行経路、hold、検査選択の受入への反映は規律2に関係する。「repo差分ゼロ」だけでは射程外にならない。

| 操作 | 透過が成立する条件と限界 |
|---|---|
| 観測wrapper | 元callableへ同じ引数を一度だけ渡し、返り値そのもの・例外を保存する。記録処理の失敗で元例外を隠さず、記録失敗の走を正常測定として使わない |
| helper | T:1000の独立実体へのcopytreeとT:1001のdocument deepcopyをそのまま実行する。共有documentの返却や複製省略は禁止。wrapper自身が追加copyして返すこともidentity保存ではない |
| shared get | T:922–938の同じlock区間内でbuild・marker確定を完了させる。buildをlock外へ移したり、失敗後に完成扱いしたりしない。観測によるlock保持時間増加は性能上の交絡として残る |
| verifier | 戻り値はboolではなく `ReceiptResolution`。`state`だけでなくrefusals、observation、head、receipt、held_checks等を保持する。never-issued時はhistoryそのものを返す経路もある |
| S1／S／C | その走の検出範囲は小さくなる。production受入は変更せず、診断走の成功を受入成功に昇格させないことが条件。planではS1/Sはnodeid直指定、追加deselectはCだけ |
| B | Aと同じitem集合、unit境界・unit内順、既存のgroup／排他／holdを維持する。集合一致だけで順序依存の不存在まで証明したとは書かない |
| held module | H:766–790によりenforcing pytestでimport可能でも、held関数のcall guardは残る。H:703–708の解除tokenや登録済みwrapperをprobeが変更しない |

根拠はT:918–1001、V:2284–2390、H:703–790、plan:64–102、118–132。

Mの破壊的変異は独立複製内にあり、base構築はlock下なので、Bの順序変更を評価する局所的根拠はある。ただし全suiteの順序独立性を、このMの読解だけから一般化してはいけない。planの限定selftestと実配布・terminal記録は、その条件を確認する方針として妥当である。

## 総括

**must-fixは4件**：固定費と終了費用の帰属、分割で失う連続検出、wall modelの下限性、pairingの判定条件。

分割案の判定は **「受理集合を縮める」**。ここでは依頼の用法どおり検出する欠陥集合を指す。独立した正例2 call／欠陥3 callへの分割は、同一root・同一processでの正例→変異後再検証を失う。現検査列を一体で保持する境界なら保存できるが、提示された並列化modelの利得は得られない。

規律2の射程は **(c) 一部射程内**。診断用選択と性能集計は受入本体を変えずに行えるが、wrapperの意味保存、hold維持、診断結果を受入証跡へ昇格させない境界が必要である。
