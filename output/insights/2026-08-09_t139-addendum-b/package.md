authority: none

## 0. 何を承認してもらうのか

本走の実験計画は「core (推論の構造) + 追補 A (数値) + 追補 B (公表側の数値)」の 3 本で組み立てる
約束になっている。core と追補 A は承認済みで、**残るのが追補 B である。**

**ただし、この 3 本は現状では完結しない。**core §16 は本走の後に「6 セルすべての調整済み p 値と
同時区間を、primary の成否にかかわらず固定表で公表する」ことを求めているのに、その公表手続き
(未調整 p 値の作り方、多重調整の方式、区間の構成) を一意に定めた凍結文書が存在しない。
追補 B は閉集合の制約でそれを定められない。**この欠落は B4 と B8 で扱う。
追補 B を承認しても、それだけでは本走を投入できる状態にならない。**

追補 B が持てるのは 3 つだけで、core がその 3 つを閉じた集合として決めている。過不足があると
機械的に「解決失敗」になる。

| 記号 | 中身 |
|---|---|
| `b01` | 候補数の上限 |
| `b02` | 個別公表のための誤り率の配分 |
| `b03` | 累積台帳をつなぎ止める「正規の根」の決め方 |

**本 wave は草案を書いただけで、凍結も発効もしていない。**また、承認の発話それ自体でも発効しない —
**承認する決定を canonical 台帳へ畳んだ commit 以後**にはじめて文書として効力を持つ (追補 A と同じ)。

**追補 B の 3 つの値は、測定値を 1 つも入力に取らない。**候補の通し番号と固定の定数だけで決まる。
ただし「実際に pilot の生データを見る前に凍結された」という**時点の独立性は、文書の中身からは
検証できない。**それは承認決定を畳んだ commit、pilot 1 本目の投入記録、台帳の予約 commit の
前後関係でしか裏付けられない。草案はこの区別を明記してある。

## 1. 草案が提案している値 (逐語は `addendum-b.md`)

- `b01` = **1**。承認済みの資源上限 26 割当てが、追補 A の内訳
  (`検証 1 + pilot 8 + pilot 予備 2 + 本走 13 + 本走 予備 2`) でちょうど候補 1 本分だから。
  **これは運用上の提案値であって、計算や観測から導いた値ではない。**
- `b02` = **`0.05 / (k × (k+1))`**。k は候補の通し番号で、今回は k=1 なので **0.025**。
  全部足すとちょうど 0.05 になるので、**上限をいくつにしても、後から上げても、
  公表全体に配る誤り率の総和は 0.05 を超えない。**
- `b03` = 根を「限定例外の決定を台帳へ畳んだ commit + 公表台帳という種別」の 2 つ組に固定する。
  公表台帳は primary 台帳とは別のままで、番号は一度取ったら失敗しても手放さない。

## 2. 段 6 の敵対レビュー 2 本がどちらも NO-GO を返した

**両方とも同じ場所を突いた — 草案の `b02` と `b03` が、core が委ねた範囲を越えていた。**
初稿は公表用の p 値の作り方・Holm の閾値列・同時区間の使い方まで書いていたが、これは
「配分の数値」を越えて**新しい推論規則を足す**ことにあたる。閉集合の契約違反である。

**この指摘を受け入れて草案を縮めた。**いまの `b02` は配分の数値だけを持ち、公表手続き
(セルの正体・検定統計量・p 値・多重調整・区間) は**定めないと明記**してある。
`b03` からも、primary 台帳の予約を必須参照する仕組みを外した。

**さらに段 6 の焦点再レビュー (第 2 巡) が、縮め残しを 1 件見つけた。**`b03` は primary 参照を
外した後も、公表台帳の path・予約 entry の digest・予約 commit を**受領証の必須項目**にし、
validator へ新しい照合条件を課したままだった。core §12 の必須項目にこれらは無く、足すことは
必須 schema と受理集合を変える core の変更にあたる。**これも外した。**いまの `b03` が持つのは
正規の根の同定方法だけ — 呼び手が選べない根、作成のみの予約、番号の一意性である。
受領証に何を書かせ validator に何を照合させるかは、producer 実装 wave の決める事柄へ戻した。

**この削除は、本 wave の停止中に出たユーザー裁定と同じ向きである。**2026-08-10 の裁定 (Q-A) は
「受領証 schema の digest 固定はこの後」と定めており (worklog エントリ 367)、受領証 schema を
先に追補 B で固定しないことを支持する。

あわせてレビューが見つけた事実誤りを 2 件直した。

- 資源の内訳を `8 + 2 + 13 + 3` と書いていたが、追補 A の確定値は
  `検証 1 + 8 + 2 + 13 + 2` である (親が追補 A の逐語で確認済み)。
- 草案が「pilot より前に公表台帳の番号を予約する」と要求していたが、これは core が
  「pilot は追補 A だけで足りる」と定めた条件を狭めてしまう。追補 B にはこれを書けない。

## 3. 裁定を求める問い

### B1. 候補数の上限をいくつにするか

**事実。**上限 1 は計算や観測から出た値ではなく、承認済み資源が候補 1 本分だという運用上の理由だけ。

- **(a) 上限 1 を承認する (推奨)。**
- (b) より大きい値 (例: 4) にする。→ 統計的な害はない (`b02` が上限に依存しない形のため)。
  ただし資源の承認が無い候補まで投入可能に見える。**資源上限は別に効くので、
  「大きくすると自動的に承認される」わけではない。**
- (c) 上限を空にする。→ core が `b01` を必須にしているので解決失敗になる。採れない。

**あわせて承認をお願いする版管理規則。**上限を上げるときは本追補を書き換えず、
**同じ根・同じ配分表を継承する新しい study と新しい追補を、その候補のデータを見る前に承認する。**
本追補の blob と過去の結果は不変のまま残す。

**成果物影響:** 上限を超える投入は本走の投入前に拒否される。版管理規則が無いと、
ordinal 2 の投入時に「永久拒否」「既存追補の書き換え」「新追補の採用」のどれになるか実装依存になる。

### B2. 公表の誤り率をどう配るか

**事実。**段 2 の案は「上限が 1 なのだから 1 本目に 0.05 全額」だった。段 3 のレビューが
blocker と判定した — 全額を使い切ると次の候補は必ず新しい根を立て、そこで 0.05 を再取得できる。
真に効果がない候補が 2 本続けば、少なくとも一方で誤公表する確率は `1 − 0.95² = 0.0975` になる。

- **(a) `0.05 / (k(k+1))` を採る。今回は 0.025 (推奨)。**追補 A が primary 側に置いた形と同じなので、
  2 つの台帳が同じ見た目になり監査しやすい。上限に依存しない。
- (b) 別の summable な配分 (例: 幾何配分 `0.05 × 2^{-k}`、あるいは先頭に厚く配る形)。
  → (a) と同じく総和を 0.05 以下に保てる。今回の候補へ配る量を増やせるが、後続候補への残りは減る。
- (c) 1 本目に 0.05 全額。→ いま最も検出しやすいが、上の抜け道が残る。塞ぐには
  「この根は永久に閉じる」という別の恒久規則が要る。

**成果物影響:** 材料レポートで「この workload のこの量は有意」と書ける敷居が変わる。
(c) は将来の候補にわたる誤公表の累積を防げない。

### B3. 公表セルの正体と統計量を、追補 B が「参照」してよいか

**事実。**core は「6 セル全件を固定表で公表する」とだけ書き、セルの正体をそこには書いていない。
一方、追補 A の `a10` は `k = 1..6` を `(N_W1, H_W1, G_W1, N_W2, H_W2, G_W2)` と逐語で列挙し、
統計量 `T_k = √J · μ̂_k / s_k` も定義している。**ただしそれは標本数設計のための定義である。**

- **(a) 追補 B は非規範的な参照としてだけ触れる (推奨。現草案の形)。**
  「この配分は、公表手続きが確定したときにその family へ与える水準である」と書くに留める。
- (b) 参照も置かない。→ `b02` の数値がどこにも接続されない。
- (c) 追補 B が公表 family を定義する。→ 閉集合違反。採れない。

**成果物影響:** (a) なら、公表手続きが決まった時点で配分がそのまま使える。

### B4. 公表の検定手続き (p 値・多重調整・区間) をどこで固定するか

**事実。ここが最大の未解決点である。**公表側の規則は 3 か所に散らばっている —
Holm または closed testing は裁定 Q7 (worklog)、正分母 guard は裁定 R5 (a) (worklog)、
6 セル固定表と同時区間は core §10・§16。**どれ 1 つも「公表手続きの正本」ではなく、
未調整 p 値の作り方も、Holm と closed testing のどちらを採るかも、一意には決まっていない。**
追補 B は閉集合により正本になれない。

さらに段 6 のレビューが**妥当性の問題**も出した。cluster の代表値が正規分布から外れる場合、
`t` に基づく p 値は名目の水準を守らない (`E[Z] = 0` の混合分布で `J ≤ 13` のとき破れる構成が示された)。
**これは primary 側 (`a11`・`a13`) にも等しく及ぶ限界**であり、追補 A も「cluster 分布が非正規なら
被覆も検出力下界も保証しない」と既に明記している。

- **(a) 公表手続きの正本を、新しい core を起こす別 study で凍結する (推奨)。**
  現 core は書き換えない。**その正本が出来るまで公表表は生成できない。**
  **現在の草案をそのまま新しい study へ接続することはできない。**本書は §0 で旧 core の三つ組
  (path・commit・blob digest) へ静的に束縛されており、別 study は新しい core を起こす以上、
  その新 core に束縛された新しい追補が要る。**引き継げるのは値であって文書ではない** —
  `b01`〜`b03` の提案値を、新 study の新しい追補で再採用する形になる。
  **したがってこれは「先に承認して本走を投入してよい」ことを含意しない** — 本走のデータを見た後に
  公表手続きを選べる経路が残るためである。投入の可否は B8 で別に裁定する。
- (b) producer 実装 wave に選ばせる。→ 実装が推論規則を選ぶことになり、事前登録が完結しない。
  段 2・段 3・段 6 のいずれもこれを不可と判定した。
- (c) 追補 B へ書く。→ 閉集合違反。採れない。
- (d) 公表を記述的な表だけにして、有意判定と区間を出さない。→ core §16 の要求を変えるので、
  やはり新しい core が要る。

**成果物影響:** これが決まらないと、材料レポートの「有意セル」欄を一意に再生成できない。
primary の certified 判定の**値**は影響を受けないが、公表手続きを本走のデータを見た後に選べば、
その公表は「事前登録どおり」ではなくなる。したがって本走の投入可否と無関係ではない。

### B5. `b03` に primary 台帳への参照を置くか

**事実。**初稿は公表側の entry に primary 予約の digest を必須で持たせ、番号の一致を求めていた。
段 6 のレビューが 2 本とも「別台帳という裁定 U8 の範囲を越えうる新しい拘束だ」と指摘し、
さらに**その参照が無くてもリセットは防げる**ことを示した — 根が呼び手に選べず、予約が
作成のみであれば、公表台帳だけで「新しい親系列 ID を名乗って番号を取り直す」経路は閉じる。

- **(a) 参照を置かない (推奨。現草案の形)。**公表台帳だけで閉じる。
- (b) 参照を置く。→ 2 系列の番号が連動する。U8 はこの連動を裁定していないので、
  裁定を足すか core の変更を伴う別 study が要る。

**成果物影響:** (b) だと、公表台帳で正しく予約できていても primary 側の digest 不一致だけで
本走が拒否される。試行台帳の親子関係も変わる。

### B6. 「pilot より前に凍結する」ことをどこに書くか

**事実。**追補 B の値を pilot の結果を見てから選べる経路を塞ぐには、承認と台帳の予約を
pilot より前に済ませるのが最も強い。**しかし core は「pilot は追補 A だけで足りる」と定めており、
追補 B がそこに条件を足すと core の admission を狭めてしまう。**

- **(a) 追補 B には書かず、運用手順として pilot より前に承認・予約する (推奨)。**
  草案は「時点の独立性は文面からは検証できない」と明記するに留める。
- (b) core を変える別 study で、pilot の受理条件へ正式に足す。
- (c) 何もしない。→ 追補 B を pilot 後に選んだ疑いが残る。

**成果物影響:** (c) だと、本走の結果を「事前登録どおり」と呼ぶ根拠が弱くなる。

### B7. 追補 A に残っている erratum の未発行 — **裁定済みにつき本パッケージでは問わない**

**事実。**2026-08-09 の裁定 R2 (a) は「core §7 の較正義務を『事前固定 stress check』へ置換する
第 2 の erratum を当てる」と決めた。**この erratum 文書は現時点で存在しない** (親が確認。
T-139 の core を対象とする既発行の erratum は §15 用の 1 本だけ。`s4-adjudication.md` の
erratum 1 も参照)。追補 A の `a12` は今も「本 field は core §7 の義務を満たしたと扱ってはならない」
と書いたままである。

**この項は本 wave の停止中に裁定された。**2026-08-10 の裁定 (Q-B、worklog エントリ 367) は
「core §7 の第 2 erratum は次の manifest wave が同梱起草し、**発効まで pilot を機械的に停止する**」
と定めた。したがって本パッケージは選択肢を再提示しない — 起草の所在は manifest wave であり、
pilot は止まったままである。

**成果物影響:** 裁定どおり manifest wave が同梱すれば、本走の結果を「事前登録どおり」と呼ぶ
根拠の鎖は core §7 でつながる。同梱されないまま pilot の機械停止だけが外れると、そこで切れる。

### B8. 追補 B を今の形で承認するか、保留するか

**事実。**縮めた後の `b02` は配分の数値 `alpha_pub_1 = 0.025` を持つが、**それを適用する先が無い。**
公表手続き (B4) が未確定だからである。未調整 p 値の作り方・多重調整の方式・区間の構成は
それ自体が推論規則であり、本走のデータを見た後まで未固定なら事前登録になっていない。
さらに core §14 は「core を変える必要が生じたらそれは別 study」と定めるので、**現 study の
空欄を後から新しい core で埋めた扱いにはできない。**

**この項の推奨は差し替えた。**初版のパッケージは「今の形で承認して段階 2 へ進め、本走の primary
判定は前へ進められる」を推奨していたが、段 6 の焦点再レビューが上の理由で退行と判定したため撤回する。

**参考 (別 ID の裁定。本項を裁定したものではない)。**2026-08-10 の裁定 (Q-D、worklog エントリ 367) は
残作業を 2 波とし、**承認 manifest + 受領証層 + 投入・測定層を同一 land** とした
(受理仕様だけを先行させる分割は採らない)。追補 B の承認そのものはこの裁定の対象ではないが、
「受理側の仕様だけを先に凍結して先へ進む」形を採らないという同じ向きの判断である。

- **(a) 承認を保留する (推奨)。**B4 の公表手続きが新しい core で凍結されるまで、追補 B も凍結しない。
  → 3 つの値を公表手続きと一緒に整合させて決められる。**本走の投入は当面できない。**
- (b) `b01`〜`b03` の**値だけを設計メモとして先に裁定する**。この裁定で追補 B は**発効しない** —
  `authority: none` のままであり、承認決定を canonical 台帳へ畳む手順も行わない。
  resolver・producer・validator は本書を契約として読まず、`submit_main` の十分条件にもならない。
  → 値の議論を先に片づけられる。**発効しないので、core の `main_admission:
  requires_addendum_a_and_b` がそのまま効き、本走は投入できないままである。**
- (c) 今の形で承認し、本走を投入できる状態にする。→ **採れない。**公表する調整済み p 値・
  同時区間・有意セル集合を一意に再生成できないまま本走が走り、公表手続きの結果依存選択経路が残る。

**成果物影響:** (c) を採ると、材料レポートの公表表と proof chain が閉じない。
(a) と (b) はどちらも閉じる。**(b) でも追補 B は発効しないので、「発効済みなのに投入できない」
という中間状態は生じない。**(a) と (b) の違いは、値の議論を先に片づけるかどうかだけである。

**段階の意味 (追補 A と同じ):** 段階 2 = 文書としては効力あり / 機械的な検査は未実装 /
**pilot も本走もまだ投入できない。**
**上の (a)・(b) はいずれも段階 2 へ進めない** — 追補 B は段階 1 (草案、`authority: none`) のままである。
段階 2 へ進むのは (c) だけであり、本 wave はそれを採れないと判定している。

## 5. 本書が主張しないこと

- 追補 B が発効した、とは主張しない。承認前は `authority: none` であり、承認発話だけでも発効しない。
- 3 つの数値が最適である、とは主張しない。`b01` は運用上の提案値、`b02` の形は
  「上限に依存しない」ことを優先した選択であり、他の summable な配分も同じ保証を持つ。
- 公表手続きが有限標本で妥当である、とは主張しない (B4 の後段を参照)。
- 段 3・段 6 の敵対検証がすべての欠陥を見つけた、とは主張しない。
