## 確定した設計 (プラン v2)

### D-1. 公表 family と周辺統計量は既存文書の参照とする (新規定義しない)

6 セル = `a10` が列挙する `k = 1..6` = `(N_W1, H_W1, G_W1, N_W2, H_W2, G_W2)`。
周辺統計量 = `a10` の `T_k = √J · μ̂_k / s_k`。帰無は core §7 の weak mean null。
**追補 B はこれらを定義せず参照する。**参照は `a13` が field 内で正規の根と ordinal を束縛した
先例と同型であり、余剰 field ではない (B-03)。

### D-2. `b02` は有限 cap に依存しない summable schedule とする

プランの「第 1 候補へ `0.05` 全額」を**採らない**。理由は A-2 — 全額を使い切ると、次候補は
必ず新しい根を立てることになり、そこで `0.05` を再取得できてしまう (独立 2 候補なら
`1 − 0.95² = 0.0975`)。採る形は `a13` と同形の

```text
alpha_pub_k = 0.05 / ( k * (k + 1) )        k = 1, 2, 3, …
```

とする。`Σ_{k≥1} 0.05/[k(k+1)] = 0.05` なので、**cap をいくつにしても、後から上げても、
系列全体の FWER は `0.05` を超えない。**本 study は `k = 1` を占め `alpha_pub_1 = 0.025`。
未使用 tail は回収も再配分もしない。これで B-04 の joint consistency 問題は構造的に消える
(`b02` は `b01` の値に依存しない)。

### D-3. `b01` は統計的荷重を持たない admission の hard stop とする

`K = 1` を提案値とする。承認済みの総ポイント上限 26 割当て (U10) が 1 候補分ちょうどであり、
第 2 候補は別途の予算裁定を要するためである。**これは governance 提案であって導出ではない。**
cap の引き上げはユーザー裁定でのみ可能とし、引き上げても**同じ根・同じ schedule を維持する**
(新しい根を立てない)。D-2 によりこの引き上げは FWER を壊さない。

### D-4. `b03` は read-only foreign key とする

公表系列の正規の根 = `(fold_commit = 88d68f9127b31df5aafc3d59607896626a1652e8,
ledger_kind = individual_publication)`。caller・受領証・親系列 ID の申告値を入力にしない。
公表台帳は primary 台帳とは**別台帳**で、残高・entry・ordinal を混合しない。
公表 entry は primary 予約 entry の digest を **read-only の親参照**として持ち、ordinal は一致を要する。
**primary 台帳へ書かない・primary の予約契約 (`a13`) へ要件を足さない。**

### D-5. 時相境界を明記する

追補の解決失敗・entry 不在・digest 不一致・ordinal 不一致は、**投入前の admission deny** とする。
性能測定の開始後に不一致が判明した場合は core §9 の既存分類へのみ写し、
**予備置換・ordinal の解放・新しい失敗分類の作成を行わない** (core §13 の否定検査 8 と §14 の線)。

### D-6. 選択時点を pilot より前へ自ら縛る

core は追補 B を「本走の投入より前」としか要求しないが、本草案は
**pilot 1 本目の投入より前に承認・commit し、公表側 ordinal もその時点で予約する**と書く。
受理集合は狭い側へ動くだけであり、pilot の raw を見てから cap・公表 alpha・根を選んだ疑いを
構造的に消す (A-7)。
