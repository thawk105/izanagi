## この wave が確かめたこと

1. **裁定 (109) の根拠値は gate から計算できない。** 裁定を記録した commit `3b095bc` で
   4 reference を再計測すると、合計 23,956 / 常に走る段の無条件節 9,668 /
   wave クラス依存 9,169 / 条件のみ 5,119 である。裁定文の「実読 10,515」「L2 3,755」は
   どの構造層の和とも一致せず、**ある 1 本の docs-only wave が実際に開いた節の実行計測**
   だったと結論できる。したがって gate は構造的な代理量を選ぶしかなく、その選択で
   しきい値は 2 倍違う。これは実装細部でなく設計択一である。

2. **現在の 3 層内訳 (worktree @ e0b9073)**: 常に読む 10,568 / wave クラス依存 9,493 /
   条件成立時のみ 5,137 = 合計 25,198 (hard ceiling 25,200、残 2 bytes)。

3. **`DW-O23` は L1 である** (段 9 行は無条件)。親 brief の L1=18,938 は分類漏れで、
   正しくは L1=20,061 / L2=5,137。段 2 プランが突き、レンズ A が全 49 節の総当たりで
   他に分類誤りがないことを確認した。

4. **提案値は受理集合を広げる。** プラン案 (L1 20,200 + L2 14×1,000) の理論上限は 34,200 bytes で、
   旧 25,200 に対し 35.7% の拡大。裁定「予算値の引上げは不採用」と整合しない。
   一方、現在値で凍結すると余白ゼロになり、後続の義務追加ができない。
   この矛盾はコードで解けず、ユーザーの再裁定を要する。

5. **動機の 1 つが陳腐化していた。** 裁定 (109) は「T-314 を入れる余地」を挙げたが、
   T-314 が要求するのは `.claude/commands/rulings.md` の余白であり、T-313 は command の
   予算に触らない。しかも実測 4,601/5,000 = 余白 399 bytes で、当時の「6 bytes」は既に古い。

6. **dispatch parser は条件性を保持しない。** `_dispatch_tables` は段キーごとに全行を
   1 集合へ畳むため、「成立した条件の」「commit するなら」という修飾が失われる。
   どの案を採るにせよ、L1/L2 分類を command 表の条件 marker へ機械的に束縛しない限り、
   marker を消すだけで gate を迂回できる。
