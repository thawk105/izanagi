# backoff の利得はスレッド数の関数である — 固定 48 スレッドでは観測できない

**種別:** 探索の妥当性文書 (measurement report)。**認証されていない** — trace-disabled の
性能測定のみで、直列性の検査は行っていない。ここにある値を根拠に variant を採用してはならない
(規律 2)。この文書の役どころは、どの軸に検査の予算を割く価値があるかを示すところまでである。

## 発見

B-10 backoff shape の 15 セルを、スレッド数を横軸にして測り直した。B-10 本走が固定 48 スレッドで
1 点だけ測っているのに対し、6〜48 スレッドの 8 点で測ると、その 1 点からは原理的に見えない構造が出た。

1. **backoff の利得は多コアでだけ現れ、低コアでは損になる。** 書き込み主体では、素の silo
   (backoff 無し) が 30 スレッドで 4,015,440 tps の頂点を打ったあと崩れ、48 スレッドで
   2,293,813 tps まで落ちる (頂点比 −42.9%)。backoff を入れた系列は崩れず、48 スレッドで
   固定 10µs が 3,906,062 tps に達する — **素に対して +70.3%**。ところが 12 スレッドでは
   素の 2,632,276 tps に対し固定 10µs は 2,129,639 tps で、**19.1% 負ける**。
   利得も損失もスレッド数の関数であり、**乗り換えが起きること自体が 1 点測定では観測できない。**

2. **最適な待ち時間はスレッド数とともに伸びる。** 頂点の位置が系列ごとに右へずれる
   (素と zero-loop は 30 スレッド、固定 2µs は 36、固定 5µs は 42、固定 10µs 以上は 48 でもまだ
   上り坂)。単一の定数を選ぶ設計は、コア数が変われば外れる。

3. **読み主体では backoff が全点で負ける。** 素の silo が 6→48 スレッドで単調に伸びて
   10,194,756 tps に達し、どの backoff セルも下回った (最良でも −5.1%)。
   **この負荷に対する正直な答えは「素のまま」である。**

4. **形状 (constant / symmetric-modulo) の差が測定ノイズに埋もれている。** 同じ大きさどうしを
   比べた 144 点で、差の中央値 0.485%・最大 1.91%。一方、同じ条件を別ノード・別ジョブで
   測り直した 180 点のばらつきは中央値 0.39%・最大 4.29%。**形状の効果は測り直しのばらつきより
   小さい。** 効いているのは形状ではなく大きさで、2µs と 100µs では 2 倍以上違う。

5. **CCBench 内蔵の adaptive backoff は、既定の調整定数のままだと全 3 負荷・全 8 点で最下位。**
   読み主体 48 スレッドで素の 4.34 分の 1 (2,350,891 tps)。**ただしこれを機構の劣位と読んではならない。**
   刻み幅 `kIncrBackoff` を 100µs から 0.5µs へ変えるだけで最良の静的値に肉薄する。
   別文書 `2026-09-02_ccbench-adaptive-backoff-step-granularity.md` を参照。
   **既定 adaptive を基準線に置いた比較は、下手に設定された定数を叩いているだけである。**

## 再現条件

| 項目 | 値 |
| --- | --- |
| スレッド数 | 6, 12, 18, 24, 30, 36, 42, 48 (論理コア 48 の 8 分割) |
| レコード数 | 1,000,000 |
| workload | zipf 0.9 / rratio 5・50・95 / rmw 0 / max_ope 10 |
| 1 点あたり | extime 3 秒 × 3 rep、中央値を採用 |
| ビルド | trace-disabled (規律 1)、perf 計測なし |
| 環境 | Pegasus 計算ノード (48 物理コア、HyperThreading 無効)、gen_S、1 ノード占有 |
| ccbench | pin 511c953 + `patches/silo-backoff-fixed.patch` |

投入は `izanagi-job-evidence/thread-scaling/` (repo 外) の probe による。
4 点格子が job 966559 / 966606 / 966607、8 点格子が 966759–966764。
**workload とスレッド数は実行時フラグなので、15 本のバイナリを全条件で共有できる。**
そのため条件を割って複数の計算ノードへ同時に投げられる — 8 点 × 3 負荷を 6 ノードで約 14 分。

## 該当コード

- `external/ccbench/include/backoff.hh` — `Backoff::backoff()` の待ちループ。
- `patches/silo-backoff-fixed.patch` — `BACKOFF_FIXED` で adaptive を迂回して固定値を入れる穴。
  形状は `BACKOFF_FIXED = shape_code * 1000 + mean_us` で符号化される。

## 仮説

abort 率 (leading indicator) が仮説を支持する。書き込み主体の素の silo は
**12 スレッドで 16.0%、48 スレッドで 79.9%** まで上がる。abort したトランザクションが
即座に再試行して同じ競合点へ戻り、競合の密度を自分で上げていると読める。同じ 48 スレッドで
固定 10µs を入れると **abort 率は 38.9% へ半減し、throughput は 2,293,813 → 3,906,062 tps**
になる。backoff は再試行の到着率を下げてこれを緩める一方、待ち時間ぶんを常に失うので、
競合密度の低い低コアでは失う側だけが効いて負ける。

読み主体で backoff が一切効かないのは、緩めるべき競合が最初から無いためと読める。
48 スレッドでの素の abort 率は **15.5%** で、固定 2µs を入れても **14.4%** にしか下がらない
(書き込み主体の 79.9% → 38.9% と対照的)。**直せるものが無いところに待ち時間だけが乗る。**

**この解釈は本測定からは「そう振る舞う」ことしか言えない。** abort の内訳 (どの検証段で落ちたか)
と待ち時間の実効値を切り分ける測定は別途要る。

## この測定が言わないこと

- **正しさを何も保証しない。** trace-disabled ビルドの性能測定だけである。
- 各点は 3 回の中央値で、信頼区間を出していない。測り直しのばらつきが中央値 0.39%・
  最大 4.29% なので、**数 % 以内の差を主張する用途には足りない**。
- 形状の差が「無い」ことは示していない。示したのは
  **この精度・この格子では検出できない**ということである。

## B-10 事前登録との関係

B-10 は形状 (constant / symmetric-modulo) を主軸に置き、スレッド数を 48 に固定している。
本測定は、その主軸が本測定の精度では空振りに見えること、および固定した側 (スレッド数) に
大きな構造があることを示す。**事前登録の改訂を要求するものではない** — 認証されていない
性能測定に、凍結された事前登録を動かす権限は無い。判断材料として提示する。
