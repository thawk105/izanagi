## 攻撃せよ

1. **上限の迂回**: wall-clock / model_calls / cli_reported の各上限を、実装のコード経路上で
   超過させたまま `outcome=accepted` に到達させる入力・状態を探せ。
   特に `limit_trigger` の latch と accepted 判定の間に隙間がないか。
2. **metering の fail-open**: `token_count` が来ない・`info` が null・重複・巻き戻る・
   rollout と stdout が食い違う各ケースで、消費が 0 または過少として受理される経路。
   `cached_input_tokens > input_tokens` の扱いが launcher と ledger で食い違っていないか。
3. **receipt の偽装と破損**: `check-receipt` が receipt の自己申告を信じている箇所。
   output/manifest/rollout を receipt 作成後に改変しても検出されない経路。
   temp+rename の原子性が実際に成立しているか (同一 filesystem か、fsync 順序、O_NOFOLLOW)。
4. **終了の不完全性**: process group 終了が実際に効かない経路。residual の数え方が
   常に 0 になる恒真検査になっていないか。`termination_verified` が偽の緑になる条件。
5. **manifest の混入**: header 照合、wave_id 束縛、lock、whole-document replace の各所で、
   別 wave / 別 job の entry を受け入れる、あるいは既存 entry を失う経路。
6. **ledger の受理集合**: `--manifest` 未指定経路が本当に不変か。三者一致検査が
   実際には成立していない (常に真、あるいは片側しか見ていない) 経路。
   R10 の無条件 rc=2 が `--strict` 依存に戻っている箇所。
7. **恒真な保証**: 謳っているのに発火しない assert、到達不能な分岐、
   例外で握り潰されて fail-open になる `except`。
