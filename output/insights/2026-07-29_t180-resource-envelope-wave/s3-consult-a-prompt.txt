## 攻撃せよ

**親 brief 自身も攻撃対象である。** 特に親の実測値とその一般化を疑え。

1. 親は「rollout JSONL は実行中に逐次 flush される」を probe2 の 1 回の観測 (liveness.tsv) から
   一般化している。この一般化が破れる条件を挙げよ (buffering、負荷、CLI 版差、`--ephemeral`、
   CODEX_HOME 差、tmpfs、同時実行、rotate 等)。破れたとき launcher は **fail-open するか
   fail-closed するか** をプラン本文から判定し、fail-open なら具体的な入力・状態で示せ。
2. 親は「thread_id は起動直後に出る」と書いた。出ない・遅れる・複数出る・途中で変わる場合に
   上限強制と receipt がどう壊れるかを示せ。
3. 上限到達時の停止が**実際には止められない**経路を探せ (子 process group の作り方、
   codex が起こす孫 process、SIGTERM 無視、kill と rollout 書き込みの race、
   停止後に到着する token_count、停止したのに receipt が正常完了に見える等)。
4. receipt と manifest の**壊れ方**を探せ: 部分書き込み、並列 job からの同時追記、
   途中で電源断相当、同一 session_id の重複、別 wave の manifest への混入、
   receipt が存在するのに中身が空/不正でも gate が通る経路。
5. **受理集合の不当な拡大・縮小**を探せ。`--manifest` selector の追加が既存 `--cwd-contains` の
   結果を変えないという主張をコードで反証せよ。manifest が「1 件も読んでいないのに健全」と
   判定される経路 (T-179 の fix と同型) が再発していないか。
6. 変異の帰属不成立を探せ: プランのテストが、上限強制の本体を消しても緑のままになる書き方に
   なっていないか。fake codex bin が実挙動と乖離していて、テストが実装でなく fake を検査して
   いないか。
