## 攻撃せよ

**本 wave は gate・検査を新設する。成果物が実際に効く全層が scope に入っているかを必ず見よ。**

1. **層の欠落**: launcher を作っても、実際に worker を起動するのは dev-wave manager である。
   プランは「誰がいつこの launcher を使うのか」を成立させているか。DW-O01 の手順・
   `.claude/commands/dev-wave.md`・`.agents/skills/dev-wave/` のどこが変わらないと死蔵になるかを
   file:line で指摘せよ。逆に、本 wave が docs 契約まで書き換えるべきでない理由があるなら述べよ
   (実装子は docs を編集しない、という凍結境界は所与)。
2. **scope 境界の妥当性**: 親は retry の分類を T-183 の所有として切り出した。この境界で
   T-180 単独が意味のある成果物になるか、それとも分類なしの retry 上限は無害化されて
   使い物にならないかを論じよ。境界を動かすべきなら、動かす側の代償も書け。
3. **既存資産との重複**: `tools/dev_waves/` (Claude wave supervisor) は既に上限と receipt を持つ。
   新規 launcher がそれと二重化・矛盾していないか。既存 schema/receipt を再利用すべき箇所を
   file:line で示せ。逆に再利用が誤りなら理由を書け。
4. **語彙と識別子**: `turn` / `model_calls` / `session` / `job` / `wave` の各語が、
   rollout JSONL・stdout event・T-179 台帳・本プランで二義化していないか。
   同名で別物、別名で同物を探せ。
5. **T-179 との整合**: receipt の token 値が T-179 の "CLI reported" 定義と一致するか。
   一致しないなら、同じ wave の 2 つの台帳が別々の数を主張することになる。
   `--manifest` selector が T-179 の凍結値 (10 session / 434 model calls / 2,757,982 tokens) を
   再現できるかを検証可能な形で述べよ。
6. **測れないものを測ったことにしていないか**: 親 brief の「純増する検出力」の主張、
   および probe が実際には示していないことを示したと書いている箇所を挙げよ。
