# 段 4 裁定 — 受入全走を 5 分へ収める

親が段 2・3 の相談 2 本 (sol = 価値レンズ、luna = 費用レンズ) と自分の実測から裁定する。

## 0. 依頼の再確認

ユーザーの発話は次の 3 つである。

1. 「受入全走が壊滅的に死んでて研究開発が死んだと思う。受入全走は 5 分と決めているが、
   数十分動いているやつがいる。すぐに 5 分に収めるようにしろ」
2. 「まずそいつらは CC 自動合成研究の実現に必要なのか？どのくらい価値が高いのか？」
3. 「価値が小さいもの、リターンが小さいものに対して毎度毎度高いコストを払うのはバカみたいでしょ」

## 1. 問い 2・3 への裁定 — 価値は小さくなかった。高いのは欠陥である

**(R1) 高コストテストの削減・毎走からの除外は採らない。**

根拠は実測と既裁定である。

- 100 秒以上の 37 node のうち、**「走ごとに答えが変わらないので毎走でなくてよい」と
  証明できたものは 0 件・0 秒**である (sol §B)。32 件は certified 選択・proof chain・
  材料レポート・試行台帳のいずれかを直接守る。
- **F485 が同じ案の実行例である。** T-080 の 11 node をコスト理由で opt-in 化し、
  11 日後に赤 2 件が発覚、凍結検証保留への追随漏れを隠していた。
- D532 は「テストの削除・skip・selection の縮小で速くする — 規律 2 に反する。
  検討対象にしない」と明記する。D700 は T-080 の別 gate 定期実行も却下している。
- 絶対規律 2 は費用を理由に緩めない。

**(R2) ただしユーザーの問いは正しく、答えは「価値ではなく欠陥」である。**

- fixture `_t080_stub_free_e2e_repo` のコピー元は、docstring が書かれた 2026-07-26 時点で
  2,094 件 / 24,427,374 bytes だった。**今日は 22,988 件 / 639,898,207 bytes** で、
  件数 11.0 倍、bytes 26.2 倍である (luna §A。お掃除 wave の独立集計
  22,994 件 / 639,961,594 bytes とほぼ一致)。
- docstring の「1 回 15〜22 秒」はその時の数字のまま残っている。
- **同一 file の 855 行に、2026-07-27 に別の肥大 (ignored な 1.8GB build cache) で
  15〜22 秒が 121.7 秒へ膨らんだ記録がある。** 同じ型が tracked 側で再発した。

## 2. 律速の分解 — 実測で確定した事実

**(F1) 最遅 shard は shard-0 である。** 112 走のうち 103 走 (92%)。shard-2 は 7 走、
shard-1 は 2 走。最遅 shard の wall が 300 秒超なのは 106/112 走 = 94.6%、中央値 345.2 秒。
**D1918 の「最遅は shard-2」は失効している。** 同決定の根拠は 2026-09-09 の 9 走であり、
標本が小さい。この訂正は記録する。

**(F2) shard-0 の wall の分解** (luna が report.json と junit から再計算):
開始側 55.74 秒 / dispatch 49.17 秒 / 実行 313.61 秒 / 終了側 20.01 秒。
親が当初書いた「終了後 約 76 秒」は誤りである。

**(F3) 300 秒の 64% は奪い合いである。** 親が単独走で実測した。

| 走り方 | `test_t080_stub_free_draft_finalize_commit_and_public_gate_e2e_b5` の所要 |
|---|---|
| 受入全走の中 (48 worker、shard-0) | **303.8 秒** |
| 計算ノードで単独 (job 996264.nqsv) | **108.69 秒** |

差 **195 秒 (64%)** は本質的費用ではない。

**(F4) 奪い合いの実体は lustre への重複読み出しである。**

- repo は `/work` = **lustre**。fixture の書き先 `/tmp` は**ローカル xfs**。
- コピー元の読み出し実費 (loaded login node、tar で /dev/null へ):
  `output/insights` 16.7〜20.9 秒 (metadata だけで 8.3 秒)、`output/env` 2.1 秒、
  `orchestrator` 0.7 秒。1 回あたり約 20〜24 秒。
- t080 の 11 node は key が 5 種類しかないが、**全部別 worker に載るため process 内 memo が
  1 回も当たらない。** これは shard-0 の実行窓 313.609 秒に対し node 所要が
  287.973〜310.177 秒であること (最小 2 件の和 357.761 秒 > 窓) から確定する。
- したがって **1 走で build 11 回・トップレベル copytree 33 回**。
  lustre に約 7GB / 25 万回の metadata 操作が集中する。

**(F5) 配分は件数で均等化されており、秒数では均等化されていない。**
`tools/acceptance_shards.py:321` の `allocate` は `weight=len(nodeids)`。
件数は 7794 / 7793 / 7792 とそろい、秒数は 13,075 / 2,865 / 7,522 に割れる。
ただし時間で均等化しても、最大単体 310.177 秒が残るため短縮は最大約 3.43 秒である (luna §D)。

**(F6) 計算ノード job が pytest 完了後に終わらない。**
`tools/pegasus/dispatch_compute.py` の `_write_result_replace` は result.json を
`os.replace` した後 `_fsync_dir` → `os.fsync` を **timeout なしで**呼ぶ。
**result.json が完全でも関数が戻った証拠にならない。**
さらに隔離 supervisor は `waitpid(child_pid, 0)` で直接の子しか待たず、
PID namespace を持たないため孫 process を回収しない。
本日の実測では 996124 が最低 2,328 秒、996191 が同型で居座り、親が qdel した。
walltime は 3600 秒なので、放置すると 1 走が 1 時間ノードを占有する。

**(F7) 非帰属の赤が走行ごとに入れ替わる。** 同一 wave の 3 attempt で落ちた test に
重複が無く、いずれも単独再走では緑。共通の形は「実 repo への subprocess または syscall へ
壁時計の短い上限 (5 秒 / 30 秒 / 60 秒) を掛け、その上限が守られることを検査する」もの。
負荷で上限が守られず赤になる。

## 3. 採る手 — 実装 scope

**(P1) t080 の base を shard ごとに 1 回だけ組み、worker 間で共有する。** 【最優先】

- 現行は process 内 memo なので worker ごとに組み直す。これを **xdist の worker を跨いで
  共有する base** へ変える。file lock で 1 本だけが組み、他は完成を待って使う。
- **コピーする bytes も全件性も 1 ミリも変えない。** `_copy_git_visible_output` の
  全件性を検査する `:1302` と `:1328` は緑のまま通らなければならない。
- 各 node へ渡す実体コピーは従来どおり独立させる (テストが破壊的に変異するため)。
  ただし**コピー元が lustre からローカルの base へ変わる**ので、その複製も安くなる。
- 期待効果: lustre からの全件読み出しが **11 回 → 1 回**。
  F3 の 195 秒のうち相当部分が消える見込み。**ただし見積りは実測前の推定であり、
  段 6 の受入実走で before/after を測って確かめる。**

**(P2) 計算ノード job が pytest 完了後に終わらない経路を直す。** 【最優先】

- `_fsync_dir` の `os.fsync` に上限を置くか、上限つきで観測して原因を記録する。
  **fsync を省いてはならない** (result の耐久性は attestation の前提である)。
- 孫 process の回収経路を閉じる。
- **この 2 つのどちらが真因かは未特定である。** 実装子はまず
  「次に再発したとき何を読めば特定できるか」を残す形を優先し、
  特定できた側だけを直す。特定できないまま両方へ推測の修正を入れない。

**(P3) shard の重みを node 件数から所要秒へ変える。**

- 効果は小さい (約 3.43 秒) が、根拠が明確で副作用がない。
- `orchestrator/tests/acceptance_duration_ledger.json` は D104 決定 4 により
  **LPT 割付のための hint であって権威ある測定ではない。** この用途 (割付) は
  hint の本来の用途である。**wall の分解や不可能性主張へ使ってはならない** (F832)。

## 4. 採らない手

- **テストの削除・skip・毎走からの除外** — (R1) のとおり。D532 / D700 / F485 / 規律 2。
- **コピー範囲を絞る** — `:1302` と `:1328` が全件性を検査しており、
  絞ると正しく赤になる。全件性の理由 (`:1000` の「subprocess が import closure を
  host から補えないようにする」) を崩す。
- **`output/` の削除** — お掃除 wave が独立に調べ、**tracked の削除確定 0 件**。
  pin 閉包が閉じている。絶対規律 7 と D1941 も保存の側に立つ。
- **K を 3 から増やす** — D1620 が canonical を K=3 と明記し、D1103 が
  「K=3 で既に単体テストの床に達している」とする。**ユーザー裁定が要る。**
- **時間依存テストの上限を伸ばす** — 検査対象が上限そのものなので恒真化する。
  (F7 の是正は本 wave の scope 外とし、裁定へ返す。)

## 5. ユーザー裁定へ返す項目

1. **認証層比較の 4 node (計 643.7 秒) を毎走走らせる価値。**
   sol は「現行 production の認証機構ではなく、別研究の比較報告を守る。
   直接 consumer の不在は確認できたが、退役可能性・代替検出力までは証明していない」とした。
   **親は裁定しない。**
2. **頻度変更一般** (毎走から外す / 条件付き / 定期走)。D747 単独には空白があるが、
   D532・D700・D690 が別経路を指定している。**人間裁定が要る。**
3. **K を 3 から増やすこと。** D1620 の canonical 定義に触れる。
4. **F7 (時間依存テストが負荷で落ちる) の是正方針。** 上限を伸ばすと恒真化する型なので、
   設計判断が要る。

## 6. 不変条件 (実装子への拘束)

- 絶対規律 2・3 を緩めない。既存テストの期待値を削除・緩和・反転しない。
- `_copy_git_visible_output` の**全件性を変えない**。`:1302` と `:1328` は緑のまま。
- fsync と attestation を省かない。
- 仮想リスク向けの gate・検査・台帳・一般化を足さない。
- 走らせていないものを緑と書かない。
