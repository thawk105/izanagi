## 1. 一時領域 I/O 軸は実 regime で棄却された

### ログインノードでは `/tmp` の fsync が並列度で崩れる (事実だが受入とは無関係)

pegasus02、loadavg 7.4 から 19.1、3 走中央値。1 process あたり write+fsync 100 回。

| 置き場 | fstype | n=1 | n=8 | n=32 |
|---|---|---|---|---|
| `/tmp` | xfs | 1.94 s | 13.49 s | **29.06 s** |
| `/work` | lustre | 0.079 s | 0.071 s | **0.081 s** |
| `/dev/shm` | tmpfs | 0.000 s | 0.000 s | 0.000 s |

`/tmp` は 1 本 19.4 ms/回 が 32 本同時で 291 ms/回 へ悪化する。中央値 column で
Lustre は `/tmp` の 358.8 倍速い (29.061 / 0.081)。総処理量は約 110 fsync/s で頭打ち。

### しかし受入はログインノードで実行されていない

`/work/SFC/tanab/.izanagi-acceptance-shards` の全 session を数えた。

```
母集合 session 数: 568
  dispatch-intents なしで除外: 1
  confirm/handled 欠落で除外: 18
  集計対象: 549
```

**549 session 中 549 が shard を計算ノードへ dispatch している。**
ログインノードで走るのは全件 `--collect-only` の**単一 process** 1 回だけであり、
並列度が無いのでこの崩れは発火しない。

### 計算ノードでは機構自体が効かない

bnode041、48 core、loadavg 0.80 (ほぼ専有)、request 958445.nqsv。wall 秒。

| 置き場 | kind | n=1 | n=8 | n=32 | n=48 |
|---|---|---|---|---|---|
| `/tmp` (xfs) | fsync | 0.012 | 0.013 | 0.039 | **0.058** |
| `/work` (lustre) | fsync | 0.097 | 0.157 | 0.180 | **0.193** |
| `/tmp` (xfs) | 小 file | 0.009 | 0.029 | 0.144 | **0.235** |
| `/work` (lustre) | 小 file | 0.181 | 0.514 | 1.868 | **2.805** |

- 計算ノードの `/tmp` は 48 並列でも崩れない (0.012 から 0.058 秒)。
- **計算ノードでは Lustre のほうが遅い** — fsync 3.3 倍、小 file 12 倍。両軸とも `/tmp` が勝つ。
- 絶対量が問題にならない。48 並列でも 0.2 秒未満であり、実行の中央値 191 秒の 0.1% に満たない。

**したがって一時領域を Lustre へ移す案は、効く場所が無い。**

### shard 不均衡は割付では取れない (D1019 の K=3 での裏取り)

3 shard 揃った 206 session の shard 間最大差は中央値 **116.3 秒** (p75 144.7、p90 225.0)。
総和の中央値 469.4 秒を 3 等分すれば 156.5 秒なので、完全均衡なら最大 shard は 156.5 秒になり、
実測の 244.9 秒との差は 88 秒である。

**しかしこれは割付で取れない。** D1019 は「完璧な予言者でも利得は 0.0 秒」を実測で確定しており、
理由は `real-repo` の排他 group が 1 worker に直列で載り続けることにある。
**本集計は D1019 を反証せず裏取りする。** D1019 の一次資料は K=2 の 2 走だったが、
本集計は K=3 の 206 session で、不均衡が K=3 でも同じ大きさで残ることを示す。
**鎖が律速である以上、不均衡はその影であって原因ではない。**

## 4. 段 3 が捕まえた near miss

レンズ A の BLOCKER 1 は、**性能目的の変更が正しさ防壁を退行させる**実例である。
plan は明示 `TMPDIR=/tmp` を尊重し未設定時だけ Lustre を使う設計だったが、
その 2 種類の session が同時に同じ tree を触ると、片方は `/tmp/izanagi_apply_*.lock`、
片方は Lustre 上の lock を取り、**互いに排他しない**。現状は両者が同じ `/tmp` lock を使うので
これは現行保証からの退行である。しかも plan が新設予定のテストは同じ TMPDIR 同士しか
検査しないので、この混在負例を KILL しない。

実装前に捕まえた。詳細は failures 台帳。
