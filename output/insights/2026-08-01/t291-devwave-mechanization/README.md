## 2. 予算 schema の変更 — 受理集合は非単調に変わった

**「総和が減ったから緩めていない」は誤りである** (段 6 レンズ D の D-01 が反証)。

- 旧受理集合: `Σsize ≤ 24,000 ∧ core ≤ 9,000 ∧ workers ≤ 5,000 ∧ mutation ≤ 3,750 ∧ operations ≤ 8,000`
- 新受理集合: `Σsize ≤ 24,000 ∧ core ≤ 8,500 ∧ workers ≤ 4,750 ∧ mutation ≤ 4,000 ∧ operations ≤ 8,250`

新旧は包含関係にない。

- **新だけが受理する状態**の例: `(7,900, 4,200, 3,751, 8,001)` = 23,852。
- **旧だけが受理する状態**の例: `(8,750, 4,200, 3,500, 7,500)` = 23,950。

正しい表現は「mutation / operations の個別 cap は**緩み**、core / workers の個別 cap は**締まった**。
合計 ceiling 24,000 は不変で、個別 cap の総和は 25,750 → 25,500 へ 250 減った」である。
本 wave の実測現物 `8,063 + 4,372 + 3,682 + 7,839 = 23,956` は**旧個別 cap にもすべて収まる**ので、
今回の差分を通すための引上げではない。

導出規則: **各 cap = 実測サイズを 250 単位で切り上げ、作業 headroom 250 を足す**。
新設した機械検査: `Σ(個別 cap) ≤ 合計 ceiling × 1.10 = 26,400`。
2 つの gate が噛み合っていなかった (総和 25,750 が ceiling を 1,750 超えるのに無検査だった) 状態を是正した。

## 3. 予算飽和の実測 — 縮約は延命にならない

`git log --first-parent` の 24 変化点で 4 冊合計 bytes を再計測した。

- 2026-07-24 に 22,604 → 07-25 に 24,379 (ceiling 超え) → **以後 7 日間ずっと 23,9xx〜24,000**。
- 前回の大再編 `a8ee4a1` (2026-07-28、T-147) が空けた 458 bytes は、
  5 first-parent 遷移・33 時間後の `226f7fd` で 23,999 まで消費された。

したがって単発の縮約は約 1〜2 日分の延命にしかならない。**規則総量を恒久的に減らす手段は
機械化 (prose → tool + テスト) だけである**というのが本 wave の設計上の結論であり、
実際に `DW-M05` / `DW-M06` の 7 義務が prose から tool へ移った。

## 4. 二層化 (「リファレンスのリファレンス」) の評価 — 現内容では NO-GO

段 6 レンズ B が実測した。

- `docs/failures.md` (152,514 bytes) と `docs/decisions.md` (535,730 bytes) は
  `tools/check_docs.py` の予算集合外にあり hard cap がない。**第 2 層は既に存在する。**
- 入口は「事故の物語は `docs/failures.md` の F 番号へ置く」と指示するが、
  **実行義務を下層へ移してよいとは書いていない**。worker は通常 F 本文を読まないため、
  leaf の実行義務は第 1 層に残さざるを得ない。
- 「主語・時点・操作・停止を変えず丸ごと落とせる説明文」だけを厳密に数えると
  **合計 205 bytes** しかない。第 1 層は 23,785 になるだけで、I2/I3 を足すと 24,275 で超過する。
- 下層への pointer を dispatch 表へ必読化すると、49 leaf 全部で約 1,225 bytes 増え、
  入口の 9,500 予算を約 632 超える。

D110 却下案 (b) と同型にしない必要条件 (下層 hard cap、namespace 閉包、三面一致、
発火条件の逐語一致、pointer の実在・一意性検査、義務が下へ滑らないことの検査) のうち、
最後の 1 つは完全機械化できず義務対応表と人間監査が必須である。

## 5. 裁定パッケージ (scope 外だが real)

- **R1 — `DW-O09` の file-set digest (F39、段 6 C-06 / 段 3 A04)。** `failures.md` が
  「`DW-O09` の既定対象へ『ファイル集合を pin する digest』を加える改訂が要る／現行実体: なし」と
  明記しているが、本 wave の I3 (role 名 key 検索) は別の穴を塞ぐものでこれを覆わない。
  新規 file の追加は特定 file の bytes pin ではなく `repository_files` 集合を変える。
- **R2 — 供給側の未機械化面 (段 6 C-07)。** 「外側の実行時間上限に掛からない経路で起動する」
  「起動前に総所要を見積る」は harness が自己検証できない。外側 supervisor の receipt を
  要求する形にするかを決める必要がある。
- **R3 — `DW-M08` / `DW-O11` / `DW-O20` / `DW-O23` の機械化余地。** 段 2 の子が実コードで確認した
  結果、`run_tests.py` は削除検出を完全に強制するが caller の記録義務は残り、
  `check_wave_startup.py` の clean-tree 検査は `mode=="fresh"` のときだけで resume 経路は素通り、
  `dev_wave_land.py` は fresh-context 回復と rebase/force/push 禁止を強制しない。
  これらを tool 側へ広げれば、さらに prose を pointer へ畳める。
- **R4 — 節の並べ替え。** `DW-CTX` は wave 開始で読むのに core.md 末尾にあり、
  `DW-O04` は commit 動線なのに `DW-O17` から離れている。bytes は回復しないため本 wave では見送った。
- **R5 — 予算の意味そのもの。** 24,000 bytes は日本語約 8,000 文字で、100 万トークン context の
  約 1% にすぎない。この上限が代理しているのは context 費用ではなく
  「エージェントが実際に守りきれる規則の総数」である。この代理関係を明示的に定義するか、
  常時読量 (docs-only wave の実読は 10,515 / 23,990 = 44%) を直接測る gate へ置き換えるかは未裁定。
