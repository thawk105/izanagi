## 最も重い反証 — 研究 routing の名指しが陳腐化していた

裁定 (74)#2 は研究側の中身として「変異軸をデータ構造水準へ」を挙げたが、**[T-140] は 2026-07-28 に
実測して択 (c) (軸の廃止) を適用済み**だった。親が一次資料で追認した内容は次のとおり。

- 変異対象の `searchReadSet` / `searchWriteSet` の走査長は **平均 5 / 上限 10** で cap され、
  n≈5 の vector 線形走査に hash / tree / sorted 構造は定数コストで勝てない
- サイズは `max_ope` の生成時 cap で決まり、データや contention で成長しない =
  **「大きい set だけ遅い」型の重尾機序が構造的に存在しない**
- 探索資源は [T-139] (劣化版 Silo の梯子) / [T-144] (スペクトル補間) へ移すと裁定済み。
  再開条件は `max_ope` の大きい workload spec を campaign が採用する場合だけ
- 一次資料 = `output/insights/2026-07-28_t140-setsize-distribution.md`

さらに [T-139] rung 1 は恒久実装まで完了しており、残件は **RF 規範化と recovery pipeline 接続**
(`recovery_measurement_eligibility=false`) である。[T-144] は「[T-139] 恒久実装 wave の後に前提が揃う」と
台帳が明記しており、**前提は既に充足している**。

## 段 4 後の追記 — 3 件目のユーザー裁定で設計が変わった (記録直前)

worklog 記録の直前に、ユーザーから逐語で次の指摘があった。

> 思うんだけど、main の凍結っていらないのでは？だって git にバージョン管理機能があるわけじゃん？
> だからどこでどういう測定したってバージョン情報見ればわかるじゃん？

親は次の 3 点で**指摘は正しい**と評価し、選択肢を返して **「廃止し、順序付けだけ残す」** の裁定を得た。

1. 凍結の表向きの目的「測定への交絡回避」は、git の版管理 + env-tag (D59) + receipt +
   「測定値は測った checkout を併記する」(F41) が既に担っており、freeze はこの目的に対し冗長である
2. **freeze には機械 gate が無い** — 本 wave の段 3 レンズ B が repo 全体を静的検索し、
   凍結状態を見て task ID を拒否する checker / command / skill 分岐が無いことを確認した
3. 走行中 campaign を道具の変更から守るのは freeze ではなく phase3 の別項「実行 revision 束縛」の仕事

よって **freeze を再発効させる草案 (段 4 時点の結論) を破棄**し、**D111 = freeze の恒久廃止 +
順序付け ([T-144] を直後の 1 wave) の維持**へ切り替えた。段 3 の所見裁定 (real 15 / refuted 0) は
すべて有効なままで、B2 (凍結対象 ID 集合の未定義) と B3 (機械 gate の不在) は
**廃止によって根本から解消**された。
