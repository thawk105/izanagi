# レンズ B の攻撃面 — 計測としての妥当性と実機での成立性

**中心の問い: この job を計算ノードへ投げたとき、R3-1 が要求する判定材料が実際に得られるか。
得られないまま「測れた」と見える結果が返ってこないか。**

1. **R3-1 checklist の被覆漏れ。** 裁定パッケージ R3-1 は
   「user/net/pid namespace 起動可、network connect と credential/home/agent socket が失敗、
   source RO・scratch 限定 write、process-tree timeout が子孫を残さない、
   CMake build/trace/`perf stat`/numactl/48-thread run が成功、stock/variant 双方で性能差と
   floor 再較正要否」を要求する。**測っていない項目、名前だけ測って中身が違う項目**を挙げよ。
2. **実機での成立性。** PBS 資源指定 (`#PBS -A/-q/-b/-l`)、walltime 予算の内訳、
   `python3.10` の解決、module / compiler / cmake の可用性、`perf` の path 候補、
   `numactl` の在否、third-party 供給経路、scratch の所在。
   **login node で成立した事実を計算ノードへ転用している箇所 (F29 型) を特に探せ。**
3. **環境変数契約。** 親が渡す 4 変数で足りるか。足りない・多すぎる・PBS が上書きする・
   `qsub -v` の引用で壊れる箇所はどれか。未設定時に検査が黙って skip しないか。
4. **規律 1 (観測者効果の分離)。** S7 の性能測定が trace-enabled build を含みうるか。
   sandbox 内外で build が同一であることを probe 自身が確認しているか。
5. **交絡。** S7 の overhead 比が、sandbox 以外の差 (cache 温度、page cache、CPU affinity、
   実行順序、他ジョブとの同居) で説明できてしまわないか。**単独性の確認**は十分か。
   1 回の対比較で比を主張してよいか、繰り返し・順序反転が要るか。
6. **時間予算の破綻。** S6 (CCBench build) と S7 が walltime に収まる見込みは妥当か。
   `blocked` に倒れたときに何が失われるか。job 全体が落ちて S1〜S5 の結果まで失う経路はあるか。
7. **receipt と provenance。** `output/env/pegasus/t316-sandbox-backend/<PBS_JOBID>/receipt.json`
   が計測 ID として後から参照できるか。create-only、既存 job ID の再利用拒否、部分結果の扱い。
   `DW-G04` の「発火条件を満たす既存 artifact path か計測 ID」を満たすか。
8. **scope 逸脱。** 本 wave は計測段であり、意味 gate・DSL/IR・SandboxProfile の production 実装は
   scope 外である。production の受理集合や既存 gate に触れている変更が無いか確認せよ。

# 制約

- **read-only である。** ファイルを編集しない。pytest 緑を要求されていない。静的検査でよい。
  実走していない結果を緑と書かない。
- 所見ごとに **blocker / must-fix / nit** を付け、`DW-G05` に従い
  「これを直さないと成果物 (計測結果と、そこから下る意味 gate 実装の判定) のどの値・受理集合・
  参照がどう変わるか」を 1 行で書け。書けない所見は nit にせよ。
- 親 brief 自身も攻撃対象である。brief の前提・provisional 裁定 (P1)〜(P3)、
  および「S6/S7 は best-effort でよい」という親の判断も攻撃してよい。
- 自分で refuted と判断した所見は、そう明記して残せ。
