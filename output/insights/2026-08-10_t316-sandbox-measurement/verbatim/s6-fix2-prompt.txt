## R1 (blocker) — `renameat2(RENAME_NOREPLACE)` はこの機体の `/work` で使えない

**親の実測 (2026-08-10、この機体):**

```
/work 上: file -> new name: EINVAL / file -> existing name: EINVAL / dir -> new name: EINVAL
/tmp 上: file -> new name: OK    / file -> existing name: EEXIST   / dir -> new name: OK
```

receipt の出力先 `output/env/pegasus/t316-sandbox-backend/<PBS_JOBID>/` は **repo 配下 = `/work`** である。
単体テストは `tmp_path` (= `/tmp`、tmpfs) で走るため緑になるが、**実機の publish は必ず EINVAL で落ちる。**
`docs/pegasus-runbook.md` は directory についてしか EINVAL を記録しておらず、
通常ファイルでも EINVAL であることは本 wave で初めて実測された。

**親の実測による代替 (同じ `/work` 上):**

```
os.link(tmp, final) -> 新規名: OK / 既存名: OSError errno=17 (EEXIST)
```

**処置:**

- final publish から `renameat2` / `RENAME_NOREPLACE` への依存を外し、
  **`os.link(tmp, final)` + `os.unlink(tmp)`** の create-only publish へ置き換えよ
  (`os.link` は既存名に対して `EEXIST` で失敗するので create-only 性は保たれる)。
  fsync 順序 (temp 書込 → fsync → publish → directory fsync → `COMPLETED`) は維持せよ。
- **probe の起動直後に、実際の出力先 directory で publish 機構が動くことを自己検査せよ。**
  小さい sentinel を作って publish し、失敗したら 90 分の測定を始める前に fail-closed で止める。
  「測定は全部終わったが receipt を書けなかった」を構造的に起こさないこと。
- **同型の再発を防ぐテストを足せ。** publish 機構が tmpfs 固有 syscall に依存していないことを
  検査せよ (実装に `RENAME_NOREPLACE` が現れないことを検査するだけの構造 assert では不十分。
  publish 関数へ EINVAL を注入して、**fail-closed で止まり canonical path に部分ファイルを
  残さない**ことを検査せよ)。

## R2 (blocker) — 正例 (全観測が正常) が `go` にならない

**親の実測:**

```
python3 tools/run_tests.py orchestrator/tests/test_t316_sandbox_probe.py -q
→ 1 failed, 44 passed
FAILED orchestrator/tests/test_t316_sandbox_probe.py::test_r3_1_coverage_does_not_overclaim
    rc, receipt = _run_injected(monkeypatch, tmp_path, _good_stages())
>   assert rc == 0
E   assert 3 == 0
```

`_good_stages()` (= 全観測が正常) を流しても overall が `go` にならず rc=3 になる。
これは **過剰拒否の検出用の正例が成立していない**ということであり、
「何を入れても `go` にならない probe」は「何を入れても `go` になる probe」と同じく無価値である。

**処置:**

- どの stage の判定が `go` を返していないかを特定し、**fixture が非現実的なのか、
  verdict 側が過剰拒否なのか**を切り分けて報告せよ。
- **判定を緩めて辻褄を合わせてはならない。** 封じ込めの要求 (F1〜F14) を弱める修正は禁止する。
  正当な観測列で `go` に到達できるよう、fixture 側と verdict 側のどちらが誤っているかを
  根拠付きで直せ。両方が誤っている場合は両方直してよいが、**要求を落とす形にしない**こと。
- 修正後、`_good_stages()` が overall `go` / rc=0 になること、および
  各 stage の 1 項目を壊すと当該 stage と overall が `go` でなくなることを、
  テストで両方向とも保証せよ。
