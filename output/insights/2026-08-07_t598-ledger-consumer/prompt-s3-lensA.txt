## レンズ A — 「この結線は before/after を実際には支えない」

[T-598] の但し書きは「結線先が決まるまで削減施策は起票しない。before/after を測れない施策は
評価できないため」である。つまりこの結線の**唯一の存在理由は、削減施策の前後比較を支えること**である。
そこが成り立たないなら、設計がどれだけ綺麗でも意味が無い。次を順に攻撃せよ。

1. **測定量そのもの。** task 単位の raw token 合計は、削減施策の効果量として使えるか。
   task ごとに難易度・turn 数・子の本数・中断回数・compaction 回数が違う。
   何で正規化すれば比較可能になるのか、その正規化子が台帳に実在するかを
   `output/task-runs/` の schema と `tools/task_runs/aggregate.py` の実コードで確認せよ。
   実在しないなら「比較可能な系列にならない」と書け。
2. **標本サイズ。** pilot v1 は 14 日 / 10 run で終わった。同じ cap の次世代を作った場合、
   得られる n はいくつか。その n で、施策の前後差を交絡から分離できるか。
   `output/task-runs/reports/20260720-20260722_task-efficiency.md` の実際の n と欠測率を読んで判定せよ。
3. **遡及不能 (brief の M8)。** before 側の値が存在しないなら、最初の施策は before/after を持てない。
   プランはこれをどう扱っているか。扱っていないなら、それは設計の穴である。
4. **帰属の健全性。** プランの帰属 key は
   「worktree → Claude project slug + cwd filter + 時間窓」である。次を検算せよ。
   - 同一 worktree で複数の task-run が時間的に重なったとき何が起きるか。
   - 同一 worktree で session が複数走ったとき (親 session + 別の背景 job) 何が起きるか。
   - worktree を使わない作業 (main checkout 直での作業、対話 session) はどう帰属するか。
     **それらが systematically 欠測するなら、残った標本は偏っている。**
   - task-run の開始・終了時刻と、transcript の event timestamp の基準は同じか。
     `tools/task_runs/ledger.py` と `tools/claude_session_ledger.py` の時刻の取り方を実コードで比べよ。
5. **親の実測値とその一般化を攻撃せよ。** brief の M4・M6・M8・M9・M11・M12・M13 は親が自分で測った。
   - M4 について: 段 2 は「`tokens` は `agent_run` 専用であり task 単位の空欄ではない」と親を訂正した。
     この訂正は正しいか。正しいなら、親の (P1) の動機付け (「欄は設計されていて producer が居なかった」)
     はどこまで壊れるか。**壊れた動機付けの上に残った推奨が、まだ正当化できるかを判定せよ。**
   - M6/M11 について: 親は本 session 1 例だけで「worktree ごとに project が分かれる」と一般化した。
     反例になりうる構成 (worktree に入らない wave、途中で worktree を移る session、
     背景 job の cwd 固定) を実際の `~/.claude/projects/` の directory 名から探し、
     一般化が成り立たない件数を数えよ。
   - M9 について: 40 file / 3.9 s から全 823 MB の走査コストを線形外挿してよいか。
     `tools/claude_session_ledger.py` の探索と上限の実装を読んで判定せよ。
6. **fail-open の帰結。** プランは収集失敗を欠測にして作業を止めない。
   欠測が偏って発生する条件 (長い session、上限到達、strict issue、slug 解決失敗) を列挙し、
   **欠測が施策の効きと相関する経路**があるかを判定せよ。あるなら、それは測定を壊す。

## 制約

- 削減施策そのものを提案するな。effort・段・出力量の削減は本 wave の scope 外である。
- 「もっと堅牢にせよ」型の一般論は書くな。D205 によりプロトタイプ基準が確定している。
  **測定として成立するか**だけを問え。
- 所見には必ず「放置した場合に何がどう壊れるか」を 1 行で書け。書けない所見は nit に落とせ。
- sandbox は read-only で書込可能 tmp が無い。pytest 緑は要求されていない。静的検査でよい。
  走らせていないものを「確認済み」と書くな。

## 出力形式

最後の節は必ず `## 総括` とする。

- `## 所見` — 各所見に severity (blocker / must-fix / nit)、根拠の file:line、放置時の壊れ方。
- `## 親 brief の実測への反証` — M 番号ごとに real / refuted / 限定付き。
- `## 測定として成立するか` — 成立 / 条件付き成立 / 不成立 のいずれかを明示し、条件を書く。
- `## 総括` — 3〜8 行。最も重い 1 件を名指しする。
