## 所見

静的検査の結論は、**調査は継続可能だが、P1-B の「内訳確定済み」と P1-D の「集合不変だから gate に触れない」は採れない**です。実走値は提示された brief の値として扱い、28 走の外部成果物は再集計していません。

1. **`disp` の 99.995% が receipt prewarm、という計算は成立しない。**
   - **主張:** 99.995% は `receipt_memo_s / barrier_s` であって、`receipt_memo_s / disp` ではない。
   - **根拠:** 同 session とされた値が `disp=28.4`、`barrier_s=31.322`。barrier は各 worker の collection 通知 hook から起動する一方、報告の collection 終端は全 worker の時刻の最大値である（`orchestrator/tests/conftest.py:2359,2384,2422`、`tools/acceptance_shards.py:1075–1092`）。先着 worker の通知後の prewarm と、残る worker の collection は重なり得る。
   - **親の記述との差:** 「barrier の主成分を特定した」は支持できる。「`disp` の全内訳を確定した」「25.6 秒の 99.995%」への転用は不可。
   - **重大度:** 高。

2. **receipt prewarm の計測値を、そのまま production resolver の走査時間とは呼べない。**
   - **主張:** 計測区間には module 取得、実 repo lock の取得待ち、memo 処理も含まれる。
   - **根拠:** タイマー起点は `conftest.py:896`、module 取得が 897、`_real_repo_locks(...)` が 899、memo 呼出しが 900。barrier の計測はさらに thread 起動・join を含む（2242–2271）。
   - **親の記述との差:** P1-D-2 の候補にはなるが、「lustre 走査を速くすればこの全量が削れる」とは未確定。
   - **重大度:** 高。

3. **per-item 正規化の呼出し数を過小計上している。**
   - **主張:** 現行 hook では `_canonical_item()` は各 item に原則 **2 回**呼ばれる。
   - **根拠:** `records_from_items()` 内の呼出し（`acceptance_shards.py:790–794`）に加え、`pytest_collection_modifyitems()` の `by_identity` 構築でも再呼出しする（901、906）。
   - **親の記述との差:** 23,970 items・48 workers なら約115万回でなく約230万回。ただし、これは呼出し回数であり削減可能 wall ではない。また 917 と 919 の digest は **records と selected という別入力**で、同一 digest の重複計算ではない。
   - **重大度:** 中。

4. **「collection 集合不変」だけでは正しさの等価性を証明できない。**
   - **主張:** nodeid に加え、正規化済み file、group、多重度、worker ごとの独立観測、実行結果まで保存する必要がある。
   - **根拠:** `_canonical_item()` は実 path の repo 内判定、file 名の導出、marker 検査、対応する `@group` 接尾辞の一段除去を担う（761–786）。重複は canonical nodeid で拒否する（790–794）。gate 2 は `ItemRecord` 全体を比較する（506–511）。
   - **親の記述との差:** P1-D の包括的な「gate に触れない」は撤回すべき。最適化案ごとの条件付き判定が必要。
   - **重大度:** 高。

5. **bytecode の entry 数は有効 cache の被覆を示さない。**
   - **主張:** `.gitignore` と entry 数から、各 source に対応する有効な pytest/import cache の存在は導けない。
   - **根拠:** dispatch は `PYTHONDONTWRITEBYTECODE` を許可し、未設定なら `"1"` を入れる（`tools/pegasus/dispatch_compute.py:127,1633`）。launcher も環境指定に応じて書込みを止める（`tools/acceptance_launcher.py:70–71`）。一方、login collection の環境は親からコピーする（`tools/run_tests.py:1295,1422`）。
   - **親の記述との差:** 「既存の有効 `.pyc` は読める」は正しいが、「したがって結論は変わらない」は誤り。欠落・陳腐化した cache が更新されず、再コンパイルが繰り返される可能性がある。個々の job の実効値は未確認。
   - **重大度:** 高。

6. **約38秒の差は、同条件の差分測定ではない。**
   - **主張:** 計算ノードの session 起点からの `pre` と、login の pytest collection 時間を引いても、並列化と plugin の寄与は確定しない。
   - **根拠:** D1830 は JUnit 起点が collection 開始より早いことを明記する（`docs/decisions.md:55298–55303`）。brief 自身も host、worker 数、plugin 搭載が異なると認めている。
   - **親の記述との差:** P1-C の「未確定」は妥当だが、38秒を候補成分へ配分する根拠はまだない。
   - **重大度:** 中。

7. **「最長単体の床が動かない」は「短縮する意味がない」を含意しない。**
   - **主張:** テスト開始前の臨界区間を短縮すれば、最長単体が同じでも shard wall は短くなり得る。
   - **根拠:** D1830 の分解、および D532 が固定費削減を明示的に認めること（`decisions.md:21930–21938`）。
   - **親の記述との差:** P1-D-3 は「何もしない」の十分な根拠にならない。削減量、他 shard への律速移動、競合の増減が必要。
   - **重大度:** 中。

## gate 影響表

現行コードの防壁を以下で略記します。

- **E:** worker digest の一致と report evidence の独立再計算（`acceptance_shards.py:537–619,1055–1074`）。
- **G1:** report/process index と rc 対応（658–668）。
- **G2:** 全 shard の canonical `observed_universe` 一致（674–678）。
- **G3:** 独立 login collection と `Counter` 一致（680–682）。login は shard plugin を除外して再収集する（`run_tests.py:1402–1455`）。
- **G4:** `Σ selected_i == U`、各 count=1、file/group/affinity 閉包（684–689、464–493）。
- **G5:** `Counter(finished_i) == Counter(selected_i)`（691–696）。
- **G6:** effective scheduler 一致（698–701）。

なお、現行 merge は全 `records` を実行母集合としており、D2003 の系列分離を実装済みと扱ってはいけません。

| lever | 触れる gate | 入力/述語/受理集合のどれが変わるか | 判定 |
|---|---|---|---|
| `Path.resolve()` を削除・字句処理へ置換 | E、G2–G5 | canonical file/nodeid が変化。repo 外拒否、symlink alias の重複検出、閉包入力まで変わる | **不可。** 761–794 の意味を保存できない置換は集合不変ではない |
| 同一 hook 内で canonical 化結果を再利用 | E、G2–G5 | 901 と906への入力を共通化。path・marker・nodeid が不変なら同値だが、現在のコードにその不変保証はない | **条件付き候補。** symlink 変化や item 状態変化、重複拒否まで保存する必要がある。「二度呼んでいる」だけでは採用根拠にならない |
| 同一の不変 payload の JSON 化・digest 結果を局所再利用 | E | 同じ bytes なら入力値・述語・受理集合は不変。canonical encoding は149–159 | **条件付き候補。** 917と919は別入力なので相互代用不可。具体的な重複箇所の特定が先 |
| worker 間で digest を共有／親の再計算を報告値で代用 | E、G2の前提 | 独立観測・検証入力を自己申告へ変更し、受理集合を広げ得る | **不可。** 552–559と1057–1068の独立性を消してはいけない |
| production resolver の走査高速化 | collection 入力を保つ限り G1–G6へ直接の変更なし。ただし実行結果へ影響 | resolver の入力被覆・失敗条件・返却 receipt が変われば、テストの意味と緑になる範囲が変わる | **現案では安全性未証明。** G5は完了したnodeを照合するだけで resolver 等価性を保証しない。本 wave の実装範囲外 |
| 何もしない | 全 gate | コード変更がないため入力生成・述語は現状維持 | **安全だが、短縮不能の証明ではない** |

「検査関数を編集しない」は「受理集合を変えない」の保証ではありません。特に、G3 が不一致を拾う可能性を、G2 の入力正規化を変更してよい理由にはできません。

## 親の一般化の当否

**(a) `pre` は固定費：標本内の記述としてのみ可。**  
「2026-09-16 の提示28走では55.4〜59.1秒」は支持できる。「今後もほぼ動かない」「56秒が必ず必要」は不可です。同日・同 checkout 群の走は、cache と共有資源の状態を共有しており、28種類の独立した環境条件ではありません。

**(b) cache が充足しているので冷 regime ではない：不可。**

| 反例条件 | 起こり得るか／今回分かること |
|---|---|
| 新規 worktree の初回受入 | 起こり得る。brief 5.4自身が cache 不在の新規 worktree を報告している。ignore 規則は cache を配布しない |
| Python 版更新 | 起こり得る。`cpython-310` の entry 数は別版の cache 被覆を示さない。28走中に起きた証拠はない |
| source の一斉変更・取り込み | 起こり得る。entry が残っても有効性は別。該当28走の source/cache 対応は未確認 |
| `PYTHONDONTWRITEBYTECODE` の実効値 | 現行 dispatch には既定で有効化する配線がある。無効 cache の更新が止まるため、cold な状態が持続し得る |
| page cache／Lustre の状態変化 | 起こり得る。`.pyc` の存在ではメモリ上の cache や metadata 応答は保証できない |

**(c) `disp` の内訳確定：不可。**  
確定できるのは「提示された barrier 計測では receipt 側が支配的」までです。prewarm と collection の重なり、lock 待ち、resolver 本体、barrier 後の処理の分離は残っています。

既存 field を増やさず進めるなら、まず同一 session のログ対応と時刻境界を照合し、その後、同一環境・同一経路で plugin の各処理と prewarm 内部の費用を診断します。観測結果がない限り、約38秒を静的読解で数値配分してはいけません。

再発し得る failures の型は、特に次です。

- **F1［捏造/幻覚・手順漏れに相当する転写事故］:** 留保付きの見立てを確定事実へ昇格。今回は「barrier の内訳」から「disp 確定」への転写（`failures.md:46–65`）。
- **F860［計測汚染］:** per-item `Path.resolve()` の合計費用を shard wall 削減量と誤読した、まさに同種の既往（23352–23367）。
- **F861［捏造/幻覚］:** call site 数と実行回数の混同。今回は逆に第二の canonical 化を落としている（23369以降）。
- **F971［測定の交絡・誤前提］:** 構造上の仕事削減を wall 改善へ直結させた。短縮可能量には同時刻対照が必要（25628以降）。
- **［恒真ゲート］:** digest の共有や縮小集合に基づく一致を、独立な完全性検査と取り違える。D711/D1728 が具体的に禁じた再発経路である。

## 短縮の可否 — 1 行の結論

**条件つきでできる：独立な全 collection・正規化・多重度・閉包・完了一致を保存する局所的な重複処理削減は候補になるが、現資料だけでは安全な具体案も wall 削減量も確定していない。**

## 総括

P1-E は維持。P1-A は「提示28走の範囲」に限定し、P1-B と cache 充足の断定は訂正、P1-C は未確定のまま残すべきです。P1-D は gate ごとの等価性条件へ書き換えてください。

本 wave を止める必要はありません。ただし現段階で insight に残せる結論は、**「支配的な barrier 処理と重複正規化を特定した。2区間の数値内訳と短縮効果の確定は未了」**です。
