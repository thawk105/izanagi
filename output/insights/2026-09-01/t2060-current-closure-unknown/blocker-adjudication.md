# 受入 blocker の裁定 — 親 (codex 2 本と相談のうえ決定)

ユーザー指示: 「codex と相談して決めて」。相談 2 本を独立レンズで走らせ、親が実測で裏取りして決めた。

## 相談の結論

| | 推奨 | 案 1 を却下した理由 |
|---|---|---|
| レンズ A (正しさ境界) | **案 4** | 既存ガードは「必要 rollout が使えなければ skip」を表明していない (F02)。案 1 は archive と無関係な sandbox / replay の正しさ node まで最大 23 件 skip にし、受入の受理集合を広げる (F06)。availability / duplicate / corruption を同じ except で吸収すると fail-closed 性を失う (F05)。 |

**両者とも案 4 (必要部分を審査して repo 内の凍結 fixture へ移す) を推奨した。**

## 親が両相談に指摘する、共有された前提の誤り

**案 4 は実行できない。凍結すべき元 bytes が既に存在しないからである。**

両相談とも「repo 内 fixture へ移す」を推奨したが、**移す元が残っているかを確かめていない。**
親の実測:

- `/home/SFC/tanab/.codex/sessions` 配下で 5 session ID の全件検索 → **0 件**。
- `/home/SFC/tanab/.codex/sessions/2026/07` は空。`08` と `09` だけが残る。
- 5 rollout は `derive_independent_golden` の**唯一の入力源**である
  (`tools/codex_reasoning_ab.py:925-970`)。route_a は統合 commit から fix2 の patch を逆適用し、
  route_b は base commit から author + fix1 の patch を順適用して一致を要求する。
  **patch は rollout からしか取れない。**
- repo 内に在るのは (a) 各 session の**最終メッセージ**
  (`output/insights/2026-07-29_t153e-t15423-review-verbatim/`、136K、追跡済み) と
  (b) rollout の **sha256 pin と期待 golden の sha256** だけである。
  レンズ A の F09 が正しく指摘するとおり、**pin は source bytes の代替にならない。**
- 期待 golden から patch を逆算して fixture を作ることは可能だが、それは
  **独立 2 経路の一致という当の性質を自作自演にする**。採らない。

したがって **案 4 は「まだできること」ではなく「元データが在れば良かったこと」である。**

## 親がもう 1 つ指摘する、両相談の枠組みの誤り

両相談は skip を「coverage を失う」と評価した。**その coverage は既に失われている。**
入力が恒久的に消えた検査は、緑にできない赤であって coverage ではない。
残る選択は「失われたことを **error として全 wave を止め続ける**」か
「失われたことを **skip として可視に記録し、他を走らせる**」かであり、
**前者は何も守らない。**

これは本 wave の主題 (D1163 / D1245) と同じ形である — 過去に成立した検証の入力が失われたとき、
記録された事実は無効にせず、現在の再検証は **unknown** として正直に表示する。

## 決定

**案 5 (親の決定): 失効した外部証拠に依存する入口だけを精密に判定し、
不在なら理由付きで skip する。module fixture 全体を落とさない。**

- 判定は「root の有無」ではなく **5 rollout の実在と sha256 一致**で行う。
  availability だけを skip 条件にし、**duplicate と corruption は従来どおり fail-closed で赤にする**
  (レンズ A の F05 を採用)。
- skip 理由に「どの session が失効したか」を出す。沈黙の skip にしない。
- **失効に依存しない node は 1 件も skip にしない** (レンズ A の F06 を採用)。
  そのために module scope fixture を落とすのではなく、
  失効依存の入口を名指しして限定する。
- 恒久的に失われた coverage は**新規 T として起票**し、
  ユーザーが別の場所に原本を持っていた場合に限り案 4 へ進む道を残す。

**採らない案と理由:**

- 案 1 (親の当初案) — 既存ガードの粒度を上げるだけでは、失効に依存しない node まで巻き込む
  (F06)。案 5 は入口を名指しして限定する点で異なる。
- 案 2 (hold 登録) — DW-O18 が要求する main 既存 F が無い。さらに、
  本 wave が新規 F を書いても、受入が緑にならなければ land できず循環する。
- 案 3 (人手で復元) — 実測で 0 件。復元元が無い。
- 案 4 (repo 内 fixture) — **元 bytes が存在しないため実行不能。**
  ユーザーが別媒体に原本を持つ場合だけ将来成立する。

## この wave で行う理由

受入が緑にならない限り**どの wave も land できない**ため、修正は「別 wave へ送る」ことで
先送りできない。修正が入った wave の受入が最初に緑になる。
実装面であるから Codex `role=author` が書き、親は直接編集しない。

## 訂正 (親の過去の主張)

- 「`2026/` の mtime は 07 が削除された時刻である」は**言い過ぎだった** (レンズ A の F08)。
  mtime は最終更新時刻であり、削除以外の要因でも動く。言えるのは
  「2026-09-01 00:54:20 JST に `2026/` の直下が変更され、現在 07 は存在しない」までである。
- 失敗 node 数は junit の entry 数で 26 と書いたが、静的な対象 node は 28 である (F03)。
