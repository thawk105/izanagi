# [T-132] `dev-waves-integration` の group 分割 — 実測、敵対検証、選択的直列への着地

2026-07-27 / branch `worktree-dev-wave-t128-t080-scan` / 計測機 cygnus (96 core、共有ノード) /
測定はすべて **worktree checkout** (F41 に従い checkout を併記する)。

## 1. 結論

`orchestrator/tests/test_dev_waves_integration.py` の **1 file 1 group を外し、テスト自身が
長命なプロセス外資源 (socket・thread・`Popen` の子・実 daemon プロセス) を作る 8 node だけを
`xdist_group("dev-waves-runtime")` に残した**。全走 wall は 71.7 → 60.8 秒 (**−15%**)。
**D91 決定 (2)「1 file 1 xdist group を維持する」を上書きする** (決定 (1) の `wait_idle` は不変)。

当初の親案は「group 指定の完全削除」だったが、敵対相談 2 本 (codex `gpt-5.6-sol`、read-only、
異なるレンズ) が独立に「完全削除の必要性は未証明」「完全削除は serve thread 終了・実 daemon
SIGKILL・socket・tight deadline の露出面を一度に 32 並列へ開く」と指摘し、**選択的直列を実測して
採った**。

## 2. 全走 wall の実測 (`-n 32`、`--dist loadgroup`)

構成 A = group あり (`[T-120]` の現状) / B = group 完全削除 / C = 選択的直列。

| ブロック | 走順 | 結果 (wall / 直前 load) |
|---|---|---|
| 順方向 A/B 交互 3 往復 | A,B,A,B,A,B | A 71.51 (1.01) / B 57.83 (6.86) / A 70.78 (10.64) / B 61.51 (9.52) / A 77.98 (12.16) / B 62.17 (9.96) |
| 逆順ブロック | B,A,A,B | B 66.94 (3.34) / A 72.00 (11.05) / A 71.47 (12.12) / B 59.80 (13.63) |

- **順方向のペア差 (`Δ = B − A`) は −13.68 / −9.27 / −15.81 秒で 3/3 符号一致。** 平均

- `[T-120]` が `-n 16` で得たペア差 (−4.5 / +9.5 / +2.5 秒) は再現条件が違う。並列度を上げると
  分割後の work / 並列度 が直列和を下回り、差が現れる。

## 4. [T-136] について判明した新事実 — 直列化はフレークを防がない

本 wave の追加実測 (計 14 走) で、**構成に依らず広範な node が高負荷でフレークする**ことが分かった。

| 構成 | 走数 | 赤が出た走 | 赤くなった node |
|---|---|---|---|
| A (group あり) | 2 | 1 | `test_fake_manifest_run_id_is_bound_to_path_namespace` (INVALID_RUN、**load 11.05**) |
| B (完全削除) | 4 | 2 | `test_max_run_bytes_counts_wal_and_all_artifacts_but_excludes_git_worktree`、`test_resume_never_duplicates_child_or_land[after-land-1]`、`test_independent_gate_failure_stops_next_wave[push_attempt-remote-ref-changed]` |
| C (選択的直列) | 2 | 0 | — |

- 前 wave (2026-07-27 (23)) は「load 21.9 以上で 3 件、15 未満は 0 件」と記録したが、
  **group あり構成・load 11.05 で赤が出た**。しきい値はそれより低い。
- 赤くなった 4 node は**互いに異なり、前 wave の 6 node とも重ならない**。[T-136] の射程は

- C の 2 走が 0 failed だったのは**根拠にならない** — 赤くなった 4 node はいずれも C でも
  ungrouped である。

## 5. 直列に残す node をどう決めたか (恣意的リストを持たない)

`dev-waves-runtime` の対象は、`test_dev_waves_isolation_contract.py` が AST から導出する。

- **語彙**: `bind_repo_socket` / `threading.Thread` / `subprocess.Popen` / `Popen(` / `SIGKILL` /
  `daemon_mod` に (module 内 helper 経由も含め推移的に) 到達する test 関数。
- 導出集合と実際の marker の**完全一致**を検査する。marker の付け忘れも付けすぎも赤になる。
- 語彙が何にもマッチしなくなったら恒真化するため (F9 型)、**導出数の下限 5 を assert** する。
- 短命な `subprocess.run` (git 呼び出し) は除外する。同期的に終了するので次の node へ残らない。

**この線引きが守るもの**: serve thread・socket FD・実 daemon プロセスが node の終了後に残り、
group 削除で**他ファイルの node と同じ worker を共有する**経路 (敵対相談レンズ 1 の blocker 2 件)。
**守らないもの**: 時間境界のフレーク ([T-136] の射程、上記 4)。

## 6. 隔離の positive control (新設)

`test_dev_waves_isolation_contract.py` に 3 本。**壊したときに必ず赤くなる検査が無い**まま
group を外すのは規律 3 (正しさシグナルを後付けにしない) に反する、という敵対相談の指摘に応えた。

1. `test_every_node_that_touches_process_external_resources_stays_serialised` —
   導出集合と marker の完全一致、group 名は 1 個だけ (xdist は複数 group 名を結合するため)。
2. `test_no_module_wide_group_and_no_overlap_with_the_real_repo_group` —
   `pytestmark` の復活を禁じ、`conftest.py` の `REAL_REPO_SERIAL_NODES` との重複を禁じる。
3. `test_no_test_function_hands_the_repository_root_to_a_rooted_helper` —
   `_temporary_repo` / `_isolated_process_environment` の第 1 引数に `_REPO` を渡さない
   (渡すと各 node の作業根が repo 本体になり、並列時に衝突する)。

## 7. 敵対相談で real と裁定し、本 wave の scope 外として起票した所見

1. **serve thread が `daemon=True` で、socket テストは `join(2)` するだけで生存を assert しない** —
   `shutdown()` が no-op に退行しても緑になる (レンズ 1 blocker 1)。分割と独立に存在する偽緑。
2. **long-path socket テストの capability probe が検査対象の本番 `bind_repo_socket()` を呼ぶ** —
   108 byte 回避が壊れても `SKIPPED` + rc=0 になる恒真ゲート (レンズ 1 blocker 2)。
3. **[T-136]** — 上記 4 のとおり射程がファイル全体へ広がった。受入判定を汚すため優先度は最上位。

いずれも「テストの検出力を上げる」改修で、group 分割 (wall 短縮) とは別軸のため本 wave では
実装せず、`DW-S04` に従い裁定パッケージへ回す。1 と 2 の露出面は選択的直列で限定されている。

## 8. 却下した案

- **完全削除 (B)**: wall は C と同等 (むしろ C の方が速い測定が出た) なのに、blocker 1・2 の
  露出面を他ファイルへ開く。両レンズが独立に「必要性が未証明」と指摘した。
- **LPT による N=2 分割**: work 増加を抑える案 (レンズ 2 の提案)。C が work・wall とも十分なので
  実測せず却下した。sub-group の割当を durations に依存させると、テストが増減するたびに
  再計算が要る (保守負担が純増する)。
- **[T-136] の同梱**: `total_timeout` の緩和や判定の時間非依存化は**テストの受理集合に触れる**
  改修で、独立の設計裁定が要る (規律 2)。本 wave は分割との独立性を実測で示すに留めた。
