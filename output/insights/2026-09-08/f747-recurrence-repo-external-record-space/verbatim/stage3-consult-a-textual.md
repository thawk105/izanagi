### 3. [real] §0 と §6 は直接矛盾しないが、final 後の分類に欠落がある

`.claude/commands/cleanup-branches.md:8` によれば、final 後は「cleanup 実行」ではない。一方、`:80-81` は、

> 同一 cleanup 実行・継続・自己 spawn では編集や記録へ移行しない。

と「継続」を別に列挙している。したがって、§6を「final 後の会話上の継続にも禁止を延長する条文」と調和的に読むことはできる。

問題は、ユーザーから届いた後続発話が、

- §6 の「継続」なのか
- `skill-self-improvement.md:66` の「後からユーザーが明示起動した別 dev-wave」なのか

を決める条件がないことである。同じ発話について両方の分類が可能で、許否が逆転する。これは時間境界そのものの矛盾ではなく、時間境界を越えた後の主体・起動分類の欠落である。

機械検査で実行時分類を完全に捕捉することはできない。`docs/skill-self-improvement.md:82-83` 自身も、意味は敵対監査と人間レビューが担うとしている。したがって runtime 検出を `check_docs.py` の成果として主張してはならない。

### 4. [real] `state = repo state` と束縛する読解を止める文言はない

command `:12-17` は、

> 状態変更の allowlist は、(1) … local branch …、(2) … worktree …の撤去だけである。
> …
> **未列挙の state mutation は…禁止する。**

と書く。無限定に読むのが安全側であり、本来はこちらを採るべきである。しかし `:18-22` の具体例は branch、worktree、index、repo 記録、Git 操作、local main、commit graph、remote、push で統一されている。remote はホスト外だが、依然として Git/repo 状態である。

さらに自己改善正本が `repo file/history` と書き下しているため、「state は cleanup が扱う Git/repo state」という領域限定解釈を明文で排除できない。`.agents/skills/cleanup-branches/SKILL.md:14-15` の不可分適用も、曖昧な語の射程を決めない。

よって plan `:44,69` の「repo 外でも現行条文だけで一義的に拒否できる」は強すぎる。F747 追記では、実行者の遵守失敗だけでなく、この scope narrowing が可能だったことも残すべきである。

### 5. [real] 親 brief と plan の双方と異なる第三の読解が最も忠実である

## 3 経路の再判定

- **(a): plan に不同意。** final 前なら拒否できる。final 後は「明示起動」に必要な表現・手続が定義されておらず、一般的な実装許可を新しい dev-wave 起動と読む余地がある。
- **(b): plan に不同意。** 無限定 default-deny の読みは有力だが、具体例が Git/repo 一色で、自己改善正本も `repo file/history` と限定するため、一義的な拒否にはなっていない。
- **(c): 条件付きで同意。** 行為が「継続・自己 spawn」と確定していれば逐語的に拒否できる。ただし final 後のユーザー発話を実際にその区分へ入れる基準が欠けており、今回への適用まで確定したという plan には同意しない。

## 条文欠落の有無

**欠落あり。**

command/SKILL.md は変更せず、自己改善終端の正本だけで二つの曖昧性を同時に閉じる最小案は次である。

`docs/skill-self-improvement.md:66`

```text
自己改善で repo 内外を変更しない。後からユーザーが別 dev-wave と明示した時だけ再照合・routing・実装する。
```

現行 line 66 に対して **+6 bytes**。これと意味等価な縮約を対にする。

`docs/skill-self-improvement.md:4`

```text
`.claude/commands/rulings.md` の自己改善に共通の発火 gate、routing、入口編集条件、commit 境界の正本である。
```

`共通する` → `共通の` で **-3 bytes**。合計は **5993 → 5996 bytes（純増3、残4）**、最長行は **78文字**で上限100以内。

機械検査は runtime 誤読を捕捉するものとして追加しない。既存の byte・行長検査で5996 bytesを確認し、意味面はこの敵対読解結果をレビュー根拠にする。
