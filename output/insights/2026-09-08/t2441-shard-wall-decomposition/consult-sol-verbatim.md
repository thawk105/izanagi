## 総括

結論1は式として通るが、0.0 秒という閉包は定義上の恒等式であり、区間名や wall の妥当性を検証していない。  
結論2の「88〜97% が必須固定費・host 差は約1割」と、結論3の「25.6秒は prewarm」は、いずれも標本下限・交絡した観測からは通らない。prewarm が有力候補であることまでは通る。  
静的検査と `decomposition.json` の再計算のみを行い、pytest は走らせていない。

## 所見

1. wall は D1620 の区間と一致しない

   - 対象: 「本書は D1620 が言う区間 (collection 開始から teardown 終了まで) と同じ区間を測る唯一の現存する源として junit の `time` を使った。」
   - 主張: pytest の JUnit suite `time` は、一般に `pytest_sessionstart` で起算し、JUnit plugin 自身の `pytest_sessionfinish` で終端を採る session 時間である。collection 開始から最終 test teardown 終了までの区間ではない。左端は collection 開始より早い。右端を最後の runtest teardown と解すれば遅く、完全な unconfigure までと解すれば早い。
   - 根拠: test の最終時刻は各 `TestReport.stop` の最大値である (`tools/acceptance_shards.py:929-948`)。JSON の `end_epoch - last_test_finish_epoch` は全174本で 2.7618〜7.0969 秒ある。したがって「最後の test teardown 終了」を右端とする D1620 wall より、JUnit wall は少なくともこの量と未観測の session-start→collection-start 分だけ長い。一方、memo cleanup は `pytest_unconfigure` で初めて実行される (`orchestrator/tests/conftest.py:2953-2968`) ため、完全な cleanup 終了を右端とするなら JUnit wall はそこまで届かない。
   - 誤りの向き: 同一区間であるとの保証を強くしすぎている。前者の解釈では `collection` と `teardown`、したがって残余を過大にする。
   - 重さ: 結論を覆す。JUnit session wall の内訳としては残るが、D1620 の exact な測定としては通らない。

2. 「全件 0.0 秒」は独立な検証ではない

   - 対象: 「左辺と右辺の差は全件 0.0 秒である。残余に未分解の区間は残っていない。」
   - 主張: 閉包は観測結果ではなく、成分の定義から必ず成立する。`S,C,F,L,E,B` を順に session start、collection end、first start、last finish、session end、最大占有とすると、右辺は `(C-S)+(F-C)+(L-F-B)+(E-L)=E-S-B` で、左辺そのものである。誤った境界や誤った名前でも閉じる。
   - 根拠: `end_epoch` は `start_epoch + wall_s`、`residual_s` は `wall_s - max_worker_busy_s` として置かれている。再計算した差の絶対値最大は浮動小数点丸め由来の `1.183×10⁻⁷` 秒で、全件が小数1桁では `0.0` 秒だった。境界値そのもの、特に shard 間の dispatch 差や各成分の分布は情報を持つが、閉包は持たない。
   - 誤りの向き: 恒等式を観測の完全性確認として強く解釈している。
   - 重さ: 表現を直せば済む。結論1の数式自体は正しい。

3. 標本下限は「必ず払う固定費」ではない

   - 対象: 「各成分の観測下限を『受入形の固定費』、下限からの超過を『host / 走間ばらつき』とする。」および「残余の 88〜97% は host を問わず必ず払う受入形の固定費である。」
   - 主張: 標本最小値は未知の母集団下限に対する上側の推定値であり、将来も払う下限ではない。しかも「固定費」は異なる走で得た成分別最小値の和で、実在する1走の固定部分ではない。
   - 根拠: 時刻順 prefix で shard-0 の残余最小値は n=5 の 81.7141 秒から、n=10 の 78.5182 秒、n=40 の 76.7645 秒へ下がった。成分別最小値の和も 79.6369→77.0970→75.7389→75.6469 秒と標本増加に伴い低下した。README の「下限は76.8秒で動かない」と逆である。
   - 誤りの向き: 固定部分を過大評価し、変動部分を過小評価する。
   - 重さ: 結論を覆す。88〜97% は「この58走の成分別標本最小値和÷残余中央値」という記述統計に限れば正しい。

4. host 差の割合は識別されていない

   - 対象: 「host / 走間ばらつきに帰属できる分は…」および「host 差はほぼ全量が collection の上振れとして出る。」
   - 主張: 標本最小値からの超過には host、repo 状態、時刻、テスト結果、走間ノイズがすべて入る。この算術から host の因果的割合や成分は得られない。
   - 根拠: shard-0 は43 hostだが、32 hostが1走だけ、7 hostが2走、4 hostが3走で、最大でも3反復しかない。host 別中央値 51.1〜79.0 秒の多くは事実上1点である。また shard-0 dispatch は repo 規模の代理である選択 node 数と `r=0.478`、開始時刻と `r=0.317`、両説明変数相互が `r=0.731` で交絡している。残余上位25%の親自身の内訳でも collection は約61%、dispatch は約36%で、「ほぼ全量 collection」ではない。
   - 誤りの向き: host に帰属可能な割合を狭く見積もりすぎている。
   - 重さ: 結論を覆す。結論2の「host 差は1割前後」はこのデータからは出ない。

5. prewarm の存在位置は支持されるが、25.6秒全量の帰属はされない

   - 対象: 「したがって controller の prewarm は必ずこの区間に落ちる。」および「内訳は collection 約51秒、controller prewarm 約18秒…である。」
   - 主張: consumer 搭載と長い dispatch の完全分離、および条件付き controller prewarm の配線は強い補助証拠である。ただし観測点は prewarm の開始・終了を採っておらず、18.4〜51.9秒の全量または下限18秒を prewarm 時間とは決められない。さらに `tryfirst` / `trylast` は controller と worker の別 process 間を順序付けないため、controller prewarm 全体が「worker timestamp の最大値より後」とも静的コードだけでは確定しない。
   - 根拠: xdist の collection end は worker payload の最大値である (`tools/acceptance_shards.py:1056-1073`)。prewarm は controller に限定され、consumer 選択時だけ実行される (`orchestrator/tests/conftest.py:774-818,830-875,2138-2154`)。JSON では dispatch≥5秒が58本すべて shard-0、他116本は0.0567〜0.8059秒で、関連は強い。一方、同じ選択数7268でも dispatch は18.44〜36.05秒、7345でも33.22〜51.89秒である。選択数と時刻を同時投入した線形回帰では標準化係数がそれぞれ `+0.528/-0.069`、`R²=0.231` で、repo 状態との関連は見えるが77%は説明されない。consumer 数そのものは JSON に無い。
   - 誤りの向き: 「prewarm と符合する」を「dispatch 全量が prewarm」と強くしすぎている。
   - 重さ: 結論を覆す。結論3は「consumer 搭載 shard 固有の controller-side work で、prewarm が有力」までなら通る。

6. teardown の memo cleanup 帰属は実行順と両立しない

   - 対象: 「`_finish_memo_sessions` は、prewarm した memo session の後始末を controller の sessionfinish で行う。」
   - 主張: `_finish_memo_sessions` は sessionfinish ではなく `pytest_unconfigure` で呼ばれる。JUnit suite `time` の終端より後なので、JSON の `teardown_s` 3〜7秒をこの cleanup が作ることはできない。
   - 根拠: conftest の `pytest_sessionfinish` (`orchestrator/tests/conftest.py:2318-2368`) には memo finish が無い。実呼出しは `pytest_unconfigure` (`orchestrator/tests/conftest.py:2953-2968`) にある。
   - 誤りの向き: 観測区間外の処理を measured teardown の原因としている。
   - 重さ: 結論を覆す。この teardown 帰属は静的に反証される。

7. report size の負相関だけでは生成量を排除できない

   - 対象: 「report を書く量の差では説明できない。…大きさと teardown の相関は −0.50 と逆向きである。」
   - 主張: 6.02〜6.08MBという狭い範囲の相関は、固定的な serialization・同期・flush 費用を排除しない。全 report がほぼ同サイズで一定の3秒を要し、別ノイズで相関が負になる入力でも、この結論は誤る。また `decomposition.json` に report byte 数がなく、`−0.50` は生データから再計算不能である。
   - 根拠: JSON の全行に共通する30 keyに report size fieldは無い。report の組立・書込みは acceptance plugin の `pytest_sessionfinish(trylast=True)` 内で行われる (`tools/acceptance_shards.py:1077-1169`)。標準の JUnit hook 順では suite stop 採取後なので、measured `teardown_s` との因果検査にこの相関を使うこと自体が不適合である。
   - 誤りの向き: 負相関が排除できる説明範囲を強くしすぎている。
   - 重さ: 表現を直せば済む。report 書込みが JUnit endpoint 後であるという別根拠なら、measured teardown の原因でないこと自体は通る。

8. 95〜207秒の「再現」は下端も選択規則も一致していない

   - 対象: 「09-04/05 の shard-0 は 79.0〜207.3 秒で、記録の『95〜207 秒』と一致する。測り方は当時と同じである。」
   - 主張: 79.0は95より16.0秒低く、範囲は一致していない。同じ source と式で似た上端を得ても、両方が同じ不適切な wall を使った可能性を排除せず、wall の外部検証にならない。さらに与件の旧量は「最遅 shard」の残余だが、README は shard-0 の残余へ置換している。
   - 根拠: README 自身の表は09-04が79.7〜207.3、09-05が79.0〜206.5である。現行 JSON でも最遅 wall は shard-0 が32/58、shard-1が17/58、shard-2が9/58で、最遅 shard と shard-0 は一般に同一でない。歴史走の行は投影された JSON に無いため、旧走での一致は独立再計算できない。
   - 誤りの向き: wall source と旧測定の同一性を強く言いすぎている。
   - 重さ: 結論を覆す。「測り方の裏取り」は wall 選択を実証していない。

9. 上位25%の「中央値超過 +20.6秒」は基準が混ざっている

   - 対象: 「裾 (残余の上位 25%) でも中央値超過は shard-0 で +20.6 秒にとどまり、その内訳は collection +12.5、dispatch +7.5、遊び +0.5、teardown +0.1 である。」
   - 主張: 残余中央値からの超過は+20.6秒にならない。+20.6は、上位15本の成分平均から全体の成分別中央値を引いて合計した値であり、残余中央値とは別の基準である。
   - 根拠: 残余中央値は85.9188秒、上位15本の残余平均は104.9353秒なので超過は19.0166秒。成分別中央値の和は84.3206秒で、104.9353−84.3206=20.6147秒となる。列挙された `12.5229+7.5170+0.4789+0.0958` も20.6147秒で一致する。
   - 誤りの向き: 裾の中央値超過を1.60秒大きく記している。
   - 重さ: 表現を直せば済む。ただし、この内訳を使った「host 差はほぼ全量 collection」の一般化も通らない。

攻撃したが所見なし: README 50〜68行の現行58走について、各 shard の中央値・範囲は小数1桁で `decomposition.json` と一致した。  
攻撃したが所見なし: 75.6/53.2/53.7秒と88/95/97%は、親が定義した「成分別標本最小値和÷残余中央値」としては再計算できた。  
攻撃したが所見なし: dispatch≥5秒が58本すべて shard-0、shard-0でdispatch<5秒が0本という集計は一致した。
