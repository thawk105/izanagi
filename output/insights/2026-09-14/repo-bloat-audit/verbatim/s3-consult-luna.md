## 2. worktree 18 本の裁定と、溜まった構造的原因

**裁定：この dev-wave が、現状の情報・権限で18本を一括撤去してはいけない。**

- D204 は対象を特定したユーザー指示を要求する。D703 の恒久例外は同一 invocation の自 wave だけ。
- DW-O28 の cleanup tool も自 wave 用。他 wave を引数へ入れることで権限を広げられない。
- D854 は生の `git worktree remove` と登録 worktree の強制削除を破壊系に分類する。
- [cleanup-branches §0–3](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-repo-bloat-cleanup/.claude/commands/cleanup-branches.md:6) は cleanup の mutation を限定し、foreign・locked・所有不明を報告限定にする。

§0 は「dev-wave は絶対に cleanup を扱えない」という逆向きの一般禁止ではない。しかし、**同一実行で cleanup の許可と dev-wave の編集・記録権限を合算する根拠にもならない。**

18本について、未commit差分、所有、HEAD の直近性、救出台帳・到達不能commit監査が未確認。非占有は所有解除や dirty 不在を意味しない。約14GBも1本774MBからの推計であり、18本それぞれの回収実測ではない。

**正しい終端は、対象を具体化した撤去判断を返すこと。** 親が既存権限でできる読み取り確認を済ませ、exact path/ref、除外理由、残る条件を示す。そのうえで必要なら対象限定の削除指示を受け、許可された cleanup 実行へ移す。

「`/cleanup-branches` を打ってください」だけで返すのは不十分。ユーザーに棚卸しやshell操作を肩代わりさせてはいけない。一方、**未付与の対象削除権限を求めることは、AI ができる作業の丸投げとは異なる。** F946 の「修正可能な赤で再開要求するな」を権限拡張に使うこともできない。

**構造的原因：lock 自体が撤去不能を作る、という仮説は refuted。**

DW-O20 は子を走らせる worktree の lock を要求するが、[dev_wave_cleanup.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-repo-bloat-cleanup/tools/dev_wave_cleanup.py:943) は、事前検査後に自対象の lock を解除して撤去を進める。

確認できた残置経路は次である。

1. land と cleanup は別工程。D702 がその分離と理由を明記する。
2. 親が land 後に対象外へ移り、cleanup を明示実行する設計。
3. 親の終了・中断、cwd 固定、占有・dirty 等による停止では残る。
4. 次 wave は他者の残置物を自動回収できず、通常 cleanup も locked・所有不明を触らない。

現行 land/startup/daemon に `dev_wave_cleanup` への直接参照もなかった。**親の生存と終端処理に依存し、残置後の回収権限が狭い**ことが滞留を許す構造である。ただし23本すべてをこの機序へ帰属させるログは無い。

分類は、設計分離と権限範囲なら既存 D702/D703 の設計判断。実際の終端漏れ・誤停止なら failures の事象であり、F26/F51 と照合して同型なら再発を追記する。原因未確定の23本を一括して新しい failure 型にしてはいけない。

## 3. 親が見落としている掃除の軸

**台帳：部分読みと worklog ローテーションは既存機構で足りている。新しい索引・ローテーション実装は今回は不要。**

見出しを数えると D は1,978件、F は966件。worklog 冒頭は、過去分の凍結移動、末尾読取、記録の簡潔化を既に定めている。

[spool_fold.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-repo-bloat-cleanup/tools/spool_fold.py:2462) は現行 decisions/failures から最大番号を取り、D/F を採番する。D は追記、F は新規追記・既存項への再発/supersede 追記で、ローテーション対象は worklog だけ。D/F の安易な分割は採番・追記先の契約変更になる。

ただし **人間・AI の部分読みと、機械処理の全読費用は別軸**。fold は canonical 台帳と worklog archive 群を読み、hash 閉包へ入れる。ローテーションしても、この費用は消えない。親の「読み込み費用」を精密化する価値はあるが、所要未測定のまま最適化を起票する根拠は無い。

**insights：件数の呼び方が間違っている。**

現物の直下は559 **entries**、内訳は264 directories・295 files。日付だけの directory 名は46件。**「559日付dir」は refuted。**

[既存README](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-repo-bloat-cleanup/output/insights/README.md) に旧名からの日付別索引があり、`tools/insights_date_layout.py::navigation` は保留理由付きリンクと、生証拠を500件ずつに分けた索引を生成する。D1941 は既に直下過密と旧名からの到達性を扱っている。これを未解決の新規裁定として再提出するのは重複。現在の全18,205 filesへの到達性は別途未検証である。

**増加速度：新gateより、既存の記録・scope 規律を適用する価値がある。**

DW-G05/D205 に従い、要求外の防御的実装・追加検査・追加台帳を増やさない。worklog はcommit内容を再説明せず、監査全文を重複掲載しない。同型 failure は既存項へ再発追記する。これらは既存契約であり、新しい「テスト数上限」「記録容量gate」は不要。

## 5. 「削除 0 件」の是非

**採る結論は、今回の tracked 削除 0 件である。**

現物で確認した重複候補は、`test_related_work_search.py` の1581行と1978行にある同一assertionの2関数。片方の述語を残せることは確認したが、nodeidを読む現役consumer・collectionへの影響は未閉鎖である。124bytesを削った実績を作るため、未確認を無影響と扱うべきではない。

残る候補も、plan が研究記録との関係を示しており、安全に削れると確定した対象は無い。worktree18本にも削除前提の欠落がある。**削除件数を達成指標にしない判断は正しい。**

ただし、親の過剰条件を残したまま「ゼロだったので不要物なし」と終了するのは誤り。0件で閉じる際には、**採用できなかった理由、未判定の範囲、権限上別実行となる撤去候補**を区別する必要がある。安全な削除ゼロと、調査対象すべての不可削除証明は同義ではない。
