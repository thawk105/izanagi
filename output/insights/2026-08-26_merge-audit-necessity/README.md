# 取り込みの合成監査 — 必要性の判定と高速化案の材料

wave: `worktree-dev-wave-merge-audit-necessity` (2026-08-26)。実装面の差分ゼロ。

ユーザーの問い: 「合成監査の必要性を確認する。必要ならば維持し高速化する。不要ならば撤廃する。」

## 結論

**維持。** ただし当初主張した「固有検出率 5 割超」は誤りで、**固有検出は最大 5 件 / 13〜15 回**。
維持の根拠は率でなく型の一意性に置いた。高速化は本 wave では実装せず、前提 3 点を条件化した。

## 親の当初主張が反証された 2 件

いずれも段 3 の独立レビューが指摘し、親が現物で確認した。

### 1. 「固有検出率 5 割超」は過大だった

台帳に「合成監査が検出した」と書いてあることを「監査が無ければ検出されなかった」と
読み替えていた。3 件は同じ回に別の機構が赤を出す型だった (git が競合を報告した件、
既存の凍結不変テストが赤を出していた件、既存の collection 検査が同型の赤を出す件)。

### 2. 「事前射影を厚くすれば監査子が速い」も誤りだった

現物比較で、射影が最も厚い走行 (diff 2 本 + merged source 4 本、repo 遮断) が
468 秒 / 28 model call、射影ゼロで親が探索範囲を 1 本に絞った走行が 320 秒 / 7 model call。
段 2 plan も独立に同じ結論を出し、因果は確定できないと書いた。

## それでも維持する理由

固有 5 件のうち 2 件は**受入全走を厚くしても届かない。**

- F481 — 「受入全走のたびに stale registry 検査が無効化される。registry が腐っても
  検出されない」型。**受入は緑のまま通る。**
- 旧 schema receipt の受理集合退行 — テスト緑・競合なし。

検査を静かに無効化する型と受理集合を静かに狭める型は、テストの緑が証拠にならない。
