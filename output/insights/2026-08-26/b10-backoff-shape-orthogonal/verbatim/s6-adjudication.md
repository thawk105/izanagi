# 段 6 レビュー裁定 — B-10 待ち方 / 待ち量の直交切り分け

段 6 の敵対レビュー 2 本 (レンズ A = 実装の正しさと検出力、レンズ B = 事前登録の実効性と帰属) の
所見を裁定する。**所見はすべて real** と判定した。refuted は 0 件である。

対象実装は `4dfd3785`。

---

## 0. 先に結論

**現状の実装は本走を起動できない。** レンズ B が見つけた投入経路の自家撞着 (投入スクリプトが
自分の receipt を作業ツリーへ書き、job 側と driver 側の clean 検査がそれを拒否する) により、
sanctioned な経路では性能測定へ 1 セルも到達しない。これは静的レビューでしか見つからない型で、
実走してから気づけば計算ノードの枠を丸ごと捨てるところだった。

**加えて、事前登録の実効範囲が主張より狭い。** 機械的に読んでいるのは 6 個の値だけで、
μ grid・形・ブロック・反復数・α・信頼区間の作り方・欠測規則は**コードの定数**である。
同じ事前登録 blob を指したまま、これらを後から変えても関門を通ってしまう。
**この wave の値打ちは「結果を見る前に判定規則を固定したこと」にあるので、ここは核心である。**

## 1. レンズ A (実装の正しさと検出力)

### A-1 6 時間枠では完走せず途中成果も再開できない — real / 採用

全規模の正しさ検証が `pipeline.py:1345` の `for _repetition in range(workload.reps)` で
**反復 5 回ぶん**回る。親も実測で確認した。3 workload × 21 genome × 5 回 × 約 120 秒 ≒ 10 時間。

- **正しさ検証の回数は減らさない。** 反復を 5 から 1 へ落とすのは、実行時間のために
  正しさゲートを弱めることであり規律 2 に反する。
- **代わりに job を相 (phase) と workload で分割する。** driver に `--phase {build,verify,perf}` と
  `--workload` を足し、次の順で投入する。
  1. build 相 1 本 (42 ビルド、共有 build cache を温める)
  2. verify 相 3 本 (workload 別。各 21 genome × 5 回 ≒ 3.5 時間)
  3. perf 相 3 本 (workload 別。各 21 genome × 3 ブロック × 5 反復 × 3 秒 ≒ 20 分)
- **事前登録束縛が一致する既存 WAL への resume を許す。** 現状は束縛の有無に関わらず
  resume を拒むので、途中で切れると再開できない。裁定 §2 B-4 の意図は
  「束縛の**無い**古い WAL を拒む」ことであり、一致する WAL は再開できなければならない。

### A-2 性能 run が certified attempt の binary 内容に束縛されていない — real / 採用

`variant_id` しか照合しておらず、`BUILD_DONE.perf_bin_sha256` と比べていない。
certified な binary と別の binary の throughput が certified セルとして受理されうる。

- **採用**: 測定直前に再取得した binary の完全 SHA を、COMMIT した attempt の
  `perf_bin_sha256` と一致させる。不一致セルは bench へ送らず判定不能にする。
  各ブロック行にその SHA を記録し、否定テストを置く。

### A-3 事前登録した変異 5 件が単一の理由で殺せない — real / 採用 (再照準)

M03 / M04 は前段の別検査が同じ入力を同じ理由で落とすので当該検査が発火しない。
M11 は `holm_adjust()` 単体しか見ておらず `judge()` が素の p を使う変異を検出しない。
M13 / M14 は実 patch を変異させていないので、意味ではなく構造 pin で落ちている。

- **採用**: DW-M01 / F28 に従い**実効 gate へ再照準する**。
  - M03 / M04: 責務を 1 つの gate へ集約するか、理由コードを分離して単一理由性を回復する。
  - M11: `judge()` の最終判定を見る検査へ差し替える。
  - M13 / M14: 実 patch を一時変異し (DW-O19 の復元規律に従う)、
    構造 pin を正しく迂回したうえで**意味の oracle だけが赤になる**構成にする。
- 変異事前登録の表を本裁定で更新する (§4)。

### A-4 申告した検出限界が実装した検定の検出力ではない — real / 採用

1.9% / 3.0% / 0.31% は 3 ブロックの座標単位の参考幅であって、
18 差を束ねた符号検定と 6 族 Holm の検出力ではない。
さらに read-heavy は Pegasus の実測ばらつき 0.22% があるのに、
採用値は linux-baremetal の 0.11% だった (親も現物で確認した)。

- **採用**: これらを「外部 floor 由来の**参考幅**」と改名し、**検出力の保証を主張しない**。
  Pegasus の実測値があるものはそれを使う。
  非有意のときに書けるのは「この設計で検出しなかった」までで、
  「検出力の範囲内で」とは書かない。信頼区間と等価範囲の関係を全セルで報告する。

### A-5 Python の厳密モデルが独立した検証器でなく式の写しである — real / 採用

同じ設計誤りが両方に入れば偽緑になる。

- **採用**: 撹拌器が奇数で全単射であることを使い、**同じ下位 63 bit を持ち最上位 bit だけが違う
  `start` の対**を C++ harness へ与え、「対の和が 2μ」を**式の構造に依らない性質**として検査する。
  端点と全剰余、0〜999 の全値も実 C++ で検査する。

## 2. レンズ B (事前登録の実効性と帰属)

### B-1 正規の投入経路が自分の receipt で作業ツリーを汚し必ず停止する — real / 採用 (最優先)

- **採用**: 投入の staging を**作業ツリーの外**の create-only な durable root へ置く。
  job 側は receipt の commit・nonce・request ID・script SHA を検証する。
  作業ツリー内に置く設計は採らない (ignore で例外を作ると clean 検査の意味が痩せる)。

### B-2 判定規則の大半が事前登録文書でなく変更可能なコード定数にある — real / 採用 (核心)

- **採用**: 事前登録文書に**機械可読な spec** を置き、次を全件 parse する。
  μ grid、形と符号化、ブロック数と実行順、workload、threads、extime、reps、
  α、Holm の族、信頼区間の作り方、欠測規則、曝露規則、判定の手続き。
- **採用**: `judge()` と解析系は global 定数でなく、この immutable な spec を**引数で**受け取る。
- **採用**: spec の SHA と解析コードの SHA / commit を、campaign lock・各ブロック記録・
  レポートへ束縛する。
- **採用**: canonical な事前登録 path を固定し、`--preregistration` で任意の文書を
  指せないようにする。
- **採用**: 式評価 cycle から物理残差の上界を**実行時に再計算**し、
  文書の申告値と一致しなければ停止する (今は個別の範囲検査だけ)。

### B-3 性能ブロックの記録が保護対象の外にあり `certified` が誤解を招く — real / 採用

- **採用**: ブロック記録を campaign の保護対象パス配下へ create-only で置く。
- **採用**: `certified` を `correctness_certified` へ改名する。性能成果物には
  `official_certification: false` を明示する。
- **採用**: trial を固定文字列でなく attempt 由来にし、投入 receipt・request ID・
  source commit・事前登録束縛・性能 binary SHA・build attempt ID を記録へ入れる。
- レポートの consumer は集計前に hash を再検証する。

### B-4 shell 経路が既存 floor campaign の安全規律を継承していない — real / 採用

- **採用**: 環境変数の掃除 (`PYTHONPATH` / `PYTHONHOME` / `PYTHONSTARTUP` を含む)、
  投入 receipt の厳密検証、`qstat` の request / host / start / **実 Elapse 上限**の完全一致、
  相ごとの失敗 receipt、signal trap を、既存 `floor_campaign.sh` と同型で実装する。
  **要求時間を自己申告しない。**

### B-5 driver 外から性能を見る経路が残る — real / 一部採用

- **採用 (安い方)**: 最終レポートと事前登録の主張を
  「**formal driver 経路については**登録前に性能を見ていない」へ明示的に限定する。
- **不採用 (scope 外)**: 一回限りの capability token による機械的封鎖は、
  repo 内の preflight より強い外部権威を要する。裁定パッケージへ送る。

### B-6 既存 generator authority の流用 — real / 採用

- **採用**: `GeneratorId` の閉集合へ B-10 用の member を足し、
  既存 inventory と policy identity を明示的に更新する。

### B-7 旧 consumer の再走で 8 件の pin が壊れうる — real / scope 外のまま

- 現在の凍結値・WAL 参照は 1 件も壊れていない (レンズ B が現物 SHA で全件照合した)。
- 段 4 の裁定どおり scope 外を維持する。`patches/README.md` の警告は正確と確認された。

### B-8 段 5 の事前登録案に修正前の SHA が残っている — real / 採用

- **採用**: 親が書く事前登録文書は段 6 の SHA
  (patch `36cd974c…`、式 `5b3d8dee…`) を使い、commit 前に現物から再計算して照合する。

## 3. レビューが確認した「壊れていないこと」(重要)

- 既知材料の SHA-256 10 件は開示表と全件一致した。
  既知の数値も WAL から再計算して一致した (write-heavy +38.3288% / balanced +11.2682% /
  read-heavy -6.6430%)。calibration も records 1,000,000、作業集合 / L3 = 4.9275、
  `saturated=false`、`lower_bound_selected=true` で一致した。
- 受理集合は広がっていない。grammar、`ALLOWLIST`、`EVOLVE_BLOCK_SOURCES`、verifier、
  hook 本体は HEAD と親 blob が同一で、在庫の差分は完全一致集合への member 追加だけだった。
- C++ の式は裁定どおりである。指示値は常に μ/2〜3μ/2、同じ下位 63 bit を持つ最上位 bit の対の和が
  2μ になるため全域一様入力では平均が厳密に μ。μ=5 / 25 の 2.5 / 7.5 / 12.5 / 37.5 は
  二進浮動小数で厳密に表せる。未定義動作なし。0〜999 は旧式と数値的に同一。
  両乱数形は実際に同じ撹拌器を使っている。
- 規律 1 の分離と規律 2 の即 reject は経路として成立している。

## 4. 変異事前登録の更新 (A-3 の再照準)
