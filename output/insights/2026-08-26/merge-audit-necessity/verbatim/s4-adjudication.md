段 1 の 8 件のうち 3 件は、合成監査が無くても別の機構が同じ回で赤にした型である。

  親が「テスト緑」と書いたのは誤り
- 0823-859 — 既存の collection 検査が `UsageError` を出す型で、次の関連走行で赤になる

0820-771-772 / F481 / 0823-863) である。

### それでも維持する理由 (レンズ A も「撤廃を支持しない」と明記)

固有 5 件のうち 2 件は、受入全走を厚くしても届かない。

- **F481** — 「受入全走のたびに stale registry 検査が無効化される。registry が腐っても
  検出されない」(`docs/failures.md` F481 本文)。**受入は緑のまま通る。**
- **0823-863** — 受理集合が意図せず狭まる退行。テスト緑・競合なし。

**受理集合を静かに狭める / 検査を静かに無効化する型は、テストの緑では検出できない。**
これは絶対規律 2 が守る面そのものである。固有検出率が 3 分の 1 でも、
1 件が main へ入れば以後の certified 選択結果すべてが無効化された検査の下で作られる。
費用 (106〜468 秒) は釣り合わない側にない。

## 2. 高速化 — 本 wave では実装しない (`4→7→8→9`)

段 1 が選んだ手段 (`tools/merge_audit_projection.py` の新設) を**取り下げる。**
段 3 が 3 件の blocker を出し、親が全件を現物で裏取りして real と裁定した。

### blocker 1 — tool が必須経路を通らない (レンズ B 所見 1、real)

親の裏取り: `tools/dev_wave_wait.py:3635-3660`。正規の main 取り込みは受入待ち手の
post-claim merge であり (`docs/dev-wave/operations.md` DW-O20)、`git merge --no-ff --no-commit`
の直後に `check_ai_provenance.py` を連続実行する。**間に親が入る停止点が無い。**
`DW-O17` は commit 直前にしか読まれない。

したがって「新 script を置いて `DW-O17` に 1 行足す」配線では、tool は
**親が思い出したときだけ通る位置**にしかない。carry stub になる形である。
必ず通すには受入待ち手そのものを変える必要があり、同 file は受入 receipt の argv まで
pin されている。本 wave の scope を超える。

### blocker 2 — Pegasus 実行分類 (レンズ A 所見 8・レンズ B 所見 6、両者 real)

`tools/README.md:11-23` は新規 script の分類を必須とし、判定量を
「同時に生きる全子孫を含む cgroup の charged memory のピーク」と定め、
**実測はユーザー端末の手番で AI・自動化は測らず依頼する**と書いている。
現ホストは `pegasus02` (login node)。

親は前例 (`tools/check_subprocess_bytecode_guard.py`、streaming 形、
wall 10.9 秒 / 最大 RSS 60 MB、未登録で常用) を示したが、
**最大 RSS は cgroup charged memory ではない**ためこの証拠要件を満たさない。
「44 script が未登録」は machine gate の被覆漏れであって規律の撤回根拠にならない
(同 README 自身が「3 層の外は緑のまま通り」と明記)。親の反論は却下する。

### blocker 3 — D697 / D554 / D770 の 3 集合を運用文の 1 語へ畳む (レンズ A 所見 6、real)

- D697 決定 8 の発火条件 = 両親が同じ実装面 file を変更
- D554 の author 昇格条件 = 結果が両親双方と食い違う実装面 path
- D770 の 2 commit 分割条件 = combined diff 非空

3 つは別の集合である。plan の `DW-O17` 置換文「実装面path差」はどれか分からない。
どれを取り違えても、監査が減るか不要な分割が増える。

### 併せて採用した所見 (tool を作る場合の必須要件)

- A1 (blocker) — F324 が要求する「満たさない件数」と母集合を schema と renderer が
  構造的に強制すること。件数欄が無いまま「静的 call 候補なし」で閉じられる
- A2 (major) — `complete` が真かつ意味的 call 不完全が両立しないこと
- A3 (major) — YAML・生成コードを含む Markdown・**submodule 内部差分**を必須手動監査へ。
  第三者 submodule は gitlink 1 行なので superproject の tree 走査では中身が列挙されない
- A5 (major) — F324 の実 merge を回帰に固定すること。t1726 の 1 path だけでは、
  走査を canonical path 集合へ狭める退行が緑で通る
- B7 (major) — blob 上限・出力上限と、rc=1 を誰が成功扱いで監査子へ渡すかの契約

### 速度主張の扱い (レンズ B 所見 3・5、採用)

- 「アンカーが探索量を減らす」因果は **n=2 で交絡が多く未確定**。plan 自身も
  「確定できない」と書いている。**短縮秒数を報告に書かない。**
- D554 が引く 52 分損失は旧待ち行列の事例で、現行は単発 claim。
  lease TTL 2400 秒に対し監査は 4.4〜19.5%。**lease 窓は律速ではない。**
  節約時間として数えない。
- ただしレンズ B 所見 4 (refuted) のとおり、監査子は当該経路の 33〜68% を占める。
  「少数派だから放置してよい」も成り立たない。

## 3. ユーザー裁定へ返す 1 件 (親は不採用にしない)

### D770 の前提が後発の D785 で崩れている (レンズ B 所見 2、real、親が裏取り済み)

D770 (2026-08-24) は「staged merge のまま author 子を起動する経路は機械的に存在しない」
ことを根拠に、実装面が重なる main 取り込みを 2 commit へ分割せよと決めた。

**D785 (2026-08-25) がこの前提を撤去している。** 親の裏取り:
`tools/dev_waves/launch_authority.py:498,507` の `allow_mid_merge`、および
`tools/codex_worker_launch.py:2634` が `stage == "author" and sandbox == "workspace-write"`
のときに capability を渡す。健全な 2 親 merge 進行中なら authority docs の bytes 比較を省く。

つまり**今は staged merge のまま author 子を起動できる。**
D785 の裁定文は D770 に言及しておらず、この supersede は台帳に未記録である。

これが本 wave で見つかった中で**最大の高速化余地**である。実現すれば
実装面が重なる取り込みのたびに、commit 1 本と `git write-tree` 照合が消え、
さらに監査子が報告だけでなく**その場で修正**できるようになる (現行は再適用が要る)。

`DW-O17` は既に単一 merge commit の手順を書いており、D770 とも食い違っている。

**`DW-S04` に従い、親はこれを自分で覆さない。** 承認済み裁定を後発の未記録な事実で
止める形なので、新事実を添えてユーザー再裁定へ返す。

**ユーザーへの問い:** 実装面が重なる main 取り込みを、D785 の mid-merge author 起動を
使う 1 commit 手順へ戻してよいか。戻すなら D770 を supersede する決定が要る。
