## レンズ B の攻撃面 — 実効性と層の網羅
1. **効く層の網羅。** この gate は launcher (`tools/codex_worker_launch.py`) の中だけで効きます。
   実際に codex worker を起動する全経路 (dev-wave の launch script、`tools/run_codex_role.py`、
   `orchestrator/codex_roles/launcher.py`、その他の caller) を repo 内で列挙し、
   受理判断がこの gate を必ず通るか、gate を通らずに成果物が採用される経路が残らないかを
   file:line で検査してください。scope 外の層があれば、実装したふりをせず
   **裁定パッケージ候補**として分けて列挙してください。
2. **実効性。** 改修後、実際に 10〜20 秒級の停滞が起きたときに何が起きるか (どの field が何になり、
   人間が読む診断に何が出るか) を追跡してください。診断が消える経路、
   停滞の原因が分からないまま not_accepted になるだけの経路があれば指摘してください。
3. **偽陽性の実害。** wall 予算を超えた job を not_accepted にすると、
   実運用 (dev-wave の子起動、受入全走と並走する状況、共有ノードの負荷) で
   どれだけ既存 job が落ちるようになるかを見積もってください。
   既定 `max_wall` 値と実測分布 (repo 内に根拠があれば file:line) を根拠に、
   この改修が既存フレーク (F57 族) を悪化させないかを判定してください。
4. **テストの実効性。** プランのテストが停滞を注入する方法は、production を汚さず、
   かつ実障害と同じ経路を通るか。monkeypatch を使うなら正規の注入 seam があるかを検査し
   (`DW-O14` の趣旨)、外側 timeout・fixture の budget・並列実行 (xdist) との干渉を検査してください。
   テストが負荷で不安定になる (新しいフレークを作る) 危険があれば指摘してください。
5. **記述の正直さ。** `wall_clock_scope` の値と docs / help / receipt の記述が、
   改修後の実際の scope と一致するか。過大な保証を謳って実際には発火しない箇所を探してください。
6. **変異の帰属。** 親が段 4 で登録する変異が、この改修の検出力を本当に測れるか。
   「production を壊しても既存テストだけで赤になる」ため新テストの純増検出力が示せない変異、
   逆に単一理由性が崩れる変異を予測してください。
