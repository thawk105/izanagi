## レンズ A の攻撃面 — 正しさ境界
1. **受理集合。** プランの改修で `accepted` になる job 集合が、意図せず**拡大**する経路はないか。
   逆に、予算内で正常に終わる job を誤って弾く経路 (偽の not_accepted) はないか。file:line で。
2. **create-only 不変条件。** receipt slot 予約 (`_reserve_receipt_slot`) と output 公開の N-3 順序、
   `_atomic_create_json_reserved` の replace_invalid 経路が、プランの再評価挿入で壊れないか。
   部分的に書かれた receipt が最終 path から見える窓が開かないか。
3. **rc と receipt の整合。** `_writer_truth` の真理値表、`launcher_rc`、process の返り値、
   `_publish_launcher_error_receipt` 経路の間に矛盾する組合せが生じないか。
   例外が飛んだ場合 (LaunchError、BaseException) の巻き戻しはどうなるか。
4. **flip 時の巻き戻し。** accepted → not_accepted へ flip したとき、既に公開した output file、
   `args.output_published_by_run`、manifest への session 追記、receipt の `output_sha256` の
   整合が全て保たれるか。漏れがあれば file:line で。
5. **checker との整合。** `_validate_receipt` の schema v2 束縛 (`wall_clock_scope` の文字列一致、
   `_RECEIPT_FIELDS_V2` の閉じた field 集合、accepted/not_accepted ごとの conjunct 検査) が、
   改修後の receipt を通すか。既存の実 receipt (schema_version=2、
   wall_clock_scope=launcher_start_to_receipt_fields_finalized) を将来も通すか。
6. **恒真な保証。** プランが追加するテストのうち、production を変えなくても緑になるもの、
   あるいは production を壊しても赤にならないものはないか。
   「変更前は赤」の主張が実際には成り立たないものを特定してください。
7. **依頼文言との差。** 依頼は「publication 完了後にも wall gate を再評価する」です。
   プランが実際に達成する範囲と依頼文言の差を明示し、測れない残余区間を全て列挙してください。
   その残余が受理判断に与える最悪ケースを構成してください。
