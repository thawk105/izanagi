## R2 の攻撃面
1. **恒真な保証。** 追加された 3 node (N1 staging 超過 / N2 audit 超過 / N3 staged temp 再利用) の
   各 assert が、**production を壊しても赤にならない**ものになっていないか。
   特に次を疑ってください。
   - `assert list(tmp_path.glob(".receipt.json.tmp.*")) == []` の glob が実際の temp 名・
     配置と一致するか (一致しないなら恒真)。
   - `stage_calls == 2` / `published_audits == 1` が本当に制約になっているか。
   - inode 同一性の観測が、helper を差し替えた自分自身を見ているだけになっていないか。
2. **変更前赤の成否。** 各 node が変更前の production では本当に赤になるか、
   赤になる理由は何か (どの assert が最初に落ちるか) を file:line で示してください。
   赤にならない node があれば特定してください。
3. **変異への耐性。** 親裁定 §4 の事前登録変異 MT1〜MT5 を 1 件ずつ検討し、
   「その変異を入れたとき、どの node が赤になるか」「単一理由性が崩れないか」を予測してください。
   生き残る (SURVIVED になる) と予想される変異があれば、その理由と、必要な追加 assert を示してください。
4. **フレーク risk。** 論理時計 (`LAUNCHER._monotonic_ns` の差し替え) が
   同一 pytest worker 内の他コード・並列実行 (xdist)・外側 timeout と干渉しないか。
   新しい負荷フレークを作らないか。実 sleep を使っていないことを確認してください。
5. **主張の正直さ。** 実装と docstring が、親裁定 §0 の縮約
   (「publication 完了後」ではなく「最後の可逆点」) を超える保証を謳っていないか。
   `actuals.wall_clock_s` の意味と late gate の観測時刻の差が正しく書かれているか。
   過大な保証・実際には発火しない assert があれば指摘してください。
6. **既存テストの弱体化。** 既存 assert の反転・緩和・skip・削除が差分に紛れていないか。
   期待値へ揮発する payload (hash 等) が焼き込まれていないか。
