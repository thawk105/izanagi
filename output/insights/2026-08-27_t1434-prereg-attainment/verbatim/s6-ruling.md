## MF-06 を不採用にした理由

**これは到達度の記述ではなく、事前登録の規則文である。**

1. 本 wave の scope はユーザーが §5.2 / §5.3 / §10 の**到達度記述**に固定した。
   規則文の改訂はそこに含まれない。
2. 段 3 レンズ B が「到達度の記述に見せかけて意味規則を変える文を持ち込むな」と警告し、
   親は段 4 でそれを採用した。ここで規則文を書き換えるのは、自分の裁定を破ることになる。
3. **誤りの向きが安全側である。** この文は gate を実際より**厳しく**書いている。
   実装を緩める方向には働かず、規律 2 が守る「到達していないものを到達したと書く」型でもない。
   同じ §10 の 2 段落上で「集合は `{null}` か `{固定 version}` のどちらかだけを許す」と
   明示しているため、節を通して読む読み手が誤解する余地も小さい。
4. fail-closed の規則文を到達度 wave のついでに書き換えるのは、失敗したときの損害が大きい。

**次タスクへ送る。** 「§10 の『上記項目が欠落する場合、schedule を無効化する』を、
全 slot `{null}` の schedule を price 未束縛として受理する実装に合わせて限定する」を
scope 外の real 所見として記録する。

## MF-01 / MF-02 / MF-04 が scope 内である理由

これら 3 件は**差し替え前から §5.2 の表にあった過大主張**であり、本 wave が持ち込んだものではない。
それでも採用するのは、本 wave の scope が「§5.2 / §5.3 / §10 の到達度記述を実装に合わせる」で
あって「実態より低い記述だけを直す」ではないからである。**過大主張の方が規律 2 に照らして危険**で
あり、到達度 wave がそれを見つけて放置するのは筋が通らない。
