# 親 brief 2 — scope 拡張分 (T-352 / T-358)

ユーザーが同一 wave の scope を 3 件へ拡張した。理由は「いずれも同じ畳み込み機構 (fold) を触るため、
別 wave にすると三つ巴の衝突になる」。(1) は既に実装・テスト済み (brief.md が正本)。
本書は追加された (2)(3) の brief である。

## (2) T-352 — `完了` の終端性を構造 field の必須化で判定する

**ユーザー裁定 = 択 (a) (確定・変更不可)。**

現状: `tools/spool_fold.py:467`

```python
            if name == "完了" and re.search(r"残件(?:[はが:]|：|[ \t])*あり|一部完了", output):
```

`### 完了` 節の item は、「残件あり」「一部完了」という 2 語が**無いだけ**で受理される。
`初期処置だけ終了。後続作業は明日行う。` は受理され、残件のある T が active から消える。
active 集合は fold が「入力 − 完了 − 見送り + 新規」で再生成するため、消えた項目は
`### 次の一手` から脱落し、後続 wave が拾えなくなる。

裁定 = **構造 field (`remaining: none` 等) を必須化する。**
不採用となった択 (b) (意味判定を諦めて `更新` を既定にする) は、完了の信号自体を失い
active 一覧が縮まらなくなるため採らない。

`docs/spool/README.md` の「この仕組みが保証しないこと」に
「`完了` と書かれた項に本当に残件がないかは、『残件あり』『一部完了』という語の検出までしか
見ない」とあり、この記述も更新対象になる (**docs は親が書く。実装子は触らない**)。

## (3) T-358 — 見送り台帳の既存項目へ「発火記録」を追記する経路を新設する

**ユーザー裁定 = 択 (a) (確定・変更不可)。**

現状: `tools/spool_fold.py:1212 _insert_deferred` は、`docs/phase3.md` の見送り台帳の
H3 region 末尾へ**新規項目を挿入するだけ**で、既存項目の本文へ追記できない。
failures には `## 再発` に相当する追記経路があるが、見送り台帳には無い。
fragment 形式 (`docs/spool/README.md`) にも該当節が無い。

一方、wave は canonical を直接編集しない規律なので、見送り台帳が**自身の慣行として要求する
「発火記録」を書く手段が存在しない**。現に `[T-058]` (述語 `safety_gate_changed`) と
`[T-059]` (述語 `validator_or_rejection_gate_changed`) は D125 / D127 / D128 で発火しているのに
記録できていない。

裁定 = **fragment に `見送り追記` 節を新設し、fold が既存項目へ追記できるようにする。
慣行は変えず手段だけ補う。**
不採用: (b) worklog 側へ移す (台帳単体で発火履歴を追えなくなる)、(c) 慣行の廃止
(条件付き見送りの追跡ができなくなる)。

**実装後、滞留している [T-058] / [T-059] の発火記録を書き戻すこと** — これは本 wave の
fragment に `見送り追記` 節を書いて fold させる形で行う (自己適用)。

既存の見送り台帳項目の形は `docs/phase3.md:597` (T-058) と同 :598 (T-059) が実例で、
1 項目が長い 1 行に「発火記録: ... 。N 度目の発火 ... 」を継ぎ足していく形式である。

## 不変条件 (追加分)

- (I5) fold の既存不変条件を壊さない。canonical への書き込みは追記と、既存 F エントリ・
  見送り台帳への挿入に限る。**見送り追記は「既存項目への追記」であり、この列挙の更新が要る**
  (`docs/spool/README.md` の不変条件節。docs は親が書く)。
- (I6) 保存則検査 (出力 active 集合 == 入力 active − 完了 − 見送り + 新規) を壊さない。
  見送り追記は active 集合を変えない操作である。
- (I7) fold は決定的かつ冪等。時刻・mtime・ディレクトリ列挙順を出力に使わない。
- (I8) **未 fold の既存 fragment を壊さない。** branch `worktree-rulings-2026-08-02-e` の
  fragment 5 件は本 wave が取り込んで一緒に畳む。親が実測した結果、5 件はいずれも
  `### 更新` と `### 新規` しか持たず `### 完了` 節を持たないため、T-352 の必須 field 化の
  影響を受けない。**実装子はこの実測を自分で再確認すること。**
- (I9) 実装面 (コードとテスト) は Codex `role=author` が書く。docs は親が書く。

## 親の provisional 裁定 (= 攻撃対象)

- **(P4)** 構造 field は item 内の行として `remaining:` を必須化し、値は閉じた語彙
  (例 `none` のみ許可、将来拡張は別裁定) とする。既存の `base:` 行 (`_strip_base`) と同じ
  「item 内の機械可読行」の枠に載せる。**この設計は攻撃対象** — `base:` と同じ枠に載せるのが
  本当に妥当か、値の語彙をどう閉じるか、`残件あり`/`一部完了` の語検査を残すか消すかを論じること。
- **(P5)** `見送り追記` は `### 見送り追記` という H3 節とし、action 節の順序
  (`carry`, `完了`, `更新`, `新規`, `見送り`) の末尾に置く。item は
  `- [T-NNN] <追記本文>` の形で、既存項目の**末尾へ追記**する。**この設計は攻撃対象** —
  節名、順序上の位置、item 形式、追記位置 (行末か新しい継続行か)、冪等性の担保、
  対象 ID が見送り台帳に存在しない場合の扱いを論じること。
- **(P6)** T-352 と T-358 は同じ `tools/spool_fold.py` を触るため、**実装子は 1 本**とし
  並列化しない。**この判断も攻撃対象。**

## 成果物影響 (DW-G05)

- (2) を実装しない場合: 残件のある T が `完了` として active から脱落し、`docs/worklog.md` の
  `### 次の一手` (可変状態の正本) から消える。後続 wave はその作業を拾えない。
- (3) を実装しない場合: 見送り台帳の発火記録を書く手段が無いままで、条件付き見送りの
  発火履歴が `docs/phase3.md` に残らない。現に T-058 / T-059 の 3 件分の発火 (D125 / D127 / D128) が
  滞留している。

## scope 外 (広げないこと)

- **T-347** (fold commit の tree を計画と blob 単位で照合する) は scope 外。ユーザーが明示した。
- **凍結ソース閉包に触れない。** T-335 の実測で、`DW-O09` の pin 閉包列挙は凍結文書側が
  ソースの sha256 を pin する経路を拾えず、targeted 全緑のあと受入全走で初めて抵触が出て
  fix 4 巡目を要した。**targeted だけで緑を主張しない。**
- 見送り台帳の慣行そのもの (何を書くか) は変えない。手段だけを補う。

## 受入 (ユーザー指定)

単体テストだけで済ませない。**実際にローテーションを伴う land を通すこと**が合格条件。
worklog は現在 97,061 / 100,000 bytes で、取り込む fragment 5 件 + 本 wave の fragment を畳めば
必ずローテーションが起きる。それがそのまま positive control になる。
