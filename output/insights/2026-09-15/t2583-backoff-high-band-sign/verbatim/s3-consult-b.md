  - 何が壊れるか: 両セルに高域観測はあるが辺が重ならない場合も、広窓に高域観測が皆無の場合も、`executable=false, common_edge_count=0, fixed_weight_sum=0` になる。`feasibility` 単体と既存 J1 の空の `edges` からは、どちらの構造か検算できない。

## 親 brief への攻撃

### P1・入力経路：import／overflow／CLI必須入力による停止説は成立しない

- **import は静的には成立する。** 解析器:8–16 は標準ライブラリのみで、相対 import はない。module 直下は定数・関数定義で、外部ファイル読込みは関数内、CLI は:1364 の `__main__` guard 内にある。`spec_from_file_location` → `module_from_spec` → `spec.loader.exec_module` でよい。package 所属というだけでは壊れない。
- **overflow だけでは `_load_new_trace` は落ちない。** `allow_overflow` 引数も `dropped == 0` 条件も存在しない。65,536 + 152,205 = 217,741、65,536 + 355 = 65,891 は整合する。D1935（`docs/decisions.md:58072`）の対象は producer の **`_parse_backoff_trace`** であり、この loader ではない。`allow_overflow=True` を loader に渡す修正は逆に `TypeError` を起こす。
- テスト:249–265、685–707 も、取りこぼしありの入力を正常系として扱う。ただし今回 trace の全 event の型は検査していないので、**実ファイル全体の通過済みとは言わない**。
- **loader の直接呼出しは成立する。** `Path` を渡して `(resolved, runs)` を受け取り、`_j4_effective_update_interval(runs)` の第2戻り値を J1 の `coverages` に渡せばよい。stock/static README はこの経路に不要。
- CLI の `--new-trace-json` は必須ではない。全解析 API で指定すると `baseline_tps` と `static_low_b` も必要になる（解析器:1207以降）。その全解析経路へ置き換える提案は、無関係な入力を増やす。

P1 の4関数を接続する `FunctionType` 案にも、現物上の破綻は見つからない。ただし bytes 不変は CLI の高域対応を意味せず、plan:143 の限定が必要である。

### P2・P3：辺の定義と「測れない」の射程

- P2 の `min(edge)>50` は「両端>50」と同一で、別の感度解析ではない。これは plan:48 で修正されている。
- P3 の `K>=10` は既存 J1 の比較資格としては正しい。しかし **`K<10` は高域符号の記述統計が計算不能という意味ではない**。brief:12 の「既存 J1 経路では測れない」は「指定された更新間隔対照の高域比較が成立しない」まで限定すべきである。
- brief:11 の「高域の勾配符号は1度も測られていない」も広すぎる。高域を含む trace に符号は既に記録され、既存 J1 の `_edge_observations` は帯域を絞らず抽出する。未充足なのは高域の対照比較・明示的な集計である。

### P4：実行前固定でも既知結果から独立にはならない

逐語 `j1-measured-facts.md:71` は広窓の `backoff_before` 最大値を **12 µs** と報告している。主定義は直前 event の before も >50 を要求するため、この既知値を信頼すれば主高域辺ゼロを既に予想できる。

したがって P4 は事後の変更を防げても、「高域結果について未知の状態で設計した」証明にはならない。plan:7、181 の既知情報の明記は必要であり、削ってはならない。

### 実測値には算術誤りがある

逐語 `j1-measured-facts.md:26` の **68.9% は誤り**。同資料:19 の整数なら、

`152,205 / 217,741 = 69.901855…%`

で、約 **69.9%** である。`nm-step1` の約0.54%は整合する。また、event の保持割合と J4 の時間被覆率 `Σwindow_us / extime_us` は別量である。

brief:58 の trace パスと **140,354,574 bytes** は現物で確認できた。brief:60–61 の J2 数値は指定逐語表と一致するが、本相談では全量から再計算していない。

### 「bytes pin は無い」という結論は、指定 brief に存在しない

指定 brief 全66行には `DW-O09` の閉包結果も「bytes pin は無い」という文もない。まず、攻撃対象として提示された版とその主張が対応していない。

広く「pin が皆無」と言うなら反例はある。指定 trace 冒頭には `prereg_sha256`、`driver_sha256`、`pbs_sha256`、`patch_stack[*].sha256` があり、既存 T-2188 の `verbatim/s4-ruling.md:61` も、旧事前登録 SHA が payload に残ることを明記する。閉包からこれらを落としてはならない。

ただし、これらは既存測定の出所の束縛であり、**今回編集しない解析器を現行 bytes に固定する live gate の発見ではない**。「無関係な歴史的 pin がある」ことを理由に、新しい pin 検査を追加する必要はない。解析器の live pin の不存在まで、この探索から証明したとは扱わない。

## scope 逸脱の列挙

- **`step_axis_descriptive` の全10組比較値**（plan:98、151、166、189）：対照成立範囲を示す共通辺数までは本題に接続するが、全組の比較値まで必須にするのは分析対象の拡張。最優先で削れる。
- **セル内低高域比較・各セルの追加3区間比較**（plan:95–96、189）：主対照の既存3区間処理とは別の追加分析。生死確認より先に必須化する根拠がない。
- **`analyzer`／`preregistration` の SHA と利用資格 field**（plan:159–161）：出所の記録としては新しい gate ではない。hash一致を測定開始条件や受理判定に転用すれば scope 外となるが、現プランにその検査実装は書かれていない。**記録 field があるだけで「台帳追加」と断罪する攻撃は通らない。**
- **事前登録本文の `K>=10` と支持閾値**（plan:185–187）：既存比較の条件を固定しており、新しい correctness gate ではない。ただし、これを単独セルの符号集計の出力条件にしてはならない。
- **insight の利用資格・限界・旧判定との関係**（plan:197–215）：散文の報告であり、現状では新しい機械的 gate や台帳ではない。JSON と重複する説明は削れる。
- **削ってはいけないもの**：元列の隣接関係、ゼロ込み母数、両セルの辺別正負数、保持範囲、主対照の共通台。これらを削ると、主題の実測と不成立の証明そのものが死ぬ。

## 総括

最も強い攻撃は、100行の probe に全10組などの追加分析を詰め込みながら、不成立理由を検算する生の計数の配置が曖昧な点である。  
高域対照の不成立と、高域符号そのものの測定不能は分ける必要がある。  
import、overflow による loader 拒否、CLI入力不足、`FunctionType` 接続不能という攻撃は現物では通らなかった。  
配置規約違反と、140 MBだから login node では危険という断定も成立しない。
