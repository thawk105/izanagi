## 所見

### 1. 左側の観測不足を入力・実行障害へ誤分類し、全結果を捨てる

- 深刻度: **major**
- 何が壊れるか: 広窓側に主帯域の非ゼロ観測があり、左側には無い正常な trace → `measurement_incomplete`、例外、終了コード 1。既に計算済みの全 6 セルの生計数、低域・感度集計、既存 J1 の返り値まで出力されない。
- 根拠: `probe.py:66`、`:69–70`。仕様 `s4-adjudication.md:110–112` は構造的不成立と入力不正・import 失敗・メモリ不足を区別する。左側欠如は表の未定義ケースであり、測定全体を破棄する根拠にはならない。今回は右側の主帯域対数が 0 なので最初の分岐で確定し、さらに左側には **43,147 件**の非ゼロ観測があるため発火しない。
- 最小の是正: 左側欠如で全体を例外終了せず、生計数と比較値 `null` を保存する。5 状態表で未定義であることを明示し、入力障害への分類を避ける。

### 2. 「刻みが違えば辺は一致しない」は今回の JSON 自体が反証している

- 深刻度: **major**
- 何が壊れるか: `nm-step25` と `nm-step100` は主・感度の両帯域で **自己辺 `(1000,1000)` を共有する**。それぞれゼロ符号 236 件・610 件だけなので推定用の共通辺数は 0 だが、README はこれを「辺そのものが一致しない」「刻み幅による設計上の必然」へ拡張している。
- 根拠: `probe.py:85` は `_edge_counts` のキー交差。解析器 `:512–513` がゼロ符号を除外する。JSON の `cells["nm-step25"].bands.both_endpoints_gt_50.edges` と `cells["nm-step100"].bands.both_endpoints_gt_50.edges` に当該自己辺が実在する。過大な記述は `README.md:20–24`、`:156–159`。
- 最小の是正: 「当該 trace では、両側で非ゼロ符号を持つ高域共通辺が 0」と限定する。共有自己辺は存在するが、その符号がすべてゼロなので比較に使えないと説明する。

### 3. 辺別 n の中央値から「下方偏りは最大でも 0.8%」とは言えない

- 深刻度: **minor**
- 何が壊れるか: `nm-step1` の主帯域には **n=1** の辺が 2 本あり、`nm-step2` にも **n=6** の辺がある。中央値を最小値として扱った説明により、辺別推定量の最大相対下方偏りを過小表示する。独立 Bernoulli 仮定ではそれぞれ 100%、約 16.7% になり得る。
- 根拠: `README.md:179–181`。JSON の主帯域 `edges` で `(120,121)` と `(121,122)` は `[n_plus,n_minus]=[1,0]`、`(442,444)` は `[0,6]`。仕様 §3.4 が明示した標本数依存性と矛盾する説明である。
- 最小の是正: 「最大でも 0.8%」と、それを根拠とする断定を削除する。中央値と辺別最小 n を区別し、平均値への影響と辺別の偏りを混同しない。

### 4. 「12 共通辺すべてに補正」は n=1 の辺で定義不能

- 深刻度: **minor**
- 何が壊れるか: 旧 J1 の `(0,1)` の広窓側は **n=1、d=0**。記載された補正 `d/(1−1/n)` は **0/0** となり、全 12 辺への適用はできない。報告値の差 **0.0380** は、この補正不能値を 0 に置いた計算で再現するが、その例外処理が記されていない。
- 根拠: `README.md:28–30`、§5 の最初の項目。JSON の `existing_j1_unmodified.overall.edges` にある `(0,1)` の `update2560.count=1`。読み取り検算では、当該辺を両側から除くと差は **0.0376106**、補正不能値を 0 とすると **0.0380008**。
- 最小の是正: 「すべてに補正」を撤回し、n=1 の処理と補正計算の対象を明記する。補正不能な辺を含む点推定から偏りの寄与を否定しない。

## 解析器の無改変の検査

- probe に解析器の module 属性・グローバルへの代入、関数差替えはない。`contrast` への追記は新しい返却辞書への変更である。
- 現物・`HEAD`・base `0600887d9`・JSON の解析器 SHA-256 はすべて `134b33d294518e0c3fb4c183dd472bff9085c928eddd4241997a18356dae0e3e` で一致した。`bytes_unmodified=True` という固定値だけに依存せず確認した。
- 解析器の import は標準ライブラリ、定数、関数定義からなり、CLI は `__main__` guard 内。import による解析・出力の実行はない。通常の import には bytecode 作成の可能性があり、仕様どおり起動側の `python3 -B` が必要。当該解析器の `.pyc` は現在見つからなかったが、過去の起動フラグまでは証明しない。
- create-only の事前確認と `open('x')` は競合時の上書きも防ぐ。`:99–100` はエラーを stderr に出し、`:104` が終了コード 1 にするため、**失敗を成功終了に変える経路はない**。
- `analyze()` または JSON 直列化中の例外では、出力はまだ開かれておらず部分ファイルは残らない。書込み・close 中の障害では空／部分ファイルが残り得て再試行も create-only に拒否されるが、その実行は非ゼロ終了する。
