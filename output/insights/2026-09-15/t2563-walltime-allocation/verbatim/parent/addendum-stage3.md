# 親からの追補 (段 3 用) — 段 2 の結果を受けた論点の移動

段 2 の plan は次を返した。段 3 はこの追補も含めて攻撃せよ。

## 1. 数値の訂正 (親の実測誤り)

親のアンカー表 D は計測前を 3230 秒としたが、**正しくは 3250 秒**。
`tools/pegasus/policy.json` の `perf_candidates` が 2 件あり、
`certify_calibration.sh` の候補ループで version(10) と smoke(10) が
最大 2 候補分まで走りうる (第 1 候補の smoke が失敗し第 2 候補が成功する経路が到達可能)。
親は 1 候補分しか数えていなかった。真値は **3250 + 4990 + 600 = 8840 秒**。

この訂正自体も検算せよ。**特に「`timeout` の付いていない重い処理が無いか」を見よ。**
あるなら 3250 は上限ではなく下限であり、案の前提が変わる。
plan は `S:197` の最大 60 回の sleep と、timeout を持たない source 検査・後処理を
「この真値には含まれない」と明記している。これが正しいか確かめよ。

## 2. 親は暫定裁定 (P1) を撤回し、別の案へ移る

親の旧 (P1) は「`certify_walltime` を 7200 → 10800 へ上げる」だった。**これを撤回する。**
撤回の理由は 2 つで、どちらも段 3 の攻撃対象である。

**(i) D1971 の逐語。** plan は「要求時間増加へ戻さず」を恒久の禁止と読んだ。
親は当初これを当該 wave 限定と読んでいた。逐語は両読みを許すが、
**より新しい D1986 (項 3 / 9 / 10) が「閉じるのに新しい関門・台帳・汎用化が要るなら閉じず、
保証の限界を成果物の文面へ出す」を既定の型として確立している。**
曖昧なユーザー裁定のもとでは、踏み越える側でなく限界を明記する側を採るのが house の型である。

**(ii) 絶対規律 4 (実験スケールを無造作に大きくしない)。** 3250 秒は各コマンドの
**kill-switch の上限の和**であって所要時間ではない。実測は桁が 2 つ違う。
2026-09-11 の 2 job (991694 / 991727、正本
`output/insights/2026-09-11/t2563-calibration-runtime/README.md`) では、
job 開始→static probe が 6 秒、static→pre attestation が 33 / 29 秒。
**計測前の実所要は 35〜39 秒**であり、cap 和 3250 秒の 1.2% にすぎない。
実績 186 秒で終わる job のために共有クラスタへ 3 時間を要求し queue 待ちを伸ばすのは、
「大きすぎるスケールは時間を食うだけで測定値を変えない」に当たる。

## 3. 親の新しい暫定裁定 (P1') — これを攻撃せよ

**要求枠 7200 秒・各 timeout・標本数をすべて据え置く。式の項を script の実体から導いた
正しいものへ入れ替え、凍結式の逐語に「何を保証し、何を保証しないか」を書く。**

- `frozen_required_s` は受理判定が要求する「要求枠に収まらねばならない配分」とする。
  = `cli_budget(4990) + finalize_reserve(600) = 5590`。
- 凍結式の文字列は、配分 5590 と**計測前の逐次 timeout cap 和 3250 を別項として両方**載せ、
  `3250 + 5590 = 8840 > 7200` であること、したがって
  **最大経路の完遂は保証しないこと**、最大経路に当たった attempt は計測窓が
  `timeout --signal=TERM` で打ち切られ rc≠0 で fail-closed に失敗し
  **誤った認定は生じない**ことを明記する。
- 冒頭 comment・`walltime_formula`・`orchestrator/tests/test_pegasus_tools.py` の逐語 pin を
  同じ 1 つの定義へ揃える。旧 `build_cap(CCBench=900+gflags=60+glog=120)(1080)` は
  script に実在しない項なので消す。
- policy の `certify_walltime` / `certify_walltime_s`、PBS directive は 1 bit も変えない。

### P1' へ向ける攻撃 (必ず全部やれ)

a. **これは D1936 項38 が名指した欠陥を閉じているか。** 項38 は
   「6910/6610/7870 秒と copy 上限 480 秒の食い違いを、既存逐次処理の上限を使う
   同じ式へ揃える」と言う。P1' は copy 360 + pristine 検証 120 を式へ入れ、
   3 つの記述を 1 つの定義へ揃える。しかし「必要分だけ要求時間を増やす」は履行しない。
   **これを「再凍結完了」と呼べるか。** 呼べないなら、何をもって完了とすべきか書け。
   完了と呼べないという結論でもよい — その場合、本 wave の成果物を何と名乗るべきかを書け。

b. **`required_s` を 6610 → 5590 へ下げることは受理集合の拡大か。**
   `orchestrator/calibrator/cli.py` の `reservation-qsub-mismatch` は
   `walltime.required_s > qsub.elapstim_req_s` で拒否する。required_s を下げると、
   以前なら拒否された小さい要求枠が通るようになる。この経路が**実際に到達可能か**を
   実装で確かめよ (PBS directive と policy が `test_pegasus_tools.py` の B4/B5 で
   束縛されているなら到達しないかもしれない。束縛の強さを実測せよ)。
   到達可能なら、下げない別の積み方があるか示せ。

c. **「保証の限界を文面へ出す」が言い訳になっていないか。** 文面に限界を書くだけで、
   実際には最大経路で計測が打ち切られる job が出る。plan は
   「実測 186 秒や outer timeout で最大経路の包含を証明したとは扱わない」(D1971) を
   引いている。P1' の文面が、この禁止に触れずに限界を述べられるか検査せよ。
   **親が上に書いた「計測前の実所要 35〜39 秒」という実測を、
   「だから 7200 で足りる」という保証の主張に流用していないかを特に疑え。**
   親の意図は「だから枠を増やす必要はない」であって「だから最大経路も収まる」ではないが、
   文面がそう読めてしまうなら指摘せよ。

d. **規律 2 が 1 mm も緩まないこと**を確かめよ。窓不足で打ち切られた attempt が
   `accepted` な成果物を 1 つも残さないことを、`certify_calibration.sh` と
   `orchestrator/calibrator/cli.py` の実際の制御フローで確かめよ。
   部分的に書かれた成果物が後段で拾われる経路も見よ。
