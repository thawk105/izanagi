# 研究開発で毎回踏むコストの棚卸し (2026-09-15 実測、本 wave の scope 外分を含む)

ユーザー依頼「リポジトリの成長で比例して大きくなる受入全走等の研究開発で必ず踏むコストを解決して
ほしい。たとえば全史検査。1 万コミット近くあって何かするたびに 1 万コミット検査するのは愚か」に対し、
**何がどれだけ掛かっているか**を親が実測して並べた表。本 wave で解くのは 1 行目だけであり、
残りは段 7 で裁定パッケージ / 次の一手へ送る。

## 本 wave が解くもの (#1)

per-commit の `git show` 2 本 (費目の 84.7 %) を `git log` 1 回へ。**検査範囲は 1 件も減らさない。**
親の実測では全史一括取得 7.73 秒 対 per-commit 507.83 秒 (16 並列)、全史 10443 件で出力 mismatch 0。

**注意 (段 3 L-4 の指摘を採用)**: これは **O(履歴) を消すのではなく定数を下げる**。一括化後も
`_ai_agent_values` の per-commit subprocess、隔離 parse の tempdir、実装 path 取得、祖先索引が残り、
残存費目のうち `_ai_agent_values` が約 71.6 %、隔離 parse が約 28.4 % を占める見込み。
**「成長比例問題を解消した」とは書かない。**

## 本 wave で解かないもの (段 7 で裁定パッケージ / 次の一手へ)

- **#3 が最大の未解決。** shard あたり約 55 秒で、技術的障壁 (`ModuleNotFoundError`) は archive 1306 が
  原因特定済み (2 つの test file が `sys.path` 上の `orchestrator/` へ暗黙依存)。**残る論点は
  「gate 2 (全 shard の universe 一致) を弱めてよいか」の一点**で、これはユーザー裁定待ちである。
  本 wave では触れない。
- **#4 は未着手**だが O(docs 量) であり O(履歴) ではない。commit ごとに 27.6 秒を払う。
- **#5 は worktree 数に比例**する。現在 69 本。撤去が滞ると伸び、30 秒 timeout を越えて非帰属赤を生む
  (直近 [T-2470] が 4 走を失った)。**コストの源が「掃除が滞っていること」なので、検査側でなく
  worktree 側の問題**である可能性が高い。
- **#2 は D1706 で分解が closed** しており、単独の短縮余地は #3 に集約されている。

## 方法論として言えること

- #1 と #6 は**同じ形**の問題で、D274 は「範囲を窓へ限定する」で解いた。本 wave は「範囲を変えず
  定数を下げる」で解く。**後者が可能なら常に先に試すべき**である。範囲限定は受領証・地平宣言という
  新しい攻撃面を作り、被覆等価の論証を要求する (D908) のに対し、定数削減は論証が軽い。
- 「遅い検査をオフにする」は既に却下例がある (`check_acceptance_reds.py`、D440)。
  **消すべきは検査でなく検査に引っかかっている入力**という順序が既定である。
