## §1 変異登録の訂正 (R-1)

裁定 §4 の **I-4 を群 I から外す**。理由は `DW-M03` / `DW-M08`。

- I-4 (「一括結果の OID 列で監査対象を上書き」) が現 fixture で赤くするのは、重複した `outside` の
  finding が消えることによる **findings 集合の差**である。残る 2 件も違反なので**拒否は維持**され、
  受理集合は動かない。これを「受理集合差による KILLED」と報告すると変異レポートが検証範囲を過大表示する。
- **措置**: I-4 を **群 II (diagnostic sensitivity pin)** へ移す。群 I は I-1 / I-2 / I-3 / I-5 の 4 件。
- R-1 が示した「同一 correction OID を二重に含む監査列を重複排除すると `candidate_count` が 2 → 1 に
  なり拒否から前方訂正による受理へ動きうる」という経路は、**本 wave では fixture を足さない**
  (`DW-G05`: 現実装の成果物影響が未検出であり、scope を広げる根拠がない)。段 7 の次の一手へ送る。

## §2 報告してよいこと / いけないこと (Q-1)

- **書いてよい**: 一括取得の失敗・framing 不成立・decode 失敗で全件が旧経路へ戻ること
  (注入 fixture 9 ケースで検査済み)。
- **書いてはいけない**: 「実 object 欠落や pack 破損からの復帰を実走で確認した」。現 fixture の
  `missing` は**出力 record の欠落**、`log-error` は**注入例外**であって実 object 欠落ではない。
  loose / packed 両形態は未検査である。段 7 の worklog へ**限界として明記**する。

## §3 親が段 6 で実測する項目 (Q-2 / Q-3)

1. **旧新の全史比較** (実行中): 同一 HEAD・同一設定で交互に 2 ラウンド。公開出力 (stdout / stderr
   bytes・rc) の exact 一致と wall。投入時 load を併記する。
2. **peak メモリ**: checker を実行する **Python process の VmHWM** を旧新で測る。
   「10.7 MB × 48 = 513.6 MB」は stdout 量の条件付き算術であって peak RSS ではないので、
   その形では書かない。32 worker はスレッドで辞書を共有する。
3. **件数別の損益分岐**: 全史に加えて小範囲 (数十件) でも旧新を測り、一括取得の直列固定費が
   利得を上回る境界があるかを見る。`--message-file` は別経路なので固定費が増えない点を確認する。
4. **成果の書き方**: 確定として書けるのは「正常経路の message 取得 subprocess を 2N 本から 1 本へ
   削減した」ことと、実測した wall の比だけ。**「成長比例問題を解消した」とは書かない** (L-4)。
