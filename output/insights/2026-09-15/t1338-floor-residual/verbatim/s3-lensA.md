## 既裁定の読み違い

### A1 — real：D811 の却下を R1〜R3 全体へ拡張している

D811 決定本文は次です（`docs/decisions.md:30934`）。

> pilot が出した値 […] を freeze へ発効させない。  
> official 経路を開き、official 走行で床値を採る。`eligible_for_refreeze` は緩めない。

却下選択肢は次に限定されます（同:30961）。

> 床値を空のまま `floor-null` の拒否だけを個別に解く

却下欄も判断根拠であり無視できません。ただし、**決定本文と同じ強さの一般的禁止へ拡張する規定は、確認資料にはありません**。この逐語が拒むのは「床値を空に保ったまま floor-null だけ解除する案」。budget-null、loader、report 経路、契約を保つ同値変更まで名指していません。

一方、D1985:59975–59978 は、

> 残すものを同時に確定する。  
> floor/budget の null 拒否と外形・budget 値・共有性の検査。

と決めています。**R1 全体の残置根拠には D1985 を使うべきです。**

- **逐語より強い親断定：** P1-a「R1 は既裁定が明示的に却下」、P1-d「R1〜R3 […] 既裁定（D811） […] に反する」。
- **成果物影響：** 放置すると裁定記録が、限定された却下を R2・R3 の撤去禁止の根拠として誤参照します。

### A3 — real：床値系列の存続は撤去要求全体の失効を証明しない

## 逆向きの見落とし

### A4 — refuted：R1〜R3 を残すだけで D496 決定 1 に違反する

D496 決定 1 の禁止は、

> 過去に凍結した床値表を比較の基礎にしない。

です。今回確認した残件は以下でした。

| 残件 | 現行の用途 |
|---|---|
| R1 | floor/budget の存在条件 |
| R2 | freeze の budget を今回の資源上限へ射影 |
| R3 | 批准床値の選択規則・公開証拠の再検証・manifest 束縛 |

R2 の `load_oracle_limits` は budget だけを読み（`s8b_budget.py:96`）、driver:1586 の台帳へ渡します。過去 throughput との比較ではありません。R3 も選択結果の性能値比較ではありません。

**D496／D501 が要求した最終判定層の撤去が R1〜R3 に化けて未実装、という経路は確認できません。** D510 と現行 verdict が反証します。

- **成果物影響：** 現状維持によって凍結床値が選択条件の数値比較へ再導入されることは、確認した経路にはありません。

## 正しさ境界と恒真性

### A5 — real：「撤去はいずれも受理集合を広げる」は成立範囲を混同している

| 対象 | 静的に言える撤去効果 |
|---|---|
| R1 の driver 2 条件だけ | null の診断が消える。ただし manifest:603–606 に独立した null 拒否が残るため、正常な実行経路全体の受理拡大は導けない。 |
| R2 の loader | 呼出しだけ消せば limits 供給が壊れる。予算制約まで外す案なら、予約上限超過を許し、台帳の計上可能量が変わる。変更案を定義せず「受理拡大」とは言えない。 |
| R3 の assertion だけ | g1 の選択規則検査を失う。後続 reverify は `ReverifiedFreeze` を指定し、選択検査の `LaunchValidatedFreeze` 分岐に入らない（ratified_freeze:3332、:3693）。 |
| R3 の解決経路全体 | freeze/manifest の束縛と store 再検証への供給にも及ぶ。report:2494–2518 では供給の有無が `store_reverification` 出力の有無を変える。 |

さらに `s8b_oracle_spec.py:23` は `APPROVED_SPEC_SHA256 = None`。:185–186 で拒否するので、**現在の official 実行・公開経路の受理集合と、承認条件を満たした場合の個別検査の受理集合は区別が必要**です。

- **逐語より強い親断定：** P1-d「R1〜R3 の撤去はいずれも受理集合を広げる」。
- **成果物影響：** 放置すると、診断変更・実行破壊・証拠欄欠落・受理拡大を同じ変更効果として記録します。

### A6 — real：null 拒否が保証するのは床値の正当性ではない

driver:524 の条件は `freeze.get("floor") is None` です。床値の存在は検査しますが、official 由来・正値・pair 内部整合・性能差が床値を超えることは検査しません。

manifest:600–628 も外形と holdout 集合までで、pair 内部を読まなくなっています。これは D1985 が明示承認した受理拡大です。

したがって D811 の「門が守っていた性質」を、

- **null を拒む性質**と読むなら実装に存在する。
- **正しい official 床値を保証する性質**と読むなら、その 1 条件だけでは証明できない。

null 条件自体は恒真ではありません。ただし実行経路では他の拒否と重複し、現在の official 成功は別の approval gate にも遮られます。

R3 も非 g1 では無条件 return（ratified_freeze:3601）。**全世代の選択規則を守る検査ではありません。** g1 の不一致拒否を扱う既存テストは確認しましたが、実走していません。

- **成果物影響：** 放置すると、検査済みでない床値の性質や世代までレポートの保証範囲として誤記できます。

### A7 — refuted：実装なしで返すこと自体が絶対規律 2 違反になる

今回、新たな anomaly 受理や verifier の迂回は立証されていません。既に消えた床値超・scale 等の保証は D510、pair 内部検査等は D1985 による変更です。

**受理集合の拡大一般と、anomaly を見逃す正しさ検証の弱体化は同義ではありません。** 規律 2 を理由に旧保証の再導入を要求するのも、後続裁定を無視します。

- **成果物影響：** 実装なしなら今回による選択値・受理集合・proof 参照の変更はありません。既存の保証上限は残ります。
