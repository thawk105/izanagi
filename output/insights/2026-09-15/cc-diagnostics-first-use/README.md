# `docs/cc-diagnostics.md` の初回利用 — 抽出元と違う protocol へ事前選別を当てる

- 実施: 2026-09-15、dev-wave `cc-diagnostic-skill`
- 手順: `docs/cc-diagnostics.md`「非完走を持続閉路で機構へ帰属する」の**事前選別**
- 対象: CCBench 現行 pin `511c9538e4e8efa54b45cda62e72389ed3b706ec` の 10 protocol
  (抽出元は ss2pl。本記録の対象はそれ以外)
- 実行環境: login node。**計算ノード走行・ビルド・性能測定は一切行っていない。**
- authority: none / default_effect: no-state-change

## 1. 何を確かめたかったか

抽出元の SS2PL ロック規律スタディは ss2pl だけを扱った。`docs/ccbench-anatomy.md` の protocol 表には
「待つか」「解決機構があるか」という列が無く、同表は古い pin (`33d74a3`) の調査である。
**ss2pl 以外のどの protocol で待ちに起因する非完走が起こりうるかは、少なくとも同表からは読めない**
(repo 全域に判定が無いことを確かめたわけではない)。ここへ事前選別を当てた。

## 2. 事前選別の結果

述語は手順書のとおり B (待ち経路) / H (同時保持) / O (取得順序の全順序化) / R (解決機構) /
G (計器配線)。判定は現行 pin の実装を読んだ結果で、grep の無一致だけを根拠にした項目は無い。

対象は 10 protocol。抽出元の ss2pl を除くと **9 protocol**。ss2pl は 2 構成に分けたので表は 11 行。

**この表は 1 回書き直している。** 初版は O (取得順序) を「ソートしている箇所がある」という事実から
「あり」と確定し、silo の H を「なし」と誤り、その結果 9 件すべてを高価な段から除外していた。
段 6 の敵対レビューが両方を反例つきで否定し、親が現物で裏取りして誤りを確認した。下表は訂正版である。

| protocol | B | H | O | R | G | 調査価値 | 実行準備 |
|---|---|---|---|---|---|---|---|
| ss2pl (DLR0) | あり | あり (commit まで保持) | なし | **なし** | あり (patch 適用時のみ) | 抽出元。実施済み | patch 必須 |
| ss2pl (DLR1、現行 pin の既定) | 対象 lock は try 形 | 未評価 | 未評価 | あり (no-wait) | あり (同上) | 低 | — |
| d2pl | あり | あり (宣言分をまとめて保持) | 宣言 lock 集合を取得前に sort する。**全待ち経路の被覆は未確認** | 事前順序化のみ | なし | **未確認** | YCSB target 無し |
| mocc | あり | あり (現在 lock 列に複数保持) | canonical mode で sort し違反分を解放して再取得する。**全経路の被覆は未確認** | try 形と abort はあるが、ブロッキング経路全体を覆う保証は未確認 | なし | **未確認** | — |
| silo | あり (読み取り経路の lock bit spin) | **あり (INSERT 経路)** | 検証段は write set を sort する。**読み取り段の spin は覆わない** | 検証段は no-wait。読み取り段は覆わない | なし | **あり (静的な反例を構成できる)** | — |
| tictoc | あり | 未確認 | write set を sort する。**全経路の被覆は未確認** | 既定の検証段は no-wait | なし | **未確認** | — |
| oze | あり | あり (write set を一括取得する経路) | 検証段で sort する。**全モードの順序保証は未確認** | 未確認 | なし | **未確認** | — |
| cicada | あり (WAL バッファ lock と版の確定待ち) | 未確認 (**資源待ちと版待ちを分けて評価していない**) | 未評価 | 未評価 | なし | **未確認** | — |
| ermia | あり (commit stamp / status 待ち + 索引 node lock) | 未確認 | 未確認 | timestamp 条件つき abort は実在。全待ちの解決保証ではない | なし | **未確認** | — |
| si | あり (inflight writer 待ち + 索引 node lock) | 未確認 | 未確認 | timestamp 条件つき abort | なし | **未確認** | — |
| mvto | あり (版の確定待ち + 索引 node lock) | 未確認 | 未確認 | 未評価 | なし | **未確認** | YCSB target 無し |

**G (計器配線) は抽出元を除く 9 件すべて「なし」だが、G を理由に除外した protocol は 1 つも無い。**
これは手順書が要求する「調査価値と実行準備を分ける」に従った結果である。

**全 protocol が共通の索引実装を通る。** その挿入経路は索引 node のロックビットが空くまで
無条件に再試行する (`while(1)` の spin)。これは**資源の holder を待つ経路**であり、版や commit の
確定待ちとは別である。表の「B: あり」にはこの経路も含む。

### 結論 (2 度目の訂正版)

- **確定的に除外できた protocol は 1 つも無い。** 2 度目の訂正前は ermia / si / mvto を
  「版・commit の確定待ちしか持たない」として確定除外していたが、3 つとも挿入経路で索引 node の
  ロックを待つ。**除外できるのは「版・commit の確定待ち」という経路であって、protocol 全体ではない。**
- **silo は調査価値が立つ。** 挿入したタプルは `lock=true` のまま索引へ公開され、読み取りは
  `absent` を判定する**前に**そのロックビットの解放を待つ。互いに挿入してから互いを読む 2 者は
  保持したまま待ち合う。**これは静的に構成した反例であり、実走の主張ではない。**
  読み取り・更新だけの workload に限るなら、その条件を表へ固定する必要がある。
- **残り 8 件は protocol 全体として未確定。** ソートや競合処理の呼び出しは見つかったが、それが
  **全待ち経路を覆う**ことは確かめていない。

**これは事前選別を終えた結果ではなく、部分的な静的利用である。** 見た経路は
`transaction.cc` の lock 取得と解放、共有 rwlock、`CMakeLists.txt` の構成、共有索引の挿入経路。
見ていない経路は各 protocol の scan・delete・abort 経路、MQLOCK 構成、索引の split / 再均衡経路。
**「他 protocol が正常終了する」「デッドロックが存在しない」という報告ではない。**

## 3. 手順のどこが役に立ったか

訂正後に残る効用だけを書く。初版が主張した「対照設計を省けた」は、誤った除外に依存していたので
撤回する。

- **どの実装事実を見れば足りるかが決まっていた。** B / H / O / R / G という 5 つの問いが与えられて
  いたので、10 protocol ぶんの読解対象が「待ちの呼び出し」「取得と解放の区間」「順序付け」
  「競合処理」「計器」に限定された。これが無ければ protocol ごとに何を読むかから決めることになる。
- **適用条件が「経路の除外」という粒度を与えた。** 「待ち手 → その資源の実 holder」という辺に
  落ちるかという受理条件があったので、版・commit の確定待ちを対象外の経路として切り出せた。
  **ただしそれを protocol 全体の除外へ広げたのは誤りで、2 度目の訂正で撤回した。**
- **計測を 1 回も走らせずに済んだ。** 見た範囲の判定はすべて実装読解で閉じ、計算ノードへの投入は
  ゼロだった。**未確認のまま残った項目があるので、対象全体の判定が閉じたわけではない。**
- **名前でなく使用箇所で判定する規則が実際に発火した。** mocc の `LOCK_TIMEOUT_US` は
  `external/ccbench/cc/mocc/include/lock.hh` に定義があるだけで、CCBench 全体で使用箇所が無い。
  名前を根拠にしていたら「mocc には timeout がある」と誤って書いていた。
- **「機構の存在と全経路の被覆は別」という注意が、誤りを見つける側の足場になった。** 初版はこの
  注意を持ちながら破っていたが、レビューはこの一文を根拠に初版の判定を倒せた。手順書に書いて
  あったことが、手順書を使った結果を検査する基準として働いた。

## 4. 手順に足りなかったもの — どの段階で誰が見つけたか

**出所を混ぜない。** 手順書の改訂点のうち、利用そのものが暴いたのは一部である。

### 4.1 利用より前に、敵対相談・起草が指摘したもの

| 足したもの | 出所 |
|---|---|
| 版の確定待ち・commit 状態待ちを「適用できない条件」へ明記。待つ相手が資源の holder でないので D791 の辺に落ちない | 段 2 起草。親の初版は「待つか」だけを見ており ermia / si / mvto を誤って対象に数えていた |
| 判定値に「未確認」を置き、grep 無一致だけで不在を主張しない | 段 2 起草 |
| 「調査価値」と「実行準備」を分ける | 段 3 (実効性レンズ)。初版は「G なし → 保留」で終わっており、全件保留でも手順が成功したことにできた |
| 発火する症状に「原因が未確定でも引いてよい」を明記 | 段 3 (実効性レンズ)。初版の索引は原因判明を前提にしていた |
| 「必要な入力」に、受理を後から再検査できる形の成果物 | 段 3 (実効性レンズ) が保存成果物の欠落を指摘し、親が現物で裏取りした |
| 未信頼入力の扱いを 1 節追加 | 段 3 (正しさ防壁レンズ) |
| 不在検査は何で効いているかを読む、という注意 | 段 3 (正しさ防壁レンズ) が witness の未接続を指摘し、親が現物で裏取りした |
| 計器と検証器の不接続を「既知の不足」として明記 | 段 3 (正しさ防壁レンズ) が指摘し、親が field 名・伝達・flag を現物で確定した |

述語 H (同時保持) と O (取得順序) は親の初版から入っていた。利用で足したものではない。

### 4.2 利用そのものが暴いたもの

1. **G (計器配線) が、抽出元を除く 9 protocol すべてで「なし」だった。** 段 3 は「G だけで走行判断が
   決まると危険」と予測した。利用はその危険が**全件で現実になる**ことを実測した。つまり
   「調査価値と実行準備を分ける」は予防的な整理ではなく、分けなければこの手順が
   1 件も結論を出せないという必須条件である。
2. **述語の評価順序が結果を決める。** 実行準備 (G) を先に見ると全件が同じ結論になる。
   除外理由 (H・O・適用条件) は調査価値を独立に評価したときにだけ現れる。
   手順書に**調査価値を先に評価する**ことを書いた。
3. **「未確認」のまま残る欄が実際に出る。** tictoc の H、oze の R は今回の読解では確定できなかった。
   あり / なし の二値を強制する手順だったら、ここで誤った確信を書いていた。
4. **述語の値に、それを支える証拠の範囲を併記しないと、初回の利用者が自分で破る。**
   手順書は「機構の存在と全経路の被覆は別である」と書いていた。にもかかわらず初版の判定は
   「ソートしている箇所がある」から O = あり を確定し、9 件すべてを除外した。
   段 6 の敵対レビューが反例を構成して倒した。**書いてあるだけでは守られない。**
   → 手順書の O・R に「未確認が既定」「覆いを確かめていない O・R では除外しない」を足した。
5. **除外の必要条件を誤って狭く書いていた。** 初版は「閉路には相異なる 2 つ以上の資源が要る」と
   書き、資源 1 個の機構を除外の根拠にした。共有 RW ロックでは、2 者が読み取り保持のまま昇格を
   待つと**同じ資源 1 個の上で**待ち合う。→ 述語 H の定義を「保持したまま、他者が保持するものの
   解放を待つ経路があるか」に直し、資源の個数を除外理由にしないと明記した。
6. **「経路の除外」を「対象の除外」へ広げる誤りを、訂正の 1 回目でも繰り返した。** 1 度目の訂正は
   ermia / si / mvto を「版・commit の確定待ちしか持たない」として確定除外へ格上げした。
   2 度目の敵対レビューが、3 つとも挿入経路で共有索引の node ロックを待つことを示して倒した。
   **適用条件は経路に効くのであって、対象全体には効かない。** 同じ誤りを 2 回踏んだので、
   手順書の「適用できない条件」に「これは経路の除外であって対象全体の除外ではない」を明記し、
   共有索引の側を見ることを求める一文を足した。
7. **「恒真でない」の実証にはならなかった。** 初版は「除外理由が分かれたから手順は恒真でない」と
   書いたが、最終判断が全件「進まない」なら、理由の違いだけでは反証にならない。この主張は撤回した。
   最終の結果 (確定除外 0 / 調査価値あり 1 / 残り 8 は未確定) は判断が分かれたが、それは
   **訂正を経た後の結果**であって、初版が示したものではない。

## 5. 敵対相談と利用の過程で確認した、izanagi 側の不足 (本 wave では直さない)

段 3 の敵対相談が指摘し、親が現物で裏取りして確定したものである。利用そのものの発見ではない。

いずれも 2026-09-15 に現物で確認した。**過去の観測報告を否定するものではない。**

### 5.1 計器と検証器が接続していない

`patches/ss2pl-lock-protocol-study.patch` の C++ 計器と、`tools/pegasus/run_ss2pl_lock_study.py` の
デッドロック証拠検証は、そのままでは繋がらない。

| 面 | 計器 (patch) | 検証器 (runner) |
|---|---|---|
| 伝達 | 指定 file へ最終的な閉路 JSON を 1 枚書く | 標準出力の `wfg_snapshot` event を読む |
| node の field | `waiting_lock_id`、`requested_mode` | `wait_lock_id`、`request_mode` |
| 辺の field | `waiter`、`holder` | `waiter_thread_id`、`holder_thread_id` |
| 持続性の判定 | 計器内部で連続 3 回一致を数え、一致後の 1 枚だけを残す | 受け取った snapshot 列から自分で連続 3 枚を検査する |

さらに patch 内に `wfg_snapshot` の出力は 1 件も無く、runner は計器の出力先 flag を一度も渡さない
(どちらも出現数 0)。**この 2 つをそのまま繋いでも D791 の証拠は採れない。**

### 5.2 保存された成果物から D791 の受理を再検査できない

`output/insights/2026-08-25_ss2pl-lock-protocol-study/raw/` の 3 件を開いた結果、
いずれも phase の走行記録が空で、`cycle` の語を 1 件も含まない。
`controls.json` は `process timeout contract mismatch: expected_timeout=True, observed=False` で
失敗している — **hard timeout を期待した走行が自力で終わっている。**

過去の観測は同 study の `report.md` と findings に記述として残っているが、
**保存された成果物からの独立な再検査はできない。**

### 5.3 不在検査の識別子列挙は飾りで、実際は総当たりの語検査が効いている

runner の計器不在検査が列挙する 8 個の識別子は、計器 patch にいずれも実在しない (出現数 0)。
**検査は空振りしていない。** 実際に受理を制約しているのは、同じ関数内で `wfg` を総当たりする
正規表現、構成表示用の文字列 1 行だけを許す規則、そして翻訳単位の集合・前処理 receipt・
symbol と strings の digest の対応検査である。**列挙された識別子だけを見て効力を判断できない**
というのが所見であって、検査全体が語検査だけだという主張ではない。
手順書の「比較対象・計測方法」に、不在検査は何で効いているかを読むこと、という注意として反映した。

## 6. 観測事実と、まだ検証していない機序仮説

| 主張 | 区分 |
|---|---|
| 共有 rwlock の `r_lock` / `w_lock` / `upgrade` は期限も abort 判定も持たず、条件成立まで再試行する | 観測事実 (現行 pin の header を読んだ) |
| `*_trylock` / `tryupgrade` は**非両立を観測したときに限り**諦める。比較交換に失敗しただけなら再試行する。「即座に諦める」は限定不足だった | 観測事実 (同上。段 6 レビューの指摘で訂正) |
| 同 rwlock は資源 1 個でも待ち合いが成立する。2 者が読み取り保持のまま `upgrade` を呼ぶと、双方が計数 1 を待ち続ける | 観測事実 (同上。段 6 レビューの指摘で訂正) |
| silo の `insert` は `lock=true` のタプルを索引へ公開し、読み取りは `absent` を判定する前にそのロックビットの解放を待つ | 観測事実 (`Tuple::init` と読み取り経路を読んだ) |
| 上の 2 者が互いに挿入してから互いを読むと保持したまま待ち合う | **静的に構成した反例。実走していない** |
| d2pl は取得前に lock 集合を sort する / mocc は canonical mode でブロッキング取得する / silo・oze・tictoc は write set を sort する | 観測事実 (各 `transaction.cc` の該当呼び出し) |
| mocc の lock timeout 定数は定義 1 箇所のみで使用が無い | 観測事実 (CCBench 全体で出現 1) |
| 計器と検証器の field 名・伝達・flag が食い違う | 観測事実 (両現物を読んだ) |
| **sort があるから当該 protocol で閉路が立たない** | **未検証の機序仮説。** sort は取得順序の全順序化を意図した設計だが、全経路が実際にその順序を守ることは確かめていない。mocc の canonical mode 復元のように、順序を崩して取り直す経路がある |
| 5.1 の不接続が 5.2 の証拠欠落の原因である | **未検証の機序仮説。** 整合はするが、別経路で採った証拠を保存しなかっただけの可能性を排除していない |

## 7. 主張しないこと

- 他 protocol が正常終了すること、デッドロックが存在しないこと。
- 本手順が節約した計算資源の量。抽出元 study の消費 (約 5.2 node 時間) には build・過剰な同一性
  gate・解析不具合が混在しており、本手順で防げる量は測っていない。
- 計器が現在ビルドできること・発火すること。`git apply --check` が通ることの確認までである。
- 版の確定待ちを持つ protocol が安全であること。**本手順の対象外というだけ**である。
