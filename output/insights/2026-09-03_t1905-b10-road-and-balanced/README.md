## 3. 「検査のピークメモリは取れない」は間違いだった。ただし読み方に罠がある

親は当初「どの成果物にも残らないので取れない」と書いた。
**走行中の job については `qstat` で観測できる。** 84 sample (15 秒間隔) を取った。

| 統計 | 値 |
|---|---:|
| 最小 | 3.36G |
| 中央 | 9.18G |
| 最大 | **115.29G** |
| 30G 超 | 11 件 (13.1%) |

ユーザ利用上限 115GiB のすぐ下である。短縮 `qstat` と `qstat -f` は同じ値を返すので
読み違いではない。**しかしこれは物理メモリではない。**

各スパイクと直前直後の sample の比:

| spike | 隣接値 | 比 |
|---:|---|---:|
| 55.98G | 3.57 / 4.12 | 13.6x |
| 114.76G | 6.67 / 8.05 | 14.3x |
| 54.14G | 3.90 / 4.75 | 11.4x |
| 114.88G | 6.73 / 8.60 | 13.4x |
| 115.29G | 6.71 / 8.10 | 14.2x |
| 115.05G | 6.72 / 8.70 | 13.2x |
| 113.98G | 6.66 / 8.43 | 13.5x |

**比は 11.4-17.1 倍で中心は 13-14 倍。並列度 16 とよく一致する。**
完全に 16 倍にならないのは、子の起動と終了がずれること、親自身の分が 1 回しか数えられないことによる。
**スパイクは約 60 秒周期で 2 段 (54-59G と 112-115G) に分かれ**、1 反復の中に fork する段が
2 つある (ファイル単位の構文解析と、依存グラフの辺候補の計算) ことと整合する。

検査器は `fork` で 16 子を作る。Linux の RSS は共有 copy-on-write ページを
**触った全プロセスへ重複計上する**。
**T-2191 はこの誤りを名指しで警告し、cgroup の `memory.current` で測り直している。**

物理メモリなら 13% の時間で上限に張り付いていることになる。それでいて反復所要は
163-173 秒のまま乱れず、swap の兆候が無い。両立しない。
queue も job も `Memory Size = Max: UNLIMITED` で、scheduler 側の上限は無い。

**それでも記憶量の risk は refuted ではなく reduced である。**
並列 16 の cgroup 峰値を read-heavy の実規模で測ってはいない。
T-2191 の 2.93KB/commit は 68 万 txn 1 点からの線形換算であり、
1 commit あたりの費用は規模とともに単調に増える。上振れの向きは残る。

## 6. 壁時計を変えても campaign 同一性は動かない — 3 者が独立に確認した

記録が比較する束縛 `PreregistrationBinding.as_dict()` は `core()` + `binding_sha256` であり、
**`analysis_commit` を含まない。** 入るのは driver 自身の bytes (`analysis_code_sha256`) だけである。
walltime は `search_config` にも enforcement source closure の 24 path にも入らない。
block record の `job_script_sha256` は 64 桁形式だけを検査し、現行 script SHA とは比較しない。

**したがって 12 時間枠の balanced と 24 時間枠の read-heavy は、同じ束縛のまま最終集約できる。**
投入順序を変える必要は無い。

**代わりに動かしてはいけないのは driver の bytes である。**
現在値は `f6246360c784813a581d7e104f116c07838106022fb9245f5de50b338e9ea0ec`。
1 byte でも変えると走行中 balanced の 45 セルが最終レポートから外れる。
本 wave の実装はこの file に触れていない。

集約レポートの上部に載る analysis commit は report を生成した側の HEAD になるので、
balanced record の `source_commit` と混在する。**値と受理集合は同じで、参照だけが混ざる。**
