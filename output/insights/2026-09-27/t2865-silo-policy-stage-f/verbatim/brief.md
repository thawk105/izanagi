# 段 1 brief — [T-2865] 段階 F (silo-function-policy の実 LLM 1 iteration E2E)

- 研究前進: 論文の中心主張「LLM が関数単位の CC 方策コードを合成し、正しさゲート (毎候補 legacy + 性能構成 verify、anomaly 即 reject) を通して stock と比べる」の最初の実 LLM データ点。完了判定 = 実 LLM coder の 1 候補が preview → auditor → 計算ノードの build・legacy verify・性能構成 verify・bench を通る (または構造化理由で reject され履歴に載る) こと、同じ job の stock との比が出ること、trace が保全口に残ること。
- 起点: local main `ad114fba0`、開始 gate rc=0。正本 D2214・D2240・D2250・D2256・D2261 項 3、runbook `docs/phase3-silo-policy-runbook.md`、段階 E 記録 §6。
- 確定済みユーザー裁定: D2212 項 4 (検査込み 2 node 時間以上は投入前確認)、coder role 2 本・auditor 改訂は承認済み (D2256 項 7)、firewall (coder 入力は projection.json の binary・scope と自系列だけ、D2243 項 1)、D2259 (「なぜ LLM か」はこの軸で取り直す、対照設計は並走 T-2867 の担当)。
- 実測事実 (親): (a) policy driver は env 契約を `linux-baremetal`・clocks 1800 固定で束縛し、site 解決・`pegasus` 契約・依存 prefix・masstree 事前 build 受領証・stock 対照を持たない (`p3_s4_loop_policy.py` の `default_cfg`・`run_one_iteration`・`main`)。(b) superproject gitlink = `6810666…` = `axis.PIN` (短縮 7 桁) = MOCC pin。既存 job body の silo 分岐は `p3_s4_loop.PIN` = `511c953…` を照合する。(c) 既存 job body の sha256 を pin する台帳・test は 0 件 (git grep)。(d) 保全口は env `IZANAGI_TRACE_ARCHIVE_ROOT` (絶対 path) だけで pipeline が発火 (`pipeline.py` `_run_one_repetition` の finally)、write-heavy 1 評価 約 0.75 GiB (見積り稿 §7)。(e) 関数単位の候補を受ける R2 (保存候補の LLM なし再評価) の入口は未実装 (見積り稿 §8.3)。(f) 単価: 直列の性能構成 verify 込み silo write-heavy 1 評価の固有費 217〜509 秒 (B-5 試走 §6.3)。pair job の実測は無い。
- (P1) 投入経路 = 既存 `tools/pegasus/p3_s4_loop_pegasus.sh` に方策 driver の mode を足す (B-5・T-2849 と同じ「mode 選択」の先例、gflags/glog/masstree 前処理と台帳登録を共用)。方策 mode は他 mode・K2・fixture・stock-control の env と排他、CCBench の照合 pin は `axis.PIN` を 40 桁に解決して使う。兄弟 body は前処理 600 行の複製になるので採らない。親の provisional 裁定・攻撃対象。
- (P2) stock baseline = 方策 driver に stock 評価を足す。stock = CCBench 原型 source (方策 patch の flag 0 相当、BACK_OFF=1 ほか BASE と同じ flag)、同じ性能動作点・同じ verify 構成・同じ campaign。job の形は「stock 単独」(初回の coder 入力用 baseline と経路の生死確認) と「候補 + stock の pair」(候補の後に同じ authorization session で stock) の 2 つ。stock 結果の JSON に throughput と abort 率 (percent) を出し、次の `--emit-coder-input` の scalar に使う。攻撃対象。
- (P3) 1 iteration の形 = C++ 形 (`--form cpp`)。IR 形は 16 点を偵察で全列挙済みで、LLM の寄与を測る E2E として弱い。攻撃対象。
- (P4) R2 の入口 = 方策 driver の保存 proposal file (coder + auditor、`--run-iteration` と同じ schema) を、loop の campaign とは別の campaign (search_config で目的を分ける) で LLM なしに評価する CLI と job mode。loop の iteration・履歴・予算を動かさない。stock pair 可。攻撃対象。
- (P5) 保全口 = 方策 mode (loop・stock・R2) では `IZANAGI_TRACE_ARCHIVE_ROOT` を必須にし (絶対 path・repo 外)、他 mode の挙動は変えない。保全先 `/work/1/SFC/tanab/izanagi-repro-archive/t2865-stage-f-20260927/`。
- 不変条件: 規律 1 (trace は compile 時除去、性能は trace-disabled build)・規律 2 (anomaly 即 reject、verify を緩めない)・firewall (偵察・小比較・再測の点 ID・因子・比・順位を coder 入力へ流さない)・既存 3 軸と既存 job body 各 mode の受理集合を変えない・`orchestrator/campaign/p3_s4_loop.py` を編集しない (flock は並走 T-2104、私的 helper の import は可)・hooks と権限を触るなら Codex author と `hooks/README.md` の契約。仮想リスク向けの gate・検査・台帳・一般化は足さない。
- 成果物: driver 差分 + job body の方策 mode + 契約 test + runbook 改訂 (§0.2・§1(f)・stock・R2・保全) + 1 iteration の実走記録 (insight) + spool fragment。
- 分割方針: 実装子 2 単位 (A: `p3_s4_loop_policy.py` と test、B: job body と job 契約 test)。runbook は親。全 9 段は回さず段 2・3 (2 レンズ) と段 6 レビュー 2 本を残す (設計択一が割れ、build admission (stock) に触れるため)。
