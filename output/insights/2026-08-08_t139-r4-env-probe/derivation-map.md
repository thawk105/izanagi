## 1. この写像が返すもの — 閾値の数値ではない

**`a03` の許容範囲 `[0, 1.0]` core-equivalents は、probe の観測とは独立に固定する。**
probe はこの数値を作らず、変更もしない。probe が返すのは次の 3 値のいずれか 1 つである。

| 終端 | 条件 | `a03` への効果 |
|---|---|---|
| `feasible` | 期待 13 窓がすべて存在し `valid` で、すべてが `48·busy ≤ total` を満たす。かつ 13 run・2 build・compiler witness がすべて成立 | `[0, 1.0]` のまま。**当該 attempt で違反を観測しなかった**という記述的結果が付く |
| `not_feasible` | 13 窓すべて `valid` だが、1 つ以上が `48·busy ≤ total` を満たさない | **数値を作らない。**観測値を添えて裁定 R4 (d) の材料としてユーザーへ返す |
| `incomplete` | 窓の malformed・欠落・重複、run 失敗、build witness 不成立、compiler witness 不成立のいずれか | 結論なし。理由を添えて返す。**`not_feasible` と混同しない** |

判定は有理数の整数演算で行い、浮動小数を使わない。
`cpu_busy_core_equivalents = 48 × busy / total ≤ 1.0` は、`total > 0` かつ `busy ≥ 0` のもとで
`48 × busy ≤ total` と厳密に同値である。

## 2. なぜ「観測から閾値を作る」設計を採らなかったか

段 1 の親案は `上限 = max(1.0, ceil_{0.1}(U) + 0.5)`、段 4 の親案は
事前凍結した梯子 `{1.0, 2.0}` からの選択だった。**どちらも敵対検証で倒れた。**

- 段 1 案: `U ≤ 3.5` の全域で `上限 ≥ U + 0.5` となり、**probe の全観測値が
  probe 自身の作った区間へ必ず入る。**「probe が閾値を支持した」は成立しない。
- 段 4 案 (梯子): 成功域 `U ≤ 2` で常に `T(U) ≥ U` となり、構造は同型だった。
  とくに `U = 1.01` は `[0, 1.0]` を**否定する**証拠であるにもかかわらず、
  その観測自身が `[0, 2.0]` への拡大を発火させ、直ちに受理される。
  「`2.0` = 他テナント 1 thread まで許容」という物理的説明も誤りだった —
  1 thread が 100% 使ったときの寄与は `1.0` であって `2.0` ではない。

いずれも凍結 core §14 が禁じる「実現値を必ず含む許容範囲」に、較正層でそのまま該当する。
**受理集合を観測に合わせて動かす操作を、粒度を粗くしても正当化できない。**

したがって本 probe は、閾値を**作る**のではなく、事前登録された閾値が
**当該環境で成立するかを決着させる**装置である。

## 3. 実測後に裁量が入らないことの担保

- 判定関数の入力は「窓の raw counter・期待 window ID 集合・run/build/compiler の成立可否」
  だけである。診断値 (`load1`、foreign process count、cgroup 値、hostname) は
  **引数に存在しない。**
- malformed 窓を黙って除外して valid 行だけで結論を出す経路は無い
  (1 件でも欠ければ `incomplete`)。
- **測定を開始した attempt は 1 回きりとし、再走を 0 回とする。**
  窓を 1 つでも観測した attempt が存在する状態で新しい attempt を起動することは、
  job body が namespace の既存 attempt を走査して拒否する。
  - **限界の明示**: これは scheduler 証拠つきの pre-submit ledger ではない。
    機械強制できるのは「同じ namespace に観測済み attempt が残っている限り起動しない」までである。
    namespace ごと捨てる経路は塞げない。この限界は受領証にも記録する。

## 4. 本 probe が主張しないこと

`feasible` が返っても、次のいずれも主張しない。

- 将来の割当てに対する分位点・上側許容限界・被覆率・偽拒否率・偽受理率
- 26 割当てに対する保証
- `[0, 1.0]` が待機の十分性検査として適切であること
- 観測された負荷の原因帰属 (自 run の残渣か、他テナントか、特定 thread か)

**割当て間 (cluster 間) 変動の観測は 0 点である。**13 窓は単一ノード・単一割当て・
単一時刻の相関した観測であり、独立標本でもなければ、本走の 3 arm・36 run の履歴の再現でもない。
`a12` が抱える「cluster 間変動が 1 点も無い」という欠陥を、本 probe は**改善しない**。
