## 総括

NO-GO です。計画どおり実装しても、認可されていない CMake 実体・CXX 版を使った床値 build が通ります。また検査が floor 専用なので、同じ contract を使う pipeline / loop / oracle / screening の認可境界にはなりません。

親 brief の実測に対する判定は次のとおりです。

| 主張 | 静的判定 |
|---|---|
| M-1 | pilot から再凍結へ至る production 経路は見つからない。core、CLI、result、ratified verifier の全てが閉じている。ただし「投入できない」は逐語には誤りで、qsub 自体は実行でき、計算ノード上で rc=2 になる。 |
| M-2 | confirmed。g1/g2 とも C/CXX の絶対 path を持つ。 |
| M-3 | 2 ノードの観測値としてのみ confirmed。`gen_S` 全体の均質性は証明されず、PBS 指定にも vnode/toolchain 制約がない。束縛対象の差は build 後に拒否、CXX 版・CMake path だけの差は通過する。 |
| M-4 | 「直接の frozen/source-role pin がない」は正しいが、「driver source の pin がない」は広すぎる。submit receipt の `source_commit` と imported-module byte 検査が driver と新 helper を間接的に束縛する。ReviewId / GeneratorId は driver pin ではない。 |
| M-5 | 現在の床値 artifact が存在しない点は confirmed。ただし、将来 artifact の proof field を省いてよい理由にはならない。 |
| M-6 | 全体主張は refuted。silo ladder に calibration/toolchain consumer がある。floor/build_v2 経路に存在しない、という狭い主張だけが正しい。 |

official unlock、`--mode` の環境変数上書き、別の production result producer は見つかりませんでした。計画のままなら既存 `contract_sha256`、`FROZEN_MANIFEST`、`floor_protocol.json`、selector seal は動きません。しかし所見 1 を閉じる新 authority は新たな事前登録対象となり得るため、pin 不変を前提に実装へ進めません。g2 calibration にも同じ既存 field はありますが、同じ欠落もあります。
