## このレンズの担当

**実装の正しさ境界と受理集合。**

必ず検討する攻撃面:

1. **過小拒否**: 実装を通り抜けて凍結できる CR/LF path 入力を構成できるか。
   非 str の外側 `path`、root 直下、深い入れ子、malformed shape、escaped 表現を試せ。
2. **過剰拒否**: 現在通っている入力で新たに落ちるものを構成できるか
   (path 以外の field の CR/LF、`path` を key に持つが値が非 str、VT / U+0085 / U+2028 / U+2029、
   文字どおりの backslash + r)。
3. **NUL の診断契約の破れ**: NUL 入り入力の理由語・pointer・優先順位が変わる系列。
   同一 node 併存、文書順で前が CR/LF・後ろが NUL、複数 NUL のいずれも追え。
4. **文書順 pointer**: canonical key 順と文書順が食い違う入力で、報告 pointer が
   文書順で最初のものになっているか。stack の pop 順を実際に追え。
5. **hash 不変**: 現行契約 hash `c4f3740202de302c…` と既発行 g1 の `protected_sha256` が不変か。
   canonical bytes と domain 定数に手が入っていないか。
6. **検査位置**: canonical 化の後に置かれているか。前に動くと何が変わるか。
7. **裁定との突き合わせ**: 段 4 裁定 B 節の F1〜F7 が実際に実装・固定されているか 1 件ずつ判定せよ。
   実装されていない項目は名指しで挙げよ。
8. **恒真テスト**: 期待値を production の派生関数から取っているテストは無いか
   (その関数を変異させると期待値も動き、比較が恒真になる)。exact hash literal が
   標準ライブラリからの独立計算になっているかを確かめよ。
