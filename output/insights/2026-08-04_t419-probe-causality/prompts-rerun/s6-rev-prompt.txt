## 最重要の攻撃点 — 「実機で決して満たせない条件」がまだ残っていないか

`execution_validity` を VALID にするために必要な条件を**全部列挙**し、それぞれについて
「Pegasus の計算ノード (48 core、非 root、NQSV batch、`/system.slice` 常駐あり) で
実際に満たせるか」を、**前回の生出力の実測値を根拠に**判定せよ。

- 前回 A0 では満たせたが A1〜A3 では満たせない条件はないか (child を起こす arm、
  busy loop を回す arm、48 CPU 全部に pin する arm で新たに発火する条件)。
- 前回は A0 で止まったため **A1 以降の validity 条件は一度も実機で試されていない**。
  そこに地雷がないかを重点的に見よ (pin 失敗、affinity 復元、child の tick 下限
  `busy >= 5 tick` / `sham <= 1 tick`、`INCONCLUSIVE 3/8` gate、cooldown、
  parser crosscheck、hash 再照合、900 秒 deadline、20 分 walltime)。
- **`busy >= 5 tick` と `sham <= 1 tick` は実機で成立するか。** 前回の実測 (arm 長、tick 単位、
  読み間隔 50ms、child の生存時間) から見積もって、成立しない恐れがあるなら具体的に述べよ。

## その他の攻撃点

- **修正が緩めになっていないか。** `incidental` (5 tick 以下) が COMPETITOR を隠す経路、
  per-CPU でなく合計で判定してしまう経路、`ATTRIBUTION_UNRESOLVED` が
  実質 CLEAN と同じ扱いになる経路。
- **uid / cgroup が判定に混入していないか** (親は所有者ベースの免除を明確に禁じた)。
- 診断 4 値の分類 (`value` / `absent` / `unreadable` / `error`) に取りこぼしはないか。
  ENOENT と EACCES 以外の errno がどこへ落ちるか。`error` が本当に致命として効くか。
- 追加テストの**単一理由性**と境界 (5 通る / 6 落ちる、`unreadable` 通る / `error` 落ちる)。
- 既存の受理集合・閾値 (0.95 / 0.05 / 46 / 445 / band / `INVALID ⇒ NOT_EVALUATED`) が
  意味的に不変か。
