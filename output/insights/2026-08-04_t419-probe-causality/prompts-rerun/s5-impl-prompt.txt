## 直すこと (2 点だけ。新機能を足さない)

### G-1 (F110) 非自 process は「誰か」でなく「どれだけ消費したか」で三分する

現行は「非自 PID が正の CPU-time delta を持てば COMPETITOR」で、batch scheduler の常駐デーモン
(`nqs_shpd`、uid 0、`/system.slice/nqs-jsv.service`) が必ず居るため**計算ノードでは永久に
COMPETITOR になる**。これを次へ変える。

- 非自 process (PID + starttime で自 tree に属さないもの) の CPU-time delta を **per-CPU で集計**する。
- 当該 arm・当該 CPU の非自消費が
  - **5 tick 以下** → `incidental`。**COMPETITOR にしない。** ただし `CLEAN` にもせず
    `ATTRIBUTION_UNRESOLVED` とし、消費量と対象 CPU を結果へ記録する。
  - **6 tick 以上** → `COMPETITOR`。arm を INVALID にし後続 arm を止める (現行どおり)。
- 閾値は定数として外出しし (`INCIDENTAL_NONSELF_TICKS_MAX = 5` 等)、**docstring に根拠を 1 行**書く:
  前 wave の A0 実測で `nqs_shpd` が CPU 22 に 4 tick を出したが、その CPU は 30/30 の読みで
  一度も帯外にならなかった。
- **uid や cgroup を判定に使ってはならない。** `/system.slice` や uid 0 の無条件免除にしない
  (「誰か」で免除すると、暴走したシステムデーモンを見逃す)。identity (uid / comm / cgroup) は
  記録用 allowlist field として従来どおり残す。**argv と env は保存しない。**
- **incidental な非自活動があった CPU の集合を結果へ列挙する**。A1 の分析側で
  「その CPU が帯外だったか」を別集計できるようにする (汚染が実際に効いたかを事後に見るため)。
  集計 field 名は自由だが、README から参照できるよう安定した名前にすること。

### G-2 (F111) 診断 field は 4 値で記録し、`error` だけを致命にする

現行は permission で読めない field を incomplete 扱いし、`cpuinfo_cur_freq` が
48 policy すべて EACCES の計算ノードでは**必ず incomplete** になる。次へ変える。

- 各 field の status を **`value` / `absent` (ENOENT) / `unreadable` (EACCES・EPERM) /
  `error` (それ以外)** の 4 値にする。
- `complete` = 全 field が `value` / `absent` / `unreadable` のいずれかで **`error` が 0 件**。
  **`unreadable` は incomplete にしない。**
- status 別の件数を結果へ記録する (`cpuinfo_cur_freq` が全 policy `unreadable` である事実が
  そのまま読み取れること)。

## 追加するテスト (変異の的。親が段 4 で事前登録済み)

`orchestrator/tests/test_t419_probe_causality.py` へ**単一理由**の合成 fixture を足す。
`/proc` も subprocess も使わない純計算であること。

1. `incidental` (非自 5 tick、1 CPU) → `ATTRIBUTION_UNRESOLVED` かつ **arm は VALID**、
   後続 arm は止まらない。消費量と CPU が記録されている。
2. `incidental` の**境界**: 5 tick は通り、**6 tick は `COMPETITOR` + INVALID + 後続停止**。
   両方を別 node で固定する (`<=` と `<` の取り違えが赤になること)。
3. **uid 0 / `/system.slice` の非自 process が 6 tick** → **`COMPETITOR`**
   (所有者で免除していないことの証明)。
4. 診断 field が `unreadable` だけ → `complete=True` かつ arm は VALID。
5. 診断 field に `error` が 1 件 → `complete=False` かつ INVALID。
6. status 4 値の件数が結果へ正しく出ること。

既存の `contention` 系 fixture と矛盾しないこと。既存 node の期待値は変えない。
