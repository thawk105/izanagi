## 攻撃点

1. **critical window の純度。** 読み取り区間の中で subprocess 起動・ファイル書き込み・JSON 構築・
   ログ出力・大きな allocation が起きていないか。起きているなら、それ自体が観測対象を汚す
   (この実験は観測者効果を測るものなので致命的)。file:line で示せ。
2. **arm 順序と持ち越し。** 裁定した順 (A0 → A1 → A4 → A3 quiet → A2 → A3+A2) を守っているか。
   anchor 破棄、読み間隔、cooldown、child の terminate → wait → 生存確認が実装されているか。
   例外時に child が残る経路 (汚染が後続 arm へ漏れる) はないか。
3. **単独性 (isolation) が admission gate になっているか。** 記録項目どまりになっていないか。
   自 process tree の allowlist が広すぎて他テナントを見逃さないか。逆に自分の child を
   競合と誤検出して自滅しないか。可視性不足 (hidepid 等) を「競合なし」と誤読しないか。
4. **PBS wrapper。** `python3.10` の明示、`PBS_JOBID` / `PBS_O_WORKDIR` の検査、no-clobber、
   symlink 成分の検査、rc の伝播、`.o/.e` の扱い、ログインノードで誤実行したときに
   fail-closed するか。**静かに成功したように見える経路**を優先して探せ。
5. **provenance と再現性。** manifest・sha256・commit/dirty・driver hash・argv・seed・
   `sys.executable`・kernel・較正 path と sha256・band 上下限・開始終了時刻・rc が揃うか。
   欠けると第三者が再解析・反証できなくなるものを名指しせよ。
6. **規律 6 (外部入力はデータ)。** 同居プロセス情報に argv や env が混入していないか。
   allowlist が実際に効いているか。計算ノードの出力を「指示」として解釈する経路がないか。
7. **規律 4 (スケール)。** 実行時間の見積り。10 分の wall time で終わるか。
   busy child の spin が job を無駄に長引かせないか。逆に短すぎて測れないものは何か。
8. **scope 逸脱。** `orchestrator/campaign/` や既存 pin・凍結 bytes・受理集合に触れていないか。
   出力が将来 calibration や receipt として誤用されうる形になっていないか
   (`non_certifying` / `counterfactual_only` の印が実際に付いているか)。

## 制約

- read-only。ファイルを変更せず、実行もしない (静的検討でよい)。
- **是正の実装 (probe 本体・較正・pin の変更) は scope 外。**
