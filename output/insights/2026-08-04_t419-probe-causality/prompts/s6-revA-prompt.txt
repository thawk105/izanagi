## 攻撃点

1. **判定契約との一致。** 段 4 が事前登録した 3 条件 (pinned_hit_rate ≥ 0.95、
   nonpinned_out_of_band_rate ≤ 0.05、paired contrast が正の CPU が 46/48 以上) と
   `INVALID ⇒ NOT_EVALUATED` の含意が、コードで**そのとおり**実装されているか。
   分母・分子の定義がずれていないか (特に「pin 対象でも reader でもない」の除外)。
2. **恒真・恒偽になる経路。** 例外を握り潰して VALID にする経路、空集合で `all()` が真になる経路、
   欠測が 0 件と数えられて条件を自動的に満たす経路、rate の分母が 0 のときの扱い。
3. **oracle の位置。** 期待 verdict の assertion が driver 自身の中にあると、実装と期待が同時に
   ずれても緑のままになる。これが実際に起きうるか、起きたとき何を見逃すかを具体的に述べよ。
4. **変異耐性 (最重要)。** 次の変異を driver に入れたとき、テストが**本当に赤になるか**を
   コードを追って判定せよ。生存しそうなものは「生存する」と明言し、どの合成 fixture を
   足せば殺せるかを書け。
   - M1: paired contrast の比較を恒真化する
   - M2: `execution_validity` の欠測・例外検査を無効化する
   - M3: canonical 述語を「較正 median への厳密一致」へ差し替える
   - M4: α の累積最小を累積最大へ差し替える
   - M5: 単独性 gate (競合検出 → INVALID) を無効化する
   - M6: should-reject 判定を「常に reject」へ倒す (過剰拒否の正例が赤になるべき)
5. **合成 fixture の単一理由性。** 各 fixture が 1 つの理由でだけ赤くなるか。
   複数の期待を 1 node に詰めていないか。過剰決定 (別の層でも赤くなる) はないか。
6. **α/β/γ の 2×3 表。** should-pass / should-reject の意味が逆転していないか。
   「γ が should-reject を通した」を**成功と記録してしまう**経路が無いか
   (これは環境逸脱の見逃し = 偽陰性であり、成功ではない)。
7. **数値の落とし穴。** 浮動小数の比較、境界値 (band 上下限ちょうど)、
   `>=` と `>` の取り違え、median の偶数個での定義、NaN/inf の扱い。
