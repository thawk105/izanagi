## 1. 依頼と結果

裁定 U-1 (2026-08-04 /rulings) は「先に計算ノードで走行 CPU・cpufreq driver・boost 設定・
同居プロセスを束縛した probe 実験を置き、**因果を立証してから**是正方式を選ぶ」だった。

**因果は立証された。** 走行 889400 (全 6 arm・445 読み完走) で
`execution_validity=VALID` / `causal_verdict=CONFIRMED`。事前登録した 3 条件は
pinned_hit_rate=1.0 (≥0.95)、nonpinned 帯外率=8.87e-05 (≤0.05)、paired contrast 48/48 (≥46)。

**機序も精密化された。** 原因は「probe の走行 CPU であること」ではなく
「**そのコアがその瞬間 busy であること**」である — 同じ CPU に sleep する子を置くと帯外は 0/40、
spin する子を置くと 40/40。probe の走行 CPU は定義上必ず busy なので必ず帯外に出る。

**是正の実装はしていない。** probe 本体・較正の再取得・凍結 bytes と `env_contract.py` の pin は
依然 U-2 の所有であり、受理集合・実行時述語・防壁は 1 bit も動かしていない。
Pegasus campaign も開いていない。

## 2. 方式 α / β / γ の受理集合と実測 (要素数でなく式と反例で書く)

`S` = 観測 48 要素、`m` = 凍結較正の中央値 (2101.0)、`t` = `tolerance_pct` (2.0)、
`B = [2058.98, 2143.02]`、`r` = probe の走行 CPU、`K` = 読み回数。

| 方式 | 受理式 | 最小反例 | should-pass (静穏) | should-reject (真の逸脱) | 変更面 |
|---|---|---|---|---|---|
| 現行 | `∀i. S[i] ∈ B` | 1 要素でも帯外 | **0** (常に落ちる) | — | — |
| **α** | `∀i. min_{k≤K} S_k[i] ∈ B`、**走行 CPU を移しながら** K 回読む | ある CPU が全 K 回帯外 | **9/9、過剰拒否 0** | **未測定** | `method` 文字列、schema (K 回保持)、**取得手続き (巡回)**、凍結較正の再取得、pin |
| **β** | `∀i≠r. S[i] ∈ B` | `r` 以外に帯外が 1 個 | 119/120 (過剰拒否 1) | **0/55 = 全拒否** | 述語、schema (`r` の記録)、凍結較正、pin |
| **γ** | `#{i : S[i] ∉ B} ≤ 1` | 帯外が 2 個 | 119/120 (過剰拒否 1) | **0/55 = 全拒否** | 述語のみ (最小)、凍結較正、pin |

**実測から言えること。**

- **α の「走行 CPU を移しながら」は省略不能。** 巡回を抜いた形は 0/24 で全滅する。
  α を採るなら本番 probe の**取得手続きそのもの**に「走行 CPU を移す」が入る。変更面は述語に閉じない。
- **β と γ は本機体の実データでは挙動が一致した** (119/120、0/55)。事前に懸念していた
  「γ は真の逸脱を 1 コア分見逃す」は、**busy 同居という形の逸脱では起きなかった** —
  競合時は帯外が reader ぶんと合わせて 2 個になるため γ も落ちる。
  ただし γ が見逃すのは定義上「帯外がちょうど 1 個の逸脱」であり、
  **reader が居ない CPU 1 個だけが劣化する形**の逸脱は今回の実験では作っていない。
- **β と γ には約 0.8% (1/120) の過剰拒否がある。** 第三者の一過性バーストで帯外が 2 個になる読みが
  実在した (pin=40 の読みで CPU 25 が 3095.5 MHz)。**α は同じ読みを含む群でも通った** —
  位置ごと最小が一過性を吸収する。運用上はこれが α の実利である。
- **α の should-reject は未測定。** 巡回しながら競合下で読む arm が 445 読みの設計に無い。

## 3. 追加で分かった、選択肢の空間を狭める事実

- **`samples_mhz` はほぼ情報を運んでいない。** 21,360 標本の 97.6% が厳密に 2101.0 で、
  残りが「probe が走ったコア」を指す。α を採ると全要素が中央値へ収束し、この field の情報量は
  実質ゼロになる (= 「実効クロックの一致」を主張しなくなる)。
- **独立した周波数源へ替える案 (δ) は Pegasus では閉じている。** `cpuinfo_cur_freq` は
  48 policy すべて非 root で読めない。`scaling_cur_freq` は要求 P-state であって実測値ではない。
- **計算ノードには batch scheduler の常駐デーモンが必ず居る** (F110)。単独性を
  「非自 process の CPU 時間ゼロ」で定義すると永久に満たせない。実測した背景ノイズは
  中央値 0.00 / 最大 11.86 tick/s で、**この水準では読み値を汚さない** (control 11,280 件中 1 件)。

## 4. 裁定をお願いしたいこと

### R-0 (最初に) 裁定の文言と実装の食い違いを追認するか

**worklog (193) に記録された裁定 U-1b(i) は「`/system.slice` の uid 0 システムデーモンを
『環境』として記録しテナント競合と区別する」= 所有者ベースだった。
実装したのは消費量ベースで、所有者 (uid / cgroup) による免除を明示的に禁じている。**

- 理由: 測定を汚すのは「誰の process か」ではなく「そのコアが busy か」である。
  所有者で免除すると、**暴走した root デーモンを見逃す**。実測でもこれは裏付けられた —
  同じ CPU でも sleep する子なら帯外 0/40、spin させると 40/40 である。
- 実装: 非自 process の消費を subwindow ごと・CPU ごとに率で見る
  (`>= 3 tick` かつ `> 25 tick/s` で競合)。identity (uid / comm / cgroup) は記録するが判定に使わない。
- 結果: 裁定の目的 (常駐デーモンで実験が止まらないこと) は達成され、実験は完走した。
  所有者ベースより**厳しい**方向の置き換えである。
- **この置き換えを追認いただきたい。** 文言どおりの所有者ベースを望まれる場合は戻せる
  (ただし暴走デーモンを見逃す性質が入る)。

なお、この判断は裁定が台帳へ記録される前に親が brief で決めていたもので、
記録済み裁定を意図的に覆したものではない。経緯は `brief-rerun.md` の (P1) と erratum に残した。


### R-1 (本命) 是正方式をどれにするか

**推奨: α (走行 CPU を移しながら K 回読み、位置ごと最小)。** 理由:

- 唯一、過剰拒否 0 で静穏環境を通した (β/γ は約 0.8% で誤って落ちる)。
- 一過性バーストに強く、持続的な逸脱には弱くならない (持続していれば全 K 回で帯外に残る)。
- ユーザーの当初裁定でも筆頭だった。

**ただし α には未解決が 2 つある**ので、採用するなら次を同時に裁定してほしい。

1. **α の should-reject が未測定。** 採用前に専用 arm (reader を巡回させつつ busy child を置く) で
   測るか、測らずに採るか。
2. **取得手続きが変わる。** 本番 probe が走行 CPU を移すようになる。これは
   `method` 文字列・schema・凍結較正の再取得・pin に加え、**取得コード自体**の変更である。

γ を採る場合は最小変更で済むが、「帯外ちょうど 1 個の逸脱」を構造的に見逃す性質は残る
(今回の実験では該当する逸脱を作っていないので、実測で否定も肯定もされていない)。

### R-2 U-2 (較正の再取得と pin 更新) の起票

方式が決まれば U-2 は実行できる。`method` 文字列が動くので凍結 bytes と
`env_contract.py` の path + sha256 pin を同時に更新する必要がある (既知)。
[T-443] (CMake argv への verified cache projection) と [T-444] (取得経路の proof chain 束縛) は
この再発行サイクルへ同梱する裁定が既に出ている。

### R-3 外的妥当性の限定

本結論は **bnode138 / 889400 の exact config** に対するものである。他ノードでの再現は
未実測で、fleet 一般化は主張しない。追加 job は自動で増やさず、必要なら次段の裁定で決める。
