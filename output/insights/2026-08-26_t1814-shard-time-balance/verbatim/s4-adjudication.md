### 根拠 1 — 完璧な予言者でも利得 0.0 秒 (独立 2 走で再現)

同一 tip の K=2 走 2 本それぞれについて、その走自身の実測 duration で 3 通りの割付を評価した
(`counterfactual.py`。makespan 予測は shard ごとに `max(最長排他鎖, 仕事量/48)`)。

| 走 | 割付 | shard-0 予測 | shard-1 予測 | makespan 予測 |
|---|---|---|---|---|
| a1k2 | count (現行) | 222.7 秒 (鎖) | 156.2 秒 | **222.7 秒** |
| a1k2 | 台帳の重み | 222.7 秒 (鎖) | 156.2 秒 | **222.7 秒** (±0.0) |
| a1k2 | oracle (本走自身) | 222.7 秒 (鎖) | 156.2 秒 | **222.7 秒** (±0.0) |
| a4k2 | count (現行) | 206.1 秒 (鎖) | 96.5 秒 | **206.1 秒** |
| a4k2 | 台帳の重み | 206.1 秒 (鎖) | 103.6 秒 | **206.1 秒** (±0.0) |
| a4k2 | oracle (本走自身) | 206.1 秒 (鎖) | 110.1 秒 | **206.1 秒** (±0.0) |

oracle 割付は仕事量を完全に均衡させる (a4k2 で 5283.4 / 5283.4 秒、1 worker あたり 110.1 秒)。
それでも `real-repo` の排他鎖はそのまま 1 worker に載り続ける。
**a4k2 では鎖 206.1 秒に対し shard-0 の仕事量/48 は 139.9 秒しかなく、鎖が 66 秒上回っている。**

この結論は模型に依存しない部分を持つ。`xdist` の `loadgroup` は 1 group を 1 worker で直列に実行するので、
その shard の pytest wall は「鎖の所要 + その worker の開始時刻」を下回れない。実測でも
鎖以外の最遅 worker は a1k2 で 191.4 秒 (鎖 222.7 秒)、a4k2 で 138.1 秒 (鎖 206.1 秒) であり、
**鎖が単独で最遅である。** 再割付は鎖以外を下げるだけで、最遅を動かさない。

### 根拠 2 — 現物台帳では機能が一度も発火しない

台帳は 15,909 nodeid、現行受入集合は 17,160 node。実測被覆は **15,878 / 17,160 = 92.5%**。
段 3 の 2 レンズが独立に指摘したとおり、plan の「1 件でも未知なら全体を要素数へ戻す」設計は
**毎走必ず発火し、duration 割付は実環境で一度も動かない。** 部分被覆で動かす設計にすると、
台帳に provenance (tip / K / scheduler / worker 数 / 入力 junit digest) が無いため、
何を重みにしたのかを走行証拠から言えない。scope 3 が台帳の再生成を除外している以上、
本 wave では両方とも成立しない。

### 根拠 3 — 追う効果より走間ばらつきが 1 桁大きい

同一 tip・同一選択・同一割付の K=2 を 2 走した結果、pytest wall は 307.29 / 275.02 秒
(差 32.27 秒)、直列総仕事量は 14862.6 / 10585.7 秒 (1.40 倍) だった。原因は割り当てられた
計算ノードの違いである (bnode009+bnode001 対 bnode016+bnode017)。
**追おうとしている効果 0.0 秒に対し、ノイズが 32 秒ある。**

## 裁定 2 — 判定式は保証ではなく再検討 trigger

次を **保証ではなく再検討の引き金**として記録する。

> ある走について、その走の最長排他鎖 `C` と直列総仕事量 `W`、shard 数 `K`、worker 数 48 を取る。
> `C > W / (48K)` である限り、その走の makespan は鎖で床が決まり、割付を均衡させても下がらない。
> `C < W / (48K)` が観測されたら、duration 重み割付を再検討してよい。

観測実績: 参照走 `C=210.5 > 7472.5/96 = 77.8`、a1k2 `C=222.7 > 14862.6/96 = 154.8`、
a4k2 `C=206.1 > 10585.7/96 = 110.3`。**3 走とも成立している。**

この式は**必要条件でしかない** (段 2 plan と luna の指摘)。逆が成り立っても短縮できるとは限らない。
また既存の成果物 field だけでは `C` を機械的に取れない (`report.json` は group ごとの直列所要を
持たない)。したがって**恒真な機械 gate は作らず**、次に測る人が junit と `report.json` を
join して求めるものとする。
