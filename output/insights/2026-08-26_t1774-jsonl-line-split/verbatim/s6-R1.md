### LF 専用分割は U+2028 / U+2029 以外の受理集合も変える

**重大度**: must-fix

**根拠**: `orchestrator/codex_roles/events.py:316` の `text.split("\n")` は、旧 `splitlines()` が境界とした U+000B、U+000C、U+001C、U+001D、U+001E、U+0085、U+2028、U+2029 を分割しない。したがって以下が発生する。

- U+0085 を JSON string または key に含む正当な LF JSONL が新規に受理される。これは裁定が許した U+2028 / U+2029 以外の受理拡大である。
- 上記 8 文字を二つの JSON object 間の区切りとしていた入力は、旧実装では複数 event として受理されたが、変更後は一つの LF line 内の不正 JSON として拒否される。
- 同じ理由で、`orchestrator/codex_roles/events.py:316-326` の `lineno` と `:319-320` の行 byte 上限は、これらの境界をまたぐ入力で意味が変わる。複数行から一つの LF line へ合成され、診断行番号や拒否理由が変化する。
- `_decode_jsonl` の全体 byte 上限、BOM、NUL、CR、NFC 検査は分割前の `orchestrator/codex_roles/events.py:170-197` にあるため、この差を閉じない。

**成果物影響**: U+0085 を含む event stream が新たに `ValidatedEventStream` へ到達し、逆に非 LF 境界を使った既存 stream が拒否されるため、certified evidence の受理集合と event digest の参照対象が裁定外で変わる。

**提案する修正**: exact な受理差を維持するなら、JSON string の quote と escape 状態を追う splitter を追加し、U+2028 / U+2029 は string 内だけ境界扱いしない一方、その他の旧 `splitlines()` 境界は旧挙動を保つ。より広い LF 専用化を意図するなら、先に裁定を更新し、U+0085 の新規受理と上記 8 境界の拒否を明記した test を追加する。

### CR だけの空行は parser 前に捨てられ、CR を含む artifact が complete になれる

**重大度**: must-fix

**根拠**: byte 側の全 5 site は `split(b"\n")` 後、CR 検査より先に `if not raw_line.strip(): continue` を実行する。

- `_drain_stdout`: `tools/codex_worker_launch.py:1273-1278`
- `_tail_rollout`: `tools/codex_worker_launch.py:1406-1411`
