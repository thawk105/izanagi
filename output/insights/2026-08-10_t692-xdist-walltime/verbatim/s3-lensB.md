## 所見1 — `M` と重なりを一つの式に押し込んでいる

- **重大度**: Critical
- **主張**: `875.67秒`は、`M=671.55`を共有 cache 完了時刻とみなし、payer と CLI が同時開始するという条件付き値に過ぎない。
- **根拠**:
  - `s2-plan.md:66-88` は `M` を cache-ready proxy とする。
  - `real_repo_receipt_memo.py:150-163` は、cache owner が `flock` を取得する実行体であることを示す。`M` の testcase が owner か waiter かは測定されていない。
  - `s2-plan.md:28-30` 自身も owner/waiter を識別不能としている。
  - xdist の `loadgroup` は group を同一 worker の work unit にするが、payer と group CLI の同時開始や lock owner を保証しない (`xdist/scheduler/loadgroup.py:45-57`, `loadscope.py:362-402`)。
- **計算**:

  `T = B + R + H + S = 2.08 + 55.07 + 69.45 + 58.35 = 184.95`

  同時開始を仮定すれば、

  `max(653.50, 671.55) + 184.95 + 19.17 = 875.67秒`

  しかし、group CLI 開始から `d` 秒遅れて payer が始まるなら、

  `max(653.50, 671.55 + d) + 184.95 + 19.17`

  となる。`d=100` なら **975.67秒**、CLI 終了後に payer が始まる `d=653.50` なら **1529.17秒**である。

  `C` と `M` が同一 worker で直列化される場合も、

  `653.50 + 671.55 + 184.95 + 19.17 = 1529.17秒`

  となる。

## 所見2 — JUnit `time` を仕事量・critical path と解釈し過ぎている

- **重大度**: Major
- **主張**: `time` の合計は elapsed な worker 占有時間の集計であり、CPU仕事量や依存関係を表す critical path ではない。
- **根拠**:
  - `analyze_junit.py:107-140` は testcase の `time` を単純加算するだけで、開始時刻・終了時刻・待ち理由を持たない。
  - JUnit `time` は setup/call/teardown と lock、I/O、subprocess 待ちを区別しない。
  - `16534.55 / 48 = 344.47秒` の算術自体は正しいが、待ちが大半なら「48 worker が処理できる仕事量の下界」としての意味は薄い。
- **正しい数値**:

  `16534.55 / 48 = 344.46979... ≒ 344.47秒`

  `real-repo` の `1388.80秒`は、同一 group が一 worker の work unit として順番に処理される場合の観測占有時間の下界にはなる。しかし、`1388.80秒 ≒ critical path`、さらに変更後もその構造が保たれる、という因果までは示さない。

- **根拠**: `s1-measurement.md:22-24` の

## 所見5 — 恒久策ではなく、増加率を残したままの一度きりの短縮

- **重大度**: Critical
- **主張**: 案1は receipt 解決の回数も、commit/output 増加に対する計算量も減らさない。
- **根拠**: `real_repo_receipt_memo.py:4-9` は commit 数に比例して解決コストが増えると記録している。案1は単に二つの処理を重ねるだけである。
- **式**:

  `q(N,F) = aN + bF + c`

  を receipt 解決コスト、`C=αq`、`M=βq` とすると、

  `W₁(N,F) = max(αq(N,F), βq(N,F)) + T(N,F) + δ`

  であり、`W₁ = Θ(N+F)` のままである。削減されるのは重複分の一部で、増加傾きは消えない。

  tail を固定と仮定しても、

  `W₁(r) = 671.55r + 204.12`

  なので、2400秒上限には `r ≒ 3.27` で到達する。全項目が同率で増えるなら `875.67r`、約 `r=2.74` で到達する。

## 所見6 — 並行 wave との合成効果が未定義

- **重大度**: Major
- **主張**: `dev-wave-suite-floor-recheck` の短縮を単純に加算できない。
- **式**:

  `C' = 653.50 - ΔC`、`M' = 671.55 - ΔM` とし、tail が不変という強い仮定を置いても、

  `W_both = max(653.50-ΔC, 671.55-ΔM) + 204.12`

  である。

  - 両方を同じ `d` 秒短縮: `875.67-d`
  - CLI だけを完全短縮: **875.67秒**（Mが支配）
  - Mだけを完全短縮: `653.50+204.12 = 857.62秒`
  - 両方を完全短縮: **204.12秒**（tail不変という非現実的仮定）

  実際には `B/R/H/S/δ` も変わり得る。一方が先に land した時点で、現在の `C/M/δ` の数値見積りは無効になり、両変更込みの全走を再測定すべきである。

## 所見8 — prewarm 案の算術は合っているが、「C と M が両方消える」は誤り

- **重大度**: Major
- **主張**: `1285.20秒`の計算は条件付きでは正しいが、prewarm の効果説明が誤っている。
- **根拠**:
  - `427.58 + 838.45 + 19.17 = 1285.20秒`。
  - しかし CLI test は子 interpreter で `driver.main()`を直接呼び (`test_s8b_oracle_driver.py:3049-3065`)、`real_repo_receipt_memo.patch_driver_resolver()` (`real_repo_receipt_memo.py:180-184`) を使わない。
- **正しい解釈**:

  worker 前の prewarm が同じ UID/HEAD の memo cache を正しく作れれば、`M`側の共有 memo は消せる可能性がある。しかし `C=653.50`の独立 CLI 解決は残る。

  `prewarm + C + B + R + H + S + δ`

  `= 427.58 + 653.50 + 2.08 + 55.07 + 69.45 + 58.35 + 19.17`

  `= 1285.20秒`

  production resolver 自体を prewarm cache 対応に変えれば `C`も変わるが、それは prewarm ではなく、テスト対象の独立解決経路を変更する別設計である。
