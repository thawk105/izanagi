## 結論

抑止の仕組みは dev-wave に**ある**が、土台 (tools / orchestrator / テスト / 台帳) へのゴミ流入を**止められていない**。
仕組みは wave の中の must-fix を篩うだけで、wave 自身の正当化 (研究を進めるか) を問わず、追加と削除が非対称で、
所見→裁定→起票の連鎖に出口が無い。

## なぜ止まらないか (dev-wave の構造的な穴)

1. **wave 自身の正当化を問う gate が無い。** `DW-G01`〜`G05` は wave 内の must-fix を篩う。「この wave が論文の
   主張・図表・実験の何を進めるか／土台なら今止めている研究は何か (実測)」を段 1 に書く義務が無い。研究最優先の
   前提は `/next-tasks` 側 (「常設の前提」節) にしかなく、dev-wave は `DW-C00` で「command 引数は worklog 候補
   より優先」するため、裁定 (D→T) やユーザー直投入、supervisor 起動の wave はこの篩を通らない。
2. **敵対レンズが「足りない防壁」しか探さない。** `DW-S03` は「gate を新設する wave では効く全層が scope に入るか」
   を必ずレンズに入れる (追加方向の義務)。「この追加は実測欠陥に対応しているか、削除・局所修正で済まないか」を
   攻撃するレンズは無い。段 6 の 2 本も同じ。
3. **所見→裁定→T 起票の連鎖に出口が無い。** scope 外 real 所見は裁定パッケージへ送られ、大半が T になる
   (持ち越し 345 件)。D730「滞留項目は原則実施しない」は docs 予算の話にしか適用されていない。
4. **コードには予算が無い。** 手順書には byte 予算、テスト時間には 5 分上限があるが、製品行・テスト行・tool 本数・
   gate 本数の純増を観測する項目すら段 7 に無い。
5. **足すのと消すのが同じコスト**で、消す方だけ追加手順 (`DW-O11`) がある。変異 matrix は「実装面の差分ゼロ」以外
   すべてに必須 (`DW-S04`) なので、campaign driver や作図 script でも kill 可能な assert とテストを書く圧力が掛かる。
   テストが製品の約 1.3 倍の行数になっている一因。
