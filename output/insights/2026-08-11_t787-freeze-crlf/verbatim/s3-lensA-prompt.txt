## このレンズの担当

**正しさ境界と受理集合。**親 brief の不変条件 1〜5 とプランの diff 案が、実際に
「key exact `path` の str 値に CR または LF を含む契約だけを新たに拒否する」に一致するかを攻撃する。

必ず検討する攻撃面:

1. **過小拒否**: プランの検査を通り抜けて凍結できる CR/LF path の入力を構成できるか。
   malformed shape (`conditions` を dict にする、path を list の中に埋める、深い入れ子、
   surrogate pair、正規化で CR/LF に化ける文字列、`\r\n` 以外の改行類) を試せ。
2. **過剰拒否**: 現在通っている入力で新たに落ちるものを構成できるか
   (path 以外の field の CR/LF、`path` を key に持つが値が非 str、U+2028 等)。
3. **理由語と優先順位の壊れ**: NUL 入り入力の理由語・pointer が変わる系列はあるか。
   NUL と CR/LF が同一 node・別 node に共存する場合の文書順・stack pop 順を具体的に追え。
4. **hash 不変の破れ**: 検査位置 (canonical 化の後) が動くと何が変わるか。
   現行契約 hash `c4f3740202de302c…` と既発行 g1 record の `protected_sha256` を変える系列。
5. **層の取りこぼし** (必須): 本 wave は gate を新設する。凍結発行・履歴検証・activation report
   のうち、この choke point を通らない経路が実在しないかを file:line で確かめよ。
   scope 外の層があれば実装したふりをせず、裁定パッケージ候補として名指しで返せ。
6. **親自身の実測の一般化**: 親は「CR/LF 入り契約は凍結層を通り hash が返る、発効層は
   `contract-path-control-char` で拒否」を 1 契約・1 位置で測っただけである。この一般化が
   成り立たない位置・条件があるかを攻撃せよ。

## 制約

- sandbox は read-only。pytest の実走は不要で、静的検査でよい。実走は親が行う。
- 「受理集合を緩めれば楽になる」方向の提案はしない。拒否を弱める案は採用されない。
- 各所見に「これを直さないと成果物 (凍結台帳・proof chain・certified 選択) のどの値・受理集合・
  参照がどう変わるか」を 1 行で付ける。書けない所見は nit と自己申告せよ。
- 結論は GO / NO-GO のいずれかを明示する。
- 出力の最後に `## 総括` 見出しで要点を 10 行以内にまとめる。
