# [T-650] 受入 lease の終端解放を親の規律から land の機械へ移す (2026-08-17)

wave `t650-lease-release` / branch `worktree-dev-wave-t650-lease-release`

## この wave が何をしたか

受入全走を直列化する lease の**解放**は、入口の契約文が親 (LLM セッション) へ要求するだけで、
機械が保証する箇所が 1 つも無かった。land が到達点ごとに解放可否を宣言し、
終端でだけ自分で解放する形にした。設計判断の正本は decisions の
「land が到達点ごとに解放可否を宣言し、終端でだけ受入 lease を自分で解放する」。

**閉じたのは「land 到達後の lease 残留」だけである。** 受入全走のボトルネック全体ではない。

## 中心にある構造的事実

**rc は解放安全性を表現できない。** 同一 rc に決定的拒否と一時障害の両方が畳まれている。
全史 provenance 監査の rc は、checker が違反を返した場合だけでなく、timeout・中断・
binding 読取失敗・dispatch の infrastructure failure (rc=16)・signal 由来の負値 (-9 / -15) も
同じ値へ畳む。段 6 の敵対レビューが I/O seam 実行で `1, 16, -9, -15` のすべてが
解放側になることを実測し、実装がこの罠を踏んでいることを示した。

したがって終端性は **rc からではなく land の到達点ごとの宣言**から決める。
2 つの述語を直交させ、既定を両方 False にして、明示宣言した到達点だけが値を上げる。

**既定を保持側に倒すのが正しさ側である。** 親は段 1 で逆 (未知は手放す側) を provisional に
置いたが、段 3 の敵対レビューが却下した。終端を再試行可能と誤る最悪値は
「TTL または誤った loop が続く間の停止」で時間損失にとどまる。一方、再試行可能・未知・
中断状態を終端と誤る最悪値は「元の lander が再開可能な間に排他を解き、別 wave の受入を重ねる」で、
正しさに隣接する。**安全側は可用性側ではない。**

## 実走の帰属

**codex 子は pytest を 1 度も実走できなかった** (`dispatch infrastructure failure:
qstat -Q preflight rc=1` / `Unknown user-id`)。実走はすべて親が行い、子の非実走を緑と記録していない。

親の bounded local 実行も 3 回 rc=16 で止まった。**rc=16 は赤ではなく「測れなかった」**であり、
赤として数えていない。本 wave が実装した「rc=16 を決定的な赤と誤認しない」判定の必要性を、
運用側が同じ夜に 3 回実演した形になった。

焦点走で残った 1 件の赤は、機械化された非帰属 checker が
`status=non-attributable-only` / `classification=non-attributable` / `rerun_rc=1` を返し、
**tested main でも再現する main 側の赤**と確定した (`acceptance-red-check.json`)。
受入形の走行では出ず焦点走 (非受入形) でだけ出る。

## 並行セッションとの協調

本 wave は 3 つの並行セッションと通信した。**協調が成果に効いた点を 2 つ記録する。**

- 相手から受け取った「merge が provenance 違反を生むかは commit 前に測れる」実測
  (merge-base からの変更 file の積集合が空なら 3 方向結合の結果は和集合そのもので違反は生まれない) を
  取り込み前に適用し、**merge を実行する前に Codex `role=author` の合成監査が要ると分かった**。
- 相手が「bounded local で rc=16 を実際に踏んだ」と教えてくれた事実を handoff へ記録し、
  レビュー prompt の攻撃面に入れた結果、**実装が同じ罠を踏んでいることが実測で出た**。
  単独セッションなら見落とした可能性が高い。

逆に本 wave からは、相手の preflight が同じ rc 畳み込み欠陥を持つこと、
待ち札の順位喪失の機序、および非帰属 checker の修正が既に main へ着地していることを渡した。
