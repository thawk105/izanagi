## 攻撃せよ (レンズ = 正しさ境界と恒真化)

1. **gate の移動が受理集合を変えないという主張の反証。** プランは self-pass gate を
   benchmark 後 (`cli.py:612`) から `_acquisition_reasons` (benchmark 前) へ移し、
   「最終 accepted publish 集合は不変」と主張する。反証せよ。
   - 早期拒否によって、後段でしか計算されない `certification_quality_reasons` や
     `window_probe` 由来の reason が rejection artifact から消えないか。
   - 「reject される理由の集合」が変わることは、成果物 (rejection.json / receipt) の
     どの値を変えるか。それは proof chain の消費者に影響するか。
   - profile が benchmark 前後で同一だと保証されているか (`_static_profile_bytes` は
     clock を除外している点に注意)。clock が benchmark 前後で変わりうるなら、
     早期 gate は「別の時刻の clock」を検査していることになる。これは受理集合の変更か。
2. **evaluator 抽出が canonical 述語を変えないという主張の反証。** プランは
   `execution_guard` から帯計算 evaluator を抽出し、`effective_clock_comparison_passes` と
   `_effective_clock_band_math_passes` の双方を委譲させる。この refactor が
   現行の受理・拒否挙動を 1 bit も変えないことを、境界値 (等号、NaN、空列、非 float、
   tolerance=0、tolerance=100) で反証せよ。変わる入力が 1 つでもあれば real 所見である。
3. **診断が admission に混入する経路。** 診断値 (`out_of_band_count` など) が
   受理判断に使われる設計になっていないか。使われていれば述語の権威が二重化する。
4. **生死 driver の non-certifying 主張の反証。** プランの liveness 出力が
   「較正として使えない」ことは構造で保証されているか、それとも命名と宣言だけか。
   出力を calibration loader へ食わせる経路、publish API へ渡す経路、
   registry へ登録する経路が本当に無いか file:line で確かめよ。
5. **変異事前登録の帰属不成立。** プランの変異表のうち、
   「その変異を入れても別の層が同じ入力を拒否するため、狙った検査の削除を証明できない」ものを
   すべて挙げよ。特に schema preflight、`_acquisition_reasons` の他条件、
   `certification_quality_reasons` による mask を疑え。
6. **gate が効く全層。** この wave は取得側にだけ gate を置き、loader 側には置かない。
   その結果「取得は塞いだが別経路から同じ穴が開いている」層が残らないか列挙せよ。
   scope 外の層を実装したふりにせず、裁定パッケージ候補として返せ。
