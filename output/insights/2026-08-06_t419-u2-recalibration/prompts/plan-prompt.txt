## タスク

本 wave の実装プラン v1 を file:line 粒度で起草せよ。次の 4 単位を扱う。

### 単位 1 (必須) — 取得経路の canonical 述語 self-pass gate

publish される新しい較正が「自分の samples が自分の median に対して tolerance 帯を外れる」場合に
`accepted` として publish されないようにする。要件:

- **述語の権威を二重化しない。** 既存の canonical 述語 (`execution_guard` 側) を呼ぶ形にし、
  帯計算を再実装しない。再実装が避けられないなら、その理由と同値性の証明方法を書け。
- 発火点を file:line で 1 つに決めよ。`_acquisition_reasons` に足すのか、`_assemble_v2` の
  status 決定へ足すのか、`window_probe` 側か。**それぞれの受理集合への影響を比較して選べ。**
- 既存 artifact の**読み取り**経路 (`load_verified_calibration`、registry、consumer) を
  一切狭めないこと。狭めると現行 g1 較正が読めなくなり、承認外の受理縮小になる。
- 拒否は fail-closed で、診断に「どの位置がどれだけ帯を外れたか」を構造化して残すこと (規律 3)。
- 恒真にならないこと。通る正例を 1 つ、落ちる負例を 1 つ、署名で書け。

### 単位 2 (必須) — 計算ノードでの α 生死 driver

2 時間の certify を投入する前に、Pegasus 計算ノード (専有 1 ノード、48 CPU) 上で本番 `ea.probe()` を
走らせ、tolerance 2% 帯内 (帯外 0 件) かどうかを実測する使い捨て driver を設計せよ。

- **既存経路を最大限使え。** `tools/pegasus/run_probe.py` + `probes/*.pbs` の先例に倣うのか、
  それとも別の既存 driver があるのか、file:line で示せ。新規コードは 100 行以内に収めよ。
- 出力は create-only で `output/env/pegasus/` 配下の job 専用ディレクトリへ置き、
  帯外件数・median・method・hostname・load1 を機械可読に残すこと。
- **この driver は non-certifying であることを自己宣言し、較正としては絶対に使えない形にせよ。**
- 単独性の確認 (専有ノード上で他プロセスが動いていないこと) を観測に含めよ。

### 単位 3 (条件付き) — [T-444] 取得経路の proof chain 束縛

裁定は「取得経路の proof chain 束縛 (acquisition receipt 新設、D96 手続) を再発行サイクルへ同梱」。
現行 artifact には既に `acquisition_receipt` オブジェクトがある。**現状で何が束縛されていて、
何が束縛されていないかを file:line で棚卸しし、純増があるかを判定せよ。**
純増が無い (既に束縛済み) なら「実装しない」と結論してよい。あるなら最小の追加を設計せよ。

### 単位 4 (調査のみ) — [T-443] certify の build が過去に成功していた機序

裁定は「各 campaign の CMake argv へ verified cache projection を足す。ただし単独では実施せず
本サイクルへ同梱する。同梱時に certify が過去に成功していた機序 (login node の network か
warm cache か) の検証を含める」。計算ノードは外部 network を持たない (runbook §7)。
それでも certify job (0:867876.nqsv) の CCBench build は成功している。
**certify_calibration.sh と CCBench の CMake を読んで、FetchContent がどこへ向かうか、
何が事前取得されているかを file:line で確定せよ。** そのうえで、certify を再実行するために
**本 wave で必要な変更があるか無いか**を判定せよ (campaign 側 argv の変更は本 wave の scope 外)。
