## 攻撃せよ (レンズ = 正しさ境界と恒真化)

1. **期待値更新の許可は正当か。** 親は「赤の原因は実装の誤りではなく採用済みの設計変更」と
   裁定した。反証せよ。赤 4 node が固定していた性質を 1 つずつ列挙し、
   **早期化と論理的に両立しない性質**と、**両立するのに落とされようとしている性質**を分けよ。
   後者が 1 つでもあれば、それは実装の欠陥であり期待値更新で隠してはならない。
   特に `test_effective_clock_policy_metamorphic_wiring_...` は metamorphic 検査なので、
   「早期化と無関係に壊れている」可能性を疑え。
2. **canonical 述語の同値性。** `_effective_clock_band_evaluation` の抽出が
   `effective_clock_comparison_passes` と `_effective_clock_band_math_passes` の
   現行挙動を 1 bit も変えていないことを反証せよ。境界を実際に列挙して比較せよ:
   非 Mapping、余分な key、key 不足、`samples_mhz` が list でない、空列、
   tolerance が bool / int / float / 文字列、tolerance が 0 / 2.0 / 100、
   NaN・inf を含む sample、numeric string、bool sample、expected と observed の長さ違い、
   帯の上下等号ちょうどと 1 ulp 外側。**1 つでも挙動が変わるなら real 所見である。**
3. **診断が admission に混入していないか。** `out_of_band_count` や `violations` が
   受理判断へ流れる経路が無いことを file:line で確かめよ。
   `input_valid=False` のとき `band_pass` と `out_of_band_count` が何になるか、
   それを誤読して「帯外 0 件だから合格」と結論できる呼び手が無いかを探せ。
4. **early gate の追加が受理集合を意図せず変えていないか。**
   `_acquisition_reasons` に足した検査が、clock 以外の理由で拒否される入力の
   reason 集合や順序を変えていないか。例外経路 (`KeyError`/`TypeError`/`ValueError` を
   `receipt-invalid` へ変換する try 節の**内側**に足されている点) が、
   従来 `receipt-invalid` にならなかった入力を `receipt-invalid` へ倒していないか。
5. **publish policy 同一性検査の位置。** `_write_exclusive(temporary, ...)` の**後**、
   `_rename_noreplace` の**前**に置かれている。この位置で
   (a) 一時ファイルが確実に掃除されるか、(b) 例外が `reasons` に載るか、
   (c) `attempt_tolerance_pct` が `None` のまま到達する経路が無いかを確かめよ。
6. **独立 self-comparison が本当に独立か。** 追加されたテストが
   「publish された bytes を読み直して canonical 述語を適用する」ことを本当にしているか、
   CLI 内部の profile や同一 dict 参照を経由していないかを反証せよ。
   改竄 fixture が実際に改竄後の bytes を検査対象にしているか確かめよ。
7. **変異帰属。** 段 4 の変異事前登録 M1〜M9 のうち、現在の実装・テスト構成で
   **単一理由性が成立しないもの**を挙げよ。特に M1 (early gate 削除) は late gate が残るため
   受理集合が変わらない。その場合に何が赤くなるべきかを述べよ。
8. **テスト弱体化の検出。** 新規テストが fixture へ現行値を差し込んで恒真になっていないか、
   assert が実質的に何も固定していない箇所が無いかを探せ。
