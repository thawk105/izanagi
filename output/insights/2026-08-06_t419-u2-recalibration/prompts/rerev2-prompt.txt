## 特に攻撃せよ

1. **G-1 (temp 掃除) が正しく直ったか。** 削除するのが
   「自分が `O_EXCL` で作成に成功した inode」だけであることを確かめよ。
   - 作成失敗 (既存ファイル・symlink 衝突) で何も消さないか。
   - inode 確認の方法が TOCTOU で騙されないか (作成後に別 process が差し替えた場合)。
   - 例外経路で二重 unlink や、削除失敗の握り潰しが残っていないか。
   - **この修正自体が新しい回帰を入れていないか** (正常系で temp が残る、fsync 失敗時に
     partial file が残る、など)。
2. **G-2 の (b) 採用が自己完結しているか。** `rejection.json` に保存された
   `attestation_profile` と canonicalization 識別子だけから、記録された SHA-256 を
   **成果物の外の情報を使わずに**再計算できるか。
   - 保存された profile が「hash を取った対象そのもの」か、部分集合や別表現でないか。
   - canonicalization 識別子が実際の実装 (`sort_keys` / `separators` / `ensure_ascii`) と
     一致するか。文字列が実装から自動生成されて自己参照 oracle になっていないか。
   - 成果物が巨大化して揮発値 (時刻・path・nonce) を巻き込んでいないか。
3. **G-3 の例外集約が public 述語の戻り値を変えていないか。**
   shape → policy → band の短絡順と戻り値が、1 巡目 snapshot および元の HEAD 版と
   同じであることを、境界入力を列挙して確かめよ。
   custom Mapping の例外が本当に構造化拒否になり、外へ漏れないか。
4. **既存テストの期待値が変更されていないか。** fix2 の diff で、
   1 巡目に許可された 4 node 以外の既存 assertion が緩められた箇所が無いか探せ。
   「fixture を強化した」と称して実質的に検査対象をずらしていないか疑え。
5. **所有外への波及。** `_write_exclusive` は publish 以外の呼び出し元にも使われる。
   全 caller を列挙し、cleanup 意味論の変更が壊す経路が無いか確かめよ。
