## 1. 前提事実 (一次資料)

- estimand の定義: 1 submission cohort から得られる量は
  `same-submission-cohort allocation-session-median CV` であり floor ではない (D145 決定 1)。
- 用途分離: within-run = 1 測定の品質ゲート (閾値 5%)、between-run = 採否の床 (D19)。
- linux-baremetal の実測 (転移知識): 同窓 between CV は rr5=0.666% / rr50=1.067% /
  rr95=0.110% と動作点間で約 10 倍非一様。**rr 軸に対する単調性はなく (rr50 > rr5)、
  「高 abort = 高分散」も D134 が反証済み** — どの点も他署名の worst-case prior にならない。
- Pegasus scoping 実測 (本 wave、request 887785.nqsv、bnode138、1 allocation 内 8 sessions × 5 reps):
  - balanced (rr50 系、registered 署名 1M/48): 同窓 between CV = **0.345%**、within CV = 0.964%
  - write-heavy (rr5 系): 同窓 between CV = **0.786%**、within CV = 2.071%
  - abort 率の注記 (ADV-10): 併記した abort (67.3% / 77.1%) は within 測定の代表 rep の値で
    あり、between 8 sessions 全体の実測 abort ではない。JSON notes の「8 独立セッション」は
    同一 allocation 内の直列 session を指し、時間窓独立性を意味しない (`time_window_clusters=1`)。
  - 両点とも同窓 between < within — linux と同構図。事前規定どおり安定性の証明とは解釈しない。
- official 側: 8b の承認済み floor は H1/H2 の **12-cell per-pair table**
  (セル別絶対 SD の RSS 合成 + wired minimum 3%、n_sessions=8 / reps=5 の凍結 protocol)。
  8c は 8b を正本とし、変更には再凍結を要求する。
- scoping の解釈制約: gen_S は Exclusive OFF。`_assert_single_tenant` は競合 bench pid のみ
  検出し、他ユーザープロセス・fabric/電力の common-mode は捉えない ((162) レンズ A5 の残余)。

## 2. 統計の骨格 (v2 — estimand 定義と検出力設計)

### 2.1 estimand と入れ子構造 (ADV-01 対応、2 巡目で consumer 単位へ是正)

- **時間窓 (window)** = 独立に投入され別々の scheduler 決定で開始した allocation。
- **推定対象 θ = 1 session-median の周辺 CV** — 現行 consumer (compare の丸め閾値) が消費する
  単位と同一にする。窓代表値 (median-of-M) の CV を θ にすると平滑化で床を過小評価し
  偽 faster 側へ倒れるため採らない (2 巡目所見)。median-of-M を consumer 契約側へ持ち込む案は
  contract 変更であり U-7 (b) と同様に本パッケージの射程外。
- 推定法: K 窓 × M sessions の一元配置 (random effects) で窓間成分 σ²_b と窓内成分 σ²_w に
  分解し、`θ̂ = √(σ̂²_b + σ̂²_w) / μ̂`。**UCL の自由度は保守側に df=K−1** を使う
  (時間成分の自由度は K からしか出ない。窓内 session をいくら増やしても K の代用にならない)。
- 今回の scoping 値 (0.345% / 0.786%) は **K=1 の窓内 session 分散**であり、θ の推定値ではない。
  θ の成分としては下限方向の参考値にだけ使う (D145 決定 1)。

### 2.2 判定規則と保証 (ADV-06 の算術訂正込み)

- 消費者側の実閾値は wired minimum 3% (official RSS 式のセル別 SD が別途あるため、
  本設計の θ は層 C の generic scalar — §U-7)。
- 判定規則 (事前登録): 署名ごとに
  `UCL_95(θ̂) · √2 < 3% なら「wired minimum 支配」、さもなくば「floor が閾値を動かす」`。
  `UCL_95(θ̂) = θ̂ · u_K`、`u_K = √((K−1)/χ²_{0.05,K−1})` (u_8=1.797、u_15=1.460、u_25=1.316)。
- **保証 (方向つき、nominal)**: 真の pair noise (θ√2) がちょうど 3% のとき「支配」と誤る確率は
  **i.i.d. 正規 SD モデル内の nominal 値として** 5% で、3% を超えるほどさらに小さい。
  危険方向 (偽 faster 側) の誤りはこれで抑える。実被覆の較正は §2.2 末尾の但し書きに従う。
- **判定境界の同窓換算 (v1 の誤りの訂正)**: 「支配」判定が期待される θ の上限は
  `3%/(√2·u_K)` = K=8 で 1.180%、K=15 で 1.453%、K=25 で 1.611%。
  観測同窓値 0.786% からはそれぞれ 1.50 倍 / 1.85 倍 / 2.05 倍。独立な時間成分の分散加算で
  言えば、必要な時間成分は K=8 で 0.878% (現在値の 1.12 倍相当) — v1 の「約 2 倍 / +1.2%pt」は
  誤りだった (レンズ ADV-06 が検出)。
- **√2 の前提 (ADV-05)**: 独立な 2 測定が同分散のときの差の SD。構成間で SD が異なる・
  同窓配置で共分散が生じる場合は成立しない近似であり、per-pair の正式な床は official RSS 式が
  持つ。本判定は「θ が 3% に対しどの側か」の層 C スクリーニングに限る。
- **被覆の但し書きと較正 (ADV-08 / ADV3-01、3 巡目で既定化)**: 本節の「5%」と §2.3 の検出力は
  すべて**窓間支配の i.i.d. 正規 SD モデル内の nominal 値**であり、§2.1 の二成分推定量に対する
  実被覆・実検出力は保証しない (推定量の分布は σ²_b/σ²_w 比と M にも依存する)。
  したがって**取得後の実判定 (U-5 の適格化を含む) は simulation-based calibration
  (実測 rep 分布からの再標本化で UCL 手続きの実被覆を較正) を既定の手続きとして事前登録する**。
  nominal 表は K 選択の設計指針に限る。window bootstrap は較正結果の独立診断として併用する
  (乖離が大きい側を保守側として採る)。較正は解析のみで費用が増える (計測は不変)。

### 2.3 効果量・検出力設計 (ADV-02 対応、D134 準拠の実体)

対立シナリオ (効果量) = 真の pair noise (θ√2) の水準。判定規則の下での「支配」判定確率。
**本表は「窓間成分が支配的 (σ²_w ≪ σ²_b) な i.i.d. 正規モデル」での nominal 値** (その極限では
θ̂ が df=K−1 の χ² に従い、表の数値はその厳密解)。§2.1 の二成分推定量の実分布は成分比と M にも
依存するため、**表は K 選択の設計指針にのみ使い、取得後の実判定は §2.2 の較正済み手続きが担う**
(ADV3-01 対応の役割分離)。境界 3% では全 K で 0.050:

| 真の pair noise | K=8 | K=15 | K=25 |
|---:|---:|---:|---:|
| 1.11% (= 観測同窓 rr5 の√2 倍相当) | 0.973 | 1.000 | 1.000 |
| 1.5% (同窓の約 1.35 倍) | 0.723 | 0.976 | 1.000 |
| 2.0% (同窓の約 1.8 倍) | 0.325 | 0.607 | 0.851 |
| 2.5% | 0.126 | 0.200 | 0.300 |
| 3.0% (境界) | 0.050 | 0.050 | 0.050 |
| 4.0% | 0.010 | 0.003 | 0.001 |

読み方 (nominal): 危険方向の保証は K に依らず 5% で固定。K は「真に支配側だったとき、それを
正しく言い切れる確率 (検出力)」を買う。**行の水準 (1.5%、2.0%、…) は測定値からの予測ではなく、
ユーザーが選ぶ設計感度である** (2 巡目 ADV-04 対応 — scoping 値・linux 値は H1/H2 へ転移しない
(D145 決定 4) ため、K 推薦の根拠に使わない。1 行目の 1.11% は参考表示に留まる)。
設計感度 1.5% で検出力 ≥95% を求めるなら K=15、2.0% で ≥85% なら K=25、
費用最小を優先し検出力 0.72 (@1.5%) を受け入れるなら K=8 になる。

### 2.4 費用 (ADV-09 対応 — 実測から導出)

実測 387 秒 = build prologue (~60 秒) + 2 署名 × (within 10 reps + 8 sessions×5 reps) ≈
session あたり ~18 秒。1 窓 (M=5 × 2 署名 + build) ≈ 約 5 分 ≈ **0.08 node-hour/窓**。
K=8 → 約 0.7、K=15 → 約 1.3、K=25 → 約 2.1 node-hours (+ queue 待ちは費用外)。
v1 の 0.7 node-hour/窓 は根拠なき過大見積りだった。**費用は制約にならず、制約は暦**
(窓間隔 × K が 8/31 保守までに収まるか) と統計である。

## 3. 裁定点

### U-1. 時間窓 cluster の定義と数 K

窓の定義 = §2.1。事前登録項目: 窓間の最小間隔、暦上の分散、K (固定、途中変更なし — U-3)。

K の選択は「設計感度 (どの pair-noise 水準まで判定を効かせたいか) × 目標検出力」の裁定である
(§2.3 の表が対応関係の正本):

- 択 (a) K=8、窓間 ≥ 12h、暦 3 日以上。約 0.7 node-hours。設計感度 1.5% で検出力 0.72。
- 択 (b) **K=15、窓間 ≥ 8h、暦 5 日以上。約 1.3 node-hours。設計感度 1.5% で検出力 0.976。
  親の推奨** — 費用が制約でない以上 (§2.4)、境界 3% に最も近い実用感度帯 (1.5%) で
  95% 級の検出力を確保する選択。scoping 値の転移を根拠にしない (§2.3)。
- 択 (c) K=25、窓間 ≥ 6h、暦 7 日以上。約 2.1 node-hours。設計感度 2.0% で 0.851。
  ユーザーが 2.0% 帯までの判定力を要求する場合。

### U-2. node cluster の数え方

- 択 (a) node は制御せず、割当 node を記録し「窓効果と node 効果が交絡した周辺分散」として
  報告する。**推奨** — 実運用 campaign も node を選ばないため、この周辺分散が採否用途に正しい
  母集団 (D134(f) の独立単位は窓が担う)。
- 択 (b) node 層別 (同一 node 系列 + 混在系列) で成分分解。費用 2 倍。採否の床には過剰。

### U-3. 標本数の導出規則と窓内 M

- K は §2.3 の検出力表から**事前に固定**し、**途中の見直し・増補をしない** (ADV-07 対応 —
  K=8 で覗いてから K=15 へ増やす逐次手続きは名目 95% を壊す。固定 K 一発で取得する)。
  記述的な中間観察は許すが、設計変更・停止判断に使わない (事前登録に明記)。
- 窓内 M=5 sessions (reps=5) を固定。**M を増やして K を節約する設計は禁止**
  (時間成分の自由度は K からしか出ない)。
- 事前登録セット: 窓定義・間隔・K・M・estimand と分解法 (§2.1)・UCL 水準 (95%)・
  判定規則 (§2.2)・**simulation-based calibration (既定・必須 — §2.2)**・bootstrap 診断・
  署名別に独立判定。nominal のまま実判定へ使う簡略化は認めない (ADV3-01 の裁定)。

### U-4. 対象 workload 署名

- 択 (a) **H1(rr80)/H2(rr20) の 2 署名。推奨** (8c が要求する対象そのもの)。
- 択 (b) H1/H2 + rr50 (診断継続)。費用 1.5 倍。
- どちらでも、各署名の records/threads はその署名で較正した calibration を先に要する
  (現 registered は rr50 のみ — 順序は U-6)。scoping (rr5/rr50 系) の値・判定は
  H1/H2 へ転移しない (ADV-04、D145 決定 4)。

### U-5. below-within の事前規定

「below-within は invalid でも安定性証明でもない」「`time_window_clusters` < **U-3 で固定した K**
のとき compare status は常に not-established」「`eligible_for_compare` は検証器が K 充足を
確認するまで false」を artifact schema とレポータで固定する (実装は floor infra wave の射程)。

### U-6. 依存の順序

(i) 本パッケージ U-1〜U-3、(ii) U-4、(iii) interpreter 版数 gate + **perf 実体のノード個体差**
([T-272] の射程 — scoping 側は preflight で自衛済み、certify 経路は未対応)、
(iv) job script bytes 束縛 ([T-424])、(v) attestation (T-419 U 系裁定待ち)、
(vi) campaign 形実行の land 経路 (T-422、F98)。
**推奨順序**: T-419 U 系裁定 → 較正再取得 (H1/H2 署名を含めるかを U-4 と同時に決める) →
T-424/T-272 → floor infra (U-1〜U-3・U-5・U-7 を実装) → K 窓の取得。

### U-7. official 8b/8c との境界 (ADV-03 対応、新設)

- 択 (a) **本設計の θ は層 C の署名別 generic scalar に限る。8b の per-pair frozen protocol
  (12-cell、RSS、n=8/reps=5) と 8c の per-pair floor 欄には触れず、充足もしない。推奨** —
  U-1〜U-6 を承認しても 8c の per-pair 義務は残る (誤誘導の遮断)。
- 択 (b) official per-pair 床の取得プロトコル自体を K 窓設計へ置換・拡張する。
  この場合 **8b の再凍結セレモニーと承認が必須**で、本パッケージの射程外の独立裁定になる。
