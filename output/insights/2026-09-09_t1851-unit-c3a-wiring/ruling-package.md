## 裁定 2 — 受理集合の「置換」を D1660 とどう整合させるか

段 6 の敵対レビューが、親の初出表現を 2 箇所で訂正した。**この訂正は採用済み**で、
記録と erratum は訂正後の表現になっている。**残る問いは、この向きの変更を今後どう扱うかである。**

### 何が起きたか (実測)

1. **ordinal 訂正は受理集合の置換である。** 旧誤軸の受理形 (planned の `0`、retry の recovery 軸 `0`)
   を新たに拒否し、契約が要求する planned の `None` と retry の measurement ordinal を新たに受理する。
   新旧は包含関係にない。意図した軸への束縛強度は上がる (retry の `1..N` が初めて実際に束縛される)。
2. **adapter の 3 遷移は限定解除である。** 「無条件拒否だった sealed terminal 後の遷移を、
   検証済み terminal 履歴に限って受理する」。これが無いと production campaign は 2 件目の
   clean attempt を予約できない。

D1660 は「受理集合は狭まる方向にしか動かない」と述べる。**上記 2 件はどちらも単調縮小ではない。**

### 択一

- **(a) 本件を D1660 の例外として明示的に追認する。** 理由は「誤った軸へ束縛した恒真な検査の訂正」と
  「production 経路が存在しないことによる過剰拒否の限定解除」であり、いずれも
  **正しさ gate の意味的強度を下げていない**。**親の推奨はこれ。**
- (b) D1660 を「受理集合は狭まるか、意図した軸へ置換されるかのいずれか」と改訂する。
- (c) いずれかの変更を差し戻す。**差し戻すと production 配線が成立しない**ため、
  単位 C3 そのものが不成立になる。

## 裁定 4 — C3b (実 campaign と値域 receipt) の設計

契約 9 節が要求する「実環境の値域」は本 wave では**供給していない**。C3b で供給する。

- 実行経路は既登録の `tools/pegasus/submit_floor.sh` で、F660 は発火しない
  (main 側登録簿に実在。ただし**静的確認であって qsub 成功の実測ではない**)。
- **1 回の campaign の min/max を母集合へ一般化できない** (段 3 レンズ B)。receipt には
  次の限界文言を載せる予定である。

  > 本 receipt は、記載した commit、Pegasus job、環境 tag、mode、protocol および freeze による
  > fresh default production campaign 1 回で、実際に観測された入力値だけを記録する。
  > 列挙値と min/max はこの run の観測集合および標本極値であり、launcher または consumer が
  > 受理しうる全値域、未発火分岐、他環境、他 mode、他 commit、将来 campaign の母集合または
  > 許容 bound を示さない。

- **(a) この設計で C3b を次単位として進める。親の推奨はこれ。**
- (b) 限界文言を変える。
- (c) 実値域の要求そのものを erratum で弱める (親の独断では変えない。単位分割と同じくユーザー裁定の対象)。
