# CCBench の adaptive backoff は機構でなく定数で負けている — 刻みを 0.5µs にすると 3.3 倍になる

**種別:** CCBench 還元候補。**認証されていない** — trace-disabled の性能測定のみで、
直列性の検査は行っていない (規律 2)。

## 発見

CCBench の adaptive backoff (Cicada 型の hill climbing) は、既定の調整定数のままだと
全 3 負荷・全 8 スレッド点で最下位になる。しかし**刻み幅 `kIncrBackoff` を 100µs から 0.5µs へ
変えるだけで、最良の静的 backoff とほぼ同等まで上がる。** 48 スレッドでの実測:

| 負荷 | 既定 (刻み 100µs) | 調整後 (刻み 0.5µs / 上限 50µs) | 既定比 | 最良の静的 backoff 比 | 無 backoff 比 |
| --- | --- | --- | --- | --- | --- |
| write-heavy | 1,382,620 | 3,587,303 | **+159.5%** | −8.2% | **+52.1%** |
| balanced | 1,219,140 | 4,161,550 | **+241.4%** | −1.0% | **+16.2%** |
| read-heavy | 2,309,644 | 9,922,478 | **+329.6%** | **+2.6%** | −2.3% |

**機構は壊れていない。定数が壊れている。**

さらに重要な性質として、**調整後の adaptive は負荷を教えられないまま、負荷ごとに正しい側へ寄る。**
read-heavy (backoff が効かない負荷) では無 backoff の 2.3% 落ちに留まり、
write-heavy (backoff が効く負荷) では無 backoff を 52.1% 上回る。
**どの静的定数を選んでも、この 2 つを同時には満たせない** — 静的 10µs は write-heavy で
最良だが read-heavy では無 backoff に 18.6% 負ける。

## 該当コード

`external/ccbench/include/backoff.hh:19-22` (pin `511c953`):

```cpp
  static constexpr double kMinBackoff = 0;
  static constexpr double kMaxBackoff = 1000;
  static constexpr double kIncrBackoff = 100;
  //static constexpr double kIncrBackoff = 0.5;
```

**最良の値がすぐ下にコメントアウトされて残っている。**

`Backoff_` は 0 から始まり、`update_backoff()` が約 10µs おきに `±kIncrBackoff` だけ動かして
`[kMinBackoff, kMaxBackoff]` へ丸める。したがって**到達可能な状態は
`{0, 100, 200, ..., 1000}` の 11 個しかない** (D1106 が既に確定させている)。
一方、静的 backoff の最適点は D1106 の記録で read-heavy=2 / balanced=5 / write-heavy=10 µs、
本測定でも同じ帯にある。**最適点は、適応機構が表現できる格子の上に一つも存在しない。**
既定の adaptive は「backoff 無し」と「10〜50 倍過大」の間を往復するしかない。

## 再現条件

`kIncrBackoff` と `kMaxBackoff` をビルド時パラメータへ開くパッチを当て、刻みを振った。
パッチは `izanagi-job-evidence/thread-scaling/cicada-adaptive-params.patch` (repo 外)。

| 項目 | 値 |
| --- | --- |
| 刻み `kIncrBackoff` | 0.5, 1, 2, 5, 10, 25, 50, 100 µs (100 = 既定) |
| 上限 `kMaxBackoff` | 1000 µs (既定)、および 50 µs |
| スレッド数 | 6, 12, 18, 24, 30, 36, 42, 48 |
| その他 | 1,000,000 レコード / zipf 0.9 / extime 3 秒 × 3 rep / trace-disabled |
| 環境 | Pegasus 計算ノード (48 物理コア、HT 無効)、job 966798–966803、6 ノード同時・約 12 分 |

**陽性対照:** 刻み 100µs / 上限 1000µs (= 既定と同値) のセルを格子に残した。
このセルは無改変ビルドの adaptive を**全 24 点で最大 2.84% の差**で再現した。
同じ走行での無 backoff の走行間ばらつきも最大 2.84% であり、
**パッチは既定値では観測可能な影響を持たない。**

## 刻みに対する応答は単調でない

write-heavy 48 スレッド (tps):

| 刻み | 0.5µs | 1µs | 2µs | 5µs | 10µs | 25µs | 50µs | 100µs (既定) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| | **3,534,405** | 1,985,237 | 1,663,671 | 1,274,115 | 1,276,069 | 1,228,561 | 1,378,696 | 1,382,620 |

0.5µs から 1µs へ刻みを 2 倍にしただけで 44% 落ちる。5〜25µs が谷で、
そこから既定の 100µs へ向けてわずかに戻る。上限を 50µs に絞ると 48 スレッドで
3,534,405 → 3,587,303 とわずかに改善する。

**この形の機序は本測定からは説明できない。** `Backoff_` の実際の軌跡を記録していないため、
「刻みが大きいと最適点を跨いで振動する」という素朴な説明が正しいかを言えない。
必要な診断は、走行中の `Backoff_` の時系列と、gradient の符号がノイズに支配される割合である。
規律 3 に従い、機序の説明は**未確定として残す**。

## 本プロジェクトの主張との関係

これは baseline の公平性に直接効く。2026-07-04 の docs 整合監査が既にこの穴を名指ししていた
(`docs/archive/audit-2026-07-04-docs-consistency.json`) —
「grid 定数 (kIncrBackoff=100us) を調整した適応 backoff とは未比較。
『デフォルトの下手な適応にしか勝っていない』と言われたら現 docs では返せない」「sweep 1 本で埋まる」。
**その sweep は 2 か月間投げられないまま残っていた。** 本測定がそれを埋める。

結論は監査が恐れていたとおりで、かつ恐れていたより良い。

- **恐れていたとおり:** 既定の adaptive を基準線に使った比較は、下手に設定された定数を
  叩いているだけであり、機構の優劣を何も言っていない。既定 adaptive に対する
  「+159%〜+330%」は、この定数の選択だけで消える。
- **恐れていたより良い:** 調整後の adaptive は最良の静的値に肉薄し、read-heavy では上回る。
  そして**負荷を知らされずに負荷ごとの正解へ寄る** — ワークロード特化の CC という本プロジェクトの
  主題そのものを、既存機構が既に部分的に達成していることを意味する。合成の目標は
  「静的最良に勝つ」ではなく「**調整済み適応**に勝つ、または適応が届かない領域を示す」へ上がる。

## 還元判断

**ユーザー確認待ち。** 上流 CCBench への報告候補として次を提示する。

1. `kIncrBackoff = 100` は、この実装の他の定数 (`kMaxBackoff = 1000`、更新間隔 10µs) と
   組み合わせると到達可能状態が 11 個になり、実測される最適点 (2〜10µs) を一つも含まない。
2. ソース中にコメントアウトされている `0.5` が、測定した 8 値の中で最良である。
3. 影響は大きい (48 スレッドで 2.6〜4.3 倍)。

**AI は還元の判断をしない。** 上流へ PR を出すか、出すとして本文をどうするかは人間が決める。
誤検出の可能性として、(a) 本測定が単一環境 (Pegasus 48 コア) のみであること、
(b) 直列性の検査を通していないこと、(c) 機序が未確定であることを明記する。
