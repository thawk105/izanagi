## 親が独立に確かめた新事実 (最重要)

**裁定 (109) の根拠値は、gate から計算できない量である。**

裁定を記録した commit `3b095bc` の時点で 4 reference を再計測した:

| 量 | 裁定文の記載 | `3b095bc` での実測 |
|---|---:|---:|
| 4 reference 合計 | 23,990 | 23,956 |
| 「実読」 | 10,515 | — (構造的に再現せず) |
| 常に走る段の無条件節 | — | 9,668 |
| wave クラス依存段の無条件節 | — | 9,169 |
| 条件成立時のみ (L2) | 3,755 | 5,119 |

裁定文の 10,515 / 3,755 は、どの構造的な層の和とも一致しない。10,515 のうち条件由来が
3,755 なら無条件由来は 6,760 で、これは当時の `core.md` 単体より小さい。すなわち
**あの数字は「ある 1 本の docs-only wave が実際に開いた節」の実行計測**であって、
repo から決定的に導ける量ではない。

したがって gate は必ず**構造的な代理量**を選ぶことになり、その選択でしきい値は 2 倍違う。
これは実装上の細部ではなく、gate が何を守るかの選択である。

## ユーザーへ返す択

いずれも「現在値で凍結し、引上げはしない」を前提にする。

- **択 1 — 3 層 gate (親の推奨)**: 上表の 3 層それぞれに現在値の上限を置く。
  常に読む量 10,568 を凍結し、クラス依存 9,493、条件のみは単節 cap (現行最大 935 → 1,000)。
  裁定の趣旨「常時読むものだけを厳しく縛る」に最も忠実。代償 = 無条件節は今後増やせない
  (縮小との交換のみ)。新しい義務は「条件付きにする」ことを強制する forcing function になる。
- **択 2 — 単層 L1 gate**: 全段の無条件節 20,061 を凍結し、条件節は単節 cap のみ。
  実装は最も軽い。ただし軽量 wave の実読の約 2 倍を縛り続け、裁定の問題意識を半分しか解かない。
- **択 3 — 段別 envelope**: 段ごとに「無条件 + 到達可能条件」の読量を現在値で pin
  (段 5 最悪 10,315 / 段 6 最悪 15,746 / 段 8 は self 込み 7,497)。実害に最も近いが最も重い。
- **択 4 — 取りやめ**: 現行 gate を維持する。逼迫 (残 2 bytes) は残るが複雑さを増やさない。

**併せて決める必要がある事項:** どの択でも「凍結」だと余白ゼロになる。
余白を認めるか (= 受理集合の意図的拡大を承認するか) を明示的に決める必要がある。
認めないなら、空きは陳腐化ルールの削除とテスト化で作る (T-127 裁定の方針)。

**動機の訂正:** 裁定 (109) が挙げた「T-314 を入れる余地を作る」は成立しない (B-03)。
T-313 の正当性は「予算が実態と別の量を縛っている」ことだけに依拠する。
