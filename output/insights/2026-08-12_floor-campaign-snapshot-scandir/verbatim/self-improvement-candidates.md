# 段 8 自己改善候補 (本 wave で実測したものだけ)

## 候補 1 — 変異は「揺れる木」を走査対象に広げてはならない (routing: failures または DW-M03)

**実測**: M10 (`_real_output_snapshot` の既定 root を `ROOT/"output"` → `ROOT`) は
2 走とも MISMATCH で、失敗 node 集合が **10 共通・1 入替**と非決定だった。
機序は「guard が `.git` や dispatch receipt を含む走行中に変化する木を走査し、
どの guard が落ちるかがレースで決まる」。**DW-M08 の完全一致要求を原理的に満たせない。**
安定した誤 root (`ROOT/"docs"`) へ分割した M10b は 1 走で KILLED・完全一致。

**行き先**: `DW-M03` (単一理由性) の既存節へ 1 文統合するのが筋。
「置換後の走査対象・入力集合が実行中に変化しうる変異は、失敗 node が非決定になるため
単一理由へ分割する」。**byte 予算次第。超過なら failures へ F として起票し、裁定へ返す。**

## 候補 2 — 単独計測の高速化率を並列環境へ一般化しない (routing: 既存 D104 の再発追記)

**実測**: `os.scandir` + 8 thread は login 単独で 5.79s → 1.43s (4.05 倍)、
競合の無い直列走行でも焦点 11 実行が 128.39s → 35.46s (3.6 倍)。
しかし **32 worker の並列走行では thread は guard を 1 秒も速くせず** (4 thread 15.3s vs
1 thread 15.4s)、**同時走行の critical path を 9.7s 飢えさせた** (39.34 → 48.9s)。

**行き先**: D104 決定 (4) 「性能施策の一次証拠を duration にしてはならない」の**同型再発**。
新しい D を作らず、既存 D104 へ「再発: 2026-08-12」を追記する形が routing 規則に合う。
本 wave では insights に凍結済み。**D 追記の可否は裁定へ返す** (親が既存 D を書き換えない)。

## 候補 3 — author 段の prompt に `## 総括` 見出しを要求し忘れた (routing: DW-O01 か本文)

**実測**: 段 5 の実装子は `codex_exit_code=0` で実装を完了したが、
`validator_rc=1` で不受理。理由は `^## 総括` 見出しの欠落で、**親の prompt が
author 段にその見出しを要求していなかった**。実装自体は採用できたので実害は小さいが、
子の成果物が機械的に捨てられる経路である。

**行き先**: `DW-O01` は既に「採用は `check_codex_output.py` の rc=0 (prompt は `## 総括` 必須)」と
**書いてある**。つまり契約の欠落ではなく**親の遵守漏れ**。→ **候補として記録するだけで
本文編集はしない** (実測のない仮想的懸念ではないが、正本は既に正しい)。

## 候補 4 — 背景待機と完了通知が実体と乖離する (routing: failures)

**実測**: `dev_wave_wait.py producer` を背景 Bash task で回すと、**producer 生存中に
待ち手だけが空出力 (0 byte) で終了する**事象が 5 度。さらに Monitor のイベントが
**実体と異なる進捗を報告**した (ledger が 4/12 のとき 5/12、7/12 のとき 8〜11)。
いずれも `.done` + 成果物 + producer 死の 3 点照合で検出し、待機を until ループへ
切り替えて回復した。**取りこぼしはゼロ。**

**行き先**: memory `background-task-notifications-can-be-fabricated` が既に正本で、
本 wave はその**再発実測**である。repo 側への新規起票は不要と判断する。
insights と worklog に実測を残した。
