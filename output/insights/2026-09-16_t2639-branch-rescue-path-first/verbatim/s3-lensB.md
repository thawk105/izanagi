## 親 brief の前提への反論

**P1 — 【real】一次資料優先は妥当だが、事実確認は留保が必要。**

「4 commit」と「3 件 indeterminate」は母数が違い、「3 commit」と単純に置換できません。archive 原本は許可対象外であり、brief の転記を独立検証できません（brief:71–74）。この不足から推測で対象を補わず、成功判定に使う実際の OID 集合を親へ要求すべきです。

**P2 — 【real】identity 索引の却下理由は強すぎる。ただし代案が優れる証拠もない。**

identity を検索キーにしても、最後に正式 schema・元 fragment の SHA・identity を検査するなら証拠条件は変わりません。ここは plan:371 の反論を支持します。

現行は既に SHA で索引し、その候補の identity を検査します（`landed:965–976`）。したがって、

- 最終条件を保つ identity 索引は、通常は新しい正例を増やさない。
- SHA が違う receipt を identity だけで受理するなら証拠条件を変える。
- re-home では wave と SHA が変わる実例があり、identity 索引だけでも解決しない（D922:19–24、`test_check_branch_landed.py:213–238`）。

**提示資料では、S2 より identity 索引が優れるとは判断しません。** 診断用の関連 receipt 検索として有用かは推測であり、実例なしに追加する必要はありません。

**P3 — 【refuted】121 倍を分布と扱わない親の留保は正しい。**

121 倍は 361 候補・1 path の参照部分だけです。候補列挙を含めると `(10.92+0.48)/(0.09+0.48) ≈ 20` 倍で、なお mode 再確認・他処理・rescue 全体を含みません（brief:42–49,131）。これを timeout 定数の倍率に流用してはいけません。

**不要な複雑化 — 【real】次は採らない。**

- 正例を増やす根拠のない identity 二重索引。
- 既に 1 process の `_find_object_any_path` の batch 化（`landed:767–773`）。
- 「decisive は常に一層」という新しい一般不変条件。D922 は証拠種別を限定しており、一層だけの選択を要求していません。plan:208–221,307–308 のためだけの状態管理・テストは縮小できます。
- 自動記帳 framework、新台帳、追加の削除許可 gate。今回の問題解決には既存証拠の伝達と運用上の引き渡しを先に整えるべきです。

batch 応答の解析、mode 再確認、危険な path の既存経路への退避は、変更の正しさに直接必要なので、この却下対象には含めません。
