read-only の測定。**実装は伴わない。** 次 wave の裁定材料として残す。

## 1. 全走 wall は何で決まっているか (main checkout、[T-128] 修正後)

`--durations=0` の 1 走から全 node の所要時間を集計し、3 つの制約を比べた。

| 制約 | 値 |
|---|---|
| work 総和 | 766.9 秒 |
| work / 並列度 32 | 24.0 秒 |
| 最長の単一 node (`..._uses_real_build_v2`) | 46.7 秒 |
| **直列 group `dev-waves-integration`** | **68.2 秒 / 78 node** |
| 直列 group `real-repo` | 0.1 秒 |
| **理論下限 (上記の最大)** | **68.2 秒** |
| 実測 wall | 69.31 / 70.90 / 71.22 秒 |

**実測は理論下限の 1.5〜4% 上にすぎず、スケジューリングの取りこぼしはほぼ無い。** 並列度を
上げる余地も無い (work を 32 で割ると 24 秒しかなく、コアは余っている)。

`real-repo` group は [T-117] の memo 化以降 0.1 秒まで縮んでおり、もはや制約ではない。

**帰結: 最長 node (46.7 秒) を短縮しても wall は 1 秒も動かない。** [T-128] の当初 scope を
引き継いだ [T-130] は、wall ではなく work 総和にしか効かない。

## 2. 前 wave のコメントにあった算数の食い違い

`test_dev_waves_integration.py` の冒頭コメント ([T-120] が書いたもの) は
「全走 wall の下限はこの group ではなく ungrouped の単一 node (実測 46〜58 秒) が決めており、
この group の直列和 (68〜70 秒) を割っても頭打ちになる」と述べていた。
**68〜70 > 46〜58 なので、当時から下限はこの group 側だった。**

[T-120] の A/B が「分割しても有意差なし」となった理由は、測定が **`-n 16`** で行われたためと
説明できる。分割後の work をその並列度で割ると元の直列和と同程度になり、差が埋もれる。
既定の並列度は現在 32 であり、結論が変わる。

| 条件 | wall | work 総和 | 当該 group の work |
|---|---|---|---|
| A: group あり・並列 32 | 70.30 / 69.99 秒 | 685.4 秒 | 67.3 秒 |

## 4. 分割で work が増える原因 = ストレージへの書き込みレイテンシ

当該 group の work は分割で 67.3 → 83.7 / 82.2 秒 (+24.4% / +22.2%、2 走で再現) に増える。
その内訳を node 別に見ると、**78 node のうち 75 node が一様に増加**していた。

- 増加の中央値 +0.23 秒、最大 +0.52 秒
- 増加率の分布: 下位 25% で +20%、中央 +29%、上位 25% で +35%

特定 node への集中がなく横並びで 3 割増える形は、重複したセットアップではなく競合の指紋である。
決め手は 2 つ。

**(a) 並列度を下げると消える。** 同じ分割でも並列度 8 では当該 group の work は 70.0 秒
(group ありの 67.3 秒に対し +4%)。node が重い仕事を重複して持つなら並列度に依存しない。

**(b) 置き場所を tmpfs に替えると消える。**

| 条件 | wall | work 総和 | 当該 group | group ありとの差 |
|---|---|---|---|---|
| 分割・`/home` (ext4、使用率 92%) | 61.06 秒 | 676.2 秒 | 82.2 秒 | **+22.2%** |
| 分割・`/dev/shm` (tmpfs) | **54.11 秒** | **568.3 秒** | 68.6 秒 | **+2.0%** |

tmpfs では全体の work も 685.4 → 568.3 秒 (**−17.1%**) に落ちる。影響は当該 group に限らない。

**帯域でも CPU でもなく待ちである。** 同時記録した vmstat の平均値:

| | `/home` | `/dev/shm` |
|---|---|---|
| CPU user | 11.8% | 13.4% |
| CPU system | 2.5% | 2.4% |
| CPU idle | **85.1%** | 84.1% |
| iowait | 0.7% | 0.0% |
| block out (/秒) | 103,901 | 13,060 |
| run queue | 12.7 | 15.1 |

96 コアのうち実質 11〜13 コア相当しか使っておらず、iowait も 1% 未満。**空いているのに遅い**のは、
git が commit や index 更新のたびに行う同期書き込みの往復が件数で効いているためと解釈できる。
各 node は temp git repo に対して subprocess で git を多用する。ext4 の使用率 92% も
空きブロック探索を重くする側に働く。

**この解釈からの予測 (未実証)**: テスト用 temp repo に耐久性は不要なので、
`core.fsync=none` 相当を渡せばメモリを消費せず同じ効果が得られるはず。テストが
`GIT_*` を除去するため外から環境変数では効かず、実装が要る。

## 5. work の偏り — 遅いのはスイート全体ではない

tmpfs・分割・並列 32 の走 (work 568.3 秒 / 1179 node) を分解した。

| | work | 占有 |
|---|---|---|
| 上位 20 node | 344.8 秒 | **61%** |
| 上位 50 node | 395.3 秒 | 70% |
| 0.1 秒未満の 782 node (全体の 66%) | 22.4 秒 | 4% |

| ファイル | work | 占有 | node |
|---|---|---|---|
| `test_s8b_oracle_driver.py` | 295.4 秒 | **52.0%** | 75 |
| `test_s8b_floor_campaign.py` | 71.3 秒 | 12.5% | 76 |
| `test_dev_waves_integration.py` | 68.6 秒 | 12.1% | 78 |
| `test_s8b_ratified_verify.py` | 67.7 秒 | 11.9% | 85 |
| 残り 52 ファイル | 19.6 秒 | 3.4% | — |

**単体テストとしての本体は健全である。** 3 分の 2 の node は 0.1 秒未満で合計 22 秒。
重いのは実 git repo を作り実 build を通す E2E 20 本だけである。

`test_s8b_oracle_driver.py` の 295.4 秒のうち、T-080 E2E の 8 node が約 200 秒 (全 work の 35%)
を占める。[T-128] で fixture 構築を 121.7 → 22.1 秒へ削ったが、**共有は 1 プロセス内だけ**なので、
並列実行で 8 node が別 worker に散ると同じ base repo を 8 回組み直している。

## 6. 残る改善余地 (効果順、いずれも「検証を減らす」方向ではない)

| # | 施策 | 効果 | 検出力への影響 |
|---|---|---|---|
| 1 | T-080 E2E の base fixture を worker 間で共有する (ディスク共有 + flock) | work −170 秒 (推定、全体の 30%) | なし (base は read-only、各 node へは実体コピー) |
| 2 | 実 build のキャッシュ (最長 node 46.7 秒 + canary 60 秒) | work −107 秒 (上限)。**wall を 47 秒より下げる唯一の道** | 要裁定 (「実 build を通す」control の意味) |

| 4 | `dev-waves-integration` の group 分割 | wall −10 秒 (実測) | なし ([T-120] の棄却を上書きする裁定が要る) |

触らなければ 47 秒、触れば 30 秒台が見込める (いずれも推定)。

安全な順序は 1 → 3 → 4 (検出力に触れない)。2 と、tmpfs を既定にする案は裁定を要する。
