## 1. なぜ全 6 permutation・18 block なのか

依頼は「腕と job 内時刻の交絡を避ける巡回 block 設計」だった。**開始位置だけを回す循環 3 通りでは
足りない。** driver は `workload → threads → cell` の順に回すので腕が最内であり、位置効果は
循環でも消えるが、**一次持越し (直前にどの腕が走ったか) が消えない。**

親が数えて確認した:

| 設計 | 有向遷移の出現回数 |
|---|---|
| 循環 3 通り × 4 (n=12) | `p0→p1` / `p1→p2` / `p2→p0` が各 284 回、**逆向き 3 通りは 0 回** |
| 全 6 permutation × 3 (n=18) | 6 通りが各 213 回、各腕が各位置に各 6 回 |

driver は washout を置かないので、この均衡が持越しへの唯一の防護である。

**反復数は検出力から決めた。** 標準偏差の想定には 2 つの参照級がある — 同じ量・別の腕
(T-2187 の CI 幅 ±1.0〜1.4% が含意する 0.0108〜0.0151) と、同じ腕・別の量 (ITT の窓単位 0.032)。
親が 20 万試行の模擬で出した表:

| SD | n=12 の等価判定力 | n=18 | n=24 | n=18 の 80% 最小検出優越 |
|---:|---:|---:|---:|---:|
| 0.013 | 100% | 100% | 100% | 3.94% |
| 0.032 | 66.2% | 91.5% | 98.2% | 5.33% |

悲観側でも 91.5% になる n=18 を採った。df=17、t_{0.975,17}=2.1098156 (親が純 Python の t 分布で
算出し、df=5/6/11 の既知値で検証)。

## 4. read-heavyの等価予測に反した結果と、機序解釈の限界

**事前登録はread-heavyでの等価を予測したが、記録値には大きな差があった**
(42 threadsで+190%、48 threadsで+185%)。
全24点の最大は balanced・30 threads の +249% である (2026-09-10 回収時の表との照合で訂正)。

予測はabortが少ないという想定を根拠にしていた。しかし既存JSONのread-heavyのabort率は、
p0で1.91〜15.40%、p1で1.36〜5.56%、p2で1.57〜12.23%であり、無abort域ではない。
したがって「無abort条件でも向きが効く」という機序の反証にはしない。棄却されたのは、
事前登録したread-heavy 8点の等価という操作的予測である。
反転腕のclamp領域への移動はITTの生死確認と整合する機序候補だが、今回のthroughputだけでは同定しない。

**事前登録した負の対照が、その役割を果たした。** 結果を見てから予測を書いていたら、
この誤りは記録に残らなかった。

最大の差+249%はbalanced・30 threadsでのp0/p1の観測である。
本18 blockの各条件では常時反転p1のthroughputがp0を下回ったが、最適性や他条件への一般化は主張しない。

## 5. 事前登録 v1 の誤り 2 件と正誤表

**測定が完走した直後、解析を当てた 1 回目が構造検査で拒否した。** 逐語は
`artifact-invalid: source bytes differ between policy arms`。
**この時点で throughput の値は 1 つも観測していない。**

原因は事前登録 v1 §3.2 の identity 要求 2 件が**原理的に成立しえない**ことだった。

| 腕 | source | genome | binary | build_cache_key |
|---|---:|---:|---:|---:|
| p0 | 1 種 | 1 種 | **18 種** | **18 種** |
| p1 | 1 種 | 1 種 | **18 種** | **18 種** |
| p2 | 18 種 | 18 種 | 18 種 | 18 種 |

1. 「腕をまたいで source bytes 一致」— step policy は patch C による source 置換なので不可能。
   v1 自身の §2 が「seed は p2 の genome と binary を変える」と書いており矛盾していた。
2. 「block 間で p0/p1 の binary identity 一定」— build は job 固有の `$TMPDIR` で行うので
   byte 再現的でない。source と genome は完全に一定だが binary は 18 通り異なる。

**bytes を束縛にしたのが誤りで、束縛すべきは意味である。** 正誤表 1 で identity 述語だけを訂正し、
v1 の bytes は変えていない (18 成果物が v1 の sha256 を束縛として記録しているため)。
**推定量・等価域・臨界値・判定語・仮説・層・欠測規則・seed・巡回・block 数は 1 文字も変えていない。**

弱めた 2 件はどちらも成立しえず実質の保護が無かった。代わりに
**「3 腕の source・genome・binary は互いに異なる (define が inert でない)」**という
v1 に無い正の対照を足した。この方向では訂正後のほうが強い。

**この訂正が結果を見た後の後付けでないことを保証するのは Git 履歴と正誤表 §0 の記述だけである。**
repo 内の検査は、gate と検査を同じ主体が変更できる限り、意図的な弱体化への完全な防壁ではない。

## 6. 検出した欠陥 — 計 19 件、棄却ゼロ

| 経路 | 件数 | 代表 |
|---|---:|---|
| 親の実走 | 6 | 新契約発火時に汎用 seed 検査を飛ばす分岐 (受理集合の弱体化) |
| 敵対レビュー 2 本 | 9 | **producer が build 証拠を出さず、正常な成果物が 1 件も解析へ入らない** |
| 実投入 | 2 | qsub の返答を job ID として読めず、投入済み job が孤児になる |
| 解析の 1 回目 | 2 | 事前登録 v1 の identity 要求が成立しえない (§5) |

**最も重いのは敵対レビューの 1 件目で、2 レンズが独立に指摘した。** driver が性能行へ
`build_trace_enabled` / build cache key / 受領証 / source evidence を出しておらず、解析は
それらを必須にしていた。**解析のテスト fixture が手作りでその 4 項目を足していたため隠れていた。**
18 block を投入する前に見つかった。

**実投入の 2 件はテストでも変異でも捕まらなかった。** どちらも scheduler の実挙動に依存し、
偽 qsub を使う負例が無かったためである。1 件目は実際に孤児 job (`982971.nqsv`) を作り、
親が `qstat` で見つけて `qdel` した。今回その負例を足した。

**fixture の甘さが 2 度、実物との差を隠した。** 1 度目は build 証拠、2 度目は腕ごとの source hash。
どちらも「実 producer の出力をそのまま解析へ通す」テストで閉じた。
