## ユーザーへ返す択一 ([T-1283] 再裁定)

**問い: 受入の主経路 (child-green、実測 22/23) が wave tip の自己証明であることを、どう扱うか。**

- **(a) β を採る** — 待ち手と runner の main==tip 等値を両経路で要求する。穴は Git 由来の検査で
  確実に閉じる。**代償 = `tools/dev_wave_wait.py` と `tools/run_tests.py` を編集した wave は
  どの経路でも land できなくなる。** 待ち手は 2026-08-10 以降 24 commit (non-merge 21、
  main first-parent 12) と最も改修頻度が高いので、この 2 file の改修は「先に空の wave で
  gate を外して land し、次の wave で直す」二段運用になる。[T-1195] と D403 が却下した代償を
  今度は受け入れる、という裁定になる。
- **(b) 候補外の trusted launcher を新設する** — 受入の権威 (待ち手・runner の選択と起動) を
  wave tip の外へ出す。穴を閉じつつ恒久 land 不能も作らない。**代償 = 新機構であり、
  [T-1131]・D487 の延長ではない。設計と実装で 1 wave 以上を要する。**
- **(c) γ を「協調的 drift 防御」としてだけ採る** — 実装は軽いが、名指しの穴は閉じない。
  **条件 = 「閉じた」と記録せず、[T-696] の受容済み残余として failures 台帳へ残す。**
- **(d) [T-1195] の裁定へ戻す** — 現状維持。**条件 = 同じく「閉じた」と記録せず failures 台帳へ
  登録し [T-696] に束ねる** (これは [T-1195] が既に課した条件であり、**未執行のまま**である)。

**親の推奨 = (d) + [T-696] への束ね直し、次点で (b)。**
理由: (a) は最も改修頻度の高い file の改修導線を恒久的に二段化する費用が、閉じる穴の実害
(内部作業者が自分を欺く経路。[T-696] で既に協調境界として受容済み) に見合わない。
(b) は正しい方向だが「粗い provenance で足りる」という既定方針の下では優先度が低く、
CC 自動合成という主目的から遠い。(c) は実装費用の割に得るものが drift 防御だけで、
A-01 の指摘どおり「閉じた」と誤読される危険がある。(d) なら [T-1195] が課した未執行の
記録条件を果たすだけで、台帳の整合が回復する。

**なお (a)〜(d) のいずれを選んでも、runner の child-green 穴 (A-03) は同じ裁定に含める必要がある。**
