必ず次を含めること。

1. **診断保存の設計。** `_run_case` (orchestrator/tests/test_codex_worker_launch.py:421) が返す
   `completed` の returncode が期待外のとき、receipt の
   `attempts[*].limit_trigger` / `evidence_status` / `metering_status` /
   `process_group_residual` / `termination_verified` / `wall_clock_s` と、
   attempt の stdout/stderr ファイルの中身 (パスは receipt の `stdout_path` / `stderr_path`) を
   assert message へ載せる。どの関数をどう変えるか、call site が何箇所あり (現状 `_run_case` の
   呼び出し元を列挙せよ)、既存の assert 文をどう書き換えるかを file:line で示せ。
   receipt が存在しない場合・壊れている場合の扱いも決めよ。
2. **どの call site の予算を広げ、どれを据え置くか。** 予算そのものを検査しているテストを
   file:line で列挙し (`max_wall` の explicit 値、`--evidence-grace-s`、`--termination-grace-s`、
   `stop_reason` / `limit_trigger` / `evidence_status` を期待している assert)、
   それ以外を「広げてよい集合」として列挙せよ。広げる値は根拠つきで提案し、
   `subprocess.run(..., timeout=10)` との整合 (予算が harness の timeout を超えると
   失敗モードが変わる) を必ず論じよ。
3. **恒真でないことの固定。** 診断が実際に発火することを示す meta-test の設計。
   どの入力で診断経路へ入り、何を assert するか。テストを甘くして緑にする案は却下すること。
4. **波及の静的列挙。** 変更が触る fixture・helper の他 test file からの利用、
   同 dir の conftest への影響を列挙せよ。
