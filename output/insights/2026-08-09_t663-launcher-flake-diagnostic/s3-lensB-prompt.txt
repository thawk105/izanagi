## レンズ B = 実効性 (次の再発で本当に原因が分かるか)

次を重点的に攻撃せよ。

1. **既往の失敗 node を全部カバーできるか。** F57 台帳に実名で載っている再発 node
   (`test_check_receipt_recomputes_usage_actuals_from_sealed_artifacts`、
   `test_manifest_is_appended_while_correlated_session_is_running`、
   `test_all_repo_policy_reasoning_values_are_accepted[high]`、
   `test_check_receipt_detects_executable_identity_change`、
   `test_check_receipt_rejects_impossible_truth_table`) を実ファイルで引き、
   プランの結線でそれぞれが診断経路に載るかを 1 件ずつ照合せよ。載らないものがあれば挙げよ。
2. **診断が人間に届くか。** 受入全走は `tools/run_tests.py` 経由で pytest-xdist 並列、
   さらに計算ノードへ dispatch され stdout が親へ中継される。assert message が
   (a) xdist worker から親へ、(b) pytest の短縮表示 (`-q`、`--tb` 既定)、
   (c) dispatch 中継、のどこかで切り詰められないかを実ファイルで確認せよ。
   attempt の stdout/stderr **全文**を載せる設計は、正常系の巨大出力
   (fake の valid_output は約 2,000 文字) を考えると読めなくなる可能性がある。
   上限つき抜粋にすべきか、根拠を添えて論じよ。
3. **33 call site の機械的書き換え。** プランは全 call site へ期待 rc を渡し、
   既存の rc assert を削除する。この一括書き換えで
   (a) 期待 rc の取り違え、(b) 既存 assert の削除しすぎ (rc 以外の assert まで消す)、
   (c) parametrize 展開で期待 rc が変わる node、が起きうる箇所を実ファイルで指摘せよ。
4. **診断が「7 択のどれか」を本当に一意に決めるか。** production の `accepted` は
   7 条件の積である。プランが載せる 6 field で 7 条件すべてを区別できるか、
   実装を読んで対応表を作れ。区別できない条件があれば、追加で載せるべき field を挙げよ。
5. **フレークが消えたことをどう確認するのか。** 本 wave の変更後、
   「フレークが直った」と主張できる証拠は何か。受入全走 1 回の緑では足りない。
   親が取るべき最小の証拠を提案せよ。逆に、証拠が原理的に得られないなら
   「得られない」と明記し、記録すべき正直な表現を提案せよ。
6. **親 brief の攻撃。** brief の provisional 裁定 (P1) production 無編集で足りる、
   (P2) 主が診断保存で従が余裕拡大、(P3) T-190 を本 wave で閉じる、の 3 点それぞれに
   反例または反論を試みよ。特に (P3) は、原因が分離できるようにしただけで
   「原因分離した」とは言えないのではないか。
