## 直すもの (親が real と裁定した must-fix。すべて対応すること)

- **F0 (親の実測)**: `test_final_drain_actuals_are_rechecked_before_acceptance` の
  `assert not _paths["output"].exists()` が `NameError`。束縛名は `paths`。
  **期待値は変えず**、名前だけ直す。
- **F1 (C1)**: wiring meta-test `test_launcher_failure_diagnostic_is_wired_to_the_returncode_assertion`
  が `_assert_launcher_returncode` を直接呼ぶだけで実 call site を通っていない。
  `_run_case` 経由、direct `Popen` 経由、in-process 経由の**それぞれ**で意図的な rc 不一致を
  起こし、sentinel formatter の出力が捕捉した専用例外の `str(exc)` に入ることを固定せよ。
- **F9 (親が probe で決定的に再現。最重要)**: **実際の launcher を走らせる meta-test が、
  その launcher の rc が特定の値になることに依存してはならない。**
  親は既定 wall 予算を 0.30 秒へ縮める probe を行い、`_run_case(..., expected_returncode=1)` を
  `pytest.raises` で包む書き方が `Failed: DID NOT RAISE LauncherReturncodeMismatch` で
  落ちることを確認した (計 23 failed / 56 passed)。これは**フレークを観測するための計装が、
  観測したいフレークそのもので壊れる**設計である。
  規則: 実 launcher を走らせて診断経路を発火させる meta-test は、
  **起こりえない期待 rc (例: 99) を渡して不一致を必ず成立させる**こと。
  そのうえで、assert は「実 rc の literal」を焼き込まず、
  注入した障害が保証する内容 (例: `metering_status=missing`, `codex_exit_code=7`) と
  メッセージの構造 (先頭行の形、末尾 `truth_summary:` の再掲) を検査せよ。
  先頭行の rc 値を検査したい場合は、その走行で観測した実 rc から期待文字列を組み立てること。
  この規則を、実 launcher を走らせる**すべての** meta-test へ適用せよ。
- **F2 (C2/D3)**: 診断が `json.loads` と緩い型検査だけで真理値行を出している。
  production 相当の strict JSON load と receipt schema/semantic 検証を通過した receipt に**限って**
  `failed_predicates` を出すこと。通過しない場合は `receipt_status=invalid:<理由>` と
  上限つき raw 抜粋だけを出し、真理値を断定しない。
  meta-test に「完全な JSON だが field 欠落」「duplicate key」「型違い」「非有限値」を追加せよ。
- **F3 (C3)**: stream 読み込みが regular file 検査なしで blocking open している。
  FIFO・symlink・非 regular file は `lstat`/`fstat` で即 `unreadable` とし、
  診断 I/O に明示的な byte 上限を設けよ。FIFO を指す receipt を使った meta-test を追加し、
  **一次の `actual rc != expected rc` 行が必ず残る**ことを固定せよ。
- **F4 (C4)**: receipt の上限を production の 16 MiB に合わせよ。
  末尾要約が先頭 8 attempt しか出さない点も直し、**最後の決定的な attempt の
  compact predicate 行を 16 KiB 予算内へ優先的に確保**せよ。
  9 attempt 超と大きい valid receipt の meta-test を追加せよ。
- **F5 (D1)**: `test_manifest_is_appended_while_correlated_session_is_running` は
  manifest 待機の assert が先にあり、launcher が早期に rc≠0 で終わると診断へ到達しない。
  待機中に `process.poll()` を確認し、終了済みなら manifest assert より**前に**
  診断付きの rc 判定を通せ。**既存の manifest 期待値は変えないこと。**
- **F6 (D2)**: production の `accepted` は `not force_not_accepted` を含むが、
  対応する receipt field は存在しない。可視 field がすべて成立しているのに
  `accepted` が偽の場合は、でっち上げの predicate を出さず
  `unrecorded_acceptance_guard` と明示せよ。さらに**複数の conjunct が同時に落ちる fixture**を
  追加し、`failed_predicates` が全件を列挙する (最初の 1 件で return しない) ことを固定せよ。
- **F7 (D4、scope 内の分だけ)**: 1 件の診断から「負荷か実障害か」を判別する材料を足せ。
  `hostname`、環境変数 `PYTEST_XDIST_WORKER` と `PBS_JOBID` (不在なら明示)、
  テスト process の PID、`os.getloadavg()`、receipt の `limits` と `actuals` 全体、
  および launcher へ渡した予算 (wall/evidence/termination/poll) の実値。
  **cgroup や pressure の収集は scope 外なのでやらないこと。**
- **F8 (D7)**: 検証を通っていない receipt に対して `failed_predicates` や
  「不成立だったゲート」という断定的表現を使わない。その場合は
  `observability_status=insufficient` を出すこと。
