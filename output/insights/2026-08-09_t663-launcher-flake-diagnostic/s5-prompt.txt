## やること

段 4 裁定「プラン v2」に従う。要点を再掲する。

1. **R6: 時間予算を一切変えない。** `max_wall` の既定 `"3"`、`--evidence-grace-s 1.0`、
   `--termination-grace-s 0.05`、`--poll-interval-s 0.01`、`subprocess.run(..., timeout=10)` を
   すべて現行値のまま据え置く。段 2 プランの第 2 節は**実装しない**。
2. **R1: 受理 conjunct の真理値行を診断へ出す。** attempt ごとに `accepted`, `limit_trigger`,
   `evidence_status`, `metering_status`, `codex_exit_code`, `validator_rc`,
   `process_group_residual`, `termination_verified`, `wall_clock_s`。
   receipt 全体の `outcome`, `stop_reason`, `launcher_rc` も添える。
   `accepted` が偽の attempt については、偽になった conjunct を `failed_predicates=[...]` として
   列挙する (複数可)。「原因」と書かず「不成立だったゲート」と書くこと。
3. **R2: 上限つき・非マスク。** stream は byte 上限つき head+tail 抜粋、
   `errors="backslashreplace"`、総 byte 数・sha256・切詰め byte 数・path を併記。
   総 message は 16 KiB 以下に収める。`actual rc != expected rc` の 1 行を**先頭**に置き、
   真理値行の短い要約を**末尾にも**繰り返す (受入全走は dispatch 経由で失敗ログの末尾
   64 KiB しか中継されないため)。診断生成中の例外は握りつぶさず
   `diagnostic_status=failed:<例外型>` として同じ例外メッセージ内へ畳むこと。
   **どんな場合でも元の rc 不一致の情報を失わせないこと。**
4. **R3: 恒真にしない。** 専用例外 `LauncherReturncodeMismatch(AssertionError)` を定義し、
   rc 不一致はこれを送出する。meta-test は `pytest.raises(LauncherReturncodeMismatch)` で
   捕捉した `str(exc)` だけを検査する。formatter を sentinel へ差し替えて
   「rc assert が本当にこの formatter を通っている」ことを固定する wiring test を別に置く。
   `assert all(...)` や真偽値になる文字列の存在確認だけで通る書き方をしないこと。
5. **R4: 機械置換の境界を守る。** 置換対象は launcher 実行の `completed.returncode` に対する
   assert のみ。`check-receipt` (checker) の rc assert、`receipt["launcher_rc"]` など
   receipt 内部の assert は**削除しない**。期待 rc が unordered `[0, 2]` の箇所
   (現行 `:1110` 付近) は単一期待 rc の helper へ機械置換せず、2 process をラベル付きで
   扱う別経路にすること。
6. **R5: 3 形態を同じ診断契約へ載せる。** `subprocess.run` の `CompletedProcess`、
   direct `Popen` (現行 `:1535` 付近ほか)、in-process (`_run_main_in_process`)、および
   `subprocess.TimeoutExpired`。in-process は stream を持たないので「stream 不在」を
   明示して receipt 行だけ出す。
