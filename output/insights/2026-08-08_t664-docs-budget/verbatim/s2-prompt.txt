## 出力形式 (Markdown。この見出しをそのまま使う)

### §0 読了確認
読んだファイルと、読めなかったものを列挙する。

### §1 L2 集合の同定
(P-L2) の検証結果。dispatcher の表の行を引用し、各節が L0 / L1 / L2 のどれかを表にする。
誤りがあれば訂正し、訂正後の L2 集合と合計 bytes を出す。

### §2 経路 A — 削除候補の棚卸し
**L2 の全節について 1 行ずつ**、次の列で表にする。判定は「候補 / 不採」の 2 値。

| 節 | bytes | (ii) 発火実績 (検索語と hit) | (iii) 機械代替 (path + テスト nodeid、無ければ「なし」) | 判定 | 理由 |

候補になった節だけ、後段で詳述する: 削除したとき**失われる義務**は何か、それを代替する機械検査が
どの入力のどの field を読み何を赤にするか、代替が恒真でない証拠、残余リスク。

### §3 経路 B — テスト化候補の棚卸し
prose 義務のうち機械検査へ移せるものを列挙する。**節 ID と file:line を必ず書く。**

| # | 対象 (節・file:line) | 現在の prose 義務 | 検査の設計 (読む実成果物と field) | 赤にする具体入力 | 既存被覆との差 (純増検出力) | 移管後に削れる bytes (実測/推定) | 実装コスト | 既裁定との重複 |

**移管後に削れる bytes が 0 の候補も、検出力が純増するなら残してよい** (その場合「予算解放 0」と明記)。
逆に、検査を新設しても prose を削れないもの (義務の文言そのものが読者への指示であるもの) は、
その旨を書いて予算候補から外す。

### §4 dispatcher (L0) の削減候補
`.claude/commands/dev-wave.md` は常時全文読了なので 1 byte の削減効果が reference より大きい。
**既存 reference 節へ意味等価に統合できる行**だけを候補にする (新規ファイルは不可)。
統合先の節 ID・統合後の文面案・削減 bytes・意味が変わらない根拠を書く。
統合できないもの (dispatch 自体を成立させる命令) は候補にしない。

### §5 既裁定との関係
[T-127] / [T-313] / [T-328] / [T-412] / [T-454] / D94 / D110 / D186 のそれぞれについて、
本棚卸しの候補が「同一 / 部分重複 / 独立」のどれかを表にする。
とくに **[T-313] (byte 予算を常時読量 gate へ置換、裁定済み・実装待ち) が実装された場合に
価値を失う候補**を明示せよ。
