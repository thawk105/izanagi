# 較正の世代交代と凍結の世代交代 — 一体再設計の設計パッケージ

由来: ユーザー裁定 2026-08-10 §54「[T-657] = A。較正 + 凍結の世代交代を一体再設計として
起票し直す。B (検出層の除去) 不採用、C (v2 chain 正式発効) は再設計内で扱う」。

**本パッケージは設計を決めていない。択一をユーザー裁定へ返すための材料である。**
実装は含まない。§10 が裁定してほしいことである。

## 1. なぜ「較正」と「凍結」を一体で設計するのか

pegasus の計測環境契約を第 2 世代へ進めようとした旧 wave は、**どちらを選んでも壊れる**という
構造に突き当たった。原因は 3 つの要求が同時に成立しないことである。

- **(式 1) live admission の一致要求** — 現在有効な floor protocol が焼き込んでいる契約 hash と、
  現在有効な環境契約の hash が一致すること。protocol builder は呼び出し時点の current 契約から
  hash を焼くため、環境を第 2 世代にすると既存 protocol は current と食い違う。
- **(式 2) 凍結の履歴不変条件** — 凍結成果物の各 path について
  「∀C ∈ rev-list(HEAD): entry(C, path) ∈ {absent, HEAD の oid}」。
  実装コメントは目的を「削除 → 別 bytes 再作成の遮断」と明記する。
  **同一 path への上書き再発行は原理的にこれを破る。**
- **(式 3) 盲検封印の紐付け** — selector の予測を封印した時点の floor protocol blob と、
  現在の floor protocol が一致すること。floor を作り直すと campaign launch が拒否される。
  これは事前登録性を守る正しい挙動である。

環境だけを進めると式 1 が壊れ、固定 path の floor を更新すると式 2 と式 3 が壊れる。
**較正の世代交代は、凍結の世代交代なしには完了しない。** これが一体設計を要する理由である。

## 2. 用語 — 「世代」を 3 つに分ける

設計で「generation」と略さない。3 つは独立に動く。

| 名前 | 実体 | 現在値 |
|---|---|---|
| 環境活性化 serial | activation record の `activation_serial` | 1 |
| 環境世代 | activation record の `active_contracts[].generation` | pegasus / linux-baremetal とも 1 |
| 凍結世代 | ratified freeze の `generation_number` | **未発効** (v2 chain の record が存在しない) |

今回の一体遷移は「環境活性化 1→2 / pegasus 環境世代 1→2 / 凍結 legacy→第 1 世代」である。
**環境世代 2 と凍結世代 1 は矛盾しない。** 番号が揃う必要はない。

## 3. 実在 field 台帳

**設計の入力にしてよいのは、実成果物に実在する field だけである。** 以下は親が 2026-08-10 に
実物を開いて確認した。段 2 のプランは 3 箇所で実在しない field を入力にしており、訂正した。

| 識別子 | 実在するか | 実在場所 |
|---|---|---|
| 環境活性化 serial / state hash | 実在 | activation record の `activation_serial`, `activation_state_sha256` |
| 有効契約の一覧 | 実在 | 同 `active_contracts[]` = `{contract_sha256, env_tag, generation}` の配列 |
| floor protocol の契約 hash | 実在 | `floor_protocol.json` の `contract_sha256` |
| 予測の同一性 | 実在 | `selector_predictions.json` の `pre_oracle_head`, `selector_basis_sha256`, `body_sha256` |
| 予測ファイル全体の hash | 実在するが**文書内 field ではない** | 凍結 manifest 側の pin として存在する |
| 較正 artifact の raw hash | **文書内には無い** | 較正 JSON の top-level は 14 key で、`raw_sha256` も `artifact_sha256` も持たない。hash は環境契約側の `calibration_ref.sha256` と、実ファイルを再計算する検証器にある |
| 凍結世代 record / 承認 record / active pointer / tombstone | **schema だけ存在し、現物は無い** | 実装は揃っているが、`output/s8b-freeze/` に record が 1 つも無い |
| 凍結世代の契約 hash | **同名 field は無い** | 世代 record の `floor_protocol.{path, sha256}` から protocol を読み、その `contract_sha256` を使う |

| campaign claim の識別子 | protocol hash は**先頭 8 桁のみ** | 本設計の入力にしない |

**この台帳に無い field を設計の入力にしてはならない。** 実装者が自己申告 field を発明する余地を
残さないため、新設する field は「新規出力」と明記して区別する。

## 4. 既にあるもの / 足りないもの

「検証機構が実装されている」ことと「今すぐ使える成果物がある」ことは別である。混同すると、
ユーザーが実装済みと新設を読み違える。

| 面 | 検証機構 | 使える成果物 | 足りないもの |
|---|---|---|---|
| 環境 | 世代 registry、後継述語、serial / state hash の連鎖、current 権限付与 — **実装済み** | activation record 1 が有効 | 「登録済みだが一度も有効化されていない」世代を、floor 候補にだけ使える型付き権限 |
| 凍結 | 世代 path、`supersedes_sha256`、承認 record、active pointer、失効 / 取消 — **実装済み** | **無い** (v2 chain 未発効) | 現物の record 一式、環境と凍結を束ねる head、世代スコープの封印束縛 |
| protocol | 世代 record 側は `{path, sha256}` を読める | 固定 path の protocol 1 本 | producer・floor 事前検査・予測 runner・certified admission の versioned path 対応 |
| 盲検封印 | `selector_basis_sha256` の算出は実装済み | 封印済みの予測 1 本 | 旧 protocol の由来と新世代 protocol を分離して束縛する record と検証器 |
| 一体化 | **無い** | — | 一度の HEAD 取得から環境と凍結の両権限を解決する resolver |

`freeze-permanent-design.md` が描く transition receipt と active-bundle pointer は**将来設計**であり、
現行実装の既成機能として数えない。

## 5. 「新しい path で発行すれば両立する」は必要条件だが十分ではない

親の当初仮説は「凍結世代を**新しい path** の record として発行すれば、履歴不変条件は path ごとなので
両立する」だった。これは**必要条件としては正しい**。新 path はその path 自身について過去に
別 bytes を持たないため、式 2 と両立する。既存実装も世代ごとに別 path を定義している。

しかし十分ではない。段 3 の敵対レビューと親の実測で、次の反例が確定した。

1. 世代 record を新 path にしても、その record の `floor_protocol.path` が**旧の固定 path を指し**、
   そこを更新すれば同じ `history-mutated` が出る。
2. protocol 自体を新 path にしても、**floor campaign・予測 runner・certified admission は
   固定 path をハードコードしている。**
3. 新しい protocol file は floor 事前検査の既知集合に属さず、現状では「未知の file」として拒否される。
4. launch certificate は凍結世代 1 専用であり、2 以上は `certificate-generation-scope` で拒否される。
5. **承認 record と active pointer は「同一 commit で、その 2 ファイルの追加だけ」であることを
   要求する。** 親が実装を読んで確認した。したがって環境の activation record を同じ commit へ
   足す既成経路は無い。しかも承認 commit は世代導入 commit と別でなければならない。
6. 登録済みだが一度も有効化されていない世代は、歴史 resolver から候補として引けない。
7. 現行の凍結世代 schema には、世代スコープの封印束縛 field が無い。

**帰結:** 一体設計は「新 path にする」だけでは終わらない。固定 path を前提にした consumer 群の
移行と、承認 commit の形状 (topology) の再設計が本体である。

## 6. 盲検封印をどう世代へ追随させるか — 保証境界を先に決める

`selector_predictions.json` は事前登録の中核である。floor が世代交代したとき、この封印をどう扱うか。

### S1 — 予測を byte 単位でそのまま再利用し、世代束縛だけを新設する

selector の入力 payload は descriptor と固定の候補集合だけで、floor protocol・契約・較正・
floor の実測結果を入力に含まない。したがって予測は floor の世代と論理的に独立であり、
**再生成せずに再利用できる**。新設するのは「この予測をこの凍結世代へ適用してよい」という
束縛 record と、その決定的な検証器である。

検証器は自己申告の真偽値を持たず、次を再導出する。

- 予測の raw bytes が旧封印から 1 byte も変わっていない。
- 全行の選択 ID・入力 payload hash・raw hash・束縛 entry hash が旧封印と同一。
- `selector_basis_sha256` が同一。
- 新旧の環境契約の差分が較正参照の path と hash の対だけ。
- 新旧の floor protocol の差分が `contract_sha256` だけ。
- 新 protocol の契約 hash が、活性化候補の pegasus 契約 hash と一致。

### S1 が保証しないこと (ここが裁定の要点)

**S1 は「予測を改変していない」ことを証明するが、「結果を見る前に選んだ」ことは証明しない。**
段 3 のレンズ A が具体的な破れ方を構成した。

1. 未登録 clone・別 `out_root`・計算ノードの scratch のいずれかで新世代の floor を先に実走し、
   結果を目視する。
2. 結果はまだ canonical path にも Git にも入れない。
3. 良い結果なら束縛 record を commit し、悪ければ束縛を作らず中止する。
4. 後から結果を導入する。

束縛 commit が結果導入より前という時系列検査は通り、予測の bytes も一致し、差分も限定されている。
それでも**可変の選択は「この予測を新世代に適用するかどうか」に移っており、結果を見た後に
行われている。** 規律 3 (正しさシグナルを後付けにしない) の観点でも、束縛の採否が
後付けの信号になる。

Git の commit 順序は実時間順を保証しない、と現行の検証器自身がコメントしている。

### S2 — 新しい世代用の封印を作り直す

新世代の floor を実走する前に、新しい予測を封印する。事前登録をやり直す形になる。
**新世代の floor 結果が 1 つでも実在または観測済みなら、盲検の保証は担保できない**ため、
その時点で停止してユーザー裁定へ戻す。

### 保証境界の 3 択

S1 を採る場合、主張できる保証をどこまでに狭めるかを決める必要がある。

- **(G-a) 受理順だけを保証する** — 「公式に受理される結果は、束縛 record より後に導入されたものに限る」。
  実装可能。外部での先行実走と目視は排除しない。
- **(G-b) 外部非観測まで要求する** — 実走の開始を束縛 hash 入りの投入 receipt と claim で必須化し、
  受理する結果を「束縛後に開始された実走」に限る。実装規模が増え、それでも別ノードでの
  非公式実走は排除しきれない。
- **(G-c) 信頼境界を人へ移す** — 盲検性は外部の保管者または宣言に委ね、機械は改変不能性だけを保証すると
  明記する。

## 7. 択一 — 共通軸で比較する

| 軸 | R1 一体 head を先に作る | R2 停止窓で順に適用する | R3 将来の恒久機構へ合流する |
|---|---|---|---|
| 概要 | 現状を指す休眠 pointer を先に導入し、全 consumer を単一の束 resolver へ挙動保存で移す。最後にユーザーが一体の有効化 commit を作る | 候補となる凍結世代を先に作り、保守停止窓の中で「承認 + pointer」「環境活性化」を順に適用する | pegasus 第 2 世代を登録済み無効のまま維持し、恒久設計の active-bundle 機構が裁定・実装されてから起票し直す |
| 停止窓 | 有効化の瞬間だけ。ただし稼働 process の静止は別途必要 | **窓の中で公式実走を全面禁止**する必要がある | 不要 |
| 途中 commit の健全性 | 各 commit が自己整合を保てる | **中間 commit は式 1 を満たさず、単独では赤**になる | 変化なし |
| 巻き戻し | 休眠 pointer のまま止められる | 窓の途中で止まると赤の状態が残る | 該当なし |
| 承認の分離 | **現行の承認 commit 形状と衝突する (§5-5)。topology の再設計が要る** | 既存の 2 ファイル形状を維持できる可能性がある | 変更なし |
| consumer 移行 | 全 consumer を束 resolver へ | 固定 path の consumer を versioned へ | 不要 |
| 封印との組合せ | S1 / S2 いずれとも組める | S1 / S2 いずれとも組める | 判断を先送り |
| 放棄する保証 | 実装の小ささ。承認 commit の「2 ファイル追加のみ」という現行 topology | 「到達可能な全 HEAD が自己整合」「各 commit が単独で緑」。**履歴不変条件は放棄しない** | pegasus 第 2 世代の可用性と時期 |
| 規模 | 大 (段階 §9 の全段) | 中〜大 + 配備窓の運用 | 今回は小、将来大 |
| 現時点の成立性 | **未解決** — §5-5 により、素案のままでは現行コードが機械的に拒否する | 未検証 | 成立する |

### R1 について — 素案は現行コードで成立しない (親の実測)

段 2 の素案は「最終のユーザー commit を、環境活性化 record・凍結承認・凍結 pointer・
一体 pointer の 4 ファイル追加ちょうどに限る」としていた。**これは現行実装で機械的に拒否される。**

- 承認 commit の差分は「承認 record と active pointer の 2 ファイル追加のみ」でなければならず、
  それ以外が 1 つでもあれば拒否される。
- さらに環境活性化 serial を 2 にするには、record の追加だけでは足りない。有効な活性化 head は
  **Python の定数**として固定されており、その変更を伴う。旧 wave も定数を同一 commit で変えていた。

したがって R1 は「案」ではなく**未解決の設計課題**である。採るなら、承認が何を束縛するか
(現状は凍結世代の hash だけ) を含めて topology を作り直す必要がある。

### 封印の択一

- **S1** — 予測を byte 単位で再利用し、世代束縛だけを新設する。保証境界は (G-a) / (G-b) / (G-c) から選ぶ。
- **S2** — 新世代用の封印を作り直す。新世代の floor 結果が観測済みなら停止する。

R1 / R2 / R3 と S1 / S2 は独立に選べる。

## 8. 実装するなら scope に入れねばならない層

**producer 側だけ世代対応にして consumer を旧経路のまま残すのは「実装したふり」である。**
段 3 のレンズが具体例を構成した。新しい検証器を足しても、launch と verdict が旧経路なら
束縛 record を消しても差し替えても結果が変わらず、検証器は死んだコードになる。

世代対応が必要な層を漏れなく挙げる。

- floor campaign 本体と、その事前検査の既知 file 集合
- 予測 runner
- certified writer admission (静的 admission も固定 path を直接読む)
- ratified launch と oracle driver
- verdict と report (現在は予測文書と floor を独立引数で結合しており、束縛を持たない)
- 計算ノードへの投入 script と、その receipt schema (現在は protocol の path / hash も
  束縛も持たない)
- 計算ノード上で実行される job script (現在は固定 path を直接実行する)
- claim の識別子

**新しい権限型は、最終の書き込み / 実行の出口まで型を保ったまま消費されなければならない。**
候補用の契約を既存の validator へ渡すと、契約オブジェクトを取り出した時点で
「候補である」「誰が発行した」「どの束に属する」が失われ、current の契約と区別できなくなる。
「登録済みだが一度も有効化されていない世代」の拒否を候補のために緩めると、
WAL と完全性検証器まで、その契約を歴史上の権限として受理するようになる。

## 9. 段階分割と完了判定

**完了判定は、満たさない実装を実際に落とせるものだけを書く。** 書けば自動的に真になる条件、
測定手段が無い条件、判定者の主観になる条件は「未定義」と明記する。

| 段 | 内容 | 完了判定 |
|---|---|---|
| 0 | 択一の裁定と語彙・schema の確定 | §10 の全問に裁定がつき、新設 field がすべて §3 の台帳か「新規出力」に分類される |
| 1 | 現状を指す休眠 pointer と束 resolver の導入 (R1 の場合) | 導入前後で、floor hash・current 契約 hash・活性化 state・**拒否の集合**が一致する。拒否集合の比較は固定の負例一覧に対して行う (自己比較にしない) |
| 2 | versioned protocol、候補権限、封印束縛の実装 | 同一 path を更新する変異が `history-mutated` になり、versioned path の候補が受理され、**束縛 record を欠いた / 別世代へ差し替えた入力を、launch・oracle driver・verdict のそれぞれが拒否する** |
| 3 | 新世代 floor の実測と候補一式の作成 | 環境活性化はまだ 1、新 protocol の契約 hash が pegasus 第 2 世代の契約 hash と一致、active pointer はまだ現状のまま |
| 4 | ユーザーによる一体有効化 | **未定義。** 承認 commit の形状が §5-5 で未解決のため、段 0 の裁定を経てから書く |
| 5 | 有効化後の受入と再検査 | 旧 path の履歴不変条件が引き続き成立し、新 path にも別 bytes の歴史が無い。consumer 一覧と、各 consumer が記録する束の識別 field を段 0 で確定してから判定式を書く |
| 6 | 次世代への継承の先行検証 | 凍結世代 2 の fixture で、`supersedes_sha256`・pointer の親・失効・世代対応 certificate を検証する。**現行は世代 2 を拒否するため、拒否を確認して終わらないよう合格条件を段 0 で定義する** |

段 4・5・6 の完了判定が現時点で書けないのは、段 0 の裁定に依存するためである。
**書けないものを書けたことにしない。**

## 10. 裁定してほしいこと

1. **R1 / R2 / R3 のどれで進めるか。** R1 は現行コードで成立しないため、採るなら承認 topology の
   再設計を含む起票になる (§7)。
2. **封印は S1 / S2 のどちらか。** S1 を採る場合、保証境界を **(G-a) 受理順 / (G-b) 外部非観測まで /
   (G-c) 信頼境界を人へ** のどれに置くか (§6)。ここは親が一存で決めない。
3. **副作用の境界を、運用上の停止と再起動に委ねるか、束の世代を機械検査するか。**
   稼働 process は環境権限を process 内で保持し続けるため、有効化の前後で古い権限のまま
   書き込みうる。現行の権限オブジェクトは束の識別子を持たず、書き込み時点で
   「まだ有効か」を検査できない (§8)。
4. **段 0 の裁定を、本パッケージへの追記で行うか、別 wave として起票するか。**

## 11. 本パッケージが引き継いだ旧 wave の成果

旧 wave (`dev-wave-t657-t660-g2-activation`) の成果のうち、世代交代がある限り再利用できるもの。
**ただし取り込みは merge でなく再導出で行う** (理由と commit 分類は同 dir の
