## 2. U1. 分母条件をどちらの母数で書くか

裁定済みの Q2 は「劣化幅の閾値 `δ_D` を、元の版に対する**相対量**として workload 別に事前登録する」
までを決めています。しかし相対量には 2 通りの書き方があり、**裁定文はどちらかを閉じていません。**

- **(a) 総量の比** — 「劣化幅の平均 ÷ 元の版の平均」が `κ` を超える。
- **(b) 比の平均** — 各回で「劣化幅 ÷ 元の版」を出し、その平均が `κ` を超える。

**同じ実測から合否が反転します。**親が検算した反例: 2 つの割当てで
`(元の版, 劣化幅) = (100, 10)` と `(1000, 50)`、閾値 `κ = 6%` のとき、
(b) は `7.5% > 6%` で合格、(a) は不合格になります。

**推奨は (a)。** 裁定済みの回復率の定義 (Q1 = 総回復率) が総量型なので、分母条件も総量型に
揃える方が整合します。**ただしこれは目的から決まる裁定であり、親が独断で決めません。**

**成果物影響:** 同じ raw から `primary` の合否と certified 選択の受理集合が反転します。

## 3. U2. 劣化幅の閾値 `κ` の数値または導出規則

`κ` は「劣化版がどれだけ遅くなっていれば、回復を測る意味があるか」の下限です。

私は当初「今回の probe の実測値 (元の版に対して W1 で 88.2%、W2 で 90.2% の劣化) より十分小さい値」を
推奨しましたが、**段 2 と両レンズが独立に棄却しました。**理由は、候補の結果を見てから閾値を
決めることになり、本走を独立した確認と呼べなくなるためです。probe 自身の事前登録も、
その値を後続の基準へ流用することを規定していません。

**推奨:** `κ_W1` / `κ_W2` を、**候補の結果と無関係に**ユーザーが定める。
現 repo からこの数値は導けず、**現状は不明**です。

**成果物影響:** `κ` 単独で正例の成立/不成立が反転します。

## 4. U3. paired 設計の例外を roadmap へ記録する手続き

3 つの arm を同じ割当ての中で測る (paired) 設計は既に裁定済み (Q3) ですが、
**roadmap は今も「variant と baseline は決して同一セッションで測らない」と書いたままです。**
D134 決定 (3) は、paired を採るなら roadmap の改訂と D19 の適用前提の限定を
**同じ変更単位で**行うことを要求しています。これが未履行です。

**推奨:** 本走・実装・事前登録より前に、ユーザーが paired 例外を再確認し、
同じ commit で roadmap §3.6 の限定例外・D19 の適用前提を限定する新 D・
「この commit が無ければ次へ進まない」という gate を置く。roadmap は戦略層なので
協議改訂の手続きに従います (版凍結は不要)。

**成果物影響:** 同じ paired 実測に対し、RF 専用の判定と既存の 3% 基準という 2 つの解釈が残り、
消費側ごとに合否が反転しえます。

## 5. U4. 検出力の目標を「成分ごと」と「全体」のどちらにするか

裁定済みの Q5 は「標準化効果 d ≈ 1.0、約 11 cluster」ですが、この 11 は
**「6 つの成分それぞれについて検出力 80%」**の概算です。
**「6 成分すべてが同時に通る確率が 80%」**を求めると、粗い見積りでも 13 前後になります。

**推奨は全体 80%。** primary は「両 workload で 3 条件すべて」の連言なので、
守るべきは全体の方です。ただし **13 は正規近似の目安**で、最終的な標本数は
pilot の推定を反映した手続きで決めます。

**あわせて 1 つ固定します。** 段 2 は「pilot の下側効果が小さければ、拾う効果を小さく取り直して
標本を増やす」規則を提案しましたが、これは裁定 (142) の
「d=0.5 の約 42 cluster を最初から払う必要はない」と逆方向で、**結果を見てから費用裁定を
書き換える経路**になります。**目標 d は 1.0 に固定**し、下回る場合は「判定不能」で終えるか、
新しい費用裁定へ戻します。

**成果物影響:** 11 と 13 で最低 2 割当て分の費用が変わります。

## 6. U5. pilot の本数と、本走へ合算しない方針

**推奨:** 先行 pilot を 8 本、予備 2 本。**pilot のデータは本走の推定・検定・区間へ一切合算しない。**

合算すると、「途中で見て足りなければ足す」形になり、帰無仮説のもとでの誤り率が
名目の 5% を超えます (段 2 が閉形式で示し、親が確認しました)。

pilot が推定するもの: 割当て間の共分散、cluster 内の残差と実行順序の影響、
待機後の環境の戻り、割当ての実時間と失敗率、**計算ポイントの単価**。

**8 本だとばらつきの推定精度は約 27%** です。16 本なら約 18% まで改善しますが費用は倍です。

**成果物影響:** pilot が小さすぎると標本数の設計が粗くなり、大きすぎると費用を二重に払います。

## 7. U6. cluster 内の反復数と実行順序の設計

**probe の「均衡した実行順序」は厳密な均衡ではありませんでした。** 3 arm の全 6 順列のうち
1 つ (`劣化版 → 元の版 → 候補`) が欠けた 5 順列で、位置と直前 arm の出現回数が 1 回と 2 回に
割れています。

- **(a) 1 cluster あたり 6 反復、全 6 順列を各 1 回** — 位置も直前 arm も厳密に均衡します。**推奨。**
- **(b) 5 反復のまま、cluster を跨いで均衡させる** — 標本数を 6 の倍数へ丸める必要があります。

**ただし (a) には U11 の制約が掛かります** — 現在の時間予算に収まりません (後述)。

**成果物影響:** 直前 arm の影響が均衡しないと、その分が候補の性能差として現れます。

## 8. U7. arm の代表値を平均にするか中央値にするか

裁定済みの Q1 は「arm 代表値」までしか決めていません。段 2 は中央値を推奨しましたが、
レンズ A が「中央値には平均用のばらつきの式が使えない」と指摘し、これは正しいです。
段 2 が出した「反復数を増やせば標本数が減る条件」の数値は、平均を使う場合にだけ成立します。

**推奨は算術平均。** 標本数の設計式がそのまま使え、裁定済みの推定量と整合します。
中央値を採るなら、pilot でその分散特性を実測してから設計式を作り直す必要があります。

**成果物影響:** 回復率の点推定・区間・必要標本数がすべて変わります。

## 9. U8. 候補系列の有意水準の使い方と候補数上限

裁定済みの Q7 は「候補系列は親系列 ID + 累積 alpha 台帳 + spending 関数 + 候補数上限」と
決めていますが、**どの family に何を割り当てるかが未定**です。
現状の案では、試行 ID を新しくするだけで有意水準を実質リセットできます。

**推奨:** primary 系列と個別公表系列に**別々の累積台帳**を置き、候補数上限と累積量を
最初の正式試行より前に固定する。台帳は最初の試行前の正規の根へ束縛し、
新しい親系列 ID の自己申告でリセットできないようにする。

**あわせて:** 個別公表は primary の成否にかかわらず **6 セル全件を固定表で公表**します
(成功セルだけを抜き出すと、認証されなくても報告が成功を強調する形になります)。

**成果物影響:** 将来の候補すべてに効きます。緩めると偽の公表主張が累積します。

## 10. U9. 着手順序 — 親の推奨が段 2 と両レンズの案を置き換えます

適格性の権威は独立 validator だけが持ち (D162)、その機械化は発火条件 3 点
((i) 3 arm で事前登録を実走前 commit した計測、(ii) 環境タグ・測定 checkout・pin・証明、
(iii) 判定を読む消費側の実 hook) が揃ってから行う、と裁定済みです。

段 2 は「9 層を原子的に許可」、レンズ B は「新しい probe を先に取るか、D162 を明示的に
書き換えるか」を求めました。**どちらも不要です。**環境タグの仕組みは既にあるので、
**pilot 自身を「発火条件を満たす計測」にできます。**

```text
段 A  producer を実装する (記録項目を確定。環境タグ・証明・checkout・pin・
      全試行・実際の実行順序・正しさの証拠を含める。適格性の申告は受け付けない)
段 B  pilot を走らせる → この時点で発火条件 (i) と (ii) が成立する
段 C  それを根拠に validator と最初の消費側を実装する → (iii) が成立する
段 D  pilot から標本数を導き、事前登録を commit してから本走を投入する
```

**推奨はこの順序。** D162 を書き換えず、「条件が揃ってから機械化する」規律をそのまま守れます。
記録項目の変更 risk も pilot に閉じます (pilot の推定値は数値なので、記録様式が変わっても
使えます)。段 C の実装は、pilot 完了から本走投入までの待ち時間に収まります。

**残る risk:** 段 A の記録項目が段 C の validator の要求を取りこぼすと、pilot を取り直しに
なります。段 A の記録項目確定を**単独の裁定 gate** にすることで緩和します。

**あわせて 1 つ縮約します。** 段 2 は「実装は 9 層すべて新規、被覆 0/9」と見積もりましたが、
**過大です。**`orchestrator/qualification/` に、T-126 環境適格性のために作られた
試行台帳・系列 FSM・投入束縛・原子公開・identity の各実装が既にあり、
Q10 が要求する「計測開始の受領証・全試行の双射・親系列 ID」に構造的に対応します。
**D162 が禁じたのは T-126 の *成果物* を 3 arm 正例と読み替えることであって、*コード* の
再利用ではありません。**再利用するか複製するかは段 A の設計択一です。

**成果物影響:** 順序を誤ると、本走の全割当てを捨てるか、条件不成立のまま機械化を先行させます。

## 11. U10. 計算ポイントの総額上限

**単価が測れません。**残高照会は group 単位で、親の実測時点で gen_S に 104 件の request が
併存していたため、差分を [T-139] に帰属できません。repo 内にポイント換算式もありません。

実測値 (2026-08-07): 残高 **5236.04 / 初期 6000**。gen_S は 104 request 中 31 running。

**推奨:** ユーザーが**総ポイント上限を先に裁定**し、pilot の 1 本目で scheduler の会計痕跡を
取得してから、1 本ずつ保守的に上限を更新する。**費用未知のまま 24 本を一括承認しない。**

参考: 推奨案 (pilot 8 + 予備 2 + 本走 13 + 予備 3) は 26 割当て = 要求 26 時間相当です。

**成果物影響:** 途中で上限に達すると標本数が足りず、成果物は恒常的に判定不能になります。

## 12. U11. 待機時間の数値と失敗分類 — これは実行可能性の問題です

現在の probe の時間予算は **1 時間の割当てに対し内部期限 3300 秒、最悪ケース 3298 秒で
余白 2 秒**です。ここに 6 反復 (30 run → 36 run) と arm 間の待機を足すと、
レンズ B の見積りで内部合計は約 4708 秒となり、**1 時間の割当てに収まりません。**

**選択肢:**
- **(a) 時間予算を組み直す** — build を割当ての外で済ませる (hash 束縛済みバイナリの事前生成) 等。
- **(b) 要求 walltime を延ばす** — 費用表を作り直します。
- **(c) 5 反復のままにする** — U6 (b) と組みます。

**推奨は (a) + 予備として (b)。**いずれにせよ、**数値が確定する前に pilot を投入できません。**

待機時間の原案は arm 間 30 秒・block 間 60 秒ですが、**現データはこの十分性を実証していません。**
待機後に環境が戻ったことを確認する指標と、戻らなかった場合の失敗分類も同時に裁定が要ります。

**成果物影響:** 性能測定の開始後に期限へ達すると、裁定済み Q8 により予備で置き換えられず、
標本数が揃わないため pilot も本走も成立しません。

## 13. あわせて確定したこと (裁定不要。親が段 4 で固定)

- **受理条件は 3 つです。** `劣化幅 > 閾値` かつ `回復量 > 0` かつ `元の版に未達`。
  私が brief で 3 つ目を書き落としていました。2 つだけだと**元の版を追い越した候補まで
  「回復した」と認証できてしまいます。**
- **区間推定と受理条件は同じ構成から導きます。** 同じ標本共分散と同じ臨界値を使えば、
  区間が `(0,1)` に収まることと 3 条件の連言は**同値**です。別々に課して不一致を
  「データ破損」として拒否する案は、何も検出しない恒真な検査になります。
- **状態は 2 軸に分けます。** 区間の形 (有界 / 非有界 / 非連結 / 空) と適格性の状態
  (弱い分母は認証不可、など) を別軸にします。有効なデータからも空区間は生じるので、
  それを「表現不整合」と同じ扱いにしません。
- **受理条件に「環境証明・割当て会計・生存性・単独性」を明示的に入れ**、正しさは申告値を
  信用せず証拠から再計算します。「失敗した投入を台帳と記録の両方から落とす」
  「新しい系列 ID で有意水準をリセットする」「異常を正常と申告する」の 3 つを
  必ず検出できることを、実装時の必須テストにします。

## 14. この裁定が終わるまで動かないもの

- pilot の投入 (U11 の時間予算が確定するまで)。

- [T-144] (スペクトル補間) のうち、正例の成立を前提にする部分。

## 15. 本書が主張しないこと

- 代替 X が適格である、とは主張しません。成立しているのは **J=1 の engineering screen** だけです。
- 回復の機序が stripe 数・cache line 分離・固定回数計算のどれによるか、は主張しません
  (3 つを同時に変えたため。ablation は別の study です)。
- 推奨した標本数が正しい、とは主張しません。**割当て間のばらつきは 1 点も推定されておらず**、
  pilot の前に確定できません。
