## 1. 対象と方法の構成

Izanagi は、ワークロードに応じたトランザクションの並行性制御 (CC) の実装変異を生成し、正しさを
検査したうえで性能を評価するシステムである。CCBench の既存実装を素材とし、既存フラグの組合せを探索する
操作と、指定されたソース領域へコードを挿入して実装の振る舞いを変える操作を組み合わせる。列挙できる軸内の
探索は機械探索へ渡し、LLM は変更の方向やコード片を提案する。対象実装が選べる操作の集合 (action
vocabulary) を拡張し、各反復に正しさの検査を組み込む点を方法の中心とする。

合成範囲は、導入済みの編集領域とその軸に認められた文法に限る。たとえば段 4 の backoff 軸では、abort 後の
待機量を定める一つの文を生成する。コードを出力する形式であっても、この軸で探索する自由度は数値一つで
ある。sort や trigger-gating は別の軸として、それぞれの制約下で扱う。2026-09-21 に採用条件を定めた関数単位の軸
`silo-function-policy` (D2214) は、Silo の待機と lock 競合への応答を 3 関数の方策として書かせる、より広い空間である
(第 2 節)。これらの実装から、任意の CC アルゴリズムを自動合成できるとは結論しない。

合成対象を Silo に限定する方針は 2026-09-17 に解除された (D2114)。第 2 の対象として MoCC を変異探索面へ
入れる前の準備として、温度述語を編集領域にした骨格 template と、その接続を機械検査する実証 (段階 A) が
2026-09-20 までに走った (D2159)。これは探索の解禁でも正式な軸の採用でもない。**CCBench の版 (pin) は、2026-09-20 に
`511c9538` から `e9e477ca` へ ([T-2304])、2026-09-23 に `e9e477ca` から MoCC の X/P 計装を持つ C (`68106660`) へ進んだ
([T-2858]、D2236)。** どちらの前進も探索・軸採用の解禁を含まない。前進の範囲は gitlink・`CCBENCH_FULL_SHA`・`CURRENT_PIN` の
同時更新と追随で、各 driver が持つ campaign の pin (たとえば比較基盤の評価入口 `p3_s4_loop.PIN` = `511c9538`、D1936 項 1) は
別に扱う (F1051。MoCC の slot だけが D2248 で C を使う、第 2 節)。非 Silo の性能比較は採用時点でも 0 件である。

2026-09-21 の研究方針 (D2212、ユーザー裁定) により、評価対象に TPC-C を段 1 (NewOrder / Payment、点読み・点書き・insert)
→ 段 2 (範囲読みを含む全 5 取引) の順で加えた (段の分割は D2219 項 2)。採用時点で方法が揃っているのは段 1 の正しさ検証の側
(trace v3・存在履歴の検査・pipeline の受理、第 3 節) で、TPC-C の合成候補を build・評価する配線、TPC-C の性能測定、段 2 は無い。
同じ方針は正しさゲートを変えないことを条件にした。

基本の評価順序は、提案、差分検疫、検証用・性能用の二つのビルド、実行トレースによる検証、独立した性能測定、
記録と次の提案へのフィードバックである。本稿で **certified** と書くときは、次の意味に限る。指定した検証構成
(workload・スレッド数・実行時間・反復数) で取得した観測トレースについて、判定器の意味論 (YCSB の point
read / write に限った観測トレース上の直列化可能性、反依存を含む循環 G2 までの検出) に照らして anomaly が
検出されず受理されたことである。これは実際にビルドされた bytes についての判定であり、要求した構成が
ビルドされたことは含意しない (それを担うのはソース識別の束縛であり、別の機構である)。性能の判定でもない。
プログラムの全入力・全実行順序に対する形式証明や、論文での性能優越の成立を意味しない。**TPC-C 段 1 の trace について
判定器が返す判定は、この定義の外にある** (第 3 節で「判定器が直列化可能と判定した」と書き、certified とは書かない)。

## 2. 変異の生成と編集範囲の限定

提案生成は planner と coder に分ける。planner は現在の性能指標と反復履歴から変更方向を提案し、coder は
その方向と与えられた基準情報から具体値とコード片を返す。critic は評価後の指標や拒否理由を読み、次の方向を
提案する。段 4 ドライバ自身は LLM を呼び出さず、これらの構造化出力を引数として受け取る。したがって、この
経路の反復運営はメインセッションが受け渡す人間監督のループである。

知識付き提案 (K2) では、既評価の測定記録に限った知識射影を planner と coder の入力に与える。2026-09-19 に、
critic が返した診断を次の planner と coder の両方へ同一内容で渡す型付き入力 `k2_critic_diagnosis` が加わった
(D2155)。親が指定した critic の逐語から既存の抽出器で 4 節を取り、データ境界とソース SHA-256 を合わせた
6 field を、既存の入力と同じ階層の兄弟 key として組み込む。この入力は K2・非 B-4・還流 on の campaign に
限り、評価と停止判定は変えない。診断が「届いた」ことと「効いた」ことは別であり、この経路の因果効果は
本稿の方法では確かめない。

編集領域は `EVOLVE-BLOCK` の開始・終了マーカーで指定する。テンプレートは合成側の分岐と既存実装を保持する
分岐を用意し、coder の変更対象は合成側の内部だけに限る。検疫はテンプレートを適用した後のソースを基準に、
マーカー、分岐骨格、既存実装側の保存と編集範囲を確認する。続いてホストへの作用を検査する有限の字句規則と
軸固有の文法を適用する。backoff 軸では、提案した値とコード中の数値リテラルが一致することも確認し、記録する
候補と実際にビルドする実装の対応を保つ。字句検査だけで任意コードの意味的安全性が証明されるとは扱わない。

検疫に通らない提案はビルドへ進めず、拒否の種類、理由、対象領域を記録する。通過した提案は、固定した
CCBench の版に対して隔離・排他された適用区間で評価し、終了時に変更を戻す。ビルドの識別にはフラグを表す
genome に加え、実際のソースに由来する識別情報 (前処理後のソース pre-image から導く `src_token`) を用いる。
この pre-image は 2026-09-17 以降、有効枝の `#define` / `#undef` 指令を含む (D2108)。指令と include の
相対位置、`push_macro` / `pop_macro` は識別の限界として残る (D2120 項 7)。同じ genome を持つ既評価候補の
重複提案では、保存済み証拠を確認して評価を再利用する場合がある。検疫通過だけの試行やビルドを省いた
配線確認を、検証済み候補へ昇格させない。

**K2 の同 job stock 対照。** 候補と同じ campaign で、CCBench 内蔵の適応 backoff (`BACK_OFF=1`、`BACKOFF_FIXED=-1`) を stock
対照として評価する独立の口が、2026-09-20 に段 4 ドライバへ加わった (D2183)。対照は無 backoff ではない。この口は
planner・coder・検疫・白板に到達せず、stock の成功は certified かつソースが stock (`src_token` が stock) であることを要求する。
最初の投入 (2 process 形) は、stock の driver が campaign の one-shot な測定 claim を取れずに build の前で止まり、不成立だった
(D2187)。2026-09-21 に driver は pair mode (`--run-iteration` と `--stock-control` の併用) に修復された (D2205) — 1 process の
中で認可と claim を 1 度だけ取り、その所有期間の内側で候補 → stock の順に評価する。claim の排他規則 (one-shot 性) は変えていない。
2026-09-22 にこの形で再投入した 1 job (`16269.nqsv`) で、候補と stock がともに certified になり stock の `src_token` は stock だった。
続く 4 巡目の 1 job (`16312.nqsv`) は round 3 の派生物から production 関数で入力を組み (pair 再投入の結果は渡していない)、
候補と同 job の stock がともに certified だった (entry 1823)。どちらも CCBench を driver の PIN `511c9538` へ checkout して走らせた
(D1777 の手順)。**同 job の比は配線 1 点の記述値であり、改善・候補間の優劣・診断の効果を示す方法にはなっていない** (4 巡目の候補と
pair の候補は別 job なので比べない)。

pin の前進は、ビルドの識別にも作用する。pin は build admission の policy の pre-image に入るため、pin が進むと
campaign ID・cache key・builder の bytes・受領証の identity が新しい epoch へ移り、較正 record・凍結した
protocol・比較 policy・過去の golden は動かない ([T-2304]・[T-2858]、規律 7)。前進前に登録した系列 (K2 の巡、A-1 sized、
凍結 v2 第 1 世代の launch、B-4 床値) は、前進前の superproject と対応する submodule の固定 checkout、または driver の旧 PIN を
checkout する手順から走らせる。新しい pin の main からそれらを再開・再投入するには、系列ごとに登録・identity・ドライバの pin・
後継 protocol・admission の整合が要る。

**関数単位の合成空間 (軸 `silo-function-policy`)。** 既存の軸は値 1 個・79 値・5 bit で列挙し尽くせるので、LLM が関数を書く空間を
条件付きで開いた (D2214)。境界は方策と仕組みの分離である — LLM が書くのは abort 後の待機量を返す関数、lock 競合時に retry / abort を
返す関数、成功 commit 時に自分の状態を更新する関数の 3 つと補助関数・状態型だけで、CAS・unlock・validation・tid 生成・writePhase・
trace・同じ取引の再試行は人間が一度入れる骨格が持つ。置き場は `cc/silo/transaction.cc` の include 列の後の単一 EVOLVE-BLOCK で、
軸 macro を切ると領域・骨格・呼出し点が消えて inert になる。受理する C++ は型付きの許可リスト部分言語 policy-C++ v1 に閉じ
(pointer・配列・loop・再帰・template・例外などを禁止し、算術の型と shift・除算の右辺を制限する)、build の前に既存の差分検疫、
既存の作用検査、型付きの構文検査、CC ヘッダ抜きの単独翻訳単位での `-Werror` compile の 4 段で機械的に検査する。状態は骨格が
所有する worker ごとの 1 個だけで、観測は abort 要因・同じ tuple での lock 試行番号・骨格の乱数に限り、待機の上限は骨格が持つ。
安全の主張は「メモリ安全・外部干渉なし・契約適合の方策が正常に返る限り、方策の選択は固定骨格の直列化可能性条件を弱めない」までで、
任意 C++ の適合性・全実行の正しさ・停止性・公平性は構成上保証しない。validation と lock の仕組みは開かない。

この軸は段階を分けて進める (D2214 の順序 C → D → 人間判断 → E → F)。段階 C (D2226) は骨格・検査器・焦点試験・機構変異・手書き方策の
生死確認で、診断 build は `pipeline.evaluate` を通さず certified 候補と称さない。段階 D (D2234) は、型付きの有限 IR (定数・abort 要因・
lock 試行番号・状態参照・比較・条件式・min / max・飽和加減算・有界 shift からなる深さ 4 以下の式木。停止と算術安全を構成で保証する) から
4 因子 × 2 水準の固定 16 点を描画し、骨格内の退化点 abort0 (待機 0・lock 競合で即 abort) を同じ job に置いて、同 job 比 3% 超が別 job でも
再現するかの二値を取る機械偵察である。abort0 は write-heavy で abort 率の高い点なので、この二値は既知最良を超える地形の有無に答えない。
そこで既知最良との小比較 (D2235 項 7、D2240) を 1 回だけ行った — 段階 D と同じ 16 点・8 job の各 job に、stock (`BACK_OFF=1`)・
`B0-L-W0` (`BACK_OFF=0`)・静的 10 µs (stock 木へ `patches/silo-backoff-fixed.patch` を当てる元の適用方法で build し、trace 有効・無効の両 build の
compile command で実効 define を検査して不成立なら verify・bench へ進まない) を置き、点・abort0・参照 3 本がすべて適格 (両 verify certified・
trace0 clean・5 rep 有効・前後の source evidence の一致) で high-abort でないときだけ、5 rep 中央値 ÷ 参照 3 本の中央値の最大 (最良参照比) を出す。
どれか欠ければ比は null で負けに数えない。3% 線は未較正の探索的な目印で、16 点から最大を選ぶ多重選択は補正せず、再測もしない。
比較の出力 (点 ID・比・順位) は後段 (段階 E / F の coder・planner の入力) へ渡さず、後段へは段階 D の二値と射程文だけを投影する
(手順書 `docs/axis-onboarding.md` §3-D の firewall)。第 35 回の裁定 (D2243 項 1) は段階 E (driver・role・firewall の機械化) へ進めることと、
越えた点を論文で既知最良超えとして書く前に別 job で再測することを定めた。**段階 E は採用時点で実装されておらず、LLM がこの空間で方策を
生成した記録は無い。**

**5 手法の比較基盤 (S1) と MoCC の差し込み。** 探索法の比較のため、random・sweep・BO (x = ln v の逐次 GP-EI)・進化 ((1+1) 変異)・
LLM (知識射影なしの K0) が共有するものを、候補の identity・評価の要求 (既存の単回評価経路 → 検疫 → Tier0 → 検証と測定、手法で経路を
変えない)・結果の分類・費用の計上の 4 契約に限った (D2220)。具体化は Silo の backoff 値空間 (1〜1000 µs) だけで、主構成 R0 では生成器へ
渡す初期情報を系列開始の stock と空間内の共通初期点 (静的 5 µs・10 µs を系列ごとに fresh に測る) の観測に限り、空間外の参照値
(`BACK_OFF=0` の最良フラグ) は報告用の対照として同じ block で測っても生成器へ渡さない。費用は、候補提出の機会 A と投入した評価 B を
分け、Tier0 の不通過は A だけを消費する。実装は B-5 の兄弟 module と既存評価入口への最小変更である (D2233)。2026-09-26 に、この
比較基盤の 1 slot 経路へ protocol 引数で MoCC を差し込んだ (D2248) — MoCC の genome は固定 flags の上で S1 と同じ literal の hole を
使い、動作点は pin C で取った MoCC の認定較正 3 件 (records は S1 と同じ 1,000,000)、MoCC の slot だけ campaign の pin を X/P 計装のある
C に移し (Silo は `511c9538` のまま)、条件の意味検査は build する protocol の翻訳単位で行う。**計算ノードで確かめたのは MoCC の stock と
literal 候補の 5 slot が certified で通る疎通であり、比較ではない。** MoCC の比較は stock 比で報告し、既知最良の参照が無いことを
明記する (D2220 項 6)。

## 3. 正しさ検証と反例のフィードバック

正しさはトレースを有効にしたビルドを別に実行して検査する。各検証構成について、正常終了、空でない
コミット履歴、実行体が報告するコミット数等の証拠を確認し、トレースを判定器へ渡す。判定器は履歴の整合性を
確認し、トランザクション間の読み書きに基づく直列化グラフを構築する。書込み間・書込みから読込み・読込みから
後続書込みへの依存を扱い、反依存を含む循環 (G2) まで検出する。診断には循環を構成するトランザクション、
依存辺とその理由を含める。anomaly が検出された候補はその時点で失格とし、性能が高くても採用しない。
空トレース、解析不能、実行失敗等も、正しさを確かめられた成功例には数えない。判定器はプロトコルの証明面
(ロック被覆等の観測点) がソースに実在するかを検査し、証明面を持たないプロトコルのトレースは certified を
名乗れない。

判定器の内部表現は 2026-09-20 に、鍵単位の packed 配列と配列だけを読む並列 worker へ変わった (D2181)。
これは長い実行時間のトレースで検査が完走しなかった原因を除くための変更であり、判定の同一性は既存トレースの
出力の byte 一致で確かめた。判定器の意味論は変えていない。

既定の検証構成に追加構成を指定した場合は、その全構成・全反復を通過させる。小規模検証と性能動作点の検証は
同義ではない。実装には legacy に S2 を追加する経路と、性能設定から検証構成を作る経路があり、どれが実際に
使われたかは試行記録の構成タグで区別する。性能を測った workload そのもので legacy 1 回と性能条件 5 回の
検証を要求する certification 経路 (第 5 節) では、policy の node 数に従い、性能条件側の検証を候補と同じ
task に束縛した別 node の worker へ分けて走らせることができる (現行 policy は 5 node。A-2 / A-6 の取得済み
attempt は 1 node で走り、2026-09-19 の同一候補 3 workload 同時期測定は 5 node で走った)。ある設定での
検証成功を、まだ試していない負荷や別プロトコルの正しさへ一般化しない。

採用済み候補について、正しさ側の追加検証として **検証相** を置く。2026-09-19〜20 に、採用候補 2 genome
(固定 5 µs と固定 10 µs) を対象に、現行ソースのトレース有効ビルドで 3 workload × 独立 8 反復の検証を
走らせた (D2160)。実行時間は候補ごとの校正で決め、校正で完走しなかった走行は「校正全体の失敗」でなく
`indeterminate` として開示し、完走した範囲から選んだ。判定は「判定集合の全件で anomaly がない」という
操作的事実であり、確率的な主張はしない。この検証相は事前登録 (S-1 の付属規則) を準用した追加検証であって
その充足ではなく、性能値を含まず、既存の certified 記録を昇格も降格もしない。走らせた runner はリポジトリ
外の job 領域に置かれ、リポジトリ内の実装ではない (判定器の呼出しは `python3 -m orchestrator.verifier`)。

**B-8 (最終候補の長時間・独立反復の trace 検証)** は、上の検証相とは別の登録で、別の対象を検査する。B-8 は
S-1 の最終候補の正しさを「種を変えた」長時間実行で検証する要件であり、その事前登録 v1
(`docs/b8-final-candidate-longrun-verify-preregistration.md`) は 2026-09-20 に、対象の 2 案 (推奨は案 A)、「種を変えた」と
「長時間」の操作的定義、校正・予算・判定の規則を結果を見る前に固定した (D2175)。対象は S-1 の最終候補である系側 gate 構成
(案 A。gate 述語は凍結した S-1 の記録の逐語で、balanced と read-heavy に `g_rl`、write-heavy に `g_rt`) で、
D2186 項 1 がこの対象と二つの定義、および発効前の試走を認可した。試走は build とソース identity の導出だけを
行い、その結果は判定集合に入れず既知結果として開示する (D2190 項 5)。「種を変えた N 反復」は、N 個の bench
process をそれぞれ新しい OS process として起動し、各 process の各 worker thread が `std::random_device` から
自己シードすることと定義する。seed 値は記録せず (CCBench に seed を与える flag は無い)、代わりに rep-id・PID・
開始時刻・argv 全文・node 名・binary の sha256・ソース identity・trace の量を記録する (事前登録 §3.2)。「長時間」は、
1 走の実行時間 (extime) が開発相と検証相の 3 s より長いこと (6 s 以上) と定義し、値は校正で決めて 3 s へ丸めない
(§4.1)。

事前登録の発効は、ユーザーの本走認可を伴う日付付き commit と、その認可を記録した決定による。発効前に校正・本走を
始めない (§0)。発効の前には **発効束** — 対象の択、ソース identity の期待値、CCBench pin・patch・configure の逐語、
判定器 module の file 別 sha256、runner の bytes の sha256、実行環境、校正 job の walltime とその根拠など、
事前登録 §12 が列挙する実値 — を固定する。発効束の JSON は、試走で揃えた draft の実験構成の値を変えず、状態の
欄だけを発効へ置き換え、`effective` 節 (承認の記録) を足したものである。発効 commit 自身の hash は発効束に書かない
(D2202 項 1)。B-8 は 2026-09-21 に D2194 項 1 の承認で発効した (発効 commit `624c84986`)。校正・本走・再検証は
すべて発効 commit の固定 checkout (1 job に 1 本の detached な木) から走らせ、runner に渡す発効束はその木の
追跡済み file に固定する。投入の直前に runner・事前登録・発効束の sha256 を照合し、一致しなければ投入しない
(D2202 項 2)。

規則の機械適用は、検証相の runner を改版した **runner v5** が担う (D2190 項 1)。runner v5 はリポジトリ外の
job 領域に保全して sha256 (`4ff6652a…`) で同定し、リポジトリへは入れない (D95)。runner は校正・本走・再検証・
集計と、試走 (build と identity の導出だけ) の各操作を持ち、ソース identity の期待値を自身の定数でなく発効束から
読む。規則 file (事前登録本文) と発効束の両方の sha256 をすべての記録に束縛し、集計は許可集合で照合する。校正・
本走・再検証は、build の前後で観測した identity が期待値と一致しなければ fail-closed で止まる (D2190 項 2)。判定器は
別 process の `python3 -m orchestrator.verifier` で、緩和オプション (`--lenient`) は使わない。判定器の版は発効時点の版に固定し、
校正と本走で同じ版を使う (D2186 項 1 (7))。判定器の強制停止時間は校正 3600 s・本走 1800 s・再検証 3600 s である (D2190 項 4)。

**校正段 (段 A)** では、各 workload で extime を {6, 10} s の昇順に各 1 回、trace 有効ビルドで走らせて判定器に
かける。適格は、bench の完走、trace の保全、判定器の完走、`serializable`、certified、anomaly 0、identity の一致、
判定器の実行時間 1800 s 以内のすべてを満たすことである。判定器が 1800 s を超えるか完走しない、または bench が
失敗した時点で、その extime 以上を打ち切る。校正の未完走は verdict を持たない運用上の `indeterminate` として開示し、
再検証しない。校正で完走した判定に anomaly が 1 件でもあれば、その対象は即失格とし本走を投入しない (規律 2)。
bench の失敗は校正・本走を問わず pass を妨げ、校正で出れば本走を投入しない (§5、D2190 項 3 (b))。
対象の extime は 3 workload の適格集合の共通部分の最大値で、共通部分が空なら「候補なし」として本走を投入しない
(§4.2)。本走の見込み所要は校正の実測から求め、本走の job 実消費の上限を超えるなら共通部分の中で 1 段下げ、下げる先が
無ければ本走を投入しない。反復数は削らない (§7)。

**本走段 (段 B)** では、決まった extime で 3 workload × 独立 8 反復 = 24 verify を走らせる。1 つの verify は
1 つの bench process (1 trace 集合) に対応し、1 node の上で build → bench → commit 行の数え直し → trace の保全
(zstd) → 判定器の順に進め、bench と判定器の直前に単独性を検査する。bench が失敗した verify は判定集合に入れず、
bench を再生成しない。判定器が完走しなかった枠は 2 通りに分けて扱う — trace を保全済みで判定器が未開始の枠は、
同じ job を再開して初回の判定器を走らせ、判定器が起動済みで完走しなかった枠だけ、同じ保全済み trace への再検証を
1 回許す。anomaly を出した枠は再検証しない (§6.4、D2202 項 3)。

**3 値判定** の判定集合は、本走 24 verify と、校正で完走した verdict の和である。判定は次の順に 1 度だけ評価し、
最初に成り立った値を採る (§6.1)。

1. **失格** — 判定集合に、`anomaly_count` が 1 以上か、verdict が `serializable` でない verify が 1 件でもある
   (判定器が完走して `indeterminate` を返した verdict もこれに含める。D2190 項 3)。校正・本走のどちらで出ても即失格で、
   再実行しない (規律 2)。
2. **pass** — 失格でなく、本走 24 verify のすべてが bench 完走・trace 保全・判定器完走・`serializable`・certified・
   anomaly 0・identity 一致を満たす。校正の完走 verdict には certified を要求せず、certified でない件数と理由を開示する。
   校正の未完走 (運用上の `indeterminate`) は pass を妨げないが、件数と保全先を必ず開示する。
3. **未確定** — 上の二つのどちらでもない (本走の未完走が再検証後も残る、bench 失敗、identity 不一致、規約不適合、
   規則 file・発効束の sha256 の不一致、判定集合外の記録の混入)。未確定は B-8 未取得のままであり、pass に丸めない。

判定は runner の集計が規則を機械適用した出力であり、pass は研究の成功宣告ではない (D12)。この手順で 2026-09-21 に、
判定集合 = 本走 24 枠 (独立 8 反復 × 3 workload・extime 10 s) + 校正の完走 6 枠 (3 workload × extime 6 s / 10 s、各 1 回) の
30 枠で、3 値判定 `pass` を得た (結果稿 `docs/paper-story/results/2026-09-21-b8-final-candidate-longrun-verify.md` §3、
worklog entry 1791)。B-8 の主張は、観測した trace の依存グラフについての certified の範囲を超えない。「種を変えた」は独立 process の
自己シードという操作的定義で、乱数列の独立性は検証していない。「長時間」は extime 10 s という操作的定義である。ソース identity は
発効時の pin `e9e477ca` と当時の patch に束縛されており、その後の pin の前進は記録された判定を変えない (規律 7) が、C の上で同じ対象を
検証し直した記録は無い。B-8 の pass は S-1 の付属規則 (iv) の充足ではなく、S-1a の不成立を変えない。

拒否は単なる二値の失敗にせず、判定器が返した構造化診断を試行記録へ残す。依存関係上の反例を含む検証失敗、
コミットが得られない等の生存性の失敗、差分検疫の拒否を区別し、どの構成で失敗したかを次の提案へ渡せる形に
する。通常の還流では、critic に成功候補の性能指標と失敗候補の診断を併せて提示し、その判断を次の方向提案に
つなぐ。第 2 節の型付き診断入力は、この critic の出力を次の生成へ運ぶ経路である。反復状態はチェックポイントに
保存し、提案履歴と停止条件の判定をプロセス間で継続する。還流の効果を調べるため、critic 用の要約へ拒否診断を
含めるかどうかを切り替える実装を持つ。この切替は診断の提示に作用し、実際の正しさ検証を省くものではない。反例を
次の生成に利用できる配線の存在と、反例還流が性能や探索効率を改善したという因果的結論は分ける。

**TPC-C 段 1 の正しさ検証。** YCSB の trace (v2) は key を 1 つの名前空間で扱うが、TPC-C では表だけが違う同じ key bytes が
実在する。そこで段 1 用の trace v3 を置いた。判定器は C 行の token 数で v2 (7) と v3 (10) を分け、v3 では object を (表, key) で識別し、
新しい整数欄 (表・取引種別・範囲読みの件数) は正規の 10 進だけを受理する (D2224)。v2 の受理・判定・出力は変えない。CCBench 側の出力は、
`include/tpcc.hh` が取引の開始直後に trace build 限定の thread-local context へ取引種別を置き、Silo (と MoCC) の write phase がそれを 1 回
読んで、非 0 なら v3、0 (YCSB ほか) なら既存の v2 の式で出す (D2225・D2230)。trace build では成功 commit を必ず数えるよう計数を
`#if !TRACE` で分け、trace を出さない build の判定と計数順序は変えない。v3 の run は、存在履歴を検査するまで一律に認定しない印を持っていたが、
段 1 の存在契約 — (表, key) は、その object の最初の committed write が insert でなければ初期ロードから存在する — の検査に置き換えた
(D2232)。違反 (初期に無い object の初期版の読み、削除版の読み、存在する object への insert、存在しない object への update / delete、同じ取引・
同じ版に異なる op) が 1 件でもあれば認定しない。この契約の根拠は Silo の版付け (初期ロードだけが特定の版を付け、insert は既存 key で失敗する)
で、別の CC を使うときは同じ 2 点を確かめ、段 2 (削除・再挿入・範囲読み) へはそのまま広げない。2026-09-23 に、campaign の pipeline の
trace 段が段 1 の v3 を受理するようになった (D2238) — binary 名が `tpcc_` で、取引比の 4 flag (`tpcc_perc_payment`=43、他の 3 取引 = 0) が
文字列で一致するときだけ trace を走らせ、判定器の直後に結果が v3 であることを要求する (v2 は既存の理由で拒否する)。57:43 は CCBench の既存
flag で範囲読み 3 取引を 0% にした比である。受理判定の CLI 出力・reject 診断・受領証の digest は v3 の構造化出力を使う。

この経路で、Silo の実 TPC-C trace 1 本 (36,156 取引) と実行体の出力を pipeline の実行部に通すと、**判定器は直列化可能と判定した** (判定器の
出力の語は certified だが、本稿の certified の定義 (第 1 節) は YCSB に限るので、この語を TPC-C の判定には使わない)。存在違反を 1 行注入した写しと
末尾の frame を欠いた写しは拒否された (entry 1852)。取引の選択は合成の編集面の外にあるので、trace の取引種別そのものは pipeline で検査しない。
**方法の限界として、production の build は YCSB の実行体だけを作るので campaign で TPC-C の候補を build・評価する配線は無く、採用時点の
pin (C) の tpcc 実行体は v2 を出すので v3 の要求で拒否される。** v3 の emitter は CCBench の別名 local branch に置かれ、pin に入っていない。
Silo と MoCC の emitter を C の上に 1 系列で並べた候補 (C → C1' → C3 → C2') については、計算ノード 1 走で両 protocol の v3 の構造と
YCSB の v2 の certified、trace を出さない build の前処理と逆アセンブルの一致、結合固有の変異 4 件の検出を確かめた (D2244)。規律 1 の
既存検査器 (`tools/check_trace0_preprocess_identity.py`、D297) は共有 header の差分を保証範囲外として拒否するので、この候補は D297 の合格も
TPC-C の認定も名乗らず、header 差分の受理方式はユーザー裁定を待つ (4 択、D2244 項 5)。TPC-C の合成候補を認定・評価した記録、TPC-C の
性能測定、段 2 は採用時点で無い。

**verifier の検出期待表の実走。** 判定器の検出力を、CCBench に意図した変異を入れた build で測る。変異は D16 の out-of-tree patch
(1 個の裸マクロの `#if` 枝) とし、既存の壊し build の経路 (patch 適用・条件関門・commit 証人つきの判定器、buildcache と admission は通さない)
で走らせる (D2239)。期待・workload・job の分割・分類の規則は投入前に事前登録し、期待と違う結果が出ても patch・workload を期待へ寄せない。
直すのは、patch が意図した機構以外を変えていることを source で示せる実装の誤りだけで、初回の結果も残す。各 patch の有効枝には **発火診断**
(変異枝に入った回数・元コードと違う挙動を生んだ回数・その取引が commit した回数を終了時に 1 行出す) を置き、判定器の判定には使わない。
分類は五つ — 期待した層で検出・別の層で検出・**盲点として certified** (変異が挙動を変えその取引が commit したのに判定器が受理した)・
**未発生** (変異が挙動を変えなかった)・誤検出 — で、発火の証拠が無いと盲点と未発生を取り違えるので分ける。MoCC の行 (pin C の上に既存の壊し
patch を計装 patch なしで単独に当てる) では、五分類に当てはまらない cell を **発火未確認の S** (発火診断の無い既存 patch の受理)・**停止** (run の
timeout。verdict を付けず、同 job の stock 同 cell の完走を対照に書き、原因は断定しない)・**対照正常**・**帰属不能** (同 job の stock が異常) として
別に記録し、1 cell で複数の層が発火したときは期待した層の counter が正なら「期待した層で検出」とし併発を別欄に書く (D2246)。停止した run の
部分 trace は判定しない。sort-nonswo (V07) は条件関門と同じ供給経路 (`-DCCBENCH_SORT_VARIANT=<v>`) で build し、同じ job の stock 対照を付けた
(entry 1855)。trigger-misattr の既存 driver は現行の source digest が裸マクロを拒否して走らないので、防壁を緩めず、その build だけを他の壊し patch と
同じ直 CMake 経路にした repo 外の起動器で走らせた (D2239 項 5)。**各 cell は 1 回の有限の走の観測であり、停止は deadlock の実証ではなく、
「盲点として certified」は判定器の欠陥の主張でもない (lock 順のように直列化可能性の条件でない変更を含む)。検出力の網羅的な証明ではない。**

第 2 の対象である MoCC については、ロック被覆と順列保存の計装 (X / P) と、G2 の読み値の出所を識別するための witness を持つ。計装は
2026-09-23 まで CCBench pin の tree に無く、pin の上に patch として当てていた (旧 pin `511c9538` について D2083、`e9e477ca` でも同じ)。
pin が C へ進んだ後は、C の source が計装を持ち、現行 pin の実 source を読む判定器の正負対は「同じ trace を MoCC として検証すると certified」へ
追随した。拒否側の被験は計装を持たない tictoc へ移し、「証拠の無い経路」の負例は旧 pin を明示 checkout する既存の test が被覆する (D2236)。
これらで取った G2 の観測 (旧 pin 上) は、原因が MoCC 実装の性質か計装側の取り違えかが未同定のため、certified な判定ではなく非 certifying の
観測記録として扱う (D2148 項 13)。観測が 0 件であることは不在の証明にならず、非有意は同等性の証明にならない。pin の前進は MoCC の
certified 系列の成立でも探索の解禁でもない。

**trace の保全。** 論文根拠の実験の trace を後で判定器に掛け直せる (R1) ように、標準評価経路に opt-in の保全口を置いた (env
`IZANAGI_TRACE_ARCHIVE_ROOT`、D2233 項 4)。検証 1 反復の一時 dir を cleanup の前に file ごとに圧縮して保全し、完了したときだけ inventory を
complete にする。2026-09-26 に、inventory へ R1 の入力 (同じ trace を CLI で再判定する等価 argv・repo commit・完全 SHA の pin と宣言値・
patch の bytes と sha256・判定器 module の sha256) を B-8 の runner と同じ名前で足し、保全時に source の HEAD が宣言 pin で始まることと patch の
sha256 が build 時に束縛した source evidence と一致することを照合して、合わなければ inventory を failed にした (D2247)。保全は判定の後に
生きた checkout から取るので、この照合で「complete = build 時と同じ source」を意味させる。保全の失敗 (照合の不一致を含む) は原本を残し、
評価結果・verdict・WAL・受領証を置き換えない。保全の記録は certification の根拠にしない。

## 4. 正しさ検証から独立した性能測定

性能はトレースを無効にした別ビルド・別実行から取得する。トレース処理と検証専用メタデータはコンパイル時に
除去し、実行時フラグで処理を飛ばすだけの構成にはしない。候補と比較対象はともにトレース無効でそろえる。
この分離により、検証のための観測処理を測定対象の CC に混ぜない。「独立」はビルドと実行の分離を指し、
探索中の逐次試行が統計的に独立だという意味ではない。TPC-C の v3 emitter と計数の変更も、追加はすべて `#if TRACE`
(計数だけ `#if !TRACE`) の内側に置き、trace を出さない build の論理行番号を `#line` で pin と一致させる (D2225)。

測定条件は、レコード数、スレッド数、ワークロード、実行時間、反復数、環境契約で指定する。探索規模には、
較正によって必要な競合やキャッシュ挙動を再現する最小規模を用いる。測定層は実行の競合を確認し、
スループットの反復標本、中央値、変動係数、abort 率等を記録する。規定範囲の再測定でも安定しない場合は
`unstable` として残す。測定が完了したこと、正しさを通過したこと、安定した比較材料になったことを別々に
判定する。性能比較は同一 campaign 内の対測定で行い、凍結した過去値を比較の基礎にしない (D496)。関数単位の軸の偵察と
小比較でも、参照は同じ job に置き、job 内の方策の順序は job 番号で巡回させる (D2234・D2240)。

ビルドに要求した条件 (定義マクロ) が実際に供給され、実行側で同じ意味を持つかは、測定の前に条件関門で
検査する (D1198)。関門は「供給されたか」と「実行側で同じ意味を持つか」を別の必須項目として持ち、意味の
証人 (どの分岐が選ばれたかの観測) を宣言した箇所ごとに確かめる。2026-09-20 には `#ifdef` 形の証人と
複数箇所に現れる指令の扱いが加わった (D2182)。2026-09-26 には、`BACKOFF_FIXED` の意味検査を build する protocol の翻訳単位で
行うようにした (MoCC なら MoCC の実装 file と実行体、D2248) — Silo の翻訳単位に固定したままだと、MoCC を build しても Silo の証拠で
通り、適応 backoff のまま走った候補が値 <v> の候補として台帳に載りうるからである。成果物には関門の admission record と、供給・
意味検査の元 record を指す `record_ids` (digest) が残る。ただし元 record の本体は残らない。

一回の測定内のばらつきと、別 run 間の比較に使う noise floor は区別する。現行環境の走行間ばらつきは
3 workload について下限 (cold-boot と温度ドリフトを含まない) が取れており、その値を「判定下限を較正した」
とは読まない。性能差の解釈には、比較対象と競合条件に対応する between-run floor を用い、別の対象で得た
定数を無条件に流用しない。関数単位の軸の 3% 線も Pegasus・新骨格で較正していない暫定値である (D2234 限定)。

床値には別の量として、B-4 (還流 ablation) が用いる **床値 pair protocol** がある (`floor-pair-spec/v3`)。
同一候補について独立な 2 つの side session を作り、各 side で candidate と reference を測り、side ごとの
reference を分母にした相対利得の差 `D` を求め、閉じた stratum の最大を成果物へ記録する。測定手順は
workload 別の 3 spec として結果を見る前に凍結し (D2138)、2 つの時間窓 (各 62 標本) と finalize を別 job で
走らせる (D2145)。2026-09-19〜20 に第 1 窓の 3 job が完走したが、第 2 窓・finalize・値の比較・集約・採用は行っていない。
この `D` の床値と、8b holdout の official 床値 (1 走行の実測 noise が配線下限を下回り、配線下限で決まった
値。科学的に十分な床とは主張しない — D2120 項 2、D2180) と、上の between-run floor は互いに別の量であり、流用しない。

試行数や検証相を満たさない中間走行は記述的に報告し、有意差や LLM 固有の優越を主張しない。

## 5. raw screening と certified 経路

本稿では、未検証の性能観測を使う候補の絞込みを raw screening と呼ぶ。性能値が存在しても、それだけでは
certified な fitness にならない。性能だけの探索・診断成果物と、評価 pipeline の明示的な bench-first
screening は区別する。後者は検証の前に性能を測って明白に遅い候補を落とす最適化であり、すべての合成反復で
使う既定経路ではない。

bench-first screening では、基準値と floor から定めた保守的閾値を下回り、かつ測定が安定し abort 率による
曖昧さがない候補を、未認証のまま棄却する。基準点が古ければ通常の検証先行へ戻す。スクリーニングに残った
候補も、指定された全検証を通過して初めて COMMIT に進める。したがって、検証前の `BENCH_DONE` は測定記録で
あり、正しさの合格証ではない。棄却候補には採用用の fitness を付けない。

B-5 と比較基盤の候補経路には、投入前の共通 **Tier0** がある (D2215)。pipeline の性能用 build と同じ経路・引数で 1 本を作り、全 arm・全候補・
全 workload で同じ argv の固定スモーク (4 thread・200 tuple・1 秒ほか) を 1 回走らせ、rc 0・commit > 0・throughput が有限正であることだけを見る。
不通過は候補起因として提出機会 A だけを消費し、評価予算 B は消費しない。スモークの数値は fitness・性能指標・生成器への射影へ流さない (規律 1)。
**Tier0 の通過は certified を意味しない。** 検証・anomaly の即失格・性能測定は従来どおり行う。

certified 経路でも、生成直後の評価結果だけを信じて後段へ転記しない。保存済み記録の対応関係と受領証を
読み手が検査し、用途に応じて受理した証拠を消費する。探索用の名前空間にある段 4 の成功記録を、正式な比較や
選択の証拠へそのまま流用することはできない。履歴を読む用途と、現行の certified な判定に使う用途も区別する。

採用候補を性能 workload そのもので認証する **certification 経路** (A-2 / A-6) は、受領証の束縛で成り立つ。
投入時の受領証、完了時の受領証、取得時の受領証を attempt ごとに create-only で記録し、cell ごとの raw 結果を
manifest で束ねる。各 cell には、実際にビルドされたソースの `src_token` と、それが policy の要求 (stock か
採用値か) に対応するかの `source_binding_status` を記録し、対応しない cell は認証しない。外側の status は
workload をまたぐ論理積で決まり、いずれかの cell に anomaly かソース不一致があれば `reject`、正しさが
未確定なら `indeterminate`、性能が未確定か効果が全 workload 分そろわなければ `performance-indeterminate`、
全 workload の効果が正なら `observed-positive`、そうでなければ `reject` である (この順に判定する)。
成果物は noise floor の状態が `open` であること、ソース経由の証拠が compile-out の証明にならないこと、
独立観測の限界を自ら宣言する。correctness 側の実 argv は既存 pipeline では独立に記録されておらず、
workload の束縛は campaign lock と pipeline constructor による (D1257)。`observed-positive` と `reject` は protocol の status であって、
研究の成功・失敗の宣告ではない。同じ経路を、正式な判定を作らない descriptive な用途 (同一候補の 3 workload 同時期
測定) に別 study として使うこともある (D2162)。

P2-4 の推定対象に合わせた対測定 (A-1) は、均衡 5 反復ブロック交互の配置で各 workload に 30 対を取り、対差
平均と登録済みの区間推定で分類する経路である。分類は「区間が床の外にある」(`resolved-above-floor`)、
「区間が床の内にある」(`bounded-below-floor`)、「未解決」の 3 値で向きを持たず、向きは平均の符号で読む。
本走 policy (v3-sized) は非認証 lane (`formal=false`、`promotion_prohibited=true`) であり、その反転は文書
編集では行えない。投入は 1 attempt ごとのユーザー認可で行い、既存の submit 経路は、先行 attempt が性能測定
の開始 (bench barrier) に到達した study の再投入を qsub の前で拒否する (規律 2 由来の gate)。2026-09-20 に、ドライバ側の
定数 1 件と耐久 base に置く exact な認可 record の一致でだけ、先行 attempt-0001 を対象に gate を解除する機構が加わり (D2178)、
同日この経路で attempt-0002 が投入されて 3 workload とも完走した (entry 1755)。2 attempt は「同一配置の反復で分類と符号が一致した観察」
として並記し、プールした推定量・差・比・再現判定は作らない (D2194 項 6)。

## 6. 選択と評価の射程

最終的な選択契約は、証拠が支持する新しい候補、既存実装 (stock)、差を支持できない場合の同率 (tie) を区別
して返すことである。stock や tie は有効な「改善を示さなかった」結果であり、新しい CC の実証達成には
数えない。候補に性能値がない場合や比較の前提が成立しない場合を、有効な tie と取り違えない。段 4 ドライバは
反復と停止を実行する部品であり、一般的な統計比較による最終勝者を自動決定する実装とは位置づけない。

ワークロード記述に基づく段 8b の選択部品は、検証した descriptor と固定候補一覧を入力にし、一覧内の候補
一つと理由を出力させる。不正な出力は既定候補に置き換えず拒否する。ここでの候補の指名は予測であり、
性能測定・正しさ検証に基づく最終評価とは別である。正式評価では、事前登録で定めた比較対象、検証構成、
floor、標本設計、報告規則を満たす必要がある。

評価設計は、同一編集面・同一予算の非 LLM 対照、軸内機械探索、還流の有無などを分けて比較する。逐次探索の
個々の試行を独立標本とせず、採用した登録に従って系列を検定単位とする。多重比較、有意性を主張しない場合、
全ワークロードの退行を含む報告を結果を見る前に定める。旧主実験の登録・改訂履歴を、新しい全比較が実走済みで
ある証拠としては使わない。B-4 は記述統計に限定する裁定が採用されており、適格な赤 precursor が必要数に
満たない間は実走しない。その実装は部分的である — 記録の writer は create-only、材料 report の 4 分類は未実効、
launcher は単一 arm までで、記述統計への限定は機械の受理集合を変えず、正式な certified 選択への接続も未完で
ある (D1936 項 9、D2016)。対応証拠の carrier と参照点の定義は実装された (D2213) が、本走・床値の第 2 窓は無い。

backoff の機序を帯域外へ広げる B-10 は、結果を見る前に固定した 2 本の事前登録で運用する。待ち方 grid は
`constant` 対 `symmetric-modulo` の対比を workload 族ごとに Holm で判定し、cell の効果量を等価域と比べる。
静的右 tail は隣接区間ごとの状態 (`saturated` / `declining` / `indeterminate`) を区間推定から決め、
workload の集団判定と全体の verdict を導く。同じ事前登録に対する第 2 cohort は、地位を投入前に事前登録の末尾追記で
固定してから走らせた (D2157)。2 cohort の統合 verdict は作らない。

事前登録は凍結物として扱い、確定値の追記が凍結束縛 (source sha256) に阻まれる場合は、未履行の繰延べと
して別の記録に日付付きで残す。事前登録の文書が存在することは測定の認可にならず、発効は本走認可を伴う日付付き
commit とその決定による。最終候補の長時間検証 (B-8) は 2026-09-21 に発効し、3 値判定まで済んだ (第 3 節)。

**生成器対照 (B-5)** は B-8 とは別の登録 (事前登録 v1、`docs/b5-generator-contrast-preregistration.md`、D2158) で、3 arm (LLM・
random・格子の sweep) を同じ評価経路・同じ予算で比べ、系列を検定単位にして workload ごとの 2 比較 (LLM 対 random、LLM 対 sweep) を
判定する。本走の投入経路は repo に最小実装され (driver の registered 出力、job body の受け渡し、launcher の逆順組の schedule と stage 投入、
LLM の巡 tool と model の記録、D2221)、LLM の親 session は 1 系列に 1 本・同時 4 本・1 機会の待ちの上限 2,700 s (D2216)、探索 3 arm の
walltime は共通 (D2217)、LLM は起動構成で exact ID に固定し記録と食い違えばその機会では何も公開しない (D2222)。発効束の draft
(D2222) の後、第 32 回の裁定 (D2227 項 2) が本走 (k = 3、総 wall 上限 ≈ 680.7 node 時間) を認可した。**本走は block 1 の stage 1 (12 job) を
2026-09-23 に投入した後に止まっている** (entry 1866)。LLM の親 4 本が週次の利用上限 (429) で同時に止まり、series job が提案待ちの上限で
系列を閉じたため、report の規則 (欠測が 1 系列でもあれば判定不能) のままでは現行 cohort `b5-registered-v1` の 6 比較すべてが判定不能 (欠測)
になった (F1050)。write-heavy の random 2 系列は系列開始 stock の品質欠測で、その比較は再開しても判定不能である。事前登録は品質欠測を
retry せず fallback でも埋めない。計算の約 95% が検証だったことを受けた費用削減の案 (LLM の待ちを計算 node の外へ、取得済み trace の同時検査、
系列数・workload の縮小) は、いずれも規律 2 の検査本数・判定器・判定・bench 前の関門を変えない形で比べられ、v1 を stage 1 で閉じて開示し
新しい cohort として登録し直すかを含めてユーザー裁定を待つ。B-5 の発効 commit は採用時点の main の祖先でない branch にある。
**判定不能は report の規則の出力であり、性能の結果ではない。** 上限付き試走 (2026-09-20〜21、53 論理 session) の結果は主標本に入れない。

**探索の独立反復 (試走) と未知条件への転移** も、測定の前に規則を登録した。試走の事前登録 v1 (`docs/search-repetition-trial-preregistration.md`、
D2231) は、5 手法 × 課題ごとに独立な系列を複数本走らせ、評価数を揃えた族と経過時間を揃えた族を分け、本比較の系列数を試走の対差 SD の
計画値から決める規則を固定した。2026-09-23 にユーザーが「write-heavy だけで試走」を選び、追補 1 と発効束のとおり発効した (D2245。
S1-wh × 5 手法 × 3 系列 + block job 3、実装は比較基盤の着地 commit `7ea9aa09d` に固定、CCBench は campaign の pin `511c9538`)。block 1 の 6 job で
random・sweep・LLM の 3 系列が欠測し (系列開始 stock の静定待ちの時間切れと、LLM 親の週次上限)、2026-09-26 にユーザー指示で block 2・3 の
投入を止めた (entry 1863)。評価 1 回の約 91% が検証で、検証の trace 5 本を同じ node で同時に検査すると判定を全件一致させたまま検査の wall が
0.24〜0.26 倍になった (静定待ちの延長と組で使う)。正典の記録は費用を削る案を「ユーザーの確認」を要する択として残し、そのうち検証の同時化を
採る判断はユーザーの委任を受けた親裁定として repo 外の job 領域にだけ記録されている。**試走の手法間の比較・T_c・対差 SD は無い。**
転移の事前登録 (YCSB 版 v1 = D2223、TPC-C 版 = D2228) は、留保条件 (学習条件の錨から 1 因子ずつ動かした条件) と、それを生成・選択に使わない
義務と解析規則を着地時点で固定し、測定の発効を計算確認の別の決定に分けた。実行器と解析器 (`orchestrator/campaign/t2851_transfer_runner.py`・
`t2851_transfer_analysis.py`、D2241) は選定と発効を凍結入力として受け取り、発効の記録が無ければ留保 cell を測定前に拒否し、検証は性能と別の
trace 有効 binary で判定器の条件を変えずに certified / disqualified / indeterminate へ写す (TPC-C は認定経路を接続するまで indeterminate)。
**留保 cell は 1 走もしておらず、転移の測定は発効していない。**

試行記録と材料レポートは、提案、拒否、検証、測定の出所を追うための補助成果物とする。材料レポートの
機序仮説層は、critic の帰属記録を非 certifying の二次 view として射影するものであり、機序の証拠ではない (K2 の 2・3・4 巡目に
適用された)。LLM が述べた機序は仮説であり、説明の生成や記録の整合性から説明の忠実性・因果機序の同定を推論しない。
本草稿は未完の性能結果を補わず、研究全体の無人化や任意 CC 合成の達成も主張しない。
