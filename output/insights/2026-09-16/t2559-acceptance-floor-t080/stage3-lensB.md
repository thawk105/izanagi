### 所見1 — 「base 144秒」は構築単体の測定ではなく、費用分解が成立しない

**根拠:** [T:1048](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2559-accept-floor/orchestrator/tests/test_s8b_oracle_driver.py:1048) のテストは、別 process の呼出しを **逐次2回**行う。各回は T:1000 の base→test コピーを実行する。さらに Git config 確認、process 起動・通信を含み、junit の集計設定によっては fixture teardown の base 削除も載る。しかも `issue_receipt=False` なので、T:1460 以降の発行処理を測っていない。

したがって144秒は概念的には、

`発行なしbase構築 + コピー2回 + process/Git確認等 [+ teardown]`

であり、発行あり consumer の base 構築時間ではない。

**影響:** plan:185 の `144 + 8.47 + 70 ≈ 222.51` は異なる測定対象を足した数値的一致にすぎない。plan:189 の「base 118.54秒未満」も根拠を失う。plan は発行なしという留保には触れているが、コピー2回の混入を織り込んでいない。

**提案:** 親の比較実測では、発行あり／なしの実 builder 区間、共有待ち、各コピーを区別する。144秒を base 単体として使う見積りは撤回する。

### 所見2 — 197秒条件は残余固定の仮定に依存し、161.1秒への床移動も未確定

**根拠と算術:** 提示されたモデルでは、

- `wall = 65 + 29.6 + span`
- 300秒未満には **`span < 205.4秒`**
- 現状の span と最長 node の差は `231.0 − 222.51 = 8.49秒`

この8.49秒を不変と仮定すると、最長 node は **`205.4 − 8.49 = 196.91秒未満`**。親の197.01秒との差0.10秒は、内訳の和325.6秒と代表値325.5秒の丸め差であり、本質的な誤算ではない。

ただし、最長 t080 一本だけを短縮しても、提示値では他の t080 が200〜222秒に残る。**全 t080 と他の競合 node が161.1秒を下回った場合に限り**、親提示の `test_repository_candidate_uses_real_s8c_budget_module` が最長単体 node の候補になる。

さらに S:325、S:381 の割付は file/group 単位の shard 割付であり、worker の総占有を最長単体 node と等しくするものではない。`orchestrator/tests/conftest.py:1012` は初期配布が48 worker × 2 unitであることも明記する。

**影響:** 161.1秒まで床が下がる理想化では `65 + 29.6 + 161.1 = 255.7秒`、旧残余も足せば264.19秒。しかし残余・後続 unit・排他 group の占有は変わり得るため、これは予測値ではない。197秒も一般的な必要条件ではなく、**残余固定モデル内の条件**である。

**提案:** 既存 report の worker 占有と timeline で、最長 node の短縮後に残る worker の仕事を比較する。300秒判定は各走の最遅 shard receipt に戻す。別々の中央値を合成した式だけで達成を宣言しない。

### 所見3 — 案Cが削る総費用と、wallに露出する費用を区別できていない

**根拠:** [T:918](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2559-accept-floor/orchestrator/tests/test_s8b_oracle_driver.py:918) は key ごとの排他 lock 内で base を構築する。T:980 で consumer が待ち、lock を出た後に各コピーを行う。D1708は同時 miss の共有化が構築を同時間の待ちへ置き換えるだけだった実例を示す。

案Cの実効短縮は、同条件での

`従来add費 − blob移送費 − index費 − 残存add費 − 再利用判定等の追加費`

で決まる。この符号は未測定である。共有構築回数や t080 所要総和が減っても、それだけでは wall の短縮を示さない。

**影響:**

- 非律速 key の構築短縮は、他 worker の実行に隠れて wall 効果ゼロになり得る。
- add を同時間の pack 作成・移送へ置換すれば、lock 保持時間も consumer の待ちも減らない。
- 律速 key が短縮しても、他の t080、次点 worker、他 shard に床が移れば以後の削減は隠れる。

brief:19 の「2611.1秒＝CPUの32%」も不適切。junit 所要には lock 待ちやI/O待ちが含まれ、CPU時間ではない。

**提案:** 案Cは構築回数ではなく、律速 key の完成時刻をどれだけ早めたかで評価する。既存の割付・duration ledgerを揃え、worker 占有と最遅 shard wallへの伝播を確認する。

### 所見6 — A/B各1走では、目標25.5秒を走間変動から分離できない

**根拠と算術:** 提示分布の幅は `482.7 − 198.8 = 283.9秒`、目標25.5秒の約11.1倍。中央値227.8秒から最小198.8秒への自然変動だけでも29.0秒あり、目標短縮を上回る。

ただし、**n=103・中央値・最小・最大だけから必要走数は決められない**。分散、中央値付近の密度、時系列相関が欠けている。しかもこれは代表nodeの分布であり、判定対象の最遅shard wallの分布ではない。

参考として、独立な正規近似、平均差25.5秒、両側5%・検出力80%なら、各条件の必要走数は概算で、

`n ≈ 2(1.96 + 0.84)² σ² / 25.5²`

となる。

| 仮定するwallの標準偏差 | 各条件の走数 |
|---|---:|
| 20秒 | 約10走 |
| 50秒 | 約61走 |
| 100秒 | 約242走 |

これは感度分析であり、提示分布から推定した必要数ではない。中央値の検出力にもそのまま使えない。

**影響:** 「A/Bで下がった」だけの完了条件は、自然変動を成果として採用できてしまう。

**提案:** 親の実測は同一入力・割付で順序を釣り合わせた対比較にする。まず既存103走の対応するreceiptからwallのばらつきを見積もり、対差の分散がなければ8〜10対程度を予備測定として追加数を決める。この予備測定数は効果証明の保証ではない。新しいgateや台帳は不要。
