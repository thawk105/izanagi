## 親自身の provisional 裁定 (P1) の決着

- **(P1-a) 支持 (限定つき)。** 記録分類としては支持される。`whiteboard.result == "rejected"` は
  diff 検疫 reject に対応し、verify・liveness 赤は `fail` になる。
  **ただし「原因が純粋な diff 検査だけ」という読みは倒れた** — sort / trigger では
  oracle 拒否・auditor 拒否も同じ `record_diff_reject` 経路を通る。base の読みには影響しない。
- **(P1-b) 訂正。** 「§5 の母集合欄が空だから 3 真偽値を真にできない」という論法は**循環であり誤り**。
  母集合欄は適格判定と選択の結果を書く欄である。
  **正しい根拠は別にあり、3 条件はそれぞれ独立に真にできない** (insight の表を参照)。
  結論 (今日は適格と確定できない) は維持する。
- **(P1-c) 支持。** 手作り proposal で検疫を落とす経路は母集合の製造にあたり、D1936 項 8 が
  不採用にしている。
- **(P1-d) 支持。** CLI 自身は LLM を呼ばない。ただし「開発 wave 内で通常合成を行えるか」は
  実装から導ける話ではなく、親の運用裁定である。**本 wave では行わない**と裁定する。

依頼文には「成功例への置換と母集合を作る作業であり」という一節があった。

不採用にしている**」であり、D1936 項 8 の本文も「成功例への置換、固定 201 だけの無言の削減、
母集合を作るための追加基盤は採らない」である。

**成功例への置換も母集合を作るための追加基盤も採らない**という結論は変わらない。
