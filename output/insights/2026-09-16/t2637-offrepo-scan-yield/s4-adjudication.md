## B-2. 採る案 — 2 段構成

**第 1 段: 並列走査 (案 6)。** 範囲・規則・出力を一切変えないので、D2034 の順序を満たし、
安全条件の議論を要しない。実測で 3.8〜4.4 倍。ただし 2 つの前提を先に片付ける必要がある。

1. `test_initial_patch_contains_no_parallel_execution` が `concurrent.futures` と
   `ThreadPoolExecutor` の不在を assert している。D985 の結論がテストとして固定されているので、
   **並列化はこのテストの改訂を伴う。ユーザー裁定が要る。**
2. Python の thread pool で C と同じ倍率が出るとは限らない。`os.scandir` / `os.lstat` は GIL を
   解放するが、per-entry の Python 処理は解放しない。**先に小さい prototype で実測する。**

**第 2 段: 用途分離 (案 5)。** 第 1 段でも cold が 300 秒に入らない見込み (387〜531 秒) なので、
掃除の入口では走査を明示 off にし、救出 triage では full を走らせる。C の 5 条件を満たすこと。

**2 段は独立に効き、順序を入れ替えない。** 第 1 段は救出 triage の全走査も同じだけ速くするので、
第 2 段を採っても無駄にならない。

## C. 案 5 に付ける条件 (両レンズの must-fix を採用)

1. **D2034 の順序を満たす。** 同範囲の定数削減 (並列走査) を先に実測し、それで 300 秒に入らないことを
   示してから範囲限定を有効化する。
2. **未実施と否定結果を分離する。** `off` の注記無しを「全走査して一致無し」と表示しない。
   root 未指定・拒否・巨大 blob・読出し失敗・`reference_failure` も「確認不能」として残し、
   `scan_performed=True` を全対象の確認成功と読み替えない。
3. **台帳への影響を開示する。** `off` で再表示された commit は `unledgered-audit-finding` を増やし、
   rescue gate の rc が 0 → 3 に変わりうる。追記候補集合が増える条件と、別実行への引き渡し契約を書く。
   T-2640 の通知契約を本 wave で暗黙変更しない。
4. **既裁定の対象範囲を越えた破棄を禁じる。** D970 は特定の 28 件、D1031 は追加の 19 件についての
   裁定であり、「控えが一部でもあれば今後の任意の commit を破棄してよい」という一般権限ではない。
5. **off/full の入口と実行主体を固定する。** どの入口が off になるか、分類をどの別実行へ渡すかを
   決め、未配線の入口を高速化済みと数えない。`check_branch_rescue.py` の子プロセス環境
   allowlist も同時に直さないと二度目の全走査が残りうる。

## E. 副産物として見つかった実在の欠陥 (本 wave では直さず記録する)

1. **境界照合の helper 2 つが既に非等価。** `_has_bounded_path_reference()` は左右だけを見るが、
   本番の `_bounded_path_reference_matches()` は探索根末尾から最初の境界までを取る。
   path 内部に空白がある候補で両者の判定が割れる。
2. **hardlink の alias 全配布が D247 条件 2 (basename 一致) の穴になっている。**
   異 basename・同 OID・同 inode の owner に、参照済み alias が配られる。
3. **`check_branch_rescue.py` が監査を再実行する。** 既存の root 環境変数がある環境では
   掃除 1 回で全走査が 2 回走りうる。
4. **並列実装を静的に禁止するテストが存在する** (`orchestrator/tests/test_audit_dangling_commits.py`)。
   案 6 を採るならこのテストの扱いを裁定に含める必要がある。
