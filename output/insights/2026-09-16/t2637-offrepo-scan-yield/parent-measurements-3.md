# 親の実測 その 3 — 定数削減 (並列走査) の実測

D2034 が要求する「範囲を削る前に定数を下げる方を先に試す」に対する実測。
段 2 プランと段 3 の両レンズが先行条件として名指しした実験に答える。

## 11. 親の先行測定の誤りと訂正

**`parent-measurements.md` §2 の「C 実装・並列 (bfs 4.1.1 既定) の cold 全走査 1583.99 秒」は誤りである。**

`find` はこの環境ではシェル関数であり、`claude` binary を `bfs` として起動する shim である
(`declare -f find` で確認)。しかし `/usr/bin/time` 越しに呼ぶとシェル関数が迂回され、
実際には `/usr/bin/find` = **GNU findutils 4.8.0 (単一 thread)** が走る。

訂正後の事実:

- **1583.99 秒は cold・単一 thread の C 実装の値である。並列は一度も測っていなかった。**
- Python cold 2429.3 秒 / C cold 1583.99 秒 = **1.53 倍は純粋な言語差であり、並列化の寄与はゼロ。**

段 3 の両レンズが「言語・syscall 形態・並列度が混ざっている」と指摘したのは正しく、
実際には混ざってすらおらず並列度が欠けていた。

## 12. 並列度の比較 (2026-09-16、warm、探索根全体)

`bfs` を絶対 path から `-S dfs -j<n>` で直接起動し、GNU find と交互に測った。
対象は `/work/1/SFC/tanab/dev-wave-jobs` 全体。

| 実装 | thread | elapsed | user | sys | file 数 |
|---|---|---|---|---|---|
| GNU findutils 4.8.0 | 1 | 243.94 | 1.07 | 43.82 | 1,761,075 |
| bfs 4.1.1 | 1 | 252.51 | 1.20 | 42.73 | 1,761,081 |
| bfs 4.1.1 | **16** | **43.78** | 1.92 | 61.70 | 1,761,112 |
| bfs 4.1.1 | 1 (再走) | 230.29 | 1.07 | 40.84 | 1,761,112 |
| bfs 4.1.1 | **16 (再走)** | **66.67** | 1.94 | 64.94 | 1,761,134 |

- **単一 thread は 3 走とも 230.29〜252.51 秒で安定** (最大/最小 = 1.10)。
  GNU find と bfs -j1 が一致するので、実装差ではなく thread 数が効いている。
- **16 thread は 43.78 秒と 66.67 秒** (最大/最小 = 1.52)。D958 の判定手順では
  最大/最小が 1.5 を超えたら 3 走追加を要するが、本 wave は受理判定ではないので追加していない。
  **保守的に最大どうしで 252.51 / 66.67 = 3.8 倍**、平均どうしなら 242.2 / 55.2 = 4.4 倍。
- 単一 job dir (`dev-wave-t2397-a1-attempt4`、59,723 file) の warm 実測では
  1 thread 1.53 秒 / 16 thread 0.40 秒 = 3.8 倍で、全体の値と整合する。

**測定順序は単一 thread → 並列 → 単一 thread → 並列 と交互にした。**
各走は 362 MB の一覧を `/home` へ書くため cache を押し出しうるが、
単一 thread の 1 走目 252.51 秒に対し 3 走目が 230.29 秒で**悪化していない**ため、
この交絡は測定を支配していない。

## 13. D985 の並列化否定の射程

D985 は「並列化は実測で否定済みである (16 thread で改善 20%)」として索引化とともに却下した。
根拠の実測は `docs/archive/worklog-phase3-0826-980.md` の
単一 thread 157.98 秒 / 4 thread 141.83 秒 / 8 thread 132.56 秒 / 16 thread 125.80 秒 である。

**この 20% は Python 実装の性質であって、この filesystem の性質ではない。**
同じ Lustre 上で C 実装は 3.8〜4.4 倍を出す。Python の thread は per-entry 処理で GIL を保持し続けるため、
metadata 待ちを重ねられない。

**したがって D985 の「並列化は効かない」は、実装を Python に固定した場合の結論としては正しく、
機構一般の結論としては成立しない。**

なお `orchestrator/tests/test_audit_dangling_commits.py` の
`test_initial_patch_contains_no_parallel_execution` が、tool の source に
`concurrent.futures` と `ThreadPoolExecutor` が現れないことを assert している。
**並列化を採るならこのテストの扱いを裁定に含める必要がある。**

## 14. cold での見込みと、測っていないこと

cold の単一 thread は 1583.99 秒 (実測)。並列の cold は**測っていない**。
warm で得た 3.8〜5.8 倍をそのまま当てると走査は 273〜417 秒になる。

- cold では待ちが長いぶん並列の余地は warm より**大きい**はずなので、この外挿は下振れ側に安全である。
  ただし外挿であって実測ではない。
- 監査全体では走査以外が cold 113.5 秒 (2026-09-15 の記録) / warm 22.7 秒 (今日の実測) 要る。
- したがって cold の監査全体は **387〜531 秒**と見込まれ、**D958 の 300 秒には入らない公算が高い。**
  現状の 2542.8 秒からは 5〜6.5 倍の改善になる。

**測っていないこと:**
- cold の並列走査。cache を意図的に落とす手段が無いため本日は測れない。
  測るなら間隔を空けた別日か、別 node で 1 走目として取る。
- Python に thread pool を入れた場合の実効速度。C の値がそのまま出るとは限らない。
- 16 thread のばらつき (1.52) の原因。D958 の手順どおりなら 3 走追加が要る。
