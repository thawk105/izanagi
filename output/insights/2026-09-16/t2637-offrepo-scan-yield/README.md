## 2. 収量 0 の説明 — 成立するところまで

bytes 一致した 17 file はすべて変異 harness の出力 (`mutation-spec*.json` /
`mutation-ledger*.json` / `mutation-out*.json` と `s6/analyze.py` 1 件) で、7 つの job dir に分かれる。
**7 dir はすべて landed 文書から参照されている。** それでも条件 5 が発火しないのは、参照の書かれ方による。

D248 は境界 byte を空白類・引用・括弧に限り、**それ以外のすべての byte は path を延長する**と定める。
`/` も `:` も境界ではない。landed 文書は job dir を「より長い path の接頭辞」として書き
(`.../dev-wave-t1086-report-receipt/brief.md`)、引用慣習は `path:line` 形式である。
したがって祖先 dir の参照も、cite された file 自身の参照も、境界条件を満たさない。
実測で `dev-wave-t1086-report-receipt` が境界 byte を直後に伴って現れる landed file は 0 件だった。

**ただし「祖先条項は構造的にほぼ不発」という一般化は成立しない。**
段 3 sol が現存の成立経路を名指しした — `orchestrator/manual_probes/test_t2397_a1_source.py:21` が
job dir path を引用符で囲んで書いており、引用符は境界 byte なので条件 5 が成立する。
親自身の被覆データでも同 dir が最大の被覆 (59,723 file) だった。
既存テストにも祖先参照の陽性例が 2 件ある。
**採用できる結論は「今回一致した 17 file には有効な landed 参照が無く、接頭辞表記と `path:line` 表記が
その説明になる」までである。**

## 3. 走査が買っているもの

走査は 2 つの成果物を出す。

1. `suppressions` (条件 1〜5 の連言) — 直近 2 走で 0。
2. `unreferenced_copies` (条件 1〜4 を満たし 5 を満たさない注記) — 17 件。

**2 には実在の consumer がある。** ただし機械 consumer ではない。
`tools/check_branch_rescue.py` は監査を別プロセスで再実行するが、commit 集合・rc・所要しか読まず、
D970 の外部控え分類はしない。消費しているのは D970 / D1031 に従って破棄・救出を分類する
人・AI の triage である (`docs/archive/worklog-phase3-0827-1019-1020.md`)。
同じ記録は、監査の注記が basename 一致条件のせいで不完全だったことも実測している。

したがって設計上の論点は依頼の当初の枠組みとは別のところにある。
**掃除が走査から得ているものは実質ゼロで、注記を要るのは救出 triage という別の活動である。**

### 親の測定の誤りと訂正

**`parent-measurements.md` §2 が「C 実装・並列」と書いた 1583.99 秒は単一 thread である。**
`find` はこの環境ではシェル関数 (bfs の shim) だが、`/usr/bin/time` 越しに呼ぶと迂回されて
GNU find が走る。並列は一度も測っていなかった。段 3 の両レンズが「言語・syscall 形態・並列度が
混ざっている」と指摘したのは正しく、実際には混ざってすらいなかった。

## 5. 採る案 — 2 段構成

### 第 1 段: 並列走査 (定数削減)

D2034 の「範囲を削る前に定数を下げる方を先に試す」に従う。
**範囲・規則・出力を一切変えないので、受理集合の議論を要しない。** 実測で 3.8〜4.4 倍。

先に片付ける前提が 2 つある。

1. `orchestrator/tests/test_audit_dangling_commits.py` の
   `test_initial_patch_contains_no_parallel_execution` が `concurrent.futures` と
   `ThreadPoolExecutor` の不在を assert している。**D985 の結論がテストとして固定されているので、
   並列化はこのテストの改訂を伴い、ユーザー裁定を要する。**
2. Python の thread pool で C と同じ倍率が出るとは限らない。`os.scandir` / `os.lstat` は GIL を
   解放するが per-entry の Python 処理は解放しない。先に小さい prototype で実測する。

### 第 2 段: 用途分離 (掃除では走査 off・救出 triage では full)

第 1 段でも cold は 300 秒に入らない見込み (走査 273〜417 秒 + 走査以外 113.5 秒 = 387〜531 秒)。
そこで掃除の入口では走査を明示 off にし、救出 triage では full を走らせる。
**findings は 1 件も減らない** (固定した core snapshot について `findings(full) ⊆ findings(off)`)。

付ける条件は 5 つ。

1. **D2034 の順序を満たす。** 第 1 段を先に実測し、それで 300 秒に入らないことを示してから有効化する。
2. **未実施と否定結果を分離する。** `off` の注記無しを「全走査して一致無し」と表示しない。
   root 未指定・拒否・巨大 blob・読出し失敗・`reference_failure` も「確認不能」として残し、
   `scan_performed=True` を全対象の確認成功と読み替えない。
3. **台帳への影響を開示する。** `off` で再表示された commit は `unledgered-audit-finding` を増やし、
   rescue gate の rc が 0 → 3 に変わりうる。追記候補集合が増える条件と、別実行への引き渡し契約を書く。
4. **既裁定の対象範囲を越えた破棄を禁じる。** D970 は特定の 28 件、D1031 は追加の 19 件についての
   裁定であり、「控えが一部でもあれば今後の任意の commit を破棄してよい」という一般権限ではない。
5. **off / full の入口と実行主体を固定する。** `tools/check_branch_rescue.py` は監査を子プロセスで
   再実行するので、環境 allowlist を同時に直さないと二度目の全走査が残りうる。

## 6. 採らなかった案

| 案 | 理由 |
|---|---|
| 索引化 + 増分更新 | 鮮度上限は D247 条件 2〜4 の証明にならない。子孫 file の内容変更は親 dir の mtime で検出できない。live 再検証が必須で、それを入れると索引の利得が縮む。 |
| 定期監査 + 鮮度上限つき cache | 安全な実体は「鮮度つき候補 cache + live 再検証」であり、「鮮度内の結果をそのまま採用」ではない。無効化問題が残る。 |
| 探索根 (job dir) の退役 | **継続課題として残す。** D985 が採った案で `docs/phase3.md` に保留記録がある。粗い比例モデルでは残せる比率が 8〜12% で、部分退役では足りない可能性が高い。復元可能性と保持期限を同じ変更で固定する必要がある。 |
| 候補先行 (走査を landed 参照の最小被覆部分木に限る) | **不採用。** 親が推していたが、段 2・段 3 の両方が反例を出した。 |

### 候補先行を採らない理由

抑止条件 5 は候補 path とその祖先のいずれかが landed 文書に境界付きで現れることを要求するので、
抑止されうる file は landed 参照の最小被覆部分木の中にしかない。実測でこの部分木は
278,272 file / 25,416 dir = 全体の dir 数の 13.1% であり、7.6 倍の縮小になる。
bytes 一致した 17 file はいずれもこの部分木の外にあり、監査自身の `suppressions=0` と一致した。

**しかし現行実装との厳密等価は成立しない。** 4 型の反例がある。

1. **hardlink の owner/alias 交差。** 実装は `(OID, device, inode)` ごとに owner と alias を集め、
   比較成功時に全 owner へ全 alias を配る。到達不能側に同じ blob の `a.py` と `b.py` があり、
   外部に `/R/out/a.py` と `/R/in/b.py` が hardlink で在り、landed 参照が `/R/in/b.py` だけの場合、
   現行は `a.py` も抑止するが候補先行では消える。
2. **hardlink 代表の交代。** 現行の代表が open 不能で被覆内の別 alias が読める場合、
   枝刈りで代表が交代し**現行には無かった抑止が生まれる**。
3. **中間 directory symlink。** 現行は `followlinks=False` で辿らないが、被覆 path から直接
   開始すると越えてしまい、**抑止が増えうる**。
4. **境界 byte を含む path / 探索根。** `_has_bounded_path_reference()` は左右だけを見るが、
   本番の `_bounded_path_reference_matches()` は探索根末尾から最初の境界までを取る。
   path 内部に空白がある候補で両者の判定が割れる。

2 と 3 は不変条件「抑止を広げない」に直接違反する。

## 7. 副産物 — 実在の欠陥 (本 wave では直していない)

1. **境界照合の helper 2 つが既に非等価。** `_has_bounded_path_reference()` と
   `_bounded_path_reference_matches()` が、path 内部に境界 byte を含む場合に割れる。
2. **hardlink の alias 全配布が D247 条件 2 (basename 一致) の穴になっている。**
   異 basename・同 OID・同 inode の owner に参照済み alias が配られる。
3. **`tools/check_branch_rescue.py` が監査を子プロセスで再実行する。**
   既存の root 環境変数がある環境では、掃除 1 回で全走査が 2 回走りうる。
4. **並列実装を静的に禁止するテストが存在する。** D985 の結論がテストとして固定されている。

## 8. 主張しないこと

- 「抑止は将来も構造的に 0」とは言わない。2 走は同じ 17 file を再観測したもので、独立標本ではない。
- 「292 → 0 の原因は D957 の除外」とは言わない。同じ走に両方が併存していた。
- 「cold でも並列は 3.8 倍」とは言わない。cold の並列は測っていない。
- 「cold と warm の差 5.3〜6.5 倍は cache だけの効果」とは言わない。
  別 checkout・別時点・別混雑度を含む。
- 「これで掃除が回るようになる」とは言わない。掃除 98 分の内訳は監査 42.4 分・
  worktree 68 件の差分検査 14.4 分・救出検査 12.6 分・`git cherry` 約 10 分・撤去約 9 分で、
  監査を 0 にしても約 56 分残る。本 wave が触るのは**監査という一費目**だけである。
- 「D985 の対処は実施されていない」とは言わない。`docs/phase3.md` に D205 で active から除外した
  保留記録と再訪条件がある。正しくは**保留記録あり、実施証拠は未確認**である。
- 「D985 の thread 比較はすべて warm」とは言わない。warm-up 廃棄は監査全体の独立 3 走についての
  記述で、thread 比較全件に同手順を適用したとは明記が無い。言えるのは
  **当時 cold の裏付けが無い**ところまでである。
