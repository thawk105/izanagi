## 1. 実行時 attestation の `effective_clock.method` を実体一致にするか

**確定済み裁定 (i)** は「恒真比較を実体一致へ変える」であり、本 wave は
**活性化の後継判定**でそれを実装した。残るのは**実行時 attestation**
(`env_attestation._recorded_verdict` の当該分岐) をどうするかである。

**未見の事実**: これは **D329 (2026-08-12、同じユーザーの裁定)** の反転にあたる。

- 当時この比較は実体一致だった。それが実投入 `905941.nqsv` を実際に拒否し、
  第 1 世代の登録が構造的に attestation を通れなくなった。原因は
  「probe が第 1 世代の取得後に改良され、現行 probe は旧 method 文字列を二度と出せない」ことで、
  **クロックの実測値は両世代とも 2101.0 MHz で一致していた**。
- ユーザー逐語: 「ソースコードがこれの時に測定しましたみたいな厳格な一致リストや保証まではいらない」
  「参考情報でいい」。commit `c9c6da84` がこれを外した。
- 8/16 の裁定パッケージは D329 にも 8/12 の裁定にも**一度も言及していない**
  (親が全文検索して 0 件)。ただし `docs/failures.md` の F339 は実害の中身
  (方式改訂で全 attestation が落ちる) を記録済みである。

**実装した場合の実測結果**: pegasus の active は第 1 世代で `attestation_mode=required` なので、
**計算ノードでの campaign は最初の WAL 書込みより前に全件停止する**。
同日の実測 `0:913859.nqsv` はこの attestation を通過して build と verify (`certified=true`) まで
到達しており、その経路が閉じる。

**選択肢**

- **(α) (i) の残余を撤回する。** D329 を維持し、実行時の method は provenance のままにする。
  **親の推奨。** 活性化の後継判定に実体一致が入ったことで、
  「新しく有効にする世代は現行 probe で取られたものに限る」という保証は既に得られている。
- **(β) D329 を明示的に覆す。** 計算ノードの campaign は、第 2 世代の活性化
  (= 上位の較正・凍結権限束、人間手番) が済むまで起動できなくなる。
- **(γ) 判定は変えず、receipt の当該行を「判定対象外の provenance」と記録し直す。**
  受理集合は変わらないが、恒真な `verdict: pass` が与える偽の保証は消える。

## 2. 既に ever-active な第 1 世代の自己不整合をどう扱うか

**確定済み裁定 (ii)** は「自己不整合な旧較正を歴史 resolver が検証済みとして受理し続けるのは
止める」である。本 wave は前向きの半分
(新たに ever-active になる較正は自己整合を満たさなければならない) を実装した。

**未見の事実**: 8/16 の裁定パッケージは是正の影響を「第 1 世代期成果物の**歴史**検証が落ちる」と
書いているが、実測では歴史専用ではない。`resolve_by_contract_sha256` の非テスト consumer は 6 件で、
**live campaign の COMMIT 監査 (`wal.py`)、床値 admission、reflux closure を含む**。
唯一の自己不整合 artifact は現に active な第 1 世代なので、gate を置けば今日動いている経路が止まる。

**選択肢**

- **(α) 現状維持。** 前向きの半分だけで閉じ、既存の第 1 世代はそのまま解決できるようにする。
  **親の推奨。** 第 2 世代の活性化が済めば第 1 世代は current から外れ、
  そのときに後ろ向きの半分を入れれば副作用なく閉じられる。
- **(β) 歴史 resolver に自己整合 gate を置き、第 1 世代を明示例外にする。**
  規律 2 を緩めた恒久例外になる (ever-active は単調増加で、例外が消える条件が無い)。
- **(γ) 例外なしで gate を置く。** 上記 6 consumer が今日から止まる。

## 3. 床値 protocol path の shell 層・driver 層を配線し直すか

本 wave は `certified_writer_admission` (preflight) を authority resolver 経由にした。
一方、実投入経路の shell wrapper と 5 module は literal path を持ったままである。
本 wave は「literal が resolver の結果と一致すること」を固定する検査だけを置き、
配線そのものは scope 外とした。

**なぜ返すか**: 世代が前進した後は preflight と実投入が別の protocol を参照しうる。
今日は全て同じ path を指すので実害はないが、「seam が閉じた」とは言えない。

**選択肢**

- **(α) 別 wave で shell と 5 module を resolver 経由へ配線する。** 親の推奨。
- **(β) 現状維持。** 一致検査が tripwire として働くので、ずれた瞬間にテストが落ちる。
- **(γ) 上位の権限束が来たときに一括で配線する。**
