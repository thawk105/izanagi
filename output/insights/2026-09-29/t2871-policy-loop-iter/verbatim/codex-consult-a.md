## 総括

2 案の **iteration 別計測 campaign** は、各計測 identity の claim を一度しか取得できないまま、同じ out_root で次の pair job を通せます。ただし、両案とも **claim 取得後、系列 state 保存前の強制終了**を解決していません。現行の保存順を維持したままでは、次 job が同じ番号を選び、残った claim に拒否され続けます。

## 所見

- **must-fix — 強制終了後に系列を継続できない。** [driver:444](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/orchestrator/campaign/p3_s4_loop_policy.py:444) は counter をメモリ上で進め、保存は [driver:465](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/orchestrator/campaign/p3_s4_loop_policy.py:465) の `finally`。claim はそれより前に [loop:698](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/orchestrator/campaign/loop.py:698) から取得され、[campaign_claim:421](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/orchestrator/campaign/campaign_claim.py:421) の `O_EXCL` で永続化されます。**影響:** SIGKILL 後、系列 state は旧番号のままなのに次番号の claim が存在し、次 job も同じ identity で拒否されるため、次候補の計測成果物を作れません。**最小修正案:** 計測開始前に番号を保存すればこの停止は避けられますが、計測前の失敗でも欠番が生じ、対応する履歴行が無いまま次番号へ進みます。単に保存位置を移すだけでは完了判定の「2 本分の履歴」と整合しません。中断番号を消費済みとしてどう記録し、次候補へ進むかを、実装前に明示してください。

- **should — critic digest の意味が変わる。** 現行は系列 layout の admitted view から digest を作り [driver:469](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/orchestrator/campaign/p3_s4_loop_policy.py:469)、runbook は「同じ系列の campaign」の digest と定めています [runbook:123](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/docs/phase3-silo-policy-runbook.md:123)。両案の計測 layout への切替えでは、過去の pair と login 側 record-reject の WAL が digest から消えます。**影響:** critic が参照する赤・緑の範囲が縮み、系列を通した帰属が変わります。同じ job の stock は元から digest 作成後なので、この点は変わりません。**最小修正案:** 当該 iteration の admitted digest を採用し、runbook §1(g) に材料の範囲が変わることを明記するのを推奨します。系列全体の digest を保つために計測 WAL を系列 WAL へ複写する案は、lock と admission の整合を新たに扱うため、今回の最小変更には収まりません。

- **should — 番号と計測成果物の対応を履歴だけから復元できない。** 両案は系列履歴を [driver:216](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/orchestrator/campaign/p3_s4_loop_policy.py:216) の既存形のまま保存し、計測 campaign ID を行に含めません。一方、計測 WAL は iteration 別 dir に移ります。**影響:** レポート作成者は履歴行の `iteration` と `policy_iteration` を再計算して参照する必要があり、強制終了による欠番があると、履歴行数を job 数や計測 dir 数と取り違えられます。**最小修正案:** 新しい台帳は作らず、runbook §3 に identity の導出、欠番、参照先の確認方法を記す。成果物に直接参照を持たせる必要があるなら scope 外の裁定に回してください。

## 変異の帰属

- iteration key の削除・固定値化は、2 process 目の **claim 数または ClaimError** で帰属できます。「stock skip」は上記のとおり期待しないでください。[plan-A:48](/work/SFC/tanab/tmp/t2871-policy-loop-iter-20260928/codex/plan-a.md:48)
- stock に系列 **cfg** を渡す変異は session binding mismatch で赤になる見込みです。一方、**layout だけ**を系列へ渡す変異は、`run_campaign` 自体が cfg から計測 layout を作るため、計測は成功し、後段の `_stock_result` が別 WAL を読んで `non-stock-source` になる可能性があります。失敗箇所を一つに決め打ちしないでください。[plan-A:50](/work/SFC/tanab/tmp/t2871-policy-loop-iter-20260928/codex/plan-a.md:50)・[driver:337](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/orchestrator/campaign/p3_s4_loop_policy.py:337)
- `_result_history` を系列 WAL に戻す変異は、候補が certified なら `result.certified` から outcome を決めるため、**outcome だけの assert は赤になりません**。verifier digest の中身や WAL 参照を狙って検査する必要があります。[plan-B「変異」](/work/SFC/tanab/tmp/t2871-policy-loop-iter-20260928/codex/plan-b.md)・[driver:228](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-t2871-policy-loop-iter/orchestrator/campaign/p3_s4_loop_policy.py:228)
- state・履歴保存先を計測 layout にする変異は、系列 counter／履歴の assert で赤になります。ただし同時に次 process が再び iteration 1 を選ぶため、ClaimError という別理由にもなり得ます。まず 1 process 目直後の系列 state と履歴を確認すると帰属が明確です。[plan-A:52](/work/SFC/tanab/tmp/t2871-policy-loop-iter-20260928/codex/plan-a.md:52)

## scope 外の裁定候補

強制終了した iteration を **欠番として消費して次へ進む**か、**同じ番号の再測定を許す別の回復契約を設ける**かは裁定が必要です。後者は claim の one-shot 性や手動退避禁止に触れるため、現 scope の実装案として扱えません。同時 job の番号予約・排他、系列全体の admitted digest を再構成する台帳も今回の案には追加しない判断が妥当です。
