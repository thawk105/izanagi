## 1. 現行の X / P / I と certified の意味

現行の `certified` は、**空でない実行履歴について、復元した依存グラフに巡回がなく、trace の integrity が clean** であることを意味する。巡回があれば `non-serializable`、巡回がなくても integrity が欠ければ `indeterminate` となる。[model.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-cicada-certified-evidence-design/orchestrator/verifier/model.py:501)、[model.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-cicada-certified-evidence-design/orchestrator/verifier/model.py:555)

| 面 | 記録と役割 | 現行の認定条件 |

認定用の追加書式は、既存の行種別と衝突しない `H <txid> <read_checked> <publish_checked> <sort_checked>` と、違反時の `V <txid> <key_hex> <reason>` を提案する。`H` は各 C frame 内で一回だけ出し、判定器は `read_checked == R 行数`、`publish_checked == W 行数`、書く取引の `sort_checked == 1`、read-only では `sort_checked == 0` を照合する。P は abort した取引でも出る独立違反行として維持する。`V` は `read-retired`、`read-generation-changed`、`read-wts-changed`、`write-not-installed`、`write-not-published`、`write-wts-changed` などを区別する。成功件数の自己申告だけで真実性は証明できないため、各 site の独立した positive control を認定導入条件にする。

[parse.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-cicada-certified-evidence-design/orchestrator/verifier/parse.py:320) の通常 parser **と compact parser** の両方で H/V を厳密に読み、frame 内の一意性・件数・txid・key を検査する。`Integrity` に `cicada_binding_violations`、`cicada_publication_violations`、`cicada_proof_count_violations` を追加し、`clean()` に 0 を連言する。`ProofSurfaceAssessment` は Cicada 専用の B/U/P emitter 文面評価を持たせ、既存 X/P/I の意味は変えない。[model.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-cicada-certified-evidence-design/orchestrator/verifier/model.py:58)、[model.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-cicada-certified-evidence-design/orchestrator/verifier/model.py:501) 文面検査には `read_internal`、退役・再利用、設置、公開、照合の**全 site**を要求する。一つの `H` emitter だけを発見して evidence-present としてはならない。`certified` の既存定義は維持し、Cicada の `Integrity.clean()` がこの追加連言を満たしたときだけ真にする。

## 3. 観測者効果

追加の台帳、世代番号、ReadElement の保存値、照合、H/V/J/K/L/N の出力はすべて `#if TRACE` 内に置く。Version に世代 field を足す案は TRACE=0 では field 自体を消す必要があり、TRACE=1 での構造体配置とキャッシュ挙動も大きく変える。まずは Version 外の TRACE 専用台帳を推奨する。ただし台帳の更新にも同期が必要で、TRACE 実行のスケジュールは変わり得る。TRACE=1 の throughput を性能値に使わず、TRACE=0 の前処理結果と対象全 TU の命令列一致を検査する。現行の一致実測は YCSB の 3 TU に限られる。[Cicada 判定器の記録](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-cicada-certified-evidence-design/output/insights/2026-09-29/vhash-cicada-verifier/README.md)

世代台帳の照合は、解放済み `ver_` の wts を読む方式にしてはいけない。既存 patch の `traceCommit()` はその再読を行うため、B を導入するときに置き換える。[instr-cicada-trace.patch](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-cicada-certified-evidence-design/patches/instr-cicada-trace.patch:80)

## 4. 費用

親 brief の基準は、stock・4 thread・1 秒で K が **175,139 txn、78.8 MB、判定 4.67 秒**、R が **917,498 txn、196 MB、13.1 秒**。H を一取引約 35〜55 byte とすると、単純増分は K 約 **6〜10 MB**、R 約 **32〜50 MB**。V は正常系では 0 行。診断用 J は read ごと、K は write ごと、L は validation の操作ごとに増えるため、全量採取なら数十〜数百 MB の追加があり得る。これは行書式からの概算で、実測値ではない。

H の解析は取引数に線形で、グラフの版順構築・辺生成・巡回探索の計算量は変えない。したがって判定時間の増分は parser と I/O が主で、**4.67 秒・13.1 秒へ一定倍率を掛けた予測はできない**。特に J/K/L を常時読む設計では、既存の直列性検査より入力処理が支配的になり得る。[dsg.py](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-cicada-certified-evidence-design/orchestrator/verifier/dsg.py:636)

実装規模の概算は、CCBench の正例 trace patch **300〜600 行**、判定器・report と両 parser **250〜450 行**、fixture・失敗系・positive control の試験 **300〜600 行**。正例 patch は既存 Cicada trace patch の改訂 **1 本**、壊し patch は下記の認定用 **B・U・P 各 1 本を最低限**とする。診断 J/K/L/N を全て作る場合はさらに増える。世代台帳と compact parser の取り込みが規模の不確実性を最も大きくする。
