**この計画を現状のまま通してはいけない最大の理由は、時間短縮の見込みが未確認のまま、受入の検出力を確実に縮める項目があることです。**

1. **R1 の T-080 削除は D700 と正面から衝突します。** D700 は、helper 検査と public driver を通す E2E では受理集合が異なり、部分削除でも縮むと明記しています。以前 opt-in にした際には、走らない間に赤が２件残りました。「旧 official 系列が論文の必須経路から外れた」だけでは、その検査対象が不要になった証拠になりません。また、提示された約 3,566 秒はテスト群の worker 時間であり、D700 の T-080 11 nodeid の時間や受入 wall 短縮幅と同一視できません。現状の「削除推奨」は撤回すべきです。

2. **R3 の変異 matrix 限定は、最優先の正しさ規律を弱めます。** 「test・gate を新設／変更した時だけ」では、verifier の依存コードや文書上の受入契約を変えた時が抜けます。D301 は、実装差分ゼロでも文書変更が実効 gate を変え得るため、免除を狭く定めています。新ルールは既裁定の上書きであるうえ、弱体化を検出する機会を減らします。削除による高速化として提案すべきではありません。

3. **md_2・md_3・md_5 は「参照ゼロ」「専用」という調査上のラベルを削除許可に変えかねません。** D1989 は動的ロード、key→path、hash、文書による拘束まで分類するよう要求します。D2179 は専用 test 内に現役コードの検査が混じる実例を記録しています。`submission_gate/` の import 0、旧文書の参照 0、8c leaf の単独性だけでは足りません。特に凍結 bytes や path に束縛された文書を移すと、規律 7 が守る成果物の対応関係を壊し得ます。個々の対象の拘束と成果物の所在は**未確認**です。

4. **B-4 と T-189 を一括で扱う根拠も弱いです。** B-4 本走が研究本流である以上、実験 test が本走の入力・記録を検査していないか確認が要ります。docstring の「production 認証層ではない」はその答えになりません。T-189 の held node は所要 0 秒なので、削除を速度改善として優先する根拠はありません。D335 の保留 test は提案どおり触らないのが妥当です。

5. **工数の配分が論文優先とずれています。** 一回限り tool の削除や `pruned/` の整備は、後で git を引きやすくする価値はありますが、154 分の主因を減らす実測はありません。phase3 の移動も、節だけ読む現行運用や `check_docs` の走査を速くするとは限りません。さらに md_4・md_7 は稼働中の cleanup wave と編集面が重なります。並行投入は避けるべきです。

**成立しない攻撃もあります。** 門番待ちに上限を設けること自体を、正しさゲートの縮小とは言えません。ただし「10 分」が適切か、投入後の資源条件と測定条件が保てるかは未確認です。README 更新はユーザーが明示的に求めており、8c を「未達の目標」と正確に書くことに反対する理由はありません。8c の目標を残すことも、個々の未使用ファイルを永久保存する義務までは意味しません。
