## attribution

- **全体比較 (候補 対 stock、同じ pair job の同じ動作点、どちらも 5 rep の中央値)**: throughput_tps は候補 2,988,984、stock 1,376,465 で、比は約 2.17 倍。between-run の noise floor (3.0%) をはるかに超える差である。一方、abort_rate は候補 37.72%、stock 12.44% で、候補のほうが約 3 倍高い。つまり「abort は増えたのに throughput は上がった」組である。abort の減少で速くなったのではない。候補仮説は「stock は待機や施錠待ちに時間を使って abort を抑えているが、そのぶん実行が止まっている。候補は短い待機ですぐ再試行するため、abort は増えても単位時間あたりの commit が多い」というもの。ただし待ち時間は独立指標として測っておらず、throughput の差としてしか見えない。llc_miss_rate と ipc は欠測なので、cache や IPC 側の機序は切り分けられない。仮説の段階にとどまる。
- **abort 後の待機 (policy_after_abort)**: 窓は「連続 abort 数 (上限 5) に応じた mask 0/1/3/7/15 と ctx.rand の AND」で、上限 15 単位の短い乱択待機である。施錠競合による abort では 1 段上げる。上の仮説の主な担い手の候補だが、施錠競合時方策の寄与と分離できない。この iteration では両方が同時に入っているため、この観測をどちらか一方の効果に帰属することはできない。
- **施錠競合時の方策 (policy_on_lock_conflict)**: attempt 12 未満は待機 0 で即 retry、12 以上 28 未満は 1〜2 us 待って retry、28 以上で abort。genome は no_wait=L (即 abort) だが、SILO_POLICY_VARIANT=1 のもとでこの方策が実際に発火したかどうかは取っていない。したがって効いた・効かないのどちらとも言えない。abort_rate が 37.72% と高いことは、retry で競合を吸収しきれていない可能性とも、abort 後の短い待機ですぐ同じ競合に再突入している可能性とも矛盾しない。
- **フラグ軸 (BACK_OFF / no_wait / WAL)**: digest の genome は 1 行だけで、各軸の水準も 1 つしかない (BACK_OFF=1, L, WAL=0)。限界効果は計算できず、このデータからはどのフラグにも帰属できない。
- **verify run の abort 統計**: candidate-0001 は 25.42% (aborts 206,427 / commits 605,635) で、stock 対照は無い。trace を有効にした build は遅く、競合の度合いが計測 run と違うため、37.72% との差は build の差で説明できる範囲にある。これ単独で異常とは読まない。
- **rejections**: 無し。候補は緑 (正しさの面では certified 済み) で、正しさ面からの次手のシグナルは無い。

## recommend

帰属を可能にするため、次の iteration は**一度に 1 つの要素だけを変える**ことを勧める。優先順に並べる。

1. **施錠競合時方策の寄与の切り分け**: abort 後の待機関数はそのままにし、policy_on_lock_conflict を「attempt 0 で即 abort (give_up)」に置き換えた版を試す。throughput_tps が noise floor 3% の範囲で変わらず、abort_rate も変わらなければ、2.17 倍の出どころは abort 後の待機側と読める (発火証拠が無いことと併せて判断する)。逆に throughput が落ち、abort_rate が上がれば、retry が効いている根拠になる。
2. **abort 後の待機窓の勾配を測る**: 施錠競合時方策は固定し、kStreakCap (窓の上限) を 1 方向だけ動かす。候補は、より短い窓 (上限 mask 3 や 7) と、より長い窓 (31 や 63) のどちらか一方。短い窓で throughput_tps が上がり abort_rate も上がるなら、「待つより早く再突入するほうが得」という仮説が強まる。長い窓で abort_rate が下がって throughput_tps も下がるなら、stock 型の「待機コスト」側に寄っていく。
3. 余力があれば、施錠競合による abort のときだけ窓を 1 段上げる処理 (`level = next + 1`) の有無を単独で比べる。abort 要因別の内訳が無いため効果は読みにくいが、abort_rate の動きで間接的に見る。
4. (計測側への要望で、variant 生成の指示ではない) 施錠競合時方策が verify 中や計測中に発火した回数と、abort 要因別の件数を取れるようにすると、上の 1・3 の帰属が直接できる。検証専用の計数は絶対規律 1 に従って計測 build から除去する前提で行う。

いずれも正しさゲートは前提のまま動かさない。abort_rate を下げるために検証や施錠の被覆を緩める方向は候補にしない。

## avoid

- **abort_rate の低下を目的関数として追うこと**: この 1 対の観測では、abort_rate の低い stock (12.44%) のほうが throughput_tps は半分以下である。この動作点では abort_rate の低さが throughput に結びついていない。abort_rate を下げるためだけに待機を長くする方向は、優先度を下げてよい (ただし 1 観測なので「再訪不要」とまでは言わない)。
- **複数の要素を同時に変えること**: iteration 2 は abort 後の待機と施錠競合時方策が同時に入っていて、帰属ができなかった。次の iteration でさらに複数の要素を動かすと、ランダム探索と区別がつかなくなる。
- **フラグ軸についての結論**: BACK_OFF・no_wait・WAL は水準が 1 つしかない。どれかを「効かない」として外す根拠は無い。
- **他の workload への一般化**: この結果は p3-silo-policy の 1 動作点だけのものであり、read-heavy など他の動作点に広げない。

## uncertainty

- **観測数**: 候補 1 件、stock との対 1 組 (5 rep の中央値)。2.17 倍という差は noise floor を大きく超えるが、同じ条件での再現は取れていない。stock は候補の後に測っているので、順序の影響 (熱や外乱) を排除できない。
- **欠測**: llc_miss_rate と ipc (機序の切り分けが不能)、施錠競合時方策の発火証拠、abort 要因別の内訳 (施錠競合かどうか)、待ち時間そのもの。「待機コストの差」説は throughput から逆算した推測であり、独立の指標で確かめたものではない。
- **stock との構成差**: stock (variant db4764543546) の BACK_OFF 設定と、施錠時に即 abort するかどうかの設定は入力に無い。2.17 倍が「方策を関数で合成したこと」によるのか、stock 側の既定の待機設定の影響なのかは、この入力だけでは区別できない。
- **待機の単位**: window_mask の値 (0〜15) と kLockWaitUs の実時間での単位 (us、clock、回数のどれか) は入力から確定できない。窓を「短い」と評価したのは相対的な読みである。
- **verify と計測の abort 率の差**: 25.42% 対 37.72% の差は build の違い (trace の有無) で説明できると読んだが、stock の verify 対照が無いため、異常かどうかは判定できない。
- **iteration 1 との比較**: 過去の iteration の値は入力に含まれていない。iteration 2 の方策が前回より改善したのかどうかは言えない。
- **入力内の指示めいた文字列**: 見当たらなかった (anomaly なし)。
