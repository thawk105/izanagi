## brief の前提の検査

- **(P1) 要修正。** `instr-cicada-trace.patch` を `#if TRACE` 内に置く設計は妥当。ただし D16 の trace-hook 本来の置き場は submodule の `izanagi-trace` 枝で、一回限りの out-of-tree 例外を Cicada へ自動適用できないことは D579 が明記している（`ruling-D16.md`、`ruling-D579.md:11-12`）。この wave では gitlink を動かさず patch を試作成果物として作り、恒久配置は decisions fragment で裁定対象にする。
- **(P2) 要修正。** `wts>>32, wts&0xffffffff` は uint64 の大小を辞書順の `(epoch,tid)` に保存し、verifier の 32 bit 各欄と整合する（`cc/cicada/include/time_stamp.hh:24-40`、`orchestrator/verifier/dsg.py:37-69`）。ただし `transaction.cc` から `param->initial_wts` へ直接は届かない。値は YCSB の `main` が保持する（`cc/cicada/ycsb_cicada.cc:28-30`）。TRACE 専用の値をそこで設定し、`transaction.cc` の emitter が参照する必要がある。また emit は「writePhase 直前」ではなく、成功した `cpv()` の後、set の clear 前に置く（`transaction.cc:895-913`）。read-only は別途 `commit():934-937` の clear 前に置く。
- **(P3) 成立。ただし上限を明記。** v2 の C/R/W/E は現行 parser が受け、DSG に protocol 分岐はない（`parse.py:355-429`、`dsg.py:752-785`）。`cicada` は X/P/I 証拠面の対象外なので、巡回なしでも verdict は `indeterminate`、`certified=false`（`model.py:37,77-82,245-247,510-519,555-572`）。既存 protocol の判定を変えずに fixture を追加できる。
- **(P4) 要修正。** 裸マクロの無条件壊し patch は条件 gate の登録を増やさず、独立 checkout にだけ重ねるなら適切。ただし「rts を更新しない」と「read set 再検査を飛ばす」は、それぞれ既存の別検査が同じ実行を止めうる。発火件数だけで成功とせず、変更された経路の commit と、その txn を含む G2 witness を照合する。
- **(P5) 要修正。** `INLINE_VERSION_OPT_CICADA=0`、`SINGLE_EXEC=0` は既定だが、`INLINE_VERSION_PROMOTION=1`、`REUSE_VERSION=1` は既定である（`cmake/Options.cmake:31-34,53-54`）。promotion は `INLINE_VERSION_OPT=1` の内側だけで働く（`transaction.cc:128-135`、`include/transaction.hh:199-215`）。D1464 に従い、少なくとも `TRACE && INLINE_VERSION_OPT && INLINE_VERSION_PROMOTION` と `TRACE && SINGLE_EXEC` を compile 時に拒否する。`REUSE_VERSION` は版オブジェクトの再利用であり版 ID の意味を変えず、`WRITE_LATEST_ONLY` も版選択・検証方針の変更なので、一律拒否は不要（`include/transaction.hh:229-245`、`transaction.cc:242-289,490-529`）。
- **親の実測は概ね成立し、一点を補う。** 初期版は `param->initial_wts` であり 0 ではない（`include/tuple.hh:13-20,74-90`）。`thid_` は `uint8_t` なので C 行では整数へ cast が必要（`include/transaction.hh:58`）。YCSB は read-only と更新の両方で `commit()` 成功後に commit counter を増やす（`external/ccbench/include/ycsb.hh:106-169`）。共有 `trace.hh` の `emit_commit` は旧 5 token 形式なので、SI v2 と同様に C と E は stream へ直接出す（`external/ccbench/include/trace.hh:78-82`、`patches/instr-si-trace-v2.patch:4-27`）。`patches/ledger.json` は変更しない。

## プラン

1. **trace hook。** `instr-cicada-trace.patch` はまず `cc/cicada/ycsb_cicada.cc:28-30` に TRACE 専用の初期 wts 設定を加え、`cc/cicada/transaction.cc:9-17` に `#if TRACE` 内の `trace.hh` include と、同値を保持する TRACE 専用の定義を置く。初期値が未設定なら trace 実行を失敗させる。YCSB 以外の Cicada binary は今回の検査対象にしない。`transaction.cc:899-913` の `cpv()` 成功後、clear 前に書込み txn の C/R/W/E を連続出力し、`commit():934-937` の早期 return 前に read-only の C/R/E を出す。C は `C txid thid epoch tid read_count write_count`、R は `re.ver_->ldAcqWts()`、W は実際の `new_ver_` の wts と `U/I/D`、E は `E txid`。txid は各成功 commit の emit 開始時に `next_txid()` で一度だけ採番する。C の件数は emit 対象と同じ set を数え、実行した R/W 行数を別途照合する。`read():153-165` の既存 read set・write set 再参照は新しい read 要素を足さない。`update():210-288` は既存 read 要素を残し RMW の write 要素を足す。`delete_record():353-401` は先行 write を消す場合があるが read 要素は残る。abort は `abort():745-773` の set 清掃だけで C/R/W/E を出さない。`TRACE=1` でも `group_commit>0` は pending 版の確定と emit 時点がずれるため、この初版は起動時に拒否する（`writePhase():899-904`）。
2. **版の写像。** `wts==trace_initial_wts` の read のみ `(1,0)`、その他は `(wts>>32, wts&0xffffffff)`。新しい W と C に genesis を使わせない。Cicada の版 chain は wts によって挿入位置を決める（`transaction.cc:497-527`）ので、verifier の `(epoch,tid)` ソートによる ww 順と一致する（`dsg.py:778-785`）。各成分は `0..2^32-1` で、`parse.py:637-665` の signed int64 列に収まり、DSG の bias 付き packed int64 と一致する。`r6_epoch_version_order` と `r7_epoch_rw_successor` が epoch 跨ぎの順序と直後版を検査している（`test_verifier.py:2078-2108`）。`genesis_commits` と `version_dups` は不正写像の受け皿になる（`dsg.py:457-469`）。初期値を `MinWts-2` から実行中に推定しない。`MinWts` は初期化後に動く値であり（`ycsb_cicada.cc:30`）、初期版の識別を固定できない。
3. **flag と D1464。** `TRACE && INLINE_VERSION_OPT && INLINE_VERSION_PROMOTION` は内部版昇格を workload write と分ける設計ができるまで `#error`、`TRACE && SINGLE_EXEC` は多版の版 chain が無くなるため `#error` とする。これらは `transaction.cc` の TRACE 専用 block に置く。`INLINE_VERSION_OPT=1, PROMOTION=0` は inline 格納でも wts が保たれるため、まず対象外として明示し、後続 cell で検証する。`REUSE_VERSION=1` は既定のまま、`WRITE_LATEST_ONLY` は 0/1 とも検査可能だが初回実走は既定 0 に固定する。genome は両者を含み、promotion の冗長組を除く（`orchestrator/campaign/genome.py:172-205`）。
4. **壊し patch。** 第一候補 `broken-cicada-no-rts-update.patch` は `transaction.cc:536` の `readTimestampUpdateInValidation()` 呼出しだけを除く。後から小さい wts の writer が、既に大きい wts の reader が読んだ旧版へ書ける。旧 writer の `read(Y genesis)→write(X)` と新 reader/writer の `read(X genesis)→write(Y)` が双方 commit すれば、X と Y の **rw + rw の G2** になる。第二候補 `broken-cicada-skip-read-recheck.patch` は `transaction.cc:566-569` の不一致 abort だけを除く。読後に自身の wts 以下の新版が入った txn を通し、同じ write skew を **G2** として検出する。いずれも `precheckInValidation():247-293`、early abort `transaction.cc:253-283`、write set 検査 `:576-593` は残す。発火可能性は断定せず、後述の焦点走で各 guard が実際に結果を変えた commit と cycle witness の対応を確かめる。第三候補の write set rts 検査除去は early abort と precheck も同条件を検査するため、単一理由性が弱く初版から外す。各 patch は別 checkout に trace patch の上へ重ね、マクロ無し・無条件とする。stderr の終了時 1 行を `CICADA_FIRED slug=... reached=N changed=N committed=N` とし、`IZANAGI_` という語を patch 本文にも診断文字列にも入れない。`changed` は元の guard が作用したはずの事象、`committed` はその事象を通った txn の成功数として定義し、該当 trace txid も保存して witness と照合する。
5. **verifier と fixture。** production の `orchestrator/verifier/{parse,dsg,model}.py` は変更しない。`orchestrator/tests/fixtures/` に `cicada_g1_genesis_readonly`（初期 wts の R、read-only C/R/E、`indeterminate`・cycle 0）、`cicada_g2_lost_update`（二つの rw が閉じる、`non-serializable`・G2）、`cicada_g3_old_snapshot`（古い版を読むだけで cycle 無し）、`cicada_g4_epoch_boundary`（32 bit 境界を跨ぐ ww/rw）、必要なら `cicada_g5_read_write_same_key`（RMW の R と W、自己辺を除外）を足す。`test_verifier.py:59-67` の共通 fixture helperを使い、`protocol="cicada"` で個別に呼び、`total_cycles`、integrity の数値項目、`anomalies[].edges[].reasons` を確認する。既存 protocol の frozen JSON や verdict を変えるコード変更はない。テストは短い固定 trace のみで、全体 5 分上限を守る。
6. **起動器と実走。** SI 起動器の `build_variant()` と `verify()` の target/protocol を `ycsb_cicada.exe` と `cicada` に変更する。CMake 入力は `-DCCBENCH_TRACE=1`、`-DCCBENCH_INLINE_VERSION_OPT_CICADA=0`、`-DCCBENCH_SINGLE_EXEC=0`、`-DCCBENCH_WRITE_LATEST_ONLY=0`、`-DCCBENCH_REUSE_VERSION=1` を記録する（`cc/cicada/CMakeLists.txt:1-14`、`cmake/Options.cmake:31-54`）。YCSB の実行 flag は `ycsb_tuple_num` 等で、Cicada の共通 `tuple_num` 等とは別である（`include/ycsb.hh:25-32`、`cc/cicada/include/common.hh:48-64`）。起動器は patch hash、適用順、toolchain、raw trace/標準出力/標準エラー、verifier JSON、C 件数と benchmark commit counter を保存する。`tools/check_trace0_preprocess_identity.py` の CLI は commit 間差分を Silo genome で調べる作りなので、この out-of-tree patch の Cicada 比較へ**そのまま適用できない**（同 tool `:1070-1124`）。同じ compiler flags の無 patch／trace patch TRACE=0 の二つの detached source を CMake compile database から同一 TU で前処理比較し、両 binary の `objdump -d` を正規化比較する。`nm`/`strings` の trace 残存も調べる。`#if TRACE` の include と実装が off で消えることは必要条件であり、最終根拠は命令列一致とする。
7. **所有と波及。** repo 内の変更候補は `patches/instr-cicada-trace.patch`、二つの `patches/broken-cicada-*.patch`、`patches/README.md`、`orchestrator/tests/test_verifier.py` と Cicada fixture、一次資料 `output/insights/2026-09-29/vhash-cicada-verifier/README.md`、必要な spool fragment。起動器と job dir は repo 外。gitlink と `patches/ledger.json` は触れない。新 patch は全件走査の `test_p3_s4_loop.py:8682-8691` と `test_mocc_template_proof.py:95,106` に見えるため、marker 語を含めないことと mocc marker 判定が変わらないことを確認する。README 節には preimage pin、touch set、適用順、無マクロ、TRACE=0 証拠、各壊しの site・期待 G2・発火診断、受入 cell、未対応範囲、D16 の配置裁定待ちを記す。

## 未解決の論点

- **D16 の恒久配置。** D579 により一回限り例外の流用は成立しない。試作 patch の実測後、`izanagi-trace` へ移す時期と pin 前進を人間の裁定に残す。
- **発火の再現性。** 上記二つの壊しは競合の順序が必要で、指定 cell が必ず G2 を出すとは静的には証明できない。生死確認後に実測し、必要なら既存の遅延 flag を使う焦点走を事前記録して追加する。別 guard に止められた実行を壊し成功に数えない。
- **trace の範囲。** 初版は YCSB の既存キーの read/update に限定する。scan phantom、挿入・削除、promotion の内部 write、`group_commit>0`、`SINGLE_EXEC=1`、他の Cicada workload は未検証として一次資料に明示する。
- **完全性 witness。** C 件数＝benchmark commit counter と v2 framing は必要だが、同じ set から作る宣言件数だけでは独立証拠にならない。起動器で counter と trace ファイルの合計を照合する。

## 総括

計画上の最大修正は、初期 wts を YCSB の `main` から TRACE 専用に渡すこと、書込み trace を `cpv()` 後・set clear 前に出すこと、D16 の配置例外を既決と扱わないことの三点である。現行 verifier の production code は変更せずに Cicada の G2 を検査できる見込みだが、stock の巡回 0 と二つの壊しの赤検出は、計算ノードでの trace・発火診断・構造化 witness の実測を経て初めて結論にできる。
