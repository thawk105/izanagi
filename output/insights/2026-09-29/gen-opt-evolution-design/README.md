## 0. 要約

1. **既にあるもの (§2):** 方策 loop の driver (`orchestrator/campaign/p3_s4_loop_policy.py`) は、メインセッションが呼んだ coder・auditor の出力を受け取り、検疫・構文検査・単独 TU compile・auditor の veto → `pipeline.evaluate` (正しさ・identity・性能の関門) → critic 用 digest の書き出しまでの評価の 1 iteration を進める。coder・auditor・critic を呼ぶのはメインセッションで、driver は LLM を起動しない。逐次の 1 系列で、1 iteration の候補は 1 個、親の選択は無く、coder は自系列の全履歴 (性能値を除く 7 key) を見る。進化と名の付く実装は比較基盤の (1+1) 変異だけで、backoff の値 1 次元に閉じている (`t2849_generators.py`)。方策空間の (1+1) は [T-2867] の事前登録草稿にあるが未実装。母集団・島・交叉・新しさの実装は `orchestrator/`・`tools/` に見つからなかった (§9)。
2. **ShinkaEvolve の「直接採用ゼロ」の再判定 (§3):** 深掘りに記録された反面教師の理由は 5 つ (R1〜R5)。並列評価の機構群 (R4) を 4 つに分けて 8 件を判定し、**前提が変わり成り立たないもの 1** (並列評価そのもの — 独立 job の並行投入が既定になった)、**条件付きになったもの 3** (スコア付きの勝ちプログラムを prompt に入れる / 交叉 — K2 のアームで宣言すれば入れてよいが候補の分類と主張の射程が変わる、島の予算配分 — 本番では可、比較では固定)、**今も成り立つもの 3** (fail-open な patch 適用 / LLM 生成物を system prompt へ昇格させる prompt evolution / 測定 rep の逐次打ち切り)、**不要のまま (理由が変わった) 1** (評価の oversubscription)。銀行預けの「親選択の新しさボーナス」は採用候補に上がる。
3. **推奨 (§4):** 段階導入。まず案 A「独立 K 系列を並べて最後に最良を選ぶだけ」を回せる状態にする (新規コードはほぼ系列 identity だけで、ablation の対照にもなる)。そのうえで足す差分は案 B「世代同期の多系列 + 外側の親選択」で、子 1 本の評価は今の pair job (候補 + 同じ job の stock) をそのまま使い、足すのは (i) 全系列の結果から親を選ぶ選択器、(ii) 親の系譜と前世代の全ての子の結果を coder 入力へ渡す口、(iii) 世代ごとに K 本の pair job を別 node へ同時に投げて揃うのを待つ起動器、の 3 つ。**案 B を探索本走に採るかは、案 A との比較 (E1・E2) の結果で決める。** 案 C (格子・交叉・移住・新しさの埋め込み) は今の予算では寄与を測れない。
4. **「進化探索」と呼ぶ条件 (§5.2・§7):** 同じ評価数で E0 (案 B 対 (1+1)、母集団の寄与)、E1 (案 B 対 案 A、足した層全体の寄与)、E2 (適応度による親選択 対 一様な親選択、選択の寄与) の 3 つの ablation を測ること。結果の正負は問わない (寄与の主張は結果に従う)。
5. **費用 (§6、write-heavy の実測単価からの換算、待ち行列を含まない):** 生死確認 (1 島・K = 3・2 世代、endpoint なし) 1.56〜1.68 node 時間 (確認の線の下)。探索 1 本 (1 島・K = 8・6 世代 = 48 評価 + endpoint の再計測) 10.8〜11.6 node 時間。用語を得る ablation (4 構成 × 10 本 × 24 評価 + endpoint、機械の IR 変異) 235〜253 node 時間、同時検査を方策 driver へ入れれば換算で 120〜152 node 時間 (参照 job は別)。LLM の変異なら別に直列 62〜75 時間で、週上限で何週かかるかは測れていない。**2 node 時間以上の規模はすべてユーザー確認が要る。**

7. **次の段の前提:** 案 A・案 B とも [T-2867] の実装 (系列ごとの campaign identity、driver の停止規則の切り離し、機械生成 IR の口、IR の生成器、系列制御と起動器) に乗る。先に作り直さない。

| R4 | 並列評価を前提にした機構群 (島の予算配分・EWMA 適応の oversubscription・逐次統計の early-stop) | 単一テナント直列・単一系統で in-flight の待ち行列が無い (規律 4 と非互換) | **分けて判定** | (a) **並列評価そのもの: 前提が変わり成り立たない。** 独立な job は別 node へ同時に投げるのが既定で、各 job は node を占有する (§1.2)。規律 4 が禁じるのは実験集合を増やすことで、投入時刻を変えることではない (runbook §7.5)。job をまたぐ比較は同じ job の stock との比を使う (比が消すのは node の共通の乗数作用だけで、それ以外の作用と測定の雑音は残る、§4.2)。(b) **島の予算配分: 条件付き。** 本番の探索では使えるが、事前登録した比較で適応的に配分すると構成間の予算が揃わず比較が崩れるので、比較では島ごとの予算を固定する。(c) **oversubscription: 不要のまま (理由は変わった)。** 評価の枠が増えた結果、律速は LLM (週上限、親の同時数 p = 4、D2216) 側に移り、評価より提案を多く出す仕組みは要らない。(d) **測定 rep の逐次打ち切り: 今も成り立つ。** Izanagi は測定を信用できるまで rep を増やす向きで (roadmap §3.6)、逆向き。候補を安い評価で絞る二段評価 (§5.4) はこれと別物で、両段とも verifier を回す |
| R5 | インデント寛容な fuzzy patch 適用 | 適用率を上げる自動補正 = fail-open (規律 2 の対極) | **今も成り立つ (前提に関係なく採らない)** | 方策の coder は marker 内の本文を全文で出し、検疫が全体を検査する。差分形式の出力とその寛容な適用は作らない |

**関連する別の判断 (深掘りの理由ではない):** D9 (Open-Ended Evolution は Phase 3.5 に予約) は「評価器が固まる前に最適化圧力を最大化する機構を載せると、reward hack が auditor の追いつかない速さで湧く」を理由にする。これは**今も成り立つ (段の順序の条件として)**。関数単位の空間の外へ編集範囲を広げる段 A・段 B では、検査用記録の差し込み点の固定と小さいモデルでの全場面検査 (proposal の懸念 2、md_3 の担当) が要る。母集団の層は、同じ空間の中で正しさを作れることを確かめた後 (段 A の試し) に載せる。今の方策空間 (待機・再試行・abort の判断だけ) の中で回す分には、既存の関門で閉じる。

### 3.4 深掘りの本文に名前だけ出る機構 (理由の記録が無いもの)

| 機構 | 判定 | 理由 |
|---|---|---|
| LLM アンサンブルと UCB バンディットによる model の選択 | 採らない | 比較の事前登録は model を固定する (例 D2222)。複数 model を常時混ぜると LLM の寄与の比較が崩れる。サブスク外の model の呼び出しは従量経路になりうる (共通指示の鉄則) |
| code embedding による近重複の除去 | 採らない (代替あり) | embedding の API は従量経路になる。重複は既存の候補 identity (source_digest、IR の本文) で判定し、再提案は A・B を消費して測り直す (D2220 項 4)。構造の近さが要れば IR の木の距離で足りる |
| LLM による新しさの判定 (novelty judge) | 探索の中では使わない | 探索中の「新しさ」は多様性の保存の問題で、選択器の構造的な量 (子の数、identity) で扱う。研究としての新しさ (段 B の「文献に無い」) は、結果を見る前に検索式を登録し別の AI に反証させる別手続き (common.txt §1) で、探索の loop に入れない |
| meta-recommendation (履歴の要約から次の方針を推奨) | 既存で代替 | critic の `recommend` / `avoid` が同じ役を担う |

### 3.5 前提に関係なく採らないもの (まとめ)

- fail-open な patch 適用 (R5)。
- LLM 生成物を system prompt・role の本文へ昇格させる prompt evolution (R3)。
- 正しさの検査を短く・少なくして評価を安くする予備評価 (§5.4)。trace の短縮は検出確率を下げるので、行うなら事前登録の改訂としてユーザーの裁定が要る。
- 従量経路を要する機構 (embedding API、サブスク外の model)。

### 4.1 足さずに済ませる案との比較

| | 案 A: 独立 K 系列 + 最後に最良を選ぶ | **案 B (足す差分): 世代同期の多系列 + 外側の親選択** | 案 C: 全機構 |
|---|---|---|---|
| 中身 | 既存の方策 loop を K 本、別系列として並べる。系列の間で情報は流れない。終わった後に同じ job の stock 比が最大の候補を選び、endpoint を測り直す | K 本の系列を世代ごとに揃え、各世代の終わりに全系列の certified 結果から親を選び、次の世代の各子の coder 入力 (または機械の変異) に親の系譜と前世代の全ての子の結果を渡す | 案 B + 行動の格子 (MAP-Elites、例: abort 率の区間)、島の間の移住 (他 workload での再評価)、交叉 (LLM / IR)、新しさの埋め込み |

| 「進化探索」と呼べるか | 呼べない (系列間の世代更新・選択が無い) | ablation (§5.2) を測れば呼べる | 同左、加えて各機構の ablation が要る |
| 危険 | 小さい | 親の適応度が 1 回の pair の値なので、雑音と node の作用で親を誤選択しうる (§4.2・§5.4 の手順 0 で程度を測る) | 規律 5 (段階導入) に反する。D9 の懸念 (評価器の拡張前に最適化圧力を最大化) |

**推奨 (段階導入):**

1. 先に案 A を回せる状態にする。要るのは [T-2867] 実装 1 (系列ごとの campaign identity・停止規則の切り離し) だけで、案 A は E1 の対照と、案 B が効かなかったときの戻り先を兼ねる。
2. 案 B は選択器・系譜と前世代の結果の口・世代の起動器の 3 つだけを足し、既存の評価・関門・台帳・job body を変えない。
3. 案 B を探索本走に採るかは、E1 (案 B 対 案 A) と E2 (適応度選択 対 一様選択) の結果で決める。寄与が観測されなければ本走は案 A で行い、母集団の層は ablation の記録として残す。

案 A だけで済ませて「系列間の共有が必要と示されたら案 B」とする順序は採らない。共有の必要は案 B との比較 (E1) でしか示せず、依頼 (ユーザーの「進化探索フレームワークを回す」) と用語の予約 (roadmap §2・§10) の解除も案 B を作って測ることを要する。案 C は、案 B で多様性不足が実測で律速になったときの拡張とする (roadmap §2「island model は多様性不足を測ってから導入」)。

### 4.2 案 B の形

- **母集団の持ち方:** 母集団 = K 本の系列 (lineage) の最新の certified 候補と、その祖先の記録。記録の正本は各系列の `policy_history.jsonl` と計測 campaign の WAL のまま。選択器はそれらを読んで世代ごとの manifest (世代番号、子の枠、選んだ親の identity、乱数の preimage) を書くだけで、評価結果を複製しない。
- **世代:** 1 世代 = K 本の子を生成し、K 本の pair job を別 node へ同時に投げ、全部の結果が揃うまで待つ。揃ってから次の世代の親を選ぶ (同期型)。非同期の定常型は、比較で世代数を揃えにくいので採らない。
- **島:** 島 = workload (write-heavy / balanced / read-heavy)。子は自分の島の workload の較正動作点で評価する。**初版は 1 島 (write-heavy) で始める** — 方策軸の単価は write-heavy しか測っておらず、read-heavy は backoff 軸の実測で 1 系列の計算が write-heavy の約 3.9 倍、候補の検査 1 本が記憶量のために同時 2 本までに制限される (t2797 cost options §2・§4.2)。島の間の移住 (ある島の最良を別の島の workload で評価する) は未知条件への転移 (P4) と同じ問いになるので、案 C へ回す。行動の格子 (MAP-Elites) は、1 島あたり数十評価ではセルが埋まらないので初版に入れない。
- **適応度:** 子の 5 rep 中央値 ÷ **同じ job の stock** の 5 rep 中央値。**node の共通の乗数作用を仮定した暫定の適応度**である。比が消すのは共通の乗数だけで、加法的な作用・node と処置の交絡・測定の雑音は残る (runbook §7.5)。子と node の割付けは記録し、比較 (§5) の事前登録で node の扱い (割付けと推定量) を決める。certified でない子 (anomaly・build 失敗・品質欠測・検査の拒否) は適応度を持たず、親にならない。**anomaly を出した子は即失格** (規律 2)。
- **親の選び方:** 既定は切り捨て選択 (適応度の上位 μ 本から、preimage の SHA-256 で決定的に K 個の親を引く)。同値は評価の早い方。選択肢として新しさボーナス (§3.3、子の数が少ない親を優遇) を足せるようにし、寄与は ablation で測る。親の値は 1 回の pair の値で、選択のために測り直さない (雑音と node の作用に弱いことは定義の一部として開示する)。**§5.4 手順 0 の順位の再現性が低ければ、案 B の採否の前に適応度の定義 (再計測の回数など) を見直す。**
- **coder に渡すもの:** 今の方策 coder の入力のうち「自系列の履歴」を 2 つに替える。(a) 選ばれた親の系譜 (親とその祖先の本文・結果の分類・拒否の分類・verifier digest、同じ 7 key の形)、(b) 前世代の全ての子の結果 (失格の子を含む、同じ 7 key の形)。**性能値は今どおり渡さない** (性能は critic 診断を通してだけ届く)。これで [T-2867] の LLM arm と入力の性質が揃い、LLM あり/なしの比較を崩さない。性能値を coder に見せる構成は、K2 のアームとして別に宣言して名乗る。
- **失敗の還流 (規律 3):** 子が verifier・検疫・auditor で落ちた理由は、今どおりその子の系列の履歴と WAL に残り、さらに (b) によって**次の世代の全ての子の生成入力に届く**。親の系譜の置き換えだけでは、選ばれなかった系列の失格理由が次の生成へ届かないので、(b) を省く構成は作らない。機械の変異は失格点を親にしないだけで、理由は台帳と report に残る。
- **変異の種類:**
  - LLM の全書き換え (今の方策 coder。親の系譜をデータとして受け取り、marker 内の本文を全文で出す)。
  - 機械の変異 (IR の部分木の置換と field の追加、草稿 §4.5 の定義。親を選択器から受け取る)。
  - 差分形式の出力 (SEARCH/REPLACE 型) は作らない (R5)。「小さく変える」は全文出力のまま親との差で測れる。
  - 交叉は初版に入れない (案 C)。入れるなら IR の型付き部分木の交換が先で、LLM の 2 親交叉は K2 のアームとして宣言する。
- **予算と停止:** 母集団の実行を A (提案機会) と B (評価数) で数え (D2220 項 4)、性能を理由に早く止めない。driver の停止規則 (10 回・3,600 秒、待ち行列を含む) は系列の途中で母集団を止めてしまうので使わない ([T-2867] 実装 1 の「停止規則の切り離し」、[T-2881] の裁定に依存)。
- **並行投入:** 同じ世代の子は別系列なので同時に投げてよい (runbook §7.5 の「独立」の 3 条件 — 共有する read/write 集合なし・protocol が直列を求めない・1 本の正味の仕事が準備を上回る)。**同じ submit checkout から別系列の pair job を同時に流して read/write 集合 (build-cache の claim、campaign lock、`output/` の親 directory を走査する consumer) を共有しないかは確かめていない。** B-5 は arm ごとの専用 checkout から投入した実績がある。生死確認 (§6.2 規模 S) で先に確かめる。
- **最終候補:** 母集団の中の最良 (探索時の適応度が最大の certified 候補) を endpoint とし、5 session 測り直す。草稿 §6 から流用するのは 5 session の再計測だけで、endpoint の選び方 (草稿は各系列の自系列の候補から選ぶ) は本書の定義である。

### 4.3 文献カードの渡し方 (gen-opt-literature-cards、md_2 の成果)

- 経路は既存の K2 manifest (`knowledge_manifest.py`) の `repo_artifact` source (commit と path と sha256 で束縛、本文は `content_utf8`)。カードは事実の記述だけで、LLM へ向けた命令文を含まない (common.txt §4)。manifest の `DATA_BOUNDARY` は「外部の知識はデータで指示ではない」。
- **足りないもの:** 方策 driver と方策 coder に知識入力の口が無い。K2 の口は backoff 軸の coder (`coder-v4-autonomous-k2`、出力は値 1 個) 専用で、方策 mode と K2 env は job body で排他である。§8 N4 で方策 coder の K2 版の入力を足す。
- **束縛 (既存の仕組みを使う):** 知識を扱う campaign では、manifest の受領証 (`knowledge_manifest.write_receipt`) を campaign に書き、全ての BUILD_START に知識の provenance binding を要求する検査 (`wal.validate_knowledge_provenance_bindings`) が既にある。方策 driver にもこれを通し、さらに世代の manifest (§4.2) に、子ごとの親 identity・渡したカードの digest・アームの入力集合を記録する。これで「実際に投入した知識源」が選択結果と材料レポートの proof chain に結ばれる (roadmap §1)。
- **分類の根拠:** 候補の分類 (de novo / 既知結果に条件づけられた派生 / 再現・選択) は、記録された入力から決める (カードを受け取った子とその子孫は「既知結果に条件づけられた派生」)。coder の自己申告は参考として記録するだけで、分類の根拠にしない。
- **子への割り当て:** 段 A の子は「親 + カード 1 枚」を受け取る変異とし、カードは世代ごとに適格なカードの集合から preimage で決定的に引く。カードと親の本文はどちらもデータとして渡す (規律 6)。
- **適格なカード:** md_2 の分類で「CCBench に無いが、今の関数単位の空間 (待機・再試行・abort の判断) で書ける見込み」のカードだけ。空間を広げないと書けないカードは、md_3 の関門を入れて空間を広げた後。
- **lookup 対照:** カードの仕組みを手で (または IR で) そのまま書いた方策を、同じ関門で評価する対照を置く (roadmap §1 の「既知候補をそのまま引く lookup 対照」)。既存の手書き方策の置き場 `orchestrator/campaign/silo_function_policy_hand/` が使える。

### 4.4 段 A と段 B を同じ枠組みで扱うか

同じ枠組み (同じ選択器・同じ評価・同じ関門) で扱う。違いは次の 4 つだけにする。

| | 段 A (文献由来) | 段 B (文献に無い仕組み) |
|---|---|---|
| 知識入力の宣言 | カードを渡す (K2) | カードを渡すか否かをアームとして宣言 (渡さない K0/K1 のアームも置ける) |
| 候補の分類 | 「既知結果に条件づけられた派生」または「再現」。新しい軸の発見や LLM 固有の成果に数えない | 新しさの判定手続き (結果の前の検索式の登録と別 AI の反証) を通ったものだけを de novo と呼ぶ |
| 主張 | 「文献にあるが CCBench に無い最適化を、正しく実装して workload 別に選べる」 | 当たれば「文献に無い仕組み」。判定前は主張しない |
| 追加の関門 | 今の空間の中なら既存の関門 | 空間を広げるなら md_3 の関門 (差し込み点の固定、小さいモデルでの全場面検査) を全アームの全候補に掛ける |

### 4.5 正しさ関門

- 全候補 (LLM・機械・lookup 対照・初期点) が同じ正しさ・identity・性能の関門を通る (規律 2)。母集団の層は関門を足しも外しもしない。
- 選択器は certified の候補だけを親にし、verifier が anomaly を出した子は即失格にする。選択器が評価器へ何かを渡す経路は作らない (評価の中立性)。
- 最適化の圧力は正しさを突きに来る前提で見る: 案 B は選択によって「速いが壊れた」方向への圧力を強める。これを受け止めるのは既存の verifier と auditor で、母集団の層の側で「検査に見えないので合格」になる経路を作らない (二段評価の扱いは §5.4)。

## 5. 比較の設計

### 5.1 D2212 の P2 (random・sweep・BO・進化・LLM を同じ口に通す) との関係

- 5 手法の比較基盤 (D2220) は 4 つの契約 (候補 identity・評価の要求・結果の分類・費用の計上) だけを共通化した。母集団の探索もこの 4 契約に乗せ、手法ごとに評価の経路を変えない。
- 基盤が具体化した backoff の値 1 次元 (S1) では母集団を持つ意味が小さい (D2220 の理由「B = 8 から μ = 4・λ = 4 を払えば初期集団の後に 1 世代しか残らない」)。母集団の探索は**方策の空間 (S3)** の比較に足す。
- 方策空間の対照 ([T-2867]、草稿 D2263) は 4 arm (LLM×C++・LLM×IR・random×IR・(1+1)×IR)、B = 10。**母集団は B = 10 では 1〜2 世代しか回らない。** 母集団の arm を入れるなら、全 arm の B を上げた別の事前登録にする (草稿の B を後から変えない)。
- 順序: [T-2867] の実装と生死確認 → [T-2867] の本比較の確認 → 母集団の arm。P5 の介入による説明も「方策空間の生成器対照の後」に置かれた (main `ab5fd6bd9`、[T-2852])。

### 5.2 「進化探索」と呼ぶための ablation

roadmap §2 は「population、世代更新、選択、変異/交叉、必要なら migration を実装し、その寄与をアブレーションするまでは進化探索や GA と呼ばない」とする。本書は、必須の ablation を次の 3 つに置き、4 構成 ((1+1)・案 A・案 B の一様選択版・案 B) で測る。いずれも同じ評価数 B・同じ提案機会 A・同じ初期点・同じ変異の種類で比べ、統計単位は独立な実行 (run) とする。

| id | 比べる構成 | 問い | 必須 |
|---|---|---|---|
| E0 | 案 B (K 系列) 対 (1+1) (1 系列、同じ B) | 母集団の寄与 | 必須 |
| E1 | 案 B (K 系列 + 適応度による選択) 対 案 A (K 系列、独立) | 足した層全体の寄与 (共有・親の再割当て・世代の同期・選択の合計。足した層に払う価値があったか) | 必須 |
| E2 | 案 B 対 案 B の一様選択版 (親を適応度によらず一様に引く、同じ K・世代) | 適応度による選択の寄与 | 必須 |
| E3〜E5 | 交叉 / 新しさボーナス / 移住 の有り無し | 各機構の寄与 | 実装したものだけ |

- E1 の差には共有・親の再割当て・世代の同期・選択が同時に入るので、E1 だけでは選択の寄与を分けられない。E2 が選択を分け、「案 B の一様選択版 対 案 A」の差 (4 構成を測れば同じ run で得られる) が選択を除いた世代更新と共有の寄与を示す。変異は全構成に共通の基盤で、交叉は初版に無い。
- 判定と主張: E0・E1・E2 を測れば「進化探索」の語を使ってよい。**結果の正負は問わない** — 寄与が floor 内なら「母集団・選択の寄与は測った範囲で観測されなかった」と書き、寄与の主張はしない。
- 検定は草稿 §7 と同じ核 (独立な実行の対の差の符号反転の正確検定、族の Holm) を使い、族・n・判定規則・node の扱いは結果の前に事前登録する。
- **先に機械の変異 (IR) で測る。** LLM を使わないので週上限に当たらず、E0〜E2 の答えが LLM の出来と混ざらない。LLM の変異での母集団は §5.3 の比較で別に扱う。

### 5.3 LLM あり/なしの対照

- roadmap §1 の LLM 固有の主張の条件 (同じ知識水準・同じ corpus・同じ retrieval 結果・同じ試行予算、lookup 対照を置く) に従い、「母集団 × LLM 変異」対「母集団 × 機械の IR 変異」を同じ選択器・K・世代数・初期点で比べる。
- カードを渡さない構成でも、LLM と機械の変異では入力が揃わない (下の開示事項: LLM 側だけが偵察の二値と射程文を受け取り、機械側は性能値を直接使い LLM 側は critic 経由)。したがってこの比較は「入力と探索器を合わせた構成の差」と名乗る。LLM 固有の寄与と言えるのは、入力・診断・性能情報を揃えた対照を別に置いた場合に限る (roadmap §1 の階層 3)。
- 文献カードを使う (K2) 比較は、非 LLM の側がカードを読めないので入力集合が揃わない。最初から「LLM + カード利用という構成の差」と名乗り、LLM 固有の寄与の主張には使わない。lookup 対照 (カードの仕組みを手で書いた方策) との差を併記するが、それで入力集合が同じになったとは書かない。
- 草稿の開示事項 (LLM arm だけが偵察の二値と射程文を受け取る、機械の進化は性能値を直接使い LLM は critic 経由) は母集団の比較にもそのまま付く。

### 5.4 安い予備評価と本評価の順位の一致を先に測る計画

**前提 (実測):** 1 候補の評価の約 9 割は正しさの検査で (§6.1)、bench は 20 秒前後にすぎない。bench の rep や秒数を減らす予備評価はほとんど安くならない。検査の trace を短くすれば安くなるが検出確率が下がるので、本評価の代わりには使わない (§3.5)。

| 手順 | 中身 | 計算 | 使い方 |
|---|---|---|---|
| 0 (計算なし、先にやる) | 既存の記録で順位の再現性を測る: (a) 方策軸の偵察 (D2234) と小比較 (D2240) は同じ固定 16 点を別 job で測っている → 2 回の順位の一致 (上位 3 点の一致と 1% 以内の値の一致は D2240 に記録済み、16 点全体の順位相関は未計算)。(b) B-5 v1・[T-2850] 試走 v2 の台帳にある「探索時の 1 session の値」と「endpoint の 5 session の score」の順位の一致 | 0 | 親の選択に 1 回の pair の値を使ってよいか (雑音で誤選択する程度) を先に知る。再現性が低ければ、案 B の採否の前に適応度の定義を見直す (§4.2) |
| 1 (同時検査) | 方策 driver の campaign 設定に既存の同時検査の key (`verify_performance_concurrent`、D2251) を足し、同じ候補を直列検査と同時検査で測って判定の一致と所要を比べる | 数本の pair (§6.2 の規模 S の中で足りる) | 検査を弱めずに安くする。backoff 軸の換算では 1 系列の計算が ×0.51〜0.60 (write-heavy) |
| (参考・現時点では推奨しない) 二段評価 | 偵察 driver (`silo_policy_recon.py`、性能構成の検査 1 本、1 方策 約 129 秒) を 1 段目にし、1 段目の予備判定を通過した子のうち上位だけを本評価 (pair job) に進める。導入を検討するなら、1 段目と本評価の順位の一致と、1 段目の検査が本評価の検査の失格をどれだけ拾うか (検出の一致) を、同じ候補の両方の評価で先に測る | 8 候補の両評価で 約 1.9〜2.1 node 時間、16 候補で 約 3.9〜4.1 node 時間 (換算、確認の線にかかる) | 1 段目の結果は「予備判定」と呼び、certified と称さない (偵察の build は NON_ADMISSIBLE、D2226 項 5)。予備判定を親・最終候補・報告・正式の正しさ判断に使わない |

- **二段評価を推奨しない理由:** 1 段目で性能を理由に落とした子は本評価の検査を受けない。1 段目の検査 (trace 1 本) では見えず本評価 (trace 5 本) でだけ見える anomaly を持つ子は、落とされても「壊れていた」ことが記録されず、その理由も次の生成へ返らない (規律 3 の正しさの信号が減る)。落とした子を何にも使わないので受理が甘くなるわけではないが、費用の削減のために正しさの信号を減らす設計は採らない。検討し直すのは、手順 1 の同時検査でも費用が見合わない場合に限り、そのときも上の点を併記してユーザーに諮る。

### 6.3 LLM の直列時間と週上限

- 子 1 本の LLM は coder + auditor + critic で 231〜280 秒 (換算)。critic を世代ごと・系列ごとに 1 回へ減らせば、coder + auditor の 132〜181 秒になる (critic の入力の意味が変わるので、採るなら事前登録に書く)。
- 親の同時数は p = 4 (D2216、B-5 の運用)。LLM の待ちは計算 node の外 (login) に置く (D2258 項 1)。1 世代の子 K 本の LLM が揃うまで、その世代の pair job は投げられない。
- **週上限は測れていない。** B-5 v1 は他 session と共有の枠の中で、4 並行・22 機会で週上限 (429) に達して全系列が止まった (F1050)。規模 M の 48 子はその 2 倍強、L の LLM 変異版の 960 子は 40 倍強の機会を要する。週上限に当たったときは系列を保留して待つ (D2258 項 2 の判定をそのまま使う) ので node 時間は増えないが、暦時間は延びる。

### 6.4 確認の線

- 1 タスクの job 合計が 2 node 時間以上なら、見積りを示してユーザーの確認を取ってから投げる (D2212 項 4、roadmap §5)。開発の検査 (受入・焦点走・変異) も同じ線で数える。
- 上の表で確認が要らないのは規模 S だけで、それも実装 wave の開発の検査と合わせて 2 node 時間を超えるなら確認が要る。試走と本比較を一括で承認しない。

## 7. 用語

- **今は「進化探索」と呼ばない。** 既存の方策 loop は逐次の 1 系列 (sequential / hybrid search)、比較基盤の進化 arm は (1+1) 変異である (roadmap §2・§10)。案 A (独立 K 系列) も呼べない。
- 案 B を実装し、§5.2 の E0 (母集団の寄与)・E1 (足した層全体の寄与)・E2 (適応度による選択の寄与) を同じ評価数で測った後に、「母集団型の進化探索」と呼んでよい。寄与が観測されなかった場合も語は使えるが、そのときは「母集団・選択の寄与は測った範囲で観測されなかった」と併記し、寄与を主張しない。E0・E1 だけを測った段階では「母集団の層全体の差を測った」までを言い、語は使わない。
- 交叉・移住・新しさボーナスは、実装して E3〜E5 を測るまで「〜を持つ進化探索」と書かない。
- 研究としての「新しい」(段 B) は探索の用語と別で、§4.4 の判定手続きを通ったものだけに使う。
