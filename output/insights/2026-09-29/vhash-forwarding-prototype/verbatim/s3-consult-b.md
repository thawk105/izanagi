## 所見

1. **must-fix — 発火の生死確認が主計測より後ろにある。** 通常 YCSB は 100 万キー、10 操作、取引時刻は `begin()` で更新される。`p>K=3` には同じキーに対する複数の新しい版が取引中に積まれる必要があり、通常型の発火頻度はコードだけでは定量化できない。待機型も、最後の read 後の 1000 µs には発火機会がない。操作数型は最も発火を期待できるが、1000 操作中の早期 abort が後半の read を減らし得る。根拠: [brief:42–46](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/brief-stage1.md:42)、[transaction.cc:34–43,79–126](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/external/ccbench/cc/cicada/transaction.cc:79)、[ycsb.hh:55–79,108–165](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/external/ccbench/include/ycsb.hh:55)、[DW-G01/G04](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/docs/dev-wave/core.md:60)。放置時: 成功率・失敗理由の図が分母ゼロ、または極少数事象の図になる。修正案: 最初に計数 build で `eligible/attempts/success` を短く測り、発火しなければ **K=1、キー数削減、skew 増加、長い取引の read 継続**を一つずつ試す。`rratio` を上げるだけでは更新版の生成も減るため、万能な解ではない。

2. **must-fix — 待機型の「発火しない」は取引全体には言えない。** 段 2 案は *10 READ と WRITE の後に待機し、新たな read をしない*。待機中の発火は構造上ゼロだが、待機前の read は発火し得る。根拠: [段2:28](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/codex/stage2r/out.md:28)、[md_6:18](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/inputs/md_6.txt:18)、[出典メモ §16.1](/work/1/SFC/tanab/tmp/vhash-2026-09-29/docs-snapshot/source-memo-2026-09-29.md:910)。放置時: 待機型の非発火という一次資料の記述が計数値と矛盾する。修正案: 待機前の試行と待機後の試行を区別し、「待機後の read がないため、その期間には試行できない」と記す。

3. **must-fix — gate の登録だけでは Cicada を admitted にできない。** `make_define_request()` は `silo` と限定的な `mocc` だけを許す。段 2 はこの問題を発見したが、brief P8 の「entry だけ」「判定変更なし」と両立しない。また段 2 の `COUNT` は本文で `LONGTX=1` も要求しながら登録表では companion が `ENABLE=1` だけである。根拠: [brief:52–63](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/brief-stage1.md:52)、[段2:21,55–67](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/codex/stage2r/out.md:55)、[condition_meaning_gate.py:1111–1142](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/orchestrator/campaign/condition_meaning_gate.py:1111)。放置時: smoke は request 拒否で止まるか、計数 build と gate 証拠の条件が食い違う。修正案: Cicada の許可を**登録した三 macro に限定**して追加し、`COUNT` の companion 契約を実際の `#if` 入れ子と一致させる。macro と witness の実 site 数は patch 完成後に確定する。

4. **should — F の throughput だけでは比較の意味が失われる。** F は深い read ごとに abort し、同じ procedure を再試行する。長い取引が完了しなくても短い取引の総 throughput は出る。根拠: [仕様草案:51–53](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/spec-draft-v1.md:51)、[ycsb.hh:108–169](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/external/ccbench/include/ycsb.hh:108)、[出典メモ §27.1](/work/1/SFC/tanab/tmp/vhash-2026-09-29/docs-snapshot/source-memo-2026-09-29.md:1488)。放置時: 「F が速い」という図が長い取引の飢餓を隠す。修正案: 長い thread の **commit 件数、F abort 件数、完了率**を必須併記する。完了ゼロなら F は「再試行の費用と進捗喪失を示す対照」と読む。

5. **should — `gc_inter_us` sweep の主張を限定する。** GC 間隔は版リストの長さと負荷を変え得るが、C/F の GC 保護時刻は据え置く設計である。したがって §28.1 の「GC 遅延下での throughput 耐性」の探索にはなる一方、保持版数の削減や GC 保護前進の証拠にはならない。根拠: [brief:27–30,42–45](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/brief-stage1.md:27)、[transaction.cc:806–887](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/external/ccbench/cc/cicada/transaction.cc:806)、[出典メモ §28.1](/work/1/SFC/tanab/tmp/vhash-2026-09-29/docs-snapshot/source-memo-2026-09-29.md:1541)。放置時: 図から GC 改善を過大に読める。修正案: 各 GC 条件で発火数と throughput を並べ、GC 保持改善は主張しない。

6. **should — 時間と統計の見積りは未較正。** 121 run の本走だけで 363 秒。段 2 の約 58 分は build 3 分・run 8 秒という未実測値に依存し、3 秒計測の準備時間や gate configure の変動が大きい。3 rep の t 分布 CI は規約に沿うが、自由度 2 で幅が不安定である。100 万件の Silo 較正も Cicada の初期化時間や版生成率を保証しない。根拠: [段2:38,42,86–90](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/codex/stage2r/out.md:86)、[runner.hh:279–300](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/external/ccbench/common/runner.hh:279)、[図規約:30–37](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/tools/plotting/FIGURE_CONVENTIONS.md:30)。放置時: 2 node 時間を超えるか、幅の広い CI を確証として扱う。修正案: smoke で **実 build、初期化込み run、gate の秒数**を取り直してから投入数を決める。3 rep は予備的な点と CI として示し、強い優劣判定をしない。

7. **should — ノード分割は arm 内比較には有効だが、workload 差は交絡する。** workload ごとに 1 node とし、その node 内で stock/C/F を順序回転するなら、同一 workload の処置比較は概ね対照できる。一方、通常型と操作数型の差には node 差も入る。根拠: [brief:30,42–46](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/brief-stage1.md:30)、[段2:34–38](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/codex/stage2r/out.md:34)、[runbook §7.5](/work/1/SFC/tanab/izanagi/.claude/worktrees/dev-wave-vhash-forwarding/docs/pegasus-runbook.md:1362)。放置時: workload 間の絶対 throughput 差を機構差として誤読する。修正案: 主張を**各 workload 内の paired 比**に限定し、node を記録する。workload 間の直接比較が必要なら割当を入れ替える追加 run が要る。

8. **should — 親 brief の所在と登録範囲に誤りがある。** brief:8 の仕様草案 path は `/work/SFC/...` と記すが、必読実体は `/work/1/SFC/...`。また brief:53–56 は `test_p3_s4_loop.py` の更新を要件化するが、段 2 は裸 macro により該当登録が不要と判断している。根拠: [brief:7–8,52–56](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/brief-stage1.md:7)、[段2:65](/work/1/SFC/tanab/tmp/vhash-forwarding-prototype-2026-09-29/codex/stage2r/out.md:65)。放置時: 読み込み失敗や不要な登録簿編集が成果物に混じる。修正案: path を直し、`test_p3_s4_loop.py` は実 patch がその検査対象になる場合だけ更新する。

## 総括

段 2 案の最大の危険は、**121 run を組んでから発火が乏しいと判明すること**と、**Cicada gate が登録だけでは通らないこと**である。短い計数 smoke で発火条件と所要時間を先に確かめ、Cicada 限定の gate 修正を明示的に裁定すべきである。通常型の発火率、build 時間、node 時間は今回の静的検査から数値化できない。K sweep や広い模擬テストは、その二点が解けた後に必要性を判断できる。
