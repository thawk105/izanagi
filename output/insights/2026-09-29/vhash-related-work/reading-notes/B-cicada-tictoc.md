### 機構の比較6列

1. **何を入力に判断するか**: 各 worker thread の local clock (経過時間) + abort 時の clock boost + thread ID のみ。版の選択は「開始時に固定された tx.ts」と各版の `wts`/`status` の比較のみで、物理配置 (inline か否か) は version 選択や timestamp 決定の入力にならない。
   根拠: §3.1 (PDF p.4) "Timestamps are generated by combining three factors: the current local clock, a clock boost, and the thread ID."
2. **どの状態を変えるか**: 版の `status` (PENDING→COMMITTED/ABORTED)、版の `rts` (CAS 更新)、head node の inline slot 状態 (UNUSED↔PENDING)、`min_wts`/`min_rts` (quiescence 時にleaderが更新)。
   根拠: §3.2 (PDF p.5) "status is initially PENDING when the version has been installed, and becomes either COMMITTED or ABORTED by the writer in its write phase."
3. **どの不変条件を保つか**: serializability。「commit したtxの実行が tx.ts の順で逐次実行したのと等価になる」ことを Appendix A で証明。
   根拠: §3.4 (PDF p.6) "Cicada's validation protocol ensures that the execution of a committed transaction appears to occur atomically at the transaction's timestamp (tx.ts)."
4. **どのコストを減らすか**: multi-clock で timestamp allocation のボトルネックを除去 (§3.1)。best-effort inlining で indirection/cache miss を削減 (§3.3)。write-set の contention-aware sort・early version consistency check・incremental version search で validation 段の footprint と無駄な version 再探索を削減 (§3.5)。rapid GC で working set (footprint) を削減 (§3.8)。Table 2 (PDF p.12) の ablation: "By omitting any single optimization, Cicada achieves 4.9–13.2% lower throughput."
5. **旧版を新たに読めるか**: 可能 (multi-version)。§3.4 (PDF p.6) "This multi-version protocol permits a transaction to freely read and write non-latest versions of records unless it violates serializability." ただし tx.ts は開始時に一度だけ割り当てられ (§3.1 "Cicada assigns a transaction a timestamp at its beginning")、実行途中で version 選択のために ts を動かして「別の hot な版」に乗り換える機構は読んだ範囲では確認できず。
6. **長い transaction への効き方**: §3.1・§3.2・§3.8・§4 概要の範囲では明示的な記述は見つからず「原典で確認できず」。読み取れる関連情報として、read-only transaction は `thread.rts` を使い read set の追跡・validation を省略する専用経路がある (§3.1、PDF p.4: "A read-only transaction uses (thread.rts) instead, and does not track or validate the read set")。長い read-write transaction が `min_wts`/`min_rts` の更新 (quiescence 宣言) を遅らせるかどうかは本文に記述がなく、Fig.1 のワークフロー (Maintenance フェーズは Write phase の後) から「長い読取フェーズの間は quiescence 宣言に到達しない」ことは推論できるが、これは推論であり原典の明記ではない。

### GC の詳細 (メモ (g) 対応)
- `min_wts`/`min_rts` の定義: §3.1 (PDF p.4) "(thread.rts) stores min_wts minus 1, where min_wts is the minimum of (thread.wts) for all threads, updated by a leader thread periodically (§3.8). min_rts is also calculated similarly to (thread.rts)."
- quiescence の定義: §3.8 (PDF p.8) "The thread then declares a quiescent state by setting a per-thread flag regularly (every 10 µs in our implementation). If a leader thread sees that every flag has been set, it resets all flags and monotonically updates min_wts and min_rts, which store the global minimum of (thread.wts) and (thread.rts) for all threads."
- GC 頻度 (rapid GC) の実測: §4 (PDF p.12) "Performing garbage collection only every 100 ms drops throughput by 36.0% for 28-warehouse TPC-C, 27.2% for 4-warehouse TPC-C, and 2.2% for 1-warehouse TPC-C vs. the default 10 µs garbage collection interval."
- 長い tx が GC を止める記述: 上述の通り「確認できず」。

### 状態名の一覧 (メモ (b) 対応)
`PENDING` / `COMMITTED` / `ABORTED` / `UNUSED` (inline slot 未使用) / `DELETED` (削除確定版)。
根拠: §3.2 (PDF p.5) "UNUSED indicates an inlined version that is not in use. Deleting a record installs a zero-length version whose status becomes DELETED when committed."

### rts の定義 (メモ (c) 対応)
§3.2 (PDF p.5) "(2) a read timestamp (rts) that indicates the maximum timestamp of (possibly) committed transactions that read this version" — メモの記述と一致。

### validation の順序 (メモ (d) 対応)
§3.4 (PDF p.6) "Validation has three required steps: (1) Pending version installation ... (2) Read timestamp update ... (3) Version consistency check ..." — 設置 → rts 更新 → consistency check の順でメモと一致。加えて §3.5 (PDF p.6) の early abort 系最適化: (1) write set を contention 順に sort、(2) early version consistency check (TicToc の preemptive abort に着想を得たと明記: "This technique is inspired by TicToc's preemptive aborts [64]")、(3) incremental version search (PDF p.7)。

### 既存最適化 (メモ (e) 対応)
- best-effort inlining: §3.3 (PDF p.6)。head node に 1 版だけを埋め込み indirection を削減。promotion 条件: "(1) a transaction reads a non-inlined version v as the visible version; (2) the version is early enough: (v.wts) < min_rts; and (3) the inlined version is currently UNUSED."
- incremental version search: §3.5 (PDF p.7)。read phase で見つけた `later_version` を記憶し、validation 段の再探索をそこから再開することで反復探索コストを削減。

### read-only 経路 (メモ (f) 対応)
§3.1 (PDF p.4) "A read-only transaction uses (thread.rts) instead, and does not track or validate the read set; it always sees consistent data because concurrent or future read-write transactions' timestamp is no earlier than min_wts and thus is later than (thread.rts)."

### PENDING 版を飛ばさず待つ記述 (メモ (h) 対応)
§3.2 (PDF p.5) "For PENDING, it spin-waits until the status is changed." および直後の根拠段落: "Blocking is short because a version remains PENDING for only a short period of time during validation. A pending version is likely to become COMMITTED instead of ABORTED because it has been installed only after the writer passes early consistency checks; thus, speculatively ignoring this pending version risks an abort." — メモの記述と一致。

### timestamp 割当て (メモ (i) 対応)
§3.1 (PDF p.4): loosely synchronized software clocks、clock boost、one-sided synchronization (peeking at a remote clock without blocking)。"tx の timestamp を後から変更・前進させる仕組み" は、abort 後のリトライで clock boost により新しい (より大きい) ts を割り当てる経路のみ確認 (§3.1, PDF p.5: "When an abort occurs due to a conflict, Cicada sets the clock boost to a fixed quantity...")。これは **再実行時の新規割当てであり、既読値を保持したまま進行中の tx の ts を前進させる機構ではない**。

### 本案4点との対応
1. **物理配置をtimestamp制御の入力にする** → **言っていない** (読んだ範囲: §3.1, §3.3)。multi-clock による timestamp 割当ては local clock / clock boost / thread ID のみに依存し、best-effort inlining の有無 (hot/cold相当の配置) が version 選択条件や timestamp 決定に現れる記述はない。
2. **version選択とtimestamp選択を同時に扱う** → **言っていない** (読んだ範囲: §3.1, §3.2)。tx.ts は開始時に一度だけ固定され (§3.1)、その後の version search (§3.2) は固定 tx.ts に対して「wts ≤ tx.ts を満たす最新の COMMITTED 版」を機械的に選ぶだけ。「既読値を保てる範囲で hot な旧版を選ぶために ts を動かす」に相当する記述はない。
3. **前進を履歴の保持義務の縮小 (GC) へ接続する** → **言っていない**。Cicada に forwarding 概念自体がなく、GC は `min_rts` (全 thread の `thread.rts` の最小値) 以下の wts を持つ版を回収するだけ (§3.8)。ただし「これ以下は誰も読まない境界を使って GC の保護条件を決める」という発想の骨格自体は min_rts と同型であり、本案の (3) が GC 側に接続する対象 (保護境界) は Cicada の min_rts と同種の量である点は指摘できる。
4. **複数版メタデータを共通の物理構造にまとめ、版選択・forwarding可否判断・validationを安くする** → **一部一致**。best-effort inlining (§3.3) は head node array という共通の物理配列に **1版だけ** のメタデータ+data を埋め込み間接参照を削減する。version list 自体は wts 降順の単純な singly-linked list のままで (§3.2)、複数版 (K個) のメタデータをまとめて 1 箇所に置き一括で走査・比較する構造ではない。また「forwarding可否判断」という工程自体が Cicada に存在しないため、そこへの適用は生じない。

### Cicada の best-effort inlining と本案 (1)(4) の異同 (指示された深掘り)
共通点: どちらも「よくアクセスされる版をレコードの主構造に直接置いて間接参照を減らす」という一点では同じ狙いを持つ。
相違点:
- **対象版の数**: Cicada は record あたり常に **1版のみ** を head node に inline する (§3.3 の promotion 条件 (3) "the inlined version is currently UNUSED" は同時に inline できるのが 1 スロットであることを示す)。本案 (VHash) は K (>1) 個の版を hot 領域にまとめて置く設計であり、規模が異なる。
- **選ばれる版の基準**: Cicada の inline 対象は「元々 UNUSED だった最初の書き込み、または `v.wts < min_rts` を満たす読み専用寄りの版」であり (§3.3)、tx がどの版を読みたいかとは独立に、書き込み側・バックグラウンドの promotion で決まる。version search 自体は §3.2 の wts ≤ tx.ts ルールに厳密に従い、「inline されているから」という理由で別の版を選ぶことはない。VHash の想定 (メモ §12, §23.2) は、hot 領域にある「最新でない版」を読むことを version 選択の選択肢として明示的に使う点で異なる。
- **timestamp 制御との接続**: Cicada の inlining は timestamp allocation・forwarding と一切結びつかない (上記 (1) の通り)。本案は物理配置 (cold 領域に入りそうであること) を forwarding 判断の入力にする点が新規性候補になっている。
- **GC との接続**: Cicada の inlining は GC の保護境界 (`min_rts`) を変えない。promotion の条件に `min_rts` を使う (読む側であって、変える側ではない)。

### 機構の比較6列

1. **何を入力に判断するか**: read/write set 中の各 tuple entry が保持するローカルな `wts`/`rts` (アクセス時にコピーした値)。write set については validation 直前に lock を取った上での `tuple.rts` の最新値。
   根拠: §3.2.2 Algorithm 2 (PDF p.4) — read set entry は `commit_ts = max(commit_ts, e.wts)`、write set entry は `commit_ts = max(commit_ts, e.tuple.rts + 1)`。
2. **どの状態を変えるか**: 各 tuple の (単一の) `wts`/`rts` を validation 成功後の write phase で `commit_ts` に上書き。根拠: §3.2.3 Algorithm 3 (PDF p.4) "w.tuple.wts = w.tuple.rts = commit_ts"。validation 中は read set entry の `tuple.rts` のみを `max(commit_ts, r.tuple.rts)` に延長 (Algorithm 2, Step 3)。§5.3 の history buffer を使う場合は、tuple ごとの「古い wts の配列」のみ追記更新 (payload は書かない)。
3. **どの不変条件を保つか**: serializable。式 (1) (§3.1, PDF p.3): "∃ commit_ts, (∀v∈{versions read by T}, v.wts ≤ commit_ts ≤ v.rts) ∧ (∀v∈{versions written by T}, v.rts < commit_ts)"。
4. **どのコストを減らすか**: 中央集権 timestamp allocator のボトルネックを除去 (§2.1, §3.1)。no-wait locking (§5.1) は write set lock 中の不要な待機によるスループット低下を削減。preemptive abort (§5.2) は write set をロックする前に (近似的な commit_ts で) 早期に abort 判定しロックの浪費を削減。timestamp history (§5.3) は rts 不足による不要 abort を削減する狙いだが、実測では効果が確認されていない (後述)。
5. **旧版を新たに読めるか**: **不可**。§5.3 (PDF p.8) "The value of the old version does not need to be stored since transactions in TicToc always read the latest data version." — history buffer が保持するのは wts の履歴のみで payload ではなく、read phase の Algorithm 1 も tuple の現在の value/wts/rts を1回だけ atomic load する設計 (§3.2.1)。write phase (Algorithm 3) は同一 tuple の単一の value/wts/rts を in-place で上書きする (旧版データは残らない)。
6. **長い transaction への効き方**: 専用の記述・section は読んだ範囲 (§3, §5, §6.4, §6.5) では見つからず「確認できず」。関連する記述として、§3.4 Spurious Aborts (PDF p.5) "a transaction aborts only if a tuple it reads or writes is overwritten by another transaction that enters the validation phase first. So only concurrent transactions (i.e., one starts before the other commits) can cause aborts." — 長時間実行される transaction ほど、commit までの間に他の transaction に validation で先行されて abort させられる機会が増える、という一般的な傾向は読み取れるが、GC や保持コストへの言及はない (TicToc はそもそも旧版を保持しないため GC という概念自体がない)。

### データ駆動 timestamp 決定の式 (メモ (a) 対応)
§3.1 式 (1) (PDF p.3) と Algorithm 2 (PDF p.4)。read set の tuple は `commit_ts ≥ e.wts`、write set の tuple は `commit_ts ≥ e.tuple.rts + 1` を要求し、両者の max を取って `commit_ts` を決める。「commit timestamp を read/write set の wts/rts から計算する」というメモの記述と正確に一致する。

### timestamp history による既読値の救済 (メモ (b) 対応)
- **持つか**: **持つ**。§5.3 "Timestamp History" (PDF p.8)。
- **節名**: §5.3、§5 "OPTIMIZATIONS" の一部 (§5.1 No-Wait Locking, §5.2 Preemptive Aborts と並ぶ最適化の1つ)。
- **既定で有効か**: **有効 (デフォルト)**。§6.4 (PDF p.11) の ablation 実験の定義: "4. All Opts: TicToc with no-wait locking, preemptive aborts, and timestamp history from Section 5.3. Recall that this last configuration is the default setting for TicToc in all of the other experiments in this paper." — つまり本論文の他の全実験 (§6.2, §6.3 など) で使われる "TICTOC" は timestamp history を含む "All Opts" 構成である。
- **何を保存するか**: 各 tuple ごとの「過去の wts の履歴 (固定長配列)」のみ。値 (payload) は保存しない。§5.3: "we can extend TicToc to maintain a history of each tuple's wts rather than just one scalar value. When a new version is created for a tuple, the wts of the old version is stored in a history buffer. The value of the old version does not need to be stored... In our implementation, the history buffer is a per-tuple array that keeps a fixed number of the most recent wts's, and thus the DBMS does not have to perform garbage collection."
- **どの条件で救済するか**: "During a transaction's validation phase, if a read tuple's local rts is less than commit_ts and the wts does not match the latest wts, then the DBMS checks if the wts matches any version in the tuple's history buffer. If so, the valid range of that version is from the local wts to the next wts in the history buffer. If commit_ts falls within that range, the tuple can still be validated." (§5.3, PDF p.8)
- **実測効果**: **効果なしという実測結果が明記されている点が重要**。§6.4 (PDF p.11): "A key finding is that the timestamp history optimization does not provide any measurable performance gain in either workload." およびその理由の考察: "TICTOC without this optimization already stores multiple versions of a tuple in each transaction's private workspace. This means that each transaction can commit in parallel using its own version." つまり、この最適化は default 有効ではあるが、著者ら自身が「TPC-C/YCSB では計測可能な性能差を生まなかった」と報告している。

### TicToc は single-version OCC で旧payloadを保持しない (メモ (c) 対応)
上記6列の5番目と同一根拠。加えて Cicada 論文側の独立した分類でも裏付けが取れる: Cicada §2.1 (PDF p.2) "Recent OCC designs are single-version concurrency control (1VCC) with in-place updates ('OCC-1V-in-place')... [55, 64, 65]" ([64] = TicToc)。これは TicToc 自身の自己申告ではなく Cicada 側の分類だが、独立した文献による裏付けとして記録する。

### rts の延長規則 (メモ (d) 対応)
§3.2.2 Algorithm 2 Step 3 (PDF p.4) および直前の説明文 (PDF p.4): "if no other transaction has modified the tuple, rts can be extended to be greater than or equal to commit_ts, making the version valid at commit_ts. Specifically, the local wts is first compared to the latest wts. If they are different, the tuple has already been modified by another transaction and thus it is not possible to extend the rts of the local version. If wts matches, but the tuple is already locked by a different transaction (i.e., the tuple is locked but it is not in the transaction's write set), it is not possible to extend the rts either." Algorithm 2 の該当行: `r.tuple.rts = max(commit_ts, r.tuple.rts)` (延長条件を満たした場合のみ実行)。

### 本案4点との対応
1. **物理配置をtimestamp制御の入力にする** → **言っていない** (読んだ範囲: §3.1〜3.2, §5)。`commit_ts` は read/write set の tuple の wts/rts という論理値のみから計算され (Algorithm 2)、物理配置 (キャッシュ上の位置など) が入力になる記述はない。
2. **version選択とtimestamp選択を同時に扱う** → **部分一致**。メモ §22.1 の通り「データ駆動で timestamp を後から決める」点は一致する (Algorithm 2)。しかし TicToc には「複数の版から選ぶ」という自由度自体が存在しない — tuple は常に単一の value/wts/rts しか持たず (Algorithm 3 の in-place 上書き)、"transactions in TicToc always read the latest data version" (§5.3)。したがって「既読値を保てる範囲で hot な旧版を選ぶ」という本案の版選択の自由度に相当する機構はなく、timestamp の事後決定のみが一致し、版選択との同時最適化は (版が1つしかないため) 成立し得ない。
3. **前進を履歴の保持義務の縮小 (GC) へ接続する** → **言っていない**。TicToc に旧版の保持義務・GC という概念自体が存在しない (旧版を保持しないため)。
4. **共通の物理構造で版選択・forwarding可否判断・validationを安くする** → **一部一致**。§5.3 の history buffer は「複数の過去 wts を 1 つの per-tuple 配列にまとめておき、validation 時にどの wts レンジが対象 commit_ts を含むかを調べる」という点で、複数版のメタデータをコンパクトな共通構造にまとめて validation を助ける発想には近い。しかし (a) 保持するのは wts のみで payload はなく「版を読む」ことはできない (read 用の版選択ではなく validation 時の事後救済のみ)、(b) 実測で性能効果が確認されていない (§6.4)、という点で本案 (4) の「版選択・forwarding可否判断・validationを安くする」とは効能の射程が異なる。
