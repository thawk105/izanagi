## 2. 裁定を求める問い

### Q1. `b03` の縮小には、裁定時点で未見だった 3 つの副作用がある

C-2b (a) は「`b03` から公表台帳の予約規定を外し、予約の正本を新 core + 追補 P へ一本化する」。
実際に行単位で切ると、次が起きる。

1. **台帳実体の取り替えによる ordinal 再取得を、追補 B 側で塞げなくなる。**
   縮小後の `b03` は「根は固定 literal から導出し caller 入力にしない」だけを言う。
   同じ根 `R` のまま**空の台帳実体を用意して ordinal 1 を再確保する**経路は、縮小後の全文を満たす。
   初版はこれを「producer が選べない canonical な台帳」「`(root, ordinal)` は一意」で塞いでいた。
   追補 B は新 core の追補 P を参照できない (C-2 (a) の「文書は互いに参照しない」) ため、
   **B 側でこの穴を塞ぐ手段が無い。**
2. **本走の投入 gate が 1 つ消える。**初版 `b03` の
   「この一意性が成立しないまま本走を投入してはならない」は `submit_main` の投入前 admission である。
   予約規定と一緒に外れる。新 core §8 は欠落・重複時に「公表表を生成しない」としか定めず、
   source の本走は止めない。→ **受理集合が広がる方向の変更**であり、親が独断で通せない。
3. **「一本化」は文言どおりには成立しない。**`b01` に `reservation_mode: create_only` /
   `release_on_failure: false` /「ordinal 2 以降は投入前 deny」が残る。
   同じ create-only・非解放は新 core §8.2 にもある。

- **(a) 裁定どおり外し、(2) の gate 喪失を受け入れる (推奨)。**「公表表が作れないだけで本走は走る」
  という切り分けを正とする。裁定 U8 の「別台帳」に最も忠実。
- (b) 予約規定は外すが、(2) の時相 1 文だけ `b03` に残す。→ 一意性の定義が B の外へ出るため、
  B が新 core を実質参照することになり、C-2 (a) の「文書は互いに参照しない」と衝突する。
- (c) `b01` の `reservation_mode` / `release_on_failure` も `p01` へ移し、`b01` は候補数上限の
  数値だけにする。→ (3) は解消するが `b01` の意味が痩せ、source core §14 の `b01` 記述からも離れる。
- (d) 本 wave では追補 B を再発行せず、C-2b を producer 実装 wave へ送る。

**推奨 (a) の理由。**(i) C-2b (a) の文言に最も忠実である。(ii) (2) の gate は現時点で機械的に
発火する層が 1 つも無く (C-5 (a) が未実装と確定済み)、文書上の規範を 1 本失うだけである。
(iii) gate が要る時点は producer 実装 wave 以降で、そこでは新 core §8.2 + `p03` が正本として効く。
**ただし (3) は (a) を採っても残る。**そのため本 wave は「予約規定の一本化」ではなく
**「予約手続きの一本化 + 根 literal と候補数会計の重複は残る」**と正確に書いた。

**成果物影響:** (a) だと、公表 entry が欠落・重複したまま本走が走り、source の試行台帳と
certified primary 選択は生成される一方、公表表だけが生成不能または参照不能になる枝が開く。

### Q2. 追補 P は新 core と同一 land では凍結できない

追補 A・追補 B はともに `core_ref.commit` を「その core を承認する決定を canonical 台帳へ
**fold した commit `F`**」と逐語で定義し、source core §15 の resolver 契約も
`core_ref.commit` を `F` またはその子孫に限定する。すなわちこれは**承認 fold commit** であって、
文書を repo へ置いた内容 commit ではない。

新 core v2 の承認 fold commit `F_p` は、**ユーザーの凍結承認とその fold の後にしか存在しない。**
承認より前の内容 commit をそこへ書けば意味のすり替えになり、既存意味の resolver では
追補 P が永続的に解決失敗し、内容 commit 意味へ緩めれば**未承認 bytes を受理する集合が新たに開く。**

→ **C-4 (a) の「同一 land」に追補 P は入らない。**

- **(a) 新 core v2 を先に凍結承認し、`F_p` 確定後の別 land で追補 P を凍結する (推奨)。**
  land 1 が確立した「承認の fold commit を後続文書が literal で持つ」設計と同型。
  新 core §10.1 の「pilot 1 本目より前」は pilot 未投入なので満たせる。
- (b) 追補 P に内容 commit を書いて同一 land で凍結する。→ 上記の理由で不可。
- (c) 新 core と追補 P の凍結をどちらも先送りする。→ §10.1 の時点独立性が弱くなる。

**成果物影響:** (b) を採ると、公表表を生成する resolver が未承認 core を受理するか、
逆に承認後も三つ組を拒否して公表表を生成できないかの、どちらかになる。

### Q4. `p03` は「pilot 前に凍結」と「実装は producer wave」を同時に満たせない

新 core §9 は `p03` を「呼び手が選べない台帳の**実体が決まらないと確定しない**」と書き、
§10.1 は「追補 P は pilot 1 本目より前に凍結」を要求し、C-5 (a) は機械執行を producer wave へ送る。
producer wave が台帳実体を決めるのが pilot より後になるなら、この 3 つは順序として閉じない。

- **(a) `p03` は要件だけを凍結し、台帳実体の同定は producer 実装 wave の裁定に残す (推奨。本 wave の実装)。**
  「呼び手が選べない」「create-only」「原子的」「`(root, ordinal)` 一意」「非解放」を要件として凍結し、

- (b) producer 実装 wave が台帳実体を決めるまで追補 P を凍結せず、**pilot もそれまで投入しない。**

- (c) §10.1 を緩める。→ 新 core の本文変更であり、承認前でも設計の後退。

**成果物影響:** (a) だと、台帳実体が pilot 後に決まった場合「実体の選択が結果を見て行われた」
疑いを文面では排除できない。(b) だと pilot の時期が producer 実装 wave に律速される。
