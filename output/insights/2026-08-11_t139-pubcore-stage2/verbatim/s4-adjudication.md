## 2. ユーザー再裁定へ返す新事実 (N1〜N4)

### N1 — C-2b (a) の実行には、裁定時点で未見だった 3 つの副作用がある

C-2b (a) は「`b03` から公表台帳の予約規定を外し、予約の正本を新 core + 追補 P へ一本化する」。
実際に行単位で切ると次が起きる。

1. **台帳実体の取り替えによる ordinal 再取得を、追補 B 側で塞げなくなる。**
   縮小後の `b03` は「根は固定 literal から導出し caller 入力にしない」だけを言う。
   同じ根 `R` のまま**空の台帳実体を用意して ordinal 1 を再確保する**経路は、
   縮小後の `b03` の全文を満たしてしまう。現 `b03` はこれを
   「producer が選べない canonical な台帳」「`(root, ordinal)` は一意」で塞いでいた。
   追補 B は新 core の追補 P を参照できない (C-2 (a) の「文書は互いに参照しない」) ため、
   B 側でこの穴を塞ぐ手段が無い。
2. **本走の投入 gate が 1 つ消える。**
   現 `b03` の「この一意性が成立しないまま本走を投入してはならない」は
   `submit_main` の投入前 admission である。予約規定と一緒に外れる。
   新 core §8 は欠落・重複時に「公表表を生成しない」としか定めず、source の本走は止めない。
   → **受理集合が広がる方向の変更**であり、規律 2 に照らして親が独断で通せない。
3. **「一本化」は文言どおりには成立しない。**
   `b01` に `reservation_mode: create_only` / `release_on_failure: false` /
   「ordinal 2 以降は投入前 deny」が残る。同じ create-only・非解放は新 core §8.2 にもある。
   C-2b (a) が想定した「予約の正本は 1 箇所」は、`b01` を残す限り成り立たない。

**選択肢**

- **(a) 裁定どおり外し、(2) の gate 喪失を受け入れる。**公表表が作れないだけで本走は走る、
  という切り分けを正とする。U8 の「別台帳」に最も忠実。
- **(b) 予約規定は外すが、(2) の時相 1 文だけ `b03` に残す。**
  ただし一意性の定義が B の外へ出るため、B が新 core を実質参照することになる。
- **(c) `b01` の `reservation_mode` / `release_on_failure` も `p01` へ移し、
  `b01` は候補数上限の数値だけにする。**(3) は解消するが、`b01` の意味が痩せる。
- **(d) 本 wave では追補 B を再発行せず、C-2b を producer 実装 wave へ送る。**

**親の推奨 = (a)。** 理由は 3 つ。(i) C-2b (a) の文言に最も忠実である。
(ii) (2) の gate は現時点で機械的に発火する層が 1 つも無く (C-5 (a) が未実装と確定済み)、
文書上の規範を 1 本失うだけである。(iii) 本走投入は B8 (a) により依然不可であり、
gate が要る時点は producer 実装 wave 以降で、そこでは新 core §8.2 + `p03` が正本として効く。
ただし **(3) は (a) を採っても残る**ので、承認パッケージには
「予約手続きの一本化であって、根 literal と候補数会計の重複は残る」と正確に書く。

### N2 — 追補 P は新 core v2 と同一 land では凍結できない

追補 A・追補 B はともに `core_ref.commit` を
「限定例外の決定 (D234) を canonical 台帳へ **fold した commit `F`**」と逐語で定義している。
凍結 source core §15 の resolver 契約も `core_ref.commit` を `F` またはその子孫に限定する。
すなわち `core_ref.commit` は**承認 fold commit**であって内容 commit ではない。

段 2 プランは追補 P の同じ key に、承認より前の内容 commit `C_core` を書く案を出した。
これは意味のすり替えであり、既存意味の resolver では追補 P が永続的に解決失敗し、
内容 commit 意味へ緩めれば**未承認 bytes を受理する集合が新たに開く**。両方とも受け入れられない。

**帰結: 新 core v2 の承認 → その決定の fold commit `F_p` の確定 → 追補 P が `F_p` を書いて凍結、
という順序が要る。C-4 (a) の「同一 land」に追補 P は入らない。**
peer が land 1 で確立した「`approval_fold_commit` を後続文書が literal で持つ」設計と同型である。

**本 wave の処置:** 追補 P は**段階 1 草案**として起草し、`core_ref.commit` を
未確定と明示する。placeholder を凍結しない。新 core §10.1 の「pilot 1 本目より前」は
pilot が未投入なので満たせる。

### N3 — 本 land 単独では成果物が 1 つも動かない

command 引数の「凍結承認はユーザーへ返す」を優先すると、land 後も
certified 選択・材料レポート・試行台帳・公表表・投入可否は land 前と同一である。
前進するのは「承認候補の 3 文書が repo に存在すること」と「承認手番がユーザーへ渡ること」だけ。
これは worklog 404 の C-4 (a)「C-1〜C-3 と同一 land で承認し、**段階 2 へ進める**」とは両立しない。

**選択肢:** (a) 引数どおり承認を返す (本 wave の既定)。
(b) C-4 (a) どおり本 land で承認決定 fragment を書き、fold をもって発効させる。

**親の推奨 = (a)。** command 引数がユーザーの直接かつ最新の指示であるため。
ただしこの齟齬自体を明示して返す。

### N4 — `p03` は「pilot 前に凍結」と「実装は producer wave」を同時に満たせない

新 core §9 は `p03` を「呼び手が選べない台帳の**実体が決まらないと確定しない**」と書き、
§10.1 は「追補 P は pilot 1 本目より前に凍結」を要求し、C-5 (a) は機械執行を producer wave へ送る。
producer wave が台帳実体を決めるのは pilot より後になりうるので、3 つは順序として閉じない。

**本 wave の処置:** `p03` からは実装 authority の literal (main 履歴・land lock など) を外し、
**要件だけ** (呼び手が選べないこと、原子性、create-only、`(root, ordinal)` の一意性) を書く。
実体の同定は producer 実装 wave の裁定に残す。この順序矛盾自体を N4 として返す。
