## あなたのレンズ — pin の実効性と fail-open

守る側に回るな。以下をすべて攻撃せよ。

1. **恒真な保証はないか。** 3 つの pin (dispatcher literal、workers slug 不在、operations slug 不在) が
   「絶対に発火しない」または「常に発火する」状態になっていないか。
   `decoded` に該当 file が入らない経路 (`text is None`) で黙って skip される条件を洗え。
   その skip が実運用で成立しうるか (file 削除、read 失敗、symlink、非 UTF-8) を検査せよ。
2. **dispatcher literal の pin は raw text への `in` 判定である。**
   HTML comment 内、fenced code block 内、あるいは打ち消し文脈に literal を置いて
   実際の契約行を消した場合、pin は通ってしまわないか。
   既存の `CODEX_DEV_WAVE_STAGE9_LAND_LITERAL` が同じ方式かを確認し、
   同型なら「既存と同じ弱さ」なのか「新しく持ち込んだ弱さ」なのかを判定せよ。
3. **slug 不在検査の抜け穴。** `DEV_WAVE_MODEL_SLUG_RE` は
   `(?<![A-Za-z0-9._-])gpt-5\.6-[A-Za-z0-9][A-Za-z0-9._-]*(?![A-Za-z0-9._-])` である。
   これをすり抜けて実質的に model を指定する書き方を構成せよ。
   例: 別の major/minor (`gpt-5.4-mini`、`gpt-6-...`)、slug の分割記載、全角文字、
   HTML comment 内、`_visible_markdown_text` が落とす領域、節見出し側への記載、
   `DW-S02`/`DW-S03`/`DW-O01` 以外の節 (`DW-S05-A`, `DW-S06-A` 等) への記載。
   **特に `DW-S05-A` に `gpt-5.6-sol` と書いても検査されない点**の帰結を述べよ。
4. **節が一意でないときの挙動。** `len(sections) != 1` で finding を出しているが、
   同じ finding 文字列を「節が無い」場合と「slug がある」場合の両方に使っている。
   これは単一理由性を壊さないか。運用上どちらが起きたか判別できるか。
5. **既存挙動の回帰。** `operations_text` と `dev_wave_text` の取得を関数前方へ移動した
   refactor が、後段の既存検査の挙動を変えていないか (定義順、None 判定、変数の再代入)。
6. **テストの甘さ。** 5 つの negative は本当に「その finding 1 件だけ」を固定しているか。
   `_assert_findings` の実装を読んで確認せよ。
   `test_dev_wave_model_pins_accept_current_docs_contract` は subprocess で実 repo を検査するが、
   これは他の wave の変更でも落ちる不安定な test ではないか。
   fixture が byte 予算 gate に先に食われる可能性は本当に無いか。
7. **段 4 裁定の変異 M1〜M5 が、この実装に対して本当に単一理由で KILL できるか。**
   できないものがあれば名指しし、代替の変異位置を提案せよ。
