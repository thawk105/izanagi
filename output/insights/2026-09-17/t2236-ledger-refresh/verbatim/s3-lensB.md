## 親の実測と一般化への反証

**P1：mode 追加の必要性は支持できるが、性能改善の必然性は支持できない。**

add-only は既存値を保持するため、約2932秒の既知側乖離を更新できない。全再生成は凍結保持条件に反する。この契約を満たす refresh の設計理由は成立する。

一方、file 表の `+2126 / +1289秒` は計算ミスではない。`refs/analyze_files.py:29` の式は、

`actual_known − pred_known + actual_unknown − n_unknown`

である。oracle は表示丸め値で `2661−676+153−13≈2125`、floor は `2366−1073+9−12≈1290`。未丸め値からの表示結果と約1秒違うことは不自然ではない。`s2-plan.md:224` の「算式を確定できない」は今回の script 射影で解消できる。ただし、これは純粋な既存値の差ではない。

さらに集計2本は `/work/1/SFC/tanab/izanagi` を読み、集合差 script は作業 worktree を読む（各 script `:4–7`、`setdiff.py:3–6`）。同一台帳・生成器を参照した証明には、読み込んだ blob/hash の照合が必要。固定値の再現性は未実測である。

**P2：1走は生成入力として妥当でも、割付の頑健性を保証しない。**

`@group` 除去自体は `_module_join` と `_coverage_nodeids` が共通の `_strip_group_suffix` を使っており整合する。問題は除去後の集計が consumer の suffix fallback を再現していないこと。

また「順位だけだから競合膨張は無害」は成立しない。全 node が同じ係数で膨らむなら順位は変わらないが、file・group ごとに膨張率が違えば順位は変わる。**shard 割付器は順位だけでなく数値の和を比較する**ため、順位が同じでも相対値の変化で割付先が変わる（`acceptance_shards.py:405–441`）。D746 の順位に関する観測を、この数値和による割付へそのまま一般化できない。

親資料にも走依存性がある。例えば `test_t316_sandbox_probe` の同名 node は約8〜9秒から約18〜19秒へ変わり、配置 shard も異なる（`parent-measurements.md:25–32,46–48`）。4走の選択で割付が変わる可能性はある。実際の変更数は未実測。最新かつ基準 collection と一致する走を選ぶ理由は、性能代表性ではなく入力の整合性である。

**P2・P4：連結成分と wall の床は別に扱う必要がある。**

提示表で最大の file は oracle の約 **2814秒**（2661＋153）、次が floor の約 **2375秒**（2366＋9）。これは連結成分の最大値を確定しない。両 file が同一成分なら約 **5189秒以上**になる。指定資料だけから置ける粗い範囲は、入力割付が成分制約を守っている前提で、最大成分の観測値和が **約2814〜8852秒**。上限は最大 shard の観測値和である。

file/group 成分は shard 間では分割できないが、その file 全体が shard 内の1 worker で直列実行されるとは限らない。2814秒をそのまま wall の床にはできない。

観測 duration を固定した反実仮想なら、shard-0 には、

- 全 node 和による床：`8852.3 / 48 ≈ 184.4秒`
- 単一 test による床：少なくとも **159.2秒**
- 153.1秒の test も別の長い実行鎖になる

がある。159秒と153秒を足せるのは、同じ worker で直列になる根拠がある場合だけ。group や投入順次第で床はさらに高くなる。これらは実際の351秒を説明し切らず、refresh 後の wall 予測でもない。

refresh 後の予測負荷は、suffix fallback 補正・量子化を一旦無視すると、

`8852.3 + 4432.9 + 4518.6 − (−334) ≈ 18137.8秒`

したがって均等化の目安は **約6046秒 / shard**。

`allocate` は group 成分を先に配置し、その後に残りを所要降順で最小負荷 shard へ置く。group の先行配置が偏らず、oracle と floor が独立な残り成分なら、両者を別の軽い bin に置き、残りで約6046秒ずつへ近づけることは期待できる。しかし group 成分が6046秒を超えて先に載れば、この目標には届かない。**6046 / 6046 / 6046 は条件付き目安であり、実際の割付結果は未実測**である。

親表の `actual−prediction` を旧 shard 別に足すと、表示されている凍結 file だけで、

before 4走は投入元が異なり、collection 件数も一致しない（`parent-measurements.md:6,15,24,34,43,52`）。同一 tip・同一条件の3走中央値ではない。after 1走との差が10%以上でも、改善の証明にはならない。
