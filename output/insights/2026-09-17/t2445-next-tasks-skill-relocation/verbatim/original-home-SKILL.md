# Next Tasks

Izanagi 専用。ユーザーが指定した件数を提案し、未指定なら 2 件とする。出力した投げ文を別 Codex セッションへそのまま貼れる形にする。

## 常設の前提 (ユーザーが毎回言わずに済むよう固定する)

ユーザーは next-tasks を打つたび次の 2 点を口頭で添えていた。以後は毎回の指示を待たず、既に言われたものとして選定・並び順・出力・Claude への brief すべてに効かせる (2026-08-29 ユーザー指示「わざわざ毎回言いたくない」)。

- **目的は論文を早く書き進めること。** 候補の価値は「論文の主張・図表・実験節がどれだけ前へ進むか」で測る。研究・実験を進める候補を上に置き、土台側を上げてよいのは研究の実行または記録を今まさに止めている場合だけ (止めている根拠を実測で書けないなら上げない)。
- **過剰な実装・ガードレールを避ける。** 成果物はアカデミアのプロトタイプであり production 級の堅牢性は目標にしない (izanagi の正本 D205)。仮想リスクや将来可能性だけの gate・検査・台帳・framework・一般化・互換層は候補にもしないし投げ文でも求めない。ただし絶対規律 1〜6 と実測で確認された正しさ欠陥の修正はこの制限の外であり、この前提を規律・受入要件・既存防壁の緩和に使わない。

## 手順

回答直前に、次の順で状態を実測する。

1. `bash /work/1/SFC/tanab/dev-wave-jobs/bin/next_tasks_snapshot.sh` を実行する。
2. Codex の稼働エージェント一覧を取得する。利用可能なエージェント一覧ツールを使い、handoff より新しい稼働状態の正本として扱う。ツールが利用不能なら、その制約を明記し、snapshot、worktree、handoff だけから非稼働を断定しない。
3. rulings-inbox の新しい控えを読む。`authority: user` とユーザーの確定発話があるものだけを裁定済みと扱う。推奨提示のみ、または収集のみの束は未裁定とする。個票単体だけでなく、同じ話題を含みうる round 集約ファイル (`rulings-fullN-*.md` 等) も突合せる — 個票の裁定が集約ファイル名を介して canonical (worklog/decisions) に反映され、個票自身の basename は参照されないことがある (2026-08-19 entry 693 実測。個票単体しか見ずに [T-396]・[T-1183] を「未裁定」と誤報告した事例あり)。
4. snapshot が抽出した worklog 末尾エントリの非 carry 項と、終了した wave の handoff が返した後続を読む。
5. **Claude へ相談する (毎回行う)。** 母集合が揃った時点で、別実装の同役 (Claude) へ独立見解を求める。自分の候補一覧を確定する前に投げる。
   - 投げ方 = `bash /work/1/SFC/tanab/scripts/next_tasks_consult.sh claude <brief>.md <out>.md`。呼出しは read-only で、相手に書き込み・commit・wave 投入はさせない。環境に API キーを置かない — 同スクリプトは `ANTHROPIC_API_KEY` / `ANTHROPIC_AUTH_TOKEN` があれば相談を中止する (鉄則の自己検査)。
   - **必ず背景で投げ、前景で待たない。** 疎通は 10 秒で返るが本番の brief では 10 分を超える (2026-08-26 実測: 前景の上限で切られ出力が 1 byte も残らなかった)。`nohup bash ... &` で投げ、**このスクリプト自体を `timeout` で包まない** — 包むとラッパーだけ死んで本体が孤児化する。締切はスクリプトの内側にあり既定 1800 秒 (`CONSULT_DEADLINE_S` で変更可)。
   - 回収は `<out>.md.done` (中身は `rc=<終了コード>`) が出てから行う。`<out>.md.log` は CLI の進捗で数 MB になるので全文を読まない (末尾数十行だけ)。判断に使うのは `<out>.md` の本文だけ。
   - brief には「原則この brief だけで答える・repo の広い探索はしない・裏取りは最大 3 件・15 分以内に返す・確信の無い点は未確認と書く」を必ず入れる。入れないと相手が repo を探索し始めて締切を使い切る (同日実測)。
   - brief は自己完結にする。相手は本セッションの文脈を持たない。最低限 (a) 件数と依頼の言い回し、(b) 実測した候補一覧 (タスク ID・優先度ラベル・裁定状態・本文要約)、(c) 稼働 wave の slug と占有状況、(d) 選定規則の要点、(e) 上の「常設の前提」2 点を逐語で入れる。(e) を落とすと相手は防壁・台帳の整備を上位に返してくる。**自分の推奨順位は brief に書かない** — 書くと相手が追認するだけになり、独立見解の価値が消える。
   - 相手に求めるのは (i) 同じ母集合からの独自の上位 N 件と理由、(ii) 母集合から落ちている候補、(iii) 各候補の着手不能リスク (裁定待ち・機構不在・稼働重複) の指摘。
   - **相談は 1 往復で終える。** スクリプトは brief の先頭へ `CONSULT-MODE` の前置きを必ず付け、相手に (i) スキルを起動しない、(ii) 手順を再実行しない、(iii) さらに相談を投げ返さない、を課す。これが無いと相手側で相手自身の next-tasks が自動発火し、相談のつもりが手順の全再実行になって往復が止まらなくなる (2026-08-26 実測)。前置きを外して呼ばない。
   - **自分が `CONSULT-MODE` の入力を受け取った側になったときは、この手順を実行しない。** snapshot も母集合の再収集もせず、渡された brief だけを読んで独立見解を返し、Claude へ相談を投げ返さない。
   - **相談が失敗しても止めない。** CLI 不在、sandbox による外部呼出しの拒否、rc≠0、出力が空のいずれでも、その事実と理由を出力の冒頭に 1 行で明記し、相談なしで提案を出す。省いたのに省いたと書かないことは許されない。

## 選定規則

次をすべて満たす候補だけを提案する。

- 裁定待ちがなく、投入・実行機構がリポジトリに実在していて、今すぐ着手できること。「裁定で認可された」だけでは足りない。機構の実在が不明なら `rg` で実測し、検証できない候補は実装差分ゼロの precheck wave と明示するか除外する。
  「裁定済み」ラベルは決定フェーズが終わったことだけを意味し、実装フェーズの完了は意味しない
  (2026-08-19 実測: P1/P2/P3 の自己申告「完了・確定・済み」候補108件を深掘り検証したところ
  close-now は0件で、全件が「決定は済んだが実装がこれから」の正当な backlog だった)。
  「裁定済み」を見て「もう対応済みだから提案しない」と早合点しない。
- **過剰追加を候補にしない** (常設の前提の具体化。迷ったら出さない側へ倒す): 確定済みの主目的・scope を満たす本体実装と、それに足りる既存機構の
  再利用・局所修正を優先する。それを超える追加実装・追加防壁は、追加手段がユーザーの明示要求の
  範囲内か、現在の目的達成・実在する正しさ欠陥の解消・現在の受入要件の充足に必要で、既存機構・
  局所修正では足りないことを既存資料または実測で確認できる場合だけ候補にする。ユーザー要求の
  範囲外では仮想リスクや将来可能性だけの framework・一般化・互換層・gate・検査・台帳は除外し、
  この基準を既存安全規律、ユーザー要求、受入要件の削除・弱化に使わない。
- 稼働エージェント、生きた worktree、handoff のいずれにも担当がいないこと。
- 「これを先に行えば着手できる」という現在着手不能な候補ではないこと。
- Claude の見解は独立に評価し、右から左に流さない。相手の推奨をそのまま採ると相談は 2 度手間にしかならない。採る候補・採らない候補それぞれについて、自分が実測した根拠で採否を決める。相手が挙げた候補を採るときも、裁定状態・機構実在・稼働重複を自分で実測してから入れる (相手の断定を実測の代わりにしない)。
- 不一致は表に出す。上位 N 件が食い違った場合、または相手が指摘したリスクを退けた場合は、その 1 件ごとに「相手の見立て / 自分の判断 / 分けた根拠」を 1 行で書く。一致した場合は「一致」と 1 行で書く。相談したことにだけ触れて中身を書かない要約は不可。
- CC 自動合成の実験タスクを最優先する (常設の前提「論文を早く進める」の主経路)。該当候補がない、または入れない場合はその理由を明記し、裁定済み P1/P2、テスト高速化、防壁など優先度の高い候補で補う。
- 取り残し成果の回収・掃除を高優先にする。snapshot の worktree 一覧と `git branch --no-merged main` を実測し、成果が残っていれば「マージして land」または「不要と判断できたら掃除」の wave を候補にする。branch 削除はユーザーの明示指示がある場合だけ行い、掃除手順は cleanup-branches スキルと runbook に従う。
- 各投げ文には自己改善の終端条件を含める。wave の最後に `docs/skill-self-improvement.md` を読み、今回の実行で見つかった dev-wave / skill 運用の改善候補を専用 handoff の `dev-wave 改善候補` 節へ記録させる。候補が無い場合も「なし」と明記させ、改善作業や次 wave の起動を同じ wave のスコープへ勝手に追加させない。
- 人間手番と wave 実行範囲を混同しない。未解決の user-only 操作（identity を要する commit、push、凍結・本走承認など）がある場合は、投げ文の前提へ隠さず、提案とは別の「ユーザー手番」1 行へ分離する。既に patch・OID・handoff が存在するなら、それをユーザーに転送・再実行させず、次の wave が読める申し送りとして束ねる。
- 補助 artifact（bundle 等）をユーザーの必須作業へ勝手に昇格させない。コマンドを提示する必要がある場合は、対象環境で検証済みの短い単独行だけを出し、長い path の引用文字列を複数行へ分割しない。未検証のコマンドでユーザーに試行錯誤させず、wave 側で回収できる情報は handoff に記録する。
- 指定件数に満たない場合は水増しせず、「M 件のみ」と報告する。perf 導入、push、凍結承認などユーザーにしかできない作業は提案枠と分けて 1 行で列挙する。

## 出力形式

- 提案番号と本文中の番号参照は半角数字の `1.` / `2.` または「項1」で表す。丸付き数字は表示が潰れて読めないため使わない。
- 冒頭を `HH:MM JST 時点 / 稼働 wave: <slug>` の 1 行にする。
- 2 行目を `Claude 相談: 一致` / `Claude 相談: 不一致 N 件 (内訳は各提案の後)` / `Claude 相談: 実施できず (理由)` のいずれかにする。
- 各提案は、タスク ID、優先度ラベル、論文のどこが前へ進むか、裁定根拠を含む 1 行の見出しと、投げ文 1 段落を fenced code block に入れる。blockquote は使わない。
- Codex 用の投げ文は `$dev-wave ` で始め、依頼本文を同じ段落に続ける。散文による起動依頼や Claude 用の `/dev-wave` は使わない。
- 投げ文を自己完結させる。裁定控えのパス、insights・handoff・canonical worklog 項などの正本、規律 2 を緩めないこと、Codex author = D95、scope 外の扱い、作業末尾に `docs/skill-self-improvement.md` を参照して `dev-wave 改善候補` を handoff へ記録すること（候補なしも明記）を含める。継承 branch がある場合は branch 名と tip を書く。
- 編集面が稼働 wave と重なりうる場合は、起動時に重複検査を行う指示を含める。
- 投げ文に scope 外を 1 句で書く: 「本題の実装だけ。仮想リスク向けの gate・検査・台帳・一般化の追加は scope 外」。長い説明にはしない。規律 2 を緩めない旨は従来どおり残す — 削るのは追加であって既存防壁ではない。
