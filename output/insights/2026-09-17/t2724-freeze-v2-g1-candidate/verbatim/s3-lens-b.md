**B-1 — 攻撃面1：床の数値は、現行 oracle の勝敗閾値ではない。重大度：must-fix**

- **対象：** brief「研究前進」、plan:422 の床採用推奨。
- **主張：** g1 の発効が実行前提を満たすことと、床の数値が性能差の判定に効くことを分ける必要がある。今回指定された攻撃仮説「床は差の検出下限として variant vs stock に効く」自体が、現行実装には当てはまらない。
- **根拠：** `s8b_oracle_judge.py:680` は eligible な構成の二段中央値の最大値を取り、完全一致だけを tie にする。`s8b_verdict.py:710` の結論は予測差と swapped 追従の連言である。D501、D555、D1985、D2024 は、この分離と床比較の撤去を明示している。
- **反例・縮小案：** 他の条件が成立すれば、床より小さい差でも raw oracle は `unique-best` になり得る。「3% の床が微小差を丸める」「床が大きいので certified 判定が保守的」は不可。説明を「g1 は床・budget・出所を充填するが、この床値を勝敗閾値としては消費しない」に直す。

  > 現行 formula v2 に従ったこの1走行の床は、両 holdout とも配線下限が支配した。between-run 変動、誤判定率、検定力は保証しない。現行 oracle／最終判定は、この数値を性能差の閾値には用いない。

  certified 経路の手続的成立と、性能優越性・再現性の科学的保証を同一視しない。

## plan を採用してよいか (GO / NO-GO と条件)

**現状のまま実行計画として採用するのは NO-GO。**

解除条件は次の3点。

1. **restore 前の授権を確定する。** 保存 branch を D2077 の自動的な例外にしない。
2. **床の科学的説明と裁定表を直す。** 現行判定では閾値に使わないこと、追加 run でも最早適格選択は変わらないことを明記する。
3. **T-750 の残余と実施状態を docs から落とさない。** 「実装済み」と「全残件解消」を分ける。

固定 candidate path、改行なし budget 抽出、既存 CLI の利用、docs と chain の land 分離という技術案は支持する。文書修正案の準備は進められる。
