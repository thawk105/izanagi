### A1 — 「親 kill で道連れ」の保証範囲が広すぎる

- **種別:** 前提
- **対象:** brief:7,26,35–37／plan:134–138,275–279
- **内容:** 同じ PGID は signal の宛先を共有できる条件であり、親の死亡を子へ通知する機構ではない。plan は親 PID だけへの SIGKILL を除外しているが、SIGHUP、launcher を停止させない上位 shell の死亡、session 終了も未保証。事故記録は実行系の停止契約を信用できない根拠にはなるが、今回の固定 `rm` が同じ形で孤児化する直接証拠ではない。
  - **P1:** 段 9 を対象外にする判断は妥当。`dev_wave_cleanup.py:869–871` の削除は同一 process 内なので、その process 自体が終了すれば削除主体は残らない。ただし「その上位の親を kill した場合」まで保証する根拠にはならない。
  - **P3:** TERM/INT 転送は、plain PID kill に対応する局所補強として裁定の範囲内と判断する。
  - brief:26 の PDEATHSIG に関する括弧書きは曖昧。plan:138 のとおり、PDEATHSIG が親の SIGKILL に対応できないという説明にはしない。
- **放置時の成果物影響:** session 終了などでも子が停止すると誤認し、孤児による削除継続を見逃す。
- **推奨:** **must-fix**。保証対象を明記する。SIGHUP 転送を追加するかは段 4 の判断事項とし、未対応なら限界として明示する。

### A2 — 記録だけの handler を動かす待機設計が未確定

- **種別:** 正しさ境界
- **対象:** plan:65,69–83,94–101
- **内容:** handler がフラグを立てても、通常フローが無期限 `wait()`・`communicate()`・pipe read・期限なし selector に留まれば転送されない。EINTR が通常コードへ露出するとは限らず、自動再試行される待機も考慮が必要。
  - 全待機を短い有界待機または明示的な wakeup で進め、取消・個別 timeout・停止期限を確認すること。
  - spawn、PGID 検査、drain、診断出力などで例外が出ても、**登録済み全子を取消・回収する共通経路**を通すこと。単に `unknown / rc2` を返すだけでは孤児を残す。
  - signal の再入で期限を延長しない設計は妥当。ただし deadline は通常フローで一度だけ確定し、handler 内の複数代入が不可分だとは仮定しない。
  - 子 rc < 0 を interrupted とする設計は正しい。`ProcessLookupError` も reap 結果で判定すべき。
- **放置時の成果物影響:** TERM を受理した launcher が子を止められず、取消後も削除が続く。
- **推奨:** **must-fix**。

### A7 — escalation と変異の帰属は条件付きで妥当

- **種別:** 前提
- **対象:** plan:75–81,264–269／親の追加論点
- **内容:** 所有する直接の子だけを対象とする TERM→KILL は、取消を終結させる局所処理であり、汎用 supervisor 化には当たらない。5 秒／1 秒は運用値であり、停止保証の実測値ではない。終了未確認を `unknown / rc2` とするのは妥当。
  - M-a＋M-h を複合変異として登録し、独立 PGID 観測で赤にすることは可能。
  - ただし、M-a 単独でも赤になるため、**M-h の単独検出や PGID 不一致時の fail-closed の検証には数えない**。
- **放置時の成果物影響:** 複合変異の赤を、検査自体の有効性の証拠として過大計上する。
- **推奨:** **nit**。

## 変異 (a) を赤にする test の形

1. 実 launcher から起動された二つの子を、削除前の同期点で保持する。
2. test 自身が `/proc/<launcher>/task/*/children` 等で直接の子を特定し、PID の取り違えを防ぐ。
3. **launcher の JSON を根拠にせず**、test 自身が `os.getpgid(child_pid)` と `os.getpgid(launcher_pid)` を比較する。
4. 通常版では二つの子が同時に存在し、PGID が一致することを確認してから解放する。実 rm による削除、rc0、全件 removed を検証する。
5. `start_new_session=True` 変異では PGID 不一致、または launcher の fail-closed による非ゼロ終了で赤にする。同期点まで来ない異常終了も成功・skip にしない。

PGID 比較は観測時点の所属確認として意味があるが、「過去にも将来にも setsid しない」の証明ではない。親が所属を強制してから比較する構成では検査の独立性が弱まる。ただし、別 session になった子を親の group に戻すことが常に可能というわけでもない。

Linux では未回収 zombie の PGID も取得できるため、短命な子の正常終了だけを理由に検査を省略する必要はない。一方、exec 前の失敗は `Popen` 自体の例外になる場合があり、既に回収された PID 等の取得失敗は unknown とする。**PGID 一致は exec 成功の証明ではない。**

## 中断負例の決定性

**原 P4 の生存確認案は不可。ptrace 案は A4 の修正が必要。TERM 負例には、条件を明示した自己停止 wrapper 案を推奨する。**

wrapper 案の成立条件は次のとおり。

- wrapper は子を増やさず、自分自身を STOP した後、同じ PID で `exec /bin/rm "$@"` する。
- 全子の状態 `T` と PGID を確認してから、launcher PID だけに TERM を送る。
- 各子の `ShdPnd` に TERM bit が立つまで停止を維持し、確認後に CONT する。
- TERM の disposition が既定で、block／ignore されていないことを確認する。
- 子 rc `-15`、launcher rc2、interrupted、sentinel 残存をすべて検証する。KILL escalation による `-9` は合格にしない。
- 転送を削った変異では pending 待機が期限切れで失敗する。失敗後に CONT して削除を許さず、finally で停止・回収する。
- **正例では wrapper を解放し、実 rm への委譲と実際の撤去まで検証する。**

この制約なら、提示された DW-O14 の「実物へ委譲する観測 wrapper」に該当すると判断する。ただし中断ケースで証明するのは「削除開始前の直接子への転送」であり、実 rm 実行中の挙動まで証明したとはしない。

`ShdPnd` は送信元 PID を示さない。送信元まで直接観測する点では ptrace が強い。wrapper は ptrace 権限・Yama・イベント処理への依存を減らすため、今回の Linux／`/proc` 前提では扱いやすい。各待機に期限を置けば、5 分規律との整合も取りやすい。ただし実環境での成立は未実測。

**TERM の結果を INT に流用しない。** shell wrapper や起動元から継承した SIGINT ignore によって同じ手順が成立しない場合がある。INT は disposition を確認した別ケースにする。

PATH 解決は plan:50 の現案と整合するが、信頼済み PATH を前提にする。`/bin/rm` 固定なら executable の選択は明確になる一方、この wrapper 案は使えない。**test の都合だけで PATH 解決を採用せず、運用上の信頼境界として選択する。** `/bin/rm` 固定を採るなら、修正した ptrace 案が候補になる。

## 孤児経路の表

| kill の形 | 子が止まるか | 対処 |
|---|---|---|
| launcher PID へ TERM | 有界な通常フローで転送できれば停止要求が届く | A2 を実装・試験する |
| launcher PID へ INT | 転送されても子の ignore／block 状態に依存 | INT を別試験し、必要時 KILL。成功にはしない |
| launcher PID へ KILL | 同じ PGID でも自動では止まらない | scope 外の限界として明記 |
| 共有 PGID へ TERM | group 内の子へ直接届く。無視・block・group 離脱には限界 | 同一 PGID を独立観測。共有 group の他 process も対象になる |
| 共有 PGID へ KILL | group 内へ KILL が届くが、即時回収までは保証しない | JSON 欠落は不明。prune 禁止 |
| Bash tool の timeout | PID／group／process tree のどこへ何を送るか次第 | 実行系固有の停止契約を未証明扱いにする |
| Claude session 終了 | 終了だけでは子停止を保証しない | 子停止と launcher 完了が確認できなければ不明 |
| SSH 切断による SIGHUP | launcher だけが受ければ現案では子が残り得る | SIGHUP 転送の追加を判断、または限界を明記 |
| launcher の上位 shell だけを kill | launcher と子が継続し得る | 「親」は launcher を指すと明記する |
