# 段 4 裁定 — [T-2159] C05 の schedule 正本

## 結論

**C05 の schedule 権威解決の実装は本 wave で行わない。** 段 5・6 を飛ばし `4→7→8→9` とする。
本 wave が着地させるのは、ユーザーが同じ依頼で指示した **runbook の stale 記述の訂正**と、
**裁定パッケージ**である。

理由は 2 本で、いずれも独立の 2 レンズが別々のレンズから同じ結論に達し、親が一次資料と実測で
裏を取ったものである。

1. **実装は、権威のない仕様を 4 件その場で決めることになる。** schedule の hash はその仕様から
   決まるので、実装が自分で決めた形を自分で検証する構図になる。先行 wave (T-1380) で
   独立した敵対相談 4 本が同じ理由で暫定権威を不採用と勧告している。
2. **裁定 D1448 の前提が不完全である。** 「schedule 正本を新設すれば formal 経路が生きる」は成り立たず、
   上流の発効判定 (D959 の (a)) と未発効の批准凍結が独立に塞いでいる。この 2 点は D1448 の裁定文にも
   worklog 1184 の該当行にも記録がない。DW-S04 に従い、親は不採用にせず新事実を添えて
   ユーザー再裁定へ返す。

## real / refuted

### real・採用・scope 外 (裁定パッケージへ)

- **R1. `whiteboard` の空配列受理は、従来拒否していた入力を新たに受理する変更である。**
  レンズ A が「述語経路を通すための受理緩和であり絶対規律 2 に抵触する」と判定した。
  親実測 (M12) では、production 実値で `validate_authority` を落とす key は whiteboard 1 件だけで、
  ここを開けない限り authority は組めない。**この 1 点だけで実装の前提が閉じる。**
- **R2. 3 つの射影の形に権威がない。** `leakproof_context` を object へ包む field 名、
  `whiteboard` の exact-empty 規則、`descriptor_binding` の全 cell 表。いずれも先行 D530 が
  裁定したのは「呼び手供給・閉じた key 集合・型・非空性」までで、18 field の名と型対応は
  実装著者の選択だったことが記録されている。
- **R3. 事前登録 §5 の予算欄に cell ごとの予約値は無い。** 規範本文は「総上限と arm ごと・holdout ごとの
  上限」だけを定め、さらに「arm ごとの上限は対称」「holdout ごとの上限の和が総上限に一致」を要求する。
  プランはこの欄へ 4 つ目の key を人に書かせる設計で、consumer が規範側の欄書式を決めることになる。
  加えて**規範が要求する対称性・合計一致を検査する consumer は現行に無い** (親実測: `s8c_budget` は
  「予約の和 ≤ 上限」しか見ない)。
- **R4. 予算台帳の canonical path が未裁定。** `reserve_all_cells` は呼び手が渡した path をそのまま使い、
  正本 path を定義しない。命名は台帳の単一性と再利用単位を決める lifecycle 方針であって、
  実装者が選んでよい名前ではない。
- **R5. 試行 slot の `schedule_row_sha256` が C05 の schedule と結線されていない。** 親実測: 検査
  (`attempt_registry_core.py:1077`) は slot 自身が記録した値を読み返すだけで、schedule artifact から
  当該 hash を導く producer が存在しない。C05 の権威を実装しても、どの slot がどの schedule 行に
  対応するかは誰も保証しない。
- **R6. 全 cell の予約値 0 が受理され、予算保証が恒真化する。** 親実測: `_check_limit_state` は
  「予約の和 ≤ 上限」だけを見るので、全ゼロ予約は `held` になり run が続く。事前停止にならない。
  **本 wave の変更に起因しない既存の穴である。**
- **R7. C05 の評価器は artifact の中身を一切検証しない。** 空 bytes でも非 JSON でも第 1 関門を通る。
  D549 自身が「artifact/authority の中身の正当性を問わない」と明記している。したがって
  「artifact を置けば C05 の理由コードが進む」ことは、正しい schedule を発行した証拠にならない。
  先行 wave も同じ理由で自らの value 主張を取り下げている。
- **R8. schedule と予算の検証位置が遅い。** 現行 call site では attempt slot の予約・分類・
  lifecycle 開始の後に schedule/budget が検証される。「実走前に固定・検証」の失敗境界になっていない。
- **R9. D1448 の前提が不完全。** 上記のとおり。加えて D959 は (e) を (a) に従属する下流症状とし
  「順序を入れ替えて先に解除してはならない」と定める。D1448 は同じ対象を名指しした後発裁定だが、
  D959・上流閉塞・未発効の批准凍結への言及がなく、知情の上での上書きと判定できない。

## ユーザーへ返す択一 (裁定パッケージ)

実装を再開するには、次の 5 件が決まっている必要がある。**いずれも受理集合か正本の形を変えるので、
AI が既成事実にしない。**

1. **順序。** D959 の「(a) を先に解く」を、D1448 が明示的に上書きするか。
   上書きしないなら、許可リスト側 (T-2158) を先に片付けてから本件へ戻る。
   **親の推奨: 上流を先に片付ける。** 本件だけを実装しても正式起動は 1 ビットも近づかず、
   一方で未裁定の schema が source へ固定される。
2. **`whiteboard` の扱い。** 正式初期状態が空であることを、共有初期状態の権威にどう表現するか。
   (a) `whiteboard` を authority から外す、(b) 空を表現できる versioned schema へ改訂する、
   (c) 権威を呼び手供給のまま据え置く、の三択。
   **親の推奨: (b)。** 「観測が 0 件である」ことは初期状態の本質なので digest に入れる価値があるが、
   それは空配列の特例ではなく、明示的に表現できる形であるべきである。
3. **cell ごとの予約値の置き場所。** §5 の予算欄へ 4 つ目の key を足すのか、
   6 cell manifest 側へ置くのか。**親の推奨: manifest 側。** §5 の欄は総量の欄であり、
   cell 単位の情報は manifest の担当である。あわせて規範が要求する対称性・合計一致の検査を
   予算 consumer へ入れる。
4. **予算台帳の正本 path。** 単一固定 path か、manifest 由来の派生名か。
   台帳の再利用単位と identity の意味を同時に決める。
5. **schedule 行 hash の正本形。** slot が持つ `schedule_row_sha256` の preimage を定め、
   genesis producer と C05 schedule を同じ digest で結線する。

  C10 が既に満たされている事実を見落とす。実測値と正本が食い違ったままになる。

  実装してもしなくても変わらない。変わるのは source に固定される未裁定 schema の有無だけである。
