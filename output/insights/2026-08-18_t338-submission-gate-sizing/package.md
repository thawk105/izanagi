# [T-338] 裁定パッケージ — 投入 gate の規模と、どう進めるか (2026-08-18)

本 wave は投入 gate を実装しなかった。**理由は「難しいから」ではない。**
2026-08-18 の裁定が付けた条件どおりに規模を実測したところ、条件が発動し、
切り直しを試みたが、**規律を緩めない切り方が存在しなかった**からである。
**判断はユーザーが行う。親は推奨を添えるが決めない。**

## 分かったこと (一言で)

投入 gate は、承認済みの記録項目が要求する検査を全部実装するということである。
その量を実測したら **production 2,570〜6,200 行** (テスト込みで概ね 3 倍) だった。
過去にユーザーが「プロトタイプ基準に照らして過大」と判定した水準は production 645〜816 行
(D220) なので、**3.2〜7.6 倍**である。

裁定は「D205 / D220 の水準に触れるなら同 wave 内で範囲を切り直せ」と条件を付けていた。
そこで親は 2 通りの切り方を用意したが、**独立した 3 本の検証子 (段 2 プラン子、段 3 敵対レンズ 2 本) が
全員、どちらも「承認済みの受理条件をこっそり緩めている」と判定した。**
起動命令は「規律 2 を緩める方向の変更は採らない」と明示しているので、親は採れない。

## ただし、閂は 1 つ外れた

前回の wave (D500) は「RF producer を止めているのは投入 gate である」と同定し、
その gate を作るには T-139 の V1 (新しい exact-byte 承認 payload を作るか) というユーザー裁定が
先に要る、という状態だった。そしてその V1 は D320 (bytes 級 provenance 機構の新設は既定で見送り) と
正面から衝突していた。**本 wave はこの衝突を消した。**

T-139 の裁定パッケージは「新しい承認 payload を作らずに B1 を閉じる案は 2 つしかなく、
どちらも駄目 (受理集合が空になるか、受理条件が弱くなるか)」と書いていた。
実測したら**第 3 の経路があった**。

- CCBench のビルド定義 (`external/ccbench/cmake/Options.cmake:59-67`) は
  `ADD_ANALYSIS` と `TRACE` をコンパイル定義として吐く。だから CMakeCache のこの 2 値は、
  各ソースファイルのコンパイル引数として `compile_commands.json` に必ず現れる。
- 凍結済みの受領証 schema は、その `compile_commands` を **path / size / sha256 の三つ組**として
  既に持っている。検証側が実ファイルの中身を読み直せる。
- 承認済み記録項目 §6.3 の逐語は、3 つ目の照合先を「`cmake_cache` の**申告値**」と定義しており、
  raw な `CMakeCache.txt` を読み直せとは書いていない。
- さらに同文書 §0 に「producer が申告した派生値は、受理集合を狭める方向にだけ使う。
  不一致を拒否理由にし、一致は受理の正の根拠にしない」という逐語が既にある。

**つまり B1 は、凍結された bytes を 1 bit も変えずに閉じられる。**
新しい承認 payload も schema 変更も要らない。D320 との衝突も起きない。

## 決めてほしいこと

### Q-A (最重要). 投入 gate に production 2,570〜6,200 行を投じるか

- **(a) 投じる。** 本 wave が確定させた 6 単位分割を複数 wave に分けて実行する
  (依存順 `1||2` → `3`,`4` → `5` → `6`。4 名前の export は最終 wave の最終 commit だけ)。
  **規律を 1 つも緩めない唯一の道。**
- **(b) RF study (T-139) 系列を畳む。** pilot も本走も行わず、受領証 gate も作らない。
  D292 の投入禁止を恒久化する。T-338 / T-139 系列の未了項目は一括で閉じる。
- **(c) 承認済みの受理条件を明示的に縮小する新しい decision を起こす** (= 自分たちで上げた
  証拠水準を、名指しで下げる)。本 wave が作った全 63 件の分類表がそのまま候補表になる。
  どれを落とすかをユーザーが指定する。

**親は Q-A に推奨を付けない。** これは費用の判断であって、親が決める性質のものではない。
ただし 1 つだけ言っておく — **止めているのは物理ではなく、自分たちで課した証拠水準である。**
(c) は正当な選択であり、D320 が既に「bytes 級 provenance の新設・維持は既定で見送り」という
同じ方向を定めている。(c) を選ぶ場合、落とす制約ごとに「これを落とすと成果物のどの値・
受理集合・参照がどう変わるか」を 1 行で書いた表を親が用意する。

### Q-B. D229 決定 (8) の必須 kill 3 件を、どの段の受入条件に置くか

D500 が「どの段の受入条件に置くかはユーザー裁定へ返す」と明記したまま未回答の項目である。
本 wave は必須 kill 2 件目 (親系列 ID の自己申告で累積有意水準をリセットする攻撃) を
止める全履歴検証を作る wave なので、これは直接の受入条件になる。

- **(a) validator / consumer 段の受入条件へ移す (producer 段では登録しない)。** ← 親の推奨
- (b) producer 段の条件として残す。→ producer は 3 件が kill できるまで完成としない。

### Q-C. B1 の閉じ方

- **(a) 上記の第 3 の経路を採る。** `cmake_cache` の申告値を**拒否専用**にし、受理は
  `compile_commands` 実体の読み直しと `configure_argv` のマクロ一致で決める。
  **新しい承認 payload は不要、凍結 bytes は不変。**
  保証境界に「受領証が raw `CMakeCache.txt` を持たないため、configure 後に cache だけを
  編集した乖離は検出しない」と逐語で書く。← **親の推奨**
- (b) T-139 V1 の イ を作る (新しい exact-byte 承認 payload で schema に
  `cmake_cache_raw` を足す)。→ D320 の既定に反するので別途承認が要る。

**注記:** 段 3 のレンズ A は (a) を「3 者一致を 2 者一致へ弱める」として blocker に挙げたが、
親は refuted と裁定した。理由は上記のとおり §6.3 の逐語自身が 3 つ目を申告値と定義しており、
レンズ A が挙げた反例 (実 cache が 1 で他が全部 0) は**凍結 schema に raw pointer が無い以上
どの実装でも検出できない**ため、(a) 固有の弱化ではなく schema 自身の限界だからである。
この判断に異論があれば Q-C を (b) にするか、schema の限界を承認し直すことになる。

## 親が本 wave で訂正した自分の誤り (4 件)

隠さず書く。いずれも独立した検証子が見つけたか、親が裏取りで確認した。

1. 「述語を保存して機構だけ粗くする」案は不成立だった。承認済み文書自身が同じ穴を
   既知として記録していたのに、親はそれを読まずに案を書いた。
2. 検査の階級分けを 4 か所で間違えた。B 級と思ったものはほぼ全部 A 級だった。
3. 「symlink 対策は既存実装で無料」は誤り。既存実装は最終要素しか守っていない。
4. 「重複キー拒否は既存実装で無料」は誤り。その実装は承認されていない別の制約
   (canonical bytes) も一緒に強制するので、そのまま流用すると受理範囲を勝手に狭める。
