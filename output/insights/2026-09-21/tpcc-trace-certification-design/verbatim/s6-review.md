## M1 — si の最終 cstamp と snapshot だけでは、読取り時の可視性を再構成できない

**本文の位置:** §4.4「挿入 ≤ snapshot < 削除なのに返っていなければ取りこぼし」、§8 項6「si は snapshot 時刻」。

**根拠 path:line:** `CC/cc/si/transaction.cc:35`, `:68-73`, `:153-158`, `:170-211`, `:424-452`, `:479-519`, `:563`, `:586`。

`read_internal()` の条件は **status が committed/deleted で、かつ cstamp ≤ txid_** です。等号は可視側ですが、時刻比較だけでは足りません。

静的に次の経路があります。

1. 最後に公開された `lastcstamp` と `Lsn` が n。
2. I が木へ初版を挿入し、まだ inflight。
3. S が begin し、`txid_=n+1`。上限なし scan で I の物理候補に触れるが、inflight なので返さない。
4. I が `cstamp=n+1` で commit。
5. S が commit。

INSERT の commit は版 status の公開であり、木を再挿入しません。この間に別の構造変更がなければ、S の node validation はこの不可視観測を排除しません。最終履歴では `I.cstamp == S.snapshot` ですが、実際の読みでは不可視でした。本文の規則はこれを取りこぼしと誤分類します。`lastcstamp` は各取引の書込み公開後に更新されるため、「その値以下の全版が読取り時に公開済み」という全体 frontier でもありません。

さらに DELETE は木から key を除去します。snapshot では旧版が見えるはずでも、scan が tuple を取得できず、その旧版へ到達しない経路があります。これは時刻から実観測を復元できない別の理由です。abort 版は cstamp に関係なく飛ばされます。`install_version()` の ww 検査も、この読取り時の公開状態を保証しません。

**放置時の影響:** si の検出専用経路が、実際の不可視観測を欠落と誤判定し、存在しない依存または不要な indeterminate を作ります。

**修正案 — 差し替え文:**

> si の txid_ と committed write の最終 cstamp は可視性の必要条件として使うが、不在の観測版を単独では決めない。read_internal は読取り時の status と cstamp の両方で版を選ぶため、Q にその場で選択した版、または不可視となった理由を値で保存する。cstamp == txid_ は committed/deleted として観測した場合に限り可視側である。木から除去済みで候補を取得できなかった key は、物理除去との前後関係を別途証明できなければ indeterminate とする。abort 版を不存在版の producer にしない。

## M2 — 「挿入のみ」「初期存在＋削除」にも直接証拠が必要

**本文の位置:** §4.4 表の「挿入前しかありえない」「削除後（返っていないので）」。

**根拠 path:line:** 本文 `README.md:150-165`、`CC/cc/silo/transaction.cc:299-318`, `:663-684`、`CC/cc/si/transaction.cc:424-452`、`TP/tpcc_tx_neworder.hh:279`。

この表は、検査対象に取りこぼしがないことを先に仮定しています。挿入済みの OrderLine を壊れた scan が落としても「挿入のみだから unborn」と扱えます。同様に、初期 key を削除前に落とした scan を、履歴後方に DELETE があるだけで「削除後」にできます。

§4.5 の「証拠あり」と矛盾しており、実装者がどちらを採るかで受理集合が変わります。初期 key の取りこぼしを検査する §4.3 とも非対称です。

**放置時の影響:** 挿入・削除の履歴が存在する key に限って、scan 欠落を正当な不在へ読み替える受理経路が残ります。

**修正案 — 表の差し替え文:**

> 挿入のみの key：挿入前を直接証明できる場合だけ S→I。初期存在＋削除の key：削除後を直接証明できる場合だけ D→S。いずれも、存在する期間の取りこぼしを証明できれば履歴不整合、観測時点を決められなければ indeterminate とする。履歴に INSERT/DELETE があること自体は観測時点の証拠ではない。

## M3 — §4.4 の反例は、提案された通し番号では G2 の赤にならない

**本文の位置:** §6.2「偽認定の反例：証拠あり: G2 で赤」。

**根拠 path:line:** 本文 `README.md:157-165`、`CC/cc/silo/transaction.cc:477-485`, `:706-709`、`CC/cc/mocc/transaction.cc:1042-1050`。

反例の順序は次です。

```text
S.scan開始 < S.scan終了 < I.挿入直前 < D.除去直後 < S.node検証終了
```

したがって、

- `D.除去直後 < S.scan開始` は偽。
- `I.挿入直前 > S.node検証終了` も偽。

R4 は不在を決められず、**indeterminate** になります。既知の辺は `I→S`（y の wr）と `I→D`（k の ww）。G2 に必要な `S→I` は証明されません。

実際の観測が unborn だったと別の証拠で確定できれば、`S→I→S` が赤になります。しかし、その証拠を現案の四つの採番位置は提供していません。stock の node validation が取引を abort する場合と、それを外した control の判定も区別が必要です。

**放置時の影響:** 実装 wave が達成できない G2 検出を受入条件にし、保守的拒否を検出力の実証と取り違えます。

**修正案 — 差し替え文:**

> この反例は現行の通し番号案では区間が重なるため indeterminate とする。直接の unborn 観測を与えた fixture では S→I の predicate rw と I→S の point wr により G2 を検出する。実 CC の同一 schedule でも G2 を確定したい場合は、scan 終了などの追加証拠を設計し、その費用を別途見積もる。

## M4 — 通し番号の保護位置と trace への保存契約が未定義

**本文の位置:** §4.4「全体通し番号（atomic）」、§3.1・§4.1 の形式、§7.1 単位6。

**根拠 path:line:** `CC/include/trace.hh:25-46`、`CC/include/masstree_wrapper.hh:135-179`, `:194-208`、`CC/cc/silo/transaction.cc:395-402`, `:682-684`、`CC/cc/mocc/transaction.cc:1187-1207`、裁定控え `2026-09-21-vldb-direction-verdicts.md:17`。

二つの不等式自体は、信頼できる位置で採番すれば保守的な十分条件です。ただし現案には次が欠けています。

- 採番値をどの record に保存し、どの取引・key・scan と結び付けるか。
- 合成される関数が呼出しを削除・移動・偽装できない位置。
- 成功した木の操作、失敗した挿入、abort 時の除去の区別。
- atomic の順序契約。既存 `next_txid()` は grouping 用の relaxed 採番であり、そのまま物理順序の証拠とする根拠にはならない。

silo は木から除去した**後**に absent と新 tid を公開し、mocc も除去後に tidword を保存してから後段で unlock します。除去後番号は「木に無い」証拠であって、保持済みポインタを読む側が tombstone を観測済みという証拠ではありません。未 commit INSERT を既に取得した reader の lock 待ちも、木の採番だけでは表せません。

また wrapper は `table_.scan()` を呼び出すだけです。指定 worktree 内で確認できた `masstree_scan.hh` は試験 fixture で、実依存の split/retry 実装ではありません。実依存は `CC/cmake/ThirdParty.cmake:35-45` の pin です。**split を含む走査保証は本レビューでも未証明**です。全 scan の線形化可能性と、必要な範囲の安定 key を落とさない保証を同一視しない方がよいです。

**放置時の影響:** メタデータを改変できる variant を認定したり、計装完成後に形式・保護境界の追加工事が発生したりします。

**修正案 — 追記文:**

> 採番器・保存状態・呼出し・include はすべて `#if TRACE` 内に置く。木の実操作と採番の対応、および scan 境界の記録は、合成 variant が変更できない保護された実行経路で取得する。採番値の record 形式、取引/key/scan への対応、成功・失敗・abort の区別、順序契約を単位6の完了条件に含める。tombstone は committed DELETE producer と対応する版を実際に観測した場合だけ証拠にする。Masstree の固定 pin に対する split/retry の保証が閉じるまでは、未決の不在を認定しない。

## M5 — 約7億は依存理由の候補数であり、現行 verifier の辺数との比較が不正確

**本文の位置:** §4.7「辺の総数は概ね `10 × N_D² / 2`」「現行 verifier の最大実績は2.9億本」。

**根拠 path:line:** `V/dsg.py:635-643`, `:680-682`、`TP/tpcc_tx_delivery.hh:199-222`、`output/insights/2026-09-20/verifier-capacity/README.md:46-47`。

同じ Delivery は10 district を処理します。各 district から同じ取引対 `D_i→D_j` を得ても、現行 adjacency は宛先を集合で重複除去します。

1倉庫で全 Delivery が全10 districtを順に配送する例では、`N_D=12,000` に対して、

- key ごとの依存理由候補：`10×N_D(N_D−1)/2 = 719,940,000`
- 重複除去後の取引対：`N_D(N_D−1)/2 = 71,994,000`

です。列挙負荷の二乗増加は残りますが、格納辺数は同じではありません。また引用先の次行には **594,786,279辺、896秒** の改修版実績があり、「最大2.9億」は反証されます。

**放置時の影響:** 隣接グラフのメモリ費用をこの例で約10倍に見積もり、間引きの必要性と計算予算を誤ります。

**修正案 — 差し替え文:**

> 1倉庫・各 Delivery が全10 districtを順に配送する条件では、削除後観測の依存理由候補数は約 `10×N_D(N_D−1)/2`。現行同様に取引対を重複除去した辺数は、この例では約 `N_D(N_D−1)/2` である。N_D=12,000なら約7.20億候補・約7200万辺となる。比較実績には5.95億辺・896秒があるが、新述語列挙の時間には直接換算しない。

**辺の間引きが健全に成立する条件（1行）:**

> 削除する各辺 u→v を、削除後も残る直接証拠付きの有向路 u→…→v が代替し、その路を構成する辺を相互依存で同時に削除しないこと。

「連続 Delivery だから鎖がある」と仮定せず、実際に証明された辺でこの条件を満たす必要があります。

## S6 — 段3 Aの mocc 高温経路の所見が落ちている

**本文の位置:** §5.1「absent の読みで abort」、§5.2・§8 項2の寿命修正。
