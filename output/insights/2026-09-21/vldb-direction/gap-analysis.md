## 0. 結論

1. **今のままでは VLDB のどのトラックにも出せない。**
   - 中心主張「合成が既知の最良を超える」は不成立。
   - 唯一の成功例 (Silo の静的 backoff) は Polyjuice (OSDI'21) が既に示した内容。
   - LLM が必要だったことは未取得。
   - 評価は Silo・YCSB 3 種・48 スレッドだけ。
2. **第一候補は EA&B (Experiments, Analysis & Benchmark) トラック。** 中心命題の案は「CC の最適化において、探索空間の構造・正しさ検証の費用・未知 workload への転移が、LLM と非 LLM の探索の有効性をどう決めるか」。Codex と私で一致した。
   ただし EA&B は、Systems で勝てなかった論文の受け皿ではない。他の研究者の判断を変える一般的な知見が要る。
3. **最優先は「LLM が本当にコードを書く空間」を 1 つ開くこと (私の見解。Codex は優先度を低く置いた → §8)。**
   - 今の合成空間 (backoff の数値 1 個・79 値の施錠順序・5 bit の発火条件) は列挙し尽くせる。LLM の出番が無い (B-5 試走で LLM・random・sweep の差 1.06%)。
   - LLM が直列化可能性を壊す余地もほぼ無い。差別化点「毎回の直列化可能性検査」について、**LLM が生成した候補を verifier が実際に捕まえた記録は見つからない** (論文ストーリー・phase3・worklog archive の grep の範囲。全数の証明ではない)。検出力は人為的に壊した Silo / si でしか示されていない。
4. **締切 (公式の投稿規定で確認、2026-09-21 取得)。**
   - PVLDB Vol.20 (VLDB 2027) は毎月 1 日締切で、**最終は 2027-03-01**。
   - **研究トラックで却下された研究は 1 年間再投稿できない。**
   - EA&B は**初回投稿時に全実験の再現パッケージのリンクが必須**。
   - → 見切り投稿はしない。現実的な目標は 2027-02-01 か 03-01 (残り約 4.5〜5 か月)。
5. **最初の 4〜6 週間は「中心結果を取りに行けるか」を判定する期間にする。** 研究の帯域を空けるため、次の 2 つをやめる。
   - 凍結・批准・受領証系の手続きで止まっている旧系列の再開を、論文の必須経路から外す。
   - 台帳の open 項 610 件を研究計画の母集合にすること。

## 1. 現状の実証状態 (論文ストーリー最新版 2026-09-21c ほか)

| 主張 | 状態 | 数値・根拠 |
|---|---|---|
| 評価器 (trace verifier・観測者効果の分離・床値) | 実証済み | 壊した Silo で G2 1,310 件、si で 3,576 件を検出、素の Silo は緑。trace は compile 時に除去 (nm で確認) |

## 2. 関連研究から見た新規性リスク (Web で実在を確認したもの)

- **Polyjuice (OSDI 2021)**: §4.5 で Silo 上の backoff も学習し、TPC-E 高競合での利得は主に学習した backoff によると明記している。
  → 静的 backoff の利得は中身としての新規性が低い (確信度: 高)。
- **Barbarians at the Gate / ADRS (Cheng ほか、arXiv 2510.06189、2025)**: OpenEvolve で transaction scheduling を扱い、既存最良 SMF を再発見、offline で makespan −34%。
  → 「LLM の進化探索で txn 処理の手法を設計する」には先行がある (確信度: 高)。ただし評価は Python シミュレータで、直列化可能性の検査の記述は無い。拡張版 arXiv 2512.14806、AI-Driven Research for Databases (arXiv 2604.06566) も同系統。
- 学習型 CC: NeurCC / CCaaLF (arXiv 2503.10036、SIGMOD 2026 採択と記載あり・本文は未確認)、ATCC (arXiv 2603.13906)、TxnSails (arXiv 2502.00991)。AI を使わない workload 特化 CC: DCDS (arXiv 2404.13359)。
- **AIChilles (arXiv 2606.15834)**: AI 進化で得た 30 本のプログラムから 49 個の弱点 (正しさの欠陥・未知 workload での退行) を発見した。**毎回検証する動機を外から支える材料。**
- LLM × DB の評価の作法 (GPTuner PVLDB 2024、λ-Tune SIGMOD 2025、R-Bot PVLDB 2025、GenDB VLDB 2026 Demo):
  - 複数のベンチを使う。
  - BO / RL など非 LLM の強い基準と比べる。
  - 調整にかかる時間を示す。
  - 成果物を公開する。
  - 学習データへの漏れを対策する。
- **残る差別化点** (確信度: 中。網羅検索はユーザー裁定 D1760 / D1931 で停止しており「世界初」は言えない):
  1. 実機で、直列化可能性を毎反復 trace から検査し、壊れた理由を構造化して返すこと。
  2. 報酬ハックの監査と、勝ち筋の漏れの制御。
  3. 同一基盤 (CCBench) での公平な比較と、否定的結果の定量化。

## 3. 投稿区分 (Codex の整理、私も同意)

| 区分 | 論文が主張すべき中心命題 | 現状との距離 |
|---|---|---|
| **EA&B (第一候補)** | 探索空間の構造・検証費用・未知 workload への転移が、LLM / 非 LLM 探索の有効性をどう決めるか | S-1a・P2-5 が出発点。Silo と小さな軸への偏り、手法間の公平な比較・一般化・失敗原因の説明が足りない |
| Regular Research (Systems) | 実行履歴から得る構造化反例を使って CC 実装の動作を合成する方式が、強い既存手法より有用な実装を実用的な費用で生む | 動作を増やす合成、反例利用の効果、強い基準に対する利得のいずれも不足 |
| Vision | CC 合成を成立させる新しい設計原理と初期証拠 | 「CC × LLM × 毎回検証」の組合せだけでは弱い |

Codex が EA&B で検証したい仮説 (結論ではない):

1. 小さく構造化された CC 設定空間では、LLM の生成能力より探索予算と空間の表現が結果を支配する。
2. コード変更の自由度を増やすと、有効候補の発見率と検証費用が支配的になる。単純な「最高 TPS」の比較は手法の選択を誤らせる。
3. 探索時の勝者と、未知 workload で採用すべき候補は異なり、その差を説明する CC 固有の要因がある。

## 4. 必須の実験・実装 (優先順。Codex の案に私の並べ替えを反映)

**P0. 検証の意味と容量を確定する。**
- **示すこと**: 何を検出でき、何を判定していないか。
- **最小構成**: 期待結果つきの小さな履歴コーパス (直列化可能な履歴・異常履歴・abort・欠損 trace・同一キーへの複数操作) と、意味の異なる CC 変異 20〜40 個で検出力を測る。
- **既存の制約**: 大きな trace の容量 (balanced 10 秒で 32 GiB、read-heavy 6 秒で約 81 GiB、ノード上限約 115 GiB) を先に測る。分割するなら、境界をまたぐ依存を保つ。
- **論文での書き方**: 「certified は有限の観測履歴に対する判定で、全実行の証明ではない」と全体で統一する。
- **費用**: 実 trace 10〜20 本の検証で約 1.3〜2.7 node 時間 (read-heavy・build・準備費は別)。

**P1. LLM が関数単位でコードを書く空間を 1 つ開く (私は第 2〜3 週から必須と見る)。**
- **何を書かせるか**: Silo の abort 後の待機・再試行方策や、競合の状態に応じた待機方策など。LLM が関数の本体を書く。
- **なぜ要るか**: ここで初めて、LLM の出番 (列挙で足りない空間) と、verifier の出番 (LLM が壊した候補を捕まえる) の両方が生まれる。
- **測るもの**: 有効候補率、anomaly で reject された率と壊れ方の分類、最良 certified 候補 vs stock・`p2_2_flag_opt`・調整済み静的 backoff。
- **前提**: 現行の編集面 (合成枝の中身だけ・#include / 関数 / 型の追加禁止・3 file) を広げる判断が要る (§7 項 3)。**正しさゲート (anomaly 即 reject、trace の compile 時除去、毎回検証と構造化フィードバック) は不変。**

**P2. 公平な比較基盤と第 2 プロトコル。**
- **比較する手法**: random・sweep (座標探索)・BO・進化探索・LLM。同じ候補適用・検証・計測の口を通し、同じ stock・既知最良・初期候補・観測情報を与える。既存研究の探索法を移植したら「再実装」と明記する。
- **第 2 プロトコル**: trace のある MOCC が第一候補。X/P 計装の pin 候補化は [T-2844] で進行予定で、完成度は未確認。
- **注意**: 有限空間だけで LLM が負けても、コード合成一般への結論にはしない (P1 が要る理由)。

**P3. 探索の独立反復で、費用と成果の曲線を取る。**
- **規模 (Codex の案)**:
  - 試走: 2 プロトコル × 2 課題 × 5 手法 × 3 独立探索 × 8 候補 = 480 候補評価 (B-5 の見積りからの換算で約 68 node 時間)。
  - 本比較: 3,600 候補評価 (約 510 node 時間)。LLM は直列で約 120〜156 時間。
- **比較の分け方**: 候補評価数を揃えた比較と、経過時間を揃えた比較を分ける。
- **指標**: 有効候補率・最初の有用候補までの時間・検証時間・人間の介入。
- **原則**: **候補を 8 回測り直すことと、探索を 8 回やり直すことは別。** 手法の比較には後者が要る。

**P4. 未知条件への転移と再現。**
- **留保条件**: 生成・選択に使わない条件 (read/write 比・競合・スレッド数・トランザクション長・アクセス集合の重なり) を先に留保し、stock・強い静的設定・各手法の選択結果を比べる。
- **追試と事前の固定**: 主要結果は別日・別割当てで追試する。同等幅は事前に決める。
- **比較の置き方**: 既知最良 `p2_2_flag_opt` を外さない。CCBench 既定比の大きな数字を主結果にしない。
- **規模**: 例 2 プロトコル × 27 条件 × 6 候補 × 8 反復 = 2,592 run ≈ 54 node 時間。

**P5. 結果の理由を介入で説明する。**
- **比較する介入**: workload 記述あり / 伏せる / 入れ替える、critic あり / なし。verifier と失敗理由の返却は外さない (規律 2・3)。
- **出力コードの分類**: 人が読んで、既知候補の再発見・無効変更・機構の変更に分ける。

**P6. 再現パッケージを実験と並行で作る (EA&B は初回投稿時に必須)。**
- **保存するもの**: コード、生成パッチ、入出力、探索設定、失敗候補を含む実験データ、図表の生成手順。
- **分けるもの**: LLM の再生成と、保存済み候補の再検証・再計測を分ける。
- **provenance**: 粗くてよい (システム名・モデル表示名・おおよその時期。ユーザーの既存方針)。凍結 chain は足さない。

**あると強くなるもの**:
- TPC-C (表識別子・app 層の abort・range 読みの意味を詰めてから。table ID を足すだけでは済まない)
- cygnus での 96 スレッド・NUMA
- 第 3 プロトコル
- 第 2 の LLM 系統
- 時間変化する workload

## 6. 最初の 6 週間 (判定の期間)

| 時期 | 着手すること | その時点の判断 |
|---|---|---|
| 第 1 週 | 中心命題・評価指標・留保条件・投稿目標月を決める。並行して P0 (検証コーパス・容量) と公開可否の確認 | 正しく比較できる範囲を確定する |
| 第 2 週 | P1 のコード空間の設計と最初の生成 (私の案)。並行して P2 の共通比較基盤と非 LLM 手法、MOCC の trace と検証 ([T-2844]) | 第 2 プロトコルへの投資を続けるか |
| 第 3 週 | 480 候補評価以下の試走 (有限空間 + P1 の空間)。探索間の分散・検証費用・失敗の種類・壊れた候補の数 | 本比較の規模を決める |
| 第 4 週 | workload 記述・critic の介入比較。P1 の結果から空間を調整 | 説明可能な兆候があるか |
| 第 5〜6 週 | 有望な問いに本比較を集中。未知条件・別日追試。再現パッケージの試走 | EA&B を続けるか、Systems へ進む根拠が出たか、組み替えるか |

**判定の基準 (Codex)**: 4〜6 週後に、強い基準との比較から新しい境界・原因・評価方法が出てこなければ、EA&B に名前を変えて投稿しない。研究課題を組み替える。

**負の結果を論文にする設計** (Codex):

| 起こりうる結果 | 論文にするために要るもの |
|---|---|
| LLM と非 LLM に差がない | 同等幅を事前に決め、「実用上同等」を十分な精度で示す (単なる有意差なしで終えない) |
| LLM が遅い・悪い | 生成費・無効候補・誤収束・空間との不適合のどれが原因かを分け、複数課題で再現する |
| 広いコード空間で壊れた候補が増える | 変異の種類と破綻原因を対応づけ、有効候補率と検証費用の関係を示す |
| 探索条件で勝ち、未知条件で負ける | 事前に留保した条件で退行を測り、どの workload 特徴が失敗を予測するか示す |
| 全手法が既知の backoff を再発見する | 既知解までの到達費用と、到達しない条件を説明する (再発見そのものを新規性にしない) |

## 7. ユーザーに決めてほしいこと

1. **主目的**: EA&B を第一候補にし、LLM が勝たない結果も主要成果として扱うか。(Codex・私とも賛成)
2. **主張の射程**: 当面は point read/write の CC 最適化に限定するか。(限定を推奨。TPC-C は後の投資判断)
3. **探索空間を開く**: LLM が関数単位でコードを書ける空間を足すため、現行の編集面の制限 (合成枝の中身だけ・#include / 関数 / 型の追加禁止・3 file) を広げてよいか。**正しさゲートは変えない。**
4. **費用**: 試走 (約 68 node 時間 + LLM 数十時間) → 本比較 (約 510 node 時間 + LLM 120〜156 時間) を段階ごとに承認する形でよいか。
5. **止まっている手続きの扱い**: 旧系列の再開 ([T-2812] の択一、8b / 8c の official 系列) を論文の必須経路から外し、凍結 chain を新設しない方針でよいか。
6. **公開**: 失敗候補と否定的結果を含む実験一式を公開できるか (EA&B では必須。できない主要部分があるなら区分を再考)。
7. **目標締切**: 2027-02-01 か 2027-03-01 (Vol.20 の最終) か。
8. (任意・要判断) **計算ノードの H100 で open-weight のコード LLM を動かすか。**
   - 得られるもの: 第 2 の LLM 系統と、サブスクの直列時間 (120〜156 時間) を超える並列度。API キーや従量課金は伴わない。
   - 鉄則との関係: 計算ノードから LLM を呼ぶ設計は、鉄則により実装前にユーザーへ諮る項目なので、ここでは提案だけに留める。

## 8. Codex と私の見解の一致・不一致

- **一致**:
  - EA&B が第一候補。
  - 小さな有限空間では LLM が要らない可能性が高い。
  - 静的 backoff を「LLM による CC 合成の成功」として運ばない。
  - TPC-C の全面対応は後回し。
  - §5 のやめる作業。
  - 再現パッケージは実験と並行で作る。
