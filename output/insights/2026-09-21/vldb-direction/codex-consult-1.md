**私なら、EA&B を第一候補に置き、最初の 4〜6 週間で成立可能性を判定します。** Systems に必要な「新しい CC 合成機構の有効性」はまだなく、EA&B に必要な「他の研究者の判断を変える一般的な知見」も現状では不足しています。ただし、強い既知最良との比較、合成の失敗、検証費用という材料は、後者へ発展させやすいです。

以下、実証状態と関連研究の内容は brief を前提とした独立見解です。追加確認は作業規律と公式 CFP・投稿規定だけです。工数・計算量は概算で、実装の難易度は未確認です。

**1．投稿区分と、論文の中心命題**

| 区分 | 主張すべき中心命題 | 現状との距離 |
|---|---|---|
| **EA&B：第一候補** | 「CC 最適化において、探索空間の構造、正しさ検証の費用、未知 workload への移行が、LLM・非 LLM 探索の有効性をどう決めるかを明らかにする」 | S-1a・P2-5 は出発点。ただし Silo・限定された軸に偏り、手法間の公平な比較、一般化、失敗原因の説明が足りない |
| **Regular Research / Systems** | 「実行履歴から得る構造化反例を利用して、CC の実装上の動作を合成する方式が、強い既存手法より有用な実装を、実用的な費用で生成する」 | 現在は小さな設定空間の探索が中心。動作を増やす合成、反例利用の効果、強い基準に対する利得のいずれも不足 |
| Vision | 「CC 合成を成立させる新しい設計原理と、その原理を支持する初期証拠」 | ①CC、②LLM、③毎回検証、という組合せだけでは弱い。独自の原理が別途必要 |
| SDS / Demo | SDS は実運用上の課題解決、Demo は動作するシステムの提示 | brief には SDS を支える運用実績がない。Demo は中間成果にはなるが、研究論文の目標とは別 |

Systems は設計・抽象化・既存技術の有効な組合せでも新規性を主張できます。新しい CC プロトコルの発明までは必須ではありません。一方、EA&B は既存手法への新しい洞察や評価方法を要求します。**EA&B は、性能で勝てなかった Systems 論文の受け皿ではありません。** [公式 CFP](https://vldb.org/2027/call-for-research-track.html)

私が EA&B で検証したい仮説は、次の三つです。いずれも現時点では結論にしません。

- 小さく構造化された CC 設定空間では、LLM の生成能力より探索予算と空間の表現が結果を支配する。
- コード変更の自由度を増やすと、有効候補の発見率と検証費用が支配的になり、単純な「最高 TPS」での比較が手法選択を誤らせる。
- 探索時の勝者と、未知 workload で採用すべき候補は異なる。その差を説明する CC 固有の要因がある。

現状で最も危険なのは、static backoff の利得を「LLM による CC 合成の成功」として運ぶことです。brief の Polyjuice の事実を前提にすると、その主張は内容面でも因果面でも支えられません。

**2．EA&B に向けた必須実験・実装**

以下の「必須」は公式の件数要件ではなく、**この中心命題で私が投稿判断の条件にするもの**です。

**優先 0：検証の意味と容量を、実験可能な範囲に確定する。**

- **示すこと：** 何を検出でき、何を判定していないか。生成候補の比較が、検証漏れや OOM によって歪んでいないか。
- **最小構成：** 既知の直列化可能な履歴、既知の異常履歴、20〜40 程度の意味の異なる CC 変異。abort、欠損 trace、初期値、同一キーへの複数操作などの扱いを、小さな期待結果付き履歴で確認する。
- **実装：** 既存 verifier と壊した Silo を再利用し、独立に期待結果を付けた小規模コーパスを追加する。大型 trace は容量実測を先に行う。分割するなら境界をまたぐ依存を保持する必要があり、時間窓ごとの独立検査をそのまま同等とは扱わない。
- **計算量：** 小履歴数百〜数千件と、代表的な実 trace 10〜20 件から開始。balanced の実績を当てれば後者の検証だけで約 1.3〜2.7 node 時間。read-heavy、ビルド、準備費は別で未確認。

**`certified` は有限の観測履歴に対する判定です。全実行の直列化可能性の証明には使えません。** この区別は論文全体で統一すべきです。毎 iteration の検証・構造化フィードバック・trace の compile 時除去は維持します。

**優先 1：比較対象と探索空間を整える。**

- **示すこと：** 差が LLM に由来するのか、与えた候補空間や人間の事前知識に由来するのか。
- **最小構成：** Silo に加えてもう一つ、異なる CC の仕組みを持つプロトコル。導入費では trace のある MOCC が第一候補ですが、patch の完成度は未確認です。手法は random、軸ごとの sweep または座標探索、BO、進化探索、LLM を基本とする。
- **実装：** 共通の候補適用・検証・計測インターフェースを作る。各手法に同じ stock、既知最良、初期候補、観測情報を与える。既存研究の探索法を移植した場合は「再実装した手法」と明示し、原システムそのものと混同しない。
- **計算量：** 第 2 プロトコルで 20〜40 候補 × 3 workload の疎通から開始。balanced 相当なら検証だけで約 8〜16 node 時間、準備・ビルド・性能測定は別。

まず既存の有限空間で公平に比較します。ただし、**この空間だけで負けても、コード合成一般への結論にはできません。** 広い主張を残すなら、実行時の状態に応じて動作を変える小さなプログラム空間を一つ追加する必要があります。例えば競合履歴に応じた待機方策ですが、これ自体の新規性は主張せず、探索空間の性質を変える実験条件にします。

なお、各軸が列挙可能でも直積全体の測定が安価とは限りません。全組合せ走破を開始条件にはしません。

**優先 2：独立した探索反復で、費用と成果の曲線を取る。**

- **示すこと：** 同じ資源から、どれだけ有用な候補を得られるか。
- **最小構成：** 小規模試走は 2 プロトコル × 2 探索課題 × 5 手法 × 3 独立探索 × 8 候補＝**480 候補評価**。本比較の出発点は 2 × 6 課題 × 5 手法 × 5 独立探索 × 12 候補＝**3,600 候補評価**。必要反復数は試走での探索間変動から決める。
- **実装：** 候補評価数を揃えた比較と、経過時間を揃えた比較を分ける。最高 TPS に加えて、有効候補率、初めて有用な候補を得るまでの時間、検証時間、node 時間、人間の介入を記録する。複製候補・コンパイル失敗も探索費用に含める。
- **計算量：** B-5 の見積りを機械的に換算すると試走約 68、本比較約 510 node 時間。ただし課題・検証長が違うので予算の尺度にすぎません。LLM が 1 手法なら本比較は 720 iteration、直列で約 **120〜156 時間**。ノード並列化だけではこの時間は消えません。

LLM はログインノード側の親から CLI で呼び、計算ノードには生成物のビルド・検証・計測を渡す構成を維持します。サブスク利用なので架空の API ドル費用を付けず、経過時間と実際の利用制約を報告します。

ここで重要なのは、**候補の性能測定を 8 回繰り返すことと、探索を独立に 8 回やり直すことは別**という点です。LLM・探索法の比較には後者が必要です。

**優先 3：未知条件への転移と、性能差の再現性を測る。**

- **示すこと：** 選ばれた候補が探索条件に過適合していないか。利得や退行がマシン・実行日だけで決まっていないか。
- **最小構成：** 生成・選択に使わない条件を先に留保し、read/write 比、競合、スレッド数、トランザクション長、アクセス集合の重なり方を変える。stock、強い静的設定、各探索法の選択結果を比較する。主要結果は別日・別割当てで追試する。
- **実装：** 既存の対測定を拡張し、測定順を無作為化する。信頼区間と実用上の同等幅を先に定める。既知最良 `p2_2_flag_opt` を外さず、CCBench 既定比の大きな数字を主結果にしない。
- **計算量：** 例として 2 プロトコル × 27 条件 × 6 候補 × 8 反復＝2,592 性能 run。提示された 30 run＝0.62 node 時間の率なら約 **54 node 時間**。検証・較正・別日追試は別枠であり、run の長さや梱包で変わります。

YCSB の mix を三つ増やすだけでは広がりとして弱いです。一方、TPC-C を走らせれば自動的に強くなるわけでもありません。

**TPC-C の全面対応は最初の必須項目から外します。** 表識別子、abort、range/predicate の意味が未解決だからです。まず point read/write の範囲でトランザクション構造を広げます。それで得られる結論の射程が狭すぎる場合に、TPC-C 対応を次の投資判断にします。TPC-C を載せるなら、table ID の追加だけで完了とは扱えません。

**優先 4：結果の理由を、介入で説明する。**

- **示すこと：** LLM がなぜ勝つ／負けるか。workload 記述や critic が本当に役立つか。
- **最小構成：** 成功・失敗を代表する少数の課題で、正しい workload 記述と伏せた／入れ替えた記述、critic あり／なしを比較する。どちらも必須の検証と構造化された失敗理由の返却は維持する。
- **実装：** 出力コードを人間が読んで、既知候補の再発見、無効変更、機構の変更を区別する。abort 原因や待機による資源消費など、仮説に必要な診断だけを追加する。診断用 run と主たる性能 run を区別する。
- **計算量：** 追加 120〜240 候補評価を最初の枠にする。同じ換算なら約 17〜34 node 時間。全て LLM の追加 iteration なら約 20〜52 時間の直列時間。

verifier を外す、あるいは失敗理由を返さない ablation は、今回の絶対規律と両立しないので提案しません。これらの構成要素の因果効果を直接切り分けられないことは、主張の限界として残します。

**優先 5：第三者が再評価できる成果物を、実験と一緒に作る。**

EA&B は**初回投稿時に全実験の再現パッケージへのリンクが必要**です。後から公開準備を始める計画では間に合いません。 [投稿規定](https://vldb.org/2027/submission-guidelines.html)

最低限、使用コード、生成パッチ、入力・出力、探索設定、失敗候補を含む実験データ、図表生成手順を保存します。LLM の再生成と、保存済み候補の再検証・再計測を分け、モデル更新後も後者を実行できるようにします。システム名・モデル表示名・おおよその時期で provenance を記録し、凍結 chain は追加しません。

計算費用は主要図の再実行分。まず実験予算の 10〜20% を仮置きし、公開する trace の量・保存費は第 1 週に見積もるべきです。

**あると強くなるもの**は、意味論を確認した TPC-C、cygnus での NUMA・96 スレッド、第 3 プロトコル、第 2 の LLM 系統、時間変化する workload です。複数 DBMS エンジンまで広げることは今回の最小条件にしません。ただし CCBench 内で複数プロトコルを比較しても、「複数 DBMS で実証した」とは言えません。

**3．やめる・減らすべき作業**

- **610 件の open 項を研究計画の母集合にすること。** 論文の図・比較・説明に対応しない台帳強化は保留する。
- **凍結・批准・受領証を増やすこと。** 既存のどの停止条件を解除できるかを一度整理し、個々の測定で同じ裁定を取り直さない。
- **現在の B-5 を 1,773 session のまま本走すること。** 有限空間で差がない可能性を詳しく測る前に、その結果が論文のどの命題を判別するかを決める。
- **sort など弱い相手への勝利を厚くすること。** 既知最良への敗北を理解する方が価値が高い。
- **無人自律・汎用 agent 基盤の完成。** 当面は人間が開始・監督する研究プロトタイプで足りる。critic も費用に見合う効果が出なければ削る。
- **全プロトコル計装と関連研究の網羅探索。** 直接比較に必要な手法だけを扱い、世界初・世界に存在しないという主張を避ける。
- **平均値の精密化だけを目的とした追加反復。** 不足しているのは、小数点以下の精度より探索の独立反復と条件の多様性です。

これは完成稿までの予定ではなく、**論文の中心結果を取りに行けるかを判断する期間**です。

先に必要な裁定は、次の六つです。

1. **主目的：** EA&B を第一候補にし、LLM が勝たない結果も主要成果として扱うか。私は賛成です。
2. **主張の射程：** 当面は point read/write の CC 最適化に限定するか。私は限定を勧めます。
3. **探索空間：** 有限設定の比較に加え、小さなコード生成空間を追加する余地を認めるか。
4. **費用：** 試走、本比較、CLI 利用、人間の時間を段階別にどこまで使うか。一括で大規模本走を承認しない。
5. **運用：** 研究を止めている手続きのどれを保留し、どの正しさ・測定条件だけを開始条件として残すか。
6. **公開：** 失敗候補と否定的結果を含む実験一式を公開できるか。公開できない主要部分があるなら EA&B の選択を再考する。

**5．最大のリスクと、負の結果でも成立する設計**

最大のリスクは、**実験が十分になっても、結論が「小さな設定空間では単純な探索で十分」という既知に近い話に留まること**です。計算量を増やすだけでは解決しません。

負の結果を論文にするには、最初から以下を設計に含めます。

| 起こり得る結果 | 論文にするために必要なもの |
|---|---|
| LLM と非 LLM に差がない | 同等幅を事前に決め、十分な精度で「実用上同等」を示す。単なる有意差なしで終えない |
| LLM が遅い・悪い | 生成費、無効候補、誤収束、探索空間との不適合のどれが原因かを分離し、複数課題で再現する |
| 広いコード空間で壊れた候補が増える | 変異の種類と破綻原因を対応づけ、有効候補率と検証費用の関係を示す |
| 学習条件では勝つが未知条件で負ける | 事前に留保した条件で退行を測り、どの workload 特徴が失敗を予測するか示す |
| 全手法が既知 backoff を再発見する | 既知解までの到達費用と、到達しない条件を説明する。再発見自体を新規性にしない |

**「LLM は CC に役立たない」という大きな否定も、「毎回検証するから安全」という大きな肯定も避けるべきです。** 目指すのは、どの範囲で何が有効で、どこから費用や退行が支配するかという、再現可能な境界です。

4〜6 週間後にも、強い基準との比較から新しい境界・原因・評価方法が出てこなければ、EA&B に名前を変えて投稿せず、研究課題を組み替える判断が必要です。
