### 1. P1・P2・P4 の無条件な安全主張は成立しない

**real / must-fix** — `B:14–18`、`S:27,76,100`、`V/D41.md:25`、`O/coder_effect_gate.py:576–605`。

方策の返値を待機量と retry/abort に限ることと、C++ 本文の副作用をその返値に限ることは別である。草稿による撤回は正しい。

| CC 状態へ届く経路 | 判定と必要な限定 |
|---|---|
| 通常の名前解決・既存 helper | **構造で塞げるが配置だけでは不足。** `T:5` → `cc/silo/include/atomic_tool.hh:3` → `common.hh:25,50,69` で epoch・FLAGS・大域への参照が見える。後置 namespace でも外側の名前は見える。許可する参照・呼出しを閉じる必要がある |
| `extern`、`asm`、別名・属性 | **字句・構造で禁止可能。** `extern` 一語の禁止だけでは関数宣言、既存名、別綴りの asm、属性などを網羅しない。宣言形・属性・外部呼出しまで契約化する |
| テンプレートの二段階名前探索・ADL | **構造で禁止可能。** 非依存名が何でも後から見えるわけではないが、依存呼出し・引数の関連 namespace による探索がある。「定義点で未宣言」を一般的な封じ込め証明にできない。v1 では template・利用者定義演算子等を外すのが小さい |
| GCC 組込関数 | **構造で禁止可能。** include 非可視性では消えない。現物にも `__atomic_compare_exchange_n` がある（`atomic_tool.hh:15`）。任意対象への書込みにはアドレス取得も必要なので、組込関数と pointer／アドレス操作の双方を対象にする |
| 配列 OOB・寿命違反 | **限定文法なら経路を排除可能。任意 C++ では事後検出も不完全。** `PolicyState` のメンバ制限だけでは局所配列などを制限していない。破壊が TxExecutor・集合・trace に波及すれば、X/P/G2 または crash に現れる場合も、無音で残る場合もある |
| 未初期化・算術 UB | **現草稿では排除未証明。** `policy_state{}` は局所変数の初期化や shift・除算を保証しない。単に待機値が変わる場合から、最適化を介した任意の破綻まである。verifier は UB 検出器ではない |
| data race | **状態を唯一の TLS に閉じ、アドレス流出を禁じれば方策起源の経路を縮められる。** atomic の使用だけでは安全にならず、別の共有非 atomic 状態が残れば UB。合法な共有 atomic でも CC 大域への操作は別途禁止が必要 |
| 例外 | **`throw`・例外を出す呼出し等を構造で禁止可能。** `noexcept` 自体は送出不能の証明ではなく、外へ出る例外は terminate に至る。現行 pipeline の異常終了拒否は verifier による直列化可能性検出とは別 |
| 再帰・巨大な局所領域によるスタック溢れ | **呼出し graph・宣言形を限定すれば縮められる。** 任意 C++ の停止・スタック使用量は待機 clamp で保証できない。crash／timeout は捕まえうるが、非停止・破壊すべての検出保証はない |

**放置時の影響：** UB・外部干渉を含む候補について、有限 trace の certified を「全実行で安全」に誤って昇格させ、受理集合の説明と reject 分類を誤る。

採用できる文言は次である。

> メモリ安全・外部干渉なし・契約適合の方策が正常に返る限り、方策の選択は固定骨格の直列化可能性条件を弱めない。任意 C++ の適合性、全実行の正しさ、停止性、公平性を構成上保証するものではない。

### 2. 草稿の「txn 内状態」は補助関数まで閉じた契約になっていない

**real / must-fix** — `S:59–61,100,427,467,480`。

許可された `PolicyState` を成功時に reset しても、補助関数内の `static`／追加の `thread_local` に残る履歴は消えない。これは OOB のような UB を必要としない、正常な C++ の経路である。

草稿の「txn をまたぐ履歴は禁止」という意味上の宣言は適切だが、次 wave が再設計なしに実装する契約としては不足する。少なくとも以下を固定する必要がある。

- 持続する可変状態は指定された `policy_state` 一個だけ。局所 static、追加 TLS、追加の可変 namespace 変数は禁止。
- `PolicyState` は指定された scalar メンバだけ。メンバ関数・変換演算子・独自代入も許可しない。
- 局所宣言、配列、参照、cast、template、lambda、補助関数の署名・呼出しについて許可範囲を明記する。
- scalar 状態数の上限を IR だけでなく C++ 側についても定めるか、差として明記する。

**放置時の影響：** 「txn 内の観測だけ」の比較に txn 間学習や共有状態を持つ候補が混ざり、到達可能集合と certified 候補の性能比較が変わる。

これは新しい検査基盤の要求ではなく、草稿が予定する軸固有宣言／参照契約の具体化である。

### 4. 明示した上限付き wait を型10として一律拒否する理由はない

**refuted / —〔wait 自体の禁止〕。残る liveness 限界は real / nit。**
根拠：`.claude/agents/auditor.md:54,61`、`V/D41.md:17–20`、`S:63–65,162,243`。

型10の問題は、固定されていた no-wait／sort 前提を変え、verifier が見ない進行性を犠牲にして throughput を得ることにある。D48 がすべての待機を禁止したわけではなく、その軸では観測と gate の範囲を固定した。

新軸として wait を公開し、全生成器で同じ上限を使うことは、旧 no-wait 契約の密かな破壊と同一ではない。ただし、上限付きでも convoy・livelock・worker 間の偏りは残る。

| 現象 | 現行の観測・帰結 |
|---|---|
| hook が戻らずプロセスも終了しない | `trace-timeout`（`O/pipeline.py:525`、既定値は `:354` 付近の120秒） |
| 正常終了するが全体の commit がゼロ | `trace-empty`（`:585`） |
| 異常終了 | `trace-run-nonzero-exit`（`:579`） |
| abort 集計なし | `trace-no-abort-counts`（`:591`） |
| 多数 abort、ただし commit もある | abort 数を `verify_done` に記録（`:633–638`）。数の大きさだけでは拒否しない |
| 一部 worker だけ飢餓 | 全体に C 行があれば trace-empty ではない。公平性認証はない |
| 性能側で usable throughput なし | `bench-no-throughput`（`:1438–1444`）。walltime は `bench_wall_s` に記録（`:1415,1459`） |

**放置時の影響：** 型10を無条件適用すれば新軸の合法な wait 候補を排除し、逆に上限を公平性保証と書けば偏った certified 勝者を公平な改善と誤報する。

草稿の全周回上限は維持すべきである。実装時には `expected.lock` 枝だけでなく、`T:172` の CAS 失敗側も上限を消費する配置にする。

### 5. P5 は代理の壁を解消せず、許容する代理を選んでいる

**real / must-fix〔境界・採否の明記〕** — `B:18`、`S:438–452`、`V/D48.md:31–35`、`V/D1409.md:16–22,45`。

`result_` を隠しても、自前の事象列から作れる代理は消えない。ただし、事象数、commit 成功率、単位時間当たり TPS は別であり、同じ精度で推定できると書いてはいけない。

**放置時の影響：** 代理を使う候補の受理範囲が auditor ごとに変わり、同一空間の比較と採用された性能値の意味が揺れる。

### 6. 草稿でも局所競合への適応は表現できる。YCSB の「長い txn を後回し」は訂正が必要

**refuted / —〔競合適応が一切表現不能〕。real / nit〔飢餓の説明〕** — `S:40–60,432`、`external/ccbench/include/ycsb.hh:59,102,108,149–169`。

lock attempt に応じた待機変更、連続する lock-conflict abort に応じた待機変更は表現できる。したがって、ユーザーが挙げた「競合の状態に応じた待機」の**局所的な形**は満たす。複数 txn にまたがる負荷追従や全 worker の協調は表現できない。

v1 には草稿の txn 内状態までを推奨する。三つの拡張はいずれも、この局所適応を成立させるための必須条件ではない。後続で持続的負荷追従を必要としたときは、共有状態・時計より先に worker 内履歴を検討する。

YCSB は `makeProcedure` が RETRY の前にあり、abort 後も同じ手順を繰り返す。手順の操作数も `FLAGS_ycsb_max_ope` で固定される。

- **成立しない説明：** 同一 worker が長い txn を捨て、短い txn を次々選び直して稼ぐ。
- **成立しうる説明：** 競合の多い txn を持つ worker が再試行を続け、別 worker の成功が集計を支配する。quit 時には未完了 txn が残りうる。

**放置時の影響：** 草稿の報告する fairness の機序が、実際の driver が許さない txn 選別に誤帰属される。今回、その機序による実際の勝者変更は未測定なので nit とする。

### 7. diff-of-diffs は実行時の観測者効果を消さないが、草稿は概ね正しく限定している

**refuted / —〔草稿が実行軌跡一致を保証しているという懸念〕。残余は real / nit。**
根拠：`S:191–195`、`O/source_digest.py:2182–2220`、`docs/decisions.md:198–210`、`V/D48.md:22–26`。

前処理差分が一致しても、trace の遅延で競合順・abort 回数が変わり、同じ方策が別の応答を選ぶ。時計を隠してもこの経路は残る。

契約適合な方策なら、それだけで直列化可能性条件を弱めない。性能値は trace-disabled build の実測として意味を持つ。ただし「verify で性能側と同じ分岐を踏んだ」「その性能実行も証明済み」とは言えない。UB・外部干渉を含めれば、正しさに無害という限定も失われる。

abort 要因・retry 状態は**実際に待機を決める用途**なら CC 方策の状態である。両 build に載せ、軸 OFF では消す設計でよい。検査結果を照合するためだけの shadow・集計は検証専用として `#if TRACE` に置く。TRACE 外にあるという配置だけでは用途は判定できない。

**放置時の影響：** trace での hook 被覆を性能側の被覆へ一般化すると、検証済み範囲のレポートが過大になる。草稿は既にこの限定を述べているため、新 gate は不要。

### 8. 草稿の変異計画は恒真ではない。ただし stale-load 負例の期待結果を直す

**refuted / —〔計画全体の恒真化〕。real / must-fix〔期待結果の指定〕** — `S:185,209–228,492`、`T:158–184`。

read 検査削除→G2、lockskip→入口 X、early unlock→retention X、要素消失→P という対応は、実際の検査機構を名指ししている。既存 coverage JSON を読むテスト（`orchestrator/tests/test_campaign.py:11423`）だけで、新骨格の検出力を実証したことにはならない。草稿の**新骨格上で既存負例を再走する条件を維持**すべきである。

一方、再読込を削除しても、全周回上限が働けば32周回後に abort するため、**timeout になるとは限らない**。焦点試験は「他者が lock を解放した後、上限内に再読込して取得に進める」を期待し、削除版が古い locked 値のまま abort することを差として捉えるべきである。

**放置時の影響：** timeout だけを赤条件にすると、再読込のない骨格を正常と扱い、retry 方策が実際には成功できない候補集合を認証・比較する。

また、inert は OFF 時の identity、同値対照は ON 時の挙動・費用差、骨格負例は検査の検出力を調べる別の対照である。骨格負例の赤を「LLM が生成した方策の anomaly」と数えない。既存の変異走行・C 段受入で足り、新しい恒常 gate は要らない。

### 9. コメント禁止は関数群でも効くが、自由文還流の契約は不足する

**real / must-fix〔設計上の入力境界〕。指示混入の実際の成功は判定不能。**
根拠：`S:177,281,301`、`O/diff_quarantine.py:477`、`O/p3_s4_loop.py:1164–1194,1245–1267`、`.claude/agents/critic.md:22`。

既存検疫のコメント・前処理指令等の禁止は、関数単位になっても適用できる。しかし、コード内コメントを禁止しても、次の経路は別に残る。

`proposal.justification／候補本文／エラー文字列 → critic の解釈 → recommend・avoid → 次の coder`

現行 `make_critic_digest` 自体が justification を自動で混ぜる証拠はない。だが、草稿は「評価済み候補」と自由文診断を次へ渡す方針を追加し、その field 射影を未定義のままにしている。既存には診断をデータと明記する K2 の形式があるが、そのラベルも内容の意味的安全を証明しない。

必要な修正は、候補本文・justification・エラー・critic 出力を、いずれも**実験契約を変更する権威を持たないデータ**として渡すこと、justification を信頼済み方策指示へ昇格させないこと、次 coder に渡す field を具体化することである。既存の入力射影と role 文言へ接続すればよく、新しい検査サービスは要らない。

**放置時の影響：** 候補自身の自由文が探索条件・次候補の選択を誘導し、critic 効果や探索法差として報告する結果を変えうる。

## 親 brief への指摘

- **P1・P2：** 「構成上壊せない」「LLM 候補の verifier 拒否は原理的にゼロ」を撤回する。契約適合な方策の中立性と、C++ 候補の適合性を分ける。
- **P3：** 待機上限は hook が戻る条件付き。deadlock 解消と公平性保証を分ける。
- **P4：** include 順序は補助的な可視性制限であり、封じ込め機構ではない。草稿の後置案を採る場合も許可参照の契約が本体になる。
- **P5：** stock の commit 数参照は、合成候補への許可の根拠にならない。代理を排除したのではなく、局所的な代理を許容する設計と書く。
- **研究主張：** v1 は差分分析 P1 の関数生成・費用評価を進めるが、CC 論理の破壊を直す構造化反例の価値までは実証しない。

新しい sanitizer 実行や公平性 gate を、本レビューから追加の採用条件として課す必要はない。

## 段 4 裁定に入れるべき変更

- 所見1の条件付き安全文言を採用し、certified は有限の観測履歴についての判定と統一する。
- v1 は validation／CAS／unlock／writePhase を開かず、abort 待機と lock 競合応答を開く。
- 持続状態は指定 TLS 一個に限定し、成功 commit 後に固定骨格が reset する。
- 局所 retry・abort 列の代理性を認めた上で、許容範囲を明記する。旧 trigger の D48 契約は維持する。
- 新骨格上の既存負例、二つの hook、reset、全周回上限、待機後再読込を既存受入で確認する。
- 検疫赤・build 赤・liveness 赤・integrity 赤・G2 赤・人為的骨格負例を混同しない。
- 本文・自由文・critic 診断を既存のデータ境界に載せ、診断から評価条件を変更させない。

## 裁定パッケージへ返すべき択一

**残すべき択一は、局所履歴の代理性を許容するかの一点。** `S:450` と D1409 の未決境界に対応する。

- **推奨：** 新軸に限り、abort 要因・lock attempt・同一 txn 内の専用状態を許容する。公平性非保証を明記し、txn 間履歴・共有状態・時刻は見送る。
- **代案：** 状態を外し、現在の要因・attempt だけの応答に限定する。表現力は縮むが、代理性そのものが完全になくなるわけではない。

関数空間を開くこと自体は承認済みなので、再承認事項にしない。validation 非開放も本 wave に委ねられた設計判断として処理できる。

## 条件付き採用の可否

**`adopt_with_conditions`**

条件は、上記の安全文言、許可 C++・唯一の状態、局所代理の裁定、還流の入力境界を設計に固定し、草稿が既に要求する新骨格上の受入・変異確認を実施すること。これらの実測完了を本レビューは認定していない。

## 総括

中心案は採用可能である。最も重要な訂正は、**「方策の返値が安全」と「任意 C++ の方策本文が安全」を同一視しないこと**。局所競合への適応は草稿の狭い観測でも表現でき、validation や共有時計を今開く必然性はない。

一方、v1 の結果だけで「LLM が壊した CC 論理を verifier が捕らえる価値」を実証したとは言えない。この限界と、YCSB で実際に成立する worker 間の進行偏りを、採用文と研究レポートに残すべきである。
