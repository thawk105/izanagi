## verdict
**adopt_with_conditions (維持)**

前回挙げた 4 つの穴は、大筋で閉じています。
- 保存域の非排他 (V2): 閉じた。
- 名前解決の乗っ取り (V3): 閉じた。

## 残る violations

**R1 [型25 案 / V4 の残り、must-fix] 部分言語は signed 算術の UB を構造的には除いていない** (§2.7「契約が構造的に除く未定義動作」、fragment 決定 4 と理由)
- **bool の昇格。** 許可された演算子 `+ - * & | ^ ~` を bool に使うと、結果は `int` になる。
  - `(b1 + b2) << 31u` は右辺が literal で 32 未満なので現行規則を通る。しかし C++17 では、`2 << 31` は unsigned でも表せないので UB。
  - `(~b) << 1u` や、単項 `-` を許すなら `-b << 1u` は、負値の左 shift で UB。
  - `(~b)*(~b)*…` を 31 項ほど重ねると signed overflow。4096 token の上限の内側で書ける。
  - `-Wbool-operation` は `~` しか捕まえず、`b1 + b2` には警告が出ない。
- **自己初期化。** `uint32_t x = x + 1u;` は「初期化子つき局所宣言」を満たすが、不定値を読む。GCC は `-fsyntax-only` ではこれを警告しない。uninitialized 系の警告は middle-end で出るため。
- **return 欠落。** GCC の「control reaches end of non-void function」は middle-end の pass で出るので、`-fsyntax-only` の単独 TU では出ない (未実測、uncertainty)。
  - 実 build は ProtocolHelpers 経由で `-Wall -Wextra -Werror` がかかるので build-error で止まり、UB は漏れない見込み。
  - ただし、§2.7 が保証の出所を単独 TU compile に帰している記述は誤り。
- **なぜ正しさに届くか。** hook は prefix lock を保持したまま呼ばれる。noinline でも GCC の IPA (noreturn や pure の推論) は関数境界を越えるので、UB から「戻らない」と推論されると、呼出し元の prefix unlock の経路が削られうる。
- **verifier が見逃す理由。** perf build でだけ最適化結果が変わる形は、trace に現れない。
- **対処。**
  - 構文検査を型付きにする。算術・ビット・shift の被演算子は `uint32_t` / `uint64_t` に限る。bool は `! && || == != ?:` と `static_cast` だけに使える。単項 `-` は明文で許可するか禁止するかを決める。
  - 初期化子が宣言中の変数を参照することを禁じる。
  - 非 void 関数には、全経路の return を構文で要求する。最後の文を `return` にするか、if/else の両枝で return する。または単独 TU を `-c -O1` で compile する。
  - 複合代入 `/= %= <<= >>=` にも、右辺 literal の規則を明記する。
- **追加する負例。** `(b1+b2) << 31u`、`(~b) << 1u`、`uint32_t x = x;`、片側の経路で return を欠く関数、`s.m /= v` (v は変数)。いずれも構文検査で赤になること。
- **非恒真性の対照。** 型付き規則を外した構文検査器では、これらの負例が通ること。これを自己試験の赤として登録する。

**R2 [型22/25 案、must-fix (仕様の明文化)] 代替綴りと digraph** (§2.7 の禁止リスト)
- 禁止リストは記号で書かれている (`[` `]`、単項 `&`)。
- 一方、C++17 では次の綴りが有効なまま残っている。
  - `bitand` は単項 `&`、つまりアドレス取得になる。
  - `<:` `:>` は `[` `]` になる。
  - `%:` は `#` になる。行頭に置けば前処理指令になる。
- 自作 parser が `bitand` を識別子として字句化し、名前解決をしなければ、`(bitand s)<:9u:> = 1u` のような範囲外書込みが単独 TU compile まで届く。
- **対処。** 代替綴り (`and` `or` `not` `bitand` `bitor` `compl` `xor` とその `_eq` 形) と digraph を字句段で全拒否すると明記する。構文検査は名前解決をし、識別子が自前の名前・Context field・`std::min` / `std::max` だけを指すことを要求する。
- **負例。** 上記の各綴り。DiffQuarantine が `%:` を前処理指令として拒否するかは未確認なので、負例で確かめる。

**R3 [型2/4、should] 軸 ON の abort hook が `BACK_OFF` に従属している** (§2.6「既存の `BACK_OFF` 条件…は保つ」、§2.4 の abort() 分岐)
- 実コードでは T:42 の `#if BACK_OFF` の内側に T:47 がある。
- `BACK_OFF=0` の genome では、`policy_after_abort` が一度も呼ばれない。方策の半分とその状態更新が黙って無効になり、V7 と同型の flag 別名化が起きる。
- 直列化可能性には影響しない。しかし探索が空振りし、identity が別挙動を表さない。
- **対処。** 軸 ON かつ `!BACK_OFF` を `#error` にするか、hook の呼出しを `BACK_OFF` の外に出す。
- **負例。** 軸 ON かつ `BACK_OFF=0` で build が赤になること。

**R4 [型15、should] V11 の発火条件は機械 IR の系統で沈黙する** (§3.4、§4 の auditor 段落)
- worker 寿命で reset されない状態があると、thid を使わずに吸収状態を作れる。例: 「abort 数が閾値を超えた worker は以後常に最大待機」。これで worker の駐車が恒久化する。
- IR も「状態 4 field と飽和加算」でこれを表せる。しかし機械 IR 候補は auditor 段を省くので、唯一の観測点である目視が働かない。
- **対処。** 発火条件をコードの形で書く。「単調に増えるだけの状態が待機の上限や abort に至る経路を持つ」なら疑いありとする。そのうえで、IR の系統でも endpoint 候補と勝ち候補に限って auditor の公平性目視を必須にする。

**R5 [型4、should] V6 の見送りに既定ラベルを付ける** (§3.4)
- 発火条件「効果を帰属する必要が出た」は主張の側から来るので、誰も気づかなければ沈黙する。
- **対処。** 報告の既定で、lock 方策を「verify 中の発火証拠なし」と表示する。解除できるのは発火の証拠を添えた場合だけにする。

**R6 [記録の正確さ、should] 状態の射程についての要約** (§2.5 末尾、fragment 決定 5 の理由)
- 私の前回の回答 (依頼 4) は、「契約が守られる限り、直列化可能性には及ばず性能値の歪みに留まる」と書いた。この点は親の記述と整合する。data race という例外は、共有状態を入れないことで除かれている。
- しかし私はもう 1 つ例外を明記していた。「型 3 と組み合わせると、認証したプログラムと計測したプログラムが別物になり、規律 1・2 の前提が崩れる」。§2.5 と fragment ではこれが落ちている。
- また私は、状態の射程について草稿どおり txn 内を支持していた (条件 9)。したがって、「3 レンズが一致した」と言えるのは害の評価についてだけで、選択についてではない。fragment は「A と B で割れた」とだけ書き、auditor の立場を記していない。
- **状態を worker 内に広げたことで増える害** (いずれも契約適合なら直列化可能性には及ばない)。
  - 型 3: 自前の commit・abort 計数から、run の長さや競合度を推定できる。legacy verify (4 threads・1 秒) と perf (48 threads・3 秒) の判別が安価になる。状態が reset されないので、verify と perf で温まり方も違う。
  - 型 12: 自前の計数が fitness の代理になる。
  - 型 15: R4 の吸収状態。
  - 型 4: 履歴で条件付けた lock 枝が verify 中に発火しない。
- **対処。**
  - §2.5 と fragment に型 3 の限定を戻す (§3.1 の「同じ分岐を踏んだとは言えない」への参照でよい)。
  - auditor が txn 内状態を支持していたことを記録に残す。
  - 性能構成の verify を、比較の時だけでなく LLM C++ の全候補に適用する (should)。

**R7 [T3 の見送り、should] 見送りの前提と発火条件**
- 見送りの理由「部分言語が UB の型を構造的に除く」は、R1 を直すまで成り立たない。
- 発火条件「構文検査を通った LLM 候補で UB が 1 件見つかった」にも、検出器がない。
- R1 を直した後なら見送りは妥当。そのうえで、C 段で 1 回だけ、手書き方策と契約負例の集合に UBSan を付けた単独 TU の harness を回す (費用は秒単位)。これを発火条件の観測点として残すことを勧める。

**T5(d) の見送りについて。** 「lock 漏れは読み手の spin で trace-timeout に落ちる」は RMW の workload に依存します。読みを伴わない blind write だけなら、書き手の no-wait abort と retry が続くだけで、timeout にならない可能性があります。ただし、lock 漏れを作れるのは方策ではなく固定骨格で、C 段の prefix unlock の変異は RMW の legacy verify で走ります。したがって見送りは妥当です。§2.1 の文に「RMW 前提」と添える程度で足ります (nit)。

## nits
- N1: 「hole は変数を一切定義しない」(§2.5、fragment 5、§8) と、§2.7 が許す自動変数・`constexpr` 定数の文言が衝突している。「静的または thread の記憶域を持つ変数を定義しない」に直す。
- N2: 必須 3 関数は、署名が完全一致する定義がちょうど 1 つずつあることを検査する。
- N3: `std::min` / `std::max` について、明示 template 引数、initializer_list 形、比較関数の引数を禁止と明記する。関数名を値として使うと関数 pointer に崩れるので、関数名は呼出し位置だけに許す。
- N4: 単独 TU の api header と実 TU の `izanagi_silo_api` 定義を同じ正本から生成し、一致を検査する。
- N5: 骨格 wrapper は `[[gnu::noinline]]` ではなく `__attribute__((noipa))` にすると、R1 の IPA による伝播も止まる (GCC 8 以降)。
- N6: `LockResponse` の構築方法 (集約初期化を許すか) を文法に明記する。

## uncertainty
- 「GCC の `-fsyntax-only` では `-Wreturn-type` の経路警告と uninitialized 系の警告が出ない」は、GCC の pass 構成からの推定で、実測していない。clang なら Sema で出る。
- `-Wall -Wextra -Werror` が silo の target に適用されることは、ProtocolHelpers.cmake のコメント (58-61 行) で確認しただけで、呼出し経路は追っていない。
- DiffQuarantine が `%:` の digraph 指令を拒否するか、構文検査器が名前解決をするかは、未実装または未読のため判断できない。
- perf build と verify build で TRACE 以外の -D (例: NDEBUG) が違うかは確認していない。違えば V1 の残りの経路になりうるが、`__` を含まないマクロ名は宣言位置で実 TU を壊すので、実害は低いと見ている。
- YCSB の perf workload が RMW かどうか (T5(d) の前提) は確認していない。
- 見積り (§6) は監査していない。

## 総括
中心の変更 2 点のうち、骨格が所有する worker 内の状態 (決定 5) は、共有状態と時刻を入れない限り、私の前回の害の評価と整合します。直列化可能性には届きません。ただし、私が付けた「型 3 と組むと、認証した経路と計測した経路が別になる」という限定と、auditor が txn 内状態を支持していた事実が、記録から落ちています (R6)。

部分言語 policy-C++ v1 (決定 4) は、前回の 4 つの穴のうち、保存域・名前解決・大域への到達を実質的に閉じました。一方で、UB を構造的に除くという主張には例外が残ります。bool 昇格による signed 算術、自己初期化、代替綴りによる pointer と添字の迂回です (R1・R2、must-fix)。これが直るまでは、T3 を見送る理由も成り立ちません。

このほか、`BACK_OFF` 従属による abort hook の空振り (R3)、機械 IR の系統で公平性の観測が沈黙すること (R4)、lock 方策の既定ラベル (R5) を should として付けます。R1・R2 を C 段の前の必須条件 (§9 の 1) に加えれば、条件付き採用を維持します。
