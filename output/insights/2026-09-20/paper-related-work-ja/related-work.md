# 2. 関連研究 (本体論文・日本語草稿、2026-09-20)

本節は、Izanagi (ワークロード特化の並行性制御を AI が合成・選択するシステム) を先行研究の中に置く。
本節が引く文献は、正典 `docs/related-work/README.md` (2026-09-20 時点の索引 28 エントリ) と、その判定記録
`docs/related-work/claim-survey/` の範囲に限る。新しい文献の取得は行っていない。先行研究の体系的な調査は、
費用対効果を理由に**限定付きで止まっている** (軸 1 = 対象の空白は `RW1`、軸 3 = 説明可能性は `RW0`。2.8 節)。
本節の書き方はその成熟度に従う — **「先行なし」「世界初」「系譜の何本目」「最も近い」は書かない。**
書けるのは、先行研究との違いを 3 つの条件で書き分けることと、調査した範囲 (母集合) を明示した限定付きの記述までである。
以下、本文は投稿本文の文体で書き、根拠の所在は末尾の「出所 (執筆者向け)」に番号で寄せる。

## 2.1 位置づけの 1 文と、落とせない 3 つの条件

Izanagi と先行研究の差は、次の 3 点で書く [1]。

- **(i) 対象がトランザクションの並行性制御 (CC) であること。** 合成と説明の対象は、abort・待機・競合検出の
  判断構造を持つ CC 実装であって、性能 knob (設定値) ではない。
- **(ii) 対象実装の action vocabulary そのものを拡張すること。** LLM が生成するのは既存 knob の上の条件付き方策や、
  固定した原始操作語彙の中の配合ではなく、CC 実装の中の新しい動作 (backoff の量と発火条件、write set の施錠順序、
  abort 要因別の gate) である。
- **(iii) 正しさゲート (直列化可能性の検証) を毎反復回すこと。** trace を有効にした build と検証器を毎 iteration 実行し、
  正しさ検査を最後にまとめて回す関門にしない。

3 点はいずれも実装と計測が動いている面である。ただし、すべての説明測定が certified な選択へ束縛されたこと、
および 3 点が一続きの証拠鎖を成すことは、本論文では実証していない。説明の忠実性・証拠の連鎖 (proof chain)・
試行の来歴 (provenance) は、核ではなく補助として扱う [1]。

位置づけについて本論文が言えるのは、次の 1 文までである [2]。

> 本調査では、**LLM が**、**トランザクションの並行性制御を対象として**、**アクション空間自体をコードで拡張する**
> (固定した原始操作語彙の中で生成するのではなく) 既存例を発見していない。

この 1 文は論文ストーリー 2026-09-20 版 §3 項目 1 の逐語引用で、正典 7.6 の空白域 2 (arXiv 横断掃引、掃引日 2026-07-10、監査前データ) に対応する限定付きの記述であり、
軸 1 の成熟度 `RW1` で許される形はこの逐語引用に限られる。太字の 3 条件はどれ 1 つ落とせない。落とした短縮形には、
すでに正典が名指しの反例を持っている [3]。

1. 「LLM が」を落として「CC を自動生成した例は無い」と書くと、Declarative Concurrent Data Structures (`2404.13359`) が反例になる。
   同論文は AI を使わずに CC のコードを機械的に生成する (2.2 節)。
2. 「アクション空間自体を拡張する」を落として「ワークロード特化の CC を作った例は無い」と書くと、同じ論文が反例になる。
   同論文は自分の勝因を "it specializes concurrency control to the target workload" と書いている。
3. 「トランザクションの並行性制御を対象とする」を落として「並行コードを自動生成した例は無い」と書くと、同論文と
   CIR+CVN (`2604.09318`) が反例になる (2.6 節)。

さらに、「アクション空間自体を拡張する」は「LLM に生成させる」と同じではない。CIR+CVN は LLM に同期構造とソースコードの
両方を書かせるが、原始操作の語彙は形式系が定めた閉じた集合であり、空間を拡張しない。**「空間の拡張であって、固定した
原始操作語彙の中の生成ではない」**という限定が要る [4]。また、「LLM に DBMS の内部を読ませて動作を変える」という粗い言い方をすると、
SysInsight (`2603.22708`) が先行に見える。SysInsight は設定チューニングが対象で、44 個の knob を拡張しない (2.3 節) [5]。

## 2.2 ワークロード特化の並行性制御 — 素材、学習型 CC、AI を使わない特化

**素材コーパス。** 本研究が変異させる素材は CCBench (`2009.11558`、VLDB 2020) である。主要な in-memory CC プロトコルを共通基盤に
再実装し、同一ワークロードで比較する分析基盤で、Silo (SOSP 2013)・TicToc (SIGMOD 2016)・MOCC (VLDB 2017)・Cicada (SIGMOD 2017)・
ERMIA と SSN (SIGMOD 2016 / VLDB 2017)・MVTO (1978) などを実装する。Izanagi はこの固定設計の集合をかき混ぜて variant を析出させる。
CCBench 自身の中心主張は「プロトコルの比較は同一基盤で測れ」であり、本研究が事前登録した対照も CCBench 内の LLM を使わない対照で
閉じている [6, 7]。Silo 系 OCC のタイムスタンプ粒度が性能に与える影響を実測した研究 (`1811.04967`) は、
フラグ空間の外に求める新しい変異軸の一例として参照する [6]。

**学習型 CC の系譜。** ワークロードに合わせて CC を設計・学習する系譜として、本節では Polyjuice (`2105.10329`、OSDI 2021) を方法論的な
参照点として取り上げる。Polyjuice は CC をアクション (wait の粒度、dirty read の有無、write expose、early validation) に分解し、進化的に学習する。CCaaLF はこれを一般化して
CC を学習可能な関数としてモデル化した — v4 (2026-03) で **NeurCC に改名**され SIGMOD 2026 (`2503.10036`、PACMMOD Vol.4 Issue 3、
DOI 10.1145/3802088) に採択されている (引用時は CCaaLF = NeurCC の対応を明記する)。ATCC (`2603.13906`) は、LLM 駆動エージェントの
非決定的なトランザクション特性に適応する学習型 CC で、未知・適応的ワークロードへの CC 適応という問題設定が本研究の対象設定
(workload descriptor で与えられる未知のワークロード) と正面から重なる。系譜の重心は、固定アクション空間の配合最適化 (Polyjuice) →
学習可能関数化 (CCaaLF / NeurCC) → 未知ワークロードへの適応 (ATCC) と移ってきた [7]。

Izanagi との差は、正典の特徴づけに合わせて次のように書く。Polyjuice は「事前定義したアクション空間の中での最適配合探索」に留まり、
CCaaLF / NeurCC は「CC を学習可能関数としてモデル化して関数近似へ一般化」した。Izanagi はこの系譜の問題設定 (CC をアクション列に
分解して探索する) を借りつつ、**アクション空間自体を LLM がコードで拡張する**点で異なる [7]。**「先行は policy table を出すだけで
説明できない」という一括りの書き方は正典から導けないので使わない** [2]。

学習型 CC との定量比較は行わない。Polyjuice と NeurCC はいずれも公開実装があるが、どちらも Silo のコードベース上の実装で
CCBench とは別基盤であり、絶対値の直接比較は CCBench の中心主張と衝突する。事前登録した対照は CCBench 内の LLM なし対照で完結し、
学習型 CC に対しては質的な差別化と論文数値のオーダー引用で足りる、というのが本研究の判断である (再判断の条件は「学習型 CC を
定量的に上回る」を headline に据える場合に限る) [7]。

**AI を使わないワークロード特化。** Declarative Concurrent Data Structures (`2404.13359`、EPFL) は、逐次仕様を宣言的 DSL で書かせ、
コンパイラが並行性制御を注入して thread-safe なデータ構造を機械語まで生成する枠組みである。宣言が「他の操作は来ない」ことを閉じるので、
汎用 DBMS には削れない同期を削れる。試作系 Rösti は S2PL + NO_WAIT を注入し、in-memory OLTP DBMS (Proteus) に対して YCSB で最大 2 倍を
報告する。本研究にとってこの論文は、**「汎用 CC はワークロード特化に負ける」を、AI を一切使わずに同一機で測った外部証拠**である [8]。

同時に、この論文は軸 1 (対象の空白) に**直接接地する競合**と判定されている — 対象が同じ (トランザクションの CC)、目的が同じ
(ワークロード特化で汎用実装に勝つ)、出力がコードである。この論文と本研究はトランザクションの CC を対象とする点を共有し、相違は
合成の主体・アクション空間の拡張・反復ごとの正しさ検査の 3 点にある: (1) LLM も進化探索も無く、自動化はコンパイラのパスである、
(2) 注入するプロトコルは S2PL + NO_WAIT の 1 種で、空間を拡張しない、(3) 正しさ検証器をループ内に持たない — CC 注入が正しいことを前提に置く
設計で、verifier を毎反復回す本研究とは立場が違う (位置づけの 1 文から落とせない 3 条件は 2.1 節に記したとおりで、この 3 点と一対一では
ない)。この論文が将来課題として挙げるのは既知アルゴリズムの実行時適応的な**選択**であって、新しい CC の合成ではない。人が逐次仕様を書く
DSL の経路は本研究では採らず、CCBench の C++ 実装を素材にする。「生成対象」を混同しないために 3 段に分ける — データ構造の実装の生成
(行う)、固定した CC プロトコルの注入コードの生成 (行う)、CC プロトコル / アクション空間そのものの生成・拡張 (行わない) [3, 8]。

**近年の CC 手法。** CCBench に追加しうる近年の stock protocol の候補 (Rebirth-Retire、Bamboo、Polaris など) は、NeurCC / ATCC の比較相手群から
通常の文献調査として棚卸しされ、一次資料・実装可用性・ライセンス・trace 移植費用などを「充足確認 / 不適合確認 / 未確認」の三値で記録した
候補表がある。追加対象の確定は 0 件であり、同表は実装追加も探索面の拡張も認可しない。本論文の比較対象にはならない [9]。

## 2.3 DBMS 自動チューニング (knob tuning) の系譜と、SysInsight との境界

**系譜。** DBMS の設定 knob を自動チューニングする系譜は、ワークロード特化の DB 自動最適化を早くから目指してきた系譜である。ML / RL 枝は OtterTune
(SIGMOD 2017、GP 回帰 + workload mapping)、CDBTune (SIGMOD 2019、DDPG による end-to-end 強化学習)、QTune (VLDB 2019、クエリ認識)、
UDO (`2104.01744`、VLDB 2021、knob + index + トランザクションコード variant 選択を統合する強化学習) と続く。LLM 枝は DB-BERT
(VLDB 2022、マニュアル文章からヒントを取る)、GPTuner (VLDB 2024、LLM がマニュアルから knob ごとの推奨範囲を構造化して BO の探索空間を
狭める)、SysInsight (`2603.22708`、PVLDB 19(6):1358-1371、2026) である [5, 10]。

**境界線の引き方。** この系譜の介入面は、設計者が事前に開けた knob の次元に閉じる。SysInsight 自身が knob は "predefined execution
paths" を制御すると書く。系譜内で探索空間が最大の UDO の "transaction code variants" ですら、人間が用意した有限候補からの**選択**である。
Izanagi はこの目標 (ワークロード特化の DB 自動最適化) を knob 空間からコード空間へ持ち出す位置に立つ [10]。

ただし、**「knob 系譜は CC の内部に手が届かない」とは書かない** [5]。SysInsight は、マニュアルではなく DBMS のソースコードを静的解析 + LLM で
読み、knob が支配する関数の因果経路から調整仮説を立て、観測から定量 rule (発火条件 + 方向 + 増分 + confidence) を誘導する。
その過程で `rw_lock_x_lock_wait_func()` から `sync_array_wait_event()` を辿り、`ut_delay()` の spin 時間と context switch 頻度の
trade-off を因果として言語化したうえで `innodb_spin_wait_delay` を動かしている。低レベルの待機挙動は**読解の対象になっている**。
一次資料で確定した限定は 3 つで、どれを落としても反例が立つ [5]。

1. 「手が届かない」の対象は**介入**であって読解ではない。介入の実体は既存 knob のスカラの大きさ (rule は「発火条件 ⇒ 方向 + 増分」の述語で、
   既存 knob の上に載る条件付き controller) であり、分岐そのもの・その条件式・新しい待機戦略の追加は起きない。
2. 届いている待機は spin-wait 同期の経路であり、それがトランザクションの競合待ち (record lock 待ち) と同じ層かは一次資料からは決まらない。
3. 競合検出と abort については「正の記述が無い」までで、「読んでいない」ではない。整形本文 87,303 文字の全体を `abort` / `deadlock` /
   `concurrency control` / `serializab` / `isolation level` / `two-phase` で走査した結果はいずれも 0 件で、精読でも正の記述を確認できなかった —
   **これはこの 1 論文という母集合の中の不在であり、世界の不在ではない。** 44 knob の全リストは論文に無いので、個々の CC 要素への介入の
   有無はこの論文からは決まらない。

したがって境界線は「コードか値か」ではなく、**「対象実装の action vocabulary と分岐構造を拡張するか、既存 knob の上に条件付き controller を
合成するか」**に引く [5, 10]。

**軸ごとの判定。** SysInsight は、軸 1 (対象の空白) については**除外**である — 対象は設定チューニングで、44 knob を拡張しない。軸 2
(帰属駆動・コーパス駆動の合成) については**部分接地・方法論的祖先**である — コーパス = ソースコード、静的な制御依存の帰属、LLM の機序仮説、
観測からの機械的 rule 誘導を持つが、合成対象は既存 knob 上の条件付き方策である。軸 3 (説明可能性) については**部分接地・方法論的祖先**
であり、**「DBMS のソースコードから LLM が機序説明を生成し、観測に接地させる」という狭い能力についてだけ競合**である。論文の主題は knob
チューニングであり、説明は中間機構である。説明の忠実性・proof chain・試行の provenance は評価していない [5]。

このため本論文は、**「LLM に DBMS のソースコードを読ませる」「コードから機序を取り出す」「観測に接地した説明を作る」の 3 語を
差別化の核に置かない** [1, 5]。忠実性・proof chain・provenance を SysInsight が評価していないことは事実だが、それは同論文が触れていないという
だけで、本研究がその実証を積んでいる面ではない (軸 3 の調査は `RW0` で、この面の先行研究一般については何も言えない。2.8 節)。空いている面を
核に据えると新たな実証が要る。残る差別化 3 点 (2.1 節) は既に実装と計測が動いている面であり、核はそこに置く [1]。

**「knob 探索は専業の機械探索で解ける」について。** 本研究の Phase 2 の否定的結果 (P2-5) は、Silo の 8 通りという列挙しきれるフラグ空間で、
LLM の誘導が機械探索に付加価値を持たなかったというものである。SysInsight は、MySQL 8.0.36 の 44 knob・1 session 20 反復 × 3 session
(別途 workload ごと 100 config の履歴データ。target workload のデータは除外して与えられる) という online 予算の下で、白紙から始める SMAC / DDPG++ が高品質な設定に届かず、TPC-C の
knob 選択 ablation でも ML ベースが最下位になったと報告する。**SysInsight は P2-5 を反証しない** (対象も空間も予算も違い、Silo のフラグ空間を
再測していない) が、**その外挿範囲を狭める** — 固定 knob 空間でも観測が乏しければコード由来の意味的 prior が効くという、反対向きの実例に
当たる。したがって「P2-5 と同方向を指す外部証拠」とは無限定には書かず、「P2-5 が実証したのは十分に覆える小空間での否定的結果である」
という限定と、「SysInsight はそれを反証しないが外挿範囲を狭める」という但し書きを組にする。SysInsight の 7.11 倍は GPTuner (LLM を使う
manual-driven 手法) に対する両システム全体の収束比であって、専業 ML / RL に対する数字ではない [5, 10]。

**外部補強としての読み。** SysInsight は LLM が出した調整仮説をそのまま使わず、観測から定量 rule へ落として confidence を付けてから使う。
本研究が LLM の出力を検証してから採用する設計と同じ向きだが、**補強するのは性能の信頼性であって直列化可能性ではない** — confidence の
定義は「その調整が目的関数を改善した割合」である。本研究の正しさ検証器と同形の外部証拠があるかのように読ませないため、この限定は
落とさない [5, 10]。

## 2.4 学習部品で DBMS を置き換える系譜 (learned DB components)

learned index (Kraska ら `1712.01208`、SIGMOD 2018 = 「インデックスはモデルである」の提案 / ALEX `1905.08898`、SIGMOD 2020 = 更新対応 /
PGM-index `1910.06169`、PVLDB 2020 = 最悪ケース保証の証明付き) と learned query optimizer (Neo `1904.03711`、VLDB 2019 / Bao `2004.03814`、
SIGMOD 2021 = 既存 optimizer を粗粒度ヒントで操縦する実用化) は、DB の中核部品を学習物で置き換える系譜である。物語の上では、Izanagi は
「learned DB components の CC 版」の章に当たる — index (データ構造) → optimizer (意思決定) と学習置換が広がってきた延長線上に、
CC (意思決定 + 最も強い正しさ制約を持つ部品) がある [11]。

手段は根本的に違う。この系譜は model-in-the-path (実行経路にモデル推論を挟む) だが、Izanagi は code-as-output (学習の費用は合成時に払い、
実行時はプレーンな C++ で推論ゼロ) である。CC はトランザクションごとに µs 以下の critical path なので推論を挟む余地が無く、この違いは
好みではなく必然である [11]。外部補強として拾うのは 2 点 — PGM の「学習部品に証明可能な保証を付けよ」という要請は、CC 合成に直列化可能性の
検証器を常設する規律と同じ問いへの別解であり、Bao の「白紙から全置換せず、実証済み部品を保ち介入面を絞る」は、stock の骨格を温存して指定領域
(EVOLVE-BLOCK) だけを変異させる本研究の設計と同型の教訓である。ALEX 型のオンライン自己適応は採らず、ワークロード適応は合成パイプラインの
再実行 (オフライン再合成) で担う [11]。

## 2.5 LLM と進化探索によるコード合成

**系譜。** LLM を変異オペレータにした進化探索でコードを合成する系譜として、本節では FunSearch (Romera-Paredes ら、*Nature* 625、468–475、2024) を
方法論的な参照点として取り上げる。FunSearch は凍結した LLM (創造役) と systematic evaluator (幻覚の門番) を対にし、programs database と島モデルで
母集団を保つ。核となる機構は best-shot prompting (スコア最良のプログラム群を prompt に戻して改良させる) である。AlphaEvolve (`2506.13131`、DeepMind の白書、査読なし) は
その後継で、進化 DB から親と inspirations をサンプルし、過去の勝ちプログラム群と評価スコアを prompt に注入し、LLM アンサンブルが
SEARCH/REPLACE 形式の diff を生成し、難易度昇順の evaluator カスケードで採点する。ShinkaEvolve (`2509.19349`、ICLR 2026) は公開され動作する
フレームワークで、母集団を島モデル + global archive で保持し、同一問題設定を解く**公開実装として本研究が比較対象に置くもの**である。
Darwin Gödel Machine (`2505.22954`) は自己改変で進化するエージェントとして、この系譜と自己改善系譜 (2.7 節) の理論的源流に当たる。OpenEvolve は
AlphaEvolve の非公式なオープン再実装で、本節は正典が一次資料として挙げるリポジトリと作者のブログを参照する (独立した査読論文の有無は
本節では判定しない) [12]。

**借用するもの、しないもの。** 借用と非採用は機構ごとに分ける。**採用するもの:** 編集面を限定する機構 — EVOLVE-BLOCK マーカーと diff 形式の
編集面限定は AlphaEvolve (§2.1、§2.3) が出典で、本研究は編集面を機械的に限定する仕組みとしてそれを採用している。evaluator カスケード
(不良の早期除去 → 本評価) も、スコアを生成側に返さず harness 内に閉じる限りで、本研究の「軽い検査 → 正しさ検証 → 性能測定」の直列ゲートと相似である。**思想として参照するもの:** 問題設定
(verifier がある所で正しさを保ちつつ性能指標を最適化する) と、母集団の多様性維持 (島モデル) の発想。**採らないもの:** 探索機構そのもの —
特に、AlphaEvolve・FunSearch・DGM・ShinkaEvolve の 4 研究について正典がサンプル効率の源泉と特徴づける**「勝ち筋 (スコア付きの勝ちプログラム) を
生成側に見せる」機構**である [12]。

AlphaEvolve の ablation は No evolution を切ると両タスクで大幅に劣化することを示し、ShinkaEvolve は過去プログラム全文と combined_score を
prompt へ載せる (`construct_eval_history_msg`、実物で確認)。これは本研究のリーク制御 (勝ち筋の値を生成側に見せない) と正面から衝突する。
もう 1 つの差は正しさの扱いである — FunSearch の evaluator は幻覚防止の門番として、ShinkaEvolve の validate は「素朴な検査で足り、最適化圧力は
敵ではない」という前提で、それぞれ特徴づけられている。本研究はこれに対して、トランザクションの直列化可能性を毎反復検査し、正しさを破る変異を
即 reject する設計を採る。この設計の差が、本研究の規律が不便な保守主義ではなく問題設定から要請された選択であることの外部証拠になる [12]。

**harness の実証と集約の理論。** Effective Harness Engineering (Vesper、`2605.15221`) は coding agent を進化探索へ組み込む harness の実証研究で、
能力の高いモデルほど評価ハックが増えた (gpt-5.2-codex で 8.2%) という結果を、本研究の独立した監査役 (auditor) の必要性と、監査役を被監査側と
同等以上の能力の model に置く方針の定量的な外部証拠として引く。worktree 並列 (3.2–3.9x) と、探索 DB の観測の効果が限定的だった結果も、本研究の
並列化と、生成側へ探索履歴の要約だけを渡す設計の判断を補強する。ただし worktree の並列化はファイルシステムの競合を避ける手段であって、
性能測定の排他制御 (物理的な干渉の防止) を代替しない。トークン予算を終了基準に直輸入はしない (本研究の律速はベンチの実時間である) [13]。
Best-of-∞ (`2509.21091`) と DISC (`2502.16706`) は探索ではなく集約・予算配分の理論で、正しさ判定の seed 数の逐次停止や評価予算の難所配分の部品として
将来予約に留める — 逐次停止を将来採用しても事前登録済みの S-1 系列には適用せず、連続量の throughput へ直用もしない。Best-of-∞ の
「多数決 > LLM-as-judge > reward model」は、LLM-as-judge を正しさ経路へ入れない現行判断の外部証拠である [14]。

## 2.6 対象特化システムの自動合成と、検証付き合成

**対象特化の自動合成。** LLM エージェントがワークロード仕様からシステム丸ごとを bespoke 合成する系譜として、Jitskit (`2605.24096`、KV ストア)、
VibeServe (`2605.06068`、LLM serving システム)、IDS (`2605.23109`、コードと証明を同時に育てる verified synthesis) がある。本研究の設計は Jitskit から
最も多くの部品を借りている — 環境・ワークロード・要求の spec cards 3 枚 (要求カードが isolation level を定める)、reward hack カタログ、
leading indicators、adversarial auditor、planner / coder 分離、却下した設計を蓄積する whiteboard memory である。VibeServe の「単一汎用システムから
ターゲット特化の自動合成へ」という賭けと、outer loop の永続計画状態は本研究と同じ向きで、Accuracy Judge の reward-hacking 検査は Jitskit の
auditor と同じ思想である。IDS からは**「正しさを後付けにしない」** — verifier を毎 iteration 回し、構造化した診断を LLM に返す (単なる
accept / reject に落とすと性能が激減する、と ablation で実証) — を借りる。完全な形式証明 (Rocq) は本研究のスコープ外である [15]。

本研究はこの evaluator-in-the-loop の対象特化合成を、single-node CC の直列化可能性と many-core 性能へ適用する。**ただし、この 3 者はいずれも
CC を対象にしていない**ので、軸 1 (対象の空白) に対しては部分接地 (方法論的祖先) であり、**系譜の中で本研究が何本目かを数える書き方は
採らない** [2, 16]。

**検証付き合成 — 並行プログラムを対象にした例。** CIR+CVN (`2604.09318`、Tongji University) は、LLM に自然言語の仕様から検証しやすい形の同期構造
(Cir) を書かせ、Petri ネット (Cvn) へ機械翻訳して全状態を数え上げ、反例を文の識別子へ差し戻して直させる。対象は mutex / condvar / semaphore の
デッドロックとシグナル消失である。本研究にとって重要なのは、**「検証器は通るが振る舞いを落とした修理」を別の検査で弾く必要が、外部で独立に
生じた実例**である点 — バグ検出を通った成果物に目標到達検査を重ね (RQ4)、5 モデル中 2 つで、61 本の静的規則もバグ検出器も素通りする意味的な
回帰が実際に発生したと報告している。反例を合否ではなく文の識別子つきの診断で返す点も、IDS の別ドメイン版として本研究の設計と同じ思想である [4]。

同時にこの論文は、軸 1 との**境界語**を 2 つ与える。対象はスレッドの同期構造であってトランザクションの並行性制御ではなく、直列化可能性も、
アプリケーションの性能 (スループット・遅延) も扱わない。**原始操作**の語彙は形式系が定めた閉じた集合 (Table 3 と `nop`) で、LLM はコードも Cir も
生成するが語彙そのものは拡張しない。判定は軸 1 に**部分接地・方法論的祖先**である。Petri ネットの全状態数え上げ (対象規模は 250 状態未満・
20 ms で閉じる) と、信頼境界を「LLM が生成した模型」に置く設計は採らない — 本研究は実際に走る C++ を計測対象にする [4]。

正典 7.6 の空白域 1「CC 合成に特化した敵対的 verifier + リーク制御を備えた進化ループ」について、以前そこに書かれていた「検証付き合成の対象は
Rust / C の逐次コード・形式仕様」という母集団の特徴づけは、この 1 件を根拠に 2026-08-26 に取り下げられている。検証付き合成には並行プログラムを
対象にする例があり、母集団全体がどちらへ寄っているかは 1 件では測れない [4, 17]。

## 2.7 自己改善・メタ最適化、研究アーティファクト、運用の点検レンズ

本研究の運用面 (手順書と規律を育てる仕組み、却下した設計の記憶、成果物の形) に接する系譜である。この節では、思想・外部補強として参照するもの、
採用済みの機構 (ARA の入力側隔離の 1 件)、将来参照するデータ構造・部品 (予約) を区別して書く [18]。

- **手順書・harness の自動改善。** SkillOpt (`2605.23904`) は手順書をテキスト空間の学習ループで改善し、validation gate を通った編集だけを採用して
  却下編集を「やってはいけない修正の記憶」として保存する。Self-Harness (`2606.09498`) はこれを harness 全体へ広げ、in-sample と held-out の両方で
  非悪化、かつ少なくとも一方で改善した提案だけを採用する。どちらも「検証を通った編集だけ採用し、それ以外は記憶する」という形で、本研究の
  whiteboard memory と、正しさゲートを緩める変異を採らない規律の外部裏付けになる。Self-Harness の verifier-grounded failure signatures は、verifier の
  失敗シグネチャを次の入力にする本研究の設計とほぼ一対一である。自己改変ループの機構そのものは、本研究では実装せず将来の予約に留める。
  Self-Developing (`2410.15639`) は accept / reject を選好データにして生成器自体を更新する最右翼で、部品として予約するが、正しさゲートを選好信号へ
  溶かさない — 直列化可能性違反は低スコアではなく即 reject とし、選好対にも入れない [18]。
- **記憶の構造。** DecentMem (`2605.22721`) は共有メモリがマルチエージェントを同質化させるとして各エージェントに独立メモリを与え、整理済み過去
  トラジェクトリと LLM 生成候補の二プール構成に理論保証を付ける。借りるのは二プール分割の発想だけで、per-agent の分散メモリ機構は借りない。
  online reweighting の LLM-as-a-judge は操作されうるので、正しさ経路には入れない [18]。
- **研究アーティファクト。** ARA / The Last Human-Written Paper (`2604.24658`) は、物語形式の論文が反復研究を圧縮して AI による理解・再現を妨げるとして、
  論文を機械実行可能な research artifact に置き換える提案である。本研究の成果物 (certified な選択結果、事実層の材料レポート、試行台帳) は ARA の要素と
  ほぼ 1:1 で対応する。3 つを区別する。**採用済み:** 検証エージェントに報告済み数値を一切見せない anti-fabrication isolation は、本研究の verifier の
  入力側隔離として採用済みである。**将来雛形・思想参照:** 型付きの研究 DAG (question / decision / experiment / dead_end / pivot) は本研究の試行台帳の
  共通データモデルの外部雛形として、主張 → code → 実測値を辿る forensic binding は本研究の説明可能性 (事実層) のデータ構造と同型の思想参照として
  扱う — データ構造の対応は証拠鎖の実証を意味しない。**採らない:** ARA は所見をループへ自動還流せず著者が手動で反復する設計であり
  (正しさ信号を毎反復還流させる本研究との差はここにある)、ARA Compiler / Live Research Manager のような重機構も採らない。本研究は
  研究アーティファクト (材料レポート) の生成までを担い、物語化・推敲は別システムに委ねる [18]。
- **探索ループの近傍と、正しさゲートの欠落。** LaMDAgent (`2505.21963`) は post-training のアクションを列挙・選択・評価しテキスト memory を更新する、
  本研究の探索ループ (列挙 → 選択 → 評価 → memory 更新) と同じ形をとる参照実装だが、評価は正しさゲートを持たずスカラー報酬に一元化される。
  本研究はその評価規律を移植しない。LLM 選択の random に対する優位が小さく、アクション空間設計が支配的だったという ablation は、P2-5 の否定的結果の
  独立の補強として引く。一方、スカラー報酬とテキスト memory だけで 100 iteration 改善した結果は、本研究が探索の進み具合を先行指標 (leading

  (`2605.03231`) は web GUI 自動化の対象で、自動 scorer の誤判定と、事後 verifier を使わない best-of-N 設計を示す対照例である — 正しさが二値でハードな

  重い計測 (profiling) を回す本研究の二段構えの経済学的な引用元で、ドメインが違うので一般化である旨を明記して引く。12-factor-agents と ECC (いずれも
  GitHub) は、設計が業界の経験則と外れていないかの点検レンズであり、取り込みの対象ではない [19]。

**説明可能性の系譜についての内部の不在。** 2026-08-26 時点の正典の索引 26 エントリの本文を「層3 / 説明可能性 / 説明生成 / 機序 / proof chain / 証拠連鎖 /

## 2.8 先行研究調査の状態と、本節が言わないこと

本節の限定は、正典が定める「検索記録の成熟度」(`RW0`〜`RW4`) に従う。これは調査の網羅率ではなく、検索記録がどこまで再現可能かの段階であり、
段階が高いことは主張が正しいことを含意しない。本稿に適用される段階は次の 2 つである — `RW1` (軸 1) は既存の限定付き文の逐語引用だけを許し、
新しい不在方向の表現を作らない。`RW0` (軸 3) は世界の不在の表現を一切許さない。参考までに上位の段階を書くと、`RW2` では索引名・検索式 ID・cutoff を
明記した限定付きの未検出だけが許され、`RW3` では母集合と cutoff を同じ文に置く。`RW4` は限定付きの不在を人間の最終裁定へ提出できる段階であり、到達自体が
論文表現を認可するものではない。`RW4` でも無限定の「先行なし」「世界初」「系譜の何本目」は使えない。**内部の不在** (自分の索引・調査記録の中の不在) は、母集合と走査した語を同じ場所に置き、
内部の不在と読める形にすれば段階を問わず書いてよい [20]。以下で「leaf」は登録した検索単位 (検索式 1 本、または検索式 × 発表年の shard)、
「pass 1」はその初回取得を指す。

**軸 1 (対象の空白) = `RW1`。** 2026-08-26 の初回棚卸しの後、7.7.4 の手続きに従う事前登録 (2026-08-27、索引 3 つ、共有の暦境界 cutoff 2026-12-31) と
