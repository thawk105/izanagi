## レンズ B

**must-fix B1 — per-base 差から受入 wall の不採用を確定している。**

- **根拠:** README 冒頭の「10%には届かない」、§7 の「最大でも数秒」、§8-1(a) の「採用理由は共有資源削減になる」、推奨理由の「受入 wall の0.5%相当で基準内」。JSON は1 job・1 node・1 tip の base 計測で、受入対比較ではない。裁定 §4 はこの読み替えを禁止している。
- **成果物への影響:** 本来の「採用再検討に進む改善候補」が、「wall 基準では採用不能、別目的裁定だけが可能」という裁定パッケージに変わる。
- **是正案:** 次へ統一する。

  > 測定条件内では C1 は改善候補。受入 wall の変化と D357／D1260 の達否は未測定。非競合で同じ per-base 差が保たれる単純模型では小さい効果を予想するが、上限ではない。

  見送り推奨自体は可能。ただし理由は「今回の効果量に対して実装・検証費用をどう評価するか」とし、未測定の基準不達を根拠にしない。(c) の proto 化等との効果合算も未検証とする。

**must-fix B2 — 撤回済みの普遍的下限と「明示 refresh 必須」が復活している。**

- **根拠:** README 冒頭「0.61秒の下限は自己完結では届かない」「明示 refresh が要る」、§6(3)「自己完結の経路は…下限に近い」「refresh を含めなければ production 等価でない」。裁定 §1 A5・§2 は、複製済み worktree を変更せず空 stat を検証する経路へ限定している。

- **是正案:** 次に置換する。

  > C2 は参照 index を無料で使い、複製済み worktree を変更せず、明示 refresh で stat を保存する経路の参考費用で、中央値8.919秒だった。他経路の下限ではない。

  production status 自体による検証と、index への stat 保存を区別する。「明示 refresh というコマンドが意味上必須」とは書かない。

## 総括

**must-fix は3件（B1〜B3）。**

主計測の区間と、n=5・中央値差−1.682秒・5/5負による **「改善候補」判定は正しい**。主要数値の整合性を崩す欠落費用や失格除外は見つからなかった。

**現草稿を段7の記録に使うのは NO-GO。** 受入 wall の不達断定、普遍的下限、copy 後 refresh の未測定効果を修正することが条件。併せて数値誤記と検査保証範囲を訂正すれば、**測定条件を限定した改善候補の記録として GO**。主判定を維持するための probe 再走は不要。
