**M1. D2148 の読取りが誤っており、480 秒関門と dispatch の期限契約が未整理。**

- **根拠:** plan:272 は「逐語資料は別裁定」とするが、今回の `D2148-item8.md:1–7` は明確に外側 timeout の裁定。`dev_wave_land.py:3545–3555` は checker 呼出し全体に `timeout=480` を設定する。一方、dispatcher の既定値は queue 待ち 900 秒、walltime 3,600 秒、grace 300 秒など（`dispatch_compute.py:66–77`）。
- **成果物への影響:** 監査本体が正常でも、queue 待ちだけで land が先に打ち切り、rc・回収結果が変わる。T-2656 の高速化だけではこの経路を解消できない。

**M2. 固定全史比較に、独立した旧版と authoritative 経路を実行する手順がない。**

- **根拠:** plan:221–225 は比較を宣言するだけ。既存 `tests:7285–7306` は内部監査の authoritative 比較と `_run_range` の公開出力比較を併用している。しかし今回の高速経路は authoritative 限定（plan:18）。`--range` の公開出力比較だけでは新経路を通らない。
- **成果物への影響:** 新経路だけが findings・順序・rc を変えても、「旧版／新版一致」が緑になり得る。
- **是正案:** 次を実行仕様として固定する。
  1. 比較対象 HEAD を brief の `b7f970dfa507558f7fb669a5ab38958d6c76b57c` に固定し、旧 checker はその OID の blob から取得する。動く `main` は使わない。
  2. 書込可能な検証用 worktree の**同じ `tools/check_ai_provenance.py` の位置**で旧版／新版を交互に実行する。HEAD・index・config・環境・worker 数を固定する。別場所の script を直接起動して、repo 解決や `__file__` の意味を変えない。
  3. 両版とも cold な authoritative 全史を通す。内部比較は `receipt_state=None`、公開経路比較は専用の空 receipt store を用いるなど、既存の共有受領証を削除せず統制する。
  4. selected の列、重複を含む監査回数、順序付き `HistoryAudit`、rc、監査の stdout/stderr を比較する。並列 worker の開始順自体は一致条件にしない。
  5. bounded scope の予算・ピーク等は実測ごとに変わる（login JSON:28–29）。「公開出力 1 bit 不変」が監査 record を指すのか、外側の動的診断も含むのかを明記する。

小 fixture と固定全史比較の併用は実行可能。ただし、「新実装の高速化を無効化した版」だけを旧版 oracle としてはならない。

**M3. 変異 matrix は、実装に届くテストと全体5分の実行予算を固定できていない。**

- **根拠:** plan:233–248 の変異対象は checker 本体であり、その点は正しい。しかし nodeid、authoritative 経路、実 Git を通す範囲、各変異の所要が未指定。既存公開出力テストには `_run_range` 経路がある。login 全史は1走88秒、計算ノードの監査本体は41.7秒。

- **是正案:** 各変異に「変更行・実行 nodeid・到達する高速経路・期待する結果差・実測時間」を付ける。破損注入は Git 出力境界に限定し、batch helper・validator・期待 finding を stub で置換しない。計算ノードの `tools/mutation_worktree.py` で、無変異緑→対象変異赤→復元緑を記録する。

「後半失敗時に前半辞書を返す」は**実 repo 全史でしか kill できる変異ではない**。実装違反を持つ小 repo で先頭の path を偽って空にし、後続を破損させ、finding と legacy 再取得を確認すれば kill できる（plan:193,239）。実 repo の56件・post-baseline 3件は、別の固定全史比較で OID・kind/value・順序を照合する。

88秒×旧新版で約176秒だが、3走なら約264秒で残りは36秒しかない。計算ノードでも41.7秒は監査本体の値であり、queue・準備・復元込み5分の証明にはならない。全史を各変異に載せる計画は避け、全体の実測予算を提出すべき。

### should

**S1. P2 の根拠は、現行の混雑時観測と同じ期限での比較を欠く。**

- **根拠:** brief:29–30,48–49。428〜574秒は D2045 以前の観測。現行 cold 全史は load 10.9 開始の1走だけ。`grant_budget:1090–1137` はメモリ予約であり、CPU 供給を保証しない。
- **成果物への影響:** 「CPU 判定不要」「480秒に確実に収まる」という裁定を、測っていない条件へ一般化する。
- **是正案:** 改善前後の現行 cold 全史を、低負荷・混雑時で交互測定する。必要なのは CPU 秒そのものではなく、期限内完了を予測する材料である。候補は履歴量・cold/warm・過去の CPU 秒と wall、実効 CPU 数・quota、競合や throttling、queue と前後処理の所要。

`os.getloadavg()` の絶対しきい値だけでは、96 CPU のホスト容量、I/O 待ち、当該 cgroup の制約を区別できない。`cpu.stat` も単発の累積値では足りず、区間差分と wall、quota 等との対応が必要。追加する場合はメモリ予約を維持した別の実行場所判断として設計し、dispatch 時の予約解放、queue 停止時の扱い、`--force-dispatch` を保存する。

**S2. 「dispatch は受領証を失う」という根拠が、cold/warm と環境差を混同している。**

- **根拠:** brief:24–27,48。`bindings-compute-1.stdout.txt:23–25` では同 partition の祖先受領証も attributes 差で失効。`checker:2241` は checker sha256 を束縛する。さらに `dispatch_compute.py:138–143` の provenance は `env_mode="inherit"` であり、brief の「clean env」は指定コードと一致しない。
- **成果物への影響:** login でも既に cold な走に「受領証を失う追加費用」を計上し、dispatch を不当に不利に評価する。
- **是正案:** 「有効な login receipt がある走」と「両経路 cold」を分けて比較する。実測された環境差は事実として使えるが、常に clean／別 partition になるとは断定しない。

改版直後は checker hash の不一致により旧 checker の受領証が使えず、全史へ戻る。これは受理集合変更ではないが、初回費用として plan に明記が必要。計算ノードへの移動は受領証だけでなく、環境/config、CPU 供給、filesystem/cache、準備・回収費用も変える。特に `_ai_agent_values` は ambient config を維持する設計なので、環境差を単なる時間差と決めつけない。

### nit

**N1. fail-closed 方針は妥当。ただし「見出し一致＝内容対応の証明」ではない。**

- **根拠:** plan:62–70,98–100,134–149、D2033:18–19。
- **成果物への影響:** 見出しを維持したまま path が別 commit に移れば見逃し得る。ただし、指定 argv で実際に起きる条件は資料から立証されておらず、現時点で実装欠陥とは断定できない。
- **是正案:** 次を実 Git の完全出力と旧取得結果で固定する。

  - 空 root／empty commit の先頭・中間・末尾で、本物の見出しが欠けたり別位置に出たりしないこと。
  - 見出し欠落と OID 同形 path の組合せ。本物の見出しが常に存在するなら、OID path は余剰見出しになり全体 fallback する。保証が崩れると、その推論も崩れる。
  - merge の同じ見出しに別親の結果を対応させないこと。出力には親 OID がなく、要求表・stdin の正しさは見出し検査だけでは確認できない。
  - 後続破損、最終親 batch 失敗、欠落 key で部分結果を公開しないこと。これは plan が既に要求している。

CR の text-mode 変換は `_git:1195–1206` 自体の既存挙動である。同じ変換と NUL 分割を両経路で使う限り、CR→LF だけを新版固有の退行とは言えない。CR・CRLF・LF を含む path の衝突と、その後の path 再利用まで比較する。新版だけ bytes を保存する「修正」も旧版との差を作り得る。

**N2. 捕捉例外を「D2033 と同じだから十分」とは言えないが、ValueError 漏れの実害も未立証。**

- **根拠:** plan:145、`_git:1195–1205`、既存捕捉 `checker:1227`。
- **成果物への影響:** speculative 取得固有の例外を取り逃すと、worker 内の既存失敗順を再現せず終了し得る。
- **是正案:** `ValueError` は不正な引数や埋込み NUL 等で起こり得る。一方、固定 argv・検証済み OID・固定 cwd の通常経路で発生する具体例は未提示。`check=True` も timeout もないため、現行 `_git` からの `CalledProcessError`／`TimeoutExpired` を前提に広く捕捉する必要はない。到達可能な取得例外を特定して狭く扱い、`BaseException` や実装バグの包括捕捉は避ける。

**N3. 残存コストの見送りは合理的だが、(a)〜(d) 全部の必要性も未証明。**

- **根拠:** profile:8–13,27–28、plan:3,254,268。
- **成果物への影響:** 現時点では、追加最適化の有無による480秒関門の成否を確定できない。
- **是正案:** (a) の後、(b)(c)(d) の追加効果を段階測定する。`--cc` 1,418回、隔離 parse の tempdir、repo parser の cwd 費用は残るが、判定や隔離を変える最適化を必須にする根拠はない。提示資料には「cwd 単独4ms」の切分け実測もない。

累積1,128秒を wall 短縮量として加算しない注記は正しい。粗いモデルは、

`wall ≈ 逐次部分 + CPU仕事量 / 実効並列度 + I/O・待機`

である。32 worker は32 CPUの常時利用を意味しない。観測された CPU/wall は計算ノードで約6.9、login で約4.2であり、288/32≒9秒、368/32≒11.5秒を予測 wall としては使えない。一括化には pool 前の逐次費用も加わるため、削減後の CPU 秒と wall を双方測る必要がある。「CPU 368秒を32スレッドで奪い合うと wall が368秒へ近づく」は、実効CPU供給が約1に落ちる等の条件を省いている。

**N4. 3.5% と過去所要時間は、母集合限定の記述値。**

- **根拠:** brief:13–17、login baseline JSON:5–24。
- **成果物への影響:** 数値自体は変わらないが、将来の dispatch 失敗率・完了時間の確率として使うと裁定を誤る。
- **是正案:** 3/86 の二項 Wilson 95%区間は約 **1.2〜9.8%**。これは独立同分布を仮定した区間であり、撤去済み worktree の欠測や時期・原因の偏りを補正しない、と記す。SIGTERM は呼出し側 timeout と独立な「基盤固有故障」とも限らない。

queue の観測対象が provenance receipt でも、待ち時間は共有 queue の他 task に依存する。最大537.6秒を provenance 固有の分布や将来上限とは扱えない。41.7秒は固定全史の監査本体、過去 receipt の run_span 15〜476秒は区間定義・版・対象量・warm/cold・資源条件を揃えていない。差の原因はこれらの候補に分解すべきで、現資料だけでは確定できない。

### P2 の判定：refuted

**親 P2 の「CPU 判定を足さず、T-2656 で480秒へ確実に収める」という根拠付き結論は refuted とする。**

現行の混雑時 cold 全史が未実測で、receipt の追加損失は cold な land では成立せず、dispatch には既存の外側480秒問題があるためである。

これは「CPU 判定を今すぐ追加すべき」が証明されたという意味ではない。**本 wave では CPU 判定追加を保留し、最適化と混雑時測定を先行する**という暫定方針なら支持できる。「不要と確定」と「証拠不足で保留」を分ける必要がある。
