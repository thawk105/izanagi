## 所見

1. **must-fix — §6 の失格条件に追加があり、pass との排他性が保証されていない。**  
   根拠: 本文:317、320、389。`docs/decisions.md:68044`（D2160 項5）。
   D2160 は anomaly の検出を失格条件とするが、本文は「または verdict が `serializable` でない」を加えている。一方、pass は校正を含む判定集合には anomaly 0 だけを要求する。そのため「本走24件は全条件成立、校正に非 `serializable`・anomaly_count=0 の完走 verdict」がある入力は、文章上は失格と pass の両方に該当する。この入力を現行 verifier が生成するかは今回未確認だが、本文には除外条件も判定優先順もない。また、校正に `serializable`・certified=false・anomaly 0 があれば、§6 の pass から§1.1 の「判定集合の全件が certified」は導けない。  
   **成果物への影響:** 同じ記録に対する判定と、pass 時に許される報告が一致しない。

2. **must-fix — 発効と校正の前後関係が循環している。**  
   根拠: 本文:36、457、467。
   §0・§12 は発効束の実値を発効前に固定するとし、その一覧に校正結果を含める。一方、同じ項目が校正を「発効の後・本走の前」に実施すると指定している。  
   **成果物への影響:** 校正結果がなければ発効できず、発効しなければ校正できない契約になる。

3. **should-fix — 保全容量の外挿で、64走の内訳を取り違えている。**  
   根拠: 本文:447。`docs/paper-story/results/2026-09-20-verify-phase-adopted-backoff.md` §0.1・§3.1・§5。
   原本213.3 GB・圧縮後48.9 GBは「3 s の64走」ではない。本走48走と校正実走16走の合計で、内訳は **3 s が54走、6 s が6走、10 s が4走**。したがって、その平均容量を3 sの容量として倍にする根拠は成立しない。  
   **成果物への影響:** 6 s本走の容量見積り160 GB／37 GBと、投入前の空き容量判断が誤った基準に依存する。

4. **should-fix — §1.3 の反例と確率表現に修正が必要。**  
   根拠: 本文:86、97、183。`external/ccbench/include/random.hh:16`、`external/ccbench/include/ycsb.hh:92`。
   - 項1の閾値例では、extime<T の見逃し確率は ε=1 であり、全走見逃しも1=εⁿ。これは εⁿ の式への反例にはならず、「非自明な ε<1 を置けない」例である。
   - 項4の10⁻⁴級は、独立・一様な32 bit抽出を仮定した算術。本文は一様性の条件を示さず「無視できるほど小さい」と評価している。
   - 48×8=384であり、1152はさらに3 workloadを含む数。実際のコードはメンバの constructor と `YcsbWorkload` の constructor で二度初期化するため、「抽出回数」と「最終的に使うseed数」も区別が要る。  
   **成果物への影響:** 数値的信頼度を主張しない登録に、条件を明示しない確率評価と成立しない反例が残る。

5. **should-fix — 不在の断定が、確認範囲より強い。**  
   根拠: 本文:150、185、388。`/work/1/SFC/tanab/dev-wave-jobs/dev-wave-b8-longrun-verify-prereg/rulings-stage4.md`「実測で支えていない否定命題」。

   **成果物への影響:** 既知結果台帳と「初回検証」という位置づけが、網羅確認済みの事実として読まれる。

6. **should-fix — 予算による段下げで、適格集合との関係が明記されていない。**

   **成果物への影響:** 校正で不適格だったextimeで本走を投入する読みが残る。
