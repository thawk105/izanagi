## 攻撃 1

**P-B は妥当。ただし停止理由は「inert 不成立」ではなく「STOCK 成立の確認前に claim 取得で停止」と書くべきである。** 実 traceback は `FileExistsError` → `ClaimError` であり、source が非 STOCK だった証拠ではない。（`evidence/attempt-0001/job.stderr:14`、同`:29`）

「停止規則は inert の検査失敗だけを指す」という反論を最大限認めても、再投入禁止・launcher 改修の scope 外指定は別に残る。さらに４巡目は「成立したら」の条件付きである。原因が claim 排他だったことから、その条件を解除できない。（`verbatim/T-2795-pair-origin.md:8`〜`:13`）

DW-STOP も無条件の修復命令ではない。「許可範囲で復旧不能」「承認前提を覆す新事実」を正式停止の条件にしている。本件はそれに該当する。（`docs/dev-wave/core.md:35`）

- **本 wave で可能:** 一次証拠の照合・保存、候補単独の評価結果と pair 未達の記録、停止判断、整合案の比較と裁定待ちの明示。
- **不可:** launcher／claim の変更、claim の削除・退避による救済、別 root への追加投入、４巡目の投入、STOCK 性の要件緩和。repo 外 glue に移しても scope 制限は消えない。（逐語依頼`:9`、`:12`、D553、`campaign_claim.py:386`）

## 攻撃 2

**P-C の最大の欠落は、案 (ii) の「１ process＝１ claim」が現行 API から自動的には成立しないこと。** `run_campaign` は呼出しごとに認可し、その認可が `acquire_claim` を呼ぶ。同一プロセスで二度呼んでも、同じ path の `O_EXCL` に拒否される。（`orchestrator/campaign/loop.py:517`、同`:236`、`campaign_claim.py:427`）

| 択 | 通してはいけない最も強い理由 | 最小差分・排他・identity |
|---|---|---|
| (i) DEAD 所有者の同 identity 再取得 | 死者の検出は、claim を置換・再取得してよい権限を意味しない。判定と置換の競合も解く必要がある。 | identity／WAL は保持できるが、one-shot の受理集合を変更する。局所 launcher 修復より防壁への影響が大きい。（D464、D553、`campaign_claim.py:386`） |
| (ii) 同一 process 内で stock 評価 | 現状の二度の `run_campaign` をまとめるだけでは失敗する。二度目だけ認可を飛ばす実装も sink-local 強制を壊す。 | **認可・claim を一度取得し、その所有範囲で両評価を行う設計**まで具体化すれば、leaf の one-shot と同 identity・同 WAL を保持できる。ただし呼出し契約の変更は必要。（D553、D2183、`loop.py:517`） |
| (iii) claim を rename | 自動退避は自動回収と同じ効果を持つ。「削除していない」は反論にならない。 | 行数は小さくても排他防壁を外す。claim 不在の窓を作るため不採用。（`campaign_claim.py:386`、同`:447`） |
| (iv) stock を別 out_root | 別 root は D464 の排他保証範囲外。同 WAL 条件も破る。 | leaf は不変だが保証を共有しない。**root を変えるだけでは identity が変わるとは限らない**ため、「別 campaign」を別 ID と同義に書けない。別 ID にするなら identity 入力の変更も必要。（D464、D2183、round3 README`:61`） |

**推奨は (ii) を具体化した案。** 「一つの所有期間で一度だけ認可・claim を取得し、既存 pipeline に候補と stock を通す」を設計条件にする。安全性を保つ最小差分は未確定であり、「driver に口を足すだけ」とは約束しない。D2183 の CLI 排他・起動契約への影響も明示して裁定する。（D553、D2183）

追加すべき択は **(v) 修復・追加計測を認可せず、未達として保留する**。４案とも変更を伴う以上、現状維持も選択肢に必要である。なお、stock を先に起動しても二番目が拒否される構造は解消しない。（逐語依頼`:9`、`campaign_claim.py:427`）

## 攻撃 3

**P-D は新 F より既存 F への再発追記を推奨する。ただし失敗の定義を狭める。**

索引の実見出しは `### F` であり、指定の `^## F` では該当しなかった。関連する型は次のとおり。

- **F1019：第一候補。** gate と driver の統合について、本物の経路を stub が覆い隠し、実走で契約の不整合が露出した型。今回は「新 gate の追加」ではなく「既存 claim を通る新 launcher」という差を明記して再発追記する。
- **F81／F722：補助参照。** 合成 fixture・期待側の検査が実経路の拒否を拾わなかった型。
- **F952：設計面の補助参照。** 固定した契約を実 consumer に当てず、次 wave で実体化不能が判明した型。
- **F1018：類似だが主分類にはしない。** launcher 前提の突合せ漏れは共通するが、今回は env 入力欠落ではない。
- **F321：再発ではない。** 今回は二重投入を通したのでなく、claim が拒否した。防壁の破れと記録してはいけない。

「実機で１ job も通さず land した」**だけ**を失敗と数えるのは強すぎる。前 wave は実測未実施・pair 未成立を明記し、実装と投入を段階化していた。（D2172 項3、launcher README`:36`）

失敗として支持できる記述は、**「同 identity・同 WAL への二段起動を設計したが、reservation 必須の実認可経路との整合を検査できず、初投入の stock が claim 取得で停止した」**。未測定の正直な開示は、統合欠陥の不存在を保証しない。一方、成功捏造・inert 検査失敗とは分類しない。（D2183、F1019、実 stderr`:29`）

routing は既存 F への再発 fragment とし、恒久修復は未実施と書く。裁定案を「恒久対応済み」にしない。（`docs/skill-self-improvement.md:22`、`docs/dev-wave/core.md:107`）
