# 裁定パッケージ — [T-139] 承認 payload fold で残った 1 問

本 wave (公表 core 段階 2 の承認 payload fold) は、ユーザー裁定 Q1〜Q7 を適用して
承認 payload を書いた。その過程で、**Q1〜Q7 から一意に導けない設計択一が 1 件**残った。
段 6 の焦点再レビューが「ユーザー裁定へ返すべき」と判定したものである。

**本 wave の land 自体はこの問いの答えを待たない** — payload は fold 時点の状態
(`pilot_submission = forbidden` / `main_submission = forbidden`) を正しく記録しており、
禁止を維持する限り嘘は生じない。**答えが要るのは、いずれ投入を再開するときである。**

## R1. pilot / 本走の投入禁止を、誰が何をもって解除するのか

### 現状

承認 payload は fold 時点の状態として次を固定した。

```text
pilot_submission = forbidden
main_submission  = forbidden
deny_basis       = 先行裁定 B8 (a) および Q3 (b)
```

**解除条件を書いていない。**理由は、Q1〜Q7 のどれもそれを裁定していないためである。
帰結として、次の 2 つが同時に起こりうる。

- **fail-closed に実装すると、投入は無期限に拒否される。**解除の根拠が canonical に無いため、
  正しく振る舞う actor ほど永久に止まる。
- **人間が暗黙に解除すると、未完成の gate のまま本走・pilot が始まる。**
  特に source 側の本走 gate は未実装であり (Q1 (a) で旧 `b03` から失われた投入前 admission)、
  公表台帳の実体束縛・原子予約も未実装である。

現在この 2 つの禁止は**根拠が異なる**のに 1 つの `deny_basis` に畳まれている。

| 禁止 | 根拠 | 解除に要ると考えられるもの |
|---|---|---|
| `pilot_submission` | Q3 (b) — 追補 P の凍結が公表台帳の実体確定を待つため | 公表台帳の実体確定 + 追補 P の凍結 |
| `main_submission` | 先行裁定 B8 (a) — 公表手続きの凍結までの保留 | 上記に加え、source 側の本走 gate の実装・検証 |

### 選択肢

- **(a) 本 wave では書かず、次に投入を再開しようとする wave が解除条件を裁定パッケージで問う (推奨)。**
  → 現状維持。payload は状態だけを記録する。禁止は canonical decision がなければ解けないので、
  安全側に閉じたままになる。代償は、投入再開時に必ず 1 往復のユーザー手番が要ること。
- **(b) 本 payload に解除条件を書き込む。**例: 「pilot は追補 P の凍結 decision が fold された後」
  「本走は source 側本走 gate の実装・検証が canonical に記録された後」。
  → 再開時の手番が減る。ただし**現時点で実装も検証もされていない gate の合格条件を、
  その中身を見ずに先に決めることになる。**Q-D が禁じた「受理仕様の先行凍結」に近づく。
- **(c) 解除権限だけを先に決め、条件は後で定める。**例: 「解除できるのは canonical decision だけであり、
  wave の自己申告・manifest の宣言では解除しない」。
  → (a) と (b) の中間。**穴の大きい方 (暗黙解除) だけを先に塞ぐ。**

### 親の推奨と理由

**(c) を推奨する。**理由は次のとおり。

- 実害の非対称性がある。fail-closed 側の失敗は「止まる」であり、暗黙解除側の失敗は
  「未完成 gate のまま本走が走り、certified primary と公表 entry が生成される」である。
  **後者だけが成果物を壊す。**
- (b) は中身を見ずに合格条件を決めることになり、公表層実装 wave の裁定事項を先取りする。
- (a) のままだと、解除権限すら canonical に書かれていないため、
  「誰も禁止していないから解除してよい」と読む actor を止める文が無い。

**(c) を採る場合、本 wave の payload へ 1 行足すだけで済む** — 「この禁止を解除できるのは
canonical decision だけである。wave の自己申告・manifest の宣言・実装 wave の完了報告では解除しない」。

### 成果物影響

- (a): 投入再開時に手番が 1 回増える。台帳の値は変わらない。
- (b): 未検証の gate に対する合格条件が canonical に固定され、後で実装が条件に合わない場合、
  条件の側を緩める圧力がかかる (絶対規律 2 が禁じる方向)。
- (c): 暗黙解除の経路が閉じる。解除条件そのものは未定のまま残るので、
  再開時に条件を裁定する手番は (a) と同じく要る。

## 本 wave が scope 外として [T-793] へ送ったもの (裁定不要。報告)

いずれも公表層実装 wave の責務であり、本 wave は実装していない。

1. source 側の本走 gate の新設 (Q1 (a) の条件。要件は台帳に記載済み、実装・検証は未了)。
2. 根から唯一の公表台帳実体への束縛、原子予約、`(root, ordinal)` の一意性、ordinal 非再利用。
   **付随して、`addendum_p_freeze_precondition` の「公表台帳の実体が確定していること」を
   誰がどの canonical 記録で証明するかも未定義である** (段 6 レビュー D の所見)。
   現状は自己申告で通せるため、実体確定の成立証拠を [T-793] が定める必要がある。
3. 追補 P の未確定 marker と `p` 系 exact-key を検出する機械 gate。現状は規律だけが止めている。
4. fold 後の `authority: none` を canonical decision の approved role へ解決する resolver / report 層。

## 本書が主張しないこと

- **R1 に答えないと land できない、とは主張しない。**payload は現状を正しく記録している。
- **禁止が解除された、とは主張しない。**本走・pilot は依然投入不可である。
- **[T-793] が上記 4 件を実装済み、とは主張しない。**いずれも未着手である。
