## Q1. 凍結事前登録 core の内部矛盾 — 追補 A の閉集合は `a01`〜`a12` か `a01`〜`a13` か

**事実。** `output/insights/2026-08-07_t139-mainrun-design/preregistration.md` (凍結、digest `ac939af4…`) は、
同じ集合を 2 通りに書いている。

- §14 の閉集合の表は **`a01` から `a13` までの 13 行**を列挙する。`a13` は
  「**primary 系列に割り当てる有意水準**。`q` はここから導くので、追補 B では動かせない」である。
  §14 の「越えてはならない線」も「`a11` と `a13` は `q` の導出規則と primary 系列の有意水準を固定する」と書く。
- §15 の投入 gate の要件 5 と、その直後の「通る正例」は、**`a01`〜`a12`** を exact-key の基準として書く。

D234 決定 (5) は有意水準を追補 A に置き pilot 前に固定するとし、決定 (7)(v) は件数を書かず
「core の列挙する閉集合を exact-key で満たす」とする。

**なぜ問題か。** exact-key は「欠落も余剰も解決失敗」なので、`{a01..a12}` と `{a01..a13}` は
**互いに素**であり包含関係にない。どちらを実装しても、他方を満たす追補 A は resolver に拒否される。

- `a01`〜`a12` を採ると、有意水準を含む追補 A が**余剰**として拒否される。
  primary alpha を pilot 前に固定する経路が閉じ、**pilot の後に alpha を選べる**状態が残る (絶対規律 3 に抵触)。
- `a01`〜`a13` を採ると、凍結 core の §15 が明示する「通る正例」を resolver が拒否する。

**選択肢。**

- **(a) `a01`〜`a13` を採り、§15 の `a01`〜`a12` を erratum として明示 supersede する (推奨)。**
  §14 が閉集合の定義箇所であり、D234 決定 (5) が有意水準を追補 A に置くと定めている。
  受理集合は狭い側 (alpha を必ず要求する) へ動く。core の bytes は変更しない。
- (b) `a01`〜`a12` を採り、有意水準は別の場所で固定する。
  → 現 core には別の場所が無く、追補 B は `q` に影響する量を一切持てない。alpha が宙に浮く。
- (c) 新しい core を起こす (別 study として扱う)。
  → 最も保守的だが、事前登録のやり直しであり、2026-08-07 の裁定 11 件の再確認を伴う。

**親の推奨は (a)。** ただし「凍結文書の受理述語を変える」ため、明示的な supersede の宣言を伴う
ユーザー裁定が要る。親が明確化として処理してはならない (レンズ B が独立に指摘)。

## Q2. D234「実装境界」と事前登録 §11 の段順序、どちらの読みを採るか

**事実。**

- 事前登録 §11 と D229 は着手順序を **「段 A producer → 段 B pilot → 段 C validator/consumer → 段 D 本走」**と定め、
  「D162 は書き換えない。pilot 自身を発火条件を満たす計測にすることで規律をそのまま守る」と書く。
- D162 決定 (10) は機械化の発火条件を (i) 事前登録済み 3 arm 計測の存在、(ii) その計測が環境タグ・
  測定 checkout・pin・attestation を持つこと、(iii) 判定を読む consumer の実 hook の実在、とする。
  **現在成立しているのは (i) だけ**である (唯一の 3 arm 計測 `892042` は環境タグと環境証明を持たない)。
- 一方 D234 の「実装境界」は、gate の機械配線として **producer の投入前検査・受領証への三つ組の必須記録・
  validator の独立再計算・consumer の受理判定・投入 script** を列挙し、そのすべてを
  「producer 実装 wave の責務」と逐語で書く。

**なぜ問題か。** 前者に従えば validator と consumer は pilot の**後**、後者の平明な読みでは**同じ wave**。
親が片方を選ぶのは、決定の非同値な読み替えになる (`DW-S04` が禁じる)。

**選択肢。**

- **(a) D234 の当該列挙を「T-139 全段の完了範囲を示すもので、同一 wave の実装範囲ではない」と限定し、
  段順序を D162 / §11 に従わせる (推奨)。** validator を今実装すると D162 決定 (10) の発火条件 (ii)(iii) を
  満たさないまま機械化することになり、`DW-G04` にも反する。
- (b) D234 の平明な読みを採り、validator と consumer も同じ wave で実装する。
  → D162 決定 (10) を実質 supersede する。発火条件を満たさない機械化を許す先例になる。
- (c) D234 の当該文を削除・改訂する新 D を起こす。

**親の推奨は (a)。**

## Q3. 段 A の記録項目 (受領証 closed schema) を承認するか

**事実。** D229 決定 (7) の直前と事前登録 §11 は、**記録項目の確定を単独の裁定 gate** と定めている
(理由: 記録項目が validator の要求を取りこぼすと pilot をやり直すことになる)。
2026-08-08 の [T-643] は (i) 認可の第一境界と (ii) trust root の 2 問を裁定したが、
**記録項目そのものは裁定していない。**

**提出する案。** 同ディレクトリの `record-items.md`。段 2 の初版に段 3 の敵対検証 2 レンズの
指摘を反映した版であり、初版から次の 5 点が変わっている。

1. 絶対規律 1 の再計算可能性 — 性能 arm に `trace_enabled: false` を必須化し、
   correctness 証拠は独立の build object を持ち、性能 binary との**非同一性を schema 制約**にする。
2. 条件付き制約と参照整合性 — ID の一意性、planned↔actual の双射、`reason_code` ごとの必須 field 分岐。
3. evidence-only の明示 — `outputs` は再実行可能な pointer に限り、verdict や boolean を置ける型を持たない。
   加えて、消費側が種別・returncode・reason_code・単独性を受理条件の入力に使ったら落ちる否定検査を必須にする。
4. 失敗投入を raw に残す authority — qsub 前の durable intent と、job 側 preflight reject の collector を
   同じ実装単位に含める (これが無いと事前登録 §13 の否定検査 1 が閉じない)。
5. 認可を受領証の**実 writer** に置く — 初版は qsub 関数にだけ binding を必須化しており、
   受領証を永続化する関数は無認可だった。T-643 (i) の「認可の第一境界は producer 側」に照らして是正した。

**選択肢:** (a) 承認する / (b) 修正を指示する / (c) 追補 A の確定後に併せて裁定する。

**親の推奨は (c)** — 記録項目のうち `arms.*.compile` と `planned_execution` の具体は
追補 A の `a07` / `a08` / `a09` に依存するため、追補 A と同時に見た方が取りこぼしが減る。
ただし (a) でも進める形にはなっている。

## Q4. 次の producer wave の vertical slice をどこで切るか

**事実。** 本 wave は測定本体を書けなかった。PBS 測定本体は追補 A の `a01`〜`a09`
(時間予算・待機・driver 引数・arm identity・schedule seed) に依存する。
両レンズが独立に「前置・sink・registry だけを land して『producer 実装済み』と数えてはならない」と判定した。

**選択肢。**

- **(a) 追補 A を先に確定し、その後 1 本の vertical slice で producer を実装する (推奨)。**
  slice に含めるもの = pilot 用 PBS 測定本体 / qsub 前の durable intent と台帳 /
  job 側 preflight reject の collector / binding を必須化した受領証 writer /
  schema-valid な受領証が end-to-end で 1 本出る正例。
  worklog (305) の [T-139] 次の一手が記録する順序 (「追補 A → producer 実装 → pilot」) と一致する。
- (b) admission resolver だけを先に land する。
  → Q1 が未裁定だと exact-key 集合が決まらず、resolver を完成できない。
- (c) 追補 A と producer を同じ wave でやる。
  → 追補 A は統計設計 (`J` の導出手続き・同時信頼領域・`q`・有意水準) を含み、
  それ自体が独立の裁定を伴う。実装と混ぜると設計が実装都合で歪む。

**親の推奨は (a)。**
