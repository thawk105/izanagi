wave `dev-wave-t1721-noncertifying-a1` が段 4 で止め、ユーザーへ返す判断。

## なぜ返すか

D1028 は承認済みのユーザー裁定であり、親は不採用にしない。本 wave が止めたのは、
**裁定時に見えていなかった事実**が出たためである。`docs/decisions.md` /
`docs/failures.md` / `docs/worklog.md` を全文検索し、この事実がどこにも記録されていないことを
確認した。

D1028 の本文は「型と consumer を同時に作ると、型が実際に昇格不能かを consumer 側で検査できる」と
書いている。**検査した結果が「昇格不能にできない」だった**場合の指示は無い。

## 出た事実

内側で「非認証」「昇格禁止」と明記した campaign lock を、公開情報だけで v2 の封筒に包み直すと、
certified 受入の gate を通る。親と段 3 の子が独立に再現し、同じ epoch 値を得た。
詳細と観測値は同 directory の `README.md`。

閉じられる場所は 2 つあり、どちらも稼働中 wave `dev-wave-t1629-ratification-broker` の所有である。
本 wave は依頼どおり起動時に重複検査を行い、この所有関係を確認した。

## 問 2 — 再開 scope の拡大を認めるか (P1)

段 2 の A/B 分割では端から端まで経路が通らないことが段 3 で判明した。再開 wave は次の 8 項目を
**1 land 単位**にまとめる必要がある。D1028 が要求する「同じ変更単位」の実体が、当初想定より
大きくなる。

1. 非認証成果物型 (鍵・記録・schema・consumer の 4 層)
2. A-1 の campaign config への型の結線
3. 投入器 (submit script + acquisition receipt producer)
4. 新 terminal stage への collector 対応
5. scheduler completion receipt の producer (現在 repo 内に 0 件)
6. materialize の起動手 (現在 呼び手が存在しない)
7. 非認証結果を限定付き観測として読む reader / pointer
8. 波及する凍結 provenance の再生成 (fig4 の validator SHA)

wave の推奨は **認める**。分割すると 1 のあとに休眠 capability が残り、D1028 が却下した型を
そのまま再生産する。

## 問 3 — 昇格不能性の実現手段 (P2)

段 3 は、禁止 2 file を編集するだけでも十分ではないと指摘した。marker を inner identity から
除去して v2 を再生成できるため、**署名された identity 束縛**か、**全 consumer が参照する
改変不能な外部台帳**まで必要になる。

これは D906 が「署名対象に実行器と検査器の bytes を含める」と書いた領域と重なり、
t1629 が構造的限界として記録した面でもある。

wave の推奨は **t1629 の署名 receipt 機構が着地してから、その上で設計する**。
ここで独自の署名機構を新設すると、批准機構が 2 本になる。

**ただし、bytes 級の pin・署名機構の新設は既定で見送りというこれまでの方針と、
ここで署名束縛を要求することは向きが違う。** どちらを採るかはユーザー判断である。

## 問 4 — 既存の恒真 marker をどう扱うか (P2)

`paper_story_a1_paired.py` の campaign config は既に `promotion_prohibited=True` を持ち、
`declared_use_class` も広く使われているが、**どちらも現状 1 つも発火していない**。
probe はこれらの値を保ったまま certified gate を通した。

択は 2 つある。

- (a) 再開 wave で実効化する (推奨)。型の実装と同じ変更単位で、この 2 つを load-bearing にする
- (b) 恒真であることを台帳に記録して据え置く

wave の推奨は **(a)**。恒真な保証を残すことは、過去に D1037 が「何も認証できないので自動的に
成り立ってしまい、承認権限が入った時点で実質的な穴になる」として却下した型と同じである。
