## must-fix

### 1. 母集合規則が一意な manifest を出力しない

- **所見:** 「一意に出力する」「規則を凍結済み」という宣言に対し、bootstrap 集合の exact artifact、proposal 選択関数、予定 attempt 数、source registry、生成器、canonical block id・順序の導出規則が未固定である。さらに「赤形状を持つ iteration が母集合」と「生成失敗・赤の非再現・重複・破損も全 attempt を残す」の関係も定義されていない。manifest が 155 行を超えた場合の選択規則もない。
- **根拠:** §5.1.1 は bootstrap を単に「事前に固定した」とし、block id と順序は manifest 生成時に決めるとしている一方、生成器と完全性 consumer が存在しないことを自認している。
- **成果物影響 1 行:** manifest の受理行・順序・155 pair の集合を生成時に変えられ、台帳へ載る certified receipt、標本 `X`、`A`、p 値、成立判定が変わる。
- **具体的な修正案:** bootstrap/source registry の path・hash、生成器の path・hash、seed、attempt 数、失敗状態への全域写像、block id・順序の純関数を同じ凍結単位へ追加し、再生成 exact equality を母集合セル解除条件にする。

### 2. 非 certified の順位が自己矛盾している

- **所見:** 順位表は `rejected/aborted > missing` とするが、直後に「非 certified 同士は常に tie」と書く。この二つは同時に成立しない。
- **根拠:** on=`rejected`、off=`missing` の block は、順位表なら `X=1`、太字文なら `X=1/2` になる。
- **成果物影響 1 行:** 該当 block 1 件ごとに標本 `A` が最大 `1/(2n)` 変わり、符号検定の非 tie 数、p 値、成立判定、レポート順位が変わる。
- **具体的な修正案:** 「`rejected` と `aborted` だけが互いに tie。`missing` は両者より下」と書き、全 status pair の順位表を明示する。

### 3. primary の入力型と無効時の出力が全域定義になっていない

- **所見:** `precursor_hash` は単数 field なのに後で「両アームの hash 不一致」を検査する。floor は入力一覧にないのに引数として使う。`treatment_fired`、`arm_contamination`、`protocol_status` の型・許容値もなく、「出力全体を無効」とした後に 4 分類のどれへ写すかがない。
- **根拠:** 「入力は上の値だけ」とする純関数性の宣言と、一覧外の floor 引数が直接矛盾する。単一 hash から両アームの不一致は観測できない。
- **成果物影響 1 行:** 同じ raw receipt 群でも adapter 解釈により pair の受理、tie、`X`、判定不能か protocol violation か、台帳の分類が変わる。
- **具体的な修正案:** arm ごとの hash・status・throughput・三種の protocol field、固定 floor artifact から導出した値を型付き入力として列挙し、各 enum と不正入力の最終分類を全域で固定する。

### 4. 「不成立」分岐が到達不能である

- **所見:** 検定を on 優越方向の片側符号検定としたまま、「同じ p が 0.05 以下かつ `A<0.50`」を不成立条件にしている。逆方向ならその片側 p は大きくなり、条件を満たさない。
- **根拠:** off の勝ちが多数なら on 優越の上側確率は 0.5 より大きくなる。Holm 補正は primary 1 件なのでこの問題を変えない。
- **成果物影響 1 行:** off が明確に優越する結果が「不成立」でなく「判定不能」へ落ち、レポートと判定台帳の値が変わる。
- **具体的な修正案:** on 優越用 `p_on` と off 優越用 `p_off` を別々に定義するか、両側検定と方向を組み合わせ、不成立条件が到達可能になるよう固定する。

### 5. `n=155` は記載した exact test で検出力 0.80 を満たさない許容例がある

- **所見:** tie なしで `P(X=1)=0.60`、`P(X=0)=0.40` は `A=0.60` を満たす許容分布だが、n=155 の片側 exact sign test は棄却境界 89 勝、実 alpha 約 0.03844、検出力約 0.77039 である。
- **根拠:** 正規近似式の算術は 155 で正しいが、本文が明記する exact test の離散性により目標 0.80へ届かない。免責文は事実を開示するが、「目標検出力 0.80」として n を固定する契約とは一致しない。
- **成果物影響 1 行:** 実際には検出力 0.80 未満の設計が n 欄を満たして受理され、最小重要効果が実在しても判定不能になる確率が宣言値より高くなる。
- **具体的な修正案:** 許容される tie 分布全体について exact test の最悪検出力から n を導出するか、0.80 を非拘束の正規近似目安と明記して「目標検出力」という受理条件から外す。

### 6. 将来 pilot 条項が凍結済み n を再び開く

- **所見:** 「pilot を置かない」「分散上限 1/4 と n=155 を凍結」とした直後に、将来 pilot が分散上限を供給してよいとしている。小さい上限を採れば n が変わり、採らなければこの許可は無意味である。
- **根拠:** 同節は項目別の後日凍結を禁じる一方、pilot による n の入力変更を明示的に残している。
- **成果物影響 1 行:** pilot 後に要求 block 数と受理される manifest サイズを縮められ、台帳の標本集合、p 値、成立判定が変わる。
- **具体的な修正案:** 現契約から将来 pilot 文を削除する。導入する場合は結果閲覧前の新しい事前登録で 4 項目すべてを同時に再凍結し、現発効版には遡及適用しない。

### 7. 実装・conformance gate が §6 と admission consumer に接続されていない

- **所見:** §5.1 は実装と conformance consumer が存在するまで発効しないとするが、§6 の前提条件には入っていない。primary セルは既に非 sentinel であり、checker は値の型・意味・参照先・実装を検査しない。
- **根拠:** 文書全体の hash 照合は参照先 bytes の差し替えを防ぐだけで、実装の存在や本文との一致を証明しない。残りの sentinel が将来埋まれば、現 consumer はこの欠落を理由に拒否できない。
- **成果物影響 1 行:** primary adapter が無い、または本文と異なる状態でも admission が開き、手作業の集計から certified 成果物やレポート値を選べる。
- **具体的な修正案:** docs-only で着地するなら primary セルを `未記入` に戻し、実装・conformance consumer の実在時に解除する。参照を今埋めるなら、§6 へ明示条件を追加し、admission consumer が実装 artifact と conformance 結果を検証する変更を必須にする。

### 8. 可変な「現在閉じていないもの」を三箇所へ再掲している

- **所見:** 新設節の「この契約が閉じないこと」は、§7.2 と §10 が管理する可変状態を再掲する。manifest consumer と pair 完全性は既に重複し、primary adapter は逆に §10 へ載っていない。
