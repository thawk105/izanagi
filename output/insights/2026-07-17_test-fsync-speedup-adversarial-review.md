## [major] conftest が /dev/shm を「書けるか」だけで採用し空き容量を見ない — 既定 Docker CI (shm 64MB) で無音 ENOSPC

orchestrator/tests/conftest.py:22 のガードは `os.path.isdir(_SHM) and os.access(_SHM, W_OK|X_OK)` のみで、tmpfs の空き容量 (os.statvfs) を一切見ない。tmpfs の容量は環境で桁違いに変わる: この HPC ノードは /dev/shm=126G だが、Docker コンテナの既定 --shm-size は 64MB。既定 Docker で回す CI では /dev/shm は存在し書けるのでガードを通過し TMPDIR=/dev/shm が選ばれるが、実測でスイートは 1 run で peak ~18MB を書き、run 後 ~13MB を残す。pytest の keep-3 retention により steady state で 3run×~13MB=~39MB が /dev/shm に恒久残留し、その上に次 run の peak ~18MB が乗ると ~57MB となり 64MB 上限に肉薄する (計測: run1=13224KB→run2=26448→run3=39672→run4=39984KB で頭打ち)。さらに TMPDIR はプロセス全体に効き、これを読む製品コード (patchharness.py:244 の git worktree add / build 木、calibrator/runner.py:238 の build dir、s8a_trigger_freq が『数百MB〜GB 級』と自称する trace) が同じ TMPDIR に落ちる。現行スイートはこれらを mock しているため peak が 18MB に収まっているだけで、将来 real trace/build を叩くテストが 1 本入るか、開発者がテストコード import 後に real 生成を回すと GB が RAM に落ちて OOM/ENOSPC になる。ENOSPC は『No space left on device』という誤誘導的エラーで出るため原因追跡が難しく、しかも disk の /tmp なら通っていた。ガードが書込可を確認して安全な顔をしている分だけ罠が深い。修正案: os.statvfs で最低空き (例: 数百MB〜1GB) を確認してから採用、あるいは採用ラインを閾値化する。

**evidence:** orchestrator/tests/conftest.py:22 (`if "TMPDIR" not in os.environ and os.path.isdir(_SHM) and os.access(_SHM, os.W_OK | os.X_OK):` — statvfs/容量チェック皆無、conftest 全 25 行に空き容量判定なし)。実測 (このリポで採取): 全スイート peak /dev/shm 使用 = 17748KB, 単 run 残留 13224KB。4 run 連続で総使用 13224→26448→39672→39984KB (keep-3 で頭打ち、pytest-1/2/3 各 12912KB)。df: このノード /dev/shm=126G だが Docker 既定は 64MB。TMPDIR を読む大容量経路: orchestrator/campaign/patchharness.py:244, orchestrator/calibrator/runner.py:238, orchestrator/campaign/s8a_trigger_freq.py:79 (コメント『trace は TMPDIR 配下 数百MB〜GB 級』)。
