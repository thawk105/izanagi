## 1. 何が問題だったのか

[T-361] / [T-362] の危険 probe controller は、attempt ごとに `racctjob` / `racctreq` を引いて
会計証拠を集める。この 2 command はログインノードで **sudo の権限の壁により恒久的に失敗する**。
本 wave で再実測した (2026-08-06、`-I <request>` 付きでも引数なしでも rc=1、
標準エラーは `sudo: パスワードが必要です`、標準出力は表の見出しだけ)。反映遅延ではない。

D161 の 3 分離により、この欠測は観測を無効にしない。したがって **probe は現に動いており、
壊れているわけではない**。欠けているのは会計側からの独立した裏取りだけである。
残っていた設計判断は 1 点、「racct を捨てて `.e` の会計ブロックを正式な会計証拠にするか」。

## 2. 会計証拠の供給源 — 実測と信頼の階層

| 供給源 | 取得可否 (実測) | 粒度 | その bytes を書ける主体 | 現在の用途 |
|---|---|---|---|---|
| `racctjob` / `racctreq` | **不可** (rc=1、sudo の壁) | job 単位 / request 単位 | scheduler の会計 DB (sudo 経由) | 正式な会計証拠。現在は恒久欠測 |
| `.e` の NQSV 会計ブロック | 可 | request 単位 1 ブロック | **scheduler と job body の共有ストリーム** | 終了原因の証拠、終端実証の第 3 経路 |
| `rbudgetcheck` | **可** (sudo 不要、rc=0) | group 単位 | 予算サービス | 費用ゲート。差分は算出済みだが換算は未確定 |
| `qstat -J -f` | 可 | request 内の job 行 (実行中のみ) | scheduler の直接応答 | 同一性・生死・終端後の不在確認 |
| `qwait` receipt | 可 | request 単位 | scheduler の直接応答 | 観測ゲート、終了原因の前提、終端実証の第 1 経路 |

**この表の核心は 3 列目である。** `.e` は `qsub -e` によって job の標準エラーと scheduler の出力が
同じファイルへ合流する。job body 自身が `>&2` へ書けるため、期待どおりの Request ID を持つ
偽の会計ブロックを、採取される**前**に混ぜられる。manifest 束縛も sha256 も「採取後に bytes が
変わっていない」ことしか示さず、書き手を認証しない。この偽造を弾く行は現行コードに存在しない
(`s4-adjudication.md` R-02)。

## 3. 検討した 4 案と、採らなかった理由

| 案 | 中身 | 受理集合 | 不採用の決め手 |
|---|---|---|---|
| A | racct を正式源に残し、権限の壁を見たら retry を 1 回で打ち切る | **広がる** | 1 回目が権限の壁、2〜5 回目に壊れた record が出る応答列で、現行なら観測無効になるものが有効へ反転する (R-01)。段 3 の 2 レンズが独立に発見 |
| B | `.e` を「非ゲートの request 要約」として正式化する | 不変 | 既存の `.e` 解析がほぼ同じ情報を既に保存しており、新しい保証を 1 つも足さない (R-08 の移行費用だけが増える) |
| C | `.e` + qstat roster + qwait の複合を新しい正式源にする | 名目は不変 | **危険な job が自分の観測を無効化できる** (R-05)。job-writable な bytes を integrity ゲートの producer にすると、危険な job body が Request ID を 1 行足すだけで自分の危険観測を台帳から排除できる。F93 の fail-blind の再発。加えて同じ `.e` を会計ゲートと終端経路の双方で数える二重計上 (R-04) |
| D | 管理者所有の scheduler export receipt を新設する | 設計次第 | 独立性を回復できる唯一の案だが、管理者権限と運用配線を要し、危険 probe 専用 controller には過大。現行の selector へ素直に挿すと既存の失敗を隠す (R-03) |

**`Number of Jobs: N` を N 件の job record と読み替える案は、成立案に数えなかった。**
2-node leg (`t361-flock`, `nodes=2`) の実 artifact を確認したところ、request ブロックを持つ `.e` が
1 個と空の `.e` が 1 個で、`Number of Jobs: 2` という総数の 1 行があるだけだった。
job 単位の会計 record は `.e` に存在しない (R-09)。

## 4. 推奨 — 案 A′

段 2 の案 A から、**取得回数を減らす部分だけを外した**もの。

1. 正式な会計源は racct のまま据え置く。`.e` を会計証拠へ昇格させない。
2. 権限の壁と分類されたときに落とすのは attempt 間の 2 秒待ちだけとし、**5 回の取得自体は行う**。
   R-01 の反例でも現行と同じ最終 snapshot に到達するので受理集合は動かない。
   減るのは固定待ち 16 秒であって、観測の情報量ではない。
3. 必須 command の列挙は据置。存在検査を外すと権限方針の変化を検出できなくなる。
4. 欠測の恒久性は「そのとき観測された分類」であって将来の保証ではないと台帳へ明記する。

**正直に言うと、案 A′ が回復するのは待ち時間 16 秒だけである。** 独立した会計裏取りはゼロのまま
であり、これは現在の権限では証拠回復が原理的に不可能だという事実の反映である (R-11)。
「恒久対応」の成功条件を証拠回復から死荷重削減へ移す判断は、親が勝手に下さずユーザー裁定へ返す。

## 5. どの案を採るにせよ守る不変条件

- **I1** job が書けるストリームから来た bytes を会計 integrity の producer にしない (R-05)。
- **I2** 新しい会計源を既存の snapshot 選択の同じ枠へ挿さない。source 別 integrity を独立させ、
  「旧源が偽 ∧ 新源が真」が必ず観測無効へ倒れることを設計表で示す (R-03)。
- **I3** 同一の artifact / hash を会計ゲートと終端経路の双方で数えない (R-04)。
- **I4** 「受理集合が同じか狭い」は、旧判定器を版固定して保存済み生データへ再適用し、
  `新 authoritative ⇒ 旧 authoritative` を機械検査したときだけ主張する (R-06)。

  の是正は受理集合を縮めるだけなので、次の起票候補として返す。
