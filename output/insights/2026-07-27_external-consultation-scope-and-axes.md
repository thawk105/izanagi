## 1. 確定した方針

以下はユーザー裁定として確定した (裁定の正本は worklog 末尾)。

1. **スコープを Silo ベースに固定する。** 最適化・組み換え・軽い書き換えの範囲でまず成果を
   出す。複数プロトコルから選ばせる問題設定は当面採らない
2. **対極として Shirakami を置く** (Project Tsurugi、arXiv:2303.18142)。選定理由は
   **本プロジェクト主宰者が設計・実装した実装であり内部構造を完全に把握している**こと。
   詳細な含意は §5
3. **テストを価値で二層化する。** 安い検証を進化探索の毎ループで回し、価値の低いものを含む
   全走は良い候補に絞ってから回す
4. **RuleOps を導入する** (§4)
5. **ワークロード入力にヒント引数を追加する** (§6-C)
6. **タスクに優先度を振り、主張に数えない側の配線検証への投資を抑える** (§6-B)
7. **profiler の出力を axis-proposer へ結線する** (§6-C)
8. **lazy 検証は保留。** 「多数ループは安い検証、最後に高い検証」という段構えは既存思想と
   合致しており、正しさゲートを緩める方向 (絶対規律 2) とは区別する

## 2. 知見 — AI 固有の価値をどこに置くか

### 2.1 指摘: パラメータ調整なら従来型探索で足りる

**外部指摘:** 探索対象がパラメータであるうちは、ベイズ最適化や既存の自動チューナで到達できて
しまう。査読で「LLM でなくてよい」と言われる。

これは izanagi が既に自分で発見した結論と一致する。P2-5 は「LLM 誘導探索 vs 全探索」を
**winner-tied set への初到達までの反復数** (= サンプル効率そのもの) で測り、
negative result を得ている (D21 / D29 再校正後):

- 誘導は機械的貪欲を有意に上回らない
- deceptive 構造 (write-heavy) では**貪欲より有意に有害** (A=0.230, exact permutation
  p=2.5×10⁻⁴)。機序は探索順序でなく「自信ある早期停止の負債」

`docs/roadmap.md` §10 は「列挙可能な軸で LLM が機械探索を上回ることを成功条件にすること」を
**明示的にスコープ外**としている。外部指摘は、この既存判断を外から独立に裏書きした。

### 2.2 指摘: LLM を 0 次最適化器 (zero-order optimizer) と見る

**外部指摘:** 数理最適化の 1 次 (勾配 = どちらへ行くか) / 2 次 (ニュートン法 = どれだけ行くか)
に対し、関数形が未知のときの 0 次最適化がある。LLM は「多数の関数の形を事前に知っている」
存在なので、性能の癖を使って探索を導ける。**到達範囲は同じでも到達までの実測回数を減らせる**
可能性がある。

**izanagi の文脈での判定:** この主張は **§2.1 の反証と矛盾しない — ただし条件付きで**。
P2-5 の舞台は Silo の 8 genome = 実質 1 ビットで決まる離散フラグ空間であり、完璧なオラクルでも
削減余地が 2.62 本しかない天井付きの箱庭だった。0 次最適化が意味を持つのは**関数形が未知で
列挙不能な空間**である。

**したがってサンプル効率の主張は、変異軸が列挙不能な水準 (§2.3) に移って初めて成立しうる。**
制御パラメータ空間のままこの主張を掲げると P2-5 の再演になる。この依存関係が本相談の最大の
含意である — 外部からは独立の 3 提案に見えたものが、izanagi の制約下では
**「軸をデータ構造水準へ移す」を土台にしないと他が立たない**という順序を持つ。

### 2.3 指摘: 攻める対象を制御パラメータでなくデータ構造にする 【最重要】

**外部指摘:** 現状の入力 (読み書き比率・abort 率などの指標) を見てフルスクラッチで考えさせる
のは LLM に不利。人間の実装者が腕を見せるのは**データ構造上の最適化を 1 つ挟む**ような
「工夫パート」であり、そこを狙う方が LLM の強みが出る。類例として GPU カーネル最適化
エージェントの operator fusion (複数カーネルを融合して通信量を減らす) が挙げられた。

**izanagi の現行 3 軸との対照:**

| 段 | 軸 | 変異の粒度 | 機械探索への還元可能性 |
|---|---|---|---|
| 4 | backoff | スカラー値 | 高 (1 次元 sweep で尽きる) |
| 5 | sort-strategy | comparator コード片 | 中 (順序の有限集合) |
| 8a | trigger-gating | bool 述語 1 行 | 中 |

**3 軸すべてが「制御の仕方」の水準にあり、「データの持ち方」に踏み込んでいない。**
decisions には既に「還元できる軸は headline 候補にしない (P2-5 既反証型のため失敗条件 (c) を
構造誘発する)」という警告が書かれている。外部指摘は、その警告に対する**具体的な出口**
(ではどこへ hole を開けるのか) を与えた点で新しい。

Silo における候補: write set / read set の格納形式と検証順序、ロック取得の粒度と表現、
検証パスと書き戻しパスの融合。

### 2.4 指摘: ボトルネックを先に特定し 1 点に集中させる

**外部指摘:** 世代ごとに別の箇所をいじっていると改善が積み上がらない。まずボトルネックを
特定し、そこ 1 点に集中して探索させ、良くなる気配が出たらその知識を探索アルゴリズム化する。
「大規模言語モデルが数学の未解決問題を解いた事例も、方針は人間が決め、その構造を満たす
対象の探索を機械が担う分業になっている」。

izanagi には profiler ロールが Phase 2 から存在し、
「cycle がどこに消えているか」を病理として名指しする役割を持つ。**しかしその出力を
axis-proposer の入力に流す配線が主経路に存在しない。** 現行 axis-proposer の入力は
critic 機序帰属の二層射影・stock 抜粋・編集面の地図の 3 点である。既存部品の再結線で
実現できる (§6-C)。

## 3. 知見 — 評価問題の再設計 (劣化版からの登り戻し) 【独立到達】

**外部指摘 (2 名が独立に、別の動機から同じ構造へ到達した):**

- 一方は**評価の観点から**: 現在のコードは既に最適化されているので、AI に改善させる余地が
  薄い。わざと下手な実装 (例: ロック取得にあえてロックマネージャを噛ませる) を用意し、
  そこから既存の最適水準まで登らせる方が、エージェントのやることが増えて筋が良い
- 他方は**学習データの観点から**: 最適化エージェントを作るには (最適でないもの, 最適なもの)
  の対が要る。**最適なコードがあれば、最適でないコードは無限に生成できる**
  (「経験の浅い実装者として振る舞ってこのコードを劣化させてください」を大量に回す)。
  得られた対を few-shot に入れるか学習させると最適化パターンが抽出できる

**同じアイデアの表裏である。**片方は「劣化版を評価の物差しにせよ」、他方は「劣化版を知識源に
せよ」。動機の異なる 2 名が独立に到達した構造は、経験上もっとも筋が良い。

**izanagi への接続:** `patches/` の positive control (既知の答えがある変異) の体系的拡張として
実装できる。現行の positive control は「壊れていることを検出できるか」を検査する単発の変異で
あるのに対し、劣化版の梯子は「**どこまで登り戻せるか**」を連続量として測る。天井問題
(最適化済み Silo には改善余地が薄く、能力測定の解像度が足りない) への直接の回答になる。

**必須の但し書き:** 既知の最適解への復帰は **recovery であって新規 CC の発明ではない**。
`docs/roadmap.md` §1 の研究目標には数えられない。**能力測定 (ability probe) として位置づけを
分けて書く**こと。ここを曖昧にすると、絶対規律 6 が警告する「謳うだけで発火しない保証」と
同型の自己欺瞞になる。

## 4. 知見 — 守りのコストをどう管理するか (RuleOps)

**背景 (izanagi 側の事実):** reward hacking を機械的に塞ぐ検査を足し続けた結果、
テスト 3000 件超・テストコード約 3 万行に対し本体約 1 万行という比率になり、全走時間が
問題になった ([T-128]〜[T-132] で 300 → 69 → 60.8 秒まで短縮、理論下限は単一ノード 46.7 秒)。
守りを足すほど 1 反復が重くなり、外すと既知の reward hack が再発する。

**外部指摘:**

1. **この問題設定自体が研究になる。** 守りのルールが単調増加する現象と、その管理手法。
2. **陳腐化したルールを回収する運用概念 (RuleOps) を提唱する。** GC・メンテナンスの体系。
3. (別案として楽観的な後置検証も提示されたが、**本プロジェクトでは保留**とした —
   §1-8 のとおり、多数ループには安い検証・最終段に高い検証という段構えを採る)

**izanagi の現状:** 失敗台帳 `docs/failures.md`、見送り台帳、変異台帳は存在するが、
**陳腐化した守りを回収する仕組みは無い**。同じ問題は `output/insights/` の肥大にも当てはまる
(価値の低い自動生成レポートが蓄積し、高価値のものが埋もれる)。

**段構えとの関係:** 「多数ループは安い検証、最終段に高い検証」は正しさゲートを緩める話では
ない。絶対規律 2 が禁じるのは**ゲートの通過基準を下げること**であって、**同じ基準へ至る
検査の順序を最適化すること**は禁じていない。ただし「最終段でしか赤にならない検査」を
早い段で省く設計は、その省略が受理集合を変えないことを機械的に示せる場合に限る。

## 5. Shirakami を対極に置くことの含意 【本書で最も重い節】

論文 (arXiv:2303.18142) の要旨から確認した事実:

1. **Shirakami-OCC は Silo を採用している。** つまり Shirakami は Silo の**対極ではなく
   上位集合**である。真に対極なのは多版 view serializability に基づく **Shirakami-LTX** 側
2. 両者は **write preservation と epoch ベースの同期**によって統合されている
3. **論文の設計目標に「動的なプロトコル切り替えを不要にすること」が含まれる**

### 5.1 帰結 (1) — スペクトル補間には既に人間の答えがある

「Silo と対極の中間を発明させる」という構想 (§2.2 の延長) を実行すると、
**Shirakami という人間による解が既に存在する領域**に踏み込むことになる。

これは弱点ではなく、**§3 の劣化版梯子と同型の強力な positive control** である:

> 人間が設計した統合機構 (write preservation + epoch 同期) に、AI は到達できるか。

既知の正解があるので到達判定が客観的にでき、内部構造を完全に把握している実装なので
部分点の設計もできる。**§3 (劣化版) と §5 (Shirakami) は、どちらも「既知の正解までの距離を
測る」という同じ評価設計に乗る。** 新規性の主張はできないが、能力測定の物差しとしては
現在の izanagi が持っていないものである。

### 5.2 帰結 (2) — 先行研究が「切り替えは不要にすべき」と主張している

外部指摘に「ワークロード最適化の色が強くなると切り替え方式に成り下がる」という警告があった。
`docs/phase3-8b-descriptor-design.md` §1 は既に自分でこう書いている:

> selector 実験は、固定された variant 集合から descriptor 条件付きで選択する。これは
> workload-aware selection を検査するにとどまり、**descriptor-conditioned synthesis の証拠には
> 数えない**。

**そこへ、本プロジェクト主宰者自身の先行研究が「動的プロトコル切り替えを不要にする」ことを
設計目標として掲げている、という事実が加わる。** 切り替え器を作ることの価値は、外部評価から
見ても、自分の先行研究の主張から見ても、そして 8b 設計書の自己申告から見ても、低い。

三方向から独立に同じ結論が出た。**8b の selector 側 (床値実測・oracle 実走・認証機構) への
資源配分は、この三点を踏まえて優先度を下げる**べきである (§6-B)。

### 6-B. 資源配分の是正 (裁定 (ii))

**主張に数えない側の配線検証への投資を抑える。** 具体的には 8b selector 側の残作業
(床値実測の前提整備・oracle 実走・認証機構の拡張) の優先度を下げ、§2.3 / §3 / §6-C を上げる。
床値実測そのものは他の候補にも必要な測定土台なので廃止はしない — **順序を下げるのであって
捨てるのではない**。

なお `docs/phase3.md` の現行チェックポイントは既に一度、旧主実験の主張 S を S' へ後退させ、
さらに「S' を Phase 3 全体の中心価値には据えない」と書いている。**同種の後退がもう一度必要
かもしれない**が、これは roadmap 級の判断であり改訂セレモニー
(`docs/roadmap-history/README.md`) の対象である。

### 6-C. ヒント引数と profiler 結線 — 受け口は既に存在する

裁定 5 (ヒント引数) と裁定 7 (profiler 結線) は**同じ受け口に流すべき同型の情報**である
(どちらも「どこを攻めるか」を伝える)。調査の結果、**その受け口は既に実装されていた**:

- `axis-proposer` の入力契約に **`hole_region_directive`** (編集面の地図の領域名 1 つ) が存在し、
  「**directive は領域の指定であって骨格・機序の指定ではない**」と明記されている
- `orchestrator/codex_roles/policy.py` が「編集面の地図に無い領域名は拒否」を機械検査する
- 段 6 の提案ラウンド実験がアーム c4 (位置指定構成) として既に使っている

**すなわち「位置のヒントは許容、方向・値のヒントは禁止」という線引きは、契約として既に
入っている。** 欠けているのは供給側だけである。

**残実装 = profiler の perf 出力から領域名を導出する橋。** 現状の profiler 用ツール
(`orchestrator/campaign/backoff_profile.py`) は `Backoff::backoff` という単一シンボルに固定
された解析しか持たないため、(a) 汎用のホットシンボル抽出、(b) シンボル → ソースファイル
(= 領域名) の写像、(c) 導出根拠と由来の記録、が要る。

**由来の型区別が必須。** 人間が書いたヒントと profiler が導出したヒントは、リーク特性が
まったく違う。人間のヒントは事前知識が答えとして流入する経路になりうる一方、profiler 由来は
機械観測である。8b descriptor が既に `source` を
`campaign_search_config_projection` / `human_declared` で型区別しているので、同じ様式に揃える。
**ヒントあり/なしの対照が取れる形にすること** — 対照がないと「人間が導いたから動いた」と
区別できず、絶対規律 6 が警告する循環に陥る。

## 7. 本書で確認した論点のすれ違い (1 件)

相談中、検証の並列化について**別の問題が同じ語で議論された**:

- **シナリオ間の並列** — 独立な N 本の実験結果それぞれに対しサイクル検出を回す。各グラフが
  独立なので自明に並列化できる (embarrassingly parallel)
- **1 グラフ内の並列** — 単一の依存グラフに対する深さ優先探索を並列化する。難しく、投資に
  値しないという評価が示された

**両者は矛盾しない。**「並列化は不要」という評価は後者に対するものであり、前者はそのまま
実行してよい。izanagi は絶対規律 1 により「正しさ検証 = trace 有効ビルド、性能計測 = trace 無効
ビルド、別ビルド・別 run」を既に分離しているため、**検証 run は性能計測を汚さずに並列化
できる構造になっている**。この区別を丸めて記憶すると、安価に取れる並列度を取り逃す。
