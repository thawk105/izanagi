### 1.1 P-C2 — prepare retry の閉表化

現行では、[s8b_oracle_report.py:283-289](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_report.py:283) が各 `trial-start` から次の `trial-start` 直前までを window にします。そのため、driver が発行する

```text
trial-start(attempt=1)
retry(attempt=2)
trial-start(attempt=2)
...
trial-result(attempt=2)
```

では第1 window の `trial-result` が0件となり、[s8b_oracle_report.py:435-456](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_report.py:435) で赤、さらに [s8b_oracle_report.py:828-859](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_report.py:828) で後続成功も過去 attempt の違反として赤になります。

#### 閉表の厳密な定義

`trial-result` が0件の window `W_i` を正当な `retried` とするのは、以下をすべて満たす場合だけとします。

1. `W_i` の先頭が manifest 行と一致する `trial-start` で、attempt は正規 issuer と同じ `1`。
2. `W_i` 内の `trial-result` は0件。
3. `W_i` 内の `retry` は厳密に1件。
4. retry payload の `schedule_index` は当該 start と一致し、`attempt == current_attempt + 1 == 2`。
5. 物理的に直後の global window `W_{i+1}` が存在する。schedule_index ごとに探索した「次」ではなく、WAL 上で直後の `trial-start` を使う。
6. `W_{i+1}` の `schedule_index / holdout_id / configuration_id` は `W_i` と完全一致し、attempt は `2`。
7. prepare 失敗は evaluate 開始前なので、`W_i` は実質的に `[trial-start, retry]` のみとする。pipeline stage、別 session event、余分な record があれば白にしない。
8. 当該 schedule 行の prepare retry は合計1回だけで、attempt 列は `[1, 2]`。`1→2→3` の連鎖や attempt 2 からの再retryは拒否する。
9. `W_{i+1}` は従来の `_assess_window()` を一切緩めず通し、trial-result、pipeline truth-table、binding、rc 等を通常どおり検査する。

`trial-result` が既にある window はこの特例に入れず、従来どおり `_assess_window()` へ送ります。これにより既存の `test_definitive_red_survives_later_committed_retry` の「確定済み correctness-red は後続成功で上書きしない」契約も残します。

## 3. リスクと縁

- driver の retry は単なる `prepare_fn` 例外全般ではありません。[s8b_oracle_driver.py:460-468](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_driver.py:460) が cause/context chainを辿り、`OSError` または `subprocess.SubprocessError` を含む場合だけ transient とします。
- retry 発行は attempt 1かつ `evaluate_started=False` の例外だけです。[s8b_oracle_driver.py:1110-1217](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_driver.py:1110)。
  - binding identity不一致は `binding-refused` でretryしない。
  - attempt 2の同種失敗も `binding-refused`。
  - evaluate開始後のcleanup例外は deviation後に再送出。
  - `evaluate_fn` 自身の例外は EvalResultへ変換され、prepare retryには入らない。
- retry payload の `attempt=2` は「失敗したattempt」ではなく「次に開始するattempt」です。reportはretryとcurrent startではなく、retryとsuccessor startを照合する必要があります。
- valid retryの第1 windowには pipeline evidence が存在しません。ここを条件に含めないと、result-lessだが部分build済みの不正windowを白扱いしてしまいます。
- completed terminalの全schedule被覆は attempt 2のtrial-resultで満たせます。terminal gate自体を緩める必要はありません。
- 旧WALで `rep_returncodes` がない committed benchは赤になります。migration、推定、manifest legacyによる免除はしません。
- failure outcomeで `bench_done` 自体がない行にはrc検査を課しません。存在しない公式性能標本を5rep成功と主張していないためです。
- non-official経路では新flagのdefaultをFalseにし、run_onceの3-tuple、ScalePoint、既存monkeypatch形を維持します。
- pipelineのdefault WALには新keyを出しません。[layer3_schema.json:12](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/layer3_schema.json:12) はrunsの追加propertyを拒否するため、generic WALへ無条件追加すると既存consumerを壊します。
- report fixtureの正規 `bench_done` を一括更新しないと、成功系・namespace系・terminal系など `_trial(..., "committed")` を使う多数の既存テストが意図せずrc欠落で赤になります。正規fixtureを更新し、欠落専用fixtureだけを意図的に残します。

## 段 3-A: 敵対相談 (レンズ = 正しさ境界)

## 結論

このプランは現状のままでは却下すべきです。P-C2 の「閉表」は result-less window の局所特例に留まり、attempt lifecycle 全体を閉じていません。P-C1(b) も通常の単一 round では機能しますが、再測定 round との対応と WAL 改竄耐性が未証明です。

### 1. result がある window を使えば retry lifecycle を丸ごと迂回できる

(a) 攻撃シナリオ

```text

P_ok(tps=5件, rc=[0,0,0,0,0])
T(0,1, committed)
R(0,2, reason="forged")
S(0,2)
P_ok(tps=攻撃者が採用させたい5件, rc=[0,0,0,0,0])
T(0,2, committed)
campaign-terminal(completed, 全件被覆)
```

第1 window には result があるため、プランどおり `_assess_window()` に送られます。しかし現行 `_assess_window()` は trial-result と pipeline record しか検査せず、retry を一度も読みません。[s8b_oracle_report.py:440](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_report.py:440)

両 attempt は completed となり、attempt を数値順に sort した後、最後の attempt 2 が採用されます。[s8b_oracle_report.py:822](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_report.py:822)

さらに次も白になります。

- `R(0,2)` 自体を削除した二重 attempt
- 単独の `S(0,99) P_ok T(0,99)`。現行検査は非負整数しか要求しない
- 物理順を `attempt 2 → attempt 1` に入れ替えた列。数値 sort が改竄順序を隠す
- result 後に retry を2件置く列。resultful window では retry 件数が見られない

既存 `test_definitive_red_survives_later_committed_retry` は、まさに「result 済み attempt の後に retry」を置きながら row を completed と期待しており、この穴を回帰契約として固定しています。[test_s8b_oracle_report.py:1160](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/tests/test_s8b_oracle_report.py:1160)

(b) 深刻度: **high**

偽 attempt 2 の性能値を正式標本として採用できる、危険側の偽陰性です。

(c) プラン修正

result-less window の helper ではなく、schedule 行ごとの lifecycle DFA を実装すべきです。受理列は厳密に次の二形だけに限定します。

```text
S1 → pipeline → T1
S1 → R(next=2) → S2 → pipeline → T2
```

全 retry をちょうど一度この遷移へ消費し、attempt 2 は正当な result-less attempt 1 の直後にしか存在できないようにします。definitive red は別軸で保持し、`lifecycle_ok=False` と `definitive_red=True` を同時に表現してください。protocol を白にしたまま red を守る設計は不可です。

## 段 3-B: 敵対相談 (レンズ = 整合・実効性)

結論: **このプランはそのまま実装へ渡せない**。P-C2 の閉表が全 `retry` record を閉じておらず、P-C1 の再測定 round と rc 列の結合契約も未確定である。

## 所見

1. **result あり／window 外の `retry` が無検査で、閉表になっていない**

   - (a) 具体根拠: `_trial_windows()` は最初の `trial-start` より前を捨てます（[s8b_oracle_report.py:283](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_report.py:283)）。また `_assess_window()` は `trial-result` と pipeline record だけを集め、`retry` を一度も読みません（[s8b_oracle_report.py:440](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_report.py:440)、[s8b_oracle_report.py:473](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/campaign/s8b_oracle_report.py:473)）。プランどおり result-less helper だけを足すと、次が依然 `completed` になり得ます。

     ```text
     start(1) + committed result(1) + retry(2)
     start(2) + committed result(2)
     ```

     さらに、最初の start より前の孤立 retry も event の型検査しか受けません。既存の definitive-red テスト自身も result 後の retry を第1 windowへ入れ、現在は無視されることを固定しています（[test_s8b_oracle_report.py:1164](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/tests/test_s8b_oracle_report.py:1164)、[test_s8b_oracle_report.py:1175](/home/SFC/tanab/github/izanagi/.claude/worktrees/dev-wave-pc2-pc1b/orchestrator/tests/test_s8b_oracle_report.py:1175)）。

   - (b) 深刻度: **high**

### 1-A. per-row attempt lifecycle DFA (A-1/B-1 採用。局所 helper 案は破棄)

schedule 行ごとに、WAL 上の物理順で次の**二形だけ**を受理する。それ以外は `lifecycle_ok=False`。

```
形1:  S(i,1) → pipeline → T(i,1)
形2:  S(i,1) → R(i, next=2) → S(i,2) → pipeline → T(i,2)
```

強制する条件:

1. attempt 番号は形1 で `{1}`、形2 で `{1,2}` 厳密一致。`S(0,99)` 単独は赤
   (現行は `_base_row`:223 が `item.get("attempt", 1)` のため `_assess_window`:443-445 の
   attempt 照合が**スキップされ通る**。親が実読で確認済み)
2. 物理順と attempt 順が一致すること (数値 sort が改竄順序を隠すのを防ぐ、A-1)
3. 形2 の attempt 1 window は `[trial-start, retry]` **ちょうど 2 record**。pipeline stage record・
   他 session event・余分 record があれば赤
4. retry payload の `schedule_index` が一致し、`attempt == 1 + 1 == 2`
5. attempt 2 の window は WAL 上の**物理的直後**であり、`schedule_index/holdout_id/
   configuration_id` が完全一致
6. attempt 2 は**正当な result-less attempt 1 を直前に持つ場合にのみ**存在できる
   (retry なしの二重 attempt は赤)
7. **全 retry record の全単射消費**: WAL 中の retry を index 化し、正当な (result-less W_i,
   物理直後 W_{i+1}) 対にちょうど一度だけ消費されること。未束縛 retry (resultful window 内・
   最初の trial-start より前・後続 start なし・schedule 外) は赤
8. attempt 2 の window は `_assess_window()` を**一切緩めず**通す

### 1-B. lifecycle と definitive-red の同時表現 (A-1(c) 採用)

  lifecycle 違反の両方。**anti-masking の意図 (緑が赤を隠さない) は a fortiori で保たれる**ことを
  テスト名・docstring に明記する
