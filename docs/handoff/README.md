# docs/handoff/ — セッション引き継ぎ (セッションの WAL)

セッションが突然死・中断しても、次のセッションが生ログを掘らずに続きから再開できるようにするための仕組み。orchestrator の WAL と同じ思想をセッション運用に適用したもの (2026-07-05 導入、経緯は worklog 参照)。

## 運用ルール

- **セッションごとに 1 ファイル**: `<日付>-<タスク短名>.md` (例: `2026-07-05-docs-restructure.md`)。自分のファイル以外に書かない — これで並行セッション間の書き込み衝突を構造的に防ぐ
- **上書き運用・上限 40 行**。追記で育てない (蓄積させないことで読み込みコストを固定する)
- **書く契機はセッション末ではなく節目ごと**: サブタスク完了時・長い処理を待つ前・設計判断の直後。中断はいつ来るか分からない
- **正常終了時は worklog エントリに吸収してファイルを削除する**。したがって「ディレクトリが空 = 全セッション綺麗に終了」「ファイルが残っている = 稼働中か中断」。最終更新が古い「作業中」ファイルは死んだセッションとみなしてよい
- 新セッションの開始手順: このディレクトリを ls し、残っているファイルを全部読む (各 40 行上限なので数百トークンで済む)

## 定型 (ヘッダ 4 行 + 本文 3 項目)

```markdown
# <タスク名>
- 目的: <1 行>
- 状態: 作業中 | 計測中 | 中断
- 最終更新: <日時>
- 基準コミット: <hash> (+ 作業ツリー dirty なら明記)

## 完了した中間成果   (ファイルパス・コミットハッシュつき)
## 未完の作業と次の一手 (具体的に)
## 落とし穴・気づき    (次のセッションが踏みそうなもの)
```

「状態:」の値は上記 3 つに限定する (check_docs.py が「状態:」行の 作業中/計測中 を stale 検出の対象にするため、値は必ずこの行に書く)。

## 宣言板としての利用 (並行セッションの調整)

- **監査セッション**は「基準コミット」に監査対象の commit を明記する。実装セッションのファイルが「作業中」なら、dirty な作業ツリーではなく固定コミットを監査する
- **性能計測に入るセッション**は自分のファイルの「状態:」を「計測中」にする。他セッションは計測開始前にここを一瞥する (pgrep による機械的確認は従来どおり必須 — こちらは宣言による事前回避)
