## 落とし穴 (新セッションが踏みそうなもの)

- **BG bash の timeout 上限は 10 分** — sweep (~50 分/workload) は必ず nohup デタッチで。
  監視は WAL: `grep -c bench_done <campaign>/runs/wal.jsonl` (完了数)、`grep '"stage":"abort"' 同` (失敗)
- **jq はこの機械に無い** (silent 空出力に注意) — WAL は grep/awk で読む
- **guard_bash**: WAL/campaign 系パスと $()/バッククォートの同居は fails-closed 拒否 — 読むだけなら
  grep 単純形で
- **二重起動事故の経緯** (stock 欠測の原因): 最初 run_in_background (10 分 timeout) で起動 →
  TaskStop → nohup 起動 → 「$! が nohup ラッパーの PID で python 本体が別 PID」となり kill 漏れ →
  一時的に 2 プロセス並走、片方の build が巻き添え死。**教訓: 起動は最初から nohup 一発、
  kill 前に `pgrep -af "python3.*s8a_trigger_sweep"` で本体 PID を確認**
- sweep の再開は同コマンド再実行 (WAL replay で評価済み点スキップ、冪等)。ただし abort 記録済みの
  variant は「評価済み」としてスキップされる (stock がこれ) — 再評価は別 trial (remeasure) で
