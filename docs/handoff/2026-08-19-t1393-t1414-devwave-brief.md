## [T-1414] — dispatch 共有機構の orphan-hold 恒久対策 (最重要・要最大限の慎重さ)

**ユーザー裁定 (2026-08-19):** 推奨どおり実装する = **(c) latch 条件自体を見直す**。

**一次資料:** `docs/worklog.md` の entry 695 (2026-08-19、[T-1409] の診断)。原因は
`tools/pegasus/dispatch_compute.py:1948` の `DispatchError("result/log/accounting-grace-expired")`
— scheduler が `END` を報告してから `accounting_grace_s` (既定60秒) 以内に result.json・
stdout/stderrログ・NQSV会計サマリ・compute markerの**全て**が揃わないと発火する。この例外が
`finally`節の`_fresh_qstat_gated_qdel` (同ファイル1195行台) に落ち、そこで打つ**新規**`qstat -f`
が既に消えたジョブを`success-request-absent`と分類、`denied("request-absent")`→
`job_may_remain=True`→`_latch_orphan_hold`(1072行)がholdを作る。

**推奨方針の詳細 (段1 brief・段2プランの出発点):**
「後始末が終わっていない」と判定する条件 (`_fresh_qstat_gated_qdel` 周辺のlatch決定ロジック) を
見直す。**具体的な修正の形は段2 codex プランに起草させる** — 私 (親) は「60秒固定値を延ばす」
「バースト投入間隔を空ける」より「latch条件自体の見直し」の方が原因箇所に近く筋が良いと考えたが、
実際のコード構造 (再試行・grace猶予の入れ方) を見た professional な設計判断は Codex 段2に委ねる。

**最大限の慎重さが要る理由 (段1 brief に明記すること):**
- `tools/pegasus/dispatch_compute.py` は受入判定・変異テストなど、ほぼ全ての重い処理が使う
  共有インフラ。本 wave 実行時点で13並行セッションがこの経路を使用中だった実績がある。
- 段3 敵対相談は最低2レンズ、うち1本は「この変更が他の呼び出しパターン (受入全走のような単発長時間
  dispatch) の挙動を変えないか」を専任で見ること。
- 段6 変異matrixに加え、実機での動作確認 (小さいjobでの実地dispatch) を段6 review内で行うことを
  検討する。
- entry 695 は「未実測」の仮説として「バースト投入パターンで相対的に厳しくなる
  (scheduler側のepilogue/会計書き込みが競合しうる、または新規probe worktreeの共有FS上の可視性
  伝播が遅れうる)」を挙げている。これを裏取りしてから修正方針を確定するとよい。
- memory `mutation-harness-orphan-hold-recovery.md`: 原因は複数種、手動qdelせずqstat内容で
  終端待ち、resume継続中はpegasus-dispatch丸ごとrm -rf厳禁。修正がこの復旧手順自体を壊さないか
  確認すること。
