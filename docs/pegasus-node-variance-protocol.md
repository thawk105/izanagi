# Pegasus ノード間性能差 測定 protocol — 事前登録 ([T-810])

同一 binary・同一 workload を同一 occasion に N ノードへ同時投入し、**ノード間の相対ばらつきを
上限つきで推定する新規測定 protocol** の事前登録である。既存 protocol (calibration certify /
floor / oracle / campaign) の通常運用ではなく、それらとは独立した meta 測定である。

**この文書は走行を許可しない。**投入は §9 の 2 段階の承認関門を通ったときだけ許される
(第 1 段 = builder と生死確認、第 2 段 = 本走)。この文書が land されたこと自体は、
いかなる投入の承認でもない。

## 0. なぜ要るか

`pegasus-runbook.md` の並行投入節が「ノード間の性能差は未測定である」と書いたとおり、
**CC ベンチをノードを変えて測った実測は本 repo に存在しない。**「仕様が同じだから性能も同じ」も
「別ノードだからズレる」も、どちらも測っていない。

登録済み calibration は 2 件あり、**互いに別ノード**である (第 1 世代 = bnode011、
第 2 世代 = bnode048)。同一 CCBench head・同一 workload・同一 thread 数で、noise floor の平均は
それぞれ 3,918,457.8 tps と 3,848,941.0 tps、差は **第 1 世代の平均を分母として 1.774%** である
(第 2 世代を分母にすると 1.806%、両者の中点なら 1.790%)。

**しかしこれをノード間差と読んではならない。**取得は UTC の日付で 19 日 (実経過 18.27 日) 離れており、
実行ファイルの bytes も異なる (§3.1)。node 効果・occasion 効果・binary 効果が完全に交絡している。

差の大小とは別に**識別可能性**の問題がある。処置と node が一対一に対応する配置は、
差がどれだけ小さくても処置差と node 差を推定上分離できない。`hostname` の記録は provenance には
なるが補正量にはならない。本 protocol はこの交絡を、**処置を 1 つに固定して node だけを変える**
ことで断ち切る。

## 1. 目的と estimand

### 1.1 尺度と主推定量

**主尺度は自然対数変換した throughput とする。**対数尺度の標準偏差はそのまま相対ばらつき
(小さい変動では変動係数に一致) であり、**平均 μ を推定せずに相対量が得られる。**
生の throughput 尺度は副次として必ず併記する。

対数尺度のモデルは、**node を変量効果・round (反復の順番) を固定効果とする二元配置**である。
round を固定効果に入れる理由は §5.2 (共通ドリフトを `MS_E` から除く) にある。

```text
z_ir = log y_ir = μ_z + a_i + b_r + e_ir      i = 1..N (node),  r = 1..R (round)
a_i ~ (0, τ²)   変量        b_r  固定 (Σb_r = 0)       e_ir ~ (0, σ_e²)
```

**主推定対象は `τ` (ノード間の相対標準偏差 = ノード CV)** である。

**主結果は片側 95% 上側限界 `τ_U`** とし、次の 1 本の式で定義する。α は 1 箇所にしか使わない。

```text
ν1 = N−1,   ν2 = (N−1)(R−1)
τ_U² = max(0, (MS_A / F_{0.05; ν1, ν2} − MS_E) / R)
τ_L² = max(0, (MS_A / F_{0.95; ν1, ν2} − MS_E) / R)
```

`MS_A` は node 間平均平方、`MS_E` は残差平均平方 (round 効果を除いた後。どちらも対数尺度)。
`τ_U = 0` は「ノード差ゼロ」ではなく推定量の切り捨てであり、そう報告する。

**構成を後から変えてはならない。**成分ごとの上限を掛け合わせる保守的構成、α の配分変更、
μ の不確実性の追加は禁じる。**§4 の assurance はこの式そのものに対して計算してある** —
別構成に替えると §4 の根拠が失効する。

**`κ = σ_a/σ_e` を主推定量にしてはならない。**κ は「ノード差の検出しやすさ」であって運用上の
ノード差ではない。同じ相対ばらつきでも測定が騒がしく `σ_e` が大きければ κ は小さくなるので、
**測定が汚いほど「ノード差は小さい」と結論する逆向きの判定**になる。κ と ICC は測定系の
診断的副次量へ置く。

### 1.2 この測定が答えること・答えないこと

**答えること。**同一 binary・同一 workload・同一 occasion における、確保できたノード集合上の
相対ばらつきの上限。それに基づく §7 の判断。

**答えないこと。**

- Pegasus 全ノードへの母集団推論。ノードは選べず scheduler が割り当てるので、
  対象は「その occasion に割当て可能だった eligible node の交換可能モデル」に限る。
- 安定したノード効果と node×occasion 交互作用の分離。1 occasion では両者の合成しか測れない。
- ノード効果が加法か乗法かの識別。単一 arm では、あるノードの偏差を加法 intercept でも
  乗法 factor でも同じだけ説明できる。
- 一処置一ノードの比較の解禁。どの結果が出ても解禁しない。

### 1.3 T-139 pilot との関係

T-139 pilot は 3 arm (stock / 劣化版 / 候補) を**同一 allocation (= 同一ノード) の中で**測り、
`回復量`・`劣化幅`・`残り` を cluster 内の差として作る。ノード効果の残り方は次のとおりである。

| ノード効果 | 3 つの差 (回復量・劣化幅・残り) | 分母条件が差の形 (`劣化幅 − κ·stock`) | 分母条件が比の形 (`劣化幅/stock − κ`) |
|---|---|---|---|
| 全 arm 共通の**加法** offset `a` | **相殺する** | `(1−κ)·a` が**残る** | **残る** |
| 全 arm 共通の**乗法** scale `q` | `q` 倍される (符号は保存) | `q` 倍される | **相殺する** |
| arm 固有 / node×arm 効果 | 残る | 残る | 残る |

**差が相殺するのは共通加法 offset、比が相殺するのは共通乗法 scale であり、両者は別物である。**
「同一 cluster 内なのでノード効果は相殺する」を、量の形を確かめずに使ってはならない。

本 protocol の出力の用途は §7 に列挙した 2 つだけである。T-139 に関しては、
共通乗法モデル `m_A,j = q_j · m°_A,j` を仮定したときに、cluster 間分散のうちノード起因の成分が
`τ² · E[回復量]²` の程度と書けることを用いた**感度表**に限る。

**禁止する使い方。** pilot の標本共分散へ加算しない (二重計上になる)。臨界値・受理確率・
本走の cluster 数を変えない。補正量として使わない。単一 arm の出力から加法/乗法の loading を
推定しない。感度表の式・入力・上限の取り方は §7 の対応表で固定したものだけを使う。

## 3. 割付けと同時性

### 3.1 同一 binary をどう成立させるか

**既存経路のままでは同一 binary にならない。**登録済み 2 件の実行ファイル hash は異なり、
build 引数の差は 26 要素中 4 要素、そのすべてが job ごとの一時ディレクトリ (`/scr/<job id>`) である。
node-local でビルドすると path が実行ファイルへ焼き込まれ、同一 head でも bytes が変わる。

手順を次に固定する。

1. 測定 job より前に、**専用の builder job を 1 回だけ**走らせる。
2. repo 外の専用 cache root を明示し、§2 の環境契約 hash を渡す。**契約なしの legacy build 経路へ
   落ちることを fail-closed で拒否する。**
3. **build 前**に preimage artifact を固定する。**commit を書いただけでは binary は定まらない** —
   次をすべて literal として含める。
   - CCBench の commit と、**作業木が clean であること**の検査結果 (dirty なら中止)。
   - 展開した source tree の hash (ファイル一覧と各 bytes の hash を畳んだ 1 値)。
   - compiler の**実行ファイル path・その SHA-256・version 文字列**。「gcc-11 系」では足りない。
   - cmake の実行ファイル path と version、module list。
   - **完全な build argv** (共有 build path を含む。§2 の build 定義はその要約である)。
   - 依存 (gflags / glog ほか) の pinned source head と、それぞれの作業木 clean 検査結果。
   - 環境契約 hash。
   builder の再試行は**同一 preimage に限り**最大 2 回。preimage を 1 field でも変えたら
   別 protocol の実行として扱い、本文書の事前登録は無効になる。
4. 完成した実行ファイルの完全 SHA-256、build preimage、completion manifest を protocol manifest へ固定する。
5. bytes を repo 外の read-only な binary store へ公開する。
6. **測定 job は build しない。**store から各ノードの一時領域へ byte copy する。
7. 各ノードで、copy 前・copy 後・測定後の 3 点で SHA-256 を照合する。
8. **bytes だけで同一性を主張しない。**依存 library の名前・解決 path・hash、module list、
   `LD_LIBRARY_PATH`、`/scr` への残存参照の有無を builder と全ノードで記録し、release token に束縛する。
   gflags / glog は静的リンクされる (`BUILD_SHARED_LIBS=OFF`、実行ファイルに内部 symbol を確認済み)
   ので配布は構造的に成立するが、system runtime の同一性は記録で閉じる。
9. trace 記号が存在しないことを全ノードで再検査する (絶対規律 1)。
10. 1 件でも不一致なら、検出の境界に応じて §5.4 の状態へ倒す — release 前なら
    `pre_release_invalid`、release 後かつ `measurement_start` 前なら
    `post_release_pre_measurement_invalid`、`measurement_start` 後なら `incomplete_after_start`。

**既存の calibration certify 経路を流用してはならない。**同経路は attempt を書いたうえ、
受理された成果物を登録先へ**自動 publish** する。使えばそれだけで §6 の非流入が破れる。

### 3.2 何が無作為化され、何がされないか

- **ノードは選べない。**投入 wrapper に host selector は無く、scheduler が割り当てる。
  したがって無作為抽出でも無作為割付けでもない。推論の対象は §1.2 のとおり限定する。
- **無作為化するのは投入順だけ**とし、seed と順列を receipt に残す。
- 処置は 1 つなので、処置とノードの割付けは存在しない (それが本 protocol の要点である)。

### 3.3 別ノードに落ちる保証は無い — 検出で閉じる

1 request が logical host の CPU 48 を占めるため同一ノードへの相乗りは起きにくいが、
キュー設定は専有を保証しない (`Exclusive submit = OFF`)。**汎用の N-job barrier も
完了 verifier も既存実装には無い。**したがって次を必須要件とする。

1. N 本を独立 request として投入し、全 request ID を group manifest へ先に書き出す。
2. 各 job は測定前に、割当て情報・ホスト名・binary hash・preflight 結果を ready receipt に書く。
3. coordinator は**ホスト名の異なり数がちょうど N** であることを検査する。重複・未承認ホスト・
   ホスト同定の不一致が 1 件でもあれば release せず、その attempt を `pre_release_invalid` とする。
4. 全 ready receipt が揃ってから共有 release を発行する。
5. **開始ばらつきはノードの単調時計を突き合わせて測ってはならない。**単調時計は各ホストの
   boot 相対でありノード間に共通の原点を持たない。**coordinator の同一時計上で**、
   release 発行時刻と各 job の測定開始応答の受領時刻を測り、その差を開始ばらつきとする。
   **開始ばらつきの上限は 5 秒**とし、超えたら attempt を `post_release_pre_measurement_invalid`
   とする (release 後の検出なので release 記録は残す。§5.4)。
6. **occasion の共通部分は「キュー投入時刻」ではなく「release 後の測定区間」**とする。
   PBS の開始時刻が揃うとは主張しない。
7. ready が揃わないまま **20 分**で timeout したら測定を開始せず、**取り消し marker を共有**して
   後発 job が単独で測り始めないようにする。各 job は測定直前に取り消しを再確認する。
8. 部分成功を集計に入れない。欠損の扱いは §5.4 に従う。

### 3.4 各ノードの単独性確認と静穏 preflight

既存の attestation probe は hardware 情報の取得であって静穏確認ではない。
load 閾値・競合 process 走査・ホスト照合はそれぞれ別の実装に分散している。
**T-810 専用 wrapper を作り、次を 1 つの閉じた schema に束ねる**ことを必須要件とする。

- CPU 型番・物理コア数・HT・memory・NUMA node 数・cache・周波数 policy。
- キューから得た割当てホストと実ホスト名の一致。
- 競合 process の走査 (自ノードしか見えないので、group 内の相互検出には使わない)。
- **静穏判定: load average (1 分) が 1.0 以下であることを 30 秒間隔で 3 回連続で観測する。
  最大待ち 1200 秒。超過は `pre_release_invalid` (release 前の検出である)。**
- 測定前後の isolation probe、binary hash、依存 manifest、trace 記号の不在。
- 反復ごとの時刻・実効 clock、終了コード、全反復値。

**投入形の固定。**Python interpreter は `python3.10` を明示し、実体と version を検査する
(`python3` との取り違えは既往がある)。`qsub` の `-o` / `-e` は**必ず repo 外の絶対 path**を指定する
(既定のままだと PBS のログが repo 内へ落ち、§6 の非流入が破れる)。作業 root と出力 root も repo 外にする。
preflight が投入 argv をこの正規形と exact に照合する。

## 4. N と R の導出

**先に目的を決めてから数を出す** (絶対規律 4)。数を決めてから理屈を付けない。

### 4.1 固定する設計目標

| 記号 | 値 | 意味 |
|---|---|---|
| `τ*` | **0.6%** | 材料的とみなすノード CV。実測 within-node CV (1.2479%) のおよそ半分へ**保守側に丸めた人間の価値判断**である (厳密な半分は 0.6239%)。運用損失関数から導いた値ではない |
| `α` | 0.05 | 片側。§1.1 の 1 箇所だけで使う |
| assurance | ≥ 0.80 | 真に `τ = 0` のとき `τ_U < τ*` を得る確率 |
| 脱落耐性 | N−1 ノードでも assurance ≥ 0.80 | §5.4 の脱落時解析と対で成立する |
| 反復精度 | per-node SD の相対標準誤差 `1/√(2(R−1))` < 0.25 | `R ≥ 10` |
| **目的関数** | **総測定回数 `N·R` の最小化** | 下記の理由による |

**目的関数に総ノード秒を採らない理由。**総ノード秒は `N·(固定費 P + R·1 反復時間)` で決まるが、
**`P` (静穏 gate・probe・binary 配布・attestation の合計) は本 repo で未計測**である。
未計測量に依存する目的関数は今は評価できない。

**`N = 13, R = 10` は確定であり、生死確認の結果で導き直さない。**生死確認が測る `P` は
将来の別 protocol の設計材料として記録するだけで、本 protocol の N・R・`τ*`・判定規則を
一切変えない。**再導出の余地を残すと、それ自体が事後の自由度になる。**

### 4.2 assurance の計算と解

assurance は **§1.1 の `τ_U` そのもの**に対して、**§1.1 の自由度** (`ν2 = (N−1)(R−1)`) で計算する。
帰無 (`τ = 0`) の下では `MS_A = σ_e² χ²(ν1)/ν1`、`MS_E = σ_e² χ²(ν2)/ν2` (独立) なので、
`P[τ_U < τ*]` を Monte Carlo で直接求めた。計画値の `σ_e` は対数尺度で 0.012479
(実測 within-node CV の大きい方を保守側に採る)。脱落後の列は `N−1` ノードでの終端解析
(`terminal_reduced`、§5.4) に対応する。

**再現条件。**NumPy 2.2.6 の `Generator(PCG64(810))` (= `default_rng(810)`)、40 万 draw、
`MS_A` を先に `chisquare(ν1, draws)/ν1`、続けて `MS_E` を `chisquare(ν2, draws)/ν2` の順で生成し、
どちらも `σ_e²` を掛ける。`τ_U` は §1.1 の式、判定は `τ_U < τ*` の狭義不等号。
この条件での当選数は 338,491 / 400,000 と 323,211 / 400,000 である。
独立に 1000 万 draw で再計算した値 (0.8463 / 0.8077) とも Monte Carlo 誤差の範囲で一致する。
**`Generator` は NumPy の版をまたぐ乱数列の同一性を保証しないので、版を固定して記録する。**

| N | R | 総回数 | assurance | 1 ノード脱落後 | 真に `τ = τ*` のとき反証しない確率 |
|---:|---:|---:|---:|---:|---:|
| **13** | **10** | **130** | **0.8462** | **0.8080** | 0.9536 |
| 11 | 12 | 132 | 0.8521 | 0.8036 | 0.9525 |
| 12 | 11 | 132 | 0.8537 | 0.8115 | 0.9530 |
| 10 | 14 | 140 | 0.8722 | 0.8191 | 0.9521 |
| 12 | 12 | 144 | 0.8898 | 0.8521 | 0.9528 |
| 12 | 10 | 120 | 0.8080 | 0.7618 | — (脱落条件を満たさない) |

**`N = 13, R = 10` を採る。**制約をすべて満たす設計のうち総測定回数が最小 (130) で、
この最小値を与える設計は他に無い。

### 4.3 費用

測定の臨界区間は 13 × 10 × 3.47 秒 ≈ **451 ノード秒**である。総量は 1 job あたりの固定費 `P` に
支配されるが `P` は未計測である (§4.1)。builder job は 1 回で、既存 certify の見積では
依存込みのビルド上限が 1080 秒である。**予算残枠との比較を投入の許可条件とする** —
builder + N job + 生死確認 + 最大 attempt 数までの総量が残枠内のときだけ投入する。
「空きノードがあるから」は本数を足す理由にならない (絶対規律 4)。

## 5. 推定・報告・判定

### 5.1 主結果と副次量

主結果は §1.1 の `τ_U` (および `τ_L`) と点推定 `τ̂` である。点推定だけを結果にしない。
副次量として、生尺度での同一 fit、`κ̂`、ICC、ノード平均の min / max / range、
ノードごとの平均・SD・CV・median・IQR、`MS_A` / `MS_E` / `F` と自由度、§5.2 の drift 診断を出す。
**すべて併記する。診断を見てから主手法を選ばない。**

### 5.2 ドリフトへの備え

F による区間は、正規性・等分散・独立性が成り立つ working model の下でしか正しくない。
**実 record には反復内の下降傾向が既に観測されている** — 第 2 世代の 10 反復は反復番号との相関が
−0.66 (自由度 8 の t で −2.48、両側 5% で有意)、1 反復あたり約 −10,454 tps、初回から最終まで −2.61%。
第 1 世代は −0.30 で有意ではない。lag-1 の系列相関は両者ほぼ 0 なので、
**問題は自己相関ではなく傾きである。**

**ドリフトは結論の向きを歪める。**推定量は `τ̂² = (MS_A − MS_E)/R` の形で `MS_E` を**引く**ので、
全ノードに共通する時間変動が `MS_E` を膨らませると `τ̂²` と `τ_U` を**押し下げる**。
すなわち実在するノード差を見落とす向きに効く。**推定対象が `σ_e` を含まないことは、
推定量が `σ_e` の汚染を受けないことを意味しない。**

したがって次を事前に固定する。

1. **round は順序位置であって時刻ではない。**全ノードで同じ反復順序 `r = 1..R` を実行し、
   `r` 番目どうしを同じ round として扱う。**round ごとの時刻同期は要求しない。**
   実測で観測されているのは**順序位置との関連**である。ただし 1 回の走行では反復番号と
   開始からの経過時間が完全に共変し、2 件の記録は別日・別 binary なので、
   **原因が順序位置なのか壁時計なのかは識別できない。**順序位置で揃える設計はこの
   識別不能を承知した上での選択であり、**壁時計に共通の外乱は吸収されない** (下記 3)。
2. **主モデルに round の固定効果を入れる** (§1.1 の二元配置)。順序位置に共通なドリフトは
   round 効果へ吸収され、`MS_E` から除かれる。§4 の assurance はこの自由度
   `ν2 = (N−1)(R−1)` で計算してある。
3. **壁時計に共通の外乱は吸収されない。**反復ごとの時刻を記録し、round 効果と実時刻の対応を
   診断として報告する。ノードごとに実時刻が大きくずれた場合はその事実を報告に明記する。
4. **ノード固有のドリフトは残る。**ただし node×round 交互作用そのものは、cell あたり 1 観測の
   設計では残差と分離できない (交互作用の自由度が残差の自由度と一致する) ので、**推定しない。**
   代わりに**傾きの不均一性**を診断に使う — これは推定できる (§5.3 行 2)。

### 5.3 結論の対応表 (測定前に固定する。排他かつ網羅)

判定はこの順に評価し、**最初に該当した行で確定する。**

| 順 | 条件 | 結論 |
|---:|---|---|
| 1 | §5.4 の終端状態が `valid` でも `terminal_reduced` でもない | 主推定による結論を出さない (状態名をそのまま報告する) |
| 2 | **傾きの不均一性 gate が発火** (下記) | 「識別力不足・未決」。モデル前提が破れている |
| 3 | `τ_U < τ*` | 「この binary・workload・occasion では、材料的なノード間差を反証した」 |
| 4 | `τ_L > τ*` | 「材料的なノード間差を支持した」 |
| 5 | 上記以外 (等号を含む。`τ_U = τ*`、`τ_L = τ*`、`τ_U ≥ τ* ≥ τ_L` のすべて) | 「識別力不足・未決」 |

**傾きの不均一性 gate (行 2) の定義。**ノード `i` ごとに、対数 throughput を round 番号 `r` へ
最小二乗回帰して傾き `β̂_i` とその標準誤差 `se_i` を得る (各ノード R−2 = 8 自由度)。

```text
S_β = Σ_i (β̂_i − β̄)² / (N−1)        ノード間の傾きの標本分散
V_β = (1/N) Σ_i se_i²                 傾きの標本誤差分散の平均
gate:  S_β > 2 · V_β  なら発火
```

これは cell あたり 1 観測でも**推定できる**量である (交互作用全体ではなく、その線形成分に限る)。
閾値 2 は測定前に固定する。

補足として常に書くこと。`τ̂ = 0` は「ノードは同じ」を意味しない (推定量の切り捨てである)。
単一 arm の結果から加法か乗法かは結論しない。どの結果でも一処置一ノードの比較を解禁しない。
零分散の検定 p 値は副次量に留め、材料性の判定に使わない。

### 5.4 終端状態・欠損・retry

**時系列の境界を 2 つ定義する。**`release` = coordinator が共有 release を発行した時点。
`measurement_start` = そのノードが 1 反復目の計測を開始した時点。

**終端状態は次の 5 つだけで、上から順に評価して最初に該当したものに確定する。**

| 順 | 状態 | 該当条件 | 主推定 | retry |
|---:|---|---|---|---|
| 1 | `pre_release_invalid` | release 前に検出した不成立 — ready receipt が揃わない (20 分 timeout)、ホストの異なり数が N でない、重複・未承認ホスト、copy 前後の binary hash 不一致、静穏判定 (§3.4) 不成立、投入 argv が正規形と不一致、投入前 inventory が不一致 | 出さない | 可 |
| 2 | `post_release_pre_measurement_invalid` | release 後・`measurement_start` 前に検出した不成立 — 開始ばらつきが 5 秒超、取り消し marker 検出後の開始、依存 manifest / module list / trace 記号 / NUMA node 数の不一致 | 出さない | **不可** |
| 3 | `incomplete_after_start` | `measurement_start` 後の不成立 — 完了ホスト数が 11 以下、完了 job の反復欠損、測定後の binary hash 不一致、投入後 inventory の不一致 (非流入違反)、期待ファイル集合または presence matrix の不一致 | 出さない | 不可 |
| 4 | `terminal_reduced` | 完了ホスト数がちょうど 12 (= `N−1`)、かつ**その 12 ノードすべて**が R = 10 反復を欠損なく持ち、かつ状態 1〜3 の他条件をすべて満たす | **12 ノードの完全行列で行う** (§4.2 の脱落後 assurance がこの解析に対応する) | 不可 |
| 5 | `valid` | 完了ホスト数が 13、全 job が R = 10 反復を持ち、全条件成立 | 13 ノードで行う | — |

**整合性条件を「全 job」に課すときの対象は、`terminal_reduced` では完了した 12 job である。**
脱落した 1 job については、脱落の事実と receipt を記録するだけで、整合性条件の評価対象にしない。

**禁じること。**complete-case の継ぎ接ぎ (反復単位の欠損補填)、補完、反復の追加、外れ値除去、
`measurement_start` 後のノード・反復の差し替え、状態の事後変更。

**retry。**`pre_release_invalid` に限り再投入を許し、**最大 attempt 数は 2** とする。
採用する attempt は「投入順で最初に `valid` または `terminal_reduced` に到達したもの」。
**全 attempt をその終端状態つきで報告する。**

## 6. 成果物へ流入させない

### 6.1 機械的に止まる部分と、止まらない部分を分ける

**測定 job のノード上に repo の作業木を置かない。**必要なのは binary と runner と repo 外の
出力 root だけである。repo が存在しなければ repo へは書けない。**これが唯一の構造的防壁**である。

次は**構造的防壁ではない**ので、そう明記して運用する。

- 共有 code の durable root 方針 (既定は repo の `output/` のみを許す) を T-810 専用 root へ
  注入し、repo 全体を forbidden root に指定する。**ただしこれは、その API を呼ぶ経路の
  path 検査にすぎない。**素の `open()`・shell の出力先変更・PBS の標準出力は迂回できる。
  したがってこれは**協調的な allowlist であって能力遮断ではない。**
- 測定 runner の argv allowlist (calibration の certify 系実行を拒否する)。
- 期待ファイル集合の列挙。

**運用上の禁止。**次のいずれにも追加・変更を許さない — 各環境の calibration の attempt /
中間 staging / 登録先、campaign の write-ahead log、freeze の journal、trial registry、
環境契約の静的 registry とその有効化記録。calibration 形式を名乗る JSON、登録・有効化・再開の
handoff、floor / oracle / certification の receipt、campaign の attempt journal、凍結成果物、
proof chain、採択レポートを作らない。

### 6.2 期待集合と失敗時の形

- 成功 attempt の**ファイル集合を exact に列挙**する (group 側と slot 側の双方)。symlink・socket・
  未列挙ファイル・入れ子ディレクトリを禁じる。
- **§5.4 の 5 状態それぞれについて presence matrix を持つ。**下表を骨格とし、
  各行の exact なファイル名一覧は §9 の凍結 artifact で確定する。

| 終端状態 | release 記録 | ノード receipt | 推定結果 |
|---|---|---|---|
| `pre_release_invalid` | **禁止** | 到達したノードの分だけ必須 | 禁止 |
| `post_release_pre_measurement_invalid` | **必須** | 全ノード必須 | 禁止 |
| `incomplete_after_start` | 必須 | 全ノード必須 | 禁止 |
| `terminal_reduced` | 必須 | 完了 12 + 脱落 1 の記録 | **必須** |
| `valid` | 必須 | 全 13 必須 | 必須 |

- 失敗時も、実在する標準出力・標準エラー・投入 receipt・ノード receipt を削除しない。
- 集合検査の失敗は性能結果と独立に protocol 失敗とし、§5.4 の該当状態へ倒す。

### 6.3 検出 — 単一の fail-closed validator

投入前と投入後に**同一の validator** を走らせ、不一致なら性能数値が完全でも結論を出さない。
この validator の存在と合格は §9 の承認条件である。

- repository の状態と追跡ファイルの hash。**filesystem を歩いて gitignore された未追跡ファイルも
  走査する** — 既存の repo 走査は ignored file を除外するので、それだけでは漏れる。
- §6.1 の禁止領域すべての inventory (path・size・hash・mtime)。
- 凍結 manifest の全 member の hash。**凍結 manifest は列挙済み path しか見ないので、
  新規ファイルの検出には使えない** — 上記の filesystem 走査で閉じる。
- calibration ディレクトリを wildcard で走査する consumer が実在するため、
  その走査対象の名前空間を明示的に deny する。
- 実行された executable と argv の allowlist 照合。

## 7. 出力が変えてよい判断

結論 (§5.3) ごとに、許可される下流判断を次に固定する。**結果を見て用途を選ばない。**

| §5.3 の結論 | job 間で性能値を比較する fan-out | T-139 感度表 |
|---|---|---|
| 材料的なノード間差を**反証**した | 既存条件 (protocol が node を block / randomization 因子として定義し、推定量と集約手順を固定していること) を満たす比較に限り許可する。**条件そのものは緩めない** | `τ_U` を上限として、cluster 間分散のうちノード起因の割合の上限を報告してよい |
| 材料的なノード間差を**支持**した | 許可しない。job 間比較は引き続き禁止する | 同上 (`τ_U` を上限として使う) |
| 識別力不足・未決 | 許可しない (未測定と同じ扱い) | 感度表を作らない |
| 終端状態が `pre_release_invalid` / `post_release_pre_measurement_invalid` / `incomplete_after_start` のいずれか | 何も変えない | 何も変えない |

感度表の入力は `τ_U` (点推定ではなく上限) と pilot 自身の点推定とし、分母は pilot の
cluster 間分散とする。共通乗法モデルを仮定したことを表の中に明記する。

**変えてはならないもの。**certified な選択結果、材料レポート、proof chain、凍結 bytes、
受理集合、環境契約の世代、既存 protocol の schedule と判定、pilot の推定量と臨界値と cluster 数。

## 8. 生死確認 (本走の前に 1 回)

`N = 2, R = 2` の生死確認だけを先に行う。確認するのは仕組みの生死と `P` の実測だけである —
共有 build の作成と公開、2 job が別ノードに落ちること (と重複の検出)、ready barrier と
coordinator 側の開始ばらつき測定、取り消し marker、bytes copy と前後照合、単独性と静穏の記録、
repo 外の期待集合と §6.3 の validator、失敗 receipt が閉じた schema で終端すること。

**性能値を見て閾値・`τ*`・結論規則を調整しない。**生死確認の値は本走と併合しない。
`P` の実測値は将来の別 protocol の材料として記録するだけで、本 protocol の N・R を変えない
(§4.1)。生死確認で仕組みが動かなければ、直すのは実装であって設計値ではない。

## 10. 未解決 (この設計では閉じない)

- **1 occasion では安定したノード効果と node×occasion 交互作用を分離できない。**scheduler 任せの
  2 回目を足しても、同じホストが再び割り当たる保証が無いので解消しない。分離が要るなら
  ホストを指定した複数 occasion の別 protocol が要る (可否は未確認)。
- **単一 arm では加法/乗法を識別できない。**T-139 への機構的な外挿が要るなら、
  同一ノード内で 2 構成を釣り合った順序で測る副次設計を別途事前登録する必要がある。
- 大量投入が fair-share でどう扱われるか (自分の後続 request の優先度が下がるか) は未測定である。
- 1 job あたりの固定費 `P` は未計測である (§4.1、生死確認で実測する)。
