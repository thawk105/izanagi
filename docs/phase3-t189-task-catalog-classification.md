# T-189 作業カタログ — task type 分類基準 (公開版 `t189-task-type/v1`)

`docs/phase3-t189-model-routing-preregistration.md` (以下「正本」) §6.2 が要求する
task type 4 層への分類の**判断規則と、その判断に使った根拠の所在**を公開する文書である。

**この文書は「誰がやり直しても同じ判断へ到達する」ことを保証しない。**
§4 の判定条件は主目的の解釈を必要とし、解釈は割れうる (§8 の限界 3、および
2026-08-23 の段6 レビューが実際に 4 件の判断へ異議を出した事実を §8 に記録してある)。
本文書が保証するのは、**どの規則を適用し、どの一次資料のどこを見て、なぜそう判断したかが
1 行ごとに残っており、第三者が同じ資料を開いて異議を申し立てられる**ことだけである。

分類結果の実体は `output/t189-routing-preregistration/task-type-classification-v1.json`。
本文書は判断規則、本文書外の JSON は判断そのもの、という分担にする。

---

## 1. この分類が置かれている条件

- **ユーザー裁定 D674 (2026-08-23)** により、独立分類者 2 名の署名確保は**見送る**。
  代わりに**分類基準を公開したうえで自前分類し、段階導入する**。
- したがって本分類に、分類者名・署名・第三者 adjudication・独立性の主張は**存在しない**。
  それらの field を artifact にも置かない。
- 2026-08-12 のユーザー方針 (論文主張に要るのは粗い provenance のみ) により、
  分類のために新しい署名・束縛機構を作らない。

## 2. 分類の単位

**1 wave (= 1 task) につき 1 判断**とする。task-stage (段2 / 段5) ごとに分けない。
同じ wave から生まれた候補行はすべて同じ `task_type` を持つ。

正本 §6.2 に従い、判断対象は **wave の主目的 1 件**である。
副次的に生じた変更 (回帰テストの追加、docs の追随、記録の整理) は主目的にしない。

## 3. 使ってよい資料と、その優先順位

分類は次の資料だけを根拠にする。**model の出力、A/B の結果、候補数、層別の充足状況を
根拠にしてはならない。**

1. **S1 = 当該 wave の worklog エントリ見出し。**
   `docs/worklog.md` および `docs/archive/worklog-*.md` の `## ` 見出しのうち、
   `branch worktree-<wave_id>` を逐語で含むもの。wave が着地したときに書かれた一次資料であり、
   本分類より前に凍結されている。
2. **S2 = 当該 wave の段2 (plan) 投げ文本文。** S1 が存在しない場合にだけ使う。
   receipt の `prompt_sha256` と sha256 が一致する file が正本。
3. **S3 = S2 が「必読事項の射影」として絶対パスで指す、同じ wave の段1 brief。**
   S2 が射影節と手順指示だけで主目的を述べていない場合に使う。
   これも当該 wave が着地した時点で書かれた一次資料であり、本分類より前に凍結されている。
   **S3 を使ったときも `evidence` には S2 (投げ文) の所在と sha256 を書く。**
   S2 は receipt の `prompt_sha256` で機械照合できる唯一の錨であり、
   S3 はその S2 が絶対パスで射影している先だからである (S2 → S3 の到達は決定的)。
   **S3 の所在と、そこで読んだ表題は `rationale` に逐語で書く。**
   これにより、第三者は「S2 を開く → 射影節の絶対パスを辿る → S3 の当該表題を読む」で
   同じ根拠へ到達できる。

S1・S2・S3 のいずれからも主目的を確定できない場合は `unclassified` にする (§6)。

> **S3 は 2026-08-23 の段6 レビューを受けて追加した。** 当初は S1・S2 だけを資料としたが、
> レビュー レンズB が `t755-mocc-trace-execution` を指摘した。同 wave の段2 投げ文は
> 射影節しか持たず `unclassified` になっていたが、射影先の段1 brief の表題が
> 「CPU model 厳密一致バグの修正」であり、主目的は一次資料に明記されていた。
> **これは規則の穴であって、判断の恣意ではない** — 追加したのは「どの資料まで辿るか」であり、
> §4 の層の定義には手を触れていない。とはいえ**基準を対象の一部を見た後に変更した**ことは
> 事実であり、§8 の限界 2 に含める。

## 4. 4 層の判定条件

正本 §6.2 の定義を、判定できる形へ言い直したものである。

### `new-mechanism` (規則 ID `TT-NEW-01`)

主目的が、**新しい実行機構・契約・防壁・経路の追加**、または
**既存契約の受理集合そのものの変更**であるもの。次を含む。

- 新しい gate・validator・防壁を通常運用の経路へ入れる
- 既存の判定が受理していた入力を拒否する (またはその逆) へ変える
- 保管方式・起動経路・予約式など、production の実行機構を置き換える・拡張する

「検査を足す」ことが目的でも、**それが通常運用を遮断する新しい gate なら本層**とする。

### `bug-fix` (規則 ID `TT-BUG-01`)

主目的が、**既存挙動の欠陥の復元**であるもの。次を含む。

- 明示された不具合・バグ・誤発火・誤認・取り違えの修正
- 「効いていなかったものを効かせる」是正
- 既存原則の適用漏れ (未閉包) を閉じる恒久対応

回帰テストの追加を伴っても層は変わらない。

### `check-or-test` (規則 ID `TT-CHECK-01`)

主目的が、**検査・fixture・テスト・変異の追加/強化/整理**であり、
**通常運用を遮断する新しい gate を伴わない**もの。次を含む。

- 既存判定を同型の強い idiom へ書き換える検査強化
- 再現用 fixture の追加、テスト在庫の整理・退役

### `docs` (規則 ID `TT-DOCS-01`)

主目的が **docs のみの変更**であるもの。実行コード・schema・fixture・
機械可読な運用データを変えない。

## 5. tie-break

複数の層が同じ主目的に対して同時に成立する場合にだけ、正本 §6.2 の固定順

> `new-mechanism` > `bug-fix` > `check-or-test` > `docs`

を適用し、artifact の `tie_break_applied` を `true` にする。
**主目的が複数あるように見える場合は tie-break を使わず `unclassified` にする** (§6)。

## 6. `unclassified` にする条件

次のいずれかに当たる wave は、層へ割り当てず `unclassified` とする。

- `TT-UNCLASSIFIED-01`: S1 へ join できず、S2 からも主目的が確定しない
  (投げ文が射影節・手順指示だけで、何を作る wave かを述べていない場合を含む)
- `TT-UNCLASSIFIED-02`: 複合 wave で、主目的が 1 つに定まらない
- `TT-UNCLASSIFIED-03`: T-181 / T-182 / T-189 の設計作業に使われた wave であり、
  正本 §6.1 により held-out 候補から外れる

**候補数を埋めるための再分類をしない** (正本 §6.2 の既存要求)。
`unclassified` が多いことは、分類の失敗ではなく母集合の性質の記録である。

## 7. 追跡可能性 — artifact が保持する項目

`task-type-classification-v1.json` の各行は次を持つ。

| field | 意味 |
|---|---|
| `wave_id` | 分類対象 |
| `task_type` | 4 層のいずれか、または `null` |
| `task_type_status` | `classified` / `unclassified` |
| `rule_id` | 発火した規則 (`TT-NEW-01` 等)。本文書 §4〜§6 の ID |
| `tie_break_applied` | §5 を適用したか |
| `evidence` | 根拠資料の所在。S1 なら repo 相対 path と行番号、S2 なら jobs root 相対 path と sha256 |
| `rationale` | なぜその層だと判断したかの 1 行 |

作業カタログ (`task-catalog-v1.json`) は、この artifact を `wave_id` で join するだけであり、
**分類を推測しない**。artifact に無い wave の行は `unclassified` になる。

## 8. 限界 (解消していない。受容した代償として記録する)

1. **分類者は実験実施者と同一人物である。** D674 が独立分類者 2 名を見送ったため、
   独立性による bias 制御は無い。
2. **本基準の著者は、基準を確定する前に対象コーパスの見出しを見ている。**
   当初は「変更面タグと見出し語の literal 照合」で機械分類する設計だったが、
   実測 (対応の取れた 34 件のうち 24 件が同じタグ `コード+テスト`) で 4 層を判別できないと
   分かり、本方式へ改めた。その過程で見出しを読んでいる。
   **後から基準を自分に有利へ書き換えられないという保証は無く、機械検査もできない。**
3. **主目的の判定には解釈が残る。** 「新機構か、既存欠陥の復元か」は、
   同じ変更を別の言葉で述べれば入れ替わりうる。§4 の条件はその境界を狭めるが、消しはしない。

   **実際に割れた境界を記録する (2026-08-23 の段6 レビュー、レンズB)。**
   レンズB は `T-1455-c12-reachability`・`dev-wave-t1372-oracle-perf-binding`・
   `dev-wave-t1442-c06-reachability` の 3 件について、
   「既知の fail-open・改竄受理の穴を塞いだのだから `bug-fix` であり、
   §5 の tie-break でも `bug-fix` が `check-or-test` に優先する」と主張した。
   **親はこれを採らなかった。** §4 の `check-or-test` が
   「既存判定を同型の強い idiom へ書き換える検査強化」を明示的にこの層へ割り当てており、
   3 件はいずれもその形だからである。production の挙動そのものが誤っていた証拠は
   一次資料に無く、誤っていたのは検査の強さである。
   **ただしこの読みが唯一とは主張しない。** 「弱い検査は既存挙動の欠陥か」という問いに
   §4 は答えを与えておらず、答え方で 3 件の層が動く。
   将来この境界を裁定する場合は `criteria_version` を上げ、旧版の artifact を上書きしない (§9)。
4. 本分類は事前選別 (pre-screen) の候補に対して行ったものであり、
   **held-out task として採用した集合に対する分類ではない。**
   採用集合は、正本 §8 の oracle ledger と §5.3 の replayer 契約が揃うまで確定しない。

## 9. 変更管理

本基準を改訂する場合は `criteria_version` を上げ、旧版で分類した artifact を上書きしない。
**実験の走行開始後は本基準を変更しない** (正本 §13 の「run 開始後は task 除外規則を変更しない」に従う)。
