# Izanagi 作業ログ (worklog)

セッションごとの進捗を時系列で記録する。git 履歴や各正本に入らない協議・異常・持ち越しを束ねる
「作業の索引」であり、commit 内容の再説明はしない。役割分担:

- 設計判断と却下案 → `docs/decisions.md`
- CCBench の構造的事実 → `docs/ccbench-anatomy.md`
- CCBench のバグ等の知見 → `output/insights/`
- タスク分解 → `docs/phaseN.md`
- **このファイル = それらを束ねる日誌 (各セッションの索引)**

## 新規エントリの書式 (D35)

過去エントリは凍結し、次の規約は新規エントリに適用する。

**新規エントリはこのファイルへ直接書かない。** `docs/spool/worklog/` へ fragment として書き、
land が lock 内で fold して本ファイルへ追記する (fragment 文法と fold producer 契約の正本は
`docs/spool/README.md`、**描画済み worklog の読み方と carry 書式の正本は本節**)。
エントリ番号・日付・carry 行 `- [T-NNN] (N)` の N・ローテーションはすべて fold が付ける。
以下の書式規約は、fold が生成する結果と、fragment に書く本文の両方に適用される。

- 本文化するのは、ユーザー承認・協議の決着、棄却 finding (refuted)、未コミット事象・セッション異常と
  救出、エージェント工数、人間判断待ち・持ち越し、次の一手など **git に入り得ない情報だけ**
- commit は「hash + 件名 (+ 位置づけ 1 行)」まで。連続群は「先頭..末尾 (N 本)」で表し、内容を再掲しない
- 監査の finding 全文と裁定は insight / audit JSON に凍結する。worklog はレンズ数、real/refuted 数、
  最重要 1〜3 件、一次資料ポインタの 10〜15 行に留める
- 論文素材になる段落は行頭に「素材:」を付ける。持ち越しは逐語再掲せず carry 行 `- [T-NNN] (N)`
  とする。N は**行内に明示された参照先エントリ番号**であり、実体本文は N を遡って読む。
  fold は、最初の fragment では現行 worklog の末尾エントリ番号を、同一 fold 内の後続 fragment では
  直前に生成したエントリ番号を入れる。**新エントリ番号 - 1 や全履歴の最大値から導出してはならない**
  (エントリ番号には欠番も非単調も起こりうる)。過去エントリの `- [T-NNN] 変わらず ((N) 参照)` は
  凍結した旧書式であり、fold は引き続き解決する
- docs(worklog) だけの commit は prose の body を付けず、件名 + 必須 trailer だけにする

### 次の一手の ID 規約 (D70)

「次の一手」の項目が黙って落ちる経路を塞ぐため、各項目に安定 ID を付け、`tools/check_docs.py` が
保存則を機械検査する。ID は角括弧で囲んだ `T-` + 連番で、**表記は 1 つに正規化する** —
1〜999 は 3 桁ゼロ埋め、1000 以上は先頭ゼロなしで書く。冗長なゼロ埋め (4 桁で 1 を表す等) は
同じ数値の二表記になるため**不正形式として赤にする**。

- **位置**: トップレベル list item (インデント無しの `1. ` または `- `) の**先頭**に置く。
  インデントされた子項目は原子として扱わない — **1 原子 = 1 トップレベル項目 = 1 ID** に平坦化する
  (子項目 `(a)(b)(c)` に原子を詰めると、その分は機械検査の網から外れる)
- **採番**: 現行 worklog (「ローテーション」節より後) + `docs/archive/worklog-*.md` + 見送り台帳に
  現存する有効 ID の最大値 + 1。並行セッションは番号を予約したとみなさず、統合直前に再走査して
  未統合側を振り直す (`landed` = main へ統合された時点)
- **不変性**: 一度 land した ID は変更・再利用しない
- **保存則 (機械検査)**: あるエントリの「次の一手」に現れた ID は、後続エントリのトップレベル項目
  (消化または継続) か、見送り台帳のトップレベル項目 (理由付き見送り) に現れなければ赤になる。
  ローテーション境界 (アーカイブ最新の末尾エントリ → 現行の先頭エントリ) も検査対象
- **この節と決定記録には有効 ID を書かない** (採番母集団と sink の自己汚染を避けるため、
  例示は `T-NNN` のようなプレースホルダで書く)

アーカイブは凍結 (訂正注記のみ追記可)。既存アーカイブの一覧は `docs/archive/README.md`。

- **裁定との整合を確認した。** D678 (着地 5 分以内・判定器を受入経路で使わない) の
  却下節に「判定器を残したまま高速化する」が入っているが、これは

  赤が 1 件でもある wave は着地できない。ただし穴の性質は限定的で、

- **`stale-main` について。** 受入 3 分台でも land が `stale-main` で弾かれる事象が
  他セッションで実測されている。親は連結スクリプト (main 取り込み → 受入 → land を 1 本)

- **子の工数 (receipt 実測、再設計分を含む累計):** codex 子 12 本。

## 2026-08-23 (846) — 散文の裁定が機構で守られず判定器が自動起動していた件を裁定し、並行セッションの実測3件を起票へ回した (裁定記録のみ、branch worktree-rulings-20260823-eleven)

前 fold の直後、並行 10 セッションからの報告で **D678 が散文だけで機構の防壁を持たない**ことが
判明した。裁定と、あわせて回収した実測を記録する。

**裁定** (D690)。自分の変更に起因しない赤で着地に
5 分以上かけない。一瞬で直せるなら直し、難しければ実行対象から外して後続 wave へ送る。
あわせて**判定器の自動起動経路を機構で塞ぐ**。受入の受理を child-green の 1 本に絞り、
赤はそのまま失敗として返す。**実測 = 使わないつもりだった wave が赤になった瞬間に判定器へ入り
29 分を失った** (受入 1 回 = queue 待ち 5 分 26 秒 + テスト本体 5 分 41 秒 + 判定器 約 29 分)。
自動起動経路は独立 2 セッションが実装で確認している。

**rulings 側の失敗を 4 件記録する。すべて同型である。** 本セッションは今日、
(1) 既知赤の除外粒度を「node ID の明示列挙に限る」と締めすぎ、(2) `stale-main` を
「直列化の残骸」と誤読し、(3) 恒久保留の棚卸しへ「原因が理解されているかを軸に」を持ち込み、
(4) 「削除と除外は別物」を一般則として配った。**いずれも裁定の文面に無いことを、趣旨から
導けると思って足した型である。** (1) はユーザーが実測を見て覆し、(2) は並行セッションが
判定述語を独立に読んで着地前に止め、(3)(4) は担当セッションが自分の対象と文面を突き合わせて
撥ねた。**(3) は成長比例コストによる保留 (D335/D451/D463) で対象が壊れておらず実走 20 items 全 PASS、
(4) は緑かつ構文木レベルで完全一致の冗長テストで D99 決定 4 の退役経路に当たる** — どちらも
赤いテストを扱う裁定の射程外だった。中継の権威は文面までであり、趣旨からの拡張は
各担当が撥ねられる形にしておく必要がある。

**oracle の SIGABRT は環境要因ではなく C++ の欠陥だった (仮説を撤回する)。** 本セッションは
「`RLIMIT_AS=512MiB` と hugepage 経路の噛み合わせ」という仮説を複数セッションへ中継したが、
**resource limit を一切かけない素の subprocess で同じ abort が再現する**ことで棄却された。
真因は `sort_swo_oracle` の `_TU_PREFIX` にある `snapshot_corpus()` が
`element.body_.get_val()` を無条件に呼ぶ点で、`WriteElement<Tuple>` の 4 引数 ctor が
`TupleBody body_` を既定構築のまま残すため `HeapObject::view()` の `assert(data_ != nullptr)` が
発火する。`_COMPILE_FLAGS` に `-DNDEBUG` が無く assert が生きている。**呼び手側の事前条件違反で
あり、上流の assert は正しい。** 修理案を当てると corpus × order の 6 組すべてが rc=0 になる。
**発見を遅らせたのは oracle 本体が stderr を DEVNULL へ捨てていた点**で、signal 6 しか見えなかった。
本セッションは仮説を裏取りせず中継した — **中継するなら「棄却できる実験は何か」を添えるべきだった。**

**「テストだけが遅い経路」型が見つかったが、全走への寄与は未確認である。**
`tools/codex_reasoning_ab.py` の `_find_rollout` は、pin 付きで 0.036 秒、pin 無しの cold で
329.75 秒 (実 corpus 5,482 file / 約 5.5 GB の全走査)。**pin 無しの経路自体は production も
使っており死んだ経路ではない** — 遅いのは「実 corpus に対して pin 無しで呼ぶ」組合せだけで、
それをしているのはテスト 1 箇所である。
**ただしこの 330 秒は受入全走の junit には現れていない。** 全 14,467 件の junit では
`codex_reasoning_ab` の 367 件合計が 74.0 秒、同 module の最長単体が 22.77 秒、全体の最長でも
85.46 秒で、**330 秒級の単体は 1 件も存在しない**。cold cache 限定の値か、当該経路が全走では
skip / hold されているか、関数単体の計測かのいずれかである。**rulings は当初これを
「直列総和のうち単一 node が約 6%」と読んで優先度の根拠にしかけたが、全走 junit では
支持されない。** 単発の probe を全走への寄与として読み替えたのが誤りで、
**優先度は全走 junit に実際に現れる所要で測る。**

**通信の異常について続報はない。** 前 fold で記録した 3 件 (偽通達 1 件と harness 通知の破損 2 件)
のほか、稼働 10 セッションへの照会でも同型の受信は出なかった。**「番号付きで

本 fold ではそれが rulings 自身の誤りを 3 回止めた。** なお不在を主張する道具の性質にも注意が要る

**最終節を構造的に必ず落とす**ものだった。不在を言う前に見出しの全列挙を取る。
