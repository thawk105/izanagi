# Izanagi 作業ログ (worklog)

セッションごとの進捗を時系列で記録する。git 履歴や各正本に入らない協議・異常・持ち越しを束ねる
「作業の索引」であり、commit 内容の再説明はしない。役割分担:

- 設計判断と却下案 → `docs/decisions.md`
- CCBench の構造的事実 → `docs/ccbench-anatomy.md`
- CCBench のバグ等の知見 → `output/insights/`
- タスク分解 → `docs/phaseN.md`
- **このファイル = それらを束ねる日誌 (各セッションの索引)**

## 新規エントリの書式 (D35)

過去エントリは凍結し、次の規約は新規エントリに適用する。

**新規エントリはこのファイルへ直接書かない。** `docs/spool/worklog/` へ fragment として書き、
land が lock 内で fold して本ファイルへ追記する (fragment 文法と fold producer 契約の正本は
`docs/spool/README.md`、**描画済み worklog の読み方と carry 書式の正本は本節**)。
エントリ番号・日付・carry 行 `- [T-NNN] (N)` の N・ローテーションはすべて fold が付ける。
以下の書式規約は、fold が生成する結果と、fragment に書く本文の両方に適用される。

- 本文化するのは、ユーザー承認・協議の決着、棄却 finding (refuted)、未コミット事象・セッション異常と
  救出、エージェント工数、人間判断待ち・持ち越し、次の一手など **git に入り得ない情報だけ**
- commit は「hash + 件名 (+ 位置づけ 1 行)」まで。連続群は「先頭..末尾 (N 本)」で表し、内容を再掲しない
- 監査の finding 全文と裁定は insight / audit JSON に凍結する。worklog はレンズ数、real/refuted 数、
  最重要 1〜3 件、一次資料ポインタの 10〜15 行に留める
- 論文素材になる段落は行頭に「素材:」を付ける。持ち越しは逐語再掲せず carry 行 `- [T-NNN] (N)`
  とする。N は**行内に明示された参照先エントリ番号**であり、実体本文は N を遡って読む。
  fold は、最初の fragment では現行 worklog の末尾エントリ番号を、同一 fold 内の後続 fragment では
  直前に生成したエントリ番号を入れる。**新エントリ番号 - 1 や全履歴の最大値から導出してはならない**
  (エントリ番号には欠番も非単調も起こりうる)。過去エントリの `- [T-NNN] 変わらず ((N) 参照)` は
  凍結した旧書式であり、fold は引き続き解決する
- docs(worklog) だけの commit は prose の body を付けず、件名 + 必須 trailer だけにする

### 次の一手の ID 規約 (D70)

「次の一手」の項目が黙って落ちる経路を塞ぐため、各項目に安定 ID を付け、`tools/check_docs.py` が
保存則を機械検査する。ID は角括弧で囲んだ `T-` + 連番で、**表記は 1 つに正規化する** —
1〜999 は 3 桁ゼロ埋め、1000 以上は先頭ゼロなしで書く。冗長なゼロ埋め (4 桁で 1 を表す等) は
同じ数値の二表記になるため**不正形式として赤にする**。

- **位置**: トップレベル list item (インデント無しの `1. ` または `- `) の**先頭**に置く。
  インデントされた子項目は原子として扱わない — **1 原子 = 1 トップレベル項目 = 1 ID** に平坦化する
  (子項目 `(a)(b)(c)` に原子を詰めると、その分は機械検査の網から外れる)
- **採番**: 現行 worklog (「ローテーション」節より後) + `docs/archive/worklog-*.md` + 見送り台帳に
  現存する有効 ID の最大値 + 1。並行セッションは番号を予約したとみなさず、統合直前に再走査して
  未統合側を振り直す (`landed` = main へ統合された時点)
- **不変性**: 一度 land した ID は変更・再利用しない
- **保存則 (機械検査)**: あるエントリの「次の一手」に現れた ID は、後続エントリのトップレベル項目
  (消化または継続) か、見送り台帳のトップレベル項目 (理由付き見送り) に現れなければ赤になる。
  ローテーション境界 (アーカイブ最新の末尾エントリ → 現行の先頭エントリ) も検査対象
- **この節と決定記録には有効 ID を書かない** (採番母集団と sink の自己汚染を避けるため、
  例示は `T-NNN` のようなプレースホルダで書く)

## ローテーション

Phase 境界または現行ファイルの肥大時 (`tools/check_docs.py` の閾値超過が
知らせる) に、過去分を `docs/archive/worklog-<範囲>.md` へ**移動**し、現行ファイルを軽く保つ
(ブート時に読むのは末尾エントリのみ、の運用を軽く保つため。2026-07-05 導入、D35)。
アーカイブは凍結 (訂正注記のみ追記可)。既存アーカイブの一覧は `docs/archive/README.md`。

## 2026-08-24 (876) — 前エントリで記録した裁定 1 件の前提が、着地時点で既に偽だったことを自己検出して訂正する (docs のみ、branch worktree-rulings-20260824-all)

- 直前のエントリで land した裁定 20 件のうち 1 件 (受領証レベルの完全性証明を実害まで作らない)
  について、**親が判断根拠に挙げた「分割は既定で動いていない」が、着地の時点で既に偽だった。**
  訂正は D733。
- **検出の経緯。** land 成功後に採番結果を検算した際、同じ fold 世代に並ぶ別 wave のエントリ題が
  「受入全走の計算ノード分割を Pegasus 既定へ切り替え、既定 K=2 にした」と読めた。該当 decision を
  引くと、`IZANAGI_ACCEPTANCE_SHARDS` 未設定でも受入形の走行を K=2 とする改訂だった。
  **さらに ancestry を測ると、その wave tip は本 wave の `tested_main` の祖先であり、
  同 `tested_main` の `docs/decisions.md` に当該 decision が実在していた** — つまり親は、
  既定が反転した後の main の上で受入を通し、反転前の記述を根拠として land していた。
- **なぜ気づけなかったか。** 収集は local main の worklog に対して行い、その後の land までに
  main を 3 度取り込んだ。**取り込みのたびに base digest の陳腐化は検査したが、
  「裁定本文が根拠にしている事実」が動いていないかは検査していない。** digest 検査は
  「同じ項目が他 wave に書き換えられたか」しか見ず、**別 ID の decision が前提を反転させる型は
  構造的に検出できない。** 本件はその型の実例である。
- **結論は動かさなかった。** ユーザーの裁定は「まだ実害が出ていないなら防がなくてよい」であり、
  実害が未観測である限り趣旨は成立し続ける (失敗台帳の全文検索で該当 0 件のまま)。
  失われたのは「既定で動いていないから費用と危険が釣り合わない」という補強論拠だけである。
  **結論を維持するか否かは親が決めず、当該 2 項をユーザー裁定待ちへ戻した。**
- **本 wave 自身の受入も、この反転後の既定で走っている。** 受領証を得た走行は分割が既定で
  有効な main の上で通っており、`verdict` は `child-green`。**分割の完全性を証明する項目が
  受領証に無いことは、この走行にもそのまま当てはまる。** 裁定の対象が自分の着地経路にも
  掛かっている点は、判断材料として明記しておく。
- 前エントリで「受入の赤の原因は自分の環境差」と書いたのは実験で否定済みで、同エントリ内で
  既に訂正した。最終的に受入は緑で通り land した (`main_before` から fold まで rc=0)。
- **前エントリの land が main を赤にした。親の退行である。** 受入 14832 passed / 0 failed で
  緑の受領証を得たのに、land 後の main で `test_spool_fold.py` の実コーパステストが赤になった。
  **原因は fold が受入の検査対象の外にあること** — fold は land の協調 lock の中で受入の後に走り、
  canonical へ書いた結果は、その land を承認した受入に一度も掛からない。本件では fold が
  「次の一手」を再生成して `[T-139]` の実体を archive から現行エントリへ移し、当該テストが
  literal 固定していた期待値と食い違った。**実コーパスを読むテストなので全 wave の受入を止める。**
  記録は F512。
- **修理は別セッションが先に着地させており、本 wave の修理は捨てた。** 本 wave は provenance の
  規約に従い Codex `role=author` に同型の修理を書かせ、親が焦点走 166 passed で裏取りしたが、
  main を取り込むと同 file が競合し、**main 側に既に 2 commit の修理が着地していた。**
  先着の緑を採り、自分の版は破棄した (churn を避ける)。**Codex 子はテストを実走できておらず
  (`qstat -Q` の権限エラーで子が起動せず rc=16)、「166 passed」は親の焦点走で初めて確かめた** —
  子の総括にある未確認事項をそのまま採らないこと。
- **捨てた版のほうが検出力は高かった**ので、その差は限界として台帳に残した。main 側の形は
  対象 ID を固定したままで、その項の実体が現行 worklog にある間は「carry 鎖を archive まで
  辿る」性質を踏まない。
- **その修理の途中で、自分の検算の被覆不足も 1 件踏んだ。** carry stub には凍結エントリ用の
  第 2 形式 `- [T-NNN] 変わらず ((N) 参照)` があるのに、自作 resolver がこれを知らず stub 自身を
  digest していた。**親は 2 つの ID で検算して一致したことを「規則は正しい」の根拠にしたが、
  その 2 件はどちらも第 2 形式を踏まない鎖だった。** 一致件数だけを見て被覆を数えていない。
  記録は F513。
- **fold 後の tree を検査する経路が無いこと自体は塞いでいない。** fold は決定的なので
  `--dry-run` 出力へ検査を掛ける経路は作れるが、受入の受理条件を変えるため裁定へ送る
  ([T-1600])。
