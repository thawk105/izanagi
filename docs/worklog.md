# Izanagi 作業ログ (worklog)

セッションごとの進捗を時系列で記録する。git 履歴や各正本に入らない協議・異常・持ち越しを束ねる
「作業の索引」であり、commit 内容の再説明はしない。役割分担:

- 設計判断と却下案 → `docs/decisions.md`
- CCBench の構造的事実 → `docs/ccbench-anatomy.md`
- CCBench のバグ等の知見 → `output/insights/`
- タスク分解 → `docs/phaseN.md`
- **このファイル = それらを束ねる日誌 (各セッションの索引)**

## 新規エントリの書式 (D35)

過去エントリは凍結し、次の規約は新規エントリに適用する。

**新規エントリはこのファイルへ直接書かない。** `docs/spool/worklog/` へ fragment として書き、
land が lock 内で fold して本ファイルへ追記する (fragment 文法と fold producer 契約の正本は
`docs/spool/README.md`、**描画済み worklog の読み方と carry 書式の正本は本節**)。
エントリ番号・日付・carry 行 `- [T-NNN] (N)` の N・ローテーションはすべて fold が付ける。
以下の書式規約は、fold が生成する結果と、fragment に書く本文の両方に適用される。

- 本文化するのは、ユーザー承認・協議の決着、棄却 finding (refuted)、未コミット事象・セッション異常と
  救出、エージェント工数、人間判断待ち・持ち越し、次の一手など **git に入り得ない情報だけ**
- commit は「hash + 件名 (+ 位置づけ 1 行)」まで。連続群は「先頭..末尾 (N 本)」で表し、内容を再掲しない
- 監査の finding 全文と裁定は insight / audit JSON に凍結する。worklog はレンズ数、real/refuted 数、
  最重要 1〜3 件、一次資料ポインタの 10〜15 行に留める
- 論文素材になる段落は行頭に「素材:」を付ける。持ち越しは逐語再掲せず carry 行 `- [T-NNN] (N)`
  とする。N は**行内に明示された参照先エントリ番号**であり、実体本文は N を遡って読む。
  fold は、最初の fragment では現行 worklog の末尾エントリ番号を、同一 fold 内の後続 fragment では
  直前に生成したエントリ番号を入れる。**新エントリ番号 - 1 や全履歴の最大値から導出してはならない**
  (エントリ番号には欠番も非単調も起こりうる)。過去エントリの `- [T-NNN] 変わらず ((N) 参照)` は
  凍結した旧書式であり、fold は引き続き解決する
- docs(worklog) だけの commit は prose の body を付けず、件名 + 必須 trailer だけにする

### 次の一手の ID 規約 (D70)

「次の一手」の項目が黙って落ちる経路を塞ぐため、各項目に安定 ID を付け、`tools/check_docs.py` が
保存則を機械検査する。ID は角括弧で囲んだ `T-` + 連番で、**表記は 1 つに正規化する** —
1〜999 は 3 桁ゼロ埋め、1000 以上は先頭ゼロなしで書く。冗長なゼロ埋め (4 桁で 1 を表す等) は
同じ数値の二表記になるため**不正形式として赤にする**。

- **位置**: トップレベル list item (インデント無しの `1. ` または `- `) の**先頭**に置く。
  インデントされた子項目は原子として扱わない — **1 原子 = 1 トップレベル項目 = 1 ID** に平坦化する
  (子項目 `(a)(b)(c)` に原子を詰めると、その分は機械検査の網から外れる)
- **採番**: 現行 worklog (「ローテーション」節より後) + `docs/archive/worklog-*.md` + 見送り台帳に
  現存する有効 ID の最大値 + 1。並行セッションは番号を予約したとみなさず、統合直前に再走査して
  未統合側を振り直す (`landed` = main へ統合された時点)
- **不変性**: 一度 land した ID は変更・再利用しない
- **保存則 (機械検査)**: あるエントリの「次の一手」に現れた ID は、後続エントリのトップレベル項目
  (消化または継続) か、見送り台帳のトップレベル項目 (理由付き見送り) に現れなければ赤になる。
  ローテーション境界 (アーカイブ最新の末尾エントリ → 現行の先頭エントリ) も検査対象
- **この節と決定記録には有効 ID を書かない** (採番母集団と sink の自己汚染を避けるため、
  例示は `T-NNN` のようなプレースホルダで書く)

アーカイブは凍結 (訂正注記のみ追記可)。既存アーカイブの一覧は `docs/archive/README.md`。

## 2026-09-02 (1189) — B-10 正式走のトレースは切り捨てられていなかった — 頭打ちは横軸の取り違えで、所要を決めていたのは試行数でなく commit 数だった (docs + insight、branch worktree-dev-wave-b10-trace-truncation-probe、実装面 0・変異 matrix 免除)

- ユーザー依頼は (1186) が残した「655 万件超で所要が頭打ちになる観察は未確認で、トレース
  切り捨ての可能性がある」の決着である。**本題の実測だけ**とし、仮想リスク向けの gate・検査・
  台帳・一般化の追加は scope 外だと最初に確定していた。実装面の差分は 0 で終わった。

- **判定: トレース側だけで件数が減る切り捨ては起きていない。** B-10 正式走系列 4 campaign の
  verify 反復 287 件すべてが `certified=true` だった。`certified` は「検査器が読んだ committed txn 数
  = CCBench 自身の commit counter」「txid に欠番なし」「取引 frame が宣言どおり閉じている」
  「orphan read なし」を同時に要求する連言なので、検査器自身が 287 回すべてで完全性を表明していた。
  `abort` stage は 0 件で、検査が拒否した走行は 1 件も無い。

- **敵対相談 2 本 (正しさ境界レンズ / 数量的主張の整合レンズ) の所見 14 件を全部 real と裁定した
  (refuted 0)。** 判定の向きは変わらなかったが、書き方の限定が 12 件入った。子が出した数値は
  すべて親が独立に検算して一致した。主なものは次の 3 つ。

  1. **親の数え直しは独立な第二の証拠ではない。** `serializable` verdict が integrity clean を
     要求し、clean が `observed==expected` と `dup_txids==0` を要求するので、WAL 上の C 行数の
     一致は verdict から導ける。確かめられるのは「WAL の投影が判定と食い違っていない」までである。
  2. **判定の射程を限定した。** D295 が明記する非検出限界 (trace と counter は同じ実行体から
     出るので common-mode failure と個数を保存する破損は検出しない) は今回の走行で閉じていない。
     「独立 witness」「切り捨て一般の否定」とは書かない。
  3. **`abort=0` から「異常終了なし」は導けない。** `build_start` 49 / `commit` 47 で、
     予定 294 反復に対し観測 287、**7 反復は実行されずに終わっている**。外側 job の壁時計
     打ち切りによるもので、検査の拒否ではない。その 2 変種は 45 cell に含まれない。

- **親自身の誤りを 2 件記録する。** (a) 655 万件の帯を mu=100 と誤帰属していた。成果物の
  variant_id→point 対応表で確認したところ正しくは **mu=25 の 2 点 (10 反復)** である。
  (b) 最大 commit 数と最大所要を組にして書いていたが、両者は別の反復である。

- **refuted 1: 「所要は取引試行数の関数」。** cell 間で所要を説明するのは commit 数で、
  相関は r=0.9991、試行数とは r=0.4044 だった。両方を入れた回帰では試行数の係数が
  -0.309 マイクロ秒 (実質 0) になる。write-heavy では commit 数が 2.5M 付近で飽和する一方
  試行数は 21M まで伸びるので、試行数を横軸に取ると平らな帯ができる。それが「頭打ち」だった。
  ただしこれは cell 間の予測関係であって機構上の限界費用ではない。**所要は混合区間**で、
  ベンチ本体・トレース書き出し・C 行の数え直し・検査・一時 dir 操作・WAL 書き込みを含む。

- **refuted 2: 「read-heavy の検査対象の合計は write-heavy とほぼ同じ約 2000 万件」。**
  それは試行数の合計で、所要を決めていた量ではない。同じ段落の「commit が 1690 万件」の方が
  正しい。起票元の「約 25.6 マイクロ秒/件」「175 秒」「655 万件」は単一の測定からは再現できず
  (`6.55M x 25.6us = 167.7 秒`で 175 秒と 4.4% ずれる)、近傍の複数行をまとめた読みである。

- **絶対規律 7 に従い、当時の判定は昇格も降格もさせない。** 45 cell の
  `correctness_certified=true` はそのまま維持される。その意味も変わらない — 15 変種 × 6 反復の
  trace 有効走に由来し、同一 point の 3 block が 1 変種の認証を共有する。

- **純増は実測だけである。** 機構は D295 (trace 外 counter による個数の裏取り) と D540
  (末尾欠番 false-green は本番 2 経路で緩和済み) が既に定めていた。誰も数えていなかったのは
  「その機構がこの走行で実際に clean だったか」であり、本 wave はそこだけを埋めた。

- **段 8 の自己改善は 1 件採用した。** 親は着手時に未採番の T 番号を wave slug と branch 名へ
  使ってしまい、commit 前に気づいて worktree ごと作り直した。`title:` は慣行として branch 名を
  含むので、既にある「未採番 ID を `title:` へ書かない」規則へ同じ理由で 1 文を足した。
  新しい機構ではなく既存規則の射程の明確化である。**もう 1 件は不採用とした** — 段 2 子への
  射影で WAL から TSV を作る抽出手順を渡し忘れた件は、DW-O02 が既に義務づけている内容を
  親が守らなかっただけで、手順の欠落ではない。
