# Izanagi 作業ログ (worklog)

セッションごとの進捗を時系列で記録する。git 履歴や各正本に入らない協議・異常・持ち越しを束ねる
「作業の索引」であり、commit 内容の再説明はしない。役割分担:

- 設計判断と却下案 → `docs/decisions.md`
- CCBench の構造的事実 → `docs/ccbench-anatomy.md`
- CCBench のバグ等の知見 → `output/insights/`
- タスク分解 → `docs/phaseN.md`
- **このファイル = それらを束ねる日誌 (各セッションの索引)**

## 新規エントリの書式 (D35)

過去エントリは凍結し、次の規約は新規エントリに適用する。

**新規エントリはこのファイルへ直接書かない。** `docs/spool/worklog/` へ fragment として書き、
land が lock 内で fold して本ファイルへ追記する (形式の正本は `docs/spool/README.md`)。
エントリ番号・日付・`変わらず ((N) 参照)` の N・ローテーションはすべて fold が付ける。
以下の書式規約は、fold が生成する結果と、fragment に書く本文の両方に適用される。

- 本文化するのは、ユーザー承認・協議の決着、棄却 finding (refuted)、未コミット事象・セッション異常と
  救出、エージェント工数、人間判断待ち・持ち越し、次の一手など **git に入り得ない情報だけ**
- commit は「hash + 件名 (+ 位置づけ 1 行)」まで。連続群は「先頭..末尾 (N 本)」で表し、内容を再掲しない
- 監査の finding 全文と裁定は insight / audit JSON に凍結する。worklog はレンズ数、real/refuted 数、
  最重要 1〜3 件、一次資料ポインタの 10〜15 行に留める
- 論文素材になる段落は行頭に「素材:」を付ける。持ち越しは逐語再掲せず「変わらず (前エントリ参照)」
  とする
- docs(worklog) だけの commit は prose の body を付けず、件名 + 必須 trailer だけにする

### 次の一手の ID 規約 (D70)

「次の一手」の項目が黙って落ちる経路を塞ぐため、各項目に安定 ID を付け、`tools/check_docs.py` が
保存則を機械検査する。ID は角括弧で囲んだ `T-` + 連番で、**表記は 1 つに正規化する** —
1〜999 は 3 桁ゼロ埋め、1000 以上は先頭ゼロなしで書く。冗長なゼロ埋め (4 桁で 1 を表す等) は
同じ数値の二表記になるため**不正形式として赤にする**。

- **位置**: トップレベル list item (インデント無しの `1. ` または `- `) の**先頭**に置く。
  インデントされた子項目は原子として扱わない — **1 原子 = 1 トップレベル項目 = 1 ID** に平坦化する
  (子項目 `(a)(b)(c)` に原子を詰めると、その分は機械検査の網から外れる)
- **採番**: 現行 worklog (「ローテーション」節より後) + `docs/archive/worklog-*.md` + 見送り台帳に
  現存する有効 ID の最大値 + 1。並行セッションは番号を予約したとみなさず、統合直前に再走査して
  未統合側を振り直す (`landed` = main へ統合された時点)
- **不変性**: 一度 land した ID は変更・再利用しない
- **保存則 (機械検査)**: あるエントリの「次の一手」に現れた ID は、後続エントリのトップレベル項目
  (消化または継続) か、見送り台帳のトップレベル項目 (理由付き見送り) に現れなければ赤になる。
  ローテーション境界 (アーカイブ最新の末尾エントリ → 現行の先頭エントリ) も検査対象
- **この節と決定記録には有効 ID を書かない** (採番母集団と sink の自己汚染を避けるため、
  例示は `T-NNN` のようなプレースホルダで書く)

## ローテーション

Phase 境界または現行ファイルの肥大時 (`tools/check_docs.py` の閾値超過が
知らせる) に、過去分を `docs/archive/worklog-<範囲>.md` へ**移動**し、現行ファイルを軽く保つ
(ブート時に読むのは末尾エントリのみ、の運用を軽く保つため。2026-07-05 導入、D35)。
アーカイブは凍結 (訂正注記のみ追記可)。既存アーカイブの一覧は `docs/archive/README.md`。

- **段ごとの main 取り込みでは T-389 は解けないことを確認した。** ユーザーの提案 (dev-wave の各段で
  local main を確認し取り込む) は**既に運用規律として存在する** (2026-08-03 の是正、
  「land 直前にまとめない、16 commit 遅れで 3 回止めた」)。取り込み差分を小さく保つ効果は実在するが、
  land の可否を決めるのは `_is_ancestor` による「検査した main が現 main の祖先か」であり、
  **判定に効くのは最後の 1 回の取り込みだけ**である。したがって**受入全走 5 分の窓は同じ幅で
  開いたまま**残る。実際、当該規律が入った後の 2026-08-04 に 6 回のやり直しが記録されている
- **(e) の交差判定を「編集面の非交差」で定義してはならない (ユーザー指摘、採用)。**
  ユーザーの反例: 実装 a / b とそれらを覆うテスト a / b があるとき、**テスト b を変更した commit は
  テスト b を変更していない commit と編集面が重ならないが、テスト結果は赤になりうる** —
  赤の定義そのものが変わったためである。**免除述語は編集面の交差だけでなくテストとの相互作用を
  含めて定義しなければならない。** 一般化すると、編集面が交差しなくても verdict が変わる経路が

     編集面の交差の有無によらず再走が要る (ユーザー指摘の直接形)

     変更面を**同じテストが通る**なら結果は変わりうる (共有 call path、共有 fixture、
     conftest、parametrize)。**ファイル単位の非交差はテスト単位の非交差を含意しない**
  3. **全体集計する制約。** 本 repo に実在する — `check_docs.py` の
     `DEV_WAVE_AGGREGATE_BYTES = 25_200` と `PROVENANCE_FAMILY_BYTES = 9_000` は**族の合計**を見る。
     `spool_fold._assert_active_conservation` の active 集合保存則も全体を見る。
     **各々単独では収まる 2 つの変更が、合算して初めて超える**ため、編集面は完全に非交差でも赤になる。
     [T-359] / [T-386] が個別ファイルではなく合計予算で塞がれた実例がこれにあたる
- **したがって (e) の免除述語は最低でも次の全成立を要求する:** incoming が test / checker /
  fixture / gate 定義に触れないこと、incoming と wave の変更面のテスト閉包が交わらないこと、
  incoming と wave が同一の全体集計制約 (族予算・保存則・閉包検査) に同時に寄与しないこと。
  **それでも免除は保証ではなく近似である** — 共有する不変条件を別々に壊す経路は残る。
  採用するなら**免除の根拠と限界を明記する** (保証していないものを保証すると書かない規律)
- **実測の設計も変わる。** 親は当初「破棄した 5 回の main 差分が wave の面と交差していたかを見れば
  追加計測は要らない」と述べたが、**これは誤り**である。上記 3 種を判定するには**ファイル差分では
  足りず、テスト閉包の写像**が要る。実測は「破棄 5 回のうち、上記 3 条件をすべて満たしたのは何回か」
  を測る形になる
- **予想と撤退条件を先に置く。** 上記の厳しさから**免除率は低い可能性が高い**。実測で低ければ
  **(e) は実装せず**、(d) の緩和と損失データの蓄積に留めて (b) を再検討する。
  免除率が低いこと自体が「窓を閉じる以外に手が無い」の根拠になる

  説明する記述は無い。**主題である staging 回収順序の是正に付随して入った変更**に見える
- **調査 2 — 同族のパターンは存在し、設計文化としては整合する。** 同ファイルの `_dependency` は
  `path.is_symlink()` を `dependency source is unsafe` として拒否する。repo 全体でも symlink は
  **同一 UID の並行 process による差し替え (TOCTOU) の攻撃面**として一貫して扱われている —
  `mkdtemp` 直後の symlink 差し替えで削除経路が解決先を消す件、collector の親 component 検査、
  safe-reader が final component だけでなく親 component まで検査する件。したがって
  「pin した path の実体を差し替えられない」という意図の**推定は妥当**である
- **調査 3 — ただし保護は最終 component だけで部分的である。** 拒否の直後に
  `Path(found).resolve(strict=True)` を呼んでおり、**親ディレクトリの symlink は黙って辿る**。
  「間接参照を許さない」という理屈は最終要素にしか効いていない。safe-reader が親 component まで
  検査しているのと非対称である
- **調査 4 — bytes 差し替えの検出は別経路で既に成立している。** `_sha256` は fd を保持したまま
  `fstat` の before/after を照合し (`st_dev` / `st_ino` / `st_size` / `st_mtime_ns`)、
