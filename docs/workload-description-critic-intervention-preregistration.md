## 1. 主張の形と、主張しないこと

### 1.1 主張しうること

本書の結果は、**backoff の値 1 個を探す数値探索**で、LLM に見せる workload の表示と critic の診断の構成が、探索の結果と
提案の過程にどう対応したかの**限定的な**結果である。LLM が機構を書く空間での「なぜ」には答えない (§9.4・§12 の U5)。

> S1-wh (Silo の backoff 値 1 個の空間、write-heavy の錨) で、P3 登録と同じ予算 (評価数 B = 10、原提案 A ≤ 30、共通の初期点 2 個) の下、
> LLM (K0) の探索系列が選んだ endpoint の score について、[正しい記述と伏せた記述の差 / 正しい記述と入れ替えた記述の差 /
> critic の有無の差] は、[優越 / 退行 / 実用上同等 / 判定不能] だった。分類は、登録した独立・近似正規の仮定の下での同時区間による (§6)。

- 動かすのは、LLM に**明示的に表示する** workload の記述と、critic の LLM による解釈の有無である。LLM が性能・leading indicators
  などの観測から workload を推し量ることは止めず、表示の外に残る露出もある (§3.4)。したがって「伏せた記述」の結果を
  「workload の情報を遮断した効果」と書かず、どの水準も盲検とは呼ばない。
- 入替は rh の表示 1 つだけである。「任意の誤った記述」の効果へ一般化しない。
- 結論は S1-wh と、発効束で固定する model・prompt・構成に限る。

### 1.2 主張しないこと

- **verifier、anomaly の即 reject、構造化された失敗理由の返却の因果効果。** これらは規律 2・3 により全 cell で外さないので、
  それぞれが結果にどれだけ効いたかは本書の設計では切り分けられない。論文には限界として書く。
- LLM 一般・他 model・他の空間・他の workload・未知条件への一般化。
- critic の効果を、critic の役割定義や prompt の特定の文言に帰すこと。critic なしの cell が省くのは critic の呼び出し全体である (§3.2)。
- S1 の結果を、LLM が関数やコードを書く空間 (S3 など) の予測として書くこと。S1 の coder 出力は数値 1 行に限られる (§9.4)。
- 記述と critic の交互作用、各記述水準での critic の効果 (§6 のとおり探索的な記述にとどめる)。
- score に差が無いことを、提案の過程に差が無いことと読むこと (§8)。
- 副 outcome (§8) と人手分類 (§9) の値を、族の分類 (§6) と同じ強さの結論として書くこと。
- token 数・費用の値を金額として書くこと。サブスクリプションで動く CLI が示す費用の値は請求額ではない。

## 2. 課題

- **課題は S1-wh の 1 つだけ** (D2265 項 3 の Q)。protocol Silo、空間 S1 (backoff 値 1..1000 µs)、workload は転移登録 §2.1 の錨 wh
  (読み比率 5、Zipf 0.9、thread 48、操作数 10、blind write、レコード 1,000,000、extime 3 秒)。
- **実際に測る workload は、全 cell で wh である。** 記述の介入は LLM に見せる表示だけを変え、verify・bench・score の引数は変えない。
- 一次資料の「成功・失敗を代表する少数の課題」は、本書では**課題の対比として実現しない**。課題が 1 つだからである。
  結果を見た後に成功例・失敗例の系列を選んで課題に数えることもしない。この欠落は §12 の U4 に書く。
- 留保条件 (転移登録 §2.3) は、記述の入替先・生成・生成のための評価・選択のどれにも使わない。入替先の rh は学習条件の錨であって
  留保条件ではなく、留保条件を参照して選んだものでもない (§3.1)。
- 生成・選択に関わる主体が repo の docs を読めたかを cell ごとに記録する (転移登録 §3.1、P3 登録 §2.3 と同じ)。planner と coder の
  role は tool を持たないので読めない。critic の role と LLM 親 session は読めるので「読めた」と記録する。親と critic には、留保条件と
  その結果を生成・選択に使わない手順 (転移登録 §3.1) を指示文で与える。これは手順上の約束で、構造的な隔離ではない。

## 3. 介入

### 3.1 workload の記述 (3 水準)

現行の K0 で workload の記述が LLM に届く主な経路は次の 3 つである (起草時点の実測。file:line は起草 insight §2)。planner の入力には
workload の記述は無い (planner は性能・leading indicators・whiteboard・初期点と拒否の列・critic 診断を受ける)。

| 経路 | 現行の表示 | 受け手 |
|---|---|---|
| (a) coder の文脈 `leakproof_context` の Measurement Setup 節 (`tools/t2849_llm_round.py` の `render_context`) | `rr5 (write-heavy)` と、レコード数・thread 数・skew・rmw・操作数・extime・rep | coder |
| (b) critic の入力 `operating_point` (同 tool の `cmd_critic`) | `workload`・`rratio` と、(a) と同じ他の field | critic |
| (c) LLM 親 session の prompt (repo 外の親起動器の header・resume・指示文) | `workload: write-heavy` など | LLM 親 (役割へは (a)(b) の形で渡る) |

錨 wh・bal・rh の引数は読み比率だけが違う (転移登録 §2.1)。そこで 3 水準は、**workload 名と読み比率の 2 つだけ**を、3 経路のすべてで
同じ規則で変える。他の field (レコード数・thread 数・skew・rmw・操作数・extime・rep) は全水準で wh の値のまま表示する。

| 水準 | 記号 | workload 名の表示 | 読み比率の表示 |
|---|---|---|---|
| 正しい記述 | C | `write-heavy` | `5` (`rr5`) |
| 伏せた記述 | H | `非開示` | `非開示` (`rr非開示`) |
| 入れ替えた記述 | S | `read-heavy` | `95` (`rr95`) |

- 入替先は錨 rh とし、発効の前に固定する。結果を見て選び直さない。rh を選んだ理由は、錨のうち読み比率の差が最も大きく、表示が
  提案に届いたかを見やすいからである。rh では固定 backoff が害になる既知の記録があり (§11)、**起草者はこの既知の性能地形を見た後に
  rh を選んだ**。
- 留保条件の読み比率 (25・75) や他の留保の水準は、どの水準の表示にも使わない。
- 3 経路と、§3.2 の失敗理由の写しの `workload:` 行の、水準ごとの exact bytes は発効束に写す。

### 3.2 critic (2 水準)

| 水準 | 記号 | 評価の後に行うこと | 次の planner・coder に渡るもの |
|---|---|---|---|
| critic あり | on | 現行 K0 と同じく critic を呼ぶ | 失敗理由の写し (下記) と、critic 診断の 6 field (`k2_critic_diagnosis`、D2155 の射影) |
| critic なし | off | critic を呼ばない | 失敗理由の写し (下記) だけ |

- **失敗理由の写し:** 各評価の後、その系列の verifier と拒否の記録から、現行の critic digest のうち失敗の節 (verify の失敗・liveness・
  差分の検疫。`orchestrator/campaign/p3_s4_loop.py` の `make_critic_digest` が `orchestrator/critic/digest.py` の `render_rejections` で
  描く部分) と同じ出所・同じ描き方の機械的な text を作り、解釈を加えずに **新しい別の key** で planner と coder の両方へ同じ bytes で渡す。
  critic あり・なしの両水準で同じ規則で作る。既存の key (`k2_critic_diagnosis`) に機械の text を入れない。
- この形の推定対象は「失敗理由の写しの上に、critic の LLM による解釈を足すかどうか」である。構造化された失敗理由の返却 (規律 3) は
  どちらの水準でも保たれる。critic ありの水準では、同じ失敗の情報が critic の解釈を通っても届くので、2 水準の差は解釈文の有無に加えて
  情報の重複の有無も含む。
- 現行の K0 では、構造化された失敗理由が planner・coder へ届く経路は critic 診断だけである (whiteboard は抽象的な `fail`、初期点と
  投入前の拒否の列 `t2849_prior_observations` は拒否の分類名だけ)。したがって critic を単に外すと規律 3 に反する。写しはそれを避ける。
- digest の失敗の節は、候補ごとに実際の `workload:` 行を描きうる (`orchestrator/critic/digest.py` の `render_rejections`)。写しでは
  この行だけを §3.1 の表示規則に従わせ、失敗の種類・依存・分類などの内容は変えない。critic が読む digest の file は変えない (§3.4)。
- 失敗が無い評価 (certified・品質正常) では、写しは「失敗なし」を表す固定の値にする。欠測を 0 や差なしとして書かない。
- 現行の harness・巡 tool は評価 2 以降に critic 診断を要求する。critic なしの水準には実装の変更が要る (§13)。

### 3.3 cell と配置

主案は 3 × 2 の 6 cell 要因配置 (C-on・C-off・H-on・H-off・S-on・S-off) である。費用を抑える択一として、4 cell 案
(C-on・H-on・S-on・C-off) を §7 に並べる。4 cell 案では critic の効果は正しい記述の下だけで見ることになり、記述と critic の
組み合わせは見えない。4 cell 案と 6 cell 案の対比は推定対象が違う (§6) ので、精度を同列に比べない。

### 3.4 この介入で操作できないもの (残る露出と限界)

- **観測からの推測:** planner は current_perf・leading indicators を受け、coder は baseline を受ける。LLM がこれらから workload を
  推し量ることは止めない。
- **表示の外に残る露出:** 起草時点で、次の面に実際の workload が残りうる — LLM 親の prompt の ledger root・materials root の path、
  親が役割を呼ぶときの説明ラベル (現行の指示文は workload 名を入れる)、critic 入力の slot・digest・系列台帳の path、critic が読む
  digest の file の `workload:` 行と系列台帳の header。発効束には、各水準で LLM に実際に見える表示 (path と説明ラベルを含む) を
  全て列挙する。変えられる面 (説明ラベルなど) は §3.1 の表示規則に従わせ、変えない面は残る露出として記録する。
- **critic の読取:** critic の role は file を読む道具を持つので、渡した入力以外から実際の workload を読みうる。critic が他の file を
  読んだかは critic の逐語出力と読取の記録で事後に確かめ、cell ごとに件数を報告する。遮断の機構は足さない。
- **LLM 親:** 親 session も filesystem を読める。親は役割の入力を機械的に射影するだけで、自分の context で知ったことを足さない
  (比較基盤 §4.2 の手順上の約束。機械的な遮断ではない)。
- **表示と観測の食い違い:** S 水準では、表示 (read-heavy) と観測 (write-heavy の性能・abort の傾向) が食い違う。食い違いに役割が
  気づいて言及したかは §9 の付記で記録する。

## 5. endpoint と score

- endpoint は P3 登録 §6.1 (比較基盤 §4.6) の規則による B = 10 時点の endpoint で、N_eval = 5 の fresh session の median を score とする。
- 欠測・fallback・判定不能の優先は P3 登録 §6.1 と比較基盤 §4.6 のとおり。anomaly による endpoint の資格の喪失は全系列へ波及させる。
- 系列開始 stock・block stock・参照点の測定値は、どの cell の生成器にも渡さない (R0)。

## 6. 族・推定量・分類

- **対比 (6 cell 案):** block b ごとに、x_{cell,b} = ln score として
  - D_H,b = ½[(x_{C-on} − x_{H-on}) + (x_{C-off} − x_{H-off})] (正しい記述 − 伏せた記述、critic 水準で平均)
  - D_S,b = ½[(x_{C-on} − x_{S-on}) + (x_{C-off} − x_{S-off})] (正しい記述 − 入れ替えた記述、critic 水準で平均)
  - K_b = ⅓[(x_{C-on} − x_{C-off}) + (x_{H-on} − x_{H-off}) + (x_{S-on} − x_{S-off})] (critic あり − なし、記述水準で平均)
- **対比 (4 cell 案):** D_H,b = x_{C-on} − x_{H-on}、D_S,b = x_{C-on} − x_{S-on}、K_b = x_{C-on} − x_{C-off}。
  6 cell 案の周辺の平均とは推定対象が違う (4 cell 案の K は正しい記述の下での critic の差だけ)。
- **推定量と区間:** 各対比の block 平均 d̄ と標本標準偏差 s_d を使い、族 M = 3 の Bonferroni 両側同時区間
  d̄ ± t(1 − 0.025/3, n − 1) × s_d / √n を作る。仮定は block 間の独立と近似的な正規性で、検査しない (P3 登録 §7 と同じ限界)。
- **同等幅と分類:** δ = ln(1.03) (P3 登録 §7 と同じ値)。区間 [L, U] で、優越 L > δ、退行 U < −δ、実用上同等 −δ < L かつ U < δ、
  それ以外は判定不能。優越・退行の向きは「正しい記述の側 / critic ありの側が高い」を正とする。結果を見た後に δ を広げない。
- **資格:** 対比に入る cell のすべてで、予定した n block のすべての score が得られた場合だけ分類する。score の欠測を含む block が
  1 つでもあれば、その対比は判定不能とし、欠測の件数と理由、残った block の d̄ と無補正の 95% 区間を記述として添える。
- **交互作用 (探索的):** 6 cell 案の対比は周辺の平均である。記述の効果が critic の水準で違う (交互作用がある) と、周辺の平均は
  片方の水準の効果を表さず、逆向きの効果は平均で打ち消し合いうる。交互作用と、各記述水準での critic の効果は**探索的な記述**とし、
  確認的な主張をしない。cell ごとの単純な差 (記述を 1 つ変える 6 対と critic を変える 3 対) を無補正の記述として必ず添え、
  周辺の対比だけで「各記述水準での critic の効果」を断定しない。交互作用の検定はしない。
- **分類不能も正規の結果**として報告する。n は結果を見て増減しない。
- 族に入らない量 (stock 比、参照点比、副 outcome、人手分類) は記述で、区間を付けるなら無補正と明記する。

## 9. 出力の人手分類

### 9.1 単位・母集団・資料

- 単位は**原提案機会**である。母集団を次の 3 つに分けて、それぞれ件数を示す。
  - **(i) 受理された候補:** coder の出力が文法・検疫を通り、pipeline に投入された機会。
  - **(ii) 拒否された coder 出力:** coder の原文があり、投入前に拒否された機会 (schema・文法・検疫・Tier0)。
  - **(iii) coder の原文が無い機会:** planner 側の拒否・役割出力の不備などで coder の出力が無い機会。評定の分母に入れず、件数と拒否の分類だけを示す。
- 資料は、coder の逐語出力 (`implementation`・`value`・`justification`)、採否と拒否の分類、その系列で既に評価した値の一覧である。
  いずれも既存の materials と台帳に保存されるものから抽出する。
- 評定用の資料は、cell の名前・系列番号・block・score・性能の値を除き、全系列の単位をまとめて乱順に並べる。乱順の鍵は発効束に書く。
  ただし `justification` の本文や拒否の理由から cell が推測できることがあるので、盲検は cell 名・score を伏せる範囲までと報告する。

### 9.2 カテゴリ

**(i) 受理された候補** — 値から機械的に決まる。人は全件を確かめる。上から順に当てる。

| 順 | カテゴリ | 操作的定義 |
|---:|---|---|
| 1 | 値不変 (無効変更) | その系列で既に評価した値 (初期点を含む) と同じ値 |
| 2 | 既知値の再発見 | 既知候補の集合 K (§9.3) に含まれる値 |
| 3 | 新しい値 | 1・2 のどちらでもない値 (静的 backoff という既知の機構の、K に無い値) |

**(ii) 拒否された coder 出力** — 人が読む。上から順に当てる。

| 順 | カテゴリ | 操作的定義 |
|---:|---|---|
| 1 | 判読不能 | 読んでも何を変えようとしたのか決められない |
| 2 | 機構の変更の試み | backoff の値の代入以外の振る舞い (条件分岐、状態・abort 回数・thread 番号などへの依存、関数呼び出し、ループ、乱数など) を変えようとした |
| 3 | 書式の誤り | 値の代入を意図したが、書式 (数値の書き方・宣言の形・値と `value` の不一致など) で拒否された |

- 一次資料の 3 分類との対応: 「既知候補の再発見」= (i)-2、「無効変更」= (i)-1、「機構の変更」= (ii)-2。S1 では受理される形が値の代入
  1 行に限られるので (§9.4)、(i)-3 と (ii) の分け方を足した。(i)-2 と (i)-3 を分けるのは、「既知の機構の再発見」と「既知の値の再発見」を
  区別するためである。
- **付記 (カテゴリと独立に、(i)(ii) の全件に記録):** `justification` が workload の記述 (読み比率・read / write の傾向・workload 名) に
  言及したか (言及なし / 表示どおりに言及 / 表示と観測の食い違いに言及)、critic 診断の recommend の値をそのまま採ったか。

  ln(1.05) に届くのは、n = 5 の 6 cell 案で相関 0 を仮定したときだけ (差 0.00002) である。実用上同等を言うための計画上の目安 (半幅 ≤ δ/2 = 0.0148、P3 登録 §8.2 の第 1 段) には、
  s_plan を当てれば表のどの規模でも届かない。√2·s_llm を当てた小さな半幅は自由度 2 の値に基づき、保証にならない。加えて S1 では coder の出力が数値 1 行なので、
  人手分類は機構の違いを説明できない (§9.4)。n を増やしてもこの射程は広がらない。D2259 が B-5 v2 を見送った理由 (値 1 個での LLM の
  対照は査読の決め手になりにくい) も同じ向きに効く。
- **U2 (T-2869 の不公平):** P3 の本比較では、axis 名の揺れによる拒否が LLM 手法だけの A を消費することが不公平だった。本書の比較は
  LLM の cell どうしなので、手法間の不公平としては効かない。ただし拒否が cell によって違う率で起きると、記述・critic の差と拒否の差が
  混ざる。本書は D2273 の修正を全 cell に同じ commit で入れる (§4)。修正後の本番での拒否率は未測定である。拒否の件数は cell ごとに
  副 outcome として報告する (§8)。
- **U3 (LLM の待ちが node の上に残る):** 本書の系列はすべて LLM 系列なので、node 時間の約 6〜7 割が LLM の待ちになる (§7.2)。
  LLM の週の利用上限 (429) に当たると、欠測と node の浪費が同時に出る。原提案機会は 132〜420 で、試走 v2 の 36 機会の 3.7〜11.7 倍である。
  D2265 項 6 は LLM の待ちを node の外へ出す案を設計しないと決めた。本書もそれを前提に見積もった。
- **U4 (課題が 1 つ):** 一次資料の「成功・失敗を代表する少数の課題」は実現していない (§2)。課題を足すには、その課題の試走の値
  (分散・費用) が要る (P3 登録 §8.1 の考え方)。bal・rh は試走されていない (D2265 項 3)。
- **U5 (機構の変更を見られる空間):** 出力コードの分類が機構の違いを説明できるのは、LLM が関数の本体を書ける空間 (S3、
  silo-function-policy、T-2867) である。本書の介入と分類の手順 (§3・§9) を、S3 の生成器対照 (`docs/silo-policy-generator-contrast-preregistration.md`)
  の後に別の登録として載せる択一がある。S3 の単価は未測定で、S3 の対照は arm 構成が別 (D2272 項 4) なので、そのままは流用できない。
- **U6 (新しい cell の分散):** H・S・off の cell の系列間の分散は測っていない。計画半幅は感度の値にすぎない (§7.2 の注)。
- **U7 (記述の届き方):** critic と LLM 親は file を読めるので、H・S 水準でも実際の workload に到達しうる。表示の外に残る露出もある (§3.4)。
  到達の記録は事後の件数で、遮断ではない。

## 13. 発効に要る実装 (後続の wave、本書では実装しない)

いずれも Codex author が書く。正しさゲート (verifier、anomaly の即 reject、trace の compile 時除去、毎回の検証) と既存の失敗の分類は
変えない。記録は既存の materials と台帳を使い、新しい台帳は作らない。

1. **記述の水準の切替:** 系列 header に cell を持たせ、`render_context` の Measurement Setup と `cmd_critic` の `operating_point` を
   §3.1 の水準で表示する。LLM 親の header・resume・指示文と、役割を呼ぶときの説明ラベルにも同じ表示規則を当てる。
2. **失敗理由の写し:** 各評価の後に、critic digest の失敗の節と同じ出所・同じ描き方の text を作り、新しい別の key で planner と coder に
   同じ bytes で渡す (両水準)。`workload:` 行だけ §3.1 の表示規則に従わせる。同じ証拠から同じ値を作り直して一致を確かめられる形にする。
3. **critic なしの経路:** 次の箇所を、系列 header の cell に束縛して変える。critic ありの cell の挙動は今のまま。
   - LLM 親の指示文の critic の起動条件 (critic なしの cell では起動しない)。
   - 巡 tool の入力の生成 (`tools/t2849_llm_round.py` の `cmd_inputs`) と proposal の公開時の読み込み (同 `cmd_proposal`) が、評価 2 以降に
     critic の逐語 file を読む箇所。
   - harness の継承の照合 (`orchestrator/campaign/t2849_comparison_harness.py` の `assert_inherited_inputs`) が評価 2 以降に critic 診断を
     要求する箇所。critic なしの cell では「critic 診断なし・失敗理由の写しあり」を受け、critic ありの cell で診断が欠けたら今どおり止める。
     既存の照合の受理形を増やす変更なので、その wave は cell への束縛を正例・負例の試験で確かめる。
   - 役割文書 (`.claude/agents/planner-v4.md`・`coder-v4-autonomous.md`) の入力節に新しい key の説明を足す。役割本文の改訂はユーザー承認事項
     (D2256 項 7・D2273 項 2 の先例) なので、差分を示して承認を得る。
4. **投入の glue:** cohort `t2852-p5-v1` の schedule (§4 の block・投入順・preimage) と cell ごとの親の指示文。試走 v2 の glue (repo 外) の
   差分として作る。
5. **集計:** 既存の集計 (P3 の harness の aggregate) に §6 の対比と §8 の副 outcome を足す。
6. **評定用の資料:** 既存の materials と台帳から §9.1 の資料を抽出し、乱順に並べる。(i) の機械的な判定を付ける。
