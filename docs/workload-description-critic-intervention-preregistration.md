## 1. 主張の形と、主張しないこと

### 1.1 主張しうること

本書の結果は、**LLM が Silo の関数方策を型付き IR で書く探索**で、LLM に表示する workload の記述と critic の構成が、
探索の結果 (score) と、書かれた出力の中身 (無効な変更・既知の再発見・既知の骨格の新しい定数・新しい骨格) にどう対応したかの**限定的な**結果である。

> S3 (Silo の関数方策の空間、write-heavy の較正動作点) で、T-2867 登録と同じ予算 (評価数の上限 B = 10、原提案の上限 A = 30、共通の初期点 2 個) の下、
> LLM×IR の探索系列が選んだ endpoint の score について、[正しい記述と伏せた記述の差 / 正しい記述と入れ替えた記述の差 /
> 正しい記述の下での critic の有無の差] は、[優越 / 退行 / 実用上同等 / 判定不能] だった。分類は、登録した独立・近似正規の仮定の下での同時区間による (§6)。

- 動かすのは、LLM に**明示的に表示する** workload の名前と読み比率と、critic の呼出しの有無である。LLM が性能・abort 率・段階 D の射影などから
  workload を推し量ることは止めず、表示の外に残る露出もある (§3.4)。したがって「伏せた記述」の結果を「workload の情報を遮断した効果」と書かず、
  どの水準も盲検とは呼ばない。
- 入替は rh の表示 1 つだけである。「任意の誤った記述」の効果へ一般化しない。
- critic の効果は**正しい記述の下だけ**で見る (4 cell 案、§3.3)。伏せた・入れ替えた記述の下での critic の効果と、記述と critic の組み合わせは見えない。
- 結論は S3・write-heavy・LLM×IR と、発効束で固定する model・prompt・構成に限る。

### 1.2 主張しないこと

- **verifier、anomaly の即 reject、構造化された失敗理由の返却の因果効果。** 規律 2・3 により全 cell で外さないので、切り分けられない。論文には限界として書く。
- **critic の LLM による解釈だけの効果。** critic なしの cell は critic の呼出し全体を省き、S3 では critic 診断が coder へ性能を届ける唯一の経路なので、
  critic の有無の差は「解釈」と「性能の還流」の両方を含む (§3.2)。
- LLM 一般・他 model・LLM×C++ 形・非 LLM の手法・他の空間・他の workload・未知条件への一般化。
- critic の効果を、critic の役割定義や prompt の特定の文言に帰すこと。
- score に差が無いことを、出力の中身に差が無いことと読むこと (§8・§9)。
- 副 outcome (§8) と人手分類 (§9) の値を、族の分類 (§6) と同じ強さの結論として書くこと。
- 本書の結果を T-2867 の生成器対照の結果と並べて、同じ比較の一部として書くこと。
- token 数・費用の値を金額として書くこと。サブスクリプションで動く CLI が示す費用の値は請求額ではない。

### 3.2 critic (2 水準)

| 水準 | 記号 | 原提案機会の中で行うこと | 次の coder に渡るもの |
|---|---|---|---|
| critic あり | on | T-2867 登録 §4.1 のとおり、前回の critic の後に新しい結果があれば最初の役割として critic を呼ぶ | 5 key (リーク防止文脈・接続仕様・baseline・段階 D の二値と射程文・自系列の履歴) と critic 診断の 6 field |
| critic なし | off | critic を呼ばない | 5 key だけ |

- **規律 3 を両水準で保つ経路と、その欠落 (発効の前提):** S3 の coder 入力の自系列の履歴は、schema の上では各候補の結果の分類・拒否の分類
  (`reject_subtype`・`reject_rule_id`)・verifier の digest (anomaly の現象・cycle・依存辺を決定的な順で先頭 8 件、件数、全 cycle 数、integrity の内訳) を
  critic と独立に載せる (D2256 項 4、`make_policy_coder_input`)。**しかし T-2867 の対照の経路では、この欄の一部が埋まっていない** (改版 insight §2):
  - 初期点と評価の結果は、結果の分類だけを書き verifier の digest を渡さない (`run_contrast_unit` の中の `_append_seed_history`・`_append_history` の呼び出し)。
  - coder 出力の schema の拒否 (`_schema_reject`) と、auditor の出力の形式・digest の不一致 (`proposal-schema`・`auditor-gate`・`auditor-digest`) による拒否は、
    対照の台帳の `opportunity-end` にだけ残り、履歴に入らない。critic の材料 (`_new_results` は stock・初期点・評価の結果だけを取る) にも入らない。
  - 検疫・構文・compile による拒否と、auditor の通常の判定 (`auditor-violation`・`auditor-uncertain`) による拒否は、`--record-reject` を通って分類つきで履歴に入る。
  現状では、評価の結果の verifier の digest (anomaly の構造) が coder へ届く経路は critic ありの cell の critic 診断だけで、critic なしの cell は規律 3 を満たさない。
  そこで、**対照の経路でも初期点を含む評価の結果の verifier の digest と、履歴に入っていない上の拒否の分類を、既存の履歴の欄に書くことを発効の前提とする** (§13 の 2)。
  新しい key や台帳は作らない。
  これが満たされれば構造化された失敗理由は両水準で同じ経路で届くので、S1 版の「失敗理由の写し」(critic の失敗の節を別 key で渡す仕組み) は作らない。
- **critic なしの cell で coder に届かなくなるもの:** 初期点と自分の候補の性能は、critic 診断を通してだけ coder に届く (T-2867 登録 §4.1 の開示。
  自系列の履歴は throughput を載せない)。critic なしの cell の coder は、baseline (系列開始 stock の throughput と abort 率) と、候補の結果の分類
  (certified か、どの失敗か) だけを受け、自分の候補の性能値を受けない。
- **推定対象:** 「critic の呼出し全体を足すかどうか」であり、その中身は critic の LLM による解釈 (方向の助言・回避の助言) と、coder への性能の還流の両方である。
  解釈だけの効果を推定するには、critic なしの cell に性能を機械的に写す別 key が要るが、それは D2256 項 4 の coder 入力の firewall を変える追加の介入なので、
  本書の射程外とする (§15)。
- critic の入力 (T-2867 登録 §4.1 の「critic への入力の要請」) と coder の検疫・診断の節抽出は変えない。

### 3.4 露出の棚卸し (介入で操作できないもの)

T-2867 の LLM が受け取る段階 D の二値・射程文・baseline の abort 率が workload を示し、記述の介入を弱めるかを、改版 insight §2 の実測で棚卸しした。
**どれも workload の名前や読み比率を含まない。** ただし write-heavy で測った情報を LLM に運ぶ。運び方は経路で違う — 段階 D の射影は全 cell に同じ bytes、
baseline は全 cell で同じ規則により系列ごとに測る値 (系列開始 stock の 1 session なので系列ごとに違う)、critic の材料は critic ありの cell だけに届き、
系列ごとの観測で中身が違う。LLM がこれらから競合の強さを推し量れば、表示との整合・食い違いを通して表示の効き目は変わりうる (弱めるとは限らず、
食い違いに気づいて強く反応することもありうる)。これらが cell の間の差を偏らせないとは言えない。特に critic の材料は critic の有無とともに変わる。

## 5. endpoint と score

- endpoint・score・anomaly の波及・欠測と fallback の優先は T-2867 登録 §6 のとおり。anomaly の波及の範囲は本書の全系列 (全 cell) とする。
- score は endpoint を N_eval = 5 の fresh session で再計測した 5 session の median throughput。endpoint の 5 session の CV を記述として添える。
- fallback (endpoint が無く失敗がすべて候補起因、または endpoint の再計測で anomaly) の score は参照 job の stock 15 session の median で、全 cell の
  不採用系列に共通である。fallback を含む系列の数を cell ごとに必ず併記する。n が小さいので fallback を除く副解析は行わない。
- 系列開始 stock・参照 job の測定値は、どの cell の生成器にも渡さない (R0)。ただし系列開始 stock の throughput と abort 率は T-2867 と同じく
  coder の baseline として渡る (§3.4)。

## 6. 族・推定量・分類

- **対比 (4 cell 案、本線):** 組 r ごとに、x_{cell,r} = ln score として
  - D_H,r = x_{C-on} − x_{H-on} (正しい記述 − 伏せた記述、critic あり)
  - D_S,r = x_{C-on} − x_{S-on} (正しい記述 − 入れ替えた記述、critic あり)
  - K_r = x_{C-on} − x_{C-off} (critic あり − なし、正しい記述)
- **推定量と区間:** 各対比の組平均 d_bar と標本標準偏差 s_d を使い、族 M = 3 の Bonferroni 両側同時区間
  d_bar ± t(1 − 0.025/3, n − 1) × s_d / √n を作る。仮定は組の間の独立と近似的な正規性で、検査しない。
  支えは、系列が fresh context で始まること、組の 4 系列がラテン方格の順で走ること。支えないものは、同じ時期に走った組に共通に入る機体・負荷の変動、
  429 の保留で組の中の系列が異なる時期に測られること、fallback の stock を全 cell で共有することである。
- **符号反転の exact 検定を使わない理由:** T-2867 登録 §7.3 の符号反転の片側 exact 検定は、n = 4 では最小の p が 1/16 = 0.0625 で、どの差でも 0.05 に届かない。
- **同等幅と分類:** δ = ln(1.03) (S1 版と同じ固定値。T-2867 登録 §7.2 の `max(0.03, CV_stock)` は使わない)。区間 [L, U] で、優越 L > δ、退行 U < −δ、
  実用上同等 −δ < L かつ U < δ、それ以外は判定不能。向きは「正しい記述の側 / critic ありの側が高い」を正とする。結果を見た後に δ を広げない。
  固定の δ は両方向に効く: 雑音から δ を決める規則より同等には分類されにくく、優越・退行には分類されやすい。
- **分類は fallback を含む運用 score についてのものである。** score は「候補を採用できなければ stock を使う」運用の性能 (T-2867 登録 §6) で、
  比べる 2 cell の全組が fallback なら対差はすべて 0、s_d も 0 で区間は [0, 0] となり「実用上同等」に分類される。これは生成の力が同等だという意味ではない。
  分類には各 cell の fallback の系列数と certified endpoint の数を必ず添え、生成の力の比較には §8・§9 の記述を使う。
- **資格:** 対比に入る cell のすべてで、予定した n 組のすべての score (fallback を含む) が得られた場合だけ分類する。score の欠測を含む組が 1 つでもあれば、
  その対比は判定不能とし、欠測の件数と理由、残った組の d_bar と無補正の 95% 区間を記述として添える。
- **分類不能も正規の結果**として報告する。n は結果を見て増減しない。
- 族に入らない量 (stock 比、静的 10 µs 比、副 outcome、人手分類) は記述で、区間を付けるなら無補正と明記する。

## 9. 出力の人手分類

### 9.1 単位・母集団・資料

- 単位は**原提案機会**である。母集団を次の 3 つに分けて、それぞれ件数を示す。
  - **(i) 受理された候補:** coder の IR が schema・`validate_ir`・driver の検査 (共有検疫・型付き構文検査・単独 TU compile)・auditor を通り、pipeline に投入された機会。
  - **(ii) 拒否された coder 出力:** coder の原文があり、投入前に拒否された機会 (台帳の `reject_subtype`・`reject_rule_id` で種類を記録する)。
  - **(iii) coder の原文が無い機会:** 役割の出力の不備・空出力などで coder の出力が無い機会。評定の分母に入れず、件数と分類だけを示す。

### 9.2 カテゴリ

**(i) 受理された候補** — 1〜4 は機械的に決まる。人は全件を確かめる。上から順に当てる。

### 9.3 既知の集合 K

  - 共通の初期点 2 個 (静的 5 µs・10 µs、T-2867 登録 §4.6)。
