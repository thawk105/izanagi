## 2026-08-12 (483) — 成長比例テスト 30 function を恒久保留し、受入の床を崩した — 保留は台帳 1 箇所で入り切りし既存 test file を編集しない (コード + docs、変異 7/7 KILLED、branch worktree-dev-wave-growth-tests)

ユーザー依頼「受入全走において、リポジトリが成長するにつれて実行コストが増えるテストの無効化を
してください。それは開発を殺します。大きなコードベースの OSS などでそのようなものはないと思います」
の wave。**同日 rulings 第 3 束で既に裁定済みの案件で、本 wave はその執行タスクの実施である。**
裁定は「削除ではなく恒久保留、解除はユーザーの明示命令のみ、可視な skip 印 + 機械可読な理由、
正しさゲート該当は保留一覧でユーザーへ提示」。

### 依頼の前提は実測で裏付けられた (雑音を含まない証拠のみ)

- `search_repository` を実 repo へ 1 回呼ぶと **26.681 秒 / 12,084 file** (repo 外・直列 probe)。
  前日 (474) の同関数実測は **11,988 file / 24.3 秒**。**1 日で +96 file・+2.4 秒 (約 10%)。**
- peer wave の集合差実測で **1 日あたり正味 +32 node**。

  `git clone --no-hardlinks` する (`tools/codex_reasoning_ab.py:1326`)。hardlink 無効なので
  全 object を実体 copy し、履歴増加に比例する。**構造の事実なので秒数の雑音と無関係。**

### 撤回 — 並列全走の per-node 秒を成長の証拠に使ってはいけない

親は当初、前日 worklog 474 の値と当日の並列全走を突き合わせて「日次増分」を主張した
(gate_refused 47.38→56.13、holdout twins 61.7→70.6、codex_reasoning_ab file 1330.8→1421.5)。
**peer wave の全 node 比較でこれが雑音支配と判明したため撤回した。** 同一 file の parametrize 族で
`[NEG-focus2.md]` 1.45→93.82、`[POS-focus2.md]` 88.48→1.46 と **±90 秒が入れ替わる**。
機序は「共有資源 (submodule clone、build cache、直列鎖の順番待ち) を最初に掴んだ node が
コストを全部計上し、次の走行では別の node が先頭に立つ」。per-node 秒は
「その node の仕事量」ではなく「その走行で待たされた量」を含む。

**ただし鎖内 node は例外**である。`xdist_group("real-repo")` でもともと直列化されているため
並列値も正確 (直列焦点走との差 -7.4%〜+4.7%)。鎖外は -15.7%〜-24.6% ずれる。
peer は「鎖内なら撤回は行き過ぎ」と示唆したが、**別 tip・別日の比較には雑音以外の交絡
(submodule 状態・cache 温度・その日の新設テスト) が残る**ため復活させない。

### 実装 — 保留は台帳 1 箇所で入り切りする

`orchestrator/tests/growth_test_holds.py` (新規) に 30 entry の frozen 台帳を置き、
`conftest.pytest_collection_modifyitems` の**既存の collection 一巡へ相乗り**して
`pytest.mark.skip` を付ける。**既存 test file の本文は 1 行も編集しない。**
これは並行 wave (t816 / freeze-chain-hold が同じ file 群を編集中) との衝突面を作らないためであり、
「削除ではなく保留」という裁定の可逆性を保つためでもある。

- `xdist_group("real-repo")` の付与は `REAL_REPO_SERIAL_NODES` 条件下のまま。**鎖外 24 件に
  group は付かない** (付けると `test_real_repo_serialization.py:567-615` の canonical golden が赤くなる)。
  付与順は group が先、skip が後 (逆にすると opt-in 実行時に鎖内 node の直列化が落ちる)。
- 解除は `IZANAGI_RUN_GROWTH_HELD_TESTS=explicit-user-command` の完全一致のみ。
  他の非空値は `pytest.UsageError`。**`dispatch_compute.py` の env allowlist へ追加した** —
  無いと受入全走が走る計算ノードへ届かず、ユーザーの明示命令による解除が機能しない。
- **opt-in 走の suite identity を分離した。** 同値だと task-run 台帳が「全保留を実行した赤」と
  「省いた緑」を同一 cycle と数える。受入形判定 4 ゲートの戻り値は不変。
- 整合検査は **commit 数・file 数・docs 分量・output 蓄積のいずれに対しても O(1)**、
  収集 test 数に対して O(T) で、**新規の走査を一切増やさない**。
  親 brief の「検査自体が O(1)」は不正確だったので言い直した。

### 敵対レビューが親の誤分類を 1 件覆した

**`test_s8b_ratified_verify.py` を対象から外した。** 親は「rev-list H で commit 数に比例」と
確定対象にしていたが、実体は `tmp_path / "launch-repo"` の一時 repo で固定サイズの攻撃行列を
回しており、実 repo からは固定 freeze の bytes しか読まない (`:2, :381, :390, :1654`)。
成長しない。しかも `result-record-sha` / `protocol-record-sha` / `closure-record-sha` /
`coherent-journal-result` を assert する別テストが repo 全体に存在せず、**保留すると
唯一の検出者が消えるところだった。** 段 2A の子は「誤検出 0」と報告しており、
**子の結論を親が一次資料で裏取りしなければ通っていた。**

### 段 6 の BLOCKER 2 件 — 片方は「検出力だけ消えてコストが残る」純損失だった

1. **解除条件 literal の自己参照。** production・validator・メタテストが全部同じ定数を参照して
   おり、定数を書き換えると一斉に追随して緑のままだった。メタテスト側で literal を
   ハードコードして断った。
2. **共有 fixture の消費者を取り残していた。** `test_campaign_import_invariant` の session fixture
   `repository_scan` (全 source を読み AST parse) の消費者は 6 function だが、台帳には 5 件しか
   入れていなかった。**5 件を保留しても残る 1 件から fixture が生成され、検出力だけ消えて
   全 source 走査コストは残る**純損失だった。6/6 を保留して fixture を生成させない形に直した。
   同型は peer wave が **F240** として登録済み。

**逆に、`test_ruleops` と `test_env_attestation` の「同居」は修正しなかった。** こちらは
コストも検出力も一緒に消えるので、裁定が想定した取引そのものである。既存 test を分割する
変更は並行 wave との衝突面を作るため採らず、台帳に **`collateral_note`** field を足して
「保留により一緒に失われる固定サイズ検査」を機械可読にし、一覧へ出力する。
