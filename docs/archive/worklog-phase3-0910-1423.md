## 2026-09-10 (1423) — [T-2028] 軸 3 の登録済み検索を走らせない裁定を記録し、依存 4 項目を見送りへ落とす (docs のみ、branch worktree-dev-wave-t2028-axis3-stop、実装面の差分 0)

- 前 wave (1419) が軸 3 live 経路の実装を land した直後、ユーザーとの往復で
  **軸 3 の登録済み検索を走らせない**ことが確定した (D1931)。
  **live preflight は 1 本も発火していない。軸 3 の外部 request は 0 のままである。**
- ユーザーの指摘は「OpenAlex は使わないと決めたのでは」だった。**そのとおりで、D1760
  (2026-09-08、ユーザー裁定) が無償枠の窓を使った軸 1 OpenAlex の継続取得をやめると
  既に決めていた。** 親は段 1 で U11 と API 版番号の裁定は decisions.md で確認したのに、
  **「この種の取得を続けるか」という上位の裁定を探していなかった。** 結果として 23 本の
  OpenAlex request を含む計画を提示した。前 wave が記録した F937 と同じ型の見落としを、
  依頼の前提そのものでやっていた (F937 の再発として記録した)。
- **依頼の前提自体も誤っていた。** 依頼は「軸 3 は B-1 (合成軸が既知軸最良を超える) の
  比較対象になる既知軸カタログを埋める作業」としていたが、B-1 は実験で埋める主張である。
  `docs/paper-story/2026-09-02.md` は「S-1a で測って不成立。現状で最も強い言い方は
  『既知軸の一部 (sort) には勝つ』まで。新しい軸か、既知軸を組み合わせた構成でしか埋まらない」と
  書いており、ここでの既知軸は CCBench に実装された軸であって文献ではない。
  **文献検索では B-1 は動かない。**
- ユーザーの整理は「無駄なことはしないでほしい。CC の自動合成にしっかり寄与するか」だった。
  親の回答は**寄与しない**。約 1 日を使って得られるのは 7.7.3 が定める「限定付きの未検出を
  裁定へ提出する資格」だけで、CC 自動合成は 1 歩も進まない。
- **無駄にならなかったのは、走らせる前に止めたことと前 wave が着地させた実装である。**
  逆に、段 1 で D1760 を引いていれば前 wave 自体をもっと早く畳めた。その分は失った。
