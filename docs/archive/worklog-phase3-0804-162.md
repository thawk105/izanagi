## 2026-08-04 (162) — floor 実測 wave は 1 cohort の量が floor でないことを示して停止した — 走行中にユーザー裁定が land し、測定は次 wave へ渡す (docs のみ、branch worktree-wave-t088-floor、実装差分なしのため変異 matrix と受入全走は対象外)

- **走行中に本 wave の findings に対するユーザー裁定が別セッションから land した。**
  裁定は「8 request 案の新規 infra は建てない。1 wave 縛りの適用先は測定規模であり、
  既存 driver の最小 env 化で安価に測る。その値は scoping であって floor ではなく品質ゲートに
  使わない」である。**本 wave は段 4 で「実装しない」と裁定していたため、裁定と食い違う**。
  食い違いは裁定を正とし、**本 wave は該当項の本文へ触れず停止する** — 更新すれば land 済みの
  裁定文を上書きすることになる。安価測定は次 wave が fresh context で行う
- **本 wave が実際に出した成果は、裁定が根拠に使った分析そのものである。** 段 2 のプランと
  段 3 の敵対レンズ 2 本 (統計的妥当性 / 実装整合) が**独立に NO-GO** を返した。
  裁定文が引く「新規 infra 約 1500 行」「40 rep」は本 wave のプランの数値である。
  逐語は `output/insights/2026-08-04_t088-between-run-floor-cohort/`
- **1 束で取れる量は floor ではない。これは設計の欠陥ではなく、量の定義がそうなっている。**
  独立な PBS request を何本並べても事前登録された時間窓は 1 つであり、得られるのは
  `same-submission-cohort allocation-session-median CV` である。D19 はまさにこの
  same-window 値を「真の run 間ドリフトを捉えない楽観的下限」として floor に採らず、
  時間分離された cross-campaign データへ錨を打った。**`stability.between_run_noise_floor` の
  docstring 自身が「本関数が返すのは fresh な same-window の between-run CV = 下限」と
  書いている** — 道具は最初から下限しか返さないと明示していた。裁定の
  「scoping であって floor ではない」はこの分析と一致する
- **「1 測定の品質ゲートとして使えるか」には、測らずに答えが出た。使えない。
  かつ問い自体が用途を取り違えている。** D19 では 1 測定の品質ゲートは **within-run** の役割
  (roadmap §3.6(2) の閾値 5%) で、between-run は**採否の床**である。そして品質ゲート側の問いは
  **既に答えが出ている** — 登録済み Pegasus calibration の within-run CV は 1.17% で、
  閾値 5% に対し十分小さい。新規計測を要さない
- **親 brief の誤りを 4 件、子が反証した。正直に記録する。**
  (a) 独立性規則の所在を D138 と書いたが正しくは D134(f) (D138 は別件の帰納契約)。
  (b) 登録済み calibration を「飽和最小」と書いたが実際は `saturated=false` で、
  4×L3 の下限規則で 1M を選んでいる。(c) 凍結 bytes の pin を 6 箇所と数えたが、
  contract digest 経由の派生 pin 2 件を落としていた (計 8)。(d) 最も重い誤りは
  「official guard は本 track を塞がない」— **コード上は正しい** (`between_run_floor.py` の
  import 閉包に official も s8b も無い) が、**台帳上の task が要求する成果物とすり替えていた**。
  8c 事前登録が求めるのは H1(rr80)/H2(rr20) の対象別 floor であり、rr50 の 1 点はそれではない
- **rr50 の値は他の動作点へ外挿できない。** roadmap は floor を
  `(env, records, threads, 代表 workload/config)` の署名別に持つと規定し、
  linux-baremetal の同窓 CV も rr5=0.666% / rr50=1.067% / rr95=0.110% と一様でない
- **次 wave の安価測定に直接効く blocker を 1 件、実測で確定した。** 計算ノードは intelpython
  既定で `python3` が **3.9** に解決される (実測 job `0:873200.nqsv` rc=1)。`env_contract` は
  3.10+ の `str | None` 構文を持ち、certify 経路の shell は裸の `python3` を呼ぶ。

- **段 3 は 2 レンズとも read-only の静的検査で、pytest は実走していない。**
  計測用の PBS job も 1 本も投入していない (投入したのは受入テストの dispatch だけ)
- **手続き上の逸脱を 3 件記録する。** (1) 段 4 で「実装しない」と裁定したため段 5・6 を飛ばした。
  `DW-C00` の軽量版条件には該当しない (設計択一が割れ、受理集合が動きうる) と段 1 で判定し、

  契約本体を読んだのは段 8 だった (候補の記録自体は wave 中に行えており実害なし)。
  (3) **fragment の `base` を carry 行の digest として算出した** — 正しくは fold の
  `substantive_digest` が carry 連鎖を遡って得る実体 block の digest である。land 前に自分で
