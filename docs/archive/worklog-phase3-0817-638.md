## 2026-08-17 (638) — ユーザー裁定 14 件 — 性能比較を凍結床値から同一 campaign 内の対測定へ移し、計測器の不在を主張の弱点として扱わないと確定した (docs のみ、branch worktree-rulings-full6-20260817)

**収集 (2026-08-17 21:53 JST、main `2b99f73c`)。** 末尾エントリの「次の一手」506 項を archive まで
機械的に解決 (未解決 0)、`docs/handoff/` は README のみ、稼働中の worktree 0 本、repo 外の裁定控え
15 件を照合した。定型句だけでなく「択一」「〜を裁定する」「ユーザーへ返す」等の変種でも総ざらいし、
実体 ID と索引 ID の差集合が空であることを確認して 14 件を提示した。

**ユーザーの一次発話 (要旨、2026-08-17 22 時台)。**

- **床値の表そのものが誤り。** 昔測った A の値と今測った B を比べるのは妥当でない。A と B は
  今、一緒に測って比較するのが筋である。過去値との比較を続けるなら比較元を無数に持たねばならず、
  それは愚かである。
- **途中で落ちた測定。** 「落ちたらその環境と手順で二度と性能を測定できない」は馬鹿馬鹿しい。
  A と B を一緒に測り直せばよいだけである。
- **計測器 (`perf`) の有無と権威。** 意味が分からない。計測器が無いと信頼できない性能である、
  という論はトップジャーナルで見たことがない。
- 残り (索引 #4〜#14) は rulings の推奨どおり。main への着地まで行ってよい。

裁定は D496 / D497 /
D498 / D499 に記録した。

**rulings 側の訂正 1 件 (親の誤り)。** 索引提示時、親は床値を「比較の物差し」として説明したが、
これは不正確だった。`orchestrator/campaign/s8b_oracle_judge.py` の `judge_oracle` docstring は
**floor を入力にも argmax の tie-break にも使わない**と明記しており、速い / 差がないの判定は
既に campaign 内の対測定である。床値が効いているのは受入関門 (測定 binary の bytes 一致、
manifest の対表の完全一致) の側だった。裁定の向きは変わらないが、**判定ロジックの書き換えは
不要で、外側の凍結装置が落ちる**という点で影響範囲は親の当初説明より小さい。

**棄却された親推奨 2 件。** (1) 索引 #1 で親が推した「再凍結の入口が期待測定条件を成果物の外から
受け取り、既定を perf 必須にする」案は、同日午前の「計測器を測定の前提にしない」を部分的に
押し戻すため採らない。rulings が代替に挙げた任意欄も、守る相手が操作者自身である以上不要と判定した。
(2) 索引 #3 の択 (δ) は「第 2 版を諦める」部分だけが生き、「現行の g1 床値表のまま進める」部分は
本裁定の下では採らない — 過去値表を比較・受入の基礎として持ち回ること自体が否定された。

**規律 2 は変更していない。** 事前登録の目的は評価基準の後出し調整の防止であり、基準値の保存では
ない。凍結対象を値から規則 (集約・判定境界・反復数) と構成集合・holdout 集合へ移すことで目的は
保たれる。本エントリを「事前登録が不要になった」と読んではならない。

**見送り台帳の 2 項は前提が崩れたが、本 wave では書き換えない。** [T-901] (床値 run の途中死に
対する救出経路) は「当面は新規 job で最初から再実行する」を理由に見送られていたが、今日の実測で
crash 点 2〜6 では再実行自体が不能と判明していた。本裁定はこの問いごと解消する (対測定では
両構成を測り直せばよい)。[T-293] (F89 perf 受理集合の残余) は再訪条件が official 化の着手時で、

下記の新規項が所有して書き換える。
