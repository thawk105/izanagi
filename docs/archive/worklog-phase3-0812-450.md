  `s8b_verdict.judge_combined` の oracle verdict が未封印である。同じ関数の隣り合う 2 行で、
  予測側は `verify_prediction` の封印 token を要求するのに、oracle 側は `load_official_verdict`
  (schema 名の確認のみ) で読んだ marker をそのまま受ける。schema と holdouts の形だけ満たす
  verdict を書けば `oracle_floor_exceeded`・combined `status`・certified 選択を変えられる。
  [T-804] は「manifest を消費する全層」までを閉じており、この層は scope 外と裁定した
  (spec 迂回とは別の既存の穴で、manifest を一切使わずに成立する)。
  **同ファイル内に `VerifiedPrediction` という既存 pattern があるため実装費用は見た目より安い。**
  掲載だけの証拠 field を足す案は恒真化として却下済み。
  択 = (a) `VerifiedOracleVerdict` を導入し `judge_combined` を封印 token 専用にする (親推奨) /
  (b) [T-657] 権威束設計へ合流させる / (c) 現状維持で主張を限定し続ける
- [T-857] **P2・新規 (ユーザー裁定待ち、B 系)**: 旧形 manifest は
  `verify_manifest` を通らずに report と observations を生成できる。[T-804] は judge 側で
  certified 結論への到達を閉じたが、**report 層自体の受理集合は狭めていない**。
  既存テストが legacy の rc=0 を契約化しており、狭めると受理集合の変更になるため裁定を要する。
  [T-807] が同型の「旧 writer を狭めるか」を現状維持で終端した先例がある。
  択 = (a) 現 report 互換を維持し legacy を恒久的に non-certified と明記する (親推奨) /
  (b) legacy observations を別 schema へ分離して段階廃止する
