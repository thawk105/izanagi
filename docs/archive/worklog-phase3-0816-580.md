## 2026-08-16 (580) — 8c 事前登録の証拠契約改訂を設計まで確定し、採番順序の閂で実装を次 wave へ渡す (docs のみ、branch worktree-dev-wave-t1132-t1134-prereg-contract)

2026-08-16 のユーザー一括裁定 #1〜#3 (逐語「推奨通りで」) に従い、8c 事前登録の証拠契約を
改訂する wave として開始した。**改訂は行っていない。行えないことが実測で確定したため、
設計判断と新事実の記録、および次 wave が必要とする前提だけを land する。**

### 止めた理由 (裁定当時に未見の事実)

D96 手続が要求する条件契約世代記録の `ruling_reference` は、記録を導入する commit の時点で
`docs/decisions.md` に決定見出しが実在することを要求する。台帳の採番は land が協調 lock の中で
ff-only 取り込みの後に行うため、wave 側の commit に新しい決定は存在しえない。受入は作業ツリーから
候補 commit を合成して同じ検証を走らせるので、そのまま進めれば受入が赤になる。
前例の第 2 世代は引いた決定が 12 時間前に別 land で着地しており通っていたが、この順序は
どこにも記録されていなかった。詳細は F340、分割規律は
D439。

### 親の provisional 裁定を 2 件撤回した

- **終端を `SATISFIED` へ変える案を撤回した。** 事前登録文書 §4 は「承認上限は 3 入口で
  機械強制する」「起動側の既定値は `G=2` ではない」「`G=2` を宣言だけで満たしたと見なさない」と
  規範として書いており、exact `G=2` は §7 の起動形の責務である。実測でも予算 validator は
  `1` 以上を受理し、起動側の既定値は `1` だった。加えて既存の字面だけ fixture は静的検査を
  通るよう設計されており、終端を動かすと実体のない実装が充足と認定される。
  D96 は AST による支配関係検査も名指しで却下している。段 3 の両レンズが同じ結論に達した。
- **世代記録の裁定参照に D96 を引く案を撤回した。** 機械検査は通るが、D96 は手続の決定であって
  本改訂の内容を承認していない。両レンズが blocker と判定した。既存決定の流用も成立しない。

### 段 3 レンズが親の実測を訂正した (受け入れた)

- 「閉じた射影」の正本は `orchestrator/campaign/s8c_generation_projection.py` であり、
  親が挙げた `_role_metric_payloads` ではない。
- 「HEAD 1 点で全条件が未充足」から「受理集合は広がらない」を導いたのは一般化として誤り。
  正しくは「現 HEAD において 6 評価器は全件 UNSATISFIED であり終端に到達しない」に限定する。
- 条件 11 の証拠は独立 4 機構ではない。上限定数と 3 入口 validator は 1 機構、
  射影と production 配線は 1 機構、負の対照は開発テストで commit 証拠に入らない。
- pin 閉包に docs checker の動的検査、runbook の旧識別子、land の採番順、
  評価器と core の bytes が凍結に束縛されていない点を含めていなかった。

### 親がレンズを訂正した

段 3 のレンズ B は「D114 が承認済み世代上限を 1 としており D410 は上限引き上げの権威に使えない」と
述べたが、D410 本文は自ら「D114 の承認上限 1 を 2 へ上げる」と定めている。D410 の当該文は
「C11 の充足状態を上限引き上げの根拠に使うな」の意であり、D410 自身が権威でないという意味ではない。
同レンズの「決定を先に land する形は D96 要件を満たさない」も、D96 が同一変更単位を要求するのは
条項 2 (境界テスト) だけであるため成立しない。
