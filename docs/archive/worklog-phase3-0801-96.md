  計算ノードで再開する」と書かれていたが、(a) `numactl` は計算ノードに在り (`/bin/numactl`)、そもそも
  pegasus env_contract は `numactl=()` で要求もしない、(b) 計算ノードは**外部 network 不可ではない** —
  直結 DNS/socket は不通のままだが、計算ノードの shell profile が `http_proxy` / `https_proxy` を
  持ち、Claude CLI はこの proxy 経由で API に到達する (算術 nonce 3 問を rc=0・3 秒で正答)
- **真の blocker を 3 条件の対照で特定した。** provider の env allowlist
  (`{PATH,HOME,LANG,LC_ALL,TERM}`) が proxy を落とす。full env=成功 / allowlist そのもの=`ENOTIMP`
  で **172 秒**後に rc=1 / allowlist+proxy=成功。8c driver でも再現し (request `876813`、bnode145)、
  3 cell とも `planner-invalid`・driver rc=2 になった。**失敗理由の誤帰属**である — 台帳には
  「LLM が schema を破った」と読める記録だけが残るが、実体は transport 断で、規律 3 が最初から狂う
- **それでも実装しないと裁定した。** D108 決定 (1) が「計算ノードで `claude -p` を起動しない」と
  明記し、runbook §8 の投入前チェックリストも同じ規範を持つ。proxy を allowlist へ通す機能の発火
  条件は「role が計算ノードで走ること」で、それは現行契約が禁止している (`DW-G04`)。かつ D108 が
  その根拠として挙げた前提 (「計算ノードから `claude -p` を呼べない」) を本 wave の実測が覆したので、
