- **[T-408] は (c) 現状維持。** `_executable` の symlink 拒否と shell 側 `[[ -x ]]` の食い違いは
  残すが、**先に拒否の意図を調べる**というユーザー指示に従い本エントリで調査した。結果は下記
- **調査 1 — 意図はどこにも文書化されていない。** 導入は `4bcbc2c` (2026-08-01、
  「[T-126] 逐次停止 v2 の attempt staging 回収順序を是正する」)。**commit 本文に symlink 拒否の
  説明は 1 行も無い**。`docs/decisions.md` / `docs/failures.md` にも `_executable` の symlink 拒否を
  説明する記述は無い。**主題である staging 回収順序の是正に付随して入った変更**に見える
- **調査 2 — 同族のパターンは存在し、設計文化としては整合する。** 同ファイルの `_dependency` は
  `path.is_symlink()` を `dependency source is unsafe` として拒否する。repo 全体でも symlink は
  **同一 UID の並行 process による差し替え (TOCTOU) の攻撃面**として一貫して扱われている —
  `mkdtemp` 直後の symlink 差し替えで削除経路が解決先を消す件、collector の親 component 検査、
  safe-reader が final component だけでなく親 component まで検査する件。したがって
  「pin した path の実体を差し替えられない」という意図の**推定は妥当**である
- **調査 3 — ただし保護は最終 component だけで部分的である。** 拒否の直後に
  `Path(found).resolve(strict=True)` を呼んでおり、**親ディレクトリの symlink は黙って辿る**。
  「間接参照を許さない」という理屈は最終要素にしか効いていない。safe-reader が親 component まで
  検査しているのと非対称である
- **調査 4 — bytes 差し替えの検出は別経路で既に成立している。** `_sha256` は fd を保持したまま
  `fstat` の before/after を照合し (`st_dev` / `st_ino` / `st_size` / `st_mtime_ns`)、
  差し替わったら `executable changed while hashing` で停止する。manifest には `path` と `sha256` が
  記録される。**「実体が差し替わったことの検出」はハッシュ側で閉じている**
- **調査 5 (最も重い) — 拒否を pin するテストが 1 件も無い。** `prepare_toolchain` / `_executable` の
  symlink 拒否を検査するテストは存在しない (symlink 関連のテストは collector の親 component 検査と
  verified executable copy という別機能のもの)。**いま拒否を外しても赤くなるテストが無い。**
  これは両向きに効く事実である — 緩める側から見れば「回帰を検出できない」、
  守る側から見れば「義務がテストで代替されていない」
- **次に動かすときの筋 (裁定ではなく所見):** (a) 拒否を外して shell と揃える / (b) shell を締めて
  Python と揃える のどちらへ倒すにせよ、**先に現行挙動を pin するテストを足すのが順序**である。
  調査 5 のとおり現状は無防備で、どちらへ動かしても回帰が検出されない。
  なお [T-293] の裁定 (a) により本件は**急がない** — qualification 経路は一度も完走しておらず
  (`toolchain-manifest.json` / `submission-intent.json` / `series-identity.json` が repo 内 0 件)、
  現時点の実損は 0 である
