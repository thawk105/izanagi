## 新規

### {{F:archive-name-entry-number-collides-with-mmdd}}. archive 名の entry 番号が日付として解釈され、番号が衝突域へ入った瞬間に全 wave の land が止まった [恒真ゲート] [ドリフト]

- 事象: 2026-08-26 の夜、**4 本の wave が順に local main を ff-only して、全部同じ commit へ
  巻き戻された** (main の reflog に 4 往復が残る)。いずれも fold が `status=fold-failed` rc=26 で、
  生成後検査が `carry 参照先 entry (1001) が全域番号 universe に実在しない — 宙吊り参照` を返す。
  main は無変更のまま。`tools/spool_fold.py --dry-run` は rc=0 でこの赤を手前で出せない。
- 根本原因: `tools/check_docs.py` の archive 名分類 `_archive_filename_entry_range` が、
  **MMDD token と entry token の正規表現が重なる**ことを考慮せず位置文法で先に日付として読む。
  rotation が作る名前は `worklog-phase3-<MMDD>-<entry>.md` で、entry 番号 `1001` は
  MMDD (10 月 01 日) としても妥当なため、「日付範囲の非採番 archive」に分類される。
  結果として当該 entry は採番 universe に一度も入らず、そこを指す carry がすべて missing 枝へ落ちる。
  **main の worklog には当該 entry を指す carry stub が 820 件ある。**
- 射程の実測: 分類器を直接叩いて entry 1000-1400 を全走査した。衝突するのは **93 件**、
  連続区間は **(1001-1031) / (1101-1131) / (1201-1231)**。日部分の正規表現が
  `0[1-9]|[12][0-9]|3[01]` で月に依らず 31 日まで許すため、11 月 31 日という実在しない日付も
  MMDD として通る (この 1 点は並行セッションの実測が親の当初の区間を訂正した)。
  entry 1000 が通っていたのは、日 `00` が不正で MMDD に一致しなかったためだけである。
  **entry 1001 は史上初めて衝突する番号であり、番号が届いた夜まで潜伏していた。**
- 恒久対応: 未実施。真因の特定までを親が行い、修理は `check_docs.py` を既に触っている
  並行 wave 側で所有する調整に入った (同 file の並行編集で双方が止まるのを避けるため)。
  **迂回 (missing を既知違反として登録する) は採らない**と決めた —
  missing 枝には allowance の分岐がそもそも存在せず免除面の新設になること、
  衝突域を抜けるまで 31 回分の暫定登録を積むことになること、820 件の登録は実質この検査を
  切ることに等しいことによる。修理を含む wave は自分自身の land で通る
  (fold は land が ff-only した**直後**に同じ lock 内で走るため、修理済み checker が
  生成後検査に使われる。`docs/spool/README.md` の fold 契約)。
- 再発検知: **番号空間を別の意味の token 空間と同じ位置文法で読む分類器を新設・変更するとき、
  両空間の重なりを番号の全域で走査して示す。** 本件の分類器には、衝突域 3 区間の
  代表値 (1001 / 1031 / 1101 / 1131 / 1201 / 1231) と非衝突値 (1000 / 1032 / 1232) を
  負例・正例として置く。

### {{F:rulings-carry-stub-has-two-forms}}. 持ち越し表記の片方だけを辿り、69 件を実体未解決のまま裁定待ち判定から落とした [手順漏れ]

- 事象: `/rulings all` の収集で、worklog 末尾エントリの持ち越し 827 件を実体解決する解決器を
  書いたが、**`- [T-N] (E)` 形だけを辿り `- [T-N] 変わらず ((E) 参照)` 形を辿らなかった。**
  69 件が実体未解決のまま残り、そのうち少なくとも 1 件は生きた裁定待ちだった。
  発覚は別系統モデルへの相談であって、親の収集ではない。
- 根本原因: 持ち越しには 2 つの表記があるが、解決器が 1 形式しか実装していなかった。
  未解決件数を出力していれば即座に気づけたが、解決成功件数だけを見て「欠落 0」と判定していた。
- 恒久対応: memory `rulings-carry-stub-has-two-forms` (2 形式とも辿る・未解決件数を print して
  0 を確認する・語ではなく状態 marker の不在で 1 次抽出する)。
  同じ収集の語による絞り込みも、「裁定」を含まず「〜を決める」で終わる項を落としていた。
- 再発検知: 収集の解決器は**未解決件数を必ず出力し、0 でなければ索引を確定しない**。
  F213 / F496 と同じ「収集の母集合が構造的に欠ける」型の 3 例目である。

### {{F:rulings-collection-is-a-snapshot}}. 収集後に稼働 wave が裁定を commit し、索引が確定時点で既に古かった [ドリフト] [手順漏れ]

- 事象: `/rulings all` の未 land fragment 走査 (20:35 頃) の後、**同じ夜に 2 本の wave が
  裁定待ちを含む fragment を commit した** (20:47 に裁定パッケージ 3 件、22:08 に
  既裁定と矛盾する「裁定へ返す」1 件)。索引確定の直前に再走査したところ、未 land fragment は
  9 件から 24 件へ増え、**追加の裁定待ちが 3 branch から 7 件**出た。
- 根本原因: 収集が snapshot であることを手順が明示しておらず、走査を 1 回だけ行っていた。
  収集の開始時刻と索引の確定時刻の差だけ取りこぼす。
- 恒久対応: memory `rulings-collection-window-vs-live-waves`
  (索引を確定する直前に branch 走査をもう一度回す。開始と確定の差が 1 時間を超えるなら必ず回す)。
  あわせて、稼働 wave が**既に裁定済みの案件を「裁定へ返す」と書いた fragment を持ったまま
  land しうる**ことも観測した。land 後の worklog に裁定待ちが増えていたら、まず既裁定と
  主題で照合する。
- 再発検知: 再走査で新規に見つかった裁定待ちの件数を索引に明記する
  (0 件でも「再走査して 0 件」と書く)。本 fold ではこの手順が実際に 7 件を拾った。
