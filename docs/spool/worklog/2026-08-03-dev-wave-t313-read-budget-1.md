## 本文

- 段 4 で**実装しないと裁定**し `4→7→8→9` とした。段 2 プランと段 3 敵対レンズ 2 本が
  いずれも NO-GO で、残った択一が**ユーザー裁定の射程を超える**ためである
  (`DW-S04`「scope 外の real 所見は実装せず裁定パッケージで返す」)。
  逐語は `output/insights/2026-08-03_t313-read-budget/`。
- **裁定 (109) の根拠値は gate から計算できない量だった。** 裁定を記録した commit `3b095bc`
  で 4 reference を再計測すると、合計 23,956 / 常に走る段の無条件節 9,668 /
  wave クラス依存 9,169 / 条件成立時のみ 5,119 である。裁定文の「実読 10,515」「L2 3,755」は
  どの構造層の和とも一致しない。10,515 のうち条件由来が 3,755 なら無条件由来は 6,760 で、
  当時の `core.md` 単体より小さい。**あの数字は 1 本の docs-only wave が実際に開いた節の
  実行計測**であり、repo から決定的に導けない。したがって gate は構造的な代理量を選ぶしか
  なく、選択でしきい値が 2 倍違う。これは実装細部でなく設計択一である。
- 現在地 (worktree @ e0b9073): 常に読む 10,568 / wave クラス依存 9,493 / 条件のみ 5,137
  = 25,198。hard ceiling 25,200 に対し**残 2 bytes**。
- **親 brief の実測に誤りがあり、段 2 プランが突いた。** `DW-O23` は段 9 の無条件行にあるため
  L1 であり、親が L2 に置いたのは分類漏れ。正しくは L1 20,061 / L2 5,137。
  レンズ A が全 49 節を総当たりし、他に分類誤りがないことを確認した。
- **提案値は「引上げ不採用」と両立しない。** プラン案 (L1 20,200 + L2 単節 1,000 × 14 節) の
  理論上限は 34,200 bytes で旧 25,200 比 +35.7%。一方、現在値で凍結すると余白ゼロになり
  後続の義務追加ができない。コードで解けない矛盾であり、余白を認めるかの再裁定が要る。
- **動機の 1 つが陳腐化していた。** 裁定 (109) は「T-314 を入れる余地」を挙げたが、T-314 が
  要求するのは `.claude/commands/rulings.md` の余白で、T-313 は command の予算に触らない。
  実測は 4,601/5,000 = 余白 399 bytes で、当時の「6 bytes」自体が古い。
- **迂回路を 1 件特定した。** `_dispatch_tables` は段キーごとに全行を 1 集合へ畳むため、
  「成立した条件の」「commit するなら」という条件修飾を保存しない。どの案を採るにせよ、
  L1/L2 分類を command 表の条件 marker へ機械的に束縛しない限り、marker を消すだけで
  gate を迂回できる。
- 親の誤りをもう 1 件訂正した。brief の受入環境「計算ノード不要」は誤りで、`AGENTS.md` は
  login ノードでの pytest を一切禁止し `tools/run_tests.py` が gen_S へ dispatch する。
- 背景 job の handoff 置き場を harness 既定の home 配下に作り、ユーザーに止められた
  (F50 の再発。前回は worktree 内、今回は home 配下で置き場を間違える型は同じ)。
  恒久対応として `DW-O20` の当該語を byte 中立で「背景jobはrepo外」へ是正した。
