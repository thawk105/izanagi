## 本文

- **依頼の 2 つの指定が両立しなかった。** 依頼は「`run_kind = t2266-tail` の残る帯 901〜998
  マイクロ秒を取る」と「投入経路は本走 driver」を同時に指定したが、前者の格子に帯は 1 点も無く、
  後者は右 tail (境界参照 1000 と 1250〜9999 の 7 点) を測る。段 2 の plan と段 3 の敵対相談 2 本が
  いずれも独立に確認した。
- **依頼の前提条件は満たされていた。** 「既投入分の回収・解析が済んでいるか確かめ、
  済んでいなければ回収から始めて再投入しない」に対し、2026-09-10 の 1000 マイクロ秒の標本は
  回収も解析も完了していた。**回収も再投入もしていない。**
- **親は段 4 で O-C (本走の投入・回収) を採り、帯を測らないことを選んだ。**
  帯を測るには専用 RUN_KIND を作る実装が要り、依頼が明示した「本題の実測だけ」に入らない。
  決定は {{D:tail-band-not-measured-by-formal-driver}}。**帯は未測のまま残る。**
- **段 7 の記録中に、帯を測れるようにする作業が既に後回しにされていたことが分かった。**
  D1936 項36 (2026-09-10 裁定) が対象 T-2562 / T-2584 で「追加 tail 測定を今進めない」と決めており、
  T-2584 の本文は「静的 `T(b)` の b > 900 マイクロ秒を測れるようにする」である。
  **親はこれを段 1 で確認していなかった。** 結果として裁定と整合する選択になったが、
  順序としては着手前に確認すべきだった。
- **棄却した所見。** 段 3 が挙げた 6 件を refuted とした — 事前登録の追補で本走が必ず止まる
  (追補版 commit なら止まらないことを親が独立に検算)、正しさゲートが緩む経路がある、
  本走 report が v1 consumer へ流れる、別ノードというだけで集団が無効になる、
  3 job 並行が作法に反する、plan が未裏取りの queue 観測に依存している。
- **親の実測の誤りを子が 1 件正した。** 段 1 brief は帯の両端の差を 0.66% 以内と書いたが、
  それは 999 対 1000 の差であって 900 対 1000 の差 (−4.2〜−5.0%) ではない。
  段 2 の plan が指摘し、親が一次資料から読み直して追補で訂正した。
- **セッション異常 2 件。** (1) worktree 作成 tool が git config を読めず失敗したため手動で作成した。
  (2) submodule 初期化 tool が 1 回目に `update-no-fetch` で失敗し、同じ引数の 2 回目で成功した
  (契約どおりの 1 回再実行で解決)。いずれも 5 session が同時に worktree を作っていた時間帯である。
- **エージェント工数。** codex 子は 3 名 (plan 1・敵対相談 2)、いずれも read-only。実装子はゼロ。
