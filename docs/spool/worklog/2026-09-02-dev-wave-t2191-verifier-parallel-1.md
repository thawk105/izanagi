## 本文

- ユーザー依頼は「直列性検査器を並列化して B-10 正式走の律速を外す」であり、
  トレース短縮など検査を弱める方向は採らない、並列化の前後で判定が一致することを
  正例・負例の両方で示す、と最初に確定していた。**本題の実装だけ**とし、
  仮想リスク向けの gate・検査・台帳・一般化の追加は scope 外とした。

- **依頼の前提を段 1 で実測して確認した。** 一次資料 (エントリ 1189) は 1 反復の所要が
  混合区間だと明記していたので、検査器だけを分離して測った。検査器単体は
  59.2-65.3 マイクロ秒/commit で、read-heavy の実測傾き 87.0 の 68-75% を占める。
  内訳は parse 54% / 依存グラフ構築 39% / cycle 検出 6%。編集面外の C 行数え直しは 1.5% しかない。

- **設計を決めた実測が 2 件ある。** (a) 子から親へ dataclass を pickle で返すと往復 11.5 秒かかり、
  同じ入力の parse 本体 6.74 秒より高い。列指向配列なら 0.11 秒。**オブジェクトを返す並列化は
  速くならない。** (b) 記憶量が 1 commit あたり 5.1KB で、全規模では約 87GB。表現を変えないと
  速さより先に記憶量で壁に当たる。

- **先行分析が道を 1 本に絞っていた。** `docs/b10-multinode-formal-run-design.md` §4 が、
  検査を別プロセスへ配る形は受領証のプロセス番号束縛で認証が成立せず規律 2 に反すること、
  Python thread は効かないこと、残る形は「判定と受領証は元プロセス、純粋なデータ処理だけ並行」で
  あることを既に確定し、**着手にはユーザーの判断が要る**として範囲外にしていた。本依頼がその判断。

- **敵対相談 2 本の所見 13 件をすべて real と裁定した (refuted 0)。** 判定の向きは変わらないが、
  目標値の主張を弱めた。プランは「parse だけの並列化では 12 時間枠に入らない」と正しく判定し、
  親 brief の Amdahl 上限 1.85 が算術誤り (正しくは 2.17) であることも指摘した。
  親自身の誤りは他に、占有率の列で分母が揃っていなかった点と、参照行番号 1 行ずれである。

- **敵対レビューが正しさの穴を 1 件見つけた。** 実装の初版は依存グラフの子への入力を
  モジュール大域変数へ排他なしで置いており、同一プロセスの別スレッドが 2 つの trace を
  同時に検証すると片方の子がもう片方の入力を継承しえた。件数の完全性検査は通るので
  **巡回のある trace が certified になりうる**。絶対規律 2 の直撃。呼出しごとの状態を作り
  子へは初期化引数で渡す形に直し、2 スレッド同時検証の回帰テストを置いた。

- **判定は変わらなかった。** 68 万 txn の同一 trace で、旧コード・新コード workers=1/16/48 の
  `result_to_dict` が sha256 まで一致した。17 万 txn では 8 通りの並列度すべてで一致。
  受入全走は 20,098 passed / 92 skipped。

- **速さは 2.2 倍で頭打ちになった。** 68 万 txn で旧 45.92 秒 → 16 並列 20.64 秒。
  並列度 16 で飽和し、24・32・48 では改善しない。親の直列部が 38.6% を占め、漸近上限は約 2.6 倍。
  段 2 プランが見込んだ 5-12 倍には届かない。**B-10 read-heavy は 660-840 秒/反復・
  full-scale 75 回で 13.7-17.5 時間となり、12 時間枠にはまだ入らない。**
  律速は大きく下がるが外れない。測定は 16 ユーザ共有・load 20-30 のログインノードで行った。

- **変異の登録に 5 走かかった。** 初回は runner argv の `--force-dispatch` 欠落で baseline が
  解析不能 (runbook 7.4 の既知事項を起動前に引かなかった親の落ち度)。M7 が 2 走生存したが
  いずれも注入の狙い違いで、防壁の不在ではなかった — 逐次経路だけを変異させた版と、
  executor 構築時に評価される引数を大域から取る版は、どちらもテストが同期させた fork 時点に
  効かない。子側の初期化関数が fork 後に大域を読む形にして KILLED になった。
  M2 は完了順に依存して赤の node 集合が走ごとに変わったため、決定的な逆順へ差し替えた。
  最終は baseline 緑・KILLED 7・SURVIVED 0・MISMATCH 0。

- **Codex が利用上限に達し (復帰 2026-09-07)、既定並列度の修正が未了で残った。**
  親が cgroup で測ったところ、所要は 16 で飽和するのに記憶量は並列度に比例して増え、
  48 では 16 と同じ所要に 1.93 倍の記憶量を払う。B-10 全規模へ換算すると 48 並列で約 142GB、
  計算ノードのユーザ上限 115GiB を超える。既定は `min(file 数, 割当てコア数, 48)` なので
  48 file・48 core の正式走はちょうど 48 を選ぶ。**修正は上限を 16 に下げるだけだが、
  実装面の代行は provenance 契約が禁じるため入れなかった。** 詳細は {{D:verifier-parallel-default}}。

- **land も塞がった。** main の 80 commit を固定 SHA で取り込んだところ、編集面の重なりは
  `orchestrator/tests/test_verifier.py` 1 file (main 側は T-2176 の負例 fixture 追加、
  production 差分 0) で、自動 merge は競合なしで通り、取り込み後の焦点走も 96 件緑だった。
  しかし「両親が同じ実装面ファイルを変更した main 取り込みでは Codex role=author の
  合成監査を行う」規則 (根拠 F481) に該当し、その Codex が起動できない。
  **merge commit 本文にその旨を書き、tip は land していない。**

- 一次資料: `output/insights/2026-09-02_t2191-verifier-parallel/README.md`。
  変異 spec と台帳 (probe + 中間 3 走 + 最終) も同 directory。
  実測に使った使い捨て probe は repo へ入れていない。
