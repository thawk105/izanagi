## 本文

D496 の実行。**実測で裁定時に見えていなかった事実が 3 件出た。裁定の向き (D496 の 4 決定) は
どれも覆らないが、作業の所在と実行可能性が変わった。**

**新事実 1 — 床値を比較の基礎として使っているのは受入関門ではなく最終判定層だった。**
裁定と本台帳の前エントリは「床値が効いているのは受入関門 (測定 binary の bytes 一致、manifest の
対表の完全一致) の側」と説明したが、実装を読むと両者は比較ではない。実際に「昔測った値と今測った値を
比べる」形は `s8b_verdict` の条件 3 (on/off の実測差が凍結 per-pair floor を超えるか) と
scale gate (stock の実測 median を床値 campaign 由来の期待値と比較) にある。
**条件 3 は 2026-07-16 のユーザー裁定が逐語凍結した truth table の一部**であり、
当時の package 自身が「裁定・再凍結必須」の一覧へ名指しで載せている。本 wave では変更しない。

**新事実 2 — D496 決定 3 (落ちたら測り直す) は現状の実装では実行できない。**
実走マーカーが freeze の byte hash を identity として出力先非依存に排他作成され、存在すれば
同じ freeze の再走を全拒否する。この resume 拒否は §9 項 8 の択 (a) が凍結した挙動である。
加えて v1 freeze の verify は毎回 repository novelty search の pass を要求し、初回観測後の再走と
両立しない。**したがって「択 (a)(b) とも不要」という裁定の前提は成り立たない** — 択 (b)
「freeze-wide の事前割当 attempt registry」がまさにこの閂を外す案として当時から書かれていた。
どちらが優先するかを裁定へ返す。

**新事実 3 — 判定境界は既存テストで pin されていなかった。** 事前登録すべき 4 要素のうち、
構成集合・holdout 集合は既存機構が凍結し、反復数は 3 量のうち 2 量が承認定数で凍結済み
(trial 数だけが承認手番待ちで、承認定数が未設定の現在は**凍結されていない**)。集約規則は既存
judge テストが値と勝者で pin していた。**しかし判定境界は pin されていなかった** — 既存の
exact tie テストは本物の完全一致しか置かないため、境界を近似一致へ緩めても赤くならない。
段 3 の敵対レンズがこれを指摘し、親が実装で裏取りした。**宣言だけを台帳へ書けば恒真な事前登録に
なるため、緩和変異を捕まえる正例つき検査を同じ land で足した。**

**変異実測 (新旧両走)。** 同一の緩和変異 2 件 (近似一致へ緩める / 固定幅で緩める) を 2 つの HEAD で
走らせた。変更前 HEAD では **2 件とも SURVIVED**、新設後は **2 件とも KILLED** で、
落ちた node は新設テスト 1 本と完全一致した (期待 node の完全集合要求を満たす)。両走とも baseline は
PASSED。旧走は使い捨て worktree で行い主 tree を変異させていない。
**本 wave の純増検出力はこの 1 点であり、それ以上を主張しない。**

**親が自分の判定を 5 件撤回した。** (a) 「測定 binary の bytes 一致は同一 campaign 内の検査なので
残す」は誤り — 照合される receipt 自体が過去の床値 campaign 由来だった。「現在の方針で検証している」は
「証拠が現在のものである」を含意しない。(b) 「対表 exact 検査は構成集合の凍結を担う機構そのもの」も
誤り — 担うのは schedule の cell 完全積を照合する別述語である。(c) 「tie は事実上到達不能」は
過剰一般化 — judge テストが本物の exact tie を構成して発火を pin している。実測データが 1 件も無いため
実害は測れていない。(d) 「集約規則と判定境界は既存テストが pin 済み」は半分誤り — 境界は未 pin だった。
(e) 従属 5 項を「4 件は要る」と断定したのも早すぎた — 要否は床値撤去を採るかに従属する。
**推論エラーの型は {{F:closure-scoped-by-task-named-modules}} に記録した。**
5 件のうち 4 件は独立コンテキストの敵対子が捕まえた。親単独なら誤った要否判定と恒真な事前登録が
land していた。

**段 2 のプランは 5 単位の実装を提案し、その診断は上記 3 件で親より正確だった。** ただし実装は
本 wave では行わない。理由は 3 つとも規律側である。(i) プラン自身が「受理集合を広げる」と書いた
変更を含み、規律 2 の下では置き換える事前登録の発効が先である。(ii) 条件 3 と実走マーカーは
逐語凍結されたユーザー裁定事項である。(iii) 境界の算式はプラン自身が「実装者が選んではならない」と
書いている。**本項の scope はもともと設計・要否判定・事前登録・台帳・従属項の判定であり、
pipeline の書き換えではない。** その 5 項目を完遂し、実装は証拠付きの裁定パッケージとして返す。

**凍結成果物の bytes は 1 byte も動かしていない。** 着手前に pin 閉包を実測し、段 6 の敵対レビューが
独立に「親が落としている pin なし・想定外の変更 file なし・凍結成果物と歴史記録の変更 0 件」を
確認した。ただし docstring の byte 変更で judge の実ファイル hash は変わるため、
**reviewed spec の generator identity は旧 hash から新 hash へ移る** (独立 golden の literal と
その派生 hash を同じ land で実測値へ追随させた)。「受理集合は完全に不変」ではない。

**見送り台帳 2 項は直接編集で書き換えた。** `見送り追記` sink は対象 item の先頭行の行末へ 1 行を
入れる規則で、両項は複数物理行にまたがるため文が壊れる。ID は同じ sink に留めて理由文だけ差し替えた。
