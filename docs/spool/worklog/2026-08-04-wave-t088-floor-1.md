## 本文

- **ユーザー裁定「着手する。ただし 1 wave 規模に収め、足りなければ拡大せず裁定へ返す」の
  後段を発動した。** 段 2 のプランと段 3 の敵対レンズ 2 本が**独立に NO-GO** を返したため、
  段 4 で「実装しない」と裁定し `4→7→8→9` を辿った。実装差分がないので変異 matrix と
  受入全走は射程外である。**PBS job は 1 本も投入していない** (裁定が求めた「使った規模」の答え)
- **1 束で取れる量は floor ではない。これは設計の欠陥ではなく、量の定義がそうなっている。**
  8 本の PBS request を一度に投入しても事前登録された時間窓は 1 つであり、得られるのは
  `same-submission-cohort allocation-session-median CV` である。D19 はまさにこの
  same-window 値を「真の run 間ドリフトを捉えない楽観的下限」として floor に採らず、
  時間分離された cross-campaign データへ錨を打った。**`stability.between_run_noise_floor` の
  docstring 自身が「本関数が返すのは fresh な same-window の between-run CV = 下限」と
  書いている** — 道具は最初から下限しか返さないと明示していた
- **裁定が求めた 2 つ目の判定「この floor が 1 測定の品質ゲートとして使えるか」には、
  測らずに答えが出た。使えない。かつ問い自体が用途を取り違えている。** D19 では 1 測定の
  品質ゲートは **within-run** の役割 (roadmap §3.6(2) の閾値 5%) で、between-run は**採否の床**である。
  そして品質ゲート側の問いは**既に答えが出ている** — 登録済み Pegasus calibration の
  within-run CV は 1.17% で、閾値 5% に対し十分小さい。新規計測を要さない
- **親 brief の誤りを 4 件、子が反証した。正直に記録する。**
  (a) 独立性規則の所在を D138 と書いたが正しくは D134(f) (D138 は別件の帰納契約)。
  (b) 登録済み calibration を「飽和最小」と書いたが実際は `saturated=false` で、
  4×L3 の下限規則で 1M を選んでいる。(c) 凍結 bytes の pin を 6 箇所と数えたが、
  contract digest 経由の派生 pin 2 件を落としていた (計 8)。(d) 最も重い誤りは (P1) —
  「official guard は本 track を塞がない」は**コード上は正しい** (`between_run_floor.py` の
  import 閉包に official も s8b も無い) が、**台帳上の task が要求する成果物とすり替えていた**。
  8c 事前登録が求めるのは H1(rr80)/H2(rr20) の対象別 floor であり、rr50 の 1 点はそれではない
- **rr50 の値は他の動作点へ外挿できない。** roadmap は floor を
  `(env, records, threads, 代表 workload/config)` の署名別に持つと規定し、
  linux-baremetal の同窓 CV も rr5=0.666% / rr50=1.067% / rr95=0.110% と一様でない。
  したがって仮に rr50 を測っても、対象別 floor の欄は埋まらない
- **実行面の blocker を 1 件、実測で確定した。** 計算ノードは intelpython 既定で `python3` が
  **3.9** に解決される (実測 job `0:873200.nqsv` rc=1)。計画が使う `env_contract` は
  3.10+ の `str | None` 構文を持ち、certify 経路の shell は裸の `python3` を呼ぶ。
  8 job すべてが driver の import 前に落ちる。**`floor_campaign.sh` は既に版数 gate を
  持つが certify 経路は持たない** — この非対称は見送り中の [T-272] の射程である
- **新しい攻撃面を 1 件見つけた。** `submit_certify.sh` は real submission でも
  `--job-script PATH` を無条件に受理し、submitter は指定ファイルの live hash を記録するだけである。
  job 側は `$0` でなく固定 path を hash し、collector は submit / acquisition / result 間の
  `job_script_sha256` を照合しない。**未承認 bytes が生成した測定値を正規 receipt として
  登録しうる**。既存の official floor 系には `$0`・commit blob を殺すテストがあり、
  certify 系だけが非対称に緩い。新規 certified artifact 種を足す前に閉じるべきである
  ({{T:certify-job-script-binding}})
- **段 3 は 2 レンズとも read-only の静的検査で、pytest は実走していない。**
  親も本 wave では実装差分を作っていないため、受入は形式検査だけに絞った
- **手続き上の逸脱を記録する。** 段 4 で「実装しない」と裁定したため段 5・6 を飛ばした。
  `DW-C00` の軽量版条件には該当しない (設計択一が割れ、受理集合が動きうる) と段 1 で判定し、
  段 2・3 は省かずに回した。結果として実装子とレビュー子は 1 本も起動していない。
  **もう 1 件** — 入口は wave 開始時に自己改善契約の 2 節を読めと命じているが、親は
  handoff の候補節だけ作り、契約本体を読んだのは段 8 だった。候補の記録自体は wave 中に
  行えていたため実害は無い。段 8 で候補 2 件を裁定したが、いずれも**既存命令の不遵守**であって
  命令の欠陥ではないため (入口は既に「F/D 番号の記憶で代用してはならない」と書いている)、
  reference・入口とも編集しない
