## 本文

- **段 3 の敵対 2 レンズが独立に「B (adapter) は発火しないので落とせ」と結論したが、
  親は実装すると裁定した。** 根拠は D734 決定 4 が「実装許可と正式測定の認可を分離する」と
  既に決めていることである。「まだ測れない」ことは裁定として実装を止める理由にならない。
  ただし plan のままは実装せず、両レンズが見つけた行き止まりを塞ぐ 8 件を scope 内で直させた。
  レンズの観測 (本 wave 完了後も production の registry / receipt は 0 件、床値成果物と
  受理集合は不変) は正しいので、記録側でその上限を守った。
- **段 1 brief の誤りを 3 件受け入れた。** とくに「core は create-only 分類受領証を持つ」は誤りで、
  core は receipt mapping を返すだけである。したがって「API の形で守れば D510 決定 4 を満たす」
  という brief の前提は成立しない。{{D:s8b-adapter-does-not-close-output-first-classification}} で
  限界の明記を実装と同格の成果物にした。
- **truth table を起こす過程で、8b の再走経路が 1 本しかないと実測で判明した。**
  core は次 ordinal の start を「直前が retryable-failure の terminal」か「検証済み recovery」の
  どちらかでしか認可せず、前者は理由が genesis の retryable 集合に属することを要求する。
  8b のその集合は空なので retryable-failure の terminal を作れない。
  **8b で落ちた attempt を測り直せるのは検証済み recovery だけである。**
  そしてその recovery も admission 層で塞がっている ({{T:s8b-recovery-ordinal-authorization}})。
  つまり D739 の復帰機構は registry 側が完成しても今日まだ発火しない。
- **変異が敵対レビュー 3 本の見落としを 3 件暴いた。** 最初の probe で MUT-7 / MUT-8 / MUT-11 が
  SURVIVED した。mask を実コードで確認したうえで「gate の固有の力を撃つ負例が無い」= テストの穴と
  判定し、実装を 1 byte も変えずに負例 3 関数 5 node を足した。詳細と方針は
  {{D:mutation-survivor-may-be-a-test-gap}} と
  `output/insights/2026-08-25_t1603-t1604-t1630-8b-production-mutation.md`。
- 段 6 の敵対レビュー 2 本は must-fix を重複除去して 11 件返した。焦点走 17 件が緑でも
  受理できない内容で、最重は (a) process 消失後に handle を復元できず durable な start / claim /
  receipt が揃っていても進めない行き止まり、(b) 公開 dataclass と共有 seal による handle 偽造
  (失敗分類を観測へ昇格でき、`dataclasses.replace` で raw output digest も差し替え可能)、
  (c) `_assert_profile` が statuses と遷移 policy を固定していない、であった。
  統合後の焦点再レビューは closed 9 / partial 2 / regressed 0 と判定し、
  残り 2 件を 3 巡目で閉じた。**partial の 1 件は焦点レビュー子が read-only probe で
  実際に攻撃を通して見せた**もので、親も独立に再構成して閉鎖を確認した。
- fix 1 巡目が holdout 汚染の回帰を 1 件持ち込み、2 巡目で解消した (F335 の 3 例目)。
  親が repo 全体 14538 file を直接走査して範囲を確定している。

### 新規

- {{T:s8b-trusted-launcher-and-collector}} **P1・ユーザー裁定待ち**: 性能出力を読む前に分類を
  確定させる信頼側の起動器と、scheduler accounting を実際に読んで受領証を発行する collector を
  作る。adapter の API 形状だけでは D510 決定 4 は閉じない
  ({{D:s8b-adapter-does-not-close-output-first-classification}})。**親の推奨は
  分類位置の移動と collector を同じ wave で行うこと** — 両者は同じ受領証契約を共有するので、
  分けると 2 度設計することになる。

- {{T:s8b-recovery-ordinal-authorization}} **P1・ユーザー裁定待ち**: 床値の marker-only 状態からの
  ledger 復旧と、検証済み recovery 後の次 ordinal 認可を admission 側で閉じる。
  現行の `consume_attempt_ticket` は retry の trigger を journal 内の失敗した planned session に
  限定しており、registry の recovery event を認可根拠にできない。**8b の再走経路は
  検証済み recovery 1 本だけ**なので、ここが閉じるまで D739 の復帰機構は発火しない。
  これは D496 の禁じる行き止まりである。**親の推奨は両方を同じ wave で閉じること** —
  片方だけ閉じても cell は進めない。

- {{T:s8b-marker-slot-binding}} **P2・ユーザー裁定待ち**: consumed marker に repetition /
  attempt ordinal / schedule digest が無く、同一 cell 内の別 slot へ同じ marker identity を
  持ち込める。段 6 の 2 レンズが独立に指摘した。authoritative な slot ↔ attempt 束縛を
  admission 側に置くか registry 側に置くかの裁定が要る。

- {{T:s8b-private-storage-scanner-scope}} **P2・ユーザー裁定待ち**: private な Git metadata 配下の
  registry / claim / 受領証にも holdout scanner を掛けているため、共通 core が受理する
  bounded text が storage 層で拒否されうる。core と adapter の受理集合が一致しない。
  scanner 対象にするか非 scan の storage primitive を別契約にするかの裁定が要る。

- {{T:s8b-round-repetition-mapping}} **P2**: round は 1 始まり、repetition は非負だが起点未規定、
  attempt ordinal は 0 始まりである。adapter は導出を実装していない。
  production caller を作る wave で写像を凍結する。

- {{T:s8b-admission-root-lock-granularity}} **P3**: adapter の registry 更新が共有 admission root の
  排他 lock を取るため、全 worktree・全 campaign を直列化する。正しさを優先して現状維持としたが、
  直列化が実測で問題になったら registry 単位 lock を検討する。
