## 本文

2026-08-18 のユーザー裁定 ([T-1336] / [T-1337] / [T-1347]) が要求する事前登録の改訂を、
裁定の条件どおり**1 回の再凍結**として発効させた。scope は改訂文書と凍結 record までで、
実装 (judge・registry・role payload・証拠契約) は後続 wave へ分けた。
設計判断は {{D:refreeze-paired-contrast-and-attempt-registry}} に記録した。

**親 brief の前提 3 件が段 3 / 段 6 の敵対レンズに反証された。** (a)「受理集合を広げない」—
床値比較を別の判定式へ置換する裁定は、定義上どこかで受理側を動かす。絶対規律 2 が守るのは
正しさの gate であって性能主張の閾値ではない。不変条件の方を訂正した。(b)「テスト編集不要」—
`test_s8c_preregistration_core.py` が事前登録 §5 の欄名集合と欄名 hash を逐語で pin していた。
実装面の差分が 2 literal 生じたため Codex `role=author` を立てた (D95)。全件検索で、床値欄名の
逐語は同 file 1 箇所、欄名 hash は同 file 1 箇所と歴史 record にだけ在ると確定した。
(c)「8b 文書の編集は凍結鎖を壊さない」— 編集**前から** bytes pin は不一致であり、当該検査が
2026-08-12 のユーザー裁定で保留中のため新たに発火しないだけである。保留は健全性の証明ではない。

**段 3 は 2 レンズとも NO-GO、段 6 も 2 レンズとも NO-GO、焦点再レビューも NO-GO を返した。**
採用した所見はいずれも「規範を書いたが拒否力が足りない」型である。数値欄に型・範囲・単位・向きの
制約が無く恒真にも永久判定不能にもできた。登録した反復数と観測反復数の一致要求が無かった。
失敗分類を性能値の閲覧後に確定でき、良い試行だけを採れた。registry の唯一性が宣言だけで、
複数 registry を走らせて良い方を公開できた。role payload から作業種別名を落としても、
descriptor binding の digest が真の対象と arm から導出されるため識別は残る。8b の §7 と §9 に
床値と再走全拒否を要求する生きた規範が残っていた。fix を 2 巡当てて閉じた。

**refuted と裁定した勧告 1 件。** 段 3 レンズ B の「8b を編集する前に凍結 pin を更新し保留を
解除して再検証せよ、できないなら 8b を編集するな」。bytes の不一致は編集前から存在し、
保留の解除はユーザーの明示命令のみと定められている。子の勧告で機構を再武装しない。

**構造的に本 wave で閉じられない限界 2 件を明記した。** 世代 record の裁定参照は、承認した決定の
番号が台帳統合時に採番されるため record を導入する commit の時点に存在しえない。参照は
**改訂の対象**である決定を指す。また世代 record の保護対象は 8c 本文と証拠契約だけで、
本改訂が依存する 8b の bytes を束縛しない。両文書を確定してから record を 1 度だけ生成する運用で
補うが、機械閉包ではない。
