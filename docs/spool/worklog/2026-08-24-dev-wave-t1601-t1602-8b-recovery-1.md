## 本文

- この wave は 2026-08-24 の日中に段6 の途中で止まり、夜に別セッションが引き取って完了させた。
  停止の原因は Codex の利用枠切れである。launcher は output 0 bytes を `f45_missing_output` として
  fail-closed に記録しており、手順の欠落ではない。同じ時間帯に他の wave も同じ理由で一斉に止まった。
  引き取り側は再開前に read-only の probe を 1 本投げて Codex の可用性を実測してから着手した。
- 引き取り時に稼働中の並行セッションを列挙し、実装面の重複が無いことを確かめた。本 wave が所有する
  3 file はいずれも稼働中のどのセッションの編集面とも交差しない。停止中の別 wave が test file を
  1 つ共有するが、その wave は非稼働である。
- 設計判断は {{D:recovery-is-a-dedicated-core-row}} と
  {{D:core-verifies-receipts-and-never-collects-them}} に置いた。
- 段6 の敵対レビュー 2 本は NO-GO で、genesis policy 束縛、reason 型、direct replay、
  starttime 同値比較を real として採用した。3 file 横断で一枚岩のため fix を 1 本へ寄せ、
  4 巡かけて閉じた。焦点再レビューは GO で、対応表は closed 3 / partial 0 / regressed 0。
- 棄却した所見が 2 件ある。(i) core に `recovery` という名前を足すだけで 8c が受理するという懸念は、
  schema lookup が先に立つため 8c profile に event が無い限り従来の unknown-event 拒否が残る。
  (ii) 専用 recovery row に primary 値が直接混入するという懸念は、exact key 集合が
  raw / report / observation / primary / terminal status を除外して拒否する。
  どちらも変異検査で裏取りした。
- 段4 で「4 file の変更を operational recovery の完了と呼ぶのは過大」という所見を real として採用し、
  完了の名前を「semantic core と exact evidence contract」に限定した。scheduler accounting を
  実際に読む collector、receipt の store、facade、journal、stats consumer はいずれも未配線であり、
  durable な 8b registry / receipt は 0 件である。したがって
  **実運用上「中断から復帰できるようになった」とは記録しない。**
- 変異 matrix は baseline PASSED、事前登録 12 件すべて KILLED、期待 node 集合と実測の完全一致で
  閉じた (SURVIVED / MISMATCH / TIMEOUT いずれも 0)。逐語の台帳は
  `output/insights/2026-08-24_t1601-t1602-8b-recovery-mutation.md` に置いた。
  同じ入力を 2 層が拒否する 2 件は、片層だけ落としても他層が拾ってしまうため両層を 1 変異として
  累積適用した。片層変異の生存を検出力の証拠にしない。
- 変異検査で 1 件だけ注記が要る。復帰 row の exact key 集合へ鍵を 1 つ足す変異は、狙った負例
  (primary 注入が受理へ反転する) と同時に、正例側も「必須の鍵が足りない」で落とす。8b の
  exact-key 契約が「過不足なし」を要求する以上、この 2 方向を分ける単一理由の変異は作れない。
  同じ 1 つの gate による 1 つの原因ではあるが、落ちる node は広い。同じ理由で、core の
  semantic event 集合から復帰を外す変異も復帰関連テストを一括で落とす。どちらも
  「gate 1 つ・原因 1 つ・node 多数」として記録し、node 数の多さを検出力の広さと読み替えない。
- 待ち手について 1 つ実測した。長時間走る producer の待ち手を親の前景で張ると、親側の実行時間上限で
  待ち手だけが先に死ぬ。producer は detach してあるので生き続けるが、外形は「待ちが終わった」に
  見える。既知の型であり、背景の待ち手へ張り直して復旧した。
- 変異本走の source には repo の独立 local clone を使った。`mutation_worktree.py` は primary
  worktree の未追跡ファイルまで含めた status を走行前後で比較するため、main に未追跡の
  worktree 置き場が見えていると、無関係な並行セッションがその下を触るだけで共有木事後検査が
  落ちる。この前提は既に別 wave が実測している。
