## 本文

- 依頼は [T-361] (Lustre の flock が bnode 間で効くか) と [T-362] (NQSV の walltime 超過が
  SIGTERM か SIGKILL か) の実測。D130 決定 (3) の条件 2 / 3 にあたる
- **production コードの差分はゼロ**である。追加したのは `output/insights/` 配下の使い捨て
  probe と login 側 controller だけ。したがって**変異 matrix と受入全走は対象外**とする ((128) と同じ射程)
- **[T-362] は危険側で決着した。** NQSV 自身が stderr へ
  `%NQSV(INFO): Batch job received signal SIGKILL. (Exceeded per-req elapse time limit)` と出力する。
  signal 種別を「観測されなかったこと」から推定したのではない。3 層 (bash / Python 親 /
  `start_new_session` の孫) いずれにも signal 受信記録がなく、canary は `MUTATED` のまま =
  **`finally` が走っていない**。既定構成は `dispatch_compute._job_script` が現に使う構成と同じ。
  **D130 条件 3 は既定構成では不充足**。詳細は {{D:t362-walltime-sigkill}}
- **[T-361] は排他されたが確定は保留。** `bnode001`/`bnode005` の間で `/work`・`/home` とも
  cross-node 6/6 `BLOCKED`、計算ノード側 mount も `flock` あり `localflock` なし。
  自己検査 (backing object の nonce 照合、両 bnode での陽性・陰性対照、最深 mount 解決、
  全 trial 通しの long-hold) はすべて通過。**ただし controller が実行時欠陥で落ちた回の attempt で
  あり `qstat -J -f` の Execution Host 照合が未完のため、probe は `dangerous` を `false` では
  なく `null` に保った。** 後から安全側へ倒していない
- **親の裁定の誤りを 2 件、独立レビューが訂正した**
  - 「復元は I/O 数本で終わるので秒オーダーの grace で間に合う」は**誤り**。`_restore_targets` の
    手前に `_stop_process` があり pytest 子へ SIGTERM 後 5 秒 + SIGKILL 後 5 秒を待つ。
    cleanup 下限は約 10 秒 + 復元である
  - 「投入・回収・費用管理は親の投入工程に委ねる」は**誤り**。段 6 の 2 レビューが独立に同じ指摘を
    し、手作業に委ねると argv・hash・deadline・会計・追跡確認のいずれかが抜けたまま
    都合のよい部分結果を authoritative へ格上げできると突いた。login 側 controller を新設した
- **実測前に判定基準を事前登録した。** 自己検査 (C1〜C6 / D1〜D4) が通らない実行の観測は読まない、
  未観測 signal は `SIGKILL` と断定せず `UNKNOWN` と記録する、を固定してから測った
- **静的検査では捕まらない欠陥を実走が 1 件出した。** controller が `QUE_DEADLINE_SECONDS` という
  未定義名を参照して NameError で落ちた (定義側は `QUEUE_DEADLINE_SECONDS`)。構文検査と AST 検査は
  通る型で、`python3 -m pyflakes` を全 driver へ走らせて同種がこの 1 件だけと確認した。
  **このとき投入済みだった request 882038 は完走したが、controller の照合なしに安全を宣言しない
  fail-closed が意図どおり働き、verdict は保留のままだった**
- **controller に未解決 session の回収経路が無く wave が前へ進めなくなった。** crash 後に
  投入済み attempt が残ると新規投入を永久に始められない。scheduler と会計から終端を実証できた
  attempt だけを解決する `resolve` を足し、qwait raw が無い場合に備えて **`.e` の NQSV 会計 block +
  `qstat` 不在**を第 3 の終端証拠として受理するようにした ({{F:controller-no-recovery-path}})
- **admissibility の連言に副作用があった。** cleanup 順序の確認を連言に入れたため、
  **SIGKILL で cleanup が走らないという危険な結末そのものが `admissible: false` を生む**。
  「probe が正しく危険を捉えた」ことと「安全な attempt だった」ことを同じ連言で表しており、
  危険側の観測は構造的に authoritative になれない。次 wave で 2 field へ分ける
- **やり残し:** T-362 の split-warning leg と mitigation leg (`--accept-sigterm=yes` +
  `elapstim_req="max,warn"`) は投入されなかった。controller が t362-default を
  `admissible: false` (racctjob / racctreq が該当レコードを返さない) と判定して恒久停止したため。
  **したがって「捕捉可能な構成が存在するか」は未解決**である
- 資源: 投入 request 3 本、requested node-min 累計 13 (上限 40)、`rbudgetcheck` の減少は
  **0.29 point** (313.97 → 313.68)。node-minute → point の換算率は未確定であり推測しない
- エージェント工数: codex 子 12 本 (段 2 プラン 1、段 3 敵対 2、段 5 実装 2 + 報告再生成 2、
  段 6 レビュー 2 + 焦点再レビュー 1、fix 4 本のうち一部は並行)。Pegasus request 3 本
- 段 3 の敵対 2 レンズと段 6 のレビュー 2 本 + 焦点再レビューが、実測前に false GO を生む経路を
  **計 33 件** (blocker 19 件を含む) 検出し、すべて裁定して塞いだ。とくに
  「自己検査不合格を `dangerous: false` と符号化していた」は事前登録に正面から反する欠陥だった
