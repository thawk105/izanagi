- **依頼の見込み「2 件は同じ probe で満たせる」は、段 1 では判定できず実測で判定した。** 依頼は

  条件関門が実在し、`BACKOFF_FIXED` の `inert_values` に `-1` が載っている」ところまでで、
  到達するか否かは走らせるまで決まらなかった。**実測後に完了判定を分けた。**
- **実測 1 は probe を 1 byte も変えずに投入した。** `0:996644.nqsv`、bnode040、束縛 commit
  `3b80b5a96`、`bound_paths_clean=True`、`login_node_rejected=True`、probe 内 26.3 秒。
  S1〜S5 go、**S6 は `S6_BUILD_NOT_ATTEMPTED` で blocked**、overall no-go。条件関門は
  `supply=red/configure-failed, meaning=unestablished/meaning-witness-undeclared` で拒否した。
  **`stock-inert-*` の比較そのものへ到達していない。** 既存の受領証 2 件 (2026-08-10) には
  `condition_gates` が 0 件で、t316 実経路での条件関門の実測は本 wave が最初である。
- **受領証には reason code しか残らず、原因が分からなかった。** `evidence` は D1849 により
  受領証へ出さず、probe の例外も `terminal_status/reason_code` しか載せていなかった。段 4 で、
  拒否の直前に `evidence.get("detail")` を job stderr へ出す局所変更を裁定し
  ({{D:condition-gate-rejection-detail-to-job-stderr}})、新しい commit を束縛して再投入した。
- **実測 2 が原因を直接証拠で確定させた。** `0:996829.nqsv`、bnode016、束縛 commit `fecb4f709`、
  25.7 秒。受領証の S6 は実測 1 と文面まで完全一致し、job stderr に
  `supply detail=successful process wrote stderr=b'CMake Warning: Manually-specified variables were
  not used by the project: CCBENCH_BACKOFF_FIXED / IZANAGI_GFLAGS_SRC_HEAD / IZANAGI_GLOG_SRC_HEAD /
  RULE_LAUNCH_COMPILE'` が出た。**CMake は rc=0 で成功しており、stderr 非空で赤になっていた。**

  ({{D:t316-inert-unreachable-on-stock-tree}})。
- **段 7 の記録を書く直前に、これが既知型の再発だと分かった。** F934「patch 由来 define の条件関門が、
  patch を materialize しない driver では構造的に通らない」が既に独立 2 例を記録しており、
  **t316 は 3 例目である**。F855 は `RULE_LAUNCH_COMPILE` を gflags / glog の install build から
  流用する点まで名指ししていた。**親は段 1 の一次資料に `docs/failures.md` を含めず、段 3 の
  レンズにも渡さなかった。** 絶対規律 6 は failures の型タグを攻撃面に含めることを求めている。
  新しい F は作らず、F934 と F855 へ再発を追記した。

  親が段 1 brief に書いた「唯一の計算ノード driver」は撤回した — backoff_sweep 経路は 2026-09-07 に
  bnode039 で同じ evaluator の緑へ到達している。

  拒否例外が置換され、受領証の error が拒否情報から出力障害へ変わる。fix 後、stderr の `write` が
  3 型の例外を投げても拒否が維持されることを実 CMake・実 gate を通す正例で検査した。
