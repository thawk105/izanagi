  という同じ結論に達したため、段 4 で「本 wave は実装しない」と裁定した** (DW-S04 の `4 → 7 → 8 → 9`)。
  plan の採否判定も 2 レンズの採否判定もすべて **no**。実装面の差分は 0 行である。

- **最も重い欠陥は、core の等値検査と台帳専用 4 語の衝突である。**
  `attempt_registry_core.py` は terminal の `failure_reason` が観測前分類の理由と等しいことを要求し、
  その直後の null matrix は同じ値が retryable 集合 (v2 では台帳専用の 4 語) に入ることを要求する。
  launcher の分類語彙は `competing_process` / `launch_failure` で 4 語と互いに素なので、
  **両方を同時に満たす値が存在せず、v2 の terminal 行は 1 行も書けない。**
  封印証拠の検査 hook は両方より**後**に呼ばれるので、C1b が作ろうとしていた機構をどれだけ
  強くしても解けない。レンズ A が 4 語を直接投入した結果、全件が等値で落ち validator 呼出しは 0 回だった。
  親が最初に出した修正案 (v2 では分類語彙を 4 語にする) はレンズ A に否定された —
  4 語のうち 2 語は `open()` の後にしか判明せず、分類は `open()` の前に起きるためである。
- **他に 6 件の欠陥と 2 件の偽造経路を実測で確定した。** 契約表の field は 24 でなく 23。
  `campaign_record` は 27 でなく exact 30 key (独立 trust root と集合等値)。3 引数の封印発行子は
  attempt 束縛に要る 3 digest を取得できない。証拠文書は三軸 literal の運び手を 5 field 以上含むため
  guarded writer が必ず拒否する。再導出 6 枝が campaign の実 precedence と一致しない。
  `exec_failures` の出所が契約と campaign で食い違い実測値が異なる。非有限値の不変条件が自己矛盾。
  封印の issuer table は table 直接 insert・private issuer 直呼び・`__reduce_ex__` で迂回でき、
  test 用 launcher が fake fact から production の封印を発行できる。
