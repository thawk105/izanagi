## 本文

- `/cleanup-branches` をクラス 2 で実行し、**branch 95 本 (121 → 33)** と
  **worktree 14 本 (38 → 24)** を撤去した。
- §1 の必須監査 (`tools/audit_dangling_commits.py --offrepo-root ...`) は argv 長超過で
  rc=2 (実行不能) を返し、同節の規定でいったん削除を全面停止した
  ({{F:dangling-audit-argv-overflow}})。**ユーザー指示で再開した。** 根拠は「対象はすべて main の
  祖先であり、枝を消しても commit は main から到達可能なまま」で、監査が探す**到達不能な変更は
  ahead=0 の削除では新たに生じない**。探索根を外した repo 内のみの監査は rc=1 で完走した
  (off-repo 探索は発見を**抑止する**方向にしか効かないので、repo 内のみは過剰報告側 = 安全側)。
  報告された到達不能 30 commit が削除対象の tip と 1 件も一致しないことを機械照合で確認した
  ({{T:triage-30-unreachable-commits}})。
- worktree は道具が login node で構造的に rc=2 になるため、`occupancy-unreadable-cwd-blocks-cleanup`
  の手順に従い**道具が見る条件を 1 つずつ自分で実測**して畳んだ。実測した条件は、占有者ゼロ・
  HEAD が main の祖先・clean・直近 2 時間に書き込みなし・計算ノード job の書き戻し先でない・
  lock なし・reflog の全 SHA が main から到達可能。
- **reflog 検査が 2 本を止めた。** `worktree-dev-wave-flaky-quarantine` (4 commit) と
  `worktree-dev-wave-lease-serialization-ban` (1 commit) の reflog に、main から到達できない
  revert・merge・fragment 改訂が残っていた。branch を消せば到達不能になるため撤去しない。
  ahead=0 だけを見ていれば消していた — **reflog 検査はこの掃除で実際に効いた**。
- 掃除の途中で罠を 3 件実測した。3 件目 ({{F:occupancy-check-relative-path-vacuous}}) は
  自分で踏んだ誤りで、worktree の中から**相対 path** で占有検査を呼び、実在しない path を
  検査させて 22 本すべてを偽の「撤去可」と判定していた。`scanned=0` に気づいて絶対 path で
  やり直し、真の占有 1 本と直近書き込み 3 本を検出した。
- `.claude/commands/cleanup-branches.md` への手順追記は、同 file が予算 4,000 bytes に対し
  3,949 bytes で**残り 51 bytes** しかなく、意味を保った縮約も同時に要るため裁定へ返す。
