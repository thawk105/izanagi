## 本文

- `/cleanup-branches` をクラス 2 で実行した。棚卸しは全量完了し、**安全条件を満たす branch 84 本を
  削除した**。worktree は 1 本も畳んでいない。
- §1 の必須監査 (`tools/audit_dangling_commits.py --offrepo-root ...`) は argv 長超過で
  rc=2 (実行不能) を返し、同節の規定によりいったん削除を全面停止した
  ({{F:dangling-audit-argv-overflow}})。**ユーザーの指示を受けて再開した。**
  再開の根拠は「84 本はすべて main の祖先であり、枝を消しても commit は main から到達可能なまま
  である」点で、監査が探す**到達不能な変更は ahead=0 の削除では新たに生じない**。
  rc2 停止は一律の安全側規則で、この対象集合には効いていなかった。
- 再開前に、探索根を外した **repo 内だけの監査を完走させた (rc=1)**。off-repo 探索は
  発見を**抑止する**方向にしか効かないため、repo 内のみの結果は過剰報告側に倒れる = 安全側である。
  報告された到達不能 30 commit が削除対象 84 本の tip と 1 件も一致しないことを機械照合で確認した
  ({{T:triage-30-unreachable-commits}} で救出判断を行う)。
- 削除は `git branch -d` を 1 本ずつ実行した。84 本すべて rc=0 で、取り込み漏れによる拒否は
  1 件も出なかった。削除直前に候補を取り直したが、初回一覧と完全に一致した (churn なし)。
  local branch は 121 本から 44 本になった。
- worktree が畳めない理由は 2 つに分かれた。`rulings-20260821-calibration-registration` は
  pid 1100953 が cwd を掴んだままの**真の占有**。残りは共有 login node (pegasus02) の性質で
  rc=2 (判定不能) になる。迂回はしていない (memory `dw-o28-cleanup-blocked-on-login-node`)。
- 罠 2 件を実測し {{F:occupancy-check-wrapper-self-match}} / {{F:dangling-audit-argv-overflow}} へ
  記録した。前者は**この掃除で実際に踏み、偽の「全件占有」を一度信じかけた**。
- `.claude/commands/cleanup-branches.md` への手順追記 (検査を wrapper で包まない) は、
  同 file が予算 4,000 bytes に対し 3,949 bytes で**残り 51 bytes** しかなく、意味を保った縮約も
  同時に必要になるため本 wave では実施せず裁定へ返す (自己改善契約の予算条項)。
- 掃除の実行中も main は進み、worktree と branch が新設され続けた。稼働 wave を巻き込まない
  3 段の弾き (checkout 照合・時刻・`git branch -d`) は全段が想定どおり働いた。
