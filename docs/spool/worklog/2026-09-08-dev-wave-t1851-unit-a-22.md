## 本文

- **前 wave の失敗原因は「条項を束縛先へ一度も通さずに固定した」ことなので、段 1 で
  consumer probe を 7 本通してから契約 v3 を書いた。** 正本は
  `output/insights/2026-09-08_t1851-unit-c1b-sealed-terminal-evidence/parent-probes.md`。
  中核の probe は一時変異を当てた実コードへ台帳行を通し、**正例 5 形すべてが受理された** —
  前 wave が「1 行も書けない」と測った状態が解消していることを実測で示した。
  負例も 7 件測り、**観測に成功した行と未消費の行が測り直しの理由を無検査で受け取る**という
  穴を 2 件見つけて条項にした。負例のうち 1 件は最初、別 gate (phase-order) で落ちていて
  狙った検査の証拠にならなかったので、条件を変えて帰属を確かめ直した。
- **段 3 の敵対レンズ 2 本がどちらも「この plan では実体化できない」と判定した。** 所見のうち
  **3 件は plan ではなく契約そのものを変えるもの**で、親が現物で裏取りして採用した。
  (a) 証拠の識別欄を予約情報と全件一致で縛る条項が、**呼び手が選べる値を権威に据えていた** —
  永続的な権威側にあるのは cell・レコード数・スレッド数・作業負荷・実行識別子だけで、
  通し番号・巡回番号・種別・契機・再試行回数には権威が無い。
  (b) 再導出の正本を計測 campaign の意味とだけ書いたが、**起動層のほうが捕捉する例外が 1 つ多く**、
  その例外では起動層は終端行を作るのに campaign 側には対応する session 行が生まれない。
  (c) 凍結固定の閉包を名前・経路・file 全体の要約値の 3 種類しか引いておらず、
  **production 全体を構文走査して file 集合を等値検査する登録簿**を落としていた。
- **(a) は本 wave で最も価値のある所見である。** 契約は実行失敗数について「等値でだけ縛り、
  各回の実行成否は証明しない」と正しく射程を切っていたのに、識別欄では同じ切り方をしていなかった。
  訂正版では権威のある群と無い群に分け、後者は要約値 1 本にまとめて縛り、帳簿上の位置が
  正しいとは主張しない形にした。{{D:evidence-identity-split-by-authority}}。
- **(b) は「枝の順序」と「入力の値域」を分けて書く必要を示した。** 訂正版では枝順は campaign を
  正本にしつつ、入力値域は起動層の捕捉集合であると明記し、捕捉集合の 3 語の外にある型名を
  拒否する条項を足した。**「campaign が同じ入力で同じ語を出す」とは主張しない。**
  {{D:rederivation-branch-order-and-input-domain-are-separate}}。
- **恒真になりうる拒否が 2 件見つかった。** 未消費の枝の拒否条項は、上流の封印経路に同じ枝の
  正例が存在しない (再導出はこの状態語を出さない) ため、常に拒否する誤実装が緑のまま通る。
  終端失敗の枝だけ旧欄のまま残す改変も、v1 は既定が同じで差が出ず v2 は後段で隠れるため生存する。
  **どちらも D1522 (上流が拒否する形でも下層の実体を直接呼ぶ) で正例を作る。**
- **親自身の実測にも記載不備が 2 件あった。** 中核 probe は v2 の無条件拒否掛け金を外して
  測っており、その 1 点を書いていなかった。測定自体は有効 (掛け金は本単位が置き換える対象で、
  測ったのはその手前の 2 検査) だが、「端から端まで通った」という一般化は取り消した。
  閉包 probe も上記 (c) のとおり不完全だった。いずれも追記で訂正した (規律 7)。
- **規模は上限を超える。** plan は葉を 850 行と自分で宣言しながら見積り表には 500〜700 と
  書いており内部矛盾していた。レンズ B の再見積りは production 1,580〜2,120 / test 1,900〜2,850 で、
  裁定済み上限を超える。**実装子の 3 本分割も成立しない** — 2 本目と 3 本目は 4 方向に依存して
  おり所有が素集合でない。訂正した計画では実装子を 2 本の直列にした。
  葉は他の 8 file を取り込まない純関数層なので単独で閉じる。
- **ユーザーは「収まらないなら切る判断は次の親に任せる。中途半端な分割は却下済みで、切るなら
  契約の文書だけまで戻る」と事前に定めていた。中途半端な分割はしていない。**
  前 wave との違いは、**次の担当が段 5 (実装) から始められること**である。
- **検査 (親が実走):** 子 3 本とも rc=0、`check_codex_output` 3 本とも rc=0、
  `check_docs` rc=0、`check_wave_startup --mode resume` rc=0、
  `check_ai_provenance` full 監査 rc=0 (8,602 件、新規違反なし)、
  `test_check_docs.py` の焦点走 571 passed / 3 skipped。
- **受入全走は `child-green` にならなかった。** 21,594 passed / 68 skipped のうち **1 件が赤**で、
  受入所要台帳の被覆率 gate が 26 / 29 = 89.655172% と閾値 0.90 を 1 node 分割った。
  単独再走でも同じ数字が出る決定的な赤で flake ではない。**本 wave への帰属は無い** —
  本 wave の commit 4 本は文書だけを触り test も production も 1 行も変えていないうえ、
  同じ branch の前 wave の受入は緑だった。台帳の最終更新以降に main が test file を
  20 本以上変えており、F684 が記録した「suite の成長が閾値を跨ぐ」機序の再発である。
  **D1341 により land しないので修復せず記録に留めた。緑として扱っていない。**
