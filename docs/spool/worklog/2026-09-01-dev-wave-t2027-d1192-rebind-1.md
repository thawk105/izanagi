## 本文

- 本 wave は D1192 択 (1) の実装を作る依頼として始まったが、**作業中に別 session が同じ実装
  (`2e35a2596`) を main へ land した**。取り込んだ 8 file は main と byte 一致であり、
  本 wave の固有の成果は**独立監査とレビューが見つけた受理境界の欠陥 4 件の修正**である。
  実装そのものの記録は着地した wave 側にあるので再掲しない。
- 未着地の実装を**素性不明の外部作業物として内容監査**した (規律 6)。file 単位の判定は
  実装面 8 file を採り、docs 12 file を捨てる。捨てた理由の一つは、spool fragment の 1 件が
  「recovery land」を主張していたが監査時点では未着地だったことである (取り込み前の local main は
  `s8b-compiler-input/v1` のままだった)。採ると台帳へ虚偽の着地記録が入る。
- **着地した実装の plan・敵対相談 2 本・段 6 レビューがいずれも見落とした欠陥を、
  親の独立監査が 3 件、本 wave の敵対レビューがさらに 1 件見つけた。** うち 3 件は実行して
  再現を確認している。
  (A) v2 の入力 path が `"."` のとき `PurePosixPath(".").parts` が空 tuple なので正規化を通過し、
  `parts[-1]` が `IndexError` を投げる。
  (R1) 入力 path の先頭が正確に `//` のとき `abspath`/`normpath` が二重 slash を保存するため、
  filesystem 根への相対化が `ValueError` を投げる。
  **(A) と (R1) は同族である。** 呼び手 (`s8b_binary_admission`、`buildcache`) はいずれも
  `except CompilerInputError` しか持たないため、binary admission receipt の発行器が
  anomaly の構造化拒否ではなく異常終了する。v1 は同じ入力を構造化拒否または正規化で
  処理していたので**受理境界の退行**である。この型を
  {{F:uncaught-non-domain-exception-at-admission-boundary}} へ記録し、再発検知を
  「拒否の有無ではなく**拒否の型**を assert する」に据えた。
  (B) masstree 根の解決が `dependency_receipt` 保持時から descriptor-bound build 全件へ広がって
  いた。external input を admit しない build に根は不要であり、D1192 が要求していない前提条件を
  足していた。読めない build があれば、直そうとしている赤が別の無条件赤へ置き換わるだけである。
  (C) `_strict_root` が symlink 経由で綴った根を拒否していた (旧経路は解決して受理)。
  実測: `/work/SFC/tanab/izanagi` は `/work/1/SFC/tanab/izanagi` への symlink で拒否される。
- 段 2・3 は着地した wave の成果物を `DW-C00` の規定に従い流用した (変更面の骨格が同一、
  再検査は段 6 へ寄せる)。親が plan と敵対相談 2 本を全文読んで判定してから流用しており、
  context 無しの子出力をレビュー結果に数えてはいない。
- 段 6 の敵対レビューが出した real 所見 2 件を **scope 外**と裁定した。
  (R2) oracle の descriptor 経路には現在の masstree 根が届かない。親が裏取りしたところ、
  `pipeline.py` と `s8b_oracle_driver.py` のいずれにも FetchContent 基底の供給が無く
  (両 file を全文検索して 0 件)、**再束縛先の安定した根がそもそも存在しない**経路だった。
  v2 化の前も同じ cache hit は `external compiler input is unavailable` で落ちており、
  本 wave が入れた欠陥ではない。**D1192 の「run 間の cache 再利用は失わない」は、
  床値の descriptor 経路についてだけ満たされ、oracle 経路では未達である。**
  (R3) floor の現在の根の供給が `sort_best` の同居に依存する。production の `build_cells`
  呼び手 2 箇所はいずれも `enumerate_cells` の完全列挙を渡すので到達しない。`DW-G04` により
  発火条件を実在 artifact で名指しできないため実装しない。
- レビューが挙げた「`filesystem` tag で stale 根を受理できる」は **refuted** とした。
  指摘された「external を許すのに根が無い」組み合わせは既存テスト 11 件が使う設計どおりの
  mode であり、修正 (B) 以降は認可された経路から到達しない。受領書は `filesystem` entry に
  ついて「現在の根で検証した」と主張していない。**ただし保護の射程は明記する** —
  現在の canonical 根へ再束縛するのは `fetchcontent-masstree` と分類された入力だけである。
- 「production floor の cache identity が run-local な source root を含むので run 間 hit が
  成立しない」も real だが backlog とした。`buildcache.py` のコメント自身が既知と記している。
  **本 wave が直す赤とは別の話である** — [T-2043] の実測どおり床値 job の赤は cache hit 条件では
  なく無条件で、同一 job 内で作業用 directory を破棄してから受領書発行へ進むために起きる (F754)。
- 変異は 10 件を登録し、**10/10 KILLED、baseline 緑**で完走した。期待 node は推測せず、
  全件 SURVIVED 期待の probe 走行で実測してから本走で照合した (`DW-M07` / `DW-M08` の既定手順)。
  本 wave が追加した 3 変異 (M11/M13/M14) はいずれも
  本 wave が追加したテストだけを落とす単一理由の kill であり、修正が実際に受理集合を
  動かしていることを示す。逐語は insight へ凍結した。
- 段 6 のレンズ A は 1 回目が内容完結のまま `## 総括` 見出しを欠いて `f43_fragment` で不採用に
  なり、166,929 CLI token を棄却した。gate は迂回せず prompt を是正して投げ直した。
  1 回目が出した所見は親が実測で確認してから採用している。
- 取り込み元 branch が wave の途中で並行 session に撤去された事象を F251 の再発として記録した。
- 工数: Codex 子 5 本 (実装 1、敵対レビュー 3 = 不採用 1 回を含む、fix 1)。
