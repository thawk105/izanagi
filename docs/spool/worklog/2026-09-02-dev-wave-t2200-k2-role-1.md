## 本文

- **既存 role の bytes は 1 byte も変えていない。** `coder-v4-autonomous` の遮断条項は
  D1429 が既定にした K2 投入と必ず衝突するが、書き換えると K0/K1 アームの対照が壊れる。
  sibling `coder-v4-autonomous-k2` を足す形にした。実測で確認した不変性は、既存 13 role の
  `.md` と既存 13 個の adapter JSON に対する pathspec 限定 `git diff --exit-code` の rc=0 である。
- **段 3 のレンズ A が親の知識境界案を反証した。** 親は「未評価候補の性能を使わない」と書く
  つもりだったが、そう書くと公開文献や過去 campaign で**測定済み**の性能まで落ちる。
  禁じるべきは候補が未評価かどうかという状態ではなく、**どの source にも根拠を持たない数値を
  測定値として扱うこと**である。この差は K2 の受理集合を実際に変える。role 本文を書き換えた。
- **親は brief で D12/D21 の帰属を誤った。** 「未評価候補の性能は評価中立性の側」と書いたが、
  D12 は材料レポートでの事実と判定の分離、D21 は critic への online digest 非開示であり、
  合成側の coder には直接かからない。段 2 待機中に親が一次資料で自ら訂正し、段 3 レンズ A も
  独立に同じ判定を出した。結論 (K2 でも遮断) は変わらず、理由が別だった。
- **段 6 のレンズ C が、性能値チャネルを見せる入力例を暴いた。** 新 role の `whiteboard` 例は
  兄弟 role から引き継いで `delta_pct: -1.2` と書いてあった。`p3_s4_loop.py` は段 4 で
  `delta_pct` が非 `None` なら `WhiteboardLeakError` (勝ち筋チャネルの混入、規律 2/6) として
  fail-closed する。つまり例は loop が塞いでいる性能値をそのまま見せていた。5 field へ直し
  `delta_pct` を `null` にした。**既存の兄弟 role にも同じ古い例が残っている** — bytes 凍結と
  対照維持のため触らず、裁定パッケージへ送る。
- **段 6 のレンズ C が、親の「機械検査する」という記述も過大だと反証した。** 参照整合性検査は
  `policy.py` に実在し単体テストが実 validator を通るが、この role は `consumer: null` で
  Codex runtime は全件 blocked、launcher は `validate_input_semantics` しか呼ばない。
  実出力経路には未配線で自動では発火しない。検査は残したまま、role 本文と設計文書を
  「`validate_output_semantics` を通した場合は機械検査する。自動では発火しない」へ限定した。
- **段 6 のレンズ D が親の変異事前登録の欠陥を出した。** 初回 M2 (backoff 分岐の membership から
  K2 を外す) は、membership の内側に参照整合性検査がネストしているため 2 機構を同時に迂回し、
  赤理由が 1 つに絞れなかった。文法 rejection だけを迂回する形へ再照準した ({{F:mutation-nested-guard-defeats-single-reason}})。
  初回登録は消さず erratum として残した。
- **`.claude/agents/*.md` は凍結登録簿と全単射で束縛されている。** file を 1 本足すだけでは
  既存検査が赤になる。親の段 1 brief は閉包を 7 面しか挙げておらず、段 2 プランと段 3 レンズ B が
  残り 2 面 (`.codex/agents/README.md` の件数、`policy.py` の 6 箇所) を出した。最終的な閉包は 9 面。
- **adapter 1 枚は親が waiver で書いた。** codex の sandbox が `.codex/` を read-only にするため
  実装子・fix 子のいずれも書けない (双方の拒否を実測)。先行事例 `8730a6e9` と同じく D105 の
  waiver 経路で親が renderer 出力を適用し、waiver を機械会計させるため別 commit に分けた。
  `check_ai_provenance.py` は `reason=codex-sandbox-readonly-dotcodex ratified=2026-08-18` として
  実際に計上した。初回生成物の 17790 bytes / sha256 `a41de8b5...` は Codex 実装子が独立に算出した
  値と一致した。
- **段 5 の 1 回目の投入を空費した。** 実装子の投げ文に書いた repo root と必読 path が親の
  worktree を指していたため、子は sandbox の書込み境界に当たって 1 byte も書かずに戻った。
  `.done` は 0、`check_codex_output.py` も rc=0 で、**成功と見分けがつかない**
  ({{F:author-prompt-paths-must-name-child-worktree}})。
- **変異走は投入形で 3 回落ちた。** login node で `--runner-mode local` は不可、spec に `schema` と
  `timeout_seconds` が必須、`run_tests.py` には `--force-dispatch` が必須 (runbook §7.4 に既記載)。
  いずれも実装の赤ではない。最終走は 3/3 KILLED で期待 node と完全一致、MISMATCH 0 / SURVIVED 0。
- 焦点走で `test_profiler_directive.py::test_derived_directive_is_accepted_by_the_role_policy_check` が
  `ModuleNotFoundError: No module named 'codex_roles'` で赤になったが、単独走でも同じで、
  本 wave の差分は sys.path に触れていない。file 選択走の import path 偽赤として受入全走で決着させる。
- **この wave は K2 role の実走行をしていない。** agent 登録は session 開始時に読まれるため、
  role を作った session からは行使できない。言えるのは契約が実在し、その一部が機械検査を通り、
  既存アームの対照が bytes 単位で保たれていることまでである。
