## 本文

- ユーザー裁定。**「一回性の制約を直します。性能測定はこのコミット ID と (環境) 条件で
  やりましたくらいの参考情報付与で良いと百回くらい言っている」。**
  裁定本文は {{D:perf-measurement-no-one-shot-enforcement}} /
  {{D:measurement-provenance-is-commit-and-conditions}} / {{D:compute-nodes-are-one-environment}}。
- **床値実測が止まっていた真因を実測で確定した。** 残骸でも混雑でもない。
  投入したジョブ (`951456.nqsv`) は計算ノードで実際に走りビルドも通ったが、
  `holdout admission reservation failed: holdout cell key was already consumed by another
  fresh run` で落ちた。**一回性の鍵が既に消費済みだった。**
- **「未実行」という記録が事実と違っていた。** 共有 git dir の消費台帳を読むと、
  役割 `floor_campaign` が **2026-08-24 の run で 12 cell 全部の鍵を消費**している
  (台帳 228 行、うち 96 行が floor_campaign)。2026-08-26 の判定は
  `output/env/pegasus/floor/` の不在だけを見て「未実行」としており、**鍵の台帳を見ていなかった。**
  実体は「一度走って途中で死に、鍵だけ焼けて成果物が残っていない」である。
- **復旧経路は 5 日間止まっていた。** 途中死の救出は既知の課題で 2026-08-22 に裁定され
  実装 wave も立っていたが、その branch は未着地のまま main から 1120 commit 遅れていた
  (最終更新 2026-08-24)。**AI が設計した厳密さが、研究の主経路を 5 日間止めていた。**
- **今夜の再投入は鍵を 1 つも消費していない** (台帳は 228 行のまま)。予約段階で落ちたため、
  状態を悪化させていない。
- **一回性は AI の設計であってユーザー裁定ではない。** 根拠の D434 / D461 のどちらにも
  ユーザー裁定の marker が無いことを実測で確認した。
- **同型が今夜 4 件出た。** AI が起草した細部が「ユーザー裁定」として台帳に残り、
  後続がそれを拘束と読む型である。(a) 床値の一回性、(b) 受入分割の「ノードを揃えた対測定」、
  (c) B-4 事前登録の「予定開始時刻」、(d) 親自身が前夜に確定させた裁定が既存の順序規定
  3 件と抵触していた件。**いずれもユーザーは要求していない。**
- **branch と worktree を掃除した。** worktree 46 → 41、branch 27 → 18。
  安全条件を満たすものだけを撤去し、占有中 1 本・未取り込みの作業が残る 18 個・
  稼働中の wave は残した。到達不能 commit の監査は要確認 22 件を返したが、
  専任セッションが triage 中なのでそちらへ渡した。
- **救出物の二重保管を準備した。** 3 bundle から 51 commit を ref へ展開し、
  **local から消えていた 1 件が bundle にしか無かったこと**を確認したうえで、
  その中身を実際に読める形で復元確認した。push は人間の手番。

## 次の一手差分

### 更新

- [T-088] **P1・前提が事実と違っていた (2026-08-27)**: 「未実行」ではなく
  **「2026-08-24 に一度走って途中で死に、12 cell 全部の一回性の鍵が消費され、成果物が
  残っていない」**が実体である。判定は成果物の不在だけを見て鍵の台帳を見ていなかった。
  一回性の強制は {{D:perf-measurement-no-one-shot-enforcement}} で撤廃したので、
  **撤廃の実装が着地すれば再測定できる**。復旧専用機構は前提条件にしない。
  base: a6aafac680d882ae10fe5cf5f4ba303fd5c3f794b6c06c780bd32cb97fbf5064

### 新規

- {{T:repeal-one-shot-admission-enforcement}} **P1・新規**: 性能測定の一回性強制を実装から
  撤去する ({{D:perf-measurement-no-one-shot-enforcement}})。予約の可否を決める経路から
  一回性 key の照合を外し、台帳は観測履歴の追記だけにする。
  `--confirm-irreversible-pilot-holdout` とその env 伝播も、承認対象が無くなるので外す。
  **既に消費済みの 12 cell が再測定を妨げないことを、実際に床値を再投入して確かめるまでを
  この項の終端とする。** 受理集合を狭めない方向の変更だが、正しさゲートを 1 つも触らないことを
  変異で示す。
- {{T:selection-side-holdout-guard-audit}} **P2・新規**: 一回性を撤去した後、
  「holdout の値を見てから選択・凍結・主張を変えない」がどこで守られているかを棚卸しする。
  一回性が実質的な防壁として働いていた面があれば、選択経路側へ移す。
  **無ければ「守られていない」と正直に記録する** — 恒真な保証を作らない。
- {{T:ai-drafted-strictness-audit}} **P2・新規**: ユーザー裁定の marker を持つ決定のうち、
  **具体的な機構が AI 起草で、ユーザーが要求していない厳密さ**を含むものを洗い出す。
  今夜 4 件が実測で判明した。判定材料は「その機構が `/rulings` の一括承認で確定したか」
  「機構の前提が実測されているか」。**洗い出しの結果は裁定へ返す** — 撤廃の可否は
  ユーザーの判断であり、AI が勝手に緩めない。
