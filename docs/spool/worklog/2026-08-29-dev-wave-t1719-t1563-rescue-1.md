着地済み」であり、救出する差分は存在しない。

**結果: 全 15 件を破棄。着地させる価値のある差分はゼロだった。** 実装面 (D95 決定 2) の

### 撤去の事前検査 (実測値)

破棄判定に伴う 5 worktree と branch 1 本の撤去は、本 wave の終端 (land 後に主 checkout へ
戻ってから) で行う。worktree に隔離された session からは対象への git 操作が機械的に拒否される
ため、この順序以外を取れない。記録 commit の時点までに済ませた検査は次のとおり。

- `tools/check_branch_rescue.py` を 2 回独立に走らせ、いずれも
  `deletion_loss_closure` が `commit_count: 0` / `complete: true` を返した。
  すなわち**この撤去で最後の耐久 root を失う commit は 1 件も無い**。
  入力側の positive tip には 4 worktree の HEAD と branch tip に加え reflog 由来の 2 tip が
  含まれており、reflog 込みで損失ゼロである。
- 2 回とも rc は 2 で、理由は `root-snapshot-moved` 1 件のみだった。これは走行の開始と終了の
  間に repo の root 一覧が動いたという注記であり、同時に 10 本前後の wave が動いている
  この repo では平常の状態である。損失の検出ではない。
- `tools/check_worktree_occupancy.py` を 5 worktree それぞれへ単独・絶対 path で実行し、
  全件 `status: unoccupied` / `issues: []` を得た。走査対象 process 数は各回 2335〜2340 で、
  走査が空振りしていないことも確認した。
- 変異 harness が主 checkout を観測していないことを process 一覧で確認した。主 checkout の
  `git status` を snapshot するのは `tools/mutation_worktree.py` であり
  (`_primary_and_source_roots` が primary worktree を観測 root に含め、`_STATUS_ARGS` は
  `--untracked-files=all` で untracked を 1 件ずつ列挙する)、その process は 0 件だった。
  走行中の `tools/mutation_harness.py` は `--repo` に与えられた自分の worktree だけを見る。
