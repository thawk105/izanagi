## 本文

- **ユーザーの依頼は「フレークテストがあればそれを直してください」だった。**
  `orchestrator/tests/flaky_test_holds.py` に 3 node が hold 登録されており、
  hold は opt-in の抜け道を持たないため受入だけでなく焦点走でも常に skip される。
  つまり登録された node はどこでも走らない。3 件とも真因を直して台帳を空にした。

- **登録と修理が別 wave に分かれると取り残しが起きる、を現物で確認した。**
  `26d7f74b` (08-25 21:22) と `9cd011fe` (08-26 05:26) がそれぞれ別 wave で hold#1 と hold#3 を
  登録し、`639f2f28` (08-26 09:17) が両方のテストを修理して main へ入れたのに登録行を消さなかった。
  2 node は約 6 時間、複数回の受入全走をまたいで検査集合の外にあった。
  {{F:stale-flaky-hold-outlives-its-fix}}。

- **hold#1 の族分類が誤っていた。F480 の記述を訂正した。**
  F480 はこの node を「絶対 wall-clock を assert するテストが並列負荷で非再現の赤になる」族に
  入れていたが、親が計装して実測すると `-n 32` で 10.015 / 10.014 秒、`-n 48` で 10.015 秒、
  **ばらつきは 1 ミリ秒**だった。正体は `DEFAULT_POLL_INTERVAL_S = 5.0` の実 sleep が 2 回入る
  **決定的な 10 秒の床**で、元の `join(10)` の余裕は 15 ミリ秒しかない。負荷は引き金であって
  支配項ではなかった。したがって `639f2f28` の `join(10)` → `join(60)` は真因に届いていない。
  同 file の標準 helper `_dispatch()` は既に偽 clock を注入しており、他 23 箇所が
  `poll_interval_s=5` でも一瞬なのはそのためである。この 2 test だけが実 clock で呼んでいた。
  偽 clock を注入して実所要は **13.5 秒 → 0.01 秒**になった。

- **親の裁定が 1 つ誤っていて、実装子の報告で判明した。**
  段 3 のレンズが指摘した「`--no-index` の prefix 除外が force-add された tracked file を隠す」を、
  親は「prefix 配下に tracked entry があれば fail-closed」で採用した。実装子が実装して報告し、
  親が現物で確認すると `.gitignore:24` の `output/env/pegasus/silo_ladder_rung1/job-staging/` 配下に
  **tracked file が 418 個**あり、全 snapshot caller が決定的に赤になった。
  正しい semantics は fail-closed ではなく「tracked path とその祖先を隠さない」だった。
  裁定を訂正し、段 6 の fix で直した。{{D:tracked-paths-are-never-ignored-in-snapshot}}。

- **段 2 プランの設計を親が変えた。** プランは「全 directory で timestamp を一律に捨てる」だったが、
  プランがその代替 (祖先だけ正規化) を退けた理由は「before / after で対象が変わる」であり、
  それは除外集合が実在依存だった前提の話だった。除外集合を規則由来へ直すと祖先集合も不変になる。
  結果として `output/insights` などの検出力を落とさずに済み、さらに
  **これまで存在しなかった「一時作成後削除を捉える」control を初めて足せた**。
  helper の docstring はその性質を謳いながら、独立に検証する検査を持っていなかった。
  {{D:snapshot-normalizes-only-rule-derived-ancestors}}。

- **修理済み hold を検出する機構は DW-G04 に従って見送った。** 3 行を撤去すると registry が

  登録と同じ commit で導入する条件付き導入とし、設計を

- **親が変異走行中に tree へ書いて 1 回分を無駄にした。** 成果物の退避を「読み取りに近い」と
  暗黙に例外扱いし、untracked file の追加も `git status` を変えることが判断から抜けていた。

- **受入全走で 3 node のいずれかが再び赤になった場合の分類手順**を段 3 のレンズが用意した。
  (1) candidate commit・shard 数・junit・failure digest・`output/` 差分を保存する。
  単独再走の緑だけで修理済みと判定しない。
  (2) hold#1 は thread 生存 assertion だけが同じ署名で落ち、結果・qsub 回数・orphan 不在に
  別の破れが無く、単独走で消えるなら元の flake の再発。別 assertion が変わるなら新しい回帰。
  (3) hold#2 は差分 path で分ける。`"runs" in ignored_prefixes` が落ちるなら規則導出の回帰。
  ignored な `runs` / `pegasus-dispatch` / directory metadata だけが差なら snapshot 修理不足。
  git-visible な `task-runs/reports` / `pilot.json` / `output/insights` が差なら残存する F136 型。
  (4) hold#3 は各 hook 1 回・controller payer 1 回・worker payer 不在が成立したまま相対順だけが
  反転するなら元 flake の再発。payer 回数・不在条件・subprocess rc が崩れるなら性質の回帰。
  (5) 「exact な過去署名」「単独緑」「同条件の全走でのみ再発」「candidate diff から対象 test body へ
  到達しない」の 4 条件が揃った場合だけ元 flake の再発と分類する。ただし wave 成功とは扱わず、
  再 hold ではなく修理を追加する。
  (6) 一度の再投入で消えても証明にしない。同じ shard 条件で再確認し、分類根拠を台帳へ残す。
