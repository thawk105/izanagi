## 本文

- 依頼は「[T-1563] を進める。投入順を arm 間で揃える実装か、揃えられないなら交絡として測定設計へ
  明示的に織り込む設計のどちらかを段 2 で決め、裁定として記録してから実装する」。
  設計判断は {{D:acceptance-order-worker-independence}} と {{D:acceptance-nproc-study-estimand}}。

- **投入順は「揃える」側で既に成立していた。** D746 が main に着地済みで、並べ替えは worker 数を
  入力に取らない純関数、窓定数も literal である。shard 割付けも worker 数を読まない。
  よって選択肢 (b)「交絡として織り込む」は採らなかった。
  ただし**主張の射程を切った** — 揃うのは最終 workqueue の大域取り出し順だけで、
  worker 割付け・初期配布幅・先取り時刻・完了順は worker 数の効果そのもの (mediator) である。
  段 3 のレンズがこの区別を出し、親が裁定へ入れた。

- **段 1 の brief を 1 度撤回して書き直した。** 段 2 起動後に、受入全走が既定で 2 shard へ分かれ
  shard ごとに別ノードへ dispatch されると実測で判明した (T-1580、commit `6c7ae156`、2026-08-23)。
  T-1563 の裁定を支えていた実測値 (48/32/16 で 391.28/358.96/345.89 秒) は分割前のものである。
  段 2 の子を停止し brief を rev.2 へ訂正して投げ直した。

- **段 3 の 2 レンズが独立に同じ blocker を出した。** 段 2 が採った「分割せず 1 ノードで全 suite を
  測る」設計では、現行 K=2 の既定 worker 数を決められない。親は実コードで**第三の経路**を見つけて
  この blocker を解消した — 内部 shard 実行は追加 argv を拒否し、worker 数を環境変数からのみ
  解決する。session 置き場は repo の外である。本番の 2 shard は別ノードで並行に走るので受入 wall は
  shard wall の max であり、**1 ノードで 1 shard を測ることが本番の量を測ること**になり、
  D531 の「同一割当内」も同時に満たす。段 2 の「明示 `-n` を渡す」案はこの経路では不成立である。

- **既定 worker 数はこの wave では動かさない。** D103 決定 (3) は既定を最大並列にするのが
  ユーザー裁定に基づく方針であり「最大並列が最速だとは主張しない」と明記する。D532 は worker 数の
  増減を提案しないと定める。`docs/decisions.md` に T-1563 の決定節は存在せず、裁定は archive の
  worklog にしかない。測定の解禁と既定値の再裁定は別の許可なので、親は後者を代行しない。

- **親の見積りは裁定の根拠値と向きが逆だった。** 現行台帳 (15,904 nodeid、work 総和 7,852.1 秒) から
  所要降順の割付けで makespan を出すと n=48 で 163.6 秒、n=32 で 245.4 秒、n=16 で 490.8 秒になる。
  D746 の並べ替えが makespan を work 下界へ寄せたためと考えられる。D531 によりこの計算は採否根拠に
  使わないが、「worker を減らすほど速い」という prior は壊れている。設計へは
  「primary contrast は 32 対 48、16 は secondary」として反映した。

- **段 6 のレビュー 2 本が blocker 1 件と must-fix 6 件を出した。** 最も重いのは、driver が JUnit の
  identity を記録するだけで **arm 間の一致を要求していなかった**ことである。1 件でも deselect された
  arm が短い所要を出すと、それが worker 数の効果として採用されうる。両レンズが独立に到達した。

- **レビューの blocker への親の refuted は、機構としては正しく方向としては誤っていた。**
  親は「受入 preflight は modules cache を見る前に marker file と submodule 配下の内部 directory の
  実在で早期に成功復帰するので該当 rc にはならない」と裁定した。これは実コードのとおりである。
  しかし試走の実測で、**その内部 directory の実在と形は別の gate 群が要求している**と判明した。
  指摘が名指しした経路は誤りだが、指摘そのものは real だった。refuted を出すときは
  「その機構では起きない」と「その事象は起きない」を分けて書く。

- **変異検査が、敵対レビュー 2 本が見つけられなかった被覆漏れを 3 件見つけた。**
  いずれも production に検査はあるが、それを無効化しても赤にならなかった。
  (a) 受領証の除外項は「鍵が無い」場合しか検査されておらず、closed-map の鍵検査に先に捕まるため
  **値が別物でも通った**。(b) shard を全部は覆わない入力を検証器へ渡す負例が無かった。
  (c) 6 順列の検査は生成側の出力を直接見るだけで**検証器を通っていなかった**。
  3 件それぞれに、診断文字列を逐語照合する負例と通る正例を対で足した。
  過剰決定は 2 件で冗長 gate と明記する。

- **試走 (生死確認) を 4 回投入し、机上のレビューが 1 件も出さなかった実機の欠陥を 3 件見つけて
  閉じた。**
  1. 独立複製を置くだけでは git は submodule を未初期化と報告し続ける。git が見ているのは
     path の実体ではなく設定への登録である。登録して初めて 1 段深い submodule が再帰列挙に現れる
     ため、**入れ子は 1 回の列挙では辿れない**。この repo は 3 段の入れ子を持つ。
  2. 走ごとに `HOME` を差し替える drift 対策が、利用者領域にある pytest と xdist の解決を壊す。
     内部 shard の経路は import できないと**診断を 1 行も出さずに**拒否するので、
     「受領証が無い」という遠い場所でしか表に出なかった。実測では素の設定で両方 True、
     差し替えで両方 False、利用者領域の位置を明示すると再び True (system 領域の package は無影響)。
  3. 複製が本物と topology 的に等価でない。submodule の内部 directory の形と、job script の
     厳しい umask による file mode の 2 点で gate 群が落ちる。
  いずれも修理し、**測定を 1 本も回す前に等価性を検査する関門**を setup へ置いた。

- **試走は最後まで緑にならなかった。「試走の受領証を必須成果物とする」という親の裁定を改めた。**
  4 回目で赤は 42 → 30 件へ減った。残る原因は 2 つで、どちらも複製の環境等価性の問題である。
  (i) 16 件は C++ oracle が使う外部依存の永続 cache に生成物が無いこと (未解明)。
  (ii) 11 件は計算ノードの job 環境が module 系の余分な export を持ち、子 process の環境を
  逐語比較するテストが落ちること。本番受入は dispatch の allowlist で環境を絞る経路を通るので
  緑である。driver も同じ allowlist へ揃えるのが筋である。
  **driver 自体は「複製を作り、測定を実行し、異常時は診断付きで止まる」ところまで実機で動いた。**
  受領証・失敗受領証・stage 追跡・process 回収はすべて実機で発火を確認している。

- **fix は 7 巡になった。** 3 巡上限は「レビュー所見への fix」の上限と解し、変異駆動の再照準
  (4 巡目) と、生死確認が実機で見つけた欠陥への fix (5〜7 巡目) は別枠として扱った。
  レビュー所見への fix は 3 巡で閉じている。
  **2 巡目の取りこぼしは親の投げ方の不手際**である — prompt の射影が「レビュー A の所見 1・2 だけが
  担当」と読め、子は must-fix 4 件を担当外と解釈した。

- **子は 1 度も pytest を実走できなかった。** 全 10 本が queue の preflight 失敗で child 未起動に
  なり、全員が「実装済み・未実走」と正しく申告した。**本 wave のテスト結果はすべて親の実測**である。

- **統合直後の焦点走 90 件の赤のうち 87 件は既知の型だった。** 権威 docs に未 commit の差分があると
  子の起動テストが大量に赤くなる。commit 後の再走で 0 件になった。自分の回帰と帰属しなかった。

- **段 8 の自己改善は 2 件とも byte 予算に阻まれ、契約どおり変更を止めて裁定へ返した。**
  候補は (a) refuted の書き方を「機構」と「事象」に分ける規律、(b) fix 子の担当所見は prompt
  本文で列挙し必読射影で絞らない規律である。どちらも本 wave の実測に基づく。該当 leaf 節へ
  追記したところ L1 が 10,785 / 10,625 bytes、L1.5 が 9,755 / 9,566 bytes で超過した。
  既存本文の縮約は exact pin を壊す危険があるので行わず、変更を revert した。
