## 本文

ユーザーが直接起票した。「dev-wave を終えた後、main land まで成功したら自分のワークツリー・
ブランチを掃除するよう dev-wave を改善して」。

**着手前の実測で、dev-wave の docs と command には撤去義務も手順ポインタも 1 件も無いことが
分かった。** 一方 F26 は 2026-08-01 と 2026-08-05 の 2 回、「dev-wave の段 9 は自分の worktree を
畳むよう求めるが、その手順の正本が `/cleanup-branches` §3 にあることを指していない」と記録して
いた。台帳は 2 度欠落を名指ししていたのに、経路は一度も作られていなかった。
現物の滞留は worktree 31 本・branch 114 本で、直近 land 済み wave のものも残っていた。

**滞留の本当の原因は運用の怠慢ではなかった。** `tools/check_worktree_occupancy.py` は
ホスト上に zombie process が 1 本あるだけで、**どの path を対象にしても
`status=indeterminate` / rc=2 を返し続ける**。zombie は `/proc/<pid>/cwd` を持たないが
`/proc/<pid>/` 自体は残るため pid 消滅と判定されず、`issues` へ積まれるからである。
pid 1035937 (`State: Z`、python3) で 2 回連続再現した。`/cleanup-branches` §3 は
「rc0 のみ進み、rc2=判定不能は停止」と定めるので、**掃除の関門が最初から誰にも通れなかった**。
これを直すまでは、今回作る自動撤去も動かない。詳細は {{F:occupancy-zombie-permanent-block}}。

**親の裁定が既裁定と衝突していた。** 当初 (P1) は `DW-O25` へ義務を統合する案だったが、
D432 末尾が「`docs/dev-wave/operations.md` は変更しない。`DW-O25` は checker が節全文を
exact pin しているため 1 byte も触らない」と明記しており、D280 が同節を規範節 4 つの 1 つに
指定していた。段 3 の正本整合レンズがこれを検出し、あわせて親が D433 と D432 を取り違えて
いたこと、および「予算引き上げを提案しない」が現行方針ではなく **D671 (同日のユーザー裁定) が
必要な分だけの引き上げを許可している**ことも指摘した。いずれも採用して裁定を訂正した。

**段 3・段 6 の敵対レンズは合計 27 所見を返し、うち 21 件を採用した。** 不採用は
lease / capability / repository-wide lock を要する 4 件で、D205 (研究プロトタイプ) により
scope 外に留めた。quarantine rename 案も不採用にした — `.claude/worktrees/` 配下に
`.git` を欠く残骸を作る経路そのもので、その残骸は持ち主に関係なく全 wave の land を
rc=21 で止める既知事故だからである。

**gate の述語を「到達可能な値域を測らずに」採用する誤りを 2 度踏んだ。** 1 度目は
`unreachable.cwd_permission == 0` で、この共有 login node の実測は 2,020〜2,213
(cwd を読めない他ユーザーの process 数) だった。2 度目は same-uid 到達不能 process の
comm 固定 allowlist で、焦点走が 11 件赤になり全件の理由が `comm is not allowlisted: 'nqs_shpd'`
だった。`nqs_shpd` はバッチスケジューラの常駐 process で、**テストを計算ノードへ dispatch した
瞬間に同 uid で現れ**、走行終了直後には消える。つまりこの allowlist は本プロジェクト自身の
作業フローの最中にだけ破れ、撤去が必要になるのはまさにその直後だった。どちらも撤回した。
型は {{F:gate-predicate-unreachable-value-range}}。

**変異を回さなければ見つからなかった穴が 2 件あった。** preflight の branch ancestry 検査を
無効化しても、どのテストも落ちなかった。mask 源は `branch-recheck` 段の 2 つ目の ancestry
検査だが、それは `rm -rf` と `prune` の**後**にある。つまり preflight が退行すると
「worktree を消してから拒否する」挙動になり、既存の負例はその差を区別していなかった。
もう 1 件は allowlist へ `worktree remove --force` を足す変異で、禁止 verb のテストが
source 走査と実行 argv spy の 2 面だけで、allowlist が禁止 argv を拒否すること自体を
検証していなかった。両方とも敵対レビュー 2 本では出ず、変異でだけ顕在化した。
詳細は {{F:preflight-gate-masked-by-post-destruction-layer}}。

間欠赤も 1 件踏んだ。3 file 同時走の 1 回目だけ mutation phase の注入テストが 1 件落ち、
2 回目は緑だった。原因は占有走査で、並列走行中に一時 process が生まれ消えするだけで
`issues` が非空になり rc=22 で早期拒否されて注入が発火しなかった。zombie と同型である。
production 側は「消えた pid 由来の indeterminate」に限って最大 3 回まで走査をやり直す形にし、
注入が主題のテストは占有結果を決定的な stub にした。占有走査を実際に通す正例 1 本と、
対象 worktree を cwd にした live process を実起動する負例 1 本は実走のまま残した。

**変異 matrix はこの機体では harness の KILLED 判定を使えなかった。** `--runner-mode local` の
collection は `tools/run_tests.py` 経由で計算ノードへ dispatch され、
`tools/pegasus/dispatch_compute.py` の成功時中継が 4 KiB 上限 (`DEFAULT_SUCCESS_RELAY_LIMIT_BYTES`)
のため、`--collect-only -q` の全 node 一覧が構造的に届かない。`--runner-mode dispatch` は
baseline が `PARSE_ERROR` になった。そこで**期待 node を走行前に凍結し
(sha256 `01c1b9eaeef1577bf99ce29f861dcd9b828d64227d6f78c62913948fcc81a877`)、
probe 形式で走らせて完全一致を親が照合した**。結果は最終 tip `118d7ba2` で baseline PASSED、
8 変異すべて期待集合と完全一致、SURVIVED 0・MISMATCH 0 である。

エージェント工数は codex 子 11 本 (plan 1 / consult 2 / author 1 / fix 6 / review 2)、
いずれも `gpt-5.6-sol` / `xhigh`。**launcher が健全な成果物を 3 回 not_accepted にした** —
author・review-luna・fix5 の 3 本で `evidence_status=invalid` が出たが、親が rollout を
検算すると `session_meta` 1 件・`turn_context` 1〜2 件・events 全行が妥当な JSON・
`termination_verified: true`・codex exit 0・上限抵触なしで、内容の欠陥ではなかった。
attempt 出力から回収し、`check_codex_output.py` rc=0 を確かめて採用した。詳細は
{{F:codex-launcher-evidence-invalid-on-healthy-output}}。

fix 子は 1 度正しく停止した。段 5 の子が書いたテストが撤回済みの述語を期待値として固定して
おり、「既存テストの期待値を変えるな」と両立しなかったためである。親が範囲を限定して
更新を許可した。子の判断は妥当だった。

**codex 子は「working tree が authority commit と一致」を起動条件にする。** 実装子が
dev-wave docs を触った後は、親が統合 commit を挟むまで後続の子を 1 本も起動できない。
段 5 / 段 6 の手順にこの前提が書かれていない。

  (lease / capability) を入れるか裁定する。現状は common git-dir 一致・branch↔tip 束縛・
