## 本文

- **ユーザー指示「codex に相談して決めて」により、C1b の裁定パッケージ 4 件を codex 2 本
  (lane sol / luna、reasoning=xhigh、read-only) へ諮り、親が決めた。** どちらの子にも
  「選択肢を並べるな、ちょうど 1 つ推奨を出せ」と指示した。一次資料は
  `output/insights/2026-09-07_t1851-unit-c1b-contract-v2-defects/rulings-resolved.md`。
- **レンズ B に「そもそもこの機構は要るのか」から疑わせたのが効いた。** 封印が無いときの
  具体的な偽装手順 (正当な予約・分類・観測開始までを通常経路で作り、terminal builder だけが
  任意の出力 bytes・状態・digest・主値・測り直し理由を返す) と、その虚偽が result の prefix proof を
  通って live verifier / holdout freeze / ratified freeze に受理される伝播経路を実測で示した。
  **床値の数値は journal から再計算されるので変わらないが、proof chain の主張が偽装される。**
  既存の防壁 (分類 receipt、観測開始 event、deferred reader、admission claim) がいずれも
  terminal の outcome を閉じていないことも確認された。機構は必要と判定した。
- **最重の (1) は 2 案が割れ、親は規律 2 に厳密に強い方を採った。** レンズ A は「検証済み証拠が
  あるときだけ既存の等値検査を飛ばす」policy flag を、レンズ B は「観測後の理由は別 field に載せ、
  既存の等値検査は 1 行も変えない」形を推した。A 案は**既存の正しさ検査へ条件付きの迂回路を
  新設する**ので、B 案を採った。B 案なら証拠を持たない呼び手は迂回路に到達すらできない。
  親が現行の null matrix (`attempt_registry_core.py:1050-1090`) と突き合わせ、観測前の失敗
  (echo が入る)・観測後の失敗 (両方 null)・観測済みの 3 通りすべてで矛盾しないことを確認した。
  A 案からは配線の規律 (capability の入口を 1 本に限る、起動層は core の capability を受け取らない、
  adapter が観測 handle から digest を補って発行する) と、7 組の対照表を採った。
  {{D:post-observation-retry-reason-is-a-separate-field}}。
- **(2) は「どちらも正しい — 別の量である」という第 3 の答えが出た。** 実行失敗数は runner が
  rep を開くときに捕捉した実行例外の数、証跡不完備数は戻り値・counter・schema・欠損の独立検査の数で、
  同じ rep で両方立ちうる。契約の「非 zero の戻り値をすべて実行失敗と数える」が誤りだった。
  レンズ A の「契約を現行の自然文算出に合わせる」案は、証拠が「campaign が自然文から何件と
  数えたか」しか証明しなくなるので却下した。**構造化記録の実装は runner と campaign を触るので
  後続単位へ割り当て、証拠を作る単位では等値束縛だけを主張して射程を明記する。**
  {{D:exec-failures-and-integrity-failures-are-distinct}}。
- **(3) は両者一致で、別 process 化を採らず脅威境界を明文で限定した。**
  同一 OS ユーザー・同一 repository・同一検査コードでは独立性が増えないため、D387 が述べた限界と
  同型である。守れないものを守ると書かない。{{D:sealed-evidence-threat-boundary}}。
- **(4) も両者一致で、production 効果のある分割は存在しない。** 縦 1 単位で作り単独 land しない。
  改訂見積りは production 約 +1,000〜1,600 行、test 約 +1,500〜2,400 行で、契約が要求していない
  自発的拡張 3 件を落とした分だけ元 plan より小さい。実装子は所有 file が素集合になる 3 本に分ける。
