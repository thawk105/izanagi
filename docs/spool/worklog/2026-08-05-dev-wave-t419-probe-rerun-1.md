## 本文

- **U-1 の因果は立証された。** 走行 889400 (計算ノード、全 6 arm・445 読み完走、probe_rc=0) で
  `execution_validity=VALID` / `causal_verdict=CONFIRMED`。事前登録 3 条件の実測は
  pinned_hit_rate=**1.0** (240/240、閾値 0.95)、nonpinned 帯外率=**8.87e-05** (1/11,280、閾値 0.05)、
  paired contrast が正の CPU=**48/48** (閾値 46)。**閾値は実装前に確定して以後動かしていない。**
- **機序が精密化された。** A2 の sham/busy 対照で、同じ CPU でも子が sleep なら帯外 **0/40**、
  spin させると **40/40**。原因は「probe の走行 CPU であること」ではなく
  「**そのコアがその瞬間 busy であること**」で、走行 CPU は定義上必ず busy なので必ず帯外に出る。
  「特定コアの個体差」仮説は全 48 CPU が pin 時だけ帯外になることで棄却された。
- **F110 / F111 の恒久対応を実装した** (両台帳の「恒久対応: 未実施」は本エントリで更新される)。
  F110 は単独性を消費量ベースの率判定へ、F111 は診断 field を 4 値にして `error` だけを致命にした。
- **裁定の文言と実装が食い違っている。追認をお願いする。** (193) の U-1b(i) は
  「`/system.slice` の uid 0 システムデーモンを環境として区別」= **所有者ベース**だったが、
  実装は**消費量ベース**で所有者による免除を明示的に禁じた。所有者で免除すると暴走した root
  デーモンを見逃すためで、実測 (sleep 0/40 対 spin 40/40) がこの判断を支持する。
  裁定の目的 (常駐デーモンで実験が止まらないこと) は達成した。**親がこの判断を brief に書いたのは
  裁定が台帳へ記録される前**であり、記録済み裁定を意図的に覆したものではない。
  裁定パッケージ §4 R-0 に置いた。
- **方式 α/β/γ の 2×3 表が実データで埋まった** (α の should-reject を除く)。
  α (巡回込み) = should-pass 9/9・過剰拒否 0、should-reject 未測定。
  **α から巡回を抜いた形は 0/24 で全滅** — 「走行 CPU を移しながら」は省略不能である。
  β と γ は本機体では挙動が一致し (should-pass 119/120、should-reject **0/55 = 正しく全拒否**)、
  懸念された「γ が真の逸脱を見逃す」は busy 同居という形の逸脱では起きなかった。
  β/γ の過剰拒否 1/120 は第三者の一過性バースト由来で、**α は同じ読みを含む群でも通った**。
- **副次診断**: 21,360 標本の 97.6% が厳密に 2101.0。`samples_mhz` が運ぶ情報は実質
  「どのコアで測ったか」だけである。`cpuinfo_cur_freq` は 48 policy すべて非 root で読めず、
  **独立した周波数源へ替える案は Pegasus では閉じている**。
- **単独性 gate の閾値を 2 度動かした (経緯を明記する)。** 因果判定の 3 条件は一度も動かしていない。
  (1) 6.7 → 25.0 tick/s: erratum-2 で**走行前に**「率の最大値を記録し次の反復では実測から引き直す」と
  事前登録した手順の実行。実測 65 subwindow で背景ノイズは中央値 0.00 / 最大 11.86 tick/s、
  かつ control 11,280 件中の帯外は 1 件で読み値を汚していなかった。
  (2) abort を signal CPU (reader / pin target / A2 target) に限定: 因果比較に入らない CPU の
  一過性負荷で 55 秒の実験を捨てないため。統計的歯止めは既存の nonpinned 帯外率 ≤ 0.05 が担う。
  **変更前の走行 889310 の時点で A1 は既に 3 条件を満たしており、通すための緩和ではない。**
  歯止めとして「次の走行でも VALID に到達しなければ裁定へ返して閉じる」を erratum-5 に明記した。
- **段 6 は敵対レビュー 1 本 (6 所見) → 焦点再レビュー 2 巡 → fix 4 巡。全所見 real、refuted 0。**
  実機投入前にレビューが摘出した 2 件が決定的だった — 「arm 合計の絶対 tick では長い arm が
  必ず落ちる」(A0 1.5 秒に対し A1 は 12 秒超) と「完走しても α 列が巡回なしの別方式の値になる」。
  どちらも放置すれば計算ノード job を消費して無価値な成果物を作っていた。
- **変異 matrix (事前登録 10 本、baseline PASSED): SURVIVED 0 / KILLED 10。**
  4 本 (M1/M2a/M2b/N3) は実際の赤 node が予測と完全一致。残り 6 本は KILLED だが node 集合が
  ずれた — M3 は過剰列挙 (3 予測に対し実 2)、M4/M6/N1/N2/N4 は**過少列挙で検出力が予測より強かった**
  (N1 は 4 予測に対し実 9)。初回結果を消さず insight へ残す。harness の赤 node 抽出が
  dispatch 経路で `None` を返すため、赤 node は job stdout 全文から親が抽出した (F71)。
- **親が生出力の数値を読み違え、それを閾値の根拠にしていた。** 前 wave の A0 について
  「`nqs_shpd` が CPU 22 で 4 tick」と brief に書いたが、生出力が示すのは per-CPU residual が
  CPU22=1 / CPU44=3 (合計 4) で、しかも旧 schema は競合 process 自身の `cpu_ticks_delta` を
  保存していない。`residual_total` をデーモンの消費量と取り違えたものである。
  段 6 のレビューが raw と突き合わせて摘出し (S6-01)、erratum-1 で訂正した。
  **`DW-S01` の「数値は一次資料の field から取る」が親自身の実測引用にも掛かる**という型で、
  レビューが無ければ誤った根拠のまま閾値を決めていた。
- **段 8 の dev-wave 改善候補は前 wave と同じ 2 件で、いずれも実装しない。**
  (a) 段 1 の前提実測が実行環境そのものの実測を欠く件は `docs/dev-wave/` が
  25,196 / 25,200 bytes (残り 4 bytes) で入らない。**上限引き上げは提案しない** ([T-454] が解放を所有)。
  (b) 変異 harness の赤 node 抽出が dispatch 経路で `None` を返す件は本 wave でも再現した
  (10 変異すべてで `None`)。実装面の修正だが本 wave の scope 外とし、記録に留める。
- **段 9 後の同一 context で継続した。** ユーザー指示「codex のアカウントが切り替わった。
  作業を継続してください」を受けたもので、`/dev-wave` 凍結境界の「1 wave = 1 fresh context」からは
  外れる。handoff にもその旨を記録した。
