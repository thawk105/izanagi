## 本文

- 前エントリで未確定として残した 2 点をユーザーが**推奨どおり**裁定した
- **[T-313] の剪定基準 = 発火実績 + 機械検査での義務代替。** 条件読み層は byte 数で剪定しない。
  自己改善契約 routing 3 が L2 節の削除条件として既に持つ述語
  (「発火実績なし × テスト/機械検査で義務代替済み」の両条件) をそのまま再利用する。
  **「発火実績なし」は ID 件数でなく repo 全体 (insights・memo 含む) の意味検索で反証されないこと**を
  確認する既存規定も継承する。これで「常に読まない層は合計上限を持たないが無制限には増えない」が
  成立する — 増えるのは発火実績のある節だけになる
- **[T-296] = Pegasus 専用 env-tag を作り、そこで層 C を取り直す。** 以後の絶対値の主張は
  Pegasus を基準に述べる
  - **これは roadmap の改訂を要さない。** §5 は「別環境を正式計測へ採用する条件」として
    (1) 専用 env-tag、(2) その env-tag での calibration と noise floor の取り直し、
    (3) 計測ノード上での単独性・静定確認、(4) module・コンパイラ・CCBench pin・ジョブスクリプトの
    成果物追跡、を既に規定している。本裁定はその手続きを発動するものであって規定の変更ではない
  - **実測した未達は (1) だけ。** 現行の env_tag は `linux-baremetal` / `env-x` / `fixture-env` の
    3 つで Pegasus 専用のものは存在しない。(2) は certification 実測 (attempt 10 で accepted、
    CV 1.17%) と較正点 (1M/48)、(3) は単独性確認手順 (F3 の恒久対応)、(4) は D125 の
    build identity + attestation で実質的に整っている
  - **多環境への一般化を明示する。** cygnus など 2 台目が増えても同じ規律が効く —
    **マシンごとに env-tag を持ち、取り直すのは層 C (絶対 throughput・floor・較正点・noise floor)
    だけ。層 A / B は転移させ、転移元 env-tag と転移根拠を provenance に残す** (roadmap §5
    可搬性節、2026-07-22 協議改訂)
  - **親の問いの立て方が誤解を招いた。** 「Pegasus を正式計測へ昇格させるか」という語は
    「研究の主張がこのマシンでしか成り立たないのか」と読める。ユーザーの指摘
    (「そもそも CC の自動合成はこのマシンじゃないと動きませんっていう方が研究としておかしい」) は
    正しく、**昇格が関わるのは層 C だけである**。層 A (軸に floor 超の地形があるか、protocol 内在の
    機序帰属、correctness 検証の意味論、コード資産) は既定で転移し再取得しない。
    以後この面の問いは層 C 限定で立てる
