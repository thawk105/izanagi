## 本文

前 fold で 11 件の裁定を着地させた直後、**その着地作業自体から本丸が 1 つ残っていることが判明した**ため、
続けて裁定を取った。

**裁定 = 着地は main の静止を要求しない** ({{D:land-must-not-require-a-frozen-main}})。
`tools/dev_wave_land.py` の `stale-main` 拒否
(`main moved outside the tested audited closure while locking`) は、受入を検査した時点から
main が進んだだけで着地を止める。**これは D662 が却下した lease 直列化と同じ要求を、各 wave に
自前で再実装させる形である。** D662 は「main への取り込み競合は特別な直列化機構ではなく通常の
git 競合解消で対応する」と明記しており、着地側の実装がその明記に追随していなかった。

**所要を縮めても消えない、という実測が決め手になった。** 赤の帰属判定を一定時間へ作り替えても
(D680)、受入全走 3〜4 分の窓は残る。実際、受入本体が
3 分 30 秒で緑になった wave が `stale-main` で弾かれている。本セッション自身も受入 6 走・
約 4 時間を消費して着地できず、うち 1 走は判定 39 分の最中に main が 2 回進んで判定不能になった。
別 wave では手動の判定器実行が 58 分走って未完了で、その間に main が 2 回進行している。

**rulings 側の失敗を 1 件記録する。** 本セッションは、この件への対処として並行セッションから
共有された「取り込み → 受入 → 着地を 1 本に連結する」を、**「着地 5 分以内を満たすには実務上
ほぼ必須」という一般則として 4 セッションへ中継した**。これは誤りで、ユーザーから
「lease 機構が競走窓を閉じるやつだったが、それは計算ノードが混雑したとき研究開発に破滅を
もたらすから却下された」と指摘を受けて撤回した。**窓を縮める話を必須として配ると、
「各 wave が競走窓を閉じにいくのが正しい姿」という含意になり、却下された前提を再配布する。**
自分が同じ窓で 4 時間溶かしておきながら、緩和策を解として広めかけた。

ただし取り下げは広すぎた。**連結スクリプトそのものと「main を止めておきたい」という願いは
別物である。** lease を握らず、他 wave を待たせず、main も止めず、弾かれたら通常の競合解消へ
落とす実行形 (親が手待ちしないだけ) は D662 と整合する。却下すべきは一般則の側だけだった。
この切り分けは指摘を受けた並行セッションから返ってきたもので、決定本文の却下節へ書き分けた。

## 次の一手差分

### 新規

- {{T:land-stale-main-requirement-removal}} **P2・新規 (2026-08-23 /rulings 追加裁定)**:
  `tools/dev_wave_land.py` の `stale-main` 拒否を、main が進んだだけでは止めない形へ変える
  ({{D:land-must-not-require-a-frozen-main}})。着地側が取り込み直して進み、実際に内容が衝突した
  ときだけ通常の競合解消へ返す。**実装条件** = 取り込み直しは fast-forward または競合なしの
  merge に限り、衝突したら止めて返す (着地側が衝突を自動解決しない)。受入受領証が束縛する tip
  との対応が崩れていないことを検査し、受領証が指す tip と別物を着地させる経路を作らない。
  `--audited-commit` の閉包検査は監査の本体なので緩めない。実装面のため Codex `role=author` が
  要る。**これが残る限り、帰属判定を一定時間へ作り替えても混雑時の詰まりは再発する。**

- {{T:monkeypatch-module-substitution-lint}} **P2・新規 (2026-08-23、横断調査で 2 例目を摘出)**:
  `monkeypatch` がモジュール属性ではなく**モジュール自体**を差し替える書き方を機械検査で禁じる。
  差し替えがプロセス全体へ波及し、並列走行下でのみ落ちる間欠赤を生む。実測 2 例で `DW-G03` の
  族一般化の条件を満たす — 1 例目は修理済み (別 wave)、2 例目は
  `orchestrator/tests/test_campaign_claim.py` の `time.sleep` 差し替えで、差し替え先が
  **ファイル書き込みの副作用を持ち**、かつ呼び出し回数を exact に検査しているため最も危険な形
  (修理は摘出した wave が引き取り済み)。無害に見える残り 2 件も、将来 assert が足された瞬間に
  危険側へ変わるため、**「危険な使い方」ではなく「モジュール自体の差し替え」そのものを禁じる
  形にする**。`time.sleep` に絞った検索での hit は 3 件だが、`os` / `subprocess` / `shutil` /
  `random` 等へ広げると同型の書き方が約 286 箇所あり、族の実際の広がりはこれより大きい。
  危険度の判定軸は (a) 記録を取るか (b) 副作用を持つか (c) 呼び出し回数を exact に検査するか。
  実装面のため Codex `role=author` が要る。

- {{T:red-attribution-main-side-cache}} **P3・新規 (2026-08-23、判定器担当からの引き継ぎ)**:
  全走差分方式の tested main 側の赤集合を `<main SHA, runner 内容ハッシュ>` を key として
  repo 外へ cache し、同じ main を tested_main とする 2 本目以降の判定費用をほぼゼロにする
  (D680 の後続)。**採否の分かれ目は安全性の非対称である** —
  cache が古くて main 側の赤集合が小さめに出た場合でも、差分が増えて再実行が増えるだけで、
  **regression を隠す方向には倒れない**。判定器本体の着地とは分けて扱う (共有 cache は
  cache key の同一性・無効化の契機・複数 wave からの同時書き込みという新しい正しさ面を増やすため)。
  実装面のため Codex `role=author` が要る。
