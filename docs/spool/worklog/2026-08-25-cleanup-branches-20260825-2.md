## 本文

- 起点は worktree 88 本 / ローカル branch 90 本。撤去は 55 本 (うち 53 本を本 job、2 本は各 wave の自己撤去)、
  branch 削除は 61 本 (ahead=0 の 59 本 + 稼働終了後に取り残された t1291 の impl 2 本)。
  remote 設定が既に失われた追跡参照 14 本も除去した。すべて main の祖先で、commit は到達可能なまま残る。
- 撤去中に新しい wave が 6 本立ち上がり (t1594 / t1669 / t1677 / rulings-20260825-adopt-p1〜p3)、
  「起動直後の wave を掃除が巻き込む」危険が実在することを再確認した。撤去は 1 本ごとに
  clean・main 取り込み済み・占有の 3 点を直前に測り直す形にし、巻き込みは 0 だった。
- 占有検査は 55 本中 53 本が rc=0、2 本が rc=1 (cwd と cmdline の双方に実プロセス) で残した。
  走査母数は毎回 2,199 前後で、`scanned=0` の偽陰性は生じていない。
- ahead>0 で worktree を持たない 8 本は、`git cherry` の `+` も含めて内容としては main へ着地済みだった
  (roadmap の逐語一致、`policy_hint` の出現数一致、孤児 spool fragment は FOLDED.md の
  content_sha256 が D650 の受領証と一致)。tip は main の祖先でないため `git branch -d` は拒否する。
  削除はユーザー裁定へ返す。
- §1 の到達不能監査は [T-1636] の着地により初めて完走し、rc=1 で要確認 28 commit を返した。
  実測 56 分で、その間 stdout は 0 byte のままである。ユーザーから「フリーズしてるよね」の指摘を受けた。
  28 件は本 job の削除とは交差せず、全件が以前から main 到達不能だった。
- 自己改善の発火は成立したが、`.claude/commands/cleanup-branches.md` は 3,949 bytes で
  上限 3,983 まで残り 34 bytes しかなく、監査の所要時間の注記は入らない。契約に従い台帳側へ記録した。
