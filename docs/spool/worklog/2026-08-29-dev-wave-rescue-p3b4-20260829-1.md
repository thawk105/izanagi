- **ユーザーが疑った contract / ledgers (48KB) / admission_record は、必要性の議論以前に
  「既に main へ着地済みのものの古い複製」だった。** t2001 側の成果は 2026-08-27 の commit
  592a08f32 (`[T-2001] B-4 の凍結分析契約を実行する 5 経路を実装する`) として、t2005 側の成果は
  worklog (1098) の `[T-2005] B-4 projection 登録の機構と規範を閉じ、値は宣言源の不在で止めた`
  として、それぞれ別 branch から着地していた。救出対象は取り残された作業ツリーの残骸である。

- 撤去前に `tools/check_branch_rescue.py` を branch 1 本と worktree 3 本を 1 操作として
  模した形で実行し、`deletion_loss_closure` が `commit_count: 0` かつ `complete: true`
  であることを確認した。同ツールは rc=2 を返したが、原因は `root-snapshot-moved`
  (実行中に他 wave が ref を動かした) 1 件のみで、**損失そのものはゼロ**である。
  59 worktree が同時に生きている環境では他 wave の進行が常に snapshot を動かすため、
  この rc は撤去対象の損失可否とは別軸である。

- 変異 harness は 2 本稼働していたが、`--repo` はいずれも自分の codex worktree
  (dev-wave-t2033-axis1-retake、dev-wave-t2061-wal-admission) であり、**主 checkout を
  観測していない**ことを実測した (harness repo 側の `git status --untracked-files=all` が
  `.codex/worktrees` を 0 件しか出さない)。よって撤去は共有 untracked 集合の観測を壊さない。

- 撤去は不可逆であり、判定対象は git object として残らない未 commit 内容のため、
  12 file 全部を `/work/1/SFC/tanab/dev-wave-jobs/rescue-20260829/salvage-20260829/` へ
  退避してから撤去した。判定が後日覆っても内容は失われない。
