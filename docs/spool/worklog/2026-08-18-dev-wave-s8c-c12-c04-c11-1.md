## 本文

2026-08-18 の裁定控え (rulings-full8) が「UNSATISFIED 5 件の consumer を実装する」を
裁定不要・実装のみとして置いていた。本 wave はその C12 と C04 分である。
設計判断は {{D:reservation-preflight-consumer}} と {{D:crash-indeterminate-failure-atomic}}。

**引数の前提が 1 件ひっくり返った。** 依頼は C11 を「EVIDENCE_UNDEFINED なので実装が要る」と
していたが、`EVIDENCE_UNDEFINED / completion-proof-not-machine-checkable` は
**機械検査を全通過した合格終端**である。`SATISFIABLE_CONDITION_IDS` が空集合で、機械検査可能
条件が `SATISFIED` を返すと `evaluate_all` が `ERROR / evaluator-internal-error` へ潰すため、
到達可能な最良状態がこの値になる。C11 は 3 境界の generation budget 検査も critic 射影の
消費も既に成立しており、runtime の被覆 (`test_two_generation_critic_feedback_precedes_next_planner`)
まであった。**production もテストも変更していない。**

**判定器は working tree でなく commit を読む。** そのため status の反転は統合 commit を
作ってはじめて観測できる。実装直後の焦点走で赤かった 8 件のうち 4 件はこれで、
`ce8c2f50` を作った時点で消えた。commit を挟まずに「実装子が反転テストを直せていない」と
判断していたら、正しい実装を疑うところだった。

**恒真な保証が 3 件見つかった。** (1) `add_note` の握り潰し ({{F:add-note-tautological-guard}})、
(2) 予約 gate の site を opt-in flag から推定していた迂回穴 ({{F:gate-site-inferred-from-flag}})、
(3) `restart_forbidden` を立てるだけで誰も読まない証拠面。(2) と (3) は段 6 の敵対レビュー
2 本が**独立に同じものを最重要として指摘**した。(1) は fix 子が「期待値の側が誤りでは」と
判断して止まり、親が実行環境の Python version を実測して real と裁定した。

**変異 probe が 4 つ目の穴を出した。** `required_s=max_wall_s` を `required_s=1` へ落とす変異が
SURVIVED した。既存の残時間不足対照は deadline を現在時刻の約 1 秒後に置くため、要求時間が
いくつでも同じく拒否され、束縛そのものを検査していなかった。残り約 1800 秒の予約に
`max_wall_s=3600` を要求する対照を足して塞ぎ、本走で KILLED になった。
probe の ledger は erratum として insight へ同梱した。

**段 6 の fix 子が 2 度、編集せずに停止した。** 診断は 3 件とも正しかった (Python version、
fixture の残時間構成、テストの観測対象)。ただし 2 巡目は**独立な 3 作業のうち 1 件の停止条件で
3 件とも止めた**。prompt へ「作業は独立である。1 つが止まっても他は進めよ」を明記して
3 巡目で回収した。fix 子は 7 巡回した。

**codex の子は今回も pytest を 1 度も実走できなかった。** login では `qstat -Q` preflight が
rc=1 になり、子の報告はすべて「実装済み・未実走」である。実測は毎巡 親が計算ノードへ
dispatch して引き受けた。

**wave 中に main が進み t1333 が land した。** 同じ production file を +187 行変えるため、
段 4 の直前に `54baeb86` を ff 取り込みし、段 1〜4 の資料の行番号が約 +176 ずれたことを
段 5 prompt に明記して実装子へ測り直させた。

**scope 外として裁定パッケージへ返した 5 件** — (1) 予約 gate の支配性が 8c launcher に
限られる (探索層の CLI と将来の PBS dispatch は `run_trial` を経ずに campaign を起動できる)、
(2) `_finish_trial` の `Exception -> partial` が C04 の意味的要求を骨抜きにしている
(reason code `crash-policy-cell-partial` が指す穴はここで、着地済みの設計テストを反転させる
変更になる)、(3) campaign launch 直前の予約再検査、(4) 予約事実の report / lifecycle への
永続束縛、(5) 判定器へ `reject_started_trial` の reachability を追加するか (契約は 3 consumer を
要求するが判定器は 2 つしか見ない。自分の実装を判定する門を同じ wave で書き換えない方針で見送り)。

## 次の一手差分

### 新規

- {{T:s8c-reservation-gate-dominance}} **P1・ユーザー裁定待ち**: 予約 gate の保証範囲を決める。
  探索層の CLI と将来の PBS dispatch は `run_trial` を経ずに campaign を起動できる。
  択: (a) 共通 launch 点へ admission を強制、(b) 直接 driver を正式に禁止して経路テストを置く、
  (c) 保証範囲を 8c CLI と `run_trial` の public boundary のみと明記する。
- {{T:s8c-crash-policy-cell-partial-semantics}} **P1・ユーザー裁定待ち**:
  `_finish_trial` の `Exception -> partial` を C04 の要求どおり実験全体の indeterminate へ
  寄せるか決める。着地済みの設計テストを反転させるため、実装せず裁定へ返した。

  永続束縛し、どの予約の上で走ったかを事後に再検証できるようにする。
  campaign launch 直前の予約再検査もここに含める。
- {{T:dev-wave-fix-child-independence-clause}} **P2・ユーザー裁定待ち**: 段 6 fix 子へ
  「独立な複数作業は 1 件の停止で他を止めない」を明記する 1 行を `DW-S06-B` へ入れる。
  段 8 で実測したところ `docs/dev-wave/**` の L1.5 予算を 52 bytes 超過して入らなかった
  (9618 > 9566)。本 wave では 2 巡ぶんの fix 子が無駄になった実害がある。

  `reject_started_trial` を足すか決める。契約 JSON は 3 consumer を要求するが判定器は 2 つしか
  見ないため、preflight の重複拒否を削除しても C04 の判定が変わらない。
