## 本文

- D1456 と D1459 の実装。受入側の走査を `_called_names` から `_live_called_names` へ替え、
  証拠契約の条件 9 の文言を「受領証発行へ到達する全 build report」「acceptance receipt issuance」へ
  直した。凍結の改訂手続きに従い `DECIDER_VERSION` を v9 へ上げ、世代記録 g15 を
  `prepare-revision` で発行した。
- **機構が必要だったことを反実仮想で実測した。** 修正を戻す変異が落とすのは本 wave の新テスト
  1 件だけで、既存の 619 件は 1 件も落ちなかった。受入側の生死は誰も守っていなかった。
- **段 3 のレンズ A が real 所見 4 件を出し、すべて scope 外と裁定した。** 生死判定に入らない
  死んだ形 (`IfExp`・短絡 `BoolOp`・`try/finally` の完了伝播)、呼出し先の実体同一性、
  policy marker の意味論、受領証経路の支配関係。前 2 件は decisions の到達性の限定列挙と
  終端 target の項を改訂する要求で、同じ helper を共有する 20 箇所以上の受理意味を同時に変える。
  後 2 件は呼出しの生死とは別の欠陥型である。C09 を充足可能集合へ入れる前の blocker として
  裁定パッケージへ返す。
- **(P1-b) の policy 文字列の生死化は採らなかった。** レンズ A が「生きた文字列に替えても
  無用途の marker を置けば通る」と示しており、半端な強化は恒真な保証を増やす。データフロー検査が要る。
- **親の段 1 brief の (P1-c) は段 2 のプランが反証した。** D1459 は `registry append` も
  不一致として名指ししており、`proof` だけ直すと訂正が半分残る。契約 JSON の 2 箇所を直した。
- **段 6 のレビュー B の must-fix 1 件は refuted。** 「親が担当する g15 が既に差分にあるので
  `prepare-revision` を実行できない」という所見だが、g15 は親が実際に同 CLI で生成 (rc=0) してから
  commit したものである。レビューへ渡した差分が commit 後だったため生成前と読まれた。
  レビュー prompt に「親の分担分は既に実行済み」と書いていれば防げた。
- **契約 bytes の pin を段 2 プランも段 3 の 2 レンズも 3 件取り残した。** 制御文字を足した
  派生 hash を pin するテストで、親の焦点走が初めて実測で出した。レンズ B は「pin の列挙は
  所見なし」と書いていたが誤りだった。fix 子を 1 本立てて閉じた。
- **実 repo snapshot テストは契約を変えた作業ツリーが未 commit のうちは必ず赤になる。**
  全条件の evidence に契約 blob の sha が入るためで、実装の回帰ではない。
- 変異走の 1 回目は共有木の事後検査で rc=125。並行 wave が共有 checkout の未追跡ファイルを
  書き換えるためで、(1127) と同型。独立 clone を `--source-repo` へ渡して構造的に断った。
- codex 子は 5 本 (plan 1・consult 2・author 1・fix 1)、いずれも `gpt-5.6-sol` / `xhigh`。
