## 本文

- 索引 8 件のうち詳説 5 件を提示し、**3 件は推奨どおり、1 件は方針を修正して採用、
  1 件はユーザーが前提そのものを問い直したため未裁定で残した**
- **[T-338] Q3〜Q11 は推奨どおり。** これで RF 統計設計 11 問のうち 10 問が確定した
  - Q3 = **scalar floor をやめ同時信頼領域で判定**する。既存 `BETWEEN_RUN_CV = 0.030` は
    「variant と baseline を別 session で測る」設計前提の周辺 CV であり RF の誤差構造とは別物
  - Q4 = **1 allocation = 1 immutable subcampaign** とし cluster 間成分は trial 層で標本化する。
    G12 (単一 allocation/node/process 完遂) は subcampaign 単位で保たれる。
    **allocation ID は独立性の必要十分条件ではない** — 独立単位は対象母集団と相関構造から定義し
    node / 時間窓を cluster として数える
  - Q5 = **pilot 先行の二段階設計**。**ただし「どの効果量まで拾うか」は未確定のまま残る** — 下記
  - Q6 = 割付可能な schedule 集合・位置と一次 carry-over の balance 条件・washout 規則・
    sharp/weak どちらを primary にするかを事前登録。weak null を primary にするなら
    cluster 数での型 I 誤りを事前 simulation で較正する
  - Q7 = **主張の型ごとに 3 分割**。全体 1 本 (`all_pass`) なら intersection-union で補正不要、
    個別公表は Holm / closed testing、候補系列は親系列 ID + 累積 alpha 台帳 + spending 関数 +
    候補数上限。**BH (FDR) は採らない** — 「1 つでも偽の certified artifact が入る確率」を制御しない
  - Q8 = **correctness anomaly は欠測ではなく候補の終端 reject** (削除も置換もしない、規律 2 の直接適用)。
    結果を見る前に外部証拠で確定する infra failure だけ事前順序固定の予備から置換可。
    走行後の性能側欠測は既定 reject または判定不能とし、救済時は worst-case bound と感度分析を併記
  - Q9 = 比の区間は **Fieller を primary**。分母 screening をやめ、状態名
    `weak_denominator_not_certifiable` を置く。**`RF > 1` を「回復」とも「新規改善」とも帰属させない**。
    分類は多重性調整済みの信頼集合全体で行い、有界/非有界/不連結 × 0 と 1 の境界を閉表で覆う
  - Q10 = **D116 方式を RF へ拡張する**ことを明示裁定。measurement-start receipt・全 attempt の双射・
    親系列 ID を一体で要求する。**既存 8c ですら成果物への事前登録 commit 束縛は未実装**であり実装 scope
  - Q11 = **状態は独立 validator が raw receipt から再計算**する。producer の自己申告 field に
    しない (D127 が裁定した恒真 gate の型になる)。層 3 の calibration floor 閉表は広げず、
    RF 統計は `trial × candidate × workload × contrast` を key とする別区画へ置く。
    後続 scope は [T-339] の中身として起票する
  - **未確定として残るもの:** Q5 の目標効果量。概算では J=16 は d≳0.81 の大きい効果しか
    検出力 80% で拾えず、d=0.5 なら 40〜50 cluster が要る。**そのまま計算資源の費用になるため
    事前登録の前に固定が要る**
- **[T-313] は (1) 3 層 gate を採用。ただし第 2 問はユーザーが方針を転換した**
  - **常に読む層は固定上限を維持する。** ここが厳しくなければ gate の意味が無い
  - **ノウハウ全体に固定の文字数上限を課すのはやめる。** ユーザー判断 =
    「必ずは読まないところにノウハウを蓄積するのは悪くない。ただしゴミを増やしたいとは思わない。
    ノウハウ全体で固定文字数制限は厳しすぎる」。**これは [T-127] の「上限を増やさず使い方を
    管理する」を、合計上限の撤廃という形で改める**。増枠ではなく**「常に読まない部分を予算対象から
    外す」**という構造変更である点を取り違えないこと
  - **未確定として残るもの:** ゴミを増やさない歯止めの実体。合計上限を外すと無制限に増える。
    親の推奨は「条件読み層は合計 byte でなく**発火実績と機械検査での義務代替**で剪定する」
    (自己改善契約 routing 3 の L2 削除条件と同じ述語を再利用する)
- **[T-387] は正規形を追加する** — receiptless な no-build 成功試行の正規形を共有 topology の
  受理集合へ加える。**受理集合の拡大なので既存の変更手続きを通す**。孤児 `VERIFY_DONE` /
  `BENCH_DONE` の variant identity 束縛も同じ裁定で扱う
- **[T-376] は義務化する** — `(Pn)` を立てるとき「その P を反証しうる最も安い実測」を 1 つ併記する
  義務を `DW-S01` へ足す。発火実績が同一 wave 内 2 件で `DW-G03` の独立 2 例を満たさない点は
  記録に残すが、コストが 1 行であり実証済みの効果が上回るとユーザーが判断した
- **[T-296] は未裁定のまま残した。** ユーザーが「正式とは何か」という前提を問い直し、
  「Pegasus はよく使うし cygnus も使うかもしれない。そもそも CC の自動合成がこのマシンでしか
  動かないという方が研究としておかしい」と述べた。**この指摘は roadmap §5 の可搬性節
  (2026-07-22 協議改訂) と一致する** — 層 A (軸に floor 超の地形があるか、protocol 内在の機序帰属、
  correctness 検証の意味論、コード資産) は既定で転移し再取得しない。昇格が関わるのは層 C
  (絶対 throughput・floor・較正点・noise floor) だけである。**親が「昇格」という語で問いを立てた
  ことが誤解を招いた**。実測: Pegasus 専用 env-tag は**未作成** (現行の env_tag は
  `linux-baremetal` / `env-x` / `fixture-env` のみ) であり 4 条件のうち (1) が未達、
  (2)〜(4) は D125 の build identity・attestation と certification 実測 (CV 1.17%)、
  単独性確認手順で実質的に整っている。次回、層 C 限定の問いとして立て直す
