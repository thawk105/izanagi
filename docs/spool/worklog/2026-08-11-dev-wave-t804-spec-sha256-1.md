## 本文

- **起票根拠 = worklog 419 の [T-804] 裁定 (B)。** 並走ガード 3 条件は brief へ記載した。
  (i) 計算ノードは機能テストの dispatch のみで性能計測はしていない。
  (ii) キュー投入の直前に毎回 `qstat` で再確認し、[T-139] の pilot / 本走 job は wave を通じて
  一度も走っていなかった。(iii) 本 wave の裁定要求は A 線の後ろに並べる。
- **段 3 の敵対 2 レンズ (max) がいずれも NO-GO を返し、親の provisional 裁定 2 件を覆した。**
  - **P3 撤回** — 「judge が承認 pin と `spec_sha256` を比較する」案は**恒真**である。
    pin は公開定数なので、迂回者は正しい値を手書き observations に書けば満たせる。
    レンズ B は独立に「module 定数参照は同じ入力の判定を module 状態で変える」と指摘した。
    裁定文の「全層で**再検証**する」の逐語に従い、judge 自身が `verify_manifest` を呼ぶ形へ
    差し替えた ({{D:judge-reverifies-not-compares-pin}})。
  - **P5 撤回** — 共有 `_validate_run_contract` を exact key 化する案は **既裁定 D288 に抵触**する。
    D288 は「gate は共有 verifier へ置く。生成側 generic builder の受理集合は変えない」と決定し、
    却下選択肢に「generic builder に置く — 既存 programmatic caller の受理集合を狭め互換を壊す」を
    明記していた。親が D288 本文を逐語で確認して撤回した。
- **親自身の段 1 実測の誤り 2 件をレンズが指摘し、brief へ訂正を追記した。**
  (i) 「凍結 bytes の pin 閉包 = 影響ゼロ」は無限定には誤り。テスト側の `PIN_GATE_SPEC_RAW` が
  **role 名を key にした pin** で judge / report / artifacts の source hash を埋めている。
  親は path だけを検索して 0 件を「pin なし」と結論しており、これは DW-O09 が名指しで警告する
  踏み外し方そのものだった。(ii) run contract の自由軸は「定義済み 9 key のうち 4 つ」ではなく、
  部分集合判定と全 key 保存により**任意の余剰 key も自由**だった。
- **段 6 の敵対レビュー 2 本も NO-GO で、独立に同じ BLOCKER を指摘した** (独立 2 例)。
  judge は manifest を再検証するようになったが、判定に使う `n_per_cell` と `expected_cells` は
  observations の自己申告値のままだった。正しい公開 hash を転記した手書き observations で
  別 schedule 相当の cell 集合を持ち込め、勝者・中央値・floor 超過判定を動かせる。
  fix で manifest schedule 由来の immutable 射影を required keyword で渡す形にした。
  レビュー 1 本は追加で、新設した CLI 負例が**恒真**であること (同じ不正ファイルを `--input` と
  `--manifest` の両方へ渡しており manifest 側で先に落ちる) も指摘した。
- **scope 外と裁定した real 所見 (裁定パッケージへ回す)** — combined verdict
  (`s8b_verdict.judge_combined`) の oracle verdict が未封印である。同じ関数の隣り合う 2 行で、
  予測側は封印 token を要求するのに oracle 側は schema 名の確認だけで通る。
  **これは spec 迂回とは別の既存の穴**で本 wave が新設も拡大もしていないため、
  主張を「manifest を消費する全層」に限定した。**本 wave は全層被覆を主張しない。**
- **段 6 の手続き上の障害と解決。** main が本 wave 所有のテスト 2 本を変更しており、そのまま
  merge すると結合結果が両親のどちらとも異なる実装面ファイルになる。DW-O17 はこれに Codex
  `role=author` を要求するが、**Codex 子は sandbox が `.git` を読み取り専用にするため merge を
  実行できない**。著作の実体は結合後のファイル内容であって git 操作ではないので、順序を変えて
  Codex author が main 側の変更を先に取り込み、後続 merge の combined path を 0 件にした
  ({{F:codex-cannot-perform-merge}})。親は取り込み結果が 3-way merge と SHA-256 一致することを
  独立に検算した。
- **変異 11 件は初回、走行ゼロで fail-closed 停止した。** 親が parametrize の期待 node に
  日本語を書いたが pytest は非 ASCII を正規化する ({{F:mutation-node-id-nonascii}})。
  実 ID を collect から採って再投入した ({{D:mutation-expected-nodes-from-collection}})。
- **変異 MISMATCH 4 件はいずれも変異の生存ではなく親の予測不足。** うち 2 件は
  source hash pin が同族ファイルの変異を必ず道連れにするためで、この結合は今後の登録でも効く
  ({{F:source-hash-pin-drags-mutations}})。

- {{T:oracle-verdict-sealing}} **P1・新規 (ユーザー裁定待ち、B 系)**: certified 結論を作る
  `s8b_verdict.judge_combined` の oracle verdict が未封印である。同じ関数の隣り合う 2 行で、
  予測側は `verify_prediction` の封印 token を要求するのに、oracle 側は `load_official_verdict`
  (schema 名の確認のみ) で読んだ marker をそのまま受ける。schema と holdouts の形だけ満たす
  verdict を書けば `oracle_floor_exceeded`・combined `status`・certified 選択を変えられる。
  [T-804] は「manifest を消費する全層」までを閉じており、この層は scope 外と裁定した
  (spec 迂回とは別の既存の穴で、manifest を一切使わずに成立する)。
  **同ファイル内に `VerifiedPrediction` という既存 pattern があるため実装費用は見た目より安い。**
  掲載だけの証拠 field を足す案は恒真化として却下済み。
  択 = (a) `VerifiedOracleVerdict` を導入し `judge_combined` を封印 token 専用にする (親推奨) /
  (b) [T-657] 権威束設計へ合流させる / (c) 現状維持で主張を限定し続ける
- {{T:legacy-observations-retirement}} **P2・新規 (ユーザー裁定待ち、B 系)**: 旧形 manifest は
  `verify_manifest` を通らずに report と observations を生成できる。[T-804] は judge 側で
  certified 結論への到達を閉じたが、**report 層自体の受理集合は狭めていない**。
  既存テストが legacy の rc=0 を契約化しており、狭めると受理集合の変更になるため裁定を要する。

  (b) legacy observations を別 schema へ分離して段階廃止する
