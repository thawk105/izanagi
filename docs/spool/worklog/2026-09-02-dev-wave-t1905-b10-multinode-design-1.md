## 本文

- D1480 が指定した 3 条件は設計へ全部落とした。所在は設計文書の対応表に書いた。
  着手時の brief は条件 2 (1 セルの試し打ちで全滅を先に潰す) を落としており、
  段 7 で worklog の item から D1480 を引き直して補った。**引数と一次資料だけを読んで
  brief を書き、承認済み裁定の本文を先に引かなかったのが原因である。**

- **親の provisional 裁定 (P2) は子 2 者と親の再確認で覆った。** brief は「1 job =
  1 (workload, block) の 9 job」を第一候補にしていたが、正しさの認証は変種ごとであって
  block ごとではないため、block で割ると律速を workload あたり 3 回払うことになり、
  壁時計はほとんど縮まずノード時間だけ約 3 倍になる。加えて現行 campaign 同一性に block が
  入っていないので 3 本が同じ claim・lock・記録ファイルへ向かう。採用は workload ごとの 3 本。

- **最大の反証は、ノード内で検査を多重化する道がそのままでは塞がっていることである。**
  `orchestrator/verifier/core.py` の検証 capability は発行時の PID を記録し、消費時に
  `issuer_pid != os.getpid()` で拒否する。別プロセスへ検査を配ると certified な成果物が
  ゼロになり、結果だけ受け取れば受理集合を広げる (規律 2 違反)。Python スレッドでは
  純 Python の検査は速くならない。**残るのは、判定と受領証の発行を元プロセスに残したまま
  検査器内部のデータ処理段だけを並行にする形だけで、これは正しさ防壁の中核に当たる。**
  本 wave では実装せず裁定へ返した。

- **一次資料の 2 か所を追記で訂正した** (`output/insights/2026-08-31_t1905-b10-formal-run/README.md`)。
  壁時計の固定値は 4 か所でなく 5 か所 (5 番目は driver の submission receipt 検査)。
  「ベンチマーク実体 1 workload 4.5 分」は性能相の値ではなく、登録値からの計算では
  675 秒 = 11 分 15 秒である。本文は測定時点の記録なので書き換えず追記にした。

- 実測で見つけた設計上の前提を 3 つ記録する。(1) トレース取得には 120 秒の打ち切りがあるので
  取得の並行化は正しい変種を落とす。並行にしてよいのは取得後の検査だけ。(2) 性能測定前の
  静定待ちは 20 秒で諦めて進み、静定したかは判定に使われない。検査を多重化した直後に測ると
  余熱が block-1 先頭セルの値に乗る。(3) ジョブは repo を複製せず投入時の作業ツリーを使うので、
  3 本同時投入はビルドキャッシュ置き場を共有し、各ジョブが他 workload の記録を走査して
  その時点のレポートを 3 通書く。

- **完走済みの write-heavy 45 セルは残せる見込みである。** campaign 同一性は既に workload ごとに
  分かれており、分散のために新しい識別子は要らない。ただし D1169 が A-2 で求めた
  「外側の認証は論理積という規則を手続きのハッシュへ入れる」を B-10 で同じ形にすると
  登録内容のハッシュが変わり write-heavy が集約から外れる。規則を集約側に持たせれば残せる。
  どちらを採るかは裁定項目に挙げた。

- 段 3 の子 2 者は「現時点では投入可能な設計ではない」で一致した。設定変更では済まず、
  検査の多重化・グループ投入・ジョブごとの置き場・集約・差し替え規則がいずれも新規実装である。
  設計文書はこれらを未実装の前提として列挙し、投入可能とは書いていない。

- **段 8 の改善候補 1 件は予算に阻まれて実施しなかった。** 候補は「brief 前に引く承認済み裁定の
  在り処 (対象 T の worklog item が名指しする D) を `DW-S01` へ書き足す」。実際に入れてみると
  `docs/dev-wave/**` の L1 unique footprint が 10753 bytes で予算 10625 bytes を 128 bytes 超え、
  **追加分とほぼ同じだけ超過した — 予算は満杯である。** D782 の手順に従い、既存記述の等価削減は
  他節の意味を弱める危険があるので採らず、独立 3 例にも満たないので上限引き上げもせず、
  「実施しない」へ落とした。**義務そのものは `DW-S01` に既にある** (「brief 前に承認済み裁定と
  引数の前提を実測し」) ので、欠けていたのは在り処の明示だけである。
