## 本文

- **是正した収集経路 (repo 外の handoff) を初めて使い、その最初の実行で親の記録誤り 2 件が
  見つかった。** 発見元は `dev-wave-jobs/handoff/wave-t088-floor.md` の段 1 前提実測
  (N1 / N4)。親はコードで裏を取り、**両方とも wave 側が正しい**と確認した
- **訂正 1 — 「Pegasus 専用 env-tag は未作成」は誤り。** 親は (140) で
  「現行の env_tag は `linux-baremetal` / `env-x` / `fixture-env` の 3 つで Pegasus 専用のものは
  存在しない」「roadmap §5 の 4 条件のうち未達は (1) 専用 env-tag のみ」と記録したが、
  **`orchestrator/campaign/env_contract.py` に `env_tag="pegasus"` が実在する** (`26a9ad6`)。
  登録先 `output/env/pegasus/calibration/registered/` も同契約が持つ。
  **原因は検証方法の不足** — 親は `"env_tag": "…"` という JSON literal 形だけを grep し、
  Python の構築子形 (`env_tag="pegasus"`) を拾わなかった。**4 条件の (1) は既に充足**であり、
  [T-296] の「env-tag 新設 → floor 実測 → 登録」という順序の第 1 段は**既済**である
- **訂正 2 — 「前提 gate 2 件が floor 実測を塞ぐ」は誤り。** 親は (145) で
  「[T-088] の段階 3・4 と実行 revision 束縛が未閉鎖であり 1 wave 束縛と両立しない可能性がある」と
  記録したが、**それらは 8b selector の床値 campaign の official guard であり、層 C の
  between-run noise floor を塞がない**。`orchestrator/campaign/between_run_floor.py` の
  import 閉包に `official` / `s8b` は**0 件**である (親が実測)。
  **原因は phase3 の散文から適用範囲を推論し、実装の依存関係で裏を取らなかったこと**
- **この 2 件から見えた規律の穴 (予算不足で入口へ入れられない)。** どちらも
  「実装状態についての事実主張」を**一次資料 (コード) でなく散文と部分 grep から書いた**ことが原因である。
  `/rulings` の入口へ「索引・記録が実装状態を断定するときは一次資料で裏を取る」を足したいが、
  `.claude/commands/rulings.md` は **4988 / 5000 bytes で余白 12 bytes** しかなく入らない。
  rulings には reference file が無いため統合先も無い。自己改善契約の
  「予算に収まらなければ reference へ統合し、それでも意味等価にできなければ変更を止めて
  ユーザー裁定へ返す」に従い、**変更を止めて裁定へ返す** ({{T:rulings-claim-verification}})
- **[T-088] の wave が親の裁定の解釈で止まっている (裁定待ち)。** handoff の段 4 論点に
  「**裁定の『足りなければ拡大せず裁定へ返す』の適用先 — 測定規模か、実装規模か**」とある。
  wave の設計は rr50 の 1 点を 8 本の独立 PBS request × 5 rep で取る案で、**実装は約 1500 行**
  (3 実装子 + 新規 registry module + 新規 bundle submitter + policy + テスト 5 面)。
  代案は既存 driver の最小 env 化 + 単一 job 内 8 セッションで**同じ下限クラスを 1/10 の費用**。
  ただし 8 request 案は allocation / build / node の分散を捉える点で**より良い下限**である。
  なお得られる量は `evidence_class: lower-bound-only` と名乗り
  **`compare` の `noise_cv` には配線しない**と設計されている。詳説と推奨は本 /rulings 実行で提示した
