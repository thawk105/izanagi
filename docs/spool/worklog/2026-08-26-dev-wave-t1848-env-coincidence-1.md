## 本文

- 依頼は「実測フレーク率への寄与が大きい順に是正せよ」だったが、**その順序は本 wave の予算では
  確定できない**と裁定した。敵対レンズが算術で示したとおり、全体率 15%/走の事象を 95% の確率で
  1 回でも観測するのに最低 19 走、候補 9 site を均等・独立と仮定しても 1 site を 95% で 1 回
  観測するのに 166 走、9 site 全部で約 287 走が要る。287 走でも各 site の期待観測は約 5 件で
  順位差の比較には足りない。絶対規律 4 に反する規模なので、代わりに**確実性順**を採った。
  機序が確定している識別子・周囲状態・因果の代理観測を先に是正し、確率的にしか現れない
  hang guard は計装なしには順位づけ不能と台帳に記録した。

- 親の provisional 裁定 1 件を段 2 プランが反証した。親は「D249 の予算拡大禁止は
  『時間が主題』のクラスにだけかかる」と置いたが、**hang guard の上限拡大も受理集合を広げる**
  ため D249 の手続き対象である。敵対レンズが検出力低下を 3 例構成した (20 秒の join を 60 秒へ
  広げると 30 秒の性能回帰が通る、など)。よって本 wave では待ち上限の値を 1 つも変えていない。
  F641 が行った `join(10)` から `join(60)` への拡大も、値の根拠が静穏な単独走 13.94 秒の
  4 倍超という外挿だったので、D249 適合例として引用しないと決めた。

- **親の走査が誤っていた。** 真偽値リテラルを数値として数えていたため母集合が 1 件 1 file 多く、
  「244 件が F641 の記録と一致する」という記述もそのバグ由来の偶然だった。敵対レンズ 2 本が
  独立に指摘し、base の blob に対して数え直して訂正した。正しくは P1 243 件 / 66 file、
  P2 260 件 / 66 file である。

- **敵対レビューは実装差分を「採用不可」と判定した。** must-fix 4 件のうち 3 件を fix で閉じた。
  排他の証明が「lock を試みた」までで止まっており scheduler 次第で壊れた実装が通る点、
  因果待ちが無期限で hook 消失時に node の赤でなく suite 全体の停止になる点、fd identity が
  open description の交換を検出できず、さらに procfs の可視性という**新しい環境依存**を
  持ち込んでいた点である。3 件目は「環境の偶然を消す是正が別の環境依存を作った」型で、
  この族の作業で最も踏みやすい失敗だと考える。

- **F4 (受入 duration 台帳への対象 node 登録) は fix 子が契約どおり止まった。** 台帳へ sort の
  node を足すと凍結された「ちょうど 69 node」の期待値が必ず落ち、実測値の捏造も既存期待値の
  変更も禁じられているため両立しない、という報告だった。本 wave の変更で新しい test node は
  1 つも増えていないので、この欠落は元からある穴である。次の一手へ送った。

- **並行 wave dev-wave-flaky-holds-20260826 との相互相談で、分類手続きの穴が 1 つ埋まった。**
  同 wave は「並列負荷で落ちるフレーク」に見えた 2 件を計装し、`-n 32` / `-n 48` で
  10.015 / 10.014 / 10.015 秒 (ばらつき 1 ミリ秒) を観測した。正体は production 側の実 sleep が
  作る**決定的な床**で、負荷は引き金にすぎなかった。この型に対しては「上限を変えない」という
  裁定は何も直さない。クラス F を足し、その判定を hang guard より先に置く手続きを台帳へ書いた。
  相手は自分の提案を 2 度訂正してきた (多数派 grep は判定器でなく並べ替え、production の seam を
  「使う」のは呼び手であって production 変更ではない)。訂正のほうが正しいのでそちらを採った。
  一次資料は同 wave の branch と job dir にあり、**land 前なので番号ではなく path で引いている**。

- 親の実測: 飽和条件 (計算ノード全コア、17,391 件) の全走を 3 本取った。1 本目だけ 3 件赤、
  2・3 本目は完全緑。赤 3 件は fresh worktree に `output/runs/` の中身が無いことに起因し、
  1 本目自身がそこへ中身を作ったため消えた。**本族の実例だが該当 file は稼働 wave が是正中**
  なので対象外とした。負荷起因のフレークは 3 走とも 0 件で、これは既知の 15%/走と矛盾しない
  (3 走すべて 0 件になる確率は約 61%)。**3 走の緑から率が下がったとは言えない。**

- 待ち手が 3 回、生産者の生存中に exit 0 を返した。`.done` の実在で毎回再確認して張り直した。
