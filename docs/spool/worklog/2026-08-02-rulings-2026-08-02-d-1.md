## 本文

- 索引 12 件を提示し、詳説した先頭 5 件をユーザーが**すべて推奨どおり**採用した
  - **[T-337] は (a)** — 正例 artifact の適格性は**新 D で権威境界を定義し `artifact_role=qualification`
    を [T-318] 準拠で置く**。凍結 ledger の exact-one contract には触れない (択 (b) は正しさ防壁の
    改訂になり独立 wave が要る)。[T-318] で既に「producer に種別を宣言させ閉表で管理する」方向を
    採用済みであり、その枠へ乗せるのが一貫する
  - **[T-338] は (a)** — **RF 統計設計 (少なくとも floor の取り方) を正例より先に裁定する**。
    段 3 レンズ B が段 2 案の floor (arm ごとの between-session CV を足す) を統計的に誤りと判定し、
    paired session 差で取るべきとした。paired 差の floor 定義は未裁定の「統計設計 5 点」の一部である
  - **[T-342] は (a)** — build provenance を**source 由来の capability へ一体で移す**。現行は caller の
    自己申告 enum の整合しか見ておらず、同一 `CODER_DERIVED` bytes を `STOCK_OR_PINNED` と申告すれば
    certified 受理集合へ入れられる (段 6 レビュー 1 の F2)。source digest / clean 検査 /
    generator identity / review receipt から capability を発行し、CLI authority も同時に移す。
    片方だけでは「自己申告」という性質が残るため択 (b) は採らない
  - **[T-343] は (a)、かつ receipt 欠落の旧 entry は拒否** — admission を cache / replay identity へ
    束縛する。現行は legacy cache key・v2 preimage・completion manifest・campaign preimage の
    いずれにも admission が入っておらず、**別 class の run から過去 binary を再利用して
    `median_tps` と certified terminal を別 provenance へ付け替えられる** (F3)。
    明示 migration は「provenance 不明を受理する経路」を残すため採らず、旧 entry は再 build させる
  - **[T-339] は (b)** — consumer は後続へ回し、正例 artifact を先に作る。理由は着手の軽さではなく
    **[T-338] の裁定で合格ラインの定義自体がこれから変わるため** — 先に consumer を設計すると
    floor 変更でやり直しになる。順序は 統計設計 → 正例 → consumer
- **親の順序案の誤りを訂正した。** (115) で [T-139] について「正例 artifact だけ先に承認、統計設計は
  その後」と推奨し裁定を得たが、(118) の実測で**正例の受理条件が未裁定の統計設計に依存する**ことが
  判明した ([T-338])。親の見落としであり、順序は「統計設計の floor → 正例」へ改める
- 収集の照合: 参照先が存在しない `変わらず` はゼロ、`docs/handoff/` は README のみ。
  未 push 31 件はユーザーへ報告した (F79 の復元が git 履歴に依存した事実を添えた)
