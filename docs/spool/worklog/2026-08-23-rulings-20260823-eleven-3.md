## 本文

- 裁定 30 件の land (entry 860) 直後に、稼働中の 2 セッションが実測を添えて 3 点を返した。
  いずれも裁定の内容を覆すものではなく、**承認済みの作業をそのまま実行すると誤った結論に
  到達する**経路を塞ぐ内容だったため、記録として反映する。
- **[T-1567] は [T-1571] の部分集合だった。** 実体を読み直すと、[T-1571] は排他鎖 2 本の
  同時短縮を求め「**両方を同時に短縮しないと床は下がらない** (片方だけでは他方が残る)」を
  既に本文に持ち、その第一候補として `s8c-preregistration-candidate` を名指ししている。
  [T-1567] はその同じ鎖の内訳測定であり、上位集合に含まれる。別々の wave が 1 本ずつ縮めると
  どちらも wall を下げられないまま終わるため、統合する。指摘は並行セッション由来だが、
  親が両項の本文を突き合わせて独立に確認した。
- **承認済みの [T-1563] 測定に交絡が 1 件見つかった。** 並行セッションが前 wave の一次資料
  (`groupmap.json` + junit) から xdist の LoadScopeScheduling を offline 再現したところ、
  work unit の投入順は collection 順そのままの FIFO で、103 秒の排他鎖が 14,373 unit 中
  11,191 番目 (77.9%) にあるため開始が約 84.5 秒遅れる。所要を固定した simulation では
  投入順を所要降順へ変えるだけで makespan が 181.6 → 111.8 秒になる。
  **この遊びは worker 数に強く依存する** (n=16 / 32 / 48 で 21.1 / 60.3 / 69.8 秒)。
  したがって現行の投入順のまま worker 数を測ると、**投入順の遊びを worker 数の効果として
  帰属してしまい、「worker を減らすと速い」向きに系統的な偏りが入る**。
- **ただし投入順は [T-1563] の実測を説明しきらない。** 報告者自身が訂正しており、所要固定の
  simulation では n=48 (181.6 秒) が n=32 (228.0 秒) より速く、実測の 391.28 対 358.96 秒とは
  向きが逆である。[T-1563] が記録した work 総和の減少 (6,705 → 4,861 → 3,361 秒) の方が本体で、
  これは競合が減って所要そのものが縮んだことを意味する。**2 つは別の機序**であり、
  投入順の発見は worker 数の効果を否定しない。親はこの訂正を採用する。
- **並行セッションの段 8 候補 4 件を [T-959] の収容対象に含める。** entry 859 本文に実測付きで
  記録済みだが T 項を持たず、収容 wave の scope から外れる位置にあった。**5 件目
  (`hooks/guard_bash.py` の interpreter 検出に前置 command の穴) は報告者自身が再検査して
  反証しており、含めない** — 素の `python3 -m pytest ... --collect-only` も許可されており、
  `/usr/bin/time` 形の拒否は解析不能な形に対する正しい fail-closed であって防壁の穴ではない。
- **測定値を固定値として引かない。** 報告された排他鎖 103.0 秒 x 2 は 2026-08-23 09:46 の 1 走で
  あり、[T-1567] 側の同じ鎖の実測が 64.7〜248.7 秒と幅を持つことから、負荷で大きく動く。
  [T-1563] の後に測り直す前提で扱う。
- **索引ツールの偽陰性を 1 件自分で踏んだ。** [T-1570]〜[T-1573] を「live でない」と読んだが、
  原因は解決済み index を再生成せずに古い結果を見たことで、着地済み worklog では 4 件とも
  entry 860 へ正しく carry されていた。**保存則の退行ではない。** 台帳側の異常を疑う前に
  自分の道具の再生成を確かめる、が正しい順序である。
