## {{D:axis1-cutoff-shared-calendar-boundary}}. 文献検索の cutoff は索引固有の日付欄へ共有の暦境界を当てる

**決定:** 7.7.4 が求める「同一 cutoff の 3 索引の和集合」を、次の形で定義する。
**上限境界は暦年境界 (軸 1 では 2026-12-31) とし、各索引は自分の日付欄にこの同じ境界を当てる。**
arXiv は `submittedDate` の閉区間、OpenAlex は `to_publication_date`、
DBLP は年 facet を使わず全年を取得して record の `year` field で client 側に判定する。
**定型名は「索引固有の日付欄へ共有の暦境界を当てた登録取得集合の和」とし、
「同一 cutoff の 3 索引の和集合」という短縮を禁じる。**

**理由:**
- **日単位の同一 cutoff は 3 索引に課せない。** DBLP には日付の範囲指定が無く、年 facet か
  record の `year` しか無い (2026-08-27 実測)。日単位を要求したままでは `RW3` に到達できない。
- 暦年境界なら 3 索引とも自分の日付欄で表現できる。**上限境界が落とすのは、その境界より後の
  日付を持つレコードだけである** — 取得日より後でも境界内なら母集合に入る。
- **境界は work 単位で一様にならない。** 同じ研究が索引ごとに違う年で記録されていれば、
  一部の索引の record だけが残る。和集合は record の和なので候補としては残るが、
  record 数は索引間で一致しない。この非一様性は work-family 台帳で可視化する。
- 3 索引は語の意味論も違う (フィールド指定 / ステミング / 前方一致)。母集合を「同じ概念の
  検索結果」と呼ぶと、この差が読者から見えなくなる。

**却下した選択肢:**
- **日単位 cutoff の維持** — DBLP が満たせず `RW3` が到達不能になる。
- **DBLP を母集合から外す** — 7.7.4 が「使えなかった索引を黙って母集合から外さない」と禁じている。
- **DBLP の枝だけ年 facet を列挙する** — 下限を決めないと有限化できず、下限を決めると
  その年より前を黙って落とす。全年取得 + client 側判定なら下限が要らない。

## {{D:axis1-completion-predicate}}. 文献検索の「全件取得した」は 6 条件の論理積で機械判定し、有限の監査であることを明記する

**決定:** 登録した各 query について、(1) 解釈後クエリが登録した期待値と正規化後に一致、
(2) ページ位置が欠落も重複もなく連続、(3) 各ページで要求件数・索引の宣言件数・実要素数が一致、
(4) 正規化主キーがページ内外で重複しない、(5) unique record 数が索引の総件数と一致、
(6) HTTP status・content type・最終 URL・必須要素が正常、の**全部が成立したときだけ**
その query を `完走` とする。**軸の成熟度は全 query の論理積でだけ上がる。**
**同数の入れ替えは 6 条件を全部満たしても検出できないことを明記し、
複数窓にまたがる枝には独立した連続 2 走の主キー集合 digest 一致を要求する。**

**理由:**
- **保存項目を並べるだけでは完走の判定にならない。** DBLP は要求 `h` の超過を黙って
  100 件へ切り詰め、エラーを出さない (2026-08-27 実測)。`@sent` と要求 `h` を突き合わせない限り
  気づけない。
- **偽陰性は静かである。** 索引は空集合と誤設定を同じ形 (200 + 0 件) で返す。
  0 件そのものを無効の理由にはできない (正しい query が真に空集合を返すこともある) ので、
  解釈照合と陽性対照で誤設定を分離する。
- D384 に従う。**有限観測は普遍性を含意しない。** 文献検索にはコード検索の厳格 parser に
  相当する「安価側と高価側が同じ意味論を通る」構造がないので、根拠を構造的制約に置けない。
  3 索引とも snapshot token を提供しないため、同数の入れ替えは原理的に排除できない。
  **この限界を落として成熟度を語ってはならない。**
- D351 に従う。**陽性対照の通過を根拠にしてはならない。** 対照だけが通る誤って狭い式が書けるので、
  独立した補助経路で得た適格候補が主 query の和集合に無ければ走行を無効にする。

**却下した選択肢:**
- **完走した枝だけで成熟度を名乗る** — 予算切れや 429 で後半の広い枝が丸ごと落ちても
  気づけない。予算切れ・429・503・再試行上限は軸全体を `未完走` にする。
- **構造的な完全性証明を要求する** — snapshot token が無い以上、要求すれば `RW3` が
  到達不能になる。有限の監査と限界の明記に留める。

## {{D:axis1-nonsemantic-repair-normalized-request}}. 登録した検索式の「非意味的修繕」は正規化 request の一致で判定する

**決定:** 事前登録した query を実行時に修繕するとき、**同じ query ID のまま許すのは
正規化 request が同一である変更だけ**とする。正規化 request は endpoint・検索フィールド・
filter 本体・sort・page size・位置パラメータの遷移規則・取得フィールドの射影からなる。
**索引が返す解釈後クエリの一致だけを根拠にしてはならない。**
それ以外の変更は意味的 amendment とし、旧走行を `未完走` に固定したうえで、
新しい日付の amendment 文書・新しい query ID・全枝の再実行・独立レビューを要求する。
**旧結果を見た後の改訂であることを amendment に明記する。**

**理由:**
- **解釈後クエリは request 全体に対して単射ではない。** DBLP の `result.query` は検索語だけを
  表し、`h` と `f` を含まない (2026-08-27 実測。`h=50` と `h=1000` で同じ echo が返る)。
  echo の一致だけを基準にすると、ページング条件を変えて別の返却集合を得ても
  「同じ interpreted query」として正式走行に通ってしまう。
- 事前登録の意味は、結果を見た後に語や式を都合よく変えられなくすることである。
  修繕の口を「実質的に別の検索」まで広げると、事前登録が事後の被覆説明に戻る。
- D350 に従う。**前置フィルタは実際に走る式へ束縛する。** 絞り込みと本体が別物になると、
  前置フィルタが正しい hit を捨て、受理集合が変わる。

**却下した選択肢:**
- **どんな修繕も新しい query ID を要求する** — API の文法変更や escaping の差で
  返却集合が変わらない場合まで全枝再実行になり、予算の面で `RW3` が到達不能になりうる。
- **実行者の判断に委ねる** — 判断の記録が残らず、後から検証できない。
