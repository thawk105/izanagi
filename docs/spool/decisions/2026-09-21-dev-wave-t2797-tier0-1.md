## {{D:b5-tier0-common}}. B-5 共通 Tier0 は子の候補経路で perf build + 固定スモークを投入前に行い、不通過は A だけを消費する

**決定:** D2200 項 1 (2) 5 に従い、B-5 生成器対照の共通 Tier0 (事前登録 §3.1 のコンパイル + 固定スモーク) を実装した。

- **置き場:** `p3_s4_loop` の B-5 mode の候補経路 (search / score の proposal slot) だけ。検疫・条件の意味検査の後、`pipeline-submitted.json` の前。
  stock slot・非 B-5 経路・`do_build=False` は不変。b5 driver に build 権限を足さない (D2198 の却下と同型)。
- **コンパイル:** pipeline の perf build (`trace=False`) と同じ build 経路・同じ引数で 1 本を投入前に作る。pipeline 側の perf build は cache hit になる。
  trace build は従来どおり投入後 (事前登録 §3.3 が correctness の build を投入後と明記)。
- **固定スモーク:** trace-disabled binary を全 arm・全候補・全 workload で同じ argv (`thread_num=4 / ycsb_tuple_num=200 / extime=1 / ycsb_rratio=50 /
  ycsb_zipf_skew=0.9 / ycsb_rmw=true / ycsb_max_ope=5`、clocks_per_us と numactl は env contract の値) で既存 gateway `run_once` から 1 回、bench lock 下で走らせる。
  通過条件は rc 0 と既存パーサでの commit > 0・throughput 有限正。timeout は 32 s (gen_S 実測 30 走の max 1.0463 s × 30)。
- **失敗の計上:** build の `(RuntimeError, subprocess.SubprocessError)` とスモークの失敗 (rc 非 0・出力不正・commit 0・timeout) は候補起因として A だけを消費し
  (B は消費しない、retry しない)、search は次の機会へ進む。これは投入後の同じ build 失敗を D2198 が候補起因 (`build-failed`、B 消費) に分類している規約を投入前へ移すだけで、
  帰属の規約は変えない。それ以外の例外は捕まえず、既存の分類不能欠測 (系列停止) に落とす。score slot での不通過は探索予算を動かさず既存の非 certified 分岐で系列を止める。
- **記録:** 子が slot ごとに `tier0.json` (契約全体・通過/不通過・理由・perf binary の sha256 と cache hit・スモークの rc / wall / commit) を投入前に durable に書く。
  driver は submission の有無に関わらずこれを読み、投入済みなのに通過証拠が無ければ分類不能欠測とする。台帳 event には状態・理由・sidecar の sha256 だけを載せ、
  スモークの数値は載せない (fitness・current_perf・leading indicators・endpoint・親への射影へ流さない、規律 1)。header の `tier0_status` は `implemented`、
  `tier0_contract` は子の定数 1 箇所の写し。report は共通構成比較に Tier0 の 2 key を加え、契約の混在を拒否する。
- Tier0 の拒否 outcome `rejected-tier0` は base driver の provenance の outcome 集合に含める (WAL を書かないので WAL 参照は空)。
  含めないと、Tier0 拒否のたびに子が provenance の記録で異常終了し、その iteration の provenance と loop state を公開しない (driver の分類は sidecar で決まるので変わらない)。
- Tier0 の通過は certified を意味しない。verify / anomaly reject / bench は従来どおり (規律 2)。

**理由:**
- 事前登録 §3.1 は「A / B の分離は Tier0 通過で決まる」と定め、D2200 項 1 は未実装の受容を却下した。投入前に置かなければ build 失敗が B を消費する (現行は `pipeline-submitted.json` が build より先)。
- コンパイル対象を perf 1 本にしたのは、スモークが走らせる binary であり、trace build の失敗を投入前へ移すと §3.3 の「投入後の correctness build」の計上を変えるため。
- 例外境界を pipeline と揃えたのは、同じ失敗集合の帰属を投入前後で変えないため。コンパイラの非ゼロ終了が候補起因の証明にならないこと自体は既存規約の限界として残る
  (試走 53 session で build 失敗 0)。
- スモーク argv は pipeline の既存の小構成 (correctness 既定値) で、保護対象の ratio を踏まない rr50。

**却下した選択肢:**
- driver 側で build する — D2198 が却下した coder build authority の新規登録と同型。
- trace / perf の両 build を投入前に作る — trace 固有の失敗が B 消費から A のみへ移り、事前登録 §3.3 の計上を変える。
- Tier0 開始印を別 sidecar で残す — A は attempt-start、B は submission で既に回収でき、失うのは中断位置の細分化だけ。
- build の全例外を候補起因にする — admission・source evidence・I/O の障害まで生成器の失敗として A を枯らす。
- score slot を Tier0 から外す — 子の経路が 2 本になり flag が要る。score も候補を pipeline へ投入する (§3.1)。
- スモークの数値を台帳 event に載せる — handshake の `slot-*.json` を経て親の射影へ流れうる。

## {{D:b5-llm-parent-operation}}. B-5 LLM arm の親運用 — 1 系列に 1 親 session、同時親数 p = 4、1 機会 2,700 s は変えない

**決定 (設計のみ、実装しない):**
- `LLM_WAIT_S = 2700` (D2198) は変えない。LLM 系列 1 本に親 session 1 本を系列開始前に確保し、系列終了でその context を廃棄する (事前登録 §4.1 の fresh context)。
- 同時に走る LLM 系列は親の本数 p 以下とし、**p = 4 を運用上の選択として採る。** p は事前登録 §7.1 の配置から導かれる値ではない
  (§7.1 の 6 通りの arm 順は workload ごとの 12 組全体へ各 2 回)。
- 実効の handshake 期限は min(2700 s, 残 walltime − 1800 s) (driver は残り `SESSION_BUDGET_S` 未満で待機を打ち切る) で、poll 15 s の誤差がある。
- 親が止まった系列は登録どおり `proposal-wait-timeout` / `allocation-exhausted` の欠測とし、救済・再抽選しない。
- 数値の出所: 1 巡 10〜13 分 = 試走の実測 (1 系列 10 巡、上限保証ではない)。780 / 2700 ≈ 29% は算術。36 系列 × 10 巡 = 360 巡 ≈ 60〜78 親時間は拒否なしの外挿
  (A = 30 まで使えば最大 1,080 機会)。p = 4 なら親作業部分の理想割算で 15〜19.5 時間 (全実験の elapsed ではない)。

**理由:**
- 1 親に複数系列を順番待ちさせると待ちが 780 s × 系列数へ伸び (4 系列で 3,120 s > 2,700 s)、系列間の context 分離も崩れる。
- 無応答は分類不能欠測で arm 非対称の欠測になるので、期限に対し試走の巡時間で 3 倍以上の余裕を残す。

**却下した選択肢:**
- 期限を延ばす — 登録済みの handshake 設計 (D2198) の変更で、欠測の発生点を後ろへずらすだけ。
- 1 親 2 系列以上 — 上記。
- 親 spawn / schedule の自動化をこの段で作る — 108 系列の schedule・launcher と同じ発効束の段で扱う。

## {{D:b5-common-walltime}}. B-5 本走の job walltime — 探索 3 arm 共通 W = ceil(21,259 s × k)、block-stock は別基準、k は再提示で決める

**決定 (設計のみ、実装しない):**
- 探索 3 arm (llm / random / sweep-matched) の series job は同じ W = ceil(21,259 s × k) を要求する (事前登録 §3.3「全 arm 同一」)。
  21,259 s = 試走の series job Elapse の実測最大 (llm arm、共有 lock 待ちと親の handshake 待ちを含む)。推定値で差し引かない。
- block-stock は探索 arm でない別 job (5 session) なので W_stock = ceil(5,447 s × k) を別基準とし、その区別を発効束 (§12) に明記する。
- k は総実行 wall の倍率と共に、完成した発効束の再提示でユーザーが決める (候補 2 → W = 42,518 s、W_stock = 10,894 s)。gen_S の上限 86,400 s から k ≤ 4.06。
- `SESSION_BUDGET_S = 1800` は次 slot 開始の残時間判定で timeout ではない。deadline は job body の scheduler 開始時刻 + 要求 walltime のまま。

**理由:**
- §3.3 は「試走で測った最大所要への倍率」を定める。LLM arm は親待ちを含むので最大になり、全 arm 同一の基準はその値になる。
- 限界: 試走は write-heavy・n = 1 系列・Tier0 追加前・共有 lock 下の値で、balanced / read-heavy や A = 30 の完走を保証しない。上限不足でも n や正しさ条件を下げない (§11)。

**却下した選択肢:**
- arm 別 walltime — §3.3 と衝突 (D2200 項 1 の理由)。
- lock 待ちの推定値を差し引いた基準 — 仮定付き模型の値を上限の基準にしない。
- block-stock も 21,259 s 基準 — 5 session の別 job に 4 倍近い予約を掛ける根拠がない。
