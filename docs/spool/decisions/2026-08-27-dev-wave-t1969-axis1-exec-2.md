## {{D:literature-search-record-and-sidecar}}. 文献検索の実行記録は凍結 docs と digest 束縛 sidecar に分ける

**決定:** 事前登録した文献検索の実行記録は、意味の正本を
`docs/related-work/claim-survey/<日付>-<軸>-search-execution.md` の凍結物に置き、
頁ごと・record ごとの機械可読な取得証拠は
`output/insights/<日付>_<topic>/` の sidecar に置く。sidecar は `manifest.json` と
`MANIFEST.sha256` で file ごとの digest を束縛し、**凍結物側が `manifest.json` の SHA-256 を
参照する**。HTTP 応答本文の全文は保存しない。

**理由:**

- 契約 §10 が要求する保存 field は record 単位まで下りる。1 軸の 1 回の実行で数万行になり、
  markdown の凍結物には載らない。載せれば読めなくなり、載せなければ再監査できなくなる。
- `output/insights/` には既に digest 束縛の構造化証拠と `.json.gz` を追跡する慣行がある。
  新しい top-level namespace を作る理由がない。
- 束縛の向きを「凍結物 → manifest」にすると、自己 hash 参照を作らずに済む。
  manifest 自身は `files` に自分を含めない。

**却下した選択肢:**

- **凍結物へ全 record を書く** — 数万行になり、凍結物としても読み物としても機能しない。
- **証拠を repo の外に置く** — 凍結物が参照する先が消えうる。再監査が不可能になる。
- **応答本文を全文保存する** — 契約が要求しているのは構造化台帳であって本文ではない。

## {{D:frozen-table-annotation-via-successor}}. 凍結表への注記は後継表で行い、恒久規則は規則の正本へ置く

**決定:** 凍結済みの表へ注記を足せと裁定されたときは、**凍結物を書き換えず**、
(a) 全行を持つ後継表を新しい日付の凍結物として作り、(b) 恒久的な禁止・義務は living な
規則の正本へ書き、(c) ディレクトリ README の一覧から原表の行に後継表を案内する。
**この 3 つでも原表だけを開いた読者へは届かない。その残余は限界として明記し、
充足と認めるかはユーザー裁定へ返す。**

**理由:**

- `claim-survey/` の決まりごとは「各ファイルは日付付きの凍結物であり、書いた後は上書きしない」
  と定めている。注記のためでも例外にすると凍結の意味が消える。
- 後継表が全行を持てば、表だけを読んだ読者にも由来と禁止が伝わる。行の一部だけを載せると
  原表と突き合わせないと読めず、precedence も曖昧になる。
- 恒久規則を日付付き凍結物だけに置くと「恒久」にならない。規則の正本に置けば、
  規則を読む経路の全員に届く。
- **到達性を完全には達成できないことを黙って落とさない。** 宣言だけの対応は恒真である。

**却下した選択肢:**

- **凍結物へ追記する** — 凍結規則を破る。1 度許すと以後の凍結物が信用できなくなる。
- **後継表に変更行だけを載せる** — precedence が曖昧になり、同じ行に 3 つの値が並ぶ。
- **恒久規則を日付付き凍結物だけに置く** — 恒久化にならない。

## {{D:multi-window-retrieval-checkpoint}}. 複数窓にまたがる取得は機械可読な再開点を残す

**決定:** 索引の無償枠や転送制限で 1 セッションに収まらない取得は、証拠 bundle へ
`checkpoints/<連番>.json` を置く。最低限、枝ごとに次を持たせる。

- `run_id` / `pass_number` / `window_number` / `state`
- `resume_action` — `continue_cursor` / `start_independent_pass` / `restart_branch` /
  `blocked_on_ruling` / `not_applicable` の enum
- **cursor を継ぐ場合と、独立した 2 走目を始める場合の、完全な request を 2 本とも**
- 完了済み台帳の path と主キー digest、2 走目があればその digest と一致の可否
- 枝別に待っている裁定の ID、quota の観測時刻と残量

**「窓をまたいで cursor を継ぐ」と「独立 2 走目を先頭から始める」は別状態として区別する。**

**理由:**

- 取得が複数日に分かれると、続きを実行するのは別のセッションになる。
  散文の説明では、cursor を継ぐのか取り直すのかが読み手の解釈に委ねられる。
- 取り違えると返却 record 数・distinct digest・2 走一致の受理可否がすべて変わる。
  再開点の曖昧さは、そのまま完走判定の曖昧さになる。
- 完全な request を書いておけば、schema を読まなくても次の 1 手が実行できる。

**却下した選択肢:**

- **散文で「ここまで取った」と書く** — 再開点が一意に決まらない。
- **cursor だけを残す** — 独立 2 走目を始めるべき場面で cursor を継いでしまう。
- **checkpoint を置かない** — 続きの実行者が最初から取り直すことになり、無償枠を無駄にする。
