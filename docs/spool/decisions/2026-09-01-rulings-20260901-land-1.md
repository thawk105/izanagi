## {{D:s8b-a6-proof-is-approved-g1-successor}}. 8b 正式起動の前提 A6 の証明は凍結 g1 の承認済み successor とし、担当は工程で割る

**決定 (ユーザー裁定):** D1264 の決定部分 (A4 / A6 を必要条件として維持し、A5 / A7 の完成待ちだけを
置換または非認証化する) はそのまま保つ。理由が着手前実測で覆った点を次の 3 つで確定する。

1. **A6 の proof は「凍結 g1 の承認済み successor」で足りる。** 環境世代を g2 へ進めることは
   要求しない。
2. **remediation owner は主体でなく工程で割る。** A4 / A6 / A7 の準備と検証は AI が担い、
   承認 record の発行と有効 pointer の発効は人間が担う。A7 の発効前閉包にも人間承認が含まれる。
3. **A5 / A7 を非認証化するときは、readiness index に「認証されていない」ことを表す列を設け、
   その列で明示する。** 未充足を空欄や省略で表さない。

**理由:**

- 正式 launch は `orchestrator/campaign/s8b_ratified_freeze.py` の
  `certificate-generation-scope` が `generation_number == 1` 専用に限定している。
  g2 まで進めると組む相手が範囲外になり、かえって拒否される。実測で確定している。
- 「A4 / A6 は人間、A7 は AI」という主体単位の割り方は粗すぎる。D437 が環境契約 g2 の活性化を
  上位権限束の人間 lockstep 待ちと定めており、準備・検証と承認・発効は同じ主体に属さない。
  工程で割ると、AI が進められる範囲と人間の手番が各条件について一意に決まる。
- 未充足を明示する列を持たないと、認証されていない条件が「まだ書かれていないだけ」と読める。
  D444 の床値 protocol 張替えだけで A6 を閉じるのは凍結側の承認を経ない近道であり、
  絶対規律 2 に触れるため採らない。

**却下した選択肢:**

- **凍結世代を g2 まで進める** — 正式 launch の適用範囲が generation 1 専用のため拒否される。
- **A5 / A7 だけを置換して A4 / A6 を後回しにする** — 律速が A6 へ移るだけで activation は進まない。
  A6 は現物が皆無で activation 経路へ未結線であることを実測済み。
- **owner を主体単位 (人間 / AI) で割る** — A7 の発効前閉包に人間承認が含まれるため、
  条件単位では担当が一意にならない。

## {{D:floor-budget-counted-by-cross-generation-replay}}. 試行台帳の予算は専用台帳を作らず、世代別台帳を横断して数える

**決定 (ユーザー裁定):** D1193 が留保し D1279 が「設計案が出た時点で諮る」と確認した予算の
置き場所を、**世代別台帳を横断して replay し予算を数える形**に確定する。
freeze 単位の予算専用 ledger は**作らない**。

**理由:**

- 専用 ledger は新しい権威を 1 つ増やす。増やすだけの必要性 — replay の所要、原子性の不足、
  二重計上の実在 — はいずれも未実測である。実測のない防壁を先に建てないという規律 5 に沿う。
- 世代は現時点で 1 つしかなく、横断 replay の対象は小さい。世代が増えて replay が実害を
  出した時点で専用 ledger を再検討すれば足り、その時点なら必要性を実測で示せる。
- D1193 の 2 つの要求 (台帳は protocol 世代ごとに分ける / 予算は凍結単位に残す) は、
  横断 replay でも両方満たせる。予算の権限を凍結単位に置いたまま、台帳の分割を保てる。

**却下した選択肢:**

- **freeze 単位の予算専用 ledger を別に置く** — 必要性が未実測のまま権威を増やす。
  親の初版はこれを推奨したが、別系統モデルの相談が規律 5 違反と判定し、撤回した。
- **予算も世代ごとにリセットする** — D1193 が明示的に却下済み。

## {{D:registry-wiring-and-binding-land-together}}. 試行台帳の配線と proof chain 束縛は同じ変更単位で land する

**決定 (ユーザー裁定):** 床値 campaign を試行台帳の書き手へ配線する作業と、D1194 が定めた
前向き束縛の検査は、**同じ変更単位で同時に land する。** 片方だけを先に land しない。

**理由:**

- 書き手だけ land すると、台帳の欠落を許したまま追跡を謳う状態になる。D1194 が却下済みである。
- 検査だけ land すると、唯一稼働している pilot campaign が result 組立の直前で停止する。
  D1114 (b) の「先行 land すると死んだ gate になる」に該当し、独立した敵対検査 2 本が
  そう判定している。
- どちらの片側 land も成果物の意味を偽る。同時 land だけがその 2 つを同時に避ける。

**却下した選択肢:**

- **配線を先行させ束縛を次に land する** — D1194 の却下欄「書き手だけ land して束縛を後続へ送る」
  に当たる。
- **束縛を諦める** — D1194 が既に却下している。

## {{D:final-table-does-not-recheck-registry-liveness}}. 公式選択表の発行層は台帳の生存を再確認しない

**決定 (ユーザー裁定):** 公式選択表を発行する最終層は、批准済み成果物を path と hash で
照合するところまでを責務とし、**消費時点で試行台帳の生存を再確認しない。**

**理由:**

- certification 自体は批准経路で起きている。消費時点の再確認は D1194 が求める
  「新規成果物への前向き束縛」より強い性質であり、要求されていない検査を足すことになる。
- 増やした検査が何を防ぐのかを示す実測がない。規律 5 (必要なものだけ持つ) に沿って持たない。

**却下した選択肢:**

- **発行時点でも台帳の生存を要求する** — D1194 の要求を超える。防ぐ対象が実測で示されていない。

## {{D:b4-proposal-binding-closes-in-the-loop}}. B-4 の先行提案と実 campaign の束縛は実行ループ側で閉じる

**決定 (ユーザー裁定):** B-4 の先行提案と実 campaign の束縛は、**実行ループ側で閉じる。**
ループが提案の canonical hash を再計算し、封印済み registry と一致しなければ**実行前に拒否する。**

**理由:**

- issuer は期待 hash を封印できるが、実際に消費される proposal との一致は強制できない。
  一致を強制できるのは実行直前のループだけである。
- 束縛が閉じないまま実走すると、raw 記録は「事前固定した 201 試行」ではなく
  「registry のラベルを付けた 201 の選択可能な証拠」に留まる。受理集合を狭める向きの検査であり、
  絶対規律 2 と整合する。

**却下した選択肢:**

- **issuer 側だけで閉じる** — 封印はできても、消費される proposal との一致を強制できない。
- **束縛を閉じないまま実走する** — 記録が事前固定を意味しなくなる。

## {{D:reference-tps-domain-measured-before-ruling}}. 非有限十進の基準値の扱いは、実際の値域を実測してから決める

**決定 (ユーザー裁定):** 非有限十進の `reference_tps` を registry で禁止するか、凍結済み consumer を
改訂して exact に受理するかは、**実測を先に置いてから決める。** 測るのは、予定されている
scheduled input すべての `reference_tps` を列挙し、非有限十進が正当な upstream 出力として
一度でも生じるかである。ゼロなら registry の受理値域を狭め、実在するなら exact ratio を
受け取れるよう consumer を改訂する。**丸めて受理する案は採らない。**

**理由:**

- どちらが正しいかを決める材料は production の値域そのものであり、現時点でそれが測られていない。
  測れば択一が消える種類の問いである。
- 丸め受理は受理集合を広げ、凍結された消費側が受け取る値を元の値と別物にする。絶対規律 2 に反する。

**却下した選択肢:**

- **実測前に registry で禁止する** — 正当な upstream 出力を拒否しうる。
- **実測前に凍結 closure を変える** — 凍結を動かす費用を、必要性を確かめずに払うことになる。
- **丸めて受理する** — 規律 2 に反する。

## {{D:raw-producer-authentication-layer-chosen-by-rejection-power}}. raw-record producer の認証層は、候補層の拒否能力を変異で比較してから決める

**決定 (ユーザー裁定):** 凍結 closure 外にある raw-record producer をどの層で認証するかは、
**候補層ごとの拒否能力を実際に測ってから決める。** 未 pin の別 producer が異なる判断値を作る変異を
通し、issuer・raw assembly・frozen consumer のどこが最小の変更で確実に拒否できるかを比較する。
5-file pin を単純に広げる案は、比較の結果それが最小と示された場合を除き採らない。

**理由:**

- 候補層ごとの拒否能力と変更閉包が示されていない状態では、どの層が正しいかを決められない。
- pin を広げるのは凍結 closure を動かす操作であり、他の候補層より変更閉包が大きい。
  最小変更で同じ拒否ができる層があるなら、そちらが規律 5 に沿う。
- source bytes の hash が一致しても producer 意味論を verdict が識別できない、という欠陥自体は
  実在する。放置はしない。

**却下した選択肢:**

- **比較せず 5-file pin を広げる** — 凍結 closure を動かす費用を、最小性を確かめずに払う。
- **現状のまま運用する** — 別 producer 由来の記録を verdict が識別できない欠陥が残る。

## {{D:campaign-flock-covers-authorization-through-checkpoint}}. campaign の advisory flock を認可から記録完了まで広げる

**決定 (ユーザー裁定):** 公式 loop の advisory flock の範囲を、実行の内側区間だけから
**authorization・preflight・実行・checkpoint 完了までを覆う範囲**へ広げる。

**理由:**

- 現状は実行中の arm を終了済みと誤判定でき、その誤判定が不可逆な `missing` として記録される。
  block score と verdict が変わるため、記録の正しさに直接効く実在の欠陥である。
- producer が「実行中か終了済みか」を確実に判定できることは、記録の意味の前提である。
  範囲を広げること以外にこれを満たす形が示されていない。

**却下した選択肢:**

- **内側区間のままにする** — 誤判定で結果が変わる経路が残る。
- **判定を producer 側の推測で補う** — 推測に基づく `missing` は不可逆な記録を生む。

## {{D:hold-evidence-is-provisional-fragment-bound-before-land}}. 非帰属 hold の登録要件は、未 fold の failure fragment を content hash で仮受理し land 前に正式 F へ束縛する

**決定 (ユーザー裁定):** 受入の非帰属赤を hold へ登録するときの証拠要件を次へ改める。
**exact node と再現証拠を持つ未 fold の failure fragment を、content hash 付きで仮に受理する。**
最終 land の前に、その仮受理を正式な F エントリへ束縛する。
「main に既存の F」を land 前の時点で要求しない。

**理由:**

- 現行契約は循環している。新しい node について F を land するには受入全走が要り、
  その全走を通すには hold が要り、hold には既存の F が要る。受入 1 回分と wave 1 本を実際に失っている。
- 循環を断つのに証拠そのものを弱めてはならない。仮受理の対象を content hash 付きの
  failure fragment に限れば、証拠の内容は固定され、land 前に正式 F への束縛を要求できる。
- **受入 receipt の「差分へ非帰属」判定だけを証拠として受理する案は採らない。**
  それを許すと、壊れた正しさ検査までを skip 対象にでき、絶対規律 2 を緩める。
  非帰属 receipt は故障がどこに属するかを言うだけで、故障の性質を証明しない。

**却下した選択肢:**

- **非帰属判定だけを hold の証拠として受理する** — 規律 2 を緩める。親の初版はこれを推奨したが、
  別系統モデルの相談が反対し、撤回した。
- **現行契約のまま運用する** — 循環が閉じたままで、性質そのものが破れる node では抜け道がない。
- **hold の要件から証拠を外す** — 受入の赤を無条件に迂回できるようになる。

## {{D:mocc-trace-oid-remedy-chosen-after-graph-probe}}. 外部 oid の到達性は、候補 commit graph と no-fetch 初期化での実在確認を経てから 3 案を選ぶ

**決定 (ユーザー裁定):** `mocc_trace.new_oid` が pin 済み submodule commit から到達できない問題の
恒久策は、**候補 commit graph を作り、通常の no-fetch 初期化をした fresh worktree で oid の実在と
witness の意味論を確認したうえで、(a) pin 済み commit から到達可能にする / (b) init tool に
provisioning を持たせる / (c) witness を upstream へ出す、の変更範囲を比較して決める。**
テストを緩める案は採らない。

**理由:**

- (a) が有利だという根拠は失敗記録から出てこない。(a) にも submodule pin の変更や履歴の
  再構成が要る可能性があり、その範囲が測られていない。
- 「主 checkout でだけ通り、どの wave worktree でも落ちる」という状態は実在する。放置しない。
- 実在確認を no-fetch 初期化で行うのは、実際の worktree が置かれる条件と同じにするためである。

**却下した選択肢:**

- **比較せず (a) を採る** — 親の初版はこれを推奨したが、優位性の根拠が示せず撤回した。
- **当該 oid の実在を assert するテストを緩める** — 外部由来の受理集合を無検査で広げる。

**決定 (ユーザー裁定):** D1203 が定めた「候補が揃った時点で 1 件ずつ裁定へ返す」の対象を、

## {{D:ratification-residue-a-rides-along-bc-deferred}}. 批准撤去の残骸は hooks 記述だけ相乗りで閉じ、他 2 件は次に触る wave で直す

**決定 (ユーザー裁定):** D1139 の批准撤去が残した 3 件のうち、
**(a) `hooks/README.md` が破棄済みの道具を現存するものとして記述している件だけを、
同じ編集面を触る wave へ相乗りさせて閉じる。**
(b) 空の互換 fixture と (c) `docs/failures.md` の F594 の根拠更新は、
**次にその編集面を触る wave で直す。** 単独の wave を起こさない。

**理由:**

- 3 件とも受理集合を変えないため緊急性はない。
- (a) は hooks の配線の正本が撤去済み機構を指したままであり、読んだ者が存在しない道具を探す。
  同じ編集面を触る予定があるので、相乗りの費用がほぼゼロである。
- (b) と (c) は別の編集面にあり、同梱できない。害が小さく、単独で wave を起こす費用に見合わない。

**却下した選択肢:**

- **3 件すべてを 1 wave で掃除する** — (b) (c) のために単独 wave を起こす費用に見合わない。
- **3 件とも放置する** — (a) は配線の正本が事実と食い違ったままになる。

## {{D:parent-may-terminate-when-superseding-ruling-names-the-old-one}}. 覆す事実が後続のユーザー裁定であり旧裁定を名指しして実効を奪っている場合、親が終端裁定を下す

**決定 (ユーザー裁定):** `DW-S04` の「承認済み裁定は裁定時の未見事実でだけ止め、親は不採用にせず
ユーザー再裁定待ちへ戻す」に、次の区別を入れる。

1. **覆す事実が台帳に未記録** — 現行どおりユーザー再裁定待ちへ戻す。
2. **覆す事実が後続のユーザー裁定であり、その裁定が旧裁定を D 番号で名指しして実装不能・実効喪失と
   明記している** — 戻さず、**親が既裁定の適用として終端裁定を下し、射程を decisions へ記録する。**

**判定基準は「後続裁定が旧裁定を D 番号で名指ししていること」に限る。**
名指しが無く含意だけの場合は 1 に倒し、従来どおり戻す。

**理由:**

- 2 を戻すと、すでに下されている裁定を同じ主題でもう一度問い直すことになる。
  問い直すべき設計択一が残っていない場合にユーザーの手番を作るのは、裁定の費用を無駄に増やす。
- D1308 が同じ批准機構について「破棄は既裁定の適用であって新しい設計判断ではない」と定めており、
  既裁定を当てはめるだけの操作が新しい裁定を要さないという先例が既にある。
- 名指しを基準にするのは、親が含意を拡大解釈して裁定境界を自分で動かすことを防ぐためである。
  含意だけの判定を許すと、親が「実効を奪われた」と読める限り何でも終端できる。

**却下した選択肢:**

- **現行のまま全件を戻す** — 決着済みの主題を問い直す手番を作り続ける。
- **含意だけでも親が終端できるようにする** — 親が裁定境界を自分で動かせるようになる。
- **親が独断で不採用にできるようにする** — `DW-S04` が禁じている当のものである。

## {{D:multinode-shard-design-precedes-ruling}}. multi-node shard は測定設計を先に作ってから諮る

**決定 (ユーザー裁定):** multi-node shard の効果は未測定であり、**まず測定設計を作り、
その設計を持って改めて諮る。** 現時点で K を再裁定しない。設計には、同一 tip・同一 collection で
node 数だけを変え、wall・総仕事量・最長単体・queue 待ち・受理集合を記録することを含める。

**理由:**

- 効果が未測定のままでは諮る材料がない。D1103 が K=3 を確定しており、本項は K の再提案ではない。
- 比較条件を先に固定しないと、node 数以外の差が結果に混ざる。
- D820 を不可能性の根拠に使わない。D1103 がその前提の失効を明記している。

**却下した選択肢:**

- **設計なしで K を再裁定する** — 材料がない。
- **効果は測らないと決める** — 唯一残る所要短縮の方向を、測らずに閉じることになる。
