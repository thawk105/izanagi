## {{D:regenerable-artifact-exclusion}}. 再生成可能物は監査対象から外し、外した事実を開示する

**決定:** `tools/audit_dangling_commits.py` は、**失われても正本から再生成できる派生物**の path 接頭辞を
監査の詳細対象から除外する。除外集合の正本は tool 内の専用定数 1 箇所とし、fold 除外
(`docs/spool/` と `docs/archive/`) とは別の定数・別の CLI flag で持つ。初期の対象は
`output/s8b-build-cache/` の 1 件である。

**除外は沈黙させない。** 除外した (commit, path) 対の総数と、**派生物だけを変更したために
詳細監査を省いた到達不能 commit** を、commit ID・subject・除外 path 数で stdout へ列挙する。
この列挙は blob 取得も repo 外走査も行わないため追加コストは実質ゼロで、rc も変えない。

**理由:**
- 除外の根拠は「速いから」ではなく「その path 集合が失われても再生成できるから」である。
  `.gitignore` は姉妹の `output/s1-build-cache/` を「数万ファイル・GB 級の生成物。WAL/report が
  正本で、キャッシュは再生成可能」として無視しており、凍結の proof chain も同 build cache を
  path 集合から明示的に排除している。同じ性質の資材である。
- 実測すると、対象 repo の到達不能 commit 2,782 本が変更した (commit, path) 対 16,395 のうち
  13,488 対 (82.3%) がこの build cache だった。除外すると要確認対は 14,104 から 616 へ減るが、
  **報告される commit は 51 のまま 1 本も消えない。** 修正前後の全走でも要確認は 47 commit で一致した。
- ただし「消える commit 0」は実測であって不変条件ではない。将来 build cache だけを変更した
  到達不能 commit ができれば、その commit は詳細監査から外れる。**だから沈黙でなく開示にする。**
  消えるのは詳細監査であって commit の存在ではない、という形にすれば検出力は落ちない。
- fold 除外と連動させないのは、解除の用途が違うためである。fold 除外の解除は
  「fold が消費する tree も見たい」であり、再生成可能物の解除は「除外が救出対象を隠していないか
  確かめたい」である。1 つの flag に束ねると、片方を確かめるためにもう片方も外れる。

**却下した選択肢:**
- **`.gitignore` を除外集合の正本にする** — `.gitignore` は現時点の無視規則であって履歴上の
  派生物の集合ではない。現に `output/s8b-build-cache/` は無視されていないのに派生物である。
- **生成 manifest に列挙された artifact だけを除外する** — 条件付き機能は発火条件を満たす
  実在の artifact path を書ける場合だけ実装するという規律 (DW-G04) を満たさない。
  manifest は現時点で実在しない。producer 側が持つようになったときの再訪候補とする。
- **除外を黙って行う** — 将来の救出対象が無言で消える。検出力を落とす変更は速度と引き換えにしない。

## {{D:audit-duration-limit-binds-acceptance-not-deletion}}. 監査の所要上限は wave の受理を拘束し、掃除の削除可否は拘束しない

**決定:** 到達不能 commit 監査の所要上限 (300.000 秒) は、**2 か所で異なる強さ**を持つ。

1. **wave の受理条件としては拘束する。** 監査を変更する wave は、warm-up 1 走を捨てた独立 3 走の
   **最大**が上限以下でなければ受理しない。最大と最小の比が 1.5 を超えたときだけ 3 走を追加し、
   全 6 走の最大で判定する。主観の「外乱の疑い」で測定値を捨てない。
2. **掃除の削除可否は拘束しない。** 遅いだけの監査も安全結果としては有効であり、遅さを理由に
   削除を止めるのは正しい監査結果を捨てる方向の縮退である。

**恒真化を避けるため、超過時に義務が 1 つ増える。** tool は所要を常に stdout の最終行へ出し、
上限を超えたときは専用の超過行を出す。掃除はそれを §5 で性能退行として報告する。
上限値の正本は tool 内の定数 1 箇所とし、`--help` と出力が開示する。docs へ数値を再掲しない。

**理由:**
- 300 秒はユーザーが与えた目標値であり、実測分布の max への倍率で導いた経験的予算ではない。
  そう書き分けないと、未検証の regime に対する受理条件が実測で裏付けられたことになってしまう。
  測定は 1 login node・1 repo・1 時点のものであり、cold cache・別 node・別混雑度は未測定である。
- 「超過したらどうするか」が書かれていない上限は恒真である。削除を止めないなら、
  代わりに報告義務を増やさなければ上限は何も変えない。
- 数値を docs へ再掲すると正本が分裂する。tool が超過行を出せば、どの入口から呼ばれても
  超過が見える。docs 側は「超過行が出たら報告する」だけを持てばよい。

**却下した選択肢:**
- **超過を rc=2 にする** — rc=2 は「監査を実行できない」であり、遅いこととは別の事象である。
  遅いだけで掃除全体が止まる。
- **`timeout` で打ち切る** — 途中終了は安全結果を返さず、新しい rc の意味を増やすだけである。
- **全入口を統一する executable wrapper を新設する** — 既存の入口が wrapper を使う保証がなく、
  族への一般化は同型 2 例の実証を要する規律 (DW-G03) も満たさない。
