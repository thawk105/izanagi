## {{D:registry-binding-blocked-by-missing-writer}}. 試行台帳の proof chain 束縛は、書き手が production から呼ばれるまで land しない

**決定 (親裁定 = ユーザー裁定待ちとして返す):** D1194 が定めた前向き束縛の設計は完成させ、
実測・所見とともに凍結する。**しかし本 wave では実装せず land もしない。** D1114 の両条件が
成立したためである。D1194 は覆さない。変えるのは land の順序だけである。

**実測 (親・独立レビュー 2 本が別々に到達):**

- `launch_floor_attempt()` を production から呼ぶ箇所は 0 件、その module を production から
  import する箇所も 0 件である。呼び手は launcher 自身の test だけである。
  AST・動的 import・`getattr`・文字列解決まで含めて追加経路は無かった。
- したがって現状、床値 campaign は attempt registry を一度も作らない。
- 検査側だけを入れると、fresh 経路は result 組立の直前で、resume 経路も同様に停止し、
  publish に到達しない。台帳不在のまま新 schema の result を発行する経路は無い。
- 現在の production CLI は pilot だけで、official は別の既存検査が既に拒否する。
  つまり止まるのは唯一稼働している pilot campaign であり、将来 official を開いても同じ位置で止まる。

**D1114 の判定:**

- (a) 発火条件を満たす既存成果物 path も計測 ID も名指しできない。追跡 repo に該当物は 0 件である。
- (b) 独立した敵対検査 2 本がともに「先行 land すると死んだ gate になる」と判定した。
- D1114 は結論の形まで「設計を凍結して裁定へ返す」と指定しており、本決定はそれに従う。

**D1279 の発火:** D1193 が留保した予算の置き場所は「設計案が出た時点で諮る」と定められている。
本 wave が設計段階であり、設計案が出た結果、独立レビューが
「凍結単位の単一 row 数と chain head を成果物の identity に採ると、台帳と予算が同じ
凍結単位の chain にある設計を暗黙に固定する」と判定した。諮らずに進めれば留保を破る。

**理由:**

- 書き手だけ land すると台帳の欠落を許したまま追跡を謳う状態になる (D1194 が却下済み)。
  検査だけ land すると唯一稼働している campaign が止まる。どちらも成果物の意味を偽る。
- 機構の形 (台帳の名前空間、予算の権限の置き場所、成果物へ pin する identity の形) が
  未裁定の択一に依存する。先に形を決めて land すると裁定の答え次第で作り直しになる。

**却下した選択肢:**

- 検査側だけ land し配線を後続へ送る — D1114 (b) に該当する。唯一稼働している campaign が止まる。
- 配線まで本 wave の scope へ入れる — D1193 が留保し D1279 が「先回りして決めない」と
  確認した予算の置き場所を、諮らずに固定することになる。
- 何も記録せず止める — 設計・実測・所見が失われ、次 wave が同じ調査をやり直す。

## {{D:registry-proof-identity-is-prefix-not-tail}}. 成果物へ pin する台帳 identity は先頭 N 行の証明であって末尾一致ではない

**決定:** 試行台帳を成果物へ束縛するとき、記録する値は「行数 N と、その N 行目までの chain head」
とし、検証は**現在の台帳の先頭 N 行がその head を再現するか**で行う。
現在の末尾との完全一致を要求してはならない。

**理由:**

- 台帳は凍結単位に append される。正当な後続試行が 1 件入るだけで行数も末尾 head も変わる。
  末尾一致を要求すると、**既に certified だった成果物が、正当な次の試行だけで参照不能になる。**
  これは D1194 が守ろうとした「既存 certified の受理面を変えない」を、
  前向きに発行した成果物に対して破ることになる。
- 先頭 N 行の証明なら、束縛の目的 (台帳を削除・不正化した状態で検証が通らないこと) を
  満たしたまま、後続の append に対して安定である。

**却下した選択肢:**

- 現在の末尾との完全一致 — 上記のとおり既発行の成果物を後から壊す。
- 行数だけを pin する — 内容の改竄を検出できない。
- chain head だけを pin する — 台帳の不在と、行が 1 件も無い状態の区別を実装で潰しやすい。
  行数を正の整数として同時に要求することで、その潰れ方を塞ぐ。
