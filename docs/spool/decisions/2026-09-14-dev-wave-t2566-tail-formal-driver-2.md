## {{D:static-tail-cohort-identity-and-refusal-reporting}}. 静的 tail 本走の集団同一性は格子点に依存しない量から作り、拒否は報告として出す

**決定:** 3 走を 1 つの集団として扱うときの同一性は、**追跡された checkout の bytes から作った
digest**で判定する。測定順の先頭の genome から作った値を使わない。また、集団が登録済みの条件に
当たって拒否されたときは、**失敗理由と観測済みの値を伴う記述的な報告を発行する。**
拒否そのものは変えない — 失敗した集団は受理しない。正本は
`docs/b10-backoff-static-tail-preregistration.md` §4.9 と §7。

**理由:**

- 3 走は設計上それぞれ別の workload を測るので、測定順の先頭の格子点が違う
  (物理 2500 / 1250 / 3535)。`BACKOFF_FIXED` は正規化 bytes に効くため、先頭の genome から
  作った source token は 3 走で必ず食い違う。同一性が完全一致を要求する以上、
  **同じ checkout・同じ toolchain で測った正常な 3 走が必ず無効になる。**
  非 `invalid` の結末が到達不能になり、事前登録が主張しようとした命題そのものが測れない。
- 先行 wave が事前登録の本文で同型の欠陥を作り込んでいる (workload 座標を同一性条件へ入れ、
  正常な集団をすべて無効にした)。**構造が同じなら実装側でも再発する**ことが実測された。
- 事前登録 §7 は失敗条件に当たった集団を `invalid` として**報告する**ことを求めている。
  loader が例外で終わると、1 点の欠測・カウンタ欠損・時間切れのいずれでも、残りの正常な観測まで
  報告から消える。観測を捨てるのは規律 3 (正しさシグナルを後付けにしない) の精神にも反する。
- 報告を出すことと受理することは別である。**受理条件は 1 つも緩めていない。**

**却下した選択肢:**

- 同一性の判定から source digest を外す — 3 走が同じ CCBench で測られたことを言えなくなる。
  集団の主張が成り立たない。
- 先頭でなく全格子点の token を集めて比較する — workload ごとに格子点集合が同じでも
  測定順が違うので、順序に依存しない正規化が別途要る。checkout から直接作れば順序の問題自体が
  消えるので、余計な正規化を持ち込まない。
- 拒否時に例外のまま終え、報告は上位の呼び手に任せる — 呼び手が無い経路 (CLI 直叩き) で
  観測が失われる。事前登録が報告を要求している以上、発行主体は driver 側に置く。

## {{D:static-tail-formal-does-not-require-perf-observation}}. 静的 tail 本走は CPU カウンタの観測を受理条件にしない

**決定:** 静的 tail 本走の loader は、CPU カウンタ (perf) の観測が在ることを受理条件にしない。
実際の `use_perf` の値と perf の条件は成果物へ記録する。正しさ記録 5 本・`certified`・
anomaly 0・mode 一致・rep ごとの整数カウンタの要求は 1 つも外さない。

**理由:**

- ユーザーの繰り返しの裁定により、この計算機では**正式系列も perf 不在で進める**。
  「正式系列だけ perf の実在を要求する」は既に却下されている。
- perf は正しさの防壁ではない。事前登録の判定規則は abort 率と throughput だけを使っており、
  CPU カウンタを要求していない。受理条件へ入れると、登録されていない条件で正常な走行を拒否する。
- 初版は loader が観測を無条件に検証しており、実際に 5 件の probe が
  受領証の型不一致で止まった。登録規則に無い要求が、登録された測定を通さなくしていた。

**却下した選択肢:**

- 受領証の検証側を緩めて通す — 検証は既存の共有契約であり、他の利用者の受理集合を動かす。
  弱めるのではなく、要求しないことで解く。
- 試験だけ perf を偽装する — 試験だけ通って実走で止まる。実環境と試験の差を作る方向は採らない。

## {{D:static-tail-rejects-balanced-with-integer-counters}}. 整数カウンタの保存指定と balanced schedule の併用は測定前に拒否する

**決定:** rep ごとの整数カウンタの保存を要求したまま balanced schedule を指定した呼び出しは、
測定に入る前に明示的に拒否する。両立させる配線は足さない。

**理由:**

- 共有 API が指定を受理しながら、balanced の経路では保存が発行されず**黙って消えていた**。
  呼び手は要求が通ったと思い、整数カウンタの無い成果物が成功として残る。
- 本走 driver はこの組合せを使わない。使わない組合せのために新しい測定・保存経路を足すのは、
  発火条件を書けない機能追加に当たる。
- 拒否なら、要求が満たせないことがその場で分かる。既定経路の payload 生成は変えていないので、
  既存 3 系列の受理集合は動かない。

**却下した選択肢:**

- balanced 側へも保存を配線する — 測定順の設計が別で、rep の対応づけと採用 round の意味が違う。
  実際に使う予定のない経路へ、検査されない保存を増やす。
- 黙って無視したままにする — 要求した保存が消えることを呼び手が知れない。
