## {{D:external-signer-parts-without-enforcement}}. 外部署名主体は部品を実装し、必須化は鍵儀式の後へ送る

**決定:** D906 が要求する外部署名主体について、**署名検証 library と repository 内の reference issuer を
実装する**。production の着地関門を署名必須へ切り替える操作は**行わない**。切り替えは、
(1) 人手による鍵と operational issuer の配置、(2) 無署名の現行受領証を正例として固定している
既存テストの所有競合の解消、の 2 つが揃った後続 wave が、待ち手と着地ツールを同時に
新 schema 専用へ変える形で行う。

**この決定が保証する範囲 — 過大に読まないこと。**

- 追加したのは部品であり、**現在の着地関門では効いていない。** 無署名受領証による既存の受理を
  1 件も置換していない。現行の着地ツールは新 schema の受領証を受理しない。
  **D906 の enforcement 完了とは数えない。**
- 着地受領証を根拠にした正しさ主張は、D1197 に従い**未閉鎖**である。

**理由:**

- **鍵を AI が生成すると D906 を満たさない。** D906 は鍵と発行権限を候補および AI が書ける領域の
  **外に置く**ことを求めており、却下選択肢に「署名だけを足し鍵の置き場を決めない = 恒真になる」を
  挙げている。生成時点で AI が秘密を支配した事実は、後から書込みを拒否しても消えない。
  したがって鍵の生成と配置は人の手番である。
- **書込み防護そのものも AI には足せない。** 書込みを止める機構は、自分の subtree への書き込みを
  自ら拒否する (同 subtree の説明文書だけが例外)。この拒否は Claude と Codex の双方へ配線済みで、
  **どの AI 作業者も防護対象を追加できない。** 外部領域を防護対象へ足す操作も人の手番である。
- **必須化は、鍵が配置されるまで着地を全面的に止める。** 影響は過去の受領証の拒否に留まらず、
  世代を持たない既存の排他権、排他権を保持しない走行、旧い待ち手で稼働中の wave、
  鍵未配置期間のすべてに及ぶ。従来の受領証 schema 版上げと同じ範囲とはみなせない。
- **必須化しても関門は不可避にならない。** 着地ツールは自身の実行 copy を `__file__` から解決し、
  cwd が wave の作業木であることだけを検査する。署名検証を含まない旧い着地ツールを wave 側から
  起動すれば、新しい検証を通らずに main を進められる。この consumer 迂回は署名の設計だけでは閉じない。
- **緩める形の回避を採らない。** 署名を任意にする、旧 schema の fallback を残す、
  設定鍵が無いときは通す、test module 名で迂回する — いずれも発行権限の迂回路であり、
  絶対規律 2 に抵触する。実装量を減らす代わりに関門を恒真にする取引はしない。

**却下した選択肢:**

- **本 wave で必須化まで行う** — 上記により、鍵が無いまま着地を止め、かつ「閉じた」とも書けない。
- **本 wave では何も実装しない** — D1197 の実装命令に反する。鍵儀式と無関係に実装できる部品がある。
- **設定鍵が無いときは無署名を通す条件付き関門にする** — 発火条件を満たす実在成果物が無く、
  かつ設定鍵を外すだけで無効化できる。恒真な関門になる。

## {{D:external-signer-unclosed-scope}}. 外部署名主体で閉じない範囲を、機序付きで確定する

**決定:** 外部署名主体について、次を**未閉鎖として記録する**。理由を伴わない列挙にしない —
機序が無いと、次に読む作業者が「やれば閉じる」と誤読する。

1. **署名が証明する範囲。** 署名検証が証明するのは、**固定された設定済み公開鍵**に対応する
   秘密鍵による payload の承認と、署名後の非改変までである。
   **特定の issuer 実装が実行されたこと、再導出手順が実施されたこと、payload の意味的正しさは
   証明しない。** 機序: 署名は鍵の保持を示すのであって、署名者が誰でどう振る舞ったかを示さない。
2. **主体の分離が無い。** 鍵と issuer を repository の外へ置くことは OS 上の主体分離ではない。
   同一 uid の process は鍵を読み、issuer を観測・変更しうる。書込みを止める機構が抑止するのは
   信頼済みの事前検査が観測した一部の直接書込み面だけであり、**認証防壁ではない**。
   機序: 同機構は自分の拒否文で「認証防壁ではなく誤操作抑止」と自己申告している。
   加えて防護判定はすべて repository root 起点の包含判定であり、**repository 外の絶対 path は
   現在 1 つも防護対象になっていない。**
3. **親の起動点。** 親は引き続き wave 側の待ち手を直接起動する。改変された起動側が issuer 呼出しを
   省略する経路は、issuer 単体の設計では閉じない。機序: 起動権の所在は issuer の内部設計の外にある。
4. **issuer の trust root。** issuer の code・鍵・toolchain を真正とみなす別の trust root が無い。
   PATH、symlink、interpreter、git、cwd、repository 内 reference と repository 外 operational copy の
   bytes 同一性および実行実在は、受領証から独立に検証されない。
   機序: issuer が自身の revision や hash を署名しても、それは自己証明であって独立の証言ではない。
5. **導入と更新の例外。** issuer の初回配置と更新は、新機構自身ではその配置を承認できない。
   機序: 承認に使う機構がまだ配置されていない期間が必ず存在する。
   定常時の署名検証を、導入・更新期間にも無条件で成立する保証として扱わない。
6. **完了通知の自己申告面。** 走行前後の指紋、環境射影、実効 scheduler、検査器の結果、
   赤および揺らぎの nodeid は、内容と供給元の実行実在について待ち手の自己申告性を残す。
   機序: issuer はこれらを独立に再現できない。構造的な整形式性と署名は意味的真正性を閉じない。
7. **署名対象と実行実在の区別。** D906 の「検査器」は赤の検査器と解釈する
   (受領証の語彙で検査器系 field が指すのは赤の検査器であり、着地ツールは受領証の consumer である)。
   署名へ入れる検査器の hash は tested main 上の**期待 content hash** であって、
   その bytes で実行されたことの独立証明ではない。**判定が緑の経路では検査器自体が実行されない。**
   **着地ツール自身および operational issuer 自身の bytes は署名対象に含まれない。**
8. **判定の意味。** 判定が緑である経路は、issuer が起動した実行器の終了コード観測と構造的に結合するが、
   実行された test の選択・import 閉包・環境全体の意味的正しさまでは証明しない。
   非帰属のみの判定の意味的正しさは、検査器の完了通知の自己申告に依存する。
9. **再送防止の射程。** 署名済み context の束縛は、別 wave・別 main・別 tip・別の排他権取得への
   再利用を拒否する。**同一 context 内での 1 回限りの使用は保証しない。**
   機序: 束縛は context の同一性を見るだけで、使用回数を数える状態を持たない。
   1 回限りにするには外部の消費台帳が要る。本 wave では実装しない。
10. **旧い着地ツールによる迂回。** 署名検証を含まない着地ツールを wave 側から起動する経路が残る。
    機序: 着地ツールは自身の実行 copy を `__file__` から解決し、cwd が wave の作業木であることしか
    検査しない。**検証器の版を束縛する関門が無い。**
11. **排他権の世代。** 排他権の payload は field 集合を厳密一致で検査し、解釈できない payload を
    **「誰も保持していない」へ縮退させる**。したがって世代を payload へ足すと、旧い実装で稼働中の
    wave が保持中の排他権を空きと読み、受入の排他が壊れる。**世代は schema の slot として
    定義するに留め、production の値の生成源は決めていない。** 実環境で取りうる値を実測していないため、
    述語として採用していない。
12. **着地の検証器自身が候補コードであること。** 機序: 検証器は候補と同じ repository にあり、
    同じ主体が変更できる。署名は検証器の外側に鍵を置くが、**検証器を呼ぶかどうかを決める層は
    依然として候補側にある** (項目 10 と同じ機序)。協調境界として残す。

**理由:**

- D1197 は「着手できない間は未閉鎖と明記し、閉じたと書かない」を逐語で命じている。
  **どこまで閉じたかの記述精度そのものが本 wave の成果物である。**
- 過去に同種の設計を記録したとき、閉じない範囲を無条件に省くと、次に読む作業者が過大な保証を
  前提に実装へ進みかねないことが指摘されている。本記録はその指摘に従う。
- 理由の無い列挙は「やれば閉じる」と誤読される。各項目に閉じない機序を添える。

**却下した選択肢:**

- **「限界がある」と 1 行だけ書く** — どの主張がどこまで成立するかが復元できず、
  次の作業者が署名済みという事実だけを根拠に使う。
- **閉じた項目だけを書く** — D1197 が禁じた「閉じたと書く」に落ちる。

## {{D:external-signer-d431-partial}}. 本 wave の positive control は部分充足であり、その境界を記録する

**決定:** D431 が義務づける positive control について、本 wave の充足状態を次のとおり**分けて**記録する。

- **充足:** 実在の production 受領証を tracked fixture として取り込み、
  canonical projection の述語へ通した。期待値は test source 内の独立 literal であり、
  実行時の環境変数・production 定数・戻り値自身・loader から作っていない。
  反対クラス (root field 欠落) を拒否する負例と対にしてある。
- **test key による control (production control ではない):** 固定された設定済み公開鍵の loader と
  高水準検証 API を実際に通る正例と、鍵違い・環境変数による差し替え・設定鍵の欠落・
  不正な鍵形式の 4 負例。**test 鍵で署名したものを production の positive control と呼ばない。**
- **unmet:** production で発行された署名付き受領証を、固定設定鍵の検証器へ通す positive control。
  operational issuer と鍵が人手で配置されるまで発行できない。
  **skip・xfail・期待反転で緑に見せてはならない。真正面に書けば現在は未取得である。**

**理由:**

- D431 は control の期待値を実行時環境・production 定数・戻り値自身・loader から作ることを
  明示的に禁じている。実在値を通すだけの control は、分類器が壊れていても緑になりうるためである。
- 段 6 の敵対レビューが、**固定鍵の loader と高水準 API を一度も通らない control** を検出した。
  低水準 API へ呼び手が作った鍵を直接渡す形では、loader が環境由来の鍵を採用しても、
  高水準 API が署名検証を迂回しても緑のままだった。これは恒真化そのものであり、fix で閉じた。
  **この初回結果は消さず記録する。**
- unmet を充足と書けば恒真化になり、実際に通した production 値まで unmet と書けば過小記載になる。
  **両方向とも誤りなので、境界を明示して分ける。**

**却下した選択肢:**

- **test 鍵の正例を production control として数える** — 鍵の出所が違うため、
  production の設定鍵が壊れていても緑になる。
- **production control が取れないことを理由に control を置かない** — 実在値を通せる述語が
  現に存在するため、部分充足を放棄する理由にならない。
