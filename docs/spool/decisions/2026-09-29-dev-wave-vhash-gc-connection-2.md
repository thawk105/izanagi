## {{D:vhash-gc-connection-sp}}. VHash の前進を GC の回収境界へつなぐ手順は、tx 自身が待機の安全点で確かめる形 (SP) にし、確定 → 公開の順と「公開した floor より古い時刻へ戻らない」を規則にする

**決定:**

1. 読み取りの後に待つ tx (出典メモ §16.1) への前進は、GC が待機中の tx に要求の印を立て、**tx 自身が待機の安全点で**前進する形 (SP) にする。手順は md_4 の forwarding と同じ「既読版の rts を t′ へ上げる → 版列を観測し直して可視を確かめる → 確定 (cand_ts := t′) → 別 step で公開 (gc_floor := cand_ts)」とする (規則 G2〜G4)。他 thread が代わりに確かめる形 (HP) は採らない。
2. **公開した floor は gc_floor そのもの**とし、gc_floor を下げる遷移を作らない。fallback の戻り先は gc_floor を下回らない。公開の後に開始時刻へ戻る fallback は GC 違反になる (危ない版 UF1)。確定の後・公開の前の取り消し (試行前の時刻へ戻る) は小モデルの範囲で反例が出なかったので禁じない。D2282 が置いた「確定の後は戻らない」(md_4 の R8) は検査のない設計選択であり、戻れない境界は公開にある。
3. 回収は md_4 の R10 (境界以下の確定した後続版があり、どの物理参照にも無い版だけ) のままとし、前進後もまだ見える古い版は回収しない。
4. 前進の効果は、forwarding の成功回数ではなく、公開直後の状態と「その tx の floor だけを戻した対照状態」の回収境界と回収できる版数の差で数える (メモ §15.4)。値はモデル内の数であって性能値ではない。
5. 検査は md_4 の小モデル (`tools/vhash_forwarding_model/`) を既定 off の option で拡張し、md_4 の 63 構成の結果を 1 行も変えない。一次資料は `output/insights/2026-09-29/vhash-gc-connection-model/README.md`。

**理由:**
- 対象の長い tx は実行中の thread が待っているので、待機の安全点で要求を確かめられる。HP は既読集合の共有と descriptor の世代つき CAS を要し、通常の読み取りのたびに共有書き込みを増やす (メモ §16.2 の「通常アクセスに余計な仕事を載せない」と逆向き)。HP が勝るのは完全に止まった thread だけで、そのときも物理参照の解除は別の仕組みが要る。
- 6 場面の全探索で、確認の前の公開 (UG1)、確定時に floor を外す (UG2)、公開の後の開始時刻への fallback (UF1) はいずれも GC 違反、確認を省く前進は O1 と組むと閉路 (UG3+O1) になり、健全版 24 構成は反例なしだった。
- 同じ trace 上の前後差は他 tx の commit や GC の回収を含み、前進に帰属できない (段 6 レビューの指摘)。

**却下した選択肢:**
- HP (代行による前進) — 通常経路の費用が増え、止まった thread でも段階 C は解けない。採るなら descriptor の世代つき CAS が確定だけでなく公開までを覆い、snapshot の後に tx が読み取りを足せないことが必要 (段 3 の相談で判明、未検査)。
- 「公開した floor の最大値」を gc_floor と別の量として持つ — アクセス駆動の公開を記録し損ね、意味が二重になる。
- 効果を同じ trace 上の「要求直前 → 公開直後」の差で数える — 他 tx の進行が混ざる。
