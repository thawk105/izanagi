## {{D:nonattributable-red-does-not-stop-the-wave}}. 非帰属の受入赤で wave を止めず、tip が変わった後だけ投げ直す

**決定:** `DW-O18` に次の 2 点を足す。D873 が書いた 4 分岐と受理条件は 1 bit も変えない。

1. **N 走で完全一致する赤は flake ではなく、非帰属の証拠にもならない。**
   走行ごとに揺れないことは環境要因仮説の反証であって、非帰属の立証ではない。
2. **停止条件の外では wave を止めない。**治すか hold 登録した後だけ受入を投げ直す。

再投入の資格は **tip が変わったこと**に置く。同一 tip の単独再走・受入再走はそれぞれ 1 回だけで、
これは D873 のままである。治すか hold 登録すれば tip は変わるので、この 2 つは衝突しない。

**理由:**
- D873 は正式手順を書いたが、「停止」を 2 度書いて「投げ直す」を一度も書いていなかった。
  そのため各 wave が非帰属の赤を wave の終端と読み、場当たりの回避をやり直していた。
- 「N 走完全一致は flake でない」は 2026-08-23 の worklog に実測として残っていたが、
  手順書へ届いていなかった。届いていないものは次の wave が使えない。
- **上限のない再投入は受理集合を実質的に広げる。** D873 が同じ理由で再走を 1 回に有界化して
  いる。「投げ直す」を無条件に書くと、失敗確率を持つ実体の受理確率が反復回数とともに 1 へ
  近づく。tip の変化を資格にすると、この経路を開かずに前進だけを許せる。
- 「治すか known violation にして投げ直す」の known violation は `flaky_test_holds.py` への
  hold 登録と同じものである。手順書では緩い別名を使わず registry へ束縛した語を使う。
  緩い別名は「完全一致 → 決定的 → known violation」の短絡を招く。

**却下した選択肢:**
- 「投げ直す」を回数の条件なしで書く — 上記のとおり受理集合を広げる。
- 待ち手側の受領証発行を機械化する — 受入の受理条件を緩める方向であり、
  2026-08-24 のユーザー裁定で不採用が確定している (択 (a))。
- 停止条件を 1 文へ統合する — D873 は分岐ごとに別の述語を与えている。統合すると
  判定不能・原因未理解へ「裁定へ送り」が付き、D961 / D1046 が減らそうとしている
  ユーザー裁定送りを増やす向きになる。分岐は分けたまま停止だけを共有述語にした。

**予算 (D782 / D730 の手順):** 手順 (a) 既存記述の削減だけで閉じた。節は 998 → 997 bytes で、
L2 単節上限 1000 は据え置く。(b) の例外収容にも (c) の上限引き上げにも進んでいない。
削ったのは重複表現だけで、安全義務は 1 件も落としていない。

**この保証が届く範囲 (実測):** `DW-O18` の節は `tools/check_docs.py` の
`DEV_WAVE_EXACT_VISIBLE_SECTIONS` が全文 exact で pin し、`orchestrator/tests/test_check_docs.py`
が同文の複製と byte 数を断定する。変異実測では、pin 登録を外すと 10 node、
L2 単節予算の上限を上げると 2 node で必ず落ちる。
**ただし守れるのは bytes だけである。**本文・checker literal・合成 literal・byte 断定を
同じ変更単位で揃えて書き換えれば、機械は通る。意味の防壁は敵対レビューと本決定が担う
({{F:doc-obligation-guard-is-bytes-only}})。
