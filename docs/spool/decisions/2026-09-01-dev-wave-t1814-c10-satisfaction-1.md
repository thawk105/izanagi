## {{D:c10-static-readiness-precedent}}. 完了証明層の先例は C10 とし、静的 readiness の限界を条件本文へ明記する

**決定:** D1026 が求める「判定が repo 内 artifact だけで閉じる条件 1 件」に C10
(cross-binding verifier の readiness) を充てる。充足証明は**commit 内 source に対する静的
readiness に限る**。確立しない事項 — 実行時の再束縛 (`globals()` 代入・module 属性代入・
置換デコレータ)、定数でない述語による意味的に常に偽の guard、呼び出し結果の実効寄与、
`getattr` や高階関数を経由する dispatch、宣言された必須 field 名の reader 引数への実束縛、
reader が実際に bytes を読み digest を照合すること — を条件本文へ列挙する。
`SATISFIABLE_CONDITION_IDS` へ入れるのは C10 だけとし、他 11 条件の fail-closed 終端と、
許可外 id が充足を返したら評価エラーへ倒す関門は変更しない。

**理由:**

- D1026 が定めた水準は「条件を意図的に破った入力で必ず不充足を返す負例」であり、
  あらゆる動的偽装を塞ぐことではない。静的判定器に実行時の再束縛は原理的に見えないため、
  後者を要求すると本裁定は充足不能になる。
- 条件 12 の証拠契約が、同一束縛のデータフロー・例外の非握り潰し・process 専有を証明しないと
  自ら明記したうえで機械検査対象になっている。限界を宣言した機械条件は既存の様式である。
- D438 が却下したのは「評価器の終端を一律に充足へ倒す」ことである。本件は 1 件だけを、
  登録した 8 種の負例と実 repository の正例を伴って開く。着手前の実測では、検証呼び出しを
  到達しない枝へ入れた実装・例外を握り潰す実装・受入側の呼び出しを殺した実装が、いずれも
  正直な実装と同じ終端へ到達していた。強化後はこの 3 形に加え、別名すり替え・本体の空化・
  `contextlib.suppress` による握り潰しも非充足を返す。
- 発効は 12 条件すべての充足を要求するため、本決定の後も事前登録は未発効である。
  測定認可・certified 選択・proof chain・campaign 起動可否は 1 件も変わらない。

**却下した選択肢:**

- **reader の内部データフロー (読取 → digest 照合 → 不一致で raise) まで静的に追跡する** —
  本番の受入経路にある verifier 呼び出しは既存の到達可能使用判定が偽を返すため、追跡を課すと
  正しい実装を偽赤にする。実測で確認した。
- **`getattr` 経由の dispatch を負例として拒否する** — 正しい refactor も同じ判定になる。
  限界の記述へ移した。
- **実装せず設計メモで止める** — D959 が最上流と定めた層が閉じず、下流のすべてが止まったままになる。
  D1326 も本層の実装後に着手すると定めている。

## {{D:satisfiable-condition-admission-procedure}}. 条件 id を充足可能集合へ足す手続きを 4 点で固定する

**決定:** `SATISFIABLE_CONDITION_IDS` へ条件 id を足せるのは、次の 4 点がすべて揃ったときに限る。
事前登録正本の改訂手続きへ規範として書く。

1. **充足証明**: 当該条件の規範本文と証拠契約の必須証拠・consumer 要求を評価器が対象 commit の
   blob 上で検査し、**実 repository と、実体を持つ正例 fixture の双方で充足を返す**こと。
   併せて、その証明が確立しない事項を条件本文へ列挙すること。
2. **負例**: 登録済みの負の対照を含む負例が、**同じ test の中で**正例の充足と対になり、
   変異後に条件別の理由で非充足になること。
3. **世代更新記録**: 判定器の版の bump と次世代の条件凍結 record を**同じ commit**に入れること。
4. **裁定の先行着地**: record が引く決定が、その commit より前に台帳へ着地していること (D439)。
   着地していなければ、決定だけを先に land する wave と、記録・契約改訂・境界テストを同じ
   commit で land する wave に分ける。

**理由:**

- D1026 が「10 件それぞれで違う開け方が生まれる」ことを禁じており、1 件目で手続きを確立する
  ことが裁定の内容である。
- 「実 repository と正例 fixture の双方」を要求するのは、検査が正しい実装を偽赤にしていないことと、
  負例が恒真でないことを 1 つの関門で同時に塞ぐためである。実 repository だけでは負例の非恒真性を、
  fixture だけでは偽赤の不在を示せない。
- 4 を明記しないと先例にならない。世代 record の検証は導入 commit 時点の台帳 blob に決定見出しを
  探すだけで、親 commit に存在したかを検査しない。

**却下した選択肢:**

- **充足証明の合格条件を「実体ある production consumer の証明」とだけ書く** —
  2 件目の担当者が何を満たせばよいか判定できない。
- **新しい機械 gate で 4 点の充足を強制する** — 本裁定の射程外であり、要求されていない
  仮想リスク向けの機構になる。手続きは規範として書き、実施は各 wave の裁定に委ねる。
