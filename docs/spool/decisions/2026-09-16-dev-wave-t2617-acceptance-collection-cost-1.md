## {{D:acceptance-pre-collection-is-parallel-collection}}. 受入の「テスト開始まで」は 48 重の全 collection が主因で、安全に削れる量は 1 秒級である

**決定:** 受入 shard の `session 開始 → collection 終了` (以下 `pre`) と
`collection 終了 → 最初のテスト開始` (以下 `disp`) について、次を確定する。
数値は 2026-09-16 の 28 走 (shard-0) と、同日の login node 対照実験。
生データと再現手順は `output/insights/2026-09-16_t2617-acceptance-collection-cost/`。

1. **`pre` は 55.4〜59.1 秒で、走を跨いでほぼ動かない。** 28 走は 33 台の別ノードに散り、
   同じ走の wall は 296.2〜604.5 秒に散るが、`pre` の幅は 3.7 秒である。
   同一 session の 3 shard でも 56.2 / 56.3 / 56.5 だった。
2. **`pre` の主因は、48 worker が同じ全 collection を並列に払うことである。**
   計算ノードは 48 physical core・HyperThreading 無効で、worker 1 本に core 1 本が当たる。
   温い単独 process の全 collection は 13.62〜18.23 秒 (user CPU 15.82〜16.54 秒) であり、
   48 重にすると約 56 秒になる。
3. **分割 plugin (`-p tools.acceptance_shards`) の per-item 費用は主因ではない。**
   同じ負荷で連続 2 走した対照実験で、plugin の有無の差は **user CPU +1.74 秒 /
   collection 報告 +1.12 秒**だった。この中に `_canonical_item` の 2 回呼び出し
   (23,970 item × 2)、その各回の `Path.resolve()`、`allocate`、2 つの digest がすべて入る。
4. **`disp` は shard-0 だけに出る (他 2 shard は 0.1 秒)。barrier の中では
   `_prewarm_receipt_memo` が `_prewarm_oracle_environment_memo` の 238 倍である**
   (31.320317 秒 対 0.131276 秒)。
5. **ただし barrier と `disp` は同じ量ではない。** 同一 session で barrier 31.32 秒に対し
   `disp` 28.44 秒で、差は 2.88 秒である。barrier は worker ごとの collection 完了通知から
   起動し、報告される collection 終端は全 worker の最大値なので、両者は重なる。
   **「`disp` の 99.995% が receipt prewarm」とは言えない。**
6. **`pre` の残り約 38 秒 (56 − 18) の成分配分は決まっていない。**
   memory 帯域、lustre の metadata 応答、controller 側の nodeid 照合の 3 者に分かれるが、
   配分は測っていない。この引き算は同条件の差分ではない — 対照は login node の単独 process、
   観測は計算ノードの 48 worker で、commit も違う (`observed_universe` 24,020 対 対照 23,970)。
   **成分へ配分してはならない。**

**上の確定の下で、短縮について次を決める。**

- **`pre` は短縮しない。** 自 shard 絞り込み (D711 gate 2 / D1728)、`Path.resolve()` の
  字句処理への置換 (repo 外拒否・symlink alias の重複検出・閉包入力の意味が変わる)、
  worker 間の digest 共有 (自己証明)、worker 数・配布順の変更 (D532 が「提案しない」と明記)、
  collection 集合の縮小 (D2003) は、いずれも採らない。
  **残るのは `_canonical_item` の 2 回目の呼び出しを 1 回目の結果で置き換える案だけだが、
  得られるのは 1 worker あたり 0.9 秒未満、48 worker でも wall 1 秒級である。**
  正規化・重複拒否・marker 検査の等価性証明を要する変更を、この量のために入れない。
- **`disp` の短縮策は本決定では起票しない。** prewarm を collection と重ねる案は
  既に別タスクが所有しており、先行 wave が 279.8 秒を実測したうえで赤 4 件のため撤去している。
- **bytecode cache の事前用意は、冷が実測されたときだけの条件つき候補として残す。**
  冷条件では 1 process あたり user CPU 約 40 秒を払う (56.37 対 16.54) ことは実測したが、
  2026-09-16 の 28 走で冷は観測していない。

**理由:**

- D1728 は自 shard 絞り込みを禁じ、その再訪条件を「独立な全体集合から導いた期待割付を
  供給する設計が具体的に示されたとき。費用の増加だけでは再訪しない」と定めた。
  **本決定はその設計を示していないので、絞り込みは採らない。**
- 分割 plugin の per-item 費用が 1.74 秒だと実測で分かったことにより、
  「per-item の正規化を減らせば大きく効く」という見込みが**否定された**。
  効果が 1 秒級である以上、正しさ防壁に触れる変更を入れる理由が無い (絶対規律 2)。
- 5 分の上限に対する寄与も小さい。同一 session で両区間を全部ゼロにする反実仮想を置くと
  最遅 shard は 307.1 秒から 222.5 秒になるが、同じ日の最遅 wall は 604.5 秒まであり、
  そこから 84.7 秒を引いても 519.8 秒である。**5 分超えの主因は実行窓と混雑であって
  この 2 区間ではない。**
- 段 3 の 2 レンズ (費用と実効性 / 正しさ境界と既裁定の射程) が独立に、
  「集合不変は等価性の証明ではない」「barrier と `disp` を同一視できない」
  「38 秒を成分へ配分できない」を指摘し、親の provisional 裁定 3 件を覆した。棄却した所見は無い。

**却下した選択肢:**

- **`_canonical_item` の重複を今回直す** — 実在の重複だが wall 1 秒級で、
  等価性証明の費用に見合わない。事実は記録し、変更は入れない。
- **計算ノードへ診断 probe を載せて 38 秒を分解する** — 依頼が内訳確定までを範囲とし、
  追加実装を scope 外としている。必要になった時点で別タスクとして起こす。
- **受入 report へ観測 field を足す** — D1729 が見送っている。本決定はその見送りを支持する
  (下記)。
- **`pre` を「物理的に短縮不能」と書く** — 言えるのは「安全に削れる量が 1 秒級である」までである。

**限界:** 標本は 2026-09-16 の 1 日ぶんで、同日の checkout 群は cache と共有資源の状態を
共有している。28 個の独立した環境条件ではない。bytecode cache の有効性は entry 数でしか
確認しておらず、計算ノードの dispatch は `PYTHONDONTWRITEBYTECODE` を既定で立てるため、
欠落・陳腐化した cache は受入走行では更新されない。冷が実測された時点で本決定の
「冷は観測していない」は見直す。

## {{D:d1729-observation-field-deferral-confirmed}}. 受入 report の観測 field を足さない見送りは、内訳を確定した結果として支持される

**決定:** D1729 が定めた「受入 report の観測 field 拡張を行わない。closed schema は v1 のまま」を
**維持する。** D1729 が置いた再訪条件「受入 wall が再び実害として観測され、かつ内訳の確定なしには
次の一手が決まらないことを示せたとき」は、**満たされていない。**

**理由:**

- D1729 の見送りの理由は「内訳を確定しても次の一手は変わらない」だった。
  2026-09-16 に実際に内訳を確定してみた結果、**次の一手は変わらなかった** —
  `disp` の打ち手は既に別タスクが所有しており、`pre` には安全な打ち手が無いという結論である。
  **したがって D1729 の判断は事後的に正しかったことが確認された。**
- 本 wave の内訳確定は、schema の外にある既存の計測行 (`IZANAGI_MEMO_PREWARM_V1`)、
  既存の `session_timeline`、`junit.xml` の属性、および repo 外の login 対照実験だけで行った。
  **field を足さずに必要な粒度まで到達できることが実測で示された。**

**却下した選択肢:**

- **両端の時刻を足す** — 本 wave が field 無しで `pre` / `disp` の境界を取れたので、
  追加の理由が無い。
- **D1729 を「再訪条件が発火した」として改める** — 内訳は確定したが、それによって
  選ぶ手が変わっていない。再訪条件の文言は「内訳の確定なしには次の一手が決まらない」であり、
  これは満たされていない。

**限界:** `pre` の残り約 38 秒の成分配分は、既存 field だけでは決まらなかった。
将来その配分が次の一手を決める段になったときは、本決定ではなく D1729 の再訪条件を
改めて評価する。そのときも受入 report の schema ではなく、schema の外の診断走を先に検討する。
