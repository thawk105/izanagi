## {{D:t316-inert-unreachable-on-stock-tree}}. t316 実経路の inert 要求は素の木では inert 比較へ到達せず、直し方は別の起票へ送る

**決定:** t316 driver の条件関門が `BACKOFF_FIXED=-1` の inert 要求について
`stock-inert-*` の比較へ到達しないことを、計算ノードの 2 走で実測した事実として記録する。
到達しない原因は次の 2 つであり、どちらも単独で赤にする。

1. 素の CCBench 木に `CCBENCH_BACKOFF_FIXED` の CMake option が無い。関門は requested 側で
   必ずこの変数を足すので、patch 未適用の木では CMake が未使用変数警告を stderr へ出す。
2. t316 が CCBench の参照しない変数 3 件 (`IZANAGI_GFLAGS_SRC_HEAD`、`IZANAGI_GLOG_SRC_HEAD`、
   `RULE_LAUNCH_COMPILE`) を関門へ渡している。

CMake configure 自体は rc=0 で成功しており、`condition_meaning_gate` が rc=0 でも stderr 非空を
`configure-failed` にする規則によって赤になる。落ちたのは requested 側で、stock 側は未実行である。

**これは新しい失敗型ではない。** F934 が「patch 由来 define の条件関門が、patch を materialize
しない driver では構造的に通らない」を既に独立 2 例で記録しており、**t316 は 3 例目である**。
未使用変数の流用という側面は F855 が既に記録している。関門は fail-closed で正しく拒否している。

**この不整合の直し方は本決定で定めない。** 未使用変数の削除、関門へ patch 木を渡すこと、
警告の抑制はいずれも採らず、設計択一として別に起票する。D1856 の繰延べは解除しない。

**理由:**
- 「関門だけを通す」修正は偽の緑を作りうる。patch 由来の cache 変数を定義しない木へ渡さない形に
  すると requested と control の configure が構成上同一になり、inert 比較が自明に緑になる。
  関門だけを patch 文脈へ入れると、関門は patch 済みの木を検査し probe は素の木を build する
  という乖離が生まれる。**検査した木と build する木を一致させる**ことがこの族の不変条件である
  (2026-09-02 の A-2 実測が同型の層 1 として記録している)。
- 族一般化の条件 (独立 2 例) は F934 で既に満たされており、本件は 3 例目である。しかし一般化の
  中身は D1864 が「silo の現行挙動は据え置き、扱いはユーザー裁定へ返す」と定めた論点そのもので、
  親が実装で先回りしてよい領域ではない。3 例目を台帳へ残すのが本 wave の正しい終端である。
- t316 は素の木を build する probe である。したがって上の 2 つの修正案はどちらも、この不変条件と
  正面から衝突する。実測を済ませた本 wave で設計を決め切るより、択一として残すほうが安全である。
- 絶対規律 2 により、関門を通すためだけの修正で受理集合を広げることは認められない。

**却下した選択肢:**
- 未使用変数 3 件だけを関門へ渡さない — `CCBENCH_BACKOFF_FIXED` が残るので赤は解けない。
  仮に解けても、検査する configure と build する configure が食い違う。
- 関門へ patch 適用木を渡す — 関門が検査する木と probe が build する木が別物になる。
- gate 側の stderr 非空判定を緩める — 共有の正しさ防壁の受理集合を広げる。規律 2 に反する。

## {{D:condition-gate-rejection-detail-to-job-stderr}}. 条件関門の拒否理由は受領証でなく job stderr へ出す

**決定:** t316 probe の条件関門が admission を拒否したとき、supply と meaning の各 record が持つ
`evidence` の `detail` を job の stderr へ出す。受領証の schema・field・文面は変えない。
`evidence` mapping を受領証へ載せる経路は作らない。`detail` は添字でなく `.get` で取り、
持たない record では出力上そう分かる形にする。診断の出力が失敗しても従来の拒否例外を
そのまま送出し、出力側の障害は例外連鎖に残す。

**理由:**
- 拒否の理由コードだけでは、計算ノードで実際に何が起きたか (CMake の rc・stderr・argv) が失われ、
  原因の切り分けが login node での再現に依存する。これは絶対規律 3 (正しさシグナルを後付けに
  しない。なぜ壊れたかを構造化して返す) の趣旨に反する。
- 受領証へ evidence mapping を出さないという既存の決定 (D1849) は、診断情報全般の保存を
  禁じてはいない。出力先を受領証の外に置けば、schema も受理集合も動かさずに要求を満たせる。
- 拒否そのものは維持する。診断の追加は受理集合を 1 mm も変えない。
- 診断出力が失敗したとき従来の拒否例外が置換されると、受領証の error が条件関門の拒否情報から
  出力障害の型・文面へ変わり、拒否理由が失われる。これは変更の目的と正反対なので、
  出力を例外から隔離する。

**却下した選択肢:**
- `RuntimeError` のメッセージへ detail を連結する — 受領証の `error.message` へ回り込み、
  D1849 が避けた経路に近づく。
- 受領証の supply entry へ detail field を足す — schema を変え、D1849 の逐語と衝突する。
- 診断専用の新しい CLI 経路や harness を計算ノードで走らせる — 新しい実行可能物が要るうえ、
  得られるのは再現走の証拠であって当該 driver 実経路の証拠ではない。同等性の証明も別途要る。
- 出力失敗を握り潰す — 障害の痕跡が消える。例外連鎖に残せば拒否を守りつつ痕跡も残る。
