## {{D:land-lock-cumulative-wait-budget}}. land の lock 待ちは累積競合待機予算とし、lock 外の作業時間を差し引かない

**決定:** `tools/dev_wave_land.py` の lock 待ち予算 `_LAND_LOCK_WAIT_SECONDS` の意味を、
「窓開始からの絶対期限」から「**累積の競合待機予算**」へ変える。`_run_outside_land_lock` は
guard (全史 provenance 監査 / fold gate) の完了後に、残予算から自前の deadline を作って再取得する。
監査後と fold gate 後の両方の再取得に適用する。**値 180 秒は据え置き、増やさない。**

D432 の「取得点ごとに同じ絶対 deadline を渡す」条項を本決定が supersede する。
**取得ごとに 180 秒を補充する禁止は維持する** — 変わるのは「lock 外の作業時間を予算から
差し引かない」ことだけである。監査の範囲・内容・`--range`・`authoritative` 述語は変えない。

あわせて 2 点を同じ変更単位で直す。

1. reason 文で「予算を使い切るまで待った末に取れなかった」と「予算が尽きていたので 1 回だけ
   試して降りた」を別の文面にする。どちらも lock は実際に保持されているが、待ったかどうかが
   違う。同じ文面だと lock 競合の激しさを誤診する。
2. 結果 JSON に窓の内訳を出す。従来は `lock-busy` の拒否 JSON にしか出ず、成功した land の
   所要を外側 wall-clock でしか測れなかった。窓に入る前に終わった経路では key を省く。

**理由:**

- **失敗条件を取り違えていた。** `_acquire_land_lock` の deadline 検査は `except BlockingIOError`
  の内側にしかなく、非 blocking `flock` が成功すれば deadline 超過でも取得できる。期限は
  「lock が埋まっていたときにあと何秒待つか」を決めるだけである。したがって真の失敗条件は
  **「lock 外の作業中に他の land が lock を取り、かつ自分の予算が尽きていること」**であり、
  「監査が窓を食うこと」自体ではない。予算を食った結果、待つ権利を失った状態で鉢合わせると落ちる。
- **実測。** 本 wave の land 42 回のうち 41 回に status が記録され、lock-busy 30 / rc=29 が 8 /
  stale-main 3、成功 0 だった。lock-busy 30 のうち 22 回が `post-provenance` または
  `post-fold-gate`、8 回が `initial` である。**監査が窓に収まっていた回でも落ちている** —
  別 wave の実測に `waited_s=150.481 / window_elapsed_s=272.504` (監査推定 122.0 秒) と
  `141.590 / 305.791` (164.2 秒) がある。これは本決定が直す混同の直接の実例である。
- **射程は限定的だが、他の手と重ならない。** 別 wave の 31 件の phase 別分解では、本決定で救えるのが
  19 件 (61%)、`initial` の 8 件は救えない (初回取得は元から満額の予算を持つため)、監査が上限を
  超える 4 件も救えない。**順番に 1 本ずつ投げる運用が `initial` を消し、本決定が残りを救う。**
- **変異で検査されている。** 「取得ごとに満額補充する」変異と「lock 外の作業時間を予算に食わせる
  (是正前の挙動)」変異を実装前に登録し、本走で 2/2 KILLED・期待 node 完全一致・置換対象一箇所を
  確認した。後者は既存 2 テストも反応するが、既存テストだけでは初回待機ゼロの fixture のため
  正実装と補充変異を区別できない。新設の境界 fixture がその穴を埋めている。

**却下した選択肢:**

- **予算を増やす (累積 370 秒、または取得ごとに満額)** — 待機を増やすと全史監査の同時流入を
  増幅する。保持者が監査のため lock を解放している間に待ち手が順に取得し、main 不変なので全員が
  preflight を通って各自監査を始め、最初に戻った 1 本が land すると残りは fingerprint 不一致で
  拒否される。増幅率の上限は記録済みで、従来は即座に降りていた待ち手がこの経路へ回る。
  増幅の発生率は未計測であり、未計測のまま数値を動かさない。増量の正当化に使われる
  「lock 保持時間の下界 max」は、それが lock 区間の上限ではないとして既に反証されている。
- **監査の履歴範囲を限定する** — `--range` を渡すと `authoritative` 述語が偽になり、既知違反台帳の
  append-only 履歴検査・policy epoch の適用範囲・pinned HEAD 再確認まで同時に落ちる。代替がない。
  加えて、その land が作る fold commit はその land の全史監査を通っておらず後続の全史監査が拾う
  ため、範囲限定はその後続検査も失う。着地 tip が tested tip と異なる前方 merge の commit も落ちる。
  **さらに、縮める対象が律速ではない** — 全史 9800 件の監査本体は計算ノードで 61 秒で終わる。
- **監査の所要そのものを短くする方向だけに賭ける** — 監査は「メモリは軽いが CPU を長時間食う」形で、
  dispatch の admission 判定はバイト予算だけを見て CPU 時間を入力にしないため、予算内に収まる限り
  構造的に混雑した login node に留まる。所要は実行場所で 7 倍振れる。これは別の是正項目であり、
  本決定とは救う対象が異なる。
