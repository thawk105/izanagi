## {{D:verifier-parallel-boundary}}. 直列性検査の並列化は純粋なデータ処理の段までとし、判定と受領証は元プロセスに残す

**決定:** `orchestrator/verifier/` の並列化は、ファイル単位の構文解析と依存グラフの
辺候補の計算までとする。SCC・cycle witness・三値 verdict・`VerifyResult` の組立て・
受領証の発行と消費は親プロセスに残す。子はオブジェクトも判定も返さず、
固定幅配列と token blob だけを返す。`orchestrator/verifier/` に新しい file を作らない。

**理由:**

- **検査を別プロセスへ配って結果だけ受け取る形は取れない。** 受領証は発行時のプロセス番号を
  記録し、消費時に現在のプロセス番号との一致を要求する。証明の連鎖を外して結果だけ受け取れば
  受理する範囲を広げることになり、絶対規律 2 に反する。
  `docs/b10-multinode-formal-run-design.md` §4 が同じ結論に達している。
- **Python のスレッドは効かない。** 検査は純 Python の CPU 仕事である。
- **オブジェクトを子から返すと速くならない。** 17 万 txn の結果を dataclass の pickle で
  往復させると 11.5 秒かかり、同じ入力の構文解析本体 6.74 秒より高い。
  列指向配列なら 0.11 秒である (親の実測)。
- **新 module は正しさ実装を閉包の外へ置く。** enforcement source closure は
  `orchestrator/campaign/campaign_lock.py` の exact 24 path で、verifier package のうち
  `__main__.py` と `cli.py` 以外をすべて含む。D442 はまさに「正しさ判定の実体が identity の
  外にある状態は規律 2 に抵触する」として閉包を広げた。閉包へ足すには編集面外の file が要る。

**判定の同一性をどう保つか:** 辺候補へ大域の論理 ordinal (txid 昇順 → read 行順 → wr → rw →
鍵の初出順の ww) を付け、結合前に ordinal 順で実際の集合へ再生する。子の結果は完了順でなく
ファイル順に消費し、全ファイル分がちょうど 1 件ずつ揃ったときだけ採用する。1 件でも欠けたら
部分結果を全廃棄して逐次で読み直す。構文解析の失敗は、親がそのファイル 1 本を既存のコードで
読み直して自然に例外を上げる (型・文言・行番号・例外連鎖が現行と一致する)。

**却下した選択肢:**

- **構文解析だけを並列化する** — 実測の占有率 54% から Amdahl 上限は 2.17 倍で、
  並列度 48 でも 1 反復 771-871 秒。full-scale 75 回で 16.1-18.1 時間となり目的を満たさない。
- **親でオブジェクトを再構築して既存の依存グラフへ渡す** — 受け渡しは軽くなるが、
  全規模で約 87GB の object graph と構築費が親へ戻る。
- **SCC も並列化する** — 占有率 6% で効果が小さく、判定そのものの層である。
- **モジュール大域変数で子へ入力を渡す** — 同一プロセスの別スレッドが 2 つの trace を
  同時に検証すると片方の子がもう片方の入力を継承しうる。件数の完全性検査は通るので
  巡回のある trace が certified になりうる (段 6 の敵対レビューが実際に指摘し、修正した)。

**射程の限界 (謳わず明記する):** 判定の同一性は測った入力についての事実である。
合成 trace 1 種 (68 万 txn) と `orchestrator/tests/test_verifier.py` の全 fixture の範囲で、
旧コードと新コードの `result_to_dict` が sha256 まで一致した。すべての入力で同一であることの
証明ではない。**既知の差が 1 件ある** — 巨大で疎な txid は従来の実用上の `MemoryError` でなく
欠番数を持つ `indeterminate` を返す (拒否側へ倒れる安全な差)。
また closure に入る file の bytes を変えるので、**既存の campaign lock は
`contract-loader-drift` で再開できなくなる。** 検査器を変える限り不可避である。

## {{D:verifier-parallel-default}}. 直列性検査の既定並列度は所要でなく記憶量で決める — 上限 16

**決定:** 既定の並列度の上限を 48 から 16 へ下げる。明示指定した `workers` の上限は変えない。

**理由:**

- 親が専用 cgroup scope で親 + 全子孫の charged memory の峰値を測った (68 万 txn、48 file)。
  所要は 21.44s (8 並列) → 19.49s (16) → 19.23s (24) → 19.16s (32) → 19.60s (48) で
  **16 で飽和する**が、峰値は 2.34GB → 2.94GB → 3.70GB → 4.50GB → 5.68GB と
  **並列度に比例して増え続ける** (worker 1 本あたり概ね +0.08GB)。
- **48 は最悪の点である。** 16 と同じ所要に 1.93 倍の記憶量を払う。
- B-10 read-heavy の 1 反復は 17M commit で本測定の 25 倍である。線形換算すると
  16 並列で約 73.5GB、48 並列で約 142GB。**計算ノードのユーザ利用上限は 115GiB
  (= 123.5GB) なので 48 では超える。** 落ちれば認証済み成果物はゼロになる。
- 既定は `min(file 数, 割当てコア数, 48)` なので、48 file・48 core の正式走はちょうど 48 を選ぶ。
- 16 までは並列化前より速くかつ軽い (2.94GB 対 3.60GB)。

**16 が最適だとは主張しない。** 根拠は「16 までは旧コードより速くかつ軽く、
それ以上は所要が縮まないのに記憶量だけ増える」という 1 点の実測である。

**却下した選択肢:**

- **記憶量を測って並列度を自動で決める機構を作る** — 新機構であり、発火条件を書ける
  実成果物 path も計測 ID も無い。呼び手が `workers` を明示できる余地は残っている。
- **既定を据え置いて呼び手に任せる** — 正式走の呼び手は `workers` を渡しておらず、
  既定がそのまま 48 になる。落ちる側の既定を放置する理由がない。

**実装済み。** 既定・1・16・48 のいずれでも判定は同じ `result_to_dict` を返すことを
68 万 txn の trace で確認し、変異 matrix (7/7 KILLED) と受入全走も通した。

**射程の限界 (謳わず明記する):** 上限 16 は 68 万 txn・1 機体・1 回の測定に基づく。
17M 規模の峰値は線形換算であって実測ではない。並列度と記憶量の関係が入力の形
(ファイル数、鍵数、辺密度) でどう変わるかは測っていない。
