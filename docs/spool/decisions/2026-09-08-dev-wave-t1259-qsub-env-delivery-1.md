## {{D:probe-submitter-not-a-repo-executable}}. 分類の実測ができない login 側 probe 投入 script は、repo へ実行体として置かない

**決定:** probe の投入 script を `tools/pegasus/` の実行体として repo へ置かない。
repo には shebang なし・実行 bit なし・拡張子 `.txt` の非実行体として置き、
親が repo 外へ退避してから実行する。`.pbs` の冒頭コメントに exact な `qsub` 呼び出しを書く。

**理由:**
- `docs/pegasus-runbook.md` の分類規定により、`local-ok` の grandfather は 4 本限りの例外であり、
  他 entry を `local-ok` にするには実測が要る。
- 同規定は **AI セッション・子エージェント・自動化が分類の実測を自分で行うことを禁じている。**
  未実測の実行体は `unknown` に倒して止め、測定依頼をユーザーへ返す。
- 一方 hook は `tools/pegasus/` 配下の登録 path のうち `local-ok` でないものを login で拒否する。
  したがって「登録には実測が要る / 実測には登録が要る」の循環に入る。
- `orchestrator/tests/test_hooks.py` の execution inventory は「拡張子 `.py`/`.sh`/`.pbs`」
  「実行 bit」「先頭 `#!`」のいずれかで実行体と数える。この 3 条件を外せば数えられない。
- 先行 probe も投入 script を repo に置かず、`qsub` 呼び出しをコメントに書いて親が打っている。

**却下した選択肢:**
- `local-ok` として登録する — 未実測の受理集合拡大であり、規定が禁じる。
- `unknown` として登録し、repo 外へ複製して実行する — 規定が名指しで禁じる迂回である。
- `tools/pegasus/` の外の subtree へ `.sh` として置く — 未登録 path が素通りする性質の利用であり、
  同じく迂回である。

**残る限界 (主張しない):** repo 外で走る投入 script は単体検査で守られない。
守るのは敵対レビューだけである。

## {{D:mutation-over-static-review-for-negative-examples}}. 負例が実効かどうかは静的レビューでなく変異で確かめる

**決定:** 「負例を足した」という fix 報告を、静的レビューの通過だけで実効と数えない。
負例が対象の述語に到達しているかは変異走で確かめる。fix の報告には
「足した負例 / その入力が最初に当たる検査 / 過剰決定なら根拠」を書かせる。

**理由:**
- 本 wave で、事前登録した 10 変異のうち 5 件が生き残った。うち 3 件は正しさゲートの中心で、
  直前の fix が「負例を追加した」と報告していた位置である。
  実際にはその負例は前段の検査が先に拒否する入力を使っていた。
- **段 3 の敵対相談 2 本、段 6 の敵対レビュー 2 本、焦点再レビュー 1 本のいずれも
  これを見つけられていない。** 静的レビューは述語の存在を見るが、その述語へ到達する入力が
  あるかを見ない。
- 変異は「壊したときに赤になるか」を直接測るので、この盲点に掛かる。

**却下した選択肢:**
- レビュー子へ「負例の到達性も見よ」と足す — 本 wave では 3 本ともそう指示されていたに等しく、
  それでも見つからなかった。指示の追加では閉じない。
- 負例の網羅を求める新しい検査を足す — ユーザーが scope 外とした一般化に当たる。

## {{D:external-command-parsers-need-measured-fixtures}}. 外部 command の出力を解析する実装は、実機出力の逐語 fixture で検査する

**決定:** 外部 command (scheduler CLI 等) の列や書式を解析する実装を足すときは、
合成 fixture だけでなく、実機から採った出力を逐語で fixture に入れた検査を同じ commit へ含める。

**理由:**
- 本 wave で、投入 script の状態列の index が 1 つずれていた。既存 test の合成 fixture が
  実装と同じ誤った列配置を共有していたため、**実装が誤っていても緑だった**。
- 実機を 1 度通せば即座に露見する種類の欠陥であり、静的レビューでは掛からない。
- 逐語 fixture は byte 単位で外部仕様を固定するので、書式変更も検知できる。

**却下した選択肢:**
- 実機での結合テストを常設する — 計算ノードの資源を使い続けることになる。
  必要なのは 1 度採った出力の逐語保存であって、毎回の実行ではない。
