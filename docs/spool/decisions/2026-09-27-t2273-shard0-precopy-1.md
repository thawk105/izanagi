## {{D:t2273-precopy-impl-land}}. 受入 shard-0 の候補 (a) の実装 (受入 controller が可視 output の写しを collection 中に作り、共有 base builder は写しから複製する) は実受入の隣接 3 対で事前登録の land 条件を満たしたので段階的改善として land する。5 分上限は未達で、次の律速は (b) 発行 subprocess とする

**決定:**

1. D2253 項 2 の形を実装し land する: `orchestrator/tests/conftest.py` の `pytest_configure_node` (早期 memo prewarm と同じ `_early_memo_selected` の分岐) で session に 1 回、計算ノード /tmp に dir を同期作成し、背景 thread で実関数 `_copy_git_visible_output` を実 repo に 1 回呼んで写しを作る。共有 base の builder は helper `_t080_copy_visible_output` で写しの完成 (`result.json`) を最長 180 秒待ってから写しを局所複製する。写しの dir が無い走 (単独走・絞り込み・受入でない xdist 走) は従来どおり実 repo から直接複製する。path は既存の共有 base と同じ識別子 (`str(ROOT)` と xdist の run ID) から導き、環境変数を新設しない。
2. 判定は段 4 で事前登録した条件どおりに行った。A = local main `a0bf57976`、B = A + 実装 (`163c5eeb7`)、順序 A,B / B,A / A,B の隣接 3 対 (infra 失敗 0) で、shard-0 W_0 の対差は +55.355 / +46.001 / +47.740 秒、対率中央値 12.7 %。「3 対すべて正 ∧ 対率中央値 ≥ 10 %」を満たした。
3. 5 分上限は別判定で未達: B の W_max 3 走の中央値 317.194 秒 (296.137 / 317.194 / 336.973)。事前登録の記録区分どおり「段階的改善として land、5 分未達、次は (b) 発行 subprocess」とし、本 wave はここで止める。(b) は D2253 項 4 の内訳 (共有発行 key の builder の発行 child 約 87 秒、CPU 支配) から始める。
4. 受理規則は変えない。写しは configure_node 時の 1 時点であり、session 中の output/ の変更は fixture に反映されない (D2242 段 4 A1 と同じ扱いで docstring に明記し、gate は足さない)。

**理由:**

- 事前登録を結果を見る前に固定し、その基準を満たした (規律 3 の後付け禁止と同じ向き)。D357 の 1 走比較でも 3 対とも差は 10 % 以上 (12.4〜15.7 %)。
- 正しさの側は不変: 実関数の本体・全件性の検査 2 か所・`_T080SharedBases`・早期 memo の挙動を変えず、事前登録の変異 M1〜M7 は全件 KILLED (期待 node と完全一致)。
- 5 分は対差の改善とは別の量で、依頼が「届かなければ (b) と記録して止める」と定めている。

**却下した選択肢:**

- 5 分未達を理由に land しない — 事前登録の land 条件は性能改善の有無で、5 分は別判定と定めていた。改善を捨てる理由にならない。
- (b) を同じ wave で足して 5 分を狙う — 依頼が止めると定め、(a) と (b) を同じ wave に入れると実受入の隣接対で効果を分けられない (D2253 項 4)。
- shard 割付を controller で先読みして写しを shard-0 だけで作る — shard は worker の collection で決まり、controller の configure_node 時点では分からない。B で shard-1 が伸びた走 (W_1 313.0 / 267.8 秒) の原因は計器が無く分けられておらず、効果を測る前に機構を足さない (D1936 項 35 と同じ向き)。
