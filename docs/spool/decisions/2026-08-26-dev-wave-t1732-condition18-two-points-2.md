## {{D:condition-18-two-point-gate-scope}}. 条件 18 の 2 点発火は入口契約の関門まで機械化し、実運用 adapter は別裁定にする

**決定:** D907 の 2 点化にあたり、機械が担保する範囲を次の 2 つに限る。

1. 入口 `.claude/commands/dev-wave.md` の条件 18 trigger が、走行点と赤処理点の**独立した 2 逐語**を
   含むことを `tools/check_docs.py` の本番検査経路 (`_main` → `_check_command_docs_guard`) で要求する。
   期待逐語は契約 dict から導出しない手書き literal とし、片方を落とすと違反 1 件を出す。
2. 入口文書だけを入力に義務を解決する `resolve_condition_sections` を production へ置き、
   投入 context と赤処理 context が別プロセスになる状況を実際に作る検査でこれを通す。

**実運用の manager / 赤処理 adapter からこの解決器を呼ぶ配線は本決定の範囲外**とし、
必要なら独立の裁定で設計する。したがって本機構が担保するのは
「入口の文書契約」と「解決器が両状況を区別できること」までであり、
**「実運用で必ず 2 点発火する」ことは担保しない**。

**理由:**
- D907 が裁定したのは trigger の 2 点化であって、実行層の新設ではない。
  「条件が発火する」の実体は現状 prompt 規律 (人・AI が節を読む) であり、節を読む program は無い。
  実運用の呼び手を作るには manager の赤処理を観測可能な adapter として作り直す必要があり、
  裁定の射程を大きく越える。
- 関門と解決器を区別して記録しないと F559 の型 (防壁の代替として必須化した検査を本番経路へ
  配線せず test からしか呼ばない恒真ゲート) と取り違えられる。本件では**関門は配線済み**である
  (実ツリーの trigger を単点化する変異が本番検査経路の違反を出すことを実測)。
  未配線なのは解決器の方であり、そちらは防壁ではなく再発防止検査を成立させる機構である。
- 段 6 の敵対レビュー 2 本が独立に同じ点を指摘し、いずれも「別タスク」と判定した。

**却下した選択肢:**
- **本 wave で manager の赤処理 adapter まで作る** — D907 の射程外を既成事実にする。
- **解決器を置かず、検査を imported module の関数呼び出しだけで済ませる** —
  投入 context と赤処理 context が別になる経路を通らず、元の欠陥を再現しない。
- **「実運用で 2 点発火する」と記録する** — 未保証の主張であり、恒真な保証になる。
