## {{D:v8-cost-breakdown-remeasure-first}}. V-8 は費用内訳を測り直してから裁定する

**決定 (ユーザー裁定):** 8c 結線設計 §11 の V-8 (物理実行の単位を「1 query ordinal = 1 campaign
run」とするか、1 run 内で 33 行を回すか) について、**費用内訳の再測定を専用の作業として起票し、
その数字を持って V-8 を裁定する。** 現時点で択一そのものは選ばない。

**理由:**

- V-8 は 2026-08-13 以来「費用内訳の再提出待ち」で止まっており、材料が来ないまま 3 週間動いていない。
  D1555 が確定させたとおり、V-8 は V-7、本番 runtime provisioning、本番 origin、P6 の発火条件へ
  続く依存鎖の根である。材料待ちのまま置くと下流が全部止まり続ける。
- 33 倍という費用は当時の見積りであり、その後 build cache と直列性検査の所要が変わっている。
  古い見積りで択一を選ぶのは、実測でない数字に依存した裁定になる。
- 材料の取得そのものを一手として起票するのは、受理集合にも成果物にも触れない調査であり、
  研究最優先・プロトタイプ基準の見送り方針とも衝突しない。

**却下した選択肢:**

- **材料なしで (a) を選ぶ** — 33 倍という数字が現行コードで再現するかを確かめずに費用を確定させる。
- **材料なしで (b) を選ぶ** — 設計文書が実測で「fail-closed なら常に aborted、既存 WAL を再利用
  すれば物理実行保証が破れる」と示しており、正しさの側で成立しない。
- **さらに材料待ちのまま置く** — 3 週間の実績が、待つだけでは材料が出ないことを示している。

## {{D:floor-official-staged-transport-into-driver}}. 床値 official の staged transport は driver 内部の既定へ移す

**決定 (ユーザー裁定):** D1396 が裁定へ返した床値 official の起動不能について、**解消案 1
(staged transport を driver 内部の production 既定にする) を採る。** payload の所在を caller の
seam でなく driver 側で導出する形にし、18 名の不適格 seam 集合と `_derive_refreeze_eligibility` の
判定式は literal には変えない。

**理由:**

- D926 が 18 名集合と判定式を「変更しない」と名指ししている。集合か判定式を緩める案 3 は
  正しさ防壁を緩める向きであり、絶対規律 2 に反する。
- 案 2 (既定経路を実測して argv から外す) は、計算ノードが直結 network を持たず FetchContent の
  外部取得が通らないため、手順書が定める pinned staging の運用と正面から衝突する。実測の前に
  運用が成り立たないことが分かっている。
- 案 1 は seam の名前と判定式を保ったまま、payload の所在の導出責任だけを driver へ移す。
  設計論点は「発見による暗黙の入力経路を作らないこと」であり、導出規則を明示的に固定すれば足りる。

**却下した選択肢:**

- **18 名集合か判定式を変える** — D926 が禁止し、正しさ防壁を緩める。
- **既定経路で投入する** — 計算ノードの offline 条件で通らないことが運用契約から分かっている。
- **承認束縛だけ先に実装する** — D1396 が既に `DW-G04` 違反として却下している。

## {{D:historical-grammar-locks-reissued}}. 旧 grammar の campaign lock 11 件は新閉包で発行し直す

**決定 (ユーザー裁定):** enforcement source closure の拡張で読めなくなった旧 grammar の
campaign lock 11 件 (B10 格子 3 件、paper-story A-2 認証 8 件) について、**新しい閉包で発行し直す。**
旧 artifact の bytes は書き換えず、新しい lock を別途発行する。限定範囲の版付き decoder は作らず、
図の生成経路を別の束縛へ移す案も採らない。現行 certified 経路は緩めない。

**理由:**

- D1550 が求めた前提の実測は完了している。受入全走で図 2c の生成経路が
  `CampaignLockCodecError` で落ち (1 failed / 19869 passed)、稼働 wave が閉包拡張への帰属と
  判定した。D1511 の再訪条件 (admission API 経由で読み直す必要が実際に生じたとき) も成立している。
- 版付き decoder は受理判定のコードへ分岐を 1 本足す向きの変更であり、正しさの関門の近くに
  機構を増やす。再訪条件が成立した今は選べるが、選ぶ理由が「読めるようにする」だけなら、
  受理側を触らない案のほうが小さい。
- 発行し直しは凍結記録の書き換えではない。旧記録の bytes はそのまま残り、当時その道具で
  その測定をした事実は変わらない (規律 7)。束縛は内容ハッシュに掛かっており、
  新しい lock は同じ内容に対する新しい束縛である。
- 図の生成経路だけを別の束縛へ逃がす案は、同じ問題が他の読み手で再発する。

**却下した選択肢:**

- **`HISTORICAL_RAW` 限定の版付き decoder を作る** — 受理側へ分岐を足す。上記のとおり
  再訪条件は成立しているが、より小さい案がある。
- **図の生成経路を別の束縛へ移す** — 同型の閉塞が他の consumer で再発する。
- **旧 artifact を新 grammar へ書き換える** — 凍結された記録の bytes を後から変えることになる
  (D1511 が既に却下)。

## {{D:openalex-condition5-hold-pending-three-checks}}. 軸 1 の条件 5 は変えず、先に欠落と版ずれを確かめる

**決定 (ユーザー裁定):** OpenAlex の完走条件 5 (`distinct_work_id_total_mismatch`) は
**現状の形のまま変えない。** 許容幅を持たせる案も、頁境界の重複を除いて厳密一致を保つ案も採らない。
D1331 が要求した 3 確認 — (a) 返却されなかった別 ID が実在するか、(b) 連続 2 走で集合が安定するか、
(c) 索引側の snapshot drift があるか — を軸 1 について完了させ、その結果を持って条件 4 と条件 5 の
改訂範囲をまとめて 1 回で決める。

**理由:**

- D1331 は同じ論点について distinct 化を明示的に却下し、先に欠落の実体を確かめると定めている。
  今回の実データ発火はその裁定を覆す新事実ではなく、裁定が予期していた事象である。
- 2026-09-03 の走行は、同じ登録 request を同日に 2 回投げて判定が両方向に反転したと実測した。
  これは D1331 の (b) が「安定しない」と出たということであり、むしろ (c) の版ずれの疑いを強める。
  原因を確かめずに述語を変えると、取得漏れを重複として片付けることになる。
- 別の索引 (arXiv) について重複排除を採った D1454 は、その索引の事象だけを対象としている。
  同じ機構に見えることを理由に軸 1 へ持ち込むのは、後続裁定との主題照合を欠いた射程超過にあたる。
  起草時の推奨はこの誤りを含んでおり、別系統モデルが独立に指摘した。
- (a)(b)(c) は取得の副産物として測れる。専用の大きな測定を要しない。

**却下した選択肢:**

- **許容幅を持たせる** — 幅の値を結果を見てから選ぶ形になりやすく、取得漏れを隠す。
- **頁境界の重複を除いて厳密一致を保つ** — D1331 が却下した distinct 化と実質同じで、
  実測でも条件が通らない可能性が高い。
- **非 shard 枝を諦める** — 原因が版ずれなら諦める必要がない。

## {{D:c09-dead-branch-first-rest-need-counterexamples}}. 条件 9 は死枝の修正だけ先行し、残る 3 穴は反例の実測後に範囲を決める

## {{D:noinline-meaning-via-branch-selection-witness}}. 診断計器の意味検査は枝選択 witness で厳格化する

**決定 (ユーザー裁定):** `BACKOFF_NOINLINE` の runtime-meaning が常に未確立のまま `paper` へ
受理される件を**厳格化する。** ただし対応 macro 集合へ追加するだけの形は採らない。D1490 の
compile-time 枝選択 witness を registry の factory から発行し、旧 `MeaningWitnessDeclaration` と
CLI の宣言経路は `BACKOFF_FIXED` に固定したまま据え置く。配線先は D1492 に従い、
成果物の未確立一覧が実際に縮む driver に限る。

**理由:**

- 意味の節が実質空のまま `paper` の受理を通るのは、D1198 が「供給と意味を独立した必須節として
  持つ」と定めた形が片方だけ空回りしている状態である。厳格化は受理集合を狭める向きなので
  絶対規律 2 に整合する。
- 対応 macro 集合を広げるだけの形は D1491 が明示的に却下している。集合を広げた瞬間に、
  別 macro を BACKOFF 用の数値復号器で評価して緑にできる経路が開く。集合の拡張が副作用として
  別経路の受理を広げるなら、正味で緩めたことになる。起草時の推奨はこの形であり、
  別系統モデルが D1490〜D1492 の現物を引いて指摘した。
- 配線先を限るのは、要求しない driver や route 不一致で admission 前に拒否される driver へ
  配線しても未確立一覧が 1 件も縮まないためである。

**却下した選択肢:**

- **`MEANING_SUPPORTED_MACROS` へ追加するだけ (起草時の推奨)** — D1491 が却下した形そのもの。
- **現状のまま未確立を受理し続ける** — 意味の節が空のまま論文用の受理を通る。
- **全 driver へ配線する** — 未確立一覧が縮まない driver まで編集面を広げる。

## {{D:k2-is-declared-scope-not-minimum-injection}}. 知識水準 K2 は宣言した範囲であって最低投入件数ではない

**決定 (ユーザー裁定):** K2 (プロジェクト蓄積を含む知識あり) は **宣言した外部取得と投入の範囲**を
指し、実際に投入した情報源の件数を条件にしない。`knowledge_manifest` が情報源 1 件以上を要求して
取得結果ゼロの K2 アームを入口で拒否する件は、**取得結果が正当に空である場合に限って通す**形へ直す。
宣言範囲・取得実績・空であるという事実は記録に残す。

**理由:**

- D1429 が「水準が指すのは知識の量ではなく、宣言した外部取得と投入の範囲である」と明記しており、
  件数を意味条件にすると既裁定の定義を別物へ変える。同決定は許した範囲と実際に投入した知識源を
  分けて記録するので、実投入 0 件も表現上は区別できる。
- 役割定義だけを緩めても manifest で落ちるため、端から端まで通らない。定義と実装のどちらかが
  誤っている状態であり、既裁定がある以上は実装側を直す。
- 緩和を「取得結果が正当に空」に閉じ、記録を残すことを条件にするのは、宣言を伴わない
  無条件の緩和にしないためである。

**却下した選択肢:**

- **最低 1 件の実投入を K2 の条件にする** — D1429 の定義を量の条件へ変える。
- **役割 schema だけ緩める** — manifest で落ちるので端から端まで通らない。

## {{D:shared-root-v1-residue-stays-rejected}}. 共有 root の合成 2 段 v1 残骸は拒否のまま維持する

**決定 (ユーザー裁定):** 共有された保存 root に残る合成 2 段 v1 の残骸 193 行は、
**受理側へ戻さず fail-closed の拒否のまま維持する。** 副作用として同じ凍結の正規 1 段 v1 の
書き込みが止まることも、現状のまま受け入れる。

**理由:**

- 共有 root の残骸を種類を確かめずに運用判断へ使った先例があり、形状だけで trusted とみなして
  戻すべきでない。
- 正規 1 段 v1 の書き込みが止まることは、実害として観測されれば再訪の根拠になる。

**却下した選択肢:**

- **受理側へ戻す** — 再構成できない profile を受理集合へ入れる。

**再訪条件:** 正規 1 段 v1 の書き込みが止まることによる実害が 1 件観測されたとき。

## {{D:axis1-evidence-time-binding-needs-challenge}}. 軸 1 の証拠の取得時点は追記専用登録では閉じない

**決定 (ユーザー裁定):** 証拠が「登録 commit の後に取得された」ことの束縛は、**追記専用の登録では
行わない。** 登録の前に予測できない challenge を固定し、提供元が応答へそれを反映することを
実測できるならその形を採る。実測できなければ、**この保証は未閉鎖であると機械可読に明記して先へ進む。**

**理由:**

- 追記専用の登録は「登録が先に存在した」ことしか示さず、後から追加した bytes が過去に保存した
  応答でないことを示さない。掲げた保証が発火しない恒真な保証になる。起草時の推奨はこの形であり、
  別系統モデルが指摘した。
- 因果を hash 鎖だけでは閉じられないという判断は既にあり、独立の機構を新設するのではなく
  偽造不能な受領証へ相乗りさせる方針が採られている。content hash が保証するのは bytes の一致
  までで、物理実行や取得時点ではない。
- ローカルの登録だけを正解側に置くと、期待側と観測側が同じ主体に由来して恒真化する型になる。
- 未閉鎖を明記する側は、保証があるように読ませないという意味で正直な閉じ方である。

**却下した選択肢:**

- **追記専用の登録で束縛する (起草時の推奨)** — 取得時点の因果を示さない。
- **束縛を置かずに黙って進める** — 検査器が旧応答の再包装を拒否しないことが読み手に伝わらない。

## {{D:permutation-witness-known-unavailable-until-settled}}. 並べ替え証拠は同値関係が確定するまで利用不可へ倒す

**決定 (ユーザー裁定):** permutation witness の同値関係と thread-hint の除外は、**確定するまで
permutation を known-unavailable へ倒しておく。** 未裁定のまま実装しない。

**理由:**

- 未裁定のまま実装すると、証拠を束ねる class SHA が未裁定の規則で固定される。後から規則を
  変えると既存の SHA が意味を変える。
- P6 の機械実装が保留へ戻る以上、本件はその下流として自然に待てる。今は他の作業を止めていない。
- known-unavailable は「まだ言えない」を機械可読に残す形であり、無いものを在るように見せない。

**却下した選択肢:**

- **同値関係を今決めて実装する** — 上流の P6 が保留である以上、決めた規則を実データで確かめられない。
