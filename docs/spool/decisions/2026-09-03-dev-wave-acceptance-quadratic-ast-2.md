## {{D:acceptance-serialization-chains}}. 受入 wall の律速は最長 node ではなく直列化される鎖である

**決定:** 受入全走の所要を論じるときは、まず「worker 数に依存しない直列鎖」を数える。
台帳の総量や最長単体 node から wall を推す前に、次の 3 種を列挙して最大値を取る。

1. `xdist_group` marker により 1 worker へ固定される group の合計
2. fixture が排他 lock を保持したまま test 本体を走らせる鎖の合計
3. 最長単体 node

**理由:**
- 既定 scheduler は `--dist loadgroup` であり、group marker の無い node は worker へ個別に
  配られる。したがって file 単位の合計は wall の下限にならない (ただし file 全体は同一
  component として同一 shard に載るので、shard = ホストへの affinity としては効く)。
- 実測で鎖 1 が 303.7 秒、鎖 2 が 258.1 秒、最長単体 node が 140.0 秒だった。
  走行外費用を足した下限 381.9 秒は、直前 wave が記録した最遅 shard の実測 388.3 秒と
  誤差 1.6% で一致する。**最長単体 node を床と見なす読み方は 2 倍以上外す。**
- worker を増やしても鎖は縮まない。並列度の議論は鎖を解いた後にしか意味を持たない。

**却下した選択肢:**
- 台帳の総量を worker 数で割った値を wall の見積りにする — 鎖がある限り到達しない。
  実測では詰め下限 186.8 秒に対し鎖が 303.7 秒あり、後者が支配する。
- 最長単体 node を床とする — 直前 wave がこの読み方で説明できない 235 秒の空白を残した。
  空白の正体は鎖 1 だった。

## {{D:read-only-nodes-must-not-be-serialized-by-group}}. 資源の排他は lock で行い、xdist group で代用しない

**決定:** 共有資源へ触る test を直列化する必要があるとき、`xdist_group` による worker 固定を
排他の手段として使わない。排他は読み書きを区別できる lock (`LOCK_SH` / `LOCK_EX`) で行う。
`xdist_group` は、shard = ホスト affinity のように lock では表現できない束縛にだけ使う。

**決定 2:** 既に lock がある資源へ後から group 固定を重ねてはならない。二重の防壁に見えて、
実際には粗い方が細かい方の設計意図 (読み手の並行) を無効化する。

**理由:**
- `real-repo` 資源には既に node ごとの読み書き lock が実装されているのに、collection hook が
  同じ node 集合へ一律の group marker を付けるため、**読み取り専用の 92 node (303.7 秒) が
  互いを待っている。**書き手は 4 node で実質 0 秒しかない。
- group は「同じ worker で走る」しか表現できず、read/write の区別を持てない。
  資源の性質を表現できない道具で排他を実装すると、必ず過剰な直列化になる。

**却下した選択肢:**
- 書き手だけを group に残して読み手を解放する — **採ってはならない。**別 shard は別ホストに
  なりうるため local の flock は跨ホストの競合を閉じない。読み手が別ホストへ移った瞬間に
  書き手との排他が失われる。速くするために防壁を外す形であり、絶対規律 2 に反する。
  shard affinity は全 node について保ったまま、worker grouping だけを割る必要がある。
- 現状維持 — 受入 5 分の要求を満たせない。

## {{D:equivalence-pin-needs-synthetic-boundary}}. 等価性テストは実 corpus の到達性を測ってから設計する

**決定:** 「新経路が旧経路と同じ値を返す」ことを要求するテストを作るときは、
**実 corpus にその故障を露出させる入力が存在するかを先に測る。**存在しない故障型については、
合成 fixture を唯一の検出経路として明示的に設計し、事前登録の期待でもそう書く。

**決定 2:** 等価性テストは helper を直接呼ぶだけでは足りない。**製品の呼び出し経路が
実際に新 helper を使っていること**と、性能不変条件 (module あたり分割 1 回) と、
その返り値が helper へ渡っていること (同一性) を別のテストで pin する。

**理由:**
- 45 module / `if` 3282 個を走査したところ、guard の直前に非 ASCII がある行は 0 件、
  form feed を含む module も 0 件だった (非 ASCII を含む module は 36 個ある)。
  **全 module を比較するテストは、byte/文字の取り違えも form feed 分割も殺せない。**
  実 corpus の網羅性は入力の多様性を意味しない。
- helper を直接呼ぶ等価性テストは、製品が旧経路のままでも通る。
  **二乗が残ったまま緑になる成果物を受領しうる。**変異 2 件 (旧経路へ戻す / `if` ごとに分割する)
  を事前登録し、配線テストと分割回数テストだけがこれらを殺すことを実測で確認した。
- 呼び出し回数だけの assert では、死んだ 1 回呼び出しを残して別 splitter を使う実装が通る。
  返り値の同一性まで要求して初めて dataflow が閉じる。

**却下した選択肢:**
- 実 corpus の全数比較だけで足りるとする — 上記のとおり 3 故障型のうち 2 つを取り逃す。
- 各 module の代表 1 件だけを比較して所要を抑える — 同一 module 内の異なる offset、
  複数行範囲、末尾位置の検出力を失う。実測で全数比較の追加費用は 1〜2 秒であり、抑える理由がない。
