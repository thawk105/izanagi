## {{D:land-must-not-require-a-frozen-main}}. 着地は main の静止を要求しない — 進んだだけでは拒否しない

**決定 (ユーザー裁定):** `tools/dev_wave_land.py` が `stale-main`
(`main moved outside the tested audited closure while locking`、rc は `RC_STALE_MAIN`) で
拒否する現行の要求を改める。**受入を検査した時点から main が進んだというだけでは着地を拒否しない。**
着地側が main を取り込み直して進み、**実際に内容が衝突したときだけ**通常の競合解消
(fetch → 再 merge → 必要なら AI が衝突を解消 → 再投入) へ落とす。

**理由:**
- 現行の要求は「自分が測っている間 main を止めておきたい」と全 wave に願わせる形であり、
  **D662 が却下した lease 直列化と同じ要求を、各 wave に自前で再実装させている**。
  D662 は「main への取り込み競合は特別な直列化機構ではなく通常の git 競合解消で対応する。
  これは push 前後の通常の並行開発ワークフローであり、専用の待ち行列を要しない」と明記しており、
  本決定はその明記を着地側の実装へ反映するものである。
- **所要を縮めても消えない。** 赤の帰属判定を一定時間へ作り替えても
  (D680)、受入全走 3〜4 分の窓は残る。実測でも、
  受入本体が 3 分 30 秒で緑になった wave が `stale-main` で弾かれている。窓の縮小は緩和であって
  解ではない。
- 実測の被害: 本セッションは受入 6 走・約 4 時間を消費して着地できず、そのうち 1 走は
  判定 39 分の最中に main が 2 回進んで判定不能になった。別 wave では手動の判定器実行が
  58 分走って未完了で、その間に main が 2 回進行した。
- 「一つの wave の失敗・競合・既知の不具合が全体を止めてはならない」という D662 の設計原則が、
  着地側にだけ適用されていなかった。

**却下した選択肢:**
- **各 wave が「取り込み → 受入 → 着地」を連結して競走窓を閉じる** — 窓を短くするだけで
  前提を変えない。混雑すれば lease 直列化と同じ破滅へ戻る。**ただし、他 wave を待たせず
  main を止めもしない実行形 (親が手待ちしないだけ、弾かれたら通常の競合解消へ落とす) は
  この却下に当たらない。** 却下するのは「競走窓を閉じにいくのが正しい姿」という一般則の側である。
- 現状維持 — 混雑が恒常化した現在、着地可能性が他 wave の着地タイミングに依存し続ける。
- 着地を再び直列化する (lease の復活) — D662 が計算ノード混雑下の破滅を理由に却下済み。

**実装時の条件:**
- 取り込み直しは **fast-forward または競合なしの merge に限る**。競合したら止めて通常の
  競合解消へ返す。着地側が衝突を自動解決してはならない。
- 取り込み直した結果に対して、**受入受領証が束縛する tip との対応が崩れていないこと**を
  検査する。受領証が指す tip と別物を着地させる経路を作らない。
- `--audited-commit` の閉包検査 (`tested_main..tested_tip` の全 commit を
  `git rev-list --reverse` の順で列挙する要求) は緩めない。ここは監査の本体であり、
  main の静止要求とは別物である。
