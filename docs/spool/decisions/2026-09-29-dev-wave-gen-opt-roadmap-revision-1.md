## {{D:gen-opt-activity-scope}}. 活動範囲を新規最適化の創出へ広げる roadmap の協議改訂 — 文献にあって CCBench に無い最適化の実装 (段 A) を (b2) の経路に上げ、文献に無い仕組みの合成 (段 B) を designated source・編集範囲・正しさ関門を保ったまま開き、新しい仕組みに足す正しさ関門の原則 2 つを置く

**背景:** 実際に回した変異軸 (backoff の数値・施錠順序 79 値・発火条件 5 bit) はどれも列挙し尽くせる小さい空間で、LLM・ランダム・総当たりの差が揺れの床の内側に収まり (D2212)、唯一の成功例 (静的 backoff) も既知だった。roadmap は「(c) ゼロから書かせる」を除外し、「他 CC の最適化を持ち込む (b2)」を後続拡張として予約していた (D32)。ユーザーがこの範囲を新規最適化の創出へ広げる相談をし、親セッションが条件付き賛成の提案を返し、ユーザーがその (a) に同意した。

**ユーザー発話 (逐語、親セッションの記録 `user-verbatim.txt` から写し):**

> [1] 相談があります。現在izanagiは最適化組み換えだけを活動スコープにしている。これを広げて、新規最適化創出をやらせるのはどう思う？VLDB / SIGMODで関連する領域の論文を調査して、考えて作ってみる、ってのを進化探索フレームワークを回してやらせてみたい
>
> [2] この形に改めて良い。dev-wave文作ってくれ

**親の解釈 (ユーザーの明示確認は取っていない):**
- 「この形に改めて良い」は、提案末尾の (a)「roadmap の『(c) ゼロから書かせない』『(b2) は後回し』を、編集範囲と正しさ関門を維持したまま改める」への同意とした。
- (b) 優先度 (ComSys と P0〜P6 の後ろに置くか、計算を使わない手順だけ今から並行で始めるか) には明示の回答が無い。dev-wave 文の作成を求めたことから、推奨どおり「計算を使わない手順 (文献カード化と設計) を今から並行で始め、試し実装と探索の本走は後で見積りを添えて確認する」と解釈した。この解釈が誤りなら、下の決定 5 の順序と、roadmap の「着手時期」の文が変わる。

**決定:**
1. **段 A** — 文献にはあるが CCBench に無い最適化を、正しく実装して workload 別に選べることを示す。(b2) を後続拡張の予約から段 A の経路へ上げ、持ち込み元を CCBench の他 CC に限らず文献の最適化まで含める。
2. **段 B** — 文献にも無い仕組みの合成を、designated source・編集範囲・正しさ関門を保ったまま行う経路として開く。制約なしにゼロから書かせる (c) は引き続きやらない。「新しい」の判定は、結果を見る前に文献の検索式を登録し、別の AI に反証させてから下す。
3. **§1 の 3 分類との対応** — 段 A の成果は「既知結果に条件づけられた派生」または「再現・選択」に当たり、新しい軸の発見や LLM 固有成果に数えない。段 B も、新しさの判定を通ったものだけを de novo と呼ぶ。
4. **新しい仕組みに足す正しさ関門 (原則だけ)** — CCBench に無い仕組みを入れる候補には、今の正しさゲートに加えて (i) 検査用記録の差し込み点を LLM の編集範囲の外に固定する、(ii) 仕組みごとに小さいモデルで全場面を検査する、を課す。どちらも既存ゲートの代わりではなく追加である。具体設計は roadmap に置かない。
5. **順序** — 計算を使わない文献カード化と設計から始め、段 A の試し 1 本で「正しく作れる」ことを確かめてから、母集団型の探索 (進化探索) の本走を見積りを添えてユーザーに確認する。カタログ化の旧着手 gate (workload descriptor と層3 材料レポートの最小 E2E の成立後) は外す。
6. 「sequential loop を進化探索と呼ぶこと」の用語予約と、ポジショニングで「世界初」を断定しない方針は維持する。

**理由:**
- 列挙できる空間では機械探索で足りることを自分たちで示した (D21/D29/D2212)。文献を読んで仕組みを考え、コードに落とすのは機械探索にはできず、LLM が効く場所はそこにある。
- 「新しい」はほぼ既知に落ちる (VHash の文献調査で中核が既知と判明)。成果を段 A (確実に主張でき、測れる) と段 B (当たれば大きい上積み) に分けると、段 B が空振りしても段 A で主張が立つ。
- 新しい仕組みは今の検査で捕まえきれない恐れがある。VHash の forwarding の初版は小さいモデルの全探索で 3 取引の閉路反例を出した (D2282)。これは有限の実行記録を調べる検査では見逃しうる種類である。さらに LLM が読み書きの経路を書き換えると、検査用記録の差し込み点を迂回した瞬間に「何も見えないので合格」になる。最適化の圧力は検証の甘さを突きに来る (規律 2)。

**却下した選択肢:**
- **現状維持 ((b2) を予約のまま、(c) を除外したまま)** — 列挙できる小さい空間では LLM の出番が無いことを自分たちで示しており、論文の中心命題を強める経路が閉じたままになる。
- **(c) を制約なしで解禁する (designated source・編集範囲・verifier を外して書かせる)** — 比較可能性と正しさを失う。roadmap §10 の「制約なしのコード生成」をやらない理由はそのまま残る。
- **正しさ関門を据え置いたまま段 B を開く** — 有限の実行記録の検査では見逃しうる反例 (D2282) と、検査用記録の差し込み点の迂回で「何も見えないので合格」になる経路が残る。規律 2 に反する。
