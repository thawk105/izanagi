## {{D:ratification-both-waves-hold}}. 批准の執行機構と批准の撤去は、どちらも先に land しない

**決定 (ユーザー裁定):** 同時刻に逆向きへ動いていた 2 wave のどちらも先に land しない。
`worktree-dev-wave-t1629-ratification-broker` (署名 broker による批准の執行機構) と
`dev-wave-b10-overthrottle-grid` (批准突き合わせの撤去) を両方止め、
**批准を維持するか、規律 2 の穴を明示的に受け入れるかを decisions で先に確定する。**
測定の閂は、認証経路の関門を緩めずに D1028 / D1038 の非認証成果物型と投入器で外す。

**理由:**

- **どちらの順序も安全でない。** t1629 が先なら、その追加物は撤去対象が増えるだけの
  休眠 capability になる。b10 が先なら、t1629 は存在しない関門のための機構になり、
  その land は撤去された関門を復活させる。両者は同じ closure を逆向きに変更する。
- **t1629 が着地しても D905 は未実装のまま残る。** 同 wave 自身の
  未 land fragment に置いた主張上限の決定 (批准機構の claim bound) が
  「『D905 / D906 を満たした』とは書いてはならない」と定め、
  判定器とその呼び出し元が判定対象の閉包の内側にあるため repo を編集できる主体は鍵を持たずに
  gate を消せる、と明記している。したがって「t1629 を通せば D905 が片付く」は成立しない。
  同 wave は resume の署名素通りも正例テストで固定しており、D1039 も未実装のまま残る。
- **b10 の撤去後に残る検査は、記録と実行の一致しか示さない。**
  `contract_loader_binding.verify_live_contract_loader_binding` は記録 commit blob・記録 digest・
  live bytes の三者一致を、`verify_committed_contract_loader_binding` は working tree を読まずに
  記録 commit blob と記録 digest の一致を検査する。activation tuple は source authority を見ない。
  弱化された bytes を正規として採用してよい主体だったかを検査するものは残らない。
- **同じ blockage に対する解決手段を、ユーザーが既に別の形で選んでいる。**
  D1028 は「非認証成果物型と投入器を同じ変更単位で作る」とし、D905 の着地待ちだけにする案を
  却下している。D1038 は昇格不能性を鍵・記録・schema・consumer の全層で固定する条件を定める。
  接続点は実在する (`trial_registry.py` の `registered-formal-non-certifying` と
  `certifying: bool = False`、`artifact_admission.py` の certified view の閉じ方)。
  この経路なら認証経路の関門を 1 つも緩めずに測定を再開できる。
- **撤去の是非そのものは否定していない。** 否定したのは現状の草案のまま通すことである。
  撤去を選ぶなら、D526 に加えて D905 / D1039 / D1028 / D1038 を無効化する関係を明示し、
  規律 2 の穴を受け入れる裁定として記録し直す必要がある。

**本裁定の後に起きたこと (記録):** 本裁定は両 wave への**直接指示を上書きしない**。
t1629 はユーザーの直接指示により `7b53f773` (08-27 07:39) で着地し、b10 も直接指示により
27 path 世界での撤去へ入った。したがって「両方 land せず」は t1629 については実現しなかった。
**それでも本裁定の中核 — 維持か撤去かを decisions で先に確定し、測定は非認証成果物型で通す —
は未決のまま残る。**t1629 の着地は D1128 が「D905 / D906 を満たしたとは書いてはならない」と
宣言しただけで、維持/撤去の裁定ではない。

**却下した選択肢:**

- **t1629 を先に land する** — 当初の親推奨だったが撤回した。根拠にした「D905 が片付く」と
  「受入所要台帳の網羅率修正という独立の価値を運ぶ」は、どちらも実測で崩れた。前者は同 wave 自身の
  限界宣言が否定し、後者は同じ修正が別 wave によって先に main へ着地したため
  (`50b364355`)、t1629 は merge で自分の修正を捨てている。
- **b10 の撤去を先に land する** — ユーザーの最新かつ明示の発話に沿う形だが、
  草案が D905 / D1039 / D1028 / D1038 を名指しせず、規律 2 の穴を受け入れる裁定として
  書かれていない。書き直せば通る水準の欠落であり、撤去そのものの否定ではない。
- **関門を残したまま計測側で迂回する** — b10 の草案自身が却下対象として名指ししている。
  関門があるという見かけだけが残る。

## {{D:ratification-retire-requires-naming-superseded}}. 批准を撤去するなら、無効化する既裁定を名指しする

**決定:** enforcement source closure の批准突き合わせを撤去する決定を書くときは、
D526 に加えて次を名指しし、それぞれが実効を失うことを本文に書く。

1. **D905** — 「AI が成りすませない実行主体の新設だけを採る」。撤去は主体を作らずに概念ごと消すため、
   明示的な上書きになる。命じられた実行主体を今後も作らないのかを書く。
2. **D1039** — 「resume で批准を再検査しない挙動は穴として塞ぐ」。verifier を削除すると実装不能になる。
3. **D1028** — 「A-1 の停止は非認証成果物型と投入器を同じ変更単位で作ることで解く」。
   同じ blockage に対してユーザーが既に選んだ解決手段であり、撤去はその選択と逆向きである。
   なぜそちらを採らないかを書く。
4. **D1038** — 非認証成果物型の設計と昇格不能性の固定条件。同上。

**理由:**

- 撤去は D526 だけを無効化するのではない。読み手が「blockage を解く手段は他に無かったのか」と
  問うたとき、決定文がその答えを持っていなければならない。
- 2026-08-27 の草案は「この決定はその防壁を捨てる」と規律 2 の穴自体は正しく書いていた。
  欠けていたのは、同じ問題に対する既存の解決手段との関係である。
- 同日に landed した D1070 / D1071 との関係は、同草案が訂正時に自ら明示した。同じ扱いを
  上記 4 件へも広げる。

**却下した選択肢:**

- **D526 だけを名指しして足りるとする** — 撤去が実効を奪う裁定はそれだけではない。
- **穴の悪用シナリオの列挙を要求する** — 草案は既に脅威を逐語で書いており、追加の列挙は
  読み手の判断を助けない。

## {{D:codex-child-web-search-allowed}}. codex 子の Web 検索を許可し、拒否の対象を成果物側へ限る

**決定 (ユーザー裁定):** codex 子の Web 検索を**許可する**。
`DW-C01` の無条件禁止は、既裁定 [T-981] の「既定 off・必要な段だけ有効化」と整合する形へ改める。

許可を実効化するには受け取り口の切り分けが要る。**重複 key の拒否は、子が書いた成果物と
evidence payload に対しては維持し、Codex CLI が自ら吐く stdout event 行に対しては
異常として記録するに留めて attempt を落とさない。** 成果物の中に重複 key があれば今も落ちることを
負例テストで固定する。落ちた理由を receipt へ書く実装 (F263 の案 1) を同じ変更単位に含める。

**理由:**

- 禁止は方針ではなく道具側の不具合が原因である。Codex CLI の `web_search` event は同一 object 内に
  `id` を 2 個持ち、`orchestrator/codex_roles/events.py` の `_pairs_without_duplicates` が
  重複 key を拒否するため `stdout_invalid` が立ち、成果物が完全でも attempt ごと捨てられる
  (F259 / F263)。実費は 848 秒 / 43 call、1242 秒 / 38 call、2668 秒 / 入力 920 万 token 相当。
- **拒否を緩めるのではなく、拒否の定義域を正す。** 壊れているのは子の仕事ではなく外部の道具の
  telemetry であり、それを evidence の破損として扱うと成果物を守るどころか破壊する。
  成果物側の健全性検査は 1 つも緩めない。
- 許可だけを入れて受け取り口を直さないと、子は検索を使うたびに全損する。方針と機構を同じ
  変更単位で扱う必要がある。

**却下した選択肢:**

- **段ごとに既定無効にする (F263 の案 2)** — 本裁定と正面から反対向きである。
- **重複 key の拒否そのものを外す** — 成果物側の健全性検査を緩めることになり、規律 2 の面に触れる。
- **許可だけを docs へ書く** — 機構が伴わないので子は全損し続ける。

## {{D:ccbench-pin-hold}}. CCBench の pin は据え置き、branch 宣言の是正だけ先行する

**決定 (ユーザー裁定):** CCBench submodule の pin は**据え置く** (案 A)。
SS2PL の SIGSEGV は既存の out-of-tree patch で扱い続ける。
`.gitmodules` の branch 宣言の是正は、pin の可否と切り離して先行してよい。

**理由:**

- 取り込むと `orchestrator/campaign/source_digest.py` の静的 CMake parser が
  `${SS2PL_DLR_MARKER}` の変数参照を解決できず fail-closed で止まる。D297 の pin 前進 gate だけでなく
  **本番 campaign 経路も止まる** (実測: 現行 pin は OK、取り込み後は RuntimeError)。
- 選択的 backport は成立しない。SIGSEGV を直す #122 は #121 が入れた guard を外すだけの commit で、
  #121 抜きでは cherry-pick が競合する (実測)。そして #121 が blocker を持ち込む。
- 現行の critical path は Silo 系であり SS2PL ではない。SS2PL の探索は現 pin と patch で現に回っている。
- **D790 が同じ費用を根拠に同じ選択をしており、本 wave の実測はその費用が実在することを裏づけた。**
  既裁定を覆す新事実は見つかっていない。
- `.gitmodules` の `branch = izanagi-trace` は upstream で旧 pin を指しており、
  `git submodule update --remote` を実行すると pin が 1 世代巻き戻る。宣言の誤りは pin の可否と
  直交するので、独立に直してよい。

**却下した選択肢:**

- **案 B (SS2PL の修正だけ izanagi 側へ持つ)** — blocker は踏まないが上流との差分が恒久化する。
  「SIGSEGV を今すぐ直したい」実需が生じたときの最小手として残す。
- **案 C (条件を満たして取り込む)** — 前提が 10 件あり、うち C-1 (parser の組合せ文脈への再設計) が
  未解決である。C-1 は pin と独立に価値があるので、先に別 wave で解いてから再提起する。
- **master 直行** — master の `cc/silo/` に trace 関連 file が無く `CCBENCH_TRACE` が消えるため、
  絶対規律 1 (D14) と規律 3 の土台を壊す。実測で落ちている。

## {{D:acceptance-runner-binding-hold}}. 受入の実行器束縛は外さず、材料を運ぶ変更を先に通す

## {{D:acceptance-duration-ledger-pin-split}}. 受入所要台帳は担い手を land 側に置き、pin を 2 種へ分ける

**決定 (ユーザー裁定):** 受入所要台帳の定期更新の担い手を **land 側**に置く。
逐語 pin は緩めるが、緩め方を 2 つに分ける。**所要値は性質述語** (有限・非負・上限内など) へ、
**node 集合は基準時点に対する exact identity** を保つ。

**理由:**

- 網羅率が 90% を割ると全 wave が同時に land 不能になるのに、閾値を割った時点で誰が直すかの
  取り決めが無かった。実際、無関係の wave が偶然踏んで直している。
- 所要値の exact pin は測定機の個体差を assert する型である。同一 tip・同一選択の 2 走で
  直列総仕事量が 1.40 倍動いた実測があり、陳腐化が分母の大きさに隠れる。
- **「delta の向きだけ」へ一律に緩めるのは弱すぎる。** 件数を保存する入れ替えや、
  消えた node の復活を検出できなくなる。T-1574 が守っていた検出力が落ちる。
  所要値と node 集合は性質が違うので、同じ緩め方を当てない。

**却下した選択肢:**

- **pin の対象を delta の向きだけへ絞る** — 当初の親推奨だったが撤回した。置換検出を失う。
- **丸ごと再生成する** — exact pin を壊す。緩め方を決めてからでないと同じ問題を繰り返す。
- **現状維持** — 凍結部分が更新できないまま陳腐化し、次に閾値を割ったときも担い手が居ない。

## {{D:env-coincidence-static-gate-not-added}}. 環境の偶然を assert する検査へ静的な件数関門は置かない

- 却下理由のうち再現性の部分が解消したことは事実だが、それは別の理由 (件数 pin の型としての
  危うさ) を打ち消さない。

**却下した選択肢:**

- **件数を pin する test を置く** — 環境の偶然を assert する型の再生産になる。

## {{D:axis1-dblp-branch-declarative-exclusion}}. 索引の構文能力による不可能は宣言的に除外してよい

**却下した選択肢:**

- **補助探索を除外枝の代替として算入する** — 事前登録した式で覆った、と言えなくなる。

## {{D:archive-name-exemption-recorded-not-closed}}. archive 名の免除路は閉じず、限界として記録する

**決定 (ユーザー裁定):** D1054 が閉じなかった archive 名の免除路
(先頭ゼロ付き 2 token の日付範囲形に entry の H2 を入れると、その archive の entry が
全域 universe に入らない) は**閉じない**。既存の免除路として記録に留める。

**理由:**

- D1054 自身が「本改訂では閉じない」と残余と先行依存を明記している。本決定はそれを追認する。

## {{D:unreachable-land-verifier-removed}}. land の到達不能な非帰属専用検証枝は撤去する

**決定 (ユーザー裁定):** land 側に残る到達不能な `non-attributable-only` 検証枝を**撤去する**。

**理由:**

- 正規の待ち手では生成できない受領証を検証しており、発火経路が無い。
- 到達不能な検査を残すと「検査している」という誤読を作る。恒真ゲートの型である。
- 撤去は受理集合を縮める方向であり安全側である。

**却下した選択肢:**

- **残す** — 到達不能な legacy verifier が誤読を生み続ける。

## {{D:flaky-hold-evidence-id-placeholder}}. 未採番の新種赤は placeholder 表記で hold 登録してよい

**決定 (ユーザー裁定):** `flaky_test_holds.py` の `evidence_id` に、
`reintroduction_task_id` と同じ **placeholder 表記を許す**。着地時に実 F 番号へ置き換わることを
検査で固定する。

**理由:**

- 現行は `^F[0-9]+$` かつ `docs/failures.md` に実在することを要求するが、F 番号は land 時の fold で
  しか生まれず、fold には緑の受入が要る。**同一 wave 内で新種の赤を hold 登録できない循環**がある。
- `reintroduction_task_id` が既に placeholder を許しており、同じ扱いへ揃えるのが素直である。
- 受理集合は広がるが、広がるのは「まだ番号の無い赤」だけで、着地後に実番号へ解決されることを
  検査で縛れる。

**却下した選択肢:**

- **fold と hold の順序を変える** — 着地の手順全体に触れる。
- **現状維持** — 新種の赤を踏んだ wave がその場で詰む。

## {{D:floor-budget-approval-user-turn}}. 床値 official の予算承認文書はユーザー手番として残す

**決定 (ユーザー裁定):** 床値 official 経路の残る閂は
`output/s8b-freeze-budget-approvals/g1.json` の**人間による承認**だけである。
AI が起草してユーザーが確認する形とし、**AI は自分を承認者にしない**。

**理由:**

- 依存していた 2 件は D964 / D979 で、§8 承認束縛は D926 で既に裁定済みである。残りはこの 1 件。
- 承認者を AI にすると「弱化した本人が承認する」形になり、D526 が却下した構造と同型になる。

**却下した選択肢:**

- **AI が承認文書を完成させる** — 承認の意味が消える。

## {{D:rescue-secondary-storage-user-designates}}. 救出物の二次保管先はユーザーが指定する

**決定 (ユーザー裁定):** D1030 の「AI は保管先を選ばない」を維持する。
共有ファイルシステムの 2 か所は同一のストレージサーバ群を指すと実測済みであり、
真に別の故障単位はこの計算機の外にある。**保管先の指定はユーザー手番のまま残す。**

**理由:**

- 保管先の選定は運用者の権限である (D1030)。
- 実測により、この計算機の中では故障単位を増やせないことが確定した。
