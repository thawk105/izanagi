## {{D:study-env-parity-toward-production}}. 対測定 driver の環境不等価は「本番へ寄せる」方向でだけ閉じる

**決定:** 作業用複製の環境が本番受入の計算ノード子と食い違う箇所は、
**本番側の値・形へ寄せて**閉じる。driver 側の都合で本番の振る舞いを変える方向は採らない。
走ごとの隔離が必要な項目 (HOME / XDG) だけは隔離を残し、
**残した非等価を受領証へ明示する**。

**理由:**
- 測りたい量は「本番受入 shard の所要」である。driver が本番より速い / 遅い条件で測ると、
  worker 数の効果に環境差が混入する。実測でも一時領域を `/scr` から本番と同じ `/tmp` へ
  移す前後で、小 file 書き込みが約 2.4 倍違った。
- 「本番と等価」と書けない項目を黙って残すと、受領証の読み手が射程を誤る。
  隔離を残す判断そのものは内部妥当性のために正しいので、消すのではなく**書く**。

**却下した選択肢:**
- 走ごとの隔離を全廃して本番と literal に同一にする — 42 走が同じ実 HOME を順に使うため、
  cache 暖まり・create-only 残置・lock・他 session の書込みが混ざる。汚染の向きが一意でなく、
  worker 数以外を固定するという内部妥当性が壊れる。
- 不等価を残したまま「本番等価」と書く — 受領証の射程を偽る。

## {{D:study-isolation-attribution-by-descent}}. 単独性の帰属は process group でなく子孫関係と job 固有 path で行う

**決定:** 測定中の外乱判定で「自分のもの」と見なす条件を、
(1) process group が exempt、(2) 過去の標本で自分と判定済み、(3) 親が自分と判定済み、
(4) cwd / exe が job 固有 root 配下、(5) command が job 固有 root を含む、の論理和とする。
外乱は「自分のものでない」かつ CPU 消費があり、かつ system account でない process とする。

**理由:**
- 受入 suite は正当に多数の process group を作る (oracle が CPU 制限のため別 session を作る、
  入れ子 pytest、git の自動 gc が daemon 化する)。process group 2 つだけを身内とする規則は
  **自分の workload 70 件を外乱と誤認**した。
- cgroup と session id は使えないことを実測した。この計算環境の job scheduler は job ごとの
  cgroup を作らず、全 process が同じ service cgroup を共有する。`setsid` した子は自分の
  session id を持つ。
- 親子関係の閉包だけが、cmdline を読めない短命 process も分類できる。daemon 化して親子鎖が
  切れる process は job 固有 path で拾う。
- 外乱の uid 条件を「自分と同じ uid」から「system account 以外」へ広げると、
  **他人の job を検出できるようになる**。従来は原理的に検出できなかったので検出力は純増する。

**却下した選択肢:**
- cgroup による帰属 — 実測で job を区別できない。
- 読めない process を安全側で外乱と見なす — 短命 process は常に存在するため常に赤になる。

## {{D:study-shard-budget-proportional}}. arm の時間予算は shard の実測所要へ比例配分する

**決定:** arm の制限時間を shard へ均等に割るのをやめ、
**較正走で実測した shard ごとの所要に比例**して配る。arm の総予算と導出規則は変えない。

**理由:**
- 2 つの shard の仕事量は均等でない (実測で shard 0 は shard 1 の約 2 倍)。均等割りは
  arm 全体の余裕を軽い shard へ寄せてしまい、**3 つの arm すべてで重い shard の配分が
  自分の実測所要を下回った** (-1.9% / -11.5% / -11.3%)。
- 予算不足で殺された shard は本物の時間超過と区別できない。どの arm が完走するかが
  仕事量ではなく配分の歪みで決まり、測定妥当性が壊れる。
- 比例配分にすると 3 arm とも両 shard の相対余裕が一致する (実測で +20.7〜21.0%)。

**却下した選択肢:**
- arm の総予算を増やす — 歪みの原因は総量でなく配分なので解決しない。
- 重い shard を先に走らせて残余を軽い shard へ渡す — 順序の交絡を持ち込む。

## {{D:study-bounded-retry-of-red-cells}}. 赤で終わった測定セルは上限付きで測り直し、記録値は緑の走行からだけ取る

**決定:** 測定走が赤で終わったとき、同じ (block, arm, shard) セルを上限付きで測り直す。
受領証と解析へ入る値は**すべて完全に緑の走行**から取り、捨てた走行は
セル・試行番号・落ちた nodeid とともに受領証へ残す。上限はセル単位と study 全体の
両方を持ち、既存の予算構造から導く。時間超過・JUnit 不在・rc=0 の赤は測り直さず即座に止める。

**理由:**
- 受入 suite には「守りたい性質」でなく環境の偶然 (絶対 wall-clock、hook 実行順序、
  fd 番号) を主張する検査が実在し、実測で約 15%/走の非決定的な赤を生んだ。
  42 走すべての緑を要求する設計では通し切る確率が 0.1% 未満になる。
- 個別の検査を直すのが本筋であり実際に 5 件直したが、静的走査では同種の候補が
  244 箇所 / 68 file あり、尾は数十件規模である。個別修正の完了を待つ設計にはできない。
- 測り直しは正しさの関門を緩めない。記録される測定値は依然としてすべて緑の走行のものであり、
  本物の回帰は 2 回とも落ちる。捨てた走行を受領証へ残すので、読み手が回数を判断できる。

**却下した選択肢:**
- 既知のフレークを登録して受入の既定集合から外す — 本番受入の受理集合を変える判断であり、
  独立の evidence 要件を持つ。測定の都合で決めてよい範囲を超える。
- 赤を含む走行の所要をそのまま採用する — 走った作業量が変わるため比較できない。
- 時間超過で殺された走行も測り直す — それは環境のフレークではなく設計不備の兆候であり、
  隠すと予算配分の欠陥を見逃す (実際に 1 度起きた)。
