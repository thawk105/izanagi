## {{D:b10-adaptive-state-coverage}}. backoff の帯域外拡張は「適応機構の全離散状態を静的点で覆う」を目標にする

**決定:** 静的 backoff の計測格子を広げる目標を、任意の上限値ではなく
**適応機構が取りうる離散状態の全被覆**として定義する。CCBench の適応 backoff は
`kMinBackoff=0` / `kMaxBackoff=1000` / `kIncrBackoff=100` なので、状態は
`{0, 100, 200, ..., 1000}` の 11 個である。拡張格子はこの 11 個をすべて含む。
旧格子 `[2, 5, 10, 25, 50, 100]` はこのうち 100 の 1 つしか含んでいなかった。

確定した格子は次の 29 点とする。既存 6 点を包含し、同一環境・同一窓で旧帯と新帯を
同じ座標系へ載せるため既存点も測り直す。

```
0, 1, 2, 3, 4, 5, 6, 8, 10, 12, 15, 20, 25, 35, 50, 75, 100,
150, 200, 250, 300, 400, 500, 560, 600, 700, 800, 900, 1000
```

**理由:**
- 上限の根拠が実装上の定数になり、恣意的な数を選ばずに済む。「可動域を覆った」という
  主張が literal に検査できる (`{0,100,...,1000} <= set(格子)`)。
- 低域 (1〜12) を密にしたのは、既知ピークが read-heavy=2 / balanced=5 / write-heavy=10 と
  **3 つとも 10µs 以下**だからである。「10µs より上へ延ばす」だけでは 3 workload の
  ピーク位置が決まらない。手段より目的を優先した。
- 静的 0 は `BACK_OFF=1, BACKOFF_FIXED=0` であり、呼び出し自体が起きない無 backoff とは別の点である。
  適応の下端状態を覆うために必要で、副次的に呼び出し overhead と待ち量を分離する。
- 560 を残したのは、spin 占有率から相当値として挙げられてきた歴史的な点への接続のためである。

**却下した選択肢:**
- 旧 `SWEEP_US` を書き換えて拡張する — 値が凍結 golden に張られており、
  実 campaign から集めた静的点集合との完全一致も要求される。既存 3 campaign の identity と
  report 経路も壊れる。別 slug の新 campaign にした。
- 上限を 800µs にする — 適応の上限 1000µs を跨がず、可動域の全被覆にならない。
- 「1〜1000µs を疎な点で span した」と主張を弱める — 離散状態を全部埋める費用が
  1 workload あたり 8 genome 分の追加でしかなく、主張を弱めるより測る方が安い。

## {{D:b10-claim-boundary-fields}}. 記述的な性能地形の主張境界は D496 の 2 項を分けて記録する

**決定:** 対測定契約の下にない記述的な性能計測の成果物には、主張境界として次の field を固定する。
`paired_under_D496` のような単一の真偽値は**使わない**。

- `paper_gain_eligible: false`
- `same_campaign_contrast: true` — D496 の第 1 項 (比べる構成をすべて同じ campaign の中で測る) を満たす
- `prereg_frozen_comparison_rule: false` — 第 2 項 (比較規則・構成集合の事前登録) を満たさない
- `estimand_matches_paper_headline: false`
- `claim_scope: descriptive_backoff_shape_only`

同じ値を人が読む Markdown 側で別の literal として持たず、**判定 JSON から生成する**。

**理由:**
- 同一 campaign 内で全構成を測る計測に `paired_under_D496: false` と書くのは実態と逆で、
  「D496 を満たさない」という誤った理由づけが下流へ伝わる。利得率に使えないことと
  D496 非該当は別の命題である。
- Markdown 側を別 literal にすると、人が読む側だけを書き換えても検査が赤にならない。
  実際、統合前の実装がその形になっていた。

**却下した選択肢:**
- 単一の `paired_under_D496` を残して値だけ直す — どちらの項を満たすかが消え、
  下流が理由を再構成できない。
- 主張境界を人手の約束にする — 検査で固定できない。

## {{D:b10-diagnostic-binding}}. 診断計装の走行は certified な対応点への機械的束縛を必須にする

**決定:** `ADD_ANALYSIS=1` のような診断計装下の走行は certified ではない。成果物には
`certified: false` と `diagnostic_only: true` を**値単位で**固定し、さらに
**同じ campaign 内で committed かつ certified になった非計装の対応点**
(flags が計装フラグを除いて完全一致する genome) の variant id へ機械的に束縛する。
対応点が存在しない、または certified でない診断点が 1 つでもあれば fail-closed で停止する。
診断由来の値を性能判定・利得率に使わないことを、診断値を任意に変えても判定が不変であるテストで固定する。

消費側でも同じ照合を行う。参照先 id の所属だけを見る実装にしない — workload、campaign id、
全 flags まで照合する。

**理由:**
- 診断計装は throughput を歪めるので、その値で性能を主張できない。一方で走行そのものを
  certified にすると計測費用が跳ね上がる。束縛と明示記録なら、主張の範囲を狭めたまま安く済む。
- 消費側が参照先の所属しか見ていないと、別 workload・別 campaign の診断行を差し替えても受理される。
  実際に入力変異で受理されることを確認した。producer 側の照合だけでは足りない。

**却下した選択肢:**
- 診断 genome 自体を verifier に通す — 計測が約 4 割伸びる。診断値に依存する主張が無いので
  費用に見合わない。**ただしこれは裁定パッケージとしてユーザーへ返す** (下記)。
- 現状どおり束縛なしで診断値を出す — 別 campaign の値が混ざっても検出できない。

**この wave で scope 外とし、裁定パッケージとしてユーザーへ返す項目:**
1. 診断 genome 自体の verifier 通過を必須にするか。
2. 適応 backoff の要求 µs を直接計装する診断 patch (D16 第 5 類) を作るか。
   spin 占有率は呼び出し回数と待ち量の積で逆写像を持たないため、現状は推定しかできない。
3. 現行環境・workload 別の between-block 床値を実測するか。判定床 0.030 は
   旧環境の write-heavy / balanced 由来で read-heavy を含まない。
4. 逆順ブロックによるピーク・開始点の再現確認を行うか。
5. 凍結成果物の bytes 照合が hold されている状態を解除するか。
