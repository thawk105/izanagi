## {{D:retire-enforcement-source-ratification}}. enforcement source closure の批准突き合わせを廃止する

**決定:** campaign 初期化時に、enforcement source closure の digest を `hooks/` 配下の
批准済み集合と突き合わせて一致しなければ拒否する、という関門を廃止する。D526 が定めた
この関門はもう発火しない。**ユーザーの決定である。**

記録はやめない。contract loader の commit ID と path→blob digest map は従来どおり受領証と
lock に残す。disk bytes と記録 commit blob の自己整合検査、記録 commit blob と記録 digest の
照合、activation tuple の真正性検査も残す。**やめるのは、批准集合との照合による拒否だけである。**

**理由:**
- ユーザーの逐語 (2026-08-27、字句無改変)。

  > なんかその突き合わせ？廃止でいいよ。私何度も言ってなかったっけ？トップジャーナルで
  > 「この文字列で実行したプログラムで測った性能です。」なんて厳密な束縛見たことないって。
  > 参考程度にビルドに必要な情報やビルド時点のコミットIDとか測定時点情報を載せておくのは
  > 良いけど。一定時間以降誰にも性能測定ができなくなってしまうルールに囚われている？
  > 不必要だねそんなものは。

- 性能主張に必要な provenance の粒度は粗いもので足りる。ビルドに必要な情報、ビルド時点の
  commit ID、測定時点の情報を参考として残せば十分であり、「この bytes で実行した」という
  byte 級の厳密な束縛は論文の主張が要求する水準を超えている。
- 批准は closure の版ごとにしか効かず、25 path のどれか 1 つが動くたびに新しい人間の批准行を
  要する。並行 wave が日常的にこの 25 path を触る以上、**批准行を書いた瞬間から古くなる。**
  実際、台帳は 2026-08-25 02:59 に 1 行で開設されたが、その行は開設の 4 時間前に既に古く、
  以後 4 commit が更に closure を動かした。結果として 2026-08-24 23:00 以降、main では
  certified campaign の新規初期化が誰にも出来ない状態が続いた。
- **一定時刻以降は誰も性能測定を開始できなくなる、という帰結を持つ関門は不要である。**
  この帰結は運用の失敗ではなく、批准単位 (closure 版) と変更頻度 (日次) の比から
  構造的に生じるものであり、運用を丁寧にしても解消しない。
- D526 が守ろうとした脅威 (verifier を弱化して commit すれば、その bytes が新しい正規として
  記録される) は残る。**この決定はその防壁を捨てる。** ただし verifier 本体・anomaly 判定・
  trace 分離・観測者効果の分離には一切触らないため、正しさの判定そのものは変わらない。
  規律 2 の中核 (anomaly を検出した variant を即 reject する) は不変である。

**却下した選択肢:**
- 批准行を都度追記して運用で回す — 批准と land の競走であり、書いた瞬間から古くなる。
  AI が追記すれば「弱化した本人が批准する」形になり、D526 自身が却下している。
- 批准単位を path ごとにする — D526 が却下済み。個別には批准済みでも組合せとして
  未審査の closure を作れる。
- 関門を残したまま campaign 側で迂回する — 迂回経路は関門より弱い保証しか与えず、
  関門があるという見かけだけが残る。廃止するなら明示的に廃止する。
- **批准行の発行を署名で機械化する** — 「誰が批准行を書くか」を人手から鍵へ移すだけで、
  **closure が動くたびに新しい批准が要る**という構造は変わらない。ユーザーが不要と述べた
  帰結 (一定時刻以降は誰も測定を開始できない) は批准単位 (closure 版) と変更頻度 (日次) の
  比から生じるものなので、鍵管理を替えても解けない。
