## {{D:retire-enforcement-source-ratification}}. enforcement source closure の批准突き合わせを廃止する

**決定:** campaign 初期化時に、enforcement source closure の digest を `hooks/` 配下の
批准済み集合と突き合わせて一致しなければ拒否する、という関門を廃止する。D526 が定めた
この関門はもう発火しない。**ユーザーの決定である。**

記録はやめない。contract loader の commit ID と path→blob digest map は従来どおり受領証と
lock に残す。disk bytes と記録 commit blob の自己整合検査、記録 commit blob と記録 digest の
照合、activation tuple の真正性検査も残す。**やめるのは、批准集合との照合による拒否だけである。**

**理由:**
- ユーザーの逐語 (2026-08-27、字句無改変)。

  > なんかその突き合わせ？廃止でいいよ。私何度も言ってなかったっけ？トップジャーナルで
  > 「この文字列で実行したプログラムで測った性能です。」なんて厳密な束縛見たことないって。
  > 参考程度にビルドに必要な情報やビルド時点のコミットIDとか測定時点情報を載せておくのは
  > 良いけど。一定時間以降誰にも性能測定ができなくなってしまうルールに囚われている？
  > 不必要だねそんなものは。

- 性能主張に必要な provenance の粒度は粗いもので足りる。ビルドに必要な情報、ビルド時点の
  commit ID、測定時点の情報を参考として残せば十分であり、「この bytes で実行した」という
  byte 級の厳密な束縛は論文の主張が要求する水準を超えている。
- 批准は closure の版ごとにしか効かず、25 path のどれか 1 つが動くたびに新しい批准行を
  要する。並行 wave が日常的にこの 25 path を触る以上、**人が 64hex を台帳へ転記する形では
  批准行は書いた瞬間から古くなる。** 実際、台帳は 2026-08-25 02:59 に 1 行で開設されたが、
  その行は開設の 4 時間前に既に古く、以後 4 commit が更に closure を動かした。
  結果として 2026-08-24 23:00 以降、main では certified campaign の新規初期化が
  誰にも出来ない状態が続いた。
- **一定時刻以降は誰も性能測定を開始できなくなる、という帰結を持つ関門は不要である。**
  なお、この帰結そのものは転記をやめれば解ける — 起動直前に digest を計算して署名で
  追記する broker があれば、批准と起動の窓は数分になる。**廃止の判断はその点に依存しない。**
  依存しないのは次の理由による。上の逐語が不要と述べているのは blockage だけでなく
  **束縛そのもの**であり、bytes 級の束縛は論文の主張が要求する粒度を超えている。
  起動のたびに人の承認を要求する形は blockage を解くが、超過した粒度は解かない。
- D526 が守ろうとした脅威 (verifier を弱化して commit すれば、その bytes が新しい正規として
  記録される) は残る。**この決定はその防壁を捨てる。** ただし verifier 本体・anomaly 判定・
  trace 分離・観測者効果の分離には一切触らないため、正しさの判定そのものは変わらない。
  規律 2 の中核 (anomaly を検出した variant を即 reject する) は不変である。

**却下した選択肢:**
- 批准行を都度追記して運用で回す — 批准と land の競走であり、書いた瞬間から古くなる。
  AI が追記すれば「弱化した本人が批准する」形になり、D526 自身が却下している。
- 批准単位を path ごとにする — D526 が却下済み。個別には批准済みでも組合せとして
  未審査の closure を作れる。
- 関門を残したまま campaign 側で迂回する — 迂回経路は関門より弱い保証しか与えず、
  関門があるという見かけだけが残る。廃止するなら明示的に廃止する。
- **批准行の発行を署名 broker で機械化する (D905 が命じ、別 wave が実装済み)** —
  起動直前に digest を計算し承認を取って署名追記する形なので、**転記に由来する陳腐化と
  blockage は解ける。** それでも採らないのは、逐語が不要としているのが blockage だけでなく
  束縛の粒度そのものだからである。起動のたびに人の承認を要求する形は、超過した粒度を
  維持したまま人の手数を足す。
- **本決定が実効を奪う既裁定 (すべてユーザー裁定)。** いずれも機構の存続を前提としており、
  本決定はそれらより後のユーザーの明示的な発話に基づいて機構そのものを廃止する。
  - **D905** — 批准の執行は AI が成りすませない実行主体の新設だけを採る、設計が着地するまで
    批准は進めない。本決定はその主体を作らずに批准概念ごと撤去するので、**D905 の明示的な
    上書き**である。命じられた実行主体は今後も作らない。
  - **D1039** — 既存 lock からの resume で批准を再検査しない挙動を穴として塞ぐ。
    批准 verifier が無くなるため**実装不能**になり、実効を失う。
  - **D1070** — 批准検査を artifact 受入と dispatch へ広げる。同上。
  - **D1071** — 批准の撤回を行削除でなく撤回記録で表す。撤回対象が無くなるため同上。
- **同じ blockage に対する既存の解決手段 (D1028 / D1038) を採らない理由。**
  D1028 と D1038 は、批准 authority を持たない**非認証成果物型**と投入器を同じ変更単位で作り、
  昇格不能性を全層で固定することで停止を解く、と定めている。**認証経路の関門を維持したまま
  停止を外す設計であり、blockage だけを見るならこちらが正しい。** 本決定がそちらを採らないのは、
  上の逐語が不要としているのが blockage だけでなく**束縛そのもの**だからである。
  非認証成果物型は、bytes 級の束縛を認証経路に残したまま、その外側へ別系統を足す。
  廃止はその束縛自体を畳む。**両者は排他ではない** — 非認証成果物型が独立に有用なら、
  本決定はその実装を妨げない。
- **凍結成果物への影響 (実測)。** closure の path 数が 25 から 24 へ減るため、
  `campaign_verifier_epoch` の `identity_scope` 説明文字列が変わる
  (`exact 25 path; ...批准比較...` → `exact 24 path; ...`)。
  `docs/paper-story/figures/fig4_s1a_9pair_direct_comparison.provenance.json` は前者を
  焼き込んでおり、`test_s1_9pair_figure_provenance` が食い違いを検出する。
  **epoch の値そのもの (`E0` / `v1-authority-absent`) は 4 campaign すべてで不変**であり、
  計測の実体と受入判定は変わらない。変わるのは説明文字列だけである。
  したがって本決定の実施には、当該 provenance の再生成 (凍結成果物の bytes 変更) が伴う。
