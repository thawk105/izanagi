**決定 1:** D1539 は有効・未実装のまま、この wave では実装しない (択 E)。字義どおりの実装 (`orchestrator/tests/test_ccbench_spawn_sites.py` の `_sink_macro_reachability` で、
buildcache / campaign の設定式が引数依存なら不在 macro を `unresolved` にする) は、16 sink・929 セルを `proven-unreachable` から外し、
うち 12 sink・715 セルを failure にする (親の実測、コード無変更の計算と一時実編集の両方で一致)。12 sink・715 セルのすべてを本題の範囲内で解消する案は、段 2 plan・段 3 相談 2 本のいずれも組めなかった。繰延べ台帳 12 entry や呼び手を含む閉包証明器は、
依頼の「これ以外の gate・検査・台帳・一般化の追加は scope 外」に当たる (S1 の flag 一致検査のように本題の一部と読める処置はあるが、その対象は s1 の 57 セルで、解消することは実装・実測していない。残る 11 sink・658 セルにも処置が要る)。
止める理由は scope と全緑の衝突であって、到達不能を証明したからではない。
再開の受入条件は、判定変更と同じ wave で 12 sink それぞれの処置を本題として行うことが認められること。資料は `output/insights/2026-09-27/t2207-closure-unresolved/README.md`。

**決定 2:** 同じ依頼の (2) [T-2344] 次段と exact-85/96 の再走査・撤去、(3) [T-734] 全 certified sink への source gate、[T-733] の 69 module の整理は、この wave で実行しない。

撤去の向きを推測で実行しない。ユーザーへ 1 問で確かめる。

**理由:**
- 「18 セル」(D1539・[T-2207] 本文) は 2026-09-02 の s1 sink 1 本だけの数 (patch 追加 define 22 個) で、現行 (61 個) は s1 だけで 57、全体で 929。
  D1502 は同日に「900 件以上」と既に書いていた。D1539 の提示が挙げた影響の規模と、実装に要る処置の規模が違う。
- 12 sink の多くは macro 名を同じ file の生成関数が固定しており、既存の引数依存判定は開放性の判定として過剰である。
  今回、未閉包の具体的な入力列を示せたのは S1 の `prepare_cell_fn` 注入口 (返却 genome の全 flag と freeze cell の flag を照合しない) だけで、静的検査の穴だが成果物の値が変わった実証は無い。
  他の sink も呼び手・policy を含めた閉包を証明したわけではない。
  P3 の stock 経路の JSON は flags の鍵を 4 つに完全一致させており閉じている (段 2 plan の誤りを段 3 相談 A が訂正)。
- 2 つのユーザー指示が同じ対象で食い違ったときは推測で片方を選ばない (2026-09-21 の fig9b の先例と同じ扱い)。

**却下した選択肢:**
- 字義どおり実装し赤のまま置く — 受入が通らず land できない。テスト期待値の反転・skip は規律 2 に反する。
- 12 sink を繰延べ台帳に載せる — 依頼が除いた台帳の追加。所有する稼働 wave も無く、lineno pin が以後の編集ごとの追随を生む。
- 別分類で数えて failure にしない — D1539 の「受理集合を狭める向き」に反する。
- 依頼の方が後なので (2)(3) を実行する — 依頼文が D2260 以前の提案の写しである可能性を排除できず、撤去は D2260 が起こさないと決めた向きである。
  最も強い反対論 (後の直接依頼を無効扱いにできない) は、実行しない根拠を「依頼は無効」から「推測で選ばない」へ改めることで受けた。
