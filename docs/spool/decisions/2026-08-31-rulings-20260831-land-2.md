## {{D:axis1-root-scope-two-classes}}. 消える根の根相対化は実測した 2 クラスへ広げる

**決定 (ユーザー裁定):** compiler input manifest の根相対化は、D1192 が名指しした build cache の
作業用 directory (31 件) だけでなく、job 専用作業領域 (7 件) にも適用する。

**ただし束ねる前に D1192 の統合条件を満たすこと。** 同 D は「同じ赤を報告している別 wave の項目とは、
同一の cache entry・同一の拒否述語・同一の descriptor・同一の是正 3 択であることを実測できた
場合にだけ 1 件へ束ねる」と定めている (F151 の再発防止)。この照合を先に実測で示してから広げる。

**理由:**

- 1 クラスだけ根相対化しても床値実測の主経路は赤のまま残り、D1192 の目的を果たさない。
- 2 クラスは同じ manifest の同じ消失であり、是正も同じ「絶対 path から根相対へ」である。
- 同じ本文の失敗であることは同一性の根拠にならない。だから照合を省かず、条件を満たしたうえで広げる。

**却下した選択肢:**

- 裁定文どおり 1 クラスだけ直す — 主経路が赤のまま残り、次の wave が同じ赤を再発見する。
- 照合せずに 2 クラスを束ねる — D1192 が F151 の再発防止として明示的に禁じた形になる。

## {{D:a1-dirty-source-rejected}}. A-1 の対測定は出所を確定できない作業ツリーを受理しない

**決定 (ユーザー裁定):** A-1 の対測定は、未コミットの変更を含む CCBench 作業ツリーを受理しない。
**判定の基準は commit ID が確定できるかどうかに置き、bytes 級の同一性検査は新設しない。**
submodule の無視設定で親側の状態確認を素通りする経路と、許可リスト内の汚れた source が
生成器の受領証を経由して有効な A-1 入力になる経路の両方を塞ぐ。再凍結と同じ変更単位で行う。

**理由:**

- 測定対象の source を後から特定できないと、A-1 が何を測ったかを論文で言えない。
- D1139 のユーザー方針は「ビルドに必要な情報とビルド時点の commit ID があれば足り、
  bytes 級の厳密な束縛は論文の要求水準を超える」である。commit ID の確定可能性を基準に置けば、
  この方針を破らずに出所を同定できる。

**却下した選択肢:**

- 現状のまま受理し記録だけ残す — A-1 が測った対象を後から特定できない。
- bytes 級の同一性検査を新設する — D1139 が不要と裁定した水準へ戻る。

## {{D:b4-model-snapshot-declaration}}. B-4 の model snapshot 欄の 4 点を確定する

**決定 (ユーザー裁定):** D1307 が値記入の前に固定するよう求めた 4 点を次のとおり確定する。

- **宣言源:** ユーザーの直接指名。実行結果・fixture・試し打ちのいずれにも依存しない。
- **承認する人間の識別子:** tanab。
- **宣言の時点:** 欄を記入する commit の日付。
- **観測 slug が宣言と食い違ったときの扱い:** 例外で停止する。**宣言を書き換えて同じ実走を
  続けることはしない** (D1307 が明示的に禁じた形)。

指名された名前は `claude-opus-5-1m` である。**実装 wave は欄を書く前に、実 CLI 応答の
`modelUsage` が返す exact slug の表記 (角括弧の有無) を確認すること。** 本 repo の成果物には
`claude-opus-5[1m]` 形の記録が実在する一方、provenance trailer は角括弧なしの表記を使う。
表記が食い違えば上記 (d) により例外停止となり、宣言の書き換えでは解けない。

**理由:**

- 3 期待値のうち projection と prompt は repository の bytes から実走前に確定するが、
  model snapshot だけは確定できないため、宣言源と承認者を人間が定める必要がある (D998 / D1307)。
- 宣言源を定めずに AI が値を選ぶと、結果を見てから宣言を選べる経路になり前向き事前登録の意味が失われる。
- 表記の食い違いは実在する危険であり、記録しないまま実走すると停止の原因が不明になる。

**却下した選択肢:**

- exact slug の指名だけで欄を埋める — D1307 が要求する残り 3 点が固定されない。
- 食い違い時に宣言を書き換える — 実行時照合が拘束でなくなる。

## {{D:floor-selection-residual-g1-only}}. 床値選択の残余は g1 限定で固定し、g2 は実在まで設計しない

**却下した選択肢:**

## {{D:s8c-section5-consumer-upstream-first}}. §5 値 gate の結線は完了証明層の実装後に着手する

**決定 (ユーザー裁定):** 8c 事前登録 §5 の値 gate を本番の処理へ結線する作業は、
**上流の完了証明層 (D1026 が手続きを定めた層) の実装が着地するまで着手しない。**
裁定パッケージが挙げた 4 点は、1 点だけ決めても成立しない相互依存の経路である。

**理由:**

- D959 が「B-2 の閉塞は独立な複数本ではなく層であり、最上流は完了証明層の不在である」と定めている。
  下流を部分結線しても、上流が開かない限り値は使われない。
- 4 点 (report producer の解釈、holdout 別 params、性能行と生値の発行者、出力先と受領証の束縛) は
  一つの consumer 経路として相互依存しており、1 点だけでは観測・束縛のいずれも成立しない。

**却下した選択肢:**

- 主経路に要る 1 本だけ先に結線する — 4 点の相互依存により、その 1 本も成立しない。
- 新しい campaign orchestrator を作って直接呼び出しを要求する — 主目的から遠い大きな実装になる。

**あわせて確認する:** 再着手する wave は、裁定パッケージの README が挙げた「拒否された近道」7 件
(report の入力順を schedule authority として使う、G1/G2 を統計反復 2 と読み替える 等) を
再提案しない。いずれも規律 2 に触れる方向として段 2・段 3・段 4 が一致して拒否した設計である。

## {{D:acceptance-wall-worker-map-declined}}. 受入 wall の worker 対応表は足さない

**決定 (ユーザー裁定):** 受入所要の残差を分解するために report へ nodeid から worker への
対応表を足す案は**採らない**。

**理由:**

- D1298 が、97 秒以上の unit が 10〜11 本並ぶ frontier を形成しており単一 node の短縮では
  makespan が動かないことを実測で確定している。内訳が分かっても打ち手が増えない。
- 研究最優先・防御的堅牢化は既定で見送りというユーザー方針に沿う。

**却下した選択肢:**

- 対応表を足して残差を分解する — 計装 1 本の実装と検査が増え、論文は進まない。

**再訪条件:** 受入 wall が再び実害として観測され、かつ frontier の構成が変わったとき。

## {{D:stale-worktree-lock-user-only}}. 陳腐化した worktree lock の解除はユーザー専任のまま残す

**決定 (ユーザー裁定):** 占有検査が不使用を返し、稼働 process が無く、最終書込から時間が経過した
worktree lock についても、**解除はユーザー専任のまま残す。** 救出 command の正常終端を
「判定 + 記録 + 引き渡し」に改める。

**理由:**

- D754 (ユーザー裁定) が Codex cleanup-branches の安全縮退 7 面をすべて維持すると定めており、
  locked worktree を inventory と report に留める面はその 1 つである。占有検査と経過時間で
  AI の解除を許す案は、この裁定が明示的に却下した「破壊操作の範囲を広げる」向きに当たる。
- 実害は救出が 1 手ぶん遅れることに留まり、所有境界を緩める変更に見合わない。
- 「AI ができる操作をユーザーに投げない」という一般方針は、名指しの既裁定を上書きしない。

**却下した選択肢:**

- 占有検査と経過時間の 2 条件で AI の解除を許す — D754 が維持すると定めた安全縮退を外す。
- lock 理由文字列へ有効期限を書かせる — 新しい書式を 1 つ増やし、同じ推定に依存する。

## {{D:dead-ratification-ledger-removal}}. 廃止済み批准台帳は近接する保守変更へ相乗りして撤去する

**決定 (ユーザー裁定):** D1139 が廃止した enforcement source closure の批准台帳は**撤去する。**
ただし独立 wave は立てず、`hooks/` の防護 path を通る近接した保守変更へ相乗りさせる。

**理由:**

- 台帳は 1 行で、production の consumer は実測ゼロである。残置は廃止済み機構を以後の監査と
  閉包検査の対象に残すだけになる。
- 撤去自体は論文を進めないので、専用の wave を立てる価値はない。

**却下した選択肢:**

- 残す — 廃止済み機構の痕跡が閉包検査に残り続ける。
- 専用 wave で撤去する — 論文に効かない作業に 1 wave を使う。

## {{D:axis1-condition5-needs-missing-id-probe}}. 頁境界重複の条件 5 は distinct 化では閉じない

**決定 (ユーザー裁定):** 索引が同じ work ID を頁境界で 2 回返す場合の取得完全性条件を、
重複を除いた distinct 数へ変える案は**採らない**。**先に欠落の実体を確かめる。**

確かめるのは (a) 返却されなかった別 ID が実在するか、(b) 連続 2 走で集合が安定するか、
(c) 索引側の snapshot drift があるか の 3 点で、その結果を見てから条件 4 と条件 5 の改訂範囲を決める。

**理由:**

- 実行記録の実測は宣言 835・返却 835 行・distinct 834 であり、**distinct 数へ変えても
  834 と 835 が一致せず条件は通らない。** 同時に条件 4 の頁間重複も落ちる。
- 1 件の差が「頁境界の重複」だけで説明できるとは限らず、欠落した別 ID がある可能性が残る。
  原因を確かめずに述語を変えると、取得漏れを重複として片付けることになる。

**却下した選択肢:**

- distinct 数へ変える — 実測上そもそも条件が通らず、取得漏れを隠す危険がある。

## {{D:s8b-budget-hold}}. 8b の予算数値は正式実行後の再凍結まで保留する

## {{D:ruled-items-must-be-restated-in-worklog}}. 裁定済みの項は worklog 本文を更新して裁定待ちから降ろす

**決定 (ユーザー裁定):** 台帳側で裁定が着地した項は、**同じ変更単位で worklog の当該項本文も
「裁定済み → 実装待ち」へ更新する。** 本文を古いまま carry させない。

**理由:**

- 2026-08-31 の全件棚卸しで、**裁定待ちとして索引された項の 10 件が既に裁定済みだった。**
  worklog の項本文が裁定後に更新されず、carry stub が古い「未裁定」の文言を運び続けていた。
- 実害が出ている。同じ棚卸しで、既裁定と**逆向き**の推奨が 3 件起草された
  (署名 token を作らない・送信前固定層を置かない・lock 解除を AI へ許す)。
  台帳を照合して初めて誤りが分かる形は、照合を怠った回にそのまま裁定へ流れる。
- 台帳と worklog の二重管理をやめる案は採れない。worklog は「次の一手」の正本であり、
  台帳は決定の正本で、役割が違う。同期の義務を書く方が安い。

**却下した選択肢:**

- 棚卸しのたびに台帳を全件照合して補正する — 照合を怠った回に誤った推奨が通る。
  実際に 3 件が起草された。
- worklog から裁定状態の記述を消して台帳だけを正本にする — 「次の一手」から優先度と
  状態が読めなくなり、起動時に台帳全体を読む運用へ戻る。
