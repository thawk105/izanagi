## {{D:compute-result-channel-boundary-scope}}. 計算ノードの所有境界は被検査コードとその子孫までとする

**決定:** 計算ノードの結果チャネルの所有境界が守る相手を、親が起動した被検査コードとその子孫に
限定する。名前空間の外にいる同一 uid の別 process は守らない。保証の言い方は
「被検査側は常に書けない」ではなく「被検査側は、親と login 側が読む実体を変更できない」とする。

**理由:**
- 同一 uid の子に対して file system の権限だけでは遮断できない。所有者は mode を戻せ、
  path を列挙でき、親の環境も読める。実効的な遮断は kernel の名前空間でしか作れない。
- 被検査側は自分の mount 名前空間に別の file system を重ねて、自分にだけ見える偽の結果を
  作れる。実測では、それが親の視界へは届かないことを確認した。守る対象は後者だけである。
- 誇張した保証を書くと、実際には守っていない範囲まで守ったことにして次の判断を誤らせる。

**却下した選択肢:**
- 「被検査コードは結果を書けない」と書く — 実測と食い違う。書ける範囲が残る。
- 同一 uid の全 process を守ると宣言する — 別 uid か特権をもつ包みが要る。この変更では作れない。

## {{D:compute-result-ancestor-pinning}}. 結果 directory の祖先はすべて mount point にする

**決定:** 被検査コードの名前空間では、結果 directory を read-only にするだけでなく、
その祖先 directory をすべて自分自身へ bind mount して mount point にする。祖先は書き込み可能な
ままでよい。

**理由:**
- 結果 directory だけを read-only にしても、被検査側は**書ける祖先を rename して同じ絶対 path を
  作り直せる**。実測では偽の結果を置くことに成功し、その効果は名前空間の外にも及んだ。
  login 側が読む先が差し替わるため、所有境界が成立しない。
- mount point 自身の rename は kernel が拒否する。祖先を mount point にすると、どの階層でも
  rename が塞がる。実測で全階層の拒否を確認した。
- 祖先を read-only にする案は、被検査コードが正当に書く先まで塞ぐ。mount point 化だけなら
  中身への書き込みは変わらない。これも実測で確認した。

**却下した選択肢:**
- 結果 directory だけを read-only にする — 上の迂回が残る。
- 祖先を read-only にする — 受入の走行が書けなくなる。
- 結果を repo の外へ移す — 迂回は塞げるが、投入・収集・受領証の path 契約を広範に変える。
  この変更の範囲を超える。

## {{D:compute-child-identity-preserved}}. 隔離しても被検査コードの実行 identity は変えない

**決定:** 名前空間を作るために外側では root へ写すが、被検査コードを起動する内側では実 uid・実 gid へ
写し戻し、capability を落とす。被検査コードから見た identity は隔離前と同じにする。

**理由:**
- 外側の写像のまま起動すると、被検査コードは自分を root と見て capability も持つ。
  実測では uid 31609 が 0 に、capability が 0 から全付与に変わった。
- 実行 identity が変わると、それに依存する既存コードの分岐が変わる。隔離は結果の所有を変える
  ためのものであって、被検査コードの意味を変えるためのものではない。

**却下した選択肢:**
- 外側の写像のまま起動する — 全 task の実行環境が変わる。
- capability だけ落として uid は root のままにする — uid を見る分岐が変わったままになる。

## {{D:scheduler-exit-code-window-too-short}}. scheduler の終了状態は受理条件に使わない

**決定:** D859 が挙げた「scheduler の終了状態との突き合わせ」を、この変更では実装しない。
実測した性質を記録に残し、採否は別の機会に判断する。

**理由:**
- 値は実在する。scheduler の man に wait(2) の終了状態を 16 進で出す欄があり、
  終了コード 7 の試験投入に対して実際にその値を読めた。
- ただし読める窓が終了の前後で約 5〜7 秒しかない。窓を過ぎると request が scheduler から消え、
  照会しても存在しないと返る。会計記録の側には欄が無い。
- 取り逃したときに拒否側へ倒せば、競走に負けただけで正常な走行が赤になる。受理側へ倒せば、
  発火しないことがある検査になり保証として数えられない。どちらも規律に反する。

**却下した選択肢:**
- 欠落も拒否する関門にする — poll の間隔に依存して正常な走行を落とす。
- 取れたときだけ照合する — 発火しないことがある検査を保証として数えることになる。
- 「入力が存在しない」と記録する — 実測と食い違う。値は存在する。
