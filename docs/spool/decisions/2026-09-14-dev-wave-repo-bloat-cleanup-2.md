## {{D:deletion-reference-taxonomy}}. 記録・テストの削除可否は参照を 4 分類してから判定する

**決定:** tracked file や test を削除できるかを判定するとき、「repo 内のどこかに名前が出るか」で
決めない。次の 4 分類へ割り、**現役の拘束的 consumer が無いこと**を削除の必要条件にする。

| 分類 | 判定 | 削除への意味 |
|---|---|---|
| 現役の拘束的 consumer | 実行コードが対象を読む / manifest が path・hash を要求する / 現行 docs が対象内容を根拠として必要とする | 破損・値の変化を解消できなければ削除不可 |
| 非拘束の参照 | 現行コードが名前を保持するが対象の実在を要求せず、消しても残存対象の処理が変わらない | 名前の存在だけでは削除を阻却しない |
| 歴史的言及 | 過去の commit・試験実行・分類結果を記録し、現在の実在を要求しない | 現行対象の存続理由にはならない。記録自体は保存する |
| 未解決 | key→path、glob、hash、動的ロードの関係が未確認 | 「pin あり」「削除可能」のどちらにも断定しない |

`DW-O09` の pin 閉包はこの判定の前提であって代替ではない。path 検索の hit 0 を pin 無しと
結論せず、key 側でも検索する義務は変わらない。

**理由:**

- D1941 が「歴史的な名前の観測だけを現役 pin と同一視しない」と定めているのに、判定側の基準が
  無かった。基準が無いと、archive worklog が名前に触れただけで全対象が削除不能になり、
  掃除が構造的に不可能になる。
- 逆に「参照ゼロなら削除可」も誤りである。証拠は参照されるために在るのではなく、
  記録として在る。絶対規律 7 が守るのは参照数ではなく測定時点の事実である。
- 実際にこの 4 分類を適用しても、記録側で削除可能側へ移った対象は 0 件だった。
  基準を緩めても結論が変わらないことを確認したうえで基準を固定する。

**却下した選択肢:**

- 「参照ゼロ」を単独条件にする — 索引に載っただけで削除不能になり、判定が恒真に近づく。
- 対象自身の本文 (「使い捨て」「撤回済み」と自称する記述) を根拠にする — 信頼境界に反する。
  外部の台帳で裏を取れないものは未解決に置く。

## {{D:repo-bloat-is-load-bearing}}. リポジトリの膨張は削除可能な不要物ではないと確定した

**決定:** 2026-09-14 時点の膨張について、**tracked file の削除確定は 0 件**とする。
以後「記録が膨れているから削ろう」という提案は、この監査を覆す新しい実測を添えない限り採らない。

実測 (main `30efab0c4` の作業ツリー): tracked 24,684 件 / 約 690 MB。
`output/` 601,392,319 bytes / 21,965 件、うち `output/insights` 396,269,908 bytes / 18,205 件、
`output/env` 195,405,078 bytes / 3,246 件。

削れない根拠:

- 同一 blob の重複は余分だけで 6,761 件 / 50,265,692 bytes あるが、大きい群は現物で pin されていた。
  `output/s6-rounds/frozen/payloads/` は `hash_ledger.json` の slot 別 hash を
  `orchestrator/campaign/s6_proposal_rounds.py:244` が全 round・全 arm ぶん照合する。
  axis1 retake の pass1/pass2 は bundle manifest が両 path と hash を個別に記録する。
- `job-staging` 1,206 件 / 123,987,396 bytes は他所に同一 blob がゼロで、実行コード 4 か所が参照する。
- 0 byte file 2,838 件にも、読まれている fixture と束縛された台帳が含まれる。
- committed build artifact は `CMakeCache.txt` 4 件 121,111 bytes だけで、`.o` / `.a` / `CMakeFiles/`
  は 0 件である。「ビルド生成物の混入」は起きていない。

テスト側は件数 23,105 / 直列総和 15,306.6 秒で、D747 実測日の 14,467 件 / 5,364.9 秒から
1.60 倍・2.85 倍に増えた。しかし `< 0.01 秒` の 12,223 件は合計 25.8 秒、`>= 10 秒` の 372 件が
8,256.0 秒 (全 work の 53.9%) であり、**D747 の「安いテストを消しても効かない」は母数 2.85 倍でも
成立する**。本体 AST 一致で拾った群のうち現物検分した 10 群はすべて入力・module・呼出先が異なり、
真の完全重複は 1 件 124 bytes だけだった。

**理由:**

- 掃除の提案は繰り返し起票されうる。そのたびに 3 経路の監査をやり直す費用は、記録された
  否定的結論より高い。否定的結論こそ台帳に残す価値がある。
- ディスク容量は制約ではない (85T 中 4%)。膨張の実害は容量ではなく、
  作業コピーの残置と、`output/` 全件を複製する受入 fixture の側にある。

**却下した選択肢:**

- 「参照ゼロの記録を消す」方針を恒久化する — {{D:deletion-reference-taxonomy}} の基準で
  実際に該当が 0 件だった。方針だけ作っても発火しない。
- 重複 test 1 件を削除して「掃除した」と記録する — 成果物の値・受理集合・参照を 1 つも変えず、
  `DW-G05` の意味で must-fix ではない。実装子・敵対レビュー 2 本・変異 matrix・dispatch 本走を
  124 bytes のために起動することになる。

## {{D:worktree-residue-needs-owner}}. worktree の残置は lock ではなく回収権限の不在が原因である

**決定:** 取り込み済み worktree が滞留する原因を、**lock ではなく「land と cleanup の分離 +
cleanup が親の生存に依存する設計 + 残置後の回収権限の狭さ」**として記録する。
原因未確定の残置を一括して新しい failure 型にはしない。

実測 (2026-09-14): `git worktree list` 42 本、local branch 44 本。branch が main へ取り込み済みの
worktree は 26 本。`tools/check_worktree_occupancy.py` が非占有 23 本・占有 3 本を返し、
lock は locked 7 / unlocked 19 だった。しかし **`git status --porcelain` が空なのは 3 本だけで、
23 本は Codex 実装子の未 commit 編集を抱えている**。「取り込み済み × 非占有 × 非 lock × clean」を
満たすのは 1 本だけだった。

**理由:**

- 「lock が撤去不能を作る」という仮説は `tools/dev_wave_cleanup.py:943` で否定される。
  同 tool は事前検査後に自対象の lock を解除して撤去へ進む。
- 残置経路は次である。(1) land と cleanup は別工程である (D702)。(2) 親が land 後に対象外へ
  移り cleanup を明示実行する設計である。(3) 親の終了・中断、cwd 固定、占有・dirty による停止では
  残る。(4) 次 wave は他者の残置物を自動回収できず、`/cleanup-branches` も locked・所有不明を触らない。
- 非占有は所有解除でも dirty 不在でもない。占有走査の rc=0 だけで撤去可能数を数えると、
  今回のように実数の 18 倍を見積もる。**撤去可能性の判定には dirty 検査を必ず含める。**

**却下した選択肢:**

- 本 wave が一括撤去する — D204 は対象を特定したユーザー指示を要求し、D703 の例外は自 wave に
  限る。D854 は生の worktree 削除を破壊系に分類し、cleanup-branches §0 は cleanup の mutation を
  その command の実行内に限定する。dev-wave がこれらを合算する根拠は無い。
- 残置 23 本をまとめて新しい F にする — 個々の残置原因を確かめていない。同型 2 例の実証を
  求める `DW-G03` も満たさない。
