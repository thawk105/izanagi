## {{D:merge-audit-stays}}. 取り込みの合成監査は固有検出率が 3 分の 1 でも維持する

**決定:** 実装面が重なる local main 取り込みで Codex `role=author` の合成監査を行う義務
(D697 決定 8) を維持する。撤廃しない。維持の根拠を「検出率」ではなく
**「他のどの機構でも検出できない型を検出すること」**に置き直す。

固有検出の下界は 5 件である。母集合は `docs/archive/` の worklog のうち合成監査の走行を
記録した 13〜15 回。内訳は下記のとおりで、**同じ回に別の機構が赤にした型は固有に数えない。**

- 固有: 相手の新設失敗経路が共通 attestation 形式を外れた件、F324、
  main 側 docstring の stale 識別子参照、F481、旧 schema receipt の受理集合退行
- 非固有: git が競合を報告した件、既存の凍結不変テストが同回で赤を出した件、
  既存の collection 検査が `UsageError` を出す件

**理由:**

- 固有 5 件のうち 2 件は**受入全走を厚くしても届かない。** F481 は
  「受入全走のたびに stale registry 検査が無効化される。registry が腐っても検出されない」型で、
  受入は緑のまま通る。旧 schema receipt の件は受理集合が静かに狭まる退行で、
  テストは緑・競合もなかった。
- 検査を静かに無効化する型・受理集合を静かに狭める型は、テストの緑が証拠にならない。
  これは絶対規律 2 が守る面そのものである。1 件が main へ入れば、
  以後の certified 選択結果はすべて無効化された検査の下で作られる。
- 費用は 106〜468 秒 / model call 6〜28 (receipt 台帳 n=5、launcher error 除く) で、
  防いでいる損失と釣り合わない側にない。
- 検出率で正当化すると、率が下がった時点で撤廃の議論が再燃する。
  正当化を**型の一意性**へ置けば、他機構が同型を覆うまでは維持が導かれる。

**却下した選択肢:**

- 撤廃して受入全走に委ねる — F481 型は受入が緑を返すため代替にならない。
- 発火条件を狭めて回数を減らす — 固有検出の 5 件は
  「競合ゼロ・テスト緑」で通った型であり、狭める述語を作れる根拠が無い。
- 検出率 5 割超という当初の主張を維持する — 3 件は同回に別機構が赤にしており誤りだった。

## {{D:merge-audit-projection-requirements}}. 合成監査を機械射影で高速化する案は、必須経路と実行分類を先に閉じるまで実装しない

**決定:** 合成監査の事前射影 (重複実装面 path、両親の diff、変更識別子の全呼出しの AST 数え上げ)
を決定的に生成する機構を新設する案について、**本 wave では実装しない。**
実装の前提として次の 3 点を先に閉じることを条件とする。

1. **必須経路への配線。** 正規の main 取り込みは受入待ち手の post-claim merge で行われ、
   merge 直後に provenance 検査が連続実行される。**間に親が入る停止点が無い。**
   commit 直前にしか読まれない reference へ 1 行足す配線では、
   機構は親が思い出したときだけ通る位置にしかない。
2. **Pegasus 実行分類。** 全 Python 母集合を走査する新規 script は、login node で
   実行する前に分類が要る。判定量は cgroup の charged memory のピークであり、
   最大 RSS は代理値にならない。既存 script が未登録で常用されている事実は
   machine gate の被覆漏れであって、分類義務の撤回根拠にならない。
3. **発火集合の名指し。** D697 決定 8 (両親が同じ実装面 file を変更)、
   D554 (結果が両親双方と食い違う実装面 path)、D770 (combined diff 非空) は
   **別々の集合**である。運用文が「実装面 path 差」と畳むと、どれを取り違えても
   監査が減るか不要な分割が増える。

**実装する場合の必須要件** (段 3 の敵対レビュー 2 本が real と判定したもの):

- F324 が要求する「満たさない件数」と母集合を、schema と renderer が**構造的に強制**する。
  件数欄が無いまま「静的 call 候補なし」で監査を閉じられる形にしない。
- 完全性を表す真偽値と、意味的な呼出し解決の不完全さが両立しないようにする。
  静的 call 数ゼロが動的 consumer ゼロへ読み替えられる経路を作らない。
- YAML・生成コードを含む文書・**第三者 submodule の内部差分**を必須手動監査へ昇格する。
  submodule は superproject の tree では gitlink 1 行であり、内部が列挙されない。
- 呼出し走査を canonical path 集合へ狭める退行が緑で通らないよう、
  F324 の実 merge を回帰に固定する。
- blob 上限・出力上限と、部分被覆を表す終了コードを誰が成功扱いで監査子へ渡すかを決める。

**速度主張の扱い:** 「事前射影を厚くすれば速い」は現物 2 件で反証された
(最も厚い射影の走行が最も遅い)。「有用なアンカーが探索量を減らす」仮説は交絡が多く未確定で、
**短縮秒数を主張しない。** 旧待ち行列で失われた時間や lease 窓の消費を節約時間に数えない
(現行は単発 claim で、監査は lease TTL の 4.4〜19.5%)。
ただし監査子は当該経路の 33〜68% を占めるため、「少数派だから放置してよい」も成り立たない。

**理由:**

- 3 点はいずれも段 3 の独立レビュー 2 本が指摘し、親が現物のコードで裏取りした。
- 1 と 2 はどちらも本 wave の scope を超える。1 は受入受領証の argv まで pin された
  待ち手の変更を要し、2 はユーザー端末での実測を要する。
- 前提を閉じずに script だけ置くと、使われないまま腐る機構が 1 つ増える。

**却下した選択肢:**

- reference へ 1 行足して親の運用規律に委ねる — 必須経路を通らないため実効ゼロになる。
- 最大 RSS の実測をもって分類済みとする — 判定量が違う。規律の自己認定にあたる。
- 3 集合を 1 語へ畳んだまま配線する — どれを取り違えても監査の受理集合が動く。
