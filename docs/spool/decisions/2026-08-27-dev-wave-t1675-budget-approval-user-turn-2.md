## {{D:budget-approval-preflight-only}}. 予算承認は発行せず、検証だけを機械化する

**決定:** 床値 official の予算承認について、承認 artifact を**発行する経路は作らない**。
AI が作るのは次の 2 つに限る。

1. `skeleton` — 承認者・日時・予算値を持たない骨組みを repository の外へ create-only で出す。
2. `verify` — 人間が書いた承認 JSON を読み、canonical loader が課す条件を検証して
   raw の sha256 と pin 行を表示する。**file を 1 つも書かない。**

承認 JSON を canonical path へ置くこと、および `BUDGET_APPROVAL_SHA256` を `None` から
変えることは、人間がコード diff をレビューして行う手番のまま残す。
tool に `--approver` およびそれに類する承認者入力を持たせない。
承認者や予算値を環境変数・git 設定・既存の凍結記録・骨組みから補う経路も持たせない。

**理由:**

- D287 が「approval を発行する CLI・API・`--approver` 引数・既定補完は作らない」と定めており、
  本 pin を作った wave 自身の裁定で未 supersede である。同 D は「pinned literal なら、AI が
  承認者になるには人間がコード diff をレビューして定数を置くしかない」を承認の実体としている。
- D526 が批准台帳について「追記 API・CLI・自動更新処理を作らない」「批准値を持つ台帳を wave 側で
  作って land するのは弱化した本人が批准する形になる」と定めており、同じ形が本 pin にも当たる。
- 承認者を対話端末から受け取る案は、D905 が却下した平文承認と同型である。同 D は
  「AI が成りすませない実行主体を新設する案だけを採る」「設計が着地するまで批准は進めない」と
  している。端末は人間と機械を区別しないため、承認境界の防壁にならない。
- 一方で、canonical bytes の組み立て・holdout 集合の対応・sha256 の算出は機械的作業であり、
  人間が手で行う理由がない。ここを機械化しても承認の意味は失われない。
  D758 が分けた「承認 (authority)」と「機械的実行」の区別のうち、**発行しない範囲でだけ**
  後者を機械へ移す。

**主張の上限:** 固定できるのは、承認者が非対話経路から流入しないこと、予算数値に既定値が
無いこと、置かれた内容が canonical loader の条件を満たすことまでである。
検証 tool と被検証対象を同じ主体が変更できる以上、意図的な改変への完全な防壁ではない
(D387、D1128)。事故的な誤りを検出する、とだけ書く。

**却下した選択肢:**

- **承認 JSON を発行し pin を書き換える CLI を作る** — D287 と正面から衝突する。
  承認の主体が「人間の reviewed diff」から「その CLI を起動した主体」へ移る。
- **承認者を対話端末から受け取る** — D905 が却下済みの形。端末は人間性の証明にならない。
- **pin を別 data file へ出す** — trust root の設計変更にあたり、本 wave の scope を超える。
- **検証も作らない** — 機械的作業を人間に残す理由がなく、
  守っている性質と払っている費用が対応しない (D758 の趣旨)。
