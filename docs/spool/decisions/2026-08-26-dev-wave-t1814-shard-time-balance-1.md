## {{D:shard-duration-weight-refused}}. 受入 shard 割付を duration 重みへ変えない — 完璧な予言者でも利得は 0.0 秒

**決定:** `tools/acceptance_shards.py` の `allocate()` が `weight = len(nodeids)` で
bin-packing している点は変えない。junit / 所要台帳の duration を重みにする改修を採用しない。
実装差分ゼロで閉じる。

**理由:**

- **完璧な予言者でも利得が 0.0 秒である。** 同一 tip の K=2 走 2 本それぞれについて、
  その走自身の実測 duration で 3 通りの割付 (要素数 / commit 済み台帳 / その走自身の実測) を
  評価した。makespan 予測は shard ごとに `max(最長排他鎖, 仕事量/48)` とした。
  3 通りとも同じ値になった (1 走目 222.7 秒、2 走目 206.1 秒)。
  oracle 割付は仕事量を完全に均衡させる (2 走目で 5283.4 / 5283.4 秒、1 worker あたり 110.1 秒)
  にもかかわらず、`real-repo` の排他 group はそのまま 1 worker に載り続ける。
- **鎖が単独で最遅である。** `xdist` の `loadgroup` は 1 group を 1 worker で直列に実行するので、
  その shard の pytest wall は「鎖の所要 + その worker の開始時刻」を下回れない。実測でも
  鎖以外の最遅 worker は 1 走目 191.4 秒 (鎖 222.7 秒)、2 走目 138.1 秒 (鎖 206.1 秒) であり、
  再割付は鎖以外を下げるだけで最遅を動かさない。
- **現物台帳では機能が一度も発火しない。** 台帳は 15,909 nodeid、受入集合は 17,160 node で
  実測被覆は 92.5%。「1 件でも未知なら要素数へ戻す」設計は毎走必ず発火し、duration 割付は
  実環境で一度も動かない。部分被覆で動かす設計にすると、台帳に provenance
  (tip / K / scheduler / worker 数 / 入力 junit digest) が無いため、何を重みにしたのかを
  走行証拠から言えない。
- **追う効果より走間ばらつきが 1 桁大きい。** 同一 tip・同一選択・同一割付の K=2 を 2 走した
  結果、pytest wall は 307.29 / 275.02 秒 (差 32.27 秒)、直列総仕事量は 14862.6 / 10585.7 秒
  (1.40 倍) だった。差の原因は割り当てられた計算ノードである。効果 0.0 秒に対しノイズが 32 秒ある。
- D531 と D713 の警告 (duration は共走の競合を含む / K を変えると duration 自体が変わる) は
  本件でも成立する。K=2 の台帳を K=1 の予測に使えないだけでなく、**同じ K の 2 走でも
  総仕事量が 1.40 倍動く**。

**却下した選択肢:**

- **台帳の duration を重みにする最小変更 (`_components()` の `weight` 1 箇所)** —
  変更自体は小さいが、上記のとおり利得がゼロで、現物台帳では発火すらしない。
- **部分被覆でも既知値だけ重み付けする** — 台帳に provenance が無く、走行証拠にも
  `allocation_mode` が残らないため、「実測したが実際は旧割付だった」を区別できない。
- **count 対 duration の同一 tip A/B を実走して判定する** — 反実仮想が 2 走とも 0.0 秒を
  示しており、0 の効果を 32 秒のノイズに対して測ることになる。計算資源を使う理由がない。
- **shard 割付の目的を wall でなく資源効率 (node 秒) に読み替えて採用する** — 依頼は
  受入の所要短縮であり、目的の置き換えは別裁定を要する。

## {{D:shard-chain-bound-trigger}}. 分割の再検討は「最長排他鎖 < 総仕事量/(48K)」を引き金にする — 保証ではない

**決定:** 受入分割について、次を**保証ではなく再検討の引き金**として記録する。

> ある走について、その走の最長排他鎖の所要を `C`、直列総仕事量を `W`、shard 数を `K`、
> 1 job あたりの worker 数を 48 とする。`C > W / (48K)` である限り、その走の makespan は
> 鎖で床が決まり、割付を均衡させても K を増やしても下がらない。
> `C < W / (48K)` が観測されたら、duration 重み割付を再検討してよい。

観測実績は 3 走とも成立側である。2026-08-24 の走で `C = 210.5 > 7472.5/96 = 77.8`、
2026-08-26 の 2 走で `C = 222.7 > 14862.6/96 = 154.8` と `C = 206.1 > 10585.7/96 = 110.3`。

次の 3 点を同時に定める。

- **この式は必要条件でしかない。** 逆が成り立っても短縮できるとは限らない。鎖の開始遅延、
  他 component の LPT 裾、worker の idle gap、collection と finalization の残差が
  critical path になりうる。
- **恒真な機械 gate を作らない。** 既存の成果物 field だけでは `C` を機械的に取れない。
  shard の `report.json` は `worker_occupancy` と `group_to_workers` を持つが、
  group ごとの直列所要を持たない。次に測る人が junit と `report.json` を join して求める。
- **`W` は当該走で測った値に限る。** 同じ tip でも走によって 1.40 倍動くため、
  過去走の `W` を将来走の床に使わない (D713)。

**理由:**

- 「割付を均衡させれば速くなる」という直観は、排他鎖が平均 capacity を上回る regime では
  成り立たない。この式はその regime にいるかどうかだけを判定する。
- 保証として書くと、逆が成り立った時点で「短縮できるはず」という誤った期待を生む。
  段 2 の plan と段 3 の 2 レンズが独立にこの点を指摘した。

**却下した選択肢:**

- **`C ≥ W/(48K)` を「短縮不能」の保証として書く** — 必要条件でしかない。
- **shard の `report.json` へ group 別直列所要を足して機械 gate にする** — 受理 schema と
  merge gate の exact 述語を変える改修であり、現時点で消費者がいない。規律 5 に反する。
- **記録しない** — 次の担当が同じ 4 走を再実行することになる。
