## {{D:offrepo-scan-parallel-before-scope}}. 到達不能監査の repo 外走査は、範囲限定より先に並列化で定数を下げる

**決定:** `tools/audit_dangling_commits.py` の repo 外走査の所要を下げるとき、
**まず走査の並列化 (範囲・規則・出力を一切変えない定数削減) を実装して実測し、
それでも D958 の所要上限に入らないことを示してから、走査の範囲や実行主体を変える案を有効化する。**

この決定は D2034 を本件へ適用したものであり、D985 が「並列化は実測で否定済み (16 thread で改善 20%)」
として並列化を却下した射程を、**Python 実装に固定した場合の結論**へ限定する。

**理由:**
- 同じ Lustre 上で C 実装 (bfs 4.1.1) を測ると、探索根全体 1,761,075 file の warm 走査で
  単一 thread 3 走 230.29〜252.51 秒 (最大/最小 1.10) に対し 16 thread は 43.78 / 66.67 秒だった。
  保守的に最大どうしで 3.8 倍、平均どうしで 4.4 倍である。**20% は filesystem の性質ではない。**
  Python の thread は per-entry 処理で GIL を保持し続けるため metadata 待ちを重ねられない。
- 並列化は受理集合を 1 ビットも変えない。範囲限定は「どこまで検査したか」の開示と被覆の論証を
  新たに要求する (D2034)。安く済むほうを先に試す。
- 律速は metadata 待ちである。同じ GNU find で cold 1583.99 秒 / warm 243.94 秒 = 6.5 倍であり、
  `/cleanup-branches` は日をまたいで散発的に走るので実運用は cold 側である。

**この決定が主張しないこと:**
- cold での並列の倍率は測っていない。cache を意図的に落とす手段が無いためである。
  warm の 3.8〜4.4 倍をそのまま当てると走査は 273〜417 秒、監査全体は 387〜531 秒となり、
  **上限に入らない公算が高い。** これは外挿であって実測ではない。
- Python に thread pool を入れて C と同じ倍率が出るとは限らない。先に prototype で実測する。

**却下した選択肢:**
- **範囲限定を先に検討する** — D2034 が明示的に禁じる順序である。加えて本件の範囲限定案には
  下記 {{D:offrepo-candidate-first-not-equivalent}} の反例がある。
- **並列化を諦めて現状維持** — 定数削減の余地が尽きていないまま上限超過を放置することになる。

## {{D:offrepo-candidate-first-not-equivalent}}. landed 参照の被覆部分木だけを走査する案は、現行の抑止集合と厳密等価ではない

**決定:** repo 外走査を「landed 参照の最小被覆部分木」に限定する案 (候補先行) は**採らない。**
D247 条件 5 が候補 path とその祖先のいずれかの境界付き参照を要求する以上、抑止されうる file は
その部分木の中にしか無いが、**現行実装の抑止集合と厳密に一致させることはできない。**

**理由:**
- **hardlink の owner/alias 交差。** 実装は `(OID, device, inode)` ごとに owner と alias を集め、
  比較成功時に全 owner へ全 alias を配る。到達不能側に同じ blob の異 basename 2 件があり、
  外部の hardlink 2 path のうち片方だけが landed 参照を持つ場合、現行は両方を抑止するが
  候補先行では片方が消える。
- **hardlink 代表の交代。** 現行の代表が open 不能で被覆内の別 alias が読める場合、
  枝刈りで代表が交代し**現行には無かった抑止が生まれる**。
- **中間 directory symlink。** 現行は `followlinks=False` で辿らない。被覆 path から直接
  走査を開始すると越えてしまい、**抑止が増えうる**。
- 後ろ 2 つは「抑止を広げない」という不変条件に直接違反する。安全側でない縮約は採らない。
- **境界 byte を含む path・探索根。** `_has_bounded_path_reference()` は出現の左右だけを見るが、
  本番の `_bounded_path_reference_matches()` は探索根末尾から最初の境界までを取る。
  path 内部に空白がある候補で両者の判定が割れるため、「候補 path を pattern にして landed を
  grep する」と「landed content から極大の非境界 byte 列を抜く」の 2 方向は一般には等価でない。

**この決定が主張しないこと:**
- 縮小率そのものは実在する。被覆部分木は 278,272 file / 25,416 dir で、探索根全体の dir 数の
  13.1% にあたる。bytes 一致した 17 file はいずれもこの部分木の外にあり、監査自身の
  `suppressions=0` と一致した。**採らない理由は効果が無いからではなく、等価性が作れないからである。**

**却下した選択肢:**
- **反例を個別に塞いで採用する** — hardlink 代表の順序依存と symlink の到達可能性まで含めた
  等価性の論証が要る。定数削減で足りるかを先に測るほうが安い (D2034)。
- **最小被覆 path を新しい探索根として渡す** — `_reference_patterns()` の停止位置が変わり、
  まさに参照された被覆 directory 自身を根拠から落とす。

## {{D:offrepo-scan-yield-cause-undetermined}}. 抑止の収量が 292 対から 0 対へ落ちた原因は未確定とする

**決定:** repo 外走査による抑止が 2026-08-26 の 292 対から 2026-09-15・2026-09-16 の 0 対へ落ちた
原因は**確定していない**と記録する。D957 の再生成可能物除外では説明しない。
「抑止は構造的に 0」も主張しない。

**理由:**
- 2026-08-26 の記録は**抑止 292 対と除外 13,488 対が同じ走に併存し、独立 4 走すべてで同値**と
  明記している。292 は D957 適用後の値なので、除外は 7,050 → 292 の説明にはなっても
  292 → 0 の説明にはならない。
- 当時の出力は repo 内に残っておらず、292 対がどの file 群に効いていたかを復元できない。
- 直近 2 走は同じ 17 file・23 対を再観測しており、独立した標本ではない。
- **祖先条項が構造的に不発という一般化も成立しない。** main に land 済みの
  `orchestrator/manual_probes/test_t2397_a1_source.py` が job dir path を引用符で囲んで書いており、
  引用符は D248 の境界 byte なので条件 5 が成立する。既存テストにも祖先参照の陽性例が 2 件ある。
- 言えるのは「今回一致した 17 file には有効な landed 参照が無く、`/` と `:` が境界 byte でないこと
  (D248) と、文書が job dir を長い path の接頭辞および `path:line` 形式で書く慣習が、その説明になる」
  までである。

**却下した選択肢:**
- **「収量は構造的に 0」を根拠に走査を既定 off にする** — 反例が現存する以上、この根拠は使えない。
  用途分離を採るなら根拠は「findings を保ったまま、注記が要る判断のときだけ全走査する」に置く。
- **境界規則を緩めて条件 5 を発火させる** — 抑止を広げる方向であり、報告を減らす = 掃除の安全条件を
  緩める側である。
