## {{D:campaign-sink-dominating-returned-evidence}}. campaign sink の被覆は、支配的な返却物検査を 4 条件つきで数える

**決定:** 静的閉包検査は、`campaign` kind の sink について、支配的な
`require_returned_condition_evidence` 呼出しを被覆として数える。ただし次の 4 条件をすべて
満たすときだけである。どれか 1 つでも示せなければ被覆なしに倒す。

1. **支配性** — 検査済み名は構造化フロー state に載せ、合流で積集合を取る。sink へ到達する
   全経路に現れる名前だけが残る。sink より後の呼出しは sink 直前 state に入らない。
2. **実行される形** — state 効果を与えるのは、その呼出しが文そのもの (`Expr` の値) か
   単一 `Name` への単純代入の値であるときだけ。`BoolOp` / `IfExp` / lambda / 内包表記の内部に
   ある呼出しは数えない。短絡すれば実行されないためである。
3. **helper の真正性** — 呼出し位置で helper 名の到達束縛が正規の `ImportFrom` だけである
   ことを scope ごとに解決する。局所定義・引数・代入・別 import・`with` / `except` / `match`
   束縛による shadow があれば数えない。
4. **must-alias** — sink の設定式の値の出所を 1 本に解決し、その根が検査済み名であることを
   要求する。属性は value 側へ降り、`Call` は選択中の属性と同名の keyword へだけ降り、
   束縛が一意でない名前・`IfExp` / `BoolOp` / 内包表記 / `Subscript` が経路に現れたら倒す。

あわせて、模型化しきれない再束縛は**名前を鍵に fail-closed** にする。checked 名または
helper 名を対象とする `global` / `nonlocal` 宣言が module にあれば、その名前は数えない。
`from ... import *` があれば helper 真正性を file 全体で落とす。

これは検査の**受理集合を広げる変更**である。広げてよいのは上の条件を満たす形だけとする。

**理由:**

- 注入枝には既に同型の機構がある。理由も同じで、helper が観測 record の macro 集合と
  期待 request digest を完全一致で検査するため、macro token がその file に字面で無くても
  被覆は exact である。campaign 枝にこれが無いのは射程の穴であって意図された区別ではない。
- 4 条件はいずれも**受理集合を狭める側**である。敵対レビューが、条件を欠いたときに通ってしまう
  入力をそれぞれ具体的に示した。実測でも、支配性を行番号順で近似した実装は
  「分岐内にしか検査が無い」「検査後に同名を再束縛する」の 2 つを誤って受理する。
- 構文ごとに模型化を足すのでなく名前を鍵に倒すのは、際限のない追随を避けるためである。
  実測では、構文を鍵にすると 53 sink 中 27 sink を巻き込むが、名前を鍵にすると
  触れる production file は 3 本だけで、いずれも無関係な名前だった。

**却下した選択肢:**

- **行番号の区間で支配性を近似する** — 注入枝が使っている形だが、区間は支配性を示さない。
  実測で 2 種類の入力を誤って受理した。
- **依存名の一部一致で被覆とする** — 未検査の別値を選べる経路まで受理する。
- **期待 request digest から macro を静的に復元して被覆を絞る** — 実 driver の期待集合は
  実行時の cell flags から作られ静的に復元できないため、絞ると守りたい経路が 1 つも
  被覆されなくなる。helper が macro 集合について exact である以上、絞る必要もない。
- **過剰拒否の形 (sink より後の walrus、未消費 generator) を通すために評価順を模型化する** —
  受理集合を広げる方向の変更が増える。本 wave 以前は campaign sink に被覆が一切付いておらず、
  これらが拒否されることは main に対する回帰ではない。保守性として維持する。

## {{D:closure-check-reports-reachable-domain-not-total}}. 閉包検査の被覆は「到達可能 domain に対する割合」で報告する

**決定:** 静的閉包検査の被覆を報告するとき、「sink あたり全 macro が被覆された」とは書かない。
**その sink の到達可能 domain (検査が到達可能と判定した macro) に対する内訳**で書く。
domain 外として `proven-unreachable` に落ちたセル数も併記する。

**理由:**

- 実測で、誤った到達不能証明を 1 つ直した sink は「被覆 4 / 到達不能 18」になった。
  22 セル全部が被覆されたわけではない。ここで「真に被覆された」とだけ書くと、
  読み手は 22/22 と読む。**読み違える。**
- 残る 18 セルは「この file の macro inventory に無い」という既存の証明で落ちている。
  この証明の妥当性 (動的入力があるときに部分 inventory を閉集合として扱ってよいか) は
  別の設計判断であり、1 つの誤った証明を直す作業の射程外である。
- 内訳で書けば、後から「どの sink がどの理由で何セル除外されているか」を数えられる。
  0 件や「全部被覆」という要約では数えられない。これは除外を沈黙でなく名前で残すという
  既存の方針を、割合の書き方へ広げたものである。

**却下した選択肢:**

- **22/22 被覆と書く** — 事実でない。
- **残り 18 セルを繰延べ台帳へ移す** — 同じ規則で落ちているセルは repo 全体に 900 件以上あり、
  1 sink だけを台帳へ移すのは一貫しない。inventory の閉包意味論そのものを裁定する別作業が要る。
- **inventory の閉包意味論をこの作業で作り直す** — 受理集合をさらに広く動かす。
  実測では、不透明な束縛 target まで扱うと無関係な driver 1 本が 22 セル赤になる。
