## {{D:b10-historical-binding-per-series}}. 歴史的な束縛を持つ campaign の再利用は系列ごとに有限集合へ閉じる

**決定 (ユーザー裁定):** B-10 の次の系列でも、完走済み campaign を集約へ受理する経路は
**その系列限りの有限な内容 digest 集合へ exact に閉じる。**「歴史的な束縛と同じ形の記録」を
一般に受理する規則は作らない。driver を編集するたびに同じ形の限定受理を新しく書く。

**理由:**
- 記録の封筒は自己 hash であって秘密鍵で署名されたものではない。一般規則にすると、
  正しさの判定結果や性能値を書き換えた記録が判定へ入る。D1588 が段 3 で棄却した論点そのもの。
- 限定受理を系列ごとに書き下す費用は有限で、しかも書いた時点で受理集合が明示される。
  一般規則は受理集合が暗黙になり、後から広がったことに気づけない。
- 受理集合を広げない向きであり、絶対規律 2 の側である。

**却下した選択肢:**
- **歴史的な束縛の形を一般に受理する規則を作る** — 改変記録が判定へ入る。
- **driver の編集を禁じて再測定を不要にする** — 測定機構の改善が止まる。

## {{D:axis3-core-rewritten-on-remaining-differentiators}}. 説明可能性の核は残る差別化 3 点で書き直す

**決定 (ユーザー裁定):** `docs/paper-story/` の軸 3 (説明可能性) の核は、
**対象がトランザクションの並行性制御であること・対象実装の action vocabulary そのものを
拡張すること・正しさゲートを毎反復回すこと**の 3 点で書き直す。SysInsight が評価していない
説明の忠実性・proof chain・試行 provenance は、核ではなく補助として書く。

**理由:**
- 「空いている」は先行研究が触れていないというだけで、こちらが実証を積んでいる面ではない。
  空いている面を核に据えると、その実証を新たに立てる必要が生じ、主目的から遠い作業が
  主経路へ入る。
- 残る差別化 3 点は既に実装と計測が動いている面であり、主経路の前進がそのまま核を強くする。
- SysInsight が埋めたのは狭い能力 3 語だけで、軸全体ではない。核を軸ごと明け渡す必要はない。

**却下した選択肢:**
- **忠実性・proof chain・試行 provenance を核に据える** — 新規の実証が 1 本要る。
- **軸 3 を差別化から外す** — 埋まったのは狭い能力だけで、軸全体は空いていない。

## {{D:s4-launch-layer-owns-classification-policy}}. 分類 policy の権威は起動層に置き、世代別台帳の記録行は capability で囲まない

**決定 (ユーザー裁定):** 世代別台帳の実装について 2 件を確定する。
(1) 分類 policy の権威は**起動層に置く**。到達不能な証拠・対応する単一 pin の不在・
probe が計測前を覆わない点は、いずれも起動層の所有面だからである。
(2) 世代別台帳の分類 claim と回復行は **capability で囲まず**、束縛範囲を検査で固定して
非束縛の集合を明記する現行の形を維持する。

**境界 signature の補正は本裁定に含めない。** 既存 8 境界で運べないことを示す反例と、
新しい入口の発行者・消費者・失効条件を揃えたうえで改めて提示する。

**理由:**
- 権威を所有面と別の層に置くと、値の更新が 2 箇所の同期になり、片方だけが動く形を作る。
- capability で囲む案は、囲むことで得られる保証が「検査で固定して非束縛を明記する」現行形を
  上回ることが示されていない。囲んだ範囲の外は結局明記が要る。
- 境界の増設は受理集合と入口の数を同時に増やす。反例と仕様が無いまま増やすと、
  発火しない境界を 1 本足すだけになりうる。

**却下した選択肢:**
- **3 件をまとめて一括承認する** — 境界の補正だけ材料が揃っていない。
- **境界の補正を別の変更単位へ丸ごと送る** — 理由語彙の有効化が同じ変更単位でしか
  できないため、送ると後続が塞がる。

## {{D:no-approved-cmake-registry}}. 承認済み CMake の登録簿は作らず、identity は記録に留める

**決定 (ユーザー裁定):** 承認済み CMake identity の権威 (登録簿・更新手順・機体差の扱い) は
**新設しない。** 判定器が環境から解決した CMake の実 path・内容 SHA-256・stat identity・
configure argv を green record へ束縛する現行の形 (記録であって拒否ではない) を維持する。
**再訪条件 = 未承認の CMake による測定が実害を出した 1 件。**

**理由:**
- 2026-08-12 のユーザー方針 (論文主張に要るのは粗い provenance のみ、bytes 級の pin・署名・
  束縛機構の新設は既定で見送り) に従う。同じ面で cmake の実 path 照合を見送った先例がある。
- D1586 が拒否を採らなかった理由は「承認済みの定義を wave が自分で決めることになる」であり、
  権威を新設すればその定義・更新手順・機体差の扱いが恒久の保守対象になる。
- 記録は残るので、実害が出たときに事後に辿ることはできる。検出できないのは事前の拒否だけである。

**却下した選択肢:**
- **登録簿を新設して未承認の CMake を拒否する** — 穴を実際に閉じる唯一の道だが、
  恒久の保守対象を作る費用が、観測されていない実害に見合わない。

## {{D:job-termination-stays-disclosure}}. 集約の全ジョブ終端確認は作らず、完全性は開示に留める

**決定 (ユーザー裁定):** 集約が他ジョブの終端記録へ到達して全ジョブの終わりを機械的に
確かめる経路は**作らない。** 完全性は開示として書き、レポート発行を止めてよいのは
入力である block record 側の検査だけとする D1590 の境界を維持する。

**理由:**
- D1590 が「完全性は開示であって受理規則にしない」と定めており、終端確認を受理条件に
  格上げすると、この境界を越える。開示のための情報が欠けたことを理由に判定と台帳が
  発行されなくなる形を、D1590 は明示的に避けている。
- 開示専用として作る案も、研究最優先・防御的堅牢化は既定で見送りという方針の下では、
  実害が観測されるまで新しい配線を足す根拠が足りない。
- block record 側の検査 (自己 hash、受領証 hash、格子の過不足と重複) は現に効いている。

**却下した選択肢:**
- **終端確認を受理条件にする** — D1590 の開示と受理の分離を逆転させる。
- **開示専用の配線を先に作る** — 他ジョブの終端記録へ到達する配線が要り、実害が無い。

## {{D:acceptance-wall-split-dominant-files}}. 受入所要は対応表を作らず、支配的な 2 file の分割で詰める

**決定 (ユーザー裁定):** 受入所要の内訳を出す計装 (nodeid から worker への対応表) は
**作らない。**代わりに、仕事量の 58% を占める支配的な 2 file の分割を直接進める。
D1327 の再訪はこれで閉じる。

**理由:**
- D1327 の再訪条件は両方成立していた — 受入 wall が 388.3 秒 = 6.47 分で 5 分上限を 29% 超え
  (実害)、frontier も「97 秒以上の unit が 10〜11 本」から「2 file が 58% を占め最長 3 件が
  一方へ集中」へ変わった (構成変化)。したがって再訪自体は正当である。
- しかし支配的な 2 file は既に名指しで特定できており、打ち手 (file 分割・重い判定の分離) は
  対応表なしで決まる。計装 1 本を挟むと「実装と検査が増え論文は進まない」という
  D1327 の却下理由がそのまま残る。
- 分割後に律速が別へ移ったときは、そのとき改めて特定すればよい。特定は今回も手作業で足りた。

**却下した選択肢:**
- **対応表を足して残差を分解する** — 打ち手は既に決まっており、計装が増えるだけである。
- **再訪せず D1327 をそのまま維持する** — 5 分上限を超えている事実を放置することになる。

## {{D:write-intent-pin-needs-materials-first}}. write-intent の pin 前進は材料 3 点を揃えてから裁定する

**決定 (ユーザー裁定):** write-intent 被覆違反の検査を pinned producer が出せるようにする
gitlink の pin 前進は、**次の 3 点を揃えてから改めて提示する。**
(1) 候補となる commit、(2) D297 が要求する「TRACE=0 の正規化前処理出力 + include 活性」の
同一性検査の結果、(3) 承認済み定数への波及範囲。3 点が揃えば前進してよい。

**理由:**
- 設計上の決着は D1360 で既に付いており、残っているのは実装である。しかし pin 前進は
  規律 1 (観測者効果の分離) の検査を通す操作なので、検査結果なしに承認すると
  「通したことにする」形になる。
- TRACE=0 前処理同一性検査には既知の穴が残っており (D986 / D751 が全件を塞ぐと裁定済み)、
  検査そのものの健全性が先に要る。
- 波及範囲が分からないまま前進すると、承認済み定数が黙って変わりうる。

**却下した選択肢:**
- **材料なしで前進を承認する** — 規律 1 の検査を形だけ通す形になる。
- **pin 前進を恒久に見送る** — write-intent 面が恒久に記録止まりになり、
  protocol 横断の certified な比較で被覆を保証に数えられない。

## {{D:axis1-write-guard-and-old-epoch-freeze-declined}}. 軸 1 の書込み先防護と旧 epoch 凍結物の検査範囲は、いずれも広げない

**決定 (ユーザー裁定):** 軸 1 の改訂契約 §8 の未決 2 件をいずれも**見送る。**
(1) 実行器が旧凍結 bundle を出力先として受け付ける点と目録生成器が任意 path を上書きできる点に
防護を新設しない。(2) 旧 epoch の凍結物を登録 preflight の凍結集合へ加えない。
**再訪条件 = いずれも同型の実害 1 件。**

**理由:**
- (1) の部分的な create-only 強制は、旧 bundle と任意 path の上書き自体を閉じない。
  実害も certified 経路への到達も示されておらず、研究最優先・防御的堅牢化は既定で見送りという
  方針に照らして先行させる根拠がない。
- (2) は追加分 2,130 file / 99,925,266 bytes で、現実装が 1 file ごとに別 process で読むため
  既存 18 秒の検査が数百秒規模になり、実行器の起動ごとに同じ費用がかかる。
  D335 (repository の成長に比例して実行コストが増える構造のテストは新設しない) に直接触れる。
- 加えるなら一括読み出しへの設計変更が先であり、その設計自体が実害なしには正当化されない。

**却下した選択肢:**
- **新規 root の create-only 強制だけ先に入れる** — 上書き経路を閉じない部分的な硬化。
- **旧 epoch の凍結物を凍結集合へ加える** — 検査費用が桁で増える。
