## {{D:b10-multinode-split-and-readheavy-path}}. B-10 正式走は workload ごと 3 本へ分け、read-heavy の道は律速測定の後に選ぶ

**決定 (ユーザー裁定):** B-10 正式走の投げ直しについて 5 点を確定する。

1. **分散の単位は workload ごとの 3 本とする。** 登録された実行順と SHA 一致条項を保てる分け方は
   これだけである。
2. **read-heavy を通す道は、先に律速の内訳と資源を測る安い実行を 1 回行い、その結果で選ぶ。**
   検査の多重化 (正しさ防壁の中核への変更) と壁時計枠の延長のどちらも、測る前には選ばない。
   **balanced はこの決定を待たずに投入してよい。**
3. **完走済みの write-heavy 45 セルは残す。** 外側の認証が論理積であるという規則は、
   登録内容ではなく集約側に持たせる。登録内容へ入れると登録のハッシュが変わり、
   完走済みの分が集約から外れる。
4. **失敗した 1 本の差し替えを認める。** ただし、どの打ち切り理由なら差し替えてよいか、
   差し替えてよい本数の上限は、**結果を見る前に凍結する**。
5. **投入前の必須修正 5 件を、この設計の前提条件として承認する。**

**理由:**
- 1 ノード直列では前回 5 時間 5 分で 15 点中 3 点しか終わらず、所要を決めていたのは性能測定でなく
  正しさ検査だった。条件を割って複数ノードへ同時に投入する以外に枠へ入れる道がない。
- 道の選択を測定の後に置くのは、規律 3 の「シグナルを見てから次の一手を決める」形であり、
  結果を見てから基準を作る形ではない。選ぶ対象は打ち手であって受理基準ではない。
- 差し替え規則を先に凍結するのは、成功した分と差し替え分を混ぜて受理する範囲が、
  結果を見た後に決まるのを防ぐためである。

**却下した選択肢:**
- 2 workload を揃えてから投げる — balanced が入る見込みなのに待たせる理由がない。
- 完走済み 45 セルを取り直す — 丸損であり、workload ごとに campaign の同一性が既に分かれている。
- 差し替えを認めない — 1 本の打ち切りが 3 本の取り直しになる。
- 事前登録を緩める — 反復数・規模・検証の厳しさを下げることは規律 2 が正面から禁じている。

## {{D:no-historical-grammar-decoder}}. 旧 grammar の campaign lock 用の互換読取器は作らない

**決定 (ユーザー裁定):** enforcement source closure の拡張で読めなくなった旧 grammar の
campaign lock について、限定範囲だけ読める版付き decoder を**新設しない**。

**理由:**
- repo 側の consumer は当該 artifact を file bytes の SHA-256 で束縛して読んでおり、
  受入は赤にならず図の再生成も壊れない。失われるのは admission API 経由で読み直す能力だけである。
- 既存の決定は当時の判定を当時の版として表示することを求めるが、任意の旧版を読める
  互換分岐までは要求していない。
- 論文主張に要るのは粗い provenance のみという既定方針の見送り側に入る。
- 互換分岐は受理範囲を広げる向きの変更であり、正しさゲートに近い場所へ新機構を足すことになる。

**却下した選択肢:**
- 版付き decoder を作る — 上記のとおり、実害が観測されないまま受理側へ分岐を足す。
- 旧 artifact を新 grammar へ書き換える — 凍結された記録の bytes を後から変えることになる。

**再訪条件:** 当該 artifact を admission API 経由で読み直す必要が実際に生じたとき。

## {{D:qualification-schema-live-bytes-bound}}. qualification schema の live bytes を記録 blob と結ぶ

**決定 (ユーザー裁定):** qualification の身元検証に、**実際に受理判定へ使われた schema の
live bytes と記録 blob の等値検査**を最小の形で足す。

**理由:**
- 現行は記録 commit の blob を検証するだけで、判定が読んだ live bytes との等値を確かめていない。
  同じ campaign epoch と同じ記録 code identity のまま、live schema を緩めるだけで
  qualification receipt の受理集合が広がりうる。これは provenance の粒度の問題ではなく
  受理境界の問題であり、規律 2 の側に入る。
- schema を含む列挙 closure の live bytes 照合は D1417 が既に採っており、同型の先例がある。
- 保証を謳いながら発火しない検査を残すと、恒真な保証が 1 つ増える。

**却下した選択肢:**
- 現状のまま射程を明記する — 受理集合が黙って広がる経路が残る。
- bytes 級の完全な provenance へ広げる — 粗い provenance の既定方針を超える。

## {{D:closure-second-layer-needs-reachability-survey}}. enforcement source closure の第 2 層は到達性調査の後に決める

**決定 (ユーザー裁定):** enforcement source closure を残り 69 module へ広げるか、
収載を止めて文言を実態へ合わせるかは、**今は決めない。**
先に 69 module の production 到達性と受理判定への寄与を実測し、その結果を持って改めて諮る。

**理由:**
- 第 1 層 62 path の代償 (受入検査 190 件増、closure member を編集するたびに epoch が動く) は
  実測されているが、広げる側の便益にあたる「残り 69 module が受理判定にどう効くか」の実測がない。
  片側だけの実測で決めると、代償の大きい方へ倒れる。
- closure を闇雲に広げて大量の無関係な赤を生んだ実測と、外すには対象 producer を実際に
  起動して確かめる必要があるという実測の両方が既にある。どちらの罠も到達性が分かれば避けられる。

**却下した選択肢:**
- 全 131 へ広げる — 便益の実測がないまま代償だけが確定する。
- 収載を止めて文言で閉じる — 推移閉包を名乗れなくなる範囲を、根拠なしに固定する。

## {{D:b10-resume-binding-conditional-and-status-quo}}. 計測値読み取りコードの束縛は改訂と同梱し、記録された commit 名は非認証のまま残す

**決定 (ユーザー裁定):** B-10 の再開束縛で残った 2 件を次のとおり確定する。

1. **計測値を読む 2 file (throughput の読み取りと安定性判定) の内容束縛は、
   B-10 の事前登録を改訂することになった場合に限り、その同じ改訂へ同梱する。**
   改訂が起きないなら現状のまま据え置き、**分割走の間は当該 2 file を編集しない運用制約**を
   投入手順へ明記する。射程を B-10 に閉じ、全 campaign の再開条件は厳しくしない。
2. **過去のブロック記録に載る投入時 commit と解析時 commit は、非認証の provenance 情報のまま残す。**
   receipt の bytes ハッシュ照合はそのまま維持する。

**理由:**
- 1 について。親の初版は「分割走の最中に読み取りコードを書き換える運用が存在しない」を根拠に
  現状維持を推奨したが、**workload ごとに 3 本へ分け、重い条件だけを後から投げる形を採る以上、
  投入の間隔が開き窓は実際に開く。** 一方で束縛を足すと事前登録文書の列挙と実装がずれ、
  文書の改訂が要る。改訂は登録内容のハッシュを動かし、完走済みの分が集約から外れうる。
  したがって改訂が起きる回に相乗りさせるのが、両方の代償を避ける唯一の置き方である。
- 2 について。除去する前も現在の HEAD と比べていただけで真正性は担保していなかった。
  守る対象が測定値でも correctness でもなく、記録された値と検証された値の区別を明記すれば足りる。

**却下した選択肢:**
- 2 file を contract-loader 閉包へ足す — 射程が B-10 を超え、無関係な campaign の再開まで止まる。
- 1 を無条件に現状維持する — 分割投入で窓が開くという実体を無視する。
- 記録された commit 名を receipt へ束縛して認証する — 守る対象が測定値でも correctness でもない。

## {{D:upstream-contribution-deferred-until-correctness-and-mechanism}}. adaptive backoff の定数の上流還元は、正しさ検査と機序の確認まで行わない

**決定 (ユーザー裁定):** CCBench 上流へ adaptive backoff の定数を還元する作業は**今は行わない。**
還元候補は単一の刻み定数から更新間隔と刻みの組み合わせへ変わったが、判断は変わらない。

**理由:**
- 材料に明記された限界が 3 つとも残っている — 単一環境でしか測っていない、
  正しさの検査を通していない、機序の直接確認が済んでいない。
- 既存の決定が確定したのは、既定値のままの適応 backoff を単独の基準線に使わないことまでであり、
  上流の既定値を変えることまでは裁定していない。
- 定数の符号化を取り違えると別の条件を測ってしまう実測が既にある。正しさ未検査のまま
  外部へ既定値の変更として出す根拠が足りない。

**却下した選択肢:**
- 今の材料のまま還元する — 上の 3 つの限界を伏せるか、変更提案として出せない添え書きが要る。
- 還元しないと終端する — 限界が解ければ還元する価値のある観測である。

**再訪条件:** 調整済み設定に対する直列性の検査が通り、かつ非単調性の機序の直接確認が済んだとき。

## {{D:rulings-must-subject-match-live-wave-fragments}}. 稼働 wave の未 land fragment から拾った裁定待ちも、索引前に台帳で主題照合する

**決定:** rulings の収集で、稼働 branch の未 land fragment から未採番の裁定待ちを拾うときは、
**索引へ載せる前に decisions で主題照合する。** 照合で決着済みと分かった項は索引へ載せず、
除外の記録に出所と決定番号を書く。

**理由:**
- 2026-09-02 第 3 回で、未 land の稼働 wave の fragment から拾った 1 件が、
  **既に台帳で同内容を裁定済み**だった。fragment は wave の作業時点で書かれるため、
  その後に land した決定を知らない。別系統モデル 2 レーンが独立にこれを指摘し、
  親が現物で追認した。
- 既存の収集規則は、insights と項本文については主題照合を求めていた (D1335) が、
  稼働 wave の未 land fragment を索引源に加える節にはこの但し書きが無かった。
  fragment は canonical 台帳より古くなりうるという点で insights と同じ性質を持つ。

**却下した選択肢:**
- 未 land fragment を索引源から外す — 稼働 wave にしか無い真の裁定待ちを落とす。
- 全項の全文を毎回突き合わせる — 索引規模に対して成立しない。
