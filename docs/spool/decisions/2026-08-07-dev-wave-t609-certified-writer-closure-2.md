## {{D:certified-writer-sink-authorization}}. 認可は呼び手ではなく certified を書く実体で強制する

**決定:** 環境契約による認可は `pipeline.evaluate` — certified 判定と WAL COMMIT を実際に書く
関数 — の必須 keyword-only 引数として強制する。上位の campaign ループ側だけで強制しない。
検査は exact 型・registry 同値・実行値の完全一致・計算ノードでの exact-Pegasus・
build selector との同値の 5 条件を持ち、layout / WAL / build のいずれよりも前に走る。

**理由:**
- 呼び手を列挙して塞ぐ方式は、列挙から漏れた経路と将来追加される経路を覆えない。実測では、
  campaign ループを通らずに評価関数を直接呼ぶ production 経路が screening driver・
  直接比較 driver に実在し、閉包対象として名指しされた driver 自身がその両方を持っていた。
- sink で必須引数にすると、新しい呼び手は認可を渡さない限り Python の signature 段階で
  止まる。閉包の維持がレビュー規律ではなく型で担保される。
- registry 同値を要求しないと、呼び手が自分で組み立てた契約で自分を認可でき、gate は
  ほぼ恒真になる。自己署名を排除して初めて「登録済み環境で走った」と言える。
- 実行値の比較で未指定と解決済みの空値を同一視すると、`numactl` を宣言しない run が
  空 numactl の契約を満たしてしまう。両者は契約型が明示的に区別している概念である。

**却下した選択肢:**
- 既存の build-v2 selector 引数を全呼び手へ渡して兼用する — 同引数は build の新旧プロトコル
  切替を兼ねており、渡すと認可の追加ではなく build 移行が同時に起きる。旧経路で拒否され
  新経路で受理される入力が構成でき、正しさゲートを緩める方向の変化を含む。
- 認可用と build 用で別々の契約を渡せるままにする — 両者が食い違う組合せを作れ、
  認可は登録済み契約で通しつつ build は別契約の名前空間を使える。同値を必須にして塞ぐ。
- 呼び先の signature を調べ、受け取らない相手には認可引数を落として呼ぶ — 注入された
  評価関数を無認可で呼べるようにする fail-open であり、目的そのものを壊す。

## {{D:tests-declare-site-not-inherit}}. テストは実行環境の識別を宣言し、ホストから継承しない

**決定:** テストセッションでは、環境識別が読む入力 (hostname とスケジューラ証拠) を中立値へ
固定し、特定環境の挙動を検査するテストだけが自分で環境を宣言する。環境識別関数そのものは
差し替えない。

**理由:**
- 受入全走は計算ノードへ dispatch されるため、素の実装ではテスト実行中の環境識別が
  計算ノードになる。環境に依存する gate を導入した途端、同じ木・同じ commit でも
  実行場所によって全走の結果が変わる。実際に 110 件が落ちた。
- 関数そのものを差し替えると、注入 seam の同一性を検査している既存テストが壊れる。
  入力側だけを中立化すれば関数オブジェクトは元のまま残り、既存の検査を壊さずに決定性が得られる。
- 環境固有 gate の検出力は、環境を明示宣言する負例テストで維持される。全テストで
  gate を無効化するのとは別物である。

**却下した選択肢:**
- 環境識別を引数として評価関数へ渡す — 過去の裁定で明示的に取り除かれた seam であり、
  その不在を固定する既存テストがある。
- 全走を計算ノードで走らせない — 実行場所は headroom から runner が決めるもので、
  テストの都合で固定できない。
