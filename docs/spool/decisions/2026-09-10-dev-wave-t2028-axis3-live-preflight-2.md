## {{D:axis3-pacing-inherits-axis1-floors}}. 軸 3 の最小 request 間隔は軸 1 の実測下限を継承する

**決定:** 軸 3 の live 経路の host 別最小間隔を、軸 1 が同一ノード・同一 3 索引で実測した下限
(arXiv 3.0 秒、OpenAlex 1.0 秒、DBLP 45.0 秒) から継承し、source literal で固定する。
CLI option・環境変数・catalog 値による上書き経路を作らない。**短くする方向の変更を許さない。**

**理由:**

- 自分で測るには、保護対象である request をまさに送る必要があり循環する。旧登録は最小間隔を
  固定せず「実行段の preflight で測り記録する」とだけ定めているので、継承は登録の裁量内にある。
- 軸 1 の値は同一の送信元ノードから同一の 3 索引に対して production で成立した実績値である。
  軸 1 の実行記録は「DBLP は連続取得で接続を切る。2 秒間隔では 24 リクエスト目付近から、
  15 秒間隔でも 7 リクエスト程度で `RemoteDisconnected`」と観測し、45 分冷却 + 30 秒間隔で
  回復したと記録している。
- 継承しない場合の代替は「無 pacing で流して壊れ方を見る」しかなく、旧登録 §8.4 により
  壊れた query は `未完走` になる。再走上限は 1 回なので、失敗が高くつく。

**却下した選択肢:**

- **軸 3 固有に測り直す** — 測定行為そのものが保護対象を攻撃する。
- **床だけを移植する** — 軸 1 の 45 秒は再試行と 45 分冷却と組で成立していた値であり、
  床だけでは軸 3 の DBLP 1415 本連続に耐えない。冷却も併せて移植する。

## {{D:axis3-n3-observation-is-record-only}}. N3 の間隔観測は記録に留め、受理関門にしない

**決定:** 軸 3 の preflight report に pacing 観測 (最小間隔・実観測間隔・request 意図時刻) を
記録するが、**`observed_interval_seconds` の値を理由に report や取得束を拒否しない。**
検査してよいのは件数と並びの構造整合だけである。再開経由で再導出した観測の実測間隔は
`null` とし、測っていない値を書かない。

**理由:**

- 旧登録 §13.2 は N3 (最小 request 間隔と cooldown) を non-blocking かつ「scheduling のみ」と
  固定している。値を受理条件へ入れると、同じ応答列・同じ行分類でも間隔値だけで成果物が
  拒否されうる。受理集合が動く。
- 意図時刻は秒精度でしか永続化されないので、WAL からの exact 再導出は構造的に不可能である。
  exact 一致を要求する検査は正常な取得束を拒否する。
- pacing が実際に効いたことの正例・負例は、production の受理条件ではなく変異検査で保証する。

**却下した選択肢:**

- **下限未満の観測値で report を拒否する** — N3 を受理集合へ持ち込む。
- **再開時に意図時刻の差を実測間隔として書く** — 測っていない値を測定値として記録する。

## {{D:axis3-retry-transport-only}}. preflight の再試行は通信失敗だけに限る

**決定:** 軸 3 の live preflight で再試行するのは transport 例外 (送信そのものが成立せず、
HTTP status を 1 つも観測していない場合) だけとする。**HTTP 非 200 は再試行せず、その場で行を
`unavailable` に確定して次の行へ進む。** 再試行の上限は登録どおり初回 + 再試行 3 の合計 4 attempt、
backoff は arXiv / OpenAlex が 3-6-12 秒、DBLP が 15-30-60 秒。尽きた行は `unavailable` として
report に残し、走行を落とさない。

**理由:**

- 旧登録 §8.4 は「429・503・空ボディ・通信失敗・再試行上限到達は、その query を `未完走` にする」と
  定める。HTTP 非 200 を再試行すると、再試行 loop が最新 attempt で行の分類を上書きするため、
  429 のあと 200 を得た行が `ready` になる。取得完全性のゲートが緩む。
- 一方、通信失敗を再試行しないと、接続切断 1 回で全走行が落ち、取得束が再開不能になる。
  通信失敗は HTTP status を観測していないので、再試行しても「観測済みの失敗を無かったことに
  する」ことにはならない。
- 上限は登録の逐語に合わせる。旧登録 §8.3 は「その各ページが最大 4 回 (初回 + 再試行 3) 送られる」と
  書いており、合計 3 attempt では登録より 1 回厳しく、3 番目の backoff 値が到達不能になる。

**却下した選択肢:**

- **429 / 503 も再試行する** — 上記の洗濯経路を作る。実際に最小再現で `[429, 200]` の行が
  `ready` になることを確認した。
- **通信失敗も再試行しない** — 接続を切る索引に対して走行が構造的に完走しない。
- **合計 3 attempt に留める** — 登録より厳しく、登録した backoff の 3 番目が死ぬ。
