## {{D:perf-measurement-no-one-shot-enforcement}}. 性能測定に一回性の機械強制を課さない — 要るのは commit ID と環境条件の記録だけ

**決定 (ユーザー裁定):** 性能測定の再実行を、durable 台帳による一回性 key の消費で
**機械的に禁止しない**。性能測定に求める provenance は
**「どの commit ID と、どの環境条件で測ったか」の記録**であって、観測回数の強制ではない。
D434 が置いた「freeze 由来 holdout を実測へ渡す下位境界の一回性台帳」のうち、
**測定の反復を拒否する部分を撤廃する**。

1. **同じ cell を何度でも測ってよい。** `(freeze bytes hash, freeze holdout key,
   configuration id, ccbench pin, env tag)` の組で 2 度目の予約を拒否する挙動をやめる。
2. **記録は残す。** 測定ごとに commit ID・環境条件 (env tag・ノード・ccbench pin・protocol)・
   実行時刻を成果物へ書く。台帳は**観測の履歴**として追記を続けてよいが、
   **予約の可否を決める権限を持たない**。
3. **既に消費済みの key は以後の再測定を妨げない。** 2026-08-24 の run が焼いた 12 cell を含む。
4. **途中死した run の復旧に専用機構を要求しない。** 落ちたら測り直す。
   事前割当 attempt registry を復旧の前提条件にしない。
5. **`--confirm-irreversible-pilot-holdout` の承認を性能測定の前提にしない。**
   不可逆な消費が無くなるので、承認すべき対象が無い。

**この決定が変えないもの (絶対規律 2 は緩まない):**

- **holdout の値を見てから選択・凍結・主張を変えることは、引き続き禁止である。**
  守るべきはそこであって、測る回数ではない。certified 選択・再凍結・論文主張が
  「どの測定を使ったか」を名指しする義務は不変で、後から測り直した値へ差し替えることも
  引き続き禁止する。
- verifier の anomaly 判定、正しさゲート、reward hack への防壁は 1 つも触らない。
- **本決定は測定の反復を拒否する関門だけを撤去する。** 正しさゲートではない。

**理由:**

- **性能測定は繰り返しても何も無効化しない。** 無効化が起きるのは「見てから選ぶ」ときだけで、
  それは選択側の規律で守る。観測回数を数える機構は、守りたいものを守らずに
  実測だけを止めていた。
- **ユーザーが繰り返し述べてきた基準は「この commit ID と条件で測りました」という
  参考情報の付与**であり、bytes 級・回数級の強制ではない。一回性の強制は
  D434 / D461 で AI が設計したもので、**ユーザー裁定の marker を持たない**。
- **実害が出た。** 2026-08-24 に途中死した床値 run が 12 cell 全部の key を焼き、
  復旧経路 (事前割当 attempt registry) は 5 日間未着地のままで、
  **床値実測が完全に停止した**。2026-08-27 の再投入も予約段階で
  `holdout cell key was already consumed by another fresh run` で落ちた。
  AI が設計した厳密さが研究の主経路を止めた。
- 「未実行」と記録されていた状態の実体は「**一度走って途中で死に、key だけ焼けて
  成果物が残っていない**」だった。成果物の不在だけを見て未実行と判定していた。

**却下した選択肢:**

- **一回性を残したまま復旧経路を実装する** — 同じ停止が再発する。復旧機構自体が
  新しい停止点になり、それが未着地の間はまた止まる。実際に 5 日間そうなった。
- **pilot だけを一回性の対象外にする** — pilot と official で測定の性質は変わらない。
  区別する根拠が無い。
- **回数上限を緩めて残す** — 上限がある限り、落ちた run が枠を焼く構造は変わらない。

## {{D:measurement-provenance-is-commit-and-conditions}}. 測定の provenance は commit ID と環境条件で足りる

**決定 (ユーザー裁定):** 性能測定の成果物に要求する provenance の水準を
**「どの commit ID で、どの環境条件で測ったか」**に統一する。
これを超える強制 (bytes 級の凍結証拠、観測回数の台帳、不可逆承認の token) を
測定の前提条件として新設しない。

**理由:**

- 論文の主張に要るのは粗い provenance である。読み手が確かめたいのは
  「どの版のコードを、どういう条件で測ったか」であって、観測が何回目かではない。
- 強い provenance を要求する機構は、そのたびに新しい停止点を作る。
  実測が止まる費用は、得られる厳密さに見合わない。
- 環境条件には env tag・実行ノード・ccbench pin・protocol の識別子を含める。
  **計算ノードの個体差は環境条件の差として扱わない** (ユーザー裁定、2026-08-27)。

**この決定が変えないもの:** certified 選択と proof chain が「どの測定を使ったか」を
名指しする義務。測定の provenance を軽くすることと、選択の追跡可能性を捨てることは別である。

**却下した選択肢:**

- **測定ごとに凍結証拠を要求する** — 実測を止める費用が主目的から遠い。
- **provenance を書かない** — どの版で測ったか分からない値は比較に使えない。

## {{D:compute-nodes-are-one-environment}}. 計算ノードはどこへ飛んでも同一の計算環境とみなす

**決定 (ユーザー裁定):** 同一クラスタの計算ノードは、**どのノードへ割り当てられても
同一の計算環境**とみなす。測定の設計・判定・主張において、ノードの個体差を
交絡要因として扱わない。ノードを揃えた対測定を、所要や性能の主張の前提条件にしない。

**理由:**

- ノードは同一仕様で運用されており、割当先を選べない環境で「揃える」ことを前提にすると、
  測定そのものが投入できなくなる。
- ノード差を交絡として扱う運用は、実際に測定を止めた
  (2026-08-26 の受入分割数の議論で、実測が撤回されかけた)。

**この決定が変えないもの:** 環境条件の**記録**は続ける。実行ノード名は成果物へ残す。
記録することと、判定の前提条件にすることは別である。

**却下した選択肢:**

- **ノードを揃えた対測定を前提にする** — 割当先を選べないため、前提が満たせない。
- **ノード差を測ってから決める** — 測るための測定がまた止まる。
