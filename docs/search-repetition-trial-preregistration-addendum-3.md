本節と §2 の値はすべて **試走 (各 cell n = 3、分類なし)** の記述である (本登録 §8.4)。

## 3. §8.2 の規模

δ = ln 1.03、M = 10 |Q|、h(n) = t(1 − 0.025/M, n − 1) × s_plan / √n。n は下限 5 からの最小値。C(n) は式の値 (bal・rh に wh の c を代入) と換算を並べる (node 時間)。

| Q | M | 第 1 段 n₁ (h ≤ δ/2) | C(n₁) 式 / 換算 | 第 2 段 n₂ (h ≤ ln 1.05) | C(n₂) 式 / 換算 |
|---|---:|---:|---|---:|---|
| {S1-wh} | 10 | 60 | 663.3 | 10 | **110.5** |
| {S1-wh, S1-bal} | 20 | 69 | 1,525.5 / 2,368〜2,457 | 11 | 243.2 / 378〜392 |
| {S1-wh, S1-rh} | 20 | 69 | 1,525.5 / 5,015〜5,078 | 11 | 243.2 / 799〜809 |
| {S1-wh, S1-bal, S1-rh} | 30 | 75 | 2,487.2 / 7,196〜7,361 | 12 | 398.0 / 1,151〜1,178 |

h(n) は計画上の半幅で、得られる区間幅や分類の確率を保証しない (本登録 §8.2)。

## 4. 課題の集合 Q の選択 (本登録 §8.4)

**Q = {S1-wh} を選ぶ。** 理由は費用・分散・実行可能性・失敗の種類だけである。

- 費用: 第 2 段で 110.5 node 時間。bal を足すと式で 243.2、直列検査の換算で 378〜392 node 時間になり、rh を含む案は換算で約 799〜809 (wh + rh)・1,151〜1,178 (3 課題) node 時間になる。
- 分散: s_plan は S1-wh の試走だけから作った値で、bal・rh への流用は未検証の外挿である。
- 実行可能性と失敗の種類: bal・rh の評価は固定 commit では直列検査 + 静定待ち上限 20 秒になる。この組み合わせで旧 block 1 は stock 12 session 中 5 件が静定の時間切れで
  品質欠測になった (追補 2 §1・§3)。bal・rh の検査の同時化と静定上限は追補 2 §7 のとおり別の追補を要し、本書の時点で登録されていない。
- 結論は S1-wh に限り、S1 の他の workload や他の空間を代表する結果とは書かない。E_T の族も S1-wh だけになる (追補 1 §4.3)。

**系列数 n は C_max で決まる** (本登録 §8.2)。Q = {S1-wh} では、C(60) = 663.263 ≤ C_max なら n = 60 (第 1 段)、C(10) = 110.544 ≤ C_max < 663.263 なら **n = 10 (第 2 段)**、
C_max < 110.544 なら n を縮めて走らせず、本登録 §8.2 の 3 のとおりユーザーへ返す。境界の判定は丸め前の C(n) (39,795.774 s × n / 3,600) で行う。本登録の提案値 C_max = 510 node 時間では n = 10 になる。
**第 2 段を選んだ場合: 計画精度の上では、実用上同等の分類はほとんど得られない** (本登録 §8.2 の 2)。n = 10・M = 10 の計画半幅 h(10) = 0.0454 (約 ±4.6%) である。

## 5. 本比較の固定値

- **系列番号:** R = 100 + b (b = 1..n は block 番号)。試走の 1〜3 と smoke の 9 と重ならない (追補 1 §3)。block b には各手法の系列 R = 100 + b を 1 本ずつと block job 1 本を置く。
- **cohort** `t2850-main-v1`。**投入順:** block ごとに識別子 `<課題>|<arm>|s<b>` と `<課題>|block|s<b>` を辞書順に並べ、鍵 `t2850-main-order-v1|<b>` で本登録 §4 と同じ手順で並べ替える。
  block 間の間隔は置かない (追補 2 §4)。
- **実装:** 試走 v2 と同じ commit `299aa022e` の repo 外 checkout で、評価の実行方法 (write-heavy の同時検査・初回静定上限 120 秒) も試走 v2 と同じにする。
  比較 harness・生成器・`pipeline.py` は、この commit と本書を起草した時点の local main とで同一の bytes である。
- **walltime:** 系列 job 24:00:00 (全 arm 同じ)、block job 08:53:30。試走 v2 の最大所要は系列 18,376 秒・block job 2,359 秒で、どちらも覆う。LLM 系列が A = 30 を
  使い切る場合や障害時の完走は保証しない。walltime の不足は系列の定義や正しさの条件を下げる理由にしない (本登録 §4)。
- **trace の保全:** 本比較のすべての job で、qsub の env に `IZANAGI_TRACE_ARCHIVE_ROOT` (絶対 path) を渡し、検証 1 反復ごとの trace を保全する
  ([T-2853] (1'') の opt-in、D2233)。保全の成否は評価の結果・正しさの判定を変えない。保全先の実 path は発効の決定に書く。
- **LLM 親の同時本数:** 投入済みで series-end の無い LLM 系列 (= 稼働中の親) を常に 4 本以下にする (D2216)。LLM 系列の job の投入と親の config への追加を、
  先の系列の series-end を見て段階的に行う。これは投入者の手順であり、glue が機械的に強制するものではない。

## 6. 案 (a) (LLM の待ちを node の外へ) の判定 — 設計しない

依頼の条件は「試走の実測で、残る待ちの node 時間が導入費を上回るときだけ設計する」である。

- node 上の待ちは、試走の中央値を外挿すると Q = {S1-wh}・n = 10 で 10 × ℓ(wh) = 26.65 node 時間 (C(10) の約 24%)。これは試走の待ちの外挿であって、
  回収できる量の実測ではない (最初の提案待ちや、job を分けたときの追加の準備時間は残る)。
- 導入費は未測定である。実行方法を変えると (評価ごとの job への分割、LLM だけの分割、1 node への複数系列の同居のどれでも)、本登録 §3.1 と追補 2 §5 の先例により、
  試走 v2 の分散と T_c を変更後の構成へ引き継げず試走のやり直しが要る。これに実装・検査・smoke と追加 job の準備時間が加わる (現方式の試走の実績は 28.70 node 時間)。
  LLM だけを分けると、系列内の node の混在と経過時間の意味が手法間で揃わない。
- 残る待ちが導入費を上回ることを実測で示せないので、本比較の前には設計しない。本比較は試走 v2 と同じ実行方法で走らせる。
