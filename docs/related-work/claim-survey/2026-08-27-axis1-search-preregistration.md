## 2. cutoff — 索引固有の日付欄へ共有の暦境界を当てる

**「同一 cutoff」を日単位で 3 索引に課すことはできない。** DBLP には日付の範囲指定が無く、
年 facet しか無い (§4 の実測)。日単位を要求したままでは `RW3` に到達できない。

そこで母集合の時間境界を次のとおり定義する。

> **上限境界 = 暦年境界 2026-12-31。** 各索引は自分の日付欄にこの同じ暦境界を当てる。
> - arXiv: `submittedDate` が `202612312359` 以前
> - OpenAlex: `to_publication_date=2026-12-31`
> - DBLP: `year` facet が 2026 以下
>
> **下限境界は置かない** (古い CC 文献を落とさないため)。
>
> **実効的な上限は取得日時である。** どの索引も、取得の瞬間に存在しないレコードは返せない。
> 上限境界が実際に働くのは、**取得時点で未来の日付を持つレコード** (OpenAlex の in-press、
> DBLP の先付け年) を 3 索引から一様に落とす場面だけである。

**したがって母集合は「同じ概念の検索結果」ではなく、「索引別に凍結した操作的 query の
返却集合の和」である。** 3 索引は語の意味論が違い (§4)、同じ語列を渡しても同じ集合にはならない。
**この文書および下流の成果物は「同一 cutoff の 3 索引の和集合」という短縮を使ってはならない。**
使う定型は **「索引固有の日付欄へ共有の暦境界を当てた登録取得集合の和」** とする。

### 3.3 索引ごとの構文と escaping

**構文はすべて 2026-08-27 に実測して通ることを確かめた** (§4)。

- **arXiv:** `search_query` に `(abs:"語" OR abs:"語") AND (...) AND submittedDate:[... TO ...]`。
  句は二重引用符で囲み、パラメータは URL エンコードする。フィールド前置子は `abs:` を使う
  (要旨と題名の双方を狙う枝では `all:`)。
  **arXiv は送った `submittedDate:[A TO B]` を `submittedDate:"A TO B"` へ書き換えて
  echo する。** これは正常であり、照合は echo された正規形に対して行う。
- **OpenAlex:** `filter=title_and_abstract.search:("語" OR "語") AND ("語" OR "語")` に
  `,to_publication_date:2026-12-31` を連結する。語はステミングされる。
- **DBLP:** `q=語|語 語|語` (空白が AND、`|` が OR)。**語は前方一致へ展開される。**
  年 facet は `year:YYYY:` を連ねる。

### 4.3 ページングと黙った切り詰め

- **arXiv:** `max_results=200` を要求して 200 entry・`itemsPerPage` 200 が返る (要求どおり)。
  `startIndex` で位置を確認できる。
- **OpenAlex:** `per-page=200` と `cursor=*` が機能し、`meta.next_cursor` が返る。
- **DBLP:** **要求超過を黙って切り詰める。** 同じ query (`@total` 4644) に対し
  `h=50` は `@sent` 50 を返すが、**`h=1000` も `h=1001` も `@sent` 100 を返す。**
  エラーは出ない。1 リクエスト 100 件が実効上限であり、`f` (offset) で送る。
  **`@sent` と要求 `h` を毎回突き合わせない限り、切り詰めに気づけない。**

## 5. 和集合、主キー、alias、重複除去

- **主キーは arXiv ID または DOI とする。名称で引かない** (7.7.6)。
- **3 索引は arXiv DOI で接続できる。** DBLP は arXiv プレプリントを CoRR エントリとして
  採録しており、`10.48550/ARXIV.2404.13359` を持つ。OpenAlex は同じ論文を
  `https://doi.org/10.48550/arxiv.2404.13359` として持つ。
- **DOI は正規化してから突き合わせる** — `https://doi.org/` の前置を除去し、小文字化する。
  **正規化せずに文字列一致を取ると 0 件になり、「片方の索引に無い」と誤読する。**
- **題名一致だけの重複除去を禁じる** (7.7.6)。
- **記録は 2 段にする。**
  - **record 台帳:** 索引が返したレコードを 1 つも落とさずそのまま持つ。完全性はここで数える。
  - **work-family 台帳:** DOI・arXiv の DOI 欄・DBLP の `ee`・著者・版履歴の複数証拠で
    `work-family-id` を付ける。**共有識別子が無ければ自動統合せず `要裁定` とする。**
- **件数の単位を混ぜない。** 取得完全性は record 数、重複除去後は work-family 数、
  主張表は研究数で数え、変換の対応表と未解決 family 数を残す。**単位の違う数を足さない。**
- **alias レコード:** 旧題・新題・略称・改名前後を 1 つの alias レコードへ束ねる。
  既知の実例は `2503.10036` — `CCaaLF` は v4 で
  `Modeling Concurrency Control as a Learnable Function` へ改題され `NeurCC` へ改名された。

## 6. positive control と補助探索

### 6.1 positive control は演算子と概念ブロックに置く

**未知の交点ごとに既知アンカーを要求してはならない。** 「CC を対象にアクション空間を
拡張する研究」の既知例が無いことを調べたい枝に、その完全一致アンカーを必須にすると、
未検出を調べる前提として検出例を要求することになり、`RW3` が循環的に到達不能になる。

したがって control は **検索演算子と概念ブロック**に置く。

| control | 確かめること |
|---|---|
| `C-OP-1` | 句検索が機能する (既知の句を含む論文が返る) |
| `C-OP-2` | OR が機能する (片方の語だけを含む論文が返る) |
| `C-OP-3` | AND が機能する (片方だけの論文が返らない) |
| `C-OP-4` | 日付境界が機能する (境界の外の既知論文が返らない) |
| `C-BLK-T` | ブロック T が既知の CC 論文を返す |
| `C-BLK-M` | ブロック M が既知の合成論文を返す |
| `C-BLK-V` | ブロック V が既知の検証論文を返す |
| `C-BLK-W` | ブロック W が既知のワークロード条件づけ論文を返す |

既知アンカー (主キーで指定する): `2105.10329` (Polyjuice) / `2503.10036` (CCaaLF→NeurCC) /
`2603.13906` (ATCC) / `2009.11558` (CCBench) / `2404.13359` (DCDS)。
**3 索引すべてで、この 5 件が主キーで到達できることを実行前に確かめる。**
到達できない索引があれば、その索引についてはその事実を記録し、母集合から黙って外さない。

### 6.2 control の通過は根拠にならない (D351)

**D351 は「gate の通過を根拠にしてはならない」と裁定している** — 陽性対照の hit を残したまま
通常形式の hit を落とす式が書けるからである。したがって control に加えて次を課す。

> **感度監査:** §6.3 の補助経路で得た候補も全件を台帳へ入れる。
> **包含条件を満たす候補が主 query の和集合に無ければ、その走行を無効とする。**

**これは構造的証明ではなく、有限の感度監査である。** D384 が言うとおり有限観測は
普遍性を含意しない。文献検索には、コード検索の厳格 parser に相当する「安価側と高価側が
同じ意味論を通る」構造がないので、根拠を構造的制約に置くことができない。
**この限界を落として `RW3` を語ってはならない。**

### 6.3 補助探索の有限化

補助経路は結果を見る前に有限値で固定する。

| 経路 | 起点 | 上限 |
|---|---|---|
| 後方引用 (参考文献) | §6.1 の既知アンカー 5 件 | 1 hop |
| 前方引用 (被引用) | 同上 | 1 hop、1 起点あたり最大 200 件 |

## 7. 完走述語 — 「全件取得した」の機械的な定義

**保存項目を並べるだけでは完走の判定にならない。** 各 (枝, 索引) について、次の全部が成立した
ときに限りその query を `完走` とする。

1. **解釈照合:** 送信した request bytes と、索引が返した解釈後クエリ (§4.1) が、
   事前登録した期待値と一致する。
2. **連続性:** arXiv は `startIndex` が、OpenAlex は cursor 連鎖が、DBLP は `f` が、
   欠落も重複もなく連続している。
3. **宣言と実数の一致:** 各ページについて、要求件数・索引が宣言した件数
   (`itemsPerPage` / `per_page` / `@sent`)・実際の要素数が一致する。
   **DBLP はここで切り詰めを検出する。**
4. **主キー重複なし:** ページ内・ページ間で主キーの重複がない。
5. **総数一致:** unique record 数が、索引が返した総件数フィールドの値と一致する。
6. **正常終端:** 最終ページが正常に終わり、HTTP status・content type・必須要素
   (arXiv は `<opensearch:totalResults>`、OpenAlex は `meta.count`、DBLP は `hits.@total`)
   がすべて存在する。

**軸 1 が `RW3` を名乗れるのは、登録した全 18 個の query ID が `完走` で、
かつ §6.2 の感度監査が無効化しなかったときだけである。** 論理積であり、部分積ではない。

**0 件そのものは走行無効の理由にしない。** 正しい query が真に空集合を返すこともあるからである。
誤設定は 1 の解釈照合と §6 の control で検査する。

  枝を足さない。**「新しい候補が出る間だけ続ける」型の停止条件を禁じる。**
- **再試行上限:** 1 リクエストあたり 3 回 (バックオフ 3→6→12 秒)。超えたらその走行は `未完走`。
- **予算切れ・429・通信失敗・再試行上限到達は、いずれも軸全体を `未完走` にする。**
  完走した枝だけを取り出して軸の成熟度を名乗ってはならない。
  部分結果から書いてよいのは、**完全に完走した単一 (枝, 索引) についての内部的な取得報告だけ**で、
  そこに不在の表現を置いてはならない。
- **窓をまたぐ実行:** OpenAlex の無償枠は 1 窓 100 リクエストなので、実行は複数窓に分かれうる。
  **preflight を必ず置く** — 各枝の初回応答の総件数から所要リクエスト数を算出し、
  窓単位の実行計画を登録してから本取得に入る。
  窓をまたぐ枝は、開始時と終了時に総件数を再確認し、**変化していたらその枝を最初から再走する。**
- **索引スナップショットの不一致:** 3 索引とも snapshot token を提供しない。
  件数が同じままレコードが 1 件入れ替わる変化は件数比較では検出できない。
  **枝ごとに unique 主キー集合の digest を保存する**ことで部分的に補い、
  **補えない範囲は限界として記録する。**
- **死んだ式の扱い (非意味的修繕と意味的 amendment の境界):**
  - **非意味的修繕:** request bytes だけが変わり、索引が返す解釈後クエリが事前登録の期待値と
    同一であると確認できる変更。これは同じ query ID のまま行ってよい。
  - **意味的 amendment:** それ以外すべて。旧走行を `未完走` に固定し、
    **新しい日付の amendment 文書・新しい query ID・全枝の再実行**を要求する。
    **旧結果を見た後の改訂であることを amendment に明記する。**

## 10. 実行の記録 (別の凍結物が持つ)

**本文書に実行値を書き戻してはならない。** 実行は新しい日付の凍結物
(`claim-survey/<日付>-axis1-search-execution.md` を想定) が持ち、次を record 単位で保存する。

| field | 中身 |
|---|---|
| `query_id` | `AX1-Q<n>[b]@<索引>` |
| `request` | 送信した完全な request (URL とパラメータ、escaping 込み) |
| `interpreted_query` | 索引が返した解釈後クエリ (§4.1) |
| `expected_interpreted_query` | 本文書が登録した期待値 |
| `retrieved_at` | 取得日時 (UTC と JST) |
| `api_identification` | endpoint と応答 schema の識別 (3 索引とも版番号を返さないため) |
| `declared_total` | 索引が返した総件数 |
| `pages` | ページ数と各ページの要求件数・宣言件数・実要素数 |
| `retrieved_unique` | 重複除去前の unique record 数 |
| `primary_key_digest` | unique 主キー集合の digest |
| `completion` | §7 の 6 条件それぞれの成否 |
| `failure` | 429 / 503 / 空ボディ / 予算切れ / 再試行上限 の別 |

候補判定は全件について `検出` / `近傍` / `除外` / `要裁定` / `未完走` を付け、
除外には理由コードを添え、**題名だけで除外しない。要旨が取れない・本文確認が要るものは
`要裁定` とする。** 補助探索由来の候補は主 query 由来と区別して記録する。

## 12. この登録自身の限界

- **3 索引とも API の版番号を返さない。** 版の束縛は endpoint と応答 schema の識別で代用する。
  索引の内容は本文書の凍結後に変わりうる。

  今回再測していない項目がある** (§4.4 に明記した)。
