## 2. 新しい登録 epoch と query ID

登録 epoch は `AX1-20260902-E1` とする。ID の一般形は旧改訂 §3.1 と同じである。

```text
AX1-20260902-E1-<branch>[-S<shard>]@<index>
```

- `<branch>` は `Q1`〜`Q6` (arXiv / OpenAlex) または `T01`〜`T12` (DBLP)。
- `<index>` は `arxiv` / `openalex` / `dblp`。
- **`-S...` を持つ ID だけが HTTP を発行する leaf である。**
- shard 記法は暦年が `SYyyyy`、暦月が `SMyyyymm`、下限側が `SPRE1991`。

**旧 epoch `AX1-20260829-E1` の ID は 1 つも継続しない。** 登録 ID の総数、枝の構成、shard 境界は
旧改訂 §3.6 のままである — logical 267、実行可能 leaf 263、aggregate 3、宣言的除外 1。

**母集合の 1 行は、epoch の名前だけを差し替えて引き継ぐ。**

> 軸 1 の母集合は、共有暦境界 2026-12-31 を各索引固有の日付欄へ当てた登録 epoch
> `AX1-20260902-E1` の query 群 (固定・非重複の日付 shard を含む) が返した、索引固有 work ID
> レコードの和である。境界の外、登録した query と登録した 3 索引の外は母集合の外であり、
> `AX1-20260902-E1-Q6-EXCLUSION@dblp` の 1 枝だけが D1155 の構文能力を理由とする宣言的除外である。
> 取得失敗・無償枠切れ・未実行は除外ではなく `未完走` である。

## 3. 完走述語 — 条件 1 の OpenAlex 節を置き換える

**旧改訂 §7 の 6 条件のうち、条件 1 の OpenAlex 節だけを次で置き換える。**
条件 1 の arXiv / DBLP 節、条件 2 から条件 6、§7.1 の導出式、§7.2 の限定は逐語で引き継ぐ。

> - **OpenAlex は `meta.x_query.oqo` の順序非依存な構造比較**とする。
>   登録した構造と索引が返した構造の**双方に同一の正規化**を当て、正規化後の完全一致を要求する。
>   **正規化が無視してよいのは、論理積または論理和として結合される兄弟要素の順序だけである。**
>   次はいずれも保存し、差があれば `否` とする。
>   - 同一要素の**多重度**。同じ filter が 2 回現れることと 1 回現れることを区別する。
>   - **入れ子の境界と深さ。** グループを平坦化しない。1 個のグループに包まれた 3 要素と、
>     平坦に並んだ 3 要素は別物である。
>   - グループの **`join` の値。** `and` と `or` を区別する。
>   - 各 filter の **field の有無と型。** 欠落・`null`・空文字列・数値・文字列を区別する。
>   - `get_rows` の値。
>
>   **`and` / `or` 以外の `join`、登録していない key、想定外の型が現れた場合は、
>   両側が同じ形であっても `否` とする (fail-closed)。** 未知の形を「同じなら可」と扱うと、
>   索引が意味を変えた場合に気づけない。
>
>   **同一 object 内に同じ key が 2 回以上現れる応答は `否` とする。**
>   JSON の素朴な読み取りは重複 key を後勝ちで潰すため、これを許すと
>   `{"join":"xor","join":"or",...}` が `{"join":"or",...}` として読まれ、
>   直前の fail-closed 条項が生応答経由で迂回される。**この拒否は条項の一部である。**
>
>   `meta.x_query.oql` の生文字列は証拠として保存するが**判定には使わない** — 旧改訂 §4.4 の
>   実測のとおり、複合 filter の `oql` は改行とインデントを含む整形済み文字列であり、
>   空白正規化だけで安定に一致させられないためである。

**この置換は受理集合を「兄弟の順序だけ」広げる。** 値・多重度・入れ子・`join`・型のいずれかが
違う応答は、置換の前後どちらでも `否` である。**条件 2 から条件 6 は 1 文字も緩めていない。**

## 7. この改訂自身の限界

旧改訂 §12 の限界を引き継ぎ、次を足す。

- **「索引が順序を正規化する」という主張の根拠は、旧走行が観測した 92 頁である。**
  OpenAlex API の恒久契約としては断定しない。索引が将来べつの正規化を加える可能性は排除しない。
- **`and` / `or` 以外の `join` を実際に観測したことはない。** §3 の fail-closed 条項は
  観測に基づく要求ではなく、未知の形を黙って受理しないための設計である。
- **順序差の実測資料は内部に食い違いを持つ** (§0.1)。計数 3 欄と旧実行記録は 92 頁、
  同 file の記述欄だけが 78 頁と書く。元の診断走行は削除済みで再導出できない。
- **本再改訂は取得を 1 件も行っていない。** 条件 1 が実際に `可` を返すことは、
  新 epoch の走行が出るまで確認されない。
- **旧走行で完走した 183 leaf の再取得費用を本文書は見積もっていない。**
  再取得の計画は実行側の記録が持つ。
- **新走行が新規 bundle を使うことを実装は強制しない。** 実行器の `--bundle` は任意の path を
  受け、無償枠の観測は渡された bundle 内の `state/runtime.json` から読まれる。
  旧 bundle を渡すと旧 epoch の持続状態を引き継ぐ。**運用で守るべき要件である。**
- **旧走行の生応答を新 epoch の証拠へ再包装する経路を、検査器は拒否しない。**
  検査器は catalog digest・再導出 request・生応答の内容を検証するが、
  「その生応答が登録 commit の後に取得された」という外部の事実を検証しない。
  証拠の時点を外部の事実へ束縛する方式 (受領証・nonce・追記専用の登録) は本再改訂には無い。
  **§4 の禁止は規範であって機械保証ではない。**
- **本再改訂の後、旧 epoch の bundle は現行の検査器では検証できない。**
  schema の登録 epoch と既定 catalog path を新値へ更新するため、旧 bundle は epoch の
  const で落ちる。旧 bundle を検証したい場合は旧 commit を checkout する。
  版ごとの schema を並存させる設計は本再改訂では採らない。
- **条件 1 の新しい比較は、未知の `join`・登録外の key・想定外の型を拒否する。**
  したがって受理集合は「兄弟の順序」の面では広がるが、未知の形の面では狭くなる。
  **無条件の緩和ではない。** これは意図した fail-closed である。
- **分類・work-family 統合・control・補助探索・感度監査の schema 層は本再改訂でも実装しない。**
  旧 §7.1 の導出式により、未実装層がある限り `axis_complete` は偽である。
