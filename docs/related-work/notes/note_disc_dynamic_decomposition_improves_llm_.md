## 問題設定 / 一言要約

推論スケーリング（inference scaling）の多くは「問題をステップに分解 → 各ステップでサンプル → 良い次手を選ぶ」構造を持つが、そのステップ境界と大きさが **事前定義またはドメイン知識による手設計（static decomposition）** に依存している。DISC は、解答・推論トレースを **推論中に動的・自動で分割**（dynamic decomposition）し、難しいステップを細かく刻んでそこにサンプリング計算を集中させることで、サンプル効率・トークン効率・実行時間を同時に改善する再帰的アルゴリズム。人手監督・ドメインヒューリスティック・プロンプト工学・プロセス報酬モデル（PRM）を **一切要求しない** のが売り。

一言でいえば「**探索の分解粒度を、固定せずに『難所ほど細かく』と自動で動かし、計算を難所に寄せる**」手法。

## 手法の核（具体的に）

1. **動的分解 = 難易度適応のステップサイズ制御**。プレフィックスが報酬改善を示せば大きく前進し、示さなければステップを縮めてその周辺にサンプリングを集中する。「LLM にとって易しい所（人間には難しく見えても）に計算を浪費し、難所を undersample する」という static 手法の失敗を避ける。

2. **Greedy 版アルゴリズム (Alg.1)**。入力は LLM π、報酬モデル R、プロンプト x、初期分割率 α₀、閾値 σ、サンプル予算 N。ベースプレフィックス p_b から完了 y=p_b·s をサンプルし報酬を計算。累積報酬が σ を超えたらサンプル停止（`M = min{m | Σ R(yᵢ) ≥ σ}`）——量と質のバランスを取る早期停止。

3. **候補プレフィックスと z-score 受理規準**。最良サフィックス s* の先頭 α 割（トークン単位）を p_b に付けて候補 p_c を作る。報酬が location-scale 族（例: ガウス）に従うと仮定すると、`Pr(改善) = 1 − CDF(z)` なので **z-score が低いほど改善確率が高い**。候補の z が現ベースの z より低ければ受理。受理→ p_b←p_c、α を α₀ にリセット。棄却→ α←α·α₀ と **分割率を縮める**（再帰的リファインメント）。予算枯渇か正解到達まで反復。

4. **critical intermediate step の自動同定**。分解の副産物として、"which"／"therefore"／"wait" のような人間には些末に見える遷移語を、autoregressive LLM にとっての **重要な分岐点（reasoning fork/pivot）** として自動検出。手設計でなく LLM データから critical step を見つける点が主張の一つ。

5. **探索アルゴリズムと plug-and-play**。DISC は「分解（ノード/エッジの構築）」であって「探索（どの枝を辿るか）」ではない、と明確に分離。ExpandNode/MakeChildren 演算子として一般化し、greedy / beam / MCTS のいずれとも組める（Alg.3）。

6. **最小の前提**。スカラーの outcome reward model (ORM) へのアクセスのみが必須。ground-truth verifier が無ければ LLM 自己生成ユニットテストや LLM critique を代理報酬として使える。PRM・手作りプロンプト・ドメインヒューリスティックは不要。

## 主要な実験結果 / 主張（数値）

- **ベンチマーク**: APPS（5000 問中 200 問サブセット、competition レベルが最難）、MATH500（12,500 問中 500 問、ORM は Llama-3.1-8B-Instruct ベース）、LiveCodeBench（汚染回避のため 2024/10/01–12/01 の 108 問）。主モデルは gpt-4o-mini。
- **pass@10 誤り率削減（vs 最良ベースライン）**: APPS 0.50→0.475（**−5.0%**）、MATH500 0.15→0.14（**−6.7%**）、LiveCodeBench 0.57→0.51（**−10.5%**）。難しいベンチほど効く。
- **総括主張**: ベースライン比で **最大 10% の誤り削減**、ベースモデル比で **最大 4x の精度向上**、いずれも **わずか 10 サンプル**で（推論モデルでも）。
- **モデル汎化**: LLaMA pass@10 0.01→0.04（相対 +300%）、Mistral 0.0→0.02、Qwen 0.095→0.17（相対 +79%）。弱いモデルでも効く。
- **推論モデル (R1)**: 10 サンプルで **相対 +85% 超**。単一サンプル分にトークン予算を絞っても **相対 +33% 超**。
- **自己生成検証（ground-truth 無し、自作ユニットテストを代理報酬に）**: ベース比 **相対 +54%**。ただしテストが不完全・偏りうるのは限界。
- **計算オーバーヘッド**: 実行時間の **90% 超は依然 LLM トークン生成**。z-score 正規化・候補管理・再帰分岐は微小。BoN/LineSplit とほぼ同じ実行時間構成。
- **ベースライン**: TokenSplit（トークン単位）、LineSplit（改行単位）、BoN（全体を1ステップ）。
- **アブレーション**: (a) **低温度が有利**（既定 τ=0.2）——BoN と逆。z-score 推定の分散が下がり推定が安定するため。(b) 受理規準は **DISC-Z（低 z 受理）が最良**、DISC-negZ（高 z 受理）はランダム未満。(c) 分割率は **0.15 ≤ α₀ ≤ 0.25** が最適、既定 α₀=0.15・σ=1.0。(d) DISC は実効的に **1–5 の commit ステップ**しか要さず、他手法より少ない分割で高性能。
- **理論**: Theorem 1（最適性）——最適解が π の台にあれば、ある n で base prefix が EOS を含み最適解で停止。ただし「reverse-engineered な強いポリシー仮定」に依存し、インスタンス依存で経験的に確認要（普遍保証ではないと明記）。

## izanagi のどの層・部品に効くか

DISC は「**高コスト評価を伴う探索で、分解粒度と評価予算を難所に動的配分する**」方法論であり、izanagi の探索ループそのものに刺さる。効き所を強→弱で:

- **層2（最適化移植ループ・進化探索）= 最も直結**。izanagi の 1 variant 評価は数十秒（roadmap §5: CCBench 1run 3秒×反復）と高コストで、DISC が解く「どの粒度で試行を刻み、限られた評価予算をどこに寄せるか」がそのまま当てはまる。DISC の「promising なら大きく前進、そうでなければ縮めて周辺に集中」は、変異の粒度制御（パラメータ 1 個だけ動かす vs 複数同時 vs コードブロック丸ごと移植）と評価予算配分の原理として移植可能。

- **評価器 / 予算設計（Phase1）= 直結**。DISC の「累積報酬が σ を超えたらサンプル停止」は、izanagi §3.6 の反復測定（N=5、CV 監視）と **同じ早期停止の思想**。DISC の z-score による「改善確率 = 1−CDF(z)」は、izanagi の「分布比較（noise floor 超えを Mann-Whitney U で有意判定）」の受理規準に理論的な骨格を与える候補。

- **層3（Pareto 選択・説明生成）= 間接的に効く**。DISC の critical step 自動同定（「どのステップが結果を左右したか」を first-order statistics で可視化）は、izanagi の「どの最適化が効いた/効かなかったか」の因果説明の方法論として類似構造。

- **orchestrator / hook = 弱い**。DISC は制御フローの原理であって永続状態・観測者効果分離とは別軸。直接の移植対象ではない。

- **層1（ベース CC 選定）= ほぼ無関係**。DISC は初期個体選定の話ではない。

## 具体的に izanagi に移植できる要素（設計レベル）

1. **難易度適応の変異粒度制御**。DISC の「受理→粗く前進、棄却→細かく」を層2に翻訳: 「low-fidelity proxy スクリーニングで有望 → 大きな変異（複数最適化を束ねる/コードブロック移植）へ前進、伸びない → 粒度を縮めて単一フラグ単位に戻す」という**適応的ステップサイズ**を進化探索に入れる。roadmap の「initial partition fraction を掛け算で縮める」機構をそのまま設計参照にできる。

2. **z-score / 改善確率ベースの受理規準**。izanagi §3.6(4) の分布比較に、DISC の `Pr(改善)=1−CDF(z)` を接続。「variant を採るか」を点比較でなく「ベース分布に対して改善確率が高い方を採る」と定式化でき、noise floor と自然に整合（分散が大きい＝ z が信頼できない＝ unstable フラグ、という接続）。

3. **累積報酬による適応的サンプル停止 (σ 閾値)**。izanagi の反復測定 N を固定せず、「累積シグナルが閾値を超えたら測定を止める」動的予算に置き換える案。安定した variant は早く切り上げ、際どい variant に測定回数を寄せられる。

4. **decomposition と search の明確な分離**。DISC の「分解＝ノード/エッジ構築、探索＝その上の枝選択」という分離は、izanagi の「変異空間の定義（最適化カタログ化）」と「探索戦略（island GA / LLM 誘導）」を概念的に切り分ける設計言語として使える。

5. **critical step 同定 → 説明生成への流用**。「どの最適化 commit が性能を左右したか」を first-order statistics（中央値・CV・改善確率）で色分け提示する層3 レポートの型。DISC の色分け分解図が UI/レポートのメタファーになる。

6. **低温度・低分散が推定を安定させる知見**。LLM に「次の変異」を提案させる（roadmap §3.5 の LLM 誘導）際、統計推定に依存する段では **低温度で分散を抑える方が受理判定が安定** という DISC のアブレーションが指針になる。

## izanagi に入れる際の障害・前提・リスク

- **報酬の性質が違う**。DISC の報酬は [0,1] スカラー ORM で「1トークン列＝1報酬」。izanagi の報酬は throughput 分布（ノイズ大、外乱混入、環境依存）。DISC の location-scale 仮定は spot 報酬には効くが、izanagi の noise floor 下では z-score が「本物の改善」か「ノイズ」かを区別できない。**§3.6 の noise floor 実測を前段に噛ませないと DISC の受理規準は誤作動する**（reward hacking の鏡像＝ノイズを最適化シグナルと誤認、に直結）。
- **「トークン列の prefix」→「variant の系譜」への写像が非自明**。DISC は自己回帰の prefix 連結という滑らかな順序構造を前提にするが、izanagi の variant はコード diff の離散空間で、「prefix を α 割だけ伸ばす」に対応する自然な操作が無い。粒度制御の翻訳には設計上の飛躍がある（本文からは自明な写像は特定できず）。
- **評価コストの絶対値**。DISC のオーバーヘッドが小さいのは「90% が LLM サンプリング」だから。izanagi は 1 評価＝ビルド＋ベンチ（make 時間が乗りうる、roadmap §6）で、DISC 流に「難所で細かくサンプル数を増やす」と評価回数が跋扈する。low-fidelity proxy とバイナリキャッシュ前提が崩れると成立しない。
- **Theorem 1 の仮定は移植不可**。最適性は「最適解が π の台にある」という強い、インスタンス依存の仮定に依存。izanagi の CC 合成では「最適 CC が LLM の生成分布の台にある」保証は無く、理論保証は借りられない（DISC 著者自身も普遍保証ではないと明記）。
- **正しさゲートとの整合**。DISC には izanagi の絶対規律2（正しさゲートを壊す変異は即 reject）に対応する制約が無い。DISC の受理は報酬（性能）のみ駆動。izanagi に載せるなら「z-score 受理の前に正しさゲートを通す」二段構えを維持する必要があり、DISC の単一スカラー受理をそのまま採ってはいけない。

## 小山田さんに聞くべき質問

1. **DISC の z-score 受理規準を、ノイズの大きい throughput 分布（izanagi の noise floor 下）に持ち込むと location-scale 仮定はどこで壊れますか?** DISC が低温度で分散を抑えて推定を安定させたのと同じ発想で、izanagi は「反復測定＋noise floor 固定」で分散を抑えれば `Pr(改善)=1−CDF(z)` を variant 受理に使えると考えていますが、spot 報酬とベンチ分布の違いで注意すべき点は。

2. **DISC の「decomposition と search の分離」を、離散なコード diff 空間（自己回帰 prefix のような順序構造が無い variant 系譜）に写すとき、『ステップサイズを縮める』に対応する自然な操作は何になりますか?** izanagi では「複数最適化の束→単一フラグ」への粒度縮小を候補にしていますが、DISC の設計思想からの示唆は。

3. **critical step 自動同定（どのステップが結果を左右したか）を、izanagi の層3 説明生成——「どの最適化 commit が性能を左右したか」の因果説明——に流用する筋はどう見ますか?** DISC は first-order statistics で pivot を可視化しましたが、CC 合成の説明可能性（本システムの差別化の核心）に同じ枠組みを持ち込む際の落とし穴は。
