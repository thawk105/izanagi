# TPC-C での未知条件への転移 — 段 1・段 2 の学習条件 (錨) と留保条件、留保を生成・選択へ入れない義務、v1 から継承する解析規則を TPC-C の生成・探索・選択の前に固定する事前登録

本書は、VLDB 向け差分分析の P4 (未知条件への転移と再現) を TPC-C で測るための規則を、TPC-C の生成・探索・選択が始まる前に
固定する ([T-2851] の残り (4)、D2212 項 2)。YCSB を扱う事前登録 v1 (`docs/unseen-condition-transfer-preregistration.md`、以下「v1」) は
§14 で、TPC-C の留保を必須の未完項目とし、別の登録で固定するとした。本書がその登録である。固定するのは次の 5 つである。

1. TPC-C の段 1 (NewOrder / Payment) と段 2 (全 5 取引) それぞれの学習条件 (以下「錨」) と、生成・選択に使わない条件
   (以下「留保条件」) の具体値 (§2)。
2. 留保条件を生成・選択へ入れない義務と、測定を始めてよい条件 (§3)。
3. 比較対象 (§4)。
4. v1 から継承する測定・推定・分類・追試・欠測の規則と、TPC-C への置換 (§5)。
5. 正しさの扱い (§6)。

**本書は事前登録の作成だけを行う。** 計算投入、選択結果を使う評価走、runner の実装、gate・検査・台帳の追加は含まない。
本書が存在することは測定の認可にならない。[T-2850] の選択結果も扱わない ([T-2850] は YCSB の探索である)。

段の分割は D2219 項 2、TPC-C の実装の事実と認定の設計は `output/insights/2026-09-21/tpcc-trace-certification-design/README.md`
(以下「設計 README」) による。起草の経緯 (相談 2 本と裁定、レビュー) は `output/insights/2026-09-23/t2851-tpcc-transfer-prereg/README.md` に置く。

## 1. 主張の形と、主張しないこと

### 1.1 主張しうること

成立時に許す主張は、次の**操作的事実**に限る。

> TPC-C の段 s・protocol p の留保条件 c (§2) で、候補 k (段 s の探索が錨 X で選んだもの) の全取引 commit throughput は、
> 強い参照 r (§4) に対し [優越 / 退行 / 実用上同等] だった。2 つの cohort (別日・別割当て) の両方で同じ分類で、分類は段 s の
> cohort ごとの同時信頼区間による。

- 「全取引 commit throughput」は、CCBench の TPC-C binary が報告する値で、同じ取引の生成規則の下で、abort 後の取引種別の再抽選・
  abort・commit 構成の変化をすべて含む。abort した取引は同じ取引を再試行せず、取引種別から引き直す (`include/tpcc.hh` の run と
  `tpcc_query.hh` の decideQueryType)。したがって候補によって commit された取引の構成も変わりうる。同じ cell の中の比 tps_k / tps_r は
  この操作的な比較として成立するが、「同じ業務を速く処理した」とは言わない。
- **勝者交代** の定義は v1 §6.4 と同じで、錨の cell は候補を選んだ錨 X の cell (§2.3 の `s-X-base`) に読み替える。
- 結論は**登録した点での局所的な転移**であり、段の中での転移である。段 1 で選んだ候補を段 2 の cell で測ることは本書の主張に入れない。
- 倉庫数の留保は 2 点 (4 と 16) だけで、どちらも錨の倉庫数 1 と 48 の間にある (内挿)。thread 数と取引構成は錨ごとに上下を置く。
  この非対称を結果の報告に添える。

### 1.2 主張しないこと

v1 §1.2 の各項 (手法単位の優劣、日とノードの効果の分離、stock 比の大きな数字を主結果にすること、正しさの一般的な保証、性能値の
trace 下での意味、同等幅の百分率としての対称性) は本書でも主張しない。加えて次を主張しない。

- **TPC-C 仕様への準拠や tpmC。** 対象は CCBench pin と patch で定まる実装の操作履歴である。設計 README §9 が挙げる仕様との差
  (OrderStatus が最古の order を読む、OrderLine の番号の初期ロードと実行時の食い違い、Delivery が NOT_FOUND を無視して続ける) を含んだまま測る。
- **取引別の改善、構成間の仕事量の等価性。** 取引別の commit 数・abort 数は記述として併記するだけである。段 1 の commit 中の NewOrder 比は、
  生成比 57% とは一致しない (NewOrder の 1% の意図的な abort だけでも 0.57 × 0.99 / (0.57 × 0.99 + 0.43) ≈ 56.75%、競合 abort で更に変わる)。
- **範囲読みの純粋な効果、phantom の検出力、定常状態の性能。** 段 2 の構成の因子は複合変更である (§2.2)。extime 3 s の 1 走は、NewOrder による
  表の成長の途中を測るので、定常状態の証拠にならない。
- **動かさなかった因子の効果。** 1 txn の明細数 (5〜15 の一様)、remote 品目 (1%)、Payment の remote 顧客 (15%) は CCBench の
  コンパイル時の定数で、本書は動かさない。v1 の「1 txn の操作数」と「アクセス集合の重なり」に当たる転移は、TPC-C では測らない (§2.2)。
- **段をまたぐ転移と、TPC-C 全体・YCSB と合わせた単一の誤り率。** 主要族と同時区間は段ごとである (§5)。
- **他環境・他 protocol・他の workload への転移** (§10)。

### 1.3 反例を作ったので書かない文

v1 §1.3 の 4 文に加え、次の 2 文を書かない。

1. **「倉庫数を増やした差は競合を減らした効果である」** — TPC-C の倉庫数は、データ量 (1 倉庫あたり一次表で約 53 万行)、各 thread の
   home warehouse の割当て (`thread_id mod 倉庫数 + 1`、`include/tpcc.hh`)、remote アクセスの有無 (倉庫 1 では remote が無い) を同時に変える。
   → 「倉庫数の変更」として報告し、競合の効果とは書かない。
2. **「範囲読み取引を増やした差は範囲読みの費用の効果である」** — NewOrder の比率は残差なので同時に下がり、Delivery が増えると
   未配送注文の表 (NewOrder 表) の在庫が 3 s の間に減る向きに変わる (§2.2)。→ 「範囲読みを使う 3 取引の生成比率を同時に変える構成変更」として報告する。

## 2. 学習条件と留保条件

### 2.1 錨 (学習条件)

TPC-C には既存の campaign 定義も学習条件も無い (起草時点の local main で `orchestrator/` と `tools/` に TPC-C の引数名は現れない。
trace witness の経路は `ycsb_` 以外の binary を拒否する、`orchestrator/campaign/pipeline.py` の `_TraceWitnessUnsupportedWorkload`)。
そこで本書が錨を定める。段ごとに、高競合を意図した設計点 H と低競合を意図した設計点 L の 2 つを置く。H・L は設計点の名前であって、
競合を測って分類した結果ではない。

| 錨 | 倉庫数 | thread 数 | Payment (%) | OrderStatus / Delivery / StockLevel (%) | NewOrder (%、残差) | think time | extime |
|---|---:|---:|---:|---|---:|---:|---:|
| s1-H | 1 | 48 | 43 | 0 / 0 / 0 | 57 | 0 ms | 3 s |
| s1-L | 48 | 48 | 43 | 0 / 0 / 0 | 57 | 0 ms | 3 s |
| s2-H | 1 | 48 | 43 | 4 / 4 / 4 | 45 | 0 ms | 3 s |
| s2-L | 48 | 48 | 43 | 4 / 4 / 4 | 45 | 0 ms | 3 s |

- CCBench の引数名は、倉庫数 = `tpcc_num_wh`、Payment = `tpcc_perc_payment`、OrderStatus = `tpcc_perc_order_status`、
  Delivery = `tpcc_perc_delivery`、StockLevel = `tpcc_perc_stock_level`、think time = `tpcc_interactive_ms`、thread 数 = `thread_num`、
  extime = `extime` である (`include/tpcc/tpcc_common.hh` と各 protocol の `include/common.hh`)。NewOrder の比率は引数でなく、
  100 から他の 4 つを引いた残差である (`tpcc_query.hh` の閾値の積み上げ)。
- 段 1 の構成は、範囲読み (`tx.scan`) を使う 3 取引を 0 にした NewOrder 57 : Payment 43 である (設計 README §3.5。CCBench 既定比
  45 : 43 の正規化は整数 % の引数では表せない)。段 2 の構成は CCBench の既定比である。
- 倉庫 1 は CCBench の既定で、48 thread が 1 つの Warehouse 行と 10 個の District 行を共有する (Payment が Warehouse と District を、
  NewOrder が District を更新する)。倉庫 48 は thread ごとに別の home warehouse になる (48 thread のとき)。Pegasus は 1 socket 48 物理コア・
  HT 無効なので、thread 数は v1 と同じく 48 を上限とする。
- 表にない実行時引数 (epoch_time、clocks_per_us など) は発効束で固定し、錨と留保 cell で同じ値にする。

**段 s の対象探索群の学習条件は、段 s の 2 錨の部分集合でなければならない** (表の引数が全て一致すること)。一致しない探索群、
他の段の錨を学習に使う探索群には本書を適用せず、その探索群の生成が始まる前に別の登録を作る (v1 §3.2 と同じ)。

### 2.2 因子の操作的定義と水準

TPC-C で CCBench の改変なしに動かせる因子は、倉庫数・thread 数・取引構成の 3 つである。v1 の 5 因子との対応は次のとおり。

| v1 の因子 | TPC-C での扱い | 理由 |
|---|---|---|
| read/write 比 | 取引構成として動かす | 取引ごとに読み書きの形が決まっているので、比率は取引構成で変わる |
| 競合 | 倉庫数として動かす (複合変更) | 倉庫数はデータ量・home 割当て・remote の有無も同時に変える (§1.3 の 1) |
| thread 数 | 動かす | v1 と同じ |
| 1 txn の操作数 | 動かさない | NewOrder の明細数 5〜15 は `tpcc_query.hh` の定数 |
| アクセス集合の重なり | 動かさない | remote 品目 1%・remote 顧客 15% は `tpcc_query.hh` の定数 |

think time (`tpcc_interactive_ms`) は SQL 相当の操作ごとに ms 単位で sleep する引数で、取引の途中で待つ別の regime になるので 0 に固定し、
留保の因子にしない。

| 因子 | 留保の水準 | 設計理由 |
|---|---|---|
| 倉庫数 | 4 (H に結ぶ)、16 (L に結ぶ) | 錨 1 と 48 の間の内挿点。log2 では 1・4・16・48 が 0・2・4・約 5.585 で、4 は H に近く (距離 2 対約 3.585)、16 は L に近い (4 対約 1.585)。48 thread のとき home 1 つあたりの thread は 12 と 3 |
| thread 数 | 12、24 | v1 と同じく並列度を 1/4 と 1/2 に縮める |
| 段 1 の取引構成 | Payment 20 (NewOrder 80)、Payment 70 (NewOrder 30) | 錨 43 の約半分と約 1.6 倍。どちらも 2 取引を残し、NewOrder 寄り (insert と District 更新が多い) と Payment 寄り (Warehouse・District の更新が多い) へ振る |
| 段 2 の取引構成 | 範囲読み 3 取引を各 1 (計 3%、NewOrder 54)、各 10 (計 30%、NewOrder 27)。Payment は 43 固定 | 錨の各 4 の 1/4 と 2.5 倍。3 取引を同じ比率で動かす |

**段 2 の構成の因子は複合変更である。** 範囲読みを使う 3 取引 (OrderStatus・Delivery・StockLevel) の生成比率を同時に変え、NewOrder の比率
(残差) と書き込み量も変わる。さらに、初期の未配送注文は 1 倉庫 9,000 行 (district ごとに 900) で、NewOrder が 1 行足し、Delivery が
district ごとに最大 1 行 (最大 10 行) を消す (設計 README §4.6、`tpcc_tx_delivery.hh`)。各 10 の cell では、commit 構成を生成構成で近似し
Delivery が毎回 10 行消せる間は、commit 1 回あたり 0.27 − 10 × 0.10 = −0.73 行の向きで在庫が減り、1 倉庫なら 9,000 / 0.73 ≈ 12,300 commit で
尽きる粗い目安になる (実際の時点は取引別の abort と district の偏りに依存し、未測定)。尽きた district の Delivery は軽くなる。
この過渡変化を含んだまま測り、範囲読みの費用を固定した状態で推定する設計とは扱わない。

**因子間の相互作用がある cell:** 倉庫 48 で thread を 12・24 にすると、home warehouse は 12・24 倉庫にしか付かない (残りの倉庫は remote
アクセスだけを受ける)。倉庫 1 では remote が無い。OFAT は「引数を 1 つ変えること」と定義し、その差を単一の因果効果とは書かない。

### 2.3 留保条件の一覧 (1 因子ずつ動かす配置)

各錨の周りで 1 因子だけを動かす。倉庫数だけは錨の周りに置かず、内挿 2 点をそれぞれ近い錨に結び付ける。表にない引数は錨と同じ値である。
s は段 (s1、s2)、X は錨 (H、L) である。

| cell | 錨 | 動かす因子 | 値 | 区分 |
|---|---|---|---|---|
| s-H-base / s-L-base | 各錨 | — | — | 錨 (学習条件) |
| s-H-wh04 | s-H | 倉庫数 | 4 | 留保 |
| s-L-wh16 | s-L | 倉庫数 | 16 | 留保 |
| s-X-thr12 | s-X | thread 数 | 12 | 留保 |
| s-X-thr24 | s-X | thread 数 | 24 | 留保 |
| s1-X-pay20 | s1-X | 段 1 の取引構成 | Payment 20 | 留保 |
| s1-X-pay70 | s1-X | 段 1 の取引構成 | Payment 70 | 留保 |
| s2-X-scan01 | s2-X | 段 2 の取引構成 | 範囲読み 3 取引を各 1 | 留保 |
| s2-X-scan10 | s2-X | 段 2 の取引構成 | 範囲読み 3 取引を各 10 | 留保 |

cell は段ごとに 2 + 2 + 2 × 4 = 12 個、うち留保 10 個。2 段で 24 cell、留保 20 個で、protocol ごとに同じである。cell の名前は §5 の順序の鍵に使う。
段 1 の cell は範囲読み 3 取引が全て 0、段 2 の cell は全て 1 以上なので、段 1 と段 2 の cell は引数の組として重ならない。
v1 の cell とは binary が違うので重ならない。**既知別枠は無い** (§7 の棚卸しの範囲で、どの cell にも既存の測定は見つからなかった)。

## 3. 不使用義務と測定の解禁

### 3.1 不使用義務

v1 §3.1 の義務を、次の読み替えで TPC-C に適用する。v1 の「§2.3 の留保条件」は本書 §2.3 の留保 cell 20 個、「本書」は本書に読み替える。
本書の着地以後、TPC-C の生成・生成のための評価・選択に関わる全ての主体 (LLM の子と role、非 LLM の探索手順、候補を選ぶ人間と AI の親) は、
次を入力に使ってはならない。

1. §2.3 の留保条件と、留保の設計 (どの因子をどちらへ動かすか、どの錨に結ぶか)。
2. 留保条件での測定結果 (性能・検証・較正・smoke のいずれも)。
3. 1・2 から作った指示・要約・設定 (workload の記述、探索範囲、目的関数、候補の手選別、選択のための較正)。
4. **留保を見て組み立てた近傍の条件や短縮版での結果。** 例えば留保 cell の extime だけを短くした走、留保の値の隣の値を選んだ較正、
   留保 cell の費用を測る試走は、名前が「検証」「smoke」「較正」でも禁止する。

禁止するのは留保条件への適応であって、個々の引数値の使用ではない。[T-2854]・[T-2855] の認定の開発で使う小規模の TPC-C 条件
(例: [T-2854] の構造検査の thread 2・extime 1 s・倉庫 1・段 1 構成) は、どの cell とも条件が違い、従来どおり使ってよい。ただし、その条件を
本書の留保を見て選び直してはならない。

**段 1 から段 2 への還流の禁止:** 段 1 の留保 cell での測定結果・失格の理由・候補の順位を、段 2 の生成・選択・参照の選定へ渡さない。
この義務は段 1 の測定の解禁後も続く。渡した場合、その段 2 の探索群の結果は本書の結果として扱わない。

**本書そのものへの到達:** v1 §3.1 の「本書そのものへの到達」と同じ。filesystem を読める生成器は本書・設計 README・起草記録を読みうる。
各 (課題, 手法) について、生成・選択に関わる主体が repo の docs を読めたかを記録し、読めた手法の転移の結果には全ての表で
「留保値に到達可能だった」と付ける。結果から除外はしない。本書は機械的な隔離を実装しておらず、隔離を主張しない。

### 3.2 対象探索群と候補の凍結

v1 §3.2 と同じ。対象探索群は段ごとに発効の決定で名指しし、候補の性能を見て選ばない。候補の凍結記録は、段 s の全 (課題, 手法, 独立探索) →
選ばれた候補の identity の対応、選択規則、選択できなかった系列、参照の identity と選定の記録 (§4)、各手法の到達可能性 (§3.1) を全て含む。

### 3.3 解禁の条件

段 s の留保 cell での実行 (stock を含む。性能・検証・較正・smoke を問わない) は、次の 3 つが揃うまで 1 走もしない。

1. 段 s の測定の発効の決定 (§0)。
2. 段 s の対象探索群の**全手法・全独立探索**について、候補の凍結記録が作られていること。
3. **段 s の認定経路があること:** 発効の対象にする protocol、測定に使う emitter と CCBench pin、段 s に登録した取引構成を扱える、
   既存の認定経路が local main にあること。段 1 では設計 README §3 の範囲 (表識別子・v3 frame・commit 計数・存在履歴の検査) を、段 2 では
   §4 の範囲 (範囲読みを述語読みとして扱う phantom 依存の検出) を含む。verifier が v3 の run に付ける印 (`Integrity.v3_existence_unverified`)
   を外すことだけを達成条件にしない。全候補・全 cell が事前に certified であることは要求しない (実測時の未確定は §6 で扱う)。

runner の smoke や動作確認は、錨の cell または §3.1 の小規模の条件で行う。認定経路が無い段の留保 cell で、性能だけを先に測ることはできない
(絶対規律 2、規律 3)。

## 4. 比較対象

protocol p・段 s・錨 X ごとに、次を比較対象とする。identity が同じ候補は 1 つにまとめて測る。

| 記号 | 名前 | 定義 |
|---|---|---|
| R0 | stock | 測定に使う CCBench pin の上流既定の build (全 option が `cmake/Options.cmake` の既定値。Silo では BACK_OFF=1)。比較は常に記述 |
| R* | 強い参照 | 起草時点で TPC-C の既知最良・既知の強い静的設定は見つかっていない (§7)。発効の決定で protocol ごとに下の 3 択を書く |
| sel | 各手法の選択結果 | 段 s の対象探索群の全 (課題, 手法, 独立探索) が錨 X で選んだ候補 |

- **R* の 3 択** (v1 §4 の MOCC の 3 択と同じ形): (a) 強い参照を固定し、主要族に入れる。(b) 記述専用とし、測る候補集合を固定して測る
  (主要族は空、結果は全て記述)。(c) その protocol を測定に含めない。**(a) の条件を満たせないときは (b) を既定とする。**
- **(a) の手続き:** 参照の選定の対象 (候補集合。例えば YCSB で選ばれた `p2_2_flag_opt` や静的 backoff の設定を TPC-C へ持ち込むもの) と
  選定の規則を、**錨での選定の測定を行う前に**書き、選定の測定は段 s の錨の cell だけで行う。選ばれた参照の identity と根拠を、段 s の留保の解禁
  (§3.3) より前に固定する。参照の選定に使った錨の測定は、本書の評価のための錨の測定 (§5 の job) と別の job とし、評価に流用しない。
  YCSB で強かったことは TPC-C で強い根拠にならない。留保条件で参照を選び直さない。
- **R0 比を主結果にしない。** 強い参照を固定できなかった protocol の結果は、R0 比の大きな数字を主要表へ上げず、全て記述として報告する
  (v1 §1.2 の禁止と同じ)。
- sel の扱い、失格した候補を次点で置き換えないこと、留保条件で最も速かった候補を事後の oracle として分けることは v1 §4 と同じ。候補 k の比較は、
  k を選んだ錨 X に結び付いた cell (`s-X-base` と X の留保 cell 5 個) だけで行う。
- 本書が扱う protocol は、TPC-C の認定対象として設計 README §1 が挙げる Silo と MOCC だけである (MOCC は認定の計装の着地後)。

## 6. 正しさ

- 性能と別に、(段, protocol, cell, R0 以外の候補) ごとに trace-enabled build で検証を 1 本行う (別 build・別 run、絶対規律 1)。workload の引数は
  性能と同じ (倉庫数・thread 数・取引構成・think time) で、extime は 3 s とする。cohort 1 の期間に行う。verifier の版と、使う認定経路 (§3.3 の 3)
  は段ごとの発効時に固定する。強い参照 R* も検証する。
- 結果は v1 §8 と同じ 3 値 (certified / 失格 / 未確定) とする。認定経路が run を認定しない印を付けた run (例: `Integrity.v3_existence_unverified`)、
  trace の完全性の検査や件数の照合に落ちた run、verifier が完走しない run は未確定であり、certified と数えない。
- **失格は候補ごと:** anomaly が 1 件でも出た候補は、本書の全 cell・両 cohort の主張から外す (絶対規律 2)。anomaly の種別・依存の構造・
  取引種別と表を報告し、「正しさが転移しなかった」ことを主要な所見として扱う。既に取った性能の測定値は測定事実として残し、主張に使わないことを
  追記で示す (絶対規律 7)。
- 未確定は別 node で 1 回だけ再検証してよい。なお未確定なら、その (候補, cell) の性能には主張の資格が無い (記述だけ)。R* が失格すれば、その参照との
  比較は全て主張から外す。
- trace の容量と検証の所要は未測定である。設計 README §7.3 の試算 (100 万 commit あたり段 1 約 1.37 GB、全 5 取引約 3.15 GB) は形式からの試算で、
  上下限ではない。容量不足・時間切れは未確定として扱い、extime を短くして certified を取り直すことはしない (検証の条件は結果を見る前に固定する)。

## 8. 費用の形 (仮定付き)

TPC-C の 1 走の所要・初期ロードの秒数・RSS は未測定なので、試算の数値を置かず、式の形だけを固定する。発効時に、凍結した候補数と実測した単価で
段ごとに見積もり、ユーザーの確認を取る (D2212 項 4)。

- 性能の走数 = 2 cohort × 32 block × Σ_(protocol, cell) K(protocol, cell)。K は cell の重複除去後の候補数 (R0 を含む) で、上限を定めない。
  静定の捨て走は job 数と同じ (段ごとに 2 cohort × protocol 数 × 12)。
- 1 走の所要 = 初期ロード (倉庫数に依存) + extime 3 s + 終了処理。初期ロードは 1 倉庫あたり一次表で約 529,011 行 (Warehouse 1、District 10、
  Stock 100,000、Customer 30,000、History 30,000、Order 30,000、NewOrder 9,000、OrderLine 約 330,000) と、共有の Item 100,000 行と二次索引を作り、
  load は 1 + 3 × 倉庫数 本の thread を起こす (`tpcc_initializer.hh`)。倉庫 48 の一次表は約 2,549 万行になる。extime だけを足した値は費用の下限の
  形でもない (ロードを落とす)。
- 検証の本数 = Σ (K − 1)。所要は trace の容量と verifier の容量に依存し、未測定 (§6)。
- 例 (上限ではない): 2 protocol・2 段・全 cell で K = 6 なら、性能は 2 × 32 × 6 × 48 = 18,432 走、捨て走 96、検証 240 本。extime だけで 15.36 node 時間相当で、
  既に D2212 項 4 の確認ライン (2 node 時間) を超える。
- 予算不足を、結果を見た後に cell や cohort を減らす理由にしない。減らすなら結果を見る前の発効の決定で、段ごとに cell を丸ごと外した旨を書く。

## 9. 発効束と改訂契約

### 9.1 発効束

段 s の測定の発効の決定に、次の実値を写す。1 つでも欠ければ段 s は発効できない。

- 認可の日付、決定 (D) 番号、承認対象の commit、本書の raw bytes の SHA-256。
- 段 s の対象探索群の名指しと、候補の凍結記録の所在 (§3.2)。段 s の M の値。
- protocol ごとの R* の扱い ((a) の参照と選定の記録 / (b) 記述専用と測る候補集合 / (c) 含めない、のどれか)。
- CCBench pin、patch の bytes と sha256、configure、toolchain の版、TPC-C binary の同一性。表にない実行時引数の値 (§2.1)。
- 段 s の認定経路 (§3.3 の 3): verifier の版 (module の file 別 sha256)、emitter と pin、扱える取引構成。
- runner の bytes と sha256、候補ごとの identity の書式と値。
- 環境 (Pegasus gen_S、node の種類、単独性の手順)、trace の保全先と空き容量。
- 凍結した候補数と実測した単価での費用の見積り (§8) とユーザーの確認。
- §7 の既知結果の差分 (着地から発効までに増えた TPC-C の測定)。

### 9.2 改訂契約

v1 §13.2 と同じ規則を本書に当てる。

- **着地から測定の発効まで:** 本文の既存 bytes を書き換えない。発効束の実値は本文でなく発効の決定と insight に置く。意味を変えない誤記の訂正と、
  発効束の項目の補足だけを、末尾に日付付きの追補として足してよい。錨・留保条件の削除・変更、不使用義務の緩和、§5 の置換の変更、継承する v1 の版の変更は
  できない。条件の追加は「追加枠」として別の節に置き、主要族に入れず別に報告する。
- **留保条件の結果を 1 つでも見た後の規則の変更** は、発効前でも事後改訂である。有利・不利の向きを問わない。当初の規則による結果を本書の結果として報告し、
  事後改訂の下の結果は別欄に分ける。段 1 の結果を見た後の段 2 の規則の変更も事後改訂である。
- **測定の発効後:** 既存本文の bytes を書き換えない (D1789)。訂正は末尾に `## N. Erratum` として足し、理由・日付・適用する段と cohort・判定への影響と、
  発効時に記録した版と追記後の版の対応を書く。
- 本書の中の「未着手」「見つからなかった」などの状態の記述は、起草時点の記述として読む。
