**読み方。** 論文の芯は、ユーザー裁定で**保持の側 (U0) に決まった** (D2322 項 1、2026-09-30「推奨通りで」)。U0 は「実行中の tx の時刻を、既読がすべて見え続ける範囲で後へ進め (前進)、その前進を確かめてから確定し、確定した後にだけ GC に公開する保護下限 (floor) へ反映する」機構である。
cold への進入を前進の契機にする U1 は同じ論文に残すが、実物にあるのは論理 K 境界で発火する構成 C だけで、hot の外れを契機にして GC へ反映する構成 D は未実装である。この版はこの 2 つを分けて書く。

- **U0 で観測できたこと (計器入り build の診断値)。** 読み取りの後に 10 ms 待つ長い tx がいる YCSB で、前進を回収境界へつなぐ構成 E は、偏りの無い負荷で回収境界の遅れを E-hb (flag だけ立てる対照) 比 −54% にした (md_14)。
  前進先を E-max にすると zipf 0.6 でも 19.5 → 10.0 ms に縮んだ (md_21)。zipf 0.9 では E-max 単独の効果は小さいが、前進できず commit できないと確定した試行を安全点で終える方策 c を足すと、
  遅れが 19.64 → 15.19 ms (rep 中央値) に縮んだ (md_31 §5.1、D2320)。
- **U0 の安全について言えること。** 抽象仕様 E について論理的な GC 安全と直列化を紙の上で論証した (md_26、D2319)。ただしその仮定を Cicada の試作のコードで照らすと、書き込み検査の走査中に版が回収されうる箇所など 3 つの不成立があった (md_36、D2326)。
  最も重い (a) の修理 (md_39) は並走中で、**起点では未着地**である。中間案 M の照合は実装され、E-max を含む 18 run で違反 0 だった (md_33、D2336)。
- **U1 と hot 配置。** 構成 C の throughput は stock と差が見えず、hot 配置は書き込み側の費用を外した設計 B-post (md_37) でも読みの利得が出なかった。
- **方針との照合 (下の §0.2)。** ユーザー方針は「論文は、ある条件 C で新しい手法が C での最高水準より大きく速いものだけ」である。**起点で、この形の証拠は 1 つも無い。** 次の §0.2 で隠さずに書く。

**この図から読み取ってはならないこと。**

- 「GC を改善した」とは書かない。回収境界の遅れと論理生存版数は計器入り build の値で、物理メモリの bytes ではなく、throughput の差は検出できていない (§2.5)。
- 「構成 E の Cicada は GC 安全 / serializable」とは書かない。定理は抽象仕様についてで、試作は仮定を満たさない箇所がある (§3)。
- 矢印は論証のつながりで、因果の強さや効果の大きさは表さない。

**この照合から言えること (親の読み、方針の当てはめ)。**

1. **方針が求める形 (C での SOTA より大きく速い) の証拠は、起点で 1 つも無い。** U0 の実測は回収境界の遅れ・生存版数という計器の値で、throughput の差は stock に対しても検出できていない。U1・hot 配置も stock と差が見えない。
   修正済みの最良 Cicada に対する比較は、どの構成にも無い。
2. **方針に照らした判定材料は md_42 で、起点で稼働中である。** T-2962 の定義では U0 (構成 E) も比較する機構に入っている。この版は md_42 の結論を書かない (起点の後の着地は README の stale 注記が指す)。
3. **U0 の確認段 S2 は、方針の問いに直接は答えない。** 評価計画の草稿 §16 の S2 は、H4 を E_sp(c) 対 E_hb(c) の回収境界の遅れ**かつ**生存版数で判定し、throughput は費用の併記に使う。
   「修正入りの Cicada に対して」を headline に書くために E_sp(c) 対 A_fix を族に入れるかは、発効の wave がユーザーに諮る論点として残っている (草稿 §16.10、推奨は入れる)。
4. **長い読み手の費用は read-only であることから来ており、今の U0 (構成 E は read-only を前進させない) の対象外である。** それを攻める RO-A は紙の上の論証だけで、試作へ進むかは md_42 の後に実装なしの診断で決める (D2334 項 4)。

**ユーザーの判断に返すもの (この版は決めない):** S2 の発効 (T-2893) と E_sp(c) 対 A_fix を族に入れるか、md_42 の結果を見た後の論文の構成。§12 にまとめた。

**読み方。** 左は先行研究と製品文書にある既知の事柄で、題名と貢献の文で新規と読ませない。中央が U0 として主張する範囲、右が同じ論文に残す U1 で、実在する構成 C と未実装の構成 D を分ける。

- **既知のもの (md_9 §5、md_27、md_18 §2):** 長い tx が回収を止める問題と、それを縮めたいという目的 (製品文書、SI-STM の動機)。実行中の tx の時刻の最小を回収境界にする規則 (Hekaton 2013、Cicada 2017)。

**読み方。** md_27 (動機づけの根拠集め) は長い tx を 4 型に分けた。**この分類は md_27 が置いたもので、出典自身の分類ではない** (md_27 §4)。
4 版目では、md_44 が read-only の読み手を「開始時点の状態が要る用途 (時点指定の読み)」と「ある一貫 snapshot でよい用途 (一貫 dump・分析 query)」に分けたことを C1 と C1′ の 2 つの箱で描いた (md_44 §1、md_15 §2.1 の 2 分類に対応)。

**集めた根拠 (md_27 §1.1・§6):** 公式文書・技術資料 38 頁 (PostgreSQL・MySQL・AWS Aurora の 17 頁と Oracle・SQL Server・MongoDB・CockroachDB・TiDB・Spanner・YugabyteDB の 21 頁) と論文・資料 10 本の計 48 件。

**論文 §1 に使える文 (md_27 §5.1 の M1〜M6 の要点):**

- M1: 最古の実行中 tx が回収境界を決める tx 型の GC (PostgreSQL・MySQL InnoDB・SQL Server・TiDB 6.1.0 以降・Aurora) では、長い tx が回収を止める。
  時間型 (Oracle・Spanner・YugabyteDB・CockroachDB) は通常の読み取りでは止まらず、代わりに長い読み取りが失敗する — と同じ段落で書く。
- M2: 回収が止まると容量・性能・可用性が悪化する。**数値はすべて C1 (固定 snapshot の読み手) の実験の値だと明記する。**
- M3: 問題は実運用で起きている。ただし頻度の根拠は HANA の 1 システムの統計 (408,664 query 中 6 cursor が 1 時間超) だけである。
- M4: 読んだ 10 製品系と HANA の範囲では、既存の対処は「長い側を終わらせる」「待ち上限で強制前進」「snapshot の失効」「書き込み側を遅らせる」のどれかで、何かを諦める。
- M5: 途中版の剪定 (区間 GC・EPO) は列を縮めるが、長い snapshot から見える版は残す。
- M6: 本案は長い tx を abort せず前進させ、その前進を保護下限へ反映する。

**使えない文:** 「長い tx は頻繁に起きる」。「本案は C1 の数値の分だけ速くなる」。**C2・C3 の大きさの数値は外部資料に無い** — 評価で自分で示す必要があり、T-2916 に登録されている (md_27 §8)。起点で未着手である。

**長い読み手が修正入りの比較相手に残す分。** 修正入りでも、長い read-only 1 本のとき公開時の境界年齢 12.5〜14.3 ms が残る (md_22 §8)。修正入り・最良 genome (md_22 の T、skew 0.9、3 秒・6 反復平均) では、長い read-only の有無で throughput が ro 0% で 3.54M → 2.72M、ro 50% で 5.73M → 2.82M、ro 95% で 13.11M → 8.03M tps だった。ただしこれは worker 1 の手続きも変わる条件間の差で、読み手の保持の費用そのものではない (md_22 §5・§7)。md_42 の負荷での直接比較は起点で未着地 (md_42 が稼働中)。
**長い読み手は read-only (C1 か C1′) で、今の U0 の実物 (C3 の構成 E) の対象外である。** T-2916 が求める C2・C3 の数値の代わりにはならない。

### 2.4 強い偏り: `no_room` の読みの訂正と、方策 c (md_21・md_31)

![E 腕の失敗理由 (md_21、未検証の診断値)](../../output/insights/2026-09-29/vhash-forwarding-target-policy/figures/target-policy-reasons.png)

**読み方 (md_21 の target-policy-reasons)。** 失敗理由ごとの panel。E-now の失敗はほぼすべて既読不一致、E-max は既読不一致 0 で `no_room` (前進先が無い) と書き込み制約、E-max-once は 2 回目以降の要求が `once skipped`。

**`no_room` の読みの訂正 (md_31 §3.3、D2320 項 3)。** 3 版目は md_21 §4.3 に従い、`no_room` を「(a) 一度成功した後で上端が動かない」と「(b) 既読のどれかが上書き済みで validation での abort が決まっている」の混合と書いた。

### 3.2 GC 接続の論証 (md_26): 読み終えて待つ型について

```mermaid

  subgraph INV["不変条件"]
    i0["I0 境界 ≤ 実行中の各 floor"]
    i1["I1 floor ≤ 候補時刻"]

  end
  subgraph COND["前提の条件"]
    fs["開始 floor の条件<br/>FS-a・FS-b・FS-c"]
    pub["PUB 確認・確定の後に<br/>確定時刻以下へだけ上げる"]
    ra["RA floor を上げる確認を<br/>始めた後は外部 read をしない"]
    rc["RC 後続の確定版を根拠に回収<br/>PENDING は回収しない"]
  end
  fs --> i2

  pub --> i2

```

**読み方。** md_26 (D2319) は、待機の安全点で tx 自身が確認 → 確定 → 別 step で公開する抽象仕様 E について、途中入場する tx と古い境界での回収も含めて次を示した。**主語は抽象仕様であり、Cicada 実装と物理的な非接触は主張しない** (md_26 §0)。

- **定理 G (論理的な GC 安全):** 回収された版は、回収の時点で実行中の tx にも、その後に始まる tx にも、読み・確認・commit の検証・書き込み検査・前進先の計算のどれでも「必要な版」として現れない。
- **定理 S (直列化):** 確定した tx の依存グラフは閉路を持たず、確定時刻の昇順が直列化の順を与える (md_13 の定理 4 の仮定 A9 を、定理 G から導いた補題 A で置き換えたもの)。
- 前進先 t′ については一意で現在の時刻より大きいことしか使わないので、E-max にも E-now にも同じく当てはまる (D2319 項 1)。

**条件 RA がこの論証の射程を決める。** md_26 は RA を崩すと floor だけでは既読版を守れない列を 2 つ紙の上で作った (探索はしていない)。列 X1 は「floor を上げた後に新しく読む」、列 X2 は「確認に成功してから公開するまでの間に新しく読む」で、
どちらも新しく読んだ版が確認に覆われず、並行する writer の確定版を根拠に回収されうる (md_26 §8)。**定理 G は、読み終えてから前進して公開する型 (C3) の抽象仕様には届き、読み続けながら floor を上げる型 (C2) には届かない。**
読み続ける read-only tx (C1′) を前進させる md_44 の抽象仕様 RO-A は、前進先を安定境界に限ることで RA を使わずに同じ結論を得る (§7.2)。

**Cicada で既読版を守る暗黙の不変条件との対応。** stock Cicada は「tx 開始時の下限を tx の間変えない」ことで既読版を物理的に守っている (md_14 §3.3)。md_26 はこれを FS-c (開始時に (I2) を成り立たせる) と PUB (floor を上げるのは確認に成功した時刻以下へだけ) の 2 つに分けて明示した (D2319 項 3)。§3.4 の P5 は PUB を破った実例である。

**前提の条件の Cicada での状態 (md_36 §2・§4、計測の設定の YCSB の read-write tx の経路に限る):**

|---|---|---|---|

### 3.3 構成 E の試作が定理の外にある 3 箇所 (md_36、D2326 項 3) — (a) の修理は未着地

md_36 は、試作のコードの手順を抽象仕様の step に対応させたうえで、対応が崩れる箇所を 3 つ挙げた。**どれも紙の上の実行列で、実走・探索・判定器では観測していない。頻度も分からない** (md_36 §9)。

**(a) 書き込み検査の走査中に、止まる予定の版が回収されうる (W* × GC)。** 計測した長い tx (10 read + 1 update の後に待機し、待機中に前進して floor を t′ − 1 へ上げ、その後に commit する) の手順に、
update の key が既読キーと異なる場合にそのまま乗る (md_36 §0 項 1・§3.2)。

```mermaid
sequenceDiagram
  participant T as T (長い tx、update の key x は既読でない)
  participant L as キー x の版の列
  participant Z as Z (T より前から活動、時刻 z は x の確定版 c と t′ の間)
  participant G as leader と Z の thread の GC
  T->>T: 安全点で t′ へ前進に成功し、floor を公開する
  T->>L: commit: 自分の版を設置 (その next = c)
  T->>L: 書き込み検査の走査: 手元の pointer が c を指す
  Z->>L: 自分の版を T の版と c の間へ設置する
  Z->>L: 自分の検査は c で通り、確定して回収の候補に積む
  G->>G: leader の round が進み、境界が z を越える
  G->>L: Z の版を根拠に c を切り離し、解放か再利用
  T->>L: 手元の pointer で c の status と rts を読む
```

**読み方。** md_36 §3.2 の列を、時刻の値を記号にして描いた。stock と構成 C では T の floor が開始時の値のままなので、境界は T の floor を越えず、Z の版は回収の根拠にならない。
構成 E では T が floor を t′ − 1 へ上げているので、境界が z を越えうる。成り立つには、T が c を指してから c の rts を読むまでの間に leader の round が少なくとも 2 つ進む必要がある。
`REUSE_VERSION=1` では、切り離された版は別の書き込みに作り直され、T はその版を見て、他人の PENDING を待つ・rts 0 で通る・next の空 pointer を辿る、のどれにもなりうる (md_36 §3.2)。
md_26 の条件 RA は外部 read だけを縛り、commit の書き込み検査の走査は縛らないので、RA を満たす計測の workload でもこの列は残る (md_36 §3.3)。

**(b) 境界の読みと開始 floor の条件 FS-b。** 構成 E では、前進の成功で thread の floor が上がり、同じ thread の次の tx の begin が無条件に floor を書き直すので、thread の単位で floor が下がる。
leader の集計は非原子的なので、前の tx の高い floor を読んだまま新しい tx の低い floor を読まずに境界を公開しうる (md_36 §4.2)。試作では thread 0 が長い thread にならず前進しないので害の列は作れなかったが、
どの thread も前進しうる一般の構成 E では、既読版が回収される列 G1 が完成する (md_36 §4.4)。**thread 0 の抑えは試作の構成に偶然ある性質で、構成 E の規則ではない** (D2326 項 3)。

**(c) 時刻の重複 (A2)。** stock の時刻生成は同じ thread の続く 2 つの tx に同じ時刻を返しうる。前進しない begin は stock の生成器を使うので、C・E も同じである (md_36 §5)。

**修理と、その結果の待ち。** (a) を再現して最小の修理を入れる md_39 は**起点で未着地**である。md_36 §6 の直し方の候補のうち「書き込み key を持つ tx は floor を公開しない」を採ると、md_14・md_21・md_31 の長い tx (1 update を持つ) は前進の対象から外れ、
確認段 S2 の cell で E_sp と E_hb が同じ動きになりうる。評価計画はこの場合に S2 をこの形で発効しないことを結果の前に登録した (草稿 §16.2、D2332 項 3)。
**過去の計測値は当時の観測として残す** (規律 7、D2326 項 5)。弱まるのは「実装が定理 G・S の前提を満たした」「早すぎる回収は無かった」という解釈だけである。

**論文に書ける文 (D2326 項 2):** 「抽象仕様について定理が成り立つ」「stock の書き込み検査は W* の局所手順に対応する」「計測した待機型の tx では、構成 E は確認に成功した後にだけ公開し、公開の後に読まない」。
**書けない文:** 「実装・試作は論証の仮定を満たす」「構成 E の Cicada は GC 安全 / serializable」。

```mermaid
  r["read(key)"] --> pos{"T.ts で見える版は<br/>先頭から K 版より奥?"}
  pos -- いいえ --> stock["stock と同じ探索"]
  pos -- はい --> pol{"構成"}
  pol -- F --> ab["abort して<br/>新しい ts で再実行"]
  pol -- C --> tgt["前進先 ts′ を決める<br/>(既定は最小の前進)"]
  tgt --> chk{"事前確認<br/>既読版が ts′ でも見えるか<br/>write set の制約"}
  chk -- 失敗 --> stock
  chk -- 成功 --> fwd["T.ts := ts′<br/>未設置の書き込み版の wts を ts′ に"]
  fwd --> reread["ts′ で探索し直す"]
  reread --> val["commit 時は stock の validation を<br/>最終 ts で走らせる"]
  stock --> val
```

**読み方。** md_6 の試作 (`patches/cicada-forwarding-variant.patch`、D2287) の流れ。物理的な hot は作らず、「先頭から K 版より奥を辿る必要がある」read を発火条件にした (論理 K 境界)。これが U1 (cold への進入を前進の契機にする) の実物である。
前進は read 相だけで行い、最終保証は stock の validation を最終 ts で走らせることに置く。**GC の保護は旧 ts のまま据え置く** — 構成 C は floor を公開しないので、単独では回収境界を動かさない (md_6 §2)。
前進は `!is_ronly_` の tx だけで、read-only の tx は前進しない (md_44 §2)。F は同じ発火条件で abort して再実行する対照である。

### 4.2 前進先の方策: 構成 C は最小の前進のまま (md_21、D2315)

```text
時刻  →   t1    t2    t3    t4    t5    t6    t7    t8
既読 A    [===========================)                  A の見える区間 [t1, t6)
B の版          B@t2        B@t4  B@t5        B@t7  B@t8
                └── cold ──┘      └──────── hot ─────────┘
T の現在              ^t3

固定          : t3 のまま → B@t2 を読む          → cold を辿る
今へ前進      : t8 へ進む → B@t8 を読む          → A が見えない (t8 は [t1, t6) の外)
最小の前進    : t5 へ進む → B@t5 を読む          → A も見える (t5 は [t1, t6) の中)、cold を避けられる
区間内の最大  : t6 の手前へ進む → B@t5 を読む    → A も見え、時刻はより新しい
```

```mermaid
flowchart LR
  fixed["固定<br/>timestamp を動かさない"] --> r1["今の時刻で見える<br/>cold の版を読む"]
  now["今へ前進<br/>(E-now・C_now)"] --> r2["自 thread の時計の<br/>新しい時刻へ進む"]
  mn["最小の前進<br/>(C-min、構成 C の既定)"] --> r3["hot の版に届く<br/>最小の時刻へ進む"]
  mx["区間内の最大<br/>(E-max・C-max)"] --> r4["既読の可視区間に収まる<br/>最大の時刻へ進む"]
  pt["部分前進<br/>(C-partial)"] --> r5["届かなくても<br/>今より新しければ進む"]
```

**読み方。** md_21 が比べた前進先の方策 (D2315) を、記号の例に並べた。例の上の帰結であって一般の性質ではない。**「最新でない hot 版を選べる」こと自体は新規性にならない** — SI-STM (2006) と CockroachDB の read refresh (2020) が既に持つ (md_9 §5、§11)。
版 v が見える区間を I(v) = [b(v), e(v)) と書くと、既読の集合 R_T が同時に見えうる区間の上限は U_T = min e(v) で、E-max・C-max はこの手前を目標にする (md_21 §2)。**これは read 集合の整合性の条件であって、更新 tx 全体の commit 条件ではない。**

## 5. hot 配置 (H1): 書き込み側の費用は外せたが、読みの利得は出ていない

```mermaid
flowchart LR
  key["キー A の Tuple"] --> hot
  subgraph hot["hot block"]
    seq["key ごとの seq"]
    d0["記述子 0<br/>wts と版への参照"]
    dk["記述子 K-1"]
  end
  hot --> list["物理的な版の列<br/>(stock の連結リスト)"]
  d0 -.選んだ版の status を読む.-> list
  list --> cold["hot より奥の版<br/>stock の走査で辿る"]
```

**読み方。** key ごとに版の列の手がかり `{wts, Version*}` を K 件以下だけ連続に置く構造 (仮称 VHash の hot block)。md_23 はこれを「物理列の先頭 min(K, 長さ) 件の正確な写し」として key ごとの seqlock で保ち (D2311)、
md_37 は書き込み側の排他を挿入の CAS の外へ出す設計 B-post に替えた (D2331、§5.4)。**論文の芯ではない** (D2322 項 1)。

### 5.1 深い版探索をするのは誰か (md_2・md_15)

![K と深部割合・楽観的候補率 (md_2)](../../output/insights/2026-09-29/vhash-cicada-version-measure/figures/k_candidates.png)

**読み方 (md_2 の図 1)。** 上段 = update tx の読み取りのうち hot 容量 K より奥へ行った割合、中段 = read-only tx の同じ割合、下段 = 深い update read のうち既読を保って前進できる候補があった割合 (観測時点の楽観値)。
**言えること:** update tx の深い探索は少なく (workload B で位置 ≥ 1 が約 0.9〜1.4%)、read-only read は 24〜48% が位置 ≥ 1 である (md_2 §0)。**言えないこと:** 計器入り build の観測で、性能や forwarding の成功率ではない。

![ro read の深さと、深い read に占める ro の割合 (md_15)](../../output/insights/2026-09-29/vhash-readonly-share/figures/depth_share.png)

**読み方 (md_15 の図 1)。** read-only read が位置 ≥ 1 へ行く割合と、深い read に占める read-only の割合を、ro 指定率・長い tx の型・GC 間隔ごとに並べた。
**言えること (md_15 §0 項 1):** ro 指定率 25% 以上の全条件で、位置 ≥ 1 の read の 87〜100% が read-only 由来、位置 ≥ 4 が観測された条件では 99.4〜100%。**言えないこと:** 割合は深い read の総量が小さい条件 (skew 0) も含む。

![探索長と位置の分布 (md_2)](../../output/insights/2026-09-29/vhash-cicada-version-measure/figures/search_length.png)

**読み方 (md_2 の図 2)。** site ごとの、stock の走査が `next` を辿った回数と、選んだ版の位置の分布。9 以上は bucket 幅が広がるので、「16」の段差は bucket 幅によるもので分布の山ではない (md_2 §8)。

**伸びしろの上限 (md_29 §0 項 3、計器入り build の機会量)。** 全 read の位置 ≥ 1 の割合 h1 は、長い read-only tx を 1 worker が続ける batchR で 0.51〜0.53、read-only 指定率 50・95% で 0.49〜0.52。
update read の位置 ≥ 1 の割合 u1 は、最良設定・長い tx なしで skew 0.99 のとき 0.10〜0.22。一方で位置 ≥ 8 はまれで、層 S の batchR 以外では最大 0.027 だった。**これは機会の大きさであって、hot 配置を実装したときの効果ではない。**

![層 O: H1 の主効果 (md_29、計器入り build の観測)](../../output/insights/2026-09-30/vhash-workload-space/figures/axes_h1.png)

**読み方 (md_29 の axes_h1)。** 層 O (強さ 2 の直交表) で、因子の水準ごとに H1 の伸びしろの指標の中央値 (各水準 18 点) を並べた主効果の図。長い tx は batchR の側、read-only 指定率は 50・95% の側で h1 が大きい (default で h1 0.53 対 0.20、0.52 対 0.15、md_29 §3.3)。
**言えないこと:** 主効果は他因子について釣り合っているが、2 因子交互作用とは分離できない (md_29 §3.3)。計器入り build の観測量で、機構の効果ではない。

### 7.1 短い read-only と長い read-only (md_15・md_22)

![境界年齢・公開回数・snapshot 年齢 (md_15、計器入り build の観測)](../../output/insights/2026-09-29/vhash-readonly-share/figures/boundary_age.png)

**読み方 (md_15 の図 2)。** 条件別の回収境界の年齢・公開回数・read-only の snapshot 年齢。境界年齢は timestamp 空間の値 (clock boost を含む)、分位点は 2 倍刻みの bucket の上界である。

- **短い read-only は、競合の強い設定では境界の遅れの主因ではない (md_15 §0 項 2):** 既定の Cicada・skew 0.9 で ro 指定率を 0 → 95% に変えても、境界年齢の平均は 1.5〜1.9 ms (GC 10 µs)・2.3〜2.7 ms (GC 1 ms)・122 ms (GC 100 ms) のままだった。
- **長い read-only が 1 本あると、stock は公開が止まる (md_15 §0 項 3、md_22):** 45 走すべてで 3 秒間の公開が 0 回。機序は §6.1 の欠陥である。

![条件間の総差の分解 (md_15、計器入り build の観測)](../../output/insights/2026-09-29/vhash-readonly-share/figures/decompositions.png)

**読み方 (md_15 の図 3)。** ro の総差・長い update の総差・交互作用と、非対応差の 95% t 区間。**条件間の総差であって、「ro のせい」の因果の内訳ではない** (D2296)。

**修正後も残る分 (md_22 §8)。** 修正入りでも、長い read-only 1 本のとき公開時の境界年齢は 12.5〜14.3 ms 残る (長い read-only の長さ 10 ms 程度)。
修正入り・最良 genome (md_22 の T、skew 0.9、3 秒・6 反復平均) では、長い read-only の有無で throughput が ro 0% で 3.54M → 2.72M、ro 50% で 5.73M → 2.82M、ro 95% で 13.11M → 8.03M tps だった。ただしこれは worker 1 の手続きも変わる条件間の差で、読み手の保持の費用そのものではない (md_22 §5・§7)。md_42 の負荷での直接比較は起点で未着地 (md_42 が稼働中)。

### 7.2 読み続ける read-only tx を前進させる抽象仕様 RO-A (md_44、D2334)

```mermaid
flowchart LR
  sp["安全点"] --> st["安定境界 σ を得る<br/>それ以下に新しい版が置かれない値"]
  st --> obs["各既読 v について<br/>v より上で σ 以下の最初の版を観測"]
  obs --> s["s := σ と、その版の wts の直前の小さい方"]
  s --> cmp{"s が今の snapshot より大きいか"}
  cmp -->|はい| mv["① snapshot を s へ移す"] --> fl["② floor を s 以下で公開"]
  cmp -->|いいえ| keep["snapshot も floor も変えない<br/>rts は書かない"]
```

**読み方。** md_44 §3 の抽象仕様 RO-A。読み続ける read-only tx (固定キーの point read だけ、昇格しない) が、安定境界 σ の snapshot で読み、全既読が σ 以下のどこまで見え続けるかを 1 回の観測で確かめ、その最大値 s へ snapshot を移してから floor を上げる。
前進の後も**全読みが 1 つの snapshot の版**であることを保つので、「ある一貫 snapshot でよい用途」(一貫 dump・分析 query) には使え、「開始時点の状態が要る用途」には使えない (md_44 §1)。

- **論証 (紙の上、md_44 §4):** 抽象仕様 RO-A について、直列化 (各 read-only tx を最後の snapshot の位置に置く、定理 S-RO) と論理的な GC 安全 (定理 G-RO) を示した。**md_26 の条件 RA を使わない。** 安定境界の条件 ST は、X1・X2 の書き手 (前進先より小さい時刻で、前進の時点でまだ活動中の書き手) をまさに除く (D2334 項 2)。
- **各条件を外すと何が起きるか (md_44 §7、紙の上の列):** 確認を外すと読みの skew の巡回 (C1)、前進先が安定でないと 3 tx の巡回と X1 型の回収 (C2)、floor を先に上げると D2317 が却下した形 (C3)、時計を進めずに持ち上げると他の read-only tx の安定境界の下に版が置かれる (C4)。モデルでも実走でも探索していない。
- **Cicada への対応 (コード読解、未確認を含む):** `MinWts − 1` を安定境界とする条件 K1〜K5 はコード読解で、未確認を含む。とくに長い read-only tx 自身が境界の集計を 3 通りに止めている (自分の ThreadWtsArray、立たない GCFlag、thread 0 なら leader の仕事) ので、`rts_ = MinWts − 1` の再実行だけでは前進しない (md_44 §6.2)。
- **効き目は細い見込み (md_44 §8):** 前進できる幅は「既読のどれかに次の確定版が来るまで」で頭打ちになる。md_29 の batchR (skew 0.99) の熱いキーの鎖の長さからの粗い目安は約 2.7 µs で、**仮定からの算術であって実測した間隔ではない**。区間 GC に対する上積みの上限は出せない。
- **推奨 (D2334 項 4):** 試作は今は作らず、md_42 の後に実装なしの診断 (md_44 §9 の D2: 既存の走から前進できた幅を後から数える、D3: 区間 GC が既に捨てられる版を除いて追加に要らなくなる版を数える) を先に行う。T-2966 として起票されている。起点で未着手である。

### 8.1 止まった thread への代行による前進 (md_16、D2298・D2318)

```mermaid
flowchart LR
  stop["sleep・preempt で<br/>止まった tx"] --> hp["別の thread が<br/>代わりに確かめて前進"]
  hp --> m["小モデルで分かった必要条件"]
  hp --> gap["Cicada の GC は<br/>全 thread の静止を待つ"]
  gap --> nogo["代行しても回収は進まない<br/>代理の静止宣言は未検証"]
  m --> keep["再審するときの規則として<br/>一次資料に残す"]
```

**読み方。** md_16 は、止まった tx を別の thread が前進・失効させる形 (HP) を小モデルに足し、6 場面 90 構成を全探索した。**HP は論文の対象に入れず、限界の節に文案を置き、付録には置かない** (D2298、D2318 項 1)。

**論文の限界の節に置く文 (md_16 §7.3 の文案、逐語):**

> 本研究の前進は、待機中の transaction が安全点で GC からの要求を確かめられることを前提とする (評価に用いる CCBench の長い transaction は busy-wait で待つため、この前提を満たす)。sleep や preempt で完全に止まった thread の代わりに別の thread が前進させる設計 (代行による前進) は、小さなモデルの全探索で、descriptor の世代つき CAS が確定と公開を覆うこと、再開時に時刻を読み直すこと、代行する thread 自身が読み取り版を保護すること、失効させる場合は再開時に失効を確かめる前に読み取り値へ触れないことが必要だと分かった。ただし、止まった thread の静止を他の thread が代わりに宣言してよい条件は未検証であり、Cicada のように全 thread の静止を待って回収境界を更新する GC では、代行による前進は回収を進めない。代行による前進の実装と評価は今後の課題とする。

**併記すること (D2318 項 1):** 安全点での前進を CCBench 自身の長い tx で評価するには、CCBench の待機ループ (`clock_delay`) に要求の確認を入れた安全点が要る。現行のループは要求を確かめない (md_16 §7.1)。
md_14・md_21・md_31 の構成 E は、md_6 の試作が足した長い tx の型 (`CICADA_LONGTX`) の待機を 100 µs に刻んで安全点を置いたもので、CCBench 自身の待つ型 (W5) ではない。W5 は pin 前進の後に測る予定である (T-2923)。

### 8.2 実装・比較相手・進行保証の限界

- **正しさの地位。** 論証はモデル仕様 v1 と抽象仕様 E・RO-A についてである。Cicada の試作は論証の仮定を満たさない箇所があり (§3.3)、(a) の修理 (md_39) は未着地である。判定の上限は indeterminate で、中間案 M の照合は検査 run について違反 0 (§3.7)。
- **進行保証。** 安全性だけを扱う。CAS は rts の CAS-max と版の設置に使うが、lock-free 性・進行保証・止まった thread の保護の解除は示していない (md_26 §11)。長い tx の完了率は観測値で、進行保証の代わりにならない。
- **GC の効果の地位。** 回収境界の遅れと論理生存版数は計器入り build の値で、物理メモリの bytes ではない。`REUSE_VERSION=1` の pool は縮まない (md_14 §7)。
- **比較相手。** 主比較の相手は修正入りの最良設定に決まった (D2322 項 2) が、U0 をその土台で測った値は無い。CCBench の修理は local branch にあり、pin は C のまま (§6.5)。区間 GC の SOTA との比較は独立の残課題 (§7.3)。
- **範囲。** 固定キーへの point read / update の YCSB だけ。md_36 の照合も YCSB の経路に限る (md_36 §1)。

|---|---|---|
| U0: 前進を回収境界へ反映して保持義務を縮める | **機構は見当たらず (範囲つき)**: OpenAlex (題名 + 要旨、2026-09-29 09:51〜10:20 JST 取得)・arXiv (同 09:49〜09:50 JST)・DBLP (Last-Modified 2026-09-28 20:23:37 GMT の全件書き出し) を事前登録した式 N01〜N05 で調べた範囲と読んだ原典の範囲。**目的と GC 規則は既知** | 芯 (D2322 項 1)。主張するのは「実行中の前進を保護下限へ反映する機構と、その確定・公開の順序」だけ |

- **新規性の検索をやり直した一次資料は、起点でもまだ無い。** md_43 (「条件 C × 手法 M × C での SOTA」を結果の前に決めて新規性を洗い直す、計算なし) は起点で未着地である。
- 区間 GC の新規性は既知 (§7.3)。方策 c (待機の安全点で commit できないと確定した tx を早く終える) の新規性一般は調べていない (md_31 §9) ので、新規性に数えない。
- AggressiveGC (CCBench 論文 §7.3、提案のみ) との違い: 回収を先に決めて tx を殺すか、tx が既に commit できないことを確かめてから境界を放すか。方策 c は commit できる tx を失わない (小モデルの範囲) 代わりに、上書きされていない長い tx が押さえる分は残す (md_31 §9、D2320 の却下理由)。

**関連研究の 5 系 (md_1 §12 の 4 系に md_9 §8 が (e) を足したもの):** (a) timestamp を後から決める系 (TicToc・Sundial・MaaT・Lomet 2012。TicToc の timestamp history は著者自身が §6.4 で効果が測れなかったと報告、md_1 §4)、
(b) 衝突で順序を動かす系 (Shirakami・Rebirth-Retire・MV3C・Morty)、(c) 版の配置の系 (Cicada・HyPer・vDriver・LeanStore・Freitag 2022)、
(d) GC と長い tx の系 (Steam・HANA・CIDR 2021・AggressiveGC と製品文書 md_27、区間 GC)、(e) 実行中に前進して既読を保つ系 (CockroachDB の read refresh、SI-STM / LSA)。

**使ってはならない言い方 (md_9 §7):** 「旧版を選べる」「前向きに進んで最新でない版を読む」「新しい側へ寄せて古い版を早く捨てる」を新規性として書く。「初めて」「先行研究が無い」。
索引名・式 ID・cutoff を落とした「見当たらなかった」。構成 E の安全点での前進を「読み取り後に待つ tx の保持を縮める」と書くときは、E の測定の範囲を同じ文に置く。
