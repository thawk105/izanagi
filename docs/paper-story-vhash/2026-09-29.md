## 0. 一目でわかる全体像

```mermaid
flowchart LR
  subgraph prob["問題 (CCBench の問題意識、メモの要約)"]
    long["長い transaction が<br/>古い timestamp に居続ける"] --> hold["GC が古い版を<br/>回収できない"]
    hold --> chain["版の列が伸びる"]
    chain --> cost["read / write / validation で<br/>版を辿るコストが増える"]
  end
  subgraph mech["提案の 3 つの部品"]
    vh["① VHash<br/>直近 K 版を手元 (hot) に置き<br/>古い版は奥 (cold) へ"]
    fw["② 選択的 forwarding<br/>cold に入りそうなときだけ<br/>timestamp を安全に進める"]
    gc["③ GC への接続<br/>進めた結果を<br/>回収できる範囲に反映"]
  end
  cost --> vh
  vh -- "cold 境界が<br/>発火の合図" --> fw
  fw -- "もう古い履歴を<br/>要求しない" --> gc
  gc -- "版の列が短く保たれる" --> vh
```

**読み方。** 左が解きたい問題の因果、右が提案の 3 部品である。部品は独立ではなく、①の hot / cold の境界が
②の発火条件になり、②で進めた結果を③で回収に結びつける、という循環を狙う。

**この図から読み取ってはならないこと。** 循環が実際に回るか (H4・H5) は未検証である。③は ②が成功しても
自動では起きない (§5)。また、読み取り後に止まっている transaction には②が発火しない (§6)。

中心の一文 (メモ §32):

> **古い version を速く探すだけでなく、古い version を探さずに済む timestamp へ transaction を動かす。
> さらに、その移動を古い履歴の回収につなげる。**

## 1. 問題: GC を速めても、長い transaction が版を抱え続ける

```mermaid
flowchart LR
  subgraph old["従来の方向"]
    o1["不要になった版を<br/>できるだけ早く回収"]
  end
  subgraph agg["AggressiveGC (CCBench §7.3 の構想、メモの要約)"]
    a1["必要とされうる版も回収"] --> a2["必要になった tx を<br/>新しい timestamp で再実行"]
  end
  subgraph ours["本案"]
    p1["古い版を必要としそうな tx を<br/>安全に前進させる"] --> p2["実行済みの仕事を<br/>保ったまま続行"] --> p3["古い履歴への依存が減る"]
  end
```

**読み方。** 3 つとも「古い版が性能を削る」ことへの答えだが、どこを変えるかが違う。従来は GC 側を速める。
AggressiveGC は版を先に捨て、困った transaction をやり直させる。本案は transaction 側を動かし、
**GC ができる状態を早く作る** (メモ §2)。やり直しを避ける点が AggressiveGC との違いになる。

**この図から読み取ってはならないこと。** CCBench 論文 §7 (図 12〜14、RapidGC の頭打ち) の内容はメモの要約であり、
この版ではまだ原典で読み直していない。論文の本文で使う前に、文献の wave が原典の節・図番号と照合する。

## 2. VHash: 直近の少数版を手元に置く

```mermaid
flowchart LR
  key["キー A"] --> hot
  subgraph hot["hot block (通常の版選択で見る範囲)"]
    d0["版の記述子 0<br/>(最新)"]
    d1["版の記述子 1"]
    d2["版の記述子 K-1"]
    cp["cold への参照"]
  end
  cp --> c1
  subgraph cold["cold 履歴 (同じ DRAM 内でよい)"]
    c1["それより古い版"] --> c2["さらに古い版"] --> c3["…"]
  end
  d0 -.payload.-> pay0[("値")]
  d1 -.payload.-> pay1[("値")]
```

記述子の候補 (メモ §5.1): 版の識別子・書き込み timestamp・状態 (PENDING / COMMITTED / ABORTED)・
値への参照・検証に要る情報。

**設計上の分かれ道 (まだ決めていない):**

```mermaid
flowchart TB
  q1{"hot に置くのは?"} -->|記述子だけ| m1["値は参照先から 1 回だけ取る<br/>(pointer を辿る回数を減らす)"]
  q1 -->|値も| m2["小さいレコードで間接参照がさらに減る<br/>大きいレコードでは hot が膨らむ"]
  q2{"構造の単位は?"} -->|キーごと| k1["キーを引いてから hot block を見る<br/>(最初の試作・切り分けに向く)"]
  q2 -->|bucket に融合| k2["複数キー・複数版を 1 bucket に<br/>(融合の利益と容量の奪い合い)"]
  q3{"K は?"} -->|固定| f1["全キー同じ K から始める"]
  q3 -->|可変| f2["更新・アクセス頻度に応じて変える"]
```

**読み方。** 「3 版を hot に置く」という言い方は、記述子だけか値もか、キー単位か bucket 単位かを決めないと
仕様にならない (メモ §5.2・§6)。**K はシステム全体の保持版数の上限ではなく、hot の容量である。**
K = 3 に特別な保証は無く、実験で決める (メモ §28.3)。

### 2.1 版選択をまとめて比べる (SIMD は必須ではない)

```mermaid
flowchart LR
  subgraph lk["連結リストを辿る"]
    n1["版 1 を読む"] --> n2["版 2 を読む"] --> n3["版 3 を読む"]
  end
  subgraph ct["連続配置"]
    arr["記述子の timestamp 列を<br/>まとめて読む"] --> sc["scalar で比較"]
    arr --> sm["SIMD で一括比較<br/>→ 候補位置の mask"]
  end
  sm --> st{"候補より新しい<br/>PENDING 版がある?"}
  sc --> st
  st -->|ある| wait["状態の確定を待つ<br/>(Cicada の意味論)"]
  st -->|ない| pick["候補の版を読む"]
```

**読み方。** 狙いは比較命令の数ではなく、**候補を見つけるまでに別々の場所を順に読む回数**を減らすことである。
比べるべきは「連結リスト」「連続配置 + scalar」「連続配置 + SIMD」の 3 つで、連続配置の利益と SIMD の利益を
混ぜない (メモ §7.4)。SIMD の結果で COMMITTED だけを拾うと、候補より新しい PENDING 版を無視することになり
Cicada の版選択と一致しない (メモ §7.3)。

## 3. 選択的 forwarding: cold に入りそうなときだけ timestamp を進める

### 3.1 読み取りの判断

```mermaid
flowchart TB
  start(["read(T, key)"]) --> own{"自分の未 commit の<br/>書き込みがある?"}
  own -->|ある| rown["それを読む"]
  own -->|ない| obs["hot block を安全に観測"]
  obs --> hit{"今の timestamp で<br/>使える版が hot にある?"}
  hit -->|ある| rhot["状態を確認して読む<br/>(追加の timestamp 制御なし)"]
  hit -->|ない| elig{"T は forwarding の<br/>対象か?"}
  elig -->|"対象外<br/>(固定 snapshot など)"| rcold["今の timestamp で<br/>cold を辿る"]
  elig -->|対象| cand["hot の版に届く<br/>最小の前進先を選ぶ"]
  cand --> keep{"前進先でも<br/>既読の版がそのまま見える?"}
  keep -->|いいえ| rcold
  keep -->|はい| sync{"並行 writer に対して<br/>保証を確立できた?"}
  sync -->|いいえ| rcold
  sync -->|はい| adv["T の状態を前進<br/>(必要なら GC 保護も)"] --> recheck["hot を再確認して読む"]
```

**読み方。** hot で当たる普通の読み取りには何も足さず、**高くつきそうな読み取りだけ**を対象にする (メモ §12.2)。
前進に失敗したら今の timestamp のまま cold を辿る。図の「安全に観測」「保証を確立」「GC 保護」の 3 か所が、
研究で具体化と証明が要る部分である (メモ §19)。

**この図から読み取ってはならないこと。** 失敗時に元の timestamp へ戻れるのは、GC へ新しい保護下限を公開する前だけ
である (§5.2)。前進先を選んだ後に hot block が書き換わることもあり、選んだ記述子をそのまま使い続けてよい保証は無い。

### 3.2 3 つの方針の違い (記号の例)

T の今の timestamp を t3 とし、既読の版 A が t1 から t6 の手前まで見えているとする。キー B の版は
新しい順に B@t8, B@t7, B@t5 が hot、B@t4, B@t2 が cold にある (t1 < t2 < … < t8)。

```text
時刻  →   t1    t2    t3    t4    t5    t6    t7    t8
既読 A    [===========================)                  A の見える区間 [t1, t6)
B の版          B@t2        B@t4  B@t5        B@t7  B@t8
                └── cold ──┘      └──────── hot ─────────┘
T の現在              ^t3

固定          : t3 のまま → B@t2 を読む          → cold を辿る
必ず最新      : t8 へ進む → B@t8 を読む          → A が見えない (t8 は [t1, t6) の外)
選択的        : t5 へ進む → B@t5 を読む          → A も見える (t5 は [t1, t6) の中)、cold を避けられる
```

```mermaid
flowchart LR
  fixed["固定<br/>timestamp を動かさない"] --> r1["cold を辿る"]
  latest["必ず最新<br/>最新版まで進む"] --> r2["既読の版の区間を<br/>外れやすい"]
  sel["選択的<br/>hot に届く最小限だけ進む"] --> r3["既読を保ったまま<br/>cold を避けられる場合がある"]
```

**読み方。** 選択的 forwarding は「最新版まで進む」必要がない。hot のうち**最新ではない版** (B@t5) を選べることが、
旧版の値を取り出せる MVCC に固有の自由度である (メモ §11.3・§12.1)。single-version の TicToc も
timestamp の履歴で既読値を救えるので、「上書きされた既読値を救える」こと自体は新規性にならない (メモ §11.2・§22.1)。

**この図から読み取ってはならないこと。** 最小限の前進は最適性が証明された方針ではなく、比べるための出発点である
(メモ §12.3)。前進先は read の下限だけでなく、書き込み側の制約と timestamp の一意性も満たさなければならない (メモ §10)。

### 3.3 可視区間で書くと

版 v が見える区間を I(v) = [b(v), e(v)) と書くと、既読の版の集合 R_T が同時に見えうる区間は

- 下限 L_T = max b(v)、上限 U_T = min e(v) (v ∈ R_T)
- 共通の timestamp が存在する条件は L_T < U_T

である (メモ §9)。これは **read 集合の整合性の条件であって、更新 transaction 全体の commit 条件ではない。**

```mermaid
flowchart LR
  rs["既読の版の集合"] --> lo["下限 = 見え始めの最大"]
  rs --> hi["上限 = 見え終わりの最小"]
  lo --> cmp{"下限 < 上限?"}
  hi --> cmp
  cmp -->|はい| ok["共通の timestamp がある<br/>(read 側の必要条件)"]
  cmp -->|いいえ| ng["この集合は同時には見えない"]
  ok --> more["加えて必要: 書き込み側の制約・一意性・<br/>並行 writer・不在キー・範囲読み取り"]
```

## 4. 並行 writer との競合: 確認してから rts を書くだけでは足りない

```mermaid
sequenceDiagram
  participant R as Reader R
  participant V as 版 A@t1 の記述子
  participant W as Writer W
  R->>V: A@t1 が t5 で見えることを確認
  W->>V: 古い rts を読む
  W->>V: t3 の版を設置 (A@t1 と t5 の間に入る)
  R->>V: rts を t5 に上げる
  R->>R: commit (t5 で見えるはずの A は、もう A@t1 ではない)
```

**読み方。** 確認と通知の間に writer が割り込むと、確認した「見える」が崩れる (メモ §13.1)。
reader が「この timestamp で読む」と writer に知らせる処理と、writer が「保証済みの読み取りを壊さない」ことを
確かめる処理が**両方向で**噛み合うプロトコルが要る (メモ §13.2)。

```mermaid
flowchart LR
  subgraph rs["reader 側"]
    r1["候補 timestamp で読むことを通知"] --> r2["その timestamp で見えることを確認"]
  end
  subgraph ws["writer 側"]
    w1["設置する版が、保証済みの<br/>読み取りを壊さないことを確認"]
  end
  rs <-->|"同じ情報を介して<br/>順序を決める"| ws
```

**この図から読み取ってはならないこと。**

- **rts は版の見える区間の終わり (end_ts) ではない。** 「rts が候補以上だから見えることの確認を省ける」は
  一般には成り立たない (メモ §13.3)。
- 「同じ記述子を CAS すれば解決」は直観であって完成したプロトコルではない。**CAS を使うことと lock-free であることは別**
  (メモ §13.4)。
- 観測した「次の版の timestamp」は、途中に別の版が設置されると縮みうる。「今見えている終わり」と
  「これ以上縮まないと保証された終わり」を区別する (メモ §14.1)。

## 5. GC への接続: 進めただけでは回収は進まない

```mermaid
flowchart LR
  A["段階 A: 探索の回避<br/>今回の cold アクセスを避ける"] --> B["段階 B: 保持義務の縮小<br/>古い時点の履歴を要求しなくなる"] --> C["段階 C: メモリの再利用<br/>不要版を安全に回収"]
  A -.必要.-> na["合法な hot 版の選択と forwarding"]
  B -.必要.-> nb["前進の確定と GC への反映"]
  C -.必要.-> nc["pointer の保護・quiescence"]
```

**読み方。** A だけでも速くなる可能性はあるが、B と C まで実現しなければ「GC を改善した」とは言えない (メモ §15.1)。

### 5.1 公開の順序

```mermaid
flowchart TB
  o1["新しい timestamp で<br/>既読の状態を保てるか確認"] --> o2["並行 writer に対する<br/>保証を確立"] --> o3["古い timestamp へ<br/>戻らない状態を確定"] --> o4["GC が見る保護条件を前進"] --> o5["物理参照の安全が<br/>成立してから回収"]
```

**読み方。** 自分の timestamp 変数を進めても、GC 側が古い値を保護条件として持っていれば回収範囲は変わらない。
逆に正当性を確定する前に保護を外すと、まだ要る版が消える (メモ §15.2)。

### 5.2 戻れる段階と戻れない段階

```mermaid
stateDiagram-v2
  state "元の timestamp" as s0
  state "前進を試行中" as s1
  state "前進を確定" as s2
  state "保護を公開" as s3
  [*] --> s0
  s0 --> s1: cold に入りそう
  s1 --> s0: 失敗 (戻ってよい)
  s1 --> s2: 確認と保証が成立
  s2 --> s3: GC の保護下限を前進
  s3 --> [*]: これより古い timestamp へは戻らない
```

**この図から読み取ってはならないこと。**

- 古い書き込み timestamp を持つ版がすべて回収できるわけではない。前進先でもまだ見えている古い版 (前の例の A) は要る (メモ §15.3)。
- 自分が前進しても、別の transaction が古い timestamp を要求していれば全体の回収境界は動かない。
  **forwarding の成功回数は GC 改善の指標にならない** — 回収境界の前進量と回収可能になった量を測る (メモ §15.4)。
- 目標は free の回数を減らすことではなく、**同時に生きている古い版の量** (≈ 発生速度 × 保持時間) を減らすこと (メモ §15.5)。

## 6. この仕組みだけでは解けないケース

```mermaid
flowchart TB
  t1["実行中の普通の tx"] -->|"次の cold アクセスで発火"| ok1["アクセス駆動 forwarding<br/>で対象になる"]
  t2["実行は進む長い tx"] -->|"読み取りのたびに発火しうる"| ok2["段階的に依存を解消できる可能性"]
  t3["読み取り後に待っている tx<br/>(CCBench 図 14 の作り方、メモの要約)"] -->|"新しい読み取りが無い"| ng3["アクセス駆動では発火しない"]
  ng3 --> ext["拡張候補: GC 圧力駆動<br/>(回収境界の停滞などを合図に)"]
  t4["止まっているスレッド"] --> ng4["自分では要求を処理できない<br/>協調処理・失効・保護解除の仕組みが別に要る"]
```

**読み方。** CCBench の長い transaction の再現方法 (読み取りの後に待つ) では、アクセス駆動の forwarding は
**一度も発火しない**。これは本案の重要な限界であり、評価でも「アクセス駆動が効かなかった」と
「forwarding が無効だった」を区別する (メモ §16・§26.2)。
**1 行目の問題を解いたことを、4 行目まで解いたように書かない。**

### 6.1 前進してよい transaction と、してはいけない transaction

```mermaid
flowchart LR
  rw["普通の read-write tx"] --> f["forwarding の対象"]
  fs["固定 snapshot を要求する tx<br/>(指定時点の読み取りなど)"] --> nf["従来の snapshot 経路を保つ<br/>(timestamp を変えてはいけない)"]
  ro["安定した read-only 経路"] --> nf
  nf -.共存時の影響も測る.-> gcb["GC 境界を支配しうる"]
```

**読み方。** 「MVCC の機能を保つ」は、旧版の取得・serializability・固定 snapshot の意味の 3 つを別々に書く (メモ §17.1)。
read-only の安価な経路に forwarding のための記録を足すと逆効果になりうる (メモ §17.2)。実時間の順序
(先に終わった tx より後に始めた tx の並べ方) を保証に含めるかも、比較相手と揃える (メモ §17.3)。

## 7. 実装で分けておく状態

```mermaid
flowchart TB
  subgraph tx["transaction が持つ状態 (分けて考える)"]
    c1["候補 timestamp<br/>次の read・validation で使う時点"]
    c2["確認済みの整合性<br/>既読をどこまで保てると確かめたか"]
    c3["GC への保護下限<br/>これより古い履歴は要求しないという約束"]
    c4["物理参照の保護<br/>まだ触りうる版や block"]
    c5["確定の印<br/>書き込み版の設置後は timestamp を変えない"]
  end
  c1 -. "進めても外せるとは限らない" .-> c3
```

**読み方。** 1 つの `ts` だけで持つと、探索の都合と GC の都合が混ざる。**候補を進めたことと、GC 保護を外せることは別**
である (メモ §18)。最初の実装では、共有構造へ PENDING の書き込み版を置く前にだけ forwarding を許す。

```mermaid
flowchart LR
  rp["read phase<br/>必要なら forwarding<br/>書き込み値は手元に"] --> pc["commit 準備<br/>timestamp を確定"] --> va["validation 以降<br/>timestamp を変えない"]
```

**まだ決めていない実装の論点 (メモ §20):** hot の更新方法 (並べ替え・ring buffer・block の差し替え)、
timestamp 順と設置順のずれ、K に PENDING 版を数えるか、複数 word の記述子を一貫して読む方法、
slot 再利用の取り違え (ABA)、不在キー・削除・範囲読み取り、hot から cold への移し替えの費用。

## 9. 評価の組み立て (メモ §25 の構成を図にしたもの)

```mermaid
flowchart TB
  A["A 基準 Cicada<br/>(最適化と GC 設定を調整済み)"]
  B["B hot 配置だけ"]
  C["C forwarding だけ<br/>(論理的な K 版の境界で発火)"]
  D["D hot 配置 + cold 境界での forwarding"]
  E["E D + GC 保護条件の前進"]
  F["F cold に入ったら abort して新しい timestamp で再実行"]
  G["G 最新を読み timestamp を後で決める単純な拡張"]
  A --> B & C
  B --> D
  C --> D
  D --> E
  A --> F
  A --> G
  F -.比べる.-> D
  G -.比べる.-> D
```

| 比較 | 何が分かるか |
|---|---|
| A と B | データ配置だけの効果 (H1) |
| A と C | forwarding だけの効果 (H2) |
| B・C と D | 組み合わせの効果 (H5) |
| D と E | 実際の保持・回収への効果 (H4) |
| F と D | 実行済みの仕事を保つ価値 |
| G と D | 最新ではない hot 版を選べる価値 (H3) |

**読み方。** 狙いは「Cicada より速い」だけでなく「何を変えたから速いか」を言えることである (メモ §25.2)。
C には物理的な hot が無いので、「先頭から K 版より奥を辿る必要があるとき」という論理的な発火条件を置かないと
比較の条件が変わる。キーの引き方 (Masstree から hash へ等) を変えるなら、版管理だけを変えた比較と分ける (メモ §25.1)。
