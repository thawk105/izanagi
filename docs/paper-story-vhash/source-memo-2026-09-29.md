# 研究メモ
# VHashとtimestamp forwardingによるMVCCの版探索・履歴保持・GCの協調最適化

## 0. この議論で到達した研究案

今回の議論の中心は、次のアイディアである。

> **MVCCにおいて、少数のversionを効率よく参照できるhot領域と、それより古い履歴を保持するcold領域を設ける。transactionがcold領域へアクセスしそうになった時点で、安全なtimestamp forwardingを試みる。これにより、古いversionの探索を回避するとともに、可能な場合には古い履歴を保持する必要性そのものを減らし、GCも改善する。**

仮称「VHash」は、この仕組みを実現するためのversion-awareなデータ構造である。研究の本体はhash table単体の高速化ではなく、

\[
\boxed{
\text{version配置}
\;\times\;
\text{version選択}
\;\times\;
\text{timestamp制御}
\;\times\;
\text{version lifetime／GC}
}
\]

の協調設計にある。

主な性能比較相手はCicadaを想定する。目標は、MVCCの旧版を取得・利用できる能力を残したまま、Cicada型の実装が負担している版探索と履歴保持のコストを大きく削減することである。

**現時点では研究構想であり、完全なプロトコル、正当性証明、実装、性能評価はまだ完成していない。** 以下では、議論の途中で修正した点も含め、現在の整理をまとめる。

---

## 1. 発想の出発点と、研究対象が絞られるまで

最初の問いは、「SIGMOD/VLDBを目指す次の研究として、新規性と需要のある高速なデータ構造は何か」というものだった。

当初は、CXLなどの異種メモリ向けindex、vector検索とrelational処理の統合、GPU向け動的構造、用途特化hash table、LLMのprefix cacheなども候補に挙がった。その中で、transaction／concurrency controlの研究蓄積と直接つながるものとして、**MVCCを前提にしたデータ構造**に焦点が移った。

議論の変遷は、次のように整理できる。

| 段階 | 発想 | そこから生じた問い |
|---|---|---|
| ① | key lookupとversion選択を一体化するVHash | そもそも古い版を探索する必要はあるのか |
| ② | timestampを前進させ、古い版を避ける | 既読の値との整合性をどう維持するか |
| ③ | 最新版を読み、後からtimestampを決める | TicTocとの関係はどうなるか |
| ④ | 更新済みの旧版をvalidationで救済する | 旧payloadとtimestamp履歴は何のために必要か |
| ⑤ | hot領域から溢れるときだけforwardする | 配置とCCをどう協調させるか |
| ⑥ | CCBenchのRapidGC分析と接続する | 探索回避だけでなく、版の保持期間も短縮できないか |

現在の案は、③の「常に最新を読む方式」ではなく、**⑤と⑥を中心にした選択的forwarding方式**である。

なお、当初話題にしたSIGMOD/VLDBの50〜100本規模の体系的な研究マップは、この議論の中では完成していない。初期の回答に挙がった個別の2026年論文名や性能倍率を、そのまま今回の新規性の根拠として引き継ぐべきではない。今回の構想を支える主な文献は、CCBench、Cicada、TicTocである。

## 2. 研究の出発点となるCCBenchの問題意識

田辺さんの論文、**“An Analysis of Concurrency Control Protocols for In-Memory Databases with CCBench”** の§7は、version lifetimeと性能の関係を分析している。今回特に重要なのは、図12〜13に関する版探索コストの分析、図14のRapidGCの限界、§7.3のAggressiveGC構想である。

その要点は、次のように整理できる。

**第一に、MVCCのコストはGC処理関数の中だけに現れるわけではない。** 論文では対象条件下のCicadaの追加コストがread/writeに現れ、version chain traversalとの関係が分析されている。

**第二に、GCを頻繁に実行すれば常に解決するわけではない。** 長いtransactionが古い履歴を必要としていると、GC間隔を短くしても性能改善が頭打ちになる。

**第三に、AggressiveGCは「必要とされ得る版も回収し、必要になったtransactionを新しいtimestampで再実行する」方向を提起している。**

今回の案は、この問題意識を次のように発展させるものである。

```text
従来の方向：
    不要になったversionを、できるだけ早く回収する

AggressiveGCの一つの方向：
    必要とされ得るversionも回収する
    → 必要になったtransactionをabort/retryする

今回の方向：
    古いversionを必要としそうなtransactionを安全に前進させる
    → 既に行った処理を維持して続行する
    → 古い履歴への依存を減らす
```

重要なのは、**GCの実装を速くすることと、GCできる状態を早く作ることは別の問題**だという点である。

今回の研究は、後者にも踏み込む。

## 3. なぜMVCCの内部改善を研究対象にしてよいのか

MVCCには実際の利用基盤がある。例えば、PostgreSQLはデータ整合性の維持にMVCCを利用し、InnoDBもconsistent readのためにmulti-versioningを利用している。

ただし、今回の研究は「既存の全MVCC DBMSにそのまま適用できる方式」を最初から主張するものではない。

最初の対象は、例えば次のように限定するのが自然である。

| 項目 | 最初の対象として考えているもの |
|---|---|
| 実行環境 | 単一ノード、共有メモリ、CPU上のin-memory処理 |
| CC | Cicada型のtimestamp-orderingを用いるserializable MVCC |
| 主な改善対象 | 通常のread-write transaction |
| version管理 | 複数版を保持し、必要なら旧版を新たに取得できる |
| メモリ | まず通常のDRAMのみ |
| 特殊なsnapshot | 固定snapshot／指定時点の読み取りは別扱い |
| 性能目標 | 同じ保証を提供する基準実装に対し、探索・保持・同期の総コストを削減 |

この範囲なら、研究の問いは、

> 「single-versionにすればよいのではないか」

ではなく、

> **「旧版を利用できる能力が必要なMVCCにおいて、その能力のために支払うコストを減らせるか」**

になる。

ただし、**MVCCという内部構造を使っていることと、どの外部的なtransaction semanticsを保証するかは別問題**である。そこは後述する。

## 4. Cicadaについて、今回必要になる前提

Cicadaは重要な比較対象だが、ここでは「現在のあらゆる条件で最速のMVCC」とは断定しない。また、単純なlinked listだけを持つ素朴な実装として扱ってはいけない。

今回に必要な原論文上の前提は、次のとおりである。

| 項目 | Cicadaの前提 |
|---|---|
| 版選択 | `wts`降順のversion listから、transaction timestampに対応する版を選ぶ |
| 状態 | `PENDING`、`COMMITTED`、`ABORTED`などを区別する |
| `rts` | その版を読んだ、commitした可能性のあるtransactionの最大timestampを表す |
| validation | pending版の設置、read版の`rts`更新、version consistency checkの順に進む |
| 既存最適化 | best-effort inlining、incremental version searchなどがある |
| read-only | 安定したtimestampを利用し、read set追跡・validationを省く経路がある |
| GC | timestampの下限情報とquiescenceを組み合わせて安全性を管理する |

また、Cicadaでは対象timestamp以下の`PENDING`版を単に飛ばすのではなく、その状態確定を待つ。この点は、SIMD化やlock-free性を議論する際に重要になる。

以降の提案は、これらを無視して置き換えるのではなく、**どの前提を維持し、どの部分を変更するかを明示して設計する必要がある**。

## 5. VHashとは何をする構造なのか

### 5.1 基本形

VHashは仮称であり、実装済みの構造ではない。

基本的には、あるキーの直近の少数版を、小さい範囲で確認できるようにする。

```text
Key A

HOT領域
    version descriptor 0
    version descriptor 1
    version descriptor 2
    cold領域への参照

COLD領域
    それより古いversion
    ...
```

descriptorに何を置くかは未確定だが、候補は次の情報である。

```text
version identity
write timestamp
commit state
payloadへの参照
必要なvalidation用情報
```

key lookupまで融合するなら、さらにkeyまたはfingerprintを持たせる。

ここでの「cold」は、最初は**VHashの小さな通常アクセス領域の外にある履歴**という意味である。同じDRAM内でよく、CXL、SSD、GPUを必須にしない。

また、hotと呼ぶ領域が常にCPU cacheに常駐する保証があるわけではない。正確には、**通常の版選択でアクセスする範囲を小さく、局所的に保つ設計**である。

### 5.2 メタデータだけをhotに置くか、payloadも置くか

この二つは分けて考える必要がある。

**メタデータのみhotに置く場合**、複数版のtimestampや状態をまとめて確認し、選んだ版のpayloadだけを取得する。探索用のpointer chasingを減らすことが主な狙いになる。

**payloadもhotに置く場合**、小さいレコードではさらに間接参照を減らせる可能性がある。ただし、レコードが大きいとhot領域が膨らみ、更新時のコピーや移動も高くつく。

したがって、

> 「3版をhotに置く」

という記述だけでは不十分で、**3版のメタデータなのか、3版の値も含むのか**を仕様にする必要がある。

### 5.3 per-key構造と、bucket内融合構造

構造には少なくとも二つの方向がある。

**per-key方式**では、まずキーを特定し、そのキー専用のhot version blockを参照する。key lookupとversion管理を切り分けやすく、最初のプロトタイプやアブレーションに向く。

**bucket融合方式**では、複数キーと複数versionのメタデータを同じbucketに置き、key fingerprintとtimestamp条件をまとめて処理する。融合による利益を狙える一方、hot keyの履歴が他のキーの容量を圧迫するなど、管理は複雑になる。

最初から後者を完成させる必要はない。**version block単体で効果を確認し、必要ならhash lookupとの融合へ進む**という順序も考えられる。

## 6. 「3 versions」の正確な意味

議論の初期には、「forwardingできれば3版程度しか保持しなくてもよいのでは」という発想があった。

現在の整理では、これは次の意味に限定する。

> **通常アクセス用のhot領域に置く版数を、K個程度に抑える。**

システム全体が保持するversion数をK個に制限する、という意味ではない。

例えば、長いtransactionがA10を読んだ後、AがA20、A30、A40へ更新されたとする。既読A10を維持したまま前進できる範囲には限界がある。ほかにも固定snapshotを使うreaderがいれば、旧版を残さなければならない。

したがって、基本構造は、

\[
\text{hotな少数版}
+
\text{必要に応じて保持するcold履歴}
\]

となる。

また、K＝3に特別な保証はない。Kは、書き込み頻度、transactionの長さ、timestampの遅れ、レコードサイズ、forwarding成功率によって適切な値が変わる設計パラメータである。

固定Kの実装から始めても、最終的には、

> 「全キーに同じKを与えるか」  
> 「更新頻度やアクセス頻度に応じて容量を変えるか」

が設計上の選択肢になる。

## 7. SIMDでvisibility checkをするとは何か

### 7.1 目的は、timestamp比較よりも探索用メモリアクセスの削減

例えば、あるキーの版が新しい順に次のtimestampを持つとする。

```text
wts = [120, 105, 93, 71]
transaction timestamp = 100
```

逐次的に調べると、

```text
120 <= 100 ? false
105 <= 100 ? false
 93 <= 100 ? true
```

となる。

timestampを連続配置して複数laneで比較できれば、

```text
wts <= 100
    ↓
[false, false, true, true]
```

という結果をまとめて得られる。

lane 0を最下位bitに対応させれば、maskは`0b1100`になる。timestamp降順に並んでいる前提なら、最初に立っているbitに対応する版が候補になる。

ただし、ここで期待している主な利益は、

> 「比較命令が数個減ること」

よりも、

> **「候補を見つけるために複数のversion nodeを順番に読み込まなくてよいこと」**

である。

### 7.2 key fingerprintとの融合

bucket融合方式なら、概念的には、

\[
\text{key候補mask}
\land
\text{timestamp条件mask}
\]

を作れる。

ただしfingerprintは完全なキーではない。衝突があるため、最終的にはfull-keyの一致確認が必要である。また、bucket内に複数キー・複数版が混在する場合、最初の候補を返すだけではなく、**対象キーについて適切なtimestampの版を選ぶ**必要がある。

### 7.3 `COMMITTED`とのANDだけでは、Cicadaの意味論を再現できない

以前の説明では、

```text
key一致
AND wts <= transaction timestamp
AND state == COMMITTED
```

とすればよいように説明していたが、これは不十分である。

対象timestamp以下に、より新しい`PENDING`版が存在する場合、それを無視して古いcommit済み版を選ぶことは、前節で確認したCicadaの動作と同じではない。

したがってSIMDは、まず、

> 「timestamp上の候補位置を見つける」  
> 「状態に応じて処理を分岐するための情報を得る」

ための高速化と捉えるべきである。**状態機械や並行更新への対処をSIMD predicateだけで省略できるわけではない。**

### 7.4 SIMDは必須ではない

Kが小さければ、連続配置したメタデータをscalarで読むだけでも十分かもしれない。

最初に比較すべきものは、

```text
linked traversal
vs.
連続配置＋scalar
vs.
連続配置＋SIMD
```

である。

**連続配置の利益とSIMDの利益を混同しない**ことが重要になる。

## 8. Timestamp forwardingの基本的な考え方

### 8.1 単純にtimestampを書き換えるだけでは安全ではない

transaction TがA10を読んだとする。

その後、AがA25に更新された。ここでTが別のキーBの新しい版を読みたいため、timestampを30へ進めたとする。

```text
既読：
    A10

Aの履歴：
    A25 → A10

これから読む：
    B30

Tのtimestamp：
    15 → 30
```

timestamp 30ではA10ではなくA25がvisibleになるなら、A10とB30を組み合わせたread setは、そのtimestampの状態を表していない。

したがって、forwardingに必要なのは、

> **前進先でも、既に利用したreadの結果を維持できることを確認すること**

である。

これは単に「古いデータを気にしない」「最新を読んでよい」という緩いisolationへの変更ではない。

### 8.2 既読の値が同じなら、実行済み計算を維持できる可能性がある

例えばTが、

```text
read A
if A.value > 0:
    compute ...
read B
```

という処理をしていたとする。

forwarding後もAについて同じ版がvisibleであれば、Aの値に依存した計算をやり直さずに済む余地がある。

一方、Aを新しい版に読み替える場合は、Aに依存した分岐、計算、write valueまで影響を受ける。これは単純なtimestamp forwardingではなく、再実行やtransaction repairの問題になる。

**今回の基本案は、既読値を読み替えて修復する方式ではなく、既読値を維持できるtimestampを探す方式である。**

## 9. Visibility intervalを使った整理

ここからの数式は、**commit済みversionの順序と可視区間が正しく確定・保護されている**と仮定した説明用モデルである。実装中に観測したtimestampだけで同じ保証が得られるわけではない。

version \(v\) の可視区間を、

\[
I(v)=[b(v),e(v))
\]

と書く。

ここで、\(b(v)\) はその版がvisibleになるtimestamp、\(e(v)\) は次の版によってvisibleでなくなる境界である。

transaction Tが読んだ版の集合を \(R_T\) とすると、それらが同時にvisibleであり得る区間は、

\[
I_T=\bigcap_{v\in R_T} I(v)
\]

である。

これを下限と上限に分けると、

\[
L_T=\max_{v\in R_T}b(v)
\]

\[
U_T=\min_{v\in R_T}e(v)
\]

となり、read setに共通するtimestampの候補が存在する条件は、

\[
L_T<U_T
\]

になる。

例えば、

```text
A10 : [10, 30)
B20 : [20, 50)
C25 : [25, 40)
```

なら、

```text
共通部分 = [25, 30)
```

である。

ただし、これは**read setの整合性についての条件**であり、更新transaction全体のcommit条件ではない。実際には、write set、並行writer、timestampの一意性、indexや不在キーへのアクセスなどの条件も必要になる。

## 10. 「最新を読んでmax(wts)を採用する」案の位置づけ

議論の途中では、次の方式を考えた。

```text
read A_latest → A100
read B_latest → B130
read C_latest → C115

候補timestamp = max(100, 130, 115) = 130
```

validationで、A100、B130、C115が130でもvisibleなら、read setを130の状態として説明できる可能性がある。

この`max(wts)`は、前節のread setの下限 \(L_T\) に対応する。

しかし、実装では少なくとも次の点を追加で考える必要がある。

**既に持っているtimestampより後退させない。**  
今回の案がforwardingであるなら、新しい候補は現在のtimestamp以上でなければならない。

**write set側の制約も満たす。**  
read版の最大`wts`だけで更新transactionのtimestampを決めてよいとは限らない。

**timestampの一意性や順序の表現を満たす。**  
別transactionが使った`wts`と同じ整数値をそのまま採用できるとは限らない。実際のtimestamp形式に従って、合法な候補を確保する必要がある。

**可視区間の上限を確認する。**  
大きい`wts`を見つけて下限を上げるだけでは、以前のreadがそのtimestampでも成立することは分からない。

したがって、この案は、

> 「timestampをデータに基づいて選ぶ」という検討の中間段階

として有用だったが、現在の本命ではない。

現在は、**必要な場面でだけ、必要な程度に前進する**方式を中心に考えている。

## 11. なぜ「1 versionでよい」にはならないのか

### 11.1 最新ではなくなっても、既読versionを救済できる

例えばTがA10とB20を読んだ後、AがA30に更新されたとする。

```text
Tが読んだもの：
    A10
    B20

validation時：
    A30 → A10
    B20
```

Tをtimestamp 20に置けるなら、

```text
A10の可視区間：[10, 30)
20はその中にある
```

ため、A10が現在の最新版でなくても、そのreadを救済できる。

従ってvalidationの条件は、

```text
読んだ版 == 現在の最新版
```

ではなく、

```text
読んだ版 == 自分の採用timestampでvisibleな版
```

である。

### 11.2 ただし、その救済だけなら旧payloadの共有保存は必須ではない

ここは議論の中で重要な訂正が入った。

TがA10の値を既にローカルに保存していれば、validationのためにA10のpayloadを共有ストアから再取得する必要はない場合がある。

必要なのは、

> 「A10が対象timestampでも有効だった」

と証明する情報である。

TicTocのtimestamp historyは、この種の救済を行う。TicTocはsingle-version OCCであり、旧payloadを保持せず、過去のtimestamp情報によって既読値を検証できる。したがって、「上書きされたreadを救えるのはMVCCだけ」という対比は正しくない。

### 11.3 MVCCの追加の自由度は、まだ読んでいない旧版を取得できること

次のケースでは、旧payloadを取得できることが重要になる。

```text
Tが既に読んだA：
    A10の可視区間 = [10, 25)

これから初めて読むB：
    B30：最新版
    B20：旧版、可視区間 = [20, 30)
```

B30を読むと、既読A10との可視区間の共通部分がない。

しかしB20を新たに取得できれば、

```text
A10：[10, 25)
B20：[20, 30)

共通部分：[20, 25)
```

が存在する。

**今回の方式では、hot領域にある「最新版ではない版」をこれから読むことで、既読値を維持しつつcoldアクセスを避けることができる。**

これが、latest-only＋timestamp履歴だけでは表現しきれないMVCC側の設計余地である。

---

## 12. 現在の中心案：cold境界での選択的forwarding

### 12.1 具体例

以下を説明用の状態とする。

```text
Tの現在のtimestamp：45

既読のA：
    A20の可視区間 = [20, 65)

これから読むB：

HOT
    B80
    B70
    B60
──────────
COLD
    B50
    B40
    ...
```

timestamp 45を維持するなら、TはB40を読む必要がある。

ここで三つの方式を比較できる。

| 方針 | 選択 | 結果 |
|---|---|---|
| timestamp固定 | B40を読む | cold領域の探索が必要 |
| 必ず最新版 | B80を読めるtimestampへ進む | A20の可視区間を外れる |
| 選択的forwarding | 例えば61へ進み、B60を読む | A20を維持しつつhot版を使える可能性 |

この例で重要なのは、**B80まで進める必要がない**ことである。

B60に届けばよいため、可能な限り小さい前進を選ぶ。

### 12.2 基本方針

基本ポリシーは、次のようになる。

```text
現在のtimestampでhot版を読める
    → そのまま読む

hot版を読めず、coldへ進む必要がある
    → hot版を読める合法な前進先を探す
    → 安全に前進できればhot版を読む
    → できなければcold経路を利用する
```

これにより、通常のhot hitに余計なtimestamp制御を載せず、**高くつきそうなアクセスだけを最適化対象にする**。

### 12.3 最小限の前進は、まず試すべきheuristic

前進幅が大きいほど新しい版に届きやすいが、既読versionとの整合性を失いやすくなる。

そのため、

> 「hot領域に届く最小限のtimestampへ進める」

は自然な初期方針である。

ただし、それがtransaction全体にとって常に最適とは限らない。小さく何度も前進するより、一度大きく前進した方が、その後のアクセスや再検証を減らせる場合もあり得る。

したがって、最小前進は**最適性が証明された方針ではなく、明確に比較できる出発点**である。

## 13. 並行writerへの対応と、`rts`の位置づけ

### 13.1 visibilityを確認してから`rts`を書くだけでは競合がある

例えば、reader RがA100をtimestamp 130で利用したいとする。

```text
Reader R                         Writer W

A100が130でvisibleと確認

                                 古いrtsを読む
                                 timestamp 120の版を設置

A100.rtsを130に上げる

commit
```

この順序だと、確認後にA120が挿入され、Rが確認したvisibilityが崩れる可能性がある。

そこで、Rが130で読んだことをwriter側に知らせる処理と、writerの設置・validationが協調する必要がある。

### 13.2 「検証前に`rts`を書くべきか」という問いは核心だった

議論で出た、

> 「validation前に、読んだversionへ読み取りtimestampを記録すべきか」

という問いは、並行writerによる過去への割り込みを扱うための重要な問いだった。

ただし、必要なのは単純なローカル順序の変更だけではない。

概念的には、少なくとも次の二方向を成立させる必要がある。

```text
Reader側：
    自分が候補timestampでその版を読むことを通知
    そのtimestampでのvisibilityを確認

Writer側：
    自分が設置する版によって
    既に保証されたreadを無効にしないことを確認
```

**readerとwriterの両方が参加するプロトコル**でなければならない。

### 13.3 `rts`と`end_ts`は同じものではない

ここは明確に区別する必要がある。

`end_ts`は、説明用モデルではそのversionの可視区間の終端である。

一方、`rts`は、readerがどのtimestampでそのversionを利用しようとしたかをwriter側へ伝えるための情報であり、必ずしもそのversionの可視区間の終端を表さない。

特に、readerが`rts`を引き上げた後でvalidationに失敗する場合も考えなければならない。

そのため、

```text
v.rts >= candidate_ts
だからvisibilityの確認を省略してよい
```

と、別方式の最適化をそのまま持ち込むことはできない。

**`rts`による競合制約と、対象timestampでどの版がvisibleかという判定は、関連するが同じ情報ではない。**

### 13.4 「同じmetadataをCASすれば解決」は完成した設計ではない

以前の回答では、readerとwriterが同じmetadataをCASすればよい、という説明をした。これは競合解決の直観としては使えるが、完成したプロトコルではない。

実際には、versionの設置位置、複数レコードの更新、commit状態、GC、pointerの再利用などが関係する。

また、**CASを使うことと、方式全体がlock-freeであることは別**である。停止したwriterを他threadが待ち続ける設計なら、単にmutexを使っていないだけではlock-free性を主張できない。

今回まず必要なのは正しい低コストなプロトコルであり、lock-free性を主張するなら、その進行保証も別途証明する。

---

## 14. 可視区間が分かればO(1) validationできるのか

read setにversionへの参照を保存しておけば、validation時にheadからその版まで再探索する必要はなくせる可能性がある。

さらに、各版に正確で安定した終端情報があれば、

\[
b(v)\le s<e(v)
\]

の確認だけで、readの整合性を検証できるように見える。

しかし、ここには二つの問題がある。

### 14.1 観測した終端が、後から変わる可能性

versionがtimestamp順に設置される方式であっても、設置やcommitが物理時間順に進むとは限らない。

例えば、現在の履歴が、

```text
A30 → A10
```

なのでA10の終端を30と観測したとしても、別のwriterがtimestamp 20の版を途中に設置できるなら、その終端は20へ変わり得る。

したがって、

> 「今見えている次版のtimestamp」

と、

> 「これ以上縮まらないと保証された可視区間」

は区別しなければならない。

### 14.2 `end_ts`の維持コストをwriterへ移している可能性

readerの探索を減らすために、writerが前版の終端を更新する設計にすると、その更新が競合やcache-line共有の原因になる可能性がある。

従って評価では、

```text
readerで減った仕事
    −
writerに増えた仕事
```

を見る必要がある。

**O(1)のread validationは魅力的な候補だが、そのためのメタデータ更新と同期まで含めて有利かを確認しなければならない。**

## 15. Timestamp forwardingとGCをどう接続するか

ここが今回の研究で最も重要な部分である。

### 15.1 効果を三段階に分ける

| 段階 | 得られる効果 | 必要なもの |
|---|---|---|
| A：探索回避 | 今回のcoldアクセスを避ける | 合法なhot版選択とforwarding |
| B：論理的な保持義務の縮小 | 古い時点の履歴を要求しなくなる | 前進した状態の確定とGCへの反映 |
| C：物理メモリの再利用 | 不要版を安全に回収・再利用する | pointer保護、quiescenceなどの安全性 |

Aだけでも性能改善になる可能性があるが、B・Cまで実現しなければ、**「GCを改善した」とは言い切れない**。

### 15.2 ローカルtimestampを書き換えるだけでは足りない

GC側がTの古いtimestampを保護条件として持ち続けているなら、T自身のローカル変数を前進させても回収可能範囲は変わらない。

逆に、Tの正当性を確定させる前にGC側の保護を解除すると、Tがまだ必要としている版が回収される危険がある。

そのため、提案では次の順序関係を定義する必要がある。

```text
新しいtimestampで既読状態を維持できるか確認
    ↓
並行writerに対して必要な保証を確立
    ↓
旧timestampへ戻らない状態を確定
    ↓
GCが参照する保護条件を前進
    ↓
物理参照の安全性が成立した後に回収
```

これは概念的な順序であり、実装では複数の処理を融合できるかもしれない。ただし、**この接続を省略することはできない**。

### 15.3 古い`wts`の版をすべて回収してよいわけではない

例えば、

```text
A20の可視区間 = [20, 65)
Tの新timestamp = 61
```

なら、A20は古い`wts`を持つが、Tにとって依然として必要である。

GCの境界が61になったとしても、

```text
wts < 61
```

という理由だけでA20を削除してはいけない。

必要なのは、**その版を置き換える後続版の存在とtimestamp、現在・将来のreaderの要求、実行中の参照**を合わせた判断である。

今回減らしたいのは、

> 「古い`wts`を持つ版すべて」

ではなく、

> **前進後には誰も必要としなくなった履歴**

である。

### 15.4 自分が前進しても、globalな回収境界が動かない場合がある

Tが45から61へ進んでも、別のtransaction Uがtimestamp 10を必要としていれば、globalな最小値はそのままかもしれない。

従って、

```text
forwarding成功回数
```

だけではGC改善の指標として足りない。

少なくとも、

```text
回収境界が実際にどれだけ前進したか
どれだけの版が回収可能になったか
物理メモリがいつ再利用可能になったか
```

を測る必要がある。

### 15.5 GC改善は「freeの回数削減」と同義ではない

同じ数の更新を実行し、同じ数のversionを生成するなら、最終的に処理しなければならないversion数は大きく変わらない可能性がある。

それでも、保持期間を短縮できれば、同時に生存する版数やworking setを小さくできる。

概念的には、安定した状態で、

\[
\text{保持中の旧版bytes}
\approx
\text{旧版の発生bytes／秒}
\times
\text{平均保持時間}
\]

という関係が考えられる。ただし実測では、allocatorの予約領域、断片化、回収待ち、常時必要な版なども別に計上する。

**削減対象はGC関数のCPU時間だけではなく、version lifetimeによって増えるシステム全体のコストである。**

## 16. coldアクセス契機だけでは解けないケース

### 16.1 read後に停止しているtransaction

CCBenchの図14では、長いtransactionを作るため、read phaseの末尾に人工的な遅延を入れている。

この場合、

```text
read A
read B
read C
    ↓
長い待機
    ↓
validation
```

となる。

待機中に新しいreadは発生しない。そのため、

> 「cold版にアクセスしそうになったらforwardする」

という機構だけでは、そのtransactionにforwardingが発火しない。

これは今回の案の重要な限界であり、評価上も切り分ける必要がある。

### 16.2 アクセス駆動とGC圧力駆動を分ける

最初の設計は**アクセス駆動forwarding**でよい。coldアクセスの回避を目的とし、通常アクセスに余計な仕事を載せない。

拡張としては、**GC圧力駆動forwarding**が考えられる。cold領域の増加、回収境界の停滞、古いtransactionの経過時間などを契機に、安全な地点で前進を試す。

ただし、完全に停止しているthreadは要求を処理できない。

そのケースまで扱うには、他threadによる協調処理、失効・abort、参照保護の解除など、追加の仕組みが必要になる。**失効flagを立てただけで、そのthreadが保持するpointer先を即座にfreeしてよいわけではない。**

### 16.3 三つの問題は同じではない

| 対象 | 問題 |
|---|---|
| 実行中の通常transaction | 次のcoldアクセスを避けたい |
| 実行は進むが長いtransaction | 古い履歴への依存を段階的に解消したい |
| 停止・待機しているtransaction | 安全な確認や保護解除をどう進めるか |

最初の論文でどこまで対象にするかは、実装コストと結果を見て決めるべきである。

**第一の問題を解けたことを、第三の問題まで解けたように説明しない**ことが重要になる。

## 17. Fixed snapshot、read-only、serializabilityの区別

### 17.1 前進できるtimestampと、前進してはいけないsnapshotがある

アプリケーションが、

```text
指定した時点のデータを読む
同じsnapshot IDを使い続ける
開始時点のsnapshotを維持する
```

ことを要求しているなら、内部都合でその時点を変更できない。

一方、

> 「実行全体が、許容される直列順序のどこかに置ける」

という保証を狙うtransactionでは、serialization位置を選ぶ自由度を利用できる可能性がある。

したがって、今回の方式で「MVCCの機能を維持する」と言うときは、

> **旧版取得を残すこと、serializabilityを維持すること、固定snapshot semanticsを維持すること**

を別々に記述する必要がある。

### 17.2 read-only経路を不用意に高コスト化しない

read-only transactionに対して、もともとread set追跡やvalidationが不要な経路を使っているなら、forwardingのために全readを記録して再検証することが逆効果になる可能性がある。

最初は、

```text
通常のread-write：
    forwarding対象

固定snapshot／安定read-only：
    従来のsnapshot経路を維持
```

と分けるのが分かりやすい。

ただし、そのread-only transactionが古い履歴を保護している間は、GCの進行が制約される場合がある。それを「提案の対象外だから測らない」で済ませるのではなく、**共存時にどの効果が残り、どの効果が失われるか**を評価する。

### 17.3 serializabilityと実時間順序も別

同じserializabilityでも、実時間上先に完了したtransactionより後に開始したtransactionを、どのように順序づけるかは別の保証に関わる。

timestampを自由に選ぶ研究では、session順序、外部的な依存、commit acknowledgmentなどをどの保証に含めるかを明示する必要がある。

比較対象と提案でこの条件を変えると、性能差の意味も変わる。

## 18. 実装に向けて分離した方がよい状態

この節は、これまでの議論を実装へ落とすための設計整理である。完成したプロトコルではない。

transactionが単一の`ts`だけを持つと、探索の都合とGCの都合が混同されやすい。

概念上は、少なくとも次を分けると考えやすい。

| 状態 | 意味 |
|---|---|
| 現在の候補timestamp | 次のread／validationで使おうとしている時点 |
| 確認済みの整合性情報 | 既読値をどの範囲まで維持できると確認したか |
| GCに公開する保護下限 | どこより古い履歴を今後要求しないと保証したか |
| 物理参照の保護状態 | どのversionやblockをまだ参照し得るか |
| timestamp確定状態 | write版の設置後など、変更不可になったか |

重要なのは、

\[
\text{候補を前進させた}
\neq
\text{GC保護を解除できる}
\]

という関係である。

実装上はこれらを一つのdescriptorにまとめられるかもしれないが、正当性の議論では分けておく方がよい。

### 18.1 timestampを変更する時期

最初の実装では、**共有構造へpending write版を設置する前にだけforwardingを許す**方が整理しやすい。

共有構造へ公開したversionの`wts`を後から変更すると、version順序、writer間の優先関係、他readerの判断などに影響するためである。

従って、初期設計は、

```text
read phase：
    必要に応じてforwarding
    write値はローカルに保持

commit準備：
    timestampを確定

validation以降：
    timestampを変更しない
```

という分離が候補になる。

### 18.2 fallbackはいつでも自由にできるわけではない

forwardingを試して失敗したとき、元のtimestampでcoldへ戻る方針は自然である。

ただし、それが許されるのは、**元の状態に戻っても安全な段階までしか進んでいない場合**に限る。

例えば、既にGCへ新しい保護下限を公開した後で古いtimestampへ戻ると、必要な版が回収済みかもしれない。

したがって、

```text
前進を試したが、まだ確定していない
    → 元のtimestampでfallbackできる余地

前進を確定し、旧履歴の保護を解除した
    → それより古いtimestampへは戻らない
```

を明確に分ける。

---

## 19. 概念的なread経路

処理の意図は、次のように表せる。

```text
Read(T, key):

    自分の未commit writeがあれば、それを読む

    hot領域を安全に観測する

    現在のtimestampで利用できる版がhotにあれば：
        必要な状態確認を行う
        read setへ記録する
        値を返す

    transactionがforwarding対象なら：
        hot版を利用できる前進先を選ぶ

        前進先で既読結果を維持できるか確認する

        並行writerと整合する保証を確立できれば：
            transactionの状態を前進させる
            必要ならGC保護条件も更新する
            hot領域を再確認して読む

    現在の有効なtimestampでcold経路を使う
```

これは実行可能なアルゴリズムではなく、**設計上必要な処理の分解**である。

特に、

```text
安全に観測する
保証を確立する
GC保護条件を更新する
```

の三つが、研究で具体化・証明しなければならない部分になる。

また、forwarding成功後にもhot領域が更新される可能性がある。候補を選んだ時点のdescriptorを、そのまま無条件に使い続けてよいわけではない。

## 20. 実装上の主要課題

### 20.1 hot領域の更新方法

直近K版を常に並べ替える方式では、更新のたびに複数slotを移動させるコストが発生する。

候補としては、小さい配列、ring buffer、immutable blockの差し替え、固定slotと別の順序情報などが考えられる。

評価では、readerの探索削減だけでなく、**writerがhot構造を維持するコスト**を見る必要がある。

### 20.2 timestamp順と設置順の違い

「新しいwriteを常に先頭に追加する」だけで済むかは、採用するCCとtimestamp設置規則に依存する。

既に割り当てられたtimestampを持つwriterが遅れて設置する場合、timestamp順に途中へ入る可能性も扱う必要がある。

hot／coldの境界も、単なる物理的な到着順ではなく、**どの順序に基づく直近K版なのか**を定義しなければならない。

### 20.3 pending／aborted版と容量

Kはcommit済み版の数なのか、pending版を含むslot数なのか。

pending版が多い場合にhot領域を埋め尽くさないか。abortした版をいつ除去するか。coldへ移した版が後でabortしたときにどう扱うか。

これらを決めないと、更新競合時の挙動が曖昧になる。

### 20.4 メタデータの一貫した観測

複数のtimestamp、状態、payload参照をまとめて読む場合、同じgenerationの情報として解釈できる必要がある。

SIMD loadを行うだけで、複数wordにまたがる更新を一貫して観測できるとは限らない。採用する言語・atomic操作・公開順序に合わせて設計する必要がある。

単に「前後でversion counterを確認する」と書くだけでは、並行して書き換えられるデータをどのように合法に読むかまで説明したことにはならない。

### 20.5 ABAとslot再利用

同じslotやpointerが別versionに再利用されると、

```text
同じアドレス
```

だけでは、

```text
同じversion
```

を意味しない。

read setには、version identityやgenerationなど、再利用を区別できる情報が必要になる可能性がある。

### 20.6 不在キー、delete、range scan

存在するレコードだけのvisibilityを確認しても、不在キーを読んだ結果やrange scanの結果は保証できない。

例えば「キーKは存在しない」という判断に基づいて処理した後、forwarding先ではKが存在しているなら、そのread結果は維持されていない。

従って、完全なtransaction機能を対象にするなら、**不在・範囲・index構造に関する整合性情報**もforwardingの対象に含める必要がある。

最初の評価を固定キー集合のpoint accessに限定する場合は、その限定を明記する。

### 20.7 allocation／spillのコスト

coldアクセスを回避できても、新しいversionを作るたびにhotからcoldへのコピーが発生するなら、write側のコストが増える。

そのため、

```text
hotから追い出すのはpayloadか、参照だけか
cold版は最初から別領域に作るか
再利用可能なslotをどう管理するか
```

が性能を左右する。

「探索が速くなった」だけではなく、**配置を維持するために増えた仕事まで含めて勝つ**必要がある。

## 21. Forwardingの費用対効果

timestamp forwardingは無料ではない。

概念的には、次の条件で実行する価値がある。

\[
C_{\text{forward}}
<
C_{\text{cold access}}
\]

ただし、左辺には単なるtimestamp更新だけでなく、

\[
C_{\text{forward}}
=
C_{\text{候補選択}}
+
C_{\text{追加検証}}
+
C_{\text{同期}}
+
E[C_{\text{追加abort／retry}}]
\]

が含まれる。

GC改善を含めるなら、さらに、版保持の短縮による将来の利益も考えられる。ただし、それをオンラインで正確に見積もるのは難しいため、最初から複雑な最適化器を作る必要はない。

### 21.1 read setが大きいほど有利とは限らない

長いtransactionは古い履歴を保持しやすい一方、forwarding時に再検証するread setも大きくなりやすい。

毎回全read setを走査し、何度もforwardingを行うと、追加仕事が大きくなる。

従って、検討すべき候補には、

```text
forwarding回数を制限する
一定以上のread setでは方針を変える
確認済みの情報を再利用する
一度の前進で複数アクセスを救えるようにする
```

などがある。

ただし、キャッシュした整合性情報を使い回せるのは、その情報が並行更新後も安全に利用できる場合だけである。

### 21.2 前進の利益はtransactionだけに閉じない

ある古いtransactionを前進させることで、ほかの大量の版が回収可能になるなら、その前進にはシステム全体の利益がある。

一方、古いtransactionがほかにも多数残っているなら、その一件を前進させてもGCへの利益は小さいかもしれない。

この違いは、

> 「アクセス時の局所的なコスト判断」

と、

> 「GC停滞を解消するための全体的な判断」

を分ける理由になる。

## 22. TicTocとの関係と、比較方針

### 22.1 新規性の議論では無視できない

TicTocには、データに基づくtimestamp決定と、timestamp historyによる既読値の救済がある。

そのため、

> 「timestampを後から決める」  
> 「上書きされた既読値を後から救う」

だけを新規性にするのは弱い。

今回の主張は、そこではない。

中心に置くのは、

> **旧版のpayloadを新たに取得できるMVCCにおいて、hot／cold配置を利用して、どの版を読むかとどのtimestampへ移るかを協調させ、その結果をGCにも接続すること**

である。

### 22.2 関連研究と性能baselineは同じではない

関連研究として重要であっても、必ずしも主たる性能baselineにする必要はない。

今回評価したいのが、旧版取得や固定snapshotとの共存を維持したMVCC内部の改善なら、まず重要なのは、

```text
同じ機能を持つ基準MVCC
同じ基盤上の自然な代替設計
提案機構を取り除いた構成
```

である。

ただし、評価するtransactionが全てlatest-onlyであり、旧版を新たに読む能力が結果に寄与していないなら、「内部に古い版を保存している」という分類だけを理由にTicTocを除外するのは弱い。

**比較対象は勝ちやすさではなく、評価している機能と保証に対する代替可能性で選ぶ。**

### 22.3 今回の実験で特に有用な対照

TicTocそのものより、まず次の二つは置く価値が高い。

**最新を読み、後からtimestampを決める単純なMVCC拡張。**  
これに対して、cold境界に応じた選択的forwardingの意味を示す。

**cold miss時にabortして新しいtimestampで再実行する方式。**  
これに対して、実行済みの仕事を維持するforwardingの価値を示す。

これらは、今回のアイディアの中身を直接検証するbaselineになる。

## 23. 新規性をどこに置くか

今回の新規性候補は、単独の既知要素ではなく、次の接続にある。

### 23.1 物理配置をtimestamp制御の入力にする

「timestampを変えられるか」だけでなく、

> **cold領域へ入ることが分かったとき、そのアクセスコストを理由に前進を試す**

という判断を導入する。

### 23.2 version選択とtimestamp選択を同時に扱う

「最新版を読む」か「現在timestampの旧版を読む」かの二択ではない。

> **既読値を維持できる範囲で、アクセスしやすいhot版を選ぶ**

という選択肢を持つ。

### 23.3 前進を履歴の保持義務の縮小へ接続する

前進によってcoldアクセスを減らすだけでなく、

> **そのtransactionが過去の履歴を要求しないことをGC側にも反映する**

ところまで設計する。

### 23.4 共通の物理構造で、版選択と検証を安くする

複数版のメタデータをまとめて扱える構造を使い、候補選択、forwarding可否の判断、validationに必要なアクセスを減らす。

ただし、**「transactionとデータ構造の協調設計」自体は既に研究されている**。例えばCIDR 2021の“Everything is a Transaction”は、transactional semanticsと物理データ構造のmaintenanceの分断を問題にしている。従って、協調設計という大きい標語だけでは新規性にならない。

最終的には、

```text
何を入力に判断するか
どの状態を変更するか
どの不変条件を維持するか
どのコストを削減するか
```

を既存研究と具体的に比較する必要がある。

## 24. 検証したい研究仮説

現時点の仮説は、以下のように整理できる。

| 仮説 | 検証したい内容 |
|---|---|
| H1：配置 | 少数版のメタデータを局所化すると、version探索のメモリアクセスを減らせる |

## 25. 評価構成：何が効いたかを切り分ける

主比較は、最適化とRapidGC設定を適切に調整したCicadaとする。

その上で、同じ基盤に次の構成を用意する。

| 構成 | 役割 |
|---|---|
| A：基準Cicada | 主baseline |
| B：VHash／hot配置のみ | データ配置単独の効果 |
| C：forwardingのみ | CC変更単独の効果 |
| D：hot配置＋cold-triggered forwarding | 協調設計の効果 |
| E：D＋GC保護条件の前進 | 実際の保持・回収への効果 |
| F：cold missでabort/retry | 再実行を避ける価値 |
| G：latest-only型の単純拡張 | 選択的版選択の価値 |

Cでは物理hot領域がないため、例えば「先頭からK版を超える探索が必要ならforwardingを試す」といった、対応する論理的なtriggerを設ける必要がある。そうしないと、比較条件そのものが変わる。

### 25.1 key lookupの変更を分離する

VHashの導入で、Masstreeなどからhash lookupへ変更する場合、単にindex種別を変えた利益が混ざる。

そのため、

```text
同じkey lookupでversion管理だけを変える比較
key lookupまで融合した最終構成の比較
```

を分ける。

### 25.2 同じ基盤の重要性

allocator、read/write set、workload generator、CPU affinity、NUMA配置などが異なると、CCの変更以外で性能差が生じる。

この研究では、**Cicadaを大きく上回ることと同じくらい、「何を変えたから上回ったか」を説明することが重要**である。

## 26. 評価すべきworkload

まずは、要因を独立に動かせるmicrobenchmarkを中心にする。

### 26.1 通常負荷

read/write比率、RMWとblind writeの違い、キー分布、transactionあたりの操作数、レコードサイズ、キー数、thread数を変える。

これにより、

> 「深い版が必要になる頻度」  
> 「forwardingによって既読値が無効になる頻度」  
> 「追加検証の大きさ」

を切り分ける。

### 26.2 長いtransaction

長さの作り方を一種類にしない。

```text
操作数が多い
readの途中に計算がある
read終了後に待機する
途中でthreadが停止する
固定snapshotを長時間保持する
```

は、forwardingの発火機会もGCへの影響も異なる。

特に、**read後の待機だけで構成された長いtransactionに効かなかったことと、アクセス時のforwardingが無効だったことは同じではない**。

### 26.3 うまくいかない条件も必要

例えば、

```text
ほとんど全てhot hit
read setが非常に大きい
既読キーが頻繁に更新され、前進余地がない
固定snapshot readerがGC境界を支配する
小さい値に対してhotメタデータが大きすぎる
```

条件では、効果が小さいか逆効果になり得る。

これらを隠さず示すことで、適用範囲が明確になる。

## 27. 測るべき指標

### 27.1 最終的な性能

throughputだけでなく、transactionの完了までのlatency、再実行を含めた処理時間、長いtransactionの完了率を見る。

短いtransactionだけが高速化し、長いtransactionが失敗し続けているなら、それを総throughputだけで成功と判断してはいけない。

### 27.2 探索に関する指標

```text
readで調べた版数
write／validationで調べた版数
hot hit率
coldアクセス率
coldで実際に辿った長さ
payload取得までの間接参照数
```

平均だけでなく、分布も見る。

### 27.3 Forwardingに関する指標

```text
試行回数
成功回数
前進幅
transactionあたりの実行回数
追加検証時間
rts更新などの共有書き込み

```

失敗理由は、少なくとも「既読値との不整合」「write制約」「競合」「固定snapshot」「費用対効果による見送り」などに分けるとよい。

### 27.4 GCとメモリ

```text
version保持時間
生存version数
hot／coldのlive bytes
論理的に回収可能だが物理的には残っているbytes
回収境界の遅れ
GC処理時間
allocatorの予約・使用量
transaction側へ移したコピーやメタデータ
```

**共有versionを減らした代わりにread set側のメモリを増やした場合、その増分も含める。**

## 28. 特に重要な実験図

### 28.1 GC間隔とthroughput

今回の問題設定に直結する図である。

期待する形は、

> 基準方式は短いGC間隔で局所性を維持する必要があるが、提案方式はGCの遅れに対して通常アクセスの性能が落ちにくい。

さらにGC保護条件まで前進できる構成では、生存version数の減少も合わせて示す。

ただし、GC間隔を不適切に大きくしたCicadaだけに勝っても不十分である。**Cicadaの最良設定に対する性能、または同等性能に必要なメモリ・GC負担の違い**を示したい。

### 28.2 長いtransactionの長さとメモリ使用量

forwardingが実際にversion lifetimeを短縮するなら、待機時間や操作数を増やしたときのメモリ増加に差が出る可能性がある。

この際、アクセス駆動だけの構成と、GC圧力駆動まで含めた構成を分ける。

### 28.3 Kと性能・メモリ

Kを増やせばhot hitは増えるかもしれないが、メモリと更新コストも増える。

従って、

```text
K
→ hot hit率
→ forwarding回数
→ throughput
→ 総メモリ
```

の関係を見る。

K＝3が有利かは、この実験で決める。

### 28.4 保存した仕事と追加した仕事

forwardingで回避したcold探索・retry時間と、そのために追加した検証・同期時間を並べる。

これは、単に「速い」という結果よりも、機構の有効性を説明しやすい。

## 29. 最初の実装・検証の進め方

### 段階1：基準実装の計測

まずCicadaに、版探索長、phase別時間、GC境界、生存版数、長いtransactionによる保護期間の計測を追加する。

ここで確認したいのは、

> **実際にcoldに相当する探索がどれだけ発生し、それを避ける余地がどの程度あるか**

である。

### 段階2：小さいモデルで正当性を検討

少数キー・少数transactionで、reader、writer、forwarding、GCのinterleavingを確認する。

特に、

```text
readerが検証した直後に古いtimestampのwriterが設置する
forwarding中にhot領域が変わる
GC保護公開の途中でthreadが停止する
pending版のcommit／abortと競合する
```

ケースを検証する。

### 段階3：GCを変えないforwarding

最初はGC保護を保守的に維持したまま、探索回避だけを実装する方法が考えられる。

これなら、

> 「forwardingそのものの正当性と費用対効果」

を、GCの複雑さから切り離して確認できる。

### 段階4：hot配置との組み合わせ

layout単独、forwarding単独、組み合わせのアブレーションを作る。

この段階で、SIMDが必要かも判断する。

### 段階5：GC保護条件を前進させる

論理的な履歴要求と物理pointer保護を整理し、成功したforwardingを実際の回収に結びつける。

ここが、版探索の高速化からversion lifetimeの改善へ進む段階になる。

### 段階6：長いtransactionと特殊操作へ拡張

固定snapshot、停止thread、不在キー、insert/delete、range scanなど、最初のモデルに含めなかった機能へ広げる。

範囲を広げるたびに、何を保証できるかを確認する。

## 30. この議論で修正された説明

今後の申し送りで誤解を残さないため、重要な訂正を一覧にする。

| 途中の説明 | 現在の整理 |
|---|---|
| 最新版だけ読めば1 versionでよい | 今回の本命では、旧版を新たに取得する能力を維持する |
| single-versionなら上書き後は必ずabort | 既読値は、timestamp履歴などで救済できる場合がある |
| `max(read wts)`だけでcommit timestampを決められる | readの下限候補であり、write制約・一意性・上限などが別途必要 |
| `rts`はversionの可視区間終端 | `rts`と`end_ts`は役割が異なる |
| `rts >= candidate`ならCicadaでもvisibility検証を省ける | その条件だけでは一般に省略を正当化できない |
| `COMMITTED`とのSIMD ANDでCicadaの版選択になる | 対象timestamp以下のpending版の扱いが必要 |
| CASを使えばlock-free | 進行保証は別問題 |
| timestampを前進させればGCが進む | GC保護の公開と物理参照保護まで接続する必要がある |
| 3版だけ残せば常に十分 | K版はhot領域の容量。cold履歴が必要な場合は残る |
| cold miss triggerだけで長いtransactionのGC問題が解決する | read後に停止しているtransactionには発火しない |
| Cicadaに勝てばMVCC全体のSOTA更新 | 対象範囲と近い代替方式を確認した上で主張する |
| 2倍出ればトップ会議に通る | 性能倍率だけでなく、問題設定・新規性・正当性・評価が必要 |

## 31. 現時点で決まっていることと、未決定のこと

### 決まっている研究の方向

**MVCCを捨てずに改善する。**  
旧版を取得できる能力を残し、通常アクセスでそのコストをできるだけ払わない。

**VHashのhot／cold境界をforwardingの契機にする。**  
全transactionで常にtimestampを動かすのではない。

**最新版まで進めることを必須にしない。**  
hot内の旧版を使うことで、既読値との整合性を維持する余地を利用する。

**探索とGCを別々に測り、その接続を提案に含める。**  
coldアクセスを減らしただけでGC改善を主張しない。

**Cicadaを主比較とし、同じ基盤のアブレーションを重視する。**

### まだ決まっていないこと

具体的なVHashのレイアウト、Kの値、metadata-onlyかpayload-inliningか、並行更新のプロトコル、forwarding時のvalidation方法、GC保護の公開方法、停止threadへの対応、lock-free性、固定snapshotとの共存方法は未確定である。

性能改善の大きさと、先行研究に対する完全な新規性も未確定である。

ただし、**何を解決したいか、どの操作を変えるか、何を測れば成功を判断できるかは、かなり具体化している。**

## 32. 研究の中心を一つの文章にまとめる

> **本研究では、MVCCの局所性を高頻度GCだけに依存させるのではなく、少数のhot versionsを中心に処理するデータ構造と、cold履歴へのアクセス時に行う選択的timestamp forwardingを協調させる。既読値との整合性を維持できる範囲でtransactionを新しい履歴側へ移動させることで、古いversionの探索を回避する。さらに、その前進をGCの保護条件へ反映することで、不要な履歴の保持時間とメモリ負担も削減することを目指す。**

CCBenchとのつながりを強調するなら、次の表現になる。

> **CCBenchで明らかにした「RapidGCを高頻度に実行しても、古いtransactionによるversion lifetimeの制約は解消しない」という問題に対し、GCを速めるだけではなく、transaction側が古い履歴を必要とする状況を安全に変えることで答える。**

そして、このアイディアを最も短く表すと、

# **「古いversionを速く探すだけでなく、古いversionを探さずに済むtimestampへtransactionを動かす。さらに、その移動を古い履歴の回収につなげる。」**

これが、ここまでの議論で到達した研究の中心である。
